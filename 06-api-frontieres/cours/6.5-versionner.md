# Leçon 6.5 — Versionner une API : rompre sans casser, et savoir quand arrêter

## L'essentiel en deux minutes

**Le problème, en une phrase.** Certains changements ne peuvent pas
être des ajouts : un montant qui devient « montant et devise », un champ
qui change de sens. Il faut alors une nouvelle version, et faire vivre
l'ancienne pendant des mois, pour des applications qu'on ne contrôle
pas.

**Trois images.**

- **Le nouveau billet de banque** : la banque centrale l'émet, mais
  l'ancien reste valable pendant des mois. Elle annonce la date de fin,
  le répète, et compte les anciens billets qui reviennent.
- **Le traducteur** : quand on garde l'ancien formulaire, on ne garde pas
  un deuxième bureau qui le traite à sa façon. On traduit l'ancien
  formulaire vers le nouveau, et un seul bureau décide.
- **La coupure annoncée** : avant de couper l'eau pour de bon, la
  commune la coupe une heure, un jour prévu. Ceux qui n'avaient pas lu
  l'affiche s'en rendent compte, pendant qu'il est encore temps.

**Le code, en quelques lignes.** L'ancienne version n'est qu'une
traduction de la nouvelle :

```go
// ToV1 writes v2 as v1: v1 is a view of v2, not a second implementation.
func ToV1(s StatementV2) StatementV1 {
    return StatementV1{s.Member, s.Balance.Amount, s.Penalties.Amount}
}
```

**Les règles à retenir.**

1. **Une nouvelle version seulement pour une rupture** : tout ce qui
   peut être un ajout reste dans la version actuelle (leçon 6.4).
2. **L'ancienne version traduit la nouvelle** : une seule règle métier,
   deux formes de réponse. Une copie de l'ancien code diverge dès la
   première correction.
3. **Annoncer dans chaque réponse** : `Deprecation` (RFC 9745) dit que
   la version est dépréciée, `Sunset` (RFC 8594) dit quand elle
   s'arrêtera, un lien donne le guide de migration.
4. **Compter qui appelle encore**, par client : la date d'arrêt se
   décide sur une mesure, pas sur un calendrier.
5. **Couper une heure avant de couper pour de bon** : certains clients
   ne réagissent qu'aux erreurs.

La suite le mesure avec la règle des pénalités, changée après la
sortie de v2.

---

La leçon 6.4 a montré ce qu'on peut faire sans rupture : ajouter à côté.
Il reste ce qui ne s'ajoute pas. Le relevé d'un membre donnait
`"balance_fcfa": 6000` ; l'API doit désormais servir d'autres devises
(des tontines au Nigeria, en nairas), et le montant devient
`"balance": {"amount": 6000, "currency": "XAF"}`. Les applications
installées lisent `balance_fcfa` et ne liront pas autre chose avant leur
mise à jour. Le problème de cette leçon :

> **Comment servir deux versions sans que leurs réponses divergent, et
> comment savoir quand on peut arrêter l'ancienne ?**

Le module de la leçon est `l65`. Il n'a besoin que de la bibliothèque
standard. Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Les deux versions

Le paquet `ledger` calcule le relevé d'un membre : ce qu'il reste à
payer, et les pénalités de retard. En octobre 2026, le bureau a plafonné
la pénalité d'un tour :

```go
// Penalty is the penalty of one round.
func Penalty(daysLate int) int64 {
    return min(int64(daysLate)*PenaltyPerDay, MaxPenaltyPerRound)
}
```

La version 2 du relevé :

```go
// StatementV2 is the answer of GET /v2/members/{id}/statement.
type StatementV2 struct {
    Member     string `json:"member"`
    Balance    Money  `json:"balance"`
    Penalties  Money  `json:"penalties"`
    RoundsLate int    `json:"rounds_late"`
}
```

La version 1 existe sous deux formes dans le module. **La copie**, telle
qu'elle a été gardée quand v2 a été écrite : son gestionnaire, et son
propre calcul, recopié du code de l'époque.

```go
// V1Copied is v1 as it was kept when v2 was written: its own handler, with
// its own computation, copied from the code of the time.
func V1Copied(book ledger.Book) http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /v1/members/{id}/statement", func(w http.ResponseWriter, r *http.Request) {
        cs, found := book[r.PathValue("id")]
        if !found {
            http.NotFound(w, r)
            return
        }
        s := StatementV1{Member: r.PathValue("id")}
        for _, c := range cs {
            s.BalanceFCFA += c.DueFCFA - c.PaidFCFA
            s.PenaltiesFCFA += int64(c.DaysLate) * 500
        }
        reply(w, s)
    })
    return mux
}
```

**La traduction** : v1 demande le relevé au même `ledger`, le met en
forme v2, puis le traduit en v1.

```go
// ToV1 writes v2 as v1: v1 is a view of v2, not a second implementation.
func ToV1(s StatementV2) StatementV1 {
    return StatementV1{s.Member, s.Balance.Amount, s.Penalties.Amount}
}
```

```go
// V1Adapted serves v1 by translating v2: one computation for both.
func V1Adapted(book ledger.Book) http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /v1/members/{id}/statement", func(w http.ResponseWriter, r *http.Request) {
        s, err := book.Statement(r.PathValue("id"))
        if err != nil {
            http.NotFound(w, r)
            return
        }
        reply(w, ToV1(ToV2(s)))
    })
    return mux
}
```

Le chemin porte la version (`/v1/...`, `/v2/...`) : c'est la forme la
plus visible, celle que les guides d'API publics recommandent souvent.
Google (AIP-185) met la version majeure en tête du chemin, et ne connaît
que des versions majeures : `v1`, jamais `v1.4`. Un en-tête
(`Accept: application/vnd.tontine.v2+json`) marche aussi ; il se voit
moins dans les journaux et dans les liens.

## 2. Mesure : la règle change, les versions divergent

`cmd/drift` crée 500 membres de 10 tours chacun, avec des retards de 1
à 30 jours sur 30 % des tours, et demande le relevé de chacun à v2, puis
à chaque forme de v1 :

```text
v1 copied   members whose v1 and v2 penalties differ: 448/500, v1 asks  5293500 FCFA more
v1 adapted  members whose v1 and v2 penalties differ:   0/500, v1 asks        0 FCFA more
```

**448 membres sur 500** voient deux pénalités différentes selon
l'application qu'ils utilisent : la version 1 recopiée ne connaît pas le
plafond de 5 000 FCFA par tour. Elle demande **5 293 500 FCFA de trop**
au total. Le membre qui a l'ancienne application paie une pénalité que
le règlement n'autorise plus ; celui qui a la nouvelle, non. Personne
n'a « oublié » de corriger v1 : la correction a été faite au seul
endroit qu'on regardait.

La version traduite n'a **aucune** différence, et ne peut pas en avoir :
il n'existe qu'un calcul. Martin Fowler décrit ce schéma comme un
**changement en parallèle** (*parallel change*, ou *expand and
contract*) : élargir (servir l'ancien et le nouveau), migrer les
clients, puis contracter (retirer l'ancien). La leçon 5.4 l'appliquait
à une colonne ; ici, c'est une API.

## 3. Annoncer : `Deprecation`, `Sunset`, et le lien

L'ancienne version continue de marcher, et le dit dans chaque réponse :

```go
// Deprecated announces that Next will go away: it adds Deprecation (RFC
// 9745), Sunset (RFC 8594) and a link to the migration guide to every
// answer, counts who still calls, and answers 410 Gone after Sunset.
type Deprecated struct {
    Next        http.Handler
    Deprecation time.Time
    Sunset      time.Time
    Guide       string
    Now         func() time.Time

    mu    sync.Mutex
    calls map[string]int // by User-Agent
}
```

```go
func (d *Deprecated) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    d.mu.Lock()
    if d.calls == nil {
        d.calls = map[string]int{}
    }
    d.calls[r.UserAgent()]++
    d.mu.Unlock()

    h := w.Header()
    h.Set("Deprecation", fmt.Sprintf("@%d", d.Deprecation.Unix()))
    h.Set("Sunset", d.Sunset.UTC().Format(http.TimeFormat))
    h.Set("Link", fmt.Sprintf(`<%s>; rel="deprecation"; type="text/html"`, d.Guide))
    if !d.Now().Before(d.Sunset) {
        h.Set("Content-Type", "application/problem+json")
        w.WriteHeader(http.StatusGone)
        _ = json.NewEncoder(w).Encode(map[string]any{
            "type": "https://api.tontine.example/problems/version-gone", "title": "Gone", "status": http.StatusGone,
            "detail": "v1 was retired; see " + d.Guide,
        })
        return
    }
    d.Next.ServeHTTP(w, r)
}
```

- **`Deprecation: @1777852800`** (RFC 9745) : la version est dépréciée
  depuis cet instant, en secondes Unix précédées d'un `@`. Elle
  fonctionne toujours ; la RFC précise que la dépréciation ne change pas
  le comportement de la ressource ;
- **`Sunset: Wed, 04 Nov 2026 00:00:00 GMT`** (RFC 8594) : la date
  prévue de l'arrêt, dans l'ancien format des dates HTTP. La RFC 9745
  interdit qu'elle soit antérieure à `Deprecation` ;
- **`Link: <...>; rel="deprecation"`** : le guide de migration ;
- **après `Sunset`**, la réponse est `410 Gone` avec un problème qui
  pointe vers le guide : « ce qui était ici n'existe plus », et non
  `404`, « je ne connais pas ».

Le compteur par `User-Agent` dit **qui** appelle encore.

## 4. Mesure : qui appelle encore v1

`cmd/usage` fait tourner le middleware sur 26 semaines, entre la
dépréciation et l'arrêt. Les personnes sont un **modèle**, pas une
mesure : 5 000 applications installées, dont 12 % de celles qui ne sont
pas encore à jour se mettent à jour chaque semaine, et 4 % jamais ; un
partenaire (mobipay) qui lit l'annonce et migre en semaine 8 ; un autre
(kash) qui ne réagit qu'aux erreurs. Deux coupures d'une heure, en
semaines 20 et 23, répondent `410` comme si v1 avait disparu (une
*brownout*).

```text
week  v1 calls  apps on v1  kash   mobipay  410 answers

   2     18137        3879   4000     2500  0
   4     15764        3088   4000     2500  0
   6     13802        2434   4000     2500  0
   8     12206        1902   4000     2500  0
  10      8509        1503   4000        0  0
  12      7549        1183   4000        0  0
  14      6868         956   4000        0  0
  16      6340         780   4000        0  0
  18      5986         662   4000        0  0
  20      5710         570   4000        0  31
  21      1608         536      0        0  0
  22      1482         494      0        0  0
  23      1413         471      0        0  6
  24      1320         440      0        0  0

```

Ce que le compteur apprend :

- **En semaine 0, kash fait 19 % des appels à v1** (4 000 sur 21 500), à
  lui seul. Les tableaux par version d'application ne le montrent pas :
  il faut compter par client.
- **L'annonce marche pour qui la lit** : mobipay disparaît en semaine 10.
  kash, lui, appelle 4 000 fois par semaine **jusqu'à la coupure** de la
  semaine 20 : 31 de ses appels reçoivent `410`, et il disparaît la
  semaine suivante. Sans la coupure, il aurait découvert l'arrêt le jour
  même, avec 4 000 appels en échec par semaine.
- **Il reste 384 applications** le jour de l'arrêt : celles qui ne se
  mettent jamais à jour, et les dernières en retard. Elles reçoivent
  `410` ; l'application doit savoir afficher « mettez à jour » sur ce
  statut, ce qui se décide **dans la première version** de
  l'application, comme le repli de la leçon 6.4.

Les chiffres de cette section viennent d'un modèle. Ce qui ne vient pas
du modèle : les en-têtes, le `410`, et le compteur par client sont le
code réel, et c'est ce compteur qui, en production, remplace le modèle
par la mesure.

## 5. La campagne

Dix mutations, dans la règle, la traduction, et l'annonce :

```text
pénalité sans plafond                        tuee
v1 traduit de travers                        tuee
Deprecation en date HTTP                     tuee
pas de Sunset                                tuee
lien sunset au lieu de deprecation           tuee
retrait répondu 404                          tuee
encore servi à l'instant du retrait          tuee
compteur jamais remis à zéro                 tuee
appels non attribués                         tuee
410 sans le guide                            tuee
10/10 tuees
```

Aucune survivante. La mutation qui retire le plafond (« pénalité sans
plafond ») est tuée par le test du `ledger` ; elle le serait aussi par
celui de v1, puisque v1 passe par le `ledger`. C'est la propriété
mesurée à la section 2, vue depuis les tests : **un seul test protège
les deux versions**. Avec la copie, il faudrait deux tests, et la
correction du plafond n'aurait touché que l'un.

## 6. La grille

| Situation | Que faire |
|---|---|
| un ajout possible | pas de nouvelle version (leçon 6.4) |
| une rupture sur un champ | d'abord l'ajouter à côté (`balance` à côté de `balance_fcfa`) ; une nouvelle version seulement si l'ancien champ doit disparaître |
| une rupture inévitable | `/v2`, l'ancienne version traduite depuis la nouvelle |
| l'annonce | `Deprecation`, `Sunset`, `Link` dans chaque réponse de l'ancienne ; un message aux partenaires ; la date dans la documentation |
| la date d'arrêt | quand le compteur par client le permet : les partenaires partis, les applications sous un seuil décidé à l'avance |
| les retardataires | des coupures d'une heure, annoncées, avant l'arrêt |
| après l'arrêt | `410 Gone`, avec le lien du guide |

## 7. Les trois erreurs qui restent

### « On copie v1 tel quel, on n'y touchera plus »

On n'y touche plus, et c'est le problème : les règles métier, elles,
changent. Section 2 : 448 membres sur 500 avec deux pénalités
différentes, dès la première correction. Une version ancienne n'est
pas figée ; c'est une **autre forme** des mêmes règles.

### « On arrête v1 dans six mois »

Le calendrier est un objectif, pas une décision. La décision se prend
sur le compteur : un partenaire qui fait 19 % des appels change la date,
ou demande une coupure plus tôt. Et le calendrier s'annonce **dans les
réponses**, pas seulement dans un courriel que personne n'a lu.

### « Une nouvelle version, c'est l'occasion de tout changer »

Chaque différence entre v1 et v2 est une ligne de traduction, et un
travail de migration pour chaque client. Une version 2 contient les
ruptures **nécessaires**, et rien d'autre ; le reste attend, ou passe par
des ajouts.

## 8. Le lien avec la production

- **Le compteur** est une métrique, par version d'API et par client
  (`User-Agent`, ou l'identifiant du partenaire authentifié), affichée à
  côté du calendrier d'arrêt.
- **Les coupures** se planifient comme une intervention : annoncées,
  courtes, à une heure où l'équipe est là, avec le compteur de `410`
  sous les yeux.
- **Les applications mobiles** ont une durée de vie plus longue que
  prévu : des téléphones qui ne se mettent pas à jour, des membres qui
  ouvrent l'application une fois par mois. Une version d'API se garde en
  général bien plus longtemps pour elles que pour les partenaires.
- **La traduction a un coût** : chaque nouveau champ de v2 se demande
  « et dans v1 ? ». Ce coût, mesuré en lignes et en tests, plaide pour
  arrêter v1 dès que le compteur le permet.

## 9. Ce qu'il faut retenir

1. Une nouvelle version seulement pour ce qui ne peut pas être un ajout.
2. L'ancienne version traduit la nouvelle : un seul calcul.
3. `Deprecation`, `Sunset` et le lien de migration, dans chaque réponse.
4. Le compteur par client décide de la date d'arrêt.
5. Une coupure d'une heure trouve les clients qui ne lisent pas les
   annonces.

## 10. Approfondissement

### Versionner par date

Certaines API publiques versionnent par date : le client envoie la date
de la version qu'il connaît, et le serveur applique, dans l'ordre, les
traductions de chaque changement depuis cette date. C'est la même idée
que `ToV1`, en chaîne : chaque rupture ajoute une traduction de la
nouvelle forme vers la précédente, et le cœur ne connaît que la
dernière.

### Les requêtes aussi

Cette leçon traduit des **réponses**. Une ancienne version reçoit aussi
des **requêtes** dans l'ancienne forme : `{"amount_fcfa": 5000}` doit
devenir `{"amount": {"amount": 5000, "currency": "XAF"}}` avant d'entrer
dans le domaine. C'est le travail de la frontière (leçon 6.2) :
l'ancienne forme est un autre format d'entrée, qui produit les mêmes
types.

## 11. Le réflexe à installer

Avant de créer une version, demande-toi :

1. Ce changement peut-il être un ajout ?
2. L'ancienne version peut-elle être une traduction de la nouvelle ?
3. Les réponses de l'ancienne annoncent-elles sa fin, avec une date et
   un guide ?
4. Qui l'appelle encore, client par client ?
5. Que verra un client qui n'a lu aucune annonce, le jour de l'arrêt ?

  « The Deprecation HTTP response header field is used to signal to

  be or has been deprecated. » ; « The timestamp given in the Sunset
  HTTP header field MUST NOT be earlier than the one given in the
  Deprecation header field. » ; « The act of deprecation does not change
  any behavior of the resource. »
- IETF, [RFC 8594 — The Sunset HTTP Header Field](https://www.rfc-editor.org/rfc/rfc8594.html) :
  « The Sunset HTTP response header field allows a server to communicate

  specific point in time. »

  « Parallel change, also known as expand and contract, is a pattern to
