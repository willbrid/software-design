# Leçon 6.4 — Les contrats : ce qu'une API promet, et comment le tester

## L'essentiel en deux minutes

**Le problème, en une phrase.** Une application installée sur des
milliers de téléphones lit les réponses de l'API telles qu'elles étaient
le jour de sa sortie. Le serveur, lui, change chaque semaine. Chaque
changement de réponse est un pari sur ce que les applications
installées savent lire.

**Trois images.**

- **Le formulaire de la mairie** : on peut ajouter une case en bas sans
  gêner personne. Renommer une case, ou demander les montants en
  centimes au lieu de francs, et tous les guichetiers habitués se
  trompent.
- **Le lecteur prudent** : il ne lit que les cases dont il a besoin, et
  écrit « inconnu » quand une case a changé, au lieu de jeter tout le
  formulaire.
- **La liste des cases lues** : chaque guichet écrit les cases qu'il
  lit. Avant de changer le formulaire, la mairie vérifie qu'aucune liste
  n'est touchée. C'est un **contrat écrit par le consommateur**.

**Le code, en quelques lignes.** Chaque application déclare ce qu'elle
lit ; le serveur vérifie sa réponse contre chaque déclaration :

```go
// The test of the provider: today's answer keeps every consumer's contract.
func TestTheAnswerKeepsEveryContract(t *testing.T) {
    for _, c := range []Contract{StrictApp, PlainApp, TolerantApp} {
        if broken := Verify(c, []byte(api.Base)); len(broken) > 0 {
            t.Errorf("%s: %q", c.Consumer, broken)
        }
    }
}
```

**Les règles à retenir.**

1. **Ajouter est sûr, changer ne l'est pas** : un champ nouveau ne casse
   qu'un client qui refuse l'inconnu ; renommer, changer un type,
   envelopper une liste cassent presque tous les clients.
2. **Côté client, lire en tolérant** : ne lire que ce dont l'écran a
   besoin, et avoir une valeur de repli pour l'inconnu (un statut
   nouveau, un champ absent).
3. **Côté serveur, tester les contrats des consommateurs**, pas la
   réponse au caractère près : un test qui compare toute la réponse
   échoue aussi sur les changements sans danger.
4. **Un contrat de forme ne voit pas un changement de sens** : des
   centimes à la place des francs gardent le même type. Seul un
   **exemple de valeur** le voit.

La suite le mesure avec onze changements du serveur, trois applications
installées, et trois façons de tester.

---

Les leçons 6.1 à 6.3 ont construit ce que l'API **reçoit**. Cette leçon
regarde ce qu'elle **envoie**, et ce qui arrive quand cela change. Le
problème :

> **Quels changements d'une réponse les applications installées
> supportent-elles, et comment le serveur le sait-il avant de déployer ?**

Le module de la leçon est `l64`. Il n'a besoin que de la bibliothèque
standard. Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. La réponse, et onze façons de la changer

`GET /tontines/1` répond aujourd'hui :

```text
{"id":1,"name":"Tontine du marché","share_fcfa":10000,"status":"open","next_round":3,
 "members":[{"phone":"+237677123456","name":"Awa"},{"phone":"+237699654321","name":"Bintou"}]}
```

(sur une seule ligne dans le code ; coupée ici pour la lecture).

Le paquet `api` garde cette réponse, et onze changements qu'une équipe
serveur peut faire en une semaine, du plus anodin au plus sournois :

| Changement | Ce qui change |
|---|---|
| add a field | un champ `created_at` en plus |
| reorder the fields | les mêmes champs, dans un autre ordre |
| add a member field | un `role` dans chaque membre |
| new status value | `status` vaut `"paused"`, une valeur nouvelle |
| next_round null | une tontine close : `next_round` vaut `null` |
| remove next_round | le champ disparaît |
| rename share_fcfa | il devient `share` |
| share as a string | `"10000"` au lieu de `10000` |
| id as a string | `"1"` au lieu de `1` (la leçon 6.2 le conseillait) |
| wrap the members | la liste devient `{"items": [...], "next": null}`, pour paginer |
| share in centimes | `1000000` : le même type, en centimes de FCFA |

## 2. Trois applications installées

Le paquet `clients` lit la réponse comme trois applications réelles.
Chacune rend ce que l'écran affiche :

```go
// View is what the screen of a tontine shows.
type View struct {
    Name      string
    Share     string // "10 000 FCFA"
    Status    string // "Ouverte", "Close", or what the application knows
    NextRound string // "3", or "—" when there is none or it is unknown
    Members   int    // -1 when the application could not count them
}
```

**L'application stricte** lit avec la version 2 de `encoding/json`,
refuse tout membre inconnu, et exige chaque champ :

```go
// Strict reads the answer as its type says it must be: no unknown member,
// every field present, a status it knows.
func Strict(body []byte) (View, error) {
    var t struct {
        ID        int64    `json:"id"`
        Name      string   `json:"name"`
        ShareFCFA int64    `json:"share_fcfa"`
        Status    string   `json:"status"`
        NextRound *int     `json:"next_round"`
        Members   []member `json:"members"`
    }
    if err := jsonv2.Unmarshal(body, &t, jsonv2.RejectUnknownMembers(true)); err != nil {
        return View{}, err
    }
    label, known := labels[t.Status]
    if !known {
        return View{}, fmt.Errorf("unknown status %q", t.Status)
    }
    if t.NextRound == nil {
        return View{}, errors.New("next_round missing")
    }
    return View{t.Name, fcfa(t.ShareFCFA), label, strconv.Itoa(*t.NextRound), len(t.Members)}, nil
}
```

**L'application ordinaire** lit avec `encoding/json` dans une structure,
comme la plupart du code : un champ inconnu est ignoré, un nombre absent
vaut zéro, un statut inconnu est une erreur.

```go
// Plain reads the answer into a struct with encoding/json, as most code
// does: unknown members are ignored, a missing number is zero, and an
// unknown status is an error.
func Plain(body []byte) (View, error) {
    var t struct {
        ID        int64    `json:"id"`
        Name      string   `json:"name"`
        ShareFCFA int64    `json:"share_fcfa"`
        Status    string   `json:"status"`
        NextRound int      `json:"next_round"`
        Members   []member `json:"members"`
    }
    if err := json.Unmarshal(body, &t); err != nil {
        return View{}, err
    }
    label, known := labels[t.Status]
    if !known {
        return View{}, fmt.Errorf("unknown status %q", t.Status)
    }
    return View{t.Name, fcfa(t.ShareFCFA), label, strconv.Itoa(t.NextRound), len(t.Members)}, nil
}
```

**L'application tolérante** ne lit que ce dont l'écran a besoin, et
affiche « — » ou « Autre » pour ce qu'elle ne sait pas lire. Martin
Fowler appelle ce style un *lecteur tolérant* (*Tolerant Reader*) : ne
prendre que ce dont on a besoin, et ignorer le reste.

```go
// Tolerant reads only what the screen needs, and shows Unknown for what it
// cannot read, instead of failing: a tolerant reader.
func Tolerant(body []byte) (View, error) {
    var t struct {
        Name      string          `json:"name"`
        ShareFCFA json.Number     `json:"share_fcfa"`
        Status    string          `json:"status"`
        NextRound *int            `json:"next_round"`
        Members   json.RawMessage `json:"members"`
    }
    dec := json.NewDecoder(bytes.NewReader(body))
    dec.UseNumber()
    if err := dec.Decode(&t); err != nil {
        return View{}, err
    }
    v := View{Name: t.Name, Share: Unknown, Status: "Autre", NextRound: Unknown, Members: -1}
    if n, err := t.ShareFCFA.Int64(); err == nil {
        v.Share = fcfa(n)
    }
    if label, known := labels[t.Status]; known {
        v.Status = label
    }
    if t.NextRound != nil {
        v.NextRound = strconv.Itoa(*t.NextRound)
    }
    var ms []json.RawMessage
    if json.Unmarshal(t.Members, &ms) == nil {
        v.Members = len(ms)
    }
    return v, nil
}
```

## 3. Mesure : onze changements, trois applications

`cmd/matrix` envoie chaque changement aux trois applications, et compare
l'écran à ce qu'un membre devrait voir. Quatre verdicts :

- **ok** : l'écran est juste ;
- **degraded** : l'écran affiche « — » ou « Autre » là où il manque une
  information, ce que l'application a choisi de faire ;
- **ERROR** : l'application affiche une erreur, l'écran est vide ;
- **WRONG** : l'écran affiche une **valeur fausse comme si elle était
  juste**.

```text
change               strict    plain     tolerant  | golden  c:strict  c:plain   c:tolerant
add a field          ERROR     ok        ok        | FAIL    FAIL      pass      pass     
reorder the fields   ok        ok        ok        | FAIL    pass      pass      pass     
add a member field   ERROR     ok        ok        | FAIL    FAIL      pass      pass     
new status value     ERROR     ERROR     degraded  | FAIL    FAIL      FAIL      pass     
next_round null      ERROR     WRONG     ok        | FAIL    FAIL      FAIL      pass     
remove next_round    ERROR     WRONG     degraded  | FAIL    FAIL      FAIL      pass     
rename share_fcfa    ERROR     WRONG     degraded  | FAIL    FAIL      FAIL      FAIL     
share as a string    ERROR     ERROR     ok        | FAIL    FAIL      FAIL      FAIL     
id as a string       ERROR     ERROR     ok        | FAIL    FAIL      FAIL      pass     
wrap the members     ERROR     ERROR     degraded  | FAIL    FAIL      FAIL      FAIL     
share in centimes    WRONG     WRONG     WRONG     | FAIL    pass      pass      FAIL     
```

Cette section lit les trois colonnes de gauche ; les quatre colonnes
après la barre sont celles de la section 5.

- **L'application stricte casse sur dix changements sur onze.** Seul le
  réordonnancement passe. Ajouter un champ, la chose la plus sûre qu'on
  puisse faire, lui vide l'écran.
- **L'application ordinaire** passe les ajouts, mais elle affiche
  **« prochain tour : 0 »** quand le champ est `null` ou absent, et
  **« 0 FCFA »** quand il est renommé : trois `WRONG`, sans compter les
  centimes. Un nombre absent devient zéro sans un mot.
- **L'application tolérante** n'affiche aucune erreur. Elle se dégrade
  sur quatre changements (« Autre », « — »), et lit juste les autres,
  même le montant en texte et l'identifiant en texte.
- **Les centimes** trompent **les trois** : `1 000 000 FCFA` s'affiche
  partout, avec la même assurance que `10 000`. Aucune lecture, stricte
  ou tolérante, ne voit un changement de sens.

Ce que la matrice dit des changements :

| Changement | Sûr pour |
|---|---|
| ajouter un champ, réordonner | tous les clients qui ignorent l'inconnu |
| ajouter une valeur à une liste fermée (un statut) | les clients qui ont une valeur de repli |
| rendre un champ `null`, le retirer | les clients qui l'ont prévu ; les autres lisent zéro |
| renommer, changer un type, envelopper une liste | presque aucun : c'est une **rupture** |
| changer le sens d'une valeur | **aucun**, et sans erreur visible |

Les guides d'API publics disent la même chose. Celui de Google
(AIP-180) permet d'ajouter des champs et des valeurs d'énumération dans
une même version majeure, interdit de changer le type d'un champ, et
interdit aussi de changer le **sens** d'un comportement visible.

## 4. Tester côté serveur : trois façons

Le serveur veut savoir, **avant de déployer**, si son changement casse
une application. Trois tests possibles :

1. **le test « golden »** : comparer la réponse, octet pour octet, à
   une réponse enregistrée ;
2. **un test de contrat par consommateur** : chaque équipe d'application
   écrit ce qu'elle lit, et le serveur vérifie sa réponse contre chaque
   contrat. Martin Fowler et Ian Robinson appellent cela des *contrats
   pilotés par les consommateurs* (*consumer-driven contracts*) ; l'outil
   Pact en est l'implémentation la plus connue ;
3. **un exemple de valeur** dans le contrat : pour la tontine 1, la part
   vaut 10 000.

Le paquet `contract` en est une version minimale. Un contrat liste les
champs lus, leurs types JSON acceptés, s'ils peuvent manquer, les
valeurs connues pour un texte, et un exemple :

```go
// Field is one thing the consumer reads in the answer.
type Field struct {
    Path     string   // "share_fcfa", or "members[].name" for each element
    Kinds    []string // the JSON kinds it can read: string, number, bool, null, array, object
    Optional bool     // it copes when the field is absent
    Values   []string // for a string, the only values it knows; empty: any
    Example  any      // if set, the value it expects in the example answer
}
```

```go
// Contract is what one consumer reads.
type Contract struct {
    Consumer string
    // Closed says the consumer refuses any member it does not list.
    Closed bool
    Fields []Field
}
```

`Closed` dit qu'un consommateur refuse tout ce qu'il ne liste pas :
c'est le contrat honnête de l'application stricte.

## 5. Mesure : ce que voit chaque test

Les quatre colonnes de droite de la matrice de la section 3 sont les
trois tests, avec les contrats tels que les équipes les ont d'abord
écrits : seul celui de l'application tolérante avait un exemple de
valeur. `cmd/matrix` donne ensuite ce que le contrat tolérant reproche à
chaque changement :

```text
tolerant, rename share_fcfa: share_fcfa: missing
tolerant, share as a string: share_fcfa: string, want number
tolerant, wrap the members:  members: object, want array
tolerant, share in centimes: share_fcfa: 1000000, the example says 10000
```

- **Le test golden échoue sur les onze changements.** Il ne distingue
  pas un réordonnancement d'un renommage. Une équipe qui le voit
  échouer à chaque ajout de champ apprend à mettre à jour le fichier
  enregistré sans regarder, et le jour du renommage, elle fait de même.
- **Chaque contrat échoue là où son application casse**, sauf pour les
  centimes : neuf fois pour l'application stricte, sept pour
  l'ordinaire. Il passe là où elle tient, y compris l'ajout d'un champ
  pour l'ordinaire et la tolérante.
- **Le contrat tolérant échoue sur « share as a string »**, alors que
  l'application lit juste : le contrat dit `number`, et l'application
  accepte aussi un texte. Le contrat est plus prudent que le code ;
  c'est une fausse alerte du bon côté.
- **Les centimes ne font échouer que le contrat qui a un exemple.** Les
  contrats de forme (strict, ordinaire) passent : le type n'a pas
  changé.

## 6. La campagne

Douze mutations, dans `Verify`, dans le lecteur tolérant, et dans les
contrats :

```text
absence toujours permise                     tuee
valeurs connues ignorées                     tuee
exemple ignoré                               tuee
contrat fermé ignoré                         tuee
seul le premier élément                      SURVIT
null lu comme un nombre                      SURVIT
inconnus des éléments ignorés                tuee
statut inconnu affiché vide                  tuee
tour absent lu 0                             tuee
membres non lus comptés 0                    tuee
contrat tolérant sans exemple                SURVIT
contrat ordinaire accepte null               SURVIT
8/12 tuees
```

Quatre survivantes :

- **seul le premier élément** : `Verify` ne vérifiait que le premier
  membre d'une liste, et aucun test n'avait de liste de deux éléments
  dont le second est faux ;
- **`null` lu comme un nombre** : aucun test n'envoyait `null` à un
  champ qui ne l'accepte pas ;
- **le contrat tolérant sans exemple**, et **le contrat ordinaire qui
  accepte `null`** : ces deux-là sont plus graves. Aucun test ne
  vérifiait que **les contrats eux-mêmes** attrapent les changements qui
  cassent leur application. Un contrat mal écrit passait sans bruit.

Le test ajouté vérifie chaque contrat contre chaque changement :

```go
// Each contract must fail on every change that makes its application fail,
// or show a wrong value as if it were right. A degraded screen ("—",
// "Autre") is what the application chose to show, not a break.
func TestEachContractCatchesWhatBreaksItsApplication(t *testing.T) {
    apps := []struct {
        c    Contract
        read func([]byte) (clients.View, error)
    }{{StrictApp, clients.Strict}, {PlainApp, clients.Plain}, {TolerantApp, clients.Tolerant}}
    right, _ := clients.Strict([]byte(api.Base))
    for _, ch := range api.Changes {
        for _, a := range apps {
            v, err := a.read([]byte(ch.Body))
            wrong := v.Share != right.Share && v.Share != clients.Unknown ||
                v.NextRound == "0" || v.Members == 0
            if (err != nil || wrong) && len(Verify(a.c, []byte(ch.Body))) == 0 {
                t.Errorf("%s breaks %s (%+v, %v), and its contract passes", ch.Name, a.c.Consumer, v, err)
            }
        }
    }
}
```

Lancé sur les contrats d'origine, il échoue :


## 7. La grille

| Je veux… | Sans rupture | Comment |
|---|---|---|
| ajouter une information | oui | un champ nouveau ; les clients tolérants l'ignorent |
| ajouter une valeur à un statut | oui, si les clients ont un repli | documenter dès la première version qu'une valeur inconnue doit s'afficher « Autre » |
| retirer un champ | non | d'abord le rendre inutile, mesurer qui le lit encore, puis le retirer (leçon 6.5) |
| renommer, changer un type | non | ajouter le nouveau champ **à côté** de l'ancien, et retirer l'ancien plus tard |
| paginer une liste | non | une nouvelle route, ou un nouveau champ ; jamais envelopper l'ancien |
| changer une unité | **jamais** | un nouveau champ au nom qui dit l'unité (`share_centimes`) |

## 8. Les trois erreurs qui restent

### « Notre type est strict, ce sera plus sûr »

Plus sûr pour qui ? L'application stricte casse sur dix changements sur
onze, dont l'ajout d'un champ. Refuser l'inconnu est juste pour une
**requête** que le serveur exécute (leçon 6.2) ; pour une **réponse**
qu'un client lit, c'est interdire au serveur d'évoluer.

### « Le test golden protège tout »

Il échoue à chaque changement, donc il ne protège de rien : on le met à
jour sans regarder. Un test utile échoue quand **quelqu'un** casse, et
passe sinon.

### « Les tests de contrat garantissent la compatibilité »

Ils garantissent la **forme** que chaque consommateur a déclarée. Ils ne
voient ni un changement de sens sans exemple, ni un consommateur qui n'a
pas écrit de contrat (le partenaire qui a écrit son intégration seul).
Ils réduisent le pari, ils ne le suppriment pas.

## 9. Le lien avec la production

- **Le contrat vit avec le code du consommateur**, dans son dépôt, et
  est publié à chaque version : la version 3.2 de l'application a son
  contrat, la 3.4 le sien. Le serveur vérifie **toutes les versions
  encore installées**, pas seulement la dernière.
- **La version de chaque client** se lit dans un en-tête
  (`User-Agent`, ou un en-tête dédié). Sans elle, on ne sait pas quels
  contrats sont encore vivants (leçon 6.5).
- **OpenAPI** décrit l'API du côté du fournisseur. C'est utile pour
  générer de la documentation et des clients ; cela ne dit pas ce que
  chaque client lit vraiment. Les deux se complètent.
- **Les valeurs de repli** se décident **dans la première version** de
  l'application : un statut inconnu s'affiche « Autre » dès le premier
  jour, sinon la première valeur nouvelle casse toutes les versions déjà
  installées.

## 10. Ce qu'il faut retenir

1. Ajouter est sûr pour un lecteur tolérant ; renommer, changer un type
   ou envelopper casse presque tout.
2. Un client lit en tolérant : ce dont il a besoin, avec un repli pour
   l'inconnu.
3. Le serveur teste les contrats de ses consommateurs, pas sa réponse au
   caractère près.
4. Un contrat de forme ne voit pas un changement de sens : il lui faut un
   exemple de valeur.
5. Les contrats eux-mêmes se testent : contre chaque changement qui
   casse leur application.

## 11. Approfondissement

### Le principe de robustesse, revu

« Sois conservateur dans ce que tu envoies, libéral dans ce que tu
acceptes » a guidé les protocoles d'Internet pendant des décennies. La
RFC 9413 (2023) en montre le revers : être libéral sur les **erreurs**
de l'autre laisse ces erreurs se répandre, et finit par les rendre
obligatoires pour tous. La leçon 6.2 refusait les corps ambigus pour
cette raison. Le lecteur tolérant de cette leçon est autre chose : il
tolère ce qui est **nouveau**, pas ce qui est **faux**.

### Les énumérations fermées

Un statut qui n'a que deux valeurs aujourd'hui en aura trois demain.
Dans le contrat publié, on écrit « liste ouverte : toute valeur inconnue
doit être traitée comme `other` ». Le serveur peut alors en ajouter sans
rupture, et les clients le savent dès le départ.

## 12. Le réflexe à installer

Avant de changer une réponse, demande-toi :

1. Est-ce un ajout, ou un changement de ce qui existe ?
2. Quels clients lisent ce champ, et dans quelles versions encore
   installées ?
3. Que fait un client ordinaire quand ce champ manque : une erreur, ou
   zéro ?
4. Le sens d'une valeur change-t-il, même si son type ne change pas ?
5. Quel contrat échouerait, et a-t-il un exemple de valeur ?

  assert that inter-application messages conform to a shared
  understanding that is documented in a contract. »
- Google, [AIP-180 — Backwards compatibility](https://google.aip.dev/180) :
  « Existing fields and messages must not have their type changed, even
  if the new type is wire-compatible » ; « APIs must not change visible
  behavior or semantics in ways that are likely to break reasonable user
  code ».
- IETF, [RFC 9413 — Maintaining Robust Protocols](https://www.rfc-editor.org/rfc/rfc9413.html) :
  « The robustness principle, often phrased as "be conservative in what
  you send, and liberal in what you accept", has long guided the design
  and implementation of Internet protocols. However, it has been
  interpreted in a variety of ways. »
