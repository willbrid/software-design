## Exercice 1 — Compréhension : payé une fois, ou deux ?

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Six situations

Avec le serveur `Keyed` de la leçon, dis combien de versements sont
faits, et ce que reçoit le client.

1. La réponse se perd ; le client renvoie la même requête avec la même
   clé 30 minutes plus tard.
2. Le client renvoie la même clé avec le même corps, mais **après** que
   la clé a été purgée.
3. Deux trésorières de deux tontines différentes tirent par hasard la
   même clé.
4. Le serveur s'arrête net juste après le `COMMIT`, avant d'écrire la
   réponse.
5. Le serveur s'arrête net **avant** le `COMMIT`.
6. Le versement échoue (montant à 0, refusé par la contrainte) ; le
   client corrige le montant et renvoie **avec la même clé**.

### 1.b — Trois pourquoi

1. Pourquoi `Keyed` insère-t-il la clé **avant** le versement, et pas
   après ?
2. Pourquoi garder la **réponse** avec la clé, plutôt qu'un simple
   « déjà fait » ?
3. Pourquoi le serveur a-t-il reçu 1 273 requêtes quand l'application
   n'en a envoyé que 1 066 ?

### 1.c — Idempotent ou pas ?

Lesquelles de ces opérations sont idempotentes par nature, sans clé ?
« Fixer la part à 10 000 FCFA » ; « ajouter un membre » ; « marquer le
tour 3 comme clos » ; « verser la cagnotte du tour 3 » ; « retirer le
membre awa » ; « augmenter la pénalité de 500 FCFA ».

```go
// Handler serves POST /contributions. Make it idempotent: the same member
// with the same key records once and gets the same answer; another member
// with the same key records their own; the same member with the same key
// and another body gets 422; no key gets 400.
func Handler(pool *pgxpool.Pool) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        member := r.Header.Get("X-Member")
        body, err := io.ReadAll(http.MaxBytesReader(w, r.Body, 4<<10))
        var req Request
        if err == nil {
            err = json.Unmarshal(body, &req)
        }
        if err != nil {
            http.Error(w, "malformed", http.StatusBadRequest)
            return
        }
        var c Contribution
        err = pool.QueryRow(r.Context(), `INSERT INTO contribution (member, round, amount_fcfa) VALUES ($1, $2, $3)
            RETURNING id, member, round, amount_fcfa`, member, req.Round, req.AmountFCFA).Scan(&c.ID, &c.Member, &c.Round, &c.AmountFCFA)
        if err != nil {
            http.Error(w, "unavailable", http.StatusServiceUnavailable)
            return
        }
        w.Header().Set("Content-Type", "application/json")
        w.WriteHeader(http.StatusCreated)
        _ = json.NewEncoder(w).Encode(c)
    })
}
```

## Exercice 3 — Refactoring : le client qui renvoie trop vite

*Niveau 3. Réécrire la politique de renvoi de l'application ; les tests
sont fournis.*

L'application renvoie un versement ainsi :

```go
// Do sends the request once with key. It returns the status, and the wait
// that Retry-After asked for (0 if none), or the error of the network.
type Do func(ctx context.Context, key string) (status int, retryAfter time.Duration, err error)
```

```go
// Policy says how to send again.
type Policy struct {
    Attempts int           // at most this many requests
    Base     time.Duration // the wait after the first failure
    Max      time.Duration // the longest wait
    // Rand returns a number in [0, 1), for the jitter.
    Rand func() float64
    // Sleep waits d, or returns ctx.Err() if ctx ends first.
    Sleep func(ctx context.Context, d time.Duration) error
}
```

```go
// Send is how the application sends today: a new key for each attempt, and
// no wait between attempts.
func (p Policy) Send(ctx context.Context, do Do) (int, error) {
    for range p.Attempts {
        status, _, err := do(ctx, client.NewKey())
        if err == nil && status < 500 {
            return status, nil
        }
    }
    return 0, ErrGaveUp
}
```

Réécris `Send` : une clé pour toute l'action ; pas de renvoi pour un
refus (`4xx`) ; entre deux essais, l'attente que demande `Retry-After`,
sinon une part aléatoire (`p.Rand()`) d'une attente qui double à partir
de `p.Base` sans dépasser `p.Max` ; arrêt quand le contexte se termine ;
le dernier statut reçu, ou `ErrGaveUp` si le réseau n'a jamais répondu.

## Exercice 5 — Incident : la purge de minuit

*Niveau 7. Un incident à expliquer avec le journal, puis à corriger.*

à minuit, une tâche purge les clés de plus de 24 heures. Le lundi
9 novembre 2026, trois trésorières signalent des membres payés deux fois
la semaine précédente, « alors que l'API est idempotente ».

Les trésorières travaillent souvent dans des marchés sans réseau :
l'application garde alors les versements en attente et les renvoie
quand le téléphone retrouve une couverture.

```go
// Server is the payout server of the lesson, in memory: one record per key,
// and a purge that runs every midnight.
type Server struct {
    mu   sync.Mutex
    keys map[string]record
    next int64
}
```

```go
// Purge forgets the keys created before before.
func (s *Server) Purge(before time.Time) {
    s.mu.Lock()
    defer s.mu.Unlock()
    for k, r := range s.keys {
        if r.created.Before(before) {
            delete(s.keys, k)
        }
    }
}
```
