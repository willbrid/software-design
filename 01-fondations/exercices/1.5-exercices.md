# Exercices 1.5 — Erreurs et contrats

**Règles.** Réponds avant d'ouvrir la correction. Pour tous les exercices, la
question n'est pas *« les erreurs sont-elles bien gérées ? »* mais :

> Quelles sont les issues de cette opération, quelle conduite chacune impose à
> l'appelant, et qu'est-ce qui reste vrai après chacune ?

Les quatre natures de la leçon : **réponse métier**, **faute de l'appelant**,
**défaillance d'environnement**, **bug**.

Écris tes réponses dans `01-fondations/mes-reponses/1.5.md` (dossier local,
ignoré par Git).

## Exercice 1 — Compréhension

Le paiement des frais de scolarité par mobile money.

```go
package frais

import (
    "database/sql"
    "encoding/json"
    "errors"
    "fmt"
    "io"
    "net/http"
    "strings"
    "time"
)

type Operateur struct {
    HTTP *http.Client
    Base string
}

type Service struct {
    DB  *sql.DB
    Ope *Operateur
}

// Payer encaisse les frais de scolarite par mobile money.
func (s *Service) Payer(matricule string, montant int64, telephone string) error {
    if len(matricule) != 8 {
        return errors.New("matricule invalide")
    }
    if montant <= 0 {
        return errors.New("montant invalide")
    }
    if !strings.HasPrefix(telephone, "6") || len(telephone) != 9 {
        return errors.New("numero invalide")
    }

    var du int64
    err := s.DB.QueryRow(
        "SELECT reste_a_payer FROM scolarites WHERE matricule = $1", matricule,
    ).Scan(&du)
    if err != nil {
        return err
    }
    if montant > du {
        return errors.New("montant superieur au reste a payer")
    }

    corps, _ := json.Marshal(map[string]any{
        "msisdn": telephone, "amount": montant, "ref": matricule,
    })
    rep, err := s.Ope.HTTP.Post(s.Ope.Base+"/collect", "application/json",
        strings.NewReader(string(corps)))
    if err != nil {
        return err
    }
    defer rep.Body.Close()

    brut, err := io.ReadAll(rep.Body)
    if err != nil {
        return err
    }

    if rep.StatusCode != http.StatusOK {
        if strings.Contains(string(brut), "INSUFFICIENT_FUNDS") {
            return errors.New("solde insuffisant")
        }
        if strings.Contains(string(brut), "WRONG_PIN") {
            return errors.New("code secret errone")
        }
        return fmt.Errorf("operateur : %d : %s", rep.StatusCode, brut)
    }

    var reponse struct {
        TransactionID string `json:"transaction_id"`
    }
    if err := json.Unmarshal(brut, &reponse); err != nil {
        return err
    }

    _, err = s.DB.Exec(
        "INSERT INTO paiements (matricule, montant, transaction, le) VALUES ($1,$2,$3,$4)",
        matricule, montant, reponse.TransactionID, time.Now(),
    )
    if err != nil {
        return err
    }

    _, err = s.DB.Exec(
        "UPDATE scolarites SET reste_a_payer = reste_a_payer - $1 WHERE matricule = $2",
        montant, matricule,
    )
    return err
}

// Appelant est le code qui appelle Payer, tel qu'il est ecrit aujourd'hui.
func Appelant(s *Service, matricule string, montant int64, tel string) error {
    var derniere error
    for essai := 0; essai < 3; essai++ {
        derniere = s.Payer(matricule, montant, tel)
        if derniere == nil {
            return nil
        }
        time.Sleep(time.Duration(essai+1) * time.Second)
    }
    return derniere
}
```

1. **Dresse le tableau des issues** de `Payer` : une ligne par issue, avec sa
   **nature**, la **conduite** que l'appelant devrait tenir, et **ce qui reste
   vrai** après. Combien d'issues as-tu trouvées, et combien sont rendues sous
   une forme que l'appelant peut distinguer ?
2. Le `HTTP.Post` expire au bout du délai du client. **Quel est l'état du
   système à cet instant ?** Que dit le contrat actuel ? Que devrait-il dire ?
3. `Appelant` réessaie trois fois dès que `err != nil`. Déroule ce qui se
   passe pour **chaque** issue de ton tableau. Laquelle **crée de l'argent**
   ou en détruit ?
4. `strings.Contains(string(brut), "INSUFFICIENT_FUNDS")`. Donne **trois
   scénarios distincts** où cette ligne cesse de fonctionner — sans qu'une
   seule ligne de ce dépôt ait changé.
5. Combien de sentinelles cette API devrait-elle exposer ? Liste-les, et
   justifie chacune par une **conduite distincte**. Puis dis explicitement
   quelles issues tu choisis de **fusionner**, et pourquoi.
6. Aujourd'hui, le *handler* qui appelle `Appelant` rend 500 sur toute erreur.
   Sur un mois où 3 % des paiements échouent pour solde insuffisant et 0,2 %
   pour une panne réelle, que dit l'indicateur de disponibilité ? Et que
   devrait-il dire ?
7. Entre les deux `Exec` finaux, le processus est tué. Quel est l'état de la
   base ? Qu'est-ce qui, dans la conception, rend cet état possible — et
   est-ce un problème d'erreur ou un problème de transaction ?

## Exercice 2 — Code

Réécris `Payer` et son appelant.

Contraintes impératives :

1. **Analyse à la frontière.** Matricule, montant et numéro deviennent des
   types qui ne peuvent pas être invalides. Le cœur de `Payer` ne contient
   **aucune** vérification de format — et si tu n'arrives pas à l'obtenir,
   dis où ça bloque.
2. Écris le **tableau des issues** dans le commentaire de l'opération, avec la
   colonne « ce qui reste vrai ». C'est le livrable principal.

7. Écris la table de correspondance issue → statut HTTP → niveau de journal,
   dans le paquet qui expose l'API, avec le test qui **énumère toutes les

## Exercice 4 — Design

Une opération peut se terminer dans un état que personne ne connaît : l'appel
à l'opérateur a expiré, et le paiement est peut-être passé.

Quatre conceptions sont proposées :

| | Conception |
|---|---|
| A | `Payer` rend une erreur ; l'appelant se débrouille |
| B | `Payer` rend un reçu dont l'état peut valoir `Incertain` |
| C | `Payer` rend immédiatement une référence ; l'appelant interroge l'état jusqu'à résolution |
| D | `Payer` ne rend que `Confirmé` ou `Échoué`, et résout l'incertitude elle-même avant de rendre la main |

1. Pour chacune : ce qu'elle garantit, ce qu'elle coûte, et surtout **qui finit
   par faire le travail de réconciliation**. Cette dernière colonne est celle
   qui tranche.
2. **C** déplace la complexité chez l'appelant. Combien d'appelants y a-t-il
   dans un système réel — compte le site, l'application mobile, le guichet, le
   script de rattrapage — et qu'est-ce que ça implique sur ton choix ?
3. **D** est la plus confortable à appeler. Qu'est-ce qu'elle promet qu'elle ne
   peut pas tenir, et dans quel cas précis ? Donne le scénario exact.
4. L'état « payé chez l'opérateur, non enregistré chez nous » peut-il être
   rendu **non représentable** (⚫) ? Réponds, puis dis quel est le meilleur
   niveau atteignable et de quoi il dépend.
5. Quelle que soit ta conception, il restera des paiements incertains. **Combien
   par mois est acceptable ?** Donne un critère, dis qui les regarde, à quelle
   fréquence, et ce qui se passe si personne ne les regarde pendant trois
   semaines.
6. Écris le commentaire de documentation de l'opération que tu retiens, en
   entier, avec les trois parties du contrat de la leçon — y compris *ce qui
   reste vrai* pour chaque issue.

## Exercice 5 — Incident de production

Plateforme de paiement de frais scolaires. Extrait du post-mortem.

```
11h02  l'opérateur mobile money déploie une nouvelle version de son API
11h04  taux d'échec des paiements : 4 % -> 31 %
11h06  quota d'appels du compte marchand : 100 % consommé
11h07  tous les paiements échouent, y compris ceux qui auraient réussi
11h22  alerte, levée par un message du directeur commercial
11h44  rétabli après désactivation du réessai automatique
```

Faits établis :

- aucun déploiement de notre côté ce jour-là ;
- l'opérateur rendait auparavant `HTTP 402` avec le corps
  `{"code":"INSUFFICIENT_FUNDS"}` pour un solde insuffisant ; il rend
  désormais `HTTP 429` avec `{"code":"INSUFFICIENT_FUNDS"}` ;
- notre client classe `429` comme « réessayable », avec trois tentatives et une
  attente croissante ;
- le quota du compte marchand est de 10 appels par seconde, tous usages
  confondus ;
- pendant tout l'incident, notre propre tableau de bord affichait un taux de
  **5xx à 0 %** et une disponibilité de 100 %.

1. La réponse de l'opérateur relève de laquelle des **quatre natures** ? De
   laquelle notre client l'a-t-il classée ? Nomme la ligne de code
   responsable — elle n'est pas dans le corps du message.
2. Pourquoi les réessais ont-ils **aggravé** la situation ? Sois précis sur le
   mécanisme et sur le quota : fais le calcul.
3. À 11h07, « tous les paiements échouent, y compris ceux qui auraient
   réussi ». Explique le lien avec la question 2, et nomme le phénomène.
4. L'opérateur a changé le code HTTP d'une réponse métier sans changer de
   version majeure. **À qui la faute ?** Réponds franchement, puis dis ce qui,
   chez nous, aurait détecté le changement — et classe tes propositions par
   délai de détection.
5. Le tableau de bord affichait 100 % de disponibilité pendant que 31 % des
   paiements échouaient. Comment est-ce possible ? Qu'est-ce que ça dit de la
   relation entre classification des erreurs et mesure de disponibilité ? Et
   quel indicateur aurait vu l'incident ?
6. L'alerte est venue du **directeur commercial**, 20 minutes après le début.
   Quelle alerte technique aurait dû partir avant, et sur quelle grandeur ?
   *Indice : elle ne porte pas sur un taux d'erreur.*
7. **Question ouverte.** Propose une règle de classification des erreurs d'un
   **tiers** qui survive au fait que ce tiers change ses erreurs sans prévenir.
   Elle doit être :
   - vérifiable mécaniquement — dis par quoi ;
   - chiffrée — dis quel facteur d'amplification elle borne ;
   - et honnête sur ce qu'on perd en l'adoptant, parce qu'on perd quelque
     chose de précis.
