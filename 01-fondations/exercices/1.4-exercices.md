# Exercices 1.4 — Abstraction : quoi cacher, quoi exposer

**Règles.** Réponds avant d'ouvrir la correction. Pour tous les exercices, deux
questions remplacent *« cette interface est-elle propre ? »* :

> Qu'est-ce que l'appelant a le droit d'ignorer ? Et si je changeais
> d'implémentation demain, qu'est-ce qui, chez lui, devrait changer ?

Et un rappel, parce que la moitié des points est là : **la question n'est pas
seulement ce qu'il faut cacher, c'est aussi ce qu'il faut refuser de cacher.**

Écris tes réponses dans `01-fondations/mes-reponses/1.4.md` (dossier local,
ignoré par Git).

## Exercice 1 — Compréhension

Une file de messages, et le module qui s'en sert.

```go
package notifs

import (
    "encoding/json"
    "fmt"
    "log/slog"
)

// File est l'abstraction de la file de messages.
type File interface {
    Publier(sujet string, message []byte) error
    Consommer(sujet string, h func([]byte) error) error
    Longueur(sujet string) (int, error)
    Purger(sujet string) error
}

type Confirmation struct {
    Reservation string `json:"reservation"`
    Telephone   string `json:"telephone"`
    Place       string `json:"place"`
}

type Expediteur interface {
    Envoyer(numero, texte string) error
}

type Service struct {
    file File
    sms  Expediteur
    log  *slog.Logger
}

func (s *Service) Confirmer(c Confirmation) error {
    corps, err := json.Marshal(c)
    if err != nil {
        return err
    }
    if err := s.file.Publier("confirmations", corps); err != nil {
        return fmt.Errorf("publication : %w", err)
    }
    return nil
}

func (s *Service) Demarrer() error {
    return s.file.Consommer("confirmations", func(m []byte) error {
        var c Confirmation
        if err := json.Unmarshal(m, &c); err != nil {
            s.log.Warn("message illisible", "err", err)
            return nil
        }
        texte := fmt.Sprintf("Votre place %s est confirmee.", c.Place)
        return s.sms.Envoyer(c.Telephone, texte)
    })
}

// Tableau sert au tableau de bord d'exploitation.
func (s *Service) Tableau() (int, error) {
    return s.file.Longueur("confirmations")
}
```

1. Dresse le relevé en **trois** colonnes, et non deux : ce que cette interface
   **cache** réellement, ce qui **fuit** à travers elle, et ce qui est
   simplement **absent du contrat**. La troisième colonne est la plus longue,
   et c'est l'intérêt de la question.
2. Le contrat ne dit rien des garanties de livraison. Énumère les comportements
   de `Consommer` qui seraient tous **conformes** à cette interface — au moins
   cinq. Pour chacun, dis ce qui casse dans `Service`.
3. `h func([]byte) error` : que signifie rendre une erreur ? Énumère les
   significations possibles — au moins quatre. Laquelle `Service` suppose-t-il ?
   Et que se passe-t-il avec un message que l'on ne pourra **jamais** traiter ?
4. `return nil` après un `json.Unmarshal` qui échoue. Nomme la décision de
   conception cachée dans cette ligne, dis qui l'a prise, et donne sa
   conséquence en production.
5. `Longueur` et `Purger` : font-elles partie de la question que `Service`
   pose ? Qui les a demandées ? Applique le test du miroir, puis dis ce que
   chacune coûte au contrat.
6. On remplace l'implémentation en mémoire par un vrai courtier (RabbitMQ,
   SQS, Kafka — choisis). Liste ce qui casse dans `Service`, et classe chaque
   point selon que **le compilateur l'attrape ou non**.
7. `Publier` ne prend pas de `context.Context`. Quelle promesse implicite cette
   absence contient-elle, et est-elle tenable ?

## Exercice 2 — Code

## Exercice 3 — Refactoring

Un dépôt de commandes, tel qu'on en trouve vraiment.

```go
package entrepot

import (
    "database/sql"
    "time"
)

type Commande struct {
    ID      int64
    Client  string
    Total   int64
    CreeeLe time.Time
    Statut  string
}

// CommandeRepository est l'interface du depot de commandes.
type CommandeRepository interface {
    FindAll(query string, args ...any) ([]*Commande, error)
    FindOne(query string, args ...any) (*Commande, error)
    Exec(query string, args ...any) (sql.Result, error)
    BeginTx() (*sql.Tx, error)
    DB() *sql.DB
}

// Quelques appels reels, pris dans trois modules differents.
func CommandesDuClient(r CommandeRepository, client string) ([]*Commande, error) {
    return r.FindAll(
        "SELECT id, client, total, creee_le, statut FROM commandes "+
            "WHERE client = $1 ORDER BY creee_le DESC LIMIT 50", client)
}

func Annuler(r CommandeRepository, id int64) error {
    tx, err := r.BeginTx()
    if err != nil {
        return err
    }
    defer tx.Rollback()

    if _, err := tx.Exec("UPDATE commandes SET statut = 'annulee' WHERE id = $1", id); err != nil {
        return err
    }
    if _, err := tx.Exec("INSERT INTO mouvements_stock (commande_id, sens) VALUES ($1, 'retour')", id); err != nil {
        return err
    }
    return tx.Commit()
}

func TotalDuJour(r CommandeRepository, jour time.Time) (int64, error) {
    var total int64
    err := r.DB().QueryRow(
        "SELECT COALESCE(SUM(total), 0) FROM commandes WHERE creee_le::date = $1",
        jour).Scan(&total)
    return total, err
}
```

1. Combien d'implémentations raisonnables cette interface admet-elle ?
   Justifie, méthode par méthode. Puis réponds à la question qui compte :
   **qu'est-ce qu'elle cache ?**
2. Applique le test du miroir. Puis un second test, plus dur : écris la liste
   des choses qu'un appelant doit savoir pour utiliser `FindAll` correctement.
3. `DB()` est une porte de sortie. Nomme ce qu'elle annule, et dis pourquoi sa
   simple existence rend les quatre autres méthodes décoratives.
4. Réécris l'interface en **questions**. Donne la signature de chaque méthode
   et, en une ligne, le besoin qu'elle sert. Combien en as-tu ?
5. **La partie difficile : les transactions.** `Annuler` a besoin que deux
   écritures soient atomiques, et l'une des deux ne concerne même pas les
   commandes. Comment exprimer « ces deux écritures sont atomiques » sans
   laisser fuir `*sql.Tx` ? Propose **deux** conceptions différentes, dis ce
   que chacune coûte, et choisis.
6. `TotalDuJour` est un agrégat. Est-ce qu'il appartient à ce dépôt ?
   Argumente avec les critères de la leçon 1.2, puis avec ceux de la 1.4 — les
   deux ne donnent pas forcément la même réponse, et c'est la réponse.
7. `ORDER BY creee_le DESC LIMIT 50` : la pagination est aujourd'hui dans la
   chaîne SQL, donc chez l'appelant. Dis où elle doit aller, et quelle
   promesse le contrat doit faire sur la stabilité des pages.

## Exercice 4 — Design

Une plateforme de petites annonces doit offrir une recherche plein texte. Il
existe un index (Elasticsearch, OpenSearch — peu importe) alimenté en
différé depuis PostgreSQL.

Quatre frontières sont proposées :

| | Frontière proposée |
|---|---|
| A | on expose le client de l'index directement aux modules métier |
| B | on expose un langage de requête maison, en chaîne de caractères |
| C | on expose des filtres typés : `Critères{Texte, Ville, PrixMax, Catégorie}` |
| D | on expose une seule méthode par cas d'usage : `RechercherAnnonces`, `Suggérer`, `AnnoncesSimilaires` |

1. Pour chacune : ce qu'elle cache, ce qu'elle laisse fuir, et combien
   d'implémentations elle admet. Puis classe-les — et dis explicitement si ton
   classement dépend du nombre de cas d'usage, parce qu'il en dépend.
2. **Peut-on abstraire la pertinence ?** L'ordre des résultats est le cœur du
   produit. Réponds, puis : si la réponse est non, qu'est-ce que le contrat
   doit exposer pour que le produit puisse l'influencer, sans pour autant
   exposer l'index ?
3. **L'index est éventuellement cohérent** : une annonce publiée apparaît dans
   la recherche après quelques secondes. Est-ce que ça peut se cacher ?
   Réponds, puis dis ce que le contrat doit en dire, et ce que le produit doit
   en faire.
4. **La pagination.** `LIMIT`/`OFFSET` et la pagination par curseur ne sont pas
   deux implémentations d'un même contrat : ce sont deux contrats. Montre-le en
   nommant une promesse que l'un peut tenir et l'autre pas. Puis choisis, et
   chiffre le coût de ton choix pour l'appelant.
5. Six mois plus tard, l'index est remplacé par une recherche vectorielle : il
   n'y a plus de filtre exact, seulement une distance. Laquelle de tes quatre
   frontières survit ? Et est-ce que ça change ton classement de la question 1 ?
6. Écris le commentaire de documentation de ta frontière, en entier, comme s'il
   devait être lu par quelqu'un d'une autre équipe. Il doit contenir les six
   rubriques de la leçon, dont **ce qui n'est pas garanti**.

## Exercice 5 — Incident de production

Catalogue produits d'une place de marché. Extrait du post-mortem.

```
09h14  incident réseau de 40 s entre les pods applicatifs et Redis
09h15  latence p99 GET /produits : 60 ms -> 4 s ; 5xx à 30 %
09h18  le réseau est rétabli, Redis répond normalement en 1 ms
09h18  la latence ne revient pas. 5xx à 60 %
09h25  PostgreSQL : 100 % des connexions du pool occupées
09h47  rétabli après redémarrage simultané de tous les pods
```

Faits établis :

- aucun déploiement ce jour-là ;
- le cache est derrière cette abstraction, inchangée depuis deux ans :

```go
type Cache interface {
    Get(cle string) ([]byte, bool)
    Set(cle string, v []byte, ttl time.Duration)
}
```

- l'implémentation Redis, en cas d'erreur réseau, journalise en `debug` et rend
  `(nil, false)` ;
- l'appelant, sur `false`, lit PostgreSQL puis appelle `Set` ;
- Redis répondait normalement dès 09h18, et le cache est resté **vide**
  jusqu'au redémarrage.

1. Nomme la fuite avec précision : **quels deux états sont confondus**, et dans
   quelle signature exactement ?
2. Pourquoi le système ne s'est-il pas rétabli à 09h18, alors que la cause
   initiale avait disparu ? Décris le mécanisme étape par étape, puis nomme la
   propriété du système qui fait du redémarrage la seule sortie.
3. L'implémentation « gérait » l'erreur Redis en se rabattant sur la source de
   vérité. Plaide d'abord que c'était la bonne décision, puis qu'elle était
   fautive. Tranche, et énonce la règle qui généralise.
4. Réécris la signature pour que l'appelant puisse distinguer les deux états.
   Puis la question qui compte vraiment : **qu'est-ce que l'appelant doit en
   faire ?** Donne trois conduites possibles et le coût de chacune.
5. Le `ttl` est un paramètre de `Set`, donc une décision de l'appelant. Est-ce
   le bon endroit ? Et qui décide du TTL d'une clé écrite par trois modules
   différents ?
6. **Question ouverte.** Propose une règle sur les replis — *fallbacks* — qui
   aurait empêché cette classe d'incidents. Elle doit être :
   - vérifiable mécaniquement : dis par quoi ;
   - chiffrée : dis quel facteur d'amplification elle borne, et à quelle
     valeur ;
   - et honnête sur ce qu'on abandonne en l'adoptant, parce qu'on abandonne
     quelque chose.

   *Indice : la réponse réutilise la règle de la correction 1.3 / 5.*
