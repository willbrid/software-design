# Exercices 1.6 — La testabilité comme révélateur de conception

**Règles.** Réponds avant d'ouvrir la correction. Pour tous les exercices, la
question n'est jamais *« comment tester ça ? »* mais *« qu'est-ce que la
difficulté de tester ça me dit de la conception ? »*

Deux obligations de méthode, valables partout dans ce chapitre :

1. **Chaque fois que tu écris un test, écris en une ligne quelle modification du
   code le ferait échouer.** Si tu ne trouves qu'une panique ou un renommage,
   le test ne vaut rien et c'est le moment de le savoir.
2. **Chaque fois que tu prétends qu'un test protège quelque chose, casse le code
   et vérifie-le.** Un test jamais vu rouge n'est pas un test vérifié.

Écris tes réponses dans `01-fondations/mes-reponses/1.6.md` (dossier local,
ignoré par Git).

## Exercice 1 — Compréhension

Clôture journalière d'une boutique. En production depuis dix-huit mois.

```go
// Package caisse cloture la journee d'une boutique.
package caisse

import (
    "bytes"
    "context"
    "database/sql"
    "fmt"
    "net/http"
    "os"
    "strconv"
    "time"
)

var (
    tauxTVA   = tauxDepuisEnv()
    cloturees = map[string]bool{}
    total     int64
)

func tauxDepuisEnv() int64 {
    if v := os.Getenv("CAISSE_TVA_POUR_MILLE"); v != "" {
        if n, err := strconv.ParseInt(v, 10, 64); err == nil {
            return n
        }
    }
    return 1925
}

type Service struct {
    db       *sql.DB
    webhooks *http.Client
}

// Cloturer calcule le total de la journee, ecrit le rapport, previent le
// partenaire comptable et marque la boutique comme cloturee.
func (s *Service) Cloturer(ctx context.Context, boutique string) error {
    jour := time.Now().Format("2006-01-02")
    if cloturees[boutique+jour] {
        return nil
    }

    lignes, err := s.db.QueryContext(ctx,
        `SELECT montant_ht FROM ventes WHERE boutique = $1 AND jour = $2`, boutique, jour)
    if err != nil {
        return err
    }
    defer lignes.Close()

    var ht int64
    for lignes.Next() {
        var m int64
        if err := lignes.Scan(&m); err != nil {
            return err
        }
        ht += m
    }
    if err := lignes.Err(); err != nil {
        return err
    }

    tva := ht * tauxTVA / 10000
    ttc := ht + tva
    total += ttc

    rapport := fmt.Sprintf("%s;%s;%d;%d;%d\n", boutique, jour, ht, tva, ttc)
    if err := os.WriteFile("/var/caisse/"+boutique+"-"+jour+".csv", []byte(rapport), 0o644); err != nil {
        return err
    }

    corps := bytes.NewBufferString(`{"boutique":"` + boutique + `","ttc":` + strconv.FormatInt(ttc, 10) + `}`)
    rep, err := s.webhooks.Post("https://comptable.exemple.cm/cloture", "application/json", corps)
    if err != nil {
        return err
    }
    defer rep.Body.Close()
    if rep.StatusCode != http.StatusOK {
        return fmt.Errorf("comptable : statut %d", rep.StatusCode)
    }

    if _, err := s.db.ExecContext(ctx,
        `INSERT INTO clotures (boutique, jour, ttc) VALUES ($1, $2, $3)`, boutique, jour, ttc); err != nil {
        return err
    }

    cloturees[boutique+jour] = true
    return nil
}
```

## Exercice 2 — Code

   permis de **supprimer** : une ligne de code défensive, un test, ou les deux.

   | # | la modification | qui crie |

## Exercice 3 — Refactoring

Validation de commande d'une boutique en ligne.

```go
// Package panier valide les commandes d'une boutique en ligne.
package panier

import (
    "context"
    "errors"
    "fmt"
)

var ErrStockInsuffisant = errors.New("panier : stock insuffisant")

type Ligne struct {
    Article  string
    Quantite int
    PrixHT   int64
}

type Commande struct {
    ID      string
    Client  string
    Lignes  []Ligne
    Valide  bool
    TotalHT int64
}

type Depot interface {
    Lire(ctx context.Context, id string) (Commande, error)
    Ecrire(ctx context.Context, c Commande) error
}

type Stock interface {
    Disponible(ctx context.Context, article string) (int, error)
    Reserver(ctx context.Context, article string, quantite int) error
}

type Service struct {
    depot Depot
    stock Stock
    // remisePourMille est la remise appliquee aux commandes de plus de dix
    // articles, en pour mille.
    remisePourMille int64
}

func Nouveau(d Depot, s Stock, remisePourMille int64) *Service {
    return &Service{depot: d, stock: s, remisePourMille: remisePourMille}
}

func (s *Service) Valider(ctx context.Context, id string) error {
    c, err := s.depot.Lire(ctx, id)
    if err != nil {
        return err
    }

    var articles int
    var ht int64
    for _, l := range c.Lignes {
        dispo, err := s.stock.Disponible(ctx, l.Article)
        if err != nil {
            return err
        }
        if dispo < l.Quantite {
            return fmt.Errorf("%w : %s", ErrStockInsuffisant, l.Article)
        }
        if err := s.stock.Reserver(ctx, l.Article, l.Quantite); err != nil {
            return err
        }
        articles += l.Quantite
        ht += int64(l.Quantite) * l.PrixHT
    }

    if articles > 10 {
        ht = ht - ht*s.remisePourMille/1000
    }

    c.Valide = true
    c.TotalHT = ht
    return s.depot.Ecrire(ctx, c)
}
```

## Exercice 5 — Incident de production

Plateforme de recouvrement. Extrait du post-mortem.

```
mar. 02h00  la campagne de relance horaire demarre
mar. 02h00  la base de donnees passe en bascule (maintenance planifiee, 90 s)
mar. 02h01  la campagne termine : « 1 180 relances, 1 180 echecs de consignation »
mar. 03h00  passe suivante : 1 180 relances, 1 180 echecs
            ... la situation se repete a chaque heure
mar. 09h12  le support signale des clients ayant recu 7 SMS identiques
mar. 09h40  la campagne est arretee a la main
mar. 11h20  8 260 SMS envoyes pour 1 180 impayes. Deux clients en resiliation.
```

Établi après coup :

- La campagne **envoie** le SMS, **puis** consigne l'envoi.
- La bascule de base a duré 90 secondes. Pendant ce temps, les écritures
  échouaient ; les lectures, servies par un réplica, réussissaient.
- La consignation échouait, donc la passe suivante redécidait le même palier.
- Le tableau de bord affichait un taux d'erreur de **0 %** : l'échec de
  consignation était compté comme une ligne en échec dans un bilan, pas comme
  une erreur HTTP.
- La CI était verte. Couverture : **94 %**. Trente-et-un tests sur la campagne.
- La suite de tests utilisait un double de journal dont `Consigner` rendait
  toujours `nil`.

1. **Nomme les trois décisions de conception** qui ont rendu cet incident
   possible. Le bug n'est pas « la base est tombée » : la base a le droit de
   tomber, c'était une maintenance annoncée.

2. 94 % de couverture, trente-et-un tests, et aucun ne voit ça. Explique le
   mécanisme exact — pas « les tests étaient mauvais », mais **quelle propriété
   du double rendait ce scénario inobservable**.

3. Écris le test qui aurait attrapé ça. Donne sa **forme** : ce que le double
   doit savoir faire, combien de passes, et quelle assertion. Puis dis combien
   de lignes il fait, et compare avec les trente-et-un autres.

4. **Sept heures** entre le début et l'arrêt manuel. Qu'est-ce qui, dans la
   conception, explique ces sept heures ? Rattache ta réponse aux deux termes du
   MTTR de la leçon 1.2.

5. L'alerte qui aurait sonné à 02h05 n'est pas un taux d'erreur — le taux
   d'erreur était à 0 %. **Quelle grandeur surveiller ?** Donne sa définition,
   sa valeur en régime normal, et pourquoi elle monte **avant** que le client ne
   s'en plaigne.

6. La correction évidente est d'inverser les deux lignes : consigner, puis
   envoyer. Elle supprime le doublon et **crée un autre risque**. Nomme-le,
   chiffre-le sur cet incident précis — 1 180 impayés, 90 secondes de bascule —
   et dis si tu prends l'échange. Puis : existe-t-il une conception qui ne prend
   ni l'un ni l'autre ? Qu'est-ce qu'elle coûte ?

7. **Question ouverte.** La direction technique demande : *« comment on
   s'assure que ça ne se reproduit pas ? »*. La réponse « on augmente la
   couverture à 100 % » est fausse, et tu dois pouvoir expliquer pourquoi en
   deux phrases.

   Propose à la place **une mesure, un seuil, et un rituel** :

   - une grandeur qui mesure la **qualité** d'une suite de tests, lisible sans
     outil exotique ;
   - un seuil défendable, avec son argument ;
   - un rituel qui tient en moins d'une heure par semaine et que l'équipe fera
     vraiment.

   Et la vraie question : **comment empêches-tu que ta mesure devienne, à son
   tour, un chiffre qu'on optimise sans rien améliorer ?** C'est exactement ce
   qui est arrivé à la couverture.
