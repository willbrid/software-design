# Exercices 1.6 — La testabilité comme révélateur de conception

**Règles.** Réponds avant d'ouvrir la correction. Pour tous les exercices, la
question n'est jamais *« comment tester ça ? »* mais *« qu'est-ce que la
difficulté de tester ça me dit de la conception ? »*

Deux obligations de méthode, valables partout dans ce chapitre :

1. **Chaque fois que tu écris un test, écris en une ligne quelle modification du
   code le ferait échouer.** Si tu ne trouves qu'une panique ou un renommage,
   le test ne vaut rien et c'est le moment de le savoir.
2. **Chaque fois que tu prétends qu'un test protège quelque chose, casse le code
   et vérifie-le.** Un test jamais vu rouge n'est pas un test vérifié.

Écris tes réponses dans `01-fondations/mes-reponses/1.6.md` (dossier local,
ignoré par Git).

## Exercice 1 — Compréhension

Clôture journalière d'une boutique. En production depuis dix-huit mois.

```go
// Package till closes a shop's day.
package till

import (
    "bytes"
    "context"
    "database/sql"
    "fmt"
    "net/http"
    "os"
    "strconv"
    "time"
)

var (
    vatRate = rateFromEnv()
    closed  = map[string]bool{}
    total   int64
)

func rateFromEnv() int64 {
    if v := os.Getenv("TILL_VAT_PER_MILLE"); v != "" {
        if n, err := strconv.ParseInt(v, 10, 64); err == nil {
            return n
        }
    }
    return 1925
}

type Service struct {
    db       *sql.DB
    webhooks *http.Client
}

// Close computes the day's total, writes the report, notifies the
// accounting partner and marks the shop as closed.
func (s *Service) Close(ctx context.Context, shop string) error {
    day := time.Now().Format("2006-01-02")
    if closed[shop+day] {
        return nil
    }

    lines, err := s.db.QueryContext(ctx,
        `SELECT net_amount FROM sales WHERE shop = $1 AND day = $2`, shop, day)
    if err != nil {
        return err
    }
    defer lines.Close()

    var ht int64
    for lines.Next() {
        var m int64
        if err := lines.Scan(&m); err != nil {
            return err
        }
        ht += m
    }
    if err := lines.Err(); err != nil {
        return err
    }

    vat := ht * vatRate / 10000
    gross := ht + vat
    total += gross

    report := fmt.Sprintf("%s;%s;%d;%d;%d\n", shop, day, ht, vat, gross)
    if err := os.WriteFile("/var/till/"+shop+"-"+day+".csv", []byte(report), 0o644); err != nil {
        return err
    }

    body := bytes.NewBufferString(`{"shop":"` + shop + `","gross":` + strconv.FormatInt(gross, 10) + `}`)
    rep, err := s.webhooks.Post("https://comptable.exemple.cm/cloture", "application/json", body)
    if err != nil {
        return err
    }
    defer rep.Body.Close()
    if rep.StatusCode != http.StatusOK {
        return fmt.Errorf("accounting: status %d", rep.StatusCode)
    }

    if _, err := s.db.ExecContext(ctx,
        `INSERT INTO closings (shop, day, gross) VALUES ($1, $2, $3)`, shop, day, gross); err != nil {
        return err
    }

    closed[shop+day] = true
    return nil
}
```

## Exercice 2 — Code

Écris la règle suivante, et rien d'autre.

> **Un prélèvement rejeté est réessayé. La nouvelle date est le prochain jour
> ouvré au moins 4 jours après le rejet, hors jours fériés. Au troisième rejet,
> on n'essaie plus : le dossier part au recouvrement.**

Contraintes impératives :

3. Le calendrier des jours fériés a **deux implémentations** : une liste figée,
   et une qui le lit ailleurs (fichier ou service, au choix). Écris **un seul**
   test de contrat, partagé par les deux. Puis réponds : **quelles clauses ce
   test de contrat ne peut pas vérifier ?** Nomme-les.
4. Rends **un** état invalide non représentable, et un seul — celui que tu juges
   le plus coûteux. Situe le mécanisme : ⚪ 🟡 🟠 🔴 ⚫. Dis ce que ça t'a
   permis de **supprimer** : une ligne de code défensive, un test, ou les deux.
5. Écris un test qui garantit que la règle **ne modifie pas** ce qu'on lui
   passe.
6. **La campagne de modifications.** Applique cinq modifications à ton propre
   code — par exemple un `>=` qui devient `>`, un seuil 3 qui devient 4, un tri
   ajouté, une branche inversée, une garde supprimée — et donne le relevé :

   | # | la modification | qui crie |
   |---|---|---|

   S'il y a un **survivant**, ne le cache pas : c'est la partie intéressante de
   l'exercice. Dis ce que tu en as fait, et lequel des trois choix tu as pris —
   ajouter un test, supprimer la ligne, rendre l'état inconstruisible.

## Exercice 3 — Refactoring

Validation de commande d'une boutique en ligne.

```go
// Package cart validates the orders of an online shop.
package cart

import (
    "context"
    "errors"
    "fmt"
)

var ErrStockTooLow = errors.New("cart: stock too low")

type Line struct {
    Article  string
    Qty      int
    NetPrice int64
}

type Order struct {
    ID       string
    Client   string
    Lines    []Line
    Valid    bool
    NetTotal int64
}

type Repo interface {
    Read(ctx context.Context, id string) (Order, error)
    Write(ctx context.Context, c Order) error
}

type Stock interface {
    Available(ctx context.Context, article string) (int, error)
    Reserve(ctx context.Context, article string, qty int) error
}

type Service struct {
    repo  Repo
    stock Stock
    // discountPerMille is the discount applied to orders of more than ten
    // articles, per mille.
    discountPerMille int64
}

func New(d Repo, s Stock, discountPerMille int64) *Service {
    return &Service{repo: d, stock: s, discountPerMille: discountPerMille}
}

func (s *Service) Validate(ctx context.Context, id string) error {
    c, err := s.repo.Read(ctx, id)
    if err != nil {
        return err
    }

    var articles int
    var ht int64
    for _, l := range c.Lines {
        avail, err := s.stock.Available(ctx, l.Article)
        if err != nil {
            return err
        }
        if avail < l.Qty {
            return fmt.Errorf("%w: %s", ErrStockTooLow, l.Article)
        }
        if err := s.stock.Reserve(ctx, l.Article, l.Qty); err != nil {
            return err
        }
        articles += l.Qty
        ht += int64(l.Qty) * l.NetPrice
    }

    if articles > 10 {
        ht = ht - ht*s.discountPerMille/1000
    }

    c.Valid = true
    c.NetTotal = ht
    return s.repo.Write(ctx, c)
}
```

Sa suite de tests. Cinq tests, tous verts, **100 % de couverture des
instructions** — c'est mesuré, pas supposé.

package cart_test

import (
    "context"
    "errors"
    "testing"

    "example/e16/cart"

type fakeRepo struct {
    order   cart.Order
    err     error
    written []cart.Order
}

func (d *fakeRepo) Read(ctx context.Context, id string) (cart.Order, error) {
    return d.order, d.err
}

func (d *fakeRepo) Write(ctx context.Context, c cart.Order) error {
    d.written = append(d.written, c)
    return nil
}

type fakeStock struct {
    avail    int
    reserved int
    availErr error
    resErr   error
}

func (s *fakeStock) Available(ctx context.Context, article string) (int, error) {
    return s.avail, s.availErr
}

func (s *fakeStock) Reserve(ctx context.Context, article string, qty int) error {
    s.reserved++
    return s.resErr
}

func orderOf(lines ...cart.Line) cart.Order {
    return cart.Order{ID: "C-1", Client: "Awa", Lines: lines}

## Exercice 4 — Design

Tu dois décider **où passe la frontière de tes tests** pour un flux de paiement
d'abonnement : un appel HTTP entrant, une écriture en base, un appel à un
prestataire externe, un message posté dans une file, un email.

Cinq périmètres possibles :

| | Périmètre |
|---|---|
| A | tout en doubles mémoire, dans le processus de test |
| B | test de contrat partagé + implémentations réelles dans des conteneurs |
| C | bout en bout sur un environnement complet, prestataire en bac à sable |
| D | préproduction, avec du trafic de production rejoué |
| E | production : déploiement canari, puis trafic dupliqué en observation |

1. Pour chacun, remplis les quatre colonnes. Sois concret — « plus de confiance »
   n'est pas une réponse.

   | Périmètre | Ce qu'il garantit vraiment | Ce qu'il ne peut **jamais** attraper | Délai pour avoir la réponse | Coût de maintenance |
   |---|---|---|---|---|

2. Un bug a échappé à A et serait attrapé par B. Un bug a échappé à B et serait
   attrapé par C. **Donne les deux bugs**, précisément, avec le mécanisme.

3. Les cinq périmètres ne se rangent pas dans un seul pipeline. Répartis-les
   entre **à chaque commit**, **chaque nuit**, **à la demande**, **en
   permanence** — et donne le **critère** de ta répartition. Pas une habitude :
   un critère qu'on peut appliquer à un sixième périmètre.

4. **La question de l'horloge.** Le métier demande un batch de rattrapage qui
   rejoue les prélèvements d'un mois passé « comme si on était le 5 ». Il y a
   donc maintenant un demandeur en production pour une horloge décalée.
   Est-ce que ça change ta réponse du §3 de la leçon ? Si oui, dis exactement
   quelle couture tu ouvres, qui a le droit de l'utiliser, et **comment tu
   empêches qu'elle serve ailleurs**. Situe le mécanisme dans la palette.

5. **Un rappel envoyé deux fois** peut-il être rendu non représentable (⚫) ? Si
   oui, décris le mécanisme complet, jusqu'au prestataire d'envoi. Si non, dis
   ce qui l'en empêche, quel est le meilleur niveau atteignable, et **par quoi
   on remplace une garantie quand on ne peut pas l'avoir**.

6. Quelqu'un propose : *« de toute façon, avec E, on n'a plus besoin de A ni de
