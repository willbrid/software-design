## Exercice 1 — Compréhension

```go
type Config struct {
    Nom     string
    Tags    []string
    Limites map[string]int
}

func Normaliser(c Config) Config {
    c.Nom = strings.ToLower(c.Nom)
    c.Tags = append(c.Tags, "normalise")
    c.Limites["max"] = 100
    return c
}

func main() {
    original := Config{
        Nom:     "PAIEMENT",
        Tags:    []string{"prod"},
        Limites: map[string]int{"max": 10},
    }
    copie := Normaliser(original)

    fmt.Println(original.Nom)
    fmt.Println(original.Tags)
    fmt.Println(original.Limites["max"])
    fmt.Println(copie.Tags)
}
```

`Config` est passé **par valeur** (pas de pointeur).

1. Qu'affichent les quatre `Println` ? Donne les quatre valeurs.
2. Pour **chacun** des trois champs, explique pourquoi il se comporte ainsi.
   Les trois champs n'ont pas le même comportement — c'est tout l'intérêt.
3. Le champ `Tags` cache un piège supplémentaire : le résultat dépend de la
   **capacité** du slice. Explique dans quel cas `original.Tags` serait modifié
   et dans quel cas il ne le serait pas.

## Exercice 3 — Refactoring

```go
type Panier struct {
    Lignes []Ligne
    Total  float64
}

func (p *Panier) Ajouter(l Ligne) {
    p.Lignes = append(p.Lignes, l)
    p.Total += l.Prix * float64(l.Quantite)
}

func (p *Panier) Lignes2() []Ligne {
    return p.Lignes
}

func CalculerFrais(lignes []Ligne) float64 {
    for i := range lignes {
        if lignes[i].Quantite > 10 {
            lignes[i].Quantite = 10   // plafonnement
        }
    }
    total := 0.0
    for _, l := range lignes {
        total += l.Prix * float64(l.Quantite)
    }
    return total * 0.02
}
```

Un appelant fait :

```go
frais := CalculerFrais(panier.Lignes2())
```

1. Quel est le bug ? Décris le **symptôme** que verrait un client.
2. Ce bug a **deux causes distinctes**, situées dans deux fonctions différentes.
   Identifie-les toutes les deux. Corriger une seule ne suffit pas — explique
   pourquoi.
3. Propose une correction pour chacune.
4. Question de conception : `Panier.Total` est maintenu à jour par `Ajouter`.
   Quel risque cela introduit-il ? Quelle serait l'alternative, et que
   coûterait-elle ?

## Exercice 4 — Design

Tu conçois un package Go réutilisable par d'autres équipes :

```go
package tarif

func Calculer(commande *Commande) (float64, error)
```

Ce package doit lire la commande pour calculer un prix. Il ne doit jamais la
modifier.

1. Pourquoi le `*Commande` est-il un mauvais choix ici ? Donne au moins deux
   raisons de nature différente.
2. Quelles options as-tu pour empêcher — ou décourager — la modification ?
   Liste-les, puis pour chacune : ce qu'elle garantit vraiment, et ce qu'elle
   coûte (performance, ergonomie, maintenance).
3. Go n'a pas de mot-clé `const` sur les paramètres, contrairement au C++.
   Est-ce un manque ? Argumente dans les deux sens avant de trancher.

## Exercice 5 — Incident de production

Système de paiement mobile money. Le service `Transfert` expose :

```go
func (s *Service) Executer(ctx context.Context, t *Transfert) error {
    if err := s.debiter(t.Source, t.Montant); err != nil {
        return err
    }
    if err := s.crediter(t.Destination, t.Montant); err != nil {
        return err
    }
    t.Statut = "termine"
    s.notifier(t)
    return nil
}
```

L'appelant est un handler HTTP avec un timeout client de 30 s. Le client mobile
réessaie automatiquement quand il ne reçoit pas de réponse.

1. Liste **tous** les états dans lesquels le système peut se retrouver si
   `Executer` est interrompu ou rejoué. Sois exhaustif.
2. Lequel de ces états produit le double débit ? Décris la séquence précise,
   étape par étape.
3. Cette fonction est-elle idempotente ? Qu'est-ce qui l'en empêche exactement ?
4. Sans introduire de technologie nouvelle — pas de file, pas de base
   distribuée — quel **changement de conception** rendrait ce double débit
   impossible ? Décris le mécanisme, pas l'outil.
5. Question ouverte : qui, dans cette architecture, est **responsable** de
   garantir qu'un transfert ne s'exécute qu'une fois ? Le client mobile ? Le
   handler HTTP ? Le service ? La base de données ? Justifie — et dis ce qui se
   casse si tu confies cette responsabilité au mauvais endroit.
