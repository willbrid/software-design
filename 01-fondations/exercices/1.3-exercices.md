## Exercice 1 — Compréhension

Le catalogue d'une boutique en ligne. Il tourne en production depuis deux ans.

```go
package catalog

import (
    "database/sql"
    "fmt"
    "os"
    "strconv"
    "strings"
    "sync"
)

var (
    Index     = map[string]*Article{}
    Currency  = "XAF"
    Discounts = map[string]int64{}
    cache     sync.Map
)

func init() {
    raw, err := os.ReadFile("/etc/shop/discounts.conf")
    if err != nil {
        return
    }
    for _, l := range strings.Split(string(raw), "\n") {
        parts := strings.SplitN(l, "=", 2)
        if len(parts) != 2 {
            continue
        }
        pct, _ := strconv.ParseInt(parts[1], 10, 64)
        Discounts[parts[0]] = pct
    }
}

type Article struct {
    Code       string
    NetPrice   int64
    Stock      int
    ShownPrice string
}

type Cart struct {
    Lines map[string]int
    Total int64
}

func Load(db *sql.DB) error {
    lines, err := db.Query("SELECT code, net_price, stock FROM articles")
    if err != nil {
        return err
    }
    defer lines.Close()

    for lines.Next() {
        a := &Article{}
        if err := lines.Scan(&a.Code, &a.NetPrice, &a.Stock); err != nil {
            return err
        }
        Index[a.Code] = a
    }
    return lines.Err()
}

func Reserve(code string, n int, p *Cart) error {
    a, ok := Index[code]
    if !ok {
        return fmt.Errorf("unknown article: %s", code)
    }
    if a.Stock < n {
        return fmt.Errorf("stock too low: %s", code)
    }

    a.Stock -= n
    p.Lines[code] += n
    p.Total += int64(n) * discounted(a)
    a.ShownPrice = Show(a)
    cache.Delete("article:" + code)
    return nil
}

func discounted(a *Article) int64 {
    pct, ok := Discounts[a.Code]
    if !ok {
        pct = Discounts["*"]
    }
    return a.NetPrice - a.NetPrice*pct/100
}

func Show(a *Article) string {
    if v, ok := cache.Load("article:" + a.Code); ok {
        return v.(string)
    }
    s := fmt.Sprintf("%d %s", discounted(a), Currency)
    if a.Stock == 0 {
        s += " (out of stock)"
    }
    a.ShownPrice = s
    cache.Store("article:"+a.Code, s)
    return s
}

func InvalidateCache(prefix string) {
    cache.Range(func(k, _ any) bool {
        if strings.HasPrefix(k.(string), prefix) {
            cache.Delete(k)
        }
        return true
    })
}
```

1. **Dresse le relevé des couplages.** Pour chacun : où il est, son degré sur
   l'échelle, et **l'hypothèse muette** qu'il impose à l'appelant. Formule
   l'hypothèse comme une phrase qui pourrait devenir fausse.
2. Deux changements. Pour chacun, dis ce qui **cesse de compiler** et ce qui
   **casse en silence** :
   - (a) renommer `NetPrice` en `PrixHorsTaxe` ;
   - (b) garder le nom `Stock` mais changer son sens — il comptait le stock
     physique, il comptera désormais le stock *disponible à la vente*
     (physique moins les réservations en cours).

   Lequel des deux te fait le plus peur, et pourquoi ?
3. Deux requêtes HTTP concurrentes appellent `Reserve` sur le même code
   article. Déroule les deux exécutions entrelacées et dis ce qu'on observe.
   Puis : `Index` est une `map` lue et écrite par plusieurs goroutines — que
   dit `go test -race`, et qu'est-ce que ça change au diagnostic ?
4. `Show` **rend** une chaîne et **modifie** `a.ShownPrice`. Nomme le
   degré de couplage que ça crée, puis dis ce que le prochain lecteur du code
   va supposer en voyant un appel à `Show` dont le résultat est ignoré.
5. Applique les **trois tests de cohésion** — retrait, nom, test — à ce
   paquet. Lequel échoue le plus franchement ? Combien de modules vois-tu
   là-dedans, et quels sont leurs demandeurs ?
6. Le `init()` lit un fichier. Cite **trois** conséquences concrètes, dont au
   moins une qui n'apparaît qu'en exploitation et une qui n'apparaît qu'en
   test.

## Exercice 4 — Design

Une plateforme de réservation de trajets interurbains. Quatre modules
existants, dans un seul binaire, un seul dépôt :

- `plan` — la disposition des véhicules et la règle d'attribution des places ;
- `reservation` — les retenues, leur échéance, la confirmation ;
- `tarif` — le prix d'un trajet selon la date, la classe et les promotions ;
- `notif` — le SMS de confirmation.

Trois coutures sont proposées en réunion de conception. Pour **chacune** :
qui voudra remplacer ce côté-là, ce que l'interface coûte, et ton verdict.

| | Couture proposée |
|---|---|
| A | une interface entre `reservation` et `plan` |
| B | une interface entre `reservation` et `tarif` |
| C | `notif` devient un service séparé, appelé en HTTP |

1. Les trois verdicts, avec les quatre critères de la leçon pour chacun. Une
   des trois ne doit pas être créée : laquelle, et quel est l'argument qui
   tranche ?
2. Pour **C** uniquement : le module `reservation` est disponible à 99,95 %, le
   service de notification à 99,9 %. Si l'appel est **synchrone et
   bloquant**, quelle est la disponibilité du parcours de réservation ?
   Chiffre-la. Puis propose une conception qui garde la séparation et annule

3. Six mois plus tard, une demande arrive : *« on vend désormais des places

4. Le tarif doit maintenant être calculé **aussi** par le site partenaire, qui

5. Écris en trois lignes la règle que tu appliquerais désormais pour décider
   de créer une couture. Elle doit pouvoir répondre « non ».

## Exercice 5 — Incident de production

Plateforme de réservation. Extrait du post-mortem.

```
20h10  lancement du nouvel export comptable mensuel (batch)
20h12  latence p99 de POST /reservations : 80 ms -> 9 s
20h14  taux d'erreur 12 % : « context deadline exceeded »
20h20  alerte, astreinte réveillée
20h41  le batch termine de lui-même, tout revient à la normale
```

Faits établis :

- **aucun déploiement ce jour-là** ; le batch était en production depuis trois
  semaines et n'avait jamais tourné, puisqu'il est mensuel ;
- le batch et l'API partagent le même `*sql.DB`, configuré il y a deux ans
  avec `SetMaxOpenConns(20)` ;
- le batch ouvre une transaction par client et la garde ouverte le temps de
  l'export, soit environ dix-huit connexions occupées pendant trente minutes ;
- `go list -deps` ne montre **aucun** lien entre le paquet `export` et le
  paquet `reservation` ;
- en pré-production, le batch tourne en 4 secondes et aucun test n'a échoué.

1. Nomme la ressource partagée et le degré de couplage. Pourquoi aucun outil
   d'analyse statique ne pouvait le voir ?
2. Le couplage existait depuis **deux ans**. Qu'est-ce qui le rendait
   invisible, et qu'est-ce qui a changé exactement à 20h10 ? Formule ta
   réponse comme une règle générale sur les couplages par ressource partagée.
3. Quatre correctifs sont sur la table. Pour chacun : ce qu'il garantit, ce
   qu'il coûte, et **ce qui reste partagé malgré tout**.

   | | Correctif |
   |---|---|
   | A | deux `*sql.DB` distincts, avec des budgets de connexions explicites |
   | B | le batch lit une réplique de lecture |
   | C | le batch traite par lots de 100 avec une transaction courte |
   | D | le batch ne tourne qu'entre 2h et 4h |

   Puis classe-les, et dis lequel tu déploies **cette nuit** et lequel tu
   planifies.
4. La pré-production était verte. Quelle propriété de la pré-production rend
   ce test sans valeur ? Et quel test — exécutable dans la CI, en moins d'une
   minute — aurait attrapé ça ? *Indice : relis la question 4 de l'exercice
   1.2 / 5.*
5. **Question ouverte.** Propose une **règle** sur les ressources partagées
   qui aurait empêché cette classe d'incidents, applicable à la base, au cache,
   au pool HTTP sortant et aux files de messages. Elle doit être :
   - vérifiable mécaniquement — dis par quoi ;
   - chiffrée — dis ce qu'elle coûte en marge inutilisée ;
   - et capable de dire ce qu'on fait quand la somme des budgets dépasse la
     capacité, parce que ce jour-là arrivera.
