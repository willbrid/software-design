# Leçon 1.1 — Effet de bord et propriété des données

## 1. Le concept, simplement

Une fonction fait deux choses possibles :

- elle **calcule** une valeur et la retourne ;
- elle **modifie** quelque chose qui existe en dehors d'elle.

Le second cas s'appelle un **effet de bord** (*side effect*).

### Définition

> Une fonction produit un **effet de bord** dès qu'elle fait quelque chose
> d'observable **en dehors du calcul de sa valeur de retour** — c'est-à-dire dès
> qu'appeler la fonction laisse une trace, ou qu'un second appel identique
> pourrait ne pas donner le même résultat.

Une fonction sans aucun effet de bord, et dont le résultat ne dépend que de ses
arguments, est dite **pure**. Deux appels avec les mêmes entrées y donnent
toujours la même sortie, et on peut la remplacer par son résultat sans rien
changer au programme. C'est le cas le plus facile à lire, à tester et à
paralléliser — mais aussi le plus rare.

### Les six familles d'effets de bord

| # | Famille | Exemples en Go | Portée |
|---|---|---|---|
| 1 | **Mémoire partagée du processus** | écrire dans un slice ou une map reçus en paramètre ; muter un champ via un receiver `*T` ; modifier une variable globale ; écrire dans une variable capturée par une closure | le processus |
| 2 | **État persistant** | `INSERT`/`UPDATE`/`DELETE` en base ; écrire un fichier ; écrire dans un cache Redis | survit au processus |
| 3 | **Monde extérieur** | appel HTTP sortant qui modifie l'autre système ; envoi d'email ou de SMS ; publication dans une file (RabbitMQ, Kafka) ; appel de webhook | irréversible |
| 4 | **Observabilité** | `log.Printf` ; incrément d'une métrique ; émission d'une trace | souvent ignorée, mais réelle |
| 5 | **Ressources et runtime** | ouvrir une connexion ou un fichier ; lancer une goroutine ; prendre un mutex ; allouer massivement | fuites, contention, blocages |
| 6 | **Dépendance à un état extérieur** *(côté entrée)* | `time.Now()` ; `rand.Intn()` ; lire une variable d'environnement ; lire l'état d'une base | rend la fonction non déterministe |

La famille 6 n'est pas un effet de bord au sens strict — la fonction ne modifie
rien — mais elle casse la même propriété : **on ne peut plus prédire le résultat
à partir de la signature et des arguments**. En pratique, elle pose exactement
les mêmes problèmes de test et de raisonnement, et se traite de la même façon :
en la rendant explicite (passer une horloge, une source d'aléa, un `context`).

### Les axes qui font qu'un effet de bord est acceptable ou non

Un effet de bord n'est jamais « bon » ou « mauvais » dans l'absolu. Quatre
questions le qualifient :

| Axe | Question | Pourquoi ça compte |
|---|---|---|
| **Visible / caché** | l'appelant peut-il le deviner depuis la signature et le nom ? | c'est le seul axe qui décide de la qualité du design |
| **Interne / externe** | reste-t-il dans le processus, ou touche-t-il le monde ? | l'externe ne se rejoue pas et ne s'annule pas |
| **Réversible / irréversible** | peut-on l'annuler ? | une transaction s'annule, un SMS non |
| **Idempotent / non** | deux appels font-ils la même chose qu'un seul ? | c'est ce qui décide si un retry est sûr |

Un effet de bord **visible, interne, réversible et idempotent** est presque
toujours inoffensif. Un effet **caché, externe, irréversible et non idempotent**
est la définition même du double débit.

Un effet de bord n'est donc pas un défaut : un programme qui n'en produit aucun
ne fait rien d'utile — il chauffe le processeur et ne laisse aucune trace. Le
défaut, c'est l'effet de bord **que l'appelant ne peut pas deviner en lisant la
signature**.

## 2. L'intuition

Pense à une signature de fonction comme à un **contrat** affiché à la porte.

```go
func AppliquerRemise(prix []float64, pourcentage float64) []float64
```

Ce que ce contrat annonce, en français : *« donne-moi des prix et un pourcentage,
je te rends des prix remisés. »*

Ce que la fonction fait réellement : *« donne-moi tes prix, je te les détruis, et
je te rends les débris. »*

Le problème n'est pas que la fonction mute. Le problème est le **mensonge** entre
ce qu'elle annonce et ce qu'elle fait. Tout appelant qui lui fait confiance a tort.

## 3. Le mécanisme en Go — pourquoi c'est piégeux

Go passe **tout par valeur**. C'est vrai, et c'est ce qui trompe.

Ce qui est copié quand tu passes un slice, c'est le *descripteur* :

```
type slice struct {
    ptr *tableau   // ← copié, mais pointe au même endroit
    len int
    cap int
}
```

Tu copies l'étiquette, pas le colis.

```
mesPrix  ──┐
           ├──> [ 100 | 200 | 300 ]   un seul tableau en mémoire
remises  ──┘
```

Après `AppliquerRemise(mesPrix, 10)`, les deux noms voient `[90 180 270]`.

Comportement identique pour les **maps**, les **channels** et bien sûr les
**pointeurs**. Comportement différent pour les **tableaux** (`[3]float64`), les
**structs sans pointeur** et les types scalaires : eux sont vraiment recopiés.

> La règle à retenir : *en Go, « passage par valeur » ne veut pas dire « copie
> profonde ». Demande-toi toujours si la valeur copiée contient un pointeur.*

## 4. Le bon exemple

Deux façons honnêtes d'écrire cette fonction. Elles sont **toutes les deux
valides** — elles ne promettent simplement pas la même chose.

### Version A — sans effet de bord (elle rend une nouvelle donnée)

```go
// AppliquerRemise retourne une nouvelle liste de prix remisés.
// Le slice reçu n'est pas modifié.
func AppliquerRemise(prix []float64, pourcentage float64) []float64 {
    remises := make([]float64, len(prix))
    for i, p := range prix {
        remises[i] = p * (1 - pourcentage/100)
    }
    return remises
}
```

### Version B — avec effet de bord, mais assumé

```go
// AppliquerRemiseSurPlace modifie le slice reçu.
func AppliquerRemiseSurPlace(prix []float64, pourcentage float64) {
    for i := range prix {
        prix[i] *= 1 - pourcentage/100
    }
}
```

Remarque le détail qui fait tout : **la version B ne retourne rien.** Impossible
de se tromper. Un appelant qui écrit `x := AppliquerRemiseSurPlace(...)` ne
compile pas. Le nom (`SurPlace`) et la signature (`aucun retour`) disent la même
chose que le corps.

C'est le principe général : **la signature doit rendre l'erreur impossible, pas
seulement improbable.**

## 5. Le mauvais exemple, et pourquoi il fait mal

```go
func AppliquerRemise(prix []float64, pourcentage float64) []float64 {
    for i, p := range prix {
        prix[i] = p * (1 - pourcentage/100)
    }
    return prix   // ← le mensonge est ici
}
```

Le `return prix` fait croire à une création. Il n'y en a pas.

### Ce que ça casse, concrètement

```go
prixCatalogue := chargerPrix()

prixSoldes  := AppliquerRemise(prixCatalogue, 20)   // soldes
prixVIP     := AppliquerRemise(prixCatalogue, 30)   // remise VIP

afficherCatalogue(prixCatalogue)  // affiche -44 % : les remises se sont cumulées
```

Le catalogue affiche `100 → 80 → 56`. Personne n'a écrit de bug. Chaque ligne est
raisonnable. Le bug est né de la **composition** de deux appels honnêtes à une
fonction malhonnête.

### Pourquoi c'est grave au-delà du bug

1. **Le bug est non local.** Le symptôme apparaît dans `afficherCatalogue`, très
   loin de la cause. Tu débuggeras au mauvais endroit.
2. **Il dépend de l'ordre des appels.** Inverse deux lignes, le résultat change.
   Ce sont les bugs les plus coûteux à reproduire.
3. **Il empêche le parallélisme.** Deux goroutines appelant cette fonction sur le
   même slice se corrompent mutuellement, sans que le mot « concurrence »
   n'apparaisse nulle part dans le code.
4. **Il est contagieux.** Toute fonction qui appelle celle-ci hérite de son effet
   de bord, sans le déclarer. L'opacité remonte la pile d'appels.

## 6. Le lien avec la production

Un effet de bord caché sur un slice fait un affichage faux. Le **même
raisonnement**, appliqué à une opération métier, fait un double débit.

```
POST /transfert  →  débiter(compte, 100)   ← effet de bord sur le monde réel
```

`débiter` modifie un état extérieur et **durable**. Si l'appelant ne sait pas
combien de fois cet effet s'est produit — timeout, retry, redélivrance
RabbitMQ — l'argent bouge deux fois.

C'est le même défaut de conception à deux échelles :

| | Slice | Compte bancaire |
|---|---|---|
| Effet de bord | mutation du tableau | débit persistant |
| Déclenché deux fois | remises cumulées | double débit |
| Symptôme | prix faux | client furieux |
| Cause | l'appelant ignore l'effet | l'appelant ignore l'effet |

La question qui protège dans les deux cas est la même : **« si cette fonction est
appelée deux fois, que se passe-t-il ? »**

Une fonction qu'on peut appeler deux fois sans changer le résultat est dite
**idempotente**. Retiens le mot, on y consacrera une leçon entière au niveau 5.

## 7. Ce qu'il faut retenir

1. Un effet de bord est légitime ; un effet de bord **caché** ne l'est pas.
2. La signature d'une fonction est un contrat. Le corps doit l'honorer.
3. En Go, « passage par valeur » ≠ copie profonde. Slices, maps, channels,
   pointeurs partagent leur contenu.
4. Le bon design rend l'erreur **impossible à écrire**, pas seulement documentée.
5. « Que se passe-t-il si on l'appelle deux fois ? » est une question de
   conception, pas une question d'exploitation.

## 8. Approfondissement : qui fait respecter la règle ?

Retirer le `return` de la version B ne rend pas la fonction plus fiable — son
corps est identique. Ce qui change, c'est **le moment où l'erreur est détectée**.

| Version | Détection de l'erreur | Coût |
|---|---|---|
| Retourne le slice | en production, sur un prix faux — ou jamais | incident, astreinte |
| Ne retourne rien | à la compilation, en 200 ms | zéro |

Même bug, pas le même prix.

Une règle de conception est toujours portée par un **garde-fou**, et tous n'ont
pas la même force :

| Garde-fou | Force | Ignoré par… |
|---|---|---|
| Commentaire / documentation | ⚪ très faible | tout le monde, tout le temps |
| Nom de la fonction | ⚪ faible | quelqu'un de pressé |
| Revue de code | 🟡 moyenne | un relecteur fatigué, un vendredi |
| Test | 🟠 bonne | si quelqu'un l'écrit |
| **Compilateur / système de types** | 🔴 **absolue** | **personne** |

> **Réflexe d'architecte : quand une règle compte, fais-la descendre le plus bas
> possible dans ce tableau.**

Le même raisonnement, à d'autres échelles, décidera plus tard :

- pourquoi un package s'appelle `internal/` au lieu de porter un commentaire
  « ne pas importer ailleurs » ;
- pourquoi on pose une contrainte `UNIQUE` en base plutôt qu'un `SELECT` avant
  l'`INSERT` ;
- pourquoi on sépare deux modules par une interface plutôt que par une
  convention d'équipe.

### Une bonne contrainte est chirurgicale

```go
AppliquerRemiseSurPlace(prix, 20)              // ✅ compile — usage correct
nouveaux := AppliquerRemiseSurPlace(prix, 20)  // ❌ ne compile pas — lecture fausse
```

La contrainte n'interdit pas d'utiliser la fonction : elle interdit de **se
tromper sur ce qu'elle fait**. Une bonne contrainte de conception ne réduit pas
ce que tu peux faire, elle réduit ce que tu peux mal comprendre. Une contrainte
qui gêne les usages légitimes sera contournée par l'équipe.

## 9. Ce que copie vraiment une copie

Un struct passé par valeur est bien copié — mais **chaque champ ne copie pas la
même chose**.

| Type du champ | Ce que contient le champ | Taille | Partagé après copie ? |
|---|---|---|---|
| `string` | `{ptr, len}`, mais **immuable** | 2 mots | inoffensif |
| `[]T` | `{ptr, len, cap}` — un *descripteur* | 3 mots | ⚠️ le tableau, oui |
| `map[K]V` | **un simple pointeur** vers la table de hachage | 1 mot | ⚠️ oui |
| `chan T` | un simple pointeur | 1 mot | ⚠️ oui |
| `[N]T`, struct sans pointeur, `int`… | la donnée elle-même | — | non |

Une map n'a pas de descripteur : c'est *déjà* un pointeur. Copier le struct copie
ce pointeur, donc les deux valeurs désignent la même table.

### La règle qui prédit tout

> **Assigner un champ ne touche que la copie.
> Écrire *à travers* un champ atteint ce qui est partagé.**

```go
c.Nom = "..."                    // assigne le champ  → copie seule
c.Tags = append(c.Tags, "...")   // assigne le champ  → copie seule
c.Limites["max"] = 100           // écrit À TRAVERS   → partagé ⚠️
```

Le test tient dans un coup d'œil à gauche du `=` :

- `c.Champ = ...` → tu **remplaces** un champ de la copie. Inoffensif.
- `c.Champ[...] = ...`, `*c.Champ = ...`, `c.Champ.Sous = ...` → tu **traverses**
  le champ pour écrire ailleurs. Cet « ailleurs » n'appartient pas à la copie.

Noter que cette règle ne parle pas de capacité : elle est vraie quelle que soit
la façon dont le slice a été construit.

### La mutation invisible

Le piège le plus dangereux du slice n'est pas la mutation visible, c'est
l'inverse. Avec `make([]string, 1, 2)` :

```
original.Tags   : [prod]            len: 1  cap: 2
copie.Tags      : [prod normalise]  len: 2  cap: 2
même tableau ?  : true
original.Tags[:2] : [prod normalise]   ← la donnée est bien là
```

`append` a écrit `"normalise"` dans une case que `original` **possède mais ne
regarde pas** : sa longueur vaut 1. La mutation a eu lieu, elle est simplement
hors de vue — jusqu'au jour où un `append` ultérieur sur `original` réutilise
cette case et écrase la donnée que `copie` croyait à elle.

Un bug visible se voit. Celui-là dort dans une case mémoire.

### Pourquoi ce bug ne se reproduit jamais en local

Le point le plus important de cette leçon :

> **La capacité ne fait pas partie des données.**

```go
a := []string{"prod"}                       // len 1, cap 1  → pas de bug
b := make([]string, 1, 2); b[0] = "prod"    // len 1, cap 2  → bug
```

Les deux affichent `[prod]`. Le log affiche `[prod]`. Le JSON contient
`["prod"]`. Le dump SQL contient `prod`. **Ils sont indiscernables dans toute
donnée observable**, et pourtant l'un déclenche le bug et l'autre non.

En production, un slice arrive d'un décodage JSON, d'un driver SQL, d'une
croissance progressive par `append` : sa capacité est un accident de son
histoire. En local, on l'écrit en littéral — `cap == len` — et le bug ne sort
jamais. C'est le profil exact du bug « ça marche en recette, ça casse en prod,
on n'arrive pas à reproduire ».

Conséquence : **cette classe de bug ne se détecte pas, elle se prévient.**
Attendre de l'observabilité qu'elle la révèle est une impasse.

### Les deux remèdes

```go
// 1. Copier — je ne partage plus rien
c.Tags = append(slices.Clone(c.Tags), "normalise")

// 2. Brider la capacité — full slice expression, cap = len
tags := original.Tags[:len(original.Tags):len(original.Tags)]
```

Le second force `cap == len` : le prochain `append` **est obligé** de réallouer.
Une règle d'équipe (« attention à ne pas partager ») devient une garantie
mécanique. C'est la section 8 appliquée : on fait descendre la règle vers le
garde-fou le plus fort disponible.

## 10. Le réflexe à installer

Devant n'importe quelle fonction, avant de lire son corps :

> **Qui possède les données qu'elle reçoit ? Qui a le droit de les modifier ?
> Et ce droit est-il visible dans la signature ?**
