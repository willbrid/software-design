# Leçon 1.2 — Responsabilités : une seule raison de changer

## L'essentiel en deux minutes

**Le problème, en une phrase.** Un même bout de code obéit à plusieurs
personnes de l'entreprise, et chaque demande de l'une risque de casser ce
qu'attend l'autre.

**L'image.** Dans un restaurant, le chef décide des recettes, le gérant des
prix, le service des horaires. Si une seule fiche plastifiée mélange les
trois, chaque changement de prix oblige à réimprimer la recette — et un jour
quelqu'un efface une ligne de recette en corrigeant un prix. Une
responsabilité, c'est **une personne (ou une équipe) qui peut exiger un
changement**.

**Le code, en une quarantaine de lignes.**

```go
// Package e12 is the two-minute version of lesson 1.2.
package e12

import "fmt"

// Line is one line of an invoice.
type Line struct {
    Price, Qty int64
}

// InvoiceText mixes three decisions: how to add up lines (sales), the VAT
// rate (accounting) and the wording (marketing). Three people can ask to
// change it.
func InvoiceText(lines []Line) string {
    var total int64
    for _, l := range lines {
        total += l.Price * l.Qty
    }
    vat := total * 1925 / 10_000
    return fmt.Sprintf("TOTAL: %d XAF (VAT %d)", total+vat, vat)
}

// Subtotal belongs to sales.
func Subtotal(lines []Line) int64 {
    var total int64
    for _, l := range lines {
        total += l.Price * l.Qty
    }
    return total
}

// VAT belongs to accounting: 19.25 %.
func VAT(subtotal int64) int64 { return subtotal * 1925 / 10_000 }

// Render belongs to marketing.
func Render(subtotal, vat int64) string {
    return fmt.Sprintf("TOTAL: %d XAF (VAT %d)", subtotal+vat, vat)
}
```

`InvoiceText` est courte et juste. Mais trois services peuvent demander de la
modifier : les ventes (le calcul du total), la comptabilité (le taux de TVA),
le marketing (le libellé). Après découpage, quand le taux de TVA change, on
ouvre `VAT` et rien d'autre, et le test de la TVA ne lit pas de texte.

**Les règles à retenir.**

1. Une responsabilité se reconnaît à **qui** demande le changement : un
   service, une équipe, un régulateur. Si tu ne sais pas le nommer, tu ne
   connais pas encore la frontière.
2. Découper par **étapes** (lire, valider, enregistrer) n'est pas découper
   par **raison de changer**. Seule la seconde découpe protège.
3. Le test décisif : *si cette règle change demain, combien de fichiers
   dois-je ouvrir ?*
4. Orchestrer — appeler les autres dans le bon ordre — est une
   responsabilité légitime, pas un défaut.
5. Ne sépare pas ce qui change **toujours ensemble** : ce serait payer deux
   fichiers à chaque modification, pour rien (leçon 1.3).

## 1. Le concept, simplement

La leçon 1.1 posait la question *« qui possède les données ? »*. Celle-ci pose la
question suivante : *« qui possède les décisions ? »*

### Définition

> Un module — fonction, type, package, service — a **une seule responsabilité**
> quand il n'existe **qu'un seul demandeur** capable d'exiger sa modification.

La formule classique est de Robert C. Martin : *« une classe ne doit avoir
qu'une seule raison de changer »*. Elle est juste, et elle est presque
inutilisable telle quelle, parce qu'une « raison » n'est pas observable.

Martin l'a d'ailleurs reformulée lui-même, et la seconde version est la bonne :
*« un module ne doit être responsable que devant un seul acteur »*. L'acteur,
c'est le service comptabilité, l'équipe mobile, le DBA, le législateur, le
marketing. Des gens, pas des concepts.

Ce déplacement change tout : **un acteur, ça se nomme**. On peut mettre un
service, une équipe, parfois une personne en face de chaque bloc de code. Si on
n'y arrive pas, ce n'est pas que la question est mal posée — c'est que le code
n'a pas de frontière à cet endroit.

### Pourquoi la formule est piégeuse

Deux malentendus tenaces, qu'il faut évacuer tout de suite.

**« Une responsabilité » ne veut pas dire « une seule chose ».** Une fonction qui
ouvre une transaction, écrit trois tables et commit fait beaucoup de choses et
n'a qu'une raison de changer : le schéma. Elle est bien conçue.

**La responsabilité n'est pas une propriété du code.** C'est une propriété du
couple *(code, organisation qui le fait évoluer)*. Le même fichier est bien
découpé dans une entreprise où la fiscalité et le marketing sont deux
directions, et mal découpé dans une startup de trois personnes où c'est le même
développeur qui décide des deux. C'est pour cette raison qu'**aucune règle
syntaxique ne peut mesurer une responsabilité** : ni le nombre de lignes, ni le
nombre de méthodes, ni la complexité cyclomatique.

### Les quatre détecteurs

Du plus faible au plus fiable.

| # | Détecteur | Question | Valeur |
|---|---|---|---|
| 1 | **Le « et »** | peux-tu décrire ce que ça fait sans dire « et » ? | ⚪ heuristique de nommage — `Traiter` cache exactement ce que `SauverEtNotifier` avoue |
| 2 | **Les demandeurs** | pour chaque bloc, qui dans l'entreprise peut exiger qu'il change ? | 🟡 solide, mais demande de connaître l'organisation |
| 3 | **L'historique** | `git log` : quelles lignes changent toujours ensemble ? | 🟠 le seul détecteur **empirique** — il mesure au lieu de supposer |
| 4 | **Le test** | pour tester cette règle, de quoi dois-tu disposer ? | 🔴 impitoyable : s'il faut une base et un SMTP pour tester un taux de TVA, la règle n'est pas seule |

Le détecteur 3 mérite qu'on s'y arrête : il se lit dans le dépôt, sans débat
d'architecture. Des lignes qui changent toujours dans le même commit
**appartiennent ensemble**, même si elles sont dans deux fichiers. Des lignes qui
ne changent jamais en même temps devraient être séparées, même si elles sont
dans la même fonction. La découpe correcte est déjà écrite dans ton historique ;
il suffit de la lire.

Le détecteur 4 est celui qu'on rencontrera partout dans la suite du cours : la
difficulté à tester n'est pas un problème de tests, c'est un **révélateur de
conception**. On y consacrera la leçon 1.6.

## 2. L'intuition

Imagine une fonction qui a trois patrons.

Le premier est l'État : il change le taux de TVA, et il ne négocie pas. Le
deuxième est le marketing : il change le texte de l'email de confirmation, tous
les quinze jours. Le troisième est le DBA : il renomme une colonne pendant une
migration.

Les trois ont raison. Les trois ont le droit. Et les trois éditent le même
fichier.

> Deux fonctions dans le même fichier, ce n'est pas un problème. Deux raisons de
> changer dans la même fonction, c'en est un — parce que la première équipe qui
> y touche décide du sort de la seconde.

Le coût n'est pas esthétique. Il est mesurable : conflits de merge, tests qui
échouent pour une raison sans rapport avec le changement, déploiements couplés,
et surtout **un changement à faible risque qui emprunte le chemin d'un
changement à haut risque**.

## 3. Le mécanisme — découper par étapes n'est pas découper par responsabilité

C'est le point le plus important de la leçon, et celui que presque tout le monde
rate.

En 1972, David Parnas écrit *On the Criteria To Be Used in Decomposing Systems
into Modules*. Sa thèse tient en une phrase : on ne découpe pas un système selon
les **étapes de son traitement**, mais selon les **décisions susceptibles de
changer**.

La découpe par étapes est celle qui vient naturellement :

```
décoder  →  valider  →  calculer  →  enregistrer  →  notifier
```

Elle a l'air propre. Elle peut même être la bonne. Mais elle ne répond à aucune
question de conception, parce qu'elle décrit **le flot d'exécution**, pas les
axes de variation. Un découpage controller / service / repository est du même
ordre : c'est un découpage par étape technique, et il est parfaitement
compatible avec le fait d'avoir six décideurs dans chaque couche.

Le test qui départage les deux découpes tient en une question :

> **Si telle règle change demain, combien de modules dois-je ouvrir ?**

- Un seul → la découpe suit les axes de changement. Elle est bonne.
- Trois → tu as découpé selon le flot. Chaque changement traverse tes couches de
  part en part, et tes frontières te coûtent sans rien te rendre.

C'est la différence entre une frontière **verticale** (par sujet : la fiscalité,
la notification) et une frontière **horizontale** (par étape : la validation, la
persistance). Les deux existent, les deux sont utiles, mais **seule la verticale
répond à la question de la responsabilité**.

## 4. Le bon exemple

Un endpoint qui enregistre une commande. Cinq packages, cinq décideurs, une
frontière par décideur.

### Le calcul, seul

```go
// Package pricing computes an amount to pay.
//
// Reason to change: taxation. Only one, and it does not come from us.
// The package imports nothing: no database, no HTTP, no logger. That is what makes it
// testable in 200 microseconds and replayable over ten years of history.
package pricing

import "errors"

type Cents int64

type Line struct {
    UnitPrice Cents
    Qty       int
}

// Request holds what the computation needs, and nothing else.
type Request struct {
    Lines   []Line
    Country string
}

var ErrUnknownCountry = errors.New("pricing: unknown country")

var vatRate = map[string]Cents{"CM": 1925, "FR": 2000}

func Compute(d Request) (Cents, error) {
    rate, ok := vatRate[d.Country]
    if !ok {
        return 0, ErrUnknownCountry
    }

    var net Cents
    for _, l := range d.Lines {
        net += l.UnitPrice * Cents(l.Qty)
    }

    return net + net*rate/10000, nil
}
```

Ce package n'importe rien d'autre que `errors`. Pas de base, pas de HTTP, pas de
journal. Conséquence directe, et c'est le détecteur 4 en action :

```go
package pricing_test

import (
    "testing"

    "example/orders/pricing"
)

// No database, no SMTP server, no context: the tax rule is tested
// alone because it lives alone.
func TestComputeVATCameroon(t *testing.T) {
    got, err := pricing.Compute(pricing.Request{
        Lines:   []pricing.Line{{UnitPrice: 50_000, Qty: 12}},
        Country: "CM",
    })
    if err != nil {
        t.Fatal(err)
    }
    if want := pricing.Cents(715_500); got != want {
        t.Fatalf("total = %d; want %d", got, want)
    }
}
```

### Le métier, seul

```go
// Package order holds the business definition of an order.
//
// Reason to change: what the company accepts as a valid order.
package order

import "errors"

type Line struct {
    UnitPrice int64
    Qty       int
}

type Order struct {
    Client  string
    Email   string
    Country string
    Lines   []Line
}

var (
    ErrEmpty    = errors.New("order: no line")
    ErrQuantity = errors.New("order: invalid quantity")
)

func (c Order) Approve() error {
    if len(c.Lines) == 0 {
        return ErrEmpty
    }
    for _, l := range c.Lines {
        if l.Qty <= 0 {
            return ErrQuantity
        }
    }
    return nil
}
```

`Approve` répond à une seule question — *qu'est-ce qu'une commande acceptable ?* —
et son demandeur est le métier. Noter qu'elle ne connaît **pas** le taux de TVA :
la validité d'une commande et son prix sont deux décisions différentes, prises
par deux acteurs différents, à deux rythmes différents.

### La persistance et la notification

```go
// Package orderstore persists orders.
//
// Reason to change: the database schema.
package orderstore

import (
    "context"
    "database/sql"

    "example/orders/order"
)

type SQL struct{ DB *sql.DB }

func (s *SQL) Save(ctx context.Context, c order.Order, total int64) (int64, error) {
    var id int64
    err := s.DB.QueryRowContext(ctx,
        "INSERT INTO orders (client, country, total) VALUES ($1, $2, $3) RETURNING id",
        c.Client, c.Country, total,
    ).Scan(&id)
    return id, err
}
```

```go
// Package notif notifies the client.
//
// Reason to change: the sending provider, or the wording. It is the module
// that changes most often and whose failure matters least: it
// so it knows no business type, it declares itself what it needs.
package notif

import (
    "context"
    "fmt"
)

type Confirmation struct {
    Recipient  string
    Client     string
    TotalCents int64
}

type Sender interface {
    Send(ctx context.Context, dest, subject, body string) error
}

type Mailer struct{ Exp Sender }

func (e *Mailer) Confirm(ctx context.Context, c Confirmation) error {
    body := fmt.Sprintf("<h1>Thank you %s</h1><p>Total: %d FCFA</p>",
        c.Client, c.TotalCents/100)
    return e.Exp.Send(ctx, c.Recipient, "Your order", body)
}
```

Regarde la différence de traitement entre les deux, elle est délibérée.

`orderstore` accepte le type métier `order.Order` : persister le domaine est
son métier, la dépendance est légitime et sans coût.

`notif` **refuse** de le connaître et déclare sa propre `Confirmation`. Pourquoi
ce traitement de faveur ? Parce que c'est le module qui change le plus souvent
(wording, fournisseur d'envoi, canal) et celui dont l'échec compte le moins. On
paie une traduction là où la volatilité est la plus forte, et nulle part
ailleurs.

> **Toutes les frontières ne se paient pas le même prix. On met le découplage là
> où ça bouge, pas partout.**

### L'orchestrateur

```go
// Package api exposes orders over HTTP.
//
// Reason to change: the HTTP contract and the order of steps. The handler calls
// a lot and decides nothing: it knows neither the VAT rate, nor the schema of
// the database, nor the text of the email.
package api

import (
    "context"
    "encoding/json"
    "log/slog"
    "net/http"

    "example/orders/notif"
    "example/orders/order"
    "example/orders/pricing"
)

// The interfaces are declared here, on the consumer side: the handler says what
// it needs, the implementations conform to it without knowing.
type Saver interface {
    Save(ctx context.Context, c order.Order, total int64) (int64, error)
}

type Confirmer interface {
    Confirm(ctx context.Context, c notif.Confirmation) error
}

type Handler struct {
    Store Saver
    Notif Confirmer
    Log   *slog.Logger
}

func (h *Handler) PostOrder(w http.ResponseWriter, r *http.Request) {
    var c order.Order
    if err := json.NewDecoder(r.Body).Decode(&c); err != nil {
        http.Error(w, "invalid json", http.StatusBadRequest)
        return
    }

    if err := c.Approve(); err != nil {
        http.Error(w, err.Error(), http.StatusBadRequest)
        return
    }

    total, err := pricing.Compute(request(c))
    if err != nil {
        http.Error(w, err.Error(), http.StatusBadRequest)
        return
    }

    id, err := h.Store.Save(r.Context(), c, int64(total))
    if err != nil {
        h.Log.Error("saving", "err", err)
        http.Error(w, "internal error", http.StatusInternalServerError)
        return
    }

    // The notification is not a condition of the order's success:
    // its failure is logged, it does not reach the client.
    if err := h.Notif.Confirm(r.Context(), notif.Confirmation{
        Recipient:  c.Email,
        Client:     c.Client,
        TotalCents: int64(total),
    }); err != nil {
        h.Log.Error("notification", "order", id, "err", err)
    }

    w.WriteHeader(http.StatusCreated)
    _ = json.NewEncoder(w).Encode(map[string]any{"id": id, "total": total})
}

// request translates the business order into the shape the computation expects.
// This translation IS the boundary: pricing does not know order.
func request(c order.Order) pricing.Request {
    lines := make([]pricing.Line, 0, len(c.Lines))
    for _, l := range c.Lines {
        lines = append(lines, pricing.Line{
            UnitPrice: pricing.Cents(l.UnitPrice),
            Qty:       l.Qty,
        })
    }
    return pricing.Request{Lines: lines, Country: c.Country}
}
```

Ce handler appelle quatre modules. Il n'a pourtant **qu'une responsabilité**,
parce qu'il ne décide rien : il ignore le taux de TVA, le nom des colonnes et le
texte de l'email. Sa seule raison de changer est le contrat HTTP et l'ordre des
étapes.

> **Le compte ne se fait pas en appels, il se fait en décisions.** Un module qui
> appelle beaucoup sans rien décider a une seule responsabilité. Un module qui
> décide peu, mais décide pour deux patrons, en a deux.

Deux détails du handler valent d'être relevés.

Les interfaces `Saver` et `Confirmer` sont déclarées **chez le
consommateur**, pas chez l'implémentation. C'est l'idiome Go, et c'est aussi ce
qui permet à `orderstore` d'ignorer complètement l'existence de `api`.

L'échec de la notification est **journalisé, pas propagé**. C'est l'exercice 1.1
/ 5 appliqué : un effet irréversible et secondaire ne doit jamais être une
condition de succès d'un effet principal déjà validé. Une panne SMTP ne doit pas
transformer une commande enregistrée en erreur 500 — et donc en rejeu du client.

### Ce que la découpe a coûté

Une correction honnête chiffre ce qu'elle facture.

| Coût | Réalité |
|---|---|
| Cinq packages au lieu d'un | plus de fichiers à ouvrir pour suivre un appel |
| Une traduction `order → pricing.Request` | ~10 lignes, et une allocation par requête |
| Deux interfaces | une indirection de plus à la lecture |
| Un type `Confirmation` qui duplique trois champs | duplication assumée, pas accidentelle |

Ce qu'on achète en échange : la règle fiscale se teste en 200 µs sans
infrastructure, le marketing modifie son texte sans traverser le code du
paiement, et une panne SMTP ne crée plus de doubles commandes. Le compromis est
favorable **ici**. Il ne l'est pas toujours — voir la section 9.

## 5. Le mauvais exemple, et pourquoi il fait mal

La même fonctionnalité, écrite comme elle l'est presque toujours la première
fois.

```go
package before

import (
    "database/sql"
    "encoding/json"
    "fmt"
    "net/http"
)

type Line struct {
    UnitPrice int64
    Qty       int
}

type Order struct {
    Client string
    Email  string
    Lines  []Line
}

type Sender interface {
    Send(dest, subject, body string) error
}

type Service struct {
    db   *sql.DB
    smtp Sender
}

// HandleOrder: six deciders in a single function.
func (s *Service) HandleOrder(w http.ResponseWriter, r *http.Request) {
    var c Order
    if err := json.NewDecoder(r.Body).Decode(&c); err != nil {
        http.Error(w, "invalid json", http.StatusBadRequest)
        return
    }

    if len(c.Lines) == 0 {
        http.Error(w, "empty order", http.StatusBadRequest)
        return
    }

    var net int64
    for _, l := range c.Lines {
        net += l.UnitPrice * int64(l.Qty)
    }
    gross := net + net*1925/10000 // Cameroon VAT

    if _, err := s.db.Exec(
        "INSERT INTO orders (client, total) VALUES ($1, $2)",
        c.Client, gross,
    ); err != nil {
        http.Error(w, "internal error", http.StatusInternalServerError)
        return
    }

    body := fmt.Sprintf("<h1>Thank you %s</h1><p>Total: %d FCFA</p>", c.Client, gross/100)
    if err := s.smtp.Send(c.Email, "Your order", body); err != nil {
        http.Error(w, "internal error", http.StatusInternalServerError)
        return // the order is saved, the client gets a 500
    }

    w.WriteHeader(http.StatusCreated)
}
```

Rien dans ce code n'est stupide. Chaque ligne est raisonnable. C'est justement
ce qui le rend représentatif.

### Les six décideurs

| Bloc | Décision prise | Qui peut exiger le changement | Rythme |
|---|---|---|---|
| `json.Decode` | la forme du payload | l'équipe mobile | à chaque version de l'app |
| `len(c.Lines) == 0` | ce qu'est une commande valide | le métier | souvent |
| `net*1925/10000` | le taux et l'assiette | **l'État** | rare, daté, non négociable |
| `INSERT INTO` | le schéma | le DBA | migrations |
| `<h1>Merci %s</h1>` | le wording et la marque | le marketing | toutes les semaines |
| `http.StatusBadRequest` | le contrat d'API | l'équipe API | versioning |

Six décideurs. Six calendriers. Six niveaux de risque. **Un seul fichier, un
seul test, un seul déploiement, un seul rayon d'explosion.**

### Ce que ça casse, concrètement

1. **Le changement à faible risque emprunte le chemin du changement à haut
   risque.** Le jour où le taux de TVA change, tu rouvres une fonction qui envoie
   des emails. Le jour où le marketing change un mot, tu redéployes le moteur de
   calcul.
2. **La règle fiscale est intestable.** Pour vérifier que 1 925 est bien
   appliqué, il faut un `*sql.DB`, un faux serveur SMTP et un `http.Request`. En
   pratique : personne n'écrit ce test, et le taux le plus critique de
   l'application n'est couvert par rien.
3. **L'échec du secondaire tue le principal.** Le `return` après `smtp.Send`
   renvoie 500 alors que la commande **est enregistrée**. Le client réessaie. Tu
   viens de recréer l'exercice 1.1 / 5 — un effet cosmétique qui déclenche le
   rejeu d'un effet durable.
4. **Deux équipes se marchent dessus.** Le marketing et la comptabilité
   produisent des conflits de merge sur le même fichier, pour des changements qui
   n'ont rien à voir l'un avec l'autre.

### Le paradoxe : fusionner les responsabilités produit de la duplication

C'est le point contre-intuitif, et c'est le plus utile à retenir.

Six mois plus tard, on demande un batch de nuit qui recalcule les totaux sans
rien envoyer à personne. Le calcul existe — il est ligne 42 — mais il est
prisonnier d'une fonction qui décode du HTTP et envoie des emails. Impossible de
l'appeler. Alors on le recopie.

Il existe maintenant **deux** endroits où vit le taux de TVA. Le jour où il
change, l'un des deux sera oublié.

> **La duplication ne vient pas d'un manque de discipline. Elle vient de
> l'impossibilité de réutiliser ce qui est fusionné à autre chose.** Une
> responsabilité mal isolée finit toujours copiée.

## 6. Le lien avec la production

Ce n'est pas une préoccupation esthétique. La découpe en responsabilités décide
de quatre choses purement opérationnelles.

| Propriété d'exploitation | Ce que la découpe détermine |
|---|---|
| **Rayon d'explosion** | ce qu'un changement peut casser d'autre que lui-même |
| **Granularité de rollback** | tu ne peux pas annuler le wording sans annuler le calcul s'ils partent dans le même binaire |
| **Localisation du diagnostic** | à 3 h du matin, « quelle responsabilité est en cause ? » doit se répondre en lisant un nom de package, pas 200 lignes |
| **Coût du changement urgent** | un correctif fiscal à appliquer en 48 h ne doit pas exiger de revalider la chaîne d'emails |

Et une asymétrie qu'on oublie toujours : dans le bon découpage, modifier le texte
d'un email relance quand même les tests du calcul fiscal — ça ne coûte rien, ces
tests sont instantanés. L'inverse coûte : pour livrer un correctif fiscal urgent,
il faut prouver que les emails partent encore.

> Une bonne découpe ne supprime pas les dépendances. Elle les **oriente** : du
> volatil vers le stable, jamais l'inverse.

Retiens la formulation opérationnelle, celle qui parle à quelqu'un qui tient une
astreinte :

> **La découpe en responsabilités détermine ce que tu peux déployer, annuler et
> diagnostiquer séparément. C'est une décision d'exploitation autant que de
> conception.**

## 7. Ce qu'il faut retenir

1. Une responsabilité, c'est **un acteur** — quelqu'un qui peut exiger un
   changement. Ça se nomme.
2. Découper par **étapes** (décoder, valider, sauver) n'est pas découper par
   **raison de changer**. Seule la seconde découpe répond à la question.
3. Le test décisif : *si cette règle change demain, combien de modules dois-je
   ouvrir ?*
4. Le compte se fait en **décisions**, pas en appels. Orchestrer est une
   responsabilité légitime.
5. `git log` sait déjà où sont les frontières : les lignes qui changent toujours
   ensemble appartiennent ensemble.
6. La difficulté à tester une règle isolément est le symptôme le plus fiable
   qu'elle ne l'est pas.
7. Fusionner des responsabilités **produit** de la duplication : ce qui n'est pas
   réutilisable est recopié.

## 8. Approfondissement : qui fait respecter une frontière ?

Même question qu'en 1.1 § 8 — une règle de conception ne vaut que par le
garde-fou qui la porte. Appliquée aux responsabilités :

| Garde-fou | Mise en œuvre | Force |
|---|---|---|
| Un commentaire « ne pas appeler d'ici » | — | ⚪ nulle |
| Une convention de nommage | `service_tarif.go` | ⚪ faible |
| Une revue de code | quelqu'un remarque l'import | 🟡 moyenne |
| Un test d'architecture | un test qui liste les imports autorisés | 🟠 bonne, si quelqu'un l'écrit |
| **Un package séparé** | le compilateur refuse le cycle d'import | 🔴 **absolue** |
| **L'absence de moyen** | le module ne détient pas la dépendance | ⚫ **non représentable** |

Les deux derniers niveaux méritent une démonstration.

**Le compilateur.** Si `pricing` tentait un jour d'appeler le handler, Go refuse,
et le message est sans appel :

```
package exemple/orders/api
    imports example/orders/pricing from handler.go
    imports exemple/orders/api from pricing.go: import cycle not allowed
```

Ce n'est pas une convention d'équipe qu'on peut assouplir un vendredi soir :
c'est le compilateur. Le sens de la dépendance est **gravé**.

**L'absence de moyen.** Le niveau ⚫, déjà rencontré à l'exercice 1.1 / 4, dit :

> Un module ne peut pas faire ce dont il ne détient pas le moyen.

`pricing` ne peut pas envoyer d'email. Non parce que c'est interdit, non parce
qu'un test le vérifie — parce qu'il n'a **aucun expéditeur dans sa struct et
aucun import réseau**. La responsabilité n'est pas surveillée, elle est
structurellement impossible à violer.

C'est aussi la vraie raison d'être de l'injection de dépendances, bien avant
toute considération de framework ou de mocks : **ce qu'un module reçoit définit
exactement ce qu'il peut faire.** Une struct de service qui contient une base, un
client HTTP, un cache et un expéditeur d'emails annonce, dans sa seule
déclaration, qu'elle a au moins quatre responsabilités.

Ouvre n'importe quel `type Service struct` de ton code : la liste de ses champs
est la liste de ses patrons.

## 9. Ce que la responsabilité n'est pas

Quatre confusions courantes, dont la dernière est la plus coûteuse.

**Ce n'est pas une taille.** Un parseur de 300 lignes ou une machine à états
peuvent n'avoir qu'une raison de changer. Une fonction de cinq lignes qui lit une
variable d'environnement, formate une date et écrit un log en a trois. Toute
règle de type « pas plus de 20 lignes par fonction » mesure la mauvaise chose.

**Ce n'est pas une action.** « Une fonction doit faire une seule chose » est une
autre règle, plus faible, et souvent fausse : une transaction fait dix choses
indissociables.

**Ce n'est pas une couche technique.** Controller / service / repository est une
découpe par étape. Utile pour d'autres raisons, mais elle n'empêche en rien
d'avoir six décideurs par couche.

**Et le piège inverse : la découpe prématurée.** Deux modules qui changent
*toujours* ensemble ne sont pas deux modules : c'est un module écrit en deux
fichiers. Tu as payé l'indirection, les interfaces et le mapping sans jamais
acheter l'indépendance — et chaque évolution coûte désormais deux ouvertures de
fichier au lieu d'une.

> Coupler deux choses qui varient ensemble est gratuit. **Découpler deux choses
> qui varient ensemble se paie à chaque changement, pour toujours.**

La responsabilité unique a donc un contrepoids, et ce contrepoids s'appelle la
**cohésion** : ce qui change ensemble doit vivre ensemble. Séparer sans mesurer,
c'est fabriquer un autre problème — c'est l'objet de la leçon 1.3.

## 10. Le réflexe à installer

Devant n'importe quel module, avant d'en lire le corps :

> **Si cette règle change demain, quels fichiers dois-je ouvrir ? Et qui, dans
> l'entreprise, signera la demande ?**

Si tu ne sais pas nommer le demandeur, tu ne connais pas encore la frontière. Si
tu en nommes deux, tu l'as trouvée.
