# Leçon 1.4 — Abstraction : quoi cacher, quoi exposer

## L'essentiel en deux minutes

**Le problème, en une phrase.** Décider ce que l'appelant n'a pas besoin de
savoir — et, tout aussi important, ce qu'on n'a **pas le droit** de lui
cacher.

**L'image.** Le tableau de bord d'une voiture. Il cache le moteur :
l'injection, l'allumage, tu n'en sais rien et tu conduis quand même. Mais il
ne cache **jamais** la jauge d'essence ni le voyant d'huile. Une voiture qui
masquerait le niveau d'essence pour « simplifier » ne serait pas plus
abstraite : elle serait piégée. Cacher une limite ou un coût, ce n'est pas
abstraire.

**Le code, en une quarantaine de lignes.**

```go
// Package e14 is the two-minute version of lesson 1.4.
package e14

import (
    "context"
    "database/sql"
    "errors"
    "fmt"
)

// ErrNotFound belongs to the vocabulary of accounts, whatever stores them.
var ErrNotFound = errors.New("account not found")

// Accounts answers one question. It hides where balances live; it does
// not hide that a call can fail or wait, hence ctx and error.
type Accounts interface {
    // Balance returns an error matching ErrNotFound for an unknown account.
    Balance(ctx context.Context, id string) (int64, error)
}

// Memory is one implementation; a SQL one would translate sql.ErrNoRows
// into ErrNotFound the same way.
type Memory map[string]int64

// Balance looks the account up.
func (m Memory) Balance(_ context.Context, id string) (int64, error) {
    b, ok := m[id]
    if !ok {
        return 0, fmt.Errorf("%w: %s", ErrNotFound, id)
    }
    return b, nil
}

// LeakyBalance answers the same question, but its error names the storage:
// to test "not found", every caller must import database/sql.
func LeakyBalance(m map[string]int64, id string) (int64, error) {
    b, ok := m[id]
    if !ok {
        return 0, sql.ErrNoRows
    }
    return b, nil
}
```

`Accounts` cache **où** vivent les soldes : mémoire, base SQL, service
distant. Elle ne cache pas qu'un appel peut échouer ou attendre — d'où le
`context.Context` et l'`error`. Et son erreur « compte inconnu » parle la
langue de l'appelant (`ErrNotFound`), pas celle du stockage. `LeakyBalance`
rend `sql.ErrNoRows` : chaque appelant doit importer `database/sql` pour
tester un cas métier, et changer de stockage casse tous les appelants.

**Les règles à retenir.**

1. Abstraire, c'est **retirer** de l'information. Généraliser, c'est
   **ajouter** des cas. `func Do(x any)` généralise tout et n'abstrait rien.
2. La mesure : combien de fois faut-il aller lire l'implémentation pour
   utiliser l'abstraction ? Si c'est à chaque fois, ce n'est qu'un alias.
3. Les erreurs font partie du vocabulaire. Une erreur qui nomme
   l'implémentation trahit l'abstraction.
4. La latence, les pannes et les limites traversent toutes les
   abstractions : expose-les, puisqu'on ne peut pas les cacher.
5. Une interface recopiée d'une implémentation est un miroir : si la
   deuxième implémentation oblige à la modifier, elle n'abstrayait rien.

Les trois leçons précédentes ont posé des frontières : la propriété des
données, les responsabilités, les coutures. Il reste à décider ce qui **passe**
une frontière et ce qui s'arrête devant.

C'est l'objet de celle-ci. Et la moitié de la leçon porte sur la question
qu'on ne pose jamais : **ce qu'il faut refuser de cacher.**

## 1. Le concept, simplement

### Définition

> **Abstraire, c'est décider ce que l'appelant a le droit de ne pas savoir.**

Formulation équivalente, et plus opérationnelle, parce qu'elle a un dual :
abstraire, c'est aussi décider ce que l'appelant **n'a pas le droit** de
savoir. Une abstraction qui laisse voir n'interdit rien, donc ne garantit
rien, donc n'est qu'une suggestion.

C'est encore Parnas, le même article de 1972 que la leçon 1.2 : *information
hiding*. On s'en est servi là-bas pour décider **où** passent les frontières.
On s'en sert ici pour décider **ce qui les traverse**.

### Abstraction n'est pas généralisation

Les deux mots sont employés l'un pour l'autre, et ce sont deux opérations
opposées.

| | Abstraction | Généralisation |
|---|---|---|
| Ce qu'elle fait | **retire** de l'information | **ajoute** des cas à traiter |
| Ce qu'elle promet | « tu n'as pas besoin de savoir » | « ça marche aussi pour ça » |
| Son excès | on cache ce dont l'appelant a besoin | on traite tout, donc on ne promet rien |

```go
func Transfer(src, dst any) error
```

Voilà une généralisation maximale et une abstraction nulle. Elle accepte tout,
donc elle ne dit rien sur ce qu'elle fait, donc l'appelant doit lire son corps
pour savoir quels couples de types elle traite réellement.

> `any` ne cache rien : il **omet**. Cacher, c'est garantir que l'appelant n'en
> a pas besoin ; omettre, c'est le laisser deviner.

On peut généraliser sans abstraire — c'est `map[string]any` — et abstraire sans
généraliser : `attachment.Ref` est une abstraction parfaite qui ne généralise
rien du tout.

### La mesure : combien de fois faut-il lire derrière ?

Le seul test qui vaille, et il est empirique :

> Combien de fois dois-je lire le code **derrière** l'abstraction pour
> l'utiliser correctement ?

| Réponse | Verdict |
|---|---|
| jamais | étanche |
| une fois, pour comprendre le modèle | normal, et acceptable |
| à chaque usage | ce n'est pas une abstraction, c'est un **alias** |
| et je dois lire le code de l'appelant d'à côté | c'est un piège |

Le troisième cas est le plus fréquent, et il a un symptôme reconnaissable : le
code appelant contient des commentaires qui expliquent le comportement de
l'appelé.

## 2. L'intuition

Un interrupteur.

Ce qu'il cache : la centrale, le réseau, la tension, le câblage, le disjoncteur,
le fait que c'est du 220 volts alternatif à 50 hertz. Tu ne sais rien de tout
ça, et tu allumes la lumière depuis l'âge de trois ans. C'est une abstraction
réussie, et elle est réussie parce que **ce qu'elle cache est vraiment sans
conséquence pour toi.**

Maintenant, ce qu'un interrupteur ne cache pas, et ne doit pas cacher :

- **que ça peut ne pas marcher.** Il y a des coupures, et personne ne prétend
  le contraire.
- **que la lumière met un instant à venir.** Avec une ampoule à économie
  d'énergie, tout le monde l'a remarqué.
- **qu'il y a un ordre.** Le disjoncteur d'abord, l'interrupteur ensuite.
- **qu'il y a une limite.** Une multiprise porte un ampérage écrit dessus.

Ces quatre choses traversent l'abstraction, et c'est très bien : personne n'a
jamais conçu un interrupteur qui prétende que l'électricité est infinie,
instantanée et toujours disponible.

> En logiciel, on conçoit ces interrupteurs-là tous les jours. Une méthode
> `Get(id)` qui ne dit pas qu'elle fait un appel réseau est un interrupteur
> qui prétend que le courant ne coupe jamais.

## 3. Le mécanisme — l'abstraction se dessine par la question

### Le miroir

Voici comment naissent la plupart des interfaces, et pourquoi elles n'abstraient
rien :

1. on écrit une implémentation ;
2. on copie la liste de ses méthodes ;
3. on change le nom du type.

Le résultat a la forme d'une abstraction. Il n'en a aucune propriété, parce
qu'il décrit **une implémentation** au lieu de décrire **un besoin**.

Et il y a un test infaillible pour le reconnaître :

> Si ajouter une seconde implémentation oblige à **modifier l'interface**,
> alors l'interface était un miroir de la première.

Une interface écrite depuis le besoin du consommateur n'a pas ce défaut :
elle ne connaissait déjà aucune implémentation.

### L'arithmétique des méthodes

```go
type Writer interface {
    Write(p []byte) (n int, err error)
}
```

Une méthode, et des milliers d'implémentations : un fichier, une connexion,
un tampon, un compteur, un chiffreur, un compresseur, `/dev/null`.

```go
type S3Storage interface {
    PutObject(...)
    GetObject(...)
    HeadObject(...)
    DeleteObject(...)
    CopyObject(...)
    ListObjectsV2(...)
    PresignGetObject(...)
}
```

Sept méthodes, et une seule implémentation possible : celle qu'on a copiée.

> Le nombre d'implémentations raisonnables d'une interface est inversement
> proportionnel à son nombre de méthodes. Ce n'est pas une loi, c'est de
> l'arithmétique : chaque méthode est une contrainte supplémentaire que tout
> candidat doit satisfaire.

### Pas « trois usages », mais « une question posée deux fois »

On entend souvent qu'il faut trois cas avant d'abstraire. C'est un
garde-fou contre l'abstraction prématurée, et c'est un mauvais critère, parce
qu'il compte des **implémentations** au lieu de compter des **questions**.

Le vrai signal :

> Tu as besoin d'une abstraction quand **la même question est posée depuis deux
> endroits qui n'ont pas besoin de la même réponse**.

Deux modules qui demandent « range-moi ça » sans se soucier d'où : voilà une
abstraction, même s'il n'existe qu'un seul coffre. Deux modules qui appellent
la même fonction pour faire la même chose : voilà une fonction, et il n'y a
rien à abstraire.

## 4. Le bon exemple

Un coffre de pièces jointes. Le consommateur est un module de gestion de
dossiers ; il veut ranger des fichiers et les récupérer. Il ne veut rien savoir
d'autre.

### Le vocabulaire — ce qui a le droit de traverser

```go
// Package attachment holds the vocabulary of attachments: what the caller
// is allowed to know, and nothing more.
//
// Reason to change: what an acceptable attachment is.
//
// This package cannot store. It knows no disk, no network, no database.
// It defines the words we use to talk about it, and the errors one can
// get: these errors are part of the abstraction, not of
// the implementation.
package attachment

import (
    "errors"
    "fmt"
    "sort"
    "strings"
)

// Ref points to a stored attachment. It is opaque: its form is
// the vault's business, and the caller may neither build it, nor
// interpret it, nor split it.
type Ref string

// Digest is the hash of the content, in hexadecimal.
//
// It is exposed on purpose. The caller needs it for a
// reason: it is what makes a put idempotent, so it is what
// lets it retry without creating a duplicate.
type Digest string

// Metadata is what we know of an attachment without opening it.
type Metadata struct {
    Ref       Ref
    Digest    Digest
    Size      int64
    MediaType string
}

var (
    ErrNotFound    = errors.New("attachment: unknown ref")
    ErrTooLarge    = errors.New("attachment: content over the maximum size")
    ErrTypeRefused = errors.New("attachment: media type not allowed")
    ErrLimits      = errors.New("attachment: invalid limits")
)

// Limits is part of the contract, not of configuration.
//
// A vault that refuses files over ten megabytes must be able to
// say so before someone sends it one of two gigabytes. Hiding a limit
// is not an abstraction: it is a trap.
type Limits struct {
    maxSize int64
    types   map[string]struct{}
}

// NewLimits copies the list of types: without this copy, Limits would be
// not a value but an alias of the caller's slice.
func NewLimits(maxSize int64, types ...string) (Limits, error) {
    if maxSize <= 0 {
        return Limits{}, fmt.Errorf("%w: zero maximum size", ErrLimits)
    }
    if len(types) == 0 {
        return Limits{}, fmt.Errorf("%w: no allowed type", ErrLimits)
    }
    m := make(map[string]struct{}, len(types))
    for _, t := range types {
        t = strings.ToLower(strings.TrimSpace(t))
        if t == "" {
            return Limits{}, fmt.Errorf("%w: empty type", ErrLimits)
        }
        m[t] = struct{}{}
    }
    return Limits{maxSize: maxSize, types: m}, nil
}

func (l Limits) MaxSize() int64 { return l.maxSize }

// Types returns a sorted copy: the caller may show it, not modify it.
func (l Limits) Types() []string {
    out := make([]string, 0, len(l.types))
    for t := range l.types {
        out = append(out, t)
    }
    sort.Strings(out)
    return out
}

func (l Limits) Allowed(mediaType string) error {
    if _, ok := l.types[strings.ToLower(strings.TrimSpace(mediaType))]; !ok {
        return fmt.Errorf("%w: %q, allowed: %s",
            ErrTypeRefused, mediaType, strings.Join(l.Types(), ", "))
    }
    return nil
}
```

Trois décisions, et chacune répond à la question « qui a le droit de savoir
quoi ».

**`Ref` est opaque.** C'est une chaîne, mais le contrat dit que l'appelant
n'a le droit ni de la construire, ni de l'interpréter, ni de la découper. Le
coffre peut donc changer sa forme — `sha256-…`, un UUID, une URL — sans que
personne ne casse.

**`Digest` est exposée, et c'est un choix.** Elle ne devrait pas l'être si
on suivait le réflexe « cacher le plus possible » : c'est un détail
d'implémentation du stockage par contenu. Elle est exposée parce que l'appelant
en a un usage précis — c'est elle qui lui garantit qu'un dépôt réessayé ne
crée pas de doublon.

> On n'expose pas ce qui est « utile ». On expose ce dont l'appelant a besoin
> pour **tenir ses propres garanties**. Si tu ne peux pas nommer la garantie,
> n'expose pas.

**Les erreurs sont dans ce paquet, pas dans les implémentations.**
`attachment.ErrNotFound` appartient au vocabulaire, exactement comme
`Ref`. C'est le point le plus souvent manqué de toute cette leçon, et la
section 5 y revient.

### Le contrat, déclaré par le consommateur

```go
// Package folder attaches attachments to a folder.
//
// Reason to change: the attach rules: how many attachments, which ones,
// in which order.
//
// It is the consumer, so it declares the vault's contract. It
// writes the question it asks; the implementations conform to it without
// knowing.
package folder

import (
    "context"
    "errors"
    "fmt"
    "io"

    "example/vault/attachment"
)

type ID string

var (
    ErrEmptyFolder        = errors.New("folder: empty identifier")
    ErrTooManyAttachments = errors.New("folder: maximum number of attachments reached")
)

// Vault is the contract. Three methods, and each has a precise
// reason to exist:
//
//   - Put and Open are the question asked: "store this" and "give it
//     back".
//   - Limits is not the question, it is the admission. It exists so that
//     the caller can refuse before reading two gigabytes, and because
//     a hidden limit is a trap.
//
// What this contract does not say: where it is stored, under which name, with what
// redundancy, in which format. The caller is not allowed to know.
//
// What it does say, and what cannot be hidden:
//
//   - both operations may be slow and cancelable, hence the context;
//   - the stream returned by Open must be closed by the caller;
//   - Put is idempotent on content: two puts of the same content
//     return the same Ref and take only one place.
type Vault interface {
    Put(ctx context.Context, content io.Reader, mediaType string) (attachment.Metadata, error)
    Open(ctx context.Context, ref attachment.Ref) (io.ReadCloser, error)
    Limits() attachment.Limits
}

// Registry holds the links between a folder and its attachments.
type Registry interface {
    Attach(ctx context.Context, id ID, m attachment.Metadata) error
    Attachments(ctx context.Context, id ID) ([]attachment.Metadata, error)
}

type Service struct {
    Vault        Vault
    Registry     Registry
    MaxPerFolder int
}

// Attach puts the attachment, then links it to the folder.
//
// The order is a decision of this module: put first, attach
// then. If attaching fails, an orphan attachment stays in the vault:
// it is a storage cost, recoverable by a garbage collector. The opposite
// would produce a link to a missing attachment, that is an
// error the user can see. Between the two, we always prefer
// the useless to the inconsistent.
func (s *Service) Attach(ctx context.Context, id ID, content io.Reader, mediaType string) (attachment.Metadata, error) {
    if id == "" {
        return attachment.Metadata{}, ErrEmptyFolder
    }

    // We refuse before reading: that is what Limits in the contract is for.
    if err := s.Vault.Limits().Allowed(mediaType); err != nil {
        return attachment.Metadata{}, err
    }

    existing, err := s.Registry.Attachments(ctx, id)
    if err != nil {
        return attachment.Metadata{}, fmt.Errorf("folder: reading attachments: %w", err)
    }
    if len(existing) >= s.MaxPerFolder {
        return attachment.Metadata{}, fmt.Errorf("%w: %d", ErrTooManyAttachments, s.MaxPerFolder)
    }

    m, err := s.Vault.Put(ctx, content, mediaType)
    if err != nil {
        return attachment.Metadata{}, err
    }

    if err := s.Registry.Attach(ctx, id, m); err != nil {
        return attachment.Metadata{}, fmt.Errorf("folder: attach: %w", err)
    }
    return m, nil
}
```

Lis le commentaire de l'interface. Il est aussi important que les signatures,
et il se divise en deux parties qu'il faut toujours écrire séparément :

- **ce que le contrat ne dit pas** : où c'est stocké, sous quel nom, avec
  quelle redondance, dans quel format ;
- **ce qu'il dit et qui ne se cache pas** : que c'est lent et annulable, que le
  flux doit être fermé, que le dépôt est idempotent sur le contenu.

Et remarque la troisième méthode :

```go
Limits() attachment.Limits
```

Elle n'est pas la question posée — la question, c'est « range ça » et
« rends-le moi ». Elle est **l'aveu**. Elle coûte une méthode de plus, donc
elle réduit le nombre d'implémentations possibles, et elle achète une chose
précise : l'appelant peut refuser avant d'avoir lu deux gigaoctets.

> Cacher une limite n'est pas une abstraction, c'est un piège. Une limite qui
> ne figure pas dans le contrat se découvre en production, sur le plus gros
> fichier que personne n'avait essayé.

### Une implémentation

```go
// Package vaultmem stores attachments in memory.
//
// Reason to change: none. It is the test and
// development implementation, and it keeps the same contract as the others:
// checked by vaulttest.
package vaultmem

import (
    "bytes"
    "context"
    "crypto/sha256"
    "encoding/hex"
    "io"
    "sync"

    "example/vault/attachment"
)

type Vault struct {
    limits attachment.Limits

    mu       sync.RWMutex
    contents map[attachment.Ref][]byte
}

func New(limits attachment.Limits) *Vault {
    return &Vault{limits: limits, contents: map[attachment.Ref][]byte{}}
}

func (c *Vault) Limits() attachment.Limits { return c.limits }

func (c *Vault) Put(ctx context.Context, content io.Reader, mediaType string) (attachment.Metadata, error) {
    if err := ctx.Err(); err != nil {
        return attachment.Metadata{}, err
    }
    if err := c.limits.Allowed(mediaType); err != nil {
        return attachment.Metadata{}, err
    }

    // We read at most MaxSize + 1 bytes. The "+ 1" is what lets us
    // tell "exactly at the limit", which is accepted, from "beyond",
    // which is refused. Without it, we cannot tell the difference.
    raw, err := io.ReadAll(io.LimitReader(content, c.limits.MaxSize()+1))
    if err != nil {
        return attachment.Metadata{}, err
    }
    if int64(len(raw)) > c.limits.MaxSize() {
        return attachment.Metadata{}, attachment.ErrTooLarge
    }

    sum := sha256.Sum256(raw)
    digest := attachment.Digest(hex.EncodeToString(sum[:]))
    ref := attachment.Ref("sha256-" + string(digest))

    c.mu.Lock()
    defer c.mu.Unlock()
    // Idempotence: if the content is already there, we do not rewrite. Two puts
    // of the same content take one place and return the same ref.
    if _, exists := c.contents[ref]; !exists {
        c.contents[ref] = raw
    }

    return attachment.Metadata{
        Ref:       ref,
        Digest:    digest,
        Size:      int64(len(raw)),
        MediaType: mediaType,
    }, nil
}

func (c *Vault) Open(ctx context.Context, ref attachment.Ref) (io.ReadCloser, error) {
    if err := ctx.Err(); err != nil {
        return nil, err
    }

    c.mu.RLock()
    raw, ok := c.contents[ref]
    c.mu.RUnlock()
    if !ok {
        return nil, attachment.ErrNotFound
    }
    return io.NopCloser(bytes.NewReader(raw)), nil
}
```

Un détail à ne pas lire trop vite :

```go
raw, err := io.ReadAll(io.LimitReader(content, c.limits.MaxSize()+1))
```

Le `+1` est ce qui permet de distinguer « exactement à la limite », qui est
accepté, de « au-delà », qui est refusé. Avec `LimitReader(content, MaxSize)`,
on lit `MaxSize` octets dans les deux cas et on ne peut plus faire la
différence : un fichier de deux gigaoctets serait silencieusement **tronqué**
et accepté.

> Une troncature silencieuse est le pire mode de panne possible : l'opération
> réussit, et la donnée est fausse. Préfère toujours un refus bruyant.

### Une seconde implémentation, très différente

Le même contrat, sur un système de fichiers. L'intégralité est dans le
dépôt ; voici les deux endroits qui comptent.

Le dépôt atomique :

```go
    // We write to a temporary file, computing the digest on the
    // way, then we rename. The rename is atomic: no reader can
    // see a half-written file, and an interrupted put
    // leaves only a temp file to clean up.
    tmp, err := os.CreateTemp(filepath.Join(c.root, "tmp"), "put-*")
    if err != nil {
        return attachment.Metadata{}, fmt.Errorf("vaultdisk: temp file: %w", err)
    }
    defer func() {
        tmp.Close()
        os.Remove(tmp.Name()) // no effect if the rename succeeded
    }()

    sum := sha256.New()
    bound := io.LimitReader(content, c.limits.MaxSize()+1)
    size, err := io.Copy(io.MultiWriter(tmp, sum), bound)
    if err != nil {
        return attachment.Metadata{}, err
    }
    if size > c.limits.MaxSize() {
        return attachment.Metadata{}, attachment.ErrTooLarge
    }
    if err := tmp.Sync(); err != nil {
        return attachment.Metadata{}, fmt.Errorf("vaultdisk: sync: %w", err)
    }
    if err := tmp.Close(); err != nil {
        return attachment.Metadata{}, fmt.Errorf("vaultdisk: close: %w", err)
    }

    digest := attachment.Digest(hex.EncodeToString(sum.Sum(nil)))
    ref := attachment.Ref("sha256-" + string(digest))
    dest := c.path(ref)

    if err := os.MkdirAll(filepath.Dir(dest), 0o750); err != nil {
        return attachment.Metadata{}, fmt.Errorf("vaultdisk: directory: %w", err)
    }
    if err := os.Rename(tmp.Name(), dest); err != nil {
        return attachment.Metadata{}, fmt.Errorf("vaultdisk: rename: %w", err)
    }
```

Le fichier temporaire puis le renommage : aucun lecteur ne peut observer un
fichier à moitié écrit, et un dépôt interrompu ne laisse qu'un temporaire à
nettoyer. C'est l'équivalent, sur un disque, du compare-and-swap de la leçon
1.3.

Et la traduction de l'erreur :

```go
func (c *Vault) Open(ctx context.Context, ref attachment.Ref) (io.ReadCloser, error) {
    if err := ctx.Err(); err != nil {
        return nil, err
    }
    if len(ref) < 12 {
        return nil, attachment.ErrNotFound
    }

    f, err := os.Open(c.path(ref))
    if errors.Is(err, os.ErrNotExist) {
        // Translation required: os.ErrNotExist would name the implementation.
        // If the caller had to test os.ErrNotExist, changing the vault
        // would change its code.
        return nil, attachment.ErrNotFound
    }
    if err != nil {
        return nil, fmt.Errorf("vaultdisk: open: %w", err)
    }
    return f, nil
}
```

Les trois lignes du milieu portent la moitié de la valeur de l'abstraction. Si
cette traduction n'existait pas, l'appelant devrait tester `os.ErrNotExist` —
et le jour où le coffre devient un service distant, son code de gestion
d'erreur serait faux.

> Une abstraction dont les erreurs nomment son implémentation n'en est pas une.
> C'est la fuite la plus fréquente, et la plus facile à boucher : trois lignes
> de traduction à la frontière.

### Le contrat, sous forme exécutable

C'est l'idée la plus utile de cette leçon.

```go
// Package vaulttest is the contract, in executable form.
//
// It tests no implementation in particular: it tests what
// folder.Vault promises. Every implementation must pass it, and it is what
// makes the difference between an interface and an abstraction: an interface
// declares signatures, a contract declares promises, and these
// are checked.
package vaulttest

import (
    "bytes"
    "context"
    "crypto/sha256"
    "encoding/hex"
    "errors"
    "io"
    "strings"
    "testing"

    "example/vault/attachment"
    "example/vault/folder"
)

// Check runs the contract. `fresh` must return an empty vault whose
// limits accept "text/plain" and refuse "application/zip".
func Check(t *testing.T, fresh func(t *testing.T) folder.Vault) {
    t.Helper()

    t.Run("round-trip", func(t *testing.T) { roundTrip(t, fresh(t)) })
    t.Run("put idempotence", func(t *testing.T) { idempotence(t, fresh(t)) })
    t.Run("digest", func(t *testing.T) { digest(t, fresh(t)) })
    t.Run("unknown ref", func(t *testing.T) { unknown(t, fresh(t)) })
    t.Run("refused type", func(t *testing.T) { refusedType(t, fresh(t)) })
    t.Run("size exactly at the limit", func(t *testing.T) { exact(t, fresh(t)) })
    t.Run("size over the limit", func(t *testing.T) { over(t, fresh(t)) })
    t.Run("canceled context", func(t *testing.T) { cancelled(t, fresh(t)) })
}

func put(t *testing.T, c folder.Vault, content string) attachment.Metadata {
    t.Helper()
    m, err := c.Put(context.Background(), strings.NewReader(content), "text/plain")
    if err != nil {
        t.Fatalf("Put: %v", err)
    }
    return m
}

func read(t *testing.T, c folder.Vault, ref attachment.Ref) string {
    t.Helper()
    f, err := c.Open(context.Background(), ref)
    if err != nil {
        t.Fatalf("Open: %v", err)
    }
    defer f.Close()
    raw, err := io.ReadAll(f)
    if err != nil {
        t.Fatalf("read: %v", err)
    }
    return string(raw)
}

func roundTrip(t *testing.T, c folder.Vault) {
    const content = "minutes of 4 October"
    m := put(t, c, content)

    if m.Size != int64(len(content)) {
        t.Errorf("size = %d, want %d", m.Size, len(content))
    }
    if m.MediaType != "text/plain" {
        t.Errorf("type = %q", m.MediaType)
    }
    if got := read(t, c, m.Ref); got != content {
        t.Errorf("returned content = %q, want %q", got, content)
    }
}

// The strongest promise of the contract, and the one that lets the caller
// retry without thinking.
func idempotence(t *testing.T, c folder.Vault) {
    a := put(t, c, "same content")
    b := put(t, c, "same content")

    if a.Ref != b.Ref {
        t.Errorf("two puts of the same content gave two refs: %q and %q",
            a.Ref, b.Ref)
    }
    if a != b {
        t.Errorf("different metadata: %+v vs %+v", a, b)
    }
    if got := read(t, c, a.Ref); got != "same content" {
        t.Errorf("content damaged by the second put: %q", got)
    }
}

func digest(t *testing.T, c folder.Vault) {
    const content = "appendix 3"
    m := put(t, c, content)

    sum := sha256.Sum256([]byte(content))
    if want := attachment.Digest(hex.EncodeToString(sum[:])); m.Digest != want {
        t.Errorf("digest = %q, want %q", m.Digest, want)
    }
    // The ref is opaque, but it must at least be stable and not
    // empty: it is all the contract allows us to check.
    if m.Ref == "" {
        t.Error("empty ref")
    }
}

// The error is part of the abstraction: the caller tests attachment.ErrNotFound,
// never os.ErrNotExist nor sql.ErrNoRows.
func unknown(t *testing.T, c folder.Vault) {
    _, err := c.Open(context.Background(), attachment.Ref("sha256-nothingnothing"))
    if !errors.Is(err, attachment.ErrNotFound) {
        t.Fatalf("err = %v, want attachment.ErrNotFound", err)
    }
}

func refusedType(t *testing.T, c folder.Vault) {
    _, err := c.Put(context.Background(), strings.NewReader("PK"), "application/zip")
    if !errors.Is(err, attachment.ErrTypeRefused) {
        t.Fatalf("err = %v, want attachment.ErrTypeRefused", err)
    }
}

// The limit is inclusive. It is not a detail: "at most ten
// megabytes" and "less than ten megabytes" are two different contracts,
// and the one that is not tested is the one that will be implemented wrong.
func exact(t *testing.T, c folder.Vault) {
    max := c.Limits().MaxSize()
    content := bytes.Repeat([]byte("x"), int(max))

    m, err := c.Put(context.Background(), bytes.NewReader(content), "text/plain")
    if err != nil {
        t.Fatalf("content exactly at the limit must be accepted: %v", err)
    }
    if m.Size != max {
        t.Errorf("size = %d, want %d", m.Size, max)
    }
}

func over(t *testing.T, c folder.Vault) {
    max := c.Limits().MaxSize()
    content := bytes.Repeat([]byte("x"), int(max)+1)

    _, err := c.Put(context.Background(), bytes.NewReader(content), "text/plain")
    if !errors.Is(err, attachment.ErrTooLarge) {
        t.Fatalf("err = %v, want attachment.ErrTooLarge", err)
    }

    // What the contract can check after a refusal: that the vault is
    // still usable. It cannot check that nothing was stored:
    // there is no operation to observe it, and the ref is
    // opaque. It is the implementation test's job.
    m := put(t, c, "after a refusal, everything works")
    if got := read(t, c, m.Ref); got != "after a refusal, everything works" {
        t.Errorf("vault damaged by a refused put: %q", got)
    }
}

func cancelled(t *testing.T, c folder.Vault) {
    ctx, cancel := context.WithCancel(context.Background())
    cancel()

    if _, err := c.Put(ctx, strings.NewReader("x"), "text/plain"); !errors.Is(err, context.Canceled) {
        t.Errorf("Put on canceled context: err = %v", err)
    }
    if _, err := c.Open(ctx, attachment.Ref("sha256-whatever")); !errors.Is(err, context.Canceled) {
        t.Errorf("Open on canceled context: err = %v", err)
    }
}
```

> Une interface déclare des **signatures**. Un contrat déclare des
> **promesses**. Seules les promesses ont de la valeur pour l'appelant, et
> seules les promesses peuvent être vérifiées. Un test de contrat partagé est
> la seule façon de savoir qu'une seconde implémentation abstrait vraiment la
> première.

### Ce que le contrat ne peut pas vérifier

Regarde la fin du sous-test `over` :

```go
// What the contract can check after a refusal: that the vault is
// still usable. It cannot check that nothing was stored:
// there is no operation to observe it, and the ref is
// opaque. It is the implementation test's job.
```

C'est une limite réelle, et elle est instructive :

> Ce qu'un test de contrat peut vérifier est exactement ce que le contrat
> **exprime**. « Rien n'a été stocké » n'est pas dans le contrat — il n'y a
> aucune opération pour l'observer — donc le contrat ne peut pas le tester.

La bonne réponse n'est **pas** d'ajouter une méthode à l'interface pour
servir un test. C'est de descendre d'un niveau : le test d'implémentation de
`coffredisque` a le droit, lui, de regarder dans le répertoire.

```go
// This one is not in the contract, and has no business there: it looks
// in the directory. It is an implementation test, and it is the only place
// where one can check that a refused put leaves no litter.
func TestARefusedPutLeavesNothing(t *testing.T)
```

Deux étages de tests, deux périmètres : le contrat pour ce que l'appelant a le
droit d'attendre, l'implémentation pour ce que l'exploitant a le droit
d'exiger. Ce découpage est l'objet de la leçon 1.6.

### L'ordre des effets, qui n'est pas un détail

Dans `folder.Attach` :

```go
// The order is a decision of this module: put first, attach
// then. If attaching fails, an orphan attachment stays in the vault:
// it is a storage cost, recoverable by a garbage collector. The opposite
// would produce a link to a missing attachment, that is an
// error the user can see.
```

> Entre deux états incomplets, choisis toujours l'**inutile** plutôt que
> l'**incohérent**. Un déchet se ramasse ; un lien cassé se réclame.

C'est la même famille de décisions que la correction 1.1 / 5, et elle mérite
d'être écrite dans le code, parce que le prochain lecteur sera tenté
d'inverser les deux lignes « pour ne pas écrire pour rien ».

## 5. Le mauvais exemple, et pourquoi il fait mal

```go
// Package before is the counter-example of lesson 1.4.
//
// It holds an interface, a layer, unexported fields and
// accessors. It has every look of abstraction, and it has
// none of the properties.
package before

import (
    "database/sql"
    "io"
    "os"
    "time"
)

// S3Storage is the "abstraction" interface of storage.
//
// It was obtained by copying the methods of the S3 client and changing the
// name of the type. It is a mirror, not an abstraction: the words "bucket",
// "ACL" and "ETag" name the provider in the signature itself.
type S3Storage interface {
    PutObject(bucket, key string, body io.Reader, contentType, acl string,
        metadata map[string]string) (etag string, err error)
    GetObject(bucket, key string) (io.ReadCloser, error)
    HeadObject(bucket, key string) (size int64, contentType string, err error)
    DeleteObject(bucket, key string) error
    CopyObject(srcBucket, srcKey, dstBucket, dstKey string) error
    ListObjectsV2(bucket, prefix string, maxKeys int) ([]string, error)
    PresignGetObject(bucket, key string, expires time.Duration) (string, error)
}

// AttachmentService is the "service layer". It passes things on.
type AttachmentService struct {
    storage S3Storage
    db      *sql.DB
    bucket  string
}

// Attach: the caller must know the bucket, the MIME type, the ACL, the
// key format, and it gets an ETag it does not know what to do with.
func (s *AttachmentService) Attach(folder, fileName string, content io.Reader) (string, error) {
    cle := folder + "/" + fileName
    etag, err := s.storage.PutObject(s.bucket, cle, content,
        "application/octet-stream", "private", nil)
    if err != nil {
        return "", err
    }
    _, err = s.db.Exec("INSERT INTO attachments (folder, key, etag) VALUES ($1,$2,$3)",
        folder, cle, etag)
    return cle, err
}

// Open returns the provider's error as is.
//
// The caller who wants to tell "missing attachment" from "network error" must
// so test os.ErrNotExist, or sql.ErrNoRows, or an S3 error depending on
// the implementation. Its code names the implementation, so changing the vault
// changes its code.
func (s *AttachmentService) Open(cle string) (io.ReadCloser, error) {
    return s.storage.GetObject(s.bucket, cle)
}

// Attachment has unexported fields and one accessor per field. Nothing is
// cache: the struct is public, with a longer syntax.
type Attachment struct {
    cle       string
    size      int64
    mediaType string
    etag      string
    createdAt time.Time
}

func (p *Attachment) Key() string              { return p.cle }
func (p *Attachment) SetKey(v string)          { p.cle = v }
func (p *Attachment) Size() int64              { return p.size }
func (p *Attachment) SetSize(v int64)          { p.size = v }
func (p *Attachment) MediaType() string        { return p.mediaType }
func (p *Attachment) SetMediaType(v string)    { p.mediaType = v }
func (p *Attachment) ETag() string             { return p.etag }
func (p *Attachment) SetETag(v string)         { p.etag = v }
func (p *Attachment) CreatedAt() time.Time     { return p.createdAt }
func (p *Attachment) SetCreatedAt(v time.Time) { p.createdAt = v }

// And the helper function that generalizes without abstracting.
func Transfer(src, dst any) error {
    switch s := src.(type) {
    case io.Reader:
        if d, ok := dst.(io.Writer); ok {
            _, err := io.Copy(d, s)
            return err
        }
    case string:
        if d, ok := dst.(string); ok {
            return os.Rename(s, d)
        }
    }
    return os.ErrInvalid
}
```

Ce paquet contient une interface, une couche de service, des champs non
exportés et des accesseurs. Il a **toutes les apparences** de l'abstraction.
Relevé :

| Défaut | Pourquoi ce n'en est pas une |
|---|---|
| `S3Storage`, 7 méthodes copiées du client | un miroir : ajouter une seconde implémentation obligerait à réécrire l'interface |
| les mots `bucket`, `acl`, `etag` dans les signatures | le fournisseur est **nommé dans le contrat** |
| `AttachmentService` transmet sans rien décider | une couche n'est pas une abstraction |
| `Open` rend l'erreur du fournisseur telle quelle | l'appelant doit tester `os.ErrNotExist` : son code nomme l'implémentation |
| un accesseur et un mutateur par champ | la struct est publique, avec une syntaxe plus longue |
| `Transfer(src, dst any)` | généralisation maximale, abstraction nulle |
| aucun `context` | « ceci peut être lent » n'est pas dit |
| aucune limite exprimée | elle se découvrira sur le plus gros fichier |

### Les deux défauts qui méritent un développement

**`etag` est le plus instructif.** `Attach` rend une clé et stocke un ETag.
L'ETag est un concept HTTP, qui se trouve être, chez ce fournisseur, le MD5 du
contenu — sauf pour les envois multipart, où ce n'en est pas un. L'appelant qui
s'en servirait pour vérifier l'idempotence aurait raison aujourd'hui et tort
le jour où un fichier dépasse la taille de bascule multipart.

> Une fuite d'implémentation est d'autant plus dangereuse qu'elle **marche
> presque toujours**. `etag` et `digest` ont la même tête ; l'un est une
> garantie du domaine, l'autre un détail de protocole avec une exception.

**Les accesseurs par champ sont le piège le plus répandu.** Ils ont la forme de
l'encapsulation et aucune de ses propriétés :

> Un accesseur et un mutateur par champ ne cachent rien : ils renomment
> l'accès. Encapsuler n'est pas abstraire. On peut avoir tous ses champs privés
> et zéro abstraction.

Compare avec `attachment.Limits`, dont les champs sont aussi non exportés : il n'y
a aucun mutateur, `Types()` rend une **copie**, et `Allowed` répond à une
question au lieu de rendre une donnée. La différence n'est pas la visibilité
des champs, c'est **qui décide**.

### Et la couche

`AttachmentService.Open` fait un appel et rend son résultat. Cette méthode est
une ligne de transmission.

> Ajouter une couche n'abstrait rien si elle transmet. Une couche qui ne
> **retire** aucune information et n'ajoute aucune garantie est un coût sans
> contrepartie : un fichier de plus à ouvrir, une pile d'appels plus profonde,
> et la même dépendance.

## 6. Le lien avec la production

### Les trois choses qui traversent toute abstraction

C'est le cœur de la leçon côté exploitation, et ça se formule en une phrase :

> On peut cacher une représentation et un algorithme. On ne peut cacher ni une
> **latence**, ni un **mode de panne**, ni un **ordre**. Ces trois-là traversent
> toutes les abstractions, qu'on le veuille ou non.

Elles traversent parce qu'elles ne sont pas des propriétés du code : ce sont
des propriétés du **monde** dans lequel il tourne. Les cacher ne les supprime
pas, ça supprime seulement la possibilité de s'en occuper.

| Ce qui fuit | Exemple | Comment l'exposer honnêtement |
|---|---|---|
| la latence | un ORM qui cache une requête par itération de boucle | `ctx` dans la signature ; documenter le coût en nombre d'allers-retours |
| le mode de panne | `Get(id)` qui peut échouer pour cinq raisons différentes | des erreurs typées, exportées, dans le vocabulaire |
| l'ordre | une file qui ne préserve pas l'ordre des messages | le dire dans le contrat, et le vérifier dans le test de contrat |
| la concurrence | un cache sûr pour un lecteur, pas pour dix | « sûr pour un usage concurrent » est une clause du contrat |
| les limites | une taille maximale, un nombre maximal, une durée maximale | dans le contrat, comme `Limits()` |

Le cas de l'ORM mérite d'être nommé précisément, parce que c'est la fuite la
plus coûteuse du métier : `for _, c := range orders { c.Client.Name }` est
une boucle en apparence, et N requêtes en réalité. L'abstraction a réussi à
cacher le SQL, et elle a échoué à cacher le **nombre d'allers-retours** — qui
est la seule chose qui compte pour la latence.

> Une abstraction qui cache le coût d'une opération déplace le problème du
> développeur vers l'astreinte. Et l'astreinte, elle, n'a pas le code sous les
> yeux.

### Le contrat écrit est un artefact d'exploitation

Dans Go, le commentaire de documentation **est** le contrat : c'est ce que
`go doc` affiche, et c'est tout ce qu'un consommateur lira. Ce qu'il doit
contenir, et presque aucun n'en contient la moitié :

1. ce qui est garanti ;
2. ce qui ne l'est **pas** — et c'est la section la plus utile ;
3. les erreurs qu'on peut recevoir, nommément ;
4. la sûreté en usage concurrent ;
5. les limites ;
6. qui doit fermer, libérer, annuler.

> Un contrat qui n'énumère que les garanties est une publicité. Ce qui empêche
> un incident, c'est la liste de ce qui n'est pas promis.

### Et la granularité du diagnostic

Une abstraction étanche a une conséquence qu'on ne mesure qu'en incident :
quand quelque chose casse derrière elle, **on sait où chercher**, parce que la
frontière est aussi une frontière de responsabilité. Une abstraction qui fuit
produit des incidents dont la cause est partout : un peu dans l'appelant, un
peu dans l'implémentation, un peu dans l'hypothèse que ni l'un ni l'autre
n'avait écrite.

## 7. Ce qu'il faut retenir

1. Abstraire, c'est décider ce que l'appelant a le droit de ne pas savoir — et
   ce qu'il n'a pas le droit de savoir.
2. Abstraction et généralisation sont opposées : l'une retire de
   l'information, l'autre ajoute des cas. `any` n'est pas une abstraction.
3. La mesure est empirique : combien de fois faut-il lire derrière ? À chaque
   usage, ce n'est pas une abstraction, c'est un alias.
4. Une interface obtenue en copiant une implémentation est un miroir. Le test :
   si une seconde implémentation oblige à modifier l'interface, c'était un
   miroir.
5. Le nombre d'implémentations raisonnables est inversement proportionnel au
   nombre de méthodes.
6. Le signal du besoin n'est pas « trois usages », c'est « la même question
   posée depuis deux endroits qui n'ont pas besoin de la même réponse ».
7. N'expose pas ce qui est utile : expose ce dont l'appelant a besoin pour
   tenir ses propres garanties.
8. Les erreurs font partie du vocabulaire, pas de l'implémentation. Une
   abstraction dont les erreurs nomment son implémentation n'en est pas une.
9. Cacher une limite ou un coût n'est pas abstraire, c'est piéger.
10. Une interface déclare des signatures, un contrat déclare des promesses.
    Écris le contrat sous forme de test partagé.
11. Latence, mode de panne et ordre traversent toutes les abstractions.
    Expose-les, puisque tu ne peux pas les cacher.
12. Encapsuler n'est pas abstraire. Un accesseur par champ ne cache rien.

## 8. Approfondissement : trois abstractions qui fuient, et où exactement

### `io.Reader`

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
```

Une méthode, des milliers d'implémentations, l'une des meilleures abstractions
jamais écrites. Et elle fuit, à deux endroits, et il faut les connaître :

- **`Read` peut rendre moins d'octets que demandé sans que ce soit une
  erreur.** Tout le monde écrit son premier `Read` en supposant le contraire.
  C'est pour ça qu'`io.ReadFull` existe.
- **`Read` peut rendre `n > 0` **et** une erreur en même temps.** Les données
  lues doivent être traitées avant de regarder l'erreur.

Ce ne sont pas des défauts de conception : c'est une fuite **nécessaire**, parce
qu'un flux réseau ne peut pas promettre autre chose. La bibliothèque standard
a fait le bon choix : elle a exposé la vérité désagréable au lieu de prétendre
que lire est simple, et elle a fourni `ReadFull` pour les cas où l'on veut la
promesse plus forte.

> Quand une garantie ne peut pas être tenue par toutes les implémentations, ne
> la mets pas dans l'interface. Mets-la dans une fonction qui s'en sert.

### `context.Context`

Celle-ci est intéressante parce qu'elle est à la fois excellente et mal aimée.

Ce qu'elle abstrait : « jusqu'à quand ai-je le droit de continuer ». C'est une
question, pas une implémentation, et c'est pourquoi elle traverse tout le
métier sans effort.

Ce qu'elle expose volontairement, et ce qui fait râler : **elle pollue toutes
les signatures.** C'est un choix assumé. L'alternative — un délai implicite, une
variable globale, un champ caché — rendrait l'annulation invisible.

> `ctx context.Context` en premier paramètre est le plus petit aveu honnête qui
> existe : il dit « ceci peut être lent, et peut être abandonné ». Une signature
> sans `ctx` promet le contraire.

Et sa fuite propre, celle de `context.WithValue` : une valeur transportée dans
un contexte est une dépendance invisible, non typée, que le compilateur ne
vérifie pas. C'est un couplage de degré 4 de la leçon 1.3, déguisé en bonne
pratique.

### Un cache

```go
type Cache interface {
    Get(cle string) ([]byte, bool)
    Set(cle string, v []byte)
}
```

Deux méthodes, et pourtant presque tout fuit :

- **l'éviction** : `Set` peut réussir et la valeur disparaître dans la seconde.
  Donc l'appelant doit traiter l'absence comme normale — ce que le `bool` dit, à
  son honneur.
- **la cohérence** : rien ne dit combien de temps une valeur reste valable. Donc
  le TTL, qui est la décision la plus importante, n'est pas dans le contrat.
- **la ruée** : mille requêtes sur une clé absente font mille calculs. Rien dans
  l'interface ne le laisse soupçonner, et c'est le mode de panne le plus
  fréquent des caches.
- **l'espace de clés**, qui est partagé, non typé et sans propriétaire — c'est
  la correction 1.3 / 3.

La bonne abstraction d'un cache n'est pas `Get`/`Set`. C'est :

```go
// Fetch returns the value, computing it if needed. One computation at
// a time per key: concurrent callers wait for the same result.
Fetch(ctx context.Context, cle Key, compute func(context.Context) ([]byte, error)) ([]byte, error)
```

Une méthode au lieu de deux, le calcul passé en paramètre, et la ruée traitée
**à l'intérieur** parce que c'est le seul endroit où elle peut l'être.

> Quand une abstraction laisse fuir un mode de panne, c'est souvent qu'elle a
> découpé l'opération au mauvais endroit. `Get` puis `Set` sont deux moitiés
> d'une seule décision, et c'est dans l'intervalle entre les deux que le
> problème vit.

C'est le même raisonnement que la correction 1.3 / 2 : une séquence
lire-décider-écrire exposée en deux appels laisse l'appelant seul au milieu.

## 9. Ce que l'abstraction n'est pas

**Ce n'est pas une interface.** En Go, un type concret à champs non exportés est
très souvent la meilleure abstraction : `attachment.Limits` et `prix.Grille` de la
leçon 1.3 n'en sont pas, et elles cachent plus que la plupart des interfaces
qu'on écrit.

**Ce n'est pas une couche.** Une couche qui transmet ne retire aucune
information.

**Ce n'est pas la généralisation.** Section 1.

**Ce n'est pas l'encapsulation.** Des champs privés avec un accesseur et un
mutateur chacun : la struct est publique, en plus long.

**Ce n'est pas le nom.** Renommer `EnvoyerParSendgrid` en `Notifier` sans
changer la signature ne change rien du tout. Et c'est même pire que de ne rien
faire :

> Un nom abstrait sur une signature qui fuit est un mensonge. L'appelant lui
> fait confiance, et il a tort.

**Et ce n'est pas gratuit à défaire.** Une abstraction publiée est un contrat :
dès qu'un second consommateur existe, la changer coûte autant qu'un changement
de schéma de base. C'est la raison pour laquelle l'abstraction prématurée est
coûteuse — plus coûteuse que le couplage qu'elle prétendait éviter :

> Une abstraction prématurée coûte deux fois : elle retire de l'information au
> lecteur, et elle n'en cache aucune au consommateur. Puis elle devient un
> contrat qu'on n'ose plus toucher.

## 10. Le réflexe à installer

Deux questions. La première se pose en écrivant, la seconde est le test.

> **Qu'est-ce que l'appelant a le droit d'ignorer ?**
>
> **Si je changeais d'implémentation demain, qu'est-ce qui, chez lui, devrait
> changer ?**

Si la réponse à la seconde est « rien », l'abstraction tient. Si c'est « sa
gestion d'erreur », « sa boucle », « son délai d'attente » ou « son nombre de
retries », alors elle fuit exactement là — et tu sais désormais où aller
boucher.

Et pour toute interface que tu t'apprêtes à écrire :

> **Est-ce que j'écris une question, ou est-ce que je recopie une
> implémentation ?**
