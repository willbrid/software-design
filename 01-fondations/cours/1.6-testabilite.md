# Leçon 1.6 — La testabilité comme révélateur de conception

Cette leçon n'est pas une leçon sur les tests. Elle ne t'apprendra pas à écrire
un test : tu en écris déjà. Elle utilise les tests comme un **instrument de
mesure** braqué sur ta conception.

Les cinq leçons précédentes t'ont donné cinq questions à poser à un morceau de
code : qui possède cette donnée (1.1), qui peut exiger que ça change (1.2), que
suppose ce module sur les autres (1.3), ce que l'appelant a le droit de ne pas
savoir (1.4), quelles sont les issues et qui décide (1.5). Toutes ont le même
défaut : elles demandent un jugement. Deux personnes honnêtes peuvent ne pas
être d'accord.

La testabilité n'a pas ce défaut. Elle produit un **fait** :

> Tu essaies d'écrire le test. Soit tu y arrives en dix lignes, soit tu n'y
> arrives pas. Il n'y a rien à discuter.

C'est la seule des six questions qui se mesure avec un chronomètre, et c'est
pour ça qu'elle clôt le niveau.

## 1. Le concept, simplement

### Un test fait exactement quatre choses

Quel que soit le langage, le framework, le style, un test exécute quatre
étapes :

1. **Construire** le sujet.
2. **L'amener** dans l'état voulu.
3. **Déclencher** le comportement.
4. **Observer** le résultat.

C'est tout. Et la phrase qui tient toute la leçon :

> La difficulté d'écrire un test n'est pas une propriété du test. C'est une
> **mesure de la conception** du code testé.

Quand un test est pénible à écrire, l'erreur est de rendre le test plus
sophistiqué. La bonne conduite est de regarder **laquelle des quatre étapes
fait mal**, parce que chacune désigne un défaut précis.

### La grille des quatre douleurs

| L'étape qui fait mal | Ce que le code t'impose | Le défaut de conception | Nommé en |
|---|---|---|---|
| **Construire** | une base, un serveur SMTP, un client HTTP, un fichier | trop de dépendances pour une seule responsabilité | 1.2, 1.3 |
| **Amener dans l'état** | une variable de paquet, une migration, un `init()`, une variable d'environnement | l'état n'est pas adressable depuis l'extérieur | 1.1, 1.3 |
| **Déclencher** | attendre, dormir, lancer un cron, faire tomber le réseau | le déclencheur est à l'intérieur au lieu d'être un argument | 1.4 |
| **Observer** | lire un fichier, requêter la base, lire un log | le résultat est un effet, pas une valeur | 1.1, 1.5 |

Retiens la grille : *dis-moi où tu as mal, je te dirai ce qui est mal conçu*.
Elle est la réciproque des cinq leçons précédentes, et elle sert dans l'autre
sens — tu n'as pas besoin de juger un code pour le diagnostiquer, il suffit
d'essayer de l'interroger.

### Le test décisif de la leçon

> **De quoi ai-je besoin pour poser une question à ce code ?**

Si la réponse tient en un appel de fonction, la conception est bonne, quel que
soit l'avis de qui que ce soit sur l'élégance du résultat. Si la réponse
commence par « il faut démarrer », la conception a un problème — et le test
n'en est que le messager.

## 2. L'intuition

Un tableau électrique, dans un immeuble de Douala.

Deux tableaux font le même travail. Le premier est un bloc fermé : les fils
entrent, les fils sortent, rien n'est accessible. Le second a des **bornes de
mesure** — des points où l'on pose les pointes d'un multimètre sans rien
démonter.

Les deux distribuent le courant exactement pareil. La différence n'apparaît que
le jour où ça ne marche plus.

Sur le premier, pour savoir si le courant passe au troisième étage, il faut
couper, dénuder, mesurer, rebrancher. Le diagnostic coûte une coupure. Donc on
ne diagnostique pas : on remplace le disjoncteur le plus probable, on remet le
courant, et on verra bien. Sur le second, on mesure en quinze secondes, sans
rien couper.

Deux choses à noter, et ce sont les deux moitiés de la leçon.

La première : **personne n'installe des bornes de mesure « pour les tests »**.
On les installe parce qu'un tableau qu'on ne peut pas mesurer est un tableau
qu'on ne peut pas réparer. La testabilité et la réparabilité sont la même
propriété, mesurée à deux moments différents.

La seconde : **une borne de mesure est aussi un point où l'on peut brancher
n'importe quoi.** Ouvrir un accès pour mesurer, c'est ouvrir un accès. On y
reviendra au §3 — c'est le coût qu'on oublie toujours de compter.

## 3. Le mécanisme

### Le sujet : une campagne de relance d'impayés

Voici la fonction d'origine. Elle tourne depuis deux ans, elle est appelée par
un cron horaire, elle est lisible, et elle marche.

```go
// Package avant est la version d'origine de la campagne de relance : une
// fonction, quarante lignes, et rien de testable.
//
// Elle n'est pas mal ecrite. Elle est lisible, elle marche, et elle a tourne
// deux ans. C'est le point : l'absence de testabilite ne se voit pas a la
// lecture. Elle se voit quand on essaie.
package avant

import (
    "context"
    "database/sql"
    "fmt"
    "net/smtp"
    "os"
    "strconv"
    "time"
)

// Le palier et le repit sont lus a l'initialisation du programme. Les changer
// dans un test demande de changer l'environnement du processus de test.
var (
    premierPalier = joursDepuisEnv("RELANCE_PALIER_1", 3)
    secondPalier  = joursDepuisEnv("RELANCE_PALIER_2", 10)
    repitHeures   = int64(72)
    envoyes       int // compteur global, pour le log de fin de journee
)

func joursDepuisEnv(cle string, defaut int) time.Duration {
    if v := os.Getenv(cle); v != "" {
        if n, err := strconv.Atoi(v); err == nil {
            return time.Duration(n) * 24 * time.Hour
        }
    }
    return time.Duration(defaut) * 24 * time.Hour
}

// RelancerImpayes est appelee par le cron horaire.
func RelancerImpayes(ctx context.Context, db *sql.DB, serveur, de string) error {
    maintenant := time.Now()

    lignes, err := db.QueryContext(ctx,
        `SELECT reference, email, echeance, dernier_palier, dernier_envoi
           FROM impayes WHERE regle = false`)
    if err != nil {
        return err
    }
    defer lignes.Close()

    rapport, err := os.Create("/var/rapports/relances-" + maintenant.Format("2006-01-02") + ".csv")
    if err != nil {
        return err
    }
    defer rapport.Close()

    for lignes.Next() {
        var reference, email string
        var echeance, dernierEnvoi time.Time
        var dernierPalier int
        if err := lignes.Scan(&reference, &email, &echeance, &dernierPalier, &dernierEnvoi); err != nil {
            return err
        }

        retard := maintenant.Sub(echeance)
        palier := 0
        modele := ""
        switch {
        case retard >= secondPalier && dernierPalier < 2:
            palier, modele = 2, "ferme"
        case retard >= premierPalier && dernierPalier < 1:
            palier, modele = 1, "courtois"
        }
        if palier == 0 {
            continue
        }
        if dernierPalier > 0 && maintenant.Sub(dernierEnvoi).Hours() < float64(repitHeures) {
            continue
        }

        corps := fmt.Sprintf("Subject: Rappel\r\n\r\nFacture %s impayee. (%s)", reference, modele)
        if err := smtp.SendMail(serveur, nil, de, []string{email}, []byte(corps)); err != nil {
            fmt.Fprintf(rapport, "%s;%d;echec\n", reference, palier)
            continue
        }
        if _, err := db.ExecContext(ctx,
            `UPDATE impayes SET dernier_palier = $1, dernier_envoi = $2 WHERE reference = $3`,
            palier, maintenant, reference); err != nil {
            fmt.Fprintf(rapport, "%s;%d;non-consigne\n", reference, palier)
            continue
        }
        envoyes++
        fmt.Fprintf(rapport, "%s;%d;ok\n", reference, palier)
    }
    return lignes.Err()
}
```

Elle n'est pas mal écrite. C'est le point : **l'absence de testabilité ne se
voit pas à la lecture.** Elle se voit quand on essaie. Essayons, étape par
étape.

### Étape 1 — construire

Pour appeler `RelancerImpayes`, il faut un `*sql.DB` et une adresse de serveur
SMTP. Pas une interface : le type concret du pilote de base de données. Donc,
pour poser la moindre question à la règle des paliers, il faut une base.

Ce que ça révèle : la règle de décision et l'accès au stockage sont dans la
même unité. **Deux demandeurs différents** — le responsable du recouvrement
pour les paliers, l'équipe infrastructure pour la base — ont une seule porte
d'entrée. C'est la leçon 1.2, et le test vient de le mesurer sans qu'on ait eu
à juger quoi que ce soit.

### Étape 2 — amener dans l'état

Les paliers sont dans des variables de paquet, initialisées depuis
l'environnement du processus. Pour tester un palier à 5 jours, il faut modifier
l'environnement du processus de test. Et `envoyes` est un compteur global : le
deuxième test de la suite part d'un état laissé par le premier.

Ce que ça révèle : c'est du couplage par état global, degré 4 de l'échelle de
la leçon 1.3. **Les tests sont le premier appelant à en souffrir, et ils en
souffrent au même endroit que la production** — le jour où deux campagnes
tournent dans le même processus.

### Étape 3 — déclencher

`maintenant := time.Now()`, première ligne. Il n'existe aucun moyen de demander
à cette fonction *« que décides-tu le 14 mars à 9 h ? »*. La seule façon de
tester le palier à 30 jours est d'attendre trente jours, ou de changer l'heure
de la machine.

Ce que ça révèle : le déclencheur de la décision est **à l'intérieur** de la
décision. On y revient dans une minute, parce que la réponse usuelle à ce
problème est mauvaise.

### Étape 4 — observer

La fonction rend `error`. Les décisions — *tel impayé, tel palier, tel modèle*
— n'apparaissent nulle part dans sa valeur de retour. Pour savoir ce qu'elle a
décidé, il faut lire un fichier CSV dans `/var/rapports/`, ou interroger la
base, ou lire les logs du serveur SMTP.

Ce que ça révèle : **le résultat du calcul est un effet de bord**. C'est la
leçon 1.1 dans sa forme la plus coûteuse — non seulement pour le test, mais
pour l'astreinte, qui n'a elle non plus aucun moyen de savoir ce que la dernière
passe a décidé.

### La règle de l'instrument

Quatre étapes, quatre blocages, quatre défauts déjà nommés dans les leçons
précédentes. D'où la règle :

> On ne corrige pas un test difficile. On corrige **ce qu'il mesure**.

Un test difficile qu'on rend possible à coups d'outillage — une base éphémère,
un faux serveur SMTP, une variable d'environnement posée dans `TestMain` — ne
guérit rien. Il déplace le symptôme et il ajoute une deuxième chose à
maintenir.

### Ce que « rendre testable » veut dire exactement

Trois transformations, pas une de plus :

| Avant | Après |
|---|---|
| une **dépendance** | un **argument** |
| un **effet** | une **valeur rendue** |
| un **état global** | un **paramètre** |

Aucune des trois ne parle de tests. Les trois sont des décisions de conception
que les leçons 1.1 à 1.5 recommandaient déjà. **Le test ne demande rien de
neuf : il rend visible ce qu'on n'a pas fait.**

### Le coût qu'on oublie de compter

Voici où presque tout le monde se trompe, y compris dans des bases de code
soignées.

La réponse réflexe au problème de l'horloge est : *« injecte une interface
`Clock` »*.

```go
// Package illustration ne sert qu'a ce que les extraits cites dans la lecon
// soient compiles comme les autres. Rien ici n'est utilise par la campagne.
package illustration

import "time"

// Horloge est la reponse reflexe au probleme du temps. Elle marche, et elle
// coute une couture publique de plus.
type Horloge interface {
    Maintenant() time.Time
}

type Service struct {
    horloge Horloge
}
```

Ça marche. Et ça coûte trois choses qu'on ne compte jamais :

1. Un **point d'extension public** de plus. `Service` accepte désormais
   n'importe quelle horloge, y compris en production. Quelqu'un, un jour, y
   mettra une horloge décalée pour rattraper un lot, et ce sera un mardi soir.
2. Une **question de plus** dans la tête de chaque lecteur : quelle horloge
   est-ce, ici ?
3. Un **mensonge possible** : le test passe avec une horloge figée, la
   production tourne avec une horloge qui avance, et la différence entre les
   deux n'est testée par rien.

> Toute couture ouverte pour un test est aussi une couture ouverte pour un
> abus.

D'où le critère d'arrêt, qui est la vraie règle de ce paragraphe :

> **On n'injecte pas pour tester. On injecte quand le remplaçant a un demandeur
> en production.**

Et pour le temps, il existe presque toujours mieux :

> Le temps n'est pas une dépendance à injecter. C'est une **donnée à faire
> descendre**.

`Decider(maintenant, …)` ne demande aucune interface, aucun double, aucune
configuration. Il y a exactement un appel à `time.Now()` dans tout le
programme, il est dans `main`, et `main` n'a pas besoin de test. Une couture
en moins, un point d'extension en moins, et un test qui tient en trois lignes.

## 4. Le bon exemple

### La règle, et le type qui ne peut pas être incohérent

```go
// Package relance decide quels rappels d'impaye doivent partir.
//
// Il ne lit rien, n'ecrit rien, n'envoie rien et ne consulte pas l'heure. Il
// recoit un etat et rend des decisions. Tout ce qui, dans ce fichier,
// ressemble a une dependance est en realite un argument.
package relance

import (
    "errors"
    "time"
)

var (
    // ErrSansReference : un impaye sans reference ne peut etre ni relance ni
    // consigne.
    ErrSansReference = errors.New("relance : impaye sans reference")
    // ErrEcheanceAbsente : sans echeance, tout retard est infini. Une echeance
    // absente n'est pas une echeance ancienne.
    ErrEcheanceAbsente = errors.New("relance : impaye sans echeance")
    // ErrPalierInvalide : les paliers commencent a 1.
    ErrPalierInvalide = errors.New("relance : palier invalide")
    // ErrDateDeRappelAbsente : un rappel parti a une date.
    ErrDateDeRappelAbsente = errors.New("relance : rappel sans date d'envoi")
)

// Impaye est l'etat d'une facture echue.
//
// Ses champs sont prives, et c'est un test de mutation qui l'a decide. Dans la
// premiere version ils etaient publics, avec une phrase de documentation
// disant que dernierEnvoi n'avait de sens que si dernierPalier etait non nul.
// Une phrase de documentation n'empeche rien : l'etat incoherent restait
// construisible, une ligne de code defendait contre lui, et aucun test ne
// pouvait dire si cette ligne servait.
type Impaye struct {
    reference     string
    echeance      time.Time
    dernierPalier int
    dernierEnvoi  time.Time
}

// NouvelImpaye construit un impaye sur lequel aucun rappel n'est encore parti.
// C'est la seule porte d'entree, et elle refuse ce que la regle ne sait pas
// traiter.
func NouvelImpaye(reference string, echeance time.Time) (Impaye, error) {
    if reference == "" {
        return Impaye{}, ErrSansReference
    }
    if echeance.IsZero() {
        return Impaye{}, ErrEcheanceAbsente
    }
    return Impaye{reference: reference, echeance: echeance}, nil
}

// AvecRappel rend une copie portant la trace d'un rappel deja parti. Le palier
// et la date entrent ensemble ou n'entrent pas : il n'y a plus d'etat ou l'un
// est renseigne sans l'autre.
func (i Impaye) AvecRappel(palier int, quand time.Time) (Impaye, error) {
    if palier < 1 {
        return Impaye{}, ErrPalierInvalide
    }
    if quand.IsZero() {
        return Impaye{}, ErrDateDeRappelAbsente
    }
    i.dernierPalier = palier
    i.dernierEnvoi = quand
    return i, nil
}

// Reference identifie la facture.
func (i Impaye) Reference() string { return i.reference }

// DernierPalier rend le palier du dernier rappel parti, ou 0 si aucun.
func (i Impaye) DernierPalier() int { return i.dernierPalier }

// Palier est un etage de la politique de relance.
type Palier struct {
    // Numero est l'ordre du palier. Il commence a 1.
    Numero int
    // Apres est le delai depuis l'echeance au-dela duquel ce palier s'applique.
    Apres time.Duration
    // Modele nomme le texte a envoyer. Le texte lui-meme n'est pas ici : il
    // change pour une autre raison que la politique.
    Modele string
}

// Politique est la regle complete. Les deux champs changent ensemble : qui
// modifie les paliers reconsidere le repit.
type Politique struct {
    Paliers []Palier
    // Repit est le delai minimal entre deux rappels pour un meme impaye.
    Repit time.Duration
}

// Rappel est une decision : ce rappel-la doit partir.
type Rappel struct {
    Reference string
    Palier    int
    Modele    string
}

// Decider rend les rappels a envoyer a l'instant maintenant.
//
// GARANTI
//
//    Pour un impaye donne, au plus un rappel : celui du palier le plus eleve
//    atteint et pas encore envoye.
//    L'ordre de sortie suit l'ordre d'entree. Deux appels avec les memes
//    arguments rendent exactement le meme resultat.
//
// CE QUI RESTE VRAI
//
//    impayes et politique ne sont pas modifies. Aucune de leurs tranches n'est
//    triee, reordonnee ni ecrite en place.
//
// NON GARANTI
//
//    Que le rappel soit pertinent : si l'appelant fournit un impaye deja regle,
//    le rappel est decide quand meme. Savoir ce qui est impaye n'est pas le
//    travail de cette fonction.
//
// maintenant est un ARGUMENT, pas une dependance. C'est la difference entre un
// module qu'on teste avec trois lignes et un module qui exige une horloge
// injectee, donc une couture publique de plus.
func Decider(maintenant time.Time, impayes []Impaye, politique Politique) []Rappel {
    var sortie []Rappel
    for _, i := range impayes {
        if r, ok := deciderUn(maintenant, i, politique); ok {
            sortie = append(sortie, r)
        }
    }
    return sortie
}

func deciderUn(maintenant time.Time, i Impaye, p Politique) (Rappel, bool) {
    // Pas de tri : parcours complet, on retient le maximum. Trier serait plus
    // court d'une ligne et modifierait la tranche de l'appelant.
    atteint := -1
    modele := ""
    for _, pal := range p.Paliers {
        if pal.Numero <= i.dernierPalier {
            continue
        }
        // Le seuil est atteint DES que le delai est ecoule : >= et non >.
        if maintenant.Sub(i.echeance) >= pal.Apres && pal.Numero > atteint {
            atteint = pal.Numero
            modele = pal.Modele
        }
    }
    if atteint < 0 {
        return Rappel{}, false
    }
    // Plus de garde sur dernierPalier : un impaye sans rappel anterieur a un
    // dernierEnvoi nul, donc un ecart infini, donc un repit toujours ecoule.
    // Le cas incoherent qui justifiait la garde n'est plus construisible.
    if maintenant.Sub(i.dernierEnvoi) < p.Repit {
        return Rappel{}, false
    }
    return Rappel{Reference: i.reference, Palier: atteint, Modele: modele}, true
}
```

Trois choses à voir.

**L'instant est un argument.** Pas d'horloge, pas d'interface, pas de double.
Le test choisit le 14 mars à 9 h en l'écrivant.

**La clause « CE QUI RESTE VRAI » est dans le contrat.** C'est la leçon 1.5 :
`Decider` promet de ne pas toucher aux tranches qu'on lui passe. Cette promesse
est tenue par une décision visible dans le code — ne pas trier — et gardée par
un test qu'on verra plus bas.

**Les champs de `Impaye` sont privés, et c'est un test qui l'a décidé.** Le
§6 raconte comment. Pour l'instant, note seulement ce que ça supprime : il n'y
a plus d'`Impaye` dont le palier est renseigné sans la date, ni d'`Impaye` sans
échéance. Donc plus de ligne de code défensive contre ces cas, donc plus de
test pour cette ligne.

### Le test de la règle

Le fichier en entier jusqu'au cinquième cas sur six :

```go
// Les quelques lignes de preparation ci-dessous sont tout l'outillage
// necessaire, et c'est la seule mesure de testabilite qui compte.
var politique = relance.Politique{
    Paliers: []relance.Palier{
        {Numero: 1, Apres: 3 * 24 * time.Hour, Modele: "courtois"},
        {Numero: 2, Apres: 10 * 24 * time.Hour, Modele: "ferme"},
        {Numero: 3, Apres: 30 * 24 * time.Hour, Modele: "mise-en-demeure"},
    },
    Repit: 72 * time.Hour,
}

var echeance = time.Date(2026, time.March, 1, 9, 0, 0, 0, time.UTC)

func jours(n int) time.Duration { return time.Duration(n) * 24 * time.Hour }

func neuf(t *testing.T, ref string) relance.Impaye {
    t.Helper()
    i, err := relance.NouvelImpaye(ref, echeance)
    if err != nil {
        t.Fatalf("NouvelImpaye : %v", err)
    }
    return i
}

func rappele(t *testing.T, ref string, palier int, quand time.Time) relance.Impaye {
    t.Helper()
    i, err := neuf(t, ref).AvecRappel(palier, quand)
    if err != nil {
        t.Fatalf("AvecRappel : %v", err)
    }
    return i
}

func TestDecider(t *testing.T) {
    cas := []struct {
        nom      string
        apres    time.Duration // depuis l'echeance
        impaye   func(*testing.T) relance.Impaye
        attendu  []int // les paliers attendus en sortie
        pourquoi string
    }{
        {
            nom:     "avant le premier palier, rien",
            apres:   jours(2),
            impaye:  func(t *testing.T) relance.Impaye { return neuf(t, "F-1") },
            attendu: nil,
        },
        {
            nom:      "pile sur le seuil, le rappel part",
            apres:    jours(3),
            impaye:   func(t *testing.T) relance.Impaye { return neuf(t, "F-1") },
            attendu:  []int{1},
            pourquoi: "le seuil est atteint des que le delai est ecoule",
        },
        {
            nom:      "un retard de 40 jours ne declenche pas trois rappels",
            apres:    jours(40),
            impaye:   func(t *testing.T) relance.Impaye { return neuf(t, "F-1") },
            attendu:  []int{3},
            pourquoi: "au plus un rappel par impaye, celui du palier le plus eleve",
        },
        {
            nom:   "palier deja envoye, et repit non ecoule",
            apres: jours(11),
            impaye: func(t *testing.T) relance.Impaye {
                return rappele(t, "F-1", 1, echeance.Add(jours(10)))
            },
            attendu: nil,
        },
        {
            nom:   "palier deja envoye, repit ecoule",
            apres: jours(14),
            impaye: func(t *testing.T) relance.Impaye {
                return rappele(t, "F-1", 1, echeance.Add(jours(10)))
            },
            attendu:  []int{2},
            pourquoi: "le repit protege le client, il ne supprime pas le palier",
        },
```

Lis le début du fichier : il n'y a **rien** avant le tableau de cas. Pas de
`setup`, pas de `defer cleanup`, pas de base éphémère, pas de `TestMain`, pas
une ligne de nettoyage. Deux constructeurs, un raccourci pour écrire des
journées, et c'est tout l'outillage. C'est la mesure, et c'est la seule qui
compte.

Note aussi la colonne `pourquoi`. Elle n'est pas de la décoration : quand le
test échoue, le message dit *pourquoi ce cas existe*, et c'est ce dont a besoin
la personne qui le lira dans deux ans — probablement parce qu'elle vient de le
casser.

### Les trois étages de tests

La leçon 1.4 annonçait deux étages. Il y en a trois, et le troisième est celui
qu'on n'écrit jamais.

| Étage | Il garde | Son demandeur | Il échoue quand | Il ne verra jamais |
|---|---|---|---|---|
| **contrat** | ce que l'appelant a le droit d'attendre | l'appelant | une implémentation ne tient plus sa promesse | la latence, le coût, la forme du stockage |
| **implémentation** | ce que l'exploitant a le droit d'exiger | l'astreinte | une implémentation devient lente, non réentrante, bavarde | ce qu'une autre implémentation ferait |
| **décision** | une décision de conception | le futur mainteneur | quelqu'un prend la décision contraire | tout comportement |

Le troisième mérite sa définition :

> Un **test de décision** n'échoue pas le jour d'un bug. Il échoue le jour où
> quelqu'un prend une décision contraire. C'est le seul test qui parle au
> mainteneur plutôt qu'au programme.

Tu en as déjà écrit un sans le nommer : le test de graphe d'imports de la leçon
1.2, qui garantit que le module de règles n'a **aucun moyen** d'envoyer un
email. Ce n'était pas un test de comportement. C'était un garde-fou 🟡 chargé de
maintenir un ⚫ dans le temps.

### Trois tests de décision, trois mécanismes

Les tests de décision se rangent par **ce qu'ils inspectent**, et c'est ce qui
détermine leur portée.

**1. Par la valeur** — on appelle, et on vérifie que l'entrée n'a pas bougé :

```go
// TestDeciderNeTouchePasAuxEntrees garde la clause « CE QUI RESTE VRAI ».
//
// Il n'y a aucun bug aujourd'hui. Ce test existe pour le jour ou quelqu'un
// remplacera le parcours de deciderUn par un sort.Slice sur politique.Paliers
// — une ligne de moins, et la tranche de l'appelant reordonnee a son insu.
func TestDeciderNeTouchePasAuxEntrees(t *testing.T) {
    paliers := []relance.Palier{
        {Numero: 3, Apres: jours(30), Modele: "mise-en-demeure"},
        {Numero: 1, Apres: jours(3), Modele: "courtois"},
        {Numero: 2, Apres: jours(10), Modele: "ferme"},
    }
    p := relance.Politique{Paliers: paliers, Repit: 72 * time.Hour}
    impayes := []relance.Impaye{neuf(t, "F-2"), neuf(t, "F-1")}

    avantPaliers := append([]relance.Palier(nil), paliers...)
    avantImpayes := append([]relance.Impaye(nil), impayes...)

    relance.Decider(echeance.Add(jours(40)), impayes, p)

    for i := range avantPaliers {
        if paliers[i] != avantPaliers[i] {
            t.Fatalf("paliers[%d] a change : %+v -> %+v", i, avantPaliers[i], paliers[i])
        }
    }
    for i := range avantImpayes {
        if impayes[i] != avantImpayes[i] {
            t.Fatalf("impayes[%d] a change", i)
        }
    }
}
```

Il n'y a aucun bug aujourd'hui. Ce test ne sert à rien aujourd'hui. Il servira
le jour où quelqu'un remplacera le parcours par un `sort.Slice` sur
`politique.Paliers` — une ligne de moins, un code plus clair, et la tranche de
l'appelant réordonnée à son insu. Les tests de décision ont tous cette forme :
**ils sont inutiles jusqu'au jour où ils sont la seule chose qui reste.**

**2. Par la répétition** — on appelle cinquante fois et on compare. C'est ce que
fait `TestDeciderEstDeterministe` : un parcours de `map` ne se trahit pas au
premier essai, et la promesse d'ordre du contrat ne vaut rien si on ne la vérifie
qu'une fois.

**3. Par la lecture du code** — quand la décision n'est visible dans aucune
valeur :

```go
// Package garde ne contient que des tests de decision. Ils ne verifient aucun
// comportement : ils verifient que des decisions de conception tiennent encore.
//
// Un test de decision n'echoue pas le jour d'un bug. Il echoue le jour ou
// quelqu'un prend la decision contraire, et c'est le seul test qui parle au
// mainteneur plutot qu'au programme.
package garde

import (
    "go/ast"
    "go/parser"
    "go/token"
    "os/exec"
    "path/filepath"
    "strings"
    "testing"
)

// TestLaRegleNeConsultePasLHorloge garde la decision centrale du module
// relance : l'instant est un argument.
//
// Aucun graphe d'imports ne peut voir cette decision — relance importe time
// legitimement, pour le type time.Time. La verifier demande donc de lire le
// code, et c'est ce que fait ce test. C'est l'outil de dernier recours, a
// reserver aux decisions qu'aucun mecanisme du langage ne protege.
func TestLaRegleNeConsultePasLHorloge(t *testing.T) {
    fichiers, err := filepath.Glob("../relance/*.go")
    if err != nil {
        t.Fatalf("glob : %v", err)
    }
    if len(fichiers) == 0 {
        t.Fatal("aucun fichier analyse : un test de decision qui n'inspecte rien passe toujours")
    }

    interdits := map[string]bool{"Now": true, "Since": true, "Until": true}

    for _, f := range fichiers {
        if strings.HasSuffix(f, "_test.go") {
            continue
        }
        arbre, err := parser.ParseFile(token.NewFileSet(), f, nil, 0)
        if err != nil {
            t.Fatalf("%s : %v", f, err)
        }
        ast.Inspect(arbre, func(n ast.Node) bool {
            appel, ok := n.(*ast.SelectorExpr)
            if !ok {
                return true
            }
            paquet, ok := appel.X.(*ast.Ident)
            if !ok || paquet.Name != "time" || !interdits[appel.Sel.Name] {
                return true
            }
            t.Errorf("%s appelle time.%s : l'instant doit rester un argument,"+
                " sinon le module redevient intestable sans horloge injectee", f, appel.Sel.Name)
            return true
        })
    }
}

// TestLaRegleNAAucunMoyenDAgirSurLeMonde est le meme test qu'au chapitre 1.2,
// a une ligne pres. Il est repris ici parce qu'une suite de tests de decision
// se constitue par accumulation : chaque lecon en ajoute un, et ils ne se
// relisent jamais.
func TestLaRegleNAAucunMoyenDAgirSurLeMonde(t *testing.T) {
    interdits := []string{"os", "net", "net/http", "net/smtp", "database/sql", "log/slog"}

    sortie, err := exec.Command("go", "list", "-deps", "exemple/relances/relance").Output()
    if err != nil {
        t.Fatalf("go list : %v", err)
    }
    deps := make(map[string]bool)
    for _, l := range strings.Split(string(sortie), "\n") {
        deps[strings.TrimSpace(l)] = true
    }

    for _, i := range interdits {
        if deps[i] {
            t.Errorf("relance depend de %q : il detient un moyen qu'il ne doit pas avoir", i)
        }
    }
}
```

Le premier test est le plus intéressant, et il faut comprendre pourquoi il doit
lire la source. La décision à garder est *« l'instant reste un argument »*. Un
graphe d'imports ne peut pas la voir : `relance` importe `time` tout à fait
légitimement, pour le type `time.Time`. Aucun mécanisme du langage ne distingue
`time.Time` de `time.Now`.

> Une décision qu'aucun mécanisme du langage ne protège demande un test qui
> lit le code. C'est l'outil de dernier recours, et il faut le réserver aux
> décisions qui le méritent.

Note aussi la troisième assertion du test : `if len(fichiers) == 0 { t.Fatal }`.
Un test de décision qui n'inspecte rien passe toujours. C'est le mode de panne
propre à cette famille, et il faut l'écrire explicitement.

### Le test de contrat, et la clause que personne n'écrit

Le contrat du journal :

```go
// Package journal definit la memoire des rappels : ce qui est du, et ce qui
// est deja parti. Il ne contient aucune implementation.
package journal

import (
    "context"
    "errors"
    "time"

    "exemple/relances/relance"
)

// ErrIndisponible : la memoire n'a pas repondu. Reessayable.
var ErrIndisponible = errors.New("journal : indisponible")

// Ligne est la forme brute d'un impaye dans un stockage : exactement ce qu'une
// base rend, y compris quand c'est incoherent.
//
// Elle existe parce que relance.Impaye, lui, ne peut pas etre incoherent. Il
// faut donc un endroit ou l'incoherence est representable, et un endroit ou
// elle est refusee. Ces deux endroits ne sont pas le meme, et la frontiere
// entre eux est l'analyse.
type Ligne struct {
    Reference string
    Echeance  time.Time
    // Palier vaut 0 quand aucun rappel n'est parti.
    Palier int
    Envoi  time.Time
}

// Journal est la memoire des relances.
type Journal interface {
    // Impayes rend les factures echues et non reglees.
    //
    // GARANTI : tout Impaye rendu est valide, parce qu'il a ete construit par
    // relance.NouvelImpaye. Une ligne stockee que le constructeur refuse fait
    // echouer l'appel avec son erreur ; elle n'est pas filtree, parce qu'un
    // impaye qui disparait ne se remarque pas.
    //
    // GARANTI : l'ordre de lecture est stable d'un appel au suivant. Lequel
    // n'est pas specifie — seule la stabilite l'est, parce que c'est tout ce
    // dont relance.Decider a besoin pour tenir sa propre promesse d'ordre.
    Impayes(ctx context.Context) ([]relance.Impaye, error)

    // Consigner enregistre qu'un rappel de ce palier est parti pour cette
    // reference.
    //
    // GARANTI : apres un retour nil, un Impayes ulterieur rend un impaye dont
    // DernierPalier est au moins egal a palier.
    //
    // CE QUI RESTE VRAI EN CAS D'ECHEC : l'operation est reprenable. Apres un
    // retour non nil, un second appel avec les memes arguments doit pouvoir
    // reussir — que la premiere tentative ait ecrit ou non. Autrement dit
    // Consigner est idempotente sur le couple (reference, palier).
    //
    // C'est cette clause-la, et pas la precedente, qui decide du nombre de
    // rappels qu'un client recoit le jour ou la base bronche.
    Consigner(ctx context.Context, reference string, palier int, quand time.Time) error
}
```

Deux clauses, et toute la leçon 1.5 dans la deuxième :

- `Consigner` rend `nil` → c'est écrit durablement. **Tout le monde teste ça.**
- `Consigner` rend une erreur → **l'opération est reprenable**. Personne ne
  teste ça.

Le test de contrat partagé a donc deux étages, et le second est écrit à part
pour qu'on voie bien qu'il existe :

```go
// VerifierApresEchec est le test de contrat que presque personne n'ecrit.
//
// Il ne verifie pas que l'ecriture marche : il verifie ce qui reste vrai quand
// elle ne marche pas. C'est la seule clause dont depend le nombre de rappels
// qu'un client recoit un jour de panne.
func VerifierApresEchec(t *testing.T, fabrique Fabrique) {
    t.Helper()

    t.Run("une consignation echouee est reprenable", func(t *testing.T) {
        j, casser := fabrique(t, uneLigne())
        if casser == nil {
            // Un saut est un trou, pas un succes. Le nombre de sauts d'une
            // suite de tests de contrat est le nombre de clauses qu'on ne
            // verifie nulle part.
            t.Skip("cette implementation ne sait pas provoquer de panne d'ecriture")
        }
        ctx := context.Background()
        quand := echeance.Add(72 * time.Hour)

        casser()
        if err := j.Consigner(ctx, "F-1", 1, quand); err == nil {
            t.Fatal("la panne n'a pas eu lieu : le test ne prouverait rien")
        }

        // L'appelant fait exactement ce que le contrat l'autorise a faire :
        // il recommence a l'identique.
        if err := j.Consigner(ctx, "F-1", 1, quand); err != nil {
            t.Fatalf("le reessai a echoue avec %v : la clause d'echec du contrat"+
                " n'est pas tenue, et l'appelant n'a aucune conduite possible", err)
        }

        impayes, err := j.Impayes(ctx)
        if err != nil {
            t.Fatalf("Impayes : %v", err)
        }
        if impayes[0].DernierPalier() != 1 {
            t.Fatalf("DernierPalier = %d apres reessai, attendu 1", impayes[0].DernierPalier())
        }
    })
}
```

Deux implémentations le passent. `journalmem` traite la reconsignation du même
palier comme un non-événement. `journalstrict` la refuse avec
`ErrDejaConsigne` — une garde qui a l'air prudente, et qui est le défaut.

### Et ce que ce test de contrat a coûté

Regarde le type `Panne` dans le paquet `journaltest`. Pour vérifier la clause
d'échec, il faut **pouvoir provoquer l'échec** — et ce moyen n'est pas dans
l'interface. Chaque implémentation doit donc ouvrir une porte supplémentaire :
`CasserProchaineEcriture`, `PerdreProchainAccuse`.

C'est exactement le coût annoncé au §3, et il faut l'assumer à voix haute :

> La clause la plus importante d'un contrat n'est vérifiable que si
> l'implémentation ouvre une couture qui n'appartient pas au contrat.

Quand une implémentation ne sait pas provoquer de panne, le test ne passe pas
en vert : il **saute**, et le saut est visible.

> Le nombre de `t.Skip` d'une suite de tests de contrat est le nombre de clauses
> que tu ne vérifies nulle part.

### Le double qui a un état

L'orchestrateur, maintenant. Il ne contient aucune règle :

```go
// Package campagne orchestre une passe de relance : lire, decider, consigner,
// envoyer. Il ne contient aucune regle.
package campagne

import (
    "context"
    "fmt"
    "time"

    "exemple/relances/journal"
    "exemple/relances/relance"
)

// Expediteur envoie un rappel. L'interface est declaree ici, chez l'appelant,
// et non chez l'implementation.
type Expediteur interface {
    Envoyer(ctx context.Context, reference, modele string) error
}

// Bilan est ce que l'exploitation lit apres la passe.
type Bilan struct {
    Decides int
    Envoyes int
    Echoues int
}

type Campagne struct {
    journal    journal.Journal
    expediteur Expediteur
    politique  relance.Politique
}

func Nouvelle(j journal.Journal, e Expediteur, p relance.Politique) Campagne {
    return Campagne{journal: j, expediteur: e, politique: p}
}

// Executer passe une fois sur les impayes et envoie les rappels dus.
//
// maintenant est un argument. Le seul appel a time.Now du programme est dans
// main, et il est passe jusqu'ici. Une consequence a connaitre : si la passe
// dure longtemps, maintenant vieillit. C'est voulu — toute la passe raisonne
// sur le meme instant, et deux executions sur le meme etat decident la meme
// chose.
//
// GARANTI
//
//    Au plus un envoi par impaye et par palier, pour cette passe.
//    Un envoi echoue n'interrompt pas les suivants : c'est une ligne du bilan.
//    Une lecture du journal echouee interrompt tout : sans l'etat, decider
//    serait deviner.
//
// CE QUI RESTE VRAI EN CAS D'ECHEC
//
//    Tout rappel envoye a ete consigne avant de partir. L'inverse est faux : un
//    rappel peut etre consigne sans avoir ete envoye, et il est alors perdu — la
//    passe suivante ne le reprendra pas.
//
// L'ordre consigner-puis-envoyer est la decision de ce fichier. Elle echange un
// risque de doublon contre un risque de perte. Pour une relance d'impaye, le
// doublon coute plus cher que la perte : il abime une relation client et
// remplit le support, alors qu'un palier manque est rattrape par le palier
// suivant. Supprimer les deux risques a la fois demande un journal d'envoi
// separe — c'est le motif outbox, et il appartient au niveau 7.
func (c Campagne) Executer(ctx context.Context, maintenant time.Time) (Bilan, error) {
    impayes, err := c.journal.Impayes(ctx)
    if err != nil {
        return Bilan{}, fmt.Errorf("campagne : lecture des impayes : %w", err)
    }

    rappels := relance.Decider(maintenant, impayes, c.politique)
    bilan := Bilan{Decides: len(rappels)}

    for _, r := range rappels {
        if err := c.journal.Consigner(ctx, r.Reference, r.Palier, maintenant); err != nil {
            // Non consigne : on n'envoie pas. Rien n'est perdu, la passe
            // suivante redecidera le meme palier.
            bilan.Echoues++
            continue
        }
        if err := c.expediteur.Envoyer(ctx, r.Reference, r.Modele); err != nil {
            bilan.Echoues++
            continue
        }
        bilan.Envoyes++
    }
    return bilan, nil
}
```

Lis le dernier paragraphe de son commentaire : l'ordre `consigner` puis
`envoyer` est **la** décision de ce fichier, et elle échange un risque de
doublon contre un risque de perte. Pour une relance d'impayé, le doublon coûte
plus cher : il abîme une relation client et remplit le support, alors qu'un
palier manqué est rattrapé par le palier suivant. C'est un arbitrage, il est
écrit, et il est gardé par un test.

Voici le double d'expéditeur, et le test qui compte :

```go
// expediteur est un double, pas une simulation. Il ne decide rien, il
// enregistre ce qu'on lui a demande. Trente lignes de ce genre valent mieux
// qu'une bibliotheque de mocks, et surtout elles se lisent.
type expediteur struct {
    envois []string
    echoue map[string]error
}

func (e *expediteur) Envoyer(ctx context.Context, reference, modele string) error {
    if err, prevu := e.echoue[reference]; prevu {
        return err
    }
    e.envois = append(e.envois, reference+":"+modele)
    return nil
}
```

```go
// TestDeuxPassesAuMemeInstantNEnvoientPasDeuxFois est le test qui compte.
//
// Le cron tourne toutes les heures ; il sera relance apres un echec, il sera
// lance deux fois le jour ou quelqu'un deploiera pendant son execution. Cette
// propriete est la seule qui protege reellement le client, et elle n'est
// verifiable qu'avec un journal qui se souvient. Un double qui se contente de
// compter les appels ne peut pas la voir.
func TestDeuxPassesAuMemeInstantNEnvoientPasDeuxFois(t *testing.T) {
    j := journalDe("F-1", "F-2")
    e := &expediteur{}
    c := campagne.Nouvelle(j, e, politique)
    maintenant := echeance.Add(jours(5))

    if _, err := c.Executer(context.Background(), maintenant); err != nil {
        t.Fatalf("premiere passe : %v", err)
    }
    bilan, err := c.Executer(context.Background(), maintenant)
    if err != nil {
        t.Fatalf("seconde passe : %v", err)
    }

    if bilan.Decides != 0 || bilan.Envoyes != 0 {
        t.Fatalf("seconde passe : bilan = %+v, attendu rien a faire", bilan)
    }
    if len(e.envois) != 2 {
        t.Fatalf("%d envois au total, attendu 2 : %v", len(e.envois), e.envois)
    }
}
```

Ce test vérifie la seule propriété qui protège réellement le client :
**relancer la campagne deux fois n'envoie pas deux fois.** Le cron tourne toutes
les heures ; il sera relancé après un échec, il sera lancé deux fois le jour
d'un déploiement pendant son exécution.

Et il n'est vérifiable qu'avec un journal **qui se souvient**. Retiens la
distinction, parce que c'est elle qui sépare une suite de tests utile d'une
suite de tests décorative :

| | Il enregistre | Il en tire une conséquence | Il peut révéler |
|---|---|---|---|
| **double avec état** | oui | oui | l'idempotence, les doublons, l'ordre réel des effets |
| **mock sans état** | oui | non | la suite des appels, et rien d'autre |

`journalmem` fait 120 lignes. Ces 120 lignes sont ce qui rend la suite de tests
capable de voir quelque chose.

## 5. Le mauvais exemple, et pourquoi il fait mal

Même campagne. Une seule différence : elle envoie avant de consigner.

```go
// Package mauvais est la meme campagne, avec une seule difference : elle
// envoie avant de consigner.
//
// C'est l'ordre qu'on ecrit naturellement, parce qu'il suit la phrase
// « envoyer le rappel et l'enregistrer ». Il echange un risque de perte contre
// un risque de doublon, c'est-a-dire qu'il prend le plus cher des deux.
package mauvais

import (
    "context"
    "time"

    "exemple/relances/journal"
    "exemple/relances/relance"
)

type Expediteur interface {
    Envoyer(ctx context.Context, reference, modele string) error
}

type Campagne struct {
    journal    journal.Journal
    expediteur Expediteur
    politique  relance.Politique
}

func Nouvelle(j journal.Journal, e Expediteur, p relance.Politique) Campagne {
    return Campagne{journal: j, expediteur: e, politique: p}
}

func (c Campagne) Executer(ctx context.Context, maintenant time.Time) error {
    impayes, err := c.journal.Impayes(ctx)
    if err != nil {
        return err
    }
    for _, r := range relance.Decider(maintenant, impayes, c.politique) {
        if err := c.expediteur.Envoyer(ctx, r.Reference, r.Modele); err != nil {
            continue
        }
        if err := c.journal.Consigner(ctx, r.Reference, r.Palier, maintenant); err != nil {
            // Le rappel est parti. Le journal ne le sait pas. Personne ne le
            // saura jamais, et la passe suivante recommencera.
            continue
        }
    }
    return nil
}
```

C'est l'ordre qu'on écrit naturellement, parce qu'il suit la phrase « envoyer le
rappel et l'enregistrer ». Il prend le plus cher des deux risques.

Et voici sa suite de tests. Elle est verte. Elle couvre **100 % des
instructions**.

```go
// journalMock est un double SANS memoire : Consigner enregistre l'appel et
// n'en tire aucune consequence. Impayes rend toujours la meme chose.
//
// C'est la ligne qui rend la suite de tests aveugle, et c'est la ligne qu'on
// ecrit sans y penser.
type journalMock struct {
    appels          []string
    erreur          error
    erreurConsigner error
}

func (j *journalMock) Impayes(ctx context.Context) ([]relance.Impaye, error) {
    j.appels = append(j.appels, "Impayes")
    i, _ := relance.NouvelImpaye("F-1", echeance)
    return []relance.Impaye{i}, j.erreur
}

func (j *journalMock) Consigner(ctx context.Context, reference string, palier int, quand time.Time) error {
    j.appels = append(j.appels, "Consigner")
    return j.erreurConsigner
}

type expediteurMock struct {
    appels []string
    erreur error
}

func (e *expediteurMock) Envoyer(ctx context.Context, reference, modele string) error {
    e.appels = append(e.appels, "Envoyer")
    return e.erreur
}
```

```go
// 2. Le test miroir. Il decrit la suite des appels de l'implementation. Il
// passe, et il passerait aussi bien si l'ordre etait le bon — il faudrait le
// reecrire. C'est un test qui casse quand le code change et jamais quand le
// comportement est faux : exactement l'inverse de ce qu'on demande a un test.
func TestExecuterAppelleEnvoyerPuisConsigner(t *testing.T) {
    j := &journalMock{}
    e := &expediteurMock{}
    c := mauvais.Nouvelle(j, e, politique)

    if err := c.Executer(context.Background(), echeance.Add(96*time.Hour)); err != nil {
        t.Fatalf("Executer : %v", err)
    }
    if len(j.appels) != 2 || j.appels[0] != "Impayes" || j.appels[1] != "Consigner" {
        t.Fatalf("appels journal = %v", j.appels)
    }
    if len(e.appels) != 1 {
        t.Fatalf("appels expediteur = %v", e.appels)
    }
}
```

```
$ go test -v -cover -run 'TestExecuter' ./mauvais/
--- PASS: TestExecuterNePasEchouer (0.00s)
--- PASS: TestExecuterAppelleEnvoyerPuisConsigner (0.00s)
--- PASS: TestExecuterGereLesErreurs (0.00s)
PASS
coverage: 100.0% of statements
ok      exemple/relances/mauvais        0.002s  coverage: 100.0% of statements
```

Trois tests, trois défauts différents. Il faut les nommer séparément parce
qu'on les écrit séparément.

### Le test qui vérifie que rien n'explose

`TestExecuterNePasEchouer` affirme `err == nil`. Il échouerait sur une panique,
et sur rien d'autre. Ce n'est pas un test : c'est un appel de fonction entouré
d'un `if`.

Le critère pour le reconnaître : **quelle modification du code le ferait
échouer ?** Si tu ne trouves qu'une panique ou une faute de frappe, le test
mesure la compilation.

### Le test miroir

`TestExecuterAppelleEnvoyerPuisConsigner` décrit la suite des appels de
l'implémentation. Il est le plus dangereux des trois, parce qu'il a toutes les
apparences d'un vrai test : des assertions précises, un nom descriptif, un
message d'échec soigné.

Regarde ce qu'il affirme. Il affirme que l'ordre est `Envoyer` puis
`Consigner` — c'est-à-dire **le défaut**. Et il passerait aussi bien si l'ordre
était le bon : il faudrait le réécrire.

> Un test qui casse quand le code change, et jamais quand le comportement est
> faux, est l'exact inverse d'un test.

Le symptôme, dans un vrai dépôt : un refactoring sans aucun changement de
comportement casse quinze tests. On les répare, on dit que c'est normal. Ce
n'est pas normal. C'est la leçon 1.2 appliquée aux tests :

> Un test a une raison de changer, et ce doit être **la même** que celle du
> contrat qu'il garde. S'il change pour une autre raison, il garde la
> structure, pas le contrat.

Et le compteur qui le mesure, lisible dans n'importe quel dépôt :

> **Combien de tests faut-il modifier pour un refactoring qui ne change aucun
> comportement ?** La bonne réponse est zéro.

### Le mock sans mémoire

Le vrai coupable est plus discret. C'est cette ligne :

```go
func (j *journalMock) Consigner(ctx context.Context, reference string, palier int, quand time.Time) error {
    j.appels = append(j.appels, "Consigner")
    return j.erreurConsigner
}
```

`Consigner` enregistre l'appel et n'en tire **aucune conséquence**. `Impayes`
rend toujours la même chose, quoi qu'il se soit passé avant. Ce double n'a pas
de mémoire, donc aucune propriété qui dépend de la mémoire n'est observable à
travers lui — et l'idempotence est exactement ça.

C'est la ligne qui rend toute la suite aveugle, et c'est une ligne qu'on écrit
sans y penser.

### Le même code, un double qui se souvient

```go
// TestCinqPassesEnvoientCinqFoisLeMemeRappel utilise un journal qui se
// souvient, et une panne d'ecriture qui se repete.
//
// Les trois tests du fichier voisin couvrent 100 % de ce code et passent. Ce
// test-ci echouerait si l'ordre etait corrige. C'est le meme code, le meme
// nombre de doubles, et la seule difference tient en une phrase : ici le
// double a un etat, et il refuse d'ecrire.
func TestCinqPassesEnvoientCinqFoisLeMemeRappel(t *testing.T) {

    }

    }
```


Même code, même nombre de doubles, trente lignes de test. La seule différence
tient en une phrase : **ici, le double a un état, et il refuse d'écrire.**

Et le symétrique exact, sur la campagne correcte — même journal, même panne,

```
$ go test -v -run 'TestCinqPasses' ./campagne/
```

Le résultat n'est pas « ça marche ». Le résultat est : *le rappel n'est pas
parti, et le bilan le dit cinq fois*. C'est ce qu'on a acheté en choisissant la
perte plutôt que le doublon, et **le prix est inscrit dans un test**. C'est la
meilleure place pour un arbitrage : un commentaire se périme, un test échoue.

### La couverture

```
coverage: 100.0% of statements
```

Cette ligne a été produite par les trois tests ci-dessus, sur un code qui
envoie cinq fois le même rappel à un client.

> La couverture mesure ce qui a été **exécuté**, pas ce qui a été **vérifié**.
> Un test sans aucune assertion couvre parfaitement.

Elle garde une utilité, et une seule : **lue à l'envers**. Du code à 0 % est du
code que personne n'a jamais exécuté avant la production. C'est une
information. Du code à 100 % n'est pas une information.

## 6. Le lien avec la production

### Casser le code pour vérifier les tests

Un test qu'on n'a jamais vu échouer n'est pas un test vérifié. La méthode
tient en une phrase : **modifie le code, et regarde qui crie.**

Six modifications, une par décision de conception, et le relevé réel :

| # | La modification | Qui crie |
|---|---|---|
| 1 | `maintenant = time.Now()` au début de `Decider` | `TestLaRegleNeConsultePasLHorloge` + 4 cas du tableau |
| 2 | `>= pal.Apres` devient `> pal.Apres` | « pile sur le seuil, le rappel part » |
| 3 | la vérification du répit supprimée | « palier déjà envoyé, et répit non écoulé » |
| 4 | le `continue` sur un palier déjà parti supprimé | « dernier palier atteint, plus rien ensuite » + un test de campagne |
| 5 | `sort.Slice` sur `politique.Paliers` | `TestDeciderNeTouchePasAuxEntrees` |
| 6 | `envoyer` avant `consigner` dans la campagne | 2 tests de campagne |

Six sur six. Chaque modification correspond à une décision de la leçon, et
chacune a un gardien nommé. Fais ça une fois sur ton code et tu sauras ce que
valent tes tests — c'est plus rapide que d'en discuter.

### Le chiffre qui résume la leçon

| Paquet | Couverture | Modifications détectées | Ce que fait le code |
|---|---|---|---|
| `relance` | **96,9 %** | 5 / 5 | correct |
| `mauvais` | **100,0 %** | 0 | envoie 5 fois le même rappel |

Le paquet le mieux couvert est celui qui ne vérifie rien. Garde ce tableau en
tête la prochaine fois qu'on te demandera un seuil de couverture en CI.

### Ce que la modification n° 3 a révélé

Au premier passage, cette modification **a survécu** : supprimer la garde du
répit ne faisait échouer aucun test. Et l'explication était intéressante.

La garde était écrite comme ceci, dans la première version du type :

```go
type Impaye struct {
    Reference string
    Echeance  time.Time
    // DernierPalier vaut 0 quand aucun rappel n'est encore parti.
    DernierPalier int
    // DernierEnvoi n'a de sens que si DernierPalier est strictement positif.
    DernierEnvoi time.Time
}

// repitEcoule est la garde telle qu'elle etait ecrite. Le test de mutation a
// montre que la premiere moitie de la condition ne sert a rien : quand
// DernierPalier vaut 0, DernierEnvoi vaut l'an 1, et l'ecart est toujours
// superieur au repit.
//
// Elle ne sert a rien SAUF pour un Impaye incoherent — palier 0, envoi
// renseigne — que le type autorise et que la documentation interdit.
func repitEcoule(maintenant time.Time, i Impaye, repit time.Duration) bool {
    if i.DernierPalier > 0 && maintenant.Sub(i.DernierEnvoi) < repit {
        return false
    }
    return true
}
```

Quand `DernierPalier` vaut 0, `DernierEnvoi` vaut l'an 1, donc l'écart est
toujours supérieur au répit, donc la première moitié de la condition ne sert à
rien. Sauf pour un `Impaye` **incohérent** — palier 0, envoi renseigné — que le
type autorisait et que le commentaire interdisait.

Trois conduites possibles. La première : ajouter un test sur l'état incohérent.
La deuxième : supprimer la ligne. La troisième, qui est celle de ce cours :
**rendre l'état inconstruisible**, et les deux autres questions disparaissent
avec lui. C'est ce que font `NouvelImpaye` et `AvecRappel` : le palier et la
date entrent ensemble ou n'entrent pas.

Conséquences, dans l'ordre : les champs deviennent privés, la ligne défensive
disparaît, la modification n° 3 devient détectable, et deux tests sont
**supprimés** — dont celui qui documentait qu'un impayé sans échéance partait
directement en mise en demeure.

```go
// TestLesEtatsIncoherentsSontInconstruisibles remplace deux tests de la
// premiere version.
//
// Le premier documentait qu'un Impaye sans echeance partait directement en
// mise en demeure — l'an 1 comme echeance, tout delai ecoule. Le second
// n'existait pas, et un test de mutation l'a reclame : la garde sur
// dernierPalier etait indistinguable de son absence.
//
// Les deux ont disparu en meme temps que les champs publics. Ce qui etait a
// tester est devenu inconstruisible, et une ligne de code defensif a ete
// supprimee avec eux. C'est le meilleur sort qu'on puisse souhaiter a un test.
func TestLesEtatsIncoherentsSontInconstruisibles(t *testing.T) {
    if _, err := relance.NouvelImpaye("F-1", time.Time{}); !errors.Is(err, relance.ErrEcheanceAbsente) {
        t.Errorf("echeance nulle : err = %v, attendu ErrEcheanceAbsente", err)
    }
    if _, err := relance.NouvelImpaye("", echeance); !errors.Is(err, relance.ErrSansReference) {
        t.Errorf("reference vide : err = %v, attendu ErrSansReference", err)
    }
    if _, err := neuf(t, "F-1").AvecRappel(0, echeance); !errors.Is(err, relance.ErrPalierInvalide) {
        t.Errorf("palier 0 : err = %v, attendu ErrPalierInvalide", err)
    }
    if _, err := neuf(t, "F-1").AvecRappel(1, time.Time{}); !errors.Is(err, relance.ErrDateDeRappelAbsente) {
        t.Errorf("date nulle : err = %v, attendu ErrDateDeRappelAbsente", err)
    }
}
```

> Un test qui disparaît parce que le type a pris sa place est le meilleur sort
> qu'on puisse lui souhaiter.

Et la leçon de méthode, qui vaut plus que l'exemple :

> Une modification qui survit ne réclame pas toujours un test de plus.
> Quelquefois elle désigne un **état que le type n'aurait pas dû permettre**.

### Les trois axes que les tests ordinaires fixent à « parfait »

La leçon 1.4 a nommé trois choses qui traversent toute abstraction : la
**latence**, le **mode de panne**, l'**ordre**. Un test ordinaire fixe les
trois à leur valeur idéale — réponse immédiate, aucune panne, un seul appelant.

C'est pourquoi une suite verte ne dit rien de la production. Les doubles de
cette leçon sont écrits pour exercer les trois :

| Axe | Le double qui l'exerce | Ce qu'il a trouvé |
|---|---|---|
| mode de panne | `CasserProchaineEcriture` | 5 rappels envoyés pour 1 impayé |
| mode de panne | `PerdreProchainAccuse` | un rappel que le journal croit parti |
| ordre | `TestDeuxPasses…` au même instant | rien — et c'est la bonne nouvelle |

### Le test de conséquence

Un dernier genre, qu'on ne trouve dans aucun manuel et qui sauve des week-ends :

```
$ go test -v -run TestAvecUnJournalStrict ./campagne/
    campagne_test.go:175: le journal dit palier 1 parti, le client a recu 0 rappel(s), et plus rien ne sera decide avant le palier 2
--- PASS: TestAvecUnJournalStrictLeRappelDisparait (0.00s)
```

Deux décisions correctes prises séparément — *consigner avant d'envoyer*, et
*refuser une consignation en double* — produisent ensemble un rappel que le
journal croit parti, que le client n'a jamais reçu, et qu'aucune passe
ultérieure ne redécidera.

Aucune des deux décisions n'est fausse. C'est leur **combinaison** qui l'est, et
aucune revue de code ne la verra, parce que les deux décisions sont dans deux
fichiers que deux personnes différentes ont écrits.

> Un test de conséquence n'affirme pas que le système est correct. Il affirme
> qu'on sait ce qu'il fait, et il échouera le jour où l'une des deux décisions
> changera.

### Testabilité et MTTR

On y revient, parce que c'est l'argument qui convainc quand « c'est plus propre »
ne convainc pas.

> La testabilité et le débogage demandent exactement la même chose : **la
> capacité de poser une question au système sans le redémarrer.**

Reprends la version d'origine. À 3 h du matin, le support signale qu'un client a
reçu quatre mises en demeure. Les questions qu'on va se poser sont :

- Qu'est-ce que la passe de 2 h a décidé ? → *la fonction rend `error`*
- Est-ce que le palier 3 était atteint pour ce client ? → *il faut rejouer avec
  l'état de 2 h, et `time.Now()` est à l'intérieur*
- Est-ce que l'envoi a été consigné ? → *il faut lire le CSV, et il est écrasé
  chaque jour*

Les trois questions sont les étapes 2, 3 et 4 de la grille du §1. Ce ne sont pas
des questions de test. **Ce sont les questions de l'astreinte, et c'est le même
blocage qui les empêche.** Le MTTR de la leçon 1.2 — temps pour former la bonne
hypothèse, plus temps pour agir — se joue entièrement sur le premier terme, et
le premier terme est une propriété de conception.

### Trois compteurs lisibles

Ce qu'on peut mesurer dans un dépôt, sans débat :

1. **Tests à modifier pour un refactoring sans changement de comportement.**
   Cible : zéro. Au-dessus, les tests gardent la structure.
2. **`t.Skip` dans les tests de contrat.** C'est le nombre de clauses non
   vérifiées. Ce compteur doit figurer quelque part, sinon il grandit.
3. **Modifications détectées sur un échantillon de dix.** C'est la seule mesure
   de qualité de tests qui ait un rapport avec la réalité. Elle se fait à la
   main en une heure.

Aucun des trois n'est la couverture.

## 7. Ce qu'il faut retenir

1. **La difficulté d'écrire un test est une mesure de la conception**, pas une
   propriété du test.
2. **Quatre étapes, quatre défauts.** Construire → trop de dépendances. Amener
   dans l'état → état non adressable. Déclencher → déclencheur à l'intérieur.
   Observer → le résultat est un effet.
3. **On ne corrige pas un test difficile, on corrige ce qu'il mesure.**
4. **Rendre testable = trois transformations** : dépendance → argument, effet →
   valeur, état global → paramètre. Aucune ne parle de tests.
5. **Toute couture ouverte pour un test est ouverte pour un abus.** On
   n'injecte pas pour tester : on injecte quand le remplaçant a un demandeur
   en production.
6. **Le temps n'est pas une dépendance, c'est une donnée à faire descendre.**
7. **Trois étages de tests** : contrat (l'appelant), implémentation
   (l'astreinte), décision (le futur mainteneur).
8. **Un test de décision échoue le jour d'une décision contraire**, pas le jour
   d'un bug.
9. **La clause qu'on ne teste jamais** est « ce qui reste vrai en cas d'échec »,
   et c'est celle qui décide du comportement sous panne.
10. **Un double sans mémoire ne peut révéler que la suite des appels.**
11. **La couverture mesure l'exécution, pas la vérification.** Utile lue à
    l'envers, inutile lue à l'endroit.
12. **Un test qu'on n'a jamais vu échouer n'est pas vérifié.** Casse le code et
    regarde qui crie.
13. **Une modification qui survit peut désigner un état que le type n'aurait pas
    dû permettre.**
14. **Testabilité et MTTR sont la même propriété**, mesurée à deux moments.

## 8. Approfondissement

### Le test interne, et la couture qui ne sort pas

Il reste un cas où l'on a besoin d'une couture et où l'on ne veut pas l'ouvrir
au public. Go a une réponse propre : un fichier de test déclaré **dans** le
paquet voit les identifiants non exportés.

```go
package coffre

// Ce fichier est compile uniquement pendant les tests du paquet. La couture
// existe pour eux, et elle n'existe pas pour les appelants.
var SeuilInterne = &seuil
```

La hiérarchie de la leçon 1.1 s'applique telle quelle à la question « où mettre
la couture de test » :

| Niveau | Mécanisme | Ce que ça donne |
|---|---|---|
| 🟡 | une convention de nommage, un commentaire | rien, dès le deuxième développeur |
| 🟠 | une méthode exportée documentée « pour les tests » | elle sera appelée en production |
| 🔴 | un fichier `export_test.go` | invisible hors des tests du paquet |
| ⚫ | pas de couture du tout : l'argument descend | rien à abuser |

Les deux derniers niveaux sont ceux de cette leçon : `maintenant` en argument
est le ⚫, `export_test.go` est le 🔴 quand le ⚫ n'est pas atteignable.

### Ce qu'un test de contrat ne peut jamais vérifier

Trois choses, et il faut les savoir pour ne pas se croire couvert :

- **Ce qui n'est pas dans l'interface.** La porte de panne, la latence, le coût
  d'un appel. Ils appartiennent à l'étage d'implémentation.
- **Le comportement de l'implémentation réelle.** `journalmem` passe tout le
  contrat et ne prouve rien sur PostgreSQL. Le contrat dit que les deux se
  comportent pareil *sur les clauses énoncées* ; il ne dit pas que les clauses
  énoncées suffisent.
- **Les clauses qu'on n'a pas écrites.** C'est de loin la plus grosse catégorie,
  et c'est pourquoi le tableau des issues de la leçon 1.5 se fait avant le
  contrat, pas après.

### `-race`, `-count`, et les tests qui ne prouvent rien

Trois réflexes, chacun contre un faux vert particulier :

- `go test -race` : le seul moyen d'exercer l'axe « ordre ». Un test concurrent
  sans `-race` est un test séquentiel écrit avec plus de lignes.
- `go test -count=20` : un test qui dépend d'un parcours de `map` ou d'un
  ordonnancement passe presque toujours une fois. On l'a utilisé en 1.3, où
  l'étalement a fait passer un test de « 0 refus » à « 46 refus ».
- `t.Parallel()` partout, puis un état partagé entre tests : c'est le moyen le
  plus rapide de rendre une suite non reproductible. Si deux tests partagent
  quelque chose, la question n'est pas comment les paralléliser — c'est ce que
  ce quelque chose fait là.

### Le meilleur test est celui qui ne compile plus

Classement des garde-fous, appliqué aux tests :

> Un état que le type interdit n'a pas besoin de test. Un test qui ne compile
> plus après une modification est plus fort qu'un test qui échoue, parce qu'il
> ne peut pas être ignoré, désactivé ni marqué *flaky*.

C'est pourquoi la modification n° 3 de ce chapitre n'a pas abouti à un test de
plus : elle a abouti à deux constructeurs, et aux tests qui ont disparu avec.

## 9. Ce que la testabilité n'est pas

Six confusions qui coûtent cher.

1. **Ce n'est pas la couverture.** Démontré ci-dessus : 100 % sur un code
   fautif, 96,9 % sur le code correct.
2. **Ce n'est pas « beaucoup de tests ».** Trois tests qui détectent six
   modifications valent mieux que quarante qui n'en détectent aucune. La
   quantité de tests mesure l'effort, pas la couverture du risque.
3. **Ce n'est pas une interface par dépendance.** Chaque interface est une
   couture publique. Le critère reste : le remplaçant a-t-il un demandeur ?
4. **Ce n'est pas un mock par collaborateur.** Un double qui n'a pas d'état ne
   peut révéler que la suite des appels. On écrit des **doubles avec mémoire**,
   et on n'en écrit que pour ce qu'on ne possède pas.
5. **Ce n'est pas TDD.** L'ordre dans lequel tu écris le test et le code est une
   question de méthode de travail. La testabilité est une propriété du code
   fini. On peut écrire du code intestable en TDD : il suffit d'injecter tout.
6. **Ce ne sont pas des tests qui ne cassent jamais.** Une suite qui ne casse
   jamais ne mesure rien. Une suite qui casse pour une raison métier fait son
   travail ; une suite qui casse pour une raison structurelle garde la mauvaise
   chose.

Et la confusion-mère, celle qui produit les cinq autres :

> **Simuler ce qu'on possède.** Si tu dois simuler ton propre module pour
> tester, ce n'est pas un problème de test : c'est que ce module fait un effet
> là où il devrait rendre une valeur. On ne simule que ce qu'on ne possède pas.

## 10. Le réflexe à installer

Devant un morceau de code dont tu doutes, n'en discute pas. **Essaie de
l'interroger**, et note où ça bloque :

> | étape | ce qu'il me faut | ce que ça révèle |
> |---|---|---|
> | construire | | |
> | amener dans l'état | | |
> | déclencher | | |
> | observer | | |

Puis, devant chaque test que tu t'apprêtes à écrire, une seule question :

> **Quelle modification du code ferait échouer ce test ?**

Si tu ne trouves qu'une panique, le test mesure la compilation. Si tu ne trouves
qu'un renommage, le test garde la structure. Si tu trouves un changement de
comportement que quelqu'un peut réclamer un jour, c'est un test.

Et avant d'ouvrir une couture pour tester, la question du §3 :

> **Ce remplaçant a-t-il un demandeur en production ?** Si non, fais descendre
> l'argument plutôt que d'injecter la dépendance.

## Le niveau 1, en une question

Six leçons, six questions. Elles n'en font qu'une, et c'est celle qui reste
quand on a oublié le reste :

| | La question | Ce qu'elle produit |
|---|---|---|
| 1.1 | Qui possède cette donnée, et qui a le droit de la modifier ? | des effets localisés |
| 1.2 | Qui peut exiger que ça change ? | des frontières |
| 1.3 | Que suppose ce module sur les autres sans le dire ? | des coutures |
| 1.4 | Qu'est-ce que l'appelant a le droit de ne pas savoir ? | des contrats |
| 1.5 | Quelles sont les issues, et qui décide de chacune ? | des conduites |
| 1.6 | De quoi ai-je besoin pour poser une question à ce code ? | la vérification des cinq précédentes |

> **Qu'est-ce que ce code me force à savoir, et qui a le droit de l'exiger ?**

Tout le niveau 2 — objets, polymorphisme, SOLID — n'est qu'une collection de
réponses déjà rédigées à cette question. On ne les apprendra pas comme des
règles. On les lira comme des réponses, et on demandera chaque fois à quelle
question elles répondaient, et ce qui arrive quand ce n'est pas la tienne.
