# Leçon 1.6 — La testabilité comme révélateur de conception

## L'essentiel en deux minutes

**Le problème, en une phrase.** Quand un test est pénible à écrire, ce
n'est presque jamais le test qui est mal fait : c'est le code qui cache
quelque chose.

**L'image.** Une voiture dont on ne peut vérifier le niveau d'huile qu'en
démontant le moteur. Le garagiste n'est pas maladroit : c'est la voiture qui
est mal conçue. Une jauge accessible ne sert pas qu'au garagiste — elle sert
aussi au conducteur. De même, ce qui rend un code facile à tester le rend
facile à comprendre et à réparer en production.

**Le code, en une vingtaine de lignes.**

```go
// Package e16 is the two-minute version of lesson 1.6.
package e16

import (
    "fmt"
    "time"
)

// RemindHidden reads the clock and sends the mail itself. To test it, you
// must wait until the card expires, and catch a real mail.
func RemindHidden(expires time.Time, send func(to, body string) error, to string) error {
    if time.Until(expires) < 7*24*time.Hour {
        return send(to, fmt.Sprintf("your card expires on %s", expires.Format(time.DateOnly)))
    }
    return nil
}

// Reminder takes the time as data and returns the mail as a value. The
// caller reads the clock and sends; the decision is testable alone.
func Reminder(expires, now time.Time) (body string, due bool) {
    if expires.Sub(now) >= 7*24*time.Hour {
        return "", false
    }
    return fmt.Sprintf("your card expires on %s", expires.Format(time.DateOnly)), true
}
```

Pour tester `RemindHidden`, il faudrait attendre qu'une carte expire
vraiment, et intercepter un vrai courriel. `Reminder` fait **la même
décision** sans rien cacher : l'heure arrive en paramètre, le courriel
repart en valeur. Le test choisit l'heure et lit le résultat. Celui qui
appelle `Reminder` lit l'horloge et envoie — deux lignes, sans décision à
tester.

**Les règles à retenir.**

1. La difficulté d'écrire un test **mesure** la conception. On ne corrige
   pas le test, on corrige ce qu'il mesure.
2. Quatre étapes d'un test, quatre défauts possibles : *construire* (trop de
   dépendances), *amener dans l'état* (état inaccessible), *déclencher*
   (déclencheur caché à l'intérieur), *observer* (le résultat est un effet,
   pas une valeur).
3. Trois transformations rendent testable : une dépendance devient un
   argument, un effet devient une valeur, un état global devient un
   paramètre.
4. Le temps est une **donnée** : on le fait descendre en paramètre.
5. Un test que tu n'as jamais vu échouer n'a rien vérifié : casse le code et
   regarde qui crie.

Cette leçon n'est pas une leçon sur les tests. Elle ne t'apprendra pas à écrire
un test : tu en écris déjà. Elle utilise les tests comme un **instrument de
mesure** braqué sur ta conception.

Les cinq leçons précédentes t'ont donné cinq questions à poser à un morceau de
code : qui possède cette donnée (1.1), qui peut exiger que ça change (1.2), que
suppose ce module sur les autres (1.3), ce que l'appelant a le droit de ne pas
savoir (1.4), quelles sont les issues et qui décide (1.5). Toutes ont le même
défaut : elles demandent un jugement. Deux personnes honnêtes peuvent ne pas
être d'accord.

La testabilité n'a pas ce défaut. Elle produit un **fait** :

> Tu essaies d'écrire le test. Soit tu y arrives en dix lignes, soit tu n'y
> arrives pas. Il n'y a rien à discuter.

C'est la seule des six questions qui se mesure avec un chronomètre, et c'est
pour ça qu'elle clôt le niveau.

## 1. Le concept, simplement

### Un test fait exactement quatre choses

Quel que soit le langage, le framework, le style, un test exécute quatre
étapes :

1. **Construire** le sujet.
2. **L'amener** dans l'état voulu.
3. **Déclencher** le comportement.
4. **Observer** le résultat.

C'est tout. Et la phrase qui tient toute la leçon :

> La difficulté d'écrire un test n'est pas une propriété du test. C'est une
> **mesure de la conception** du code testé.

Quand un test est pénible à écrire, l'erreur est de rendre le test plus
sophistiqué. La bonne conduite est de regarder **laquelle des quatre étapes
fait mal**, parce que chacune désigne un défaut précis.

### La grille des quatre douleurs

| L'étape qui fait mal | Ce que le code t'impose | Le défaut de conception | Nommé en |
|---|---|---|---|
| **Construire** | une base, un serveur SMTP, un client HTTP, un fichier | trop de dépendances pour une seule responsabilité | 1.2, 1.3 |
| **Amener dans l'état** | une variable de paquet, une migration, un `init()`, une variable d'environnement | l'état n'est pas adressable depuis l'extérieur | 1.1, 1.3 |
| **Déclencher** | attendre, dormir, lancer un cron, faire tomber le réseau | le déclencheur est à l'intérieur au lieu d'être un argument | 1.4 |
| **Observer** | lire un fichier, requêter la base, lire un log | le résultat est un effet, pas une valeur | 1.1, 1.5 |

Retiens la grille : *dis-moi où tu as mal, je te dirai ce qui est mal conçu*.
Elle est la réciproque des cinq leçons précédentes, et elle sert dans l'autre
sens — tu n'as pas besoin de juger un code pour le diagnostiquer, il suffit
d'essayer de l'interroger.

### Le test décisif de la leçon

> **De quoi ai-je besoin pour poser une question à ce code ?**

Si la réponse tient en un appel de fonction, la conception est bonne, quel que
soit l'avis de qui que ce soit sur l'élégance du résultat. Si la réponse
commence par « il faut démarrer », la conception a un problème — et le test
n'en est que le messager.

## 2. L'intuition

Un tableau électrique, dans un immeuble de Douala.

Deux tableaux font le même travail. Le premier est un bloc fermé : les fils
entrent, les fils sortent, rien n'est accessible. Le second a des **bornes de
mesure** — des points où l'on pose les pointes d'un multimètre sans rien
démonter.

Les deux distribuent le courant exactement pareil. La différence n'apparaît que
le jour où ça ne marche plus.

Sur le premier, pour savoir si le courant passe au troisième étage, il faut
couper, dénuder, mesurer, rebrancher. Le diagnostic coûte une coupure. Donc on
ne diagnostique pas : on remplace le disjoncteur le plus probable, on remet le
courant, et on verra bien. Sur le second, on mesure en quinze secondes, sans
rien couper.

Deux choses à noter, et ce sont les deux moitiés de la leçon.

La première : **personne n'installe des bornes de mesure « pour les tests »**.
On les installe parce qu'un tableau qu'on ne peut pas mesurer est un tableau
qu'on ne peut pas réparer. La testabilité et la réparabilité sont la même
propriété, mesurée à deux moments différents.

La seconde : **une borne de mesure est aussi un point où l'on peut brancher
n'importe quoi.** Ouvrir un accès pour mesurer, c'est ouvrir un accès. On y
reviendra au §3 — c'est le coût qu'on oublie toujours de compter.

## 3. Le mécanisme

### Le sujet : une campagne de relance d'impayés

Voici la fonction d'origine. Elle tourne depuis deux ans, elle est appelée par
un cron horaire, elle est lisible, et elle marche.

```go
// Package before is the original version of the reminder campaign: one
// function, forty lines, and nothing testable.
//
// It is not badly written. It is readable, it works, and it ran for
// two years. That is the point: lack of testability does not show on
// reading. It shows when one tries.
package before

import (
    "context"
    "database/sql"
    "fmt"
    "net/smtp"
    "os"
    "strconv"
    "time"
)

// The tier and the grace period are read at program start. Changing them
// in a test requires changing the environment of the test process.
var (
    firstTier  = daysFromEnv("REMINDER_TIER_1", 3)
    secondTier = daysFromEnv("REMINDER_TIER_2", 10)
    graceHours = int64(72)
    sent       int // global counter, for the end-of-day log
)

func daysFromEnv(key string, fallback int) time.Duration {
    if v := os.Getenv(key); v != "" {
        if n, err := strconv.Atoi(v); err == nil {
            return time.Duration(n) * 24 * time.Hour
        }
    }
    return time.Duration(fallback) * 24 * time.Hour
}

// RemindUnpaid is called by the hourly cron.
func RemindUnpaid(ctx context.Context, db *sql.DB, server, from string) error {
    now := time.Now()

    lines, err := db.QueryContext(ctx,
        `SELECT reference, email, due, last_tier, last_sent
           FROM unpaid WHERE rule = false`)
    if err != nil {
        return err
    }
    defer lines.Close()

    report, err := os.Create("/var/reports/reminders-" + now.Format("2006-01-02") + ".csv")
    if err != nil {
        return err
    }
    defer report.Close()

    for lines.Next() {
        var reference, email string
        var due, lastSent time.Time
        var lastTier int
        if err := lines.Scan(&reference, &email, &due, &lastTier, &lastSent); err != nil {
            return err
        }

        late := now.Sub(due)
        tier := 0
        template := ""
        switch {
        case late >= secondTier && lastTier < 2:
            tier, template = 2, "firm"
        case late >= firstTier && lastTier < 1:
            tier, template = 1, "courteous"
        }
        if tier == 0 {
            continue
        }
        if lastTier > 0 && now.Sub(lastSent).Hours() < float64(graceHours) {
            continue
        }

        body := fmt.Sprintf("Subject: Reminder\r\n\r\nInvoice %s unpaid. (%s)", reference, template)
        if err := smtp.SendMail(server, nil, from, []string{email}, []byte(body)); err != nil {
            fmt.Fprintf(report, "%s;%d;failed\n", reference, tier)
            continue
        }
        if _, err := db.ExecContext(ctx,
            `UPDATE unpaid SET last_tier = $1, last_sent = $2 WHERE reference = $3`,
            tier, now, reference); err != nil {
            fmt.Fprintf(report, "%s;%d;not-recorded\n", reference, tier)
            continue
        }
        sent++
        fmt.Fprintf(report, "%s;%d;ok\n", reference, tier)
    }
    return lines.Err()
}
```

Elle n'est pas mal écrite. C'est le point : **l'absence de testabilité ne se
voit pas à la lecture.** Elle se voit quand on essaie. Essayons, étape par
étape.

### Étape 1 — construire

Pour appeler `RemindUnpaid`, il faut un `*sql.DB` et une adresse de serveur
SMTP. Pas une interface : le type concret du pilote de base de données. Donc,
pour poser la moindre question à la règle des paliers, il faut une base.

Ce que ça révèle : la règle de décision et l'accès au stockage sont dans la
même unité. **Deux demandeurs différents** — le responsable du recouvrement
pour les paliers, l'équipe infrastructure pour la base — ont une seule porte
d'entrée. C'est la leçon 1.2, et le test vient de le mesurer sans qu'on ait eu
à juger quoi que ce soit.

### Étape 2 — amener dans l'état

Les paliers sont dans des variables de paquet, initialisées depuis
l'environnement du processus. Pour tester un palier à 5 jours, il faut modifier
l'environnement du processus de test. Et `sent` est un compteur global : le
deuxième test de la suite part d'un état laissé par le premier.

Ce que ça révèle : c'est du couplage par état global, degré 4 de l'échelle de
la leçon 1.3. **Les tests sont le premier appelant à en souffrir, et ils en
souffrent au même endroit que la production** — le jour où deux campagnes
tournent dans le même processus.

### Étape 3 — déclencher

`now SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f:= SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2ftime.Now()`, première ligne. Il n'existe aucun moyen de demander
à cette fonction *« que décides-tu le 14 mars à 9 h ? »*. La seule façon de
tester le palier à 30 jours est d'attendre trente jours, ou de changer l'heure
de la machine.

Ce que ça révèle : le déclencheur de la décision est **à l'intérieur** de la
décision. On y revient dans une minute, parce que la réponse usuelle à ce
problème est mauvaise.

### Étape 4 — observer

La fonction rend `error`. Les décisions — *tel impayé, tel palier, tel modèle*
— n'apparaissent nulle part dans sa valeur de retour. Pour savoir ce qu'elle a
décidé, il faut lire un fichier CSV dans `/var/rapports/`, ou interroger la
base, ou lire les logs du serveur SMTP.

Ce que ça révèle : **le résultat du calcul est un effet de bord**. C'est la
leçon 1.1 dans sa forme la plus coûteuse — non seulement pour le test, mais
pour l'astreinte, qui n'a elle non plus aucun moyen de savoir ce que la dernière
passe a décidé.

### La règle de l'instrument

Quatre étapes, quatre blocages, quatre défauts déjà nommés dans les leçons
précédentes. D'où la règle :

> On ne corrige pas un test difficile. On corrige **ce qu'il mesure**.

Un test difficile qu'on rend possible à coups d'outillage — une base éphémère,
un faux serveur SMTP, une variable d'environnement posée dans `TestMain` — ne
guérit rien. Il déplace le symptôme et il ajoute une deuxième chose à
maintenir.

### Ce que « rendre testable » veut dire exactement

Trois transformations, pas une de plus :

| Avant | Après |
|---|---|
| une **dépendance** | un **argument** |
| un **effet** | une **valeur rendue** |
| un **état global** | un **paramètre** |

Aucune des trois ne parle de tests. Les trois sont des décisions de conception
que les leçons 1.1 à 1.5 recommandaient déjà. **Le test ne demande rien de
neuf : il rend visible ce qu'on n'a pas fait.**

### Le coût qu'on oublie de compter

Voici où presque tout le monde se trompe, y compris dans des bases de code
soignées.

La réponse réflexe au problème de l'horloge est : *« injecte une interface
`Clock` »*.

```go
// Package illustration only serves so that the excerpts quoted in the lesson
// are compiled like the others. Nothing here is used by the campaign.
package illustration

import "time"

// Clock is the reflex answer to the problem of time. It works, and it
// costs one more public seam.
type Clock interface {
    Now() time.Time
}

type Service struct {
    clock Clock
}
```

Ça marche. Et ça coûte trois choses qu'on ne compte jamais :

1. Un **point d'extension public** de plus. `Service` accepte désormais
   n'importe quelle horloge, y compris en production. Quelqu'un, un jour, y
   mettra une horloge décalée pour rattraper un lot, et ce sera un mardi soir.
2. Une **question de plus** dans la tête de chaque lecteur : quelle horloge
   est-ce, ici ?
3. Un **mensonge possible** : le test passe avec une horloge figée, la
   production tourne avec une horloge qui avance, et la différence entre les
   deux n'est testée par rien.

> Toute couture ouverte pour un test est aussi une couture ouverte pour un
> abus.

D'où le critère d'arrêt, qui est la vraie règle de ce paragraphe :

> **On n'injecte pas pour tester. On injecte quand le remplaçant a un demandeur
> en production.**

Et pour le temps, il existe presque toujours mieux :

> Le temps n'est pas une dépendance à injecter. C'est une **donnée à faire
> descendre**.

`Decide(now, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f…)` ne demande aucune interface, aucun double, aucune
configuration. Il y a exactement un appel à `time.Now()` dans tout le
programme, il est dans `main`, et `main` n'a pas besoin de test. Une couture
en moins, un point d'extension en moins, et un test qui tient en trois lignes.

## 4. Le bon exemple

### La règle, et le type qui ne peut pas être incohérent

```go
// Package reminder decides which unpaid reminders must leave.
//
// It reads nothing, writes nothing, sends nothing and does not read the time. It
// receives a state and returns decisions. Everything in this file that
// looks like a dependency is in fact an argument.
package reminder

import (
    "errors"
    "time"
)

var (
    // ErrNoReference: an unpaid without a reference can be neither reminded nor
    // recorded.
    ErrNoReference = errors.New("reminder: unpaid without reference")
    // ErrMissingDue: without a due date, any delay is infinite. A missing
    // due date is not an old due date.
    ErrMissingDue = errors.New("reminder: unpaid without due date")
    // ErrInvalidTier: tiers start at 1.
    ErrInvalidTier = errors.New("reminder: invalid tier")
    // ErrMissingReminderDate: a reminder that left has a date.
    ErrMissingReminderDate = errors.New("reminder: reminder without send date")
)

// Unpaid is the state of an overdue invoice.
//
// Its fields are private, and a mutation test decided it. In the
// first version they were public, with a documentation sentence
// saying lastSent made sense only if lastTier was non-zero.
// A documentation sentence prevents nothing: the inconsistent state could still
// be built, a line of code defended against it, and no test could
// tell whether this line was useful.
type Unpaid struct {
    reference string
    due       time.Time
    lastTier  int
    lastSent  time.Time
}

// NewUnpaid builds an unpaid on which no reminder has left yet.
// It is the only way in, and it refuses what the rule cannot
// handle.
func NewUnpaid(reference string, due time.Time) (Unpaid, error) {
    if reference == "" {
        return Unpaid{}, ErrNoReference
    }
    if due.IsZero() {
        return Unpaid{}, ErrMissingDue
    }
    return Unpaid{reference: reference, due: due}, nil
}

// WithReminder returns a copy carrying the trace of a reminder already sent. The tier
// and the date come in together or not at all: there is no state left where one
// is set without the other.
func (i Unpaid) WithReminder(tier int, when time.Time) (Unpaid, error) {
    if tier < 1 {
        return Unpaid{}, ErrInvalidTier
    }
    if when.IsZero() {
        return Unpaid{}, ErrMissingReminderDate
    }
    i.lastTier = tier
    i.lastSent = when
    return i, nil
}

// Reference identifies the invoice.
func (i Unpaid) Reference() string { return i.reference }

// LastTier returns the tier of the last reminder sent, or 0 if none.
func (i Unpaid) LastTier() int { return i.lastTier }

// Tier is one step of the reminder policy.
type Tier struct {
    // Number is the tier's rank. It starts at 1.
    Number int
    // After is the delay since the due date beyond which this tier applies.
    After time.Duration
    // Template names the text to send. The text itself is not here: it
    // changes for another reason than the policy.
    Template string
}

// Policy is the whole rule. Both fields change together: whoever
// changes the tiers reconsiders the grace period.
type Policy struct {
    Tiers []Tier
    // Grace is the minimum delay between two reminders for the same unpaid.
    Grace time.Duration
}

// Reminder is a decision: this reminder must leave.
type Reminder struct {
    Reference string
    Tier      int
    Template  string
}

// Decide returns the reminders to send at instant now.
//
// GUARANTEED
//
//    For a given unpaid, at most one reminder: the one of the highest tier
//    reached and not yet sent.
//    The output order follows the input order. Two calls with the same
//    arguments return exactly the same result.
//
// WHAT STAYS TRUE
//
//    unpaid and policy are not modified. None of their slices is
//    sorted, reordered or written in place.
//
// NOT GUARANTEED
//
//    That the reminder is relevant: if the caller provides an unpaid already settled,
//    the reminder is decided anyway. Knowing what is unpaid is not the
//    job of this function.
//
// now is an ARGUMENT, not a dependency. It is the difference between a
// module tested with three lines and a module that needs an injected
// injected, so one more public seam.
func Decide(now time.Time, unpaid []Unpaid, policy Policy) []Reminder {
    var out []Reminder
    for _, i := range unpaid {
        if r, ok := decideOne(now, i, policy); ok {
            out = append(out, r)
        }
    }
    return out
}

func decideOne(now time.Time, i Unpaid, p Policy) (Reminder, bool) {
    // No sorting: full scan, we keep the maximum. Sorting would be one line
    // shorter and would modify the caller's slice.
    reached := -1
    template := ""
    for _, tier := range p.Tiers {
        if tier.Number <= i.lastTier {
            continue
        }
        // The threshold is reached AS SOON AS the delay is over: >= and not >.
        if now.Sub(i.due) >= tier.After && tier.Number > reached {
            reached = tier.Number
            template = tier.Template
        }
    }
    if reached < 0 {
        return Reminder{}, false
    }
    // No more guard on lastTier: an unpaid without an earlier reminder has a
    // zero lastSent, so an infinite gap, so a grace period always over.
    // The inconsistent case that justified the guard can no longer be built.
    if now.Sub(i.lastSent) < p.Grace {
        return Reminder{}, false
    }
    return Reminder{Reference: i.reference, Tier: reached, Template: template}, true
}
```

Trois choses à voir.

**L'instant est un argument.** Pas d'horloge, pas d'interface, pas de double.
Le test choisit le 14 mars à 9 h en l'écrivant.

**La clause « CE QUI RESTE VRAI » est dans le contrat.** C'est la leçon 1.5 :
`Decide` promet de ne pas toucher aux tranches qu'on lui passe. Cette promesse
est tenue par une décision visible dans le code — ne pas trier — et gardée par
un test qu'on verra plus bas.

**Les champs de `Unpaid` sont privés, et c'est un test qui l'a décidé.** Le
§6 raconte comment. Pour l'instant, note seulement ce que ça supprime : il n'y
a plus d'`Unpaid` dont le palier est renseigné sans la date, ni d'`Unpaid` sans
échéance. Donc plus de ligne de code défensive contre ces cas, donc plus de
test pour cette ligne.

### Le test de la règle

Le fichier en entier jusqu'au cinquième cas sur six :

```go
// The few setup lines below are all the tooling
// needed, and it is the only measure of testability that counts.
var policy = reminder.Policy{
    Tiers: []reminder.Tier{
        {Number: 1, After: 3 * 24 * time.Hour, Template: "courteous"},
        {Number: 2, After: 10 * 24 * time.Hour, Template: "firm"},
        {Number: 3, After: 30 * 24 * time.Hour, Template: "formal-notice"},
    },
    Grace: 72 * time.Hour,
}

var due = time.Date(2026, time.March, 1, 9, 0, 0, 0, time.UTC)

func days(n int) time.Duration { return time.Duration(n) * 24 * time.Hour }

func fresh(t *testing.T, ref string) reminder.Unpaid {
    t.Helper()
    i, err := reminder.NewUnpaid(ref, due)
    if err != nil {
        t.Fatalf("NewUnpaid: %v", err)
    }
    return i
}

func reminded(t *testing.T, ref string, tier int, when time.Time) reminder.Unpaid {
    t.Helper()
    i, err := fresh(t, ref).WithReminder(tier, when)
    if err != nil {
        t.Fatalf("WithReminder: %v", err)
    }
    return i
}

func TestDecide(t *testing.T) {
    tc := []struct {
        name     string
        after    time.Duration // since the due date
        unpaid   func(*testing.T) reminder.Unpaid
        want     []int // the tiers expected as output
        why string
    }{
        {
            name:     "before the first tier, nothing",
            after:   days(2),
            unpaid:  func(t *testing.T) reminder.Unpaid { return fresh(t, "F-1") },
            want: nil,
        },
        {
            name:      "exactly on the threshold, the reminder leaves",
            after:    days(3),
            unpaid:   func(t *testing.T) reminder.Unpaid { return fresh(t, "F-1") },
            want:  []int{1},
            why: "the threshold is reached as soon as the delay is over",
        },
        {
            name:      "40 days late does not trigger three reminders",
            after:    days(40),
            unpaid:   func(t *testing.T) reminder.Unpaid { return fresh(t, "F-1") },
            want:  []int{3},
            why: "at most one reminder per unpaid, the one of the highest tier",
        },
        {
            name:   "tier already sent, and grace not over",
            after: days(11),
            unpaid: func(t *testing.T) reminder.Unpaid {
                return reminded(t, "F-1", 1, due.Add(days(10)))
            },
            want: nil,
        },
        {
            name:   "tier already sent, grace over",
            after: days(14),
            unpaid: func(t *testing.T) reminder.Unpaid {
                return reminded(t, "F-1", 1, due.Add(days(10)))
            },
            want:  []int{2},
            why: "the grace period protects the client, it does not remove the tier",
        },
```

`setup`, pas de `defer SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fcleanup`, pas de base éphémère, pas de `TestMain`, pas
une ligne de nettoyage. Deux constructeurs, un raccourci pour écrire des
journées, et c'est tout l'outillage. C'est la mesure, et c'est la seule qui
compte.

Note aussi la colonne `why`. Elle n'est pas de la décoration : quand le
test échoue, le message dit *pourquoi ce cas existe*, et c'est ce dont a besoin
la personne qui le lira dans deux ans — probablement parce qu'elle vient de le
casser.

### Les trois étages de tests

La leçon 1.4 annonçait deux étages. Il y en a trois, et le troisième est celui
qu'on n'écrit jamais.

| Étage | Il garde | Son demandeur | Il échoue quand | Il ne verra jamais |
|---|---|---|---|---|
| **contrat** | ce que l'appelant a le droit d'attendre | l'appelant | une implémentation ne tient plus sa promesse | la latence, le coût, la forme du stockage |
| **implémentation** | ce que l'exploitant a le droit d'exiger | l'astreinte | une implémentation devient lente, non réentrante, bavarde | ce qu'une autre implémentation ferait |
| **décision** | une décision de conception | le futur mainteneur | quelqu'un prend la décision contraire | tout comportement |

Le troisième mérite sa définition :

> Un **test de décision** n'échoue pas le jour d'un bug. Il échoue le jour où
> quelqu'un prend une décision contraire. C'est le seul test qui parle au
> mainteneur plutôt qu'au programme.

Tu en as déjà écrit un sans le nommer : le test de graphe d'imports de la leçon
1.2, qui garantit que le module de règles n'a **aucun moyen** d'envoyer un
email. Ce n'était pas un test de comportement. C'était un garde-fou 🟡 chargé de
maintenir un ⚫ dans le temps.

### Trois tests de décision, trois mécanismes

Les tests de décision se rangent par **ce qu'ils inspectent**, et c'est ce qui
détermine leur portée.

**1. Par la valeur** — on appelle, et on vérifie que l'entrée n'a pas bougé :

```go
// TestDecideLeavesItsInputs guards the clause "WHAT STAYS TRUE".
// There is no bug today. This test exists for the day someone
// replaces the scan of decideOne with a sort.Slice on policy.Tiers
// : one line fewer, and the caller's slice reordered behind its back.
func TestDecideLeavesItsInputs(t *testing.T) {
    tiers := []reminder.Tier{
        {Number: 3, After: days(30), Template: "formal-notice"},
        {Number: 1, After: days(3), Template: "courteous"},
        {Number: 2, After: days(10), Template: "firm"},
    }
    p := reminder.Policy{Tiers: tiers, Grace: 72 * time.Hour}
    unpaid := []reminder.Unpaid{fresh(t, "F-2"), fresh(t, "F-1")}

    tiersBefore := append([]reminder.Tier(nil), tiers...)
    unpaidBefore := append([]reminder.Unpaid(nil), unpaid...)

    reminder.Decide(due.Add(days(40)), unpaid, p)

    for i := range tiersBefore {
        if tiers[i] != tiersBefore[i] {
            t.Fatalf("tiers[%d] changed: %+v -> %+v", i, tiersBefore[i], tiers[i])
        }
    }
    for i := range unpaidBefore {
        if unpaid[i] != unpaidBefore[i] {
            t.Fatalf("unpaid[%d] changed", i)
        }
    }
}
```

Il n'y a aucun bug aujourd'hui. Ce test ne sert à rien aujourd'hui. Il servira
le jour où quelqu'un remplacera le parcours par un `sort.Slice` sur
`policy.Tiers` — une ligne de moins, un code plus clair, et la tranche de
l'appelant réordonnée à son insu. Les tests de décision ont tous cette forme :
**ils sont inutiles jusqu'au jour où ils sont la seule chose qui reste.**

**2. Par la répétition** — on appelle cinquante fois et on compare. C'est ce que
fait `TestDeciderEstDeterministe` : un parcours de `map` ne se trahit pas au
premier essai, et la promesse d'ordre du contrat ne vaut rien si on ne la vérifie
qu'une fois.

**3. Par la lecture du code** — quand la décision n'est visible dans aucune
valeur :

```go
// Package guard holds only decision tests. They check no
// behavior: they check that design decisions still hold.
//
// A decision test does not fail on the day of a bug. It fails on the day
// someone takes the opposite decision, and it is the only test that speaks to the
// maintainer rather than to the program.
package guard

import (
    "go/ast"
    "go/parser"
    "go/token"
    "os/exec"
    "path/filepath"
    "strings"
    "testing"
)

// TestTheRuleDoesNotReadTheClock guards the central decision of the module
// reminder: the instant is an argument.
//
// No import graph can see this decision: reminder imports time
// legitimately, for the time.Time type. Checking it therefore requires reading the
// code, and that is what this test does. It is the tool of last resort, to
// keep for decisions no language mechanism protects.
func TestTheRuleDoesNotReadTheClock(t *testing.T) {
    files, err := filepath.Glob("../relance/*.go")
    if err != nil {
        t.Fatalf("glob: %v", err)
    }
    if len(files) == 0 {
        t.Fatal("no file parsed: a decision test that inspects nothing always passes")
    }

    forbidden := map[string]bool{"Now": true, "Since": true, "Until": true}

    for _, f := range files {
        if strings.HasSuffix(f, "_test.go") {
            continue
        }
        arbre, err := parser.ParseFile(token.NewFileSet(), f, nil, 0)
        if err != nil {
            t.Fatalf("%s: %v", f, err)
        }
        ast.Inspect(arbre, func(n ast.Node) bool {
            call, ok := n.(*ast.SelectorExpr)
            if !ok {
                return true
            }
            pkg, ok := call.X.(*ast.Ident)
            if !ok || pkg.Name != "time" || !forbidden[call.Sel.Name] {
                return true
            }
            t.Errorf("%s calls time.%s: the instant must stay an argument,"+
                " or the module becomes untestable again without an injected clock", f, call.Sel.Name)
            return true
        })
    }
}

// TestTheRuleHasNoMeansToActOnTheWorld is the same test as in chapter 1.2,
// but for one line. It is repeated here because a suite of decision tests
// builds up over time: each lesson adds one, and they are
// never reread.
func TestTheRuleHasNoMeansToActOnTheWorld(t *testing.T) {
    forbidden := []string{"os", "net", "net/http", "net/smtp", "database/sql", "log/slog"}

    out, err := exec.Command("go", "list", "-deps", "example/reminders/reminder").Output()
    if err != nil {
        t.Fatalf("go list: %v", err)
    }
    deps := make(map[string]bool)
    for _, l := range strings.Split(string(out), "\n") {
        deps[strings.TrimSpace(l)] = true
    }

    for _, i := range forbidden {
        if deps[i] {
            t.Errorf("reminder depends on %q: it holds a means it must not have", i)
        }
    }
}
```

Le premier test est le plus intéressant, et il faut comprendre pourquoi il doit
lire la source. La décision à garder est *« l'instant reste un argument »*. Un
graphe d'imports ne peut pas la voir : `reminder` importe `time` tout à fait
légitimement, pour le type `time.Time`. Aucun mécanisme du langage ne distingue
`time.Time` de `time.Now`.

> Une décision qu'aucun mécanisme du langage ne protège demande un test qui
> lit le code. C'est l'outil de dernier recours, et il faut le réserver aux
> décisions qui le méritent.

Note aussi la troisième assertion du test : `if SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2flen(files) SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f== SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f0 SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f{ SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2ft.Fatal SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f}`.
Un test de décision qui n'inspecte rien passe toujours. C'est le mode de panne
propre à cette famille, et il faut l'écrire explicitement.

### Le test de contrat, et la clause que personne n'écrit

Le contrat du journal :

```go
// Package journal defines the memory of reminders: what is due, and what
// has already left. It holds no implementation.
package journal

import (
    "context"
    "errors"
    "time"

    "example/reminders/reminder"
)

// ErrUnavailable: the memory did not answer. Retryable.
var ErrUnavailable = errors.New("journal: unavailable")

// Line is the raw form of an unpaid in storage: exactly what a
// database returns, including when it is inconsistent.
//
// It exists because reminder.Unpaid, for its part, cannot be inconsistent. It
// needs a place where the inconsistency can be represented, and a place where
// it is refused. These two places are not the same, and the boundary
// between them is the analysis.
type Line struct {
    Reference string
    Due       time.Time
    // Tier is 0 when no reminder has left.
    Tier int
    Send time.Time
}

// Journal is the memory of reminders.
type Journal interface {
    // Unpaid returns the overdue invoices that are not settled.
    //
    // GUARANTEED: every Unpaid returned is valid, because it was built by
    // reminder.NewUnpaid. A stored line the constructor refuses makes
    // fail the call with its error; it is not filtered, because an
    // unpaid that disappears goes unnoticed.
    //
    // GUARANTEED: the read order is stable from one call to the next. Which
    // is not specified: only stability is, because it is all
    // that reminder.Decide needs to keep its own order promise.
    Unpaid(ctx context.Context) ([]reminder.Unpaid, error)

    // Record saves that a reminder of this tier left for this
    // reference.
    //
    // GUARANTEED: after a nil return, a later Unpaid returns an unpaid whose
    // LastTier is at least equal to tier.
    //
    // WHAT STAYS TRUE ON FAILURE: the operation can be retried. After a
    // non-nil return, a second call with the same arguments must be able to
    // succeed, whether or not the first attempt wrote. In other words
    // Record is idempotent on the pair (reference, tier).
    //
    // It is this clause, not the previous one, that decides the number of
    // reminders a client gets the day the database flinches.
    Record(ctx context.Context, reference string, tier int, when time.Time) error
}
```

Deux clauses, et toute la leçon 1.5 dans la deuxième :

- `Record` rend `nil` → c'est écrit durablement. **Tout le monde teste ça.**
- `Record` rend une erreur → **l'opération est reprenable**. Personne ne
  teste ça.

Le test de contrat partagé a donc deux étages, et le second est écrit à part
pour qu'on voie bien qu'il existe :

```go
// CheckAfterFailure is the contract test almost nobody writes.
// It does not check that writing works: it checks what stays true when
// it does not. It is the only clause the number of reminders depends on
// a client gets on an outage day.
func CheckAfterFailure(t *testing.T, make Make) {
    t.Helper()

    t.Run("a failed record can be retried", func(t *testing.T) {
        j, broken := make(t, oneLine())
        if broken == nil {
            // A skip is a hole, not a success. The number of skips of a
            // suite of contract tests is the number of clauses one never
            // checked anywhere.
            t.Skip("this implementation cannot cause a write failure")
        }
        ctx := context.Background()
        when := due.Add(72 * time.Hour)

        broken()
        if err := j.Record(ctx, "F-1", 1, when); err == nil {
            t.Fatal("the failure did not happen: the test would prove nothing")
        }

        // The caller does exactly what the contract allows it to do:
        // it starts again identically.
        if err := j.Record(ctx, "F-1", 1, when); err != nil {
            t.Fatalf("the retry failed with %v: the contract's failure clause"+
                " is not kept, and the caller has no possible conduct", err)
        }

        unpaid, err := j.Unpaid(ctx)
        if err != nil {
            t.Fatalf("Unpaid: %v", err)
        }
        if unpaid[0].LastTier() != 1 {
            t.Fatalf("LastTier = %d after retry, want 1", unpaid[0].LastTier())
        }
    })
}
```

Deux implémentations le passent. `journalmem` traite la reconsignation du même
palier comme un non-événement. `journalstrict` la refuse avec
`ErrDejaConsigne` — une garde qui a l'air prudente, et qui est le défaut.

### Et ce que ce test de contrat a coûté

Regarde le type `Panne` dans le paquet `journaltest`. Pour vérifier la clause
d'échec, il faut **pouvoir provoquer l'échec** — et ce moyen n'est pas dans
l'interface. Chaque implémentation doit donc ouvrir une porte supplémentaire :
`BreakNextWrite`, `PerdreProchainAccuse`.

C'est exactement le coût annoncé au §3, et il faut l'assumer à voix haute :

> La clause la plus importante d'un contrat n'est vérifiable que si
> l'implémentation ouvre une couture qui n'appartient pas au contrat.

Quand une implémentation ne sait pas provoquer de panne, le test ne passe pas
en vert : il **saute**, et le saut est visible.

> Le nombre de `t.Skip` d'une suite de tests de contrat est le nombre de clauses
> que tu ne vérifies nulle part.

### Le double qui a un état

L'orchestrateur, maintenant. Il ne contient aucune règle :

```go
// Package campaign orchestrates a reminder pass: read, decide, record,
// send. It holds no rule.
package campaign

import (
    "context"
    "fmt"
    "time"

    "example/reminders/journal"
    "example/reminders/reminder"
)

// Sender sends a reminder. The interface is declared here, at the caller,
// and not in the implementation.
type Sender interface {
    Send(ctx context.Context, reference, template string) error
}

// Summary is what operations read after the pass.
type Summary struct {
    Decided int
    Sent    int
    Failed  int
}

type Campaign struct {
    journal journal.Journal
    sender  Sender
    policy  reminder.Policy
}

func New(j journal.Journal, e Sender, p reminder.Policy) Campaign {
    return Campaign{journal: j, sender: e, policy: p}
}

// Run makes one pass over the unpaid and sends the reminders due.
//
// now is an argument. The program's only call to time.Now is in
// main, and it is passed down to here. A consequence to know: if the pass
// lasts long, now gets old. It is intended: the whole pass reasons
// on the same instant, and two runs on the same state decide the same
// thing.
//
// GUARANTEED
//
//    At most one send per unpaid and per tier, for this pass.
//    A failed send does not stop the next ones: it is a line of the summary.
//    A failed journal read stops everything: without the state, deciding
//    would be guessing.
//
// WHAT STAYS TRUE ON FAILURE
//
//    Every reminder sent was recorded before it left. The converse is false: a
//    reminder can be recorded without being sent, and it is then lost: the
//    next pass will not pick it up.
//
// The record-then-send order is the decision of this file. It trades a
// risk of duplicate for a risk of loss. For an unpaid reminder, the
// duplicate costs more than the loss: it harms a client relationship and
// fills the support queue, while a missed tier is caught by the next
// tier. Removing both risks at once needs a send journal
// apart: it is the outbox pattern, and it belongs to level 8.
func (c Campaign) Run(ctx context.Context, now time.Time) (Summary, error) {
    unpaid, err := c.journal.Unpaid(ctx)
    if err != nil {
        return Summary{}, fmt.Errorf("campaign: reading unpaid: %w", err)
    }

    reminders := reminder.Decide(now, unpaid, c.policy)
    summary := Summary{Decided: len(reminders)}

    for _, r := range reminders {
        if err := c.journal.Record(ctx, r.Reference, r.Tier, now); err != nil {
            // Not recorded: we do not send. Nothing is lost, the next
            // pass will decide the same tier again.
            summary.Failed++
            continue
        }
        if err := c.sender.Send(ctx, r.Reference, r.Template); err != nil {
            summary.Failed++
            continue
        }
        summary.Sent++
    }
    return summary, nil
}
```

Lis le dernier paragraphe de son commentaire : l'ordre `consigner` puis
`envoyer` est **la** décision de ce fichier, et elle échange un risque de
doublon contre un risque de perte. Pour une relance d'impayé, le doublon coûte
plus cher : il abîme une relation client et remplit le support, alors qu'un
palier manqué est rattrapé par le palier suivant. C'est un arbitrage, il est
écrit, et il est gardé par un test.

Voici le double d'expéditeur, et le test qui compte :

### Casser le code pour vérifier les tests

Un test qu'on n'a jamais vu échouer n'est pas un test vérifié. La méthode

```go
// set: that the type allows and the documentation forbids.
func graceOver(now time.Time, i Unpaid, grace time.Duration) bool {
    if i.LastTier > 0 && now.Sub(i.LastSent) < grace {
        return false
    }
    return true
}
```

Quand `LastTier` vaut 0, `LastSent` vaut l'an 1, donc l'écart est
toujours supérieur au répit, donc la première moitié de la condition ne sert à
rien. Sauf pour un `Unpaid` **incohérent** — palier 0, envoi renseigné — que le
type autorisait et que le commentaire interdisait.

Trois conduites possibles. La première : ajouter un test sur l'état incohérent.
La deuxième : supprimer la ligne. La troisième, qui est celle de ce cours :
**rendre l'état inconstruisible**, et les deux autres questions disparaissent
avec lui. C'est ce que font `NewUnpaid` et `WithReminder` : le palier et la
date entrent ensemble ou n'entrent pas.

Conséquences, dans l'ordre : les champs deviennent privés, la ligne défensive
disparaît, la modification n° 3 devient détectable, et deux tests sont
**supprimés** — dont celui qui documentait qu'un impayé sans échéance partait
directement en mise en demeure.

```go
// TestInconsistentStatesCannotBeBuilt replaces two tests of the
// first version.
//
// The first one documented that an Unpaid without a due date went straight to
// formal notice: year 1 as due date, every delay over. The second
// did not exist, and a mutation test asked for it: the guard on
// lastTier could not be told from its absence.
//
// Both disappeared together with the public fields. What had to be
// test became unbuildable, and a line of defensive code was
// removed with them. It is the best fate one can wish for a test.
func TestInconsistentStatesCannotBeBuilt(t *testing.T) {
    if _, err := reminder.NewUnpaid("F-1", time.Time{}); !errors.Is(err, reminder.ErrMissingDue) {
        t.Errorf("zero due date: err = %v, want ErrMissingDue", err)
    }
    if _, err := reminder.NewUnpaid("", due); !errors.Is(err, reminder.ErrNoReference) {
        t.Errorf("empty reference: err = %v, want ErrNoReference", err)
    }
    if _, err := fresh(t, "F-1").WithReminder(0, due); !errors.Is(err, reminder.ErrInvalidTier) {
        t.Errorf("tier 0: err = %v, want ErrInvalidTier", err)
    }
    if _, err := fresh(t, "F-1").WithReminder(1, time.Time{}); !errors.Is(err, reminder.ErrMissingReminderDate) {
        t.Errorf("zero date: err = %v, want ErrMissingReminderDate", err)
    }
}
```

> Un test qui disparaît parce que le type a pris sa place est le meilleur sort
> qu'on puisse lui souhaiter.

Et la leçon de méthode, qui vaut plus que l'exemple :

> Une modification qui survit ne réclame pas toujours un test de plus.
> Quelquefois elle désigne un **état que le type n'aurait pas dû permettre**.

### Les trois axes que les tests ordinaires fixent à « parfait »

La leçon 1.4 a nommé trois choses qui traversent toute abstraction : la
**latence**, le **mode de panne**, l'**ordre**. Un test ordinaire fixe les
trois à leur valeur idéale — réponse immédiate, aucune panne, un seul appelant.

C'est pourquoi une suite verte ne dit rien de la production. Les doubles de
cette leçon sont écrits pour exercer les trois :

| Axe | Le double qui l'exerce | Ce qu'il a trouvé |
|---|---|---|
| mode de panne | `BreakNextWrite` | 5 rappels envoyés pour 1 impayé |
| mode de panne | `PerdreProchainAccuse` | un rappel que le journal croit parti |
| ordre | `TestDeuxPasses…` au même instant | rien — et c'est la bonne nouvelle |

### Testabilité et MTTR

On y revient, parce que c'est l'argument qui convainc quand « c'est plus propre »
ne convainc pas.

> La testabilité et le débogage demandent exactement la même chose : **la
> capacité de poser une question au système sans le redémarrer.**

Reprends la version d'origine. À 3 h du matin, le support signale qu'un client a
reçu quatre mises en demeure. Les questions qu'on va se poser sont :

- Qu'est-ce que la passe de 2 h a décidé ? → *la fonction rend `error`*
- Est-ce que le palier 3 était atteint pour ce client ? → *il faut rejouer avec
  l'état de 2 h, et `time.Now()` est à l'intérieur*
- Est-ce que l'envoi a été consigné ? → *il faut lire le CSV, et il est écrasé
  chaque jour*

Les trois questions sont les étapes 2, 3 et 4 de la grille du §1. Ce ne sont pas
des questions de test. **Ce sont les questions de l'astreinte, et c'est le même
blocage qui les empêche.** Le MTTR de la leçon 1.2 — temps pour former la bonne
hypothèse, plus temps pour agir — se joue entièrement sur le premier terme, et
le premier terme est une propriété de conception.

### Trois compteurs lisibles

Ce qu'on peut mesurer dans un dépôt, sans débat :

1. **Tests à modifier pour un refactoring sans changement de comportement.**
   Cible : zéro. Au-dessus, les tests gardent la structure.
2. **`t.Skip` dans les tests de contrat.** C'est le nombre de clauses non
   vérifiées. Ce compteur doit figurer quelque part, sinon il grandit.
3. **Modifications détectées sur un échantillon de dix.** C'est la seule mesure
   de qualité de tests qui ait un rapport avec la réalité. Elle se fait à la
   main en une heure.

Aucun des trois n'est la couverture.

## 7. Ce qu'il faut retenir

1. **La difficulté d'écrire un test est une mesure de la conception**, pas une
   propriété du test.
2. **Quatre étapes, quatre défauts.** Construire → trop de dépendances. Amener
   dans l'état → état non adressable. Déclencher → déclencheur à l'intérieur.
   Observer → le résultat est un effet.
3. **On ne corrige pas un test difficile, on corrige ce qu'il mesure.**
4. **Rendre testable = trois transformations** : dépendance → argument, effet →
   valeur, état global → paramètre. Aucune ne parle de tests.
5. **Toute couture ouverte pour un test est ouverte pour un abus.** On
   n'injecte pas pour tester : on injecte quand le remplaçant a un demandeur
   en production.
6. **Le temps n'est pas une dépendance, c'est une donnée à faire descendre.**
7. **Trois étages de tests** : contrat (l'appelant), implémentation
   (l'astreinte), décision (le futur mainteneur).
8. **Un test de décision échoue le jour d'une décision contraire**, pas le jour
   d'un bug.
9. **La clause qu'on ne teste jamais** est « ce qui reste vrai en cas d'échec »,
   et c'est celle qui décide du comportement sous panne.
10. **Un double sans mémoire ne peut révéler que la suite des appels.**
11. **La couverture mesure l'exécution, pas la vérification.** Utile lue à
    l'envers, inutile lue à l'endroit.
12. **Un test qu'on n'a jamais vu échouer n'est pas vérifié.** Casse le code et
    regarde qui crie.
13. **Une modification qui survit peut désigner un état que le type n'aurait pas
    dû permettre.**
14. **Testabilité et MTTR sont la même propriété**, mesurée à deux moments.

## 8. Approfondissement

### Le test interne, et la couture qui ne sort pas

Il reste un cas où l'on a besoin d'une couture et où l'on ne veut pas l'ouvrir
au public. Go a une réponse propre : un fichier de test déclaré **dans** le
paquet voit les identifiants non exportés.

```go
package vault

// This file is compiled only during the package's tests. The seam
// exists for them, and it does not exist for callers.
var InternalThreshold = &threshold
```

La hiérarchie de la leçon 1.1 s'applique telle quelle à la question « où mettre
la couture de test » :

| Niveau | Mécanisme | Ce que ça donne |
|---|---|---|
| 🟡 | une convention de nommage, un commentaire | rien, dès le deuxième développeur |
| 🟠 | une méthode exportée documentée « pour les tests » | elle sera appelée en production |
| 🔴 | un fichier `export_test.go` | invisible hors des tests du paquet |
| ⚫ | pas de couture du tout : l'argument descend | rien à abuser |

Les deux derniers niveaux sont ceux de cette leçon : `now` en argument
est le ⚫, `export_test.go` est le 🔴 quand le ⚫ n'est pas atteignable.

### Ce qu'un test de contrat ne peut jamais vérifier

Trois choses, et il faut les savoir pour ne pas se croire couvert :

- **Ce qui n'est pas dans l'interface.** La porte de panne, la latence, le coût
  d'un appel. Ils appartiennent à l'étage d'implémentation.
- **Le comportement de l'implémentation réelle.** `journalmem` passe tout le
  contrat et ne prouve rien sur PostgreSQL. Le contrat dit que les deux se
  comportent pareil *sur les clauses énoncées* ; il ne dit pas que les clauses
  énoncées suffisent.
- **Les clauses qu'on n'a pas écrites.** C'est de loin la plus grosse catégorie,
  et c'est pourquoi le tableau des issues de la leçon 1.5 se fait avant le
  contrat, pas après.

### `-race`, `-count`, et les tests qui ne prouvent rien

Trois réflexes, chacun contre un faux vert particulier :

- `go SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2ftest SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f-race` : le seul moyen d'exercer l'axe « ordre ». Un test concurrent
  sans `-race` est un test séquentiel écrit avec plus de lignes.
- `go SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2ftest SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f-count=20` : un test qui dépend d'un parcours de `map` ou d'un
  ordonnancement passe presque toujours une fois. On l'a utilisé en 1.3, où
  l'étalement a fait passer un test de « 0 refus » à « 46 refus ».
- `t.Parallel()` partout, puis un état partagé entre tests : c'est le moyen le
  plus rapide de rendre une suite non reproductible. Si deux tests partagent
  quelque chose, la question n'est pas comment les paralléliser — c'est ce que
  ce quelque chose fait là.

### Le meilleur test est celui qui ne compile plus

Classement des garde-fous, appliqué aux tests :

> Un état que le type interdit n'a pas besoin de test. Un test qui ne compile
> plus après une modification est plus fort qu'un test qui échoue, parce qu'il
> ne peut pas être ignoré, désactivé ni marqué *flaky*.

C'est pourquoi la modification n° 3 de ce chapitre n'a pas abouti à un test de
plus : elle a abouti à deux constructeurs, et aux tests qui ont disparu avec.

## 9. Ce que la testabilité n'est pas

Six confusions qui coûtent cher.

1. **Ce n'est pas la couverture.** Démontré ci-dessus : 100 % sur un code
   fautif, 96,9 % sur le code correct.
2. **Ce n'est pas « beaucoup de tests ».** Trois tests qui détectent six
   modifications valent mieux que quarante qui n'en détectent aucune. La
   quantité de tests mesure l'effort, pas la couverture du risque.
3. **Ce n'est pas une interface par dépendance.** Chaque interface est une
   couture publique. Le critère reste : le remplaçant a-t-il un demandeur ?
4. **Ce n'est pas un mock par collaborateur.** Un double qui n'a pas d'état ne
   peut révéler que la suite des appels. On écrit des **doubles avec mémoire**,
   et on n'en écrit que pour ce qu'on ne possède pas.
5. **Ce n'est pas TDD.** L'ordre dans lequel tu écris le test et le code est une
   question de méthode de travail. La testabilité est une propriété du code
   fini. On peut écrire du code intestable en TDD : il suffit d'injecter tout.
6. **Ce ne sont pas des tests qui ne cassent jamais.** Une suite qui ne casse
   jamais ne mesure rien. Une suite qui casse pour une raison métier fait son
   travail ; une suite qui casse pour une raison structurelle garde la mauvaise
   chose.

Et la confusion-mère, celle qui produit les cinq autres :

> **Simuler ce qu'on possède.** Si tu dois simuler ton propre module pour
> tester, ce n'est pas un problème de test : c'est que ce module fait un effet
> là où il devrait rendre une valeur. On ne simule que ce qu'on ne possède pas.

## 10. Le réflexe à installer

Devant un morceau de code dont tu doutes, n'en discute pas. **Essaie de
l'interroger**, et note où ça bloque :

> | étape | ce qu'il me faut | ce que ça révèle |
> |---|---|---|
> | construire | | |
> | amener dans l'état | | |
> | déclencher | | |
> | observer | | |

Puis, devant chaque test que tu t'apprêtes à écrire, une seule question :

> **Quelle modification du code ferait échouer ce test ?**

Si tu ne trouves qu'une panique, le test mesure la compilation. Si tu ne trouves
qu'un renommage, le test garde la structure. Si tu trouves un changement de
comportement que quelqu'un peut réclamer un jour, c'est un test.

Et avant d'ouvrir une couture pour tester, la question du §3 :

> **Ce remplaçant a-t-il un demandeur en production ?** Si non, fais descendre
> l'argument plutôt que d'injecter la dépendance.

## Le niveau 1, en une question

Six leçons, six questions. Elles n'en font qu'une, et c'est celle qui reste
quand on a oublié le reste :

| | La question | Ce qu'elle produit |
|---|---|---|
| 1.1 | Qui possède cette donnée, et qui a le droit de la modifier ? | des effets localisés |
| 1.2 | Qui peut exiger que ça change ? | des frontières |
| 1.3 | Que suppose ce module sur les autres sans le dire ? | des coutures |
| 1.4 | Qu'est-ce que l'appelant a le droit de ne pas savoir ? | des contrats |
| 1.5 | Quelles sont les issues, et qui décide de chacune ? | des conduites |
| 1.6 | De quoi ai-je besoin pour poser une question à ce code ? | la vérification des cinq précédentes |

> **Qu'est-ce que ce code me force à savoir, et qui a le droit de l'exiger ?**

Tout le niveau 2 — objets, polymorphisme, SOLID — n'est qu'une collection de
réponses déjà rédigées à cette question. On ne les apprendra pas comme des
règles. On les lira comme des réponses, et on demandera chaque fois à quelle
question elles répondaient, et ce qui arrive quand ce n'est pas la tienne.
