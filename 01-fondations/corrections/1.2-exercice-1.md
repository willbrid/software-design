# Correction — Exercice 1.2 / 1 (compréhension)

## L'énoncé

Un cron horaire synchronise l'annuaire de l'entreprise vers la base
applicative. Une méthode, trente-cinq lignes, un nom qui promet une seule
chose : `SynchroniserUtilisateurs`.

```go
func (s *Service) SynchroniserUtilisateurs(ctx context.Context) error {
    entrees, err := s.ldap.Rechercher("(objectClass=person)")
    if err != nil {
        return err
    }

    var rapport bytes.Buffer
    fmt.Fprintln(&rapport, "login;email;statut")

    for _, e := range entrees {
        login := strings.ToLower(strings.TrimSpace(e.Attr("uid")))
        email := login + "@exemple.cm"

        res, err := s.db.ExecContext(ctx,
            "INSERT INTO utilisateurs (login, email) VALUES ($1, $2) ON CONFLICT DO NOTHING",
            login, email,
        )
        if err != nil {
            return err
        }

        if n, _ := res.RowsAffected(); n == 1 {
            corps := fmt.Sprintf("Bienvenue %s, ton compte est actif.", login)
            if err := s.smtp.Envoyer(email, "Bienvenue", corps); err != nil {
                return err
            }
            s.metriques.Inc("utilisateurs_crees")
        }

        fmt.Fprintf(&rapport, "%s;%s;ok\n", login, email)
    }

    return os.WriteFile("/var/rapports/sync.csv", rapport.Bytes(), 0o644)
}
```

L'énoncé complet est dans
[1.2-exercices.md](../exercices/1.2-exercices.md).

## La méthode

Ne cherche pas ce qui est mal écrit. Cherche, ligne par ligne, **une décision**,
puis demande-toi qui, dans l'entreprise, a le droit de la changer.

Une décision se reconnaît à ceci : si tu changeais cette valeur ou cette règle,
quelqu'un t'appellerait. Un `for` n'est pas une décision. `"@exemple.cm"` en est
une.

## Question 1 — Les décideurs

| Bloc | Ce qui y est décidé | Qui peut l'exiger | Rythme |
|---|---|---|---|
| `Rechercher("(objectClass=person)")` | ce qui compte comme une personne dans l'annuaire | l'équipe qui administre l'annuaire | rare, brutal |
| `e.Attr("uid")` | le nom de l'attribut porteur de l'identifiant | la même équipe | rare |
| `ToLower`, `TrimSpace` | la convention de nommage des logins | l'équipe IAM / sécurité | rare |
| `login + "@exemple.cm"` | le domaine de messagerie | l'équipe messagerie | rare, brutal |
| `INSERT INTO utilisateurs (...)` | le schéma de la table | le DBA | moyen |
| `ON CONFLICT DO NOTHING` | la politique de conflit : un login déjà présent est ignoré | **personne** | — |
| `"Bienvenue %s, ton compte est actif."` | le texte et l'objet du message | le marketing / la comm interne | fréquent, trivial |
| `Inc("utilisateurs_crees")` | le nom de la métrique | l'équipe SRE / observabilité | moyen |
| `"%s;%s;ok\n"` et l'en-tête | le format, le séparateur, les colonnes, le statut | le destinataire du rapport (contrôle interne, RH, audit) | moyen |
| `/var/rapports/sync.csv`, `0o644` | la destination, les droits, la rétention | l'exploitation | moyen |
| chaque `return err` | la politique d'erreur : toute erreur avorte le lot | **personne** | — |

Sept demandeurs identifiables, onze décisions, trente-cinq lignes.

Ce n'est pas une fonction **longue**. C'est une fonction **surpeuplée**. La
longueur n'a jamais été le critère : on peut écrire deux cents lignes qui ne
répondent qu'à une seule personne, et onze lignes qui en concernent sept.

### Les deux lignes les plus dangereuses sont celles dont le demandeur est « personne »

`ON CONFLICT DO NOTHING` et `return err` n'ont pas de propriétaire. Ce ne sont
pas des oublis : ce sont des **décisions prises par défaut**, parce qu'elles
étaient la façon la plus courte d'écrire la ligne.

`ON CONFLICT DO NOTHING` dit : *« une personne dont le login existe déjà ne
m'intéresse plus. »* Cette phrase a des conséquences métier considérables — un
employé qui change de nom ne verra jamais son email mis à jour — et personne
ne l'a jamais formulée. Elle a été écrite pour éviter une erreur de clé
dupliquée.

Retiens la règle : **une décision que personne n'a prise est quand même une
décision, et c'est statistiquement celle qui produira l'incident.** Quand tu
recenses des décideurs, les cases vides sont les plus informatives.

### Le détail qui trahit tout

Regarde `fmt.Fprintf(&rapport, "%s;%s;ok\n", ...)`.

Le statut est `"ok"`, en dur, écrit avant de savoir quoi que ce soit. Il vaut
`"ok"` quand la ligne a été créée, `"ok"` quand elle existait déjà, `"ok"`
quand l'email a été envoyé, et `"ok"` quand il ne l'a pas été — puisque dans ce
cas la fonction est déjà sortie.

Un rapport dont la colonne « statut » ne prend qu'une valeur n'est pas un
rapport. C'est un décor. Et il est là parce que le module qui écrit le rapport
n'existe pas : le rapport est écrit par celui qui fait tout le reste, et qui
n'avait pas besoin de la réponse.

## Question 2 — Les trois demandes du trimestre

### (a) L'annuaire expose `department`, il faut le stocker

**Ce qu'on ouvre :** la recherche LDAP (demander l'attribut), la boucle (le
lire), l'`INSERT` (le stocker), plus une migration de schéma. Et le rapport,
si son destinataire veut la colonne.

**Ce qui casse sans qu'on y touche :**

- `ON CONFLICT DO NOTHING` fait que les 200 personnes déjà présentes
  n'auront **jamais** de `department`. La colonne reste `NULL` pour tout
  l'existant, la synchro passe au vert chaque heure, et le problème ne se
  manifestera que le jour où quelqu'un filtrera sur ce champ.
- le CSV gagne une colonne : tout consommateur qui le lit par index de colonne
  casse — et ce consommateur n'est pas dans ce dépôt, donc aucun compilateur,
  aucun test, aucune revue ne le verra.
- le texte de l'email est redéployé. Pour une migration de schéma.

### (b) Le marketing réécrit le texte de bienvenue

**Ce qu'on ouvre :** deux lignes. La plus petite demande du trimestre.

**Ce qu'elle emporte :** un déploiement de la synchronisation complète, de la
requête LDAP, de l'`INSERT`, de la politique d'erreur. Le marketing n'a pas
demandé ça. Personne ne le lui a dit.

Garde cette asymétrie en tête : **le coût d'un changement n'est pas
proportionnel à sa taille, il est proportionnel à la taille de ce avec quoi il
est livré.** C'est tout l'exercice 5 de cette série, et c'est un incident réel.

### (c) Le rapport passe du CSV au JSON

**Ce qu'on ouvre :** l'en-tête, le `Fprintf` dans la boucle, l'écriture
finale, l'extension du fichier.

Et là, un détail de structure se réveille : le rapport est construit **dans**
la boucle, par écriture incrémentale dans un `bytes.Buffer`. Du JSON ne
s'écrit pas comme ça : il faut accumuler des valeurs, puis sérialiser. Donc il
faut modifier le corps de la boucle.

Relis ce que contient ce corps de boucle : un `INSERT` et un envoi d'email.

> Pour changer le format d'un rapport interne, on doit éditer la ligne
> d'à côté de celle qui envoie des emails aux employés.

Voilà. Il n'y a rien à ajouter. C'est la définition opérationnelle du défaut.

### Ce que le tableau des trois demandes révèle

| Demande | Demandeur | Fichiers à ouvrir | Modules à ouvrir |
|---|---|---|---|
| (a) `department` | annuaire + DBA | 1 | 1 |
| (b) le texte | marketing | 1 | 1 |
| (c) JSON | contrôle interne | 1 | 1 |

La colonne « modules à ouvrir » vaut 1 partout, et c'est précisément le
problème : **trois demandeurs indépendants, trois branches, un seul fichier.**

Le symptôme mesurable n'est pas l'esthétique du code. C'est le conflit de
merge. Trois équipes qui ne se connaissent pas vont se retrouver à se
coordonner — sur un fichier dont aucune des trois ne comprend les deux tiers —
pour des changements qui n'ont aucun rapport entre eux.

Et au bout : un seul déploiement qui emporte les trois. Donc une seule
occasion de tout casser, et un rollback qui annule les trois demandes à la
fois.

## Question 3 — L'échec d'email au 40ᵉ utilisateur sur 200

### L'état à l'instant de l'échec

| Observable | Valeur |
|---|---|
| lignes insérées en base | 40 — dont la 40ᵉ, insérée juste avant l'échec |
| emails envoyés | 39 |
| `utilisateurs_crees` | 39 |
| utilisateurs 41 à 200 | pas lus, pas créés, pas notifiés |
| `/var/rapports/sync.csv` | **le rapport de l'heure précédente, intact** |
| valeur rendue | l'erreur SMTP, remontée telle quelle au cron |

La ligne qui compte est l'avant-dernière. `os.WriteFile` est **après** la
boucle. Le `return err` a sauté par-dessus. Le buffer de rapport, avec ses 40
lignes, est perdu avec la pile d'appels.

Donc à 14h05, l'exploitant qui va voir le rapport trouve un fichier complet,
cohérent, avec 200 lignes et des `ok` partout. Celui d'il y a une heure.

> Le rapport n'est pas faux. Il est **périmé**. C'est pire, parce qu'un rapport
> périmé est indiscernable d'un rapport correct.

C'est exactement la colonne « trace durable : aucune » de la
[correction 1.1 / 5](1.1-exercice-5.md). Le même défaut, dans un autre
costume : l'état de l'opération n'a jamais existé ailleurs que dans la pile
d'appels.

### Ce que fait l'exécution suivante, à 15h00

- Utilisateurs 1 à 39 : `ON CONFLICT DO NOTHING` → `RowsAffected() == 0` → pas
  d'email, pas de métrique. Correct, et c'est tant mieux.
- **Utilisateur 40** : la ligne a été insérée à 14h. `RowsAffected() == 0`.
  Donc **pas d'email. Ni maintenant, ni jamais.**
- Utilisateurs 41 à 200 : créés, notifiés, comptés.
- Rapport : écrit, 200 lignes, `ok` partout.

État final : les 200 comptes existent, 199 personnes ont reçu leur message de
bienvenue, une ne l'aura jamais, et le compteur `utilisateurs_crees` indique
199 pour toujours.

### Correct ? Prévisible ?

**Correct : non**, et l'incorrection est permanente. Ce n'est pas un retard,
c'est une perte. Le système a convergé vers un état stable et faux.

**Prévisible : les deux à la fois, et c'est tout l'intérêt de la question.**

- Déterministe : oui. Étant donné le point d'échec, la suite est entièrement
  déterminée.
- Prévisible par celui qui exploite : non. Rien, nulle part, ne dit qu'une
  personne manque. Il n'y a ni ligne en base, ni métrique, ni entrée de
  rapport qui porte cette information. Pour la retrouver, il faut savoir
  qu'elle existe.
- Et surtout : *quelle* personne est perdue dépend de l'ordre dans lequel
  l'annuaire a répondu, qui n'est pas spécifié par LDAP.

> Le résultat n'est pas aléatoire. Il est **arbitraire** : il dépend de l'ordre
> de réponse d'un serveur tiers. Un système dont l'état final dépend d'un
> détail que personne ne contrôle n'est pas prévisible, même s'il est
> déterministe.

### La cause, et elle est bien une cause de découpe

On peut lire ce bug comme un défaut de reprise sur erreur. Ce serait passer à
côté.

La cause est à cette ligne :

```go
if n, _ := res.RowsAffected(); n == 1 {
```

`RowsAffected() == 1` répond à la question *« ai-je créé une ligne ? »*. Le
code s'en sert pour répondre à *« dois-je envoyer un email ? »*. Deux
questions, un seul critère.

Ça marche tant que les deux effets réussissent ou échouent ensemble. Ils
n'ont aucune raison de le faire : l'un est une écriture transactionnelle dans
une base qu'on contrôle, l'autre est un appel réseau vers un tiers.

**Deux responsabilités qui partagent un critère de décision partagent aussi
leurs pannes.** L'envoi de l'email a besoin de son propre état durable — une
colonne, une date, quelque chose qui survive à la requête. C'est ce que
construit l'exercice 2.

Note au passage l'écho de la leçon 1.1 : un `return err` sur un effet
**cosmétique** (un email de bienvenue) arrête une opération **structurante**
(la synchronisation de l'annuaire). La hiérarchie de gravité du code est
l'inverse de celle du métier.

## Question 4 — Découpe A ou découpe B

- **A** — `lire()`, `transformer()`, `ecrire()`, `notifier()`, `rapporter()`
- **B** — `annuaire`, `comptes`, `notif`, `rapport`

### La réponse, puis la preuve

A découpe par **étapes**. B découpe par **raison de changer**.

On peut le voir aux noms : les éléments de A sont des verbes qui décrivent
l'ordre d'exécution. Mais l'énoncé demande mieux que ça, parce qu'un nom se
maquille. Un module nommé `rapport` peut parfaitement contenir cinq
responsabilités, et une fonction nommée `transformer()` peut n'en contenir
qu'une. Il faut une demande de changement, et un décompte.

### La demande qui coûte cher dans A et rien dans B

> *L'annuaire LDAP est remplacé par Microsoft Entra ID : API REST, JSON,
> l'identifiant s'appelle désormais `userPrincipalName`.*

**Dans B** — on réécrit `annuaire` de fond en comble. `comptes`, `notif`,
`rapport` ne sont pas ouverts. **Un module.**

**Dans A** — on réécrit `lire()`, évidemment. Puis on ouvre `transformer()`,
parce que c'est là que se trouve `e.Attr("uid")` : le nom de l'attribut est
une affaire de **format**, et il a fui dans l'étape qui porte la **règle**.
Puis probablement `rapporter()`, s'il touche au type d'entrée. **Deux ou trois
fonctions, dont celle qui contient la règle métier.**

Pourquoi ? Parce que les étapes de A se passent toutes **le même type de
données**. C'est leur raison d'être : un pipeline fait circuler une valeur. Et
un type partagé est un couplage.

> Une découpe par étapes partage son vocabulaire. C'est ça, son couplage — pas
> les appels de fonction, le **type qui traverse**.

### La demande symétrique, qui coûte cher dans B

Il serait malhonnête de s'arrêter là. Cherche une demande où B est la mauvaise
découpe :

> *Le rapport doit lister toutes les personnes lues dans l'annuaire, y compris
> celles rejetées, avec leurs attributs LDAP bruts.*

**Dans A** — `rapporter()` est au bout d'un pipeline où les entrées sont
encore à portée. C'est presque gratuit.

**Dans B** — `rapport` a un vocabulaire volontairement pauvre (`login`,
`email`, `statut`) : il ne sait pas ce qu'est un attribut LDAP, et c'est
exactement ce qu'on a acheté. Donc il faut élargir le type qui franchit la
frontière, donc ouvrir `rapport`, le type exporté d'`annuaire`, et
l'orchestrateur. **Trois modules.**

> La frontière de B se paie quand une **information nouvelle doit la
> traverser**. C'est le vrai coût, il est réel, et c'est le sujet de la
> leçon 1.3.

### Le critère général

Une découpe par étapes est bon marché pour les changements *à l'intérieur*
d'une étape, et chère pour ceux qui suivent un **sujet**. Une découpe par
raison de changer fait l'inverse.

Alors pourquoi B gagne-t-elle en pratique ? Pas par principe. Parce que les
demandes qui arrivent réellement suivent des sujets — et elles suivent des
sujets parce que **les demandeurs possèdent des sujets, pas des étapes.**
Personne, dans l'entreprise, n'est responsable de « l'étape de
transformation ». Quelqu'un est responsable de la messagerie.

> A découpe le code comme la fonction s'exécute. B le découpe comme
> l'entreprise décide. La fonction s'exécute une fois par heure ; l'entreprise
> décide tous les jours.

### Et A n'est pas à jeter

Ouvre le module `annuaire` de la découpe B : tu y trouveras lire, décoder,
transformer. Ouvre `rapport` : formater, écrire.

A et B ne sont pas en concurrence, elles sont **à deux échelles
différentes**. Lire-transformer-écrire est une excellente structure *à
l'intérieur* d'un module. L'erreur n'est pas de penser en étapes ; c'est de
s'en servir comme **frontière de module**, c'est-à-dire comme frontière de
propriété, de revue, de test et de déploiement.

## À retenir

1. Recenser les décideurs, bloc par bloc. Pas « le métier » : une équipe
   qu'on peut appeler au téléphone.
2. Les décisions dont le demandeur est **« personne »** sont les plus
   dangereuses. `ON CONFLICT DO NOTHING` et `return err` sont des décisions
   métier prises pour raccourcir une ligne.
3. Une fonction surpeuplée n'est pas une fonction longue. Le critère est le
   nombre de personnes qui peuvent exiger qu'elle change.
4. Le coût d'un changement est proportionnel à la taille de ce avec quoi il
   est **livré**, pas à la sienne.
5. Quand changer un format de rapport oblige à éditer la ligne voisine d'un
   envoi d'email, le diagnostic est posé.
6. Un rapport écrit après la boucle n'existe pas les jours où ça casse. Et un
   rapport périmé est indiscernable d'un rapport correct.
7. Deux responsabilités qui partagent un critère de décision
   (`RowsAffected() == 1`) partagent aussi leurs pannes. Chaque effet durable
   a besoin de son propre état durable.
8. Une découpe par étapes partage le type qui la traverse : c'est là qu'est
   son couplage.
9. Une découpe par sujets se paie quand une information nouvelle doit
   franchir la frontière. Ce coût est réel — c'est la leçon 1.3.
10. Étapes et responsabilités vivent à deux échelles. Lire-transformer-écrire
    à l'intérieur d'un module, oui. Comme frontière de module, non.
