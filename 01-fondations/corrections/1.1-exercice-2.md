# Correction — Exercice 1.1 / 2 (code)

## L'énoncé

```go
type Config struct {
    Name   string
    Tags   []string
    Limits map[string]int
}

func MergeConfig(base, override Config) Config
```

> Elle produit une configuration où les valeurs de `override` écrasent celles de
> `base` **quand elles sont renseignées**.
>
> Contrainte impérative : ni `base` ni `override` ne doivent être modifiés, et le
> résultat ne doit partager **aucune** structure mutable avec eux.
>
> Écris aussi, en commentaire au-dessus, le contrat que ta fonction garantit.

Cet exercice a l'air d'un exercice de code. Il n'en est pas un. La partie
mécanique — ne rien partager — se règle en cinq lignes. Les trois mots
**« quand elles sont renseignées »** cachent une décision de conception que
l'énoncé ne tranche pas, et c'est là que se joue l'exercice.

---

## Étape 1 — L'isolation : la partie facile

```go
result := Config{
    Name:   base.Name,
    Tags:   slices.Clone(base.Tags),
    Limits: maps.Clone(base.Limits),
}
```

Trois points méritent d'être explicités, parce que chacun est une erreur
classique.

**`Name` n'a pas besoin d'être cloné.** Un `string` contient un pointeur, mais il
est immuable : aucune écriture ne peut passer à travers. Cloner une chaîne est
du gaspillage, pas de la prudence.

**`Limits` doit l'être.** Une `map` est un pointeur nu. Copier la struct copie
le pointeur, pas la table. C'était l'erreur de l'exercice 1.

**`override` doit être clonée aussi.** C'est l'oubli le plus fréquent. Le
raisonnement fautif est : « la surcharge, c'est justement ce qu'on veut garder,
autant la prendre telle quelle ». Sauf que la prendre telle quelle, c'est
conserver une référence vers la map de l'appelant. Le résultat n'est pas isolé
de `override`, et la contrainte de l'énoncé dit **aucune** structure mutable
avec **aucun** des deux paramètres.

> **Règle générale à retenir :** on clone quand on s'apprête à **conserver une
> référence** vers la structure mutable de quelqu'un d'autre. Ni plus, ni moins.
> Cloner « au cas où » n'est pas de la prudence : c'est le signe que le modèle
> mental de ce qui est partagé n'est pas encore net.

### Le piège de la map nil

Dès qu'on passe du remplacement à la fusion clé par clé, on cesse d'**assigner**
la map pour **écrire dedans**. Or en Go :

```go
var m map[string]int
_ = len(m) // OK
_ = m["a"] // OK, returns 0
for range m {
} // OK, zero iterations
m["a"] = 1 // panic: assignment to entry in nil map
```

La map nil est le seul type du langage qui soit **lisible mais pas écrivable**.
Et `maps.Clone(nil)` renvoie `nil`. Donc un code qui clonait puis assignait
fonctionnait ; le même code qui clone puis **insère** panique dès que la base
n'a pas de limites.

Le point général dépasse ce bug : **changer la nature d'une opération change ses
préconditions.** Passer d'« assigner » à « écrire dedans » n'est pas un détail
d'implémentation.

## Étape 2 — Remplacer ou fusionner ?

L'énoncé dit « écraser ». Écraser quoi, exactement ?

Considérons :

```
base.Limits       = {max_amount: 500000, timeout_ms: 30000, retries: 3}
override.Limits = {timeout_ms: 45000}
```

Un opérateur veut passer le timeout de 30 s à 45 s ; il écrit une surcharge d'une
ligne. Si `Limits` est remplacée en bloc, le résultat est
`{timeout_ms: 45000}` : **`max_amount` et `retries` ont disparu.** Le service
part en production sans plafond de montant.

C'est la pire catégorie de défaut : rien ne plante, rien n'est loggé, la
configuration produite est parfaitement valide — et fausse.

Pour `Tags`, la question a l'air identique. Elle ne l'est pas. Supposons l'union :

```
base.Tags = ["prod", "legacy", "audit"]
```

L'environnement de préproduction veut les mêmes tags **sauf** `legacy`. Avec une
union, aucune valeur de `override.Tags` ne permet d'obtenir ce résultat :
l'union ne sait qu'ajouter. La règle rend un état **inatteignable**.

**Conclusion : fusion clé par clé pour `Limits`, remplacement pour `Tags`.**

Et le critère qui explique la différence — c'est lui qu'il faut emporter, pas le
verdict :

> Une `map` est un ensemble de réglages **indépendants et adressables** : chaque
> clé a un nom, on peut donc parler de l'une sans parler des autres → **fusion**.
>
> Un `slice` est **une valeur unique** qui se trouve être une liste : aucun
> élément n'a de nom, le seul objet désignable est la liste entière →
> **remplacement**.

La distinction n'est pas « map vs slice » au sens du type Go. Elle est
sémantique : elle porte sur l'existence, ou non, d'une façon de désigner un
élément pour le modifier seul.

Le remplacement a un prix qu'il faut assumer consciemment : l'environnement qui
veut juste retirer `legacy` doit réécrire la liste complète. Le jour où
`"pci-dss"` est ajouté à `base.Tags`, la préproduction ne l'aura pas —
silencieusement. C'est un vrai risque de dérive de configuration, accepté en
échange de l'expressivité. **Un compromis assumé, c'est savoir ce qu'on paie et
pourquoi.**

## Étape 3 — Le vrai piège : « quand elles sont renseignées »

Voici la forme spontanée, celle qu'écrivent presque tous les candidats :

```go
if override.Name != "" {
    result.Name = override.Name
}
if len(override.Tags) > 0 {
    result.Tags = slices.Clone(override.Tags)
}
if override.Limits != nil {
    // …
}
```

Trois champs, **trois critères différents** :

| Champ | Critère écrit | « Absent » signifie |
|---|---|---|
| `Name` | `!= ""` | chaîne vide |
| `Tags` | `len(...) > 0` | nil **ou** slice vide |
| `Limits` | `!= nil` | nil seulement |

Un seul appel suffit à rendre l'incohérence visible :

```
override = { Name: "", Tags: []string{}, Limits: map[string]int{} }
            // « vide » exprimé partout de la même façon

result    = { Name: <celui de base>, Tags: <ceux de base>, Limits: {} }
```

Même intention pour les trois champs, trois comportements différents. `Limits`
a été vidé ; `Name` et `Tags` ont été ignorés — et par accident, pas par décision.

### La cause : la valeur zéro détournée en sentinelle

Le code ci-dessus décrète que la valeur zéro du type signifie « absent ».
Ce n'est pas absurde — c'est même très courant en Go. Mais c'est un **choix**,
et il a un prix : **la valeur zéro était une valeur légitime.** En la
réquisitionnant pour dire « ne touche pas », on perd la capacité d'exprimer
« mets à vide ».

Posée mécaniquement, la question est :

> Dans une `Config`, **à quel endroit** est stockée l'information « je n'y touche
> pas » ?

Nulle part. Le type n'a pas de place pour elle. C'est pour cette raison que
toute correction qui reste dans ce cadre ne fait que déplacer le problème :

- avec les `if` : on ne peut jamais **effacer** ;
- sans les `if` (surcharge inconditionnelle) : on ne peut jamais **conserver**,
  et le paramètre `base` ne sert plus à rien pour deux champs sur trois.

Les deux extrêmes ont la même cause. Quand deux corrections opposées échouent
symétriquement, le problème n'est pas dans le code : il est dans le **type**.

### Le commentaire comme test de la conception

L'énoncé demandait le contrat en commentaire. Ce n'était pas un exercice de
rédaction. Essayons d'écrire la règle de surcharge de la version ci-dessus :

```
- Name    est surchargé si override.Name != ""
- Tags    est surchargé si len(override.Tags) > 0
- Limits est surchargé si override.Limits != nil
```

Un appelant qui lit ça n'a pas une règle à comprendre, il a un tableau à
apprendre par cœur. La tentation est alors d'écrire « si le champ n'est pas
renseigné » — sauf qu'**en Go, un champ de struct existe toujours**.
`override.Name` existe même quand on ne l'a pas écrit : il vaut `""`. Une telle
phrase décrit un langage à clés optionnelles, du JSON — pas le type qu'on a
écrit. **L'écart entre les deux est exactement le bug.**

> **Un contrat qu'on n'arrive pas à écrire en une phrase simple n'est pas un
> problème de rédaction. C'est le symptôme que la conception n'est pas décidée.**
>
> Le commentaire n'est pas la dernière étape de l'écriture du code : c'est un
> **test de la conception**. Si l'énoncer fait mal, c'est le design qu'il faut
> changer, pas la phrase.

Corollaire : un commentaire **faux** est plus dangereux qu'un commentaire vague.
Le vague met en garde ; le faux rassure.

## Étape 4 — La meilleure version sous la signature imposée

L'énoncé impose `MergeConfig(base, override Config) Config`. Avant d'aller
plus loin, il faut écrire la meilleure fonction possible **sous cette
signature** — parce qu'en pratique une signature est souvent imposée : API
publique déjà diffusée, interface d'un tiers, code existant qu'on n'a pas le
droit de casser.

Le progrès décisif tient en une observation. Sur les trois champs, deux ont un
type qui possède **déjà** une valeur distincte de toutes ses valeurs légales :
`[]string` et `map[string]int` ont `nil`, qui n'est pas la même chose que la
liste vide ou la map vide. Seul `string` n'en a pas.

Il devient donc possible d'énoncer **une règle unique** au lieu de trois :

> **Un champ de `override` laissé à sa valeur zéro n'est pas appliqué.**

```go
// MergeConfig returns a new Config combining base and override.
// Override rule, a single one for every field:
// an override field left at its zero value is not applied.
//
//   - Name  : replaced if override.Name != ""
//   - Tags  : replaced as a whole if override.Tags != nil
//     (an empty non-nil list, []string{}, so it empties the tags)
//   - Limits: merged key by key if override.Limits != nil
//     (keys absent from override are kept)
//
// Guarantees:
//   - neither base nor override is modified;
//   - the result shares no mutable structure with them.
//
// KNOWN LIMIT: `Name` cannot be reset to the empty string, because `string`
// has no value distinct from all its legal values to mean
// "absent". If that need appears, this signature is no longer enough.
func MergeConfig(base, override Config) Config {
    result := Config{
        Name:   base.Name,
        Tags:   slices.Clone(base.Tags),
        Limits: maps.Clone(base.Limits),
    }

    if override.Name != "" {
        result.Name = override.Name
    }
    if override.Tags != nil {
        result.Tags = slices.Clone(override.Tags)
    }
    if override.Limits != nil {
        if result.Limits == nil {
            result.Limits = make(map[string]int, len(override.Limits))
        }
        maps.Copy(result.Limits, override.Limits)
    }
    return result
}
```

Trois changements par rapport à la version naïve, et chacun a une raison :

**`override.Tags != nil` au lieu de `len(override.Tags) > 0`.** C'est le
changement le plus important du lot, et il ne coûte rien. `len(...) > 0`
confond `nil` et `[]string{}` ; `!= nil` les distingue. Résultat :
`Config{Tags: []string{}}` veut désormais dire « vide les tags », et cette
intention devient exprimable. Un caractère de différence, une fonctionnalité
gagnée.

**La map nil est traitée sur place.** `maps.Copy` écrit dans la destination ;
si `base.Limits` est nil, `maps.Clone` a rendu nil et l'écriture paniquerait.
Le `make` conditionnel règle le cas sans changer le comportement des autres.

**La limite est écrite dans le contrat, en majuscules.** `Name` reste
inaccessible à l'effacement. Ce n'est pas grave — c'est *déclaré*. La différence
entre un défaut et une limite tient entièrement à ce mot :

> **Une limite documentée est une décision de conception. La même limite non
> documentée est un piège.**

Cette version est **acceptable en production**. Elle est cohérente, sûre,
nil-safe, et honnête sur ce qu'elle ne sait pas faire. Si la signature est
imposée, on s'arrête ici.

### Et le test qui documente la limite

```go
// Documents the limit: the name cannot be reset to empty.
func TestKnownLimit(t *testing.T) {
    r := MergeConfig(Config{Name: "payment"}, Config{Name: ""})
    if r.Name != "payment" {
        t.Fatalf("limit does not match the doc: %q", r.Name)
    }
}
```

Un test sur un comportement qu'on **regrette** peut sembler absurde. Il ne l'est
pas : il transforme la limite en fait vérifié, il empêche qu'elle soit
« corrigée » par accident sans que la documentation suive, et il signale au
lecteur que ce comportement est subi et non choisi.

## Les trois familles de solutions

Le besoin, formulé précisément : pour chaque champ, pouvoir exprimer **une
valeur de plus** que ce que son type permet — toutes ses valeurs légales,
**plus** « je n'y touche pas ».

### Famille A — agrandir le champ : le pointeur

```go
type Config struct {
    Name   *string
    Tags   *[]string
    Limits map[string]int
}
```

Pour tout type `T`, `*T` possède toutes les valeurs de `T` **plus** `nil`. C'est
la place qui manquait : `nil` = « je n'y touche pas », `&""` = « mets la chaîne
vide ». Les deux intentions deviennent enfin distinctes.

**Le prix est lourd :** les champs d'une configuration *complète* deviennent
optionnels. Or une config résolue n'a rien d'optionnel — chaque champ a
forcément une valeur. Tout le reste du programme devra écrire `*cfg.Name`, et
déréférencer un `nil` panique. Le problème n'est pas résolu, il est **exporté**
vers tous les consommateurs de `Config`.

### Famille B, piste 1 — un type dédié à la modification

```go
type ConfigPatch struct {
    Name   *string
    Tags   *[]string
    Limits map[string]int // merged key by key
}

func Apply(base Config, p ConfigPatch) Config
```

Même mécanisme, mais l'optionnalité reste **là où elle a un sens** : dans la
description d'un changement. `Config` redevient un type propre où tout est
toujours renseigné.

Rien n'oblige une *description de modification* à avoir la même forme que la
chose modifiée. Le réflexe de réutiliser `Config` pour la surcharge est la
racine du problème.

### Famille B, piste 2 — des actions plutôt que des données

```go
type Option func(*Config)

func WithName(name string) Option        { /* … */ }
func WithTags(tags ...string) Option     { /* … */ }
func WithLimit(key string, v int) Option { /* … */ }
func WithoutLimit(key string) Option     { /* … */ }

func Apply(base Config, opts ...Option) Config
```

Comparons les sites d'appel pour l'opérateur qui veut seulement passer le
timeout à 45 s :

```go
// raw data  (first version, ambiguous)
MergeConfig(base, Config{Limits: map[string]int{"timeout_ms": 45000}})

// patch
Apply(base, ConfigPatch{Limits: map[string]int{"timeout_ms": 45000}})

// options
Apply(base, WithLimit("timeout_ms", 45000))
```

Et surtout : **regarder ce qui a disparu.** Il n'existe plus nulle part de valeur
signifiant « absent ». Une option qu'on ne passe pas ne s'exécute pas, voilà
tout. Le problème n'a pas été résolu — il a **cessé d'exister**.

> **Quand une représentation force à inventer des valeurs spéciales, la bonne
> réponse est souvent de changer de représentation, pas d'ajouter un cas.**

### Le critère de maintenance

Un quatrième champ arrive dans `Config`. Ce qui compte n'est pas combien
d'endroits il faut toucher, mais **ce qui se passe le jour où l'on en oublie un** :

| Approche | Conséquence de l'oubli | Qui le détecte |
|---|---|---|
| Pointeurs dans `Config` | le champ n'est jamais surchargeable | quelqu'un qui en aura besoin, un jour |
| `ConfigPatch` | champ ajouté au patch mais ligne oubliée dans `Apply` → **le patch est ignoré en silence** | ☠️ personne, jusqu'à l'incident |
| Options | la fonction `AvecX` n'existe pas → **erreur de compilation au site d'appel** | 🔴 le compilateur, immédiatement |

C'est la hiérarchie des garde-fous du cours, appliquée : le patch laisse la règle
au niveau « revue de code » ; les options la font descendre jusqu'au
**compilateur**.

### Comment choisir

Le critère décisif n'est pas esthétique, c'est une contrainte du système :

> **D'où vient la surcharge ?**
>
> - D'un fichier YAML, d'un appel HTTP, d'une table en base → **`ConfigPatch`**.
>   Un patch est une **donnée** : il se désérialise, se logge, se compare, se
>   stocke, s'audite. Une fonction ne fait rien de tout cela.
> - Du code Go lui-même (tests, assemblage de services, valeurs par défaut d'une
>   bibliothèque) → **options**. Le compilateur devient le garde-fou et le site
>   d'appel se lit comme une phrase.

Les deux réponses sont correctes. Ce qui serait faux, c'est de choisir sans
poser la question.

## Solution de référence (options)

**Cette solution ne fournit plus `MergeConfig` : elle change la signature.**
C'est volontaire, et c'est le fond de la réponse à l'exercice.

`MergeConfig(base, override Config)` oblige la surcharge à être une
`Config`, c'est-à-dire un type conçu pour décrire une configuration *complète*.
La cause du problème est dans la signature elle-même, pas dans le corps de la
fonction. Tant qu'on la conserve, on ne peut que choisir laquelle des deux
intentions sacrifier — d'où la limite documentée à l'étape 4.

À retenir, et c'est plus large que cet exercice :

> **Quand l'énoncé impose une signature qui rend la garantie demandée
> impossible, la bonne réponse d'ingénieur n'est pas de contourner : c'est de
> livrer la meilleure version possible sous la contrainte, d'en documenter la
> limite, puis de proposer explicitement le changement de signature avec son
> coût de migration.** Les deux étapes, pas l'une ou l'autre.

```go
package config

import "slices"

type Config struct {
    Name   string
    Tags   []string
    Limits map[string]int
}

// Option describes a change to apply to a Config.
// An absent option does nothing: so there is no value
// meaning "do not override".
type Option func(*Config)

// WithName replaces the name. The empty string is a legitimate value.
func WithName(name string) Option {
    return func(c *Config) { c.Name = name }
}

// WithTags replaces the whole list of tags.
// WithTags() with no argument empties the list.
func WithTags(tags ...string) Option {
    // Required: f(s...) passes the caller's slice without copying it.
    cp := slices.Clone(tags)
    return func(c *Config) { c.Tags = cp }
}

// WithLimit sets one limit without touching the others.
func WithLimit(key string, value int) Option {
    return func(c *Config) { c.Limits[key] = value }
}

// WithoutLimit removes a limit inherited from the base.
func WithoutLimit(key string) Option {
    return func(c *Config) { delete(c.Limits, key) }
}

// Apply returns a new Config obtained by applying opts to base,
// in the given order.
//
// Guarantees:
//   - base is not modified;
//   - the result shares no mutable structure with base nor with the
//     values captured by the options;
//   - the result's Limits field is never nil.
//
// Options are applied in order: on conflict, the last one wins.
func Apply(base Config, opts ...Option) Config {
    result := Config{
        Name:   base.Name,
        Tags:   slices.Clone(base.Tags),
        Limits: make(map[string]int, len(base.Limits)),
    }
    for key, value := range base.Limits {
        result.Limits[key] = value
    }
    for _, opt := range opts {
        opt(&result)
    }
    return result
}
```

### Deux décisions à justifier dans ce code

**1. La map nil est traitée une seule fois, dans `Apply`, pas dans chaque
option.**

`WithLimit` écrit dans `c.Limits`. Si chaque option devait se protéger
elle-même, la règle deviendrait « toute option qui écrit dans la map doit
d'abord vérifier qu'elle n'est pas nil » — une règle que le prochain contributeur
doit connaître, et dont l'oubli produit une panique en production. En la
garantissant dans `Apply` (`make` au lieu de `maps.Clone`), c'est une
**précondition de l'opération**, établie une fois, impossible à oublier. C'est
encore la hiérarchie des garde-fous : faire descendre la règle le plus bas
possible.

Contrepartie assumée, et documentée dans le contrat : `Limits` n'est jamais nil
en sortie, même quand la base n'en avait pas.

**2. `WithTags` clone son argument, et ce n'est pas facultatif.**

En Go, `f(s...)` ne copie pas le slice : il transmet celui de l'appelant.
Démonstration avec une version sans clone :

```go
myTags := []string{"prod", "legacy"}
var c Config
WithTagsNaive(myTags...)(&c)
c.Tags[0] = "MUTE"

fmt.Println(myTags)                   // [MUTE legacy]   ← modified!
fmt.Println(&myTags[0] == &c.Tags[0]) // true            ← same array
```

Sans ce `slices.Clone`, l'isolation est rompue — non pas vis-à-vis de `base`,
mais vis-à-vis du slice capturé par l'option. C'est exactement le même piège que
`override` non clonée à l'étape 1, sous une forme que la signature rend
invisible.

## Le test qui tente de casser le contrat

Afficher le résultat d'une fusion n'est pas un test : c'est un log qu'un humain
doit relire.

> **Un test conclut tout seul.** S'il faut lire la sortie pour savoir si c'est
> bon, il n'y a pas de test.

Et un test ne cherche pas à confirmer que le cas nominal marche : il cherche à
**violer les garanties annoncées**.

```go
func TestApplyIsolation(t *testing.T) {
    tags := []string{"prod"}
    base := Config{"payment", tags, map[string]int{"max": 10}}

    result := Apply(base, WithTags(tags...))

    result.Tags[0] = "MUTE"
    result.Limits["max"] = 999
    result.Tags = append(result.Tags, "audit")

    if base.Name != "payment" || !slices.Equal(base.Tags, []string{"prod"}) ||
        !maps.Equal(base.Limits, map[string]int{"max": 10}) {
        t.Fatalf("base changed by writes to the result: %+v", base)
    }
    if !slices.Equal(tags, []string{"prod"}) {
        t.Fatalf("the slice passed to WithTags was changed: %v", tags)
    }
}

func TestApplyDoesNotPanic(t *testing.T) {
    var zero Config // Name "", Tags nil, Limits nil
    r := Apply(zero, WithLimit("max", 10), WithoutLimit("absent"))
    if r.Limits["max"] != 10 {
        t.Fatalf("Limits = %v", r.Limits)
    }
    if Apply(zero).Limits == nil {
        t.Fatal("the result's Limits must never be nil")
    }
}
```

Le reste se met en table — **une seule** table dont chaque entrée porte son nom,
son entrée et sa sortie attendue. Deux slices parallèles indexées ensemble sont à
proscrire : rien ne garantit qu'elles aient la même longueur, et rien ne relie
visuellement le cas *n* de l'une au cas *n* de l'autre.

```go
tc := []struct {
    name string
    opts []Option
    want Config
}{
    {"without options, the base is kept", nil /* … */},
    {"one limit changes, the others survive", []Option{WithLimit("timeout_ms", 45000)} /* … */},
    {"the name can be emptied explicitly", []Option{WithName("")} /* … */},
    {"the tags can be emptied explicitly", []Option{WithTags()} /* … */},
    {"an inherited limit can be removed", []Option{WithoutLimit("max_amount")} /* … */},
    {"the last option wins", []Option{WithName("a"), WithName("b")} /* … */},
}
```

Les trois cas du milieu sont ceux qui échouaient dans toutes les versions
naïves. Ce sont eux qui prouvent que le problème de conception est réglé, pas les
autres.

## À retenir

1. **On clone quand on va conserver une référence vers la structure mutable d'un
   autre.** Ni « jamais », ni « au cas où ».
2. **Une map est un ensemble de réglages adressables → fusion. Un slice est une
   valeur unique → remplacement.** Le critère est la possibilité de désigner un
   élément seul.
3. **Détourner la valeur zéro en sentinelle « absent » coûte la valeur zéro
   elle-même.** C'est parfois acceptable, jamais gratuit, et toujours à
   documenter.
4. **Quand une représentation force à inventer des valeurs spéciales, changer de
   représentation vaut mieux qu'ajouter un cas.**
5. **Une limite documentée est une décision de conception ; la même limite
   passée sous silence est un piège.** Sous signature imposée, on livre la
   meilleure version *et* on écrit ce qu'elle ne sait pas faire — puis on
   propose le changement de signature à part, avec son coût.
6. **Le contrat écrit est un test de la conception.** Ce qu'on ne peut pas
   énoncer simplement n'est pas conçu.
7. **Une API se juge à son site d'appel**, pas à son implémentation.
8. **Choisir entre patch et options est une question de contrainte** (d'où vient
   la surcharge ?), pas de goût.
9. **Un test conclut tout seul, et cherche à casser le contrat**, pas à confirmer
   le cas nominal.
