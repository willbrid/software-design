# Correction — Exercice 1.4 / 3 (refactoring)

## L'énoncé

Une interface de dépôt à cinq méthodes, dont quatre prennent du SQL en
paramètre et la cinquième rend la connexion. Et trois appels réels, pris dans
trois modules différents. Le code est dans
[1.4-exercices.md](../exercices/1.4-exercices.md).

## Question 1 — Combien d'implémentations, et qu'est-ce qu'elle cache ?

### Méthode par méthode

| Méthode | Ce qu'elle exige d'une implémentation |
|---|---|
| `FindAll(query string, ...)` | comprendre le SQL de PostgreSQL |
| `FindOne(query string, ...)` | idem |
| `Exec(query string, ...)` | idem, et rendre un `sql.Result` |
| `BeginTx() (*sql.Tx, error)` | **être** `database/sql` |
| `DB() *sql.DB` | **être** `database/sql` |

Les deux dernières ne demandent pas de ressembler à une base SQL : elles
exigent de rendre des types concrets de `database/sql`. Donc :

> Cette interface admet exactement **une** implémentation : `*sql.DB`. Et un
> double de test qui prétendrait l'implémenter devrait fabriquer un `*sql.Tx`,
> ce qui n'est pas possible sans une vraie base.

### Qu'est-ce qu'elle cache ?

**Rien.** C'est la réponse, et il faut la dire sans nuance.

Elle ne cache pas le dialecte, puisque l'appelant écrit le SQL. Pas le schéma,
puisque l'appelant nomme les colonnes. Pas les transactions, puisqu'elles sont
dans la signature. Pas le pilote, puisque `DB()` le rend.

Ce qu'elle ajoute, en revanche : un niveau d'indirection, un fichier, une
structure à construire et à injecter, et le mot « Repository » — qui donne à
tout le monde l'impression que la question de la persistance a été traitée.

> Une abstraction qui ne cache rien et qui porte un nom de patron de
> conception est pire qu'un appel direct à `*sql.DB`. L'appel direct est
> honnête : on voit qu'on parle à une base. Celle-ci fait croire qu'une
> frontière existe.

## Question 2 — Le test du miroir, et le second test

### Le miroir

`CommandeRepository` est le miroir de `*sql.DB` : ses cinq méthodes sont cinq
méthodes de `database/sql`, renommées pour deux d'entre elles. Ajouter une
seconde implémentation — un dépôt en mémoire, un dépôt sur une API — obligerait
à réécrire l'interface entièrement.

### Ce qu'un appelant doit savoir pour utiliser `FindAll` correctement

C'est le test le plus dur, et la liste est accablante :

1. que le SGBD est PostgreSQL, pas MySQL ni SQLite ;
2. que les paramètres sont numérotés `$1`, `$2` — pas `?` ;
3. le nom de la table ;
4. le nom et l'ordre des colonnes ;
5. que les colonnes doivent correspondre aux champs scannés, dans le bon
   ordre, et que ce mapping est invisible depuis l'appel ;
6. que `NULL` dans une colonne non nullable fera échouer le `Scan`, à
   l'exécution ;
7. qu'il faut une clause `LIMIT`, sinon on charge toute la table en mémoire ;
8. qu'il faut un index sur `client` et `creee_le`, sinon le `ORDER BY` fait un
   tri complet ;
9. qu'il n'y a pas de `context`, donc pas de délai maximal ;
10. que l'erreur rendue peut être `sql.ErrNoRows`, une erreur de syntaxe, une
    erreur de contrainte, ou une erreur réseau, et que rien ne les distingue.

Dix choses. Le critère de la leçon — *combien de fois dois-je lire derrière
l'abstraction ?* — donne la réponse : **à chaque usage**.

> Une abstraction qui exige de son appelant qu'il connaisse le dialecte, le
> schéma, les index et le mapping n'abstrait pas la base : elle la rend
> seulement plus pénible à appeler.

## Question 3 — `DB()`

### Ce qu'elle annule

Tout. Elle rend la connexion brute, donc quiconque détient l'interface peut
faire **n'importe quoi** : lire une autre table, écrire dans une autre table,
poser un verrou, lancer une migration, ouvrir une transaction de trente
minutes — l'incident de la correction 1.3 / 5.

Et `TotalDuJour` l'utilise, ce qui montre que ce n'est pas une porte de secours
théorique : c'est un chemin normal.

### Pourquoi sa seule existence rend les quatre autres décoratives

Parce qu'une garantie est définie par ce qu'elle rend **impossible**. Les
quatre autres méthodes prétendent encadrer l'accès aux commandes. `DB()` rend
cet encadrement contournable en un appel, sans erreur, sans revue, sans
avertissement.

> Un garde-fou avec une porte de sortie non gardée n'est pas un garde-fou
> affaibli : c'est une **décoration**. Le périmètre protégé n'est pas « presque
> tout », il est vide.

C'est la même conclusion qu'à la correction 1.2 / 4, par l'autre bout : là-bas,
une porte de sortie **documentée et auditée** était nécessaire ; ici, elle est
anonyme et permanente. La différence entre les deux n'est pas l'existence de la
porte, c'est qui la franchit et si on le sait.

## Question 4 — L'interface réécrite en questions

```go
// Package commande possede les commandes : il est le seul a ecrire dans la
// table, et le seul a savoir qu'il y a une table.
//
// Raison de changer : ce qu'est une commande et ce qui peut lui arriver.
package commande

import (
    "context"
    "errors"
    "time"
)

type (
    ID     int64
    Client string
    Statut string
)

const (
    Enregistree Statut = "enregistree"
    Annulee     Statut = "annulee"
    Expediee    Statut = "expediee"
)

// Commande est un modele de lecture : une photographie, pas un objet vivant.
// Ses champs sont exportes parce qu'il n'a aucun invariant a defendre — il
// est deja le resultat d'une lecture. Ce qui a des invariants, ce sont les
// operations ci-dessous.
type Commande struct {
    ID      ID
    Client  Client
    Total   int64
    CreeeLe time.Time
    Statut  Statut
}

var (
    ErrIntrouvable  = errors.New("commande : introuvable")
    ErrDejaAnnulee  = errors.New("commande : deja annulee")
    ErrDejaExpediee = errors.New("commande : expediee, annulation impossible")
    ErrCurseur      = errors.New("commande : curseur invalide")
    ErrPage         = errors.New("commande : taille de page invalide")
)

// Curseur designe une position dans une suite de resultats. Il est opaque :
// l'appelant le recoit et le rend, il ne le lit pas.
type Curseur string

type Page struct {
    Taille int
    Apres  Curseur // vide = depuis le debut
}

// Tranche est une page de resultats, avec de quoi demander la suivante.
type Tranche struct {
    Commandes []Commande
    Suivante  Curseur
    Fin       bool
}

// Journal est la question que posent les modules de lecture.
//
// Garanties :
//   - les commandes sont rendues de la plus recente a la plus ancienne ;
//   - la pagination par curseur est STABLE : une commande creee pendant la
//     pagination n'apparait pas, et aucune commande existante n'est sautee
//     ni rendue deux fois. C'est une promesse que LIMIT/OFFSET ne peut pas
//     tenir.
//
// Ce qui n'est pas garanti :
//   - la fraicheur : une commande creee a l'instant peut ne pas apparaitre ;
//   - le nombre total de resultats. Il n'est pas rendu, et c'est volontaire :
//     un COMPTE exact sur une grande table coute plus cher que la page
//     elle-meme.
type Journal interface {
    Recentes(ctx context.Context, c Client, p Page) (Tranche, error)
}

// Annulation est l'operation, et c'est le point important de l'exercice.
//
// Annuler passe la commande en « annulee » ET enregistre le mouvement de
// stock de retour. Les deux ecritures sont ATOMIQUES : c'est une promesse du
// contrat, pas un detail d'implementation.
//
// C'est pourquoi il n'y a pas de type Transaction dans cette interface. La
// frontiere de l'abstraction et la frontiere de la transaction coincident :
// ce qui doit etre atomique est UNE operation.
//
// Annuler est idempotent sur le statut : annuler une commande deja annulee
// rend ErrDejaAnnulee et n'ecrit rien.
type Annulation interface {
    Annuler(ctx context.Context, id ID, motif string) (Commande, error)
}
```

**Deux interfaces, trois méthodes au total**, et chacune porte un besoin
nommé :

| Interface | Méthode | Le besoin |
|---|---|---|
| `Journal` | `Recentes` | « montre au client ses dernières commandes » |
| `Annulation` | `Annuler` | « annule cette commande et rends le stock » |

Trois observations.

**Les erreurs sont dans ce paquet.** `ErrIntrouvable`, `ErrDejaAnnulee`,
`ErrDejaExpediee`. `sql.ErrNoRows` ne franchit plus la frontière, et
`ErrDejaExpediee` est une information métier que l'ancienne interface ne
pouvait pas exprimer du tout.

**`Commande` garde ses champs exportés**, et c'est un choix assumé :

```go
// Commande est un modele de lecture : une photographie, pas un objet vivant.
// Ses champs sont exportes parce qu'il n'a aucun invariant a defendre — il
// est deja le resultat d'une lecture.
```

Ce n'est pas une contradiction avec `piece.Limites` ou `prix.Grille`, qui
cachent les leurs. La différence est l'existence d'un invariant : un modèle de
lecture n'en a aucun à défendre. Cacher des champs sans invariant à protéger,
c'est l'accesseur-par-champ de la leçon.

**Ce qui n'est pas garanti est écrit**, et il y a une absence volontaire :

```go
//   - le nombre total de resultats. Il n'est pas rendu, et c'est volontaire :
//     un COMPTE exact sur une grande table coute plus cher que la page
//     elle-meme.
```

C'est la rubrique que personne n'écrit, et c'est celle qui évite une demande
produit impossible six mois plus tard.

## Question 5 — Les transactions

C'est la partie difficile, et il y a deux conceptions défendables.

### Conception A — l'unité de travail

```go
type Transaction interface {
    // Dans execute f dans une transaction : si f rend une erreur, rien
    // n'est ecrit.
    Dans(ctx context.Context, f func(ctx context.Context) error) error
}
```

L'appelant écrit :

```go
err := tx.Dans(ctx, func(ctx context.Context) error {
    if err := commandes.Annuler(ctx, id); err != nil {
        return err
    }
    return stock.Retourner(ctx, id)
})
```

**Ce qu'elle apporte :** n'importe quelle combinaison d'écritures devient
atomique, sans que `*sql.Tx` apparaisse nulle part.

**Ce qu'elle coûte**, et c'est sévère :

1. **La transaction voyage dans le `ctx`.** C'est la seule façon de faire en
   Go, et c'est un couplage de degré 4 de la leçon 1.3 : une dépendance
   invisible, non typée, que le compilateur ne vérifie pas. Oublier de
   propager le `ctx` dans un appel donne une écriture **hors** transaction, et
   rien ne le signale.
2. **Elle expose l'existence des transactions** à des appelants qui ne
   devraient pas en entendre parler. Un module de notification qui reçoit cette
   interface sait maintenant qu'il y a une base relationnelle derrière.
3. **Elle ne compose pas.** Une transaction imbriquée doit être détectée et
   aplatie, ce qui demande à `Dans` d'inspecter le `ctx` — plus de magie.
4. **Elle rend la frontière poreuse** : le périmètre de la transaction est
   désormais décidé par l'appelant, donc le propriétaire de la table ne
   contrôle plus la durée de ses propres verrous.

### Conception B — l'opération atomique

```go
type Annulation interface {
    // Annuler passe la commande en « annulee » ET enregistre le mouvement de
    // stock de retour. Les deux ecritures sont ATOMIQUES : c'est une promesse
    // du contrat, pas un detail d'implementation.
    Annuler(ctx context.Context, id ID, motif string) (Commande, error)
}
```

**Ce qu'elle apporte :** l'atomicité devient une **promesse du contrat** au lieu
d'un mécanisme exposé. L'appelant ne sait pas qu'il y a une transaction, et
c'est précisément ce qu'on veut.

Et la raison de fond :

> La frontière de l'abstraction et la frontière de la transaction doivent
> coïncider. Si deux écritures doivent être atomiques, elles sont **une seule
> opération**, et cette opération est l'abstraction.

**Ce qu'elle coûte, et c'est un coût réel :** l'opération touche deux tables,
`commandes` et `mouvements_stock`. Donc un module écrit dans une table qui ne
lui appartient pas — ce qui contredit la règle « un écrivain, N lecteurs » de
la correction 1.3 / 3.

### Mon choix : B, et comment je paie son coût

Je choisis B, parce que le coût de A — une transaction qui voyage dans un
`ctx`, non vérifiée par le compilateur — est le genre de couplage muet qui
produit des bugs qu'on ne trouve pas.

Et la contradiction avec « un écrivain par table » se résout de l'une de ces
deux façons, selon le critère de la leçon 1.3 :

**Si `commandes` et `mouvements_stock` changent toujours ensemble** — même
demandeur, même rythme —, alors elles n'avaient pas à être dans deux modules.
Le module est `commande`, et il possède les deux tables. La frontière était au
mauvais endroit, et c'est l'historique git qui le dira.

**Si elles ont vraiment deux demandeurs distincts**, alors l'atomicité entre
elles n'est pas tenable à moindre coût, et il faut renoncer à la transaction
commune : `Annuler` écrit dans `commandes` **et dépose un message dans la
boîte d'envoi** — la `sortie` de la correction 1.3 / 4 —, dans la même
transaction. Le module de stock consomme et retourne la marchandise. On passe
d'une atomicité à une cohérence éventuelle, et on le dit dans le contrat.

> Quand deux écritures doivent être atomiques et vivent dans deux modules, il
> n'y a que trois issues : fusionner les modules, accepter la cohérence
> éventuelle, ou mentir. Les deux premières sont des décisions ; la troisième
> est ce qu'on obtient par défaut.

## Question 6 — `TotalDuJour` appartient-il à ce dépôt ?

Les deux grilles ne donnent pas la même réponse, et c'est le point de la
question.

**Avec les critères de la leçon 1.2 — qui peut exiger que ça change ?** Le
demandeur de `TotalDuJour` est le contrôle de gestion. Celui de `Recentes` est
le produit. Celui d'`Annuler` est le service client. Trois demandeurs : donc
`TotalDuJour` n'appartient pas au même module. Verdict : **sors-le.**

**Avec les critères de la leçon 1.4 — quelle question l'appelant pose-t-il ?**
« Combien ai-je facturé aujourd'hui » n'est pas une question sur les
commandes, c'est une question sur un **agrégat**. Elle a sa propre fraîcheur
acceptable (la journée d'hier suffit), sa propre latence acceptable (quelques
secondes), et son propre volume. Verdict : **sors-le aussi**, mais pour une
raison différente et plus forte.

### Et la réponse est la conjonction des deux

La leçon 1.2 dit *où* : dans un module `statistiques`, avec son demandeur.

La leçon 1.4 dit *quoi* : pas une méthode de plus sur le journal des
commandes, mais une abstraction à part, dont le contrat promet autre chose —
une fraîcheur approximative, et donc le droit de lire une réplique ou une table
d'agrégats pré-calculés.

> Deux questions qui ont des exigences de fraîcheur différentes ne sont pas
> deux méthodes de la même abstraction. Les mettre ensemble force la plus
> exigeante sur les deux, ou la plus laxiste.

C'est d'ailleurs exactement l'arbitrage de la correction 1.3 / 3 sur le module
`statistiques` : réplique de lecture et vue dédiée.

## Question 7 — La pagination

### Où elle doit aller

Dans le contrat, et pas dans une chaîne SQL chez l'appelant. Elle y est :

```go
type Page struct {
    Taille int
    Apres  Curseur
}

type Tranche struct {
    Commandes []Commande
    Suivante  Curseur
    Fin       bool
}
```

Le `Curseur` est **opaque** : l'appelant le reçoit et le rend, il ne le lit
pas. Donc l'implémentation peut changer sa forme — un couple
`(horodatage, id)`, un identifiant de curseur côté serveur, un *token*
chiffré — sans casser personne.

### La promesse que le contrat doit faire

```go
//   - la pagination par curseur est STABLE : une commande creee pendant la
//     pagination n'apparait pas, et aucune commande existante n'est sautee
//     ni rendue deux fois. C'est une promesse que LIMIT/OFFSET ne peut pas
//     tenir.
```

Et ce n'est pas une opinion. Deux implémentations, le même scénario, et les
deux résultats :

```go
// Package commandemem implemente le journal des commandes en memoire, de
// deux facons : par curseur et par decalage.
//
// Les deux existent uniquement pour que le test puisse montrer qu'elles ne
// tiennent pas la meme promesse. En production, il n'y en aurait qu'une.
package commandemem

import (
    "context"
    "fmt"
    "sort"
    "strconv"
    "strings"

    "exemple/entrepot/commande"
)

type Depot struct {
    commandes []commande.Commande
}

func New(cs ...commande.Commande) *Depot {
    d := &Depot{commandes: append([]commande.Commande(nil), cs...)}
    d.trier()
    return d
}

func (d *Depot) Ajouter(c commande.Commande) {
    d.commandes = append(d.commandes, c)
    d.trier()
}

func (d *Depot) Supprimer(id commande.ID) {
    for i, c := range d.commandes {
        if c.ID == id {
            d.commandes = append(d.commandes[:i], d.commandes[i+1:]...)
            return
        }
    }
}

// trier : de la plus recente a la plus ancienne, l'ID departageant les
// ex aequo. Sans ce second critere, l'ordre n'est pas total, donc la
// pagination n'est pas stable — meme avec un curseur.
func (d *Depot) trier() {
    sort.Slice(d.commandes, func(i, j int) bool {
        a, b := d.commandes[i], d.commandes[j]
        if !a.CreeeLe.Equal(b.CreeeLe) {
            return a.CreeeLe.After(b.CreeeLe)
        }
        return a.ID > b.ID
    })
}

// RecentesParCurseur est l'implementation du contrat.
//
// Le curseur encode la position dans l'ordre total : « donne-moi ce qui vient
// strictement apres ce point ». Il ne compte pas, il situe.
func (d *Depot) RecentesParCurseur(_ context.Context, cl commande.Client, p commande.Page) (commande.Tranche, error) {
    if p.Taille <= 0 {
        return commande.Tranche{}, commande.ErrPage
    }

    debut := 0
    if p.Apres != "" {
        h, id, err := decoder(p.Apres)
        if err != nil {
            return commande.Tranche{}, err
        }
        debut = -1
        for i, c := range d.commandes {
            if c.Client != cl {
                continue
            }
            ch := c.CreeeLe.UnixNano()
            if ch < h || (ch == h && c.ID < id) {
                debut = i
                break
            }
        }
        if debut == -1 {
            return commande.Tranche{Fin: true}, nil
        }
    }

    var out []commande.Commande
    i := debut
    for ; i < len(d.commandes) && len(out) < p.Taille; i++ {
        if d.commandes[i].Client == cl {
            out = append(out, d.commandes[i])
        }
    }

    t := commande.Tranche{Commandes: out}
    if len(out) < p.Taille {
        t.Fin = true
        return t, nil
    }
    dernier := out[len(out)-1]
    t.Suivante = encoder(dernier)
    return t, nil
}

// RecentesParDecalage est le contre-exemple : la meme signature, une promesse
// en moins.
func (d *Depot) RecentesParDecalage(_ context.Context, cl commande.Client, taille, decalage int) ([]commande.Commande, error) {
    if taille <= 0 {
        return nil, commande.ErrPage
    }

    var duClient []commande.Commande
    for _, c := range d.commandes {
        if c.Client == cl {
            duClient = append(duClient, c)
        }
    }
    if decalage >= len(duClient) {
        return nil, nil
    }
    fin := decalage + taille
    if fin > len(duClient) {
        fin = len(duClient)
    }
    return duClient[decalage:fin], nil
}

func encoder(c commande.Commande) commande.Curseur {
    return commande.Curseur(fmt.Sprintf("%d:%d", c.CreeeLe.UnixNano(), c.ID))
}

func decoder(cur commande.Curseur) (int64, commande.ID, error) {
    parties := strings.SplitN(string(cur), ":", 2)
    if len(parties) != 2 {
        return 0, 0, commande.ErrCurseur
    }
    h, err := strconv.ParseInt(parties[0], 10, 64)
    if err != nil {
        return 0, 0, commande.ErrCurseur
    }
    id, err := strconv.ParseInt(parties[1], 10, 64)
    if err != nil {
        return 0, 0, commande.ErrCurseur
    }
    return h, commande.ID(id), nil
}
```

```go
package commandemem_test

import (
    "context"
    "testing"
    "time"

    "exemple/entrepot/commande"
    "exemple/entrepot/commandemem"
)

const client = commande.Client("awa")

func jeu() *commandemem.Depot {
    base := time.Date(2026, 10, 1, 8, 0, 0, 0, time.UTC)
    var cs []commande.Commande
    // Six commandes, de la plus ancienne a la plus recente.
    for i := 1; i <= 6; i++ {
        cs = append(cs, commande.Commande{
            ID:      commande.ID(i),
            Client:  client,
            Total:   int64(i) * 1000,
            CreeeLe: base.Add(time.Duration(i) * time.Hour),
            Statut:  commande.Enregistree,
        })
    }
    return commandemem.New(cs...)
}

func ids(cs []commande.Commande) []commande.ID {
    out := make([]commande.ID, 0, len(cs))
    for _, c := range cs {
        out = append(out, c.ID)
    }
    return out
}

// La promesse du contrat : une insertion pendant la pagination ne fait ni
// sauter ni dupliquer une commande existante.
func TestLeCurseurNeSauteRien(t *testing.T) {
    d := jeu()
    ctx := context.Background()

    page1, err := d.RecentesParCurseur(ctx, client, commande.Page{Taille: 2})
    if err != nil {
        t.Fatal(err)
    }
    if got := ids(page1.Commandes); len(got) != 2 || got[0] != 6 || got[1] != 5 {
        t.Fatalf("page 1 = %v, attendu [6 5]", got)
    }

    // Une commande arrive entre les deux pages. Elle est la plus recente.
    d.Ajouter(commande.Commande{
        ID: 99, Client: client, Total: 500,
        CreeeLe: time.Date(2026, 10, 1, 20, 0, 0, 0, time.UTC),
        Statut:  commande.Enregistree,
    })

    page2, err := d.RecentesParCurseur(ctx, client, commande.Page{Taille: 2, Apres: page1.Suivante})
    if err != nil {
        t.Fatal(err)
    }
    if got := ids(page2.Commandes); len(got) != 2 || got[0] != 4 || got[1] != 3 {
        t.Fatalf("page 2 = %v, attendu [4 3] : rien saute, rien duplique", got)
    }
}

// Le meme scenario avec un decalage : l'insertion decale tout, et la
// commande 5 est rendue une seconde fois.
func TestLeDecalageDupliqueApresUneInsertion(t *testing.T) {
    d := jeu()
    ctx := context.Background()

    page1, err := d.RecentesParDecalage(ctx, client, 2, 0)
    if err != nil {
        t.Fatal(err)
    }
    if got := ids(page1); len(got) != 2 || got[0] != 6 || got[1] != 5 {
        t.Fatalf("page 1 = %v, attendu [6 5]", got)
    }

    d.Ajouter(commande.Commande{
        ID: 99, Client: client, Total: 500,
        CreeeLe: time.Date(2026, 10, 1, 20, 0, 0, 0, time.UTC),
        Statut:  commande.Enregistree,
    })

    page2, err := d.RecentesParDecalage(ctx, client, 2, 2)
    if err != nil {
        t.Fatal(err)
    }
    got := ids(page2)
    if len(got) != 2 {
        t.Fatalf("page 2 = %v", got)
    }
    // Le decalage de 2 pointe une position que l'insertion a deplacee : la
    // commande 5, deja vue en page 1, revient en page 2.
    if got[0] != 5 {
        t.Fatalf("page 2 = %v : on attendait la commande 5 rendue une seconde fois", got)
    }
    t.Logf("page 1 = [6 5], page 2 = %v : la commande 5 est rendue deux fois", got)
}

// Le symetrique, et le plus grave : une suppression decale dans l'autre sens,
// et une commande n'est JAMAIS rendue. L'utilisateur ne la verra pas, et rien
// ne le signale — ni erreur, ni trou visible dans la liste.
func TestLeDecalageSauteApresUneSuppression(t *testing.T) {
    d := jeu()
    ctx := context.Background()

    page1, err := d.RecentesParDecalage(ctx, client, 2, 0)
    if err != nil {
        t.Fatal(err)
    }
    if got := ids(page1); got[0] != 6 || got[1] != 5 {
        t.Fatalf("page 1 = %v, attendu [6 5]", got)
    }

    d.Supprimer(6) // la plus recente est annulee et purgee

    page2, err := d.RecentesParDecalage(ctx, client, 2, 2)
    if err != nil {
        t.Fatal(err)
    }
    got := ids(page2)
    if len(got) != 2 || got[0] != 3 {
        t.Fatalf("page 2 = %v, attendu [3 2]", got)
    }
    t.Logf("page 1 = [6 5], page 2 = %v : la commande 4 n'est rendue nulle part", got)

    // Et la preuve, avec le curseur : rien n'est saute.
    d2 := jeu()
    p1, _ := d2.RecentesParCurseur(ctx, client, commande.Page{Taille: 2})
    d2.Supprimer(6)
    p2, _ := d2.RecentesParCurseur(ctx, client, commande.Page{Taille: 2, Apres: p1.Suivante})
    if got := ids(p2.Commandes); len(got) != 2 || got[0] != 4 || got[1] != 3 {
        t.Fatalf("curseur, page 2 = %v, attendu [4 3]", got)
    }
}

func TestFinDePagination(t *testing.T) {
    d := jeu()
    ctx := context.Background()

    var vues []commande.ID
    page := commande.Page{Taille: 4}
    for i := 0; i < 10; i++ {
        tr, err := d.RecentesParCurseur(ctx, client, page)
        if err != nil {
            t.Fatal(err)
        }
        vues = append(vues, ids(tr.Commandes)...)
        if tr.Fin {
            break
        }
        page.Apres = tr.Suivante
    }

    if len(vues) != 6 {
        t.Fatalf("%d commandes vues, attendu 6 : %v", len(vues), vues)
    }
    vu := map[commande.ID]bool{}
    for _, id := range vues {
        if vu[id] {
            t.Errorf("commande %d rendue deux fois", id)
        }
        vu[id] = true
    }
}

```

Les deux tests du décalage sont la démonstration :

```
page 1 = [6 5], page 2 = [5 4] : la commande 5 est rendue deux fois
page 1 = [6 5], page 2 = [3 2] : la commande 4 n'est rendue nulle part
```

Une insertion décale tout vers le bas, donc une ligne déjà vue revient. Une
suppression décale vers le haut, donc **une ligne n'est jamais rendue** — et
c'est le cas grave : aucune erreur, aucun trou visible, l'utilisateur ne la
verra simplement pas.

> `LIMIT/OFFSET` et la pagination par curseur ne sont pas deux
> implémentations d'un même contrat : ce sont **deux contrats**. L'un promet la
> stabilité, l'autre ne peut pas. Les cacher derrière la même signature est le
> type de fuite que la leçon appelle « d'autant plus dangereuse qu'elle marche
> presque toujours ».

### Le détail qui conditionne tout

```go
// trier : de la plus recente a la plus ancienne, l'ID departageant les
// ex aequo. Sans ce second critere, l'ordre n'est pas total, donc la
// pagination n'est pas stable — meme avec un curseur.
```

Un curseur situe une position dans un ordre. Si l'ordre n'est pas **total** —
deux commandes au même horodatage —, la position est ambiguë et le curseur
saute ou duplique, exactement comme le décalage. C'est l'erreur classique de
mise en œuvre d'une pagination par curseur, et elle ne se manifeste que sur
les ex aequo, donc rarement, donc tard.

> Un curseur exige un ordre **total**. `ORDER BY creee_le` n'en est pas un ;
> `ORDER BY creee_le DESC, id DESC` en est un. La différence se voit le jour où
> deux lignes partagent un horodatage.

### Ce que le curseur coûte à l'appelant

Il faut le dire : on perd le saut direct à la page 7. Un curseur ne permet que
« la suite ». Donc :

- pas de numéros de page dans l'interface utilisateur ;
- pas de « dernière page » sans parcourir ;
- et pas de nombre total de résultats, ce qui est de toute façon ce que le
  contrat refusait déjà de promettre.

C'est un changement de **produit**, pas seulement de code. En échange, on obtient
une pagination qui reste correcte sous écriture concurrente, et dont le coût ne
grandit pas avec la profondeur — un `OFFSET 100000` fait lire et jeter cent
mille lignes.

## À retenir

1. Une interface qui prend du SQL en paramètre ne cache rien. Avec un nom de
   patron de conception, elle est pire qu'un appel direct : elle fait croire
   qu'une frontière existe.
2. Compte ce que l'appelant doit savoir pour appeler correctement. Dix choses,
   c'est un alias, pas une abstraction.
3. Un garde-fou avec une porte de sortie non gardée n'est pas affaibli : il est
   décoratif. Le périmètre protégé est vide.
4. Un modèle de lecture n'a pas d'invariant à défendre : ses champs peuvent
   être exportés. Cacher sans invariant à protéger, c'est l'accesseur par
   champ.
5. La frontière de l'abstraction et celle de la transaction doivent coïncider.
   Ce qui doit être atomique est une seule opération.
6. Une transaction qui voyage dans un `ctx` est un couplage que le compilateur
   ne vérifie pas. Oublier de propager donne une écriture hors transaction,
   sans aucun signal.
7. Deux écritures atomiques dans deux modules : fusionner, accepter la
   cohérence éventuelle, ou mentir. La troisième est le défaut.
8. Deux questions qui ont des exigences de fraîcheur différentes ne sont pas
   deux méthodes de la même abstraction.
9. `LIMIT/OFFSET` et le curseur sont deux contrats, pas deux implémentations.
   Une insertion duplique, une suppression fait disparaître.
10. Un curseur exige un ordre **total**. Sinon il saute, comme le décalage, mais
    seulement sur les ex aequo — donc tard.
11. Un curseur coûte les numéros de page. C'est une décision produit, et elle
    doit être prise par le produit.
