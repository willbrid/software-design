# Correction — Exercice 1.1 / 3 (refactoring)

## L'énoncé

```go
type Ligne struct {
    Prix     float64
    Quantite int
}

type Panier struct {
    Lignes []Ligne
    Total  float64
}

func (p *Panier) Ajouter(l Ligne) {
    p.Lignes = append(p.Lignes, l)
    p.Total += l.Prix * float64(l.Quantite)
}

func (p *Panier) Lignes2() []Ligne {
    return p.Lignes
}

func CalculerFrais(lignes []Ligne) float64 {
    for i := range lignes {
        if lignes[i].Quantite > 10 {
            lignes[i].Quantite = 10   // plafonnement
        }
    }
    total := 0.0
    for _, l := range lignes {
        total += l.Prix * float64(l.Quantite)
    }
    return total * 0.02
}
```

```go
panier := &Panier{}
panier.Ajouter(Ligne{Prix: 500, Quantite: 12})

frais := CalculerFrais(panier.Lignes2())

fmt.Println(frais)
fmt.Println(panier.Total)
fmt.Println(panier.Lignes[0].Quantite)
```

Prises isolément, les trois fonctions semblent correctes. `Ajouter` ajoute,
`Lignes2` renvoie les lignes, `CalculerFrais` calcule des frais. Aucune revue de
code portant sur une seule d'entre elles ne signalerait quoi que ce soit. Le
défaut n'existe qu'**entre** elles — c'est la signature d'un problème de
conception, pas d'une faute de codage.

---

## Étape 1 — Ce qu'affichent les trois `Println`

```
100
6000
10
```

Le déroulé, parce que c'est là que se voit le mécanisme :

1. `Ajouter` place `{500, 12}` dans `p.Lignes` et porte `p.Total` à `6000`.
2. `Lignes2()` renvoie `p.Lignes`. Pas une copie : **le même en-tête de slice**,
   donc le même tableau sous-jacent.
3. `CalculerFrais` reçoit une **copie de l'en-tête** — pointeur, longueur,
   capacité. Le tableau, lui, n'est pas copié. `lignes[i].Quantite = 10` écrit
   dans la mémoire du panier.
4. Elle calcule ensuite `500 × 10 = 5000`, puis `5000 × 0.02 = 100`.

Le point de langage, à énoncer précisément : **passer un slice par valeur copie
sa description, pas son contenu.** Un slice n'est pas un tableau, c'est une *vue*
sur un tableau. Copier une vue ne duplique pas ce qu'on regarde à travers. Il en
va de même pour les `map`, les canaux et les pointeurs : le type est copié, la
chose désignée ne l'est pas.

---

## Étape 2 — Le bug

Le bug n'est pas « une variable a changé ». C'est qu'une **règle** a été rompue.

`Panier` porte une promesse implicite que tout lecteur de ce type tient pour
acquise :

> `Total` est la somme des lignes.

Après l'appel, comparons ce que le panier raconte :

| Ce que dit le panier | Valeur |
|---|---|
| `Total` | 6000 (soit 12 × 500) |
| `Lignes[0].Quantite` | 10 |
| Somme réelle des lignes | 5000 |

Le panier affirme deux choses incompatibles. Cette promesse a un nom, et il faut
l'employer : c'est un **invariant** — une propriété qui doit rester vraie à tout
instant où le type est observable de l'extérieur. Le bug, ce n'est pas la
quantité modifiée ; c'est l'invariant violé.

### Le symptôme côté client

Le client a commandé **12 unités à 500 F**. Après le passage sur l'écran des
frais, son panier affiche **10 articles pour 6000 F** — soit 600 F l'unité. Selon
l'écran qu'il consulte, il est facturé 12 et livré 10, ou l'inverse. Et les
frais de 100 F sont assis sur une base de 5000 qui ne correspond à aucun des deux
montants affichés.

Trois caractéristiques rendent ce défaut redoutable, et elles sont plus
importantes que le bug lui-même :

**1. Une règle *de frais* a fuité dans la *commande*.** Plafonner à 10 servait à
limiter l'assiette de calcul des frais. Personne n'a jamais décidé de réduire la
quantité commandée. Une décision locale à un calcul est devenue une décision
métier globale — sans que quiconque l'écrive.

**2. C'est silencieux et durable.** Aucune erreur, aucun log, aucun panic. Le
panier reste faux après le retour de la fonction, pour toute la session. Le
comptable le découvrira des semaines plus tard, sur un écart d'inventaire.

**3. La cause et l'effet sont éloignés.** Le symptôme apparaît dans l'écran de
facturation ; la cause est dans une fonction de calcul de frais appelée trois
couches plus haut. C'est la catégorie de bug la plus coûteuse à diagnostiquer :
celle où la pile d'appels au moment du symptôme ne contient plus le coupable.

> **Un effet de bord ne se paie pas au moment où il est écrit. Il se paie au
> moment où quelqu'un d'autre lit une valeur, ailleurs, plus tard.**

### La fausse piste

Une réponse fréquente est : « il suffit d'appeler `CalculerFrais` deux fois pour
voir le problème ». Vérifions : le second appel retrouve `Quantite = 10`, ne
plafonne rien et renvoie `100`, comme le premier. La fonction est **accidentellement
idempotente**.

Cette vérification négative a une valeur : elle montre qu'un test qui ne
regarderait que la **valeur de retour** de `CalculerFrais` passerait au vert. Le
dommage n'est pas dans ce que la fonction renvoie, il est dans ce qu'elle laisse
derrière elle. Un test ne trouve ce défaut que s'il inspecte l'**état de
l'appelant après l'appel**.

## Étape 3 — Les deux causes

Elles sont de natures différentes, et c'est tout l'intérêt de la question.

### Cause 1 — `Lignes2` : un défaut d'encapsulation

```go
func (p *Panier) Lignes2() []Ligne {
    return p.Lignes    // livre le tableau interne
}
```

Cette méthode a l'apparence d'un accesseur en lecture. Elle n'en est pas un :
elle remet à l'appelant une **poignée d'écriture** sur l'intérieur du panier. Le
`Panier` a beau avoir des méthodes, il ne contrôle plus son propre état. Tout
appelant peut écrire dedans sans passer par lui, et sans qu'il le sache.

### Cause 2 — `CalculerFrais` : un défaut de contrat

```go
func CalculerFrais(lignes []Ligne) float64
```

Cette signature annonce : « donne-moi des lignes, je te rends un nombre ». Le nom
commence par `Calculer`. Rien — ni le nom, ni les types, ni la valeur de retour —
ne laisse deviner qu'elle **écrit** dans ce qu'on lui prête. Le contrat affiché
et le comportement réel divergent.

> Une signature est une promesse. Quand le corps en fait plus que ce que la
> signature annonce, ce « plus » est invisible sur tous les sites d'appel.

### Pourquoi corriger une seule ne suffit pas

L'argument est **symétrique**, et il découle directement du fait que les deux
causes ne vivent pas au même endroit.

**Ne corriger que `CalculerFrais`** (copie défensive à l'intérieur) : le panier
continue de distribuer ses entrailles à qui les demande. La *prochaine* fonction
qui recevra `Lignes2()` — un tri, un filtre, une remise, une sérialisation —
réintroduira exactement le même bug. On a soigné un symptôme, la maladie est
intacte.

**Ne corriger que `Lignes2`** (renvoyer une copie) : le panier est protégé, mais
`CalculerFrais` reste un piège pour **tous les autres appelants**. L'équipe qui
lui passe un slice venu d'une base, d'un JSON ou d'un fichier CSV se fait saccager
ses données sans qu'aucun panier ne soit impliqué.

Chaque correctif ne protège qu'un seul côté de la frontière :

| Correctif | Protège le panier de `CalculerFrais` | Protège le panier des **autres** fonctions | Protège les **autres** appelants de `CalculerFrais` |
|---|---|---|---|
| `Lignes2` seule | oui | oui | **non** |
| `CalculerFrais` seule | oui | **non** | oui |
| Les deux | oui | oui | oui |

`Lignes2` est un défaut d'**encapsulation** : le type ne protège pas son état.
`CalculerFrais` est un défaut de **contrat** : la fonction ne fait pas ce qu'elle
dit. Ce sont deux problèmes distincts qui se sont rencontrés. Réparer l'un ne
dit rien de l'autre.

### La troisième fuite, que l'énoncé ne mentionne pas

```go
type Panier struct {
    Lignes []Ligne   // exporté
    Total  float64   // exporté
}
```

Même avec `Lignes2` corrigée, n'importe qui peut écrire `CalculerFrais(panier.Lignes)`
et retrouver le bug d'origine — ou pire, `panier.Total = 0` directement. Un champ
exporté est une méthode `Set` que l'on n'a pas écrite et que l'on ne peut pas
contrôler.

**Passer les champs en minuscules est la première correction à faire**, avant les
deux autres : c'est elle qui rend les deux autres exécutoires. Tant que le champ
est public, toute garantie du type est une convention de politesse.

## Étape 4 — Les corrections

### `CalculerFrais` : ne pas copier, ne pas muter

La correction spontanée est la copie défensive :

```go
func CalculerFrais(lignes []Ligne) float64 {
    copie := slices.Clone(lignes)     // je copie…
    for i := range copie {
        if copie[i].Quantite > 10 {
            copie[i].Quantite = 10    // …pour avoir le droit de muter
        }
    }
    // …
}
```

Elle est **correcte**, et il faut la savoir. Mais elle traite le symptôme. La
bonne question est en amont : **cette écriture était-elle seulement nécessaire ?**

La quantité plafonnée ne sert qu'à une addition, immédiatement, puis elle est
jetée. Elle n'a aucune raison d'être écrite où que ce soit :

```go
// CalculerFrais renvoie les frais dus pour ces lignes : 2 % du montant,
// la quantite de chaque ligne etant plafonnee a 10 pour ce calcul.
//
// Les lignes ne sont pas modifiees.
func CalculerFrais(lignes []Ligne) float64 {
    total := 0.0
    for _, l := range lignes {
        q := min(l.Quantite, 10)      // valeur locale, jetee aussitot
        total += l.Prix * float64(q)
    }
    return total * 0.02
}
```

Plus d'allocation, une seule boucle, et surtout **plus rien à protéger puisque
plus rien n'écrit**. La copie défensive est la bonne réponse quand on doit
réellement transformer une donnée et conserver le résultat ; ici, elle masquait
une écriture qui n'avait pas lieu d'être.

> **Avant de protéger une mutation, demande-toi si elle est nécessaire.
> Supprimer une écriture vaut toujours mieux que la rendre inoffensive.**

*Note Go :* `min` et `max` sont des fonctions natives du langage depuis Go 1.21,
sur tous les types ordonnés. Inutile de passer par `math.Min`, qui force une
conversion en `float64` aller-retour et fait perdre le type entier.

### `Lignes2` : trois options, trois coûts

Le nom d'abord : `Lignes2` est un nom de champ de bataille — il existe parce que
`Lignes` était déjà pris par le champ. Une fois le champ passé en `lignes`
minuscule, la méthode peut s'appeler `Lignes()`. Un nom né d'une collision est
toujours le signe qu'une décision a été évitée.

**Option A — renvoyer une copie.**

```go
func (p *Panier) Lignes() []Ligne {
    return slices.Clone(p.lignes)
}
```

*Garantit* : l'appelant peut faire ce qu'il veut de ce qu'il reçoit.
*Coûte* : une allocation et une copie O(n) **à chaque appel**, y compris pour les
appelants qui ne feront que lire. `Ligne` ne contenant que des types valeur, un
`Clone` suffit ; si `Ligne` contenait un slice ou une map, il faudrait une copie
profonde — et `slices.Clone` ne le ferait pas.

**Option B — exposer un itérateur en lecture seule** (Go 1.23+).

```go
func (p *Panier) Lignes() iter.Seq[Ligne] {
    return func(yield func(Ligne) bool) {
        for _, l := range p.lignes {
            if !yield(l) { return }   // chaque Ligne est une copie
        }
    }
}
```

*Garantit* : aucune allocation, et l'appelant reçoit des copies de valeurs, sans
jamais toucher au tableau.
*Coûte* : l'appelant ne peut plus indexer, trier ni mesurer directement ; il
range et c'est tout. Contrainte réelle, mais souvent suffisante.

**Option C — ne pas exposer les lignes du tout.**

```go
func (p *Panier) Frais() float64 {
    return CalculerFrais(p.lignes)   // interne : aucune copie necessaire
}
```

*Garantit* : le mieux des trois — ce qui n'est pas exposé ne peut pas être
corrompu.
*Coûte* : le panier connaît désormais la règle de tarification. C'est un couplage,
et il n'est pas gratuit : si les frais deviennent une affaire de pays, de client
ou de promotion, `Panier` se met à dépendre de tout cela.

Le critère de choix : **la question « puis-je ne pas exposer ceci ? » se pose
avant « comment l'exposer sans risque ? »**. Ici, C si le calcul des frais reste
simple et stable, A ou B dès que la tarification devient un domaine à part
entière.

## Étape 5 — `Total` maintenu par `Ajouter`

C'est la question la plus riche de l'exercice.

### Le risque

`Total` est une donnée **dérivée** : elle ne porte aucune information nouvelle,
elle est entièrement recalculable à partir de `lignes`. La stocker crée **deux
sources de vérité pour un seul fait**, et impose un invariant —
`total == somme(lignes)` — que **chaque** chemin de code touchant `lignes` devra
désormais maintenir.

Aujourd'hui un seul chemin existe, `Ajouter`, et il le maintient correctement.
Mais le jour où arrivent `Supprimer`, `Vider`, `ModifierQuantite` ou
`AppliquerRemise`, chacune devra y penser. Celle qui oubliera ne produira ni
erreur ni exception : juste un nombre faux, quelque part, plus tard.

Et c'est **exactement ce qui vient de se produire dans cet exercice** : la
corruption est passée par un chemin qui ne traversait pas `Ajouter`. Le bug de
l'étape 2 n'est pas seulement voisin de cette question de conception — il en est
la démonstration.

> **Un état dérivé stocké est un cache. Un cache se périme.**

### L'alternative

Supprimer le champ, calculer à la demande :

```go
func (p *Panier) Total() float64 {
    total := 0.0
    for _, l := range p.lignes {
        total += l.Prix * float64(l.Quantite)
    }
    return total
}
```

Une seule source de vérité : `lignes`. L'incohérence devient **impossible par
construction**, et non plus improbable par discipline. C'est la différence entre
« nous avons corrigé le bug » et « ce bug ne peut plus exister ».

### Ce que ça coûte

Un compromis n'est honnête que si l'on nomme le prix.

**Performance.** O(n) à chaque lecture au lieu de O(1). Sur un panier de dix
lignes, c'est du bruit — quelques nanosecondes. Sur une facture de 50 000 lignes
dont le total est relu dans une boucle, cela se mesure. Le réflexe correct est
de **mesurer avant de s'inquiéter** : la version incohérente rapide est un
mauvais échange tant que la lenteur n'est pas prouvée.

**Ergonomie et API.** `Total` devient une méthode, plus un champ. Fini le
littéral `Panier{Total: …}`, et l'encodage JSON ne le voit plus automatiquement :
il faudra un DTO ou un `MarshalJSON`. Ce coût est réel et il tombe sur tous les
consommateurs du type.

**Précision.** À rebours de l'intuition, recalculer est ici **plus sûr**. Un total
accumulé en `float64` dérive à chaque opération et ne se répare jamais ; un total
recalculé repart toujours des données brutes. Au passage, `float64` pour de
l'argent est un défaut en soi : `0.1 + 0.2 != 0.3`. En paiement, on stocke des
centimes en `int64`, ou l'on utilise un type décimal dédié.

### Le troisième terme, souvent oublié

Entre « stocker » et « recalculer », il existe une voie intermédiaire : **garder
le cache, mais rendre son contournement impossible** — champs privés, toute
mutation passant par une méthode qui met le total à jour ou l'invalide.

Elle ne supprime pas le risque, elle le déplace vers la discipline : chaque
nouvelle méthode devra penser à l'invariant. C'est acceptable quand la mesure a
prouvé que le recalcul coûte trop cher. Ce n'est pas un choix par défaut, c'est
une optimisation — et comme toute optimisation, elle se justifie par un chiffre.

### La règle à emporter

Stocker une valeur dérivée est parfaitement légitime dans un cas : quand ce n'est
pas un cache, mais un **fait figé dans le temps**. Le total d'une `Commande`
validée doit être gelé au moment de l'achat — si les prix changent demain, la
facture d'hier ne doit pas bouger. Là, le stocker est la bonne décision, et
recalculer serait le bug.

> **On ne stocke pas le dérivé d'un état mutable ; on stocke le dérivé d'un fait
> immuable.**
>
> `Panier` est mutable → `Total()` se calcule.
> `Commande` est figée → `Total` se stocke.

C'est la même distinction que dans tout le chapitre : ce qui change et ce qui ne
change pas ne se traitent pas de la même façon.

## Solution de référence

```go
package panier

import "slices"

type Ligne struct {
    Prix     float64
    Quantite int
}

// Panier est une collection mutable de lignes.
//
// Invariant : il n'y en a aucun a maintenir. Le total etant calcule a la
// demande, aucun etat derive ne peut se desynchroniser.
type Panier struct {
    lignes []Ligne   // prive : le panier controle son etat
}

func (p *Panier) Ajouter(l Ligne) {
    p.lignes = append(p.lignes, l)
}

// Total renvoie la somme des lignes. Calcule a chaque appel : il ne peut
// pas etre en desaccord avec les lignes.
func (p *Panier) Total() float64 {
    total := 0.0
    for _, l := range p.lignes {
        total += l.Prix * float64(l.Quantite)
    }
    return total
}

// Lignes renvoie une copie des lignes. L'appelant peut la modifier
// librement : le panier n'en est pas affecte.
func (p *Panier) Lignes() []Ligne {
    return slices.Clone(p.lignes)
}

// CalculerFrais renvoie 2 % du montant des lignes, la quantite de chaque
// ligne etant plafonnee a 10 pour ce calcul uniquement.
//
// Les lignes ne sont pas modifiees.
func CalculerFrais(lignes []Ligne) float64 {
    total := 0.0
    for _, l := range lignes {
        q := min(l.Quantite, 10)
        total += l.Prix * float64(q)
    }
    return total * 0.02
}
```

Sortie du scénario de l'énoncé : `100`, `6000`, `12`. La quantité commandée reste
celle qu'a demandée le client, et le total lui correspond.

### La hiérarchie des garde-fous, appliquée

Le point à retenir n'est pas la liste des correctifs, c'est **à quel niveau chacun
place la garantie** :

| Correctif | Ce qui empêche la rechute | Qui la détecte |
|---|---|---|
| Copie défensive dans `CalculerFrais` | rien : le prochain oubli rejoue le bug | 🟠 une revue de code, si elle est attentive |
| `Lignes()` renvoie une copie | l'appelant n'a plus de poignée d'écriture | 🟡 un test, s'il inspecte l'état après appel |
| Champs privés | le compilateur refuse l'accès hors du package | 🔴 le compilateur, immédiatement |
| `Total()` calculé | l'état incohérent n'est pas représentable | ⚫ personne : il ne peut pas exister |

On cherche toujours à faire **descendre** la garantie dans ce tableau. Une règle
tenue par la vigilance humaine est une règle qui sera oubliée ; une règle tenue
par le type ne peut pas l'être.

## Le test qui aurait attrapé le bug

```go
func TestCalculerFraisNeModifiePasSesEntrees(t *testing.T) {
    lignes := []Ligne{{Prix: 500, Quantite: 12}}
    avant := slices.Clone(lignes)

    _ = CalculerFrais(lignes)

    if !slices.Equal(lignes, avant) {
        t.Fatalf("les lignes ont ete modifiees : %v -> %v", avant, lignes)
    }
}

func TestPanierResteCoherent(t *testing.T) {
    p := &Panier{}
    p.Ajouter(Ligne{Prix: 500, Quantite: 12})

    _ = CalculerFrais(p.Lignes())

    if got := p.Lignes()[0].Quantite; got != 12 {
        t.Fatalf("quantite commandee alteree : %d", got)
    }
    if got := p.Total(); got != 6000 {
        t.Fatalf("total = %v, attendu 6000", got)
    }
}
```

Le premier test **ne regarde pas la valeur de retour**. C'est ce qui fait sa
valeur : il teste une garantie *négative* — « cette fonction ne fait rien
d'autre ». Un test qui n'aurait vérifié que `frais == 100` serait passé au vert
sur le code bogué.

> **Un contrat qui promet de ne pas modifier ses entrées se teste en vérifiant
> les entrées après l'appel, pas la sortie.**

## À retenir

1. **Passer un slice par valeur copie sa description, pas son contenu.** Même
   chose pour les maps, les canaux, les pointeurs.
2. **Un invariant est une promesse du type.** Le bug n'est pas « une valeur a
   changé », c'est « une promesse a été rompue ».
3. **Une méthode qui renvoie une structure interne n'est pas un accesseur en
   lecture : c'est une poignée d'écriture** distribuée à tout le monde.
4. **Un champ exporté est un `Set` que l'on n'a pas écrit.** Tant qu'il est
   public, aucune garantie du type n'est exécutoire.
5. **Deux causes de natures différentes** — encapsulation côté `Panier`, contrat
   côté `CalculerFrais` — appellent deux corrections. Chacune ne protège qu'un
   côté de la frontière.
6. **Avant de protéger une mutation, vérifier qu'elle est nécessaire.** Supprimer
   une écriture vaut mieux que la rendre inoffensive.
7. **Un état dérivé stocké est un cache, et un cache se périme.** On ne stocke pas
   le dérivé d'un état mutable ; on stocke le dérivé d'un fait immuable.
8. **Un compromis s'annonce avec son prix** : O(n) par lecture, une API en
   méthode, un JSON à écrire à la main. Et l'on mesure avant d'optimiser.
9. **Faire descendre la garantie** : de la revue de code vers le test, du test
   vers le compilateur, du compilateur vers l'impossibilité de représenter
   l'état faux.
10. **Une garantie de non-modification se teste sur les entrées après l'appel**,
    jamais sur la valeur de retour.
