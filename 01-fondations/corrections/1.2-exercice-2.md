# Correction — Exercice 1.2 / 2 (code)

## Ce qui était demandé

Découper la fonction de l'exercice 1, avec quatre contraintes :

1. la règle `uid → login → email` testable sans annuaire, sans base, sans
   SMTP, sans système de fichiers ;
2. qu'il soit **impossible** que le module portant cette règle envoie un
   email — en nommant le mécanisme et son niveau ⚪ 🟡 🟠 🔴 ⚫ ;
3. qu'un échec d'envoi n'interrompe pas les 160 utilisateurs suivants ;
4. deux tests, plus une phrase de « raison de changer » par module.

La contrainte 2 est celle qui sépare une bonne réponse d'une excellente. La
contrainte 3 est un piège.

## La découpe

| Module | Raison de changer | Ce qu'il ne sait pas | Dépendances |
|---|---|---|---|
| `accounts` | la convention de login et le domaine de messagerie | tout le reste | `errors`, `strings` |
| `report` | le format attendu par le destinataire du rapport | les comptes, la base, l'annuaire | `encoding/csv`, `encoding/json`, `io` |
| `directory` | le protocole et le schéma de l'annuaire | la règle de nommage, la base | le client LDAP |
| `repo` | le schéma de la base | la règle, le texte, le format | `database/sql` |
| `notif` | le texte et le canal du message | qui doit le recevoir, et pourquoi | le client SMTP |
| `syncdir` | l'ordre des étapes et la politique d'erreur | aucune des cinq décisions ci-dessus | les cinq contrats |

Six modules pour trente-cinq lignes : ça paraît beaucoup. Compte autrement —
il y avait sept demandeurs. Six modules, c'est encore moins que le nombre de
personnes qui peuvent exiger un changement.

Et note ce que la troisième colonne te donne gratuitement : la réponse à
*« qui dois-je prévenir quand je touche ça ? »*

## Contrainte 2 — le mécanisme qui rend l'envoi impossible

C'est la question intéressante, et il y a cinq réponses possibles. Quatre sont
insuffisantes, et il faut savoir dire pourquoi.

### ⚪ Le commentaire

```go
// Do not send email from this file.
```

Zéro garantie. On le cite pour mémoire : c'est la réponse que donne un
document d'architecture.

### 🟠 La revue

L'ajout d'un `import "net/smtp"` est visible dans un diff. Un relecteur
attentif le verra.

Réel, mais humain, et asymétrique : il faut que *chaque* relecteur sache que
cette règle existe, pour *toujours*, y compris le nouveau qui arrive dans deux
ans.

### 🔴 Le compilateur — mais pas pour la raison qu'on croit

Beaucoup répondent : *« je mets la règle dans un module qui n'a pas de champ
`smtp`, donc `s.smtp.Send(...)` ne compile pas. »*

C'est vrai, et c'est utile. Mais fais attention à ce que le compilateur
garantit exactement :

> Le compilateur interdit d'**utiliser** ce qui n'est pas déclaré. Il
> n'interdit pas de le **déclarer**.

Il protège contre l'usage accidentel. Il ne protège pas contre quelqu'un qui
ajoute un champ, un paramètre ou un import.

### ⚫ L'absence de moyen

La bonne réponse est structurelle, et elle tient dans la signature :

```go
func Derive(uid string) (Account, error)
```

Pas de récepteur, donc pas de champ. Un seul paramètre, et c'est une `string`.
Aucun chemin par lequel un expéditeur pourrait arriver. La fonction ne peut
pas envoyer d'email **parce qu'elle ne détient aucun moyen d'en envoyer un**.

C'est la formulation de la leçon : *un module ne peut pas faire ce dont il ne
détient pas le moyen.* Et on l'applique ici à l'échelle la plus fine possible,
celle de la fonction.

Retiens surtout où vit la garantie :

> La garantie n'est pas dans le corps de la fonction, elle est dans sa
> **signature**. Le corps, on le relit. La signature, on la compile.

### 🟡 Le test qui maintient le ⚫ dans le temps

Il reste une faille, et il faut la nommer : rien n'empêche quelqu'un d'écrire
demain `func Derive(uid string, exp Sender)`, ou d'ajouter une variable de
paquet. Le ⚫ décrit le code **tel qu'il est**, pas le code tel qu'il sera.

Ce qui le maintient, c'est un test — et c'est un test d'un genre qu'on écrit
rarement :

```go
// Package guard holds only structure tests. They check
// no behavior: they check that some capabilities stay
// out of reach of some modules.
package guard

import (
    "os/exec"
    "strings"
    "testing"
)

// forbidden are the means to act on the world. The rules module must not
// acquire any, even transitively, even by accident.
var forbidden = []string{
    "os",
    "net",
    "net/http",
    "net/smtp",
    "database/sql",
    "log/slog",
}

// This test is the 🟡 guard that keeps the ⚫ over time.
//
// It does not say "accounts sends no email": it says "accounts has no
// means to send one". The difference is that it can be checked without reading
// the code, and that it fails on the day the import is added, not on the day of
// the incident.
func TestAccountsHasNoMeansToActOnTheWorld(t *testing.T) {
    out, err := exec.Command("go", "list", "-deps", "example/directory/accounts").Output()
    if err != nil {
        t.Fatalf("go list: %v", err)
    }

    deps := make(map[string]bool)
    for _, l := range strings.Split(string(out), "\n") {
        deps[strings.TrimSpace(l)] = true
    }

    for _, i := range forbidden {
        if deps[i] {
            t.Errorf("accounts depends on %q: it now holds a means it must not have", i)
        }
    }
}
```

Lance-le après avoir ajouté `net/smtp` dans `accounts`, et il dit ceci :

```
--- FAIL: TestAccountsHasNoMeansToActOnTheWorld (0.05s)
    imports_test.go:42: comptes depend de "os" : il detient desormais un moyen qu'il ne doit pas avoir
    imports_test.go:42: comptes depend de "net" : il detient desormais un moyen qu'il ne doit pas avoir
    imports_test.go:42: comptes depend de "net/smtp" : il detient desormais un moyen qu'il ne doit pas avoir
```

Trois lignes pour un seul import ajouté : `net/smtp` traîne `net`, qui traîne
`os`. C'est une illustration gratuite de ce qu'est une dépendance transitive —
on n'importe jamais un paquet, on importe sa fermeture.

### Le verdict, formulé honnêtement

> Le mécanisme est l'**absence de moyen** : ⚫ pour le code tel qu'il est écrit,
> 🔴 contre l'usage accidentel, et il retombe à 🟠 face à quelqu'un qui ajoute
> délibérément une dépendance — sauf si un test du graphe d'imports (🟡) le
> maintient.

Si tu as répondu ⚫ sans cette dernière phrase, tu as la bonne réponse mais
pas tout à fait le bon raisonnement. Un niveau de garde-fou n'est pas un
attribut du code : c'est une propriété du couple *(code, ce qui empêche de le
changer)*.

## Contrainte 3 — le piège

### La réponse naturelle, et ce qu'elle coûte

La réponse immédiate est de remplacer

```go
if err := s.smtp.Send(email, "Welcome", body); err != nil {
    return err
}
```

par un `continue` et une ligne de journal. La contrainte est satisfaite : les
160 suivants sont traités.

Sauf que relis la question 3 de l'exercice 1. Le compte de la 40ᵉ personne est
**déjà inséré**. À l'exécution suivante, `ON CONFLICT DO NOTHING` rend
`RowsAffected() == 0`, donc la condition d'envoi est fausse, donc l'email ne
repartira **jamais**.

Avec un `return`, l'incident est bruyant : le cron est rouge, quelqu'un
regarde.

Avec un `continue`, le cron est vert et une personne ne reçoit jamais son
message. On a transformé une panne visible en **perte silencieuse
permanente**.

> C'est la même règle que dans la correction 1.1 / 5 : entre deux bugs,
> préfère toujours celui qui fait du bruit. Un `continue` posé sur un effet
> dont l'état n'est pas durable n'est pas une correction, c'est un
> étouffement.

### La vraie réponse

L'envoi a besoin de **son propre état durable**. Pas d'une variable, pas d'un
booléen en mémoire : une colonne.

```sql
ALTER TABLE utilisateurs ADD COLUMN welcome_le TIMESTAMPTZ;
```

Et dès lors que cet état existe, l'envoi n'a plus besoin d'être dans la boucle
de synchronisation. Il devient une **seconde passe**, qui ne lit pas
l'annuaire mais l'état laissé par la première.

```go
func (s *Service) Sync(ctx context.Context) error         // reads the directory, writes the database
func (s *Service) SendWelcomes(ctx context.Context) error // reads the database, writes emails
```

Et là, regarde ce qui s'est passé pour la contrainte 3 :

> Un échec d'envoi ne peut plus interrompre la synchronisation, parce que la
> synchronisation est **déjà terminée** quand le premier email part.

La contrainte n'est plus satisfaite par une politique d'erreur. Elle est
satisfaite par la structure. C'est toujours ça qu'il faut chercher.

> La contrainte 3 n'est pas un problème de boucle. C'est un problème d'état.

Et au passage, les deux passes ont des cadences différentes et tu peux les
exploiter séparément : la synchro toutes les heures, les bienvenues toutes les
cinq minutes, ou l'inverse. Deux responsabilités, deux rythmes — ce qui est
toujours le signe qu'elles n'avaient rien à faire ensemble.

## Solution de référence

### Le module de règles — aucune dépendance, aucun moyen

```go
// Package accounts holds the naming rule of application accounts.
//
// Reason to change: the login convention and the mail domain of
// the company. Nothing else.
//
// This package imports no database, no network, no file system,
// and holds no means to send an email. It is the guarantee asked for,
// and it is structural: not a convention, an absence of means.
package accounts

import (
    "errors"
    "strings"
)

const domain = "example.cm"

// Account is the application identity derived from a directory entry.
type Account struct {
    Login string
    Email string
}

var (
    ErrEmptyUID   = errors.New("accounts: empty uid")
    ErrInvalidUID = errors.New("accounts: uid holds a forbidden character")
)

// Derive applies the rule: uid -> login -> email.
//
// Validation lives here because the rule lives here: a uid
// holding a space produces an invalid address, a uid holding a
// semicolon corrupts the CSV report. Neither the sending module nor the
// report module has a way to notice.
func Derive(uid string) (Account, error) {
    login := strings.ToLower(strings.TrimSpace(uid))
    if login == "" {
        return Account{}, ErrEmptyUID
    }
    if strings.ContainsAny(login, " \t;,@\"\r\n") {
        return Account{}, ErrInvalidUID
    }
    return Account{Login: login, Email: login + "@" + domain}, nil
}
```

### Le module de rapport

```go
// Package report writes the summary of a synchronization.
//
// Reason to change: the format the report's recipient expects. The
// request "move from CSV to JSON" is handled entirely here, by adding a
// type: no other module is opened.
package report

import (
    "encoding/csv"
    "encoding/json"
    "io"
)

// Line is the vocabulary of the report. It is deliberately poorer than
// Account: the report does not need to know everything.
type Line struct {
    Login  string `json:"login"`
    Email  string `json:"email"`
    Status string `json:"status"`
}

// ReportWriter is the contract the orchestrator consumes.
type ReportWriter interface {
    Write(lines []Line) error
}

// CSV writes to an io.Writer, not to a path: the destination is the
// caller's decision, and the test needs no file system.
type CSV struct{ W io.Writer }

func (c CSV) Write(lines []Line) error {
    w := csv.NewWriter(c.W)
    w.Comma = ';'
    if err := w.Write([]string{"login", "email", "status"}); err != nil {
        return err
    }
    for _, l := range lines {
        if err := w.Write([]string{l.Login, l.Email, l.Status}); err != nil {
            return err
        }
    }
    w.Flush()
    return w.Error()
}

// JSON is request (c) of exercise 1: one more type, zero lines
// changed elsewhere.
type JSON struct{ W io.Writer }

func (j JSON) Write(lines []Line) error {
    return json.NewEncoder(j.W).Encode(lines)
}
```

La demande (c) de l'exercice 1 — « passer du CSV au JSON » — est le type
`JSON` en bas du fichier. Trois lignes, aucun autre module ouvert.

Deux détails qui ne sont pas du détail :

- `encoding/csv` au lieu d'un `Fprintf`. L'échappement est une décision du
  format, et un `uid` contenant un point-virgule n'est pas une hypothèse
  théorique — c'est pour ça qu'il est aussi rejeté par `accounts`. Deux
  garde-fous à deux endroits, pour deux raisons différentes : l'un protège la
  validité du login, l'autre la validité du fichier.
- un `io.Writer`, pas un chemin. La destination (`/var/reports/sync.csv`, un
  bucket, un buffer de test) est la décision de l'appelant. Et c'est ce qui
  permet aux tests de ne pas toucher le disque.

### L'orchestrateur

```go
// Package syncdir orchestrates the hourly directory synchronization.
//
// Reason to change: the order of steps and the error policy: what
// stops the batch, what does not. This module calls a lot and
// decides nothing else: it knows neither the login convention, nor the schema
// database, nor the text of the emails, nor the format of the report.
package syncdir

import (
    "context"
    "errors"
    "fmt"
    "log/slog"

    "example/directory/accounts"
    "example/directory/report"
)

// Person is what this module needs from a directory entry: nothing
// more. The LDAP format, attribute names and filters stay in
// the adapter.
type Person struct{ UID string }

// The four contracts are declared here, on the consumer side.
type (
    Source interface {
        People(ctx context.Context) ([]Person, error)
    }

    Repo interface {
        // Create inserts the account if it does not exist. The boolean says whether the
        // row was created.
        Create(ctx context.Context, c accounts.Account) (created bool, err error)
        // WithoutWelcome returns the created accounts whose welcome email
        // has not left yet.
        WithoutWelcome(ctx context.Context) ([]accounts.Account, error)
        MarkWelcomed(ctx context.Context, login string) error
    }

    Notifier interface {
        Welcome(ctx context.Context, c accounts.Account) error
    }

    Counter interface{ Inc(name string) }
)

type Service struct {
    Source  Source
    Repo    Repo
    Notif   Notifier
    Report  report.ReportWriter
    Counter Counter
    Log     *slog.Logger
}

// Sync aligns the database on the directory. No email leaves from here.
//
// Error policy, explicit because it is the responsibility of this
// module: a failure on one person does not stop the batch, it is gathered and
// returned at the end. Context cancellation, however, stops everything: it is not
// an element error, it is the end of the allotted time.
func (s *Service) Sync(ctx context.Context) error {
    people, err := s.Source.People(ctx)
    if err != nil {
        return fmt.Errorf("sync: reading directory: %w", err)
    }

    lines := make([]report.Line, 0, len(people))
    var failures []error

    for _, p := range people {
        if err := ctx.Err(); err != nil {
            failures = append(failures, err)
            break
        }

        l, err := s.handle(ctx, p)
        if err != nil {
            failures = append(failures, fmt.Errorf("%s: %w", p.UID, err))
        }
        lines = append(lines, l)
    }

    // The report is written even if some people failed: a report that
    // that only comes out on total success is useless the day it breaks.
    if err := s.Report.Write(lines); err != nil {
        failures = append(failures, fmt.Errorf("sync: report: %w", err))
    }

    return errors.Join(failures...)
}

// handle always returns a line: the report must say what happened,
// not only what succeeded.
func (s *Service) handle(ctx context.Context, p Person) (report.Line, error) {
    c, err := accounts.Derive(p.UID)
    if err != nil {
        s.Counter.Inc("uid_rejected")
        return report.Line{Login: p.UID, Status: "rejected"}, err
    }

    l := report.Line{Login: c.Login, Email: c.Email}

    created, err := s.Repo.Create(ctx, c)
    if err != nil {
        l.Status = "db-failure"
        return l, err
    }

    l.Status = "existing"
    if created {
        l.Status = "created"
        s.Counter.Inc("users_created")
    }
    return l, nil
}

// SendWelcomes is the second pass. It does not read the directory: it
// reads the durable state left by the first one.
//
// This split is what meets constraint 3 without tricks: a failure
// email cannot stop a synchronization that has already finished.
func (s *Service) SendWelcomes(ctx context.Context) error {
    pending, err := s.Repo.WithoutWelcome(ctx)
    if err != nil {
        return fmt.Errorf("sync: reading pending welcomes: %w", err)
    }

    var failures []error
    for _, c := range pending {
        if err := ctx.Err(); err != nil {
            failures = append(failures, err)
            break
        }

        if err := s.Notif.Welcome(ctx, c); err != nil {
            s.Counter.Inc("welcome_failed")
            s.Log.Error("welcome", "login", c.Login, "err", err)
            failures = append(failures, fmt.Errorf("%s: %w", c.Login, err))
            continue
        }

        // If marking fails after a successful send, the email will go again on the
        // next pass. At least once, never zero: for a
        // welcome, it is the right direction for the error.
        if err := s.Repo.MarkWelcomed(ctx, c.Login); err != nil {
            failures = append(failures, fmt.Errorf("%s: marking: %w", c.Login, err))
            continue
        }
        s.Counter.Inc("welcome_sent")
    }

    return errors.Join(failures...)
}
```

Les quatre contrats sont déclarés **ici**, côté consommateur. `syncdir` dit ce
dont il a besoin ; les adaptateurs s'y conforment sans le savoir. C'est
pourquoi `Person` ne contient qu'un `UID` : c'est tout ce que
l'orchestrateur a besoin de savoir d'une entrée d'annuaire. Le format LDAP, les
noms d'attributs et les filtres restent chez l'adaptateur.

### La politique d'erreur, explicitée

Puisque c'est la responsabilité de ce module, elle doit être lisible d'un coup
d'œil :

| Panne | Effet |
|---|---|
| lecture de l'annuaire | arrête tout — sans entrées, il n'y a rien à faire |
| `uid` invalide | la personne est rejetée, rapportée, comptée ; le lot continue |
| erreur base sur une personne | rapportée en échec ; le lot continue ; l'erreur est rendue |
| échec d'envoi | n'arrête rien ; l'état durable reste « à envoyer » ; la passe suivante réessaie |
| échec de marquage après envoi réussi | l'email repartira : au moins une fois, jamais zéro |
| contexte annulé | arrête tout — ce n'est pas une erreur d'élément, c'est la fin du temps imparti |

Cette dernière ligne mérite qu'on s'y arrête. Dans la boucle :

```go
if err := ctx.Err(); err != nil {
    failures = append(failures, err)
    break
}
```

Une erreur sur une personne et une annulation de contexte sont deux choses de
nature différente. La première dit « celle-là n'a pas marché », la seconde dit
« arrête, le temps est écoulé ». Les traiter pareil, c'est soit abandonner le
lot pour un `uid` mal formé, soit s'acharner pendant dix minutes sur un
contexte mort.

## Les deux tests

### La règle, sans rien brancher

```go
package accounts

import "testing"

// This test plugs in nothing: no directory, no database, no SMTP, no disk.
// It is constraint 1 of the statement, and it can be checked by reading the
// file's imports.
func TestDerive(t *testing.T) {
    tc := []struct {
        name  string
        uid   string
        login string
        email string
        err   error
    }{
        {"nominal", "jdupont", "jdupont", "jdupont@example.cm", nil},
        {"upper case and spaces", "  JDupont ", "jdupont", "jdupont@example.cm", nil},
        {"empty", "   ", "", "", ErrEmptyUID},
        {"inner space", "j dupont", "", "", ErrInvalidUID},
        {"csv injection", "jdupont;admin", "", "", ErrInvalidUID},
        {"already an address", "jdupont@other.cm", "", "", ErrInvalidUID},
    }

    for _, c := range tc {
        t.Run(c.name, func(t *testing.T) {
            got, err := Derive(c.uid)
            if err != c.err {
                t.Fatalf("error = %v, want %v", err, c.err)
            }
            if got.Login != c.login || got.Email != c.email {
                t.Errorf("got %+v, want {%s %s}", got, c.login, c.email)
            }
        })
    }
}
```

Ce test satisfait la contrainte 1, et la preuve est **vérifiable en lisant les
imports** : `testing`, et c'est tout. Pas de `httptest`, pas de `sqlmock`, pas
de `t.TempDir()`. Quand un test de règle métier a besoin de trois faux
objets, ce n'est pas le test qui est mauvais, c'est la place de la règle.

### L'échec d'envoi qui n'interrompt rien

```go
package syncdir

import (
    "bytes"
    "context"
    "errors"
    "io"
    "log/slog"
    "strings"
    "testing"

    "example/directory/accounts"
    "example/directory/report"
)

type fakeRepo struct {
    created []accounts.Account
    pending []accounts.Account
    marked  []string
}

func (d *fakeRepo) Create(_ context.Context, c accounts.Account) (bool, error) {
    d.created = append(d.created, c)
    d.pending = append(d.pending, c)
    return true, nil
}

func (d *fakeRepo) WithoutWelcome(context.Context) ([]accounts.Account, error) {
    return d.pending, nil
}

func (d *fakeRepo) MarkWelcomed(_ context.Context, login string) error {
    d.marked = append(d.marked, login)
    return nil
}

// brokenNotif fails on one login and counts every attempt.
type brokenNotif struct {
    broken   string
    attempts []string
}

func (n *brokenNotif) Welcome(_ context.Context, c accounts.Account) error {
    n.attempts = append(n.attempts, c.Login)
    if c.Login == n.broken {
        return errors.New("smtp: connection refused")
    }
    return nil
}

type fakeCounter map[string]int

func (c fakeCounter) Inc(name string) { c[name]++ }

type fakeSource []string

func (s fakeSource) People(context.Context) ([]Person, error) {
    p := make([]Person, 0, len(s))
    for _, uid := range s {
        p = append(p, Person{UID: uid})
    }
    return p, nil
}

func service(src fakeSource, d *fakeRepo, n Notifier, rep report.ReportWriter) *Service {
    return &Service{
        Source:  src,
        Repo:    d,
        Notif:   n,
        Report:  rep,
        Counter: fakeCounter{},
        Log:     slog.New(slog.NewTextHandler(io.Discard, nil)),
    }
}

// Constraint 3: a send failure does not stop the next ones.
func TestEmailFailureDoesNotStopTheOthers(t *testing.T) {
    src := fakeSource{"a", "b", "c", "d", "e"}
    d := &fakeRepo{}
    n := &brokenNotif{broken: "b"}
    var buf bytes.Buffer
    s := service(src, d, n, report.CSV{W: &buf})

    if err := s.Sync(context.Background()); err != nil {
        t.Fatalf("synchronization: %v", err)
    }
    if len(d.created) != 5 {
        t.Fatalf("%d accounts created, want 5", len(d.created))
    }

    err := s.SendWelcomes(context.Background())
    if err == nil {
        t.Fatal("the failure must be returned, not swallowed")
    }
    if !strings.Contains(err.Error(), "b :") {
        t.Errorf("the error must name the faulty login, got %q", err)
    }

    if len(n.attempts) != 5 {
        t.Errorf("%d send attempts, want 5: the failure stopped the loop", len(n.attempts))
    }
    if len(d.marked) != 4 {
        t.Errorf("%d accounts marked, want 4", len(d.marked))
    }
    for _, login := range d.marked {
        if login == "b" {
            t.Error("a send failure must not mark the welcome as done")
        }
    }
}

// An invalid uid is rejected, reported, and does not stop the others.
func TestInvalidUIDDoesNotStopTheBatch(t *testing.T) {
    src := fakeSource{"a", "x;y", "c"}
    d := &fakeRepo{}
    var buf bytes.Buffer
    s := service(src, d, &brokenNotif{}, report.CSV{W: &buf})

    err := s.Sync(context.Background())
    if err == nil || !errors.Is(err, accounts.ErrInvalidUID) {
        t.Fatalf("error = %v, want ErrInvalidUID", err)
    }
    if len(d.created) != 2 {
        t.Errorf("%d accounts created, want 2", len(d.created))
    }
    if n := strings.Count(buf.String(), "\n"); n != 4 {
        t.Errorf("%d report lines, want 4 (header + 3)", n)
    }
    if !strings.Contains(buf.String(), "rejected") {
        t.Error("the report must record the rejection")
    }
}
```

Trois assertions à remarquer dans le premier test :

- `len(n.attempts) != 5` — c'est **la** vérification de la contrainte 3. Elle
  ne porte pas sur le résultat final mais sur le nombre de tentatives : la
  preuve que la boucle n'a pas été interrompue.
- `len(d.marked) != 4` — l'échec ne doit pas marquer la bienvenue comme
  faite. Sans cette assertion, on pourrait « satisfaire » le test précédent en
  avalant l'erreur, et on retomberait dans la perte silencieuse.
- `err == nil` → échec du test. L'erreur doit être **rendue**, nommément, avec
  le login fautif. Ne pas interrompre n'est pas la même chose que ne pas
  signaler.

## Ce que la découpe a coûté

Il faut savoir le dire, sinon on devient le genre de concepteur qui découpe
par réflexe :

- six paquets et huit fichiers au lieu d'un ;
- un type de frontière, `syncdir.Person`, qui n'existait pas et qu'il faut
  maintenir ;
- l'interface `Repo` est passée d'une opération à trois ;
- une colonne de plus en base, donc une migration ;
- le cron appelle désormais **deux** méthodes : la configuration de
  l'ordonnanceur change, et c'est un changement hors du code.

En échange : chacun des sept demandeurs a maintenant un seul endroit à ouvrir,
et la règle de nommage des comptes se teste en deux millisecondes sans rien
démarrer.

Le troisième point est le plus instructif. L'interface `Repo` a grossi parce
qu'on a rendu durable un état qui ne l'était pas. **Une frontière honnête est
souvent plus large qu'une frontière confortable** : les trois méthodes disent
la vérité sur ce que ce système fait, là où une seule la cachait.

## Ce que ça ne règle pas

- **L'accumulation d'erreurs identiques.** Si la base tombe, on accumule 200
  erreurs rigoureusement identiques et on les rend dans un seul
  `errors.Join`. C'est du bruit. Une version de production ajoute un
  disjoncteur : N échecs consécutifs de même nature → on arrête le lot et on
  le dit.
- **Le `ON CONFLICT DO NOTHING` est toujours là**, caché derrière `Create`. Un
  employé qui change de nom ne verra toujours pas son email mis à jour. La
  différence, c'est qu'aujourd'hui cette décision a un seul endroit, un nom et
  un propriétaire — donc on peut en discuter.
- **L'email part au moins une fois, pas exactement une fois.** Si le marquage
  échoue après un envoi réussi, la personne reçoit deux messages de
  bienvenue. C'est le bon sens de l'erreur pour ce cas précis, et c'est un
  choix — pas un oubli. Pour un effet monétaire, il faudrait la machinerie de
  la correction 1.1 / 5.
- **Deux instances du cron en parallèle** écrivent toujours le même fichier de
  rapport. Le `io.Writer` déplace le problème chez l'appelant au lieu de le
  résoudre ; la solution est au niveau de l'ordonnanceur, pas du code.

## La phrase par module, et le module qui n'en a pas

L'énoncé disait : *« Si tu n'arrives pas à écrire une seule phrase de raison de
changer pour un module, c'est la réponse. »*

Les six du tableau en ont une. Y compris `syncdir` — *« l'ordre des étapes et
la politique d'erreur »* — et c'est important : **orchestrer est une
responsabilité légitime.** Un module qui appelle cinq autres modules sans rien
décider d'autre que l'ordre et la gestion des pannes a une seule raison de
changer.

Le module qui échoue au test, et qu'on est très tenté de créer, est celui-ci :

```go
// package model  : Account, Line, Person, Entry...
```

Sa raison de changer ? *Toutes.* Son demandeur ? *Tout le monde.* Un paquet de
types partagés est le point où les responsabilités se refusionnent après
qu'on a pris la peine de les séparer. Même remarque pour `utils`, `common`,
`helpers`.

> Si tu ne peux pas nommer le demandeur d'un module, ce n'est pas un module.
> C'est un tiroir.

## À retenir

1. La garantie qu'un module ne peut pas faire quelque chose vit dans sa
   **signature**, pas dans son corps.
2. ⚫ = absence de moyen : pas de champ, pas de paramètre, pas d'import par
   lequel la capacité pourrait arriver.
3. Un niveau de garde-fou qualifie le couple *(code, ce qui empêche de le
   changer)*. ⚫ sans test du graphe d'imports redevient 🟠 au premier
   contributeur pressé.
4. Un test peut porter sur la **structure** et pas sur le comportement :
   `go list -deps` est un test de conception.
5. `continue` sur un effet dont l'état n'est pas durable transforme une panne
   bruyante en perte silencieuse. Ce n'est pas une correction.
6. Quand un effet doit pouvoir réessayer, il a besoin de son propre état
   durable. Et une fois cet état durable, il devient presque toujours une
   passe séparée.
7. Une erreur d'élément et une annulation de contexte sont de natures
   différentes. Les confondre coûte dans les deux sens.
8. Ne pas interrompre n'est pas ne pas signaler. Accumule, puis rends.
9. Un test de règle métier qui a besoin de faux objets dénonce la place de la
   règle, pas la qualité du test.
10. Orchestrer est une responsabilité. `package model` n'en est pas une.
