# Correction — Exercice 1.2 / 2 (code)

## Ce qui était demandé

Découper la fonction de l'exercice 1, avec quatre contraintes :

1. la règle `uid → login → email` testable sans annuaire, sans base, sans
   SMTP, sans système de fichiers ;
2. qu'il soit **impossible** que le module portant cette règle envoie un
   email — en nommant le mécanisme et son niveau ⚪ 🟡 🟠 🔴 ⚫ ;
3. qu'un échec d'envoi n'interrompe pas les 160 utilisateurs suivants ;
4. deux tests, plus une phrase de « raison de changer » par module.

La contrainte 2 est celle qui sépare une bonne réponse d'une excellente. La
contrainte 3 est un piège.

## La découpe

| Module | Raison de changer | Ce qu'il ne sait pas | Dépendances |
|---|---|---|---|
| `comptes` | la convention de login et le domaine de messagerie | tout le reste | `errors`, `strings` |
| `rapport` | le format attendu par le destinataire du rapport | les comptes, la base, l'annuaire | `encoding/csv`, `encoding/json`, `io` |
| `annuaire` | le protocole et le schéma de l'annuaire | la règle de nommage, la base | le client LDAP |
| `depot` | le schéma de la base | la règle, le texte, le format | `database/sql` |
| `notif` | le texte et le canal du message | qui doit le recevoir, et pourquoi | le client SMTP |
| `synchro` | l'ordre des étapes et la politique d'erreur | aucune des cinq décisions ci-dessus | les cinq contrats |

Six modules pour trente-cinq lignes : ça paraît beaucoup. Compte autrement —
il y avait sept demandeurs. Six modules, c'est encore moins que le nombre de
personnes qui peuvent exiger un changement.

Et note ce que la troisième colonne te donne gratuitement : la réponse à
*« qui dois-je prévenir quand je touche ça ? »*

## Contrainte 2 — le mécanisme qui rend l'envoi impossible

C'est la question intéressante, et il y a cinq réponses possibles. Quatre sont
insuffisantes, et il faut savoir dire pourquoi.

### ⚪ Le commentaire

```go
// Ne pas envoyer d'email depuis ce fichier.
```

Zéro garantie. On le cite pour mémoire : c'est la réponse que donne un
document d'architecture.

### 🟠 La revue

L'ajout d'un `import "net/smtp"` est visible dans un diff. Un relecteur
attentif le verra.

Réel, mais humain, et asymétrique : il faut que *chaque* relecteur sache que
cette règle existe, pour *toujours*, y compris le nouveau qui arrive dans deux
ans.

### 🔴 Le compilateur — mais pas pour la raison qu'on croit

Beaucoup répondent : *« je mets la règle dans un module qui n'a pas de champ
`smtp`, donc `s.smtp.Envoyer(...)` ne compile pas. »*

C'est vrai, et c'est utile. Mais fais attention à ce que le compilateur
garantit exactement :

> Le compilateur interdit d'**utiliser** ce qui n'est pas déclaré. Il
> n'interdit pas de le **déclarer**.

Il protège contre l'usage accidentel. Il ne protège pas contre quelqu'un qui
ajoute un champ, un paramètre ou un import.

### ⚫ L'absence de moyen

La bonne réponse est structurelle, et elle tient dans la signature :

```go
func Deriver(uid string) (Compte, error)
```

Pas de récepteur, donc pas de champ. Un seul paramètre, et c'est une `string`.
Aucun chemin par lequel un expéditeur pourrait arriver. La fonction ne peut
pas envoyer d'email **parce qu'elle ne détient aucun moyen d'en envoyer un**.

C'est la formulation de la leçon : *un module ne peut pas faire ce dont il ne
détient pas le moyen.* Et on l'applique ici à l'échelle la plus fine possible,
celle de la fonction.

Retiens surtout où vit la garantie :

> La garantie n'est pas dans le corps de la fonction, elle est dans sa
> **signature**. Le corps, on le relit. La signature, on la compile.

### 🟡 Le test qui maintient le ⚫ dans le temps

Il reste une faille, et il faut la nommer : rien n'empêche quelqu'un d'écrire
demain `func Deriver(uid string, exp Expediteur)`, ou d'ajouter une variable de
paquet. Le ⚫ décrit le code **tel qu'il est**, pas le code tel qu'il sera.

Ce qui le maintient, c'est un test — et c'est un test d'un genre qu'on écrit
rarement :

```go
// Package garde ne contient que des tests de structure. Ils ne verifient
// aucun comportement : ils verifient que certaines capacites restent
// inaccessibles a certains modules.
package garde

import (
    "os/exec"
    "strings"
    "testing"
)

// interdits sont les moyens d'agir sur le monde. Le module de regles ne doit
// en acquerir aucun, meme transitivement, meme par inadvertance.
var interdits = []string{
    "os",
    "net",
    "net/http",
    "net/smtp",
    "database/sql",
    "log/slog",
}

// Ce test est le garde-fou 🟡 qui maintient le ⚫ dans le temps.
//
// Il ne dit pas « comptes n'envoie pas d'email » : il dit « comptes n'a aucun
// moyen d'en envoyer un ». La difference est qu'on peut le verifier sans lire
// le code, et qu'il echoue le jour de l'ajout de l'import, pas le jour de
// l'incident.
func TestComptesNaAucunMoyenDAgirSurLeMonde(t *testing.T) {
    out, err := exec.Command("go", "list", "-deps", "exemple/annuaire/comptes").Output()
    if err != nil {
        t.Fatalf("go list : %v", err)
    }

    deps := make(map[string]bool)
    for _, l := range strings.Split(string(out), "\n") {
        deps[strings.TrimSpace(l)] = true
    }

    for _, i := range interdits {
        if deps[i] {
            t.Errorf("comptes depend de %q : il detient desormais un moyen qu'il ne doit pas avoir", i)
        }
    }
}
```

Lance-le après avoir ajouté `net/smtp` dans `comptes`, et il dit ceci :

```
--- FAIL: TestComptesNaAucunMoyenDAgirSurLeMonde (0.05s)
    imports_test.go:42: comptes depend de "os" : il detient desormais un moyen qu'il ne doit pas avoir
    imports_test.go:42: comptes depend de "net" : il detient desormais un moyen qu'il ne doit pas avoir
    imports_test.go:42: comptes depend de "net/smtp" : il detient desormais un moyen qu'il ne doit pas avoir
```

Trois lignes pour un seul import ajouté : `net/smtp` traîne `net`, qui traîne
`os`. C'est une illustration gratuite de ce qu'est une dépendance transitive —
on n'importe jamais un paquet, on importe sa fermeture.

### Le verdict, formulé honnêtement

> Le mécanisme est l'**absence de moyen** : ⚫ pour le code tel qu'il est écrit,
> 🔴 contre l'usage accidentel, et il retombe à 🟠 face à quelqu'un qui ajoute
> délibérément une dépendance — sauf si un test du graphe d'imports (🟡) le
> maintient.

Si tu as répondu ⚫ sans cette dernière phrase, tu as la bonne réponse mais
pas tout à fait le bon raisonnement. Un niveau de garde-fou n'est pas un
attribut du code : c'est une propriété du couple *(code, ce qui empêche de le
changer)*.

## Contrainte 3 — le piège

### La réponse naturelle, et ce qu'elle coûte

La réponse immédiate est de remplacer

```go
if err := s.smtp.Envoyer(email, "Bienvenue", corps); err != nil {
    return err
}
```

par un `continue` et une ligne de journal. La contrainte est satisfaite : les
160 suivants sont traités.

Sauf que relis la question 3 de l'exercice 1. Le compte de la 40ᵉ personne est
**déjà inséré**. À l'exécution suivante, `ON CONFLICT DO NOTHING` rend
`RowsAffected() == 0`, donc la condition d'envoi est fausse, donc l'email ne
repartira **jamais**.

Avec un `return`, l'incident est bruyant : le cron est rouge, quelqu'un
regarde.

Avec un `continue`, le cron est vert et une personne ne reçoit jamais son
message. On a transformé une panne visible en **perte silencieuse
permanente**.

> C'est la même règle que dans la correction 1.1 / 5 : entre deux bugs,
> préfère toujours celui qui fait du bruit. Un `continue` posé sur un effet
> dont l'état n'est pas durable n'est pas une correction, c'est un
> étouffement.

### La vraie réponse

L'envoi a besoin de **son propre état durable**. Pas d'une variable, pas d'un
booléen en mémoire : une colonne.

```sql
ALTER TABLE utilisateurs ADD COLUMN bienvenue_le TIMESTAMPTZ;
```

Et dès lors que cet état existe, l'envoi n'a plus besoin d'être dans la boucle
de synchronisation. Il devient une **seconde passe**, qui ne lit pas
l'annuaire mais l'état laissé par la première.

```go
func (s *Service) Synchroniser(ctx context.Context) error     // lit l'annuaire, écrit la base
func (s *Service) EnvoyerBienvenues(ctx context.Context) error // lit la base, écrit des emails
```

Et là, regarde ce qui s'est passé pour la contrainte 3 :

> Un échec d'envoi ne peut plus interrompre la synchronisation, parce que la
> synchronisation est **déjà terminée** quand le premier email part.

La contrainte n'est plus satisfaite par une politique d'erreur. Elle est
satisfaite par la structure. C'est toujours ça qu'il faut chercher.

> La contrainte 3 n'est pas un problème de boucle. C'est un problème d'état.

Et au passage, les deux passes ont des cadences différentes et tu peux les
exploiter séparément : la synchro toutes les heures, les bienvenues toutes les
cinq minutes, ou l'inverse. Deux responsabilités, deux rythmes — ce qui est
toujours le signe qu'elles n'avaient rien à faire ensemble.

## Solution de référence

### Le module de règles — aucune dépendance, aucun moyen

```go
// Package comptes porte la regle de nommage des comptes applicatifs.
//
// Raison de changer : la convention de login et le domaine de messagerie de
// l'entreprise. Rien d'autre.
//
// Ce package n'importe ni base de donnees, ni reseau, ni systeme de fichiers,
// et ne detient aucun moyen d'envoyer un email. C'est la garantie demandee,
// et elle est structurelle : pas une convention, une absence de moyen.
package comptes

import (
    "errors"
    "strings"
)

const domaine = "exemple.cm"

// Compte est l'identite applicative derivee d'une entree d'annuaire.
type Compte struct {
    Login string
    Email string
}

var (
    ErrUIDVide     = errors.New("comptes : uid vide")
    ErrUIDInvalide = errors.New("comptes : uid contenant un caractere interdit")
)

// Deriver applique la regle : uid -> login -> email.
//
// La validation vit ici parce que c'est ici que la regle vit : un uid
// contenant un espace produit une adresse invalide, un uid contenant un
// point-virgule corrompt le rapport CSV. Ni le module d'envoi ni le module de
// rapport n'ont de quoi s'en apercevoir.
func Deriver(uid string) (Compte, error) {
    login := strings.ToLower(strings.TrimSpace(uid))
    if login == "" {
        return Compte{}, ErrUIDVide
    }
    if strings.ContainsAny(login, " \t;,@\"\r\n") {
        return Compte{}, ErrUIDInvalide
    }
    return Compte{Login: login, Email: login + "@" + domaine}, nil
}
```

### Le module de rapport

```go
// Package rapport ecrit le compte rendu d'une synchronisation.
//
// Raison de changer : le format attendu par le destinataire du rapport. La
// demande « passer du CSV au JSON » se traite entierement ici, en ajoutant un
// type : aucun autre module n'est ouvert.
package rapport

import (
    "encoding/csv"
    "encoding/json"
    "io"
)

// Ligne est le vocabulaire du rapport. Il est volontairement plus pauvre que
// Compte : le rapport n'a pas besoin de tout savoir.
type Ligne struct {
    Login  string `json:"login"`
    Email  string `json:"email"`
    Statut string `json:"statut"`
}

// Ecrivain est le contrat consomme par l'orchestrateur.
type Ecrivain interface {
    Ecrire(lignes []Ligne) error
}

// CSV ecrit vers un io.Writer, pas vers un chemin : la destination est la
// decision de l'appelant, et le test n'a pas besoin de systeme de fichiers.
type CSV struct{ W io.Writer }

func (c CSV) Ecrire(lignes []Ligne) error {
    w := csv.NewWriter(c.W)
    w.Comma = ';'
    if err := w.Write([]string{"login", "email", "statut"}); err != nil {
        return err
    }
    for _, l := range lignes {
        if err := w.Write([]string{l.Login, l.Email, l.Statut}); err != nil {
            return err
        }
    }
    w.Flush()
    return w.Error()
}

// JSON est la demande (c) de l'exercice 1 : un type de plus, zero ligne
// modifiee ailleurs.
type JSON struct{ W io.Writer }

func (j JSON) Ecrire(lignes []Ligne) error {
    return json.NewEncoder(j.W).Encode(lignes)
}
```

La demande (c) de l'exercice 1 — « passer du CSV au JSON » — est le type
`JSON` en bas du fichier. Trois lignes, aucun autre module ouvert.

Deux détails qui ne sont pas du détail :

- `encoding/csv` au lieu d'un `Fprintf`. L'échappement est une décision du
  format, et un `uid` contenant un point-virgule n'est pas une hypothèse
  théorique — c'est pour ça qu'il est aussi rejeté par `comptes`. Deux
  garde-fous à deux endroits, pour deux raisons différentes : l'un protège la
  validité du login, l'autre la validité du fichier.
- un `io.Writer`, pas un chemin. La destination (`/var/rapports/sync.csv`, un
  bucket, un buffer de test) est la décision de l'appelant. Et c'est ce qui
  permet aux tests de ne pas toucher le disque.

### L'orchestrateur

```go
// Package synchro orchestre la synchronisation horaire de l'annuaire.
//
// Raison de changer : l'ordre des etapes et la politique d'erreur — ce qui
// arrete le lot, ce qui ne l'arrete pas. Ce module appelle beaucoup et ne
// decide rien d'autre : il ne connait ni la convention de login, ni le schema
// de la base, ni le texte des emails, ni le format du rapport.
package synchro

import (
    "context"
    "errors"
    "fmt"
    "log/slog"

    "exemple/annuaire/comptes"
    "exemple/annuaire/rapport"
)

// Personne est ce dont ce module a besoin d'une entree d'annuaire : rien de
// plus. Le format LDAP, les noms d'attributs et les filtres restent chez
// l'adaptateur.
type Personne struct{ UID string }

// Les quatre contrats sont declares ici, cote consommateur.
type (
    Source interface {
        Personnes(ctx context.Context) ([]Personne, error)
    }

    Depot interface {
        // Creer insere le compte s'il n'existe pas. Le booleen dit si la
        // ligne a ete creee.
        Creer(ctx context.Context, c comptes.Compte) (cree bool, err error)
        // SansBienvenue rend les comptes crees dont l'email de bienvenue
        // n'est pas encore parti.
        SansBienvenue(ctx context.Context) ([]comptes.Compte, error)
        MarquerBienvenue(ctx context.Context, login string) error
    }

    Notificateur interface {
        Bienvenue(ctx context.Context, c comptes.Compte) error
    }

    Compteur interface{ Inc(nom string) }
)

type Service struct {
    Source   Source
    Depot    Depot
    Notif    Notificateur
    Rapport  rapport.Ecrivain
    Compteur Compteur
    Log      *slog.Logger
}

// Synchroniser aligne la base sur l'annuaire. Aucun email ne part d'ici.
//
// Politique d'erreur, explicite parce que c'est la responsabilite de ce
// module : l'echec sur une personne n'arrete pas le lot, il est accumule et
// rendu a la fin. L'annulation du contexte, elle, arrete tout : ce n'est pas
// une erreur d'element, c'est la fin du temps imparti.
func (s *Service) Synchroniser(ctx context.Context) error {
    personnes, err := s.Source.Personnes(ctx)
    if err != nil {
        return fmt.Errorf("synchro : lecture annuaire : %w", err)
    }

    lignes := make([]rapport.Ligne, 0, len(personnes))
    var echecs []error

    for _, p := range personnes {
        if err := ctx.Err(); err != nil {
            echecs = append(echecs, err)
            break
        }

        l, err := s.traiter(ctx, p)
        if err != nil {
            echecs = append(echecs, fmt.Errorf("%s : %w", p.UID, err))
        }
        lignes = append(lignes, l)
    }

    // Le rapport est ecrit meme si des personnes ont echoue : un rapport qui
    // ne sort qu'en cas de succes total ne sert a rien le jour ou ca casse.
    if err := s.Rapport.Ecrire(lignes); err != nil {
        echecs = append(echecs, fmt.Errorf("synchro : rapport : %w", err))
    }

    return errors.Join(echecs...)
}

// traiter rend toujours une ligne : le rapport doit dire ce qui s'est passe,
// pas seulement ce qui a reussi.
func (s *Service) traiter(ctx context.Context, p Personne) (rapport.Ligne, error) {
    c, err := comptes.Deriver(p.UID)
    if err != nil {
        s.Compteur.Inc("uid_rejete")
        return rapport.Ligne{Login: p.UID, Statut: "rejete"}, err
    }

    l := rapport.Ligne{Login: c.Login, Email: c.Email}

    cree, err := s.Depot.Creer(ctx, c)
    if err != nil {
        l.Statut = "echec-base"
        return l, err
    }

    l.Statut = "existant"
    if cree {
        l.Statut = "cree"
        s.Compteur.Inc("utilisateurs_crees")
    }
    return l, nil
}

// EnvoyerBienvenues est la seconde passe. Elle ne lit pas l'annuaire : elle
// lit l'etat durable laisse par la premiere.
//
// C'est ce decoupage qui satisfait la contrainte 3 sans artifice : un echec
// d'email ne peut pas interrompre une synchronisation qui est deja terminee.
func (s *Service) EnvoyerBienvenues(ctx context.Context) error {
    attente, err := s.Depot.SansBienvenue(ctx)
    if err != nil {
        return fmt.Errorf("synchro : lecture des bienvenues en attente : %w", err)
    }

    var echecs []error
    for _, c := range attente {
        if err := ctx.Err(); err != nil {
            echecs = append(echecs, err)
            break
        }

        if err := s.Notif.Bienvenue(ctx, c); err != nil {
            s.Compteur.Inc("bienvenue_echouee")
            s.Log.Error("bienvenue", "login", c.Login, "err", err)
            echecs = append(echecs, fmt.Errorf("%s : %w", c.Login, err))
            continue
        }

        // Si le marquage echoue apres un envoi reussi, l'email repartira a la
        // prochaine passe. Au moins une fois, jamais zero : pour un message de
        // bienvenue, c'est le bon sens de l'erreur.
        if err := s.Depot.MarquerBienvenue(ctx, c.Login); err != nil {
            echecs = append(echecs, fmt.Errorf("%s : marquage : %w", c.Login, err))
            continue
        }
        s.Compteur.Inc("bienvenue_envoyee")
    }

    return errors.Join(echecs...)
}
```

Les quatre contrats sont déclarés **ici**, côté consommateur. `synchro` dit ce
dont il a besoin ; les adaptateurs s'y conforment sans le savoir. C'est
pourquoi `Personne` ne contient qu'un `UID` : c'est tout ce que
l'orchestrateur a besoin de savoir d'une entrée d'annuaire. Le format LDAP, les
noms d'attributs et les filtres restent chez l'adaptateur.

### La politique d'erreur, explicitée

Puisque c'est la responsabilité de ce module, elle doit être lisible d'un coup
d'œil :

| Panne | Effet |
|---|---|
| lecture de l'annuaire | arrête tout — sans entrées, il n'y a rien à faire |
| `uid` invalide | la personne est rejetée, rapportée, comptée ; le lot continue |
| erreur base sur une personne | rapportée en échec ; le lot continue ; l'erreur est rendue |
| échec d'envoi | n'arrête rien ; l'état durable reste « à envoyer » ; la passe suivante réessaie |
| échec de marquage après envoi réussi | l'email repartira : au moins une fois, jamais zéro |
| contexte annulé | arrête tout — ce n'est pas une erreur d'élément, c'est la fin du temps imparti |

Cette dernière ligne mérite qu'on s'y arrête. Dans la boucle :

```go
if err := ctx.Err(); err != nil {
    echecs = append(echecs, err)
    break
}
```

Une erreur sur une personne et une annulation de contexte sont deux choses de
nature différente. La première dit « celle-là n'a pas marché », la seconde dit
« arrête, le temps est écoulé ». Les traiter pareil, c'est soit abandonner le
lot pour un `uid` mal formé, soit s'acharner pendant dix minutes sur un
contexte mort.

## Les deux tests

### La règle, sans rien brancher

```go
package comptes

import "testing"

// Ce test ne branche rien : ni annuaire, ni base, ni SMTP, ni disque.
// C'est la contrainte 1 de l'enonce, et c'est verifiable en lisant les
// imports du fichier.
func TestDeriver(t *testing.T) {
    cas := []struct {
        nom   string
        uid   string
        login string
        email string
        err   error
    }{
        {"nominal", "jdupont", "jdupont", "jdupont@exemple.cm", nil},
        {"majuscules et espaces", "  JDupont ", "jdupont", "jdupont@exemple.cm", nil},
        {"vide", "   ", "", "", ErrUIDVide},
        {"espace interne", "j dupont", "", "", ErrUIDInvalide},
        {"injection csv", "jdupont;admin", "", "", ErrUIDInvalide},
        {"deja une adresse", "jdupont@autre.cm", "", "", ErrUIDInvalide},
    }

    for _, c := range cas {
        t.Run(c.nom, func(t *testing.T) {
            got, err := Deriver(c.uid)
            if err != c.err {
                t.Fatalf("erreur = %v, attendu %v", err, c.err)
            }
            if got.Login != c.login || got.Email != c.email {
                t.Errorf("got %+v, attendu {%s %s}", got, c.login, c.email)
            }
        })
    }
}
```

Ce test satisfait la contrainte 1, et la preuve est **vérifiable en lisant les
imports** : `testing`, et c'est tout. Pas de `httptest`, pas de `sqlmock`, pas
de `t.TempDir()`. Quand un test de règle métier a besoin de trois faux
objets, ce n'est pas le test qui est mauvais, c'est la place de la règle.

### L'échec d'envoi qui n'interrompt rien

```go
package synchro

import (
    "bytes"
    "context"
    "errors"
    "io"
    "log/slog"
    "strings"
    "testing"

    "exemple/annuaire/comptes"
    "exemple/annuaire/rapport"
)

type depotFaux struct {
    crees   []comptes.Compte
    attente []comptes.Compte
    marques []string
}

func (d *depotFaux) Creer(_ context.Context, c comptes.Compte) (bool, error) {
    d.crees = append(d.crees, c)
    d.attente = append(d.attente, c)
    return true, nil
}

func (d *depotFaux) SansBienvenue(context.Context) ([]comptes.Compte, error) {
    return d.attente, nil
}

func (d *depotFaux) MarquerBienvenue(_ context.Context, login string) error {
    d.marques = append(d.marques, login)
    return nil
}

// notifCassee echoue sur un login precis et compte toutes les tentatives.
type notifCassee struct {
    casse      string
    tentatives []string
}

func (n *notifCassee) Bienvenue(_ context.Context, c comptes.Compte) error {
    n.tentatives = append(n.tentatives, c.Login)
    if c.Login == n.casse {
        return errors.New("smtp : connexion refusee")
    }
    return nil
}

type compteurFaux map[string]int

func (c compteurFaux) Inc(nom string) { c[nom]++ }

type sourceFausse []string

func (s sourceFausse) Personnes(context.Context) ([]Personne, error) {
    p := make([]Personne, 0, len(s))
    for _, uid := range s {
        p = append(p, Personne{UID: uid})
    }
    return p, nil
}

func service(src sourceFausse, d *depotFaux, n Notificateur, rap rapport.Ecrivain) *Service {
    return &Service{
        Source:   src,
        Depot:    d,
        Notif:    n,
        Rapport:  rap,
        Compteur: compteurFaux{},
        Log:      slog.New(slog.NewTextHandler(io.Discard, nil)),
    }
}

// Contrainte 3 : un echec d'envoi n'interrompt pas les suivants.
func TestEchecEmailNInterromptPasLesSuivants(t *testing.T) {
    src := sourceFausse{"a", "b", "c", "d", "e"}
    d := &depotFaux{}
    n := &notifCassee{casse: "b"}
    var buf bytes.Buffer
    s := service(src, d, n, rapport.CSV{W: &buf})

    if err := s.Synchroniser(context.Background()); err != nil {
        t.Fatalf("synchronisation : %v", err)
    }
    if len(d.crees) != 5 {
        t.Fatalf("%d comptes crees, attendu 5", len(d.crees))
    }

    err := s.EnvoyerBienvenues(context.Background())
    if err == nil {
        t.Fatal("l'echec doit etre rendu, pas avale")
    }
    if !strings.Contains(err.Error(), "b :") {
        t.Errorf("l'erreur doit nommer le login fautif, got %q", err)
    }

    if len(n.tentatives) != 5 {
        t.Errorf("%d tentatives d'envoi, attendu 5 : l'echec a interrompu la boucle", len(n.tentatives))
    }
    if len(d.marques) != 4 {
        t.Errorf("%d comptes marques, attendu 4", len(d.marques))
    }
    for _, login := range d.marques {
        if login == "b" {
            t.Error("un echec d'envoi ne doit pas marquer la bienvenue comme faite")
        }
    }
}

// Un uid invalide est rejete, rapporte, et n'empeche pas les autres.
func TestUIDInvalideNArretePasLeLot(t *testing.T) {
    src := sourceFausse{"a", "x;y", "c"}
    d := &depotFaux{}
    var buf bytes.Buffer
    s := service(src, d, &notifCassee{}, rapport.CSV{W: &buf})

    err := s.Synchroniser(context.Background())
    if err == nil || !errors.Is(err, comptes.ErrUIDInvalide) {
        t.Fatalf("erreur = %v, attendu ErrUIDInvalide", err)
    }
    if len(d.crees) != 2 {
        t.Errorf("%d comptes crees, attendu 2", len(d.crees))
    }
    if n := strings.Count(buf.String(), "\n"); n != 4 {
        t.Errorf("%d lignes de rapport, attendu 4 (entete + 3)", n)
    }
    if !strings.Contains(buf.String(), "rejete") {
        t.Error("le rapport doit porter la trace du rejet")
    }
}
```

Trois assertions à remarquer dans le premier test :

- `len(n.tentatives) != 5` — c'est **la** vérification de la contrainte 3. Elle
  ne porte pas sur le résultat final mais sur le nombre de tentatives : la
  preuve que la boucle n'a pas été interrompue.
- `len(d.marques) != 4` — l'échec ne doit pas marquer la bienvenue comme
  faite. Sans cette assertion, on pourrait « satisfaire » le test précédent en
  avalant l'erreur, et on retomberait dans la perte silencieuse.
- `err == nil` → échec du test. L'erreur doit être **rendue**, nommément, avec
  le login fautif. Ne pas interrompre n'est pas la même chose que ne pas
  signaler.

## Ce que la découpe a coûté

Il faut savoir le dire, sinon on devient le genre de concepteur qui découpe
par réflexe :

- six paquets et huit fichiers au lieu d'un ;
- un type de frontière, `synchro.Personne`, qui n'existait pas et qu'il faut
  maintenir ;
- l'interface `Depot` est passée d'une opération à trois ;
- une colonne de plus en base, donc une migration ;
- le cron appelle désormais **deux** méthodes : la configuration de
  l'ordonnanceur change, et c'est un changement hors du code.

En échange : chacun des sept demandeurs a maintenant un seul endroit à ouvrir,
et la règle de nommage des comptes se teste en deux millisecondes sans rien
démarrer.

Le troisième point est le plus instructif. L'interface `Depot` a grossi parce
qu'on a rendu durable un état qui ne l'était pas. **Une frontière honnête est
souvent plus large qu'une frontière confortable** : les trois méthodes disent
la vérité sur ce que ce système fait, là où une seule la cachait.

## Ce que ça ne règle pas

- **L'accumulation d'erreurs identiques.** Si la base tombe, on accumule 200
  erreurs rigoureusement identiques et on les rend dans un seul
  `errors.Join`. C'est du bruit. Une version de production ajoute un
  disjoncteur : N échecs consécutifs de même nature → on arrête le lot et on
  le dit.
- **Le `ON CONFLICT DO NOTHING` est toujours là**, caché derrière `Creer`. Un
  employé qui change de nom ne verra toujours pas son email mis à jour. La
  différence, c'est qu'aujourd'hui cette décision a un seul endroit, un nom et
  un propriétaire — donc on peut en discuter.
- **L'email part au moins une fois, pas exactement une fois.** Si le marquage
  échoue après un envoi réussi, la personne reçoit deux messages de
  bienvenue. C'est le bon sens de l'erreur pour ce cas précis, et c'est un
  choix — pas un oubli. Pour un effet monétaire, il faudrait la machinerie de
  la correction 1.1 / 5.
- **Deux instances du cron en parallèle** écrivent toujours le même fichier de
  rapport. Le `io.Writer` déplace le problème chez l'appelant au lieu de le
  résoudre ; la solution est au niveau de l'ordonnanceur, pas du code.

## La phrase par module, et le module qui n'en a pas

L'énoncé disait : *« Si tu n'arrives pas à écrire une seule phrase de raison de
changer pour un module, c'est la réponse. »*

Les six du tableau en ont une. Y compris `synchro` — *« l'ordre des étapes et
la politique d'erreur »* — et c'est important : **orchestrer est une
responsabilité légitime.** Un module qui appelle cinq autres modules sans rien
décider d'autre que l'ordre et la gestion des pannes a une seule raison de
changer.

Le module qui échoue au test, et qu'on est très tenté de créer, est celui-ci :

```go
// package modele  — Compte, Ligne, Personne, Entree...
```

Sa raison de changer ? *Toutes.* Son demandeur ? *Tout le monde.* Un paquet de
types partagés est le point où les responsabilités se refusionnent après
qu'on a pris la peine de les séparer. Même remarque pour `utils`, `common`,
`helpers`.

> Si tu ne peux pas nommer le demandeur d'un module, ce n'est pas un module.
> C'est un tiroir.

## À retenir

1. La garantie qu'un module ne peut pas faire quelque chose vit dans sa
   **signature**, pas dans son corps.
2. ⚫ = absence de moyen : pas de champ, pas de paramètre, pas d'import par
   lequel la capacité pourrait arriver.
3. Un niveau de garde-fou qualifie le couple *(code, ce qui empêche de le
   changer)*. ⚫ sans test du graphe d'imports redevient 🟠 au premier
   contributeur pressé.
4. Un test peut porter sur la **structure** et pas sur le comportement :
   `go list -deps` est un test de conception.
5. `continue` sur un effet dont l'état n'est pas durable transforme une panne
   bruyante en perte silencieuse. Ce n'est pas une correction.
6. Quand un effet doit pouvoir réessayer, il a besoin de son propre état
   durable. Et une fois cet état durable, il devient presque toujours une
   passe séparée.
7. Une erreur d'élément et une annulation de contexte sont de natures
   différentes. Les confondre coûte dans les deux sens.
8. Ne pas interrompre n'est pas ne pas signaler. Accumule, puis rends.
9. Un test de règle métier qui a besoin de faux objets dénonce la place de la
   règle, pas la qualité du test.
10. Orchestrer est une responsabilité. `package modele` n'en est pas une.
