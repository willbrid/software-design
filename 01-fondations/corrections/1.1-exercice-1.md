# Correction — Exercice 1.1 / 1 (compréhension)

## Le code

```go
type Config struct {
    Name    string
    Tags    []string
    Limits map[string]int
}

func Normalize(c Config) Config {
    c.Name = strings.ToLower(c.Name)
    c.Tags = append(c.Tags, "normalized")
    c.Limits["max"] = 100
    return c
}

original := Config{
    Name:     "PAYMENT",
    Tags:    []string{"prod"},          // len 1, cap 1
    Limits: map[string]int{"max": 10},
}
cp := Normalize(original)
```

## 1. Les quatre sorties

| Expression | Valeur | Piège |
|---|---|---|
| `original.Name` | `PAYMENT` | — |
| `original.Tags` | `[prod]` | ⚠️ le seul champ piégé |
| `original.Limits["max"]` | `100` | ⚠️ modifié malgré le passage par valeur |
| `cp.Tags` | `[prod normalized]` | — |

## 2. Pourquoi les trois champs se comportent différemment

### `Name` — intact

Un `string` est en mémoire un `{ptr, len}`, donc il contient bien un pointeur.
Deux raisons indépendantes le rendent inoffensif :

1. les chaînes sont **immuables** en Go : rien ne peut écrire à travers ce
   pointeur ;
2. `c.Name = strings.ToLower(...)` **assigne le champ** de la copie — le champ de
   `original` garde son ancienne valeur.

### `Limits` — modifié ⚠️

Une map n'est pas un descripteur : c'est **un simple pointeur** vers une table de
hachage allouée sur le tas. Copier le struct copie ce pointeur, donc `original`
et `c` désignent **la même table**.

Et surtout, la ligne :

```go
c.Limits["max"] = 100
```

**n'assigne pas le champ `c.Limits`**. Elle passe *à travers* lui pour écrire
dans la table partagée. `original` voit donc `100`.

### `Tags` — intact, pour **deux raisons indépendantes**

C'est le cœur de l'exercice. Deux mécanismes distincts protègent `original`, et
il faut les tenir séparés.

**Raison A — l'assignation du champ.**

```go
c.Tags = append(c.Tags, "normalized")
```

Le résultat de `append` est assigné au champ **de la copie**. Le champ
`original.Tags` conserve son descripteur d'origine `{ptr, len:1, cap:1}`, quoi
qu'il arrive. Cette raison est vraie **indépendamment de la capacité**.

**Raison B — la réallocation.**

`[]string{"prod"}` a `len == cap == 1`. Il n'y a pas de case libre. `append` ne
peut pas écrire après la fin du tableau (cette mémoire appartient peut-être à
quelqu'un d'autre) : il **alloue un nouveau tableau**, y recopie l'existant, puis
ajoute l'élément. Les deux slices sont dès lors totalement déconnectés.

> Ne retenir que la raison B est dangereux : c'est un modèle mental qui prédit
> faux dès que la capacité change. La raison A, elle, ne dépend de rien.

## La règle générale

> **Assigner un champ ne touche que la copie.
> Écrire *à travers* un champ atteint ce qui est partagé.**

```go
c.Name = "..."                 // assigns the field  → copy only
c.Tags = append(c.Tags, "...") // assigns the field  → copy only
c.Limits["max"] = 100          // writes THROUGH   → shared ⚠️
```

Test au coup d'œil, à gauche du `=` :

- `c.Champ = ...` → remplacement d'un champ de la copie. Inoffensif.
- `c.Champ[...] = ...`, `*c.Champ = ...`, `c.Champ.Sous = ...` → traversée. On
  écrit ailleurs, et cet « ailleurs » n'appartient pas à la copie.

Cette règle prédit correctement les trois champs et ne parle jamais de capacité.

## 3. Le rôle de la capacité — et la mutation invisible

Avec `make([]string, 1, 2)` au lieu de `[]string{"prod"}` :

```
original.Tags   : [prod]            len 1  cap 2
cp.Tags      : [prod normalized]  len 2  cap 2
même tableau ?  : true
original.Tags[:2] : [prod normalized]   ← la donnée est bien là
```

`append` a trouvé une case libre et y a écrit `"normalized"` — **dans le tableau
que `original` possède**. Mais `original.Tags` a une longueur de 1 : `Println`
s'arrête à la première case. La mutation a eu lieu, elle est simplement hors de
vue.

### Le bug complet

```go
original.Tags = append(original.Tags, "audit")
```

`original.Tags` vaut `{len 1, cap 2}` : il **reste une case libre de son point de
vue**. Pas de réallocation — `append` écrit `"audit"` en case 1, **par-dessus**
`"normalized"`.

```
--- before ---
original : [prod]              len 1  cap 2
cp       : [prod normalized]
--- après ---
original : [prod audit]
cp       : [prod audit]        ← personne n'a touché à cp
```

Une variable a changé de valeur sans que personne ne l'écrive.

## Pourquoi ce bug est un cauchemar en production

- Aucun `panic`, aucune erreur retournée, aucun HTTP 500.
- Aucune ligne de log ne le signale.
- Le code de `cp` est irréprochable — rien n'y écrit.
- **Il ne se reproduit pas en local.**

Ce dernier point vient de l'invariant à retenir :

> **La capacité ne fait pas partie des données.**

```go
a := []string{"prod"} // len 1, cap 1  → no bug
b := make([]string, 1, 2)
b[0] = "prod" // len 1, cap 2  → bug
```

Les deux affichent `[prod]`, sérialisent en `["prod"]`, se dumpent en `prod`.
**Indiscernables dans toute donnée observable.** En production, la capacité d'un
slice est un accident de son histoire (décodage JSON, driver SQL, croissance par
`append`). En local, on écrit un littéral, `cap == len`, et le bug ne sort jamais.

## Conclusion : détecter vs prévenir

Cette classe de bug **ne se détecte pas** — ni par les logs, ni par les métriques,
ni par la reproduction. Elle se **prévient par la conception** :

```go
// 1. Copy: share nothing any more
c.Tags = append(slices.Clone(c.Tags), "normalized")

// 2. Cap the capacity: full slice expression, cap = len
tags := original.Tags[:len(original.Tags):len(original.Tags)]
```

Le second force `cap == len`, donc le prochain `append` **est obligé** de
réallouer : une règle d'équipe devient une garantie mécanique (cf. §8 du cours,
hiérarchie des garde-fous).

> Un SRE demande : « comment le verrai-je ? »
> Un architecte demande : « comment le rendre impossible ? »
