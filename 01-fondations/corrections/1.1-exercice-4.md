# Correction — Exercice 1.1 / 4 (design)

## L'énoncé

```go
package tarif

func Calculer(commande *Commande) (float64, error)
```

Ce package doit lire la commande pour calculer un prix. Il ne doit jamais la
modifier. Il est destiné à être **réutilisé par d'autres équipes**.

---

## Le cadre change tout

Les exercices 1 à 3 portaient sur du code que tu écris et que tu relis. Celui-ci
porte sur du code que **d'autres appelleront sans lire ton implémentation**.

C'est un basculement de nature. Tant qu'un contrat vit à l'intérieur d'un
package, une convention d'équipe suffit à le tenir. Dès qu'il traverse une
frontière de package, il ne reste au lecteur que trois sources d'information :

1. la **signature** — il la voit ;
2. la **documentation** — il la lit peut-être ;
3. l'**implémentation** — il ne la lira pas.

Toute garantie qui ne vit qu'en (2) ou en (3) n'existe pas pour lui. C'est la
grille de lecture de tout cet exercice.

---

## Question 1 — Pourquoi `*Commande` est un mauvais choix

### Distinguer un mécanisme d'une raison

Première chose à séparer, parce qu'on la confond presque toujours :

> « La fonction reçoit un pointeur, donc toute écriture affecte l'appelant. »

C'est **exact**, mais ce n'est pas un argument de conception : c'est la
définition d'un pointeur. Un pointeur qui laisse écrire n'est un défaut que si
l'écriture n'est pas voulue. Le mécanisme est le même dans les deux cas ; ce qui
change, c'est l'intention.

Une *raison* explique pourquoi ce mécanisme est inadapté **ici**. Il y en a
quatre, de quatre natures différentes.

### Raison 1 — La signature contredit le contrat (nature : contractuelle)

Le commentaire dit « ne modifie jamais la commande ». Le type dit « je peux
modifier la commande ».

> **Quand la signature et la documentation se contredisent, c'est la signature
> qui gagne.**

Le commentaire est un souhait, le type est une règle. Le lecteur pressé, le
compilateur et l'outillage suivent tous le type. Un `*T` en paramètre annonce
par convention Go : *« je vais écrire dedans, ou j'ai une raison de ne pas
copier. »* Annoncer l'un pour faire l'autre, c'est mentir dans le seul document
que tout le monde lit.

C'est la reprise directe de l'exercice 3 : un contrat que seule la documentation
exprime est un contrat non exprimé.

### Raison 2 — L'aliasing temporel (nature : dynamique)

Même si `Calculer` ne modifie **rien**, le pointeur crée une fenêtre pendant
laquelle la valeur peut changer sous ses pieds. Deux scénarios distincts, qui
n'ont pas le même correctif :

| Scénario | Ce qui se passe | Correctif |
|---|---|---|
| **Mutation concurrente** | une autre goroutine écrit dans `commande` pendant que `Calculer` la lit | copie à l'entrée, ou synchronisation |
| **Rétention** | `tarif` conserve le pointeur (cache, champ de struct, closure, goroutine) et le relit plus tard, après que l'appelant l'a modifié | copie à l'entrée — la synchronisation n'y suffit pas |

Le second est le plus vicieux, parce qu'il casse **même en programme
séquentiel**. Un cache mémoire indexé sur `*Commande`, et le bug de l'exercice 3
revient avec un décalage temporel en prime : le résultat est faux *plus tard*,
loin du site d'appel, dans une trace où `Calculer` n'apparaît même plus.

Retiens la formulation générale :

> **Un pointeur ne partage pas une valeur, il partage une fenêtre ouverte sur
> cette valeur — et cette fenêtre reste ouverte aussi longtemps que quelqu'un
> garde le pointeur.**

### Raison 3 — Le pointeur admet un état invalide (nature : ensemble des valeurs)

```go
tarif.Calculer(nil)   // compile parfaitement
```

Le type `*Commande` a une valeur de plus que le type `Commande` : `nil`. Cette
valeur supplémentaire n'a aucun sens métier — une demande de tarif sans commande
n'existe pas — mais elle est représentable, donc tu es obligé de la traiter :

```go
func Calculer(commande *Commande) (float64, error) {
    if commande == nil {
        return 0, errors.New("commande nil")   // un chemin d'erreur inventé
    }
    ...
}
```

Tu viens d'ajouter un chemin d'erreur que personne ne testera, pour un cas qui
n'aurait pas dû exister. Dans la hiérarchie de l'exercice 3, tu es descendu d'un
cran dans le mauvais sens : d'« état non représentable » vers « erreur à
l'exécution ».

> **Chaque valeur qu'un type admet et que le métier refuse devient une branche
> de code à écrire, à tester et à maintenir.**

### Raison 4 — Le couplage (nature : architecturale)

`*Commande` oblige le package `tarif` à connaître le type `Commande` **en
entier** : tous ses champs, y compris ceux qui n'ont rien à voir avec le prix,
y compris ceux qui n'existent pas encore.

Conséquences concrètes :

- `tarif` importe le package métier de l'appelant — l'inversion de dépendance
  est à l'envers : le composant générique dépend du composant spécifique ;
- une autre équipe, dont le type s'appelle `Order` ou `Facture`, **ne peut pas
  utiliser le package**, alors que c'était l'objectif affiché ;
- tout changement de `Commande` est un changement potentiel pour `tarif`, même
  sur des champs qu'il n'a jamais lus.

Un package « réutilisable par d'autres équipes » qui exige le type métier
complet de l'appelant n'est pas réutilisable : il est **accouplé**.

### Quand `*Commande` serait le bon choix

Par honnêteté intellectuelle — la règle n'est pas « jamais de pointeur » :

- `Commande` contient un `sync.Mutex` ou tout type non copiable : `go vet`
  (`copylocks`) refusera la copie, à raison ;
- `Commande` pèse plusieurs kilo-octets et `Calculer` est dans une boucle
  chaude — **après mesure**, jamais avant ;
- les méthodes de `Commande` ont des récepteurs pointeurs, donc un `Commande`
  passé par valeur ne permettrait pas de les appeler ;
- la fonction *doit* muter, et le nom le dit (`Appliquer`, `Enregistrer`).

> **Le pointeur doit être justifié par une raison. Ici, aucune ne s'applique.**

## Question 2 — L'espace des options

La question ne demandait pas la meilleure réponse, elle demandait de **lister**
puis d'évaluer. Un architecte ne se juge pas à l'option qu'il retient, mais à
celles qu'il sait écarter et pourquoi.

| Option | Ce qu'elle garantit *vraiment* | Ce qu'elle coûte | Niveau |
|---|---|---|---|
| A — commentaire `// ne modifie pas` | rien | rien | 🟠 revue de code |
| B — test de non-mutation | pas de **régression** : le bug est détecté, pas empêché | maintenance ; ne couvre que les champs auxquels on a pensé | 🟡 test |
| C — passage par valeur | les champs **scalaires** sont isolés ; `nil` disparaît | copie de la struct ; garantie **superficielle** | 🟡 partiel |
| D — copie défensive profonde | isolation réelle, champs mutables compris | allocation par appel ; **chaque nouveau champ mutable doit être ajouté à la copie** | 🟡 fragile |
| E — interface en lecture seule | `tarif` ne peut appeler que les méthodes exposées | indirection ; contournable ; transporte souvent un pointeur | 🟠 dissuasion |
| F — champs non exportés dans `Commande` | le compilateur refuse l'accès hors du package | il faut posséder le type ; `encoding/json` exige des champs exportés | 🔴 compilateur |
| G — type d'entrée dédié, possédé par `tarif` | `tarif` ne voit jamais `Commande` : il ne peut pas modifier ce qu'il ne tient pas | l'appelant doit traduire | ⚫ non représentable |

Quatre de ces lignes méritent d'être développées, parce que ce sont celles où
l'intuition se trompe.

### Option C — le passage par valeur ne garantit qu'une couche

```go
func Calculer(c Commande) (float64, error)
```

`nil` disparaît, la signature ne ment plus, `Commande` est copiée. Mais
`Commande.Lignes` est un slice : la copie duplique le descripteur, pas le
tableau sous-jacent.

```go
func Calculer(c Commande) (float64, error) {
    c.Lignes[0].Quantite = 10   // modifie la commande de l'appelant
    ...
}
```

C'est **exactement l'exercice 1**, et le bug de l'exercice 3 à l'identique. La
valeur protège la coquille, pas le contenu.

> **Le passage par valeur est une garantie de profondeur 1.** Elle est totale si
> le type ne contient que des scalaires et des `string` ; elle est nulle sur
> tout ce que le type atteint par indirection.

### Option D — une garantie qui exige de la vigilance n'est pas une garantie

```go
func Calculer(commande Commande) (float64, error) {
    c := commande
    c.Lignes = slices.Clone(c.Lignes)
    c.Remises = maps.Clone(c.Remises)
    ...
}
```

Cela fonctionne — **le jour où c'est écrit**. Le jour où quelqu'un ajoute un
champ `Metadonnees map[string]string` à `Commande` sans toucher à cette
fonction, la protection se dégrade en silence : pas d'erreur de compilation, pas
de test rouge, pas de revue alertée. La garantie devient fausse sans que rien ne
le signale.

> **Une garantie qui se dégrade silencieusement est pire qu'une absence de
> garantie : elle est crue.**

C'est le même raisonnement que pour `Panier.Total` à l'exercice 3. Un correctif
qui doit être **ré-appliqué** à chaque évolution du type est un correctif
temporaire.

### Option E — une interface dissuade, elle n'interdit pas

```go
// Definie par le consommateur, comme le veut l'idiome Go.
package tarif

type CommandeLisible interface {
    Lignes() iter.Seq[Ligne]
    Client() ClientID
}
```

Ce qu'elle apporte réellement : le découplage (n'importe quel type satisfaisant
l'interface convient — `Order`, `Facture`), et une testabilité excellente (un
faux s'écrit en dix lignes).

Ce qu'elle **ne** garantit **pas**, et il faut le savoir :

1. **Les méthodes exposées peuvent elles-mêmes muter.** `Lignes()` peut très
   bien incrémenter un compteur interne. L'interface contraint la *surface*, pas
   le *comportement*.
2. **L'assertion de type reste ouverte.** Si `tarif` importe malgré tout le type
   concret, `c.(*Commande)` redonne tous les droits.
3. **Une interface satisfaite par un pointeur transporte un pointeur.** Si les
   méthodes de `Commande` ont des récepteurs pointeurs, seul `*Commande`
   satisfait l'interface : tu as caché le pointeur, tu ne l'as pas supprimé, et
   les raisons 2 et 3 de la question 1 s'appliquent toujours.

L'interface est un excellent outil de **découplage**. C'est un outil médiocre
d'**immuabilité**. Ne lui demande pas ce qu'elle ne sait pas faire.

### Option G — le type d'entrée dédié

```go
package tarif

// Demande contient tout ce dont le calcul a besoin, et rien d'autre.
type Demande struct {
    Lignes []Ligne
    Client ClientID
    Pays   string
}

func Calculer(d Demande) (Centimes, error)
```

C'est la seule option du tableau qui atteint le niveau ⚫ : `tarif` ne peut pas
modifier une `Commande` **parce qu'il n'en tient jamais**. On ne protège pas la
mutation, on supprime l'objet à protéger. C'est le même geste qu'à l'exercice 3,
où l'on a préféré supprimer l'écriture plutôt que la rendre inoffensive.

Elle résout les quatre raisons d'un coup : la signature ne ment plus, il n'y a
plus de `nil`, il n'y a plus de fenêtre ouverte sur la commande de l'appelant,
et le couplage a disparu.

#### Pourquoi une struct, et non des paramètres positionnels

```go
func Calculer(lignes []Ligne, client ClientID, pays string) (Centimes, error)
```

Fonctionnellement équivalent, mais :

| | Paramètres positionnels | Struct `Demande` |
|---|---|---|
| Ajouter un critère de prix | **casse tous les appelants** | additif : ils continuent de compiler |
| Lisibilité au site d'appel | `Calculer(l, c, "CM")` | champs nommés |
| Deux `string` consécutifs | inversion silencieuse possible | impossible |

Pour un package destiné à d'autres équipes, l'évolutivité additive est le seul
critère qui compte à long terme. Une signature publique est une promesse qu'on
ne peut plus reprendre.

### Le piège qui reste, et que presque personne ne voit

> **Réduire la surface ne supprime pas l'aliasing, elle le réduit.**

`Demande.Lignes` est toujours un slice qui partage son tableau avec l'appelant.
Si `Calculer` écrit dans `d.Lignes[i]`, tu as reproduit l'exercice 3 — sur une
surface plus petite, ce qui rend le bug plus rare et donc plus difficile à
trouver.

Trois façons de fermer ce dernier trou, par force croissante :

```go
// 1. tarif copie a l'entree. Cout : une allocation par appel.
//    Obligatoire si tarif conserve quoi que ce soit apres le retour.
d.Lignes = slices.Clone(d.Lignes)

// 2. lecture seule par construction, zero allocation.
//    Cout : une iter.Seq nil panique au range, il faut la garder.
Lignes iter.Seq[Ligne]

// 3. rien, plus un test de non-mutation. Niveau 🟡.
Lignes []Ligne
```

Pour un package public dont le calcul est un simple parcours, **2**. Dès que
`tarif` mémorise quelque chose, **1**. **3** seulement en interne, entre gens
qui relisent le même code.

### Le coût de la traduction est exactement ce qu'on achète

L'objection habituelle contre l'option G est le *mapping* que l'appelant doit
écrire :

```go
func (c *Commande) DemandeTarif() tarif.Demande {
    lignes := make([]tarif.Ligne, 0, len(c.lignes))
    for _, l := range c.lignes {
        lignes = append(lignes, tarif.Ligne{
            PrixUnitaire: tarif.Centimes(l.PrixUnitaire),
            Quantite:     l.Quantite,
        })
    }
    return tarif.Demande{
        Lignes: lignes,
        Client: tarif.ClientID(c.client),
        Pays:   c.pays,
    }
}
```

C'est du code à écrire, c'est vrai. Mais regarde ce qu'il fait : il construit un
`make` neuf. **La traduction est la copie.** Le coût qu'on reproche à cette
option est précisément ce qui achète l'isolation — il n'est pas ajouté à la
protection, il *est* la protection. Et il est écrit une fois, au seul endroit
qui connaît les deux types, au lieu d'être re-vérifié à chaque évolution comme
dans l'option D.

## Question 3 — L'absence de `const` en Go est-elle un manque ?

C'est la question la plus intéressante des cinq, et celle qu'on pose en
entretien d'architecte. Voici comment on l'instruit — à charge, à décharge,
puis on tranche.

### À charge : oui, c'est un manque

- **Le contrat « je ne modifie pas mon entrée » est le plus fréquent de toute
  API.** Go n'a aucun moyen de l'exprimer dans le système de types. Il est donc
  exprimé en commentaire, c'est-à-dire pas exprimé.
- **En C++, `const` compose à travers le graphe d'appels.** Une valeur `const`
  ne peut être passée qu'à des fonctions qui acceptent `const`. La garantie se
  propage seule, en profondeur. En Go, chaque fonction re-décide seule et
  re-copie seule : l'option D doit être répétée à chaque frontière.
- **Rust démontre que c'est faisable sans surcoût.** `&T` contre `&mut T` est
  vérifié à la compilation, sans GC, sans coût à l'exécution — et Rust va plus
  loin que C++ : il garantit aussi l'**exclusivité** de `&mut`, donc l'absence
  d'alias. Le bug de l'exercice 3 est *inexprimable* en Rust sûr.
- **Sans ce mécanisme, toute API Go doit choisir entre copier (coût) et faire
  confiance (risque).** C'est un impôt permanent, payé sur chaque frontière de
  package.

### À décharge : non, ce n'en est pas un

- **`const` n'est pas transitif — c'est l'objection décisive.** En C++, `const`
  s'arrête à la première indirection *stockée dans l'objet* : dans une méthode
  `const`, un membre `T* p` devient `T* const p`, pas `const T* p`. Tu peux
  donc écrire `p->x = 1` dans une méthode marquée `const`. `const` protège la
  boîte, pas ce qu'il y a au bout des fils qui en sortent — **exactement la même
  limite que le passage par valeur de Go**, avec en plus la prétention du
  contraire. Une fausse garantie est plus dangereuse qu'une absence de garantie,
  parce qu'un relecteur cesse de vérifier.
- **`const_cast` existe.** Le langage fournit lui-même la porte de sortie.
- **La « const correctness » est un coût de maintenance célèbre.** Ajouter un
  `const` en un point déclenche une cascade dans toute la base ; l'oublier
  condamne des branches entières de l'API. Il faudrait en outre décider comment
  `const` interagit avec les interfaces, les méthodes, les génériques et les
  closures. L'équipe Go a rejeté à plusieurs reprises les propositions de types
  en lecture seule, essentiellement sur ce coût de complexité.
- **Go possède déjà deux mécanismes d'immuabilité, placés ailleurs** : le
  passage par valeur, et les **champs non exportés**. Le second est décisif :
  Go a choisi de mettre le contrôle à la frontière du **package**, pas à la
  frontière de l'**appel de fonction** — parce que c'est au niveau du package
  que se situe réellement la frontière de confiance entre équipes.
- **Là où l'immuabilité comptait le plus, Go l'a mise dans le type, pas dans un
  modificateur** : `string` est immuable, point. Et le mot-clé `const` existe
  bel et bien en Go — il désigne des constantes de compilation de types de base.
  Le langage a délibérément refusé de l'étendre aux paramètres et aux types
  composites.

### Le verdict

C'est un manque **réel mais mineur, et surtout mal formulé.**

Ce qui manque à Go, ce n'est pas `const`. C'est la capacité d'exprimer deux
choses différentes :

1. « **je** ne modifierai pas cette valeur » → c'est tout ce que `const` sait
   dire ;
2. « **personne d'autre** ne la modifiera pendant que je m'en sers » → c'est ce
   dont on a réellement besoin (raison 2 de la question 1).

`const` ne répond qu'à la première. Et répondre à la première en laissant croire
qu'on a répondu à la seconde, c'est le mécanisme même par lequel on écrit un bug
d'exercice 3 en toute confiance.

La réponse de Go à la seconde question est plus rustre : **ne partage pas —
copie, ou encapsule.** Moins élégante que celle de Rust, mais non contournable,
et transitive dès qu'on l'applique à la frontière du package.

D'où la phrase à emporter :

> **En Go, l'immuabilité est une propriété des *types*, pas des *paramètres*.**

Un type immuable se conçoit une fois, et la garantie est acquise à tous les
sites d'appel, gratuitement. Un `const` sur un paramètre s'obtient un appel à la
fois, et se paie sur toutes les signatures.

### Ce que Go te donne concrètement à la place

Par force décroissante :

| Moyen | Force |
|---|---|
| Un type ne contenant que des scalaires et des `string`, passé par valeur | 🔴 le compilateur, en profondeur totale |
| Des champs non exportés + des accesseurs qui copient | 🔴 le compilateur, à la frontière du package |
| Un type d'entrée dédié que l'appelé ne partage avec personne | ⚫ il n'y a rien à protéger |
| Une interface aux seules méthodes de lecture | 🟠 dissuasion |
| Un commentaire | rien |

## Solution de référence

```go
// Package tarif calcule le prix d'une demande.
//
// Le package ne connait pas le type Commande de l'appelant : il definit
// lui-meme la forme de ce dont il a besoin. Il ne peut donc pas modifier une
// commande, faute d'en tenir une.
package tarif

import "errors"

// Centimes est un montant exprime dans la plus petite unite monetaire.
// Un prix ne se represente pas en float64 : 0.1 + 0.2 != 0.3.
type Centimes int64

type ClientID string

type Ligne struct {
    PrixUnitaire Centimes
    Quantite     int
}

// Demande contient tout ce dont le calcul a besoin, et rien d'autre.
//
// Contrat : Calculer ne modifie aucune valeur atteignable depuis une Demande,
// et n'en conserve aucune reference apres son retour.
type Demande struct {
    Lignes []Ligne
    Client ClientID
    Pays   string
}

var (
    ErrPaysInconnu = errors.New("tarif : pays inconnu")
    ErrQuantite    = errors.New("tarif : quantite negative")
)

var tauxTVA = map[string]Centimes{"CM": 1925, "FR": 2000}

func Calculer(d Demande) (Centimes, error) {
    taux, ok := tauxTVA[d.Pays]
    if !ok {
        return 0, ErrPaysInconnu
    }

    var ht Centimes
    for _, l := range d.Lignes {
        if l.Quantite < 0 {
            return 0, ErrQuantite
        }
        ht += l.PrixUnitaire * Centimes(l.Quantite)
    }

    return ht + ht*taux/10000, nil
}
```

Ce qu'il faut remarquer, dans l'ordre :

1. **Aucun pointeur.** Pas de `nil` à traiter, pas de fenêtre ouverte, pas de
   mensonge de signature.
2. **Aucun import du package métier.** `tarif` est réutilisable par une équipe
   dont le type s'appelle `Order`.
3. **`Centimes`, pas `float64`.** Un package de tarification est précisément
   l'endroit où l'on ne commet pas cette faute. On y consacrera une leçon.
4. **La boucle ne fait que lire.** Aucun `d.Lignes[i] = ...`, donc pas besoin de
   `slices.Clone` : la copie ne devient nécessaire que si l'on mémorise. Et
   c'est le test ci-dessous qui verrouille cette propriété.
5. **Les erreurs sont des valeurs déclarées**, comparables par `errors.Is` chez
   l'appelant, et non des `errors.New` anonymes construits sur place.

### Variante avec itérateur

Si l'on veut supprimer l'aliasing résiduel sur `Lignes` sans payer de copie :

```go
type Demande struct {
    Lignes iter.Seq[Ligne]
    Client ClientID
    Pays   string
}

func Calculer(d Demande) (Centimes, error) {
    // ...
    if d.Lignes != nil {          // une iter.Seq nil panique au range
        for l := range d.Lignes {
            ht += l.PrixUnitaire * Centimes(l.Quantite)
        }
    }
    // ...
}
```

Honnêteté sur le compromis : l'itérateur ferme le trou d'aliasing mais
**réintroduit un cas `nil`** — celui qu'on avait justement chassé en question 1.
Un slice `nil` se parcourt en zéro tour ; une `iter.Seq` `nil` panique. On
échange une garantie contre une autre, et il faut le savoir avant de choisir.

## Le test qui verrouille le contrat

```go
func TestCalculerNeModifiePasSaDemande(t *testing.T) {
    lignes := []tarif.Ligne{
        {PrixUnitaire: 50_000, Quantite: 12},
        {PrixUnitaire: 1_500, Quantite: 3},
    }
    avant := slices.Clone(lignes)

    if _, err := tarif.Calculer(tarif.Demande{Lignes: lignes, Pays: "CM"}); err != nil {
        t.Fatal(err)
    }

    if !slices.Equal(lignes, avant) {
        t.Fatalf("les lignes ont ete modifiees : %v -> %v", avant, lignes)
    }
}
```

Comme à l'exercice 3, ce test **ne regarde pas la valeur de retour**. Il teste
une garantie négative — « cette fonction ne fait rien d'autre » — en inspectant
les entrées après l'appel.

Et il te dit quelque chose de plus, propre à cet exercice : c'est un test que
tu peux écrire **parce que la signature prend une `Demande` que tu construis
toi-même**. Avec `Calculer(commande *Commande)`, ce test aurait exigé de
construire une `Commande` complète, avec tous ses champs obligatoires, ses
invariants et ses dépendances. La testabilité n'est pas une qualité qu'on ajoute
à une API : c'est une conséquence de sa surface.

## À retenir

1. **Un mécanisme n'est pas une raison.** « C'est un pointeur, donc ça modifie »
   décrit le langage. La raison explique pourquoi c'est inadapté *ici*.
2. **Quand la signature et la documentation se contredisent, la signature
   gagne.** Elle est le seul document que tous les appelants lisent.
3. **Un pointeur ne partage pas une valeur : il ouvre une fenêtre**, et cette
   fenêtre reste ouverte tant que quelqu'un garde le pointeur — d'où la mutation
   concurrente *et* la rétention.
4. **Chaque valeur qu'un type admet et que le métier refuse devient une branche
   de code** à écrire, tester et maintenir. `*T` en ajoute une : `nil`.
5. **Un package générique qui exige le type métier de l'appelant n'est pas
   réutilisable, il est accouplé.**
6. **Le passage par valeur est une garantie de profondeur 1.** Totale sur les
   scalaires, nulle sur tout ce que le type atteint par indirection.
7. **Une garantie qui exige de la vigilance à chaque évolution n'est pas une
   garantie** — elle est seulement crue.
8. **Une interface découple ; elle n'immobilise pas.** Elle contraint la
   surface, pas le comportement, et satisfaite par un pointeur elle transporte
   un pointeur.
9. **Réduire la surface réduit l'aliasing, elle ne le supprime pas.** Le slice
   dans le type d'entrée reste partagé.
10. **Le coût du mapping est ce qu'on achète, pas ce qu'on paie en plus** : la
    traduction *est* la copie.
11. **En Go, l'immuabilité est une propriété des types, pas des paramètres.**
    Un type immuable se conçoit une fois ; un `const` se paie à chaque
    signature.
12. **`const` répond à « je ne modifierai pas », jamais à « personne d'autre ne
    modifiera ».** C'est la seconde question qui produit les incidents.
