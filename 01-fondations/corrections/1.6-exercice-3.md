## Question 1 — classement des cinq tests

| # | Test | Ce qui le ferait échouer | Genre |
|---|---|---|---|
| 1 | `TestValiderRetourneNil` | une panique, une faute de frappe | **vide** |
| 2 | `TestValiderReserveChaqueLigneUneFois` | une boucle déplacée, un regroupement des appels, une réservation par lot | **miroir** |
| 3 | `TestValiderUneCommandeVide` | une erreur rendue sur un panier vide | **test du double** |
| 4 | `TestLaRemiseEstAppliquee…` | l'arithmétique de Go | **tautologique** |
| 5 | `TestValiderGereLesErreurs` | une panique dans une branche d'erreur | **vide**, avec une assertion |

Les deux du même genre, demandés par l'énoncé, sont **1 et 5** : les deux sont
vides. Le n° 5 a l'air mieux parce qu'il contient un `errors.Is` — mais sur ses
quatre scénarios, trois se contentent de `_ = …Valider(…)`. Il exerce les
branches, il ne vérifie rien. Il a été écrit pour la couverture, et il remplit
parfaitement sa mission : c'est lui qui fait passer le paquet de 90 % à 100 %.

### Le n° 2 en détail, parce que c'est le plus coûteux

```
if st.reserves != 2 {
    t.Fatalf("reserves = %d, attendu 2", st.reserves)
}
```

Il affirme que `Reserver` est appelée **deux fois** — une par ligne. C'est la
forme de l'implémentation, pas une attente de l'appelant. Et la correction que
nous allons faire — réserver le panier **en une seule opération** — le fait
échouer, alors qu'elle **améliore** le comportement sur trois points.

> Un test qui casse quand on corrige un bug garde la mauvaise chose.

### Le n° 3, le genre qu'on nomme rarement

```
d := &depotFaux{commande: commandeDe()}      // le double rend un panier vide
...
if len(d.ecrites[0].Lignes) != 0 { … }       // on vérifie qu'il est vide
```

Le test fournit un panier vide au double, puis vérifie que la commande écrite
est vide. Le code testé n'a rien à voir avec ce résultat : **il a transporté la
valeur du double jusqu'à l'assertion.** C'est un test du double, pas du code.

Le signe qui le dénonce : si tu remplaces `Valider` par une fonction qui fait
`c, _ := depot.Lire(…); depot.Ecrire(c)`, le test passe toujours.

## Question 2 — pourquoi le n° 4 ne vérifie rien

```
var ht int64
for _, l := range lignes {
    ht += int64(l.Quantite) * l.PrixHT
}
attendu := ht - ht*100/1000
```

La valeur attendue est **recalculée dans le test avec la même formule que le
code**. Donc :

- change le taux dans le code → le test échoue, mais parce que `100` est écrit
  en dur dans le test, pas parce qu'il a détecté quoi que ce soit ;
- change la **formule** — l'arrondi, l'ordre des opérations, le seuil — et le
  test reste vert, parce que la formule du test est restée la même.

Vérifions. Le code original applique la remise au-delà de 10 articles. Le test
utilise 12 articles. Que se passe-t-il avec 10 ? **Le test ne le dit pas**, et
c'est exactement là qu'est le bug de la question 3.

### La seule façon correcte d'écrire l'assertion d'un calcul

Une **constante écrite à la main**, obtenue ailleurs — une calculatrice, un
tableur, le comptable :

```
{nom: "onze articles : remise", montant: 12000, articles: 11,
 taux: 100, attendu: 10800, pourquoi: "10 % de 12 000"},
```

`10800`. Pas `ht - ht*taux/1000`. Si écrire la constante demande un effort,
c'est le signe que l'assertion a de la valeur.

Et la variante déguisée, à reconnaître partout :

```
attendu := service.Calculer(entree)
if resultat != attendu { … }
```

## Question 3 — les quatre défauts que la suite ne voit pas

### Défaut 1 — `Ecrire` échoue : le stock fuit

Le code réserve, puis écrit. Si l'écriture échoue, la réservation est faite et
la commande n'est pas validée. Le client réessaie — ou le client **clique deux
fois**, ce qui est le cas le plus fréquent — et `Reserver` est appelée une
seconde fois. Sur cinq tentatives, dix unités réservées pour une commande de
deux.

| | |
|---|---|
| **Scénario client** | « Erreur, veuillez réessayer. » Il réessaie quatre fois. L'article passe en rupture de stock alors qu'il reste quarante pièces en entrepôt. |
| **Étape de la grille empêchée** | **observer** — `Reserver` du double ne décrémente rien, donc la fuite n'a aucune trace observable |

### Défaut 2 — la deuxième ligne manque de stock : réservation partielle

La boucle réserve ligne par ligne. Si la ligne 3 manque de stock, les lignes 1
et 2 sont déjà réservées, et la fonction rend une erreur sans rien défaire.

| | |
|---|---|
| **Scénario client** | la commande est refusée, et deux articles sur trois sont bloqués pour un panier qui n'existe pas. Ils se libéreront à l'expiration — s'il y a une expiration. |
| **Étape empêchée** | **observer**, pour la même raison |

### Défaut 3 — valider deux fois réserve deux fois

Rien ne regarde `c.Valide`. Une commande déjà validée est revalidée, et tout le
panier est réservé une deuxième fois.

| | |
|---|---|
| **Scénario client** | un rafraîchissement de page, un double clic, un réessai de passerelle de paiement. Même conséquence, en pire : la commande est valide, donc personne ne s'en aperçoit. |
| **Étape empêchée** | **amener dans l'état** — le double ne garde pas la commande écrite, donc on ne peut pas construire l'état « déjà validée » |

### Défaut 4 — dix articles exactement

`if articles > 10` : à dix articles, pas de remise. Est-ce voulu ? La règle dit
*« plus de dix articles »*, donc oui — mais **rien ne le dit dans le code et
rien ne le vérifie**. Le jour où quelqu'un lit « à partir de dix », il change
`>` en `>=` et personne ne le remarque.

| | |
|---|---|
| **Scénario client** | un client avec exactement dix articles réclame sa remise. Le support ne sait pas qui a raison. |
| **Étape empêchée** | aucune — celui-là est un simple trou dans le tableau de cas. Tous les défauts ne sont pas des défauts de conception. |

### Et le cinquième, qui n'était pas dans les indices

`Disponible` puis `Reserver` sont **deux appels**. Entre les deux, un autre
processus passe. C'est un `check-then-act`, le défaut de la leçon 1.3, et aucun
test séquentiel ne peut le voir.

> Quatre des cinq défauts sont invisibles **pour la même raison** : les doubles
> n'ont pas de mémoire. Ce n'est pas cinq oublis, c'est un seul, répété cinq
> fois.

## Question 4 — la suite réécrite

### D'abord, le code

La correction est dans **une signature**, et il faut la lire avant les tests :

```go
// Stock reserve le panier EN UNE SEULE OPERATION.
//
// C'est la correction la plus importante de ce fichier, et elle est dans la
// signature. La version d'origine avait deux methodes, Disponible puis
// Reserver, appelees ligne par ligne. Elle avait donc trois defauts d'un coup :
//
//   - un check-then-act entre les deux appels (lecon 1.3) ;
//   - une reservation partielle si la troisieme ligne manque de stock ;
//   - aucune idempotence, donc une double reservation au moindre reessai.
//
// Les trois disparaissent avec une operation unique, atomique et clee par la
// commande.
type Stock interface {
    // Reserver reserve toutes les lignes, ou aucune.
    //
    // GARANTI : l'operation est idempotente sur l'identifiant de commande. Un
    // second appel avec le meme id ne reserve rien de plus et rend nil.
    //
    // CE QUI RESTE VRAI EN CAS D'ECHEC : rien n'est reserve. Il n'existe pas
    // d'etat « la moitie du panier est reservee ».
    Reserver(ctx context.Context, idCommande string, lignes []Ligne) error
}
```

Trois défauts disparaissent avec une seule opération atomique, idempotente et
clée par la commande. Et la conséquence qu'il faut voir :

```go
// Valider reserve le stock et enregistre la commande validee.
//
// GARANTI
//
//    Une commande deja validee rend ErrDejaValidee et ne reserve rien.
//    Le total est calcule apres remise, par le module remise.
//
// CE QUI RESTE VRAI EN CAS D'ECHEC
//
//    Si la reservation echoue, rien n'est reserve et la commande n'est pas
//    validee.
//    Si l'ECRITURE echoue apres une reservation reussie, le stock est reserve
//    et la commande n'est pas validee. Ce n'est pas une fuite : la reservation
//    est idempotente sur l'id, donc le reessai de l'appelant reprend exactement
//    ou il s'etait arrete.
//
// C'est cette derniere clause qui rend l'ordre des deux ecritures indifferent.
// Sans l'idempotence de Reserver, il n'existe aucun ordre correct — seulement
// le choix entre une fuite de stock et une double reservation.
func (s Service) Valider(ctx context.Context, id string) (Commande, error) {
    c, err := s.depot.Lire(ctx, id)
    if err != nil {
        return Commande{}, fmt.Errorf("commande : lecture : %w", err)
    }
    if c.Valide {
        return c, ErrDejaValidee
    }

    var articles int
    var ht int64
    for i, l := range c.Lignes {
        if l.Quantite <= 0 {
            return Commande{}, fmt.Errorf("%w : ligne %d : %d", ErrLigneVide, i, l.Quantite)
        }
        articles += l.Quantite
        ht += int64(l.Quantite) * l.PrixHT
    }

    if err := s.stock.Reserver(ctx, c.ID, c.Lignes); err != nil {
        return Commande{}, err
    }

    total, err := remise.Appliquer(ht, articles, s.taux)
    if err != nil {
        return Commande{}, fmt.Errorf("commande : %w", err)
    }

    c.Valide = true
    c.TotalHT = total
    if err := s.depot.Ecrire(ctx, c); err != nil {
        return Commande{}, fmt.Errorf("commande : ecriture : %w", err)
    }
    return c, nil
}
```

> **L'idempotence de `Reserver` est ce qui rend l'ordre des deux écritures
> indifférent.** Sans elle, il n'existe aucun ordre correct — seulement le
> choix entre une fuite de stock et une double réservation.

C'est le résultat le plus utile de l'exercice. L'énoncé invitait à se demander
quel ordre choisir ; la bonne réponse est de rendre la question sans objet.

### La règle de remise, sortie dans son module

```go
// Package remise porte la politique commerciale, et elle seule.
//
// Elle a ete sortie du service de validation pour une raison mesurable : le
// demandeur de la remise est le directeur commercial, celui de la reservation
// de stock est la logistique. Deux demandeurs, deux raisons de changer.
package remise

import (
    "errors"
    "fmt"
)

// ErrTauxInvalide : un taux negatif ou superieur a 100 % n'est pas une remise.
var ErrTauxInvalide = errors.New("remise : taux invalide")

// SeuilArticles est le nombre d'articles AU-DELA duquel la remise s'applique.
//
// « Plus de dix articles » veut dire onze. Cette phrase est la raison d'etre de
// la constante et des deux cas de test qui l'entourent : 10 sans remise, 11
// avec. C'est le seul endroit du programme ou la frontiere est ecrite.
const SeuilArticles = 10

// Taux est une remise en pour mille. 100 vaut 10 %.
type Taux int64

// Appliquer rend le montant apres remise.
//
// GARANTI
//
//    Au plus SeuilArticles articles : le montant est rendu inchange.
//    Au-dela : le montant est diminue du taux, arrondi vers le bas — l'arrondi
//    va dans le sens du client, et c'est une decision commerciale, pas un
//    detail de calcul.
//
// CE QUI RESTE VRAI
//
//    Le montant rendu n'est jamais negatif ni superieur au montant d'entree.
func Appliquer(montantHT int64, articles int, taux Taux) (int64, error) {
    if taux < 0 || taux > 1000 {
        return 0, fmt.Errorf("%w : %d pour mille", ErrTauxInvalide, taux)
    }
    if articles <= SeuilArticles {
        return montantHT, nil
    }
    return montantHT - montantHT*int64(taux)/1000, nil
}
```

### Les doubles, avec une mémoire

```go
// Les deux doubles de cette suite. Ils ENREGISTRENT et ils EN TIRENT DES
// CONSEQUENCES — c'est la seule difference avec les mocks de la version
// d'origine, et c'est elle qui rend la suite capable de voir quelque chose.

type depotMem struct {
    mu        sync.Mutex
    commandes map[string]commande.Commande
    echoue    error
    ecritures int
}

func nouveauDepot(cs ...commande.Commande) *depotMem {
    d := &depotMem{commandes: map[string]commande.Commande{}}
    for _, c := range cs {
        d.commandes[c.ID] = c
    }
    return d
}

func (d *depotMem) Lire(ctx context.Context, id string) (commande.Commande, error) {
    d.mu.Lock()
    defer d.mu.Unlock()
    c, connu := d.commandes[id]
    if !connu {
        return commande.Commande{}, errors.New("depotMem : commande inconnue")
    }
    return c, nil
}

func (d *depotMem) Ecrire(ctx context.Context, c commande.Commande) error {
    d.mu.Lock()
    defer d.mu.Unlock()
    if d.echoue != nil {
        return d.echoue
    }
    d.commandes[c.ID] = c
    d.ecritures++
    return nil
}

// CasserEcriture fait echouer toutes les ecritures a venir. C'est la couture
// ouverte pour les tests dont la lecon parle : elle n'est pas dans l'interface
// Depot, et elle est le prix de la clause d'echec.
func (d *depotMem) CasserEcriture(err error) {
    d.mu.Lock()
    defer d.mu.Unlock()
    d.echoue = err
}

func (d *depotMem) Reparer() {
    d.mu.Lock()
    defer d.mu.Unlock()
    d.echoue = nil
}
```

```go
type stockMem struct {
    mu sync.Mutex
    // disponible est l'etat reel. Reserver le DECREMENTE : c'est toute la
    // difference avec un mock qui compte les appels.
    disponible map[string]int
    // reservations garde la trace par commande, ce qui rend Reserver
    // idempotente comme le contrat l'exige.
    reservations map[string][]commande.Ligne
    echoue       error
}

func nouveauStock(disponible map[string]int) *stockMem {
    d := map[string]int{}
    for a, n := range disponible {
        d[a] = n
    }
    return &stockMem{disponible: d, reservations: map[string][]commande.Ligne{}}
}

func (s *stockMem) Reserver(ctx context.Context, idCommande string, lignes []commande.Ligne) error {
    s.mu.Lock()
    defer s.mu.Unlock()

    if s.echoue != nil {
        return s.echoue
    }
    // Idempotence sur l'id : deja reserve, rien a faire.
    if _, deja := s.reservations[idCommande]; deja {
        return nil
    }

    // Tout ou rien : on verifie l'ensemble avant de toucher a quoi que ce soit.
    for _, l := range lignes {
        if s.disponible[l.Article] < l.Quantite {
            return fmt.Errorf("%w : %s", commande.ErrStockInsuffisant, l.Article)
        }
    }
    for _, l := range lignes {
        s.disponible[l.Article] -= l.Quantite
    }
    s.reservations[idCommande] = append([]commande.Ligne(nil), lignes...)
    return nil
}

func (s *stockMem) Disponible(article string) int {
    s.mu.Lock()
    defer s.mu.Unlock()
    return s.disponible[article]
}

func (s *stockMem) CasserReservation(err error) {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.echoue = err
}
```

Cent vingt et une lignes. C'est le prix, et il faut le regarder en face :
**c'est plus que la suite de tests d'origine entière.** Ce que ces 121 lignes
achètent :

| Le double fait | Ce que ça rend visible |
|---|---|
| `Reserver` décrémente | la fuite de stock |
| `Reserver` est idempotente par id | que le code en dépend vraiment |
| `Ecrire` conserve | l'état « déjà validée » |
| `CasserEcriture` / `CasserReservation` | les deux clauses d'échec |
| un `sync.Mutex` | l'exercice sous `-race` |

Et noter `CasserEcriture` : c'est exactement la couture dont parle la leçon —
elle n'est pas dans l'interface `Depot`, elle existe pour les tests, et c'est le
prix de la clause d'échec. Il n'y a pas de version gratuite.

### Les tests

```go
// Defaut 1 de la question 3 : « que reste-t-il de vrai si Ecrire echoue ? »
//
// Dans la version d'origine : le stock est reserve, la commande n'est pas
// validee, et le reessai reserve une deuxieme fois. Le stock fuit a chaque
// tentative. Le double sans memoire ne pouvait pas le voir, parce que son
// Ecrire ne savait pas echouer et que son Reserver ne decrementait rien.
func TestUneEcritureEchoueeNeFuitPasDeStock(t *testing.T) {
    d := nouveauDepot(panier(deuxA))

    d.CasserEcriture(errors.New("base : indisponible"))
```

Un test par défaut de la question 3, et **zéro assertion sur l'ordre ou le

Et celui que la version d'origine ne pouvait pas écrire du tout :

```go
// TestCinquanteValidationsConcurrentesNeReserventQuUneFois : le check-then-act
// de la version d'origine, exerce.
//
// Avec deux methodes — Disponible puis Reserver — cinquante goroutines lisent
// « 10 disponibles » et reservent toutes. Avec une seule operation atomique et
// idempotente, le stock baisse de 2, une fois.
func TestCinquanteValidationsConcurrentesNeReserventQuUneFois(t *testing.T) {
    d := nouveauDepot(panier(deuxA))
    s := nouveauStock(map[string]int{"A": 10})
    svc := commande.Nouveau(d, s, 100)

    var attente sync.WaitGroup
    for i := 0; i < 50; i++ {
        attente.Add(1)
        go func() {
            defer attente.Done()
            _, _ = svc.Valider(context.Background(), "C-1")
        }()
    }
    attente.Wait()

    if s.Disponible("A") != 8 {
        t.Fatalf("stock A = %d apres 50 validations concurrentes, attendu 8", s.Disponible("A"))
    }
    t.Logf("50 validations concurrentes : stock A = %d, %d ecriture(s)",
        s.Disponible("A"), d.ecritures)
}
```

## Question 5 — quels tests doivent échouer avant la correction

Exercice de discipline, et il faut le faire **dans cet ordre** : écrire la
suite, prédire, puis corriger.

Prédiction, sur le code d'origine :

| Test | Doit échouer ? |
|---|---|
| `TestUneEcritureEchoueeNeFuitPasDeStock` | **oui** — défaut 1 |
| `TestUnPanierPartiellementDisponibleNeReserveRien` | **oui** — défaut 2 |
| `TestValiderDeuxFoisNeReservePasDeuxFois` | **oui** — défaut 3 |

## Question 6 — le compteur

> Déplace la règle de remise dans son propre module, sans changer aucun
> comportement. Combien de tests as-tu dû modifier ?

**Zéro**, dans la suite réécrite. `TestLaFrontiereDeLaRemise` appelle
`commande.Valider` et lit `TotalHT`. Que le calcul soit dans le service ou dans
un module voisin ne change rien à ce qu'il observe.

**Deux, dans la suite d'origine** : le test n° 4 et le test n° 5. Le n° 4 parce
qu'il réimplémente la formule — il faudrait décider s'il importe désormais
`remise`. Le n° 5 parce qu'il compte les appels.

Et c'est tout le compteur :

> **Combien de tests faut-il modifier pour un refactoring qui ne change aucun
> comportement ?** La bonne réponse est zéro. Chaque test au-dessus de zéro
> garde la structure et non le contrat, et il faudra le payer à chaque
> refactoring suivant.

## Ce que la campagne de modifications a appris sur elle-même

Dix modifications, dix détectées. Mais il faut raconter le chemin, parce qu'il
contient le piège.

Au premier passage, **deux modifications avaient l'air de survivre** : « écrire
avant de réserver » et « avaler l'erreur de réservation ». J'ai failli écrire
deux paragraphes sur des survivantes instructives.

Elles ne survivaient pas. **Elles ne s'étaient pas appliquées.** La première
replaçait l'appel à `Reserver` juste avant `Ecrire` — c'est-à-dire au même
endroit. La seconde utilisait un motif `sed` contenant un `\n`, que `sed` ne
fait pas correspondre ligne à ligne. Dans les deux cas le fichier était
inchangé, les tests passaient, et le relevé affichait « SURVIT ».

> **Le mode de panne d'une campagne de modifications est la modification qui ne
> modifie rien.** Elle apparaît comme une survivante, et elle accuse à tort la
> suite de tests.

La garde, et elle est obligatoire : **vérifier que la modification a bien été
appliquée** avant de lire le résultat. Un `git diff`, un `grep` sur la ligne
attendue, n'importe quoi — mais pas rien. Appliquées pour de bon, les deux
modifications font tomber trois tests et deux tests.

Le relevé complet :

| # | La modification | Qui crie |
|---|---|---|
| 1 | `remise` : seuil `<=` → `<` | `TestLaFrontiereDeLaRemise` + `TestAppliquer` |
| 2 | `remise` : `SeuilArticles` 10 → 11 | `TestLaFrontiereDeLaRemise` + `TestAppliquer` |
| 3 | `remise` : arrondi vers le haut | `TestAppliquer` |
| 4 | la ligne de quantité nulle n'est plus refusée | `TestUneLigneInvalideEstRefuseeAvantToutEffet` |
| 5 | revalider est permis | `TestValiderDeuxFoisNeReservePasDeuxFois` |
| 6 | `Ecrire` avant `Reserver` | 3 tests |
| 7 | l'erreur de réservation est avalée | 2 tests |
| 8 | le total ignore la quantité | 2 tests |
| 9 | `articles` compte les lignes et non les unités | `TestLaFrontiereDeLaRemise` |
| 10 | `Valide` n'est pas positionné | 3 tests |

Noter le n° 9. Il ne change **aucun** total tant que chaque ligne a une quantité
de 1, et il casse la remise dès qu'un client commande douze exemplaires du même
article. Un seul test le voit, et c'est celui dont les deux cas sont à 10 et 11
articles sur **une seule ligne**. Les cas limites bien choisis attrapent des
modifications qu'on n'avait pas prévues.

## Ce que ça ne règle pas

**`Reserver` idempotente par id suppose un stockage.** Dans le double, c'est une
`map`. Dans la vraie vie, c'est une table `reservations` avec une contrainte
d'unicité sur `(id_commande)` — un ⚫ côté base. Tant que cette contrainte
n'existe pas, l'idempotence est une promesse du contrat que rien ne tient. Le
test de contrat du stock est l'endroit où ça s'écrit, et il n'est pas dans cette
correction.

**L'expiration des réservations n'existe pas.** Une commande réservée et jamais
validée bloque du stock pour toujours. C'est un besoin réel, il a un demandeur
— la logistique —, et il appartient à un autre module : une tâche qui libère les
réservations au-delà d'un délai. Ce qu'il faut retenir, c'est qu'on ne peut pas
l'écrire sans que `Reserver` soit clée par la commande. **La correction de
l'idempotence a rendu possible une fonction qui n'était pas demandée.**

**Le test concurrent prouve moins qu'il n'en a l'air.** Mon double sérialise
tout avec un `sync.Mutex` : c'est le comportement d'une base avec une contrainte
d'unicité, et ce n'est pas celui d'une base sans. Le test vérifie que le
**service** ne fait rien de faux quand le stock est atomique. Il ne prouve pas
que le stock réel l'est. Cette clause appartient au test de contrat du stock,
exécuté contre la vraie base — c'est le périmètre B de l'exercice 4.

**Il reste un `check-then-act` dans `Valider`** : `Lire` puis `Ecrire`. Deux
validations concurrentes lisent toutes les deux `Valide == false`. Ici c'est
sans conséquence, parce que `Reserver` est idempotente et que la seconde
écriture écrit la même chose. Mais le raisonnement est fragile : il repose sur
le fait que l'écriture est idempotente **par accident**. La version solide est
une écriture conditionnelle — `UPDATE … WHERE valide = false` — et son contrat
doit dire ce qu'elle rend quand zéro ligne est touchée.

## Ce qu'il faut retenir

1. **Cinq genres de tests inutiles**, et il faut savoir les nommer : vide,
   miroir, tautologique, test du double, test écrit pour la couverture.
2. **Un test qui casse quand on corrige un bug garde la mauvaise chose.**
3. **Une valeur attendue recalculée dans le test ne vérifie rien.** Écris la
   constante à la main ; l'effort est le signe de la valeur.
4. **Un test qui transporte la valeur du double jusqu'à l'assertion teste le
   double.**
5. **Quatre défauts invisibles pour une seule raison** : les doubles n'ont pas
   de mémoire. C'est un oubli, pas quatre.
6. **Une opération atomique et idempotente supprime trois défauts d'un coup** :
   le check-then-act, la réservation partielle, la double réservation.
7. **L'idempotence rend l'ordre des écritures indifférent.** Sans elle, aucun
   ordre n'est correct.
8. **Un test qui ne passe pas du rouge au vert fige un comportement correct.**
   C'est utile aussi.
9. **Zéro test modifié pour un refactoring sans changement de comportement.**
   C'est le compteur.
10. **Le mode de panne d'une campagne de modifications est la modification qui
    ne modifie rien.** Vérifie toujours qu'elle s'est appliquée.
11. **Trois fois plus de lignes de test, moins de couverture, dix fois plus de
    défauts détectés.** La couverture n'est pas la mesure.
