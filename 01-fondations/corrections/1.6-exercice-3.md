## Question 3 — les quatre défauts que la suite ne voit pas

### Défaut 1 — `Write` échoue : le stock fuit

Le code réserve, puis écrit. Si l'écriture échoue, la réservation est faite et
la commande n'est pas validée. Le client réessaie — ou le client **clique deux
fois**, ce qui est le cas le plus fréquent — et `Reserve` est appelée une
seconde fois. Sur cinq tentatives, dix unités réservées pour une commande de
deux.

| | |
|---|---|
| **Scénario client** | « Erreur, veuillez réessayer. » Il réessaie quatre fois. L'article passe en rupture de stock alors qu'il reste quarante pièces en entrepôt. |
| **Étape de la grille empêchée** | **observer** — `Reserve` du double ne décrémente rien, donc la fuite n'a aucune trace observable |

### Défaut 2 — la deuxième ligne manque de stock : réservation partielle

La boucle réserve ligne par ligne. Si la ligne 3 manque de stock, les lignes 1
et 2 sont déjà réservées, et la fonction rend une erreur sans rien défaire.

| | |
|---|---|
| **Scénario client** | la commande est refusée, et deux articles sur trois sont bloqués pour un panier qui n'existe pas. Ils se libéreront à l'expiration — s'il y a une expiration. |
| **Étape empêchée** | **observer**, pour la même raison |

### Défaut 3 — valider deux fois réserve deux fois

Rien ne regarde `c.Valid`. Une commande déjà validée est revalidée, et tout le
panier est réservé une deuxième fois.

| | |
|---|---|
| **Scénario client** | un rafraîchissement de page, un double clic, un réessai de passerelle de paiement. Même conséquence, en pire : la commande est valide, donc personne ne s'en aperçoit. |
| **Étape empêchée** | **amener dans l'état** — le double ne garde pas la commande écrite, donc on ne peut pas construire l'état « déjà validée » |

### Défaut 4 — dix articles exactement

`if SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2farticles SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f> SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f10` : à dix articles, pas de remise. Est-ce voulu ? La règle dit
*« plus de dix articles »*, donc oui — mais **rien ne le dit dans le code et
rien ne le vérifie**. Le jour où quelqu'un lit « à partir de dix », il change
`>` en `>=` et personne ne le remarque.

| | |
|---|---|
| **Scénario client** | un client avec exactement dix articles réclame sa remise. Le support ne sait pas qui a raison. |
| **Étape empêchée** | aucune — celui-là est un simple trou dans le tableau de cas. Tous les défauts ne sont pas des défauts de conception. |

### Et le cinquième, qui n'était pas dans les indices

`Available` puis `Reserve` sont **deux appels**. Entre les deux, un autre
processus passe. C'est un `check-then-act`, le défaut de la leçon 1.3, et aucun
test séquentiel ne peut le voir.

> Quatre des cinq défauts sont invisibles **pour la même raison** : les doubles
> n'ont pas de mémoire. Ce n'est pas cinq oublis, c'est un seul, répété cinq
> fois.

## Question 4 — la suite réécrite

### D'abord, le code

La correction est dans **une signature**, et il faut la lire avant les tests :

```go
// Stock reserves the cart IN ONE OPERATION.
// It is the most important fix of this file, and it is in the
// signature. The original version had two methods, Available then
// Reserve, called line by line. So it had three flaws at once:
//
//   - a check-then-act between the two calls (lesson 1.3);
//   - a partial reservation if the third line lacks stock;
//   - no idempotence, so a double reservation on the slightest retry.
//
// All three disappear with a single operation, atomic and keyed by the
// order.
type Stock interface {
    // Reserve reserves all the lines, or none.
    //
    // GUARANTEED: the operation is idempotent on the order ID. A
    // second call with the same id reserves nothing more and returns nil.
    //
    // WHAT STAYS TRUE ON FAILURE: nothing is reserved. There is no
    // "half the cart is reserved" state.
    Reserve(ctx context.Context, orderID string, lines []Line) error
}
```

Trois défauts disparaissent avec une seule opération atomique, idempotente et
clée par la commande. Et la conséquence qu'il faut voir :

```go
// Validate reserves the stock and saves the validated order.
// GUARANTEED
//
//    An order already validated returns ErrAlreadyValidated and reserves nothing.
//    The total is computed after discount, by the discount module.
//
// WHAT STAYS TRUE ON FAILURE
//
//    If the reservation fails, nothing is reserved and the order is not
//    validated.
//    If the WRITE fails after a successful reservation, the stock is reserved
//    and the order is not validated. It is not a leak: the reservation
//    is idempotent on the id, so the caller's retry resumes exactly
//    where it had stopped.
//
// It is this last clause that makes the order of the two writes irrelevant.
// Without Reserve's idempotence, there is no correct order: only
// the choice between a stock leak and a double reservation.
func (s Service) Validate(ctx context.Context, id string) (Order, error) {
    c, err := s.repo.Read(ctx, id)
    if err != nil {
        return Order{}, fmt.Errorf("order: read: %w", err)
    }
    if c.Valid {
        return c, ErrAlreadyValidated
    }

    var articles int
    var ht int64
    for i, l := range c.Lines {
        if l.Qty <= 0 {
            return Order{}, fmt.Errorf("%w: line %d: %d", ErrEmptyLine, i, l.Qty)
        }
        articles += l.Qty
        ht += int64(l.Qty) * l.NetPrice
    }

    if err := s.stock.Reserve(ctx, c.ID, c.Lines); err != nil {
        return Order{}, err
    }

    total, err := discount.Apply(ht, articles, s.rate)
    if err != nil {
        return Order{}, fmt.Errorf("order: %w", err)
    }

    c.Valid = true
    c.NetTotal = total
    if err := s.repo.Write(ctx, c); err != nil {
        return Order{}, fmt.Errorf("order: write: %w", err)
    }
    return c, nil
}
```

> **L'idempotence de `Reserve` est ce qui rend l'ordre des deux écritures
> indifférent.** Sans elle, il n'existe aucun ordre correct — seulement le
> choix entre une fuite de stock et une double réservation.

C'est le résultat le plus utile de l'exercice. L'énoncé invitait à se demander
quel ordre choisir ; la bonne réponse est de rendre la question sans objet.

### La règle de remise, sortie dans son module

```go
// Package discount holds the commercial policy, and only it.
//
// It was taken out of the validation service for a measurable reason: the
// requester of the discount is the sales director, the one of reservation
// of stock is logistics. Two requesters, two reasons to change.
package discount

import (
    "errors"
    "fmt"
)

// ErrInvalidRate: a negative rate or one above 100 % is not a discount.
var ErrInvalidRate = errors.New("discount: invalid rate")

// ArticleThreshold is the number of articles BEYOND which the discount applies.
//
// "More than ten articles" means eleven. This sentence is the reason for
// the constant and of the two test cases around it: 10 without discount, 11
// with it. It is the only place in the program where the boundary is written.
const ArticleThreshold = 10

// Rate is a discount per mille. 100 is 10 %.
type Rate int64

// Apply returns the amount after discount.
//
// GUARANTEED
//
//    At most ArticleThreshold articles: the amount comes back unchanged.
//    Beyond: the amount is reduced by the rate, rounded down: rounding
//    goes in the client's favor, and it is a commercial decision, not a
//    detail of computation.
//
// WHAT STAYS TRUE
//
//    The returned amount is never negative nor above the input amount.
func Apply(netAmount int64, articles int, rate Rate) (int64, error) {
    if rate < 0 || rate > 1000 {
        return 0, fmt.Errorf("%w: %d per mille", ErrInvalidRate, rate)
    }
    if articles <= ArticleThreshold {
        return netAmount, nil
    }
    return netAmount - netAmount*int64(rate)/1000, nil
}
```

### Les doubles, avec une mémoire

```go
// The two doubles of this suite. They RECORD and they DRAW
// CONSEQUENCES: it is the only difference with the mocks of the
// original version, and it is what makes the suite able to see anything.

type memRepo struct {
    mu     sync.Mutex
    orders map[string]order.Order
    failed error
    writes int
}

func newRepo(cs ...order.Order) *memRepo {
    d := &memRepo{orders: map[string]order.Order{}}
    for _, c := range cs {
        d.orders[c.ID] = c
    }
    return d
}

func (d *memRepo) Read(ctx context.Context, id string) (order.Order, error) {
    d.mu.Lock()
    defer d.mu.Unlock()
    c, known := d.orders[id]
    if !known {
        return order.Order{}, errors.New("memRepo: unknown order")
    }
    return c, nil
}

func (d *memRepo) Write(ctx context.Context, c order.Order) error {
    d.mu.Lock()
    defer d.mu.Unlock()
    if d.failed != nil {
        return d.failed
    }
    d.orders[c.ID] = c
    d.writes++
    return nil
}

// BreakWrites makes every coming write fail. It is the seam
// opened for tests that the lesson talks about: it is not in the interface
// Repo, and it is the price of the failure clause.
func (d *memRepo) BreakWrites(err error) {
    d.mu.Lock()
    defer d.mu.Unlock()
    d.failed = err
}

func (d *memRepo) Repair() {
    d.mu.Lock()
    defer d.mu.Unlock()
    d.failed = nil
}
```

```go
type memStock struct {
    mu sync.Mutex
    // available is the real state. Reserve DECREASES it: it is the whole
    // difference from a mock that counts calls.
    available map[string]int
    // reservations keeps the trace per order, which makes Reserve
    // idempotent as the contract requires.
    reservations map[string][]order.Line
    failed       error
}

func newStock(available map[string]int) *memStock {
    d := map[string]int{}
    for a, n := range available {
        d[a] = n
    }
    return &memStock{available: d, reservations: map[string][]order.Line{}}
}

func (s *memStock) Reserve(ctx context.Context, orderID string, lines []order.Line) error {
    s.mu.Lock()
    defer s.mu.Unlock()

    if s.failed != nil {
        return s.failed
    }
    // Idempotence on the id: already reserved, nothing to do.
    if _, already := s.reservations[orderID]; already {
        return nil
    }

    // All or nothing: we check everything before touching anything.
    for _, l := range lines {
        if s.available[l.Article] < l.Qty {
            return fmt.Errorf("%w: %s", order.ErrStockTooLow, l.Article)
        }
    }
    for _, l := range lines {
        s.available[l.Article] -= l.Qty
    }
    s.reservations[orderID] = append([]order.Line(nil), lines...)
    return nil
}

func (s *memStock) Available(article string) int {
    s.mu.Lock()
    defer s.mu.Unlock()
    return s.available[article]
}

func (s *memStock) BreakReservation(err error) {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.failed = err
}
```

**c'est plus que la suite de tests d'origine entière.** Ce que ces 121 lignes

## Ce que ça ne règle pas

**`Reserve` idempotente par id suppose un stockage.** Dans le double, c'est une
`map`. Dans la vraie vie, c'est une table `reservations` avec une contrainte
d'unicité sur `(id_commande)` — un ⚫ côté base. Tant que cette contrainte
n'existe pas, l'idempotence est une promesse du contrat que rien ne tient. Le
test de contrat du stock est l'endroit où ça s'écrit, et il n'est pas dans cette
correction.

**L'expiration des réservations n'existe pas.** Une commande réservée et jamais
validée bloque du stock pour toujours. C'est un besoin réel, il a un demandeur
— la logistique —, et il appartient à un autre module : une tâche qui libère les
réservations au-delà d'un délai. Ce qu'il faut retenir, c'est qu'on ne peut pas
l'écrire sans que `Reserve` soit clée par la commande. **La correction de
l'idempotence a rendu possible une fonction qui n'était pas demandée.**

**Le test concurrent prouve moins qu'il n'en a l'air.** Mon double sérialise
tout avec un `sync.Mutex` : c'est le comportement d'une base avec une contrainte
d'unicité, et ce n'est pas celui d'une base sans. Le test vérifie que le
**service** ne fait rien de faux quand le stock est atomique. Il ne prouve pas
que le stock réel l'est. Cette clause appartient au test de contrat du stock,
exécuté contre la vraie base — c'est le périmètre B de l'exercice 4.

**Il reste un `check-then-act` dans `Validate`** : `Read` puis `Write`. Deux
validations concurrentes lisent toutes les deux `Valid SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f== SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2ffalse`. Ici c'est
sans conséquence, parce que `Reserve` est idempotente et que la seconde
écriture écrit la même chose. Mais le raisonnement est fragile : il repose sur
le fait que l'écriture est idempotente **par accident**. La version solide est
une écriture conditionnelle — `UPDATE SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f… SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fWHERE SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fvalide SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f= SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2ffalse` — et son contrat
doit dire ce qu'elle rend quand zéro ligne est touchée.

## Ce qu'il faut retenir

1. **Cinq genres de tests inutiles**, et il faut savoir les nommer : vide,
   miroir, tautologique, test du double, test écrit pour la couverture.
2. **Un test qui casse quand on corrige un bug garde la mauvaise chose.**
3. **Une valeur attendue recalculée dans le test ne vérifie rien.** Écris la
   constante à la main ; l'effort est le signe de la valeur.
4. **Un test qui transporte la valeur du double jusqu'à l'assertion teste le
   double.**
5. **Quatre défauts invisibles pour une seule raison** : les doubles n'ont pas
   de mémoire. C'est un oubli, pas quatre.
6. **Une opération atomique et idempotente supprime trois défauts d'un coup** :
   le check-then-act, la réservation partielle, la double réservation.
7. **L'idempotence rend l'ordre des écritures indifférent.** Sans elle, aucun
   ordre n'est correct.
8. **Un test qui ne passe pas du rouge au vert fige un comportement correct.**
   C'est utile aussi.
9. **Zéro test modifié pour un refactoring sans changement de comportement.**
   C'est le compteur.
10. **Le mode de panne d'une campagne de modifications est la modification qui
    ne modifie rien.** Vérifie toujours qu'elle s'est appliquée.
11. **Trois fois plus de lignes de test, moins de couverture, dix fois plus de
    défauts détectés.** La couverture n'est pas la mesure.
