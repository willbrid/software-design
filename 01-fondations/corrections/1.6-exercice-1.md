# Correction 1.6 — Exercice 1 : compréhension

## Ce que l'exercice mesure

Rien sur les tests. L'exercice vérifie une seule chose : **est-ce que tu sais
lire un défaut de conception dans une difficulté de test ?**

La fonction `Cloturer` est lisible. Elle fait ce qu'elle dit. Elle tourne depuis
dix-huit mois. Quatre-vingts pour cent des revues de code la laisseraient
passer, et c'est le piège : **l'absence de testabilité ne se voit pas à la
lecture.**

---

## Question 1 — la grille des quatre étapes

### Construire

| | |
|---|---|
| **Ce que le code impose** | un `*sql.DB` — le type concret, pas une interface — et un `*http.Client` |
| **Le défaut** | la règle de calcul et quatre moyens d'agir sur le monde sont dans la même unité |
| **Déjà nommé en** | 1.2 (une seule raison de changer), 1.3 (cohésion) |

Fais l'inventaire des demandeurs, comme en 1.2 :

| Décision dans la fonction | Qui peut exiger qu'elle change |
|---|---|
| le taux de TVA et son application | le comptable |
| le format du rapport CSV | le comptable, ou le partenaire qui le lit |
| le chemin `/var/caisse/` | l'équipe qui exploite les machines |
| l'URL du partenaire et le format JSON | le partenaire comptable |
| le statut HTTP considéré comme un succès | le partenaire, ou toi, après un incident |
| le schéma des tables `ventes` et `clotures` | l'équipe base de données |
| la clé d'idempotence `boutique+jour` | personne — et c'est le problème, voir la question 6 |

Sept décisions, au moins cinq demandeurs. Pour poser une question à la
**première** ligne de ce tableau, il faut satisfaire les six autres.

### Amener dans l'état

| | |
|---|---|
| **Ce que le code impose** | une variable d'environnement, une `map` de paquet, un compteur de paquet, et des lignes dans deux tables |
| **Le défaut** | l'état n'est pas adressable depuis l'extérieur de la fonction |
| **Déjà nommé en** | 1.1 (propriété des données), 1.3 (couplage par état global, degré 4) |

Trois états distincts, trois façons de ne pas y accéder :

- `tauxTVA` est lu **une fois**, à l'initialisation du paquet. Pour tester un
  taux de 20 %, il faut modifier l'environnement du processus de test avant que
  le paquet ne s'initialise. Ce n'est pas une configuration : c'est une
  constante déguisée.
- `cloturees` est une `map` de paquet. Le deuxième test de la suite part de
  l'état laissé par le premier.
- `total` est un compteur de paquet qui n'est jamais remis à zéro et que
  personne ne lit. On y revient en question 6.

### Déclencher

| | |
|---|---|
| **Ce que le code impose** | attendre le bon jour, ou changer l'heure de la machine |
| **Le défaut** | le déclencheur de la décision est à l'intérieur de la décision |
| **Déjà nommé en** | 1.4 (ce que l'appelant a le droit de ne pas savoir — ici il n'a pas le droit de **choisir**) |

Il n'existe aucun moyen de demander à cette fonction *« que clôtures-tu pour le
14 mars ? »*. Et retiens que ce n'est pas une question de test : c'est la
question que le comptable posera au premier écart, et la question de l'astreinte
au premier incident.

### Observer

| | |
|---|---|
| **Ce que le code impose** | lire un fichier dans `/var/caisse/`, ou requêter la table `clotures`, ou lire les logs du partenaire |
| **Le défaut** | le résultat du calcul est un effet de bord, pas une valeur |
| **Déjà nommé en** | 1.1, et 1.5 (une opération doit rendre son issue) |

`Cloturer` rend `error`. Le HT, la TVA, le TTC, le nombre de ventes — rien
n'apparaît dans la valeur de retour. Le calcul a eu lieu ; son résultat est
parti ailleurs.

## Question 2 — la ligne qui bloque deux étapes

```
jour := time.Now().Format("2006-01-02")
```

Elle bloque **déclencher**, évidemment : on ne peut pas choisir l'instant.

Elle bloque aussi **amener dans l'état**, et c'est la partie qu'on voit moins.
Regarde où `jour` sert :

- dans la requête `SELECT … AND jour = $2` ;
- dans le nom du fichier de rapport ;
- dans la clé d'idempotence `cloturees[boutique+jour]` ;
- dans l'insertion `INSERT INTO clotures`.

`jour` n'est pas un paramètre du calcul : c'est **la clé primaire de tout
l'état du système**. Ne pas pouvoir la choisir, c'est ne pas pouvoir mettre le
système dans l'état *« le 14 mars est déjà clôturé »* — ni pour un test, ni pour
un rattrapage, ni pour un diagnostic.

> Une ligne qui prend une décision **et** fabrique une clé d'état bloque deux
> étapes à la fois. C'est le genre de ligne dont le coût réel est invisible dans
> une revue.

## Question 3 — les trois tests

### (a) `Post` est appelé une seule fois

| | |
|---|---|
| **Ce qui le ferait échouer** | une boucle ajoutée autour de l'appel, un `retry` ajouté, l'appel déplacé |
| **Classement** | **casse pour une raison structurelle** |

C'est un **test miroir**. Il décrit la forme de l'implémentation. Le jour où
quelqu'un ajoute un réessai légitime sur le webhook — ce qui est une bonne
idée — le test devient rouge sans qu'aucun comportement attendu n'ait changé.
On le « réparera » en changeant `1` en `2`, et à ce moment-là il ne gardera
plus rien du tout.

Et il ne verrait **pas** le vrai danger : que `Post` soit appelé une fois par
exécution mais que l'exécution ait lieu trois fois.

### (b) une boutique sans vente produit un TTC de 0

| | |
|---|---|
| **Ce qui le ferait échouer** | une erreur rendue sur zéro vente, un total initialisé autrement, une TVA appliquée à un minimum forfaitaire |
| **Classement** | **casse pour une raison métier** |

C'est le seul vrai test des trois. Il porte sur une décision que quelqu'un peut
réclamer : *« une boutique fermée doit-elle apparaître dans l'export
comptable ? »* — et la réponse peut changer. C'est exactement ce qu'un test doit
garder.

Note qu'il est aujourd'hui **impossible à écrire** sans base, et que c'est tout
le problème de l'exercice.

### (c) `Cloturer` rend `nil` sur une boutique normale

| | |
|---|---|
| **Ce qui le ferait échouer** | une panique, une faute de frappe dans le SQL |
| **Classement** | **ne peut pas casser** |

Il ne vérifie rien du calcul. Il mesure la compilation et l'absence de panique.
C'est le test le plus répandu dans les bases de code réelles, et celui qui donne
le plus de confiance pour le moins de garantie.

## Question 4 — le test qui passera toujours

```go
func TestLaTVAEstAppliquee(t *testing.T) {
    ht := int64(100000)
    tva := ht * 1925 / 10000
    if ht+tva != 119250 {
        t.Fatalf("TTC = %d", ht+tva)
    }
}
```

**Il n'appelle pas le code testé.** Pas une seule fois. Il recalcule la formule
dans le test, puis vérifie que son propre calcul est juste.

C'est un **test tautologique**. Il échouerait si l'arithmétique de Go changeait.
Modifie `Cloturer` comme tu veux — mets le taux à 2 %, inverse HT et TVA,
supprime la ligne — ce test reste vert.

Le mécanisme à reconnaître, parce qu'il est fréquent sous des formes plus
subtiles :

> Dès que la valeur attendue est **calculée** dans le test avec la même formule
> que le code, le test ne vérifie plus la formule : il la répète.

La forme correcte d'une assertion sur un calcul est une **constante écrite à la
main** : `119250`, obtenue en faisant le calcul ailleurs, sur une calculatrice,
ou en demandant au comptable. Si écrire la constante demande un effort, c'est
que l'assertion a de la valeur.

Et la variante déguisée, qu'on trouve partout :

```
attendu := service.Calculer(entree)
if resultat != attendu { … }
```

Même faute, un cran plus loin.

## Question 5 — les doubles, et à qui appartient quoi

Pour tester `Cloturer` tel quel, il faut :

| Ce qu'il faut doubler | Tu le possèdes ? | Légitime ? |
|---|---|---|
| la base de données | non | oui — on ne possède pas PostgreSQL |
| le serveur du partenaire comptable | non | oui |
| le système de fichiers | non | oui, à contrecœur |
| l'horloge | **oui** — c'est ton code qui appelle `time.Now` | **non** |
| la règle de TVA | **oui** | **non** |
| la décision d'idempotence | **oui** | **non** |

Les trois premiers sont des frontières réelles : du code que tu ne possèdes pas,
derrière une couture légitime. Les trois derniers sont du **code à toi**, et
c'est le signal :

> On ne simule que ce qu'on ne possède pas. Si tu dois doubler ton propre code
> pour le tester, ce n'est pas un problème de test : c'est que ce code produit
> un **effet** là où il devrait rendre une **valeur**.

Le nombre de doubles de code que tu possèdes est donc un compteur utile, et il
se lit comme ceci : **chaque double de ton propre code est une valeur que tu
n'as pas rendue.**

Ici, trois. Les trois disparaissent sans aucun double — en descendant le jour en
argument, en sortant la règle de TVA, et en confiant l'idempotence à la base.

## Question 6 — la `map` de paquet

### Ce qu'elle fait à une suite de tests

- **Les tests ne sont plus indépendants.** Le second part de l'état laissé par
  le premier.
- **L'ordre compte.** Go ne garantit pas l'ordre d'exécution entre fichiers, et
  `-shuffle` le randomise exprès.
- **`t.Parallel()` est impossible**, ou alors avec une course sur la `map` —
  détectée par `-race`, et c'est la bonne nouvelle.
- **Le nettoyage est à la charge de chaque test**, donc oublié une fois sur
  trois.

### Ce qu'elle fait en production

- **Elle ne garantit rien.** Deux processus — deux instances, un redéploiement,
  un cron qui tourne sur deux machines — ont deux `map` différentes. La journée
  est clôturée deux fois, et le partenaire comptable reçoit deux fois le même
  TTC.
- **Elle fuit.** Une entrée par boutique et par jour, jamais supprimée. Sur
  deux cents boutiques, c'est lent, mais ça monte.
- **Elle survit à un échec.** Si `Post` échoue, `cloturees` n'est pas marquée —
  correct. Mais si l'`INSERT` échoue après un `Post` réussi, la journée sera
  reclôturée et le partenaire prévenu deux fois.

### Ce que ça confirme

Les deux réponses se ressemblent, et ce n'est pas une coïncidence :

> Un test est le deuxième appelant d'un module. L'état global gêne les tests
> pour la raison exacte qui le rend faux en production : **il suppose qu'il n'y
> a qu'un seul appelant à la fois.**

C'est le théorème central de la leçon. La difficulté de test n'est pas une taxe
payée à l'outillage : c'est le **premier symptôme** d'un défaut que la
production manifestera plus tard, plus cher.

Et le compteur `total` est le même défaut dans sa forme la plus pure : une
variable de paquet, jamais remise à zéro, que personne ne lit. Elle ne sert à
rien, elle casse les tests, et elle sera fausse le jour où on la lira.

## Ce que ça donne

La règle, seule, sans rien autour :

```go
// Package cloture calcule le total d'une journee de ventes.
//
// C'est la seule partie de la cloture que le comptable peut exiger qu'on
// change, et c'est la seule qui n'a besoin de rien pour etre interrogee.
package cloture

import (
    "errors"
    "fmt"
)

var (
    // ErrMontantNegatif : un avoir n'est pas une vente a montant negatif. S'il
    // faut les traiter, ce sera une ligne du contrat, pas un cas tolere.
    ErrMontantNegatif = errors.New("cloture : montant de vente negatif")
    // ErrTauxInvalide : un taux de TVA nul ou negatif est une erreur de
    // configuration, pas une journee sans TVA.
    ErrTauxInvalide = errors.New("cloture : taux de TVA invalide")
)

// Taux est un taux de TVA exprime en pour dix-mille. 1925 vaut 19,25 %.
// Ce n'est pas un float : un taux de TVA est une fraction exacte, et la
// comptabilite n'accepte pas « a peu pres ».
type Taux int64

// Vente est une ligne de vente, en unites monetaires entieres.
type Vente struct {
    MontantHT int64
}

// Total est le resultat de la cloture. C'est une VALEUR : l'appelant peut la
// lire, la comparer, l'ecrire ou l'ignorer. C'etait le probleme numero quatre
// de la version d'origine, et il disparait ici.
type Total struct {
    Ventes int
    HT     int64
    TVA    int64
    TTC    int64
}

// Totaliser additionne les ventes et applique le taux.
//
// GARANTI
//
//    TTC vaut exactement HT + TVA. L'arrondi se fait une fois, sur le total, et
//    non ligne par ligne — deux politiques d'arrondi differentes donneraient deux
//    resultats, et celui-ci est celui que le comptable a demande.
//
// CE QUI RESTE VRAI
//
//    ventes n'est pas modifiee. Aucun total partiel n'est rendu avec une erreur :
//    si une ligne est invalide, la journee entiere echoue, parce qu'un total
//    comptable amputé est pire qu'un total absent.
func Totaliser(ventes []Vente, taux Taux) (Total, error) {
    if taux <= 0 {
        return Total{}, fmt.Errorf("%w : %d", ErrTauxInvalide, taux)
    }

    var ht int64
    for i, v := range ventes {
        if v.MontantHT < 0 {
            return Total{}, fmt.Errorf("%w : ligne %d : %d", ErrMontantNegatif, i, v.MontantHT)
        }
        ht += v.MontantHT
    }

    tva := ht * int64(taux) / 10000
    return Total{Ventes: len(ventes), HT: ht, TVA: tva, TTC: ht + tva}, nil
}
```

expliquer de plus :

```go
// Jour est la journee comptable, au format AAAA-MM-JJ. C'est un ARGUMENT :
// time.Now est appele une fois, dans main, et la valeur descend jusqu'ici.
type Jour string

// Ventes lit les ventes d'une journee.
type Ventes interface {
    DuJour(ctx context.Context, boutique string, jour Jour) ([]cloture.Vente, error)
}

// Clotures est la memoire des journees cloturees. Elle remplace la map de
// paquet de la version d'origine : l'etat est devenu une dependance explicite,
// donc adressable par un test ET partageable entre deux processus.
type Clotures interface {
    Deja(ctx context.Context, boutique string, jour Jour) (bool, error)
    Enregistrer(ctx context.Context, boutique string, jour Jour, t cloture.Total) error
}

// Diffusion est tout ce qui part vers l'exterieur : le rapport, le partenaire
// comptable. Une seule interface, parce qu'un seul demandeur decide des deux.
type Diffusion interface {
    Publier(ctx context.Context, boutique string, jour Jour, t cloture.Total) error
}

type Service struct {
    ventes    Ventes
    clotures  Clotures
    diffusion Diffusion
    taux      cloture.Taux
}

func Nouveau(v Ventes, c Clotures, d Diffusion, taux cloture.Taux) Service {
    return Service{ventes: v, clotures: c, diffusion: d, taux: taux}
}
```

```go
// Cloturer cloture une journee et rend son total.
//
// Les quatre corrections de la version d'origine se lisent dans cette
// signature, et nulle part ailleurs :
//
//    jour est un argument          -> on peut demander « et le 14 mars ? »
//    cloture.Total est rendu       -> le resultat est observable
//    les dependances sont 3 ports  -> on peut construire sans base
//    plus de map de paquet         -> l'etat est adressable et partage
//
// GARANTI
//
//    Une journee deja cloturee n'est pas recloturee : le total enregistre est
//    rendu tel quel. Appeler deux fois est sans effet.
//
// CE QUI RESTE VRAI EN CAS D'ECHEC
//
//    La journee est enregistree AVANT d'etre diffusee. Si la diffusion echoue,
//    la journee reste cloturee et l'erreur est rendue : au pire une diffusion
//    manquante, jamais un total comptable qui change entre deux lectures.
func (s Service) Cloturer(ctx context.Context, boutique string, jour Jour) (cloture.Total, error) {
    deja, err := s.clotures.Deja(ctx, boutique, jour)
    if err != nil {
        return cloture.Total{}, fmt.Errorf("journee : etat de cloture : %w", err)
    }
    if deja {
        return cloture.Total{}, ErrDejaCloturee
    }

    ventes, err := s.ventes.DuJour(ctx, boutique, jour)
    if err != nil {
        return cloture.Total{}, fmt.Errorf("journee : lecture des ventes : %w", err)
    }

    total, err := cloture.Totaliser(ventes, s.taux)
    if err != nil {
        return cloture.Total{}, fmt.Errorf("journee : %w", err)
    }

    if err := s.clotures.Enregistrer(ctx, boutique, jour, total); err != nil {
        return cloture.Total{}, fmt.Errorf("journee : enregistrement : %w", err)
    }
    if err := s.diffusion.Publier(ctx, boutique, jour, total); err != nil {
        // La journee est cloturee. La diffusion a echoue. L'appelant doit le
        // savoir, et il ne doit pas recommencer la cloture pour autant.
        return total, fmt.Errorf("journee : diffusion : %w", err)
    }
    return total, nil
}
```

| observer | `cloture.Total` est **rendu** |

## Ce que ça ne règle pas

Quatre choses, et il faut les dire.

**1. L'arbitrage enregistrer-puis-diffuser reste un arbitrage.** Si la diffusion
échoue, la journée reste clôturée et la diffusion est perdue tant que personne
ne la relance. On a choisi une diffusion manquante plutôt qu'un total comptable
qui change entre deux lectures. C'est écrit dans le contrat, et c'est gardé par
`TestUneDiffusionEchoueeLaisseLaJourneeCloturee`. La solution qui ne prend ni
l'un ni l'autre est un journal de diffusion séparé — le motif *outbox*, niveau 7.

**2. La couverture de `journee` est de 82,4 %, et je la laisse là.** Les
branches non couvertes sont deux propagations d'erreur d'une ligne chacune
(`Deja` et `DuJour`), qui ne font qu'envelopper avec `%w`. Les couvrir
ajouterait deux tests qui vérifient qu'un `%w` enveloppe. Ce qui me ferait
changer d'avis : si l'une de ces lignes portait une **décision** — un repli, une
valeur par défaut, une conversion d'erreur en réponse métier. Alors il y aurait
quelque chose à garder.

**3. L'idempotence dépend maintenant de la base.** `Deja` puis `Enregistrer`
sont deux appels : entre les deux, un second processus peut passer. C'est un
`check-then-act`, le défaut exact de la leçon 1.3. La vraie garantie est une
contrainte d'unicité sur `(boutique, jour)` — un ⚫ côté base — et
`Enregistrer` doit traduire sa violation en `ErrDejaCloturee`. Le test de
contrat du dépôt est l'endroit où cette clause s'écrit.

**4. `Jour` est un `string`.** `journee.Jour("14 mars")` compile. C'est un 🟠 :
un type distinct qui n'empêche rien. La correction de l'exercice 2 montre à quoi
ressemble la version ⚫ — un type avec un constructeur qui refuse le 31 février.

## Ce qu'il faut retenir

1. **La grille des quatre étapes diagnostique sans jugement.** Dis où tu as mal,
   la grille nomme le défaut.
2. **Une ligne qui décide et fabrique une clé d'état bloque deux étapes.**
   `time.Now()` au milieu d'un calcul en est l'exemple canonique.
3. **Trois classes de tests inutiles** : le miroir (casse pour une raison
   structurelle), le vide (ne peut pas casser), le tautologique (n'appelle pas
   le code).
4. **Une valeur attendue calculée dans le test ne vérifie rien.** Écris la
   constante à la main.
5. **Chaque double de ton propre code est une valeur que tu n'as pas rendue.**
6. **L'état global gêne les tests pour la raison qui le rend faux en
   production** : il suppose un seul appelant.
7. **Un test est le deuxième appelant d'un module.** C'est pour ça qu'il trouve
   ce qu'une revue ne trouve pas.
