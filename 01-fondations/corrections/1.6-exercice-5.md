La base a le droit de tomber. C'était une maintenance annoncée. Le bug est

Cet ordre place l'effet **irréversible** avant sa trace. Il n'y a donc aucun
état intermédiaire sûr : entre les deux lignes, le système a agi sans le savoir.

La règle générale, et elle vaut au-delà de ce cas :

> Quand deux effets doivent aller par paire et qu'un seul est réversible, **le
> réversible passe en premier**. Un SMS ne se rappelle pas ; une ligne en base
> se supprime.

### Décision 2 — la décision est recalculée à chaque passe, à partir d'un état que la passe elle-même doit écrire

La campagne est **sans mémoire propre** : elle relit l'état, décide, agit, écrit
l'état. C'est une boucle de rétroaction, et elle n'est stable que si l'écriture
réussit. Dès que l'écriture échoue, la boucle se referme sur elle-même et
**entretient sa propre panne**.

C'est le défaut structurel, et c'est celui qu'on ne voit jamais en revue, parce
que chaque ligne prise isolément est correcte.

### Décision 3 — l'échec de consignation est une ligne de bilan, pas une erreur

> Le tableau de bord affichait un taux d'erreur de **0 %**.

`summary.Failed++` puis `continue`. La fonction rend `nil`. Du point de vue de
tout ce qui observe le système — la supervision, les alertes, l'astreinte —
**la passe a réussi**.

C'est le point exact de la leçon 1.5 : *« un `continue` sur un effet dont l'état
n'est pas durable transforme une panne bruyante en perte silencieuse »*. Sauf
qu'ici ce n'est pas une perte, c'est une **amplification silencieuse**, ce qui
est pire.

### Et la quatrième, qui n'était pas demandée

La bascule ne coupait que les **écritures** ; les lectures étaient servies par
un réplica. Le système était donc à moitié disponible, et c'est la moitié
dangereuse : il pouvait décider sans pouvoir se souvenir.

> Un système qui peut lire mais pas écrire est plus dangereux qu'un système
> complètement arrêté. Arrêté, il ne fait rien. À moitié, il agit sans mémoire.

Ce mode de panne — lecture oui, écriture non — est le plus courant dans une
base répliquée, et le plus mal couvert par les doubles : la plupart échouent sur
tout ou sur rien.

## Question 2 — 94 % de couverture, 31 tests, et rien

Pas « les tests étaient mauvais ». Le mécanisme précis, en une phrase :

> Le double de journal avait un `Record` qui rendait toujours `nil`. **Dans
> l'univers de la suite de tests, la décision 3 n'existait pas** — il n'y avait
> aucun échec de consignation à mal traiter.

Et c'est pour ça que les trois défauts sont invisibles **ensemble** :

| Décision | Pourquoi la suite ne la voit pas |
|---|---|
| l'ordre envoyer/consigner | sans échec de consignation, les deux ordres donnent le même résultat |
| la boucle de rétroaction | elle a besoin de **plusieurs passes** et d'un journal qui se souvient |
| l'échec compté en bilan | il n'y a pas d'échec |

Les trente-et-un tests ne testaient pas trente-et-une choses. Ils testaient la
même chose trente-et-une fois : **le chemin où tout marche.**

### Les trois propriétés manquantes

Pour voir cet incident, il faut exactement trois choses, et la suite d'origine
en avait **zéro** :

1. **un double qui se souvient** — sinon rien ne se cumule d'une passe à
   l'autre ;
2. **une panne qui ne coupe que les écritures** — le mode de panne réel ;
3. **plusieurs passes** — une seule passe ne montre rien du tout.

La troisième est la plus négligée. Un test qui appelle la fonction **une fois**
ne peut par construction rien dire d'un système qui tourne toutes les heures.

> Pour un traitement périodique, le test minimal n'est pas un appel. C'est
> **deux appels**, et le second est celui qui compte.

## Question 3 — le test qui aurait attrapé ça

### Le double, d'abord

C'est là que tout se joue. Trois capacités, et la bascule asymétrique est celle
que personne n'écrit :

```go
// ErrWritesUnavailable: the database does not take writes. Reads,
// go through: they are served by a replica.
//
// It is the exact failure mode of the incident, and the least covered of
// all: most doubles fail on everything or on nothing.
var ErrWritesUnavailable = errors.New("journal: writes unavailable")

// Unpaid is a line of the journal.
type Unpaid struct {
    Reference string
    Due       time.Time
    Tier      int
}

// Journal is the memory of reminders, with a failover that cuts only the
// writes.
type Journal struct {
    mu         sync.Mutex
    unpaid     map[string]Unpaid
    order      []string
    writesDown bool
    records    int
}

func NewJournal() *Journal {
    return &Journal{unpaid: map[string]Unpaid{}}
}

func (j *Journal) Add(i Unpaid) {
    j.mu.Lock()
    defer j.mu.Unlock()
    if _, known := j.unpaid[i.Reference]; !known {
        j.order = append(j.order, i.Reference)
    }
    j.unpaid[i.Reference] = i
}

// ToggleWrites cuts or restores writes. Reads are never
// affected: that is what makes the failure silent.
func (j *Journal) ToggleWrites(outOfService bool) {
    j.mu.Lock()
    defer j.mu.Unlock()
    j.writesDown = outOfService
}

func (j *Journal) Records() int {
    j.mu.Lock()
    defer j.mu.Unlock()
    return j.records
}

// Unpaid reads. Served by the replica, so always available.
func (j *Journal) Unpaid() []Unpaid {
    j.mu.Lock()
    defer j.mu.Unlock()
    out := make([]Unpaid, 0, len(j.order))
    for _, ref := range j.order {
        out = append(out, j.unpaid[ref])
    }
    return out
}

// Record writes. Unavailable during the failover.
func (j *Journal) Record(reference string, tier int) error {
    j.mu.Lock()
    defer j.mu.Unlock()
    if j.writesDown {
        return ErrWritesUnavailable
    }
    i, known := j.unpaid[reference]
    if !known || i.Tier >= tier {
        return nil
    }
    i.Tier = tier
    j.unpaid[reference] = i
    j.records++
    return nil
}
```

Noter `ToggleWrites`. Elle ne coupe **que** `Record`. `Unpaid`
continue de répondre. Cinq lignes, et elles sont la différence entre une suite
de tests qui voit l'incident et une suite qui ne le voit pas.

### Le test

```go
// TestTheIncidentReproduced is the test that would have caught the incident.
// It needs THREE things, and that is the answer to question 3:
//
//  1. a journal that remembers: otherwise nothing adds up from one pass to
//     the next;
//  2. a failure that cuts ONLY writes: the exact failure mode of a
//     failover served by a replica, and the one nobody simulates;
//  3. SEVERAL passes: a single pass shows nothing at all.
//
// The thirty-one tests of the original suite had none of the three.
func TestTheIncidentReproduced(t *testing.T) {
    tc := []struct {
        name         string
        order        reminders.Order
        smsWant      int
        maxPerClient int
        records      int
        why          string
    }{
        {
            name:         "send then record: the incident",
            order:        reminders.SendThenRecord,
            smsWant:      7 * unpaid,
            maxPerClient: 7,
            records:      0,
            why:          "each pass sends everything again, and none records anything",
        },
        {
            name:         "record then send: nothing leaves",
            order:        reminders.RecordThenSend,
            smsWant:      0,
            maxPerClient: 0,
            records:      0,
            why:          "no record, no send. The work is postponed, not lost",
        },
    }

    for _, c := range tc {
        t.Run(c.name, func(t *testing.T) {
            j, p := loadedJournal(), reminders.NewGateway()

            // 02:00: the failover starts, and it lasts longer than
            // planned. Seven hourly passes, from 02:00 to 08:00.
            j.ToggleWrites(true)

            var total reminders.Summary
            for hour := 2; hour <= 8; hour++ {
                now := due.Add(4 * 24 * time.Hour).Add(time.Duration(hour) * time.Hour)
                b := reminders.Pass(j, p, now, c.order)
                total.Decided += b.Decided
                total.Sent += b.Sent
                total.Failed += b.Failed
            }

            if p.SMS() != c.smsWant {
                t.Fatalf("%d SMS, want %d (%s)", p.SMS(), c.smsWant, c.why)
            }
            if p.MaxPerClient() != c.maxPerClient {
                t.Fatalf("%d SMS for the most-served client, want %d",
                    p.MaxPerClient(), c.maxPerClient)
            }
            if j.Records() != c.records {
                t.Fatalf("%d records, want %d", j.Records(), c.records)
            }

            t.Logf("7 passes, %d unpaid: %d SMS sent, %d max per client,"+
                " %d records, %d failures in the summary",
                unpaid, p.SMS(), p.MaxPerClient(), j.Records(), total.Failed)
        })
    }
}
```

### Sa forme, et le compte

| | |
|---|---|
| **Ce que le double doit savoir faire** | se souvenir, et échouer **en écriture seulement** |
| **Nombre de passes** | 7 — mais 2 suffisent à voir l'amplification |
| **L'assertion** | le nombre de SMS **réellement partis**, et le maximum par client |
| **Lignes** | 70, dont 35 de tableau de cas |

Soixante-dix lignes. La suite d'origine en faisait plusieurs centaines pour
trente-et-un tests.

> Un test qui vaut quelque chose ne coûte pas plus cher qu'un test qui ne vaut
> rien. Il coûte plus cher **à concevoir**, parce qu'il faut savoir quelle
> question poser. Écrire trente tests est une façon de ne pas choisir la
> question.

Et le choix de l'assertion mérite un mot : elle porte sur le **nombre de SMS
reçus par le client le plus servi**. Pas sur les appels, pas sur l'ordre, pas
sur le bilan. Sur ce que le client a reçu. C'est le genre d'assertion qui ne
casse jamais pour une raison structurelle, parce qu'elle est exprimée dans les
termes du métier.

## Question 4 — les sept heures

### Ce qui, dans la conception, les explique

Reprends les deux termes du MTTR de la leçon 1.2 — *temps pour former la bonne
hypothèse* + *temps pour agir*.

**Temps pour agir : vingt-huit minutes.** De 09h12 à 09h40. C'est correct.

**Temps pour former la bonne hypothèse : sept heures et douze minutes.** Tout
est là, et la conception en est entièrement responsable :

| L'obstacle | La décision qui l'a créé |
|---|---|
| le taux d'erreur était à 0 % | décision 3 : l'échec est une ligne de bilan |
| la passe rendait `nil` | décision 3 |
| aucune métrique ne comptait les envois | le résultat de la passe n'était pas observé |
| le bilan existait mais n'était lu par personne | il était rendu, pas publié |
| rien ne distinguait un SMS neuf d'un SMS répété | pas de clé d'idempotence, pas de compteur par référence |

> Le système n'a pas mis sept heures à être détecté. Il n'avait **aucun moyen**
> d'être détecté. La détection est venue de l'extérieur — un client au support —
> parce que c'était le seul capteur branché.

### Et le lien avec la leçon

C'est le théorème du chapitre, sous sa forme la plus chère :

> Les trois questions que l'astreinte a dû se poser — *qu'est-ce que la passe de
> 02h00 a décidé ? combien de SMS sont partis ? pourquoi la consignation a-t-elle
> échoué ?* — sont les étapes **observer**, **observer** et **amener dans
> l'état** de la grille. **Ce sont les mêmes blocages que pour les tests.**

La testabilité n'était pas une dette technique abstraite. Elle valait sept
heures et 7 080 SMS, un mardi.

## Question 5 — quelle grandeur surveiller

L'énoncé disait que ce n'est pas un taux d'erreur. Il faut aller plus loin : la
grandeur à laquelle on pense d'abord **ne marche pas non plus**, et c'est le
résultat le plus utile de la question.

```go
// TestWhichIndicatorSeesTheIncident compares two candidate figures, one of which
// does not work. It is the useful part of question 5.
//
// Candidate 1: sent / decided, per pass. It is the figure one
// thinks of first, and it is 1.00 during the whole incident. Each pass decides
// 1,180 reminders and sends 1,180: from its point of view, all is well.
//
// Candidate 2: records / sent, per pass. It is 0.00 from the
// first pass. It is the ratio between two effects that are supposed to come in
// pair, and that is what makes it immediate.
func TestWhichIndicatorSeesTheIncident(t *testing.T) {
    j, p := loadedJournal(), reminders.NewGateway()
    base := due.Add(4 * 24 * time.Hour)
    j.ToggleWrites(true)

    smsBefore, recBefore := 0, 0
    for pass := 1; pass <= 3; pass++ {
        b := reminders.Pass(j, p, base.Add(time.Duration(pass)*time.Hour), reminders.SendThenRecord)

        sentPass := p.SMS() - smsBefore
        recPass := j.Records() - recBefore
        smsBefore, recBefore = p.SMS(), j.Records()

        sentOverDecided := float64(sentPass) / float64(b.Decided)
        recOverSent := float64(recPass) / float64(sentPass)
        totalOverDistinct := float64(p.SMS()) / float64(unpaid)

        t.Logf("pass %d: sent/decided = %.2f | records/sent = %.2f"+
            " | total SMS / distinct unpaid = %.2f",
            pass, sentOverDecided, recOverSent, totalOverDistinct)

        // Candidate 1 does not move. It is the result to remember.
        if sentOverDecided != 1.00 {
            t.Fatalf("pass %d: sent/decided = %.2f, want 1.00:"+
                " this figure sees nothing, and that is the point", pass, sentOverDecided)
        }
        // Candidate 2 is at zero from the first pass.
        if recOverSent != 0.00 {
            t.Fatalf("pass %d: records/sent = %.2f, want 0.00",
                pass, recOverSent)
        }
    }

    // And the third figure, the one that confirms an hour later.
    if total := float64(p.SMS()) / float64(unpaid); total != 3.00 {
        t.Fatalf("total SMS / distinct unpaid = %.2f, want 3.00", total)
    }
}
```

## Question 7 — la mesure, le seuil, le rituel

### Pourquoi « 100 % de couverture » est faux, en deux phrases

> La couverture mesure les lignes **exécutées**, pas les propriétés
> **vérifiées** : la suite de l'exercice 3 couvre 100 % d'un code qui envoie
> cinq fois le même rappel. Et dans cet incident précis, aucune ligne n'était
> manquante — c'est un **mode de panne** qui n'était pas exercé, et un mode de
> panne n'est pas une ligne.

La seconde phrase est la plus importante, et elle est spécifique à cet
incident : la couverture n'aurait **jamais** pu voir ça, à aucun pourcentage.

### La mesure

> **Le taux de modifications détectées** : sur dix modifications appliquées à la
> main dans le code de production, combien font échouer au moins un test.

Pourquoi celle-là :

- **lisible sans outil** — un `git SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fstash`, un éditeur, dix minutes ;
- **elle mesure ce qu'on veut savoir** : si le code se dégrade, est-ce qu'on
  l'apprend par un test ou par un client ;
- **elle se compare** d'un module à l'autre et d'un trimestre à l'autre.

Et il faut la dire avec sa règle de choix des modifications, sinon elle ne vaut
rien : **les dix modifications doivent viser les décisions du module** — un
seuil, un ordre d'effets, une propagation d'erreur, une clause d'échec — et non
des détails de forme. Ce chapitre en donne quatre relevés complets, et ils sont
le modèle.

### Le seuil

| Portée | Seuil | Argument |
|---|---|---|
| modules qui décident ou agissent | **10 / 10** | une modification non détectée sur un module qui envoie des SMS est un incident qui attend |
| le reste | **8 / 10**, avec les deux survivantes **nommées et justifiées** | il existe des survivantes légitimes — coût, constante de sûreté, modification équivalente. L'exercice 2 en donne deux |

La colonne de droite est le seuil réel. « 8 sur 10 » sans justification des deux
restantes, c'est 8 sur 10 de chance.

### Le rituel

**Quarante-cinq minutes, une fois par semaine, sur un seul module.** Celui qui a
changé le plus dans la semaine — `git SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2flog SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f--name-only` le donne en dix secondes.

1. Choisir dix modifications sur les décisions du module *(10 min)*
2. Les appliquer une par une, relever qui crie *(20 min)*
3. **Vérifier que chaque modification s'est bien appliquée** *(5 min)*
4. Écrire le relevé dans le dépôt, à côté du code *(10 min)*

L'étape 3 n'est pas de la bureaucratie. Dans ce chapitre, **deux modifications
sur dix ne s'étaient pas appliquées** et apparaissaient comme des survivantes.
Une campagne non vérifiée accuse à tort la suite de tests.

Pourquoi ce rituel-là sera fait : il est **borné** (un module, dix
modifications, quarante-cinq minutes), il produit un **artefact** (le relevé,
versionné), et il est **intéressant** — on y apprend toujours quelque chose sur
le code, pas seulement sur les tests. Un rituel qui n'apprend rien à celui qui
le fait est abandonné en six semaines, quel que soit l'engagement pris.

### Et la vraie question : empêcher que la mesure devienne un chiffre

C'est la partie de la question qui compte, parce que c'est exactement ce qui est
arrivé à la couverture. Quatre gardes, par ordre d'efficacité.

**1. Ne jamais l'automatiser en CI.** C'est contre-intuitif, et c'est la garde
la plus forte. Dès qu'un chiffre bloque une fusion, l'équipe optimise le
chiffre : un outil de mutation en CI produit des tests écrits pour tuer des
mutants, pas pour garder des contrats. La mesure reste **manuelle et
périodique** — elle informe, elle ne barre pas la route.

**2. Les modifications sont choisies par quelqu'un qui n'a pas écrit les
tests.** C'est la garde décisive. Une mesure qu'on s'applique à soi-même mesure
ce qu'on avait prévu de mesurer. En binôme, à tour de rôle, et c'est aussi la
meilleure revue de code que l'équipe fera cette semaine.

**3. Le relevé publie les survivantes et leur justification, pas le ratio.**
« 8/10 » est un chiffre à optimiser. « Les deux survivantes sont une constante
de sûreté et un coût d'appel non documenté » est une information qu'on ne peut
pas falsifier sans mentir explicitement.

**4. Changer d'angle quand le chiffre sature.** Si un module fait 10/10 trois
fois de suite, la mesure ne mesure plus rien **pour ce module** : on en change.
Une mesure utile est une mesure qui bouge encore.

Et le principe derrière les quatre, qui vaut pour toutes les métriques de ce
cours :

> Une mesure devient un chiffre à optimiser dès qu'elle a des **conséquences
> automatiques**. Garde-la lente, manuelle, contradictoire et narrative, et elle
> reste une mesure. Branche-la sur une porte de déploiement, et tu as fabriqué
> la prochaine couverture de code.

   entretient sa propre panne** dès que l'écriture échoue.
3. **Un `continue` sur un échec d'effet durable rend une panne invisible** —
   ici, 0 % d'erreur affiché pendant sept heures.
4. **Un système qui lit mais n'écrit pas est plus dangereux qu'un système
   arrêté.** C'est le mode de panne d'une base répliquée, et le plus mal
   couvert.
5. **Pour un traitement périodique, le test minimal est de deux appels.** Un
   seul ne peut rien dire.
6. **Trois propriétés rendent cet incident visible** : un double qui se
   souvient, une panne qui ne coupe que les écritures, plusieurs passes.
7. **Un bon test ne coûte pas plus cher qu'un mauvais, il coûte plus cher à
   concevoir.** Trente tests sont souvent une façon de ne pas choisir la
   question.
8. **Une grandeur calculée à l'intérieur d'une unité de travail ne voit pas la
   répétition de l'unité de travail.** `envoyés/décidés` vaut 1,00 pendant tout
   l'incident.
9. **Le rapport de deux effets appariés est une alerte**, de valeur de référence
   1, qui bouge au premier découplage.
10. **On ne supprime pas l'arbitrage perte/doublon, on le déplace** — et on paie
    le déplacement en exploitation.
11. **La couverture n'aurait jamais pu voir cet incident** : aucune ligne ne
    manquait, c'est un mode de panne qui n'était pas exercé.
12. **Une mesure devient un chiffre dès qu'elle a des conséquences
    automatiques.** Garde-la manuelle, contradictoire et narrative.
