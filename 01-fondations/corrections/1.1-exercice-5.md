# Correction — Exercice 1.1 / 5 (incident de production)

## L'énoncé

Système de paiement mobile money. Le service `Transfert` expose :

```go
func (s *Service) Executer(ctx context.Context, t *Transfert) error {
    if err := s.debiter(t.Source, t.Montant); err != nil {
        return err
    }
    if err := s.crediter(t.Destination, t.Montant); err != nil {
        return err
    }
    t.Statut = "termine"
    s.notifier(t)
    return nil
}
```

L'appelant est un handler HTTP avec un timeout client de 30 s. Le client mobile
réessaie automatiquement quand il ne reçoit pas de réponse.

---

## Ce que le code ne dit pas

Avant toute analyse, quatre faits que la lecture rapide laisse passer. Ils
portent l'essentiel du problème.

1. **`ctx` est reçu et n'est passé à personne.** Ni à `debiter`, ni à
   `crediter`, ni à `notifier`. Le timeout de 30 s existe du côté du client ;
   du côté du serveur, rien ne s'arrête jamais.
2. **`t.Statut = "termine"` écrit dans une struct qui meurt avec la requête.**
   Le `*Transfert` a été désérialisé du corps HTTP ; il sera ramassé par le GC
   quelques millisecondes plus tard. Cette ligne ressemble à une écriture d'état
   et n'en est pas une.
3. **`s.notifier(t)` ne rend pas d'erreur.** Ce qu'il fait — ou ce qu'il casse —
   n'est pas dans le flot de contrôle.
4. **Le transfert n'a pas d'identité.** Rien dans `Transfert` ne distingue
   *cette* opération d'une autre opération de mêmes source, destination et
   montant.

D'où la phrase qui résume l'exercice :

> Il n'y a pas *un bug* dans cette fonction. Il y a une fonction **sans état**,
> dans un monde qui en a un.

---

## Question 1 — Tous les états

### La méthode : découper le long des points d'interruption

On n'énumère pas des états au hasard : on numérote les points où l'exécution
peut s'arrêter, puis on décrit le monde à chacun d'eux.

```go
func (s *Service) Executer(ctx context.Context, t *Transfert) error {
    // P0 — rien n'est fait
    if err := s.debiter(t.Source, t.Montant); err != nil {
        return err
    }
    // P1 — source débitée
    if err := s.crediter(t.Destination, t.Montant); err != nil {
        return err
    }
    // P2 — destination créditée
    t.Statut = "termine"
    // P3 — statut écrit... en mémoire
    s.notifier(t)
    // P4 — notification partie
    return nil
    // P5 — réponse HTTP émise, pas forcément reçue
}
```

« Interrompu » ne veut pas dire seulement « panique ». Ça veut dire : kill -9,
OOM, redéploiement, nœud perdu, coupure réseau, et aussi — le cas le plus
fréquent et le moins anticipé — **retour d'erreur normal**.

### Les états d'une exécution unique

| # | Arrêt | Source | Destination | Trace durable | Le client voit |
|---|---|---|---|---|---|
| E0 | P0 | intacte | intacte | aucune | erreur ou rien |
| E1 | P1, crash | **débitée** | intacte | **aucune** | rien |
| E2 | P1, `crediter` rend une erreur | **débitée** | intacte | aucune | une erreur |
| E3 | P2, crash | débitée | créditée | aucune | rien |
| E4 | P3, crash | débitée | créditée | aucune | rien |
| E5 | P4, `notifier` panique | débitée | créditée | aucune | **une 500** |
| E6 | P5, réponse perdue | débitée | créditée | aucune | rien |

Trois remarques sur ce tableau, et ce sont elles qui comptent.

**E2 est plus grave que E1.** E1 est un crash : c'est de la malchance. E2 est le
chemin nominal — le code *décide* de retourner une erreur en laissant le
système incohérent. L'argent a quitté la source et n'est arrivé nulle part, et
c'est le comportement écrit, testé, revu. Un bug d'inattention se corrige ; un
bug de conception se reproduit à chaque `return err` du même style.

**La colonne « trace durable » ne contient que des « aucune ».** C'est la
colonne la plus éloquente du tableau. Quel que soit l'endroit où ça casse, il
n'existe **aucun moyen, après coup, de savoir où c'est passé**. E1, E3, E4 et E6
sont indiscernables pour un opérateur qui arrive le lendemain matin. Ce n'est
pas un défaut de logging : c'est que l'état de l'opération n'a jamais existé
ailleurs que dans la pile d'appel.

**E5 est le chemin le plus vicieux.** `notifier` est un effet cosmétique — un
SMS. S'il panique, la panique remonte, le handler renvoie 500, et le client
mobile réessaie. Autrement dit : **l'échec d'un effet cosmétique déclenche le
rejeu d'un effet monétaire.** La hiérarchie de gravité du code est l'inverse de
celle du métier.

### Les états d'un rejeu

Le client réessaie. On repart à P0 avec un `*Transfert` neuf, désérialisé du
même JSON — donc `Statut` vaut `""`, pas `"termine"`.

| # | Situation | Résultat |
|---|---|---|
| R1 | rejeu après E6 | **débit ×2, crédit ×2** |
| R2 | rejeu après E1 ou E2 | **débit ×2, crédit ×1** — la moitié de l'argent n'existe plus |
| R3 | rejeu après E5 | débit ×2, crédit ×2, **deux SMS** |
| R4 | rejeu, mais le solde ne suffit plus (à cause du premier débit) | le client reçoit « solde insuffisant » **pour un transfert qui a réussi** |
| R5 | rejeu qui casse à son tour en P1 | débit ×2, crédit ×0 |

R4 mérite une seconde de plus. C'est le ticket de support typique : *« ça m'a dit
solde insuffisant, et pourtant j'ai été débité »*. Le message d'erreur est
techniquement exact et métier absurde. Quand tu liras un incident, cherche
toujours quelle vérité partielle produit un message faux.

### Les états d'une exécution concurrente

Le retry part à t = 30 s. Rien ne garantit que la première requête soit finie :
elle est justement lente, c'est pour ça qu'il y a eu timeout. Les deux
exécutions se recouvrent.

| # | Situation | Résultat |
|---|---|---|
| C1 | deux `Executer` entrelacés, `debiter` correctement verrouillé | débit ×2, crédit ×2 |
| C2 | `debiter` en lecture-modification-écriture non atomique | **une mise à jour perdue** : débit ×1, crédit ×2 |
| C3 | `notifier` asynchrone lit `t.Statut` pendant que l'autre goroutine l'écrit | course de données sur le pointeur partagé |

C2 est le pire état atteignable par ce code, et presque personne ne le liste.
Si `debiter` fait `solde := lire(); ecrire(solde - montant)` sans transaction,
deux exécutions concurrentes peuvent lire le même solde de départ : un seul
débit est appliqué, deux crédits le sont. **Le système a créé de l'argent.**
Un double débit se rembourse ; de la monnaie créée ne se retrouve pas.

C3 est l'exercice 4 qui revient : `*Transfert` traverse une frontière, quelqu'un
le retient, la fenêtre reste ouverte. « Un pointeur ne partage pas une valeur,
il ouvre une fenêtre. »

### Le décompte

Le nombre exact d'états n'a aucun intérêt. Ce qui compte, c'est sa forme :

> points d'interruption × nombre de tentatives × entrelacements possibles

C'est un produit, donc ça explose. On ne teste pas un espace d'états qu'on ne
sait pas énumérer — **on le rend petit par conception.** C'est tout l'objet de
la question 4.

## Question 2 — La séquence exacte du double débit

Alice envoie 250 000 centimes à Bob. Le crédit sort vers un autre opérateur et
prend du temps.

| t | Client mobile | Serveur | Soldes |
|---|---|---|---|
| 0,0 s | `POST /transferts` → requête **A** | A reçue | alice 1 000 000, bob 0 |
| 0,2 s | | A : `debiter(alice, 250k)` OK | **alice 750 000** |
| 0,3 s | | A : `crediter(bob)` — appel sortant, lent | |
| 30,0 s | timeout, aucune réponse | A toujours en vol | |
| 30,1 s | `POST /transferts` → requête **B**, *même payload* | B reçue | |
| 30,3 s | | B : `debiter(alice, 250k)` OK | **alice 500 000** |
| 41,0 s | | A : `crediter` OK | **bob 250 000** |
| 41,1 s | | A : `t.Statut = "termine"`, `notifier` → SMS 1, 200 OK que personne n'écoute | |
| 52,0 s | | B : `crediter` OK | **bob 500 000** |
| 52,1 s | reçoit 200 OK | B : SMS 2, 200 OK | |

Alice a perdu 500 000 pour un virement de 250 000. Bob en a reçu 500 000. Deux
SMS. Le client a reçu **une** confirmation et considère l'affaire réglée.

### Le client n'est pas fautif

Le réflexe est d'accuser le retry. Il est faux, et c'est important de savoir
pourquoi.

Le client mobile, à t = 30 s, sait une seule chose : **il n'a pas reçu de
réponse.** Il ne peut pas distinguer ces trois mondes :

- la requête n'est jamais arrivée ;
- elle est arrivée, a échoué, la réponse d'erreur s'est perdue ;
- elle est arrivée, a réussi, la réponse de succès s'est perdue.

Aucune information disponible de son côté ne les sépare. C'est le problème des
deux généraux, et il n'a pas de solution : **sur un réseau, l'émetteur ne peut
jamais savoir si c'est son message ou l'accusé de réception qui a été perdu.**
Face à ça, il n'y a que deux politiques : réessayer, et risquer le doublon ; ou
ne pas réessayer, et perdre des transferts. Le client a choisi la bonne — celle
dont l'erreur est visible et réparable.

Donc :

> Le double débit n'est pas produit par le rejeu. Il est produit par le fait que
> le rejeu soit **indiscernable d'un nouveau transfert**.

Les requêtes A et B sont identiques octet pour octet. Le serveur ne peut pas
inventer la distinction : refuser « même payload dans les 60 s » casserait le
cas parfaitement légitime de deux paiements de 1 000 F au même marchand à une
minute d'intervalle, ce qui arrive en permanence sur du mobile money.

L'ambiguïté n'est pas levable par de l'intelligence côté serveur. Elle est
levable seulement si **quelqu'un la déclare**. C'est la question 5.

## Question 3 — Cette fonction est-elle idempotente ?

Non. Mais la réponse utile est dans le « pourquoi exactement ».

### Une définition utilisable

> Une opération est idempotente quand l'**état du système** après n ≥ 1
> applications est identique à l'état après une seule.

Deux pièges dans cette définition, tous les deux déjà rencontrés :

- **« état du système », pas « valeur de retour ».** L'exercice 3 montrait une
  fonction qui rendait deux fois `100` en ayant modifié son entrée. Ici c'est
  le miroir : `Executer` peut rendre deux fois `nil` en ayant débité deux fois.
  On ne juge jamais une garantie de non-effet sur le retour.
- **L'idempotence n'est pas une propriété du code seul**, mais du couple
  *(code, état sur lequel il agit)*. La même fonction est idempotente ou non
  selon l'endroit où vit son état.

### Trois obstacles, de natures différentes

**1. L'opération est relative, pas absolue.** `debiter` fait `solde -= montant`.
Un delta dépend de l'état antérieur ; une affectation `solde = x` n'en dépend
pas. Toute opération formulée comme un delta est non idempotente *par
construction* — c'est le niveau le plus profond, aucune plomberie ne rendra `-=`
idempotent. Il faudra une garde extérieure.

**2. L'opération n'a pas d'identité.** Même avec des opérations absolues, la
fonction n'a aucun moyen de savoir que cet appel-ci est le même que le
précédent. Sans identité, « une seule fois » n'a pas de référent : **on ne peut
pas compter les occurrences de quelque chose qu'on ne sait pas nommer.**

**3. L'état de l'opération n'est pas persisté.** Supposons qu'on ajoute la garde
évidente :

```go
if t.Statut == "termine" {
    return nil // déjà fait
}
```

Elle ne garde rien. Le rejeu arrive avec un `*Transfert` fraîchement
désérialisé : `Statut` vaut `""`. La garde teste une mémoire que le rejeu n'a
jamais vue.

Ces trois obstacles sont de natures différentes — **algébrique**, **nominale**,
**temporelle** — et c'est pour ça qu'il faut les trois réponses de la question 4.

### Le piège : une affectation idempotente qui ne sert à rien

`t.Statut = "termine"` est une affectation, donc idempotente en elle-même.
L'appliquer dix fois donne le même résultat qu'une fois. Et pourtant elle
n'apporte rien.

> On ne rend pas un système idempotent en rendant idempotentes ses instructions
> une par une. L'idempotence est une propriété de la **transition**, pas de ses
> lignes.

### Un quatrième effet, qu'on oublie toujours

Même un transfert parfaitement dédupliqué enverra deux SMS si `notifier` n'est
pas conditionné. L'idempotence se raisonne **effet observable par effet
observable**, et ici il y en a quatre, qui sortent du système par quatre portes
différentes :

| Effet | Sortie | Annulable ? |
|---|---|---|
| le solde | la base | oui (transaction) |
| le statut | la base | oui (transaction) |
| le SMS | l'opérateur | **non** |
| la réponse HTTP | le réseau | **non** |

Chaque porte a besoin de sa propre réponse. Les deux dernières ne se rollbackent
pas : c'est la contrainte structurante du design.

## Question 4 — Le changement de conception

### Le renversement

Aujourd'hui, la fonction **fait** le transfert : elle lance une suite d'actions
en aveugle. Demain, elle **acquiert le droit** de le faire, et cette acquisition
est atomique. L'exécution devient la conséquence d'une transition gagnée.

Cinq mécanismes, aucun outil nouveau.

### Mécanisme 1 — l'identité vient de l'appelant

Le transfert reçoit un identifiant **fourni par le client**, stable à travers
les tentatives.

Il ne peut pas être généré par le service : un identifiant créé à l'arrivée de
la requête est différent à chaque rejeu, donc inutile. Il doit être stable *à
travers* le retry, donc produit là où naît l'intention, et régénéré uniquement
quand l'utilisateur relance volontairement.

C'est aussi une exigence sur le client, et c'est le bug classique en
production :

> **Rejouer avec une nouvelle clé n'est pas un rejeu, c'est un second virement.**

### Mécanisme 2 — réserver avant d'agir

Avant tout mouvement d'argent, une insertion sur une clé primaire :

```sql
INSERT INTO transferts (id, source, destination, montant, statut)
VALUES ($1, $2, $3, $4, 'initie');
```

Cette insertion est le seul endroit où la course se joue, et la base la tranche :
**exactement un gagnant**. Le perdant reçoit une violation de contrainte
d'unicité, qu'il n'interprète pas comme une erreur mais comme un fait —
« quelqu'un d'autre détient cette opération » — et va lire l'état enregistré
pour le renvoyer.

La contrainte d'unicité est un garde-fou de niveau ⚫ appliqué aux **données** :
deux mouvements pour un même identifiant deviennent non représentables dans le
schéma. Ce n'est plus détecté après coup, c'est impossible.

### Mécanisme 3 — une seule transition atomique

Débit, crédit et statut dans la même transaction, sous condition :

```sql
BEGIN;
  UPDATE transferts SET statut = 'termine'
   WHERE id = $1 AND statut = 'initie';
  -- 0 ligne affectée : quelqu'un d'autre a déjà réglé → on ne touche à rien

  UPDATE comptes SET solde = solde - $2 WHERE numero = $3 AND solde >= $2;
  UPDATE comptes SET solde = solde + $2 WHERE numero = $4;
COMMIT;
```

Deux propriétés distinctes, qu'il faut savoir nommer séparément :

- **l'atomicité** supprime E1, E2 et C2 : il n'existe plus d'instant où l'argent
  a quitté la source sans atteindre la destination ;
- **la condition `AND statut = 'initie'`** est un *compare-and-swap*. Le nombre
  de lignes affectées répond à la question « est-ce moi qui ai gagné ? ». C'est
  exactement la primitive de `atomic.CompareAndSwap` — la base n'est rien
  d'autre que la mémoire partagée de ton architecture.

Note au passage : `AND solde >= $2` et `CHECK (montant > 0)` relèvent du même
principe qu'au mécanisme 2 — rendre l'état interdit impossible plutôt que le
détecter.

### Mécanisme 4 — les effets non annulables sortent de la transaction

Le SMS ne se rollback pas. Donc il part **après** le commit, et seulement chez
celui qui a gagné le compare-and-swap. Et s'il échoue, il ne doit surtout pas
faire échouer le transfert — c'est l'état E5, le SMS raté qui provoque le double
débit.

> Un effet irréversible ne doit jamais être une condition de succès d'un effet
> réversible.

### Mécanisme 5 — le contexte gouverne l'acquisition, pas le règlement

`ctx` était ignoré. Le corriger naïvement — le propager partout — **empire les
choses** : annuler entre le débit et le crédit, c'est fabriquer E1 à volonté, et
le timeout de 30 s le ferait plusieurs fois par jour.

La règle : le contexte de l'appelant gouverne ce qui est **abandonnable** —
l'attente, l'acquisition, la lecture ; jamais ce qui est **engagé**. D'où
`context.WithoutCancel` autour du règlement.

C'est un point de conception, pas une astuce : *qui a le droit d'annuler quoi*
est une décision d'architecture au même titre que *qui a le droit d'écrire quoi*.

### Ce que ça ne règle pas

Une correction honnête dit ce qu'elle laisse ouvert.

- **L'état « réservé mais non réglé » existe toujours** si le process meurt
  entre l'insertion et la transaction. Mais il a changé de nature : il est
  nommé, persisté et visible, donc repris par une boucle de réconciliation.
  **On n'a pas supprimé la panne, on a supprimé l'ignorance** — et c'est
  précisément ce qui distingue un incident réparable d'un incident subi.
- **Le crédit vers un opérateur tiers ne rentre pas dans ta transaction.** Ce
  que tu commits alors n'est pas « l'argent est arrivé » mais « l'ordre est
  émis » ; le transfert devient une machine à trois états et le tiers doit à son
  tour accepter une clé d'idempotence. Le mécanisme se propage de proche en
  proche ; il ne se dilue pas.
- **Aucune technologie n'a été ajoutée.** Ni file, ni base distribuée, ni
  verrou externe. On a seulement déplacé la vérité : d'une struct en mémoire
  vers une ligne de table.

## Question 5 — Qui est responsable de l'exécution unique ?

### La question est piégée

Elle attend un nom, et la bonne réponse est une **répartition**. Mais ce n'est
pas un « ça dépend » : la répartition est contrainte, et chaque rôle n'a qu'un
seul endroit possible.

Tout tient dans une distinction que la question teste sans la nommer :
**déclarer l'unicité n'est pas la garantir.**

- On ne peut pas **déclarer** l'unicité ailleurs qu'à l'endroit où naît
  l'intention — seul lui sait si deux requêtes sont la même.
- On ne peut pas **garantir** l'unicité ailleurs qu'au point de sérialisation le
  plus bas — seul lui voit toutes les tentatives.

Ces deux exigences pointent vers des composants opposés. D'où la répartition.

### Les quatre candidats

| Rôle | Qui | Pourquoi lui, et lui seul |
|---|---|---|
| **Déclarer** l'identité de l'intention | le client mobile | seul à savoir si deux requêtes sont une intention ou deux |
| **Transporter** cette identité sans l'altérer | le handler HTTP | il traduit du HTTP vers du métier ; il ne décide rien |
| **Définir** l'unité de travail | le service | seul à savoir ce qu'est « un transfert » au sens métier, et ce qu'un rejeu doit renvoyer |
| **Faire respecter** l'unicité | la base | seul composant unique et sérialisant de l'architecture |

Le client déclare, le handler transporte, le service définit, la base arbitre.
Aucun des quatre ne peut prendre le rôle d'un autre.

### Ce qui casse à chaque mauvais placement

**Si on confie la garantie au client mobile.** C'est le composant sur lequel tu
as le moins de pouvoir : vieilles versions installées, réseau hostile,
utilisateur qui tape deux fois, application réécrite un jour par une autre
équipe. Une garantie déployée dans la poche des gens ne se corrige pas : le
correctif met des mois à se propager et les anciennes versions restent en
circulation.

> On n'implémente jamais une garantie dans un composant qu'on ne peut pas
> redéployer.

Le client reste indispensable — il *déclare* — mais une déclaration qu'on ne
vérifie pas n'est pas une garantie.

**Si on confie la garantie au handler HTTP.** C'est la tentation la plus
naturelle : une `map[ID]bool` protégée par un mutex, et ça marche parfaitement
en recette. Ça casse au premier de ces trois événements : un second pod, un
redémarrage, un load balancer qui route le retry sur une autre instance.

C'est le pire type de panne : **le code est juste, la topologie le contredit.**
Le test unitaire est vert, la recette mono-instance est verte, et la production
casse le jour du scale-out — c'est-à-dire le jour du pic de trafic, c'est-à-dire
le jour où ça coûte le plus cher.

> Une garantie qui dépend du nombre d'instances n'est pas une garantie, c'est
> une coïncidence.

**Si on confie la garantie au service sans persistance.** C'est exactement le
code de l'énoncé. Le service *croit* porter la garantie — il y a bien un champ
`Statut`, quelqu'un l'a écrit exprès — mais il l'inscrit dans une mémoire qui
meurt avec la requête. C'est la panne la plus coûteuse à diagnostiquer, parce
que le code **dit** ce qu'il ne **fait** pas : en revue, tout le monde lit
`t.Statut = "termine"` et coche mentalement la case « le statut est géré ».

**Si on confie la garantie à la base seule, sans identité déclarée.** La base ne
peut dédupliquer que ce qu'elle sait distinguer. Sans clé fournie, il ne reste
qu'une heuristique : unicité sur *(source, destination, montant, fenêtre de
temps)*. Alors tu refuses le cas légitime — deux paiements de 1 000 F au même
marchand à une minute d'intervalle, qui arrive tous les jours.

Tu as troqué un double débit contre un **débit manquant**, et l'échange est
mauvais dans les deux sens :

- un client débité deux fois appelle le support : l'incident est visible,
  compté, réparable ;
- un client dont le second paiement est silencieusement avalé **croit avoir
  payé**. Le marchand ne livre pas, la dispute arrive trois jours plus tard, et
  tu n'as aucune trace de ce qui n'a pas eu lieu.

> Entre deux bugs, préfère toujours celui qui fait du bruit.

### La règle

1. La responsabilité de **déclarer** va là où naît l'information.
2. La responsabilité de **garantir** va au point de sérialisation le plus bas —
   le seul composant que toutes les tentatives traversent.
3. Entre les deux, **tout le monde transporte sans interpréter**.

Corollaire, qui sert bien au-delà de cet exercice : chaque fois qu'un composant
intermédiaire « améliore » la donnée qu'il transporte — normalise, régénère,
complète —, il devient un endroit où la garantie peut se perdre.

Et pour finir sur ce qu'on ne peut pas acheter :

> **L'exécution exactement-une-fois n'existe pas sur un réseau.** Ce qui existe,
> c'est une livraison au-moins-une-fois plus un traitement idempotent. Le
> résultat est indiscernable d'un exactly-once — mais il s'obtient au niveau de
> l'**effet**, jamais au niveau du **transport**.

## Solution de référence

### Le schéma qui porte la garantie

```sql
CREATE TABLE transferts (
    id          TEXT PRIMARY KEY,       -- la clé d'idempotence, fournie par le client
    source      TEXT   NOT NULL,
    destination TEXT   NOT NULL,
    montant     BIGINT NOT NULL CHECK (montant > 0),   -- centimes, jamais float
    statut      TEXT   NOT NULL CHECK (statut IN ('initie', 'termine', 'echoue')),
    cree_le     TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

C'est la ligne la plus importante de toute la correction :

```sql
id TEXT PRIMARY KEY
```

Tout le reste du code n'est que la façon d'en tirer parti.

### Le service

```go
// Package transfert execute un mouvement d'argent entre deux comptes.
//
// Contrat : une Commande donnee, identifiee par son ID, produit au plus un
// mouvement, quel que soit le nombre d'appels a Executer, en sequence ou en
// parallele. Un second appel avec le meme ID ne rejoue rien : il rend le recu
// de l'execution qui a gagne.
package transfert

import (
    "context"
    "errors"
)

type (
    ID       string
    Compte   string
    Centimes int64
    Statut   string
)

const (
    StatutInitie  Statut = "initie"
    StatutTermine Statut = "termine"
)

// Commande est l'intention exprimee par l'appelant.
//
// L'ID est fourni par le client, pas genere ici : le service ne peut pas
// deviner si deux requetes identiques sont un rejeu ou deux virements
// volontaires. Seul l'emetteur de l'intention le sait.
type Commande struct {
    ID          ID
    Source      Compte
    Destination Compte
    Montant     Centimes
}

// Recu est le resultat observable d'un transfert.
type Recu struct {
    ID     ID
    Statut Statut
    Rejeu  bool // vrai si cet appel n'a produit aucun mouvement
}

var (
    ErrSansIdentite = errors.New("transfert : commande sans identite")
    ErrMontant      = errors.New("transfert : montant invalide")
    ErrConflit      = errors.New("transfert : identite deja utilisee pour une autre commande")
    ErrSolde        = errors.New("transfert : solde insuffisant")
)

// Store est le point de serialisation. Ses deux methodes sont atomiques :
// c'est la seule hypothese dont depend la garantie du service.
type Store interface {
    // Reserver insere la commande si son ID est libre et renvoie rejeu=false.
    // Si l'ID est deja pris, il n'ecrit rien et renvoie le statut enregistre
    // avec rejeu=true, ou ErrConflit si la commande enregistree differe.
    Reserver(ctx context.Context, c Commande) (statut Statut, rejeu bool, err error)

    // Regler debite, credite et passe le statut a termine, dans une seule
    // transaction, a la condition que le statut soit encore initie.
    // Si la condition n'est pas remplie, il ne fait rien et renvoie le statut
    // courant : un autre appel a deja regle ce transfert.
    Regler(ctx context.Context, id ID) (Statut, error)
}

type Notificateur interface {
    Notifier(ctx context.Context, r Recu)
}

type Service struct {
    store    Store
    notifier Notificateur
}

// Executer applique la commande au plus une fois.
//
// La commande est passee par valeur : le service ne modifie pas l'intention de
// l'appelant, et l'etat du transfert ne vit pas dans une struct en memoire mais
// dans le store, seul endroit qui survit a la requete.
func (s *Service) Executer(ctx context.Context, c Commande) (Recu, error) {
    if c.ID == "" {
        return Recu{}, ErrSansIdentite
    }
    if c.Montant <= 0 {
        return Recu{}, ErrMontant
    }

    statut, rejeu, err := s.store.Reserver(ctx, c)
    if err != nil {
        return Recu{}, err
    }

    // Le contexte de l'appelant gouverne l'acquisition, pas le reglement :
    // le timeout client de 30 s ne doit pas pouvoir annuler une transaction
    // deja engagee, sous peine de recreer l'etat incoherent qu'on supprime.
    if statut == StatutInitie {
        statut, err = s.store.Regler(context.WithoutCancel(ctx), c.ID)
        if err != nil {
            return Recu{}, err
        }
    }

    r := Recu{ID: c.ID, Statut: statut, Rejeu: rejeu}

    // La notification est hors transaction : elle n'est pas annulable. Au mieux
    // elle est au-moins-une-fois, et c'est au recepteur de dedupliquer sur
    // l'ID. Une notification perdue est un incident ; un debit perdu n'en est
    // pas un, c'en est deux.
    if s.notifier != nil && !rejeu {
        s.notifier.Notifier(ctx, r)
    }

    return r, nil
}
```

Compare cette signature à celle de l'énoncé :

```go
func (s *Service) Executer(ctx context.Context, t *Transfert) error
func (s *Service) Executer(ctx context.Context, c Commande) (Recu, error)
```

Quatre changements, tous porteurs de sens :

| Avant | Après | Ce que ça dit |
|---|---|---|
| `*Transfert` | `Commande` (valeur) | le service ne modifie pas l'intention de l'appelant |
| `Transfert` (état) | `Commande` (intention) | l'état n'est plus dans l'argument, il est dans le store |
| `error` seul | `(Recu, error)` | le résultat d'un rejeu est **observable** : `Rejeu: true` |
| implicite | `ID` obligatoire | l'identité est une entrée du contrat, pas un détail |

C'est l'exercice 4 appliqué : la signature porte le contrat, parce qu'elle est
le seul document que tous les appelants lisent.

### Le cœur du store

Le reste — l'implémentation mémoire utilisée par les tests — n'a d'intérêt que
pour ces deux méthodes, qui sont la traduction exacte du SQL plus haut :

```go
// Reserver correspond a un INSERT sur une cle primaire : il reussit une fois.
func (s *StoreMemoire) Reserver(_ context.Context, c Commande) (Statut, bool, error) {
    s.mu.Lock()
    defer s.mu.Unlock()

    if l, existe := s.lignes[c.ID]; existe {
        if l.cmd != c {
            return "", false, ErrConflit
        }
        return l.statut, true, nil
    }

    s.lignes[c.ID] = ligne{cmd: c, statut: StatutInitie}
    return StatutInitie, false, nil
}

// Regler correspond a une transaction contenant un UPDATE conditionnel :
// la condition « statut = initie » est le compare-and-swap.
func (s *StoreMemoire) Regler(_ context.Context, id ID) (Statut, error) {
    s.mu.Lock()
    defer s.mu.Unlock()

    l, existe := s.lignes[id]
    if !existe {
        return "", ErrSansIdentite
    }
    if l.statut != StatutInitie {
        return l.statut, nil // un autre appel a deja regle : ne rien faire
    }
    if s.soldes[l.cmd.Source] < l.cmd.Montant {
        return "", ErrSolde
    }

    s.soldes[l.cmd.Source] -= l.cmd.Montant
    s.Debits++ // compteurs d'observation, pour les tests
    s.soldes[l.cmd.Destination] += l.cmd.Montant
    s.Credits++

    l.statut = StatutTermine
    s.lignes[id] = l
    return StatutTermine, nil
}
```

Un avertissement à ne pas escamoter : **ce mutex ne prouve rien.** Il joue en
test le rôle que la base joue en production — sérialiser en un seul point. Dans
un service déployé en plusieurs instances, le seul mutex qui existe est celui de
la base. Un test vert ici valide la logique du service, pas la garantie du
système.

## Les tests qui verrouillent le contrat

Le contrat est une garantie de **non-effet** : on ne le teste donc jamais sur la
valeur de retour, mais en **comptant les mouvements**.

```go
// Le test central : rejouer la meme commande ne produit aucun second mouvement.
func TestRejeuNeDebitePasDeuxFois(t *testing.T) {
    s, st := nouveau()
    ctx := context.Background()

    for i := range 5 {
        r, err := s.Executer(ctx, cmd())
        if err != nil {
            t.Fatalf("appel %d : %v", i, err)
        }
        if (i > 0) != r.Rejeu {
            t.Fatalf("appel %d : rejeu=%v", i, r.Rejeu)
        }
    }

    if st.Debits != 1 || st.Credits != 1 {
        t.Fatalf("mouvements : %d debits, %d credits ; attendu 1 et 1", st.Debits, st.Credits)
    }
    if got := st.Solde(alice); got != 750_000 {
        t.Fatalf("solde alice = %d ; attendu 750000", got)
    }
}

// Le cas reel : le retry part avant que la premiere requete ait fini.
// A lancer avec -race.
func TestRejeuConcurrent(t *testing.T) {
    s, st := nouveau()

    const n = 50
    var wg sync.WaitGroup
    wg.Add(n)
    for range n {
        go func() {
            defer wg.Done()
            if _, err := s.Executer(context.Background(), cmd()); err != nil {
                t.Error(err)
            }
        }()
    }
    wg.Wait()

    if st.Debits != 1 || st.Credits != 1 {
        t.Fatalf("mouvements : %d debits, %d credits ; attendu 1 et 1", st.Debits, st.Credits)
    }
}

// Deux virements identiques et volontaires doivent passer : la deduplication
// porte sur l'identite declaree, jamais sur le contenu.
func TestDeuxVirementsIdentiquesMaisDistincts(t *testing.T) {
    s, st := nouveau()

    a, b := cmd(), cmd()
    b.ID = "req-43"

    for _, c := range []Commande{a, b} {
        if _, err := s.Executer(context.Background(), c); err != nil {
            t.Fatal(err)
        }
    }

    if st.Debits != 2 {
        t.Fatalf("%d debits ; attendu 2", st.Debits)
    }
}

// Le contexte annule apres la reservation ne doit pas laisser un transfert
// a moitie fait : le reglement est protege par WithoutCancel.
func TestContexteAnnuleNeCoupePasLeReglement(t *testing.T) {
    s, st := nouveau()
    ctx, annuler := context.WithCancel(context.Background())
    annuler()

    r, err := s.Executer(ctx, cmd())
    if err != nil {
        t.Fatal(err)
    }
    if r.Statut != StatutTermine {
        t.Fatalf("statut %q ; attendu termine", r.Statut)
    }
    if st.Debits != 1 || st.Credits != 1 {
        t.Fatalf("%d debits, %d credits ; attendu 1 et 1", st.Debits, st.Credits)
    }
}
```

Le troisième test est celui que personne n'écrit, et c'est le plus important des
quatre. Sans lui, la « correction » la plus simple — dédupliquer sur le contenu
de la requête — passerait les trois autres au vert tout en cassant un cas
métier parfaitement légitime. **Un test qui n'interdit que le bug attrapé laisse
passer le sur-correctif.**

Et `-race` n'est pas optionnel ici : le bug d'origine est un bug de
concurrence.

## La hiérarchie des garde-fous, appliquée

| Niveau | Ce que ça donne dans cet exercice |
|---|---|
| 🟠 revue de code | « pensez à vérifier le statut avant de débiter » — tenu tant que l'auteur est là |
| 🟡 test | un test de rejeu : **détecte** une régression, n'empêche rien |
| 🔴 compilateur | la signature `Executer(ctx, Commande) (Recu, error)` : impossible d'appeler sans passer une `Commande`, impossible d'ignorer le `Recu` par distraction |
| ⚫ non représentable | `id TEXT PRIMARY KEY` : deux mouvements pour un même identifiant **ne peuvent pas exister** dans le schéma |

Une nuance qui vaut le détour. Dans l'exercice 4, le garde-fou ⚫ était dans le
**système de types**. Ici, il est dans le **schéma de la base** — et le
compilateur ne peut rien pour nous : il ne sait pas vérifier qu'un `ID` est non
vide, d'où le contrôle à l'exécution en tête de fonction.

Le principe n'a pas changé de nature, il a changé de support :

> Le garde-fou se place là où **vit l'état**. Si l'état est en mémoire, c'est le
> système de types. S'il est en base, c'est le schéma. S'il est chez un tiers,
> c'est le protocole.

## À retenir

1. **Une fonction sans état, dans un monde qui en a un.** Le bug n'est pas une
   ligne fautive : c'est que l'état de l'opération n'existe nulle part de
   durable.
2. **Un retour d'erreur est un point d'interruption.** `return err` au milieu
   d'une suite d'effets laisse le système incohérent par le chemin nominal —
   c'est plus grave qu'un crash, parce que c'est écrit, testé et revu.
3. **On énumère les états en numérotant les points d'interruption**, puis en
   croisant avec le nombre de tentatives et les entrelacements. C'est un
   produit : il explose, donc on le réduit par conception.
4. **Un effet cosmétique ne doit jamais pouvoir faire échouer un effet
   monétaire.** Le SMS qui panique déclenche le rejeu qui double le débit.
5. **Le double débit n'est pas causé par le rejeu, mais par le fait que le rejeu
   soit indiscernable d'une nouvelle intention.**
6. **Sur un réseau, l'émetteur ne peut jamais savoir si c'est son message ou
   l'accusé de réception qui s'est perdu.** Réessayer est la bonne politique ;
   c'est au serveur de rendre le rejeu inoffensif.
7. **L'idempotence se juge sur l'état, jamais sur la valeur de retour**, et elle
   est une propriété du couple *(code, état sur lequel il agit)*.
8. **Rendre chaque instruction idempotente ne rend pas la transition
   idempotente.** `t.Statut = "termine"` est une affectation parfaitement
   idempotente et parfaitement inutile.
9. **Sans identité, « une seule fois » n'a pas de référent** : on ne compte pas
   les occurrences de ce qu'on ne sait pas nommer.
10. **Le contexte de l'appelant gouverne ce qui est abandonnable, jamais ce qui
    est engagé.** Propager `ctx` partout sans réfléchir fabrique l'état
    incohérent au lieu de l'éviter.
11. **Déclarer l'unicité n'est pas la garantir.** Le client déclare, le handler
    transporte, le service définit l'unité de travail, la base arbitre.
12. **Une garantie qui dépend du nombre d'instances est une coïncidence** ; et
    on n'implémente jamais une garantie dans un composant qu'on ne peut pas
    redéployer.
13. **Entre deux bugs, préfère celui qui fait du bruit.** Un double débit se
    réclame ; un paiement silencieusement avalé se découvre trois jours plus
    tard, sans trace.
14. **L'exactly-once n'existe pas sur le transport.** Il s'obtient au niveau de
    l'effet : livraison au-moins-une-fois plus traitement idempotent.
