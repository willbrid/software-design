# Correction — Exercice 1.3 / 3 (refactoring)

## L'énoncé

Pas de logique : une struct de configuration à treize champs, passée **par
valeur** à sept modules, et trois recherches dans le dépôt.

| Recherche | Modules concernés |
|---|---|
| `FROM commandes` | `commande`, `facturation`, `export`, `support`, `statistiques` |
| `"commande:"` (préfixe Redis) | `commande`, `facturation`, `statistiques` |
| `time.Now()` | 23 fichiers dans 9 modules |

L'exercice ne demande pas de lire du code. Il demande de lire une **struct** et
trois `grep` — et c'est volontaire : ces trois sources d'information sont
celles qui révèlent les couplages qu'aucun graphe d'imports ne montre.

## Question 1 — Un demandeur par champ

| Champ | Demandeur | Rythme |
|---|---|---|
| `DSNPostgres` | l'exploitation | par environnement |
| `MaxConnexions` | l'exploitation | rare, et chargé de conséquences (exercice 5) |
| `URLRedis` | l'exploitation | par environnement |
| `TTLCache` | l'exploitation | au réglage de performance |
| `TauxTVA` | **l'État** | à chaque loi de finances |
| `DeviseAffichage` | le produit | à l'ouverture d'un pays |
| `SeuilRuptureStock` | la logistique | quelques fois par an |
| `GabaritEmail` | le marketing | **toutes les semaines** |
| `ExpediteurEmail` | le marketing, la conformité | rare |
| `URLPrestatairePSP` | le commerce | à chaque changement de prestataire |
| `DelaiPSP` | l'infrastructure | rare, et crucial (exercice 1.2 / 5) |
| `CheminRapports` | le contrôle interne | rare |
| `FuseauHoraire` | le produit | à l'ouverture d'un pays |

Sept demandeurs, treize champs, une struct.

### La découpe

```go
// Package base : la connexion. Demandeur : l'exploitation.
package base

type Config struct {
    DSN           string
    MaxConnexions int
}
```

```go
// Package cache : le cache. Demandeur : l'exploitation.
package cache

import "time"

type Config struct {
    URL string
    TTL time.Duration
}
```

```go
// Package affichage : la presentation. Demandeur : le produit.
package affichage

type Config struct {
    Devise        string
    FuseauHoraire string
}
```

```go
// Package stock : les seuils. Demandeur : la logistique.
package stock

type Config struct {
    SeuilRupture int
}
```

```go
// Package notif : les messages. Demandeur : le marketing.
package notif

type Config struct {
    Gabarit    string
    Expediteur string
}
```

```go
// Package psp : le prestataire de paiement. Demandeur : le commerce et
// l'infrastructure.
package psp

import "time"

type Config struct {
    URL   string
    Delai time.Duration // obligatoire, jamais herite : incident 1.2 / 5
}
```

```go
// Package rapport : la destination des rapports. Demandeur : le controle
// interne.
package rapport

type Config struct {
    Chemin string
}
```

Et le treizième champ, qui n'est pas une configuration du tout :

```go
// Package fiscalite : les taux. Demandeur : l'Etat.
//
// Et ce n'est pas une configuration : un taux de TVA a une date d'effet, et
// il faut pouvoir refacturer janvier au taux de janvier. C'est une donnee.
package fiscalite

import "time"

type Taux struct {
    Pourcentage int64
    EffetDu     time.Time
}
```

**Huit configurations**, chacune dans le paquet qui la consomme, chacune avec
un demandeur unique.

Deux remarques sur la découpe.

**`TauxTVA` n'est pas une configuration.** Une configuration décrit
l'environnement où tourne le programme ; un taux de TVA décrit le monde, il a
une date d'effet, et il faut pouvoir refacturer janvier au taux de janvier. Mis
dans un fichier de configuration, il est écrasé à chaque changement et l'ancien
est perdu. C'est une **donnée**, elle est historisée, elle est en base.

> Si tu dois un jour répondre à la question « quelle valeur avait ce paramètre
> le 12 mars ? », ce n'est pas une configuration.

**`FuseauHoraire` est allé dans `affichage`**, pas dans un paquet commun. Un
fuseau sert à présenter une date à un humain. Si quelque chose d'autre en a
besoin — un rapport, par exemple —, il déclare le sien : deux consommateurs
peuvent légitimement vouloir deux fuseaux, et les forcer à partager le même
champ est une décision qu'on prend sans le savoir.

### Celle qui changera un mardi après-midi

`notif.Config`, et plus précisément `GabaritEmail`.

C'est le champ dont le demandeur a le cycle le plus court et les enjeux les
plus faibles. Dans la struct unique, cette volatilité contaminait les douze
autres champs : une struct change au rythme de son champ le plus agité.

> Une struct de configuration change au rythme de son champ le plus volatile.
> Le `GabaritEmail` du marketing imposait son tempo au `DSNPostgres` de
> l'exploitation.

Et c'est le fil direct vers l'incident de l'exercice 1.2 / 5. Même cause, autre
costume.

## Question 2 — Le passage par valeur

Non, ça ne la rend pas inoffensive. Il faut être précis sur ce qu'il protège.

**Ce que le passage par valeur protège :** un module ne peut pas modifier la
configuration des autres. `cfg.TauxTVA = 20` dans un module ne se propage pas.
C'est réel, et ça élimine le degré 5.

**Ce qu'il ne protège pas**, et c'est tout le reste :

1. **Le couplage au moment de la construction.** Les treize champs doivent être
   renseignés au même endroit, au même instant, par le même code. Donc le
   module de démarrage dépend des sept demandeurs. Ajouter un champ pour le
   marketing modifie le fichier que l'exploitation relit.
2. **Le couplage par structure, degré 2.** Renomme `TauxTVA`, et les sept
   modules cessent de compiler — y compris les six qui ne l'utilisent pas,
   s'ils nomment le type.
3. **Ce que chaque module *peut voir*.** Le module de notification reçoit le
   DSN de la base. Il n'en a aucun usage, et il peut l'écrire dans un journal.
   Ce n'est pas théorique : c'est l'un des chemins les plus fréquents de fuite
   de secret.
4. **La copie est superficielle.** `Config` n'a ici que des types scalaires. Le
   jour où quelqu'un ajoute `Entetes map[string]string` ou
   `PaysActifs []string`, le passage par valeur partage le tableau sous-jacent,
   et le degré 5 revient sans que personne ne change une signature. C'est
   exactement la leçon 1.1.

> Le passage par valeur empêche d'écrire chez l'autre. Il n'empêche ni de lire
> ce qui ne nous regarde pas, ni de dépendre de la forme de sa struct, ni de
> partager un tableau le jour où quelqu'un en ajoute un.

## Question 3 — Cinq modules lisent `FROM commandes`

### Le degré, et qui casse

**Degré 2, couplage par structure** — et dans sa variante la pire, celle que le
compilateur ne voit pas.

Renomme une colonne, et les cinq modules continuent de compiler. Ils cassent à
l'exécution, au premier `SELECT`, chacun à son rythme : `commande` tout de
suite parce qu'il est sur le chemin critique, `export` à la fin du mois,
`statistiques` quand quelqu'un ouvrira le tableau de bord.

> Un schéma de base est une interface publique avec zéro vérification de
> compatibilité. C'est le seul contrat de ton système qu'aucun outil ne
> vérifie.

### La règle de propriété

**Un seul écrivain, N lecteurs, et les lecteurs ne lisent pas la table.**

- `commande` est le **propriétaire** : il est le seul paquet où apparaissent
  `INSERT`, `UPDATE`, `DELETE` et `SELECT` sur `commandes`.
- Les quatre autres passent par une interface que **chacun déclare pour lui**,
  avec la question qu'il pose :

```go
// dans facturation
type Commandes interface {
    ALivrer(ctx context.Context, periode Periode) ([]Facturable, error)
}

// dans statistiques
type Commandes interface {
    Comptage(ctx context.Context, jour time.Time) (Agregat, error)
}
```

Deux interfaces différentes, dans deux paquets différents, pour la même table.
C'est voulu : `facturation` et `statistiques` ne posent pas la même question, et
leur donner le même type d'accès les coupleraient l'un à l'autre.

Le garde-fou qui tient la règle n'est pas un commentaire. C'est un test de
structure, comme celui de la correction 1.2 / 2 :

```sh
grep -rn 'FROM commandes\|INTO commandes\|UPDATE commandes' --include='*.go' . \
  | grep -v '^./commande/'
```

Zéro ligne attendue. En CI, 🟡. Et 🔴 si la base accorde les droits
d'écriture sur `commandes` à un rôle que seul le module `commande` utilise —
ce qui est possible, et presque jamais fait.

### Ce que ça coûte, chiffré

Il faut le dire, sinon la règle est un slogan.

1. **Les requêtes transverses deviennent pénibles.** Une statistique qui
   joignait `commandes` et `factures` en un `SELECT` devient deux appels et une
   jointure en mémoire. C'est plus lent, parfois beaucoup : une jointure que
   PostgreSQL fait en 5 ms peut coûter 200 ms en deux allers-retours plus une
   boucle Go.
2. **Un changement qui concerne deux modules demande deux ouvertures.** Si
   `facturation` a besoin d'un champ de plus, il faut modifier son interface
   **et** l'implémentation chez `commande`.
3. **Le propriétaire devient un goulot d'étranglement humain.** Toute évolution
   de la table passe par une équipe.
4. **Le `support` est le cas douloureux.** Un script de rattrapage a
   légitimement besoin d'écrire. La règle doit prévoir une porte de sortie
   documentée et auditée — c'est la conclusion de la correction 1.2 / 4, et
   sans elle la contrainte sera retirée un soir de crise.

Mon arbitrage : la règle en vaut le prix pour `commande` ↔ `facturation` ↔
`support`, parce que ce sont des chemins d'écriture. Pour `statistiques`, qui
ne lit que de l'agrégat et tolère de la fraîcheur approximative, la bonne
réponse est différente : **une réplique de lecture et une vue dédiée**. On ne
paie pas la même frontière partout.

## Question 4 — Trois modules construisent des clés `commande:`

### Le jour où `statistiques` change son format de clé

Rien ne casse. Les anciennes clés ne sont plus lues, elles expirent — ou pas,
si personne n'a mis de TTL. Le cache grossit avec des entrées orphelines que
plus aucun code ne peut nommer.

Symptôme typique : une consommation mémoire Redis qui monte lentement pendant
trois mois, puis une éviction, puis une dégradation de latence sur un chemin
sans rapport.

### Le jour où `facturation` invalide par motif `commande:*`

Là, c'est immédiat. Elle supprime **aussi** les clés de `commande` et de
`statistiques`, qui ne lui appartiennent pas. Elles seront recalculées, donc
rien ne casse fonctionnellement : il y a juste une rafale de requêtes vers la
base, au pire moment, puisqu'on invalide précisément quand il y a de
l'activité.

Et surtout : **personne ne saura pourquoi.** La trace montrera une charge base
anormale ; rien ne montrera qu'un module en a effacé les clés d'un autre.

> Un espace de clés en chaînes de caractères est un espace de noms **global,
> non typé et sans propriétaire**. C'est la même chose qu'une variable
> globale, avec le réseau en plus.

La correction est celle de l'exercice 1.2 / 3 : la clé devient un **type**,
construit par le module propriétaire, et personne ne peut invalider par motif
ce qu'il n'a pas construit.

## Question 5 — `time.Now()` dans 23 fichiers

Le critère, en une phrase :

> `time.Now()` est acceptable là où l'instant présent **entre** dans le
> système, et nulle part ailleurs.

Ça donne une règle applicable sans lire la logique :

**Acceptable :**

- au point d'entrée : le `main`, le *handler* HTTP qui horodate une requête, le
  déclencheur du cron ;
- dans la journalisation et les métriques, qui mesurent le temps réel par
  définition ;
- dans un adaptateur qui lit ou écrit une date vers l'extérieur.

**Inacceptable :**

- dans toute fonction qui porte une **règle** — une expiration, un préavis, une
  échéance, une date d'effet, un calcul de prorata. Celles-là reçoivent une
  date en paramètre ou une horloge en champ.

Et le test mécanique, qui ne demande aucun jugement :

```sh
grep -rn 'time\.Now()' --include='*.go' . | grep -v '_test.go'
```

Pour chaque ligne : *est-ce que je peux écrire un test de cette fonction qui
vérifie son comportement à une date donnée, sans attendre ?* Si non, l'appel
est au mauvais endroit.

La version encore plus simple, et c'est celle que j'appliquerais : **un paquet
qui contient une règle ne doit pas importer `time` pour autre chose que le
type `time.Time` et `time.Duration`.** Vérifiable par un test de structure,
comme pour les imports de la correction 1.2 / 2.

> L'horloge est la dépendance la plus répandue et la moins déclarée du métier.
> Elle ne se voit pas dans un graphe d'imports, parce que `time` est dans la
> bibliothèque standard et a l'air inoffensif.

## Question 6 — Lesquels apparaîtraient dans un graphe d'imports

| Couplage | Visible dans le graphe d'imports ? |
|---|---|
| la struct `Config` partagée par sept modules | **oui** — c'est le seul |
| cinq modules lisant la table `commandes` | non |
| trois modules construisant des clés `commande:` | non |
| `time.Now()` dans 23 fichiers | non |
| les droits d'écriture en base | non |
| le fait que tout se déploie ensemble | non |

Un sur six. Et celui qui est visible est **le moins grave** des six : un
renommage de champ dans `Config` casse à la compilation, donc il coûte dix
minutes.

> Les outils d'analyse d'architecture mesurent ce que le langage sait
> exprimer. Tout ce qui se partage en dehors du langage — un schéma, un espace
> de clés, une horloge, un artefact de déploiement, un rôle en base — leur est
> invisible. Et c'est précisément là que sont les couplages qui coûtent cher.

Ce n'est pas un argument contre ces outils ; c'est un argument contre
l'idée qu'un graphe propre vaut une architecture propre. La leçon 1.3 l'a
montré avec un contre-exemple à sept couplages et un graphe parfait.

La conséquence pratique : **les trois `grep` de cet exercice valent mieux que
n'importe quel outil d'analyse statique pour cette question-là.** Nom de table,
préfixe de clé, `time.Now()`. Trois commandes, dix minutes, et la carte des
couplages invisibles d'un dépôt que tu ne connais pas.

1. Un demandeur par champ de configuration. Deux demandeurs, deux
   configurations.
2. Une struct de configuration change au rythme de son champ le plus volatile.
3. Si tu peux avoir à répondre « quelle valeur avait ce paramètre le 12
   mars ? », ce n'est pas une configuration, c'est une donnée historisée.
4. Le passage par valeur empêche d'écrire chez l'autre. Il n'empêche ni de lire
   ce qui ne nous regarde pas, ni de dépendre de la forme de la struct, ni de
   partager un tableau dès que quelqu'un en ajoute un.
5. Un schéma de base est une interface publique sans aucune vérification de
   compatibilité : le seul contrat du système qu'aucun outil ne vérifie.
6. Un écrivain, N lecteurs, et chaque lecteur déclare sa propre question.
7. On ne paie pas la même frontière partout : une réplique de lecture est
   parfois la bonne réponse là où une interface serait la mauvaise.
8. Un espace de clés en chaînes est une variable globale, avec le réseau en
   plus.
9. `time.Now()` est acceptable là où l'instant présent entre dans le système,
   et nulle part ailleurs.
10. Un graphe d'imports propre ne vaut pas une architecture propre. Trois
    `grep` — nom de table, préfixe de clé, `time.Now()` — en disent plus.
