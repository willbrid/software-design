# Correction — Exercice 1.2 / 3 (refactoring)

## L'énoncé en deux lignes

Un service de facturation SaaS, trois ans d'existence. Une struct à six
champs — `db`, `cache`, `smtp`, `facturier`, `log`, `cfg` — et huit méthodes :
`CreerAbonnement`, `ResilierAbonnement`, `CalculerQuota`, `ConsommerQuota`,
`GenererFacture`, `EnvoyerFacture`, `ExporterComptabilite`, `PurgerCache`.

Et dix commits. L'énoncé ne te donne pas le code des huit méthodes, et c'est
volontaire : **on va découper sans le lire.**

## La méthode : lire un historique comme une matrice de co-changement

Les trois premiers détecteurs de la leçon — le « et », les demandeurs, le
test — demandent de lire le code et de connaître l'entreprise. Le quatrième
est le seul **empirique** : l'historique dit ce qui a changé ensemble, et il
ne se trompe pas sur le passé.

La question n'est pas *« ces deux méthodes se ressemblent-elles ? »* mais :

> Combien de fois ces deux-là ont-elles changé dans le même commit ?

Voici le dépouillement de l'énoncé. Pour chaque paire, le nombre de commits
communs :

| Paire | Commits communs | Lesquels |
|---|---|---|
| `CalculerQuota` + `ConsommerQuota` | **3** | 1, 2, 3 |
| `GenererFacture` + `ExporterComptabilite` | **3** | 4, 5, 10 |
| `CreerAbonnement` + `ResilierAbonnement` | **2** | 6, 7 |
| `GenererFacture` + `EnvoyerFacture` | **0** | — |
| `CalculerQuota` + `GenererFacture` | **0** | — |
| toute paire franchissant un groupe | **0** | — |

La partition est nette : trois paires soudées, une méthode seule, et aucun
commit qui franchit une frontière. `PurgerCache` est le seul à traverser tout,
et il a droit à sa propre question.

Dans la vraie vie tu n'auras jamais un historique aussi propre. Voici de quoi
le dépouiller pour de vrai, sur n'importe quel dépôt :

```sh
#!/bin/sh
# cochange.sh <motif-A> <motif-B> — compte les commits qui touchent A seul,
# B seul, et les deux. Sur une fenetre d'un an.
git log --since='12 months ago' --format='@%H' --name-only |
awk -v A="$1" -v B="$2" '
  /^@/   { fin(); a=0; b=0; next }
  NF==0  { next }
  $0 ~ A { a=1 }
  $0 ~ B { b=1 }
  END    { fin(); printf "A seul : %d\nB seul : %d\nles deux : %d\n", sa, sb, sab }
  function fin() { if (a && b) sab++; else if (a) sa++; else if (b) sb++ }
'
```

Il travaille au fichier, donc il ne sert qu'après une première découpe — pour
vérifier qu'elle tient. Au niveau de la méthode dans un seul fichier, il n'y a
pas d'outil : il y a `git log -L`, et il y a toi.

Garde les trois nombres qu'il affiche en tête. On s'en servira à l'exercice 5
pour répondre à *« à partir de quand séparer vaut-il son coût ? »*

## Question 1 — Les frontières que l'historique dicte

**Quatre modules.**

| Module | Méthodes | Raison de changer | Demandeur | Commits |
|---|---|---|---|---|
| `quota` | `CalculerQuota`, `ConsommerQuota` | les paliers et les règles de consommation | l'équipe produit | 1, 2, 3 |
| `comptable` | `GenererFacture`, `ExporterComptabilite` | la réglementation fiscale et les règles comptables | l'État, le cabinet comptable | 4, 5, 10 |
| `abonnement` | `CreerAbonnement`, `ResilierAbonnement` | les conditions contractuelles | le juridique, le commerce | 6, 7 |
| `envoi` | `EnvoyerFacture` | le canal de remise et la politique de relance | le recouvrement, l'infrastructure | 8, 9 |

Remarque d'où viennent les **noms**. Pas des méthodes : des demandeurs. Le
module qui contient `GenererFacture` ne s'appelle pas `facture`, il s'appelle
`comptable`, parce que la personne qui le fait changer est comptable. C'est
une petite discipline qui rapporte beaucoup : un module nommé d'après son
patron ne peut pas accueillir n'importe quoi.

## Question 2 — La découpe que les noms suggèrent, et que l'historique dément

### Laquelle

Celle-ci, et tout le monde la propose en réunion :

```
facture : GenererFacture, EnvoyerFacture
```

Les deux méthodes parlent de factures. Elles se suivent dans le temps : on
génère, puis on envoie. Elles se suivent probablement dans le fichier.

L'historique dit :

- `GenererFacture` a changé 3 fois, et **3 fois sur 3** avec
  `ExporterComptabilite` ;
- `EnvoyerFacture` a changé 2 fois, et **0 fois sur 2** avec
  `GenererFacture`.

Ce n'est pas un signal faible. C'est 100 % contre 0 %.

### Laquelle croire — et pourquoi

L'historique. Mais pas par autorité : parce qu'en regardant **pourquoi**, il
devient évident.

- Commits 4, 5, 10 : TVA 19,25 % → 20 %, arrondi comptable sur les avoirs,
  export au format FEC. Trois demandes fiscales.
- Commits 8, 9 : migration Mailgun → Sendgrid, relance automatique à J+7. Deux
  demandes de canal et de recouvrement.

Deux mondes. Ils n'ont en commun qu'un substantif.

> Le mot « facture » est un faux ami : il désigne un **document** pour le
> comptable et un **message** pour le recouvrement. La proximité des noms est
> linguistique ; la co-occurrence dans l'historique est causale.

Et le cas de `EnvoyerFacture` est le plus parlant du lot : seul dans ses deux
commits, jamais accompagné. Une méthode qui change toujours seule est un
module à elle seule — c'est le signal le plus propre qu'un historique puisse
donner.

### Les cinq réserves qu'il faut savoir énoncer

Si tu as répondu « l'historique » sans réserve, la réponse est juste et le
raisonnement incomplet. Un historique est une mesure, et une mesure a des
limites :

1. **L'échantillon est minuscule.** 3 observations sur 3 n'est pas un
   pourcentage, c'est une anecdote avec une bonne tête. Sur dix commits, on
   forme une hypothèse ; on ne conclut pas.
2. **Le biais de sélection.** On ne voit que les commits qui ont touché *ce
   fichier*. Un changement de quota qui a surtout touché le frontend est
   invisible ici — et il dirait peut-être que la vraie frontière passe
   ailleurs.
3. **Le silence est ambigu.** Une méthode qui ne change jamais est soit une
   abstraction stable et réussie, soit du code mort. Deux significations
   opposées, exactement le même signal.
4. **L'historique décrit le passé.** Il est aveugle à un changement de
   stratégie produit — c'est tout l'objet de la question 5.
5. **La qualité du signal est la qualité des commits.** Une équipe qui livre
   `feat: sprint 12` avec quarante fichiers produit un historique où tout
   co-change avec tout, donc un historique qui ne dit rien.

Cette dernière réserve est aussi un argument : **tes commits sont la mesure de
ton couplage. Commits atomiques, mesure utilisable.** C'est probablement la
raison la plus concrète qu'on puisse donner à quelqu'un de bien découper ses
commits — elle n'a rien à voir avec l'élégance du journal.

Alors la bonne méthode complète : l'historique fournit l'hypothèse, puis on va
**demander aux auteurs des commits pourquoi**. Dix minutes de conversation
confirment ou démolissent ce que trois heures de lecture de code n'auraient
pas tranché.

## Question 3 — `PurgerCache`, 5 commits sur 10

### Ce que le chiffre révèle

`PurgerCache` apparaît dans les commits 1, 3, 5, 6 et 10 : au moins un dans
chacun des trois groupes.

Une méthode qui co-change avec tout le monde a exactement la même signature
statistique qu'une méthode qui appartient à tout le monde — c'est-à-dire à
personne.

> Un module qui change avec tous les autres n'est pas un module. C'est une
> **dépendance**.

### Est-ce une responsabilité ? Non.

« Purger le cache » n'est pas une décision que quelqu'un, dans l'entreprise,
peut exiger de changer. C'est une **conséquence** d'une écriture. Ce n'est pas
un sujet, c'est un effet.

La cause est visible dans l'interface donnée par l'énoncé :

```go
type Cache interface {
    Get(cle string) ([]byte, bool)
    Set(cle string, v []byte)
    Supprimer(motif string)
}
```

`Supprimer(motif string)`. L'invalidation se fait par **motif de chaîne**, dans
un espace de clés global, partagé et non typé. Donc :

- chaque module doit connaître les conventions de nommage des clés — au moins
  les siennes, mais par une porte commune ;
- chaque fois que quelqu'un ajoute un chemin d'écriture, il doit **se
  souvenir** d'invalider ;
- rien, nulle part, ne le lui rappelle.

Voilà pourquoi la méthode apparaît dans la moitié des commits : elle est
l'endroit où l'on répare, à la main, à chaque fois, un invariant que le code
ne maintient pas.

> Un invariant maintenu par la mémoire humaine est un bug programmé. La seule
> question est la date.

### Ce que je propose

**Supprimer `PurgerCache` de la surface publique.** Le cache devient un détail
d'implémentation *à l'intérieur* de chaque module qui lit, derrière la propre
interface de lecture de ce module — un décorateur.

Alors l'invalidation se produit sur le même chemin de code que l'écriture,
dans le même module, et l'oublier devient une erreur **locale et testable** au
lieu d'une erreur à distance.

Trois précisions, parce que ce n'est pas une baguette magique :

- **Ce qui reste partagé.** L'instance Redis est toujours une infrastructure
  commune. Ce qu'on a supprimé, ce n'est pas le partage du cache, c'est le
  partage de son **protocole d'invalidation**. C'est ça qui couplait.
- **L'alternative honnête : le TTL.** Renoncer à l'invalidation explicite et
  accepter une fenêtre d'incohérence bornée. Le compromis est net :

  > Un cache à TTL a des bugs **bornés dans le temps**. Un cache à
  > invalidation explicite a des bugs **non bornés en nombre**.

  Pour un quota, le TTL est presque toujours le bon choix ; pour un solde de
  facture, non. Cette décision est une décision d'exploitation, et elle a un
  propriétaire.
- **Si la purge doit rester partagée**, alors au minimum : la clé devient un
  **type**, pas une chaîne, et seul le module propriétaire peut en
  construire. On passe de ⚪ (une convention de nommage dans un wiki) à 🔴 (le
  compilateur refuse qu'un module invalide les clés d'un autre).

## Question 4 — Les six champs

| Champ | Où il va |
|---|---|
| `db *sql.DB` | `quota`, `comptable`, `abonnement` — mais **jamais comme `*sql.DB`** : chacun déclare son interface étroite |
| `cache Cache` | nulle part publiquement : détail interne de chaque module qui lit |
| `smtp Expediteur` | `envoi`, seul |
| `facturier *http.Client` | `comptable` — avec un délai explicite, pour les raisons de l'exercice 5 |
| `log *slog.Logger` | tous |
| `cfg Config` | **à démonter** |

### Un champ peut-il apparaître dans deux modules ? Oui, et il faut savoir ce qu'on partage

Trois modules utiliseront la même connexion à la base. Ce n'est pas un
couplage :

> Partager une **connexion** est gratuit. Partager un **schéma** est un
> couplage.

Le test est simple et sans appel : si `quota` lit la table `factures`, la
frontière est un mensonge, quel que soit le nom des paquets. C'est pour ça que
chaque module déclare son interface étroite plutôt que de recevoir un
`*sql.DB` : ce qu'on passe n'est pas « la base », c'est « les deux opérations
dont j'ai besoin sur mes tables ».

Le cas de `log` est différent et vaut d'être nommé : un champ présent dans
**tous** les modules n'est pas une dépendance métier, c'est une **capacité
d'infrastructure**. Il ne compte pas dans le décompte des patrons. Mais si un
jour il entre dans un test — « vérifier qu'on journalise bien tel
événement » — alors il vient de devenir une dépendance métier, et son
demandeur est l'équipe d'astreinte.

### `cfg` est la découverte la plus utile de l'exercice

```go
type Config struct {
    SeuilQuota int
    TauxTVA    int64
}
```

`SeuilQuota` part dans `quota`, demandé par le produit. `TauxTVA` part dans
`comptable`, demandé par l'État. Deux champs, deux destinations, deux
demandeurs, et zéro raison de voyager ensemble.

> Un struct de configuration dont les champs partent dans des modules
> différents n'a jamais été une configuration. C'était un sac.

Et un sac de configuration est le pire des couplages, parce qu'il est
invisible : il ne crée aucun appel, aucun import, rien à voir dans un graphe
de dépendances. Il se contente de forcer deux modules à être construits par le
même code, avec le même fichier, au même moment.

Au passage : `TauxTVA` ne devrait pas non plus être une constante compilée. Le
commit 4 — « TVA 19,25 % → 20 % » — a été un déploiement. Un taux de TVA est
une **donnée** avec une date d'effet, et il faut pouvoir refacturer janvier à
l'ancien taux en février.

### Un module peut-il n'avoir aucun champ ? Oui — et c'est celui qu'on veut

```go
package argent

func TVA(ht Montant, tauxCentiemesDePourcent int64) Montant
```

Aucun champ, aucune interface, aucune dépendance. Et c'est exactement là que
vivait le bug du commit 5 : « fix: arrondi comptable sur les avoirs ».

Un arrondi sur un montant négatif. Trois lignes d'arithmétique entière,
noyées au milieu de `GenererFacture`, entre un appel à la base et un appel au
prestataire — donc impossibles à tester sans tout démarrer, donc jamais
testées, donc fausses pendant un temps indéterminé, donc fausses **au bilan**.

> La liste des champs d'un struct est la liste de ses patrons. Zéro champ,
> zéro patron, et un test qui tourne en deux millisecondes.

## Question 5 — Le changement qui rendrait ma découpe fausse

Trois candidats, du moins grave au plus grave.

**Un : « le quota consommé doit figurer sur la facture. »** Ça crée une
dépendance `comptable → quota`. Ce n'est **pas** un problème : une dépendance
n'est pas une fusion. Il faut seulement qu'elle soit orientée du volatil vers
le stable — et c'est le cas, un quota consommé est un fait, pas une règle.

**Deux : « quotas et TVA pilotés par une même table réglementaire par pays. »**
Là, un nouveau demandeur apparaît — « conformité pays » — et il traverse
`quota` et `comptable`. Chacune de ses demandes ouvrira deux modules. La vraie
frontière serait devenue `territoire`, et ma découpe serait à refaire.

**Trois, le vrai danger : « on passe au paiement à l'usage. »** Le quota n'est
plus une limite, il devient l'assiette de facturation. Produit et comptabilité
deviennent le même sujet, avec le même demandeur. Ma partition la plus solide —
trois paires nettes, zéro commit traversant — s'effondre en un module.

### Ce qu'il faut en conclure

> Une découpe est une **hypothèse sur l'avenir**. Elle est donc falsifiable, et
> une hypothèse qu'on ne retestera jamais n'a aucune valeur.

Le critère pour savoir qu'on s'est trompé est le même qui a servi à découper :
**recalculer la matrice de co-changement dans six mois.** Si une paire qui
franchit une frontière arrive en tête du classement, la frontière a bougé — et
elle a bougé avant qu'on s'en aperçoive.

C'est symétrique, et c'est ce qui en fait un vrai critère : la même mesure qui
justifie de séparer justifie de **refusionner**. Peu d'équipes refusionnent. La
plupart gardent des frontières dont la raison d'être a disparu, parce que
défaire une frontière ressemble à un aveu.

## Solution de référence

### Le module sans aucun champ

```go
// Package argent porte l'arithmetique monetaire et l'arrondi comptable.
//
// Raison de changer : la regle d'arrondi exigee par la comptabilite.
//
// Aucun champ, aucune dependance, aucune interface : c'est le seul module du
// lot qui se teste sans rien brancher. Les commits 4, 5 et 10 de l'historique
// le touchaient tous les trois, noyes dans GenererFacture.
package argent

// Montant est un entier exprime dans la plus petite unite de la devise :
// jamais un float pour de l'argent. Pour une devise sans subdivision en
// usage, comme le FCFA, une unite vaut un franc.
type Montant int64

// TVA applique un taux exprime en centiemes de pourcent (1925 = 19,25 %),
// arrondi au centime le plus proche, moitie a l'oppose de zero.
//
// Le traitement du signe est la raison d'etre de cette fonction : un avoir est
// un montant negatif, et un arrondi « moitie vers le haut » sur un negatif
// arrondit vers zero. C'est exactement le bug du commit 5.
func TVA(ht Montant, tauxCentiemesDePourcent int64) Montant {
    n := int64(ht) * tauxCentiemesDePourcent
    if n < 0 {
        return Montant((n - 5000) / 10000)
    }
    return Montant((n + 5000) / 10000)
}
```

```go
package argent

import "testing"

func TestTVA(t *testing.T) {
    cas := []struct {
        nom  string
        ht   Montant
        taux int64
        want Montant
    }{
        {"19,25 % exact", 10000, 1925, 1925},
        {"20 % exact", 10000, 2000, 2000},
        {"arrondi au centime superieur", 333, 1925, 64}, // 64,1025
        {"arrondi au centime inferieur", 100, 1925, 19}, // 19,25
        {"pile a la moitie", 200, 2500, 50},
        {"avoir : symetrique du positif", -333, 1925, -64},
        {"avoir pile a la moitie", -200, 2500, -50},
        {"zero", 0, 2000, 0},
    }
    for _, c := range cas {
        t.Run(c.nom, func(t *testing.T) {
            if got := TVA(c.ht, c.taux); got != c.want {
                t.Errorf("TVA(%d, %d) = %d, attendu %d", c.ht, c.taux, got, c.want)
            }
        })
    }
}

// La propriete que la comptabilite exige : un avoir annule exactement la
// facture qu'il corrige. Un arrondi asymetrique casse ca, et la difference
// est d'un centime par ligne — invisible en test unitaire naif, visible au
// bilan annuel.
func TestAvoirAnnuleLaFacture(t *testing.T) {
    for ht := Montant(1); ht <= 10000; ht++ {
        if TVA(ht, 1925)+TVA(-ht, 1925) != 0 {
            t.Fatalf("ht=%d : TVA non symetrique", ht)
        }
    }
}
```

Le second test est celui qui compte. Il ne vérifie pas une valeur, il vérifie
une **propriété** que la comptabilité exige : un avoir annule exactement la
facture qu'il corrige. Un arrondi asymétrique la casse, d'un centime par
ligne — invisible dans un test à trois cas, visible au bilan annuel.

Ce test ne pouvait pas exister avant. Pas parce que personne n'y avait pensé :
parce que la fonction n'existait pas.

### Les quatre modules

```go
// Package quota decide ce qu'un abonnement a le droit de consommer.
//
// Raison de changer : les paliers et les regles de consommation.
// Demandeur : l'equipe produit.
// Commits de l'historique : 1, 2, 3.
package quota

import "context"

// Compteurs est ce dont ce module a besoin de la base : deux operations, pas
// un *sql.DB. La frontiere n'est pas la connexion, c'est le schema.
type Compteurs interface {
    Consommation(ctx context.Context, abonnement string) (int64, error)
    Ajouter(ctx context.Context, abonnement string, n int64) error
}

// Paliers lit la grille des limites. Separe des compteurs parce que les
// paliers sont une donnee de configuration, pas un etat applicatif.
type Paliers interface {
    Limite(ctx context.Context, abonnement, pays string) (int64, error)
}

type Service struct {
    compteurs Compteurs
    paliers   Paliers
}

func NewService(c Compteurs, p Paliers) *Service {
    return &Service{compteurs: c, paliers: p}
}
```

```go
// Package comptable produit les documents comptables : factures et exports.
//
// Raison de changer : la reglementation fiscale et les regles de la
// comptabilite. Demandeurs : l'Etat, le cabinet comptable.
// Commits de l'historique : 4, 5, 10.
//
// Le nom de ce module est le resultat le moins intuitif de l'exercice :
// l'historique dit que generer une facture et l'exporter changent toujours
// ensemble, et que les envoyer n'a rien a voir.
package comptable

import (
    "context"

    "exemple/facturation/argent"
)

type Lignes interface {
    LignesDuMois(ctx context.Context, abonnement string, mois string) ([]Ligne, error)
}

type Ligne struct {
    Libelle string
    HT      argent.Montant
}

// Bareme porte les taux. C'est une donnee, pas une constante compilee : le
// commit 4 (« TVA 19,25 % -> 20 % ») ne doit pas etre un changement de code.
type Bareme interface {
    Taux(ctx context.Context, pays string, mois string) (int64, error)
}

type Service struct {
    lignes Lignes
    bareme Bareme
}

func NewService(l Lignes, b Bareme) *Service {
    return &Service{lignes: l, bareme: b}
}
```

```go
// Package abonnement porte le cycle de vie d'un abonnement.
//
// Raison de changer : les conditions contractuelles — preavis, date d'effet,
// renouvellement. Demandeur : le juridique et le commerce.
// Commits de l'historique : 6, 7.
package abonnement

import (
    "context"
    "time"
)

type Depot interface {
    Enregistrer(ctx context.Context, a Abonnement) error
    Lire(ctx context.Context, id string) (Abonnement, error)
}

type Abonnement struct {
    ID       string
    Debut    time.Time
    FinEffet time.Time
    Resiliee bool
    Preavis  time.Duration
}

type Service struct {
    depot   Depot
    horloge func() time.Time
}

func NewService(d Depot, horloge func() time.Time) *Service {
    return &Service{depot: d, horloge: horloge}
}
```

```go
// Package envoi remet une facture au client et relance.
//
// Raison de changer : le canal de remise et la politique de relance.
// Demandeur : l'equipe recouvrement et l'infrastructure.
// Commits de l'historique : 8, 9 — et aucun autre. Ce module n'a jamais
// change en meme temps que la generation des factures.
package envoi

import (
    "context"
    "time"
)

type Expediteur interface {
    Envoyer(ctx context.Context, dest, sujet, corps string) error
}

// Echeancier porte les relances. Il a besoin de savoir qu'une facture existe
// et si elle est payee, pas comment elle a ete calculee.
type Echeancier interface {
    ImpayeesDepuis(ctx context.Context, d time.Duration) ([]string, error)
    NoterRelance(ctx context.Context, facture string, le time.Time) error
}

type Service struct {
    expediteur Expediteur
    echeancier Echeancier
    relance    time.Duration
}

func NewService(e Expediteur, ech Echeancier, relance time.Duration) *Service {
    return &Service{expediteur: e, echeancier: ech, relance: relance}
}
```

Ce qui est publié ici, ce sont les **façades** : les types, les contrats, les
champs. Pas les corps de méthodes — ils n'étaient pas dans l'énoncé, et c'est
le point de l'exercice. On a découpé un service de facturation sans lire une
seule ligne de son implémentation, à partir de dix lignes de `git log`.

Note enfin le commentaire en tête de chaque fichier. Trois lignes : la raison
de changer, le demandeur, les commits de l'historique qui en témoignent. C'est
la trace de la décision, elle vit à côté du code, et elle sera lue par le
prochain qui se demandera pourquoi `GenererFacture` n'est pas rangé avec
`EnvoyerFacture`.

## À retenir

1. On peut découper un module sans lire son code. Dix lignes d'historique
   suffisent à former l'hypothèse.
2. La question n'est pas « ces deux méthodes se ressemblent-elles » mais
   « combien de fois ont-elles changé dans le même commit ».
3. Nomme les modules d'après leurs demandeurs, pas d'après leurs méthodes. Un
   module nommé d'après son patron n'accueille pas n'importe quoi.
4. Un nom commun n'est pas une responsabilité commune. « Facture » est un
   document pour le comptable et un message pour le recouvrement.
5. Une méthode qui change toujours seule est un module à elle seule : c'est le
   signal le plus propre d'un historique.
6. Une méthode qui change avec tout le monde n'est pas un module, c'est une
   dépendance.
7. Un invariant maintenu par la mémoire humaine est un bug programmé.
8. Partager une connexion est gratuit, partager un schéma est un couplage.
9. Un struct de configuration dont les champs partent dans des modules
   différents n'était pas une configuration, c'était un sac — et c'est le
   couplage le plus invisible qui existe.
10. Zéro champ, zéro patron. C'est le module qu'on cherche, et c'est là que
    vivent les bugs qu'on ne teste jamais.
11. Tes commits sont la mesure de ton couplage. Commits atomiques, mesure
    utilisable.
12. Une découpe est une hypothèse falsifiable. La même mesure qui justifie de
    séparer justifie de refusionner — et presque personne ne refusionne.
