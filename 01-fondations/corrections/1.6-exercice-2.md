## 1. La date civile : le type qu'on n'avait pas demandé

Avant la règle, un type. Et il faut justifier pourquoi, parce que personne ne le
demandait.

Une date de prélèvement n'est **pas un instant**. Le 5 du mois est le 5 du mois
à Douala comme à Paris. Utiliser `time.Time` pour ça, c'est transporter une
heure et un fuseau dont personne n'a besoin, et découvrir six mois plus tard
qu'un prélèvement a sauté un jour parce que le serveur est passé en UTC et que
`2026-03-05T00:00:00+01:00` est le 4 mars à 23 h.

```go
// Package day defines the civil date.
//
// A debit date is not an instant: it is a calendar day.
// The 5th of the month is the 5th in Douala as in Paris. Using time.Time for
// that means carrying a time and a time zone nobody needs, and
// find out six months later that a debit skipped a day because the
// server switched to UTC.
package day

import (
    "errors"
    "fmt"
    "time"
)

var ErrNoSuchDate = errors.New("day: non-existent date")

// Day is a civil date, without time or time zone.
type Day struct {
    a int
    m time.Month
    j int
}

// New refuses what does not exist. 31 February is not a day on
// which we can debit.
func New(year int, month time.Month, dayOfMonth int) (Day, error) {
    t := time.Date(year, month, dayOfMonth, 0, 0, 0, 0, time.UTC)
    if t.Year() != year || t.Month() != month || t.Day() != dayOfMonth {
        return Day{}, fmt.Errorf("%w: %d-%02d-%02d", ErrNoSuchDate, year, month, dayOfMonth)
    }
    return Day{a: year, m: month, j: dayOfMonth}, nil
}

// MustNew panics if the date does not exist. For literals written
// in the code: a wrong date written by hand is a programming bug,
// not input data.
func MustNew(year int, month time.Month, dayOfMonth int) Day {
    j, err := New(year, month, dayOfMonth)
    if err != nil {
        panic(err)
    }
    return j
}

// Plus returns the day moved by n days. Months and years take care of
// by themselves, and so do leap years.
func (j Day) Plus(n int) Day {
    t := j.instant().AddDate(0, 0, n)
    return Day{a: t.Year(), m: t.Month(), j: t.Day()}
}

// Weekday returns the day of the week.
func (j Day) Weekday() time.Weekday { return j.instant().Weekday() }

// Year is needed by the calendar, which is organized by year.
func (j Day) Year() int { return j.a }

// Before orders two days.
func (j Day) Before(other Day) bool { return j.instant().Before(other.instant()) }

// IsZero says whether the day is the zero Day, the one no constructor returns.
func (j Day) IsZero() bool { return j == Day{} }

func (j Day) String() string {
    if j.IsZero() {
        return "zero day"
    }
    return fmt.Sprintf("%04d-%02d-%02d", j.a, int(j.m), j.j)
}

// instant is the only place in the program where a civil date becomes an
// instant, and it is always at midnight UTC. Unexported: nobody else
// needs to do this conversion, so nobody else can do it
// wrong.
func (j Day) instant() time.Time {
    return time.Date(j.a, j.m, j.j, 0, 0, 0, 0, time.UTC)
}
```

Trois décisions à relever.

**`New` refuse ce qui n'existe pas.** C'est le ⚫ de la question 4, et on y
revient plus bas. `day.New(2026, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2ftime.February, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f30)` rend une erreur ; il
n'existe aucun `Day` du 30 février dans tout le programme.

**`instant` n'est pas exportée.** C'est la seule conversion date civile →
instant du programme, elle est toujours en UTC à minuit, et personne d'autre ne
peut la faire de travers. La leçon 1.4, appliquée à une unité de mesure.

**`Plus` ne connaît ni les mois ni les années bissextiles** — ou plutôt, elle
les connaît toute seule, et c'est le point : plus aucun code du programme n'a à
les connaître. Le test le vérifie sur quatre cas, dont un 29 février.

### Le test du ⚫

Sans lui, la garantie *« un `Day` existe toujours dans le calendrier »* n'est
qu'une phrase de commentaire :

```go
// TestNonExistentDatesAreRefused: it is the ⚫ test. Without it, the
// guarantee "a Day always exists in the calendar" is only a sentence
// comment.
func TestNonExistentDatesAreRefused(t *testing.T) {
    tc := []struct {
        year  int
        month time.Month
        day   int
    }{
        {2026, time.February, 30},
        {2026, time.February, 29}, // 2026 is not a leap year
        {2026, time.April, 31},
        {2026, time.January, 0},
        {2026, time.January, 32},
        {2026, time.Month(13), 1},
        {2026, time.Month(0), 1},
    }

    for _, c := range tc {
        if _, err := day.New(c.year, c.month, c.day); !errors.Is(err, day.ErrNoSuchDate) {
            t.Errorf("New(%d, %d, %d) = (_, %v), want ErrNoSuchDate",
                c.year, c.month, c.day, err)
        }
    }
}

func TestTheLeapTwentyNinthOfFebruaryExists(t *testing.T) {
    if _, err := day.New(2024, time.February, 29); err != nil {
        t.Fatalf("2024-02-29 refused: %v", err)
    }
}
```

Et un point de méthode souvent raté : `time.Month(13)` et le jour `0` sont dans
le tableau. Un constructeur qui valide le jour du mois mais pas le mois est un
constructeur qui donne une fausse impression de sûreté.

## 2. Le contrat du calendrier, et la clause qui change tout

```go
// Package calendar defines the contract of a holiday calendar. It
// holds no implementation and no data.
package calendar

import (
    "errors"

    "example/debits/day"
)

// ErrUnknownYear: the calendar does not cover this year.
//
// It is the clause that matters. A calendar that does not know 2027 must
// say so. If it answers "not a holiday", it answers wrong with confidence, and a
// debit leaves on 1 January.
var ErrUnknownYear = errors.New("calendar: year not covered")

// Calendar says which days are holidays.
type Calendar interface {
    // Holiday says whether this day is a holiday.
    //
    // GUARANTEED: the answer is stable. Two calls on the same day return the
    // same result, and the call is safe for concurrent use.
    //
    // WHAT STAYS TRUE ON FAILURE: a year not covered returns
    // ErrUnknownYear and NEVER false. The boolean returned with an error has
    // no meaning.
    Holiday(j day.Day) (bool, error)
}
```

Lis la signature deux fois :

```
Holiday(j SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fjour.Day) SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f(bool, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2ferror)
```

Un débutant écrirait `Holiday(j) SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fbool`. C'est plus simple, c'est plus agréable à
appeler, et c'est **faux** — pour une raison qui n'a rien à voir avec le style :

> Un calendrier qui ne connaît pas 2027 n'a aucune façon de le dire s'il ne rend
> qu'un booléen. Il répondra « pas férié » sur le 1er janvier 2027, et il le
> dira **sur le même ton** que lorsqu'il sait.

C'est la leçon 1.4 — `(nil, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2ffalse)` qui fusionne « absent » et « cassé » — et la
leçon 1.5 — la clause *« ce qui reste vrai en cas d'échec »*. Les deux se
rejoignent sur une signature de quatre mots.

## 3. Le test de contrat, et ses deux étages

Le premier étage est celui que tout le monde écrit : un férié est férié, un jour
ordinaire ne l'est pas, la réponse est stable, et l'appel est sûr en
concurrence.

Le second est celui que personne n'écrit :

```go
// CheckOutsideCoverage is the contract test nobody writes.
// It does not ask the calendar to know 2027. It asks it to KNOW
// that it does not know 2027. The difference between the two is a debit
// that leaves on 1 January.
func CheckOutsideCoverage(t *testing.T, make Make) {
    t.Helper()

    t.Run("a year not covered is announced, not guessed", func(t *testing.T) {
        c := make(t)

        _, err := c.Holiday(outsideYear)
        if !errors.Is(err, calendar.ErrUnknownYear) {
            t.Fatalf("Holiday(%s) = (_, %v), want ErrUnknownYear."+
                " Answering \"not a holiday\" for an unknown year is asserting"+
                " what we do not know", outsideYear, err)
        }
    })
}
```

Il ne demande pas au calendrier de **connaître** 2027. Il lui demande de
**savoir qu'il ne connaît pas** 2027. La différence entre les deux est un
prélèvement qui part un 1er janvier.

Et là arrive le résultat le plus intéressant de tout l'exercice. **Le défaut
n'était pas dans le code. Il était dans le format du fichier.**

Un fichier qui liste des dates ne sait pas distinguer *« 2027 n'a aucun
férié »* de *« je ne connais pas 2027 »*. L'information n'y est pas. Aucune
correction du code ne pouvait la faire apparaître.

```go
// Package calendarfile reads holidays from a file.
//
// Format, one directive per line:
//
//    # years 2026 2027       the years this file covers
//    2026-01-01              a holiday
//
// The first directive exists because of the contract. A file that lists
// dates cannot tell "2027 has no holiday" from "I do not know
// 2027". The contract requires this distinction, so the format had to change.
// It is the clearest case of this chapter: a clause nobody writes has
// ended up spreading all the way to the data format.
package calendarfile

import (
    "fmt"
    "os"
    "strconv"
    "strings"
    "time"

    "example/debits/calendar"
    "example/debits/day"
)

type Calendar struct {
    years    map[int]bool
    holidays map[day.Day]bool
}

func Load(path string) (*Calendar, error) {
    content, err := os.ReadFile(path)
    if err != nil {
        return nil, err
    }

    c := &Calendar{years: make(map[int]bool), holidays: make(map[day.Day]bool)}
    for number, line := range strings.Split(string(content), "\n") {
        line = strings.TrimSpace(line)
        if line == "" {
            continue
        }
        if err := c.readLine(line); err != nil {
            return nil, fmt.Errorf("%s line %d: %w", path, number+1, err)
        }
    }

    if len(c.years) == 0 {
        return nil, fmt.Errorf("%s: no \"# years\" directive:"+
            " a calendar that does not say what it covers cannot keep its contract", path)
    }
    // A holiday outside the declared years is an inconsistency of the file, not
    // data to ignore. We refuse it at load time, once, rather than
    // answering wrong at each call.
    for f := range c.holidays {
        if !c.years[f.Year()] {
            return nil, fmt.Errorf("%s: holiday %s is outside the declared years", path, f)
        }
    }
    return c, nil
}
```

> Une clause de contrat que personne n'écrit a fini par se propager jusqu'au
> **format des données**. C'est le cas le plus net de ce chapitre : un test de
> contrat n'est pas une vérification après coup, c'est une contrainte de
> conception qui remonte.

Et une décision secondaire, prise au même moment : un férié hors des années
déclarées fait **échouer le chargement**. On refuse l'incohérence une fois, au
démarrage, plutôt que de répondre de travers à chaque appel. C'est la leçon 1.5 —
analyser plutôt que valider — appliquée à un fichier de configuration.

## 4. Ce que le test de contrat ne peut pas vérifier

C'était une question explicite de l'énoncé, et c'est la partie que presque tout
le monde escamote. Cinq choses, et il faut les nommer une par une :

| Ce qui échappe au contrat | Pourquoi | Où ça se vérifie alors |
|---|---|---|
| **la justesse des données** | le contrat vérifie la *forme* de la réponse, jamais la *vérité* du contenu. Un calendrier qui déclare le 14 juillet férié au Cameroun passe tout le contrat | une relecture humaine, une source de référence |
| **le format du fichier** | l'autre implémentation n'a pas de fichier | un test d'implémentation |
| **la latence et le coût** | la fabrique ne dit rien du temps de réponse | un test d'implémentation, un budget |
| **le rechargement** | si le fichier change pendant l'exécution, que se passe-t-il ? La question n'existe pas pour le calendrier figé | un test d'implémentation |
| **le fichier corrompu en cours de lecture** | il faudrait pouvoir provoquer la panne, et ce moyen n'est pas dans l'interface | une couture ouverte exprès, comme le `Panne` de la leçon |

Les quatre dernières lignes ont un point commun : elles appartiennent à l'étage
**implémentation**. Voilà à quoi il ressemble, et noter qu'aucun de ces tests
n'aurait de sens pour l'autre implémentation :

```go

// The tests that follow are IMPLEMENTATION tests. They have no business
// in the contract: they are about the file format, which the other
// implementation does not have. It is exactly the boundary between the two levels.
func TestLoadingRefusesAFileThatDoesNotSayWhatItCovers(t *testing.T) {

        "without directive":     "2026-01-01\n",
        "empty directive":       "# years\n2026-01-01\n",
        "unreadable year":       "# years two-thousand-twenty-six\n",
        "holiday outside years": "# years 2026\n2027-01-01\n",
        "non-existent date":     "# years 2026\n2026-02-31\n",
        "unreadable date":       "# years 2026\n01/01/2026\n",

    for name, content := range tc {
        t.Run(name, func(t *testing.T) {
            path := filepath.Join(t.TempDir(), "holidays.txt")

                t.Fatalf("write: %v", err)
            }
            if _, err := calendarfile.Load(path); err == nil {
                t.Fatal("loaded without error: the file would be used as is")
            }
        })
    }
}

func TestACoveredYearWithoutHolidaysIsNotAnUnknownYear(t *testing.T) {
    path := filepath.Join(t.TempDir(), "holidays.txt")
    if err := os.WriteFile(path, []byte("# years 2026 2027\n2026-01-01\n"), 0o600); err != nil {

    }
```

> La frontière entre les deux étages n'est pas une question de goût : elle est
> **déductible**. Un test qui n'a pas de sens pour toutes les implémentations
> n'appartient pas au contrat.

## 5. La règle

```go
// Package debit decides what to do with a rejected direct debit.
//
// It reads nothing, writes nothing, does not read the time. The rejection day is
// an argument; the calendar is an argument; the decision is a value.
package debit

import (
    "errors"
    "fmt"
    "time"

    "example/debits/calendar"
    "example/debits/day"
)

const (
    // MinDelay is the number of days to wait after a rejection before
    // retry.
    MinDelay = 4
    // MaxRejections is the number of rejections beyond which we stop trying.
    MaxRejections = 3
    // horizon bounds the search for the next business day. Three weeks of
    // consecutive holidays do not exist; if we find them, it is the
    // calendar that is wrong, and an infinite loop would be the worst way to
    // learn it.
    horizon = 21
)

var (
    // ErrNegativeRejections: a negative number of rejections is a mistake of the
    // the caller.
    ErrNegativeRejections = errors.New("debit: negative number of rejections")
    // ErrZeroDay: the rejection day was not built.
    ErrZeroDay = errors.New("debit: zero rejection day")
    // ErrNoBusinessDay: no business day in the next three weeks.
    // It is a calendar to check, not a business case.
    ErrNoBusinessDay = errors.New("debit: no business day within the horizon")
)

// Next is the kind of decision.
type Next int

const (
    // Retry: we present the debit again on a given date.
    Retry Next = iota + 1
    // Collection: we stop, the file changes hands.
    Collection
)

// Decision is what to do next. Its fields are private, and it is the most
// important point of the file: there is no Decision "collection on
// 12 March". The two outcomes do not carry the same information, so they
// cannot be read the same way.
type Decision struct {
    next Next
    when day.Day
}

// Retry returns the date of the next attempt, and false if the decision
// is not a retry. The caller cannot read the date without having
// checks the kind of decision: it is the same mechanism as the value
// (result, ok) of lesson 1.4, and it forbids the same mistake.
func (d Decision) Retry() (day.Day, bool) {
    if d.next != Retry {
        return day.Day{}, false
    }
    return d.when, true
}

// IsCollection says whether the file goes to collection.
func (d Decision) IsCollection() bool { return d.next == Collection }

func (d Decision) String() string {
    if d.next == Collection {
        return "collection"
    }
    return "retry on " + d.when.String()
}

// Decide returns what to do after a rejection.
//
// GUARANTEED
//
//    Beyond MaxRejections rejections, the decision is collection, and it
//    carries no date.
//    Otherwise, the decision is a retry on a business day, at least MinDelay
//    days after the rejection. Never a Saturday, never a Sunday, never a day
//    the calendar declares a holiday.
//
// WHAT STAYS TRUE ON FAILURE
//
//    The decision returned with an error is the zero decision. No retry
//    is never decided on the basis of a calendar that failed: if the
//    calendar does not know, we do not decide.
//
// NOT GUARANTEED
//
//    That the returned date is a day when the client's bank accepts
//    debits. The calendar of national holidays is not the calendar
//    of bank value dates.
func Decide(rejectedOn day.Day, totalRejections int, c calendar.Calendar) (Decision, error) {
    if totalRejections < 0 {
        return Decision{}, fmt.Errorf("%w: %d", ErrNegativeRejections, totalRejections)
    }
    if rejectedOn.IsZero() {
        return Decision{}, ErrZeroDay
    }
    if totalRejections >= MaxRejections {
        return Decision{next: Collection}, nil
    }

    candidate := rejectedOn.Plus(MinDelay)
    for attempt := 0; attempt < horizon; attempt++ {
        business, err := isBusinessDay(candidate, c)
        if err != nil {
            // The calendar does not know. We do not guess in its place.
            return Decision{}, err
        }
        if business {
            return Decision{next: Retry, when: candidate}, nil
        }
        candidate = candidate.Plus(1)
    }
    return Decision{}, fmt.Errorf("%w: from %s", ErrNoBusinessDay, rejectedOn.Plus(MinDelay))
}

func isBusinessDay(j day.Day, c calendar.Calendar) (bool, error) {
    switch j.Weekday() {
    case time.Saturday, time.Sunday:
        return false, nil
    }
    holiday, err := c.Holiday(j)
    if err != nil {
        return false, err
    }
    return !holiday, nil
}
```

Les deux issues — réessai et recouvrement — **ne portent pas les mêmes
informations**. Un recouvrement n'a pas de date. Avec une structure à champs
publics, `Decision{Next: SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fCollection, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fQuand: SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2funJour}` serait constructible, et
un appelant distrait prélèverait à cette date.

Avec le couple `(day, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fbool)`, l'appelant **ne peut pas** lire la date sans
avoir vérifié la nature de la décision. C'est le mécanisme exact de la leçon 1.4,
et il interdit la même faute.

Le test qui le garde :

```go
// TestACollectionCarriesNoDate guards the type's decision: the two
// outcomes do not carry the same information.

        t.Fatalf("Decide: %v", err)

        t.Fatal("want a collection")
    }
    if when, ok := d.Retry(); ok {
        t.Fatalf("Retry() returned %s: the caller could debit on that date", when)
    }

```

### La clause d'échec, et le test qui la garde

```go
// TestIfTheCalendarDoesNotKnowWeDoNotDecide guards the clause "WHAT STAYS TRUE
// ON FAILURE". It is the test that sets this rule apart from a rule that
// will debit on 1 January.
func TestIfTheCalendarDoesNotKnowWeDoNotDecide(t *testing.T) {
    // A calendar that covers only 2025.
    cal := calendarfixed.New([]int{2025}, nil)

```

Ce test est le seul qui sépare cette règle d'une règle qui prélèvera un
1er janvier. Trois assertions, et chacune compte :

- l'erreur est bien celle du calendrier, remontée telle quelle ;
- **aucune date de réessai n'est rendue** avec l'erreur ;
- **aucun recouvrement n'est décidé** sur une erreur de calendrier — parce que
  décider le recouvrement parce qu'on n'a pas su lire un calendrier serait la
  pire des conduites possibles.

### L'horizon, et pourquoi ce n'est pas une boucle

```
horizon SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f= SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f21
```

Vingt-et-un jours fériés consécutifs n'existent pas. Si on les rencontre, c'est
le calendrier qui est faux — et une boucle infinie serait la pire façon de
l'apprendre. Le test le vérifie avec quarante jours fériés d'affilée.

C'est une habitude à prendre : **toute recherche qui avance jusqu'à trouver doit
avoir une borne, et le dépassement de la borne est une erreur distincte**, pas
un cas métier.

```go
// TestTheRuleHasNoMeansToActOnTheWorld completes the previous one with what the
// graph, for its part, can see very well, provided it is read at the right
// granularite.
//
// The version published in chapter 1.2 asked "go list -deps", that is

//
// It fails here, and the message is misleading: "debit depends on os".
// It is true, and it does not matter. The chain is:
//
//    debit -> fmt -> os
//
// fmt imports os to write to standard output. Forbidding os in the
// transitive closure is therefore to forbid fmt.Errorf, which nobody
// wants, and what nobody will understand when reading the failure.
//
// The right granularity is not the same for the two questions:
//
//   - "does this module hold a means to act?" is read on the
//     DIRECT imports. A package does not gain the ability to open a socket because
//     one of its providers can; it gains it by importing.
//   - "does this module depend on a module it should not know?" is
//     read on the transitive closure, but restricted to the project's code, where
//     there can be no false positive.
func TestTheRuleHasNoMeansToActOnTheWorld(t *testing.T) {
    forbidden := map[string]bool{
        "os": true, "os/exec": true, "net": true, "net/http": true,
        "net/smtp": true, "database/sql": true, "log": true, "log/slog": true,
    }
    pkgs := []string{"example/debits/debit", "example/debits/day"}

    for _, p := range pkgs {

            }
        }

func TestTheRuleKnowsNoImplementation(t *testing.T) {
    allowed := map[string]bool{
        "example/debits/debit":    true,
        "example/debits/calendar": true,
        "example/debits/day":      true,
    }

    out, err := exec.Command("go", "list", "-deps", "example/debits/debit").Output()
    if err != nil {

    }

        if !strings.HasPrefix(l, "example/debits/") {
            continue
        }
        if !allowed[l] {
            t.Errorf("debit depends on %q, which is not in the allowed list", l)

func directImports(t *testing.T, pkg string) []string {
    t.Helper()
    out, err := exec.Command("go", "list", "-f", "{{join .Imports \"\\n\"}}", pkg).Output()
    if err != nil {
        t.Fatalf("go list %s: %v", pkg, err)
    }
    var imports []string
    for _, l := range strings.Split(string(out), "\n") {
        if l = strings.TrimSpace(l); l != "" {
            imports = append(imports, l)
        }
    }
    if len(imports) == 0 {
        t.Fatalf("%s: no import read, the test would check nothing", pkg)
    }
    return imports
}
```

### Les deux survivantes

L'énoncé demandait de ne pas cacher les survivantes. Je suis allé en chercher,
et j'en ai trouvé deux.

**S1 — `horizon` 21 → 20.** Aucun test ne tombe.

Pourquoi : le seul test qui touche l'horizon utilise quarante jours fériés
consécutifs, donc il échoue avec 21 comme avec 20. La valeur exacte n'est
gardée par rien.

Que faire : **rien.** C'est le bon choix, et il faut savoir le défendre. La
valeur 21 n'est pas une règle métier : c'est une borne de sûreté dont seule
l'existence compte. Écrire un test qui vérifie que la borne vaut exactement 21,
ce serait écrire un test miroir — il casserait le jour où quelqu'un met 30, sans
qu'aucun comportement attendu n'ait changé.

> Une modification qui survit sur une constante de sûreté n'appelle pas un test.
> Elle confirme que la constante est un détail d'implémentation, et c'est une
> information.

**S2 — le calendrier est interrogé *avant* le week-end.** Aucun test ne tombe.

Pourquoi : un samedi férié n'est pas ouvré dans les deux ordres. Le résultat est
identique ; seul le **nombre d'appels au calendrier** change — et il augmente de
40 % environ, puisque deux jours sur sept sont des week-ends.

Que faire : **pas de test sur le nombre d'appels.** Ce serait exactement le test
miroir de la leçon. La différence est un **coût**, pas un comportement. Si ce
coût devient réel — un calendrier qui interroge un service distant —, alors il
mérite un test d'implémentation avec un budget chiffré, de la forme *« moins de
N appels pour une décision »*. Et à ce moment-là, le test aura un demandeur :
l'astreinte.

> Une modification survivante qui ne change que le coût désigne une décision de
> performance non documentée. On l'écrit dans un commentaire, et on la teste le
> jour où quelqu'un paie pour elle.

Les deux survivantes ont donc la même morale, et c'est l'inverse de celle qu'on
attend :

> **Toutes les modifications survivantes n'appellent pas un test de plus.**
> Elles appellent une question : *qu'est-ce que cette ligne décide vraiment ?*
> Les trois réponses possibles sont : ajouter un test, supprimer la ligne, ou
> rendre l'état inconstruisible. La leçon en a montré une de chaque.

## 8. Ce que ça ne règle pas

**`NON SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fGARANTI` est dans le contrat, et c'est une vraie limite.** Le calendrier
des fériés nationaux n'est pas le calendrier des jours de valeur bancaires. La
date rendue est un jour ouvré ; ce n'est pas forcément un jour où la banque du
client accepte les prélèvements. La règle le dit au lieu de le laisser croire.

**Le compteur de rejets n'est pas protégé.** `Decide(rejectedOn, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2f2, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fcal)` est
appelable avec n'importe quel entier. Le vrai ⚫ serait un type `Rejets` avec un
constructeur, ou mieux : un `Dossier` qui porte son propre compteur et une
méthode `Rejeter`. Je ne l'ai pas fait, parce que le compteur vient de la base
et que le gain est faible comparé au type `Day` — mais c'est un arbitrage, pas
une omission, et il devient faux dès qu'un deuxième appelant apparaît.

**L'horizon ne distingue pas deux causes.** `ErrNoBusinessDay` peut signifier
« le calendrier est faux » ou « le pays a vraiment trois semaines de congés ».
Un seul sentinelle pour deux causes, c'est la leçon 1.5 — sauf qu'ici les deux
mènent à la même conduite : alerter un humain. Donc une seule erreur suffit, et
c'est la bonne réponse.

**Rien ne garantit que les données du calendrier sont justes.** Le contrat
vérifie la forme de la réponse. Aucun test de ce chapitre ne dirait qu'on a mis
le 14 juillet au lieu du 20 mai. Ça se vérifie par une relecture humaine contre
une source officielle, et il faut le savoir plutôt que de se croire couvert.

   « je ne sais pas ». Le booléen rendu avec une erreur n'a aucune
   signification.
3. **Un test de contrat est une contrainte de conception qui remonte.** Celui-ci
   a changé le format d'un fichier.
4. **Un test qui n'a pas de sens pour toutes les implémentations n'appartient
   pas au contrat.** C'est le critère, et il est déductible.
5. **Un test de contrat ne vérifie jamais que les données sont justes.**
6. **Deux issues qui ne portent pas les mêmes informations ne se lisent pas de
   la même façon.** `(valeur, SMS cumules / impayes distincts = %.2f| | total SMS / distinct unpaid = %.2fok)` interdit la faute que la structure publique
   autorise.
7. **La bonne granularité d'un test de graphe** : imports directs pour les
   capacités, fermeture transitive restreinte au projet pour les connaissances.
   `fmt` apporte `os`.
8. **Toute recherche qui avance jusqu'à trouver doit avoir une borne**, et le
   dépassement est une erreur distincte.
9. **Une modification survivante ne demande pas toujours un test.** Elle demande
   ce que la ligne décide : un comportement, un coût, ou rien.
10. **Un test de décision qui n'inspecte rien passe toujours.** Écris la garde.
