## 1. La date civile : le type qu'on n'avait pas demandé

Avant la règle, un type. Et il faut justifier pourquoi, parce que personne ne le
demandait.

Une date de prélèvement n'est **pas un instant**. Le 5 du mois est le 5 du mois
à Douala comme à Paris. Utiliser `time.Time` pour ça, c'est transporter une
heure et un fuseau dont personne n'a besoin, et découvrir six mois plus tard
qu'un prélèvement a sauté un jour parce que le serveur est passé en UTC et que
`2026-03-05T00:00:00+01:00` est le 4 mars à 23 h.

```go
// Package jour definit la date civile.
//
// Une date de prelevement n'est pas un instant : c'est un jour du calendrier.
// Le 5 du mois est le 5 du mois a Douala comme a Paris. Utiliser time.Time pour
// ca, c'est transporter une heure et un fuseau dont personne n'a besoin, et
// decouvrir six mois plus tard qu'un prelevement a saute un jour parce que le
// serveur est passe en UTC.
package jour

import (
    "errors"
    "fmt"
    "time"
)

var ErrDateInexistante = errors.New("jour : date inexistante")

// Jour est une date civile, sans heure et sans fuseau.
type Jour struct {
    a int
    m time.Month
    j int
}

// Nouveau refuse ce qui n'existe pas. Le 31 fevrier n'est pas un jour sur
// lequel on peut prelever.
func Nouveau(annee int, mois time.Month, jourDuMois int) (Jour, error) {
    t := time.Date(annee, mois, jourDuMois, 0, 0, 0, 0, time.UTC)
    if t.Year() != annee || t.Month() != mois || t.Day() != jourDuMois {
        return Jour{}, fmt.Errorf("%w : %d-%02d-%02d", ErrDateInexistante, annee, mois, jourDuMois)
    }
    return Jour{a: annee, m: mois, j: jourDuMois}, nil
}

// MustNouveau panique si la date n'existe pas. Reserve aux litteraux ecrits
// dans le code : une date fausse ecrite a la main est un bug de programmation,
// pas une donnee d'entree.
func MustNouveau(annee int, mois time.Month, jourDuMois int) Jour {
    j, err := Nouveau(annee, mois, jourDuMois)
    if err != nil {
        panic(err)
    }
    return j
}

// Plus rend le jour decale de n jours. Les mois et les annees se gerent tout
// seuls, et les annees bissextiles aussi.
func (j Jour) Plus(n int) Jour {
    t := j.instant().AddDate(0, 0, n)
    return Jour{a: t.Year(), m: t.Month(), j: t.Day()}
}

// Semaine rend le jour de la semaine.
func (j Jour) Semaine() time.Weekday { return j.instant().Weekday() }

// Annee est necessaire au calendrier, qui est organise par annee.
func (j Jour) Annee() int { return j.a }

// Avant ordonne deux jours.
func (j Jour) Avant(autre Jour) bool { return j.instant().Before(autre.instant()) }

// EstNul dit si le jour est le Jour zero, celui qu'aucun constructeur ne rend.
func (j Jour) EstNul() bool { return j == Jour{} }

func (j Jour) String() string {
    if j.EstNul() {
        return "jour nul"
    }
    return fmt.Sprintf("%04d-%02d-%02d", j.a, int(j.m), j.j)
}

// instant est le seul endroit du programme ou une date civile devient un
// instant, et c'est toujours en UTC a minuit. Non exportee : personne d'autre
// n'a besoin de faire cette conversion, donc personne d'autre ne peut la faire
// de travers.
func (j Jour) instant() time.Time {
    return time.Date(j.a, j.m, j.j, 0, 0, 0, 0, time.UTC)
}
```

Trois décisions à relever.

**`Nouveau` refuse ce qui n'existe pas.** C'est le ⚫ de la question 4, et on y
revient plus bas. `jour.Nouveau(2026, time.February, 30)` rend une erreur ; il
n'existe aucun `Jour` du 30 février dans tout le programme.

**`instant` n'est pas exportée.** C'est la seule conversion date civile →
instant du programme, elle est toujours en UTC à minuit, et personne d'autre ne
peut la faire de travers. La leçon 1.4, appliquée à une unité de mesure.

**`Plus` ne connaît ni les mois ni les années bissextiles** — ou plutôt, elle
les connaît toute seule, et c'est le point : plus aucun code du programme n'a à
les connaître. Le test le vérifie sur quatre cas, dont un 29 février.

### Le test du ⚫

Sans lui, la garantie *« un `Jour` existe toujours dans le calendrier »* n'est
qu'une phrase de commentaire :

```go
// TestLesDatesInexistantesSontRefusees : c'est le test du ⚫. Sans lui, la
// garantie « un Jour existe toujours dans le calendrier » n'est qu'une phrase
// de commentaire.
func TestLesDatesInexistantesSontRefusees(t *testing.T) {
    cas := []struct {
        annee int
        mois  time.Month
        jour  int
    }{
        {2026, time.February, 30},
        {2026, time.February, 29}, // 2026 n'est pas bissextile
        {2026, time.April, 31},
        {2026, time.January, 0},
        {2026, time.January, 32},
        {2026, time.Month(13), 1},
        {2026, time.Month(0), 1},
    }

    for _, c := range cas {
        if _, err := jour.Nouveau(c.annee, c.mois, c.jour); !errors.Is(err, jour.ErrDateInexistante) {
            t.Errorf("Nouveau(%d, %d, %d) = (_, %v), attendu ErrDateInexistante",
                c.annee, c.mois, c.jour, err)
        }
    }
}

func TestLeVingtNeufFevrierBissextileExiste(t *testing.T) {
    if _, err := jour.Nouveau(2024, time.February, 29); err != nil {
        t.Fatalf("2024-02-29 refuse : %v", err)
    }
}
```

Et un point de méthode souvent raté : `time.Month(13)` et le jour `0` sont dans
le tableau. Un constructeur qui valide le jour du mois mais pas le mois est un
constructeur qui donne une fausse impression de sûreté.

## 2. Le contrat du calendrier, et la clause qui change tout

```go
// Package calendrier definit le contrat d'un calendrier de jours feries. Il ne
// contient aucune implementation et aucune donnee.
package calendrier

import (
    "errors"

    "exemple/prelevements/jour"
)

// ErrAnneeInconnue : le calendrier ne couvre pas cette annee.
//
// C'est la clause qui compte. Un calendrier qui ne connait pas 2027 doit le
// dire. S'il repond « pas ferie », il repond faux avec assurance, et un
// prelevement part un 1er janvier.
var ErrAnneeInconnue = errors.New("calendrier : annee non couverte")

// Calendrier dit quels jours sont feries.
type Calendrier interface {
    // Ferie dit si ce jour est ferie.
    //
    // GARANTI : la reponse est stable. Deux appels sur le meme jour rendent le
    // meme resultat, et l'appel est sur pour un usage concurrent.
    //
    // CE QUI RESTE VRAI EN CAS D'ECHEC : une annee non couverte rend
    // ErrAnneeInconnue et JAMAIS false. Le booleen rendu avec une erreur n'a
    // aucune signification.
    Ferie(j jour.Jour) (bool, error)
}
```

Lis la signature deux fois :

```
Ferie(j jour.Jour) (bool, error)
```

Un débutant écrirait `Ferie(j) bool`. C'est plus simple, c'est plus agréable à
appeler, et c'est **faux** — pour une raison qui n'a rien à voir avec le style :

> Un calendrier qui ne connaît pas 2027 n'a aucune façon de le dire s'il ne rend
> qu'un booléen. Il répondra « pas férié » sur le 1er janvier 2027, et il le
> dira **sur le même ton** que lorsqu'il sait.

C'est la leçon 1.4 — `(nil, false)` qui fusionne « absent » et « cassé » — et la
leçon 1.5 — la clause *« ce qui reste vrai en cas d'échec »*. Les deux se
rejoignent sur une signature de quatre mots.

## 3. Le test de contrat, et ses deux étages

Le premier étage est celui que tout le monde écrit : un férié est férié, un jour
ordinaire ne l'est pas, la réponse est stable, et l'appel est sûr en
concurrence.

Le second est celui que personne n'écrit :

```go
// VerifierHorsCouverture est le test de contrat que personne n'ecrit.
//
// Il ne demande pas au calendrier de connaitre 2027. Il lui demande de SAVOIR
// qu'il ne connait pas 2027. La difference entre les deux est un prelevement
// qui part un 1er janvier.
func VerifierHorsCouverture(t *testing.T, fabrique Fabrique) {
    t.Helper()

    t.Run("une annee non couverte est annoncee, pas devinee", func(t *testing.T) {
        c := fabrique(t)

        _, err := c.Ferie(horsAnnee)
        if !errors.Is(err, calendrier.ErrAnneeInconnue) {
            t.Fatalf("Ferie(%s) = (_, %v), attendu ErrAnneeInconnue."+
                " Repondre « pas ferie » sur une annee inconnue, c'est affirmer"+
                " ce qu'on ignore", horsAnnee, err)
        }
    })
}
```

Il ne demande pas au calendrier de **connaître** 2027. Il lui demande de
**savoir qu'il ne connaît pas** 2027. La différence entre les deux est un
prélèvement qui part un 1er janvier.

### Ce qui s'est passé quand je l'ai lancé

La première version du calendrier sur fichier ressemblait à ceci — on charge ce
qu'on trouve, et on répond avec ce qu'on a :

```go
// Ferie repond avec ce qui a ete charge. Rien de plus.
//
// Et c'est tout le probleme : si le fichier couvre 2026 et qu'on l'interroge
// sur 2027, cette fonction rend (false, nil). Elle affirme qu'aucun jour de
// 2027 n'est ferie. Elle n'en sait rien, et elle le dit sur le meme ton que
// lorsqu'elle sait.
func (c *Calendrier) Ferie(j jour.Jour) (bool, error) {
    return c.Feries[j], nil
}
```

```
--- FAIL: TestContrat/une_annee_non_couverte_est_annoncee,_pas_devinee
    calendriertest.go:83: Ferie(2027-03-10) = (_, <nil>), attendu ErrAnneeInconnue. Repondre « pas ferie » sur une annee inconnue, c'est affirmer ce qu'on ignore
```

Et là arrive le résultat le plus intéressant de tout l'exercice. **Le défaut
n'était pas dans le code. Il était dans le format du fichier.**

Un fichier qui liste des dates ne sait pas distinguer *« 2027 n'a aucun
férié »* de *« je ne connais pas 2027 »*. L'information n'y est pas. Aucune
correction du code ne pouvait la faire apparaître.

```go
// Package calendrierfichier lit les jours feries dans un fichier.
//
// Format, une directive par ligne :
//
//    # annees 2026 2027      les annees que ce fichier couvre
//    2026-01-01              un jour ferie
//
// La premiere directive existe a cause du contrat. Un fichier qui liste des
// dates ne sait pas distinguer « 2027 n'a aucun ferie » de « je ne connais pas
// 2027 ». Le contrat exige cette distinction, donc le format a du changer.
// C'est le cas le plus net de ce chapitre : une clause que personne n'ecrit a
// fini par se propager jusqu'au format des donnees.
package calendrierfichier

import (
    "fmt"
    "os"
    "strconv"
    "strings"
    "time"

    "exemple/prelevements/calendrier"
    "exemple/prelevements/jour"
)

type Calendrier struct {
    annees map[int]bool
    feries map[jour.Jour]bool
}

func Charger(chemin string) (*Calendrier, error) {
    contenu, err := os.ReadFile(chemin)
    if err != nil {
        return nil, err
    }

    c := &Calendrier{annees: make(map[int]bool), feries: make(map[jour.Jour]bool)}
    for numero, ligne := range strings.Split(string(contenu), "\n") {
        ligne = strings.TrimSpace(ligne)
        if ligne == "" {
            continue
        }
        if err := c.lireLigne(ligne); err != nil {
            return nil, fmt.Errorf("%s ligne %d : %w", chemin, numero+1, err)
        }
    }

    if len(c.annees) == 0 {
        return nil, fmt.Errorf("%s : aucune directive « # annees » :"+
            " un calendrier qui ne dit pas ce qu'il couvre ne peut tenir son contrat", chemin)
    }
    // Un ferie hors des annees declarees est une incoherence du fichier, pas
    // une donnee a ignorer. On la refuse au chargement, une fois, plutot que de
    // repondre de travers a chaque appel.
    for f := range c.feries {
        if !c.annees[f.Annee()] {
            return nil, fmt.Errorf("%s : le ferie %s est hors des annees declarees", chemin, f)
        }
    }
    return c, nil
}
```

> Une clause de contrat que personne n'écrit a fini par se propager jusqu'au
> **format des données**. C'est le cas le plus net de ce chapitre : un test de
> contrat n'est pas une vérification après coup, c'est une contrainte de
> conception qui remonte.

Et une décision secondaire, prise au même moment : un férié hors des années
déclarées fait **échouer le chargement**. On refuse l'incohérence une fois, au
démarrage, plutôt que de répondre de travers à chaque appel. C'est la leçon 1.5 —
analyser plutôt que valider — appliquée à un fichier de configuration.

## 4. Ce que le test de contrat ne peut pas vérifier

C'était une question explicite de l'énoncé, et c'est la partie que presque tout
le monde escamote. Cinq choses, et il faut les nommer une par une :

| Ce qui échappe au contrat | Pourquoi | Où ça se vérifie alors |
|---|---|---|
| **la justesse des données** | le contrat vérifie la *forme* de la réponse, jamais la *vérité* du contenu. Un calendrier qui déclare le 14 juillet férié au Cameroun passe tout le contrat | une relecture humaine, une source de référence |
| **le format du fichier** | l'autre implémentation n'a pas de fichier | un test d'implémentation |
| **la latence et le coût** | la fabrique ne dit rien du temps de réponse | un test d'implémentation, un budget |
| **le rechargement** | si le fichier change pendant l'exécution, que se passe-t-il ? La question n'existe pas pour le calendrier figé | un test d'implémentation |
| **le fichier corrompu en cours de lecture** | il faudrait pouvoir provoquer la panne, et ce moyen n'est pas dans l'interface | une couture ouverte exprès, comme le `Panne` de la leçon |

Les quatre dernières lignes ont un point commun : elles appartiennent à l'étage
**implémentation**. Voilà à quoi il ressemble, et noter qu'aucun de ces tests
n'aurait de sens pour l'autre implémentation :

```go

// Les tests qui suivent sont des tests d'IMPLEMENTATION. Ils n'ont rien a faire
// dans le contrat : ils portent sur le format du fichier, que l'autre
// implementation n'a pas. C'est exactement la frontiere entre les deux etages.
func TestLeChargementRefuseUnFichierQuiNeDitPasCeQuIlCouvre(t *testing.T) {
    cas := map[string]string{
        "sans directive":    "2026-01-01\n",
        "directive vide":    "# annees\n2026-01-01\n",
        "annee illisible":   "# annees deux-mille-vingt-six\n",
        "ferie hors annees": "# annees 2026\n2027-01-01\n",
        "date inexistante":  "# annees 2026\n2026-02-31\n",
        "date illisible":    "# annees 2026\n01/01/2026\n",
    }

    for nom, contenu := range cas {
        t.Run(nom, func(t *testing.T) {
            chemin := filepath.Join(t.TempDir(), "feries.txt")
            if err := os.WriteFile(chemin, []byte(contenu), 0o600); err != nil {
                t.Fatalf("ecriture : %v", err)
            }
            if _, err := calendrierfichier.Charger(chemin); err == nil {
                t.Fatal("charge sans erreur : le fichier serait utilise tel quel")
            }
        })
    }
}

func TestUneAnneeCouverteSansAucunFerieNEstPasUneAnneeInconnue(t *testing.T) {
    chemin := filepath.Join(t.TempDir(), "feries.txt")
    if err := os.WriteFile(chemin, []byte("# annees 2026 2027\n2026-01-01\n"), 0o600); err != nil {
        t.Fatalf("ecriture : %v", err)
    }
    c, err := calendrierfichier.Charger(chemin)
    if err != nil {
        t.Fatalf("Charger : %v", err)
    }

    // 2027 est declaree et n'a aucun ferie. C'est la distinction que l'ancien
    // format ne savait pas exprimer.
    ferie, err := c.Ferie(jour.MustNouveau(2027, time.March, 10))
    if err != nil {
        t.Fatalf("Ferie : %v", err)

    }
}
```

> La frontière entre les deux étages n'est pas une question de goût : elle est
> **déductible**. Un test qui n'a pas de sens pour toutes les implémentations
> n'appartient pas au contrat.

## 5. La règle

```go
// Package prelevement decide la suite a donner a un prelevement rejete.
//
// Il ne lit rien, n'ecrit rien, ne consulte pas l'heure. Le jour du rejet est
// un argument ; le calendrier est un argument ; la decision est une valeur.
package prelevement

import (
    "errors"
    "fmt"
    "time"

    "exemple/prelevements/calendrier"
    "exemple/prelevements/jour"
)

const (
    // DelaiMinimal est le nombre de jours a attendre apres un rejet avant de
    // reessayer.
    DelaiMinimal = 4
    // RejetsMax est le nombre de rejets au-dela duquel on arrete d'essayer.
    RejetsMax = 3
    // horizon borne la recherche du prochain jour ouvre. Trois semaines de
    // jours feries consecutifs n'existent pas ; si on les trouve, c'est le
    // calendrier qui est faux, et une boucle infinie serait la pire facon de
    // l'apprendre.
    horizon = 21
)

var (
    // ErrRejetsNegatifs : un nombre de rejets negatif est une faute de
    // l'appelant.
    ErrRejetsNegatifs = errors.New("prelevement : nombre de rejets negatif")
    // ErrJourNul : le jour du rejet n'a pas ete construit.
    ErrJourNul = errors.New("prelevement : jour de rejet nul")
    // ErrAucunJourOuvre : aucun jour ouvre dans les trois semaines qui suivent.
    // C'est un calendrier a verifier, pas un cas metier.
    ErrAucunJourOuvre = errors.New("prelevement : aucun jour ouvre dans l'horizon")
)

// Suite est la nature de la decision.
type Suite int

const (
    // Reessai : on represente le prelevement a une date donnee.
    Reessai Suite = iota + 1
    // Recouvrement : on arrete, le dossier change de main.
    Recouvrement
)

// Decision est la suite a donner. Ses champs sont prives, et c'est le point
// important du fichier : il n'existe pas de Decision « recouvrement le
// 12 mars ». Les deux issues ne portent pas les memes informations, donc elles
// ne sont pas lisibles de la meme facon.
type Decision struct {
    suite Suite
    quand jour.Jour
}

// Reessai rend la date de la prochaine tentative, et false si la decision
// n'est pas un reessai. L'appelant ne peut pas lire la date sans avoir
// verifie la nature de la decision — c'est le meme mecanisme que la valeur
// (resultat, ok) de la lecon 1.4, et il interdit la meme faute.
func (d Decision) Reessai() (jour.Jour, bool) {
    if d.suite != Reessai {
        return jour.Jour{}, false
    }
    return d.quand, true
}

// EstRecouvrement dit si le dossier part au recouvrement.
func (d Decision) EstRecouvrement() bool { return d.suite == Recouvrement }

func (d Decision) String() string {
    if d.suite == Recouvrement {
        return "recouvrement"
    }
    return "reessai le " + d.quand.String()
}

// Decider rend la suite a donner apres un rejet.
//
// GARANTI
//
//    Au-dela de RejetsMax rejets, la decision est le recouvrement, et elle ne
//    porte aucune date.
//    Sinon, la decision est un reessai sur un jour ouvre, au moins DelaiMinimal
//    jours apres le rejet. Jamais un samedi, jamais un dimanche, jamais un jour
//    que le calendrier declare ferie.
//
// CE QUI RESTE VRAI EN CAS D'ECHEC
//
//    La decision rendue avec une erreur est la decision nulle. Aucun reessai
//    n'est jamais decide sur la base d'un calendrier qui a echoue : si le
//    calendrier ne sait pas, on ne decide pas.
//
// NON GARANTI
//
//    Que la date rendue soit un jour ou la banque du client accepte les
//    prelevements. Le calendrier des feries nationaux n'est pas le calendrier
//    des jours de valeur bancaires.
func Decider(rejetLe jour.Jour, rejetsCumules int, c calendrier.Calendrier) (Decision, error) {
    if rejetsCumules < 0 {
        return Decision{}, fmt.Errorf("%w : %d", ErrRejetsNegatifs, rejetsCumules)
    }
    if rejetLe.EstNul() {
        return Decision{}, ErrJourNul
    }
    if rejetsCumules >= RejetsMax {
        return Decision{suite: Recouvrement}, nil
    }

    candidat := rejetLe.Plus(DelaiMinimal)
    for essai := 0; essai < horizon; essai++ {
        ouvre, err := estOuvre(candidat, c)
        if err != nil {
            // Le calendrier ne sait pas. On ne devine pas a sa place.
            return Decision{}, err
        }
        if ouvre {
            return Decision{suite: Reessai, quand: candidat}, nil
        }
        candidat = candidat.Plus(1)
    }
    return Decision{}, fmt.Errorf("%w : a partir du %s", ErrAucunJourOuvre, rejetLe.Plus(DelaiMinimal))
}

func estOuvre(j jour.Jour, c calendrier.Calendrier) (bool, error) {
    switch j.Semaine() {
    case time.Saturday, time.Sunday:
        return false, nil
    }
    ferie, err := c.Ferie(j)
    if err != nil {
        return false, err
    }
    return !ferie, nil
}
```

### La décision la plus importante du fichier

Ce n'est ni le délai, ni le seuil. C'est ceci :

```
type Decision struct {
    suite Suite
    quand jour.Jour
}

func (d Decision) Reessai() (jour.Jour, bool)
```

Les deux issues — réessai et recouvrement — **ne portent pas les mêmes
informations**. Un recouvrement n'a pas de date. Avec une structure à champs
publics, `Decision{Suite: Recouvrement, Quand: unJour}` serait constructible, et
un appelant distrait prélèverait à cette date.

Avec le couple `(jour, bool)`, l'appelant **ne peut pas** lire la date sans
avoir vérifié la nature de la décision. C'est le mécanisme exact de la leçon 1.4,
et il interdit la même faute.

Le test qui le garde :

```go
// TestUnRecouvrementNePorteAucuneDate garde la decision du type : les deux
// issues ne portent pas les memes informations.
func TestUnRecouvrementNePorteAucuneDate(t *testing.T) {
    d, err := prelevement.Decider(j(2026, time.March, 2), 3, feries())
    if err != nil {
        t.Fatalf("Decider : %v", err)
    }

    if !d.EstRecouvrement() {
        t.Fatal("attendu un recouvrement")
    }
    if quand, ok := d.Reessai(); ok {
        t.Fatalf("Reessai() a rendu %s : l'appelant pourrait prelever a cette date", quand)
    }
}
```

### La clause d'échec, et le test qui la garde

```go
// TestSiLeCalendrierNeSaitPasOnNeDecidePas garde la clause « CE QUI RESTE VRAI
// EN CAS D'ECHEC ». C'est le test qui separe cette regle d'une regle qui
// prelevera un 1er janvier.
func TestSiLeCalendrierNeSaitPasOnNeDecidePas(t *testing.T) {
    // Un calendrier qui ne couvre que 2025.
    cal := calendrierfixe.Nouveau([]int{2025}, nil)

    d, err := prelevement.Decider(j(2026, time.March, 2), 1, cal)
    if !errors.Is(err, calendrier.ErrAnneeInconnue) {
        t.Fatalf("err = %v, attendu ErrAnneeInconnue", err)
    }
    if _, ok := d.Reessai(); ok {
        t.Fatal("une date de reessai a ete rendue avec une erreur")
    }
    if d.EstRecouvrement() {
        t.Fatal("un recouvrement a ete decide sur une erreur de calendrier")
    }
}
```

Ce test est le seul qui sépare cette règle d'une règle qui prélèvera un
1er janvier. Trois assertions, et chacune compte :

- l'erreur est bien celle du calendrier, remontée telle quelle ;
- **aucune date de réessai n'est rendue** avec l'erreur ;
- **aucun recouvrement n'est décidé** sur une erreur de calendrier — parce que
  décider le recouvrement parce qu'on n'a pas su lire un calendrier serait la
  pire des conduites possibles.

### L'horizon, et pourquoi ce n'est pas une boucle

```
horizon = 21
```

Vingt-et-un jours fériés consécutifs n'existent pas. Si on les rencontre, c'est
le calendrier qui est faux — et une boucle infinie serait la pire façon de
l'apprendre. Le test le vérifie avec quarante jours fériés d'affilée.

C'est une habitude à prendre : **toute recherche qui avance jusqu'à trouver doit
avoir une borne, et le dépassement de la borne est une erreur distincte**, pas
un cas métier.

## 6. Les tests de décision

```go
// Package garde ne contient que des tests de decision.
package garde

import (
    "go/ast"
    "go/parser"
    "go/token"
    "os/exec"
    "path/filepath"
    "strings"
    "testing"
)

// TestLaRegleNeConsultePasLHorloge garde la decision : le jour du rejet est un
// argument.
//
// Un test de graphe d'imports ne suffit pas, et il faut comprendre pourquoi :
// prelevement importe time legitimement, pour time.Saturday et time.Month. Le
// graphe voit « prelevement depend de time » et c'est vrai, c'est normal, et
// ca ne dit rien. La decision a garder porte sur TROIS IDENTIFIANTS de ce
// paquet, pas sur le paquet. Seule une lecture du code peut la voir.
func TestLaRegleNeConsultePasLHorloge(t *testing.T) {
    interdits := map[string]bool{"Now": true, "Since": true, "Until": true}

    // jour contient la seule conversion date civile -> instant du programme, et
    // elle n'appelle pas l'horloge non plus.
    for _, motif := range []string{"../prelevement/*.go", "../jour/*.go"} {
        fichiers, err := filepath.Glob(motif)
        if err != nil {
            t.Fatalf("glob : %v", err)
        }
        if len(fichiers) == 0 {
            t.Fatalf("%s : aucun fichier analyse. Un test de decision qui"+
                " n'inspecte rien passe toujours", motif)
        }

        for _, f := range fichiers {
            if strings.HasSuffix(f, "_test.go") {
                continue
            }
            arbre, err := parser.ParseFile(token.NewFileSet(), f, nil, 0)
            if err != nil {
                t.Fatalf("%s : %v", f, err)
            }
            ast.Inspect(arbre, func(n ast.Node) bool {
                selecteur, ok := n.(*ast.SelectorExpr)
                if !ok {
                    return true
                }
                paquet, ok := selecteur.X.(*ast.Ident)
                if !ok || paquet.Name != "time" || !interdits[selecteur.Sel.Name] {
                    return true
                }
                t.Errorf("%s appelle time.%s : le jour du rejet doit rester un"+
                    " argument", f, selecteur.Sel.Name)
                return true
            })
        }
    }
}

// TestLaRegleNAAucunMoyenDAgirSurLeMonde complete le precedent par ce que le
// graphe, lui, sait tres bien voir — a condition de le lire a la bonne
// granularite.
//
// La version publiee au chapitre 1.2 interrogeait « go list -deps », c'est-a-dire
// la FERMETURE TRANSITIVE, et elle interdisait "os". Elle passait, parce que le
// module de regles de ce chapitre-la n'importait que errors et strings.
//
// Elle echoue ici, et le message est trompeur : « prelevement depend de os ».
// C'est vrai, et c'est sans interet. La chaine est :
//
//    prelevement -> fmt -> os
//
// fmt importe os pour ecrire sur la sortie standard. Interdire os dans la
// fermeture transitive, c'est donc interdire fmt.Errorf — ce que personne ne
// veut, et ce que personne ne comprendra en lisant l'echec.
//
// La bonne granularite n'est pas la meme pour les deux questions :
//
//   - « ce module detient-il un moyen d'agir ? » se lit sur les imports
//     DIRECTS. Un paquet n'acquiert pas la capacite d'ouvrir un socket parce
//     qu'un de ses fournisseurs sait le faire ; il l'acquiert en l'important.
//   - « ce module depend-il d'un module qu'il ne devrait pas connaitre ? » se
//     lit sur la fermeture transitive, mais restreinte au code du projet, ou
//     il n'y a pas de faux positif possible.
func TestLaRegleNAAucunMoyenDAgirSurLeMonde(t *testing.T) {
    interdits := map[string]bool{
        "os": true, "os/exec": true, "net": true, "net/http": true,
        "net/smtp": true, "database/sql": true, "log": true, "log/slog": true,
    }
    paquets := []string{"exemple/prelevements/prelevement", "exemple/prelevements/jour"}

    for _, p := range paquets {
        for _, imp := range importsDirects(t, p) {
            if interdits[imp] {
                t.Errorf("%s importe directement %q : il detient un moyen qu'il ne doit pas avoir", p, imp)
            }
        }
    }
}

// TestLaRegleNeConnaitAucuneImplementation garde la direction des dependances :
// la regle connait le contrat du calendrier, jamais un calendrier.
func TestLaRegleNeConnaitAucuneImplementation(t *testing.T) {
    autorises := map[string]bool{
        "exemple/prelevements/prelevement": true,
        "exemple/prelevements/calendrier":  true,
        "exemple/prelevements/jour":        true,
    }

    sortie, err := exec.Command("go", "list", "-deps", "exemple/prelevements/prelevement").Output()
    if err != nil {
        t.Fatalf("go list : %v", err)
    }
    for _, l := range strings.Split(string(sortie), "\n") {
        l = strings.TrimSpace(l)
        if !strings.HasPrefix(l, "exemple/prelevements/") {
            continue
        }
        if !autorises[l] {
            t.Errorf("prelevement depend de %q, qui n'est pas dans la liste autorisee", l)
        }
    }
}

func importsDirects(t *testing.T, paquet string) []string {
    t.Helper()
    sortie, err := exec.Command("go", "list", "-f", "{{join .Imports \"\\n\"}}", paquet).Output()
    if err != nil {
        t.Fatalf("go list %s : %v", paquet, err)
    }
    var imports []string
    for _, l := range strings.Split(string(sortie), "\n") {
        if l = strings.TrimSpace(l); l != "" {
            imports = append(imports, l)
        }
    }
    if len(imports) == 0 {
        t.Fatalf("%s : aucun import lu, le test ne verifierait rien", paquet)
    }
    return imports
}
```

### Pourquoi le graphe d'imports ne suffit pas (question 2)

`prelevement` importe `time`, et c'est **légitime** : il a besoin de
`time.Saturday`, `time.Sunday` et `time.Month`. Le graphe d'imports voit
« `prelevement` dépend de `time` », c'est vrai, c'est normal, et ça ne dit rien.

> La décision à garder porte sur **trois identifiants** d'un paquet, pas sur le
> paquet. Aucun graphe de dépendances ne descend à cette granularité. Seule une
> lecture du code peut la voir.

D'où le parcours d'arbre syntaxique. Et le garde-fou du garde-fou, à ne jamais
oublier :

```
if len(fichiers) == 0 {
    t.Fatalf("%s : aucun fichier analyse. Un test de decision qui"+
        " n'inspecte rien passe toujours", motif)
}
```

Un test de décision qui n'inspecte rien passe toujours. C'est son mode de panne
propre, et il doit être écrit explicitement.

### Une correction du test publié au chapitre 1.2

En écrivant le second test, je suis tombé sur un faux positif, et il faut le
dire parce qu'il touche du matériel déjà publié.

La version du chapitre 1.2 interrogeait `go list -deps` — la **fermeture
transitive** — et interdisait `"os"`. Elle passait, parce que le module de
règles de ce chapitre-là n'importait que `errors` et `strings`.

Ici, elle échoue, avec un message trompeur : *« prelevement depend de os »*.
C'est vrai, et c'est sans intérêt. La chaîne est :

```
prelevement  ->  fmt  ->  os
```

`fmt` importe `os` pour écrire sur la sortie standard. Vérifiable en une
commande :

```
$ go list -f '{{join .Imports " "}}' fmt
errors internal/fmtsort internal/stringslite io math os reflect slices strconv sync unicode/utf8
```

**Interdire `os` dans la fermeture transitive, c'est donc interdire
`fmt.Errorf`.** Ce que personne ne veut, et ce que personne ne comprendra en
lisant l'échec.

La bonne granularité n'est pas la même pour les deux questions, et c'est la
leçon à retenir :

| La question | Où elle se lit | Pourquoi |
|---|---|---|
| ce module **détient-il un moyen d'agir** ? | les imports **directs** | un paquet n'acquiert pas la capacité d'ouvrir un socket parce qu'un de ses fournisseurs sait le faire. Il l'acquiert en l'important |
| ce module **connaît-il** un module qu'il ne devrait pas ? | la fermeture transitive, **restreinte au code du projet** | là, aucun faux positif n'est possible |

Le troisième test — `TestLaRegleNeConnaitAucuneImplementation` — est le second
cas : il garde la direction des dépendances. La règle connaît le **contrat** du
calendrier, jamais un calendrier.

### Et ces gardes, je les ai cassées pour voir

| La modification | Qui crie |
|---|---|
| `prelevement` importe `os` | `TestLaRegleNAAucunMoyenDAgirSurLeMonde` |
| `prelevement` importe `calendrierfixe` | `TestLaRegleNeConnaitAucuneImplementation` |
| `maintenant = time.Now()` dans `Decider` | `TestLaRegleNeConsultePasLHorloge` |

Trois sur trois. Un test de décision qu'on n'a jamais vu rouge est une
décoration.

## 7. La campagne de modifications (question 6)

### Les cinq demandées

| # | La modification | Qui crie |
|---|---|---|
| 1 | `DelaiMinimal` 4 → 5 | 5 cas du tableau |
| 2 | `rejetsCumules >= RejetsMax` → `>` | « troisième rejet : recouvrement » + `TestUnRecouvrementNePorteAucuneDate` |
| 3 | le dimanche n'est plus un jour non ouvré | 3 cas du tableau |
| 4 | l'erreur du calendrier est avalée (`ferie, _ := c.Ferie(j)`) | `TestSiLeCalendrierNeSaitPasOnNeDecidePas` |
| 5 | la boucle de recherche fait un seul tour | 3 cas + `TestDeciderEstDeterministe` + `TestDeciderNeModifiePasLeCalendrier` |

Cinq sur cinq, plus les deux gardes du paragraphe précédent : **7 / 7**.

Noter la modification n° 4. Elle ne change **aucun** résultat dans le cas
normal — elle ne se manifeste que lorsque le calendrier échoue. Un seul test la
voit, et c'est celui que presque personne n'écrit. C'est la démonstration la
plus utile de l'exercice : *la clause « ce qui reste vrai en cas d'échec » n'est
gardée par rien d'autre qu'un test qui la vise.*

### Les deux survivantes

L'énoncé demandait de ne pas cacher les survivantes. Je suis allé en chercher,
et j'en ai trouvé deux.

**S1 — `horizon` 21 → 20.** Aucun test ne tombe.

Pourquoi : le seul test qui touche l'horizon utilise quarante jours fériés
consécutifs, donc il échoue avec 21 comme avec 20. La valeur exacte n'est
gardée par rien.

Que faire : **rien.** C'est le bon choix, et il faut savoir le défendre. La
valeur 21 n'est pas une règle métier : c'est une borne de sûreté dont seule
l'existence compte. Écrire un test qui vérifie que la borne vaut exactement 21,
ce serait écrire un test miroir — il casserait le jour où quelqu'un met 30, sans
qu'aucun comportement attendu n'ait changé.

> Une modification qui survit sur une constante de sûreté n'appelle pas un test.
> Elle confirme que la constante est un détail d'implémentation, et c'est une
> information.

**S2 — le calendrier est interrogé *avant* le week-end.** Aucun test ne tombe.

Pourquoi : un samedi férié n'est pas ouvré dans les deux ordres. Le résultat est
identique ; seul le **nombre d'appels au calendrier** change — et il augmente de
40 % environ, puisque deux jours sur sept sont des week-ends.

Que faire : **pas de test sur le nombre d'appels.** Ce serait exactement le test
miroir de la leçon. La différence est un **coût**, pas un comportement. Si ce
coût devient réel — un calendrier qui interroge un service distant —, alors il
mérite un test d'implémentation avec un budget chiffré, de la forme *« moins de
N appels pour une décision »*. Et à ce moment-là, le test aura un demandeur :
l'astreinte.

> Une modification survivante qui ne change que le coût désigne une décision de
> performance non documentée. On l'écrit dans un commentaire, et on la teste le
> jour où quelqu'un paie pour elle.

Les deux survivantes ont donc la même morale, et c'est l'inverse de celle qu'on
attend :

> **Toutes les modifications survivantes n'appellent pas un test de plus.**
> Elles appellent une question : *qu'est-ce que cette ligne décide vraiment ?*
> Les trois réponses possibles sont : ajouter un test, supprimer la ligne, ou
> rendre l'état inconstruisible. La leçon en a montré une de chaque.

## 8. Ce que ça ne règle pas

**`NON GARANTI` est dans le contrat, et c'est une vraie limite.** Le calendrier
des fériés nationaux n'est pas le calendrier des jours de valeur bancaires. La
date rendue est un jour ouvré ; ce n'est pas forcément un jour où la banque du
client accepte les prélèvements. La règle le dit au lieu de le laisser croire.

**Le compteur de rejets n'est pas protégé.** `Decider(rejetLe, 2, cal)` est
appelable avec n'importe quel entier. Le vrai ⚫ serait un type `Rejets` avec un
constructeur, ou mieux : un `Dossier` qui porte son propre compteur et une
méthode `Rejeter`. Je ne l'ai pas fait, parce que le compteur vient de la base
et que le gain est faible comparé au type `Jour` — mais c'est un arbitrage, pas
une omission, et il devient faux dès qu'un deuxième appelant apparaît.

**L'horizon ne distingue pas deux causes.** `ErrAucunJourOuvre` peut signifier
« le calendrier est faux » ou « le pays a vraiment trois semaines de congés ».
Un seul sentinelle pour deux causes, c'est la leçon 1.5 — sauf qu'ici les deux
mènent à la même conduite : alerter un humain. Donc une seule erreur suffit, et
c'est la bonne réponse.

**Rien ne garantit que les données du calendrier sont justes.** Le contrat
vérifie la forme de la réponse. Aucun test de ce chapitre ne dirait qu'on a mis
le 14 juillet au lieu du 20 mai. Ça se vérifie par une relecture humaine contre
une source officielle, et il faut le savoir plutôt que de se croire couvert.

## Ce qu'il faut retenir

1. **Une date civile n'est pas un instant.** Le type coûte 78 lignes et
   supprime une classe entière de bugs de fuseau.
2. **`Ferie(j) bool` est une signature fausse** : elle ne permet pas de dire
   « je ne sais pas ». Le booléen rendu avec une erreur n'a aucune
   signification.
3. **Un test de contrat est une contrainte de conception qui remonte.** Celui-ci
   a changé le format d'un fichier.
4. **Un test qui n'a pas de sens pour toutes les implémentations n'appartient
   pas au contrat.** C'est le critère, et il est déductible.
5. **Un test de contrat ne vérifie jamais que les données sont justes.**
6. **Deux issues qui ne portent pas les mêmes informations ne se lisent pas de
   la même façon.** `(valeur, ok)` interdit la faute que la structure publique
   autorise.
7. **La bonne granularité d'un test de graphe** : imports directs pour les
   capacités, fermeture transitive restreinte au projet pour les connaissances.
   `fmt` apporte `os`.
8. **Toute recherche qui avance jusqu'à trouver doit avoir une borne**, et le
   dépassement est une erreur distincte.
9. **Une modification survivante ne demande pas toujours un test.** Elle demande
   ce que la ligne décide : un comportement, un coût, ou rien.
10. **Un test de décision qui n'inspecte rien passe toujours.** Écris la garde.
