# Correction — Exercice 1.3 / 4 (design)

## L'énoncé

Une plateforme de réservation de trajets interurbains : `plan`,
`reservation`, `tarif`, `notif`. Un binaire, un dépôt. Trois coutures
proposées en réunion :

| | Couture proposée |
|---|---|
| A | une interface entre `reservation` et `plan` |
| B | une interface entre `reservation` et `tarif` |
| C | `notif` devient un service séparé, appelé en HTTP |

## Question 1 — Les trois verdicts

Les quatre critères de la leçon, appliqués mécaniquement. Je les mets en
tableau avant de commenter, parce que la discipline consiste à répondre aux
quatre avant d'avoir une opinion.

| Critère | A — `plan` | B — `tarif` | C — `notif` |
|---|---|---|---|
| même demandeur que `reservation` ? | **oui** — celui qui décide comment on remplit un car | non — le commerce, les promotions | non — le marketing, l'infrastructure |
| même rythme ? | **oui** | non — plus rapide | non — beaucoup plus rapide |
| un sens l'un sans l'autre ? | **non** — une réservation sans place n'existe pas | oui — un tarif se calcule sans réserver | oui, complètement |
| quelqu'un voudra remplacer ? | **non** | oui — un moteur de promotions, un partenaire | oui — opérateur SMS, e-mail, push |

### A — à refuser

Quatre fois la mauvaise réponse. L'interface `Attributeur` coûterait un
fichier, une indirection, un type `reservation.Seat` et une fonction de
traduction — payés à chaque changement, pour un droit de remplacement dont
personne n'usera.

L'argument qui tranche n'est aucun des quatre critères pris isolément, c'est
le second :

> `plan` et `reservation` ont le **même rythme de changement**. Une interface
> entre deux modules qui changent toujours ensemble n'achète rien et se paie
> deux ouvertures de fichier par changement, pour toujours.

C'est le contrepoids de la leçon 1.2, et c'est la couture que quelqu'un de
fraîchement converti à la responsabilité unique créera avec le plus
d'enthousiasme.

### B — à créer, et c'est la plus rentable

Le tarif a son propre demandeur, son propre rythme — les promotions changent
par campagne, c'est-à-dire par semaine —, il se calcule sans réserver quoi que
ce soit, et il **sera** remplacé : un moteur de promotions, une grille
partenaire, un prix dynamique.

Et l'interface est déclarée par `reservation`, pas par `tarif` :

```go
// in reservation
type Pricer interface {
    Price(ctx context.Context, trip string, class Class) (int64, error)
}
```

La flèche est orientée du volatil vers le stable : c'est `tarif` qui se
conforme à la question de `reservation`, et non `reservation` qui apprend le
vocabulaire de `tarif`.

### C — à créer, mais pas comme ça

La séparation est justifiée par les quatre critères. C'est **l'appel HTTP
synchrone** qui est l'erreur, et la question 2 le chiffre.

> La bonne réponse à « faut-il séparer ? » et la bonne réponse à « comment les
> faire communiquer ? » sont deux réponses. Confondre les deux est la
> manière la plus courante de transformer une bonne découpe en dégradation de
> service.

## Question 2 — Le chiffre

`reservation` est disponible à 99,95 %, le service de notification à 99,9 %.
L'appel est synchrone et bloquant, donc les deux doivent fonctionner :

```
0,9995 × 0,999 = 0,99850...
```

**99,85 %.** En minutes par mois de trente jours — 43 200 minutes :

| | Indisponibilité mensuelle |
|---|---|
| `reservation` seul | 21,6 min |
| `reservation` + notification synchrone | **64,8 min** |
| le prix de la couture, tel quel | **+43,2 min par mois** |

On a triplé l'indisponibilité du parcours de réservation pour pouvoir déployer
un gabarit de SMS séparément. Et le pire est le détail métier : **une place
est réservée, puis le client reçoit une erreur parce que le SMS n'est pas
parti.** Un effet cosmétique fait échouer un effet structurant — c'est E5 de
la correction 1.1 / 5, et on vient de le reconstruire avec une architecture.

### La conception qui garde la séparation et annule la dégradation

Le producteur n'appelle plus le consommateur : il **écrit une ligne**, dans la
même transaction que la réservation. Un travailleur séparé la lit et émet.

```go
// Package outbox is the outbox: messages to send are written to the
// database, in the same transaction as the fact that justifies them.
//
// Reason to change: the delivery guarantee and the retry policy.
//
// It is the mechanism that keeps notif separate without paying for its
// availability: reservation no longer calls notif, it writes a row.
package outbox

import (
    "context"
    "errors"
    "time"
)

type Message struct {
    ID        string // provided by the caller: it is the idempotency key
    Type      string
    Charge    []byte
    CreatedAt time.Time
    SentAt    *time.Time
    Attempts  int
}

var ErrNoIdentity = errors.New("outbox: message without identity")

// Outbox is written by the producer, in its transaction.
//
// Put must be callable with the current transaction: that is the whole
// the trick. If the put and the business fact are not in the same
// transaction, we are back to the two generals of correction 1.1 / 5.
type Outbox interface {
    Put(ctx context.Context, m Message) error
}

// Emitter is what the worker consumes. It is called outside any
// transaction, and it can fail without consequence: the message stays in the
// database.
type Emitter interface {
    Emit(ctx context.Context, m Message) error
}

// Queue is the worker side's read.
type Queue interface {
    ToSend(ctx context.Context, max int) ([]Message, error)
    MarkSent(ctx context.Context, id string, at time.Time) error
}

type Worker struct {
    Queue   Queue
    Emitter Emitter
    Batch   int
    Now     func() time.Time
}

// Round handles a batch. One message failing does not stop the others: same
// error policy as correction 1.2 / 2, for the same reason.
func (t *Worker) Round(ctx context.Context) error {
    msgs, err := t.Queue.ToSend(ctx, t.Batch)
    if err != nil {
        return err
    }

    var failures []error
    for _, m := range msgs {
        if err := ctx.Err(); err != nil {
            failures = append(failures, err)
            break
        }
        if m.ID == "" {
            failures = append(failures, ErrNoIdentity)
            continue
        }
        if err := t.Emitter.Emit(ctx, m); err != nil {
            failures = append(failures, err)
            continue
        }
        // At least once: if marking fails, the message goes again.
        // That is why the ID is the recipient's idempotency key.
        if err := t.Queue.MarkSent(ctx, m.ID, t.Now()); err != nil {
            failures = append(failures, err)
        }
    }
    return errors.Join(failures...)
}
```

La disponibilité du parcours de réservation redevient 99,95 % : il ne dépend
plus que de sa base, qu'il utilise déjà.

### Ce que ça coûte, et il faut le dire en entier

1. **Cohérence éventuelle.** Le SMS part dans la seconde, ou dans la minute, ou
   après la panne. Le parcours client doit donc afficher « c'est confirmé »
   sans attendre le SMS — ce qui est un changement de **produit**, pas de code.
2. **Au moins une fois, pas exactement une fois.** Si `MarkSent` échoue
   après une émission réussie, le message repart. Le destinataire doit être
   idempotent sur l'`ID` — d'où le fait que l'`ID` soit fourni par
   l'appelant, pour la raison établie dans la correction 1.1 / 5.
3. **Une table, un travailleur, une supervision.** Il faut une alerte sur
   l'âge du plus vieux message non émis. Sans elle, la boîte d'envoi se
   remplit en silence, et on découvre le problème par les réclamations.
4. **L'ordre n'est pas garanti** sans travail supplémentaire.
5. **Le dépôt doit être dans la même transaction que le fait métier.** Si
   `Put` ouvre sa propre transaction, on retombe exactement sur le problème
   des deux généraux : réservation enregistrée, message perdu.

> On n'a pas supprimé le couplage, on a changé sa nature : d'un couplage de
> **disponibilité** à un couplage de **cohérence**. Le premier se paie en
> minutes d'indisponibilité, le second en secondes de retard. Pour un SMS de
> confirmation, l'échange est évident. Pour un débit bancaire, il ne l'est
> pas.

## Question 3 — Les bateaux

> *« On vend désormais des places dans des bateaux, qui n'ont ni rangées ni
> lettres mais des ponts et des cabines. »*

Les deux questions de l'énoncé n'ont pas la même réponse, et c'est tout
l'intérêt.

### Est-ce que ça change mon verdict sur A ? Oui.

Le quatrième critère vient de basculer : quelqu'un veut **remplacer** `plan`
par une autre implémentation. Il y a maintenant deux dispositions, et il y en
aura une troisième.

La couture devient justifiée, et sa forme est dictée par ce qui est commun aux
deux : pas la numérotation, mais la **question**.

```go
// in reservation
type Layout interface {
    Assign(taken map[Seat]bool, pref Preference) (Seat, error)
    Contains(p Seat) bool
}
```

`Seat` devient une chaîne opaque pour `reservation` : `"12A"` pour un car,
`"P2-C14"` pour un bateau. Et c'est la bonne conception, parce que
`reservation` n'a jamais eu besoin de savoir lire une place — seulement de la
transporter.

Remarque le détail : l'interface est quasiment la **signature existante** de
`plan.Vehicle`. C'est le signe que le module était bien découpé : on peut
extraire son contrat sans le réécrire.

> Le test d'une bonne frontière n'est pas qu'elle soit abstraite. C'est qu'on
> puisse l'abstraire plus tard **sans réécrire le code qui est derrière**.

### Est-ce que j'avais tort en réunion ? Non.

Et c'est un point qui compte plus que le reste de l'exercice.

En réunion, l'information disponible disait : un seul type de véhicule, aucun
demandeur distinct, aucun projet de remplacement. Avec cette information, créer
l'interface aurait été payer six mois d'indirection sur un pari.

> Une décision de conception se juge sur l'information disponible au moment où
> elle est prise, pas sur ce qui s'est passé ensuite. Sinon, la seule stratégie
> gagnante est de tout abstraire — et elle perd toujours, parce qu'on abstrait
> aussi les quatre-vingt-dix pour cent de choses qui ne changeront jamais.

Ce qui serait une faute, en revanche, c'est de n'avoir **rien écrit**. Si la
réunion a conclu « pas d'interface entre `reservation` et `plan` » sans
consigner les quatre critères et leur réponse, alors six mois plus tard la
discussion recommence de zéro, avec quelqu'un qui dit « on aurait dû » et
personne pour montrer que non.

> Écris la décision et les quatre réponses. C'est ce qui transforme un
> changement d'avis en **apprentissage** au lieu d'un reproche. Un ADR de dix
> lignes suffit.

## Question 4 — Le tarif calculé aussi par le site partenaire

Un autre binaire, une autre équipe, un autre langage.

### Ce que ça change pour B

L'interface Go `Pricer` ne sert plus à rien pour ce consommateur-là : il
ne peut pas l'implémenter, et il ne peut pas l'appeler.

Trois options, et elles n'ont pas le même couplage :

| Option | Ce qui devient partagé | Degré |
|---|---|---|
| le partenaire appelle notre API de tarification | un **contrat réseau** : URL, schéma JSON, codes d'erreur, latence, disponibilité | 2, et sans compilateur |
| on publie la grille, le partenaire recalcule | la **règle** elle-même, dupliquée dans deux langages | 2, et pire |
| on publie une bibliothèque partagée | le **code**, et son cycle de version | 1, mais seulement si même langage |

### Ce qui devient partagé et ne l'était pas

**Un contrat réseau**, et c'est un couplage de degré 2 avec une aggravation
majeure : **plus aucun compilateur ne le vérifie, et le consommateur n'est plus
dans ton dépôt.**

Tant que `tarif` et `reservation` étaient dans le même binaire, changer la
signature cassait la compilation. Maintenant, ajouter un champ obligatoire dans
la réponse JSON ne casse rien chez toi et casse tout chez le partenaire —
en production, chez un tiers, qui l'apprendra par ses clients.

Et la deuxième option est la pire des trois, même si c'est celle qui paraît la
plus découplée : deux implémentations de la même règle de tarification, dans
deux langages, qui divergeront. Le jour où elles divergent, deux prix existent
pour le même trajet, et il faut décider lequel est le bon — devant un client.

> Dupliquer une règle pour éviter un couplage réseau échange un couplage
> vérifiable contre un couplage **invérifiable**. Deux implémentations d'une
> même règle ne sont pas découplées : elles sont couplées par une obligation
> d'identité que rien ne contrôle.

### Ce que j'en ferais

La première option, avec trois choses qui ne sont pas négociables :

- le schéma est **versionné et publié** — c'est devenu une interface publique ;
- un **test de contrat** tourne dans notre CI contre le schéma que le
  partenaire consomme, pas contre notre propre code ;
- on n'ajoute jamais un champ obligatoire. On ajoute des champs optionnels, et
  on retire après une période d'annonce.

C'est beaucoup de cérémonie. C'est le prix d'une frontière qui traverse une
organisation, et ce prix n'a rien à voir avec celui d'une interface Go. Ce qui
nous ramène à la règle.

## Question 5 — La règle, en trois lignes

> **1. Compte les demandeurs et les rythmes des deux côtés.** Un seul
> demandeur et un seul rythme : pas de couture.
>
> **2. S'ils diffèrent, demande qui voudra remplacer quoi.** Personne : pas de
> couture — mais écris la décision et ses raisons.
>
> **3. Si une couture est justifiée, choisis sa nature séparément de son
> existence.** Dans le même binaire, elle coûte une interface. À travers le
> réseau, elle coûte une disponibilité, une cohérence et un contrat
> versionné — et ça se chiffre avant, pas après.

Et le test qui rend la règle capable de dire non :

> Si je ne peux pas nommer la personne qui voudra remplacer ce côté-là, je ne
> crée pas la couture. J'écris pourquoi, et je garde le droit de changer d'avis
> quand cette personne existera.

## À retenir

1. Réponds aux quatre critères avant d'avoir une opinion. Quatre fois « oui » :
   pas de couture.
2. Le critère qui tranche le plus souvent est le **rythme**. Deux modules qui
   changent toujours ensemble ne gagnent rien à être séparés.
3. « Faut-il séparer ? » et « comment communiquer ? » sont deux questions.
   Confondre les deux transforme une bonne découpe en dégradation de service.
4. Une dépendance synchrone multiplie les disponibilités : 99,95 % × 99,9 %
   = 99,85 %, soit trois fois plus d'indisponibilité pour le parcours.
5. La boîte d'envoi change la nature du couplage : de la **disponibilité** vers
   la **cohérence**. Minutes d'indisponibilité contre secondes de retard.
6. Une boîte d'envoi exige que le dépôt soit dans la transaction du fait
   métier, un identifiant fourni par l'appelant, et une alerte sur l'âge du
   plus vieux message.
7. Le test d'une bonne frontière n'est pas qu'elle soit abstraite : c'est qu'on
   puisse l'abstraire plus tard sans réécrire ce qui est derrière.
8. Une décision se juge sur l'information disponible au moment où elle est
   prise. Sinon la seule stratégie gagnante est de tout abstraire, et elle
   perd toujours.
9. Écris la décision et ses raisons. C'est ce qui transforme un changement
   d'avis en apprentissage au lieu d'un reproche.
10. Un contrat réseau est un couplage de degré 2 qu'aucun compilateur ne
    vérifie, chez un consommateur qui n'est pas dans ton dépôt.
11. Deux implémentations d'une même règle ne sont pas découplées : elles sont
    couplées par une obligation d'identité que rien ne contrôle.
