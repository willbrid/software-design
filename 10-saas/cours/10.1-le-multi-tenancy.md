# Leçon 10.1 — Le multi-tenancy : chaque association chez elle, dans les mêmes tables

## L'essentiel en deux minutes

**Le problème, en une phrase.** Quand une seule application sert
beaucoup d'associations, une seule requête qui oublie de filtrer par
association suffit à montrer à une trésorière les membres de toutes les
autres.

**Trois images.**

- **L'immeuble et ses appartements** : tout le monde partage les murs,
  l'eau et l'escalier, mais chaque porte a sa clé. On ne compte pas sur
  la politesse des voisins pour ne pas entrer.
- **Le gardien qui vérifie chaque fois** : il ne retient pas « la
  dernière personne était du 3e, celle-ci doit l'être aussi » ; il
  demande la clé à chaque passage.
- **Le carnet à deux colonnes** : on n'écrit pas « Awa a payé » mais
  « Awa, de la tontine des commerçants, a payé ». Le nom de l'association
  fait partie de chaque ligne et de chaque référence.

**Le code, en quelques lignes.** PostgreSQL lui-même ne montre à une
session que les lignes de l'association qu'elle a déclarée :

```go
// Policies makes PostgreSQL itself keep each session to the association
// named in the setting app.tenant. An unset tenant sees no row.
const Policies = `
ALTER TABLE members ENABLE ROW LEVEL SECURITY;
ALTER TABLE contributions ENABLE ROW LEVEL SECURITY;
CREATE POLICY same_tenant ON members
    USING (tenant_id = current_setting('app.tenant', true));
CREATE POLICY same_tenant ON contributions
    USING (tenant_id = current_setting('app.tenant', true));`
```

**Les règles à retenir.**

1. **L'association fait partie de chaque ligne et de chaque clé** :
   `tenant_id` en tête de la clé primaire et de chaque clé étrangère.
2. **La base fait respecter l'isolement**, pas la mémoire des
   développeurs : des politiques de sécurité par ligne.
3. **L'association se déclare pour une transaction**, jamais pour une
   connexion qui retournera dans le pool.
4. **L'application ne se connecte pas en propriétaire des tables** : le
   propriétaire passe à travers les politiques.
5. **Un schéma par association** isole mieux, et coûte à chaque
   migration ; on le choisit pour une raison, pas par défaut.

La suite le mesure sur 40 associations, puis sur 500.

---

Jusqu'ici, l'application servait une tontine. Elle en sert désormais
beaucoup : chaque association s'inscrit, choisit son offre, invite ses
membres. C'est un **SaaS**, et chaque association est un **tenant**
(un locataire). Ce niveau en tire les conséquences : l'isolement, les
rôles, la facturation, les quotas, l'audit, et les webhooks vers les
systèmes des clients. Le premier problème :

> **Comment ranger les données de toutes les associations sans qu'aucune
> ne voie jamais celles d'une autre ?**

Le module de la leçon est `l101`. Il utilise le PostgreSQL 17 du niveau 5
(`sd-pg`, port 55432). Tout ce qui suit est mesuré sur un module vert
sous `gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Trois façons de ranger les associations

Les guides de SaaS d'AWS nomment trois modèles :

| Modèle | Ce qui est partagé | Isolement | Ce qu'il coûte |
|---|---|---|---|
| **silo** : une base par association | rien | le plus fort | une base à créer, sauvegarder et migrer par client |
| **bridge** : un schéma par association | le serveur | fort | des milliers de tables, une migration par schéma |
| **pool** : les mêmes tables pour toutes | tout | celui que le code tient | un filtre à ne jamais oublier |

La plupart des SaaS commencent par le **pool**, parce qu'il ne coûte
presque rien par client. Toute la difficulté est alors de tenir
l'isolement. Les tables de la leçon portent l'association dans chaque
ligne, et en tête de chaque clé :

```go
// Schema is one set of tables for every association: each row carries the
// association it belongs to, and every key starts with it.
const Schema = `
CREATE TABLE associations (
    id   text PRIMARY KEY,
    name text NOT NULL
);
CREATE TABLE members (
    tenant_id text NOT NULL REFERENCES associations (id),
    id        text NOT NULL,
    name      text NOT NULL,
    PRIMARY KEY (tenant_id, id)
);
CREATE TABLE contributions (
    tenant_id text   NOT NULL,
    id        bigint GENERATED ALWAYS AS IDENTITY,
    member_id text   NOT NULL,
    amount    bigint NOT NULL,
    PRIMARY KEY (tenant_id, id),
    FOREIGN KEY (tenant_id, member_id) REFERENCES members (tenant_id, id)
);`
```

## 2. Mesure : le filtre oublié

L'écran de la trésorière a trois lectures : la liste des membres, celle
des membres qui n'ont pas payé, et le travail de fond qui envoie les
rappels. Deux de ces requêtes oublient `WHERE tenant_id = $1` :

```go
// The three reads of the screen. Two of them forget the association: the
// list of unpaid members, and the reminders job.
const (
    membersSQL = `SELECT tenant_id, id, name FROM members
        WHERE tenant_id = $1 ORDER BY id`
    unpaidSQL = `SELECT m.tenant_id, m.id, m.name FROM members m
        WHERE NOT EXISTS (SELECT 1 FROM contributions c
                          WHERE c.tenant_id = m.tenant_id AND c.member_id = m.id)
        ORDER BY m.id`
    remindersSQL = unpaidSQL
)
```

`cmd/leak` envoie 2 000 lectures de 40 associations, de cinq façons :

```text
40 associations of 100 members, 50 of them unpaid; 2000 reads by 8 workers
(members 50 %, unpaid 40 %, reminders job 10 %)

                                                 route       reads  leaking  rows of others  empty
a filter in each query                           members      1018        0               0      0
                                                 unpaid        784      784         1528800      0
                                                 reminders     198      198          386100      0
policies, setting kept by the session            members      1018        0               0      0
                                                 unpaid        784        0               0      0
                                                 reminders     198      190            9500      2
policies, setting for the transaction            members      1018        0               0      0
                                                 unpaid        784        0               0      0
                                                 reminders     198        0               0    198
policies, but logged in as the owner             members      1018        0               0      0
                                                 unpaid        784      784         1528800      0
                                                 reminders     198      198          386100      0
for the transaction, one old route per session   members      1018        0               0      0
                                                 unpaid        784        0               0      0
                                                 reminders     198      193            9650      0
```

- **Un filtre dans chaque requête** : les deux requêtes qui l'oublient
  renvoient, à chaque appel, les membres impayés des 39 autres
  associations. **1 528 800 lignes d'autres associations** pour la seule
  liste des impayés. Aucune erreur, aucun test rouge si les tests n'ont
  qu'une association.
- **Les politiques, réglées pour la session** : la liste des impayés est
  juste, la base filtre à la place du code. Mais le travail de fond ne
  passe pas par le code qui déclare l'association ; il hérite de celle
  que la connexion du pool gardait de la requête précédente. **190
  rappels sur 198 partent vers les membres d'une autre association**
  (entre 186 et 193 selon les exécutions ; les autres tombent sur une
  connexion encore vierge).
- **Les politiques, réglées pour la transaction** : le travail de fond
  ne voit **aucune ligne**. Il est cassé, et cela se voit tout de suite :
  zéro rappel envoyé, au lieu de rappels envoyés aux mauvaises personnes.
  C'est un échec **fermé** : l'oubli refuse, il ne divulgue pas.
- **Les politiques, mais connecté en propriétaire des tables** : rien
  n'est filtré. La documentation de PostgreSQL le dit : le
  superutilisateur et, sauf `FORCE ROW LEVEL SECURITY`, le propriétaire
  passent à travers les politiques.
- **La transaction, avec une ancienne route qui règle encore pour la
  session** : la fuite revient (193 rappels). Une seule ligne restée
  dans le code suffit à laisser un réglage sur des connexions partagées
  par tout le monde.

La version qui tient règle l'association dans la transaction, avec
`set_config(..., true)` (l'équivalent de `SET LOCAL`) :

```go
// LocalSetting sets the association for one transaction only: when it
// ends, the connection goes back to the pool with no association.
func LocalSetting(pool *pgxpool.Pool) Reader {
    return func(ctx context.Context, tenant, route string) ([]Row, error) {
        var out []Row
        err := pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
            if route != "reminders" {
                if _, err := tx.Exec(ctx, "SELECT set_config('app.tenant', $1, true)", tenant); err != nil {
                    return err
                }
            }
            q, args := query(route, tenant)
            var err error
            out, err = collect(tx.Query(ctx, q, args...))
            return err
        })
        return out, err
    }
}
```

Le rôle de l'application est créé à part : il lit et écrit, il ne
possède rien, donc les politiques s'appliquent à lui. Les migrations
tournent avec le propriétaire ; les requêtes, jamais.

## 3. Mesure : une référence qui traverse les associations

Le filtre ne protège que les lectures. Les écritures ont leur propre
fuite : une ligne d'une association qui pointe vers une ligne d'une
autre. L'opérateur de paiement ne connaît le payeur que par son numéro,
et une personne peut être membre de deux associations. La recherche par
numéro oublie l'association :

```go
// Record finds the payer by phone and records the contribution in the
// association that received it. The lookup forgets the association.
func Record(ctx context.Context, pool *pgxpool.Pool, tenant, phone string, amount int64) error {
    var member string
    err := pool.QueryRow(ctx,
        `SELECT id FROM members WHERE phone = $1 ORDER BY id LIMIT 1`, phone).Scan(&member)
    if err != nil {
        return err
    }
    _, err = pool.Exec(ctx,
        `INSERT INTO contributions (tenant_id, member_id, amount) VALUES ($1, $2, $3)`,
        tenant, member, amount)
    return err
}
```

`cmd/crossref` enregistre 2 000 confirmations, avec une clé étrangère
simple, puis avec une clé qui commence par l'association :

```text
40 associations of 100 members; 300 people belong to two of them
2000 confirmations, each for one member of the association paid

                          recorded   to another association  refused
simple foreign key            2000                      129        0
composite foreign key         1871                        0      129
```

- **La clé simple** vérifie que le membre existe, **quelque part** : 129
  cotisations sont enregistrées dans une association au nom d'un membre
  d'une autre. Son tableau est faux des deux côtés.
- **La clé composite** vérifie que le membre existe **dans la même
  association** : les 129 enregistrements sont refusés, et l'erreur
  désigne le bug de recherche.

```go
// CompositeKey checks that the member exists in the same association.
const CompositeKey = members + `
CREATE TABLE contributions (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id text   NOT NULL,
    member_id text   NOT NULL,
    amount    bigint NOT NULL,
    FOREIGN KEY (tenant_id, member_id) REFERENCES members (tenant_id, id)
);`
```

C'est pour cela que la clé primaire du schéma de la section 1 commence
par `tenant_id` : chaque référence doit pouvoir le reprendre.

## 4. Mesure : un schéma par association

Le modèle **bridge** règle la fuite à la racine : chaque association a
ses tables, et une requête sans filtre ne voit que les siennes.
`cmd/schemas` compare 500 associations dans les mêmes tables et 500
schémas :

```text
500 associations of 20 members, each member has paid once

                                    shared tables  one schema each
create and fill                            283 ms          3713 ms
relations in the catalog                        7             2500
total of the platform                        2 ms           167 ms
add a column                                 2 ms          1445 ms
a check that fails at t137             0 migrated     136 migrated
```

- **La création** : 13 fois plus longue, et **2 500 relations** dans le
  catalogue au lieu de 7. Chaque table, index et séquence se multiplie
  par le nombre de clients.
- **Le total de la plateforme** (combien d'argent passe par le service ?)
  demande 500 requêtes au lieu d'une : 80 fois plus long ici, et chaque
  nouvelle association l'allonge.
- **Une migration** devient 500 migrations. Ajouter une colonne passe de
  2 ms à près d'1,5 s.
- **Une migration qui échoue** : dans les tables partagées, PostgreSQL
  l'annule entièrement, et toutes les associations restent à la même
  version. Avec un schéma par association, elle s'arrête à la 137e :
  **136 associations migrées, 364 non**. Le code doit alors vivre avec
  deux versions du schéma, jusqu'à ce que quelqu'un répare.

Le schéma par association se justifie pour une raison précise : une
association qui exige ses données à part, une restauration d'un seul
client, un très gros client qui mérite ses propres ressources. Le guide
d'AWS cite la réglementation et le voisin bruyant comme raisons de
passer en silo une partie du système.

## 5. La campagne

Neuf mutations, dans les politiques, les réglages, les droits et les
clés :

```text
politique qui laisse tout voir               tuee
politique d'écriture ouverte                 tuee
politiques non activées                      tuee
réglage local devenu de session              tuee
filtre oublié partout                        tuee
compte des fuites inversé                    tuee
rôle sans droit d'écrire                     tuee
clé étrangère simple                         tuee
autre membre trouvé                          tuee
9/9 tuees
```

La plus instructive est « rôle sans droit d'écrire » : elle a d'abord
survécu. Le test vérifiait qu'une session de `t001` ne pouvait pas
écrire pour `t002` ; un rôle qui ne peut rien écrire du tout passe ce
test. Le test vérifie maintenant aussi que la session peut écrire pour
elle-même. Un test d'isolement prouve qu'on refuse **et** qu'on accepte.

## 6. La grille

| Pour chaque table et chaque route | À vérifier |
|---|---|
| la ligne | `tenant_id` non nul, en tête de la clé primaire |
| les références | des clés étrangères composites `(tenant_id, ...)` |
| les lectures | une politique de sécurité par ligne, activée sur chaque table |
| le réglage | par transaction (`set_config(..., true)`), posé par un seul endroit du code |
| les connexions | un rôle d'application qui ne possède rien ; le propriétaire pour les migrations seulement |
| les tâches de fond | elles déclarent l'association comme une requête, ou elles ne voient rien |
| les tests | au moins deux associations dans chaque jeu de données |

## 7. Les trois erreurs qui restent

### « Il suffit de relire les requêtes »

Les deux requêtes fautives de la section 2 ont l'air justes, et elles
renvoient des lignes justes quand le jeu de test n'a qu'une
association. La relecture trouve les oublis qu'on cherche ; la politique
de la base attrape ceux qu'on n'a pas imaginés.

### « Les politiques nous protègent, on peut enlever les filtres »

Les politiques sont la seconde ligne. Le filtre dans la requête reste
utile : il dit l'intention au lecteur, et il aide le planificateur à
choisir l'index. Et la section 2 montre deux façons de vider les
politiques de leur sens : le propriétaire, et un réglage laissé sur la
connexion.

### « Un schéma par client, c'est plus propre »

C'est plus isolé. C'est aussi 500 migrations qui peuvent s'arrêter au
milieu, un catalogue qui grossit avec chaque inscription, et des
statistiques de plateforme qui deviennent des boucles. Le choix se fait
association par association : les tables partagées par défaut, un silo
pour celles qui le paient ou l'exigent.

## 8. Le lien avec la production

- **Le contexte** : l'association vient de l'authentification (le jeton,
  le sous-domaine), jamais d'un paramètre que l'appelant choisit. Le
  middleware l'ouvre dans la transaction, le reste du code ne la touche
  pas.
- **Les poolers** : derrière PgBouncer en mode transaction, un réglage
  de session reste sur la connexion du serveur et passe au client
  suivant, quel qu'il soit ; le réglage par transaction est le seul qui
  tienne.
- **Les index** commencent par `tenant_id` : chaque requête d'une
  association ne lit que ses pages.
- **Les tests** créent toujours deux associations, et vérifient que la
  seconde ne voit rien de la première.
- **Les exports et l'administration** : les outils internes qui lisent
  toutes les associations passent par un rôle à part, journalisé
  (leçon 10.5).

## 9. Ce qu'il faut retenir

1. L'association dans chaque ligne et chaque clé.
2. La base fait respecter l'isolement.
3. Réglée pour la transaction, jamais pour la connexion.
4. Jamais connecté en propriétaire.
5. Un schéma par client se choisit pour une raison.

## 10. Approfondissement

### Le silo pour quelques-uns

Les modèles se mélangent. Une plateforme peut garder ses milliers de
petites associations dans les tables partagées, et donner à la grande
mutuelle qui l'exige sa propre base. Le code ne doit alors connaître
qu'une question : « où sont les données de cette association ? ». Un
annuaire (association → base) y répond, et le reste du code est le même.

### Le voisin bruyant

Partager les tables, c'est aussi partager le processeur, les connexions
et le disque. Une association qui lance un gros export ralentit toutes
les autres. La leçon 10.4 mesure ce voisin, et les quotas qui le
contiennent.

## 11. Le réflexe à installer

Devant chaque table, chaque requête et chaque tâche de fond, demande-toi :

1. Où est l'association dans cette ligne, et dans cette clé ?
2. Si la requête oublie le filtre, qui l'arrête ?
3. Avec quel rôle cette connexion parle-t-elle à la base ?
4. Le réglage de l'association peut-il survivre à la requête ?
5. Mes tests ont-ils au moins deux associations ?
