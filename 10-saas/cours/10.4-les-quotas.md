# Leçon 10.4 — Les quotas : ce que chaque offre permet, tenu même sous la concurrence, et sans voisin bruyant

## L'essentiel en deux minutes

**Le problème, en une phrase.** Une limite vérifiée par « je compte, puis
j'ajoute » se laisse dépasser dès que deux personnes ajoutent en même
temps, et une association qui lance un gros travail peut prendre toutes
les connexions dont les autres ont besoin.

**Trois images.**

- **Le taxi-brousse de 15 places** : si deux rabatteurs comptent les
  passagers chacun de leur côté, et chacun en fait monter un dernier
  quand il compte 14, il en part 16. Il faut une seule liste, tenue par
  une seule personne.
- **Le ticket numéroté** : on ne compte pas la foule, on distribue des
  tickets ; quand il n'y en a plus, il n'y en a plus.
- **La file des grossistes** : au marché, le grossiste qui achète cent
  sacs ne passe pas devant la ménagère qui en veut un ; il a sa file, ou
  il est servi deux sacs à la fois.

**Le code, en quelques lignes.** La place se prend en une seule
instruction, qui ne réussit que s'il en reste :

```go
// TakeASeat increments the counter only if it is under the limit, in one
// statement, and inserts the member in the same transaction.
func TakeASeat(ctx context.Context, pool *pgxpool.Pool, tenant, member string) error {
    return pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
        tag, err := tx.Exec(ctx, `UPDATE associations SET members = members + 1
            WHERE id = $1 AND members < max_members`, tenant)
        if err != nil {
            return err
        }
        if tag.RowsAffected() == 0 {
            return ErrFull
        }
        _, err = tx.Exec(ctx, `INSERT INTO members (tenant_id, id) VALUES ($1, $2)`, tenant, member)
        return err
    })
}
```

**Les règles à retenir.**

1. **Vérifier puis agir n'est pas atomique** : entre les deux, une autre
   transaction a vérifié la même chose.
2. **Une limite se tient à un seul endroit** : une ligne verrouillée, un
   compteur mis à jour sous condition, ou une transaction sérialisable
   qu'on sait recommencer.
3. **Une offre limite aussi les ressources partagées** : pas seulement
   ce que l'association possède, mais ce qu'elle occupe en même temps.
4. **Chaque association a sa part de la capacité** : un nombre de
   travaux en cours, ou un pool à part pour les travaux lourds.
5. **Une limite se mesure en concurrence**, pas avec un test qui ajoute
   un membre après l'autre.

La suite le mesure sur 200 associations, puis sur 50.

---

La leçon 10.3 a fait payer chaque offre. Il reste à la faire
respecter : l'offre gratuite admet 50 membres, l'offre standard 500 ;
l'export complet est réservé aux offres payantes. La leçon 9.3 avait
limité le débit de chaque client ; celle-ci limite ce que chaque
association **possède** (des membres) et ce qu'elle **occupe** (des
connexions). Le problème :

> **Comment tenir les limites de chaque offre quand tout arrive en même
> temps, et empêcher une association de priver les autres ?**

Le module de la leçon est `l104`. Il utilise le PostgreSQL 17 du
niveau 5 (`sd-pg`, port 55432). Tout ce qui suit est mesuré sur un
module vert sous `gofmt -l`, `go vet ./...` et `go test -race -count=1
./...`.

## 1. Mesure : trente personnes cliquent sur le même lien

La trésorière envoie le lien d'invitation dans le groupe WhatsApp de
l'association. Trente personnes cliquent dans la même seconde. Il reste
dix places. La première version compte, puis ajoute :

```go
// CountThenInsert counts the members, then inserts if there is room.
// Two transactions can count the same number, and both insert.
func CountThenInsert(ctx context.Context, pool *pgxpool.Pool, tenant, member string) error {
    return pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
        var n, max int
        if err := tx.QueryRow(ctx, `SELECT count(*), (SELECT max_members FROM associations WHERE id = $1)
            FROM members WHERE tenant_id = $1`, tenant).Scan(&n, &max); err != nil {
            return err
        }
        if n >= max {
            return ErrFull
        }
        _, err := tx.Exec(ctx, `INSERT INTO members (tenant_id, id) VALUES ($1, $2)`, tenant, member)
        return err
    })
}
```

`cmd/race` joue la scène dans 200 associations à la fois, chacune avec 40
membres et de la place pour 50 :

```text
200 associations with 40 members and room for 50; in each, 30 people
accept the invitation at the same time

                               joined  refused    above the limit     associations     time
count, then insert               3422     2578               1422              186    970ms
lock the association first       2000     4000                  0                0    1.78s
take a seat in the counter       2000     4000                  0                0     2.2s
serializable, and retry          2000     4000                  0                0    6.01s

serializable: 18683 transactions started again
```

- **Compter, puis ajouter** : **1 422 membres au-delà de la limite**,
  dans 186 associations sur 200 (entre 888 et 1 422 selon les
  exécutions). En `READ COMMITTED`, chaque transaction compte les
  membres validés ; trente transactions comptent 40, et toutes ajoutent.
  Un test qui ajoute un membre après l'autre ne le voit jamais.
- **Verrouiller l'association d'abord** (`SELECT ... FOR UPDATE`) : les
  adhésions d'une même association s'attendent ; chacune compte après la
  précédente. Exactement 10 par association.
- **Prendre une place dans le compteur** : une seule instruction qui
  n'incrémente que s'il reste de la place. PostgreSQL verrouille la ligne
  le temps de la transaction ; la suivante relit la valeur à jour. Exact
  aussi, et le compteur se lit sans rien compter.
- **Sérialisable, et recommencer** : exact, mais trois fois plus lent,
  avec **18 683 transactions recommencées**. PostgreSQL ne suit pas les
  lectures ligne par ligne : il les retient par page, ou par table
  entière (la documentation précise qu'un parcours séquentiel pose
  toujours un verrou sur toute la table). Des adhésions d'associations
  différentes se retrouvent alors en conflit, et l'une des deux
  recommence.

Les deux solutions à verrou ont le même coût mesuré, à quelques
centaines de millisecondes près selon les exécutions. Le compteur a un
avantage de plus : l'offre se lit dans une colonne, et l'écran de la
trésorière affiche « 47 sur 50 » sans compter.

```go
// LockThenCount locks the association's row first: the joins of one
// association wait for each other, and each counts after the last one.
func LockThenCount(ctx context.Context, pool *pgxpool.Pool, tenant, member string) error {
    return pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
        var max int
        if err := tx.QueryRow(ctx, `SELECT max_members FROM associations WHERE id = $1 FOR UPDATE`, tenant).Scan(&max); err != nil {
            return err
        }
        var n int
        if err := tx.QueryRow(ctx, `SELECT count(*) FROM members WHERE tenant_id = $1`, tenant).Scan(&n); err != nil {
            return err
        }
        if n >= max {
            return ErrFull
        }
        _, err := tx.Exec(ctx, `INSERT INTO members (tenant_id, id) VALUES ($1, $2)`, tenant, member)
        return err
    })
}
```

Le compteur doit rester vrai : l'ajout du membre est dans la même
transaction que l'incrément. Si l'ajout échoue (un membre déjà inscrit),
la transaction est annulée, et la place est rendue. Le test
`TestSeatKeepsTheCounterTrue` le vérifie.

## 2. Mesure : le voisin bruyant

Une limite de membres ne suffit pas. La grande association `big` lance
trente exports d'un coup, chacun 300 ms de calcul dans la base. Le pool
de l'application a 10 connexions, partagées par toutes les associations.
`cmd/neighbour` sert pendant ce temps 300 écrans par seconde aux 50
autres associations :

```text
50 associations: 300 screens a second (5 ms each) for 6 s, pool of 10
connections; at 1 s, the association 'big' starts 30 exports of 300 ms

                                    screens      p50      p99      max    exports
one pool, no limit                     1779     5 ms   875 ms   908 ms      930ms
at most 2 at once per association      1779     5 ms    11 ms    35 ms      4.52s
exports on a pool of their own         1779     5 ms     7 ms    32 ms      4.55s
```

- **Un pool, sans limite** : les trente exports prennent les dix
  connexions pendant près d'une seconde. Les écrans des autres
  associations attendent une connexion : **875 ms au 99e centile**, au
  lieu de 5 ms. Le guide de SaaS d'AWS appelle cela le voisin bruyant :
  un utilisateur qui charge les ressources partagées au détriment des
  autres.
- **Au plus deux à la fois par association** : `big` n'occupe jamais
  plus de deux connexions ; ses autres exports attendent **avant** de
  prendre une connexion. Les autres associations restent à 11 ms. Les
  exports de `big` durent 4,5 s au lieu d'une : c'est elle qui paie sa
  charge.
- **Les exports sur un pool à part** (deux connexions), les écrans sur
  les huit autres : le même effet, par type de travail au lieu de par
  association.

```go
// Do runs fn when one of tenant's places is free, or gives up with the
// context.
func (l *Limiter) Do(ctx context.Context, tenant string, fn func() error) error {
    s := l.slot(tenant)
    select {
    case s <- struct{}{}:
    case <-ctx.Done():
        return ctx.Err()
    }
    defer func() { <-s }()
    return fn()
}
```

Les deux protections se complètent. Une limite par association
empêche **une** association de tout prendre ; un pool par type de
travail empêche **les travaux lourds de toutes les associations
ensemble** de tout prendre (cinquante associations qui exportent
chacune deux fichiers, c'est cent exports).

## 3. Les offres, en données

Les limites sont des données de l'offre, pas des constantes dans le
code :

| Offre | Membres | Exports simultanés | SMS par mois | Au-delà |
|---|---|---|---|---|
| gratuite | 50 | 0 | 0 | refus, avec un lien vers l'offre supérieure |
| standard | 500 | 1 | 200 | refus pour les membres ; SMS facturés (leçon 10.3) |
| fédération | 5 000 | 4 | 2 000 | une alerte à 80 %, un appel commercial à 100 % |

Changer d'offre change `max_members` dans la même transaction que
l'abonnement. Passer à une offre **inférieure** quand on a déjà plus de
membres que la nouvelle limite ne supprime personne : on refuse les
nouveaux, on prévient la trésorière, et on décide ensemble.

## 4. La campagne

Dix mutations, dans les quatre façons d'adhérer et dans le limiteur :

```text
verrou oublié                                tuee
un membre de trop (verrou)                   tuee
un siège de trop                             tuee
compteur ignoré                              tuee
lecture répétable au lieu de sérialisable    tuee
pas de nouvelle tentative                    tuee
une place de trop                            tuee
une file pour tous                           tuee
place jamais rendue                          tuee
abandon silencieux                           tuee
10/10 tuees
```

Deux mutations ont d'abord survécu : « verrou oublié » et « pas de
nouvelle tentative ». Le test de concurrence lançait vingt adhésions
dans **une** association, et elles se chevauchaient trop peu pour que la
course apparaisse à chaque fois. Il en lance maintenant vingt dans
chacune de vingt associations ; trois campagnes de suite tuent les deux
mutations. Une course se teste avec assez de concurrence pour qu'elle
arrive à chaque exécution.

## 5. La grille

| Pour chaque limite | À vérifier |
|---|---|
| l'atomicité | la vérification et l'ajout sont une seule opération, ou sous le même verrou |
| la vérité | le compteur change dans la même transaction que ce qu'il compte |
| la source | la limite vient de l'offre en vigueur, lue dans la même transaction |
| l'occupation | les travaux lourds ont une limite par association, et un pool à eux |
| le dépassement | refus clair, avec la limite et l'offre qui la lève ; jamais une suppression |
| les tests | des adhésions simultanées, en nombre, dans plusieurs associations |

## 6. Les trois erreurs qui restent

### « La limite est vérifiée dans l'écran »

L'écran grise le bouton « inviter » à 50 membres. Les trente personnes
qui ont déjà le lien ne passent pas par cet écran. La limite se tient là
où le membre est ajouté, dans la même transaction.

### « Un quota approximatif suffit »

Pour un compteur de SMS facturés, un dépassement de 1 422 est de
l'argent non facturé ou facturé à tort. Pour une offre gratuite, c'est
un client qui n'a plus besoin de payer. Une limite approximative est une
offre qui ne vaut rien.

### « Plus de connexions résoudront le voisin bruyant »

La leçon 9.1 l'a mesuré : au-delà du nombre de cœurs, plus de
connexions servent moins. Et `big` en lancerait simplement plus. La
capacité se partage ; elle ne s'agrandit pas à la demande d'un seul.

## 7. Le lien avec la production

- **Les compteurs** vivent dans la table de l'association, sous les
  politiques de la leçon 10.1 ; un travail de nuit les compare aux vrais
  nombres et alerte au moindre écart.
- **Le limiteur par association** est par instance ; avec trois
  instances, `big` a trois fois deux connexions. Pour une limite
  globale, le compteur de travaux en cours va dans la base ou dans un
  service partagé.
- **Les travaux lourds** passent par une file de travaux, servie par un
  petit nombre de travailleurs, avec un pool de connexions à eux, et
  souvent une réplique en lecture.
- **Les métriques** : utilisation de chaque limite par association,
  refus par cause, attente dans le limiteur ; une association qui
  attend toujours est une association qui a besoin d'une autre offre.

## 8. Ce qu'il faut retenir

1. Compter puis ajouter laisse passer.
2. Une seule instruction conditionnelle, ou un verrou.
3. Le compteur change avec ce qu'il compte.
4. Une part de la capacité par association.
5. Les limites se testent en concurrence.

## 9. Approfondissement

### Les limites douces

Certaines limites préviennent avant de refuser : à 80 % des SMS, un
message ; à 100 %, les SMS continuent mais sont facturés ; à 150 %, un
refus. La règle se décrit en données (seuils, actions), et chaque
franchissement de seuil est un événement, envoyé une fois (leçon 8.3).

### Les contraintes de la base

Une limite simple peut parfois s'écrire comme une contrainte de la base
(une contrainte `CHECK (members <= max_members)` sur le compteur). La
base la tient alors quel que soit le code qui écrit ; il reste à
traduire son erreur en un refus compréhensible.

## 10. Le réflexe à installer

Devant chaque limite, demande-toi :

1. Que se passe-t-il si trente personnes la franchissent dans la même
   seconde ?
2. Où est la seule vérité de cette limite ?
3. Le compteur change-t-il dans la même transaction que ce qu'il compte ?
4. Une association peut-elle, seule, occuper ce que les autres
   partagent ?
5. Mon test lance-t-il assez d'opérations simultanées ?
