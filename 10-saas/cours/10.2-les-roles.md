# Leçon 10.2 — Les rôles : qui peut faire quoi, dans quelle association, et jusqu'à quand

## L'essentiel en deux minutes

**Le problème, en une phrase.** Une même personne peut être trésorière
dans une tontine et simple membre dans une autre, élue pour un an, puis
remplacée : un rôle qui ne dit ni **où** ni **jusqu'à quand** donne des
droits à ceux qui n'en ont plus.

**Trois images.**

- **Le badge d'entreprise** : il ouvre les portes d'un bâtiment, pas de
  tous les bâtiments de la ville. Un rôle vaut dans une association.
- **Le mandat** : la trésorière est élue jusqu'à la prochaine assemblée.
  Le jour de la passation, la clé de la caisse change de main ; on ne
  fait pas un double pour l'ancienne.
- **La liste à l'entrée** plutôt que le bracelet : un bracelet donné le
  matin reste au poignet de celui qu'on vient d'exclure ; la liste, on
  la consulte à chaque passage.

**Le code, en quelques lignes.** Un rôle est donné à une personne, dans
une association, jusqu'à une date ; chaque demande se décide sur les
rôles en vigueur à cet instant :

```go
// Can says whether user may do p in tenant at now: a role they hold
// there, still in force, grants it.
func (d *Directory) Can(user, tenant string, p Permission, now time.Time) bool {
    for _, role := range d.Roles(user, tenant, now) {
        if Allows(role, p) {
            return true
        }
    }
    return false
}
```

**Les règles à retenir.**

1. **Le code demande des permissions**, jamais des noms de rôles : une
   table unique dit ce que chaque rôle permet.
2. **Un rôle vaut dans une association**, pas pour une personne.
3. **Un rôle a une fin** : celle du mandat.
4. **La décision se prend à chaque requête**, sur des rôles lus il y a
   quelques secondes au plus, pas dans un jeton d'une heure.
5. **Ce qui n'est pas écrit est refusé.**

La suite le mesure sur 100 associations.

---

La leçon 10.1 a isolé les associations : une trésorière de `t004` ne
voit pas les données de `t009`. Mais **dans** `t004`, tout le monde
n'a pas le droit de tout faire : un membre consulte, la trésorière
enregistre et verse, le président approuve. C'est l'autorisation par
rôle (RBAC, *role-based access control*). La leçon 9.5 a posé la
question « à qui est cet objet ? » ; celle-ci pose la suivante :

> **Que peut faire cette personne, dans cette association, aujourd'hui ?**

Le module de la leçon est `l102`. Il n'a besoin que de la bibliothèque
standard. Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Des permissions, et des rôles qui les regroupent

Le code ne demande jamais « est-ce une trésorière ? » ; il demande
« peut-elle exécuter un versement ? ». La réponse est dans une table,
à un seul endroit :

```go
// The permissions of the platform.
const (
    ReadMembers        Permission = "members.read"
    InviteMembers      Permission = "members.invite"
    RecordContribution Permission = "contributions.record"
    ReadReports        Permission = "reports.read"
    ApprovePayout      Permission = "payouts.approve"
    ExecutePayout      Permission = "payouts.execute"
    EditSettings       Permission = "settings.edit"
)
```

```go
// Roles says what each role may do. A role that is not listed may do
// nothing, and a permission that is not listed is refused to everyone.
var Roles = map[string][]Permission{
    "member":    {ReadMembers},
    "treasurer": {ReadMembers, RecordContribution, ReadReports, ExecutePayout},
    "president": {ReadMembers, InviteMembers, ReadReports, ApprovePayout, EditSettings},
    "auditor":   {ReadMembers, ReadReports},
}
```

Ajouter un rôle (une commissaire aux comptes qui lit tout et ne touche à
rien) est une ligne de cette table. Avec des tests sur le nom du rôle
éparpillés dans les routes (`if role == "treasurer" || role ==
"president"`), c'est une modification par route, et chaque route
oubliée est un trou ou un refus. L'exercice 3 le fait vivre.

Le NIST décrit le modèle ainsi : chaque utilisateur reçoit un ou
plusieurs rôles, et chaque rôle un ou plusieurs droits.

## 2. Mesure : un rôle par personne, ou par association

La version écrite pour une seule tontine donnait à chaque compte **un**
rôle. Devenue plateforme, elle a gardé ce rôle, et vérifié seulement que
la personne appartient à l'association :

```go
// CanGlobal is the check of the single-tontine version: the user belongs
// to the association, and their one role grants p.
func CanGlobal(a Account, tenant string, p Permission) bool {
    return a.Tenants[tenant] && Allows(a.Role, p)
}
```

`cmd/scope` crée 100 associations et 1 600 utilisateurs, dont 400
entrent dans une seconde association avec un autre rôle. Il compare
chaque décision avec celle d'un rôle par association :

```text
100 associations; 1600 users, 400 of whom belong to a second association
one role per user, compared with a role per user and association:

permission                      wrongly allowed        wrongly refused
payouts.execute                              41                     88
payouts.approve                              21                      0
settings.edit                                21                      0
contributions.record                         41                     88
reports.read                                 56                     82
```

- **41 versements possibles par quelqu'un qui n'est pas trésorier** dans
  l'association : la trésorière de sa première tontine, simple membre
  de la seconde, peut y vider la caisse.
- **88 trésoriers refusés chez eux** : élus trésoriers dans leur seconde
  association, ils n'ont que le rôle de membre de la première.
- **21 personnes peuvent changer les réglages** d'une association où
  elles ne sont pas présidentes.

Les deux erreurs vont ensemble. Les refus sont signalés tout de suite,
parce que la personne se plaint ; les droits en trop ne le sont jamais.
Corriger seulement les refus (« donnons-lui le rôle de trésorier ») les
transforme en droits en trop dans sa première association.

## 3. Mesure : des mandats qui finissent

Dans une tontine, le bureau est élu pour un an. Le jour de la passation,
on donne le rôle à la nouvelle trésorière ; retirer celui de l'ancienne
est une action de plus, que personne ne fait. `cmd/mandates` élit chaque
année, de 2022 à 2026, un président et deux trésoriers dans 100
associations (un tiers réélus) :

```text
100 associations of 20 members; every January, a president and two
treasurers are elected for one year (a third of them re-elected)

                              may execute payouts today    of whom not treasurer
roles given forever                                 622                      422
roles until the mandate ends                        200                        0
```

- **Des rôles donnés pour toujours** : le 14 novembre 2026, **622
  personnes** peuvent exécuter un versement, dont **422 qui ne sont plus
  trésorières**. Chaque élection ajoute des droits ; aucune n'en retire.
- **Des rôles donnés jusqu'à la fin du mandat** : 200, les deux
  trésoriers en exercice de chaque association.

Un rôle porte donc sa date de fin, et la vérification la lit :

```go
// Grant gives a user a role in one association, until a date; a zero
// Until never ends.
type Grant struct {
    User, Tenant, Role string
    Until              time.Time
}
```

```go
func (g Grant) inForce(now time.Time) bool {
    return g.Until.IsZero() || now.Before(g.Until)
}
```

Un rôle sans fin reste possible (le fondateur de la plateforme), mais
c'est un choix écrit, pas un oubli.

## 4. Mesure : les rôles dans le jeton

Pour éviter de lire l'annuaire à chaque requête, beaucoup de systèmes
écrivent les rôles dans le jeton de connexion, signé, valable une
heure. `cmd/revoke` retire 200 trésoriers à 10 h ; chacun continue à
tenter un versement toutes les 10 secondes jusqu'à midi :

```text
200 treasurers removed at 10:00; each tries a payout every 10 s until noon

                                payouts after removal    longest   directory reads per hour
roles in a 60-min token                         38183     59m45s                          1
directory, answers kept 30 s                      221        29s                        100
directory at each request                           0         0s                        360
```

- **Les rôles dans un jeton d'une heure** : **38 183 versements
  autorisés** après le retrait, pendant près d'une heure. Le jeton dit
  vrai sur le passé ; il ne sait rien du retrait.
- **L'annuaire, réponses gardées 30 s** : 221 versements, tous dans les
  29 secondes qui suivent le retrait. C'est la fenêtre choisie.
- **L'annuaire à chaque requête** : aucun versement, au prix de 360
  lectures par heure et par personne, au lieu de 100.

Le jeton répond à la question « **qui** est-ce ? », qui change rarement.
Les rôles répondent à « **que** peut-elle faire ? », qui change à chaque
élection, démission ou exclusion. Le jeton porte l'identité ; les rôles
se lisent dans l'annuaire, avec un cache court :

```go
// Can says whether user may do p in tenant at now.
func (c *Cached) Can(user, tenant string, p authz.Permission, now time.Time) bool {
    if c.kept == nil {
        c.kept = map[[2]string]kept{}
    }
    k := [2]string{user, tenant}
    e, ok := c.kept[k]
    if !ok || now.Sub(e.at) >= c.TTL {
        c.Lookups++
        e = kept{c.Dir.Roles(user, tenant, now), now}
        c.kept[k] = e
    }
    for _, role := range e.roles {
        if authz.Allows(role, p) {
            return true
        }
    }
    return false
}
```

La durée du cache est une exigence, qui se discute avec l'association :
« un trésorier exclu ne peut plus rien faire 30 secondes après ». Pour
les actions les plus graves (un versement), on peut lire l'annuaire
sans cache.

## 5. La campagne

Douze mutations, dans les rôles, les mandats, l'annuaire, le jeton et le
cache :

```text
trésorière qui approuve aussi                tuee
rôle connu = tout permis                     tuee
mandat sans fin                              tuee
mandat d'une seconde de trop                 tuee
rôle valable partout (ajout)                 tuee
révocation partout                           tuee
rôle global sans appartenance                tuee
jeton valable une seconde de trop            tuee
jeton aux rôles inventés                     tuee
réponse gardée une seconde de trop           tuee
réponse gardée pour toujours                 tuee
cache sans association                       tuee
12/12 tuees
```

Les mutations « d'une seconde de trop » sont tuées parce que les tests
vérifient les bornes exactes : refusé à la fin du mandat, pas une
seconde après ; refusé quand la réponse a 30 secondes, pas 31.

## 6. La grille

| Pour chaque action | À vérifier |
|---|---|
| la permission | une permission nommée, dans la table des rôles ; le code ne cite aucun nom de rôle |
| la portée | le rôle est cherché pour cette personne **dans cette association** |
| la durée | chaque rôle a une fin, ou une absence de fin écrite et justifiée |
| la fraîcheur | les rôles sont lus à l'annuaire, avec un cache dont la durée est une exigence |
| le refus | ce qui n'est pas dans la table est refusé |
| les tests | une matrice rôle × permission, plus les bornes des mandats et du cache |

## 7. Les trois erreurs qui restent

### « Un administrateur a tous les droits »

Un rôle « admin » qui passe toutes les vérifications est un rôle dont
personne ne sait ce qu'il permet. Le jour où une permission s'ajoute
(supprimer un membre), l'administrateur l'a sans que personne l'ait
décidé. L'administrateur est un rôle comme les autres, avec sa ligne
dans la table.

### « On mettra des rôles plus fins plus tard »

Les rôles se multiplient vite : « trésorier adjoint », « trésorier
sans versement », « trésorier du groupe nord ». Chaque nouveau rôle doit
répondre à une question : quelle permission différente donne-t-il ? Un
rôle qui n'a pas de permission propre n'est qu'un nom de plus.

### « Le jeton expire dans une heure, c'est court »

Une heure, c'est 38 183 versements dans la mesure. La durée d'un jeton
se juge sur ce qu'une personne exclue peut faire pendant ce temps. Un
jeton court qui ne porte que l'identité, et des rôles lus à l'annuaire,
séparent les deux questions.

## 8. Le lien avec la production

- **L'annuaire** est une table `grants (user_id, tenant_id, role,
  until)`, dans la base de la plateforme, sous les politiques de la
  leçon 10.1.
- **Le cache** est par instance, de quelques secondes ; un événement
  « rôle retiré » (leçon 8.1) peut le vider plus tôt.
- **La passation** est une opération du domaine : « élire le bureau »
  retire les anciens rôles et donne les nouveaux dans la même
  transaction.
- **L'audit** (leçon 10.5) journalise chaque rôle donné et retiré, et
  chaque refus.
- **Au-delà des rôles** : « seule la trésorière qui a créé le versement
  ne peut pas l'approuver » ne s'exprime pas avec des rôles. L'OWASP
  recommande de préférer les attributs et les relations aux rôles seuls
  pour ces règles ; l'exercice 5 en rencontre une.

## 9. Ce qu'il faut retenir

1. Des permissions dans le code, des rôles dans une table.
2. Un rôle vaut dans une association.
3. Un rôle a une fin.
4. L'identité dans le jeton, les rôles dans l'annuaire.
5. Refuser par défaut.

## 10. Approfondissement

### La séparation des tâches

Certaines actions demandent deux personnes : la trésorière prépare le
versement, le président l'approuve. Le contrôle ne porte plus sur un
rôle, mais sur la relation entre la personne et l'objet : celle qui a
préparé ne peut pas approuver, même si elle a les deux rôles. Le
mécanisme est simple ; ce qui compte est de le vérifier au moment de
l'approbation, sur l'objet chargé.

### Les relations

Quand les droits suivent des liens (« le garant d'un prêt peut voir ce
prêt », « le responsable d'un groupe voit les tontines du groupe »), on
parle d'autorisation par relations (ReBAC). Le modèle de la leçon y
mène naturellement : une permission se décide sur la personne, l'objet,
et le lien entre les deux.

## 11. Le réflexe à installer

Devant chaque action protégée, demande-toi :

1. Quelle permission demande-t-elle ?
2. Dans quelle association le rôle est-il cherché ?
3. Jusqu'à quand ce rôle est-il valable ?
4. Combien de temps une personne exclue peut-elle encore agir ?
5. Un test refuse-t-il ce qui n'est pas écrit ?
