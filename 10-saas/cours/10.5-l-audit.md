# Leçon 10.5 — L'audit : savoir qui a fait quoi, et pouvoir le prouver

## L'essentiel en deux minutes

**Le problème, en une phrase.** Le jour où une association demande « qui
a versé ces 200 000 FCFA ? », un journal qui oublie des actions, en
invente, ou peut être réécrit par quelqu'un qui a accès à la base, ne
répond pas.

**Trois images.**

- **Le cahier de caisse aux pages numérotées** : on n'arrache pas une
  page sans que ça se voie ; on ne corrige pas une ligne, on en écrit
  une nouvelle.
- **Le reçu et le paiement dans la même main** : le caissier ne note
  pas le paiement avant de l'encaisser, ni après être parti. Il écrit
  pendant qu'il encaisse.
- **Le double chez le notaire** : chaque soir, on envoie le total du
  jour à quelqu'un d'autre. Si le cahier change, il ne correspond plus
  au double.

**Le code, en quelques lignes.** Chaque entrée est liée à la précédente
par un hachage, et s'écrit dans la transaction de l'action qu'elle
décrit :

```go
// Hash chains e, at position seq, to the hash of the entry before it.
// Every field is written with its length, so that no two entries write
// the same bytes.
func Hash(prev []byte, seq int64, e Entry) []byte {
    h := sha256.New()
    h.Write(prev)
    binary.Write(h, binary.BigEndian, seq)
    for _, f := range []string{e.Tenant, e.Actor, e.Action, e.Object, e.Detail, e.At.UTC().Format(time.RFC3339Nano)} {
        binary.Write(h, binary.BigEndian, int64(len(f)))
        h.Write([]byte(f))
    }
    return h.Sum(nil)
}
```

**Les règles à retenir.**

1. **L'entrée s'écrit dans la même transaction que l'action** : les
   deux existent, ou aucune.
2. **Le journal n'est que complété** : l'application n'a pas le droit de
   le modifier, et des déclencheurs le refusent même au propriétaire.
3. **Chaque entrée est chaînée à la précédente** : une modification ou
   une suppression dans le passé casse la chaîne à cet endroit.
4. **Le dernier maillon sort de la base** chaque nuit : même celui qui
   peut tout réécrire ne peut pas réécrire ce qui est ailleurs.
5. **Une entrée dit qui, quoi, sur quel objet, quand, et dans quelle
   association**, en clair, sans secret.

La suite le mesure sur 2 000 versements et un journal de 10 000 entrées.

---

Les leçons 10.1 et 10.2 ont dit qui peut faire quoi. Il faut maintenant
pouvoir dire, après coup, qui **a fait** quoi. Une association qui se
dispute sur un versement, un auditeur qui contrôle la plateforme, une
enquête après l'incident de la leçon 10.2 : tous demandent le journal.
La leçon 9.4 a parlé des journaux techniques (pour comprendre une
panne) ; celui-ci est un journal **métier**, qui doit être complet,
exact et digne de confiance. Le problème :

> **Comment tenir un journal qui n'oublie rien, n'invente rien, et dont
> on peut prouver qu'il n'a pas été réécrit ?**

Le module de la leçon est `l105`. Il utilise le PostgreSQL 17 du
niveau 5 (`sd-pg`, port 55432). Tout ce qui suit est mesuré sur un
module vert sous `gofmt -l`, `go vet ./...` et `go test -race -count=1
./...`.

## 1. Mesure : quand écrire l'entrée ?

Un versement s'enregistre dans la table `payouts`, et une entrée dans
`audit_log`. L'opérateur refuse 5 % des versements (la transaction est
annulée), et le processus meurt dans 2 % des cas au pire moment.
`cmd/sametx` exécute 2 000 versements de trois façons :

```text
2000 payouts in 20 associations; the operator refuses 5 %, the process dies in 2 %

                              payouts  payouts not journaled entries with no payout
journal after the commit         1891                     39                      0
journal before the payout        1852                      0                    148
journal in the same tx           1852                      0                      0
```

- **Le journal après la validation** : 39 versements sans aucune trace.
  Le processus est mort entre les deux transactions. Ce sont justement
  ceux qu'on cherchera.
- **Le journal avant le versement** : 148 entrées décrivent des
  versements qui n'ont jamais eu lieu (refusés, ou processus mort). Le
  journal accuse quelqu'un d'une action qu'il n'a pas faite.
- **Le journal dans la même transaction** : aucune différence. Une
  action refusée ou interrompue n'a ni versement ni entrée.

```go
// SameTransaction writes the payout and its entry in one transaction:
// both are committed, or neither.
func SameTransaction(ctx context.Context, pool *pgxpool.Pool, p Payout, f Faults) error {
    return pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
        if err := insert(ctx, tx, p, f); err != nil {
            return err
        }
        if err := audit.Record(ctx, tx, entry(p)); err != nil {
            return err
        }
        if f.Crash {
            return ErrCrash
        }
        return nil
    })
}
```

C'est le raisonnement de l'outbox de la leçon 8.2, appliqué au journal :
ce qui doit être vrai en même temps s'écrit en même temps.

## 2. Mesure : qui peut changer le journal ?

`cmd/rights` essaie d'ajouter une entrée, d'en changer une, d'en
supprimer une et de vider le journal, avec quatre identités :

```text
                                               add an entry    change an entry    delete an entry  empty the journal
the application's role                                 done            refused            refused            refused
the owner, no trigger                                  done               done               done               done
the owner, append-only triggers                        done            refused            refused            refused
the owner, who disables them                           done               done               done               done
```

- **Le rôle de l'application** peut ajouter et lire, rien d'autre : il
  n'a reçu que `SELECT` et `INSERT`. Une injection SQL ou un bug de
  l'application ne peut pas effacer de traces.
- **Le propriétaire, sans déclencheur**, peut tout.
- **Le propriétaire, avec les déclencheurs** d'ajout seul : refusé. Une
  migration maladroite (`DELETE FROM audit_log WHERE ...` lancée sur la
  mauvaise base) ne passe plus.
- **Le propriétaire qui désactive d'abord les déclencheurs** peut tout,
  de nouveau.

```go
// AppendOnly refuses UPDATE, DELETE and TRUNCATE on the journal, even to
// its owner.
const AppendOnly = `
CREATE FUNCTION audit_refuse() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'audit_log is append-only';
END $$;
CREATE TRIGGER append_only BEFORE UPDATE OR DELETE ON audit_log
    FOR EACH ROW EXECUTE FUNCTION audit_refuse();
CREATE TRIGGER no_truncate BEFORE TRUNCATE ON audit_log
    FOR EACH STATEMENT EXECUTE FUNCTION audit_refuse();`
```

Les droits et les déclencheurs arrêtent les erreurs et l'application
compromise. Ils n'arrêtent pas celui qui a les clés de la base. Pour
celui-là, il faut une preuve qui ne dépende pas de la base.

## 3. Mesure : la chaîne et l'ancre

Chaque entrée porte le hachage de son contenu, de sa position, et du
hachage de l'entrée précédente. L'écriture verrouille le dernier
maillon de l'association le temps de la transaction : les entrées d'une
association se chaînent l'une après l'autre, même quand elles arrivent
ensemble.

```go
// Record appends e to the association's journal, inside tx: the entry
// exists if and only if what it describes was committed with it. The
// chain's last link is locked until tx ends, so entries of one
// association are chained one after the other.
func Record(ctx context.Context, tx pgx.Tx, e Entry) error {
    e.At = e.At.UTC().Truncate(time.Microsecond)
    if _, err := tx.Exec(ctx, `INSERT INTO audit_heads (tenant_id, seq, hash) VALUES ($1, 0, '')
        ON CONFLICT (tenant_id) DO NOTHING`, e.Tenant); err != nil {
        return err
    }
    var seq int64
    var prev []byte
    if err := tx.QueryRow(ctx, `SELECT seq, hash FROM audit_heads WHERE tenant_id = $1 FOR UPDATE`,
        e.Tenant).Scan(&seq, &prev); err != nil {
        return err
    }
    seq++
    hash := Hash(prev, seq, e)
    if _, err := tx.Exec(ctx, `INSERT INTO audit_log (tenant_id, seq, actor, action, object, detail, at, hash)
        VALUES ($1, $2, $3, $4, $5, $6, $7, $8)`, e.Tenant, seq, e.Actor, e.Action, e.Object, e.Detail, e.At, hash); err != nil {
        return err
    }
    _, err := tx.Exec(ctx, `UPDATE audit_heads SET seq = $2, hash = $3 WHERE tenant_id = $1`, e.Tenant, seq, hash)
    return err
}
```

`cmd/tamper` écrit 10 000 entrées pour une association, envoie le
dernier maillon hors de la base (l'**ancre**), puis laisse quelqu'un qui
a les clés de la base changer le journal de quatre façons :

```text
a journal of 10000 entries; its last link is sent out as an anchor

someone with access to the database           chain broken at anchor holds    verified in
nothing                                                     -         true           24ms
changes the amount of entry 4321                         4321         true           24ms
deletes entry 7000                                       7000         true           23ms
changes entry 4321 and recomputes the chain                 -        false           48ms
deletes the last 50 entries                                 -        false           23ms
```

- **Changer le montant de l'entrée 4 321** : la chaîne casse
  exactement là. L'ancre tient encore, puisque le hachage stocké de la
  dernière entrée n'a pas bougé ; c'est la chaîne qui parle.
- **Supprimer l'entrée 7 000** : la position fait partie du hachage ;
  l'entrée suivante n'est plus à sa place, la chaîne casse à 7 000.
- **Changer l'entrée 4 321 et recalculer toute la chaîne** : celui qui
  connaît l'algorithme refait tous les hachages. La chaîne est de
  nouveau cohérente. **Seule l'ancre le voit** : le dernier maillon
  n'est plus celui qu'on a envoyé hier.
- **Supprimer les 50 dernières entrées** : la chaîne qui reste est
  cohérente, puisque rien avant n'a changé. L'ancre le voit : l'entrée
  10 000 n'existe plus.

Vérifier 10 000 entrées prend environ 25 ms. L'ancre est petite (une
position et 32 octets) ; chaque nuit, la plateforme l'envoie à
l'association, ou la publie là où ni elle ni personne ne peut la
changer. L'OWASP le demande pour les journaux : détecter qu'un
enregistrement a été modifié ou supprimé.

## 4. Ce qu'une entrée contient

| Champ | Pourquoi |
|---|---|
| l'association | chaque association a sa chaîne, et peut la vérifier seule |
| l'acteur | la personne, ou le support avec son ticket (leçon 10.2), ou le travail de fond qui agit |
| l'action | un nom stable : `payout.execute`, `role.grant`, `member.remove` |
| l'objet | ce sur quoi on a agi : `p00421`, `m017` |
| le détail | ce qui change, avant et après : `amount=200000` |
| la date | celle de la base, à la microseconde |

Ce qui n'y va pas : un mot de passe, un code, un numéro complet de
carte. Le journal est lu par des auditeurs, exporté, conservé des
années ; il ne contient rien qu'on regretterait d'avoir écrit.

## 5. La campagne

Dix mutations, dans le hachage, l'écriture, la vérification, les droits
et les versements :

```text
maillon précédent oublié                     tuee
position oubliée                             tuee
champs sans longueur                         tuee
date hors du hachage                         tuee
tête non verrouillée                         tuee
tête jamais avancée                          tuee
ancre jamais comparée                        tuee
vidage permis                                tuee
rôle qui peut changer                        tuee
même transaction sans journal                tuee
10/10 tuees
```

Deux mutations de la première campagne ont survécu, et elles étaient
**équivalentes**. La vérification comparait la position stockée à la
position attendue, en plus du hachage ; or la position fait partie du
hachage, et un trou change toujours le hachage de l'entrée suivante. La
comparaison a été retirée. Et la vérification enchaînait sur le hachage
stocké ; enchaîner sur le hachage recalculé ne change que les maillons
**après** la première cassure, que la vérification ne signale pas. Une
troisième, « rôle qui peut changer », a survécu parce que le seul test
du rôle avait aussi les déclencheurs : les déclencheurs refusaient à la
place des droits. Un test sans déclencheur vérifie maintenant les droits
seuls.

## 6. La grille

| Pour chaque action qui compte | À vérifier |
|---|---|
| le moment | l'entrée s'écrit dans la transaction de l'action |
| les droits | l'application ajoute et lit ; jamais `UPDATE`, `DELETE`, `TRUNCATE` |
| les déclencheurs | ajout seul, même pour le propriétaire |
| la chaîne | par association, avec le contenu, la position et le maillon précédent |
| l'ancre | le dernier maillon sort de la base chaque nuit |
| le contenu | qui, quoi, quel objet, quand, quelle association ; aucun secret |
| la vérification | régulière, automatique, avec une alerte |

## 7. Les trois erreurs qui restent

### « Nos journaux applicatifs suffisent »

Les journaux de la leçon 9.4 sont faits pour comprendre une panne : on
les échantillonne, on les tourne, on les supprime au bout de trente
jours. Un journal d'audit est une donnée métier : complet, conservé,
vérifiable. Les deux ne se remplacent pas.

### « On corrigera l'entrée si elle est fausse »

Une entrée fausse se corrige par une nouvelle entrée (« correction de
l'entrée 4 321 : ... »), comme une facture se corrige par un avoir
(leçon 10.3). Corriger l'entrée elle-même, c'est exactement ce que la
chaîne doit détecter.

### « Une chaîne de hachage, c'est une blockchain »

C'est un mécanisme beaucoup plus simple : un seul écrivain, une base,
une ancre envoyée chaque nuit. La chaîne suffit à prouver qu'un passé
n'a pas changé depuis l'ancre ; elle ne demande ni consensus ni
réseau.

## 8. Le lien avec la production

- **La vérification** tourne chaque nuit pour chaque association, et
  alerte à la première cassure ; c'est l'équivalent du rapprochement de
  la leçon 10.3.
- **L'ancre** part par un canal que la plateforme ne contrôle pas
  seule : un courriel à la présidente, un dépôt chez un tiers, ou un
  journal de transparence public.
- **La rétention** : le journal se garde le temps que la loi ou le
  contrat demande ; on archive par association et par année, avec
  l'ancre de fin d'année.
- **Les volumes** : une chaîne par association évite qu'un seul verrou
  sérialise toute la plateforme ; les associations écrivent en
  parallèle.
- **La lecture** du journal est elle-même journalisée : qui a consulté
  quoi.

## 9. Ce qu'il faut retenir

1. Dans la même transaction que l'action.
2. Ajout seul, par les droits et les déclencheurs.
3. Chaque entrée chaînée à la précédente.
4. Le dernier maillon sort de la base.
5. Qui, quoi, quel objet, quand ; aucun secret.

## 10. Approfondissement

### Les arbres de Merkle

Une chaîne se vérifie du début à la fin. Pour prouver qu'une entrée
précise est dans le journal sans tout relire, ou qu'un journal
d'aujourd'hui prolonge celui d'hier, on range les hachages en arbre :
c'est la structure des journaux de Certificate Transparency (RFC 6962),
qui prouvent leur propriété d'ajout seul par des preuves de cohérence.

### Les entrées signées

Avec une clé privée hors de la base, la plateforme peut signer chaque
ancre : l'association vérifie alors non seulement que le journal n'a
pas changé, mais que l'ancre vient bien de la plateforme.

## 11. Le réflexe à installer

Devant chaque action qui touche à l'argent, aux droits ou aux données
personnelles, demande-toi :

1. Son entrée de journal s'écrit-elle dans la même transaction ?
2. Qui peut modifier ou supprimer cette entrée ?
3. Si quelqu'un la modifie, qu'est-ce qui le détecte, et quand ?
4. Quelle trace de ce journal existe hors de la base ?
5. Que dit l'entrée, et que ne doit-elle jamais dire ?
