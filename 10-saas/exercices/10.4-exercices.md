## Exercice 1 — Compréhension : où passe-t-on ?

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Six situations

Pour chacune, dis si la limite tient, et pourquoi.

1. L'écran grise le bouton « inviter » quand le compteur affiché vaut 50.
2. `SELECT count(*)` puis `INSERT`, dans une transaction `REPEATABLE
   READ`.
3. `UPDATE associations SET members = members + 1 WHERE id = $1 AND
   members < max_members`, puis l'`INSERT` du membre dans une **autre**
   transaction.
4. `SELECT ... FOR UPDATE` sur l'association, puis `count(*)` et
   `INSERT`, dans la même transaction.
5. Le limiteur de `fair` à deux places par association, sur trois
   instances de l'application.
6. Une contrainte `CHECK (members <= max_members)` sur la table des
   associations, et l'incrément sans condition.

### 1.b — Trois pourquoi

1. Pourquoi les exports en trop de `big` attendent-ils **avant** de
   prendre une connexion, et pas après ?
2. Pourquoi passer à une offre inférieure ne supprime-t-il aucun membre ?
3. Pourquoi la transaction sérialisable recommence-t-elle des adhésions
   d'associations qui n'ont rien à voir entre elles ?

### 1.c — Le sens des mesures

Dans `cmd/race`, « compter, puis ajouter » fait entrer entre 888 et
1 422 membres de trop selon les exécutions. Pourquoi ce nombre change-t-il
autant, alors que le code et les données sont les mêmes ? Que donnerait
la même mesure avec un pool de 2 connexions ?

## Exercice 3 — Refactoring : les SMS du mois

*Niveau 3. Réécrire une fonction ; les tests sont fournis.*

Chaque offre a un nombre de SMS de rappel par mois. L'envoi compte ceux
déjà partis, puis enregistre :

```go
// Schema is the SMS sent, and a counter per association and month.
const Schema = `
CREATE TABLE sms_usage (
    tenant_id text NOT NULL,
    month     date NOT NULL,
    used      int  NOT NULL,
    PRIMARY KEY (tenant_id, month)
);
CREATE TABLE sms_log (
    tenant_id text NOT NULL,
    month     date NOT NULL,
    member    text NOT NULL
);`
```

```go
// Send records one SMS of tenant to member in month, if the offer's limit
// allows it. Rewrite it so that it holds the limit when many reminders
// leave at once, with the counter of sms_usage, in the same transaction
// as the log.
func Send(ctx context.Context, pool *pgxpool.Pool, tenant string, month time.Time, member string, limit int) error {
    return pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
        var n int
        if err := tx.QueryRow(ctx, `SELECT count(*) FROM sms_log WHERE tenant_id = $1 AND month = $2`,
            tenant, month).Scan(&n); err != nil {
            return err
        }
        if n >= limit {
            return ErrQuota
        }
        _, err := tx.Exec(ctx, `INSERT INTO sms_log (tenant_id, month, member) VALUES ($1, $2, $3)`,
            tenant, month, member)
        return err
    })
}
```

## Exercice 5 — Incident : les associations pleines à moitié

*Niveau 7. Un incident à mesurer, puis à rejouer comme il aurait dû
être fait.*

En décembre 2026, plusieurs présidentes d'associations gratuites se
plaignent : « l'application dit que nous sommes 50, nous sommes 43 ».
L'équipe exporte le journal des adhésions et des départs de l'année :

```go
// AsItRan plays the journal as the platform did: a join takes a seat in
// the counter if it is under Limit; a leave removes the member, and
// forgets the counter. It returns the joins refused.
func AsItRan(start map[string]int, events []Event) []Event {
    counter := map[string]int{}
    for t, n := range start {
        counter[t] = n
    }
    var refused []Event
    for _, e := range events {
        switch {
        case e.Leave:
            // the member is deleted; the counter is not touched
        case counter[e.Tenant] < Limit:
            counter[e.Tenant]++
        default:
            refused = append(refused, e)
        }
    }
    return refused
}
```
