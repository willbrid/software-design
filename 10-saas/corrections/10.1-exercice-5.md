# Correction 10.1 — Exercice 5 : les rappels du 1er décembre

> Rappel de l'énoncé : des rappels envoyés aux membres d'autres
> associations, une semaine après l'activation des politiques ; mesurer,
> rejouer, rédiger.

L'audit et le rejeu sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **1 950 rappels sur 2 000 mal adressés** : 39 associations sur 40 ont
  envoyé leurs rappels hors de chez elles.
- **Les victimes viennent de 6 associations seulement** : celles que les
  connexions du pool gardaient de la matinée.
- **Avec le réglage par transaction**, plus aucune fuite, mais plus aucun
  rappel ; **avec un travail qui déclare son association**, les 2 000
  rappels arrivent à la bonne personne.

## 1. L'audit

```go
func Audit(sent []Sent, n int) Report {
    r := Report{Sent: len(sent)}
    ran, leaky, exposed := map[string]bool{}, map[string]bool{}, map[string]bool{}
    for _, s := range sent {
        ran[s.For] = true
        if s.Tenant != s.For {
            r.Wrong++
            leaky[s.For] = true
            exposed[s.Tenant] = true
        }
    }
    r.Silent = n - len(ran)
    r.Leaky, r.Exposed = len(leaky), len(exposed)
    return r
}
```

## 2. Les chiffres

`cmd/december` rejoue la matinée trois fois :

```text
1 December 2026: 40 associations, 600 requests, then 40 reminder jobs

                                       sent  wrong  silent  leaky  exposed
as it ran: setting kept by session     2000   1950       0     39        6
setting for the transaction               0      0      40      0        0
the job declares its association       2000      0       0      0        0
```

- **Comme elle s'est passée** : chaque travail de rappels lit
  l'association que sa connexion gardait de la dernière requête de la
  matinée. **1 950 rappels** partent vers des membres d'une autre
  association (entre 1 950 et 2 000 selon les exécutions : parfois une
  connexion garde, par chance, l'association du travail).
- **6 associations exposées** (6 ou 7 selon les exécutions) : le pool n'a
  que 8 connexions, qui ne gardent chacune qu'une association, et les
  travaux ne changent jamais le réglage. Les 40 travaux lisent donc les
  impayés des 6 ou 7 mêmes associations : chacun de leurs membres
  impayés reçoit **plusieurs rappels**, au nom d'associations inconnues.
  C'est ce qui a fait sonner le support.
- **Le réglage par transaction** : aucun rappel n'est envoyé. La fuite
  est fermée, et l'échec se voit dans le tableau de bord dès 9 h.
- **Le travail qui déclare son association** : 2 000 rappels, tous
  justes.

## 3. Le rejeu

```go
// Fixed is the reader the platform should have used: every read,
// the reminders job included, sees only the rows of its association.
func Fixed(pool *pgxpool.Pool) tenancy.Reader {
    requests := tenancy.LocalSetting(pool)
    return func(ctx context.Context, tenant, route string) ([]tenancy.Row, error) {
        if route == "reminders" {
            // The job reads what the screen of unpaid members reads, and
            // goes through the same door: a transaction of its association.
            route = "unpaid"
        }
        return requests(ctx, tenant, route)
    }
}
```

Le travail de rappels n'est pas une exception : il passe par la même
porte que les requêtes, une transaction de son association. L'exercice 2
en est la version générale.

## 4. La cause

**En une phrase** : le travail de rappels ne déclarait pas son
association, et la connexion du pool qu'il recevait gardait celle de la
dernière requête, parce que le middleware la réglait pour la session.

**La cause de la cause** : les politiques avaient été activées comme une
protection complète, alors qu'elles filtrent fidèlement **l'association
déclarée**, quelle qu'elle soit. Le code qui déclare l'association était
dans le middleware HTTP ; tout ce qui ne passe pas par HTTP (travaux de
fond, consommateurs de messages, scripts) était hors de la protection,
sans le savoir. Et les tests n'avaient qu'une association.

## 5. Le compte rendu

1. **Quoi** : le mardi 1er décembre 2026, entre 9 h et 9 h 40, 1 950
   rappels de paiement ont été envoyés à des membres de 6 associations au
   nom de 39 autres associations ; leurs noms et l'existence de leur
   dette ont été exposés.
2. **Cause** : le travail de rappels ne déclarait pas son association ;
   le réglage de session laissé par les requêtes sur les connexions du
   pool a décidé à sa place.
3. **Détection** : par le support, à 9 h 40, après les appels de
   membres ; aucune alerte technique.
4. **Correction** : le travail est arrêté ; l'association est réglée par
   transaction (`set_config(..., true)`) dans une fonction unique
   (`WithTenant`), utilisée par les requêtes **et** les travaux ; les
   rappels sont renvoyés aux bons membres ; les associations exposées et
   leurs membres sont prévenus.
5. **Prévention** : chaque jeu de test a au moins deux associations ; un
   test vérifie qu'une connexion rendue au pool n'a plus d'association ;
   le code ne contient aucun `SET app.tenant` ni `set_config(..., false)`
   ; une alerte surveille les envois dont le destinataire n'appartient
   pas à l'association émettrice.
