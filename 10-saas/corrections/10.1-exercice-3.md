# Correction 10.1 — Exercice 3 : les prêts d'une seule tontine

> Rappel de l'énoncé : réécrire le schéma des prêts et des garanties pour
> plusieurs associations.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **`tenant_id` en tête de chaque clé primaire**, y compris celle des
  garanties.
- **Chaque clé étrangère reprend `tenant_id`** : trois clés composites.
- **Une politique par table**, activée.

## 1. La solution

```go
// Schema is the loans of many associations: the association leads every
// key, every reference repeats it, and the policies keep the application's
// role to the association set in app.tenant.
const Schema = `
CREATE TABLE members (
    tenant_id text NOT NULL,
    id        text NOT NULL,
    name      text NOT NULL,
    PRIMARY KEY (tenant_id, id)
);
CREATE TABLE loans (
    tenant_id text   NOT NULL,
    id        text   NOT NULL,
    borrower  text   NOT NULL,
    amount    bigint NOT NULL,
    PRIMARY KEY (tenant_id, id),
    FOREIGN KEY (tenant_id, borrower) REFERENCES members (tenant_id, id)
);
CREATE TABLE guarantees (
    tenant_id text NOT NULL,
    loan_id   text NOT NULL,
    guarantor text NOT NULL,
    PRIMARY KEY (tenant_id, loan_id, guarantor),
    FOREIGN KEY (tenant_id, loan_id) REFERENCES loans (tenant_id, id),
    FOREIGN KEY (tenant_id, guarantor) REFERENCES members (tenant_id, id)
);
ALTER TABLE members ENABLE ROW LEVEL SECURITY;
ALTER TABLE loans ENABLE ROW LEVEL SECURITY;
ALTER TABLE guarantees ENABLE ROW LEVEL SECURITY;
CREATE POLICY same_tenant ON members
    USING (tenant_id = current_setting('app.tenant', true));
CREATE POLICY same_tenant ON loans
    USING (tenant_id = current_setting('app.tenant', true));
CREATE POLICY same_tenant ON guarantees
    USING (tenant_id = current_setting('app.tenant', true));`
```

```text
ok      example/corrections101/ex3
```

## 2. Les garanties ont leur propre `tenant_id`

Sans `tenant_id`, une garantie ne peut pas dire « mon garant est de la
même association que mon prêt ». La clé vers le prêt dirait que le prêt
existe ; la clé vers le membre dirait que le membre existe ; aucune ne
relie les deux. La colonne répétée est ce qui permet aux **deux** clés
de partager la même association : `(tenant_id, loan_id)` et
`(tenant_id, guarantor)` ne peuvent pointer que dans la même
association, puisqu'elles partagent la colonne.

Elle sert aussi à la politique : sans elle, la politique des garanties
devrait faire une jointure vers les prêts à chaque ligne lue, plus lente
et plus facile à oublier.

## 3. La migration réelle

Ce schéma est un nouveau départ. Sur une base en production, le passage
se fait en plusieurs étapes (la leçon 11.3 y revient) : ajouter
`tenant_id` aux garanties et le remplir depuis les prêts, créer les
contraintes composites avec `NOT VALID` puis les valider, et seulement
ensuite changer les clés primaires.

## Ce qu'il faut retenir

- L'association est une colonne de chaque table, même quand on « pourrait
  la retrouver ».
- Deux clés qui partagent `tenant_id` relient deux lignes de la même
  association.
- Une table oubliée dans les politiques est une table ouverte.
