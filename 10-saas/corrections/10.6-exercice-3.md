# Correction 10.6 — Exercice 3 : le versement qui attend la comptabilité

> Rappel de l'énoncé : réécrire `ExecutePayout` pour qu'il n'appelle plus
> le système de l'association, et écrire `Deliver`.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Le versement et l'événement s'enregistrent ensemble**, sous le même
  verrou (dans une vraie base, dans la même transaction).
- **`Deliver` vide l'outbox, envoie, et remet ce qui n'est pas passé.**
- **Une réponse qui n'est pas un `2xx` n'est pas une livraison.**

## 1. La solution

```go
// ExecutePayout records a payout, and the event that tells the
// association's system, together; it never calls that system.
func (p *Platform) ExecutePayout(ctx context.Context, tenant, id string, amount int64) error {
    body := fmt.Sprintf(`{"type":"payout.executed","id":%q,"amount":%d}`, id, amount)
    p.mu.Lock()
    defer p.mu.Unlock()
    p.Payouts = append(p.Payouts, id)
    p.Outbox = append(p.Outbox, Event{Tenant: tenant, Body: body})
    return nil
}
```

```go
// Deliver tries once to send each event of the outbox, and keeps those
// that were not taken. It returns the number delivered.
func (p *Platform) Deliver(ctx context.Context) int {
    p.mu.Lock()
    pending := p.Outbox
    p.Outbox = nil
    p.mu.Unlock()
    var kept []Event
    delivered := 0
    for _, e := range pending {
        if err := p.send(ctx, e); err != nil {
            kept = append(kept, e)
            continue
        }
        delivered++
    }
    p.mu.Lock()
    p.Outbox = append(kept, p.Outbox...)
    p.mu.Unlock()
    return delivered
}
```

```go
// send posts e; anything but a 2xx answer is a failure.
func (p *Platform) send(ctx context.Context, e Event) error {
    req, err := http.NewRequestWithContext(ctx, "POST", p.Subscribers[e.Tenant], strings.NewReader(e.Body))
    if err != nil {
        return err
    }
    resp, err := p.Client.Do(req)
    if err != nil {
        return err
    }
    resp.Body.Close()
    if resp.StatusCode/100 != 2 {
        return fmt.Errorf("%s answered %s", e.Tenant, resp.Status)
    }
    return nil
}
```

## 2. Ce que devenait le versement

Dans l'ancienne version, l'appel au système de l'association venait
**avant** l'enregistrement du versement : si ce système était en panne,
`ExecutePayout` renvoyait une erreur, et le versement n'était pas
enregistré. Le système de l'association, simple destinataire
d'information, avait le pouvoir d'empêcher la plateforme de verser. Et
s'il répondait `503`, l'ancienne version considérait le versement comme
communiqué.

Personne n'avait voulu cela ; c'est la conséquence d'un appel synchrone
(leçon 8.1).

## 3. Livrer sans perdre

`Deliver` prend l'outbox sous le verrou, puis la relâche pendant les
envois : un versement peut s'enregistrer pendant qu'on livre. À la fin,
les événements gardés sont remis **devant** ceux arrivés entre-temps,
pour garder l'ordre d'émission. Avec plusieurs abonnés, la leçon passe
ensuite à une file par abonné.

## Ce qu'il faut retenir

- Ce que la plateforme fait ne dépend pas de la disponibilité de ceux
  qu'elle prévient.
- Une livraison est un `2xx` ; le reste se garde.
- Un verrou ne se garde pas pendant un appel réseau.
