# Correction 10.4 — Exercice 4 : des limites sur trois instances

> Rappel de l'énoncé : dire où vivent les compteurs de trois sortes de
> limites, ce que coûte chaque vérification, et ce qui arrive quand une
> instance meurt.

## En bref

- **Ce que l'association possède** se compte dans la base, avec les
  données.
- **Ce qu'elle occupe** se compte avec un bail, qui expire si
  l'instance meurt.
- **Ce qu'elle consomme par seconde** se compte au plus près, avec une
  tolérance écrite.

## 1. Les membres et les SMS

| Question | Réponse |
|---|---|
| où | la base, dans la ligne de l'association et dans `sms_usage` |
| instance qui meurt | la transaction est annulée ; la place est rendue d'elle-même |
| coût | rien de plus : la vérification est dans la transaction qui écrit |
| refus | `409` avec la limite, le nombre actuel, et l'offre qui la lève |

Ces limites portent sur des données : leur compteur est une donnée, et
la base les tient pour toutes les instances.

## 2. Les exports simultanés

Le limiteur de la leçon est par instance : trois instances, six exports
par association. Pour une limite globale :

- **une table `export_slots (tenant_id, slot, holder, expires_at)`**,
  avec deux places par association et six pour la plateforme ; un export
  prend une place par un `UPDATE ... WHERE holder IS NULL OR expires_at
  < now()` (une seule instruction, comme la leçon) ;
- **un bail** : la place expire après 2 minutes si l'export ne la
  renouvelle pas. Une instance qui meurt rend ses places à l'expiration
  (leçon 9.6) ;
- **le coût** : un aller et retour vers la base au début, un toutes les
  minutes, un à la fin. Pour des exports de plusieurs secondes, c'est
  négligeable ;
- **le refus** : l'export est mis en file, avec sa position ; la
  trésorière voit « votre export démarrera dans environ 3 minutes ».

## 3. Les requêtes par seconde

Vérifier dans la base à chaque requête coûterait un aller et retour par
requête, sur un compteur que toutes les instances écrivent. Deux choix :

- **une limite par instance**, à 20 / 3 ≈ 7 requêtes par seconde, si
  l'équilibreur répartit à peu près également : simple, sans aller et
  retour, faux de quelques requêtes quand la répartition est inégale ;
- **un compteur partagé** dans un service rapide (un Redis, par
  exemple), avec un aller et retour de moins d'une milliseconde ; si ce
  service est en panne, on applique la limite par instance plutôt que de
  tout refuser.

La tolérance est écrite dans l'offre : « 20 requêtes par seconde,
mesurées sur une minute ». Le refus est un `429` avec `Retry-After`
(leçon 9.3).

## Ce qu'il faut retenir

- Les données se limitent dans la base, avec les données.
- L'occupation se limite avec des baux, qui survivent aux pannes.
- Le débit se limite au plus près, avec une tolérance écrite.
