# Correction 10.3 — Exercice 5 : le 1er novembre

> Rappel de l'énoncé : un travail de débit relancé du début, une clé
> par tentative ; rapprocher, rejouer, rédiger.

Le rapprochement et le rejeu sont dans `ex5` du module de correction,
verts sous `go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **1 223 associations débitées deux fois, 8 870 750 FCFA de trop.**
- **1 200 à cause de la relance**, 23 à cause des réponses perdues
  après la 1 200e facture : la relance multiplie les doubles débits par
  plus de cinquante.
- **Avec une clé tirée de la facture**, aucun double débit.

## 1. Le rapprochement

```go
func Reconcile(invoices []collect.Invoice, op *operator.Operator) Report {
    r := Report{Invoices: len(invoices)}
    for _, inv := range invoices {
        debits := op.Debits(inv.Wallet)
        switch {
        case len(debits) == 0:
            r.Missing++
        case len(debits) > 1:
            r.Twice++
        }
        for i, a := range debits {
            if a != inv.Total {
                r.Wrong++
            }
            if i > 0 {
                r.ExtraFCFA += a
            }
        }
    }
    return r
}
```

## 2. Les chiffres, et le rejeu

`cmd/november` rejoue la journée deux fois :

```text
1 November 2026: 2000 invoices, 3 % of answers lost, the job dies after 1200
invoices and is run again from the start

                               invoices  missing    twice  FCFA too much    wrong
as it ran: a key per attempt       2000        0     1223        8870750        0
a key from the invoice             2000        0        0              0        0
```

- **Comme elle s'est passée** : les 1 200 factures traitées avant
  l'arrêt sont débitées une seconde fois par la relance, puisque chaque
  tentative porte une nouvelle clé. S'y ajoutent les réponses perdues
  des 800 dernières factures : 23 de plus. Les réponses perdues des
  1 200 premières ne se voient pas à part : ces associations sont déjà
  comptées dans les doubles.
- **Avec une clé tirée de la facture** : la relance renvoie les mêmes
  clés ; l'opérateur reconnaît chaque débit déjà fait et répond comme la
  première fois.

## 3. La cause

**En une phrase** : chaque appel à l'opérateur portait une clé neuve,
générée par la bibliothèque HTTP ; ni les nouvelles tentatives ni la
relance n'étaient reconnues comme le même débit.

**La cause de la cause** : la clé d'idempotence avait été vue comme un
réglage technique de la bibliothèque, et non comme l'identité métier du
débit. Le travail n'avait jamais été relancé en production : la
procédure d'astreinte disait « relancer », sans savoir ce que cela
faisait.

## 4. Le compte rendu

1. **Quoi** : le dimanche 1er novembre 2026, 1 223 associations ont été
   débitées deux fois (ou plus) pour leur facture de novembre, 8 870 750
   FCFA de trop au total.
2. **Cause** : le travail, arrêté après 1 200 factures, a été relancé du
   début ; chaque débit portait une clé neuve, et l'opérateur ne pouvait
   pas reconnaître les débits déjà faits.
3. **Détection** : par le support, le lundi, après les premiers appels ;
   aucun rapprochement automatique ne tournait le dimanche.
4. **Correction** : les 1 223 doubles débits sont remboursés à partir
   du rapprochement ; la clé de débit devient `debit-` suivi du numéro de
   facture ; la relance est sûre et documentée comme telle.
5. **Prévention** : un test relance le travail deux fois et vérifie un
   débit par facture ; le rapprochement tourne une heure après chaque
   exécution et alerte au premier double débit ; la procédure
   d'astreinte dit ce qu'une relance fait.
