# Correction 10.6 — Exercice 5 : les numéros d'octobre

> Rappel de l'énoncé : un système qui applique chaque webhook comme il
> arrive ; auditer les rappels du mois, rejouer, rédiger.

L'audit et le rejeu sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **89 rappels mal adressés**, dont **86 vers un numéro plus ancien
  qu'un numéro déjà reçu**.
- **3 membres ont encore un mauvais numéro le 31 octobre**.
- **En ignorant les versions plus anciennes**, il reste 3 rappels mal
  adressés, tous dus au retard d'un événement encore en route à 18 h,
  et aucun mauvais numéro à la fin du mois.

## 1. L'audit

```go
func Audit(history []order.Update, arrivals []order.Arrival, evenings []time.Time, sub order.Subscriber) Report {
    version := map[string]int{}
    byMember := map[string][]order.Update{}
    for _, u := range history {
        version[u.Phone] = u.Version
        byMember[u.Member] = append(byMember[u.Member], u)
    }
    truth := func(member string, at time.Time) string {
        phone := ""
        for _, u := range byMember[member] {
            if !u.Sent.After(at) {
                phone = u.Phone
            }
        }
        return phone
    }
    sorted := slices.Clone(arrivals)
    slices.SortStableFunc(sorted, func(a, b order.Arrival) int { return a.At.Compare(b.At) })
    received := map[string]int{} // member -> highest version received
    var r Report
    i := 0
    for _, evening := range evenings {
        for ; i < len(sorted) && !sorted[i].At.After(evening); i++ {
            sub.Receive(sorted[i])
            received[sorted[i].Update.Member] = max(received[sorted[i].Update.Member], sorted[i].Update.Version)
        }
        for member, seen := range received {
            r.Reminders++
            phone := sub.Phone(member)
            if phone == truth(member, evening) {
                continue
            }
            r.Wrong++
            if version[phone] < seen {
                r.Stale++
            }
        }
    }
    for ; i < len(sorted); i++ {
        sub.Receive(sorted[i])
    }
    for member, h := range byMember {
        if sub.Phone(member) != h[len(h)-1].Phone {
            r.WrongEnd++
        }
    }
    return r
}
```

L'audit distingue deux erreurs. Un rappel **en retard** part vers
l'ancien numéro parce que le changement n'est pas encore arrivé :
c'est la cohérence éventuelle de la leçon 8.4, qui se rattrape au
prochain soir. Un rappel **vers un numéro plus ancien qu'un numéro déjà
reçu** vient d'une réécriture : le système avait le bon numéro, et l'a
remplacé par un ancien. Celui-là ne se rattrape pas tout seul.

## 2. Les chiffres, et le rejeu

`cmd/october` rejoue le mois trois fois :

```text
October 2026: 800 members, 1822 phone changes, a reminder to each member every evening

the federation's system             reminders    wrong   older than known  wrong on 31 Oct
as it ran: each event as it comes       24598       89                 86                3
ignores an older version                24598        3                  0                0
asks the API on each event              24598        3                  0                0
```

- **Chaque événement comme il arrive** : 86 rappels vers un numéro que
  le système avait déjà remplacé, et 3 membres avec un mauvais numéro à
  la fin du mois, jusqu'à leur prochain changement. Les membres qui
  changent de numéro deux fois en quelques minutes sont ceux qui ont été
  touchés : la nouvelle tentative de l'ancien changement arrive 10
  minutes plus tard, après le nouveau.
- **En ignorant une version plus ancienne** : il reste 3 rappels en
  retard (un changement fait juste avant 18 h, livré juste après), et
  aucun numéro faux à la fin.
- **En relisant l'API à chaque événement** : le même résultat, avec un
  appel à l'API par événement.

## 3. La cause

**En une phrase** : le système de la fédération appliquait chaque
changement de numéro dans l'ordre d'arrivée, et les nouvelles tentatives
de la plateforme livraient parfois un ancien changement après le
nouveau.

**La cause de la cause** : la plateforme envoyait une version dans
chaque événement, mais sa documentation n'en parlait pas, et ne disait
pas que l'ordre n'était pas garanti. La fédération a écrit le code le
plus simple, raisonnable dans un monde où rien n'est réessayé.

## 4. Le compte rendu

1. **Quoi** : en octobre 2026, 89 rappels de la fédération sont partis
   vers d'anciens numéros, dont 86 parce que son système avait remplacé
   un numéro récent par un ancien ; 3 membres avaient encore un mauvais
   numéro le 31 octobre.
2. **Cause** : les événements réessayés arrivaient après des événements
   plus récents, et le système de la fédération ne comparait pas les
   versions.
3. **Détection** : par des membres qui ne recevaient plus de rappels, et
   par le nouveau titulaire d'un ancien numéro.
4. **Correction** : le système de la fédération ignore désormais une
   version plus ancienne que celle qu'il a ; la plateforme renvoie
   l'état courant des 800 membres pour remettre le tableau à jour.
5. **Prévention** : la documentation des webhooks dit en tête que
   l'ordre n'est pas garanti et que chaque objet porte une version ; un
   exemple de code d'abonné l'utilise ; la plateforme propose des
   événements-signaux pour les abonnés qui préfèrent relire l'API.
