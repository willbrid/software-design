# Correction 10.1 — Exercice 4 : trois clients, trois modèles ?

> Rappel de l'énoncé : choisir pool, bridge ou silo pour une petite
> tontine, une mutuelle exigeante et une fédération, et dire comment le
> code s'y retrouve.

## En bref

- **La petite tontine** : dans les tables partagées.
- **La mutuelle** : un silo, parce que le contrat l'exige et qu'elle le
  paie.
- **La fédération** : dans les tables partagées, avec une notion de
  groupe au-dessus des associations.
- **Un annuaire** dit au code où sont les données de chaque association.

## 1. Les trois choix

| Client | Modèle | Pourquoi | Ce que ça coûte |
|---|---|---|---|
| tontine de Mokolo | pool | 35 membres, offre gratuite : son coût doit être presque nul | rien de plus que la grille de la leçon |
| mutuelle | silo | le contrat exige une base à part, sauvegardée et restaurée seule ; 40 000 adhérents justifient des ressources dédiées | une base à créer, surveiller, sauvegarder, migrer ; une migration de plus à chaque version, qui peut échouer seule |
| fédération | pool | 200 petites tontines : 200 schémas coûteraient comme la section 4 de la leçon, sans raison | une politique de plus, pour le tableau consolidé |

Le bridge (un schéma par association) n'a ici pas de client : il est
moins isolé que le silo (même serveur, mêmes ressources) et presque
aussi coûteux à migrer.

## 2. Un code, plusieurs modèles

Le code ne demande jamais « dans quel modèle est cette association ? » ;
il demande « donne-moi une transaction pour cette association ». Un
annuaire répond :

| association | base | modèle |
|---|---|---|
| `t001` à `t812` | `pool-1` | partagé |
| `mutuelle` | `silo-mutuelle` | dédié |

La fonction de l'exercice 2 (`WithTenant`) prend l'association, consulte
l'annuaire, choisit le pool de la bonne base, puis ouvre la transaction
avec le réglage. Dans le silo, les politiques restent en place : elles ne
coûtent presque rien, et le même code de migration sert partout.

## 3. La fédération

Deux niveaux d'appartenance : chaque tontine est une association ; la
fédération est un **groupe** d'associations. La politique accepte deux
réglages :

- une session d'une tontine voit ses lignes (`app.tenant`) ;
- une session de la fédération voit les lignes de ses tontines
  (`app.group`, et une table `group_members (group_id, tenant_id)`).

Le tableau consolidé tourne avec le réglage de groupe, en lecture seule.
Les écritures se font toujours au nom d'une tontine. Et la leçon 10.2
ajoute ce qui manque : qui, à la fédération, a le droit de voir le
tableau.

## Ce qu'il faut retenir

- Le modèle se choisit par client, pour une raison écrite.
- Le code passe par un annuaire, jamais par un `if` sur le modèle.
- Un regroupement d'associations est une nouvelle portée, pas une
  exception à l'isolement.
