# Exercices 11.2 — Partitionner

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 11.2](../cours/11.2-partitionner.md) (`internal/pg`, `shard`,
`partition`), recopiés tels quels dans le module des exercices. Les
exercices 2 et 3 utilisent le PostgreSQL 17 du niveau 5 (`sd-pg`, port
55432). Tout le code ci-dessous compile et passe `go vet` ; les chiffres
de la plateforme sont **fictifs**.

## Exercice 1 — Compréhension : couper ou pas ?

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Six décisions

Pour chacune, dis si elle est justifiée, ce qu'elle apporte et ce
qu'elle coûte.

1. Partitionner par mois le journal d'audit (leçon 10.5), gardé dix ans.
2. Partitionner par association la table des membres, pour que chaque
   association ait « sa » partition.
3. Répartir les membres entre bases par `hash(id) % 8`.
4. Répartir par association, et mettre la fédération seule sur sa base.
5. Garder la table des offres et des taux de taxe sur chaque base.
6. Partitionner les cotisations par mois et chercher les doublons de
   l'opérateur avec un index unique sur la référence.

### 1.b — Trois pourquoi

1. Pourquoi un `DELETE` d'un an de lignes ne rend-il pas la place sur
   le disque ?
2. Pourquoi le hachage cohérent déplace-t-il presque le minimum, mais
   répartit-il moins bien que des cases ?
3. Pourquoi la clé de répartition doit-elle être dans chaque clé
   primaire dès aujourd'hui, même sans répartir ?

### 1.c — Le sens des mesures

Dans `cmd/hotshard`, couper la fédération en ses tontines fait passer
la base la plus chargée de 3,36 à 1,79 fois la moyenne, et pas à 1,0.
D'où vient le reste ? Que ferais-tu ensuite ?

## Exercice 3 — Évolution : l'unicité perdue

*Niveau 8. Faire évoluer un schéma sans perdre une garantie.*

En passant aux partitions mensuelles, la référence de l'opérateur n'est
plus unique sur toute la table (leçon, section 1). Une table à part la
garde :

```go
// Schema adds to partition.Partitioned a table of the references already
// recorded, not partitioned.
const Schema = `
CREATE TABLE operator_refs (
    ref     text        PRIMARY KEY,
    paid_at timestamptz NOT NULL
);`
```

```go
// Record writes c. Rewrite it so that a reference already recorded, in
// any month, is refused with ErrDuplicate, and nothing is written.
func Record(ctx context.Context, pool *pgxpool.Pool, c Contribution) error {
    _, err := pool.Exec(ctx, `INSERT INTO contributions (tenant_id, id, paid_at, amount, operator_ref)
        VALUES ($1, $2, $3, $4, $5)`, c.Tenant, c.ID, c.PaidAt, c.Amount, c.Ref)
    return err
}
```

## Exercice 4 — System design : répartir la fédération nationale

*Niveau 6. Une page, un schéma.*

La fédération nationale (300 000 associations, 12 millions de membres)
signe. Dans dix-huit mois, une base ne suffira plus. Conçois la
répartition : la clé, la table des cases et où elle vit, le routage des
requêtes, ce que deviennent les requêtes qui traversent les
associations (statistiques de la plateforme, recherche d'un membre par
téléphone), et la migration d'une base à huit sans arrêter le service.

## Exercice 5 — Problème ouvert : partitionner, maintenant ?

*Niveau 10. Une décision argumentée, écrite comme une ADR.*

En novembre 2026, la plateforme a une base de 40 Go. Les cotisations
grandissent de 1,5 Go par mois ; le journal d'audit de 2 Go par mois ;
les livraisons de webhooks de 3 Go par mois, gardées 30 jours. Le
contrat avec les associations dit : cotisations en ligne deux ans, puis
archivées ; journal d'audit dix ans. Le `VACUUM` de la table des
livraisons prend déjà 40 minutes chaque nuit.

Que partitionnes-tu, comment, quand ? Que refuses-tu de faire ? Écris
l'ADR, avec les nombres qui la justifient, et ce qui te ferait changer
d'avis.
