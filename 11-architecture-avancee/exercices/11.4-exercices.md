# Exercices 11.4 — La reprise après sinistre

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 11.4](../cours/11.4-la-reprise-apres-sinistre.md) (`internal/pg`,
`replica`, `backup`), recopiés tels quels dans le module des exercices.
L'exercice 3 utilise le PostgreSQL 17 du niveau 5 (`sd-pg`, port
55432). Tout le code ci-dessous compile et passe `go vet` ; l'incident
est **fictif**.

## Exercice 1 — Compréhension : qu'est-ce qui protège de quoi ?

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Six sinistres

Pour chacun, dis ce qui le rattrape (réplique asynchrone, réplique
synchrone, sauvegarde de nuit, journal archivé, copie dans un autre
compte), ce qui est perdu, et combien de temps le service s'arrête à
peu près.

1. Le disque du primaire meurt à 14 h.
2. Un développeur lance `DELETE FROM contributions` sans `WHERE` à 11 h
   12.
3. Le centre de données entier est inondé.
4. Un attaquant obtient les droits d'administration du compte du
   fournisseur et supprime les machines et les sauvegardes du compte.
5. La réplique synchrone ne répond plus pendant 30 s.
6. Un bug écrit des montants faux depuis trois jours.

### 1.b — Trois pourquoi

1. Pourquoi la perte d'une réplique asynchrone dépend-elle surtout de
   ses pauses, et pas de son retard moyen ?
2. Pourquoi une réplique synchrone unique peut-elle arrêter les
   écritures ?
3. Pourquoi la restauration dure-t-elle plusieurs fois la sauvegarde ?

### 1.c — Le sens des mesures

Dans `cmd/replication`, la perte moyenne en asynchrone est de 0,70
écriture, mais le maximum de 68. Lequel des deux chiffres écris-tu dans
le RPO, et pourquoi ?

## Exercice 5 — Incident : le 30 novembre à 18 h 03

*Niveau 7. Un incident à mesurer, puis à rejouer comme il aurait dû
être fait.*

Le 30 novembre 2026, à 18 h 03, le disque du primaire meurt. L'astreinte
promeut la réplique, dans une autre région, en neuf minutes. Le
lendemain, des trésorières montrent des SMS de confirmation pour des
cotisations que la plateforme ne connaît pas. La soirée se rejoue
ainsi :

```go
// Evening plays 30 November 2026 from 18:00: contributions arrive at 73 a
// second (the peak of lesson 11.1); the replica, in another region (40 ms
// away), writes each in about 2 ms; from 18:02:58.2 to 18:03:01 its disk
// pauses. sync says whether the primary waits for the replica before
// confirming. Evening returns the writes until 18:04.
func Evening(sync bool) []replica.Write {
    r := rand.New(rand.NewPCG(2026, 11))
    lag := replica.TypicalLag(40 * time.Millisecond)
    pause, resume := Crash-1800*time.Millisecond, Crash+time.Second
    var ws []replica.Write
    var at, applied time.Duration
    for at < 4*time.Minute {
        at += time.Duration(r.ExpFloat64() / 73 * float64(time.Second))
        done := at + time.Millisecond
        reach := done + lag(r)
        if reach >= pause && reach < resume {
            reach = resume
        }
        applied = max(applied, reach)
        w := replica.Write{Asked: at, Committed: done, Replicated: applied}
        if sync {
            w.Committed = max(done, applied) + 20*time.Millisecond
        }
        ws = append(ws, w)
    }
    return ws
}
```
