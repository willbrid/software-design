# Leçon 11.3 — Changer sans arrêter : des migrations qui ne bloquent personne

## L'essentiel en deux minutes

**Le problème, en une phrase.** Sur un service qui ne s'arrête jamais,
une migration de schéma peut bloquer toutes les écritures pendant des
secondes, figer chaque requête derrière elle, ou casser le code qui
tourne encore dans l'ancienne version.

**Trois images.**

- **Refaire la route sans fermer la circulation** : on ouvre une voie
  provisoire, on fait passer les voitures, on refait l'ancienne voie,
  puis on supprime la provisoire.
- **Le camion qui attend au carrefour** : s'il s'arrête au milieu en
  attendant qu'une voiture devant lui démarre, toute la file derrière
  lui attend aussi. Mieux vaut qu'il recule et repasse dans une minute.
- **Le changement d'adresse** : on reçoit le courrier aux deux adresses
  pendant quelques mois, avant de fermer l'ancienne boîte.

**Le code, en quelques lignes.** La migration n'attend son verrou que
quelques dizaines de millisecondes ; si elle ne l'obtient pas, elle
s'efface et réessaie :

```go
// Cautiously runs ddl with a short lock_timeout, and tries again after a
// pause when it could not get its lock in time: it never makes other
// queries wait more than timeout behind it.
func Cautiously(ctx context.Context, pool *pgxpool.Pool, ddl string, timeout, pause time.Duration, tries int) (Attempts, error) {
    start := time.Now()
    var a Attempts
    for a.Tries < tries {
        a.Tries++
        err := pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
            if _, err := tx.Exec(ctx, "SELECT set_config('lock_timeout', $1, true)", timeout.String()); err != nil {
                return err
            }
            _, err := tx.Exec(ctx, ddl)
            return err
        })
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) && pgErr.Code == "55P03" { // lock_not_available
            time.Sleep(pause)
            continue
        }
        a.Took = time.Since(start)
        return a, err
    }
    a.Took = time.Since(start)
    return a, errors.New("migrate: lock not obtained")
}
```

**Les règles à retenir.**

1. **On sait ce que chaque instruction verrouille, et combien de
   temps** : certaines sont instantanées, d'autres réécrivent la table.
2. **Une migration attend son verrou avec un délai court**
   (`lock_timeout`), et réessaie : elle ne doit jamais faire la queue
   devant tout le monde.
3. **Les index se créent `CONCURRENTLY`**, les contraintes `NOT VALID`
   puis `VALIDATE`.
4. **Un renommage se fait en plusieurs déploiements** : ajouter, écrire
   les deux, recopier, lire le nouveau, supprimer l'ancien.
5. **À chaque instant, deux versions du code tournent** : le schéma doit
   convenir aux deux.

La suite le mesure sur une table de deux millions de membres.

La leçon 11.2 a décidé de partitionner certaines tables ; la leçon 10.1
a ajouté `tenant_id` à toutes les clés. Sur la plateforme, chaque
changement de ce genre se fait **en production**, pendant que des
milliers de trésorières travaillent, et pendant que le déploiement remplace
les instances une à une. Le problème :

> **Comment changer le schéma d'une base qui ne s'arrête jamais, servie
> par un code qui n'est jamais tout entier dans la même version ?**

Le module de la leçon est `l113`. Il utilise le PostgreSQL 17 du
niveau 5 (`sd-pg`, port 55432). Tout ce qui suit est mesuré sur un
module vert sous `gofmt -l`, `go vet ./...` et `go test -race -count=1
./...`.

## 1. Mesure : ce que chaque changement bloque

`cmd/ddl` applique neuf changements courants à une table de deux
millions de membres, pendant qu'un écrivain ajoute un membre chaque
milliseconde ; il mesure la durée du changement et l'insertion la plus
longue pendant ce temps :

```text
2 000 000 members; a writer inserts one member every millisecond

change                                                           took     longest insert
ADD COLUMN note text                                             39ms               14ms
ADD COLUMN joined date DEFAULT '2026-01-01'                      34ms               18ms
ADD COLUMN token uuid DEFAULT gen_random_uuid()                8.493s             8.368s
ALTER COLUMN amount TYPE bigint                                2.628s             2.583s
ADD CHECK (amount > 0)                                          183ms              163ms
ADD CHECK (amount > 0) NOT VALID                                 39ms               21ms
  then VALIDATE CONSTRAINT                                      153ms               22ms
CREATE INDEX ON members (phone)                                4.844s             4.846s
CREATE INDEX CONCURRENTLY ON members (phone)                   5.181s               89ms
```

- **Ajouter une colonne**, vide ou avec une valeur par défaut fixe :
  quelques millisecondes. PostgreSQL range la valeur par défaut dans le
  catalogue, sans toucher aux lignes.
- **Ajouter une colonne avec une valeur par défaut calculée**
  (`gen_random_uuid()`), ou **changer le type d'une colonne** : la table
  et ses index sont **réécrits**. Les écritures sont bloquées tout du
  long : **8,4 s** et **2,6 s** ici (entre 6,8 et 8,5 s, et entre 2,6 et
  4,2 s selon les exécutions).
- **Une contrainte `CHECK`** lit toute la table sous un verrou qui
  bloque les écritures. En deux temps, `NOT VALID` (instantané, vaut
  pour les nouvelles lignes) puis `VALIDATE` (lit la table sans bloquer
  les écritures), l'insertion la plus longue reste vers 20 ms.
- **Un index** : `CREATE INDEX` bloque les écritures pendant toute sa
  construction, **4,8 s**. `CONCURRENTLY` prend un peu plus longtemps,
  mais l'insertion la plus longue reste sous 100 ms (jusqu'à 570 ms dans
  une exécution, pendant ses phases d'attente).

La règle se lit dans la documentation de chaque instruction ; la mesure
la confirme sur la vraie table. Une migration qui réécrit une table de
production se refait autrement : une nouvelle colonne, remplie par lots,
puis une bascule.

## 2. Mesure : la file derrière la migration

Même un changement instantané peut tout bloquer. Un rapport lit la table
des membres pendant 3 s. À 0,5 s, la migration ajoute une colonne : il
lui faut un verrou exclusif, elle attend la fin du rapport. Pendant ce
temps, l'écran des trésorières lit un membre 200 fois par seconde.
`cmd/lockqueue` :

```text
a report reads the members for 3 s; at 0.5 s, ADD COLUMN; 200 screens a second for 5 s

                                screens      p50      p99        max       over 1 s ALTER at
plain ALTER TABLE                  1000    88 ms  2503 ms    2542 ms            316       3s
lock_timeout 100 ms, retries       1000     0 ms    95 ms     116 ms              0     3.1s
```

- **L'`ALTER TABLE` ordinaire** : la migration attend le rapport, et
  **chaque lecture arrivée après elle attend derrière elle**, car
  PostgreSQL sert les verrous dans l'ordre de la demande. **316 écrans
  sur 1 000 attendent plus d'une seconde**, jusqu'à 2,5 s : une panne de
  2,5 s, causée par un changement « instantané ».
- **Avec un `lock_timeout` de 100 ms et des tentatives** : la migration
  n'attend jamais plus de 100 ms ; si elle n'a pas son verrou, elle
  s'efface, laisse passer les écrans, et réessaie 400 ms plus tard. Le
  pire écran attend un peu plus de 100 ms. La migration se fait au même
  moment (3,1 s), dès la fin du rapport.

## 3. Mesure : renommer une colonne pendant un déploiement

La colonne `phone` doit devenir `msisdn`. Le code est déployé instance
par instance : pendant dix secondes, l'ancienne et la nouvelle version
servent ensemble. Trois versions du code :

```go
// The versions of the code.
var (
    // V1 is the code before the change.
    V1 = Version{"v1", `SELECT phone FROM members WHERE id = $1`,
        `UPDATE members SET phone = $2 WHERE id = $1`}
    // V2 writes both columns, and reads the new one when it is filled.
    V2 = Version{"v2", `SELECT coalesce(msisdn, phone) FROM members WHERE id = $1`,
        `UPDATE members SET phone = $2, msisdn = $2 WHERE id = $1`}
    // V3 knows only the new column.
    V3 = Version{"v3", `SELECT msisdn FROM members WHERE id = $1`,
        `UPDATE members SET msisdn = $2 WHERE id = $1`}
)
```

`cmd/rename` sert 300 requêtes par seconde pendant 16 s, un tiers
d'écritures, et compte les erreurs et les numéros perdus :

```text
10 000 members; 300 requests a second for 16 s, a third of them change a number;
the code is deployed instance by instance

                                           requests     errors     numbers lost
rename, then deploy v3                         4800       1556                0
add and copy, then deploy v3                   4800          0              465
expand, v2, backfill, v3, contract             4800          0                0
```

- **Renommer, puis déployer** : l'ancienne version ne trouve plus
  `phone`. **1 556 requêtes en erreur**, un tiers du trafic, pendant tout
  le déploiement. Déployer d'abord ne vaudrait pas mieux : la nouvelle
  version ne trouverait pas `msisdn`.
- **Ajouter, recopier, puis déployer la version qui ne connaît que
  `msisdn`** : aucune erreur, mais **465 numéros perdus**. Les anciennes
  instances continuent d'écrire dans `phone` après la copie ; la
  nouvelle version ne lit que `msisdn`. Aucune erreur ne le signale.
- **Étendre, puis contracter** : on ajoute `msisdn` ; on déploie une
  version qui écrit **les deux** colonnes et lit la nouvelle si elle est
  remplie ; quand plus aucune ancienne instance ne tourne, on recopie ce
  qui diffère ; on déploie la version qui ne connaît que `msisdn` ; puis
  on supprime `phone`. Aucune erreur, aucun numéro perdu.

```go
// Backfill copies phone into msisdn where they differ: to run once no
// instance of V1 is left, since V2 keeps the two equal from then on.
const Backfill = `UPDATE members SET msisdn = phone WHERE msisdn IS DISTINCT FROM phone`
```

La recopie a lieu **après** le départ de la dernière ancienne instance :
avant, une ancienne instance pourrait encore écrire dans `phone` seule.
C'est l'ordre des étapes qui fait la correction, pas les étapes.

## 4. La campagne

Six mutations, dans la prudence de la migration et dans les versions :

```text
pas de délai de verrou                       tuee
abandon au premier refus                     tuee
une tentative de trop                        tuee
v2 n'écrit que la nouvelle colonne           tuee
v2 lit une colonne vide                      tuee
remplissage des vides seulement              tuee
6/6 tuees
```

« V2 lit une colonne vide » a d'abord survécu : la fonction `Run` ne
rendait que l'erreur, et lire `NULL` n'en est pas une. Elle rend
maintenant la valeur lue, et le test vérifie que la version 2 lit
l'ancien numéro tant que le nouveau est vide.

## 5. La grille

| Pour chaque migration | À vérifier |
|---|---|
| le verrou | lequel, combien de temps, sur une table de la taille de la production |
| la réécriture | jamais en une instruction sur une grosse table : colonne neuve, remplissage par lots, bascule |
| l'attente | `lock_timeout` court, tentatives espacées, abandon propre |
| les index | `CREATE INDEX CONCURRENTLY` ; et sa reprise s'il échoue (l'index invalide reste à supprimer) |
| les contraintes | `NOT VALID`, puis `VALIDATE` |
| les versions | chaque étape convient au code d'avant et au code d'après |
| l'ordre | étendre, écrire les deux, recopier quand l'ancien code est parti, lire le nouveau, contracter |

## 6. Les trois erreurs qui restent

### « C'est une petite migration, elle est instantanée »

Elle l'est, quand elle a son verrou. La section 2 montre qu'une
migration instantanée, qui attend derrière un rapport de trois secondes,
fait attendre tout le monde deux secondes et demie. La durée d'une
migration, c'est la durée de son attente plus la durée de son travail.

### « On fera la migration la nuit »

La plateforme n'a pas de nuit : les tontines du Canada et du Cameroun ne
dorment pas à la même heure, les travaux de fond tournent la nuit, et
une migration de nuit sans procédure est une migration faite par une
personne fatiguée. Une migration qui ne bloque personne se fait à 15 h.

### « Un renommage, c'est une ligne »

Une ligne de SQL, et trois déploiements. Le coût réel d'un renommage
fait réfléchir : bien des colonnes gardent un nom imparfait, documenté,
plutôt que de passer par cinq étapes.

## 7. Le lien avec la production

- **Les migrations sont du code** : versionnées, revues, testées sur une
  copie de la production (taille réelle), avec la durée et le verrou de
  chaque étape notés dans la revue.
- **L'outil de migration** pose `lock_timeout` et `statement_timeout`
  par défaut, et refuse les instructions connues pour réécrire une
  grosse table.
- **Les étapes d'un changement en plusieurs déploiements** sont suivies
  comme une tâche : on n'oublie pas la contraction.
- **Le retour arrière** : chaque étape d'extension se défait sans perte ;
  la contraction est la seule étape irréversible, et vient en dernier.

## 8. Ce qu'il faut retenir

1. Chaque instruction a son verrou et sa durée.
2. Un délai de verrou court, et des tentatives.
3. `CONCURRENTLY` et `NOT VALID`.
4. Étendre, écrire les deux, recopier, lire le nouveau, contracter.
5. Le schéma convient toujours à deux versions du code.

## 9. Approfondissement

### Les lots

Remplir une colonne neuve sur deux millions de lignes en une instruction
réécrit autant de lignes qu'un `ALTER TYPE`, en une seule transaction.
On remplit par lots de quelques milliers, chacun dans sa transaction,
avec une pause entre deux : la leçon 11.5 mesure ces traitements de
masse.

### Les vues comme adaptateurs

Pour un renommage de table, une vue qui porte l'ancien nom et lit la
nouvelle table permet à l'ancien code de continuer à lire pendant le
déploiement. C'est l'adaptateur de la leçon 3.3, appliqué au schéma.

## 10. Le réflexe à installer

Devant chaque migration, demande-toi :

1. Quel verrou prend-elle, et pendant combien de temps ?
2. Que se passe-t-il si une transaction longue tient déjà la table ?
3. Réécrit-elle la table ?
4. Le code d'avant et le code d'après fonctionnent-ils avec chaque
   étape ?
5. Laquelle des étapes est irréversible ?
