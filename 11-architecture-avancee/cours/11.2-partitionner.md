# Leçon 11.2 — Partitionner : couper les données quand une base ne suffit plus, et pas avant

## L'essentiel en deux minutes

**Le problème, en une phrase.** Couper une table en morceaux, ou les
données entre plusieurs bases, rend certaines opérations bien plus
simples et d'autres bien plus difficiles ; mal coupées, les données
gardent un morceau surchargé, ou chaque question doit les visiter tous.

**Trois images.**

- **Les classeurs par année** : jeter l'année 2019, c'est jeter un
  classeur, pas retirer une à une des milliers de feuilles. Mais
  retrouver un reçu dont on ne connaît pas l'année oblige à ouvrir tous
  les classeurs.
- **Les guichets par lettre** : « A à F au guichet 1 ». Si une famille
  très nombreuse s'appelle Fotso, le guichet 1 a toute la file.
- **Le plan de table numéroté** : quand on ajoute une table au mariage,
  on ne redistribue pas tous les invités ; on déplace quelques
  numéros.

**Le code, en quelques lignes.** Une table de cases dit quelle base tient
chaque case ; ajouter une base, c'est lui donner quelques cases :

```go
// Slots cuts the keys into a fixed number of slots, and keeps a table of
// which database holds each slot. Adding a database moves whole slots,
// chosen by whoever runs the move.
type Slots struct {
    Table []int // slot -> database
}
```

**Les règles à retenir.**

1. **On partitionne pour une raison mesurée** : la purge, la taille, le
   débit d'écriture ; pas « parce que ça grandira ».
2. **Les partitions par date** rendent la purge instantanée ; elles ne
   rendent pas les requêtes indexées plus rapides.
3. **Toute contrainte unique doit contenir la clé de partition** : une
   unicité globale se perd, et doit se garantir autrement.
4. **La clé de répartition entre bases** suit les questions qu'on pose
   le plus : par association, si chaque écran parle d'une association.
5. **On répartit par cases**, pas par `hash mod N` : ajouter une base
   ne doit déplacer que sa part.

La suite le mesure sur 2,4 millions de cotisations, puis sur un million
de membres et seize bases.

---

La leçon 11.1 a conclu qu'en 2028, une seule base suffirait aux
écritures, avec 40 fois de marge. Il reste deux raisons de couper les
données, qui ne sont pas le débit : **la durée de vie** (on ne garde les
cotisations que deux ans en ligne, la loi et le contrat disent combien)
et **la croissance au-delà de 2028** (la fédération nationale de
l'exercice 4 de la leçon 11.1). Le problème :

> **Quand et comment couper les données, pour que ce qui doit être
> simple le reste ?**

Le module de la leçon est `l112`. Il utilise le PostgreSQL 17 du
niveau 5 (`sd-pg`, port 55432) pour les partitions ; la répartition
entre bases est simulée avec la bibliothèque standard. Tout ce qui suit
est mesuré sur un module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. Mesure : partitionner par mois

Deux ans de cotisations, 2,4 millions de lignes, dans une table, puis
dans 24 partitions mensuelles :

```go
// Partitioned is the same contributions, cut by month. Every unique
// index must contain the month: the operator's reference alone can no
// longer be unique across the table.
const Partitioned = `
CREATE TABLE contributions (
    tenant_id    text        NOT NULL,
    id           bigint      NOT NULL,
    paid_at      timestamptz NOT NULL,
    amount       bigint      NOT NULL,
    operator_ref text        NOT NULL,
    PRIMARY KEY (tenant_id, id, paid_at)
) PARTITION BY RANGE (paid_at);
CREATE INDEX contributions_month ON contributions (tenant_id, paid_at);
CREATE INDEX contributions_ref ON contributions (operator_ref);`
```

`cmd/partitions` charge, interroge, puis retire l'année 2025 :

```text
2 400 000 contributions of 2025 and 2026, 2000 associations

                                                one table    24 partitions
unique reference on the partitions: ERROR: unique constraint on partitioned table must include all partitioning columns (SQLSTATE 0A000)

load                                                46.5s            40.9s
size                                               462 MB           472 MB
1000 months of one association                      461ms            628ms
1000 lookups by reference                           123ms            475ms
remove 2025                                         2.75s            130ms
size after                                         462 MB           236 MB
```

- **Retirer 2025** : 2,75 s pour la table, 130 ms pour les partitions
  (entre 1,4 et 2,8 s contre 90 à 130 ms selon les exécutions). Surtout,
  **la table garde ses 462 Mo** après le `DELETE` : les lignes sont
  mortes, pas rendues au disque, jusqu'à ce qu'un `VACUUM FULL` (qui
  bloque la table) les récupère. Les partitions supprimées rendent leur
  place tout de suite : 236 Mo.
- **Le mois d'une association** : à peu près le même temps (entre 0,5 et
  1 s pour mille requêtes, des deux côtés). L'index suffisait déjà ; la
  partition ne rend pas une requête indexée plus rapide.
- **Retrouver une cotisation par la référence de l'opérateur** : trois
  fois plus lent avec les partitions dans la plupart des exécutions (120
  à 160 ms contre 410 à 475 ms), parce que la requête ne connaît pas le
  mois et doit sonder l'index de chaque partition.
- **Et l'unicité est perdue** : PostgreSQL refuse un index unique sur la
  référence seule, puisqu'il ne vérifie l'unicité que dans chaque
  partition. Les leçons 8.3 et 9.5 comptaient sur une telle unicité
  pour ne jamais créditer deux fois la même confirmation de l'opérateur. Il faut la
  garantir autrement : une table à part `operator_refs (ref PRIMARY
  KEY)`, non partitionnée, écrite dans la même transaction.

Le partitionnement par date se justifie par la purge. Il se paie par les
requêtes qui ne connaissent pas la date, et par les contraintes
globales.

## 2. Mesure : sur quoi répartir entre bases

Au-delà d'une base, on répartit les données entre plusieurs (le
*sharding*). La première décision est la clé. `cmd/hotshard` répartit les
membres de 2 000 associations entre seize bases, dont une fédération de
40 000 membres :

```text
2000 associations, 228188 members, 16 databases

placed by                                   fullest / average reports visiting several databases
association                                              3.36                             0 of 2000
member                                                   1.01                          2000 of 2000
association; the federation by tontine                   1.79                             1 of 2000
```

- **Par association** : chaque rapport d'association ne visite qu'une
  base. Mais la base de la fédération tient **3,36 fois la moyenne** :
  c'est elle qui saturera la première.
- **Par membre** : la charge est parfaite (1,01), mais **chaque**
  rapport, même celui d'une tontine de vingt membres, interroge les
  seize bases et assemble les réponses. La leçon 11.1 a mesuré ce que
  coûte d'attendre seize réponses.
- **Par association, la fédération par tontine** : la fédération est
  coupée en ses 200 tontines, les autres restent entières. Un seul
  rapport (celui de la fédération) visite plusieurs bases ; la base la
  plus chargée tombe à 1,79 fois la moyenne, le reste venant des vingt
  grandes associations.

La clé suit les questions : si presque tout ce qu'on demande porte sur
une association, la clé est l'association, et les très grandes se
coupent selon leur propre structure.

## 3. Mesure : ajouter une base

Un jour, seize bases ne suffisent plus. `cmd/rebalance` place un million
de membres sur seize bases de trois façons, ajoute une dix-septième, et
compte les membres qui doivent déménager :

```text
1000000 members on 16 databases, then 17

                                          moved  fullest / average, 17
hash mod N                                94.1%                   1.01
consistent hashing, 100 points             6.3%                   1.14
1024 slots, a table of owners              5.8%                   1.02

the best possible: 5.9% moved (the 17th database's share)
```

- **`hash mod N`** : passer de 16 à 17 change le reste de presque toutes
  les divisions : **94 % des membres déménagent**. Une opération de
  plusieurs jours, pendant laquelle chaque requête doit savoir où est
  chaque membre.
- **Le hachage cohérent** (des points sur un cercle) : 6,3 % déménagent,
  presque le minimum ; la répartition reste un peu inégale (1,14) avec
  cent points par base.
- **Des cases et une table** : 5,8 % déménagent, le minimum possible à
  une case près, et la répartition reste égale (1,02). C'est le choix de
  Redis Cluster, qui découpe les clés en 16 384 cases, chaque nœud en
  tenant une partie.

La table des cases a un autre avantage : on choisit **quelles** cases
déménager. La case de la fédération peut aller seule sur une base
neuve.

## 4. La campagne

Neuf mutations, dans le hachage, l'anneau, les cases et les partitions :

```text
hachage sans mélange                         tuee
anneau qui ne boucle pas                     tuee
un seul point par base                       tuee
une base sans case                           tuee
nouvelle base trop servie                    tuee
prise aux plus pauvres                       tuee
mois de 30 jours                             tuee
un mois de trop supprimé                     tuee
référence non unique                         tuee
9/9 tuees
```

« L'anneau qui ne boucle pas » a d'abord survécu : une clé dont le
hachage dépasse le dernier point doit revenir au premier point du
cercle, et aucun test ne prenait une telle clé. Le test
`TestRingWrapsAround` en cherche une.

## 5. La grille

| Avant de couper | À vérifier |
|---|---|
| la raison | une mesure : purge, taille, débit ; pas une crainte |
| la clé de partition | les requêtes fréquentes la connaissent ; les autres sont mesurées |
| les contraintes uniques | chacune contient la clé, ou vit dans une table à part |
| la clé de répartition | celle de la plupart des questions ; les très grands clients coupés à part |
| le rééquilibrage | des cases et une table, jamais `mod N` |
| les requêtes transverses | listées, mesurées, et servies par une vue séparée si besoin |

## 6. Les trois erreurs qui restent

### « Partitionner rend les requêtes plus rapides »

Pas les requêtes indexées : la section 1 l'a mesuré. Les partitions
aident les requêtes qui parcourent beaucoup de lignes d'une période (un
rapport annuel qui ne lit qu'une partition) et la maintenance (purger,
`VACUUM`, réindexer un mois à la fois).

### « Le sharding se fera plus tard, sans changer le code »

Chaque requête qui traverse les associations (les statistiques de la
plateforme, la recherche d'un membre par téléphone) devient une requête
sur toutes les bases. Chaque transaction qui touche deux associations
devient distribuée (leçon 8.5). Se préparer, c'est garder dès
aujourd'hui l'association dans chaque clé (leçon 10.1), pas répartir
aujourd'hui.

### « Le hachage répartit toujours bien »

Le hachage répartit bien les **clés**. Si les clés n'ont pas toutes la
même taille (une association de 40 000 membres, une de 20), la charge
reste inégale. La section 2 l'a mesuré.

## 7. Le lien avec la production

- **Les partitions se créent d'avance** : un travail mensuel crée les
  trois mois suivants ; une insertion sans partition échoue (le test
  `TestMonthsAndDrop` le vérifie).
- **La purge** détache la partition (`DETACH PARTITION`), l'archive
  (leçon 11.4), puis la supprime.
- **La table des cases** vit dans un service de configuration, lue par
  chaque instance ; un déménagement copie une case, bascule l'écriture,
  puis supprime l'ancienne copie (leçon 11.3).
- **Les requêtes transverses** sont servies par une base d'analyse
  alimentée par les événements (leçon 8.4), pas en interrogeant toutes
  les bases à chaque écran.

## 8. Ce qu'il faut retenir

1. On coupe pour une raison mesurée.
2. Les partitions par date servent la purge.
3. L'unicité globale se paie.
4. La clé suit les questions.
5. Des cases, pas `mod N`.

## 9. Approfondissement

### Les outils de répartition

Des extensions comme Citus répartissent une table PostgreSQL entre
plusieurs serveurs, avec une clé de distribution choisie par table. Le
choix de la clé reste le même problème que la section 2 ; l'outil
déplace le travail, pas la décision.

### La table de référence

Les petites tables lues partout (les offres, les taux de taxe) ne se
répartissent pas : on les recopie sur chaque base. La règle : on répartit
ce qui grandit avec les clients, on recopie ce qui n'en dépend pas.

## 10. Le réflexe à installer

Avant de couper des données, demande-toi :

1. Quel nombre mesuré m'y oblige ?
2. Quelles requêtes connaissent la clé, et lesquelles non ?
3. Quelles contraintes uniques vais-je perdre ?
4. Que se passe-t-il pour le plus gros client ?
5. Combien de données déménagent quand j'ajoute une base ?
