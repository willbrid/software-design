# Correction 11.3 — Exercice 5 : le 30 novembre à 17 h 58

> Rappel de l'énoncé : un déploiement qui ajoute une colonne pendant le
> rapport mensuel ; mesurer la panne, rejouer avec une migration
> prudente, rédiger.

Le journal et le rejeu sont dans `ex5` du module de correction, verts
sous `go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **319 écrans sur 1 000 au-delà d'une seconde**, entre 0,5 s et 2,1 s,
  jusqu'à 2,6 s d'attente.
- **À l'échelle réelle** (le temps a été divisé par cinquante) : une
  panne d'environ une minute vingt, jusqu'à plus de deux minutes
  d'attente, à deux minutes du rappel du dernier soir.
- **Avec un `lock_timeout` de 100 ms et des tentatives**, aucun écran
  au-delà d'une seconde ; le pire attend 100 ms.

## 1. Le journal

```go
func Outage(log []Request, threshold time.Duration) Report {
    r := Report{Requests: len(log)}
    for _, q := range log {
        r.Worst = max(r.Worst, q.Took)
        if q.Took <= threshold {
            continue
        }
        if r.Slow == 0 || q.At < r.From {
            r.From = q.At
        }
        r.To = max(r.To, q.At)
        r.Slow++
    }
    return r
}
```

```go
// Cautiously is the migration the deploy should have run: it never makes
// a screen wait more than 100 ms behind it, and tries for a minute.
func Cautiously(ctx context.Context, pool *pgxpool.Pool, ddl string) (migrate.Attempts, error) {
    return migrate.Cautiously(ctx, pool, ddl, 100*time.Millisecond, 400*time.Millisecond, 120)
}
```

## 2. Les chiffres, et le rejeu

`cmd/deploy` rejoue la soirée deux fois :

```text
30 November 2026, 17:58, time shrunk fifty times: the monthly report holds the
members; the deploy adds a column; 200 screens a second

                                 screens      over 1 s          between      worst
as the deploy ran it                1000           319        0.5-2.1 s      2.57s
lock_timeout, retries               1000             0                -      100ms
```

- **Comme le déploiement l'a fait** : la migration demande son verrou à
  0,5 s, attend la fin du rapport (3 s), et tous les écrans arrivés
  entre-temps attendent derrière elle. Les écrans lents vont de 0,5 à
  2,1 s ; au-delà, ils attendent moins d'une seconde avant que la
  migration ne passe.
- **Avec la migration prudente** : elle essaie, abandonne au bout de
  100 ms, laisse passer les écrans, réessaie ; elle passe dès la fin du
  rapport, au même moment que l'autre. Les écrans n'ont jamais attendu
  plus de 100 ms.

## 3. La cause

**En une phrase** : la migration du déploiement a attendu son verrou
derrière le rapport mensuel, sans délai, et toutes les lectures de la
table des membres ont attendu derrière elle.

**La cause de la cause** : l'outil de migration n'avait aucun
`lock_timeout` par défaut ; la migration était « instantanée » et
personne n'avait pensé à son attente ; le rapport mensuel lisait la
table de production dans une seule transaction longue ; et le
déploiement était autorisé à 17 h 58 un jour de clôture.

## 4. Le compte rendu

1. **Quoi** : le lundi 30 novembre 2026, de 17 h 58 à 18 h 00 environ,
   l'écran des trésorières n'a pas répondu ; près d'un tiers des
   requêtes ont attendu plus d'une seconde, jusqu'à plus de deux minutes.
2. **Cause** : l'ajout d'une colonne a attendu son verrou derrière le
   rapport mensuel, et les lectures ont fait la queue derrière lui.
3. **Détection** : par les alertes de latence (leçon 9.4), et par les
   appels de trésorières à deux minutes du rappel.
4. **Correction** : l'outil de migration pose `lock_timeout = 100ms` et
   réessaie ; le rapport mensuel lit une réplique, ou par morceaux
   (leçon 11.5) ; aucun déploiement de schéma le dernier jour du mois
   entre 17 h et 21 h.
5. **Prévention** : chaque migration passe une revue qui note son verrou
   et sa durée ; un test d'intégration lance une transaction longue, une
   migration, et vérifie que les lectures ne dépassent pas 200 ms.
