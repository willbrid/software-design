# Correction 11.2 — Exercice 3 : l'unicité perdue

> Rappel de l'énoncé : réécrire `Record` pour que la référence de
> l'opérateur reste unique sur toutes les partitions.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **La référence entre d'abord dans `operator_refs`**, avec `ON
  CONFLICT DO NOTHING`.
- **Si elle y était déjà, rien n'est écrit** : `ErrDuplicate`.
- **Les deux écritures sont dans une transaction** : une cotisation qui
  échoue libère la référence.

## 1. La solution

```go
// Record writes c, and its reference in operator_refs, in one
// transaction: a reference already recorded, in any month, is refused
// with ErrDuplicate, and nothing is written.
func Record(ctx context.Context, pool *pgxpool.Pool, c Contribution) error {
    return pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
        tag, err := tx.Exec(ctx, `INSERT INTO operator_refs (ref, paid_at) VALUES ($1, $2)
            ON CONFLICT (ref) DO NOTHING`, c.Ref, c.PaidAt)
        if err != nil {
            return err
        }
        if tag.RowsAffected() == 0 {
            return ErrDuplicate
        }
        _, err = tx.Exec(ctx, `INSERT INTO contributions (tenant_id, id, paid_at, amount, operator_ref)
            VALUES ($1, $2, $3, $4, $5)`, c.Tenant, c.ID, c.PaidAt, c.Amount, c.Ref)
        return err
    })
}
```

## 2. Pourquoi l'ordre et la transaction

Deux confirmations de la même référence arrivent ensemble. La première
insère dans `operator_refs` ; la seconde attend la fin de sa
transaction. Si la première valide, la seconde voit le conflit et
renvoie `ErrDuplicate`. Si la première échoue (pas de partition pour
son mois), sa ligne disparaît, et la seconde passe. Le test
`TestFailedInsertKeepsTheReferenceFree` vérifie ce second cas ; hors
transaction, la référence resterait prise par une cotisation qui
n'existe pas.

## 3. Une table qui grandit pour toujours

`operator_refs` garde une ligne par paiement. Quand les partitions de
2025 sont supprimées, les références de 2025 peuvent l'être aussi : un
opérateur ne renvoie pas une confirmation de l'an passé. La colonne
`paid_at` sert à cela : `DELETE FROM operator_refs WHERE paid_at <
'2026-01-01'`, après la suppression des partitions. Et si cette table
devient grande à son tour, elle se partitionne elle aussi, par mois de
`paid_at`, pourvu que la clé primaire devienne `(ref, paid_at)` : on
retrouve le même problème, déplacé. La vraie limite est la fenêtre de
temps pendant laquelle un doublon est possible ; au-delà, l'unicité n'a
plus besoin d'être vérifiée.

## Ce qu'il faut retenir

- Une contrainte globale perdue par le partitionnement se reconstruit
  dans une table à part, écrite dans la même transaction.
- L'ordre des écritures décide qui attend qui.
- Une unicité n'a besoin d'être tenue que sur la fenêtre où un doublon
  peut arriver.
