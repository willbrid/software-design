# Correction 11.3 — Exercice 3 : changer un type sans réécrire la table

> Rappel de l'énoncé : faire passer `amount` de `int` à `bigint` en
> étapes qui ne bloquent jamais les écrivains plus de 300 ms.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Une colonne neuve**, tenue égale par un déclencheur pour toute
  ligne écrite.
- **Un remplissage par lots** de l'existant, puis des lignes écrites
  avant le déclencheur.
- **`NOT NULL` par une contrainte validée**, puis **un échange** dans une
  transaction courte.

## 1. La solution

```go
// Steps returns the statements of the migration of a table whose ids go
// up to maxID. None rewrites the table under an exclusive lock: a new
// column kept equal by a trigger, filled in batches of 20 000 ids, made
// NOT NULL through a validated CHECK, then swapped with the old one in
// one short transaction.
func Steps(maxID int64) []string {
    steps := []string{
        `ALTER TABLE members ADD COLUMN amount_new bigint`,
        `CREATE FUNCTION members_amount_sync() RETURNS trigger LANGUAGE plpgsql AS $$
        BEGIN
            NEW.amount_new := NEW.amount;
            RETURN NEW;
        END $$`,
        `CREATE TRIGGER amount_sync BEFORE INSERT OR UPDATE ON members
            FOR EACH ROW EXECUTE FUNCTION members_amount_sync()`,
    }
    for from := int64(1); from <= maxID; from += 20000 {
        steps = append(steps, fmt.Sprintf(
            `UPDATE members SET amount_new = amount WHERE id BETWEEN %d AND %d AND amount_new IS NULL`, from, from+19999))
    }
    // The rows written after maxID was read and before the trigger
    // existed: few, and the trigger fills every row written since.
    steps = append(steps, fmt.Sprintf(
        `UPDATE members SET amount_new = amount WHERE id > %d AND amount_new IS NULL`, maxID))
    return append(steps,
        `ALTER TABLE members ADD CONSTRAINT amount_new_set CHECK (amount_new IS NOT NULL) NOT VALID`,
        `ALTER TABLE members VALIDATE CONSTRAINT amount_new_set`,
        `ALTER TABLE members ALTER COLUMN amount_new SET NOT NULL`,
        `ALTER TABLE members DROP CONSTRAINT amount_new_set`,
        `DROP TRIGGER amount_sync ON members;
        ALTER TABLE members DROP COLUMN amount;
        ALTER TABLE members RENAME COLUMN amount_new TO amount`,
        `DROP FUNCTION members_amount_sync()`,
    )
}
```


## 2. Les lignes qui échappent

Le test lit `maxID` (un million) **avant** de démarrer l'écrivain et la
migration. Entre ce moment et la création du déclencheur, l'écrivain
insère quelques lignes : leurs identifiants dépassent `maxID`, et le
déclencheur n'existait pas encore. Les lots s'arrêtent à `maxID` : ces
lignes resteraient avec `amount_new` vide, et `VALIDATE` échouerait. La
première version de la solution a échoué exactement ainsi. L'étape « au
delà de `maxID` » les rattrape ; après elle, le déclencheur garantit
qu'aucune ligne écrite ne peut être vide.

## 3. Ce que chaque étape verrouille

| Étape | Verrou | Durée |
|---|---|---|
| ajouter la colonne, la fonction, le déclencheur | court, exclusif | quelques millisecondes |
| les lots | des lignes, pas la table | quelques millisecondes par lot |
| `CHECK ... NOT VALID` | court | instantané |
| `VALIDATE` | n'empêche pas les écritures | lit la table |
| `SET NOT NULL` | court : PostgreSQL utilise la contrainte validée au lieu de lire la table | instantané |
| l'échange | exclusif, court | quelques millisecondes |

Le premier essai faisait le remplissage en un seul `UPDATE` : aucune
étape ne bloquait par un verrou, mais l'`UPDATE` d'un million de lignes
a fait attendre une insertion 1,2 s, par la seule charge du disque. Les
lots ont réglé le problème. C'est aussi pourquoi le test mesure les
attentes de **verrou** (`lock_timeout` de l'écrivain) et pas la durée
brute des insertions : la seconde dépend de la charge de la machine, et
rendait le test fragile quand les autres paquets tournaient en même
temps.

## Ce qu'il faut retenir

- Un changement de type se fait par une colonne neuve et un échange.
- Le déclencheur couvre l'avenir ; le remplissage couvre le passé ; une
  étape couvre l'entre-deux.
- `NOT NULL` sur une grosse table passe par une contrainte validée.
