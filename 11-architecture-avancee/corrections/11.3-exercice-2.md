# Correction 11.3 — Exercice 2 : remplir par lots

> Rappel de l'énoncé : écrire `Batches`, qui recopie `phone` dans
> `msisdn` par lots, chacun dans sa transaction.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Une instruction par lot** : choisir les identifiants, les mettre à
  jour, rendre le plus grand.
- **Reprendre après le dernier identifiant traité** : chaque lot lit la
  suite de l'index, pas son début.
- **S'arrêter quand un lot ne change rien.**

## 1. La solution

```go
func Batches(ctx context.Context, pool *pgxpool.Pool, batch int, pause time.Duration) (rows, batches int, err error) {
    var last int64
    for {
        var upTo *int64
        var n int
        err = pool.QueryRow(ctx, `
            WITH picked AS (
                SELECT id FROM members WHERE id > $1 AND msisdn IS DISTINCT FROM phone ORDER BY id LIMIT $2
            ), done AS (
                UPDATE members m SET msisdn = m.phone FROM picked WHERE m.id = picked.id RETURNING m.id
            )
            SELECT max(id), count(*) FROM done`, last, batch).Scan(&upTo, &n)
        if err != nil || n == 0 {
            return rows, batches, err
        }
        rows += n
        batches++
        last = *upTo
        time.Sleep(pause)
    }
}
```

## 2. Pourquoi des lots

Un seul `UPDATE` de deux millions de lignes ne prend pas de verrou de
table qui gêne les insertions, mais :

- il **verrouille deux millions de lignes** jusqu'à la fin : toute
  écriture d'un membre (un changement de numéro) attend la fin du tout ;
- il écrit **en une transaction** autant de journal que de lignes ; les
  écritures des autres attendent le disque. L'exercice 3 l'a mesuré : un
  seul `UPDATE` d'un million de lignes a fait attendre une insertion
  1,2 s, sans aucun verrou de table ;
- s'il échoue à la fin, **tout est perdu**, et tout recommence.

Des lots de mille lignes verrouillent mille lignes quelques
millisecondes, et un échec ne coûte qu'un lot.

## 3. Reprendre après le dernier

La fonction se souvient du plus grand identifiant traité, et le lot
suivant commence après. Sans cela, le résultat serait le même (les
lignes traitées ne diffèrent plus), mais chaque lot relirait l'index
depuis le début, de plus en plus loin : la campagne a montré que cette
version passe les tests, parce qu'ils ne mesurent pas le temps. C'est
une différence de coût, pas de résultat.

## Ce qu'il faut retenir

- Un remplissage se fait par lots, chacun dans sa transaction.
- Chaque lot reprend où le précédent s'est arrêté.
- L'absence de verrou de table ne veut pas dire l'absence de gêne.
