# Correction 11.2 — Exercice 4 : répartir la fédération nationale

> Rappel de l'énoncé : concevoir la répartition de 12 millions de
> membres entre plusieurs bases, et la migration d'une base à huit.

## En bref

- **La clé est l'association** ; les très grandes sont coupées en leurs
  sous-groupes.
- **Une table de 4 096 cases**, dans un service de configuration, dit
  quelle base tient chaque case.
- **Les requêtes transverses** passent par une base d'analyse, pas par
  les huit bases.
- **La migration** déménage case par case : copier, rattraper, basculer,
  supprimer.

## 1. La clé et les cases

- Clé de répartition : `tenant_id`, présent dans chaque clé primaire
  depuis la leçon 10.1. Pour la fédération et les associations de plus
  de 20 000 membres : `tenant_id/groupe`.
- Case : `hash(clé) % 4096`. Table `slots (slot, database, state)`, où
  `state` vaut `serving` ou `moving`.

## 2. Le routage

Chaque instance de l'application lit la table des cases au démarrage, et
la relit à chaque changement (un événement « cases modifiées »). La
fonction `WithTenant` de la leçon 10.1 devient : trouver la case, puis
la base, puis ouvrir la transaction sur le bon pool. Le reste du code ne
change pas.

## 3. Les requêtes transverses

| Requête | Où |
|---|---|
| statistiques de la plateforme | une base d'analyse, alimentée par les événements (leçons 8.2 et 8.4), avec quelques minutes de retard |
| recherche d'un membre par téléphone | un index global `phone → (tenant, member)`, une petite table répliquée, mise à jour par événement |
| paiement entre deux associations | une saga (leçon 8.5) |

Aucun écran ne doit interroger les huit bases à la fois : la leçon 11.1
a montré ce que coûte d'attendre beaucoup de réponses.

## 4. La migration d'une base à huit

Pour chaque case, une à la fois au début, puis par lots :

1. **copier** les lignes de la case vers la base cible, pendant que
   l'ancienne sert encore ;
2. **rattraper** les écritures faites pendant la copie (par le journal
   de la base, ou par l'outbox) ;
3. **basculer** : passer la case en `moving`, refuser brièvement les
   écritures de cette case (quelques secondes), rattraper la fin, puis
   pointer la case vers la nouvelle base ;
4. **supprimer** les lignes de l'ancienne base après une période de
   vérification.

Une case représente environ 3 000 membres : chaque bascule ne bloque
qu'une poignée d'associations, quelques secondes. La leçon 11.3 détaille
ce genre de migration sans arrêt.

## Ce qu'il faut retenir

- La clé suit les questions ; les géants se coupent à part.
- Une table de cases rend chaque déménagement petit et réversible.
- Ce qui traverse les associations se lit ailleurs que dans les bases
  réparties.
