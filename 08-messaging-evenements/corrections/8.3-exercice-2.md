# Correction 8.3 — Exercice 2 : garer une clé

> Rappel de l'énoncé : dès qu'un message d'une clé part aux lettres
> mortes, les suivants de la même clé attendent avec lui, jusqu'à ce
> qu'on les relâche dans l'ordre.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **`Dead` gare la clé**, avec le message mort en tête.
- **`Handler` regarde si la clé est garée** : si oui, le message s'ajoute
  derrière, et il est acquitté (il est en sûreté, au parking).
- **`Release` rejoue dans l'ordre**, et s'arrête au premier échec.

## 1. La solution

```go
// Dead is the delivery's Dead option: it parks the key of m, with m.
func (p *Parking) Dead(m delivery.Message, err error) {
    p.mu.Lock()
    defer p.mu.Unlock()
    if p.parked == nil {
        p.parked = map[string][]delivery.Message{}
    }
    p.parked[m.Key] = append(p.parked[m.Key], m)
}
```

```go
// Handler handles m with p.Handle, unless the key of m is parked: then
// m is parked behind the others of its key, and acknowledged.
func (p *Parking) Handler(ctx context.Context, m delivery.Message) error {
    p.mu.Lock()
    if _, ok := p.parked[m.Key]; ok {
        p.parked[m.Key] = append(p.parked[m.Key], m)
        p.mu.Unlock()
        return nil
    }
    p.mu.Unlock()
    return p.Handle(ctx, m)
}
```

```go
// Release hands the parked messages of key to p.Handle, in order, once
// the consumer is fixed; it stops at the first error, and keeps the rest
// parked.
func (p *Parking) Release(ctx context.Context, key string) error {
    p.mu.Lock()
    defer p.mu.Unlock()
    for len(p.parked[key]) > 0 {
        if err := p.Handle(ctx, p.parked[key][0]); err != nil {
            return err
        }
        p.parked[key] = p.parked[key][1:]
    }
    delete(p.parked, key)
    return nil
}
```


`Handler` relâche le verrou **avant** d'appeler `p.Handle` : le travail
de l'abonné peut être long, et le parking ne doit pas bloquer les autres
clés pendant ce temps. `Release`, au contraire, garde le verrou : un
message de la même clé qui arriverait pendant le rejeu doit attendre
derrière, pas passer devant.

## 2. Ce que coûte le parking

Quand le message mort est le seul défectueux, les suivants de sa clé
**attendent pour rien** : l'annulation, valide, attend que quelqu'un
corrige l'enregistrement. Pour une cotisation, c'est quelques messages ;
pour une clé trop large (la tontine entière), c'est toute la tontine
bloquée pour un seul message. Le parking rend le choix de la clé (leçon
8.2, exercice 4) encore plus important : la clé est ce qui doit rester
ordonné, et rien de plus.

En échange, aucune annulation n'est appliquée sans l'enregistrement
qu'elle annule.

## 3. Le parking en production

Le parking vit dans la base de l'abonné, pas en mémoire : une table
`parked (key, seq, message)`, consultée avant chaque traitement. En
mémoire, comme ici, un redémarrage le viderait, et les messages garés,
déjà acquittés, seraient perdus.

## Ce qu'il faut retenir

- Mettre de côté un message, c'est mettre de côté sa clé.
- Le rejeu suit l'ordre, et s'arrête au premier échec.
- Le parking se stocke comme une inbox : dans la base de l'abonné.
