# Correction 8.4 — Exercice 5 : la vue figée du 11 décembre

> Rappel de l'énoncé : une transaction oubliée dans un outil SQL fige la
> vue pendant deux heures et demie ; mesurer, rejouer avec un délai sur
> les transactions inactives, rédiger.

L'audit et le rejeu sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **74 membres sur 200 ont payé deux fois, 740 000 FCFA.**
- **Avec un délai de 5 minutes** sur les transactions inactives, la
  session de l'analyste est coupée, la vue repart : **aucun** double
  paiement.
- **La cause** : une transaction ouverte retient `xmin` pour toute la
  base ; **la cause de la cause** : rien ne coupait une transaction
  oubliée, et rien ne surveillait le retard de la vue.

## 1. L'audit

```go
func Audit(ctx context.Context, pool *pgxpool.Pool) (Report, error) {
    var r Report
    err := pool.QueryRow(ctx, `
        SELECT count(*), count(*) FILTER (WHERE n > 1), coalesce(sum(total - first), 0)
        FROM (SELECT member, count(*) AS n, sum(amount) AS total, min(amount) AS first
              FROM contributions WHERE round = 'r1' AND NOT reversed GROUP BY member) AS m`).
        Scan(&r.Members, &r.PaidTwice, &r.OverpaidFCFA)
    return r, err
}
```

## 2. Les chiffres, et le rejeu

`cmd/friday` rejoue la journée deux fois :

```text
200 members, one payment every 2 minutes from 8:00; an analyst's transaction open from 10:12 to 12:42

                                              members  paid twice  overpaid FCFA
as it happened                                    200          74         740000
idle_in_transaction_session_timeout = 5 min       200           0              0
```

- **Comme elle s'est passée** : de 10 h 12 à 12 h 42, la transaction de
  l'analyste retient `xmin`. Le projecteur ne lit que les transactions
  plus anciennes : il n'applique plus rien. Chaque membre qui paie
  attend 10 minutes, ne voit rien, paie à nouveau, et ne voit toujours
  rien. **74 membres** ont payé dans cette fenêtre (et juste avant) : 74
  doubles paiements, **740 000 FCFA**.
- **Avec `idle_in_transaction_session_timeout = 5 min`** sur la session
  de l'analyste : PostgreSQL ferme la session après 5 minutes sans
  activité dans sa transaction, `xmin` avance, la vue rattrape, chaque
  membre voit son paiement à temps.

La transaction de l'analyste ne faisait **rien** : un `SELECT`, puis
l'attente. Elle n'écrivait pas, ne verrouillait rien de ce que les
paiements touchaient. Elle a quand même arrêté la vue.

## 3. La cause

**En une phrase** : une transaction ouverte et oubliée par une analyste
a retenu le `xmin` de la base pendant deux heures et demie, et le
projecteur, qui attend que les transactions plus anciennes se terminent,
s'est arrêté sans erreur.

**La cause de la cause** : trois protections manquaient. Aucun délai ne
coupait une transaction inactive ; aucune alerte ne surveillait le retard
de la vue ; et l'écran des membres lisait la vue sans secours vers la
source (exercice 2), si bien qu'une vue arrêtée montrait des paiements
manquants au lieu de paiements en retard.

## 4. Le compte rendu

1. **Quoi** : le vendredi 11 décembre 2026, de 10 h 12 à 12 h 42, le
   tableau des tours ne s'est plus mis à jour ; 74 membres, ne voyant pas
   leur paiement, ont payé une seconde fois, pour 740 000 FCFA.
2. **Cause** : une transaction ouverte dans un outil SQL et laissée
   inactive retenait l'horizon des transactions (`xmin`) de la base ; le
   projecteur ne lit que les événements des transactions plus anciennes
   que cet horizon.
3. **Détection** : par les appels des membres, puis par la trésorière en
   début d'après-midi. Aucune alerte sur le retard de la vue.
4. **Correction** : les 74 seconds paiements sont remboursés, après
   vérification dans la source ; la transaction est fermée à 12 h 42.
5. **Prévention** : `idle_in_transaction_session_timeout` sur les rôles
   des outils et des personnes ; une alerte sur l'âge du plus ancien
   événement non appliqué (plus de 2 minutes) et sur les transactions
   ouvertes depuis plus de 5 minutes (`pg_stat_activity`) ; l'écran des
   membres répond par la source quand la vue tarde ; les analyses se font
   sur un réplica, pas sur la base qui enregistre les paiements.

## Ce qu'il faut retenir

- Une transaction inactive arrête une vue qui suit les transactions.
- `idle_in_transaction_session_timeout` coupe ce qu'on oublie.
- Une vue arrêtée se voit par son retard, pas par une erreur.
