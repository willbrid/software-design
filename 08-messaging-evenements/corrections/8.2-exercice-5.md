# Correction 8.2 — Exercice 5 : les reçus en double du 30 novembre

> Rappel de l'énoncé : une journée de fin de mois avec « publier puis
> valider », des doubles appuis et un déploiement ; mesurer, rejouer avec
> l'outbox, rédiger.

L'audit et le rejeu sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **25 cotisations fantômes et 75 annoncées deux fois** : le tableau des
  tours compte **1 000 000 FCFA** de plus que les comptes.
- **Avec l'outbox, 0, 0 et 0** : le second appui est refusé par la base,
  et l'événement avec lui.
- **La cause** : publier avant de valider ; **la cause de la cause** :
  croire que la base dirait oui.

## 1. L'audit

```go
func Audit(recorded map[string]int64, bodies [][]byte) (Report, error) {
    r := Report{Recorded: len(recorded), Announcements: len(bodies)}
    seen := map[string]int{}
    var board, books int64
    for _, b := range bodies {
        var m struct {
            Contribution string
            Amount       int64
        }
        if err := json.Unmarshal(b, &m); err != nil {
            return Report{}, fmt.Errorf("body %q: %w", b, err)
        }
        seen[m.Contribution]++
        board += m.Amount
    }
    for id, n := range seen {
        if _, ok := recorded[id]; !ok {
            r.Phantom++
        }
        if n > 1 {
            r.Twice++
        }
    }
    for _, amount := range recorded {
        books += amount
    }
    r.BoardOverFCFA = board - books
    return r, nil
}
```

L'audit lit les corps comme du JSON, et non comme du texte : le relais
de l'outbox publie le corps tel que PostgreSQL le rend (`jsonb`), avec
ses espaces et son ordre des champs. Comparer les octets aurait compté
deux fois la même cotisation.

## 2. Les chiffres, et le rejeu

`cmd/month` rejoue la journée deux fois :

```text
1200 contributions, 75 double taps, 25 stopped by the deployment of 14:00

                        recorded  announcements  phantom  twice  board over, FCFA
publish, then commit        1175           1275       25     75           1000000
outbox                      1175           1175        0      0                 0
```

- **Publier puis valider** : 1 175 cotisations en base, 1 275 annonces.
  Les **75 doubles appuis** ont été annoncés deux fois : le second appel a
  publié, puis la base l'a refusé (clé primaire déjà prise). Les **25
  cotisations du déploiement** ont été annoncées, jamais enregistrées. Le
  tableau des tours additionne les annonces : **1 000 000 FCFA** de trop,
  soit 100 cotisations de 10 000 FCFA, de quoi déclarer complets des tours
  qui ne le sont pas.
- **L'outbox** : 1 175 cotisations, 1 175 annonces, rien de trop. Le
  second appui échoue dans la transaction, qui emporte son événement ; la
  cotisation interrompue n'a écrit ni la ligne, ni l'événement.

## 3. La cause

**En une phrase** : les paiements annonçaient chaque cotisation avant que
la base l'accepte, et la base en a refusé ou perdu 100.

**La cause de la cause** : le code supposait que l'enregistrement
réussirait toujours. Or la base refuse pour de bonnes raisons (la clé
primaire contre le double appui, la contrainte du montant), et le
programme s'arrête un jour de déploiement. Les protections de la base ne
protègent que ce qui passe **après** elles.

## 4. Le compte rendu

1. **Quoi** : le lundi 30 novembre 2026, le tableau des tours a compté
   100 cotisations qui n'existent pas, pour 1 000 000 FCFA : 75 doubles
   appuis et 25 cotisations interrompues par le déploiement de 14 h.
2. **Cause** : les paiements publiaient l'événement avant de valider la
   transaction ; un refus ou un arrêt après la publication laissait une
   annonce sans cotisation.
3. **Détection** : par la trésorière, le soir, en rapprochant le tableau
   des tours et ses comptes. Aucune métrique ne comparait les deux.
4. **Correction** : les tours sont recalculés depuis la table des
   cotisations ; aucune cagnotte n'est versée d'après le tableau ce soir-là ;
   les paiements écrivent leurs événements dans l'outbox.
5. **Prévention** : une revue de code refuse toute publication hors d'une
   transaction (la grille de la leçon) ; un contrôle quotidien compare les
   totaux du tableau et ceux des cotisations ; les versements se décident
   sur la table des cotisations, jamais sur une vue alimentée par des
   événements (leçon 8.4).

## Ce qu'il faut retenir

- Une annonce faite avant le commit annonce aussi ce que la base refusera.
- L'outbox fait des refus de la base des refus de l'événement.
- Un tableau alimenté par des événements se contrôle contre la source.
