# Correction 8.2 — Exercice 2 : surveiller et purger l'outbox

> Rappel de l'énoncé : écrire `Lag`, l'âge du plus ancien événement non
> publié, et `Purge`, qui supprime par lots ce qui est publié depuis
> longtemps.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **`Lag` lit l'horloge de la base**, pas celle du programme : les deux
  dates comparées viennent du même endroit.
- **`Purge` ne touche que des lignes publiées**, par lots, et saute les
  lignes verrouillées.
- **Un seul `DELETE` géant** tiendrait ses verrous et grossirait le
  journal d'un coup.

## 1. La solution

```go
// Lag returns the age of the oldest event not yet published, at the
// database's clock, and 0 when nothing waits.
func Lag(ctx context.Context, pool *pgxpool.Pool) (time.Duration, error) {
    var lag time.Duration
    err := pool.QueryRow(ctx, `
        SELECT coalesce(now() - min(created_at), interval '0')
        FROM outbox WHERE published_at IS NULL`).Scan(&lag)
    return lag, err
}
```

```go
// Purge deletes the events published more than olderThan ago, by batches
// of at most batch rows, each in its own statement, and returns how many
// it deleted. It never deletes an event that is not published.
func Purge(ctx context.Context, pool *pgxpool.Pool, olderThan time.Duration, batch int) (int, error) {
    total := 0
    for {
        tag, err := pool.Exec(ctx, `
            DELETE FROM outbox WHERE id IN (
                SELECT id FROM outbox
                WHERE published_at < now() - $1::interval
                ORDER BY id LIMIT $2
                FOR UPDATE SKIP LOCKED)`, olderThan, batch)
        if err != nil {
            return total, err
        }
        n := int(tag.RowsAffected())
        total += n
        if n == 0 {
            return total, nil
        }
    }
}
```

`coalesce(..., interval '0')` donne 0 quand rien n'attend : `min` d'un
ensemble vide vaut `NULL`, que pgx refuserait de lire dans un
`time.Duration`.

`now()` est l'heure de la base : `created_at` aussi. Si `Lag` comparait
`created_at` à l'horloge du programme, un écart de quelques secondes
entre les deux machines se lirait comme un retard du relais (la leçon
9.6 revient sur les horloges).

## 2. Pourquoi par lots

- **Les verrous** : un `DELETE` de dix millions de lignes les verrouille
  toutes jusqu'à la fin ; par lots de mille, chaque instruction est
  courte.
- **Le journal** : une seule transaction écrit tout son journal (WAL)
  d'un coup, et les réplicas prennent du retard ; par lots, l'écriture
  s'étale.
- **L'arrêt** : interrompue, une purge par lots a gardé ce qu'elle a fait.

`FOR UPDATE SKIP LOCKED` dans la sous-requête évite d'attendre une ligne
qu'un relais tiendrait, en théorie. En pratique, `published_at < now() -
$1` ne désigne que des lignes publiées depuis longtemps, qu'aucun relais
ne lit plus. Le test `TestPurgeIsNotBlockedByARelay` vérifie la propriété
qui compte : la purge ne touche pas une ligne en attente.

## 3. L'alerte

`Lag` devient une métrique, et une alerte : « plus ancien événement non
publié depuis plus de 5 minutes ». Elle couvre à la fois un relais
arrêté, un relais trop lent, et un courtier en panne, sans rien savoir de
leurs causes.

## Ce qu'il faut retenir

- Mesurer un retard avec une seule horloge.
- Purger par lots, et seulement ce qui est publié.
- L'âge du plus ancien en attente est la métrique du relais.
