# Correction 8.4 — Exercice 3 : verser d'après la source

> Rappel de l'énoncé : réécrire la décision de versement pour qu'elle
> lise la source, une seule fois par tour, sans qu'une annulation se
> glisse entre le compte et le versement.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **On compte dans la source**, dans une transaction.
- **`FOR SHARE`** tient les cotisations du tour jusqu'au commit : une
  annulation attend la décision.
- **La clé primaire de `payouts`** refuse un second versement, traduit en
  `ErrPaid`.

## 1. La solution

```go
func Payout(ctx context.Context, pool *pgxpool.Pool, round string, members int) error {
    tx, err := pool.Begin(ctx)
    if err != nil {
        return err
    }
    defer tx.Rollback(ctx)
    // FOR SHARE holds the rows of the round until the commit: a reversal,
    // which updates one of them, waits for the decision.
    rows, err := tx.Query(ctx, `SELECT amount FROM contributions WHERE round = $1 AND NOT reversed FOR SHARE`, round)
    if err != nil {
        return err
    }
    var n int
    var pot int64
    for rows.Next() {
        var amount int64
        if err := rows.Scan(&amount); err != nil {
            return err
        }
        n++
        pot += amount
    }
    if err := rows.Err(); err != nil {
        return err
    }
    if n < members {
        return ErrIncomplete
    }
    if _, err := tx.Exec(ctx, `INSERT INTO payouts (round, pot) VALUES ($1, $2)`, round, pot); err != nil {
        var pe *pgconn.PgError
        if errors.As(err, &pe) && pe.Code == "23505" {
            return ErrPaid
        }
        return err
    }
    return tx.Commit(ctx)
}
```

Le montant de la cagnotte est la somme des cotisations lues, et non

## 2. Le troisième test

`TestAReversalWaitsForADecisionThatHoldsTheRound` vérifie le
**mécanisme** sur lequel repose la correction : une transaction qui tient
les cotisations en `FOR SHARE` fait attendre un `UPDATE` sur l'une
d'elles. Il passe avec le code d'origine, parce qu'il n'appelle pas
`Payout` pendant que la ligne est tenue. Qu'un `Payout` prenne bien ce
verrou se lit dans le code ; un test qui le prouverait devrait arrêter
`Payout` au milieu de sa transaction.

Il n'utilise pas un délai côté Go (`context.WithTimeout`) pour
l'annulation qui attend : quand le délai du client expire, pgx abandonne
la requête, mais le serveur peut **continuer d'attendre le verrou**, et
appliquer l'`UPDATE` dès que la décision se termine. La première version
du test le faisait, et échouait de temps en temps : l'annulation
« abandonnée » passait après coup. `SET lock_timeout` fait abandonner le
**serveur** lui-même. C'est la leçon 6.3 vue de la base : un délai
expiré côté client ne dit pas ce qui s'est passé côté serveur.

## Ce qu'il faut retenir

- Décider, c'est lire la source dans la transaction qui agit.
- `FOR SHARE` empêche les lignes lues de changer avant le commit.
- Un délai se pose côté serveur quand on veut que le serveur abandonne.
