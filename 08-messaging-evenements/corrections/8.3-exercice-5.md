# Correction 8.3 — Exercice 5 : le dimanche des scores

> Rappel de l'énoncé : un abonné qui déduplique en mémoire, un courtier
> qui relivre deux heures d'événements après un redémarrage ; mesurer,
> rejouer avec une inbox, rédiger.

L'audit et le rejeu sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **250 membres sur 300 ont un score trop haut**, de 8 au plus, et **41
  peuvent emprunter à tort**.
- **Avec une inbox qui survit au redémarrage**, aucun.
- **La cause** : la mémoire effacée au redémarrage ; **la cause de la
  cause** : croire qu'un événement n'arrive qu'une fois.

## 1. L'audit

```go
func Audit(scores map[string]int, day []Event, threshold int) Report {
    truth := map[string]int{}
    for _, e := range day {
        truth[e.Member]++
    }
    r := Report{Members: len(truth)}
    for member, want := range truth {
        over := scores[member] - want
        if over <= 0 {
            continue
        }
        r.OverScored++
        r.MostOver = max(r.MostOver, over)
        if scores[member] >= threshold && want < threshold {
            r.WronglyEligible++
        }
    }
    return r
}
```

## 2. Les chiffres, et le rejeu

L'inbox est écrite dans le magasin des scores, sous le même verrou que le
score : elle survit au redémarrage.

```go
// Handle adds one to the score, unless the store has handled the event.
func (c *InboxConsumer) Handle(e Event) {
    c.Store.mu.Lock()
    defer c.Store.mu.Unlock()
    if c.Store.OnTime == nil {
        c.Store.OnTime, c.Store.Handled = map[string]int{}, map[string]bool{}
    }
    if c.Store.Handled[e.ID] {
        return
    }
    c.Store.OnTime[e.Member]++
    c.Store.Handled[e.ID] = true
}
```

`cmd/sunday` rejoue la journée avec les deux abonnés :

```text
3000 events, 500 delivered again at 16:00; a member may borrow from 10

                  members  over-scored  most over  wrongly eligible
memory dedupe         300          250          8                41
inbox                 300            0          0                 0
```

- **500 événements** (ceux de 14 h à 16 h) ont été livrés une seconde
  fois. L'abonné venait de redémarrer : sa mémoire était vide, il les a
  tous comptés.
- **250 membres** avaient au moins une cotisation dans ces deux heures,
  et un score trop haut d'autant ; **8 au plus**.
- **41 membres** franchissent le seuil de 10 grâce aux doublons : ils
  peuvent emprunter alors que leurs cotisations réelles ne le permettent
  pas.
- **Avec l'inbox** : aucun score faux.

## 3. La cause

**En une phrase** : l'abonné des scores retenait les événements traités
dans sa mémoire, que son redémarrage a effacée au moment où le courtier
lui relivrait deux heures d'événements.

**La cause de la cause** : l'abonné supposait qu'un événement n'arrive
qu'une fois. Or un courtier « au moins une fois » relivre précisément
après un redémarrage ou une réorganisation, et la déduplication en
mémoire ne protège que des doublons qui n'arrivent presque jamais.

## 4. Le compte rendu

1. **Quoi** : le dimanche 6 décembre 2026, 250 scores de prêt sur 300
   ont été gonflés, de 8 points au plus ; 41 membres sont devenus
   éligibles à un prêt à tort.
2. **Cause** : à 16 h, le courtier a réorganisé ses consommateurs ;
   l'abonné des scores a redémarré et reçu une seconde fois les 500
   événements de 14 h à 16 h, qu'il a comptés, sa mémoire de
   déduplication ayant été effacée.
3. **Détection** : le lundi, par l'équipe des prêts, sur le volume de
   demandes acceptées. Aucun contrôle ne comparait les scores aux
   cotisations.
4. **Correction** : les demandes de prêt acceptées depuis dimanche 16 h
   sont suspendues et réexaminées ; les scores sont recalculés depuis les
   cotisations ; l'abonné écrit l'identifiant de chaque événement dans sa
   base, dans la transaction du score.
5. **Prévention** : aucune déduplication en mémoire seulement (grille de
   la leçon) ; un test qui redémarre l'abonné et relivre ; un contrôle
   quotidien qui compare les scores et les cotisations ; à terme, le
   score calculé depuis les faits (exercice 3).

## Ce qu'il faut retenir

- Le redémarrage est le moment des doublons ; la mémoire ne les voit pas.
- L'inbox vit avec l'effet, dans la même transaction.
- Un score tiré d'événements se contrôle contre la source.
