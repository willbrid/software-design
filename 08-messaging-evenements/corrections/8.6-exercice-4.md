# Correction 8.6 — Exercice 4 : quoi garder comme événements ?

> Rappel de l'énoncé : choisir entre table d'état et event sourcing pour
> cinq éléments, et écrire les politiques de versions, d'instantanés et
> de conservation.

## En bref

- **Deux éléments en événements** : le portefeuille d'épargne et le
  prêt. Leur historique **est** le métier.
- **Trois en tables** : le profil, le tour, les paramètres ; avec un
  journal d'audit pour ce qui doit être tracé.
- **Les versions** se décident en revue, comme un contrat d'API.

## 1. Les cinq éléments

| Élément | Choix | Pourquoi | Ce que ça coûte |
|---|---|---|---|
| portefeuille d'épargne | **événements** | le membre demande « pourquoi ce solde ? » ; un contrôle demande le solde au 31 décembre | une vue pour les soldes, des instantanés, les versions pour toujours |
| prêt | **événements** | accordé, décaissé, remboursements, relances : l'histoire est le dossier | idem, sur des flux courts (quelques dizaines d'événements) |
| profil d'un membre | table | on veut l'état actuel ; l'historique d'un numéro de téléphone n'est pas le métier | un journal d'audit des modifications, pour la sécurité |
| tour | table | son état (ouvert, complet, versé) se lit d'un coup ; ses cotisations sont déjà des faits ailleurs | aucun de plus |
| paramètres d'une tontine | table, avec date d'effet | « quelle règle s'appliquait au tour de mars ? » se règle par une colonne `valid_from`, pas par des événements | une requête plus soignée |

Le test de décision : **un membre ou un contrôleur demandera-t-il un jour
« comment en est-on arrivé là ? »**, et la réponse a-t-elle de la valeur
en argent ? Oui pour le portefeuille et le prêt ; pour le reste, une table
et un journal d'audit suffisent.

## 2. La politique de versions

- **Qui décide** : l'équipe qui écrit l'événement propose, les équipes
  qui le lisent relisent, comme une modification de l'API publique.
- **Où vivent les traducteurs** : dans le paquet du contrat de
  l'événement, à côté des types de chaque version ; les lecteurs
  n'importent que la version courante et le traducteur.
- **Comment ils sont testés** : sur un échantillon **réel** de chaque
  version, extrait du journal de production (anonymisé), gardé dans le
  dépôt ; chaque nouvelle version ajoute son échantillon.

## 3. Instantanés et conservation

- **Instantanés** : pour le portefeuille, tous les 500 événements du
  membre ; pour le prêt, aucun (ses flux sont courts). L'instantané porte
  la version du code qui l'a calculé : un changement de règle de calcul
  les invalide tous, et on les recalcule.
- **Conservation** : les événements du portefeuille et des prêts, pour
  toujours, ou au moins la durée légale de conservation des pièces
  comptables. Les événements d'intégration (les notifications, les
  événements des abonnés) : 30 jours, assez pour rejouer après un
  incident.

## Ce qu'il faut retenir

- L'event sourcing là où l'historique a une valeur.
- Une table avec date d'effet suffit souvent.
- Les traducteurs se testent sur des échantillons réels.
