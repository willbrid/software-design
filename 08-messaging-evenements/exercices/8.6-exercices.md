# Exercices 8.6 — Faire évoluer les événements, et les rejouer

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 8.6](../cours/8.6-faire-evoluer-les-evenements.md) (`store`,
`contract`, `rounds`, `receipts`, `wallet`), recopiés tels quels dans le
module des exercices. Ils n'ont besoin que de la bibliothèque standard.
Tout le code ci-dessous compile et passe `go vet` ; les tontines et
l'incident sont **fictifs**.

## Exercice 1 — Compréhension : version ou pas ?

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Six changements

Pour chacun, dis s'il garde la version ou en demande une nouvelle, ce
que fait un lecteur tolérant de l'ancienne version, et dans quel ordre
déployer lecteurs et écrivains.

1. Ajouter `channel` (« ussd », « app »).
2. Renommer `amount` en `amount_fcfa`.
3. Passer `amount` d'un entier à une chaîne (`"10000"`).
4. Compter `amount` en centimes au lieu de francs, sans changer le nom.
5. Retirer `channel`, que plus personne ne lit.
6. Découper `ContributionRecorded` en `ContributionReceived` (l'argent est
   arrivé) et `ContributionAllocated` (il est affecté à un tour).

### 1.b — Trois pourquoi

1. Pourquoi le lecteur tolérant de v1 donne-t-il un résultat pire que le
   lecteur strict, alors qu'il lit plus d'événements ?
2. Pourquoi le traducteur ne réécrit-il pas les anciens événements dans le
   journal ?
3. Pourquoi charger un portefeuille depuis un instantané lit-il encore
   10 009 événements, et pas 1 000 ?

### 1.c — Rejouer

Le rejeu de la table des reçus a envoyé 100 000 SMS. Cite trois autres
effets qui ne doivent pas se reproduire pendant un rejeu, dans
l'application de tontine.

## Exercice 3 — Refactoring : reconstruire sans envoyer

*Niveau 3. Réécrire une reconstruction ; les tests sont fournis.*

```go
// Gateway sends SMS to the members' phones.
type Gateway interface {
    Send(member, text string) error
}
```

```go
// Handle records a reminder for each late member and sends it. It is the
// domain logic: it does not know whether it runs live or in a replay.
func (r *Reminders) Handle(e store.Event) error {
    var d struct {
        Round string   `json:"round"`
        Late  []string `json:"late"`
    }
    if err := json.Unmarshal(e.Body, &d); err != nil {
        return fmt.Errorf("event %d: %w", e.Seq, err)
    }
    if r.Sent == nil {
        r.Sent = map[string]int{}
    }
    for _, m := range d.Late {
        r.Sent[m]++
        if err := r.Gateway.Send(m, "round "+d.Round+": your contribution is late"); err != nil {
            return err
        }
    }
    return nil
}
```

```go
// Rebuild empties the table and replays every DeadlinePassed of the log
// into it. No SMS may leave during the rebuild, and the gateway must be
// back in place afterwards, without Handle knowing anything about it.
//
// Today it calls Handle as is.
func Rebuild(r *Reminders, log []store.Event) error {
    r.Sent = nil
    for _, e := range log {
        if e.Type != "DeadlinePassed" {
            continue
        }
        if err := r.Handle(e); err != nil {
            return err
        }
    }
    return nil
}
```

## Exercice 4 — Design : quoi garder comme événements ?

*Niveau 4. Aucune ligne de code : une page.*

Pour cinq éléments de l'application (le portefeuille d'épargne d'un
membre, le profil d'un membre, un tour, un prêt, les paramètres d'une
tontine), décide : table d'état ou event sourcing. Justifie par le
besoin d'historique, et dis ce que chaque choix coûte. Pour ceux que tu
gardes en événements, écris la politique de versions (qui décide d'une
nouvelle version, où vivent les traducteurs, comment ils sont testés), la
politique d'instantanés, et la durée de conservation.

## Exercice 5 — Incident : le rapport de l'année 2026

// Build reads the log with read.
func Build(s *store.Store, read func(store.Event) (contract.V2, error)) (Report, error) {
