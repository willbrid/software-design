# Leçon 8.2 — L'outbox transactionnelle : publier sans perdre ni inventer

## L'essentiel en deux minutes

**Le problème, en une phrase.** Enregistrer une cotisation dans la base
et l'annoncer au courtier de messages, ce sont **deux écritures** dans
deux systèmes ; si le programme s'arrête entre les deux, ou si la
seconde échoue, l'une existe sans l'autre.

**Une image.** Le **cahier des courriers à envoyer** du secrétariat : on
n'écrit pas la lettre et on ne la poste pas séparément. On note la
lettre dans le cahier **au moment même** où l'on prend la décision, sur
la même page que la décision. Le coursier passe ensuite, poste tout ce
qui n'est pas coché, et coche. S'il est interrompu, il repasse : il peut
poster une lettre deux fois, jamais l'oublier.

**Le code, en quelques lignes.** La cotisation et son événement sont
écrits dans la **même transaction** :

```go
// WithOutbox writes the contribution and its event in one transaction;
// the relay publishes the event later.
func (r *Recorder) WithOutbox(ctx context.Context, c Contribution) error {
    tx, err := r.Pool.Begin(ctx)
    if err != nil {
        return err
    }
    defer tx.Rollback(ctx)
    if _, err := tx.Exec(ctx, insert, c.ID, c.Member, c.Round, c.Amount); err != nil {
        return fmt.Errorf("record: %w", err)
    }
    if r.crash() {
        return ErrCrash
    }
    if err := outbox.Append(ctx, tx, c.Round, "ContributionRecorded", body(c)); err != nil {
        return err
    }
    return tx.Commit(ctx)
}
```

**Les règles à retenir.**

1. **Deux écritures dans deux systèmes ne sont jamais atomiques** :
   « enregistrer puis publier » perd des événements, « publier puis
   enregistrer » en invente.
2. **L'événement s'écrit dans la base**, dans la transaction du
   changement : il existe si, et seulement si, le changement existe.
3. **Un relais publie ensuite**, et marque ce qu'il a publié. S'il
   s'arrête entre les deux, il republie : **au moins une fois**, donc des
   doublons possibles (leçon 8.3).
4. **Plusieurs relais se partagent la table avec `FOR UPDATE SKIP
   LOCKED`**, sinon chacun publie tout ; mais l'ordre par clé n'est plus
   garanti, sauf si chaque clé a un seul relais.
5. **L'ordre se demande** : `ORDER BY id`, jamais l'ordre du disque.

La suite le mesure sur PostgreSQL 17.

La leçon 8.1 a laissé un trou : le bus était en mémoire, et l'événement
était publié **après** l'enregistrement. Un arrêt du programme entre les
deux, et la cotisation est enregistrée sans que personne ne le sache.
Le problème de cette leçon :

> **Comment annoncer chaque cotisation enregistrée, et seulement
> celles-là, même si le programme s'arrête au pire moment ?**

Le module de la leçon est `l82`. Il utilise le PostgreSQL 17 du niveau 5
(`sd-pg`, port 55432) et le pilote pgx. Chaque test et chaque programme
travaille dans son propre schéma. Tout ce qui suit est mesuré sur un
module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. Deux écritures, deux ordres, deux défauts

Le courtier (`sink`) tient le rôle de RabbitMQ ou de Kafka : il reçoit
des messages. La base garde les cotisations. Première façon : valider,
puis publier.

```go
// CommitThenPublish commits the contribution, then publishes.
func (r *Recorder) CommitThenPublish(ctx context.Context, c Contribution) error {
    if _, err := r.Pool.Exec(ctx, insert, c.ID, c.Member, c.Round, c.Amount); err != nil {
        return fmt.Errorf("record: %w", err)
    }
    if r.crash() {
        return ErrCrash
    }
    return r.Sink.Publish(ctx, sink.Message{Key: c.Round, Kind: "ContributionRecorded", Body: body(c)})
}
```

Deuxième façon : publier, puis valider.

```go
// PublishThenCommit publishes, then commits the contribution.
func (r *Recorder) PublishThenCommit(ctx context.Context, c Contribution) error {
    if err := r.Sink.Publish(ctx, sink.Message{Key: c.Round, Kind: "ContributionRecorded", Body: body(c)}); err != nil {
        return err
    }
    if r.crash() {
        return ErrCrash
    }
    if _, err := r.Pool.Exec(ctx, insert, c.ID, c.Member, c.Round, c.Amount); err != nil {
        return fmt.Errorf("record: %w", err)
    }
    return nil
}
```

`Crash` simule l'arrêt du programme **entre les deux écritures** : un
déploiement qui tue le processus, une machine qui redémarre, un `panic`.
Ce n'est pas rare : un programme qui écrit des milliers de fois par
heure finit toujours par s'arrêter entre deux lignes.

## 2. Mesure : ce qui se perd, ce qui s'invente

`cmd/dualwrite` enregistre 1 000 cotisations de trois façons. Le
programme s'arrête entre les deux écritures pour 3 % d'entre elles, et
la base en refuse 2 % (un montant de 0, refusé par la contrainte
`CHECK (amount > 0)` de la leçon 5.1). Le relais de l'outbox s'arrête,
lui aussi, une fois toutes les 500 publications :

```text
1000 contributions; the program stops between the two writes for 3 %; the database refuses 2 %

                        recorded  announced  lost  phantom  duplicated
commit, then publish         980        949    31        0           0
publish, then commit         949       1000     0       51           0
outbox + relay               949        949     0        0          41
```

- **Valider puis publier : 31 cotisations perdues pour les autres.**
  Elles sont dans la base, l'argent est arrivé, mais aucun reçu,
  aucun tableau de tour, aucun score ne le saura jamais.
- **Publier puis valider : 51 cotisations fantômes.** Les 20 refusées
  par la base et les 31 interrompues ont été annoncées : 51 membres
  reçoivent un reçu pour une cotisation qui n'existe pas, et le tableau
  du tour les compte payées.
- **L'outbox : ni perdue, ni fantôme.** Les cotisations interrompues ne
  sont pas enregistrées non plus (la transaction est annulée), et le
  membre lit une erreur qu'il peut réessayer. Le prix : **41
  événements publiés deux fois**, quand le relais s'est arrêté après
  avoir publié, et avant d'avoir coché.

## 3. L'outbox

La table `outbox` est écrite dans la même transaction que la
cotisation :

```go
// Schema is the table of contributions and the outbox.
const Schema = `
```

```go
// Append writes an event in tx: it is published if, and only if, tx
// commits.
func Append(ctx context.Context, tx pgx.Tx, key, kind string, body []byte) error {
    _, err := tx.Exec(ctx, `INSERT INTO outbox (key, kind, body) VALUES ($1, $2, $3)`, key, kind, body)
    return err
}
```

Le **relais** lit les événements non publiés, les publie dans l'ordre,
puis les coche, dans une transaction :

```go
// Once publishes one batch and returns how many events it published.
func (r *Relay) Once(ctx context.Context) (int, error) {
    tx, err := r.Pool.Begin(ctx)
    if err != nil {
        return 0, err
    }
    defer tx.Rollback(ctx)
    q := `SELECT id, key, kind, body FROM outbox
          WHERE published_at IS NULL AND ($2 = 0 OR (hashtext(key) & 2147483647) % $2 = $3)
          ORDER BY id LIMIT $1`
    if r.Lock {
        q += ` FOR UPDATE SKIP LOCKED`
    }
    rows, err := tx.Query(ctx, q, r.Batch, r.Parts, r.Part)
    if err != nil {
        return 0, err
    }
    msgs, err := pgx.CollectRows(rows, func(row pgx.CollectableRow) (sink.Message, error) {
        var m sink.Message
        err := row.Scan(&m.ID, &m.Key, &m.Kind, &m.Body)
        return m, err
    })
    if err != nil {
        return 0, err
    }
    ids := make([]int64, 0, len(msgs))
    for _, m := range msgs {
        if err := r.Sink.Publish(ctx, m); err != nil {
            return 0, fmt.Errorf("publish %d: %w", m.ID, err)
        }
        if r.Crash != nil && r.Crash() {
            return 0, ErrCrash
        }
        ids = append(ids, m.ID)
    }
    if _, err := tx.Exec(ctx, `UPDATE outbox SET published_at = now() WHERE id = ANY($1)`, ids); err != nil {
        return 0, err
    }
    return len(msgs), tx.Commit(ctx)
}
```

Trois détails comptent :

- **`ORDER BY id`** : sans lui, PostgreSQL rend les lignes dans l'ordre
  qui l'arrange. La campagne (section 6) montre que les tests ne le
  voyaient pas.
- **Publier, puis cocher** : dans l'autre ordre, un arrêt entre les deux
  perdrait l'événement. On choisit le doublon plutôt que la perte, car
  un doublon se détecte chez l'abonné (leçon 8.3), une perte nulle part.
- **L'index partiel** `WHERE published_at IS NULL` : le relais ne relit
  que ce qui reste à publier, même quand la table contient des millions
  de lignes déjà publiées.

## 4. Mesure : plusieurs relais

Un relais publie environ 800 événements par seconde quand chaque
publication prend 1 ms. Pour aller plus vite, on en lance quatre.
`cmd/relays` vide une outbox de 4 000 événements de 40 tours :

```text
4,000 events of 40 rounds, batches of 100, 1 ms per publication

                                     published duplicated  out of order      time
4 relays, plain SELECT                    4000       4000             0     5.17s
    1 relay runs failed: ERROR: deadlock detected (SQLSTATE 40P01)
4 relays, FOR UPDATE SKIP LOCKED          4000          0          2420    1.328s
4 relays, SKIP LOCKED, one part each      4000          0             0    1.688s
1 relay                                   4000          0             0    5.105s
```

- **Quatre relais avec un `SELECT` simple** : chaque événement est
  publié **plusieurs fois** (les 4 000 ont des doublons), c'est aussi
  lent qu'un seul relais, et PostgreSQL détecte un **interblocage** :
  deux relais cochent les mêmes lignes dans des ordres différents.
- **Avec `FOR UPDATE SKIP LOCKED`** : chaque relais verrouille son lot,
  les autres sautent les lignes verrouillées et prennent les suivantes.
  Aucun doublon, quatre fois plus vite. Mais **2 420 événements arrivent
  après un événement plus récent du même tour** : le relais B a publié le
  lot 101-200 pendant que le relais A publiait encore le lot 1-100.
- **Un relais par part des tours** (`hashtext(key) % 4`) : aucun doublon,
  **aucune inversion**, et presque aussi rapide. Les parts ne sont pas
  égales (40 tours répartis par un hachage), d'où 1,7 s au lieu de 1,3 s.

La documentation de PostgreSQL le dit de `SKIP LOCKED` : il donne une vue
incohérente des données, ne convient pas à un usage général, mais sert à
éviter la contention entre plusieurs consommateurs d'une table utilisée
comme une file. C'est exactement l'outbox.

## 5. Ce que l'ordre veut dire

L'outbox garantit l'ordre **par clé**, pas l'ordre global. Pour un tour,
`ContributionRecorded` puis `ContributionReversed` doivent arriver dans
cet ordre, sinon l'abonné annule une cotisation qu'il ne connaît pas
encore, puis l'enregistre comme payée. Entre deux tours différents,
l'ordre n'a pas de sens, et c'est ce qui permet de paralléliser.

Choisir la clé, c'est choisir ce qui doit rester ordonné : le tour, le
membre, la tontine. Les courtiers suivent la même règle (une partition
Kafka par clé, une file par clé).

## 6. La campagne

Huit mutations, dans le relais et l'enregistrement :

```text
relais sans verrou                           tuee
déjà publiés relus                           tuee
sans ORDER BY                                SURVIT
parts qui se chevauchent                     tuee
pas de redémarrage                           tuee
lot marqué à moitié                          tuee
événement après le commit                    tuee
cotisation hors de la transaction            tuee
7/8 tuees
```

**Le relais sans `ORDER BY` survivait.** Les tests passaient, parce que
le planificateur choisissait l'index partiel, qui rend les lignes dans
l'ordre des `id`. Rien ne le garantit : une outbox qui grossit peut être
lue autrement. Le test ajouté écrit de nouvelles versions des premières
lignes à la fin de la table (une mise à jour, en PostgreSQL, écrit une
nouvelle version), interdit l'index sur sa connexion, et vérifie l'ordre :

```go
func TestTheRelayFollowsTheOutboxOrderNotTheDiskOrder(t *testing.T) {
    ctx := context.Background()
    s := &sink.Sink{}
    // One connection, on which the planner may not use the index: the
    // order of the rows is then the order on disk, as it can be when the
    // planner prefers a scan of the table.
    r := &Relay{Pool: pg.ForTestConns(t, Schema, 1), Sink: s, Batch: 7}
    fill(t, r, 1, 50)
    // An update writes new versions of the first rows at the end of the
    // table: a scan without ORDER BY now meets them last.
    for _, q := range []string{`UPDATE outbox SET kind = 'E2' WHERE id <= 10`, `SET enable_indexscan = off`, `SET enable_bitmapscan = off`} {
        if _, err := r.Pool.Exec(ctx, q); err != nil {
            t.Fatal(err)
        }
    }
    if err := r.Run(ctx); err != nil {
        t.Fatal(err)
    }
    if s.Total() != 50 || s.OutOfOrder() != 0 {
        t.Fatalf("total %d, out of order %d; want 50 and 0", s.Total(), s.OutOfOrder())
    }
}
```

## 7. La grille

| Pour chaque événement | À vérifier |
|---|---|
| l'écriture | dans la transaction du changement, jamais avant ni après |
| le relais | publie, **puis** coche ; redémarre après un arrêt |
| l'ordre | `ORDER BY id`, et une clé qui dit ce qui doit rester ordonné |
| plusieurs relais | `FOR UPDATE SKIP LOCKED`, et un relais par part si l'ordre par clé compte |
| les doublons | attendus : l'abonné les supporte (leçon 8.3) |
| la table | un index partiel sur ce qui reste à publier ; une purge de ce qui est publié depuis longtemps |
| la surveillance | l'âge du plus ancien événement non publié |

## 8. Les trois erreurs qui restent

### « Une transaction distribuée réglerait le problème »

Le protocole à deux phases (2PC) entre la base et le courtier demande
que les deux le supportent, et lie la disponibilité du service à celle
des deux à la fois. Chris Richardson, qui décrit le motif de l'outbox,
écarte ce chemin pour ces raisons. L'outbox n'a besoin que de la
transaction que la base offre déjà.

### « On publie après le commit, et on réessaie si ça échoue »

Réessayer couvre l'échec de la publication, pas l'arrêt du programme :
après un arrêt, il ne reste personne pour réessayer, et aucune trace de
ce qui restait à publier. Les 31 cotisations perdues de la section 2 ne
sont pas des échecs de publication, ce sont des arrêts.

### « L'outbox publie exactement une fois »

Non : au moins une fois. 41 doublons sur 949 avec un relais qui s'arrête
une fois toutes les 500 publications. Aucun relais ne peut publier et
cocher atomiquement, puisque ce sont encore deux systèmes. L'abonné doit
reconnaître un événement déjà reçu : c'est le sujet de la leçon 8.3.

## 9. Le lien avec la production

- **L'âge du plus ancien événement non publié** est la métrique du
  relais : il dit à la fois que le relais est arrêté, lent, ou bloqué par
  un courtier en panne.
- **La purge** : l'outbox grossit à chaque écriture. Une tâche supprime
  ce qui est publié depuis plus de quelques jours, par lots (leçon 5.4),
  pour ne pas tenir de verrou longtemps.
- **La capture des changements** (CDC, avec Debezium par exemple) lit le
  journal de PostgreSQL au lieu de lire la table : moins de charge sur la
  base, mais un outil de plus à exploiter. La table `outbox` reste la
  source ; seul le relais change.
- **Le délai de publication** s'ajoute à celui des abonnés : un relais
  qui lit toutes les secondes ajoute jusqu'à une seconde à chaque
  événement. `LISTEN/NOTIFY` peut réveiller le relais dès le commit.

## 10. Ce qu'il faut retenir

1. Base et courtier : deux écritures, jamais atomiques ensemble.
2. L'événement s'écrit dans la transaction du changement.
3. Le relais publie puis coche : au moins une fois, jamais zéro.
4. Plusieurs relais : `SKIP LOCKED`, et une part par relais si l'ordre
   compte.
5. L'ordre se demande par `ORDER BY`.

## 11. Approfondissement

### L'inbox, symétrique de l'outbox

L'abonné qui reçoit un événement et écrit dans sa propre base a le même
problème dans l'autre sens : traiter puis accuser réception, ou
l'inverse. La solution est symétrique : noter l'identifiant de
l'événement reçu **dans la transaction** du traitement. C'est l'**inbox**,
construite à la leçon 8.3.

### Un seul relais, élu

Plutôt que des parts, on peut faire tourner un seul relais à la fois sur
plusieurs machines, avec un verrou consultatif de PostgreSQL
(`pg_try_advisory_lock`) pour l'élire. Il est plus simple, mais plus
lent, et le jour où il perd son verrou sans le savoir, deux relais
publient. La leçon 9.6 traite ce problème du chef qui croit l'être
encore.

## 12. Le réflexe à installer

Devant chaque « enregistrer, puis prévenir », demande-toi :

1. Si le programme s'arrête entre les deux lignes, que reste-t-il ?
2. L'événement est-il écrit dans la même transaction que le changement ?
3. Le relais coche-t-il après avoir publié ?
4. Quelle clé doit rester ordonnée, et combien de relais la lisent ?
5. Qui voit qu'un événement attend depuis dix minutes ?
