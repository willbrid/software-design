# Leçon 8.3 — Au moins une fois : des abonnés qui supportent le doublon, le désordre et le message empoisonné

## L'essentiel en deux minutes

**Le problème, en une phrase.** L'outbox (leçon 8.2) publie chaque
événement **au moins une fois** : l'abonné recevra des doublons, des
événements dans le désordre, et un jour un message qu'il ne sait pas
lire, qui bloquera tous les suivants.

**Trois images.**

- **Le cahier de caisse coché** : la caissière qui reçoit deux fois le
  même bordereau regarde son numéro dans le cahier ; déjà coché, elle ne
  l'encaisse pas une seconde fois. Le numéro est noté **en même temps**
  que l'argent est rangé.
- **Le courrier qui arrive dans le désordre** : la lettre « j'annule ma
  commande » arrive avant la commande. Si l'on traite chaque lettre comme
  la dernière, la commande annulée est livrée. Il faut regarder la date
  de chaque lettre.
- **La lettre illisible** : le facteur qui la représente sans fin à la
  même porte ne distribue plus rien d'autre. On la met de côté, au
  service des lettres en souffrance, et on continue la tournée.

**Le code, en quelques lignes.** L'identifiant de l'événement est écrit
dans la même transaction que son effet ; s'il y est déjà, rien n'est
refait :

```go
    tag, err := tx.Exec(ctx, `INSERT INTO inbox (event_id) VALUES ($1) ON CONFLICT DO NOTHING`, m.ID)
    if err != nil {
        return err
    }
    if tag.RowsAffected() == 0 {
        return nil // handled before
    }
```

**Les règles à retenir.**

1. **Un abonné reçoit des doublons** : il est idempotent, par une
   **inbox** (les identifiants déjà traités, dans sa base) ou par un
   effet qui pose un état au lieu d'ajouter.
2. **La mémoire du programme ne suffit pas** : elle s'efface au
   redémarrage, précisément quand les doublons arrivent.
3. **Un abonné reçoit dans le désordre** : il compare la séquence de
   l'événement à celle qu'il a déjà appliquée.
4. **Une erreur permanente va aux lettres mortes** tout de suite ; une
   erreur passagère se réessaie. Ne pas les distinguer, c'est bloquer la
   file, ou jeter de bons messages.
5. **Les lettres mortes se surveillent et se rejouent** : ce sont des
   cotisations que le tableau n'a pas comptées.

La suite le mesure avec le tableau des tours, qui reçoit les événements
des paiements.

---

Le tableau des tours (leçon 8.1) affiche, pour chaque tour, ce que les
membres ont versé. Il ne lit pas la table des paiements : il garde ses
propres tables, alimentées par les événements `ContributionRecorded` et
`ContributionReversed`. Le problème de cette leçon :

> **Comment tenir un tableau juste, quand chaque événement peut arriver
> deux fois, en retard, ou illisible ?**

Le module de la leçon est `l83`. Il utilise le PostgreSQL 17 du niveau 5
(`sd-pg`, port 55432) et le pilote pgx. Tout ce qui suit est mesuré sur
un module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. Ce que le courtier fait vraiment

Le paquet `delivery` joue le rôle du courtier, avec les trois défauts
qu'ont tous les courtiers « au moins une fois » :

```go
// Options says how the broker and the consumer misbehave.
type Options struct {
    Again   func(i int) bool // deliver message i once more, after it was acknowledged
    Crash   func(i int) bool // the consumer stops after handling message i, before acknowledging it
    Restart func()           // called when the consumer starts again after a stop

    MaxAttempts int // 0: retry a failing message forever
    // DeadOnPermanent sends a message to the dead letters at its first
    // permanent error.
    DeadOnPermanent bool
    Retry           time.Duration // pause between two attempts
    Dead            func(m Message, err error)
}
```

- **`Again`** : le courtier redonne un message déjà acquitté. Chez
  RabbitMQ ou Kafka, cela arrive quand un acquittement se perd, ou quand
  un groupe de consommateurs se réorganise.
- **`Crash`** : l'abonné fait son travail, puis s'arrête avant
  d'acquitter. Le courtier, qui n'a pas reçu l'acquittement, redonne le
  message à l'abonné redémarré.
- **Le désordre** vient d'ailleurs : de deux relais (leçon 8.2), de deux
  partitions, ou d'un message réessayé pendant que les suivants passent.

## 2. Cinq abonnés

Le plus simple ajoute chaque événement au total du tour :

```go
// add adds the event to the total of its round: plus for a recording,
// minus for a reversal.
func add(ctx context.Context, db execer, m delivery.Message) error {
    c, err := events.Decode(m)
    if err != nil {
        return err
    }
    amount := c.Amount
    if m.Kind == "ContributionReversed" {
        amount = -amount
    }
    _, err = db.Exec(ctx, `
        INSERT INTO round_totals (round, paid) VALUES ($1, $2)
        ON CONFLICT (round) DO UPDATE SET paid = round_totals.paid + excluded.paid`, c.Round, amount)
    return err
}
```

Le deuxième retient, **en mémoire**, les identifiants déjà vus. Le
troisième les écrit dans une table `inbox`, **dans la même transaction**
que l'ajout :

```go
// Handle adds m once, however many times it arrives.
func (b *Inbox) Handle(ctx context.Context, m delivery.Message) error {
    tx, err := b.Pool.Begin(ctx)
    if err != nil {
        return err
    }
    defer tx.Rollback(ctx)
    tag, err := tx.Exec(ctx, `INSERT INTO inbox (event_id) VALUES ($1) ON CONFLICT DO NOTHING`, m.ID)
    if err != nil {
        return err
    }
    if tag.RowsAffected() == 0 {
        return nil // handled before
    }
    if err := add(ctx, tx, m); err != nil {
        return err
    }
    if b.Crash != nil && b.Crash() {
        return ErrCrash
    }
    return tx.Commit(ctx)
}
```

Les deux derniers ne comptent pas : ils posent l'**état** de chaque
cotisation (« payée » ou « annulée »). Écrire deux fois le même état ne
change rien : l'effet est idempotent par nature. Le premier garde le
dernier état reçu ; le second ne l'applique que si l'événement est plus
récent que celui déjà appliqué, d'après sa **séquence** (l'`id` de
l'outbox) :

```go
// Handle sets the status m says, if m is newer than what the board has.
func (b *Sequenced) Handle(ctx context.Context, m delivery.Message) error {
    return setStatus(ctx, b.Pool, m, `ON CONFLICT (contribution) DO UPDATE SET status = excluded.status, seq = excluded.seq
        WHERE contribution_status.seq < excluded.seq`)
}
```

## 3. Mesure : doublons et désordre

`cmd/duplicates` livre les 2 200 événements de 2 000 cotisations (une sur
dix est annulée) à chacun des cinq abonnés. Le courtier redonne 3 % des
messages, l'abonné s'arrête avant d'acquitter pour 1 %, et une
annulation sur dix arrive avant l'enregistrement qu'elle annule :

```text
2200 events of 2,000 contributions; owed to the rounds: 18000000 FCFA

                             deliveries    board, FCFA  off by FCFA
increment                          2290       18860000       860000
increment, memory dedupe           2290       18190000       190000
increment, inbox                   2290       18000000            0
status, last write wins            2290       18200000       200000
status, sequenced                  2290       18000000            0
```

- **L'ajout naïf compte 860 000 FCFA de trop** : chaque doublon est
  ajouté une seconde fois. C'est l'exemple même de Chris Richardson : un
  abonné qui soustrait un débit du solde calcule un solde faux.
- **La déduplication en mémoire en laisse 190 000** : elle oublie tout à
  chaque redémarrage, et le redémarrage est justement ce qui provoque le
  doublon.
- **L'inbox est juste**, quels que soient les doublons et l'ordre (des
  ajouts et des retraits donnent le même total dans tous les ordres).
- **Le dernier état reçu compte 200 000 FCFA de trop** : 20 cotisations
  annulées sont marquées payées, parce que leur enregistrement est arrivé
  **après** leur annulation, et l'a écrasée. Aucun doublon n'y est pour
  rien : c'est le désordre.
- **L'état séquencé est juste** : l'enregistrement en retard porte une
  séquence plus petite que l'annulation déjà appliquée, il est ignoré.

## 4. Mesure : le message empoisonné

Un jour, une nouvelle version des paiements écrit le montant en texte
(`"amount":"10000"`). Aucune version du tableau ne sait le lire, et aucune
nouvelle tentative n'y changera rien. `cmd/poison` livre 1 000 événements
dans une seule file ; l'événement 10 est illisible, et la base du
tableau est en panne pendant 200 ms au moment de l'événement 500 :

```text
1,000 events; event 10 cannot be read; the database is down for 200 ms at event 500; retry every 10 ms; 3 s at most

                                          handled  failures    time  dead letters
retry forever                                  10       289      3s
5 attempts, then dead letter                  995        29   250ms  10 500 501 502 503
permanent: dead letter; others: retry         999        21   210ms  10
```

- **Réessayer sans fin** : le tableau traite les 10 premiers événements
  (0 à 9), puis bute sur l'événement 10 **pendant 3 secondes** (et, en
  production, jusqu'à ce que quelqu'un intervienne). Les 989 suivants
  attendent : c'est le bus de la leçon 8.1, qui réessayait toujours.
- **Cinq essais, puis lettre morte** : le message illisible part aux
  lettres mortes, mais **quatre bons messages aussi** (500 à 503), qui ont
  épuisé leurs cinq essais pendant la panne de la base. Quatre
  cotisations valides manquent au tableau.
- **Distinguer** : une erreur **permanente** (un corps illisible) part aux
  lettres mortes au premier essai ; une erreur **passagère** (la base en
  panne) se réessaie jusqu'à la fin de la panne. Un seul message en
  lettre morte, le bon.

La distinction se fait au décodage, qui marque ses erreurs :

```go
// Decode reads a body; a body it cannot read is an error that no retry
// will fix.
func Decode(m delivery.Message) (Contribution, error) {
    var c Contribution
    if err := json.Unmarshal(m.Body, &c); err != nil {
        return c, fmt.Errorf("event %s: %w: %w", m.ID, delivery.ErrPermanent, err)
    }
    if c.Contribution == "" || c.Round == "" || c.Amount <= 0 {
        return c, fmt.Errorf("event %s: %w: incomplete body %s", m.ID, delivery.ErrPermanent, m.Body)
    }
    return c, nil
}
```

## 5. La campagne

Neuf mutations, dans les abonnés, la livraison et le décodage :

```text
inbox non consultée                          tuee
effet hors de la transaction                 tuee
séquence <= au lieu de <                     SURVIT
séquence ignorée                             tuee
annulation ajoutée                           tuee
toute erreur permanente                      tuee
une tentative de trop                        tuee
montant non vérifié                          tuee
JSON illisible non permanent                 tuee
8/9 tuees
```

- **L'effet hors de la transaction** survivait au premier passage : écrire
  l'ajout par le pool au lieu de la transaction ne changeait aucun test,
  puisque rien ne s'arrêtait entre l'ajout et le commit. Le test ajouté
  arrête l'abonné à cet endroit, et vérifie que la nouvelle livraison ne
  compte pas deux fois :

```go
func TestAStopBeforeTheCommitUndoesTheWorkAndTheInbox(t *testing.T) {
    pool := pg.ForTest(t, Schema)
    stop := true
    b := &Inbox{Pool: pool, Crash: func() bool { return stop }}
    if err := b.Handle(context.Background(), rec1); !errors.Is(err, ErrCrash) {
        t.Fatalf("Handle = %v, want ErrCrash", err)
    }
    stop = false
    if got := total(t, pool, b, rec1); got != 100 {
        t.Fatalf("total %d after the new delivery, want 100", got)
    }
}
```

- **`<=` au lieu de `<`** survit, et c'est normal : réappliquer un
  événement de même séquence, c'est réécrire le même état. La mutation ne
  change pas le comportement ; aucun test ne peut la tuer.

## 6. La grille

| Pour chaque abonné | À vérifier |
|---|---|
| les doublons | inbox dans la transaction de l'effet, ou un effet qui pose un état |
| la mémoire | rien de ce qui protège des doublons ne vit seulement en mémoire |
| le désordre | une séquence par clé, comparée avant d'appliquer ; ou un effet indépendant de l'ordre |
| les erreurs | permanentes : lettres mortes au premier essai ; passagères : nouvelles tentatives, espacées |
| les lettres mortes | une alerte dès la première, un outil pour les rejouer |
| l'inbox | une purge, plus lente que le plus long délai de redélivrance |

## 7. Les trois erreurs qui restent

### « Notre courtier garantit exactement une fois »

Certains courtiers l'annoncent, dans des limites précises : à l'intérieur
du courtier, ou entre le courtier et une base qui participe à la même
transaction. Entre le courtier et **la base de l'abonné**, il reste deux
écritures, et le problème de la leçon 8.2 à l'envers. L'abonné qui ne
supporte pas le doublon attend que le premier incident le lui apprenne.

### « On déduplique en mémoire, c'est plus rapide »

190 000 FCFA de trop dans la section 3 : le redémarrage efface la mémoire
au moment précis où les doublons arrivent. Une table `inbox` coûte une
insertion par événement, dans une transaction déjà ouverte.

### « On réessaie cinq fois, puis on jette »

Quatre bonnes cotisations jetées pendant une panne de 200 ms. Le nombre
d'essais ne distingue pas une base en panne d'un message illisible ; le
type d'erreur, si.

## 8. Le lien avec la production

- **Les lettres mortes** sont une file à part, surveillée : une alerte à
  la première, avec le message, l'erreur, et l'heure. Le rejeu passe par
  un outil (relire, corriger le consommateur, republier), jamais par une
  requête SQL à la main.
- **Un message empoisonné et l'ordre** : mettre de côté un enregistrement
  et traiter l'annulation suivante de la même cotisation donne un état
  faux. Quand l'ordre par clé compte, on met de côté **la clé** (les
  messages suivants de la même cotisation attendent), pas seulement le
  message.
- **La purge de l'inbox** : les identifiants ne servent que tant qu'un
  doublon peut encore arriver. Une semaine suffit pour un courtier qui ne
  garde pas les messages plus de trois jours.
- **Les tentatives** s'espacent (la leçon 9.2 règle le délai et le
  hasard) : réessayer toutes les 10 ms pendant une panne d'une heure, c'est
  360 000 requêtes inutiles vers une base qui essaie de redémarrer.

## 9. Ce qu'il faut retenir

1. Au moins une fois veut dire doublons : inbox, ou effet qui pose un
   état.
2. Pas de déduplication en mémoire seulement.
3. Le désordre se traite par une séquence par clé.
4. Erreur permanente : lettre morte au premier essai ; passagère :
   nouvelle tentative.
5. Une lettre morte est une alerte, et un rejeu.

## 10. Approfondissement

### Idempotent par l'effet, ou par l'inbox ?

Un effet qui pose un état (`status = 'paid'`, avec la séquence) est
idempotent sans table de plus, et supporte le désordre. Un effet qui
**ajoute** (un total, un solde, un compteur) ne l'est pas : il lui faut
l'inbox. Quand c'est possible, on préfère garder les faits (les
cotisations et leur état) et **calculer** le total à la lecture, plutôt
que de tenir un total qui s'incrémente : c'est ce que fait
`contribution_status`.

### L'identifiant de l'événement

L'inbox repose sur un identifiant **stable** : le même événement, livré
deux fois, porte le même. L'`id` de l'outbox l'est. Un identifiant
fabriqué par le relais au moment de publier ne l'est pas : un relais qui
republie après un arrêt (leçon 8.2) en fabriquerait un nouveau, et l'inbox
ne verrait plus le doublon.

## 11. Le réflexe à installer

Devant chaque abonné, demande-toi :

1. Que fait-il s'il reçoit deux fois le même événement ? Et après un
   redémarrage ?
2. Que fait-il si l'annulation arrive avant l'enregistrement ?
3. Quelles erreurs sont permanentes, lesquelles passagères ?
4. Où vont les messages qu'il ne peut pas traiter, et qui le voit ?
5. Comment rejoue-t-on une lettre morte une fois le défaut corrigé ?
