# Leçon 8.4 — La cohérence éventuelle : des vues en retard, et comment vivre avec

## L'essentiel en deux minutes

**Le problème, en une phrase.** Une vue construite à partir des
événements (le tableau des tours) suit la source **avec un retard** : le
membre qui vient de payer ne voit pas son paiement, et celui qui décide
d'après la vue décide sur un passé de quelques centaines de
millisecondes.

**Trois images.**

- **Le relevé bancaire** : le virement fait ce matin n'apparaît que
  demain. La banque n'a pas perdu l'argent ; le relevé est en retard sur
  le compte.
- **Le ticket de caisse** : au guichet, on vous donne un numéro de
  reçu. Si le relevé ne montre pas encore l'opération, on montre le
  numéro et on attend qu'il y soit. C'est « lire ce qu'on vient
  d'écrire ».
- **Le caissier qui rend la monnaie d'après le relevé d'hier** : il ne
  verra pas le chèque revenu impayé ce matin. On décide d'après le
  compte, pas d'après le relevé.

**Le code, en quelques lignes.** Après son paiement, le membre attend que
la vue ait appliqué l'événement de son paiement, puis la lit :

```go
            pos, err := l.Record(ctx, c)
            if err != nil {
                panic(err)
            }
```

```go
            if err := projection.WaitFor(ctx, pool, pos, 10*time.Millisecond, 2*time.Second); err != nil {
                panic(err)
            }
```

**Les règles à retenir.**

1. **Une vue construite par des événements est en retard**, toujours :
   on mesure ce retard, on ne le suppose pas nul.
2. **On montre à chacun ce qu'il vient d'écrire** : l'écriture rend une
   position, la lecture attend que la vue l'ait atteinte.
3. **On ne décide jamais sur la vue** ce qui engage de l'argent : on
   relit la source.
4. **Suivre une position exige qu'elle avance dans l'ordre où les
   écritures deviennent visibles** : un `id` qui augmente ne le garantit
   pas.
5. **Une transaction longue, n'importe où dans la base, retarde la vue**.

La suite le mesure sur PostgreSQL 17, avec le tableau des tours.

---

Les leçons 8.2 et 8.3 ont fait arriver les événements, une fois et dans
l'ordre, jusqu'au tableau des tours. Ce tableau est une **vue** : une
table taillée pour l'écran (« qui a payé dans ce tour ? »), séparée de la
table des paiements, et construite par un **projecteur** qui lit les
événements. Le problème de cette leçon :

> **Que voit-on dans une vue qui suit la source avec un retard, et
> comment décider et afficher juste malgré lui ?**

Le module de la leçon est `l84`. Il utilise le PostgreSQL 17 du niveau 5
(`sd-pg`, port 55432) et le pilote pgx. Tout ce qui suit est mesuré sur
un module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. La source, la vue, le projecteur

La source écrit la cotisation et son événement dans la même
transaction (leçon 8.2), et rend la **position** de l'événement :

```go
func (l *Ledger) write(ctx context.Context, kind string, c Contribution, sql string, args ...any) (int64, error) {
    tx, err := l.Pool.Begin(ctx)
    if err != nil {
        return 0, err
    }
    defer tx.Rollback(ctx)
    if _, err := tx.Exec(ctx, sql, args...); err != nil {
        return 0, err
    }
    if l.Ordered {
        if _, err := tx.Exec(ctx, `SELECT pg_advisory_xact_lock(84)`); err != nil {
            return 0, err
        }
    }
    body, _ := json.Marshal(c)
    var pos int64
    if err := tx.QueryRow(ctx, `INSERT INTO outbox (kind, body) VALUES ($1, $2) RETURNING id`, kind, body).Scan(&pos); err != nil {
        return 0, err
    }
    return pos, tx.Commit(ctx)
}
```

La vue a sa table, et la position du projecteur :

```go
// Schema is the view and the position of the projector in the outbox.

```

Le projecteur lit les événements après sa position, les applique à la
vue, et avance sa position **dans la même transaction** que la vue. C'est
une inbox réduite à un seul nombre (leçon 8.3) : comme il applique dans
l'ordre, il lui suffit de savoir jusqu'où il est allé.

## 2. Le piège : suivre les `id`

La première version du projecteur lisait `WHERE id > position ORDER BY
id`. C'est le code qu'on écrit naturellement, et il **perd des
événements**. `cmd/gaps` enregistre 4 000 cotisations depuis 20
écrivains simultanés, pendant qu'un projecteur lit toutes les 5 ms :

```text
4,000 contributions, 20 writers at once, a projector reading every 5 ms

projector follows               source     view   missed  writes/second
ids, commit in any order          4000     3777      223           3838
ids, outbox lock until commit     4000     4000        0            337
transactions, then ids            4000     4000        0           4561
```

**223 cotisations ne sont jamais arrivées dans la vue** (et 6, 12 ou 14
lors d'autres exécutions : le nombre dépend du hasard des commits). Le
mécanisme :

1. la transaction A prend l'`id` 10 pour son événement, mais ne valide
   pas encore ;
2. la transaction B prend l'`id` 11, et valide ;
3. le projecteur lit : il voit 11 (10 est invisible, A n'a pas validé),
   l'applique, et avance sa position à 11 ;
4. A valide ; l'événement 10 devient visible, derrière la position.
   Le projecteur ne le lira jamais.

Une séquence donne des numéros **dans l'ordre où on les demande**, pas
dans l'ordre où les transactions valident. Le test qui le reproduit
ouvre une transaction, la laisse ouverte pendant qu'une autre valide,
puis la valide :

```go
func TestFollowingIDsSkipsAnEventCommittedLate(t *testing.T) {
    ctx := context.Background()
    pool, l := setup(t)
    commit := lateWriter(t, pool, "c1") // takes id 1, commits last
    if _, err := l.Record(ctx, contribution("c2", "m2")); err != nil {
        t.Fatal(err)
    }
    p := &Projector{Pool: pool, Batch: 10, IDOnly: true}
    catchUp(t, p)
    commit()
    catchUp(t, p)
    if n := paidInRound(t, pool); n != 1 {
        t.Fatalf("view counts %d, want 1: c1 was skipped for good", n)
    }
}
```

Deux corrections :

- **un verrou sur l'outbox jusqu'au commit** (`pg_advisory_xact_lock`) :
  les événements deviennent visibles dans l'ordre de leurs `id`. Juste,
  mais le débit tombe de 3 838 à **337 écritures par seconde** : chaque
  transaction attend que la précédente ait écrit son journal sur le
  disque ;
- **suivre les transactions** : chaque événement porte l'identifiant de
  sa transaction (`xid8`), et le projecteur ne lit que les événements des
  transactions **plus anciennes que toute transaction encore en cours**.
  Celles-là ne peuvent plus changer. Juste, et sans perte de débit.

```go
const (
    nextByID = `SELECT id, tx, kind, body, created_at FROM outbox
        WHERE id > $1 ORDER BY id LIMIT $2`
    nextByTransaction = `SELECT id, tx, kind, body, created_at FROM outbox
        WHERE (tx, id) > ($1::xid8, $2) AND tx < pg_snapshot_xmin(pg_current_snapshot())
        ORDER BY tx, id LIMIT $3`
)
```

La documentation de PostgreSQL définit `xmin` d'un instantané comme
« l'identifiant de transaction le plus bas encore actif » : toutes les
transactions en dessous ont validé ou annulé, définitivement.

## 3. Mesure : voir son propre paiement

`cmd/lag` enregistre 600 cotisations, une toutes les 10 ms. Le projecteur
lit toutes les 300 ms. Chaque membre regarde son tour tout de suite après
avoir payé, après avoir attendu que la vue atteigne la position de son
paiement, et une seconde après :

```text
600 contributions, one every 10 ms; the projector reads every 300 ms

the member looks at the round          sees their payment
right after paying                                  0/600
after waiting for its position                    600/600
one second after paying                           600/600

wait for the position: p50 200ms, p99 370ms, max 385ms
lag of the view: up to 38 events waiting, the oldest 375ms old
```

- **Tout de suite : aucun des 600 membres ne voit son paiement.** Le
  membre qui ne voit pas son paiement fait ce que fait tout le monde : il
  paie une seconde fois, ou il appelle.
- **En attendant sa position : les 600 le voient**, après 200 ms en
  médiane, 370 ms au pire (le temps que le projecteur repasse).
- **Le retard de la vue** ne dépasse pas 375 ms, avec 38 événements en
  attente au plus : c'est la métrique à surveiller (`Lag`).

Lire ce qu'on vient d'écrire, c'est ce que Werner Vogels appelle la
cohérence *read-your-writes* : celui qui a écrit voit toujours au moins
ce qu'il a écrit. L'écriture rend sa position ; l'écran l'attend :

```go
// WaitFor waits until the view has applied the event at pos, checking
// every poll, for at most max.
func WaitFor(ctx context.Context, pool *pgxpool.Pool, pos int64, poll, max time.Duration) error {
    deadline := time.Now().Add(max)
    for {
        var applied bool
        if err := pool.QueryRow(ctx, `
            SELECT (o.tx, o.id) <= (p.tx, p.position)
            FROM outbox o, projection_position p WHERE p.name = 'rounds' AND o.id = $1`, pos).Scan(&applied); err != nil {
            return err
        }
        if applied {
            return nil
        }
        if time.Now().After(deadline) {
            return ErrNotYet
        }
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-time.After(poll):
        }
    }
}
```

Deux autres façons, selon l'écran : **afficher l'écriture tout de suite**
côté application (« paiement en cours de confirmation »), ou **lire la
source** pour ce membre-là, le temps que la vue rattrape.

## 4. Mesure : décider d'après la vue

À la fin du tour, les tontines versent la cagnotte des tours complets.
`cmd/decide` prend 40 tours complets de 25 cotisations, et décide d'un
versement toutes les 50 ms. Huit tours reçoivent une annulation de
paiement de 20 à 400 ms avant leur décision :

```text
40 complete rounds of 25; one payout decision every 50 ms; 8 rounds get a reversal 20 to 400 ms before their decision; the projector reads every 300 ms

decided from      paid out   wrongly paid out     held back
the view                34                  2             6
the source              32                  0             8
```

- **D'après la vue : deux cagnottes versées à tort.** L'annulation était
  dans la source, pas encore dans la vue : le tour paraissait complet.
- **D'après la source : aucune.** Les huit tours avec une annulation
  attendent.

La vue n'est pas fausse : elle dit vrai **sur un passé récent**. Elle
convient pour afficher, pour chercher, pour compter approximativement.
Elle ne convient pas pour engager de l'argent.

## 5. La campagne

Sept mutations, dans le projecteur et la source :

```text
transactions en cours lues                   tuee
ordre par id seul                            tuee
position non avancée                         tuee
annulation ignorée                           tuee
attente d'un cran de trop                    tuee
verrou de l'outbox retiré                    tuee
retard compté par id                         tuee
7/7 tuees
```

Deux tests ont été ajoutés après un premier passage où trois mutations
survivaient : l'un fabrique deux transactions dont l'ordre des `id` et
l'ordre des transactions s'opposent (il tue « ordre par id seul » et
« retard compté par id ») ; l'autre tient le verrou de l'outbox dans une
transaction et vérifie qu'un écrivain ordonné l'attend.

Un troisième défaut est apparu en écrivant les tests : ils échouaient
**parfois**, quand un test d'un autre paquet tenait une transaction
ouverte. Le projecteur attendait cette transaction, qui n'avait rien à
voir avec lui : `xmin` vaut pour **toute la base**. Les tests attendent
désormais que la vue ait rattrapé ; la production, elle, doit le savoir
(section 8).

## 6. La grille

| Pour chaque vue | À vérifier |
|---|---|
| la position | avance dans l'ordre de visibilité (transactions, ou verrou), pas dans l'ordre des `id` |
| la position et la vue | écrites dans la même transaction |
| le retard | mesuré : événements en attente, âge du plus ancien |
| l'écran de celui qui écrit | attend sa position, ou affiche l'écriture, ou lit la source |
| les décisions | lisent la source ; jamais la vue pour ce qui engage de l'argent |
| les transactions longues | surveillées dans toute la base : elles retardent toutes les vues |

## 7. Les trois erreurs qui restent

### « Le retard est de quelques millisecondes, ça ne se voit pas »

Il est de 375 ms ici avec un projecteur qui lit toutes les 300 ms, et
**aucun** des 600 membres ne voit son paiement tout de suite. Un écran
qui se rafraîchit juste après une écriture tombe exactement dans la
fenêtre. Le retard se voit toujours par celui qui vient d'écrire.

### « Il suffit de lire les événements dont l'`id` est plus grand »

223 cotisations perdues pour toujours dans la section 2, et aucun test
ne le montrait tant qu'il n'y avait qu'un écrivain à la fois. Une
position n'a de sens que si rien ne peut plus apparaître derrière elle.

### « On n'a qu'à lire la source partout »

Alors la vue ne sert à rien, et la source porte toute la charge des
écrans : c'est souvent la bonne décision (leçon 5.5 : une requête bien
indexée suffit longtemps). Martin Fowler prévient que séparer le modèle
d'écriture et le modèle de lecture (CQRS) ajoute, pour la plupart des
systèmes, une complexité risquée. Une vue se justifie par une lecture
que la source ne sait pas servir vite.

## 8. Le lien avec la production

- **L'alerte sur le retard** : âge du plus ancien événement non appliqué
  au-delà de quelques secondes. Elle couvre un projecteur arrêté, lent,
  ou **bloqué par une transaction longue** ailleurs dans la base.
- **Les transactions longues** (un export, une migration, une session
  oubliée dans un outil SQL) retiennent `xmin` : la vue s'arrête, sans
  erreur. `pg_stat_activity` montre les transactions ouvertes depuis
  longtemps ; `idle_in_transaction_session_timeout` coupe celles qu'on a
  oubliées.
- **Reconstruire une vue** : elle se jette et se reconstruit depuis les
  événements (position remise à zéro). C'est sa grande force, à
  condition que les événements soient gardés (leçon 8.6).
- **Le réplica en lecture** a le même défaut, pour la même raison : une
  lecture sur un réplica après une écriture sur le primaire peut ne pas
  la voir.

## 9. Ce qu'il faut retenir

1. Une vue est en retard ; on le mesure.
2. Celui qui écrit attend sa position, ou voit son écriture autrement.
3. On décide sur la source.
4. Une position suit l'ordre de visibilité, pas l'ordre des `id`.
5. Une transaction longue retarde toutes les vues.

## 10. Approfondissement

### Le verrou ou les transactions ?

Le verrou de l'outbox est simple et lisible ; il coûte un commit à la
fois. Il convient tant que le volume d'écriture est faible : 337
écritures par seconde, c'est déjà des centaines de fois le pic d'un
dernier jour du mois pour l'application de tontine (environ 5 000
cotisations par heure, moins de deux par seconde). Le suivi par transaction ne coûte
rien à l'écriture, mais lie le projecteur à un mécanisme interne de
PostgreSQL, et le rend sensible aux transactions longues. Le relais de la
leçon 8.2, qui coche les lignes au lieu de garder une position, n'a
aucun des deux problèmes : il publie dans le désordre de visibilité, et
l'abonné ordonne par séquence (leçon 8.3).

### Cohérence de session

Vogels décrit aussi la cohérence **de session** : read-your-writes tant
que dure la session. Une application mobile garde la dernière position
écrite par le membre, et l'envoie avec chaque lecture ; le serveur
attend que la vue l'ait atteinte, ou lit la source. C'est `WaitFor`,
étendu à toutes les lectures de la session.

## 11. Le réflexe à installer

Devant chaque vue, demande-toi :

1. Quel est son retard, mesuré, et qui le surveille ?
2. Que voit celui qui vient d'écrire ?
3. Quelle décision est prise sur elle, et ne devrait pas l'être ?
4. Sa position peut-elle laisser un événement derrière elle ?
5. Qu'est-ce qui, ailleurs dans la base, peut l'arrêter sans erreur ?

## Sources

- Werner Vogels, [Eventually Consistent - Revisited](https://www.allthingsdistributed.com/2008/12/eventually_consistent.html) :
  « Read-your-writes consistency. This is an important model where
  process A, after it has updated a data item, always accesses the
  updated value and will never see an older value » ; et l'éventuelle :
  « if no new updates are made to the object, eventually all accesses
  will return the last updated value. »
- Martin Fowler, [CQRS](https://martinfowler.com/bliki/CQRS.html) :
  « you can use a different model to update information than the model
  you use to read information » ; « beware that for most systems CQRS

  IDs less than xmin are either committed and visible, or rolled back
  and dead. »
