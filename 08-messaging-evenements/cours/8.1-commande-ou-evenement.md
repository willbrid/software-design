# Leçon 8.1 — Commande ou événement : découpler par les messages

## L'essentiel en deux minutes

**Le problème, en une phrase.** Quand une cotisation est enregistrée,
quatre parties de l'application doivent l'apprendre : le reçu par SMS,
le tableau du tour, le score de prêt, la trésorière. Si les paiements les
appellent une par une, la panne de la moins importante (le SMS) fait
refuser la cotisation elle-même.

**Deux images.**

- **L'annonce au marché** : le crieur annonce « la cotisation d'Awa est
  arrivée ». Il ne sait pas qui écoute, et n'attend la réponse de
  personne. C'est un **événement** : un fait, au passé.
- **La commande au guichet** : la trésorière dit à la caissière « verse
  la cagnotte à Awa ». Une seule personne doit le faire, peut refuser, et
  la trésorière attend la réponse. C'est une **commande** : un ordre, à
  l'impératif.

**Le code, en quelques lignes.** Les paiements enregistrent, annoncent,
et n'attendent personne :

```go
// Record records c and publishes ContributionRecorded; it does not wait
// for anyone.
func (p *Payments) Record(ctx context.Context, c ledger.Contribution) error {
    p.Ledger.Append(c)
    p.Bus.Publish(ContributionRecorded{Contribution: c, At: time.Now()})
    return nil
}
```

**Les règles à retenir.**

1. **Un événement dit ce qui s'est passé**, au passé, dans la langue de
   celui qui le publie : `ContributionRecorded`, pas `SendReceipt`.
2. **Une commande dit ce qu'il faut faire**, à une seule partie, qui
   répond : `PayOut`, et l'expéditeur apprend si c'est fait.
3. **Ce qui peut attendre passe par un événement** : la panne d'un
   abonné ne touche que lui.
4. **Ce dont on a besoin de la réponse reste une commande** : une
   annonce que personne n'écoute ne fait pas d'erreur.
5. **Un abonné en retard se surveille** : sa file et son retard sont les
   métriques qui remplacent l'erreur qu'on ne voit plus.

La suite le mesure avec un bus en mémoire. La leçon 8.2 rend l'annonce
sûre quand le programme s'arrête entre l'enregistrement et la
publication.

---

La leçon 7.6 a fini sur une promesse : le service des paiements serait
tenu à jour par les **événements** du registre. Avant de construire ces
événements sur une base de données, il faut savoir ce qu'est un
événement, ce qu'il n'est pas, et ce qu'il coûte. Le problème de cette
leçon :

> **Quand une cotisation est enregistrée, comment prévenir les parties
> qui doivent le savoir, sans que leur panne bloque la cotisation ?**

Le module de la leçon est `l81`. Il n'a besoin que de la bibliothèque
standard. Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Les appels, un par un

Les paiements connaissent les quatre parties, et les appellent dans
l'ordre :

```go
// Record records c, then tells each part in turn; the first failure is
// the member's answer, although c is already in the ledger.
func (p *Payments) Record(ctx context.Context, c ledger.Contribution) error {
    p.Ledger.Append(c)
    if err := p.Receipts.Notify(ctx, c); err != nil {
        return fmt.Errorf("send receipt: %w", err)
    }
    if err := p.Rounds.Notify(ctx, c); err != nil {
        return fmt.Errorf("advance round: %w", err)
    }
    if err := p.Scores.Notify(ctx, c); err != nil {
        return fmt.Errorf("update score: %w", err)
    }
    if err := p.Treasury.Notify(ctx, c); err != nil {
        return fmt.Errorf("notify treasurer: %w", err)
    }
    return nil
}
```

Ce code est celui qu'on écrit naturellement, et il a trois défauts qui
ne se voient pas à la lecture :

- **la cotisation dépend du SMS** : si le prestataire SMS ne répond pas,
  le membre lit une erreur, alors que son argent est arrivé ;
- **l'enregistrement est déjà fait** quand l'erreur remonte : le membre
  qui réessaie l'enregistre une seconde fois ;
- **ajouter une cinquième partie** (l'audit, par exemple) oblige à
  modifier les paiements, qui n'ont rien à voir avec l'audit.

## 2. L'annonce

Avec un **événement**, les paiements enregistrent puis annoncent un fait,
et c'est tout. Le bus de la leçon (`bus`) donne à chaque abonné **sa
propre file** et **son propre travailleur**, qui réessaie tant que
l'abonné échoue :

```go
func (b *Bus) run(s *subscriber) {
    defer b.wg.Done()
    for {
        s.mu.Lock()
        for len(s.queue) == 0 && !s.closed {
            s.cond.Wait()
        }
        if len(s.queue) == 0 {
            s.mu.Unlock()
            return
        }
        q := s.queue[0]
        s.mu.Unlock()
        for s.h(b.ctx, q.m) != nil {
            s.mu.Lock()
            s.stats.Failures++
            s.mu.Unlock()
            select {
            case <-b.ctx.Done():
                return
            case <-time.After(b.Retry):
            }
        }
        s.mu.Lock()
        s.queue = s.queue[1:]
        s.stats.Delivered++
        s.stats.MaxDelay = max(s.stats.MaxDelay, time.Since(q.at))
        s.cond.Broadcast()
        s.mu.Unlock()
    }
}
```

Qui écoute ? Les paiements ne le savent pas. Un seul endroit le sait, le
câblage de l'application :

```go
// Subscribe has each notifier receive ContributionRecorded under its own
// name.
func Subscribe(b *bus.Bus, notifiers map[string]paysync.Notifier) {
    for name, n := range notifiers {
        b.Subscribe("ContributionRecorded", name, func(ctx context.Context, m bus.Message) error {
            return n.Notify(ctx, m.(payevents.ContributionRecorded).Contribution)
        })
    }
}
```

Les dépendances sont **inversées** : avant, les paiements dépendaient des
quatre parties ; maintenant, chaque partie dépend de l'événement des
paiements, et les paiements ne dépendent de personne.

## 3. Mesure : le SMS tombe en panne

`cmd/outage` enregistre 1 000 cotisations, une toutes les 4 ms. Le SMS
répond en 2 ms, les trois autres parties en 0,3 ms. Le SMS est en panne
pendant 600 ms (de la cotisation 300 à la 450), et le score échoue une
fois pour 2 % des cotisations. Un membre qui lit une erreur réessaie,
trois fois en tout :

```text
1000 contributions, one every 4ms; receipts down from contribution 300 to 450; scores fail once for 2 %

                   refused  ledger rows  receipts  double receipts  scores  member p50  member p99
calls one by one       149         1317       851               17     851      5.98ms     10.83ms
events                   0         1000      1000                0    1000        10µs       110µs

events, receipts  delivered 1000, failed attempts  46, backlog up to 153, late up to 609ms
events, rounds    delivered 1000, failed attempts   0, backlog up to   1, late up to 2ms
events, scores    delivered 1000, failed attempts  20, backlog up to   4, late up to 14ms
events, treasury  delivered 1000, failed attempts   0, backlog up to   1, late up to 2ms
```

Avec les appels un par un :

- **149 cotisations refusées** : tous les membres qui ont payé pendant
  la panne du SMS lisent « échec », alors que leur argent est arrivé ;
- **1 317 lignes au registre pour 1 000 cotisations** : chaque essai a
  enregistré avant d'échouer ;
- **17 membres reçoivent deux reçus** : le SMS est parti, puis le score
  a échoué, et le membre a réessayé ;
- **le score n'a appris que 851 cotisations** : les 149 refusées sont au
  registre, mais aucune autre partie ne le sait.

Avec les événements :

- **aucune cotisation refusée**, 1 000 lignes, 1 000 reçus, aucun double ;
- **le membre attend 10 µs** au lieu de 6 ms : il n'attend plus personne ;
- **le prix** : des reçus arrivés **jusqu'à 609 ms en retard**, et une
  file du SMS qui a monté à **153 événements** pendant la panne, puis
  s'est vidée.

C'est l'échange que fait un événement : la cotisation ne dépend plus du
SMS, et le reçu arrive **plus tard**. Le monde ne devient pas cohérent
d'un coup, il le devient avec un retard qu'on mesure : la leçon 8.4 en
fait son sujet.

## 4. L'erreur inverse : annoncer ce qui devait être commandé

Tout ne doit pas devenir un événement. Quand un tour se ferme, la
cagnotte doit être versée. Deux façons de l'écrire :

```go
// CloseAnnouncing closes the round and announces it: someone, somewhere,
// is expected to pay.
func CloseAnnouncing(ctx context.Context, b *bus.Bus, round, beneficiary string, pot int64) error {
    b.Publish(RoundClosed{Round: round, Beneficiary: beneficiary, Pot: pot})
    return nil
}

// CloseAsking closes the round and orders the payout: the answer says
// whether it happened.
func CloseAsking(ctx context.Context, b *bus.Bus, round, beneficiary string, pot int64) error {
    return b.Send(ctx, PayOut{Round: round, Beneficiary: beneficiary, Pot: pot})
}
```

`cmd/silence` ferme 40 tours. Dans la deuxième ligne de chaque paire,
les paiements écoutent sous un mauvais nom, après un changement mal relu
(`RoundClose` au lieu de `RoundClosed`, `Payout` au lieu de `PayOut`) :

```text
40 rounds closed

the tontines                       the payments listen to      paid  errors they see
announce RoundClosed (event)       RoundClosed                   40                0
announce RoundClosed (event)       RoundClose                     0                0
order PayOut (command)             PayOut                        40                0
order PayOut (command)             Payout                         0               40
```

**Avec l'événement, 40 cagnottes ne sont pas versées, et personne ne
voit d'erreur.** C'est normal : un événement que personne n'écoute n'est
pas une erreur, c'est même ce qui le rend découplé. Avec la commande, les
40 fermetures échouent, et les tontines le savent tout de suite.

La règle : **si l'expéditeur a besoin que la chose soit faite, c'est une
commande**. Verser une cagnotte, débiter un compte, réserver une place :
une seule partie en est chargée, elle peut refuser, et son refus doit
revenir. Envoyer un reçu, mettre à jour un score, prévenir la
trésorière : les paiements n'en ont pas besoin pour continuer, ce sont
des réactions à un événement.

## 5. Nommer : au passé, dans la langue de l'émetteur

Un événement porte un nom **au passé**, dans le langage du contexte qui
le publie (leçon 7.2) :

| Nom | Pourquoi |
|---|---|
| `ContributionRecorded` | un fait des paiements ; chacun en fait ce qu'il veut |
| `SendReceiptSMS` | une commande déguisée : les paiements décident à la place des reçus, et dépendent du SMS |
| `UpdateLoanScore` | idem : le jour où les prêts changent de règle, les paiements changent |
| `ContributionEvent` | trop vague : enregistrée ? annulée ? remboursée ? |
| `PayOut` | une commande, et assumée comme telle : un ordre, une réponse |

Un événement nommé comme un ordre (`SendReceiptSMS`) garde tout le
couplage de l'appel direct, sans la réponse.

## 6. La campagne

Dix mutations, dans le bus, les paiements et les tontines :

```text
événement envoyé à tous                      tuee
seul le premier abonné                       tuee
une seule tentative                          tuee
dernier d'abord                              tuee
commande sans destinataire acceptée          tuee
réponse de la commande perdue                tuee
deux destinataires acceptés                  tuee
pas d'annonce                                tuee
annonce en double                            tuee
commande publiée comme un événement          tuee
10/10 tuees
```

Toutes sont tuées. La plus instructive est la dernière : la commande
publiée comme un événement compile, et ne fait échouer que le test qui
demande une erreur quand personne ne traite l'ordre. Sans ce test, la
section 4 serait passée inaperçue.

## 7. La grille

| Pour chaque message | À vérifier |
|---|---|
| l'expéditeur a-t-il besoin du résultat ? | oui : commande, une partie, une réponse ; non : événement |
| le nom | au passé pour un événement, à l'impératif pour une commande, dans la langue de l'émetteur |
| qui écoute | écrit à un seul endroit : le câblage |
| un abonné en panne | ne touche que lui : sa propre file, ses tentatives |
| le retard | mesuré par abonné : file, retard du plus ancien |
| l'annonce perdue | la publication suit-elle l'enregistrement, même si le programme s'arrête entre les deux ? (leçon 8.2) |
| le message reçu deux fois | l'abonné le supporte-t-il ? (leçon 8.3) |

## 8. Les trois erreurs qui restent

### « Avec des événements, tout est découplé »

Martin Fowler le dit dans *What do you mean by "Event-Driven"?* : un flux
qui traverse plusieurs événements est difficile à voir, car il n'est
écrit dans aucun programme ; souvent, on ne le comprend qu'en observant
le système en production. La section 4 en donne le pire cas : 40
cagnottes non versées, et aucune erreur. Le couplage n'a pas disparu, il
est devenu invisible.

### « Un événement, c'est un appel qui ne bloque pas »

Non : un appel attend une réponse, un événement n'en attend aucune. Si
on publie un événement puis qu'on attend qu'un autre événement revienne
pour continuer, on a écrit un appel lent, sans délai et sans erreur.
C'est une commande qu'il fallait.

### « Le bus réessaie, donc rien ne se perd »

Le bus de cette leçon est en mémoire : si le programme s'arrête, les 153
reçus en attente sont perdus, et l'événement publié juste après
l'enregistrement peut ne jamais partir. La leçon 8.2 met l'événement dans
la même transaction que l'enregistrement.

## 9. Le lien avec la production

- **Le tableau de bord change** : avec des appels, une panne se voit dans
  le taux d'erreur ; avec des événements, elle se voit dans la **file** et
  le **retard** de chaque abonné. Une alerte sur « reçu en retard de plus
  de 5 minutes » remplace l'alerte sur les erreurs du SMS.
- **Les tentatives d'un abonné** espacent leurs essais (la leçon 9.2 les
  règle) : un abonné qui réessaie toutes les 10 ms pendant une panne d'une
  heure fait 360 000 appels pour rien.
- **Le catalogue des événements** (nom, émetteur, contenu, abonnés) est
  la documentation du flux que le code ne montre plus.
- **Un courtier** (RabbitMQ, Kafka, NATS, ou une table PostgreSQL) joue
  le rôle du bus entre plusieurs programmes ; les règles de cette leçon ne
  changent pas.

## 10. Ce qu'il faut retenir

1. Un événement est un fait au passé ; une commande, un ordre à une
   partie, qui répond.
2. Ce qui peut attendre devient une réaction à un événement : la panne de
   l'abonné ne touche que lui.
3. Ce dont l'expéditeur a besoin reste une commande : une annonce sans
   auditeur ne fait pas d'erreur.
4. Le couplage devient invisible : le câblage et le catalogue le rendent
   lisible.
5. Le retard de chaque abonné se mesure.

## 11. Approfondissement

### Ce que porte l'événement

`ContributionRecorded` porte la cotisation entière. Martin Fowler
distingue la **notification** (« la cotisation c0042 est enregistrée »,
l'abonné vient chercher le reste) et le **transfert d'état** (l'événement
porte tout ce qu'il faut). La notification garde l'événement petit, mais
chaque abonné rappelle l'émetteur, qui redevient une dépendance ; le
transfert d'état rend l'abonné autonome, au prix d'un contenu qui devient
un contrat (leçon 6.4), à faire évoluer avec soin (leçon 8.6).

### Commandes par messages

Une commande peut aussi passer par une file : l'expéditeur dépose
`PayOut`, et reçoit plus tard `PayoutCompleted` ou `PayoutRefused`. Elle
reste une commande : un seul destinataire, et une réponse attendue, qui
arrive par un événement. C'est la brique des sagas (leçon 8.5).

## 12. Le réflexe à installer

Avant d'écrire un message, demande-toi :

1. L'expéditeur a-t-il besoin du résultat pour continuer ?
2. Le nom dit-il un fait passé, ou un ordre ?
3. Si personne n'écoute, qui s'en aperçoit, et quand ?
4. Si un abonné tombe en panne une heure, que voit-on, et où ?
5. Si le programme s'arrête juste après l'enregistrement, l'événement
   part-il quand même ?
