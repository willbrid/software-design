# Leçon 8.6 — Faire évoluer les événements, et les rejouer

## L'essentiel en deux minutes

**Le problème, en une phrase.** Un événement écrit en janvier sera relu
en décembre, par un code qui a changé entre-temps : si son format
évolue sans précaution, les vues reconstruites depuis le journal se
trompent, sans erreur ; et si on rejoue le journal sans précaution, on
renvoie aux membres des SMS d'il y a six mois.

**Deux images.**

- **Les registres de l'état civil** : un acte de 1960 ne se réécrit pas
  au format de 2026. Celui qui le lit aujourd'hui sait lire l'ancien
  format, ou un traducteur le lui transcrit. On ne corrige pas le
  registre, on apprend à le lire.
- **La rediffusion d'un match** : on la regarde pour revoir les buts, pas
  pour que l'arbitre siffle une seconde fois. Rejouer les événements
  reconstruit un état ; ça ne doit pas refaire ce qui est sorti vers le
  monde.

**Le code, en quelques lignes.** Un **traducteur** (*upcaster*) met
chaque ancien événement au format courant avant qu'on le lise ; les
lecteurs ne connaissent qu'une version :

```go
// Upcast turns an event of any known version into the current one,
// before anyone reads it: the readers know only v2.
func Upcast(e store.Event) (V2, error) {
    switch e.Version {
    case 1:
        var v V11
        if err := json.Unmarshal(e.Body, &v); err != nil {
            return V2{}, fmt.Errorf("event %d: %w", e.Seq, err)
        }
        return V2{Contribution: v.Contribution, Round: v.Round, AmountFCFA: v.Amount, Channel: v.Channel}, nil
    case 2:
        return TolerantV2(e)
    }
    return V2{}, fmt.Errorf("event %d: unknown version %d", e.Seq, e.Version)
}
```

**Les règles à retenir.**

1. **Un événement écrit ne change plus** : son format est un contrat
   avec tous ceux qui le liront, y compris le code de l'an prochain.
2. **Ajouter un champ** se fait dans la même version ; les lecteurs
   ignorent ce qu'ils ne connaissent pas (lecteur tolérant).
3. **Renommer, changer un type ou un sens** fait une nouvelle version,
   avec un traducteur de l'ancienne vers la nouvelle.
4. **Un rejeu reconstruit, il n'agit pas** : les effets vers l'extérieur
   (SMS, paiements) sont coupés pendant le rejeu.
5. **Garder les événements comme source** (event sourcing) se justifie
   par un besoin d'historique ; il se paie en versions et en
   instantanés.

La suite le mesure sur un journal de cotisations d'un an.

---

Les leçons 8.2 à 8.5 ont fait circuler les événements, puis les ont
oubliés une fois traités. Mais une vue se reconstruit depuis eux (leçon
8.4), un abonné nouveau veut l'historique, et certains contextes gardent
**tous** leurs événements comme source de vérité. Le journal devient
alors une archive, relue par du code qui n'existait pas quand il a été
écrit. Le problème de cette leçon :

> **Comment faire évoluer le format d'un événement déjà écrit des
> milliers de fois, et rejouer le journal sans dommage ?**

Le module de la leçon est `l86`. Il n'a besoin que de la bibliothèque
standard : le journal est en mémoire. Tout ce qui suit est mesuré sur un
module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. Trois formats en un an

`ContributionRecorded` a changé deux fois :

```go
// V1 is the first format.
type V1 struct {
    Contribution string `json:"contribution"`
    Round        string `json:"round"`
    Amount       int64  `json:"amount"`
}
```

```go
// V11 only added Channel: the same version, a reader of V1 may ignore it.
type V11 struct {
    V1
    Channel string `json:"channel,omitempty"`
}
```

```go
// V2 renamed the amount, to say its unit.
type V2 struct {
    Contribution string `json:"contribution"`
    Round        string `json:"round"`
    AmountFCFA   int64  `json:"amount_fcfa"`
    Channel      string `json:"channel,omitempty"`
}
```

- en v1.1, un champ **ajouté** (`channel`) : un ancien lecteur peut
  l'ignorer, la version ne change pas ;
- en v2, un champ **renommé** (`amount` devient `amount_fcfa`, pour dire
  l'unité) : un ancien lecteur ne trouve plus le montant. C'est une
  rupture, la version passe à 2.

Le journal garde tout : 5 000 événements v1, 3 000 v1.1 et 2 000 v2.

## 2. Mesure : reconstruire les totaux des tours

`cmd/evolve` reconstruit le total de chaque tour depuis le journal, avec
quatre lecteurs :

```text
10,000 contributions: 5,000 v1, 3,000 v1.1, 2,000 v2; owed to the rounds: 100000000 FCFA

reader                           unreadable   rounds total   off by FCFA
v1, strict                             5000       50000000     -50000000
v1, tolerant                              0       80000000     -20000000
v2, tolerant                              0       20000000     -80000000
upcast to v2, then read                   0      100000000             0
```

- **Le lecteur strict de v1** (`DisallowUnknownFields`) refuse les 3 000
  événements v1.1 à cause d'un champ ajouté, et les 2 000 v2 : la moitié
  du journal est illisible. Il a au moins le mérite de le dire.
- **Le lecteur tolérant de v1** lit les v1.1 sans peine, mais lit les v2
  avec un montant de **0**, sans erreur : il manque **20 millions de
  FCFA** aux tours. C'est le pire résultat, parce qu'il est silencieux.
- **Le lecteur tolérant de v2** fait la même erreur dans l'autre sens :
  il lit les 8 000 anciens avec un montant de 0.
- **Le traducteur, puis la lecture en v2** : tout juste.

Deux leçons en une. **Être tolérant** (Martin Fowler, *TolerantReader*,
qui reprend la loi de Postel : « be conservative in what you do, be
liberal in what you accept from others ») rend sans danger les champs
ajoutés. Mais la tolérance **cache** un champ renommé : il faut une
nouvelle version, et un traducteur qui la connaît.

## 3. Rejouer sans agir

On découvre un défaut dans la table des reçus ; on la jette, et on la
reconstruit depuis le journal. `cmd/replay` rejoue 100 000 cotisations :

```text
rebuilding the receipts table from 100,000 events

handler                    receipts   SMS sent      time
sends whatever it is told    100000     100000      97ms
knows it is replaying        100000          0      90ms
```

**100 000 SMS envoyés** par le gestionnaire qui ne sait pas qu'il rejoue :
des membres reçoivent, un mardi soir, le reçu de leurs cotisations de
mars. Le second gestionnaire reconstruit la même table, sans un SMS :

```go
// Handle records the receipt; it sends the SMS only for a live event,
// never while the table is being rebuilt from the log.
func (r *Receipts) Handle(e store.Event, replaying bool) error {
    v, err := contract.Upcast(e)
    if err != nil {
        return err
    }
    if r.Have == nil {
        r.Have = map[string]bool{}
    }
    r.Have[v.Contribution] = true
    if !replaying {
        r.SMS.Send(v.Contribution, "contribution received")
    }
    return nil
}
```

Martin Fowler le décrit dans *Event Sourcing* : les systèmes externes ne
font pas la différence entre un vrai traitement et un rejeu ; il faut
les envelopper dans une passerelle, qu'on peut couper pendant le rejeu,
de façon invisible pour la logique du domaine.

## 4. Les événements comme source : l'event sourcing

Le portefeuille d'épargne d'un membre ne garde pas son solde : il garde
ses dépôts et ses retraits, et **calcule** le solde en les rejouant. C'est
l'*event sourcing* :

```go
// Load rebuilds the wallet of member from snap (zero: from the start),
// and returns how many events it read.
func Load(s *store.Store, member string, snap Wallet) (Wallet, int, error) {
    w := snap
    w.Member = member
    events, read := s.Stream(member, snap.Seq)
    for _, e := range events {
        if err := w.apply(e); err != nil {
            return Wallet{}, read, err
        }
    }
    return w, read, nil
}
```

On y gagne ce qu'une table de soldes ne donne pas : **l'historique
complet** (pourquoi ce solde ?), **l'état à n'importe quelle date** (le
solde au 31 décembre), et la possibilité de **reconstruire** toute vue
depuis la source.

On le paie. Le solde d'un membre ancien demande de relire tous ses
événements. `cmd/snapshot` charge le portefeuille d'un membre qui a
20 000 événements, dans un journal de 200 000 :

```text
200,000 events, 20,000 of them for awa; a snapshot every 1,000 of awa's events

loading awa                   events read      balance      time
from the start                     200000     20000000  10.517ms
from a snapshot 1,000 back          10009     20000000     517µs
```

Depuis le début, 200 000 événements lus, 10,5 ms ; depuis un
**instantané** (le solde enregistré tous les 1 000 événements du membre),
20 fois moins. L'instantané est une vue comme une autre : on peut le
jeter et le recalculer, mais il faut le tenir.

Et on paie surtout **les versions** : chaque format d'événement écrit
depuis le premier jour doit rester lisible pour toujours, par le
traducteur. Greg Young, qui a popularisé l'event sourcing, a consacré un
livre entier à ce seul sujet (*Versioning in an Event Sourced System*).

## 5. La campagne

Neuf mutations, dans les lecteurs, les reçus, le portefeuille et le
journal :

```text
v1 lu comme v2                               tuee
version inconnue acceptée                    tuee
lecteur strict devenu tolérant               tuee
canal perdu                                  tuee
tous les types comptés                       tuee
SMS envoyés pendant le rejeu                 tuee
découvert autorisé                           tuee
position non suivie                          tuee
instantané ignoré                            tuee
9/9 tuees
```

Toutes sont tuées. Le test qui tue « SMS envoyés pendant le rejeu » est
aussi le plus court : il rejoue un événement et compte les SMS. Un test
de rejeu sans effet vers l'extérieur vaut la peine d'être écrit **avant**
le premier rejeu en production.

## 6. La grille

| Pour chaque événement et chaque rejeu | À vérifier |
|---|---|
| le format | versionné dans l'événement lui-même (`Version`) |
| un champ ajouté | même version ; les lecteurs ignorent ce qu'ils ne connaissent pas |
| un champ renommé, un type ou un sens changé | nouvelle version, et un traducteur de l'ancienne |
| les lecteurs | ne connaissent qu'une version ; le traducteur passe avant eux |
| le traducteur | testé sur un échantillon réel de chaque ancienne version |
| le rejeu | les effets externes (SMS, paiements, courriels) coupés, par une passerelle |
| l'event sourcing | justifié par un besoin d'historique ; instantanés pour les longs flux |

## 7. Les trois erreurs qui restent

### « On renomme le champ, et on migre les anciens événements »

Réécrire le journal, c'est perdre la propriété qui le rend précieux :
ce qui a été écrit ne change plus. Et c'est risqué : une migration de
millions d'événements, sans retour en arrière, sur la source de vérité.
Le traducteur laisse le journal intact, et se teste sur un échantillon.

### « Le lecteur tolérant suffit »

Il suffit pour les ajouts. Pour un renommage, il lit 0 sans rien dire :
20 millions de FCFA de moins dans la section 2. La tolérance protège de
la casse, pas du sens.

### « L'event sourcing, c'est l'architecture des systèmes sérieux »

C'est un choix coûteux : chaque format vit pour toujours, les vues se
construisent toutes par projection (leçon 8.4), et les requêtes simples
(« quels membres ont un solde négatif ? ») passent par une vue. Il se
justifie quand l'historique **est** le métier : un portefeuille, un
registre de cotisations audité. Pour le profil d'un membre, une table
suffit.

## 8. Le lien avec la production

- **Le registre des formats** : chaque type d'événement, ses versions,
  leurs exemples réels. Les tests du traducteur s'en nourrissent.
- **L'ordre des déploiements** pour une nouvelle version : d'abord les
  lecteurs (ils savent lire v1 et v2), ensuite les écrivains (ils écrivent
  v2). Dans l'autre ordre, des v2 arrivent chez des lecteurs qui ne les
  connaissent pas (leçon 6.5, appliquée aux événements).
- **Le rejeu** est une opération planifiée : passerelles coupées, vue
  reconstruite à côté de l'ancienne, bascule une fois rattrapée.
- **La durée de rétention** du courtier (Kafka garde 7 jours par défaut)
  n'est pas un journal : si l'on veut rejouer un an, les événements
  doivent être gardés ailleurs, dans une table ou un stockage d'archives.

## 9. Ce qu'il faut retenir

1. Un événement écrit est un contrat avec le futur.
2. Ajouter : même version, lecteurs tolérants.
3. Rompre : nouvelle version, traducteur.
4. Rejouer reconstruit ; les effets externes sont coupés.
5. L'event sourcing se paie en versions et en instantanés.

## 10. Approfondissement

### Le sens qui change sans que le format change

Le pire changement ne touche aucun champ : `amount` reste un entier,
mais, à partir d'une date, il compte des centimes au lieu de francs
(leçon 6.4). Aucun lecteur ne casse, et tous se trompent. Un changement
de sens est une nouvelle version, comme un renommage, même si la
structure est identique.

### Rejouer pour une nouvelle vue

Un abonné nouveau (un rapport annuel, par exemple) peut lire tout le
journal pour construire sa vue, puis suivre les événements nouveaux. Il
démarre avec une position à zéro, et la même règle que les autres : ses
effets externes ne partent que pour les événements arrivés après son
démarrage.

## 11. Le réflexe à installer

Avant de changer un événement, demande-toi :

1. Un lecteur de l'ancienne version, tolérant, lira-t-il juste, ou lira-t-il
   0 ?
2. Est-ce un ajout, ou une rupture qui demande une version ?
3. Qui traduit les anciens, et sur quel échantillon est-ce testé ?
4. Dans quel ordre déployer lecteurs et écrivains ?
5. Si l'on rejoue demain, qu'est-ce qui sortira vers le monde ?
