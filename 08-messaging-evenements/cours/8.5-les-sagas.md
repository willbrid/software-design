# Leçon 8.5 — Les sagas : une action en plusieurs étapes, qui peut échouer au milieu

## L'essentiel en deux minutes

**Le problème, en une phrase.** Accorder un prêt touche trois contextes
(les tontines bloquent une garantie, l'opérateur envoie l'argent, les
prêts enregistrent la dette), et aucune transaction ne les couvre tous :
si l'une des étapes échoue, ou si le programme s'arrête entre deux, il
faut savoir quoi défaire et quoi terminer.

**Deux images.**

- **Le voyage réservé en trois fois** : l'hôtel, puis le vol, puis la
  voiture. Si le vol est complet, on annule l'hôtel. L'annulation ne
  remet pas le monde dans l'état d'avant (l'hôtel garde peut-être des
  frais) : elle **compense**.
- **Le point de non-retour** : une fois l'argent parti chez le membre,
  on ne le rappelle pas. Après ce point, on ne défait plus : on termine,
  quitte à réessayer longtemps.

**Le code, en quelques lignes.** Après un délai dépassé, on ne conclut
pas : on demande à l'opérateur ce qui s'est passé.

```go
        case errors.Is(err, parts.ErrTimeout) && o.CheckTimeouts:
            if sent, err := o.Parts.Operator.Status(ctx, st.Loan.ID); err == nil && sent {
                return Sent
            }
```

**Les règles à retenir.**

1. **Une saga est une suite d'étapes locales**, chacune dans son
   contexte, avec son état enregistré après chaque étape : un programme
   arrêté reprend où il en était.
2. **Chaque étape avant le point de non-retour a sa compensation** ;
   après, on ne compense plus, on termine.
3. **Chaque étape est idempotente** (une clé par prêt) : la refaire après
   un arrêt ne fait rien de plus.
4. **Un délai dépassé n'est pas un échec** : c'est une question, qu'on
   pose à celui qui sait.
5. **Une saga qui ne finit pas se voit** : une alerte sur les sagas
   bloquées dans une étape.

La suite le mesure sur 1 000 prêts.

---

Les leçons 8.1 à 8.4 ont fait circuler des **faits** entre les
contextes. Certaines actions, elles, traversent plusieurs contextes **et
doivent aboutir ensemble** : un prêt accordé sans garantie, ou une
garantie bloquée pour un prêt jamais versé, sont des erreurs que les
membres paient. Le problème de cette leçon :

> **Comment mener une action qui traverse trois contextes, sans
> transaction commune, sans perdre d'argent quand une étape échoue ou
> que le programme s'arrête ?**

Le module de la leçon est `l85`. Il n'a besoin que de la bibliothèque
standard : les trois contextes sont simulés en mémoire, et le magasin
des sagas survit aux arrêts, comme le ferait une table. Tout ce qui suit
est mesuré sur un module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. Trois contextes, trois étapes

Le prêt de 50 000 FCFA d'un membre demande :

1. **les tontines** : bloquer sa cagnotte future comme garantie ;
2. **l'opérateur Mobile Money** : envoyer l'argent ;
3. **les prêts** : enregistrer le prêt comme actif (le membre le doit).

L'opérateur est le maillon fragile. Il refuse 5 % des demandes (pas assez
de liquidités), et ne répond pas à temps pour 5 % : pour 3 %, il a
**quand même** envoyé l'argent ; pour 2 %, non. On ne sait pas lequel des
deux sans lui demander :

```go
// Operator sends money. For each loan it answers, on the first attempt:
// refused 5 %; a timeout after sending 3 %; a timeout before sending 2 %;
// sent otherwise. A request carries a key: the same key is never sent
// twice (lesson 6.3).
type Operator struct {
    mu    sync.Mutex
    byKey map[string]bool // key -> sent
    sends map[string]int  // loan -> money sent
    tries map[string]int  // loan -> attempts
}
```

La version écrite d'abord appelle les trois, l'un après l'autre :

```go
// Disburse holds the guarantee, sends the money, and activates the loan.
// Each attempt sends under a new key; a failure leaves what is done as
// it is.
func Disburse(ctx context.Context, p parts.Parts, loan parts.Loan, crash func(loan string, step int) bool) error {
    p.Tontines.Reserve(loan.ID)
    if crash(loan.ID, 1) {
        return parts.ErrCrash
    }
    key := fmt.Sprintf("%s-%d", loan.ID, attempt.Add(1))
    if err := p.Operator.Send(ctx, key, loan); err != nil {
        return fmt.Errorf("send: %w", err)
    }
    if crash(loan.ID, 2) {
        return parts.ErrCrash
    }
    p.Loans.Activate(loan.ID)
    return nil
}
```

## 2. La saga

Une **saga** (Hector Garcia-Molina et Kenneth Salem, 1987) est une suite
de transactions locales, chacune dans son contexte, dont chacune a une
**transaction de compensation**. Leur article le dit : la compensation
défait l'action « d'un point de vue sémantique », sans forcément remettre
la base dans l'état d'avant.

L'**orchestrateur** tient l'état de chaque saga, et l'enregistre après
chaque étape :

```go
// The steps. Sent is the pivot: once the money is out, the saga can only
// go forward.
const (
    Started      Step = "started"
    Reserved     Step = "guarantee reserved"
    Sent         Step = "money sent"
    Active       Step = "loan active"
    Compensating Step = "releasing guarantee"
    Compensated  Step = "refused, guarantee released"
)
```

```go
// Run takes the saga of loan from where it stands to its end.
func (o *Orchestrator) Run(ctx context.Context, loan parts.Loan) error {
    st := o.Store.Begin(loan)
    for {
        switch st.Step {
        case Started:
            o.Parts.Tontines.Reserve(loan.ID)
            st.Step = Reserved
            o.Store.Save(st)
            if o.Crash(loan.ID, 1) {
                return parts.ErrCrash
            }
        case Reserved:
            st.Step = o.send(ctx, &st)
            o.Store.Save(st)
            if o.Crash(loan.ID, 2) {
                return parts.ErrCrash
            }
        case Sent:
            o.Parts.Loans.Activate(loan.ID)
            st.Step = Active
            o.Store.Save(st)
        case Compensating:
            o.Parts.Tontines.Release(loan.ID)
            st.Step = Compensated
            o.Store.Save(st)
        case Active:
            return nil
        case Compensated:
            return ErrNotDisbursed
        }
    }
}
```

L'envoi est le **point de non-retour** (Microsoft l'appelle la
*transaction pivot*) : avant lui, une erreur fait compenser (libérer la
garantie) ; après lui, il n'y a plus que la suite (activer le prêt).
L'envoi lui-même utilise **l'identifiant du prêt comme clé** : l'opérateur
n'envoie jamais deux fois sous la même clé (leçon 6.3).

```go
// send tries to send the money under the loan's key, and returns the
// next step.
func (o *Orchestrator) send(ctx context.Context, st *State) Step {
    for st.Sends < o.MaxSends {
        st.Sends++
        err := o.Parts.Operator.Send(ctx, st.Loan.ID, st.Loan)
        switch {
        case err == nil:
            return Sent
        case errors.Is(err, parts.ErrTimeout) && o.CheckTimeouts:
            if sent, err := o.Parts.Operator.Status(ctx, st.Loan.ID); err == nil && sent {
                return Sent
            }
            // not sent: the same key may be tried again
        default:
            return Compensating
        }
    }
    return Compensating
}
```

## 3. Mesure : 1 000 prêts

`cmd/loans` accorde 1 000 prêts de trois façons. En plus des réponses de
l'opérateur, le programme s'arrête entre deux étapes pour 4 % des prêts.
Un membre dont la demande échoue (autrement que par un refus) réessaie
deux fois :

```text
                                    active  refused sent twice sent, no loan  unguaranteed  stuck
three calls                            901        0         40            11             0     59
saga, a timeout is a failure           903       68          0            29            29      0
saga, a timeout is a question          951       49          0             0             0      0
```

Avec **trois appels** :

- **40 prêts versés deux fois** : l'opérateur avait envoyé l'argent
  malgré le délai dépassé, le membre a réessayé, le second essai est
  parti sous une nouvelle clé ;
- **59 garanties bloquées** pour des prêts jamais versés : un refus, ou
  un arrêt, laisse la garantie où elle est. Rien ne la libère ;
- **11 versements sans prêt** : le programme s'est arrêté entre l'envoi
  et l'activation. L'argent est chez le membre, et personne ne le lui
  réclamera.

Avec **une saga qui prend le délai pour un échec** :

- plus de doublon (une seule clé par prêt), plus de garantie bloquée
  (chaque échec compense, et les sagas arrêtées reprennent) ;
- mais **29 versements sans prêt et sans garantie** : l'opérateur avait
  envoyé l'argent, la saga a cru à un échec, a libéré la garantie et
  refusé le prêt. Elle a compensé **après** le point de non-retour.

Avec **une saga qui pose la question** : 951 prêts actifs, 49 refusés
proprement, **rien d'autre**. Après un délai, elle demande à l'opérateur
si l'argent est parti ; s'il l'est, elle continue ; sinon, elle
réessaie sous la même clé.

## 4. Orchestration ou chorégraphie

Chris Richardson décrit deux façons de coordonner une saga :

- **l'orchestration** (cette leçon) : un orchestrateur dit à chaque
  contexte quoi faire, et garde l'état. Le flux se lit dans un seul
  fichier, `saga.go` ; l'état de chaque prêt se lit dans une seule table ;
- **la chorégraphie** : chaque contexte réagit aux événements des autres
  (`GuaranteeReserved` déclenche l'envoi, `MoneySent` déclenche
  l'activation). Aucun chef, mais le flux n'est écrit nulle part : c'est
  l'avertissement de Martin Fowler de la leçon 8.1, et les sagas qui
  restent bloquées ne se voient qu'en cherchant dans trois contextes.

Pour une action qui engage de l'argent, l'orchestration est presque
toujours le bon choix : on veut pouvoir répondre à « où en est le prêt
`loan-0042` ? » en une requête.

## 5. La campagne

Neuf mutations, dans l'orchestrateur et l'opérateur :

```text
pas de compensation                          tuee
délai pris pour un succès                    tuee
nouvelle clé à chaque essai                  tuee
étape non enregistrée                        SURVIT
reprise partielle                            tuee
envoi non enregistré                         SURVIT
un seul essai                                tuee
prêt jamais activé                           tuee
opérateur sans idempotence                   tuee
7/9 tuees
```

Deux survivantes, et elles enseignent quelque chose :

- **ne pas enregistrer l'étape après la garantie**, ou **après l'envoi** :
  après un arrêt, la saga reprend une étape plus tôt, et **refait** la
  réservation ou l'envoi. Rien de faux n'arrive, parce que chaque étape
  est idempotente : réserver deux fois la garantie d'un prêt ne change
  rien, et l'opérateur n'envoie pas deux fois sous la même clé.
- la preuve : la mutation **« opérateur sans idempotence »** est tuée.
  Sans la clé, l'étape refaite enverrait l'argent deux fois.

L'enregistrement de l'état évite de **refaire** le travail ;
l'idempotence rend le travail refait **sans danger**. Une saga a besoin
des deux, car on ne peut pas enregistrer l'état dans la même transaction
que l'appel à l'opérateur : il reste toujours un instant entre l'action
et son enregistrement.

## 6. La grille

| Pour chaque saga | À vérifier |
|---|---|
| les étapes | chacune locale, dans un seul contexte, et idempotente (une clé par saga) |
| l'état | enregistré après chaque étape ; un programme redémarré reprend les sagas inachevées |
| le point de non-retour | nommé ; avant, une compensation par étape ; après, seulement la suite |
| les délais dépassés | une question à celui qui sait (statut, clé), jamais une conclusion |
| les compensations | idempotentes, et réessayées jusqu'au bout : une compensation qui échoue laisse le pire état |
| la surveillance | les sagas dans la même étape depuis plus de N minutes ; l'état de chaque saga, lisible |

## 7. Les trois erreurs qui restent

### « Un délai dépassé, c'est un échec : on annule »

29 versements sans prêt et sans garantie dans la section 3. Un délai
dépassé veut dire « je ne sais pas ». L'opérateur, lui, sait : on lui
demande, avec la clé.

### « On met tout dans une transaction distribuée »

L'opérateur Mobile Money ne participe pas à une transaction en deux
phases, et ne le fera jamais : c'est un service externe. Même entre nos
propres contextes, une transaction distribuée lie leur disponibilité
(leçon 8.2). La saga accepte que les trois contextes soient, un instant,
dans un état intermédiaire (« garantie bloquée, argent pas encore
envoyé »), et le rend visible.

### « La compensation remet tout comme avant »

Non : Garcia-Molina et Salem le disent dès 1987. Libérer une garantie ne
défait pas le SMS « votre prêt est en cours d'examen » déjà envoyé ;
l'annulation d'un versement (s'il était possible) serait un nouveau
mouvement d'argent, avec ses frais. La compensation se conçoit étape par
étape, avec le métier, comme une action à part entière.

## 8. Le lien avec la production

- **La table des sagas** : identifiant, étape, nombre d'essais, dernière
  erreur, dates. Elle répond au téléphone : « où en est mon prêt ? ».
- **La reprise** : au démarrage, et périodiquement, l'orchestrateur
  relance les sagas inachevées. Plusieurs instances le font en prenant
  chaque saga avec `FOR UPDATE SKIP LOCKED` (leçon 8.2).
- **L'alerte** : une saga dans l'étape « argent envoyé » depuis plus de
  cinq minutes est un prêt versé et non enregistré ; une saga qui
  compense depuis une heure est une garantie bloquée.
- **Les délais et les nouvelles tentatives** suivent la leçon 9.2 :
  espacés, bornés, et toujours sous la même clé.

## 9. Ce qu'il faut retenir

1. Une saga : des étapes locales, un état enregistré, une reprise.
2. Avant le point de non-retour, compenser ; après, terminer.
3. Chaque étape idempotente, sous une clé par saga.
4. Un délai dépassé est une question.
5. Une saga bloquée est une alerte.

## 10. Approfondissement

### Les étapes qui se réessaient

Après le point de non-retour, les étapes doivent **finir par réussir** :
activer le prêt ne peut pas échouer pour une raison métier (le prêt a été
décidé avant). Si une étape après le pivot peut être refusée, elle est
mal placée : il faut la mettre **avant** l'envoi. C'est le travail de
conception d'une saga : ordonner les étapes pour que tout ce qui peut
dire non passe avant le point de non-retour.

### L'isolation qui manque

Une saga n'a pas l'isolation d'une transaction : pendant qu'elle tourne,
les autres voient ses états intermédiaires (une garantie bloquée pour un
prêt qui sera refusé). On s'en protège par des états explicites
(« garantie en attente », que l'écran affiche comme tel) et par l'ordre
des étapes : réserver avant d'engager.

## 11. Le réflexe à installer

Devant une action qui traverse plusieurs contextes, demande-toi :

1. Quelles sont les étapes, et laquelle est le point de non-retour ?
2. Quelle compensation pour chaque étape avant lui ?
3. Quelle clé rend chaque étape idempotente ?
4. Que fait-on d'un délai dépassé, et à qui pose-t-on la question ?
5. Où lit-on l'état d'une saga, et qui voit celles qui ne finissent pas ?

  SIGMOD 1987 : chaque transaction d'une saga reçoit une transaction de

- Chris Richardson, [Pattern: Saga](https://microservices.io/patterns/data/saga.html) :
  « A saga is a reliably coordinated sequence of local transactions » ;
  la chorégraphie, où « each local transaction publishes domain events
  that trigger local transactions in other services », et
  l'orchestration, où « an orchestrator (object) tells the participants
  what local transactions to execute. »

  « Pivot transactions serve as the point of no return in the saga.

  longer relevant. »

  « A compensating transaction doesn't necessarily return the system data
