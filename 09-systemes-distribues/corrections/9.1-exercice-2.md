# Correction 9.1 — Exercice 2 : lire un test de capacité

> Rappel de l'énoncé : écrire `Capacity`, le plus haut débit servi à
> 99 % avec un 99e centile dans l'objectif, et `Headroom`, la marge au
> pic.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Deux conditions** par palier : le débit servi, et la latence.
- **L'ordre des paliers** ne compte pas : on garde le plus haut qui passe.
- **La marge** est négative au-dessus de la capacité.

## 1. La solution

```go
func Capacity(points []Point, slo time.Duration) int {
    best := 0
    for _, p := range points {
        if p.Served >= 0.99*float64(p.Offered) && p.P99 <= slo {
            best = max(best, p.Offered)
        }
    }
    return best
}
```

```go
func Headroom(capacity, peak int) float64 {
    if capacity <= 0 {
        return -1
    }
    return float64(capacity-peak) / float64(capacity)
}
```

Avec les mesures de la leçon : 480 requêtes par seconde pour un objectif
de 100 ms, 450 pour un objectif de 23 ms. La capacité **dépend de
l'objectif** : un système n'a pas une capacité, il en a une par promesse
de latence.

## 2. Pourquoi deux conditions

Le 99e centile ne porte que sur les requêtes **servies**. Un palier où le
serveur refuse vite la moitié des requêtes (des `503` en 2 ms) a un
excellent 99e centile, et sert la moitié de la charge. Le palier à 520
requêtes par seconde de la leçon sert 474 : 91 %. Sans la condition sur
le débit, un serveur qui échoue vite passerait pour rapide.

## 3. La marge

Avec une capacité de 480 et un pic attendu de 360, la marge est de 25 %.
C'est le bas de ce qu'on vise : la section 2 de la leçon montre qu'une
pointe au-delà de la capacité crée une file qui met longtemps à se
vider.

## Ce qu'il faut retenir

- Une capacité se lit pour un objectif de latence.
- Un test de capacité mesure aussi ce qui est servi.
- 20 à 30 % de marge au pic.
