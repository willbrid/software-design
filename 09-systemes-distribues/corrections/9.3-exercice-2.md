# Correction 9.3 — Exercice 2 : la garde HTTP

> Rappel de l'énoncé : un intergiciel qui applique la limite par client
> (`429`), puis l'admission (`503`), et libère sa place à la fin.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **La limite d'abord** : elle ne coûte qu'une lecture en mémoire.
- **L'admission ensuite**, avec le contexte de la requête : un client
  parti libère sa place dans la file.
- **`defer release()`** rend la place même si le gestionnaire panique.

## 1. La solution

```go
func (g *Guard) Wrap(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        client := r.Header.Get("X-Client")
        if client == "" {
            client = "anonymous"
        }
        if !g.Limit.Allow(client, g.Now()) {
            w.Header().Set("Retry-After", "1")
            http.Error(w, "too many requests", http.StatusTooManyRequests)
            return
        }
        release, err := g.Admission.Admit(r.Context(), g.PriorityOf(r))
        if err != nil {
            w.Header().Set("Retry-After", "2")
            http.Error(w, "overloaded", http.StatusServiceUnavailable)
            return
        }
        defer release()
        next.ServeHTTP(w, r)
    })
}
```

Les clients sans en-tête partagent le seau `anonymous` : c'est voulu.
Une requête qui ne dit pas qui elle est n'a pas droit à un seau
neuf à chaque appel ; sinon, il suffirait d'omettre l'en-tête pour
échapper à la limite.

## 2. Pourquoi la limite avant l'admission

Si l'admission passait d'abord, le script du partenaire prendrait une
place dans la file, puis serait refusé par la limite : il aurait occupé
une place pour rien, et peut-être fait refuser un membre. La limite,
placée avant, écarte le client en trop **sans qu'il touche à rien** de
partagé. L'ordre suit le coût : d'abord ce qui est le moins cher à
vérifier et le plus juste à refuser.

## 3. Ce qui manque pour la production

L'identité du client ne vient pas d'un en-tête que chacun peut écrire :
elle vient de l'authentification (la clé d'API du partenaire, le jeton du
membre, leçon 9.5). Un en-tête `X-Client` libre permettrait à un script de
se présenter sous mille noms.

## Ce qu'il faut retenir

- La limite avant l'admission.
- Un client inconnu partage un seau, il n'en reçoit pas un neuf.
- L'identité du client vient de l'authentification.
