# Correction 9.4 — Exercice 5 : les alertes ignorées du 9 décembre

> Rappel de l'énoncé : une alerte trop bavarde coupée par l'astreinte,
> une vraie panne vue avec 50 minutes de retard ; noter les alertes,
> rejouer avec le taux de combustion, rédiger.

L'audit et le rejeu sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **L'alerte du moment : 1 007 notifications** en un mois pour deux
  incidents ; sa précision par alerte (92 %) cache le vrai défaut, le
  volume.
- **Les alertes sur le budget : 4 notifications**, toutes vraies ; la
  panne est vue en **10 minutes**, la fuite par un ticket au bout d'un
  jour.
- **La cause** : une alerte qui sonnait à chaque minute de la fuite ;
  **la cause de la cause** : une alerte sur un taux d'erreur instantané,
  sans objectif.

## 1. L'audit

```go
func Rate(alerts []slo.Alert, incidents []Incident) Score {
    s := Score{Alerts: len(alerts), Detection: make([]int, len(incidents))}
    for i := range s.Detection {
        s.Detection[i] = -1
    }
    for _, a := range alerts {
        for i, in := range incidents {
            if a.Minute < in.Start || a.Minute >= in.End+60 {
                continue
            }
            s.True++
            if s.Detection[i] < 0 {
                s.Detection[i] = a.Minute - in.Start
            }
            break
        }
    }
    seen := 0
    for _, d := range s.Detection {
        if d >= 0 {
            seen++
        }
    }
    if s.Alerts > 0 {
        s.Precision = float64(s.True) / float64(s.Alerts)
    }
    if len(incidents) > 0 {
        s.Recall = float64(seen) / float64(len(incidents))
    }
    return s
}
```

Une alerte qui tombe dans l'heure après la fin d'un incident compte
comme vraie : elle en parle encore. Chaque alerte n'est comptée que pour
un incident.

## 2. Les chiffres, et le rejeu

`cmd/december` note les deux jeux d'alertes sur le même mois :

```text
December 2026, 300 requests a minute, objective 99.5 %; a leak on days 3 to 5, an outage on 9 December at 02:10

alerts                                  alerts   true  precision  recall  minutes to detect (leak, outage)
error rate over 1 % for 1 minute          1007    928      92.2%    100%  [2 0]
burn rate, multiwindow                       4      4     100.0%    100%  [1519 10]
```

- **Le taux d'erreur instantané** : 1 007 notifications, dont 928
  « vraies » (92 %) et un rappel de 100 %. Sur le papier, une bonne
  alerte. En pratique, plus de 900 notifications pour la seule fuite, une toutes
  les quelques minutes pendant trois jours : la personne d'astreinte les
  a coupées, et la panne du 9 décembre, pourtant détectée en 0 minute,
  n'a été lue qu'à 3 h.
- **Le taux de combustion** : 4 notifications, toutes vraies. La panne
  déclenche une page **10 minutes** après son début ; la fuite, un
  ticket après 1 519 minutes (un peu plus d'un jour), ce qui est voulu :
  elle consomme le budget lentement, elle n'a pas à réveiller quelqu'un
  la nuit.

La précision par alerte ne suffit pas à juger une stratégie : il faut
aussi compter les **notifications par incident**. Une alerte vraie qui
sonne 900 fois est une alerte qu'on coupe.

## 3. La cause

**En une phrase** : la panne du 9 décembre a été vue avec 50 minutes de
retard parce que les notifications avaient été coupées, après des
centaines d'alertes pour une fuite lente qui oscillait autour du seuil.

**La cause de la cause** : l'alerte portait sur le taux d'erreur d'une
minute, sans lien avec un objectif ; elle ne savait pas distinguer une
fuite qui consomme le budget en trois jours d'une panne qui le consomme
en trois heures, et sonnait à chaque passage du seuil.

## 4. Le compte rendu

1. **Quoi** : le mercredi 9 décembre 2026, de 2 h 10 à 3 h, 40 % des
   paiements ont échoué ; la panne n'a été prise en charge qu'à 3 h.
2. **Cause** : les notifications de l'astreinte avaient été coupées la
   veille, après plus de 500 alertes « plus de 1 % d'erreurs sur une
   minute » déclenchées par une fuite lente du 3 au 5 décembre.
3. **Détection** : l'alerte a sonné à 2 h 10, sans être lue ; un membre a
   écrit au support à 2 h 55.
4. **Correction** : la panne elle-même (une mise à jour de l'opérateur) a
   été contournée à 3 h 20 ; les paiements échoués ont été réessayés par
   les membres, sans doublon grâce aux clés d'idempotence.
5. **Prévention** : un objectif de 99,5 % pour les paiements ; les
   alertes sur le taux de combustion à deux fenêtres remplacent l'alerte
   instantanée ; la fuite lente devient un ticket ; le nombre de
   notifications par semaine est suivi, et toute alerte qui sonne sans
   action est revue.

## Ce qu'il faut retenir

- Une alerte se juge aussi au nombre de notifications par incident.
- Une fuite lente est un ticket, une panne est une page.
- Une alerte qu'on coupe est pire qu'une alerte qui n'existe pas.
