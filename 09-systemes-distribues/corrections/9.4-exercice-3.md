# Correction 9.4 — Exercice 3 : le reçu qui se souvient de sa requête

> Rappel de l'énoncé : des journaux JSON avec l'identifiant de la
> requête sur chaque ligne, y compris celles du reçu envoyé en arrière-plan.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **L'identifiant entre dans le contexte** au début de la requête.
- **Le membre est attaché au journal** (`With`), le montant à la ligne
  où il a un sens.
- **Le reçu reçoit `context.WithoutCancel(ctx)`** : les valeurs de la
  requête, sans sa fin.

## 1. La solution

```go
func (s *Service) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    member, amount := r.URL.Query().Get("member"), r.URL.Query().Get("amount")
    ctx := logs.WithRequest(r.Context(), r.Header.Get("X-Request-Id"))
    log := logs.New(s.Out).With("member", member)
    log.InfoContext(ctx, "payment received", "amount", amount)
    // The receipt keeps the values of the request (its id), not its end:
    // the request is answered before the SMS leaves.
    bg := context.WithoutCancel(ctx)
    s.wg.Go(func() {
        if err := s.Receipt(bg, member); err != nil {
            log.ErrorContext(bg, "receipt failed", "err", err)
            return
        }
        log.InfoContext(bg, "receipt sent")
    })
    w.Write([]byte("paid"))
}
```

## 2. L'autre défaut

Le reçu recevait `r.Context()`, le contexte de la requête. Ce contexte
est **annulé dès que la réponse est envoyée** : le reçu, lancé en
arrière-plan, travaillait avec un contexte déjà mort, et le prestataire
SMS aurait vu chaque envoi annulé. Les tests du code d'origine ne le
montraient pas, parce que leur faux prestataire ne regardait pas le
contexte. Le second test le fait (`return ctx.Err()`), et attend 10 ms :
avec le contexte de la requête, il échoue.

`context.WithoutCancel` (depuis Go 1.21) garde les **valeurs** du contexte
(l'identifiant de la requête, la trace) et retire son **annulation**.
C'est exactement ce qu'il faut pour un travail qui continue après la
réponse. Il ne retire pas le besoin d'un délai : le reçu en prendrait un
à lui (`context.WithTimeout(bg, 30*time.Second)`), pour ne pas attendre
le prestataire indéfiniment.

## Ce qu'il faut retenir

- L'identifiant voyage dans le contexte, jusqu'au travail en
  arrière-plan.
- Un travail qui survit à la requête prend `context.WithoutCancel`, et
  son propre délai.
- Un faux qui ignore le contexte cache les défauts de contexte.
