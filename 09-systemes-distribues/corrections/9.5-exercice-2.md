# Correction 9.5 — Exercice 2 : la politique d'accès

> Rappel de l'énoncé : écrire `Allowed`, qui dit qui peut faire quoi sur
> quel objet.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Un seul endroit** décrit toutes les règles.
- **Chaque règle nomme le type d'objet et l'action**.
- **Ce qui n'est pas écrit est refusé**.

## 1. La solution

```go
func Allowed(c authz.Claims, action string, o Object) bool {
    sameTontine := c.Tontine == o.Tontine
    treasurer := c.Role == "treasurer" && sameTontine
    switch o.Kind + " " + action {
    case "wallet read":
        return c.Member == o.Owner || treasurer
    case "wallet withdraw":
        return c.Member == o.Owner
    case "round read":
        return sameTontine
    case "round close":
        return treasurer
    }
    return false // what is not written is refused
}
```

## 2. Refuser par défaut

Une politique qui autorise tout ce qu'elle n'interdit pas a une faille
le jour où quelqu'un ajoute un type d'objet (un prêt) ou une action
(supprimer) sans y penser : tout le monde y a droit. Une politique qui
refuse tout ce qu'elle ne nomme pas a un défaut le même jour : la
trésorière ne peut pas lire les prêts. Le second défaut se voit au
premier essai, et se corrige en ajoutant une ligne ; le premier ne se
voit qu'à l'incident.

Les deux dernières lignes du tableau de test (`delete` sur un
portefeuille, `read` sur un prêt) vérifient ce refus par défaut.

## 3. Où l'appeler

`Allowed` s'appelle là où l'objet est chargé, avec l'objet chargé, pas
avec l'identifiant de la requête : la tontine du portefeuille vient de la
base, pas de ce que l'appelant prétend. Et chaque route a sa ligne dans
la table de tests de la grille (route × rôle × propriétaire).

## Ce qu'il faut retenir

- Une politique d'accès écrite à un seul endroit.
- Refuser par défaut.
- Décider sur l'objet chargé, pas sur ce que dit la requête.
