# Correction 9.1 — Exercice 3 : un paiement en deux temps, sur deux instances

> Rappel de l'énoncé : rendre le paiement en deux temps indépendant de
> l'instance, et confirmable une seule fois.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Le paiement préparé va dans la base**, que toutes les instances
  lisent.
- **Une seule instruction** le retire et l'enregistre : deux
  confirmations simultanées, une seule trouve la ligne.
- **L'instance ne garde plus rien** : elle peut redémarrer entre les deux
  étapes.

```go
// Handler serves /pay and /confirm.
func (in *Instance) Handler() http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("POST /pay", func(w http.ResponseWriter, r *http.Request) {
        amount, err := strconv.ParseInt(r.URL.Query().Get("amount"), 10, 64)
        if err != nil || amount <= 0 {
            http.Error(w, "bad amount", http.StatusBadRequest)
            return
        }
        b := make([]byte, 8)
        rand.Read(b)
        code := hex.EncodeToString(b)
        if _, err := in.Pool.Exec(r.Context(), `INSERT INTO pending_payments (code, member, amount) VALUES ($1, $2, $3)`,
            code, r.URL.Query().Get("member"), amount); err != nil {
            http.Error(w, err.Error(), http.StatusInternalServerError)
            return
        }
        w.Write([]byte(code))
    })
    mux.HandleFunc("POST /confirm", func(w http.ResponseWriter, r *http.Request) {
        // Taking the prepared payment out and recording it in one
        // statement: two confirmations at once, one finds the row.
        err := in.Pool.QueryRow(r.Context(), `
            WITH taken AS (DELETE FROM pending_payments WHERE code = $1 RETURNING code, member, amount)
            INSERT INTO payments (code, member, amount) SELECT code, member, amount FROM taken
            RETURNING code`, r.URL.Query().Get("code")).Scan(new(string))
        if errors.Is(err, pgx.ErrNoRows) {
            http.Error(w, "unknown code", http.StatusNotFound)
            return
        }
        if err != nil {
            http.Error(w, err.Error(), http.StatusInternalServerError)
            return
        }
        w.Write([]byte("paid"))
    })
    return mux
}
```

`DELETE ... RETURNING` dans un `WITH`, suivi de l'`INSERT` : une seule
instruction, donc une seule transaction. Si deux confirmations arrivent
en même temps, la seconde attend le verrou de la ligne, puis ne la trouve
plus : `ErrNoRows`, et un `404`.

## 2. Le test qui passait déjà

`TestACodeIsConfirmedOnceEvenOnTwoInstancesAtOnce` passe avec le code
d'origine, mais **pas pour la bonne raison** : le code est préparé sur
l'instance A, et seules les confirmations envoyées à A le trouvent. Le
verrou de l'instance garantit qu'une seule d'entre elles gagne ; les
confirmations envoyées à B échouent parce que B ne connaît pas le code.
Le test vérifie « une seule confirmation acceptée », et c'est vrai, mais
les membres dont la confirmation tombe sur B voient un `404` pour un
paiement qui existe. C'est le premier test qui le montre.

## 3. Le prix

Deux écritures dans la base au lieu d'une, et une table à purger (les
paiements préparés et jamais confirmés). On ajoute une expiration : une
tâche supprime les lignes de plus de 15 minutes, et la confirmation
refuse une ligne trop vieille.

## Ce qu'il faut retenir

- Ce qui doit survivre entre deux requêtes va dans un service partagé.
- Une instruction qui retire et enregistre décide qui gagne.
- Un test qui passe peut passer pour une mauvaise raison.
