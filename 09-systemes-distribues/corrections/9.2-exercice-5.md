# Correction 9.2 — Exercice 5 : la panne de l'opérateur du 2 décembre

> Rappel de l'énoncé : une panne de 3 s, des tentatives sans hasard ni
> budget ; mesurer le temps de rétablissement, rejouer, rédiger.

L'audit et le rejeu sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Avec la politique du jour, l'application met 5 s à se rétablir**
  après une panne de 3 s, et seules 26 % des requêtes réussissent.
- **Avec du hasard, elle ne se rétablit pas** avant la fin du rejeu.
- **Avec un budget de 10 %, elle se rétablit à l'instant** où l'opérateur
  revient, et 70 % des requêtes réussissent : toutes celles qui ne
  tombaient pas pendant la panne.

## 1. L'audit

```go
func Recovery(outcomes []Outcome, up time.Duration) time.Duration {
    const window = 500 * time.Millisecond
    type count struct{ ok, all int }
    windows := map[time.Duration]*count{}
    var last time.Duration
    for _, o := range outcomes {
        w := o.SentAt.Truncate(window)
        if windows[w] == nil {
            windows[w] = &count{}
        }
        windows[w].all++
        if o.OK {
            windows[w].ok++
        }
        last = max(last, w)
    }
    good := func(w time.Duration) bool {
        c := windows[w]
        return c == nil || float64(c.ok) >= 0.95*float64(c.all)
    }
    from := time.Duration(-1)
    for w := up.Truncate(window); w <= last; w += window {
        switch {
        case !good(w):
            from = -1
        case from < 0:
            from = w
        }
    }
    if from < 0 {
        return -1
    }
    return from - up
}
```

Les fenêtres sans requête comptent comme bonnes : il n'y avait personne
à servir. La fenêtre de départ redevient `-1` dès qu'une fenêtre est
mauvaise : on cherche le début de la **dernière** série de bonnes
fenêtres, pas la première bonne fenêtre.

## 2. Les chiffres, et le rejeu

`cmd/morning` rejoue la matinée trois fois :

```text
200 requests per second for 10 s; the operator is down from 1 s to 4 s

retries                                 succeeded recovered after 4 s in
5 attempts, doubling from 100 ms            26.5%                     5s
the same, with jitter                       27.0%     not before the end
the same, with jitter and a 10 % budget      70.0%                     0s
```

- **La politique du jour** : chaque requête de la panne réessaie quatre
  fois, à 100, 200, 400 et 800 ms. Quand l'opérateur revient, il reçoit
  le trafic normal **et** toutes ces tentatives : sa file s'allonge, les
  appels dépassent 300 ms, sont abandonnés, réessayés. Il faut **5 s**
  après son retour pour que les requêtes réussissent de nouveau ; sur la
  matinée, **26 %** seulement réussissent.
- **Avec du hasard** : les tentatives sont étalées, mais aussi nombreuses ;
  le service ne sort pas de la surcharge avant la fin du rejeu.
- **Avec un budget de 10 %** : pendant la panne, les tentatives s'arrêtent
  dès que le budget est vide. À son retour, l'opérateur ne reçoit que le
  trafic normal : rétabli **tout de suite**, et 70 % de réussite, le
  maximum possible (30 % des requêtes tombaient dans la panne).

## 3. La cause

**En une phrase** : les tentatives des requêtes échouées pendant la
panne sont arrivées sur l'opérateur à son retour, en plus du trafic
normal, et l'ont gardé en surcharge plus longtemps que la panne elle-même.

**La cause de la cause** : la politique de tentatives n'avait aucune
borne globale ; chaque requête décidait seule de réessayer, sans savoir
que toutes les autres faisaient de même. Les tests ne couvraient qu'une
erreur isolée, jamais une panne de tout le service.

## 4. Le compte rendu

1. **Quoi** : le mercredi 2 décembre 2026, l'opérateur a été indisponible
   trois minutes ; l'application a mis encore cinq minutes à servir
   normalement après son retour, et les trois quarts des requêtes de la
   matinée ont échoué.
2. **Cause** : à son retour, l'opérateur a reçu, en plus du trafic
   normal, les tentatives de toutes les requêtes échouées pendant la
   panne ; saturé, il a fait dépasser leur délai aux appels, qui ont été
   réessayés à leur tour.
3. **Détection** : par l'alerte sur le taux d'échec, puis par l'opérateur,
   qui a signalé un trafic quatre fois supérieur à la normale à son
   retour.
4. **Correction** : un budget de tentatives de 10 % par instance, du
   hasard dans les pauses, et le respect du `Retry-After` de l'opérateur
   (exercice 2).
5. **Prévention** : un test de résilience qui coupe l'opérateur trois
   secondes sous charge et mesure le temps de rétablissement (il doit
   être nul) ; une alerte sur l'épuisement du budget ; une seule couche
   réessaie (exercice 3).

## Ce qu'il faut retenir

- Après une panne, les tentatives arrivent toutes ensemble.
- Le hasard ne réduit pas leur nombre ; le budget, si.
- On mesure le temps de rétablissement, pas seulement la panne.
