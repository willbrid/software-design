# Correction 9.3 — Exercice 5 : le script du partenaire du 7 décembre

> Rappel de l'énoncé : un script à 300 requêtes par seconde, des membres
> refusés pendant deux heures ; mesurer, rejouer avec une limite par
> client, rédiger.

L'audit et le rejeu sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Les membres ne sont servis qu'à 27,5 %** ; le partenaire prend **83 %**
  du service.
- **Avec 10 requêtes par seconde par client**, les membres sont servis à
  **99,8 %**, et le partenaire garde 15 % du service : ses 10 par seconde.
- **La cause** : une admission qui ne regarde pas qui envoie ; **la cause
  de la cause** : aucun client n'avait de limite propre.

## 1. L'audit

```go
func Audit(res map[string]*loadgen.Class) Report {
    var r Report
    m, p := res["members"], res["partner"]
    if m != nil {
        r.MembersSent, r.MembersServed = m.Sent, m.Served
        if m.Sent > 0 {
            r.MembersShare = float64(m.Served) / float64(m.Sent)
        }
    }
    if p != nil && p.Served+r.MembersServed > 0 {
        r.PartnerShareOfServed = float64(p.Served) / float64(p.Served+r.MembersServed)
    }
    return r
}
```

## 2. Les chiffres, et le rejeu

`cmd/monday` rejoue la matinée deux fois :

```text
members 60 per second, a partner's script 300 per second, a server of 100 per second; 8 s per run

                             member sent   member served    member share  partner share of served
admission alone                      480             132           27.5%                    83.4%
10 per second per client             480             479           99.8%                    15.1%
```

- **L'admission seule** : le serveur sert sa capacité, mais aux
  requêtes qui arrivent, et le script en envoie cinq fois plus que les
  membres. **132 requêtes de membres sur 480** passent ; 83 % de ce que le
  serveur sert va au partenaire.
- **Une limite par client** : le script est ramené à 10 par seconde, et
  la capacité libérée va aux membres : **479 sur 480**. Le partenaire
  reçoit des `429` avec `Retry-After`, et son script, s'il est bien écrit,
  ralentit.

L'admission protégeait le **serveur** : il n'a jamais été saturé de
travail gâché. Elle ne protégeait pas les **membres** les uns des autres.

## 3. La cause

**En une phrase** : le script du partenaire envoyait cinq fois plus de
requêtes que tous les membres réunis, et l'admission, qui refuse sans
regarder qui envoie, lui a donné cinq fois plus de place.

**La cause de la cause** : l'API n'avait aucune limite par client ; le
contrat du partenaire disait 20 requêtes par seconde, mais rien ne le
faisait respecter, et personne n'avait prévu qu'un script de
rapprochement tournerait un lundi matin, à l'heure des paiements.

## 4. Le compte rendu

1. **Quoi** : le lundi 7 décembre 2026, de 9 h à 11 h, environ trois
   paiements de membres sur quatre ont été refusés (« service
   surchargé »).
2. **Cause** : un script de rapprochement d'une banque partenaire
   interrogeait l'API 300 fois par seconde ; sans limite par client, il
   occupait 83 % de la capacité.
3. **Détection** : par l'alerte sur les refus, à 9 h 05 ; la cause
   (le client) n'a été trouvée qu'à 10 h 40, faute de métrique des refus
   par client.
4. **Correction** : le partenaire a arrêté son script à 11 h ; une limite
   de 20 requêtes par seconde (son contrat), globale sur les instances,
   est déployée le soir même.
5. **Prévention** : une limite par client pour chaque type de client
   (exercice 4) ; les refus mesurés par client ; les traitements des
   partenaires programmés hors des heures de pointe, sur une API ou un
   réplica dédiés.

## Ce qu'il faut retenir

- L'admission protège le serveur ; la limite protège les clients les uns
  des autres.
- Un contrat de débit se fait respecter par le code.
- Les refus se mesurent par client, sinon on ne trouve pas qui les cause.
