# Leçon 9.3 — La surcharge : refuser tôt, par ordre d'importance, et chaque client à sa mesure

## L'essentiel en deux minutes

**Le problème, en une phrase.** Quand il arrive plus de requêtes que le
serveur ne peut en servir, le laisser tout accepter ne sert personne :
toutes attendent, la plupart échouent après avoir coûté du travail, et le
serveur sert **moins** que sa capacité.

**Trois images.**

- **La salle d'attente du dispensaire** : quand elle est pleine, on ne
  fait pas entrer tout le monde pour que chacun attende six heures ; on
  dit aux derniers arrivés de revenir demain, et on soigne ceux qui sont
  là.
- **Le tri aux urgences** : sous la pression, on soigne d'abord ce qui ne
  peut pas attendre. Les cotisations avant les rapports.
- **La pompe à eau du quartier** : chaque famille a droit à ses bidons ;
  celle qui vient avec un camion-citerne ne prive pas tout le monde.

**Le code, en quelques lignes.** Avant tout travail, la demande entre si
une place est libre, attend un peu dans une file courte, ou est refusée
tout de suite :

```go
// Admit returns a release function once the request may go, or
// ErrRefused.
func (c *Controller) Admit(ctx context.Context, p Priority) (func(), error) {
    c.mu.Lock()
    if c.inFlight < c.MaxInFlight && len(c.queue) == 0 {
        c.inFlight++
        c.mu.Unlock()
        return c.release, nil
    }
    limit := c.MaxQueue
    if p == Low {
        limit = int(float64(c.MaxQueue) * c.LowShare)
    }
    if len(c.queue) >= limit {
        c.mu.Unlock()
        return nil, ErrRefused
    }
    turn := make(chan struct{})
    c.queue = append(c.queue, turn)
    c.mu.Unlock()

    timer := time.NewTimer(c.MaxWait)
    defer timer.Stop()
    select {
    case <-turn:
        return c.release, nil
    case <-timer.C:
    case <-ctx.Done():
    }
    c.mu.Lock()
    defer c.mu.Unlock()
    for i, q := range c.queue {
        if q == turn {
            c.queue = append(c.queue[:i], c.queue[i+1:]...)
            return nil, ErrRefused
        }
    }
    return c.release, nil // our turn came while we gave up: take it
}
```

**Les règles à retenir.**

1. **Le débit utile compte, pas le débit reçu** : une requête servie
   après que le membre est parti est du travail perdu.
2. **On refuse tôt**, avant de travailler : une file courte, une attente
   courte, et un `503` avec `Retry-After` pour les autres.
3. **On refuse d'abord ce qui peut attendre** : une priorité par type de
   requête.
4. **Chaque client a sa limite** (`429`) : un script ne prive pas les
   membres.
5. **La file se borne en longueur et en durée** ; une file sans borne
   n'est qu'une panne lente.

La suite le mesure sur un serveur de 100 requêtes par seconde.

---

La leçon 9.1 s'est arrêtée sur un constat : en surcharge, agrandir le
pool fait servir **moins**, et la seule réponse est de refuser tôt. La
leçon 9.2 a protégé l'appelant d'un service en panne. Celle-ci protège le
service de ses appelants. Le problème :

> **Quand la demande dépasse la capacité, comment servir au moins la
> capacité, et d'abord ce qui compte ?**

Le module de la leçon est `l93`. Il n'a besoin que de la bibliothèque
standard : le serveur est simulé dans le processus (4 travailleurs, 40 ms
par requête, 100 requêtes par seconde au plus), et chaque membre attend
1 s au plus. Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Ce qu'une requête coûte

Le serveur a 4 travailleurs. Une requête attend son tour, puis travaille
40 ms jusqu'au bout, même si le membre est parti entre-temps :

```go
// Do waits for a worker and works. It returns ErrGaveUp if ctx ended
// while waiting, and the context's error if it ended while working.
func (s *Server) Do(ctx context.Context) error {
    select {
    case s.slots <- struct{}{}:
    case <-ctx.Done():
        return ErrGaveUp
    }
    time.Sleep(s.Service)
    <-s.slots
    if err := ctx.Err(); err != nil {
        s.wasted.Add(1)
        return err
    }
    s.done.Add(1)
    return nil
}
```

C'est le comportement de la plupart des serveurs : une requête SQL
commencée va au bout, un calcul aussi. Le travail fait pour un membre
parti est **gâché**.

## 2. Mesure : laisser tout entrer, ou admettre

`cmd/overload` envoie 80 puis 150 requêtes par seconde pendant 8 s, à un
serveur qui laisse tout le monde attendre un travailleur, puis à un
serveur qui en admet 4 en cours et 4 en file, 100 ms au plus :

```text
4 workers, 40 ms per request: 100 per second at most; 1 s of patience; 8 s per run

offered server                     served/s  refused  timed out  wasted   p99 served  p99 refused
     80 everyone waits                 80.0        0          0       0         41ms           0s
     80 admission: 4 + 4, 100 ms       80.0        0          0       0         41ms           0s
    150 everyone waits                 34.5        0        924     609        992ms           0s
    150 admission: 4 + 4, 100 ms       99.0      408          0       0         82ms          2µs
```

- **Sous la capacité (80 par seconde)**, les deux font pareil : 41 ms au
  99e centile, rien de refusé. L'admission ne coûte rien quand tout va
  bien.
- **Au-delà (150 par seconde), le serveur qui laisse tout entrer ne sert
  que 34,5 requêtes par seconde**, le tiers de sa capacité. La file
  grandit jusqu'à ce que chaque requête attende presque sa seconde de
  patience ; celles qui obtiennent un travailleur finissent après le
  départ du membre : **609 requêtes servies pour personne**, 924 abandons,
  et un 99e centile de 992 ms pour celles qui réussissent.
- **Le serveur qui admet sert 99 requêtes par seconde**, sa capacité,
  avec un 99e centile de **82 ms**. Les 408 requêtes de trop sont refusées
  en quelques microsecondes : le membre le sait tout de suite, et peut
  réessayer plus tard (leçon 9.2), au lieu d'attendre une seconde pour
  rien.

La Builders' Library d'AWS appelle cette différence le **goodput** : la
part du débit servie sans erreur et assez vite pour que le client en
profite. Sans admission, le débit reçu monte, et le débit utile
s'effondre.

## 3. Mesure : refuser d'abord ce qui peut attendre

Le soir du 30 novembre, 30 % des requêtes sont des cotisations, 70 % des
rapports (la trésorière, les statistiques). `cmd/priority` envoie 150
requêtes par seconde ; dans le second cas, les rapports n'ont droit qu'au
quart de la file :

```text
150 requests per second (30 % contributions, 70 % reports) to a server of 100 per second; 8 s per run

admission                  requests         sent   served    share   p99 served
one queue for all          contributions     360      242    67.2%        122ms
one queue for all          reports           840      553    65.8%        123ms
reports: a quarter of it   contributions     360      360   100.0%         79ms
reports: a quarter of it   reports           840      429    51.1%         70ms
```

- **Une file pour tous** : les cotisations sont servies à 67,5 %, comme
  les rapports. Un membre sur trois ne peut pas payer, pour qu'un rapport
  sur trois soit calculé.
- **Les rapports limités au quart de la file** : **toutes** les
  cotisations passent, et les rapports se partagent ce qui reste (51 %).
  Le serveur sert autant ; il sert d'abord ce qui compte.

Le livre SRE de Google décrit le même mécanisme sous le nom de
*criticality* : chaque requête porte une importance, et sous la pression
les moins importantes sont refusées les premières.

## 4. Mesure : un client qui prend toute la place

Un partenaire lance un script qui interroge l'API 300 fois par seconde,
pendant que les membres font 60 requêtes par seconde depuis 600
téléphones. `cmd/fair` compare l'admission seule, et l'admission précédée
d'une limite de 10 requêtes par seconde par client :

```text
members 60 per second + a partner's script 300 per second, to a server of 100 per second; 8 s per run

protection                     client      sent   served    share  refused  limited
admission only                 members      480      142    29.6%      338        0
admission only                 partner     2400      651    27.1%     1749        0
10 per second per client       members      480      479    99.8%        1        0
10 per second per client       partner     2400       85     3.5%        4     2311
```

- **L'admission seule** est juste… envers les requêtes : elle refuse sans
  regarder qui les envoie. Le script envoie cinq fois plus que les
  membres, il obtient cinq fois plus de place : **les membres ne sont
  servis qu'à 26,5 %**.
- **Une limite par client** : le script est limité à 10 par seconde (2 311
  refus en `429`), et **les membres sont servis à 99,8 %**.

La limite est un seau de jetons par client : il se remplit à un rythme
fixe, et chaque requête en prend un.

```go
// Allow takes a token from client's bucket at now, if there is one.
func (l *PerClient) Allow(client string, now time.Time) bool {
    l.mu.Lock()
    defer l.mu.Unlock()
    if l.buckets == nil {
        l.buckets = map[string]*bucket{}
    }
    b, ok := l.buckets[client]
    if !ok {
        b = &bucket{tokens: l.Burst, last: now}
        l.buckets[client] = b
    }
    b.tokens = min(l.Burst, b.tokens+now.Sub(b.last).Seconds()*l.Rate)
    b.last = now
    if b.tokens < 1 {
        return false
    }
    b.tokens--
    return true
}
```

Le statut `429 Too Many Requests` (RFC 6585) dit au client qu'il dépasse
son débit, et peut porter un `Retry-After` ; le `503` de l'admission dit
que le serveur, lui, est plein.

## 5. La campagne

Neuf mutations, dans l'admission, la limite et le serveur :

```text
dépasse la file                              SURVIT
une place de trop                            tuee
pas de priorité                              tuee
dernier arrivé servi                         tuee
file jamais nettoyée                         tuee
attente sans fin                             tuee
seau sans fond                               tuee
un seau pour tous                            tuee
travail gâché compté servi                   tuee
8/9 tuees
```

La survivante, « dépasse la file », est **équivalente** : la condition
`len(c.queue) == 0` empêche un nouveau venu de passer devant ceux qui
attendent, mais cette situation n'arrive jamais. Un travailleur libéré
est donné au premier de la file sans décrémenter `inFlight` ; il ne peut
donc pas y avoir à la fois une place libre et une file non vide. La
condition reste dans le code, pour le lecteur.

## 6. La grille

| Pour chaque serveur | À vérifier |
|---|---|
| l'admission | un nombre maximal en cours, une file courte, une attente maximale, mesurés sur la capacité |
| le refus | immédiat, `503` avec `Retry-After`, avant tout travail coûteux |
| les priorités | chaque route a son importance ; les moins importantes n'ont qu'une part de la file |
| les clients | une limite par client (par clé d'API, par membre) ; `429` au-delà |
| le travail gâché | le contexte du membre est transmis : une requête abandonnée n'est pas commencée |
| la mesure | débit utile, refus, abandons, travail gâché ; jamais le seul débit reçu |

## 7. Les trois erreurs qui restent

### « Refuser une requête, c'est perdre un membre »

Le serveur qui accepte tout a servi 34,5 requêtes par seconde ; celui qui
refuse, 99. En refusant 408 requêtes, il en a servi 516 de plus. Un refus
immédiat avec `Retry-After` est une réponse ; une attente d'une seconde
suivie d'une erreur n'en est pas une.

### « Une grande file absorbe les pointes »

Une file absorbe une pointe **courte**, plus courte que la patience des
membres. Une surcharge qui dure fait seulement attendre chaque requête
jusqu'à ce qu'elle échoue. Une file se borne en durée : au-delà de
quelques centaines de millisecondes, ceux qui attendent sont déjà
perdus.

### « Le partenaire a un contrat, on ne peut pas le limiter »

Le contrat dit un débit ; la limite le fait respecter, et protège les
membres de son dépassement. Sans limite, la section 4 montre que c'est le
plus gros client qui décide de la qualité de service de tous les autres.

## 8. Le lien avec la production

- **Les métriques** : refus par cause (`503` admission, `429` limite), par
  route et par client ; longueur et attente de la file ; travail gâché
  (requêtes terminées après le départ du client).
- **Les paramètres** se règlent sur la capacité mesurée (leçon 9.1) : en
  cours = le nombre de travailleurs utiles ; file = quelques fois ce
  nombre ; attente maximale = une petite part de la patience.
- **Plusieurs instances** : une limite par client tenue en mémoire est
  par instance ; un client réparti sur trois instances a trois fois sa
  limite. Pour une limite globale, le compteur va dans un service
  partagé, au prix d'un appel de plus.
- **La bibliothèque** `golang.org/x/time/rate` fournit un seau de jetons
  éprouvé ; celui de la leçon montre le principe.

## 9. Ce qu'il faut retenir

1. Le débit utile, pas le débit reçu.
2. Refuser tôt, avant de travailler.
3. D'abord ce qui compte : des priorités.
4. Une limite par client.
5. Une file bornée en longueur et en durée.

## 10. Approfondissement

### Le dernier arrivé d'abord

Sous surcharge, servir la file dans l'ordre sert d'abord ceux qui ont le
plus attendu, donc ceux qui sont le plus près d'abandonner. Certains
serveurs passent alors en **dernier arrivé, premier servi** : le dernier
arrivé a toute sa patience devant lui. C'est injuste pour ceux qui
attendent, mais cela sert plus de requêtes utiles. L'attente maximale de
cette leçon obtient un effet voisin, plus simplement : personne n'attend
assez longtemps pour devenir inutile.

### L'admission qui s'adapte

Les paramètres fixes supposent une capacité connue. Quand elle varie (une
requête plus chère, une base plus lente), on peut régler le nombre admis
d'après la latence mesurée : il baisse quand la latence monte, il remonte
quand elle baisse, comme le contrôle de congestion de TCP.

## 11. Le réflexe à installer

Devant chaque serveur, demande-toi :

1. Que fait-il de la requête en trop : la sert-il, la fait-il attendre,
   la refuse-t-il ?
2. Combien de temps une requête peut-elle attendre avant d'être perdue ?
3. Quelles requêtes refuser en premier ?
4. Un client peut-il, seul, priver tous les autres ?
5. Mesure-t-on le débit utile, ou seulement le débit reçu ?
