# Leçon 9.2 — La résilience : des délais, des tentatives qui n'aggravent pas la panne, et un coupe-circuit

## L'essentiel en deux minutes

**Le problème, en une phrase.** Le service de l'opérateur tombe deux
secondes, ou cesse de répondre trois secondes : sans délai, chaque
requête attend aussi longtemps que lui ; avec des nouvelles tentatives
mal réglées, on lui envoie quatre fois plus de travail au moment précis
où il essaie de se relever.

**Trois images.**

- **Le coup de téléphone** : on raccroche après dix sonneries, on ne
  reste pas en ligne une heure. C'est le **délai**.
- **La foule devant une porte qui rouvre** : si tout le monde se rue au
  même instant, personne ne passe. Si chacun attend un moment au hasard,
  la porte se vide. C'est le **hasard** (*jitter*) dans les tentatives.
- **Le disjoncteur** : quand le circuit est en court-circuit, il coupe ;
  on ne rebranche qu'après avoir vérifié. C'est le **coupe-circuit**.

**Le code, en quelques lignes.** Chaque requête gagne un dixième de
tentative ; chaque nouvelle tentative en dépense une : quand tout
échoue, les tentatives plafonnent à 10 % du trafic.

```go
func (b *Budget) retry() bool {
    b.mu.Lock()
    defer b.mu.Unlock()
    if b.tokens < 1 {
        return false
    }
    b.tokens--
    return true
}
```

**Les règles à retenir.**

1. **Chaque appel a un délai**, plus court que celui de l'écran qui
   l'attend. Un client HTTP de Go sans `Timeout` attend sans limite.
2. **Une nouvelle tentative est du travail en plus** pour un service peut-
   être déjà surchargé : peu de tentatives, espacées, au hasard.
3. **Un budget de tentatives** borne le travail en plus quand tout
   échoue ; le hasard seul ne le borne pas.
4. **Un coupe-circuit** cesse d'appeler un service qui échoue en série,
   et le teste avec un seul appel avant de reprendre.
5. **On ne réessaie que ce qui peut réussir** : pas un refus, et une
   écriture seulement avec une clé d'idempotence (leçon 6.3).

La suite le mesure avec un service simulé qui tombe, ou se tait.

> **Quand un service dont on dépend tombe ou ralentit, comment ne pas
> l'attendre indéfiniment, et ne pas l'empêcher de se relever ?**

Le module de la leçon est `l92`. Il n'a besoin que de la bibliothèque

mesuré sur un module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. Le service, et ce qu'il fait d'une requête abandonnée

Le service simulé travaille sur 6 requêtes à la fois, 20 ms chacune (300
par seconde au plus) ; les autres attendent leur tour. Comme beaucoup de
vrais services, il **finit une requête commencée**, même si l'appelant
est parti :

```go
// ServeHTTP serves one call.
func (d *Dep) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    d.calls.Add(1)
    d.mu.Lock()
    if d.perTick != nil {
        d.perTick[int64(time.Since(d.start)/(100*time.Millisecond))]++
    }
    d.mu.Unlock()
    switch Mode(d.mode.Load()) {
    case Down:
        http.Error(w, "down", http.StatusServiceUnavailable)
        return
    case Hang:
        select {
        case <-r.Context().Done():
        case <-time.After(30 * time.Second):
        }
        return
    }
    d.once.Do(func() { d.slots = make(chan struct{}, d.Capacity) })
    select {
    case d.slots <- struct{}{}:
    case <-r.Context().Done():
        return // the caller left while waiting its turn
    }
    time.Sleep(d.Service)
    <-d.slots
    if r.Context().Err() != nil {
        d.wasted.Add(1) // done for nobody
        return
    }
    w.Write([]byte("ok"))
}
```

Une requête abandonnée par l'appelant, mais déjà commencée, est du
travail **gâché** : le service l'a payée, personne n'en profite.

## 2. Les tentatives

Une politique dit combien d'essais, quelle pause entre eux, avec ou sans
hasard, et dans quel budget :

```go
// Pause returns the pause before attempt n+1, after n failed attempts.
func (p Policy) Pause(n int) time.Duration {
    d := p.Base << (n - 1) // Base, 2 Base, 4 Base...
    if d > p.Max || d <= 0 {
        d = p.Max
    }
    if p.Jitter {
        d = rand.N(d + 1)
    }
    return d
}
```

```go
// Do calls fn until it succeeds, fails for good, runs out of attempts or
// budget, or ctx ends.
func (p Policy) Do(ctx context.Context, fn func(context.Context) error) error {
    if p.Budget != nil {
        p.Budget.request()
    }
    for n := 1; ; n++ {
        err := fn(ctx)
        if err == nil || errors.Is(err, ErrPermanent) || n >= p.Attempts {
            return err
        }
        if p.Budget != nil && !p.Budget.retry() {
            return err
        }
        select {
        case <-ctx.Done():
            return err
        case <-time.After(p.Pause(n)):
        }
    }
}
```

## 3. Mesure : la tempête de tentatives

`cmd/storm` envoie 200 requêtes par seconde pendant 8 s. Le service tombe
de 2 s à 4 s (il répond `503` tout de suite) ; chaque appel abandonne
après 300 ms. Cinq politiques :

```text
200 requests per second for 8 s; the service serves 300 per second at most, and is down from 2 s to 4 s; 300 ms per call

                                   succeeded  calls to it   wasted   peak after 4 s  after 4.5 s
no retry                               75.0%         1600        0         20/100ms       100.0%
3 attempts, at once                    75.0%         2402        0         22/100ms       100.0%
5 attempts, doubling pause             45.7%         6165     1609        102/100ms        30.1%
5 attempts, doubling, jitter           56.8%         5336     1236        106/100ms        42.3%
5, doubling, jitter, budget 10 %       75.0%         1649        0         20/100ms       100.0%
```

- **Sans tentative** : les 25 % de requêtes arrivées pendant la panne
  échouent, les autres réussissent ; à 4,5 s, tout est rétabli.
- **Trois essais tout de suite** : rien de gagné. Pendant la panne, les
  trois essais tombent dans la même seconde, sur un service qui répond
  toujours `503`.
- **Cinq essais, pause qui double** (100, 200, 400, 800 ms) : **pire que
  rien**. Les tentatives de la panne retombent toutes **après** elle,
  en plus du trafic normal : le service reçoit jusqu'à 102 appels par
  100 ms pour une capacité de 30, sa file s'allonge, les appels
  dépassent leurs 300 ms, sont abandonnés, réessayés. 1 609 requêtes
  sont traitées pour personne, et **une demi-seconde après la panne,
  seules 30 % des requêtes réussissent** : la panne de deux secondes en
  dure huit.
- **Avec du hasard** : à peine mieux (42 % après la panne, et 18 % lors
  d'une autre exécution). Le hasard étale les tentatives, il ne les
  **réduit** pas : 5 336 appels pour 1 600 requêtes.
- **Avec un budget de 10 %** : 1 649 appels, rien de gâché, et **100 %**
  après la panne. Quand tout échoue, les tentatives s'arrêtent d'elles-
  mêmes.

Le livre SRE de Google recommande les deux : des pauses exponentielles
au hasard, **et** un budget de tentatives par serveur. La Builders' Library d'AWS
résume la raison : les nouvelles tentatives sont égoïstes ; elles
demandent au service de dépenser plus pour leur requête.

## 4. Mesure : le service qui se tait

Un service en panne qui répond `503` est un bon service en panne. Le pire
est celui qui **ne répond plus**. `cmd/hang` envoie 200 requêtes par
seconde pendant 6 s à un service qui se tait de 1 s à 4 s :

```text
200 requests per second for 6 s; the service hangs from 1 s to 4 s

                               succeeded      p50      p99  max waiting   calls to it
timeout 10 s                       50.0%      10s  10.001s          602          1200
timeout 300 ms                     50.0%    300ms    301ms           61          1200
timeout 300 ms, breaker            44.1%       0s    301ms           61           599
```

- **Un délai de 10 s** : les requêtes de la panne attendent toutes 10 s.
  **602 requêtes attendent en même temps** (200 par seconde × 3 s, la loi
  de Little de la leçon 9.1) : autant de goroutines, de connexions, de
  mémoire, et un écran qui tourne 10 s. Sans délai du tout (le
  `http.Client` de Go par défaut), elles attendraient la fin du monde.
- **Un délai de 300 ms** : même taux de succès, mais une requête de la
  panne échoue en 300 ms, et 61 attendent au plus.
- **Un délai et un coupe-circuit** : après 5 échecs de suite, le
  coupe-circuit s'ouvre ; les requêtes suivantes échouent **en moins
  d'une milliseconde**, sans appeler le service (599 appels au lieu de
  1 200). Toutes les 200 ms, un seul appel teste le service. Le prix :
  quelques requêtes échouent juste après le rétablissement, le temps
  qu'une sonde le constate (44 % de succès au lieu de 50 %).

```go
func (b *Breaker) allow() (probe, ok bool) {
    b.mu.Lock()
    defer b.mu.Unlock()
    if !b.open {
        return false, true
    }
    if time.Since(b.openedAt) < b.Cooldown || b.probing {
        return false, false
    }
    b.probing = true // half open: one call tests the service
    return true, true
}
```

Michael Nygard a popularisé ce motif dans *Release It!* ; Martin Fowler
le décrit : l'appel protégé est enveloppé dans un objet qui surveille les
échecs, et qui, passé un seuil, renvoie une erreur sans plus appeler.

## 5. La campagne

Huit mutations, dans les tentatives et le coupe-circuit :

```text
pas de hasard                                tuee
pause constante                              tuee
débordement de la pause                      tuee
budget ignoré                                tuee
erreur permanente réessayée                  tuee
budget sans plafond                          tuee
plusieurs sondes                             tuee
compteur jamais remis à zéro                 tuee
8/8 tuees
```

Le premier passage avait deux survivantes. « Un budget sans plafond » :
un budget qui accumule pendant une semaine calme libère des centaines de
tentatives le jour de la panne ; le test ajouté fait 1 000 requêtes
réussies, puis 100 qui échouent. « Une sonde ratée ignorée » était
**équivalente** : le compteur d'échecs n'est jamais remis à zéro en
s'ouvrant, donc une sonde ratée le garde au-dessus du seuil. La condition
redondante a été retirée du code, avec un commentaire.

## 6. La grille

| Pour chaque appel à un service | À vérifier |
|---|---|
| le délai | présent, plus court que le budget de l'écran (leçon 6.6) ; jamais le client HTTP par défaut |
| les tentatives | peu (3 à 5), pause exponentielle au hasard, et seulement pour les erreurs passagères |
| le budget | les tentatives plafonnées en proportion du trafic (10 %) |
| les écritures | réessayées seulement avec une clé d'idempotence (leçon 6.3) |
| le coupe-circuit | sur les appels qui peuvent se taire ; une réponse de repli quand il est ouvert |
| les couches | une seule couche réessaie : sinon, 3 couches × 3 essais = 27 appels |

## 7. Les trois erreurs qui restent

### « On réessaie trois fois, c'est plus robuste »

Robuste pour une erreur isolée (un paquet perdu). Pour une panne, c'est
trois fois la charge sur un service qui tombe. La section 3 le montre :
les tentatives ont transformé une panne de deux secondes en huit secondes
de service dégradé.

### « Chaque couche réessaie, par sécurité »

L'application réessaie 3 fois le service des prêts, qui réessaie 3 fois
l'opérateur, qui réessaie 3 fois sa base : un échec de la base devient 27
requêtes. Le livre SRE de Google le dit : limiter les tentatives par
requête, et ne réessayer qu'à **un seul** niveau.

### « Le coupe-circuit règle les pannes »

Il règle l'attente, pas la panne : les requêtes échouent quand même,
plus vite. Il faut décider ce que voit le membre quand il est ouvert : une
réponse de repli (« le score de prêt est indisponible, réessayez dans une
minute »), une valeur en cache, ou une fonction dégradée.

## 8. Le lien avec la production

- **Les métriques** : par service appelé, le taux d'échec, la latence, le
  nombre de tentatives, l'état du coupe-circuit. Un coupe-circuit qui
  s'ouvre est une alerte.
- **Les délais en cascade** : l'écran a 800 ms ; il appelle les prêts
  avec 600 ms ; les prêts appellent l'opérateur avec 400 ms. Un appel
  plus long que celui qui l'attend travaille pour personne. Le contexte
  Go transporte le délai restant : `context.WithTimeout` sur un contexte
  qui a déjà un délai garde le plus court.
- **Les bibliothèques** : le motif est assez simple pour être écrit (cette
  leçon), mais une bibliothèque éprouvée évite les erreurs fines
  (comptage par fenêtre, état partagé entre instances).

## 9. Ce qu'il faut retenir

1. Un délai sur chaque appel.
2. Peu de tentatives, espacées, au hasard, et dans un budget.
3. Le hasard étale ; seul le budget borne.
4. Un coupe-circuit pour ce qui peut se taire, et une réponse de repli.
5. Une seule couche réessaie.

## 10. Approfondissement

### Pourquoi le hasard aide quand même

Sans hasard, toutes les requêtes tombées à la même seconde réessaient à
la même milliseconde, 100 ms plus tard, puis 200 ms, puis 400 ms : des
vagues. Le hasard les étale sur toute la fenêtre. Dans la mesure, il ne
suffit pas parce que le **volume** total dépasse la capacité ; quand le
volume tient, le hasard évite qu'une vague synchronisée sature le
service un court instant.

### Le délai de la première tentative

Un délai trop court échoue sur des requêtes qui auraient réussi, et les
réessaie : il ajoute de la charge. On le règle au-dessus du 99e centile
normal du service (ici, 20 ms ; 300 ms laisse de la place), et on le
revoit quand ce centile change.

## 11. Le réflexe à installer

Devant chaque appel à un service, demande-toi :

1. Quel délai, et est-il plus court que celui qui m'attend ?
2. Quelles erreurs réessayer, combien de fois, avec quelle pause ?
3. Que devient le service si tous mes appels réessaient en même temps ?
4. Que voit le membre quand le service se tait ?
5. Qui d'autre, en amont ou en aval, réessaie déjà ?
