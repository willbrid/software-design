# Leçon 9.5 — La sécurité dans la conception : à qui est cet objet, qui m'appelle vraiment, et que peut faire mon code s'il est trompé

## L'essentiel en deux minutes

**Le problème, en une phrase.** Les failles les plus graves d'une API ne
viennent pas d'un chiffrement cassé, mais de trois oublis de conception :
vérifier que l'utilisateur est connecté sans vérifier que l'objet est à
lui, croire un appel parce qu'il arrive à la bonne adresse, et donner au
programme plus de droits qu'il n'en a besoin.

**Trois images.**

- **Le casier de la gare** : la clé du casier 12 ouvre le casier 12, pas
  tous les casiers. Être client de la consigne ne suffit pas.
- **La lettre cachetée et datée** : le cachet prouve qui l'a écrite ; la
  date et le numéro empêchent qu'on la présente deux fois.
- **Le caissier sans clé du coffre** : s'il se fait berner, il ne peut
  donner que ce qui est dans sa caisse.

**Le code, en quelques lignes.** L'API vérifie, pour **chaque objet**
demandé, que le porteur du jeton y a droit :

```go
// May says whether the bearer of c may read wallet.
func May(c Claims, wallet Wallet) bool {
    return c.Member == wallet.Member || c.Role == "treasurer" && c.Tontine == wallet.Tontine
}
```

**Les règles à retenir.**

1. **Authentifier n'est pas autoriser** : chaque route qui reçoit
   l'identifiant d'un objet vérifie que l'utilisateur y a droit.
2. **Un objet interdit ressemble à un objet absent** (`404`) : ne pas
   confirmer son existence.
3. **Un appel entrant se vérifie** : une signature sur le contenu, un
   horodatage court, et un identifiant qu'on n'accepte qu'une fois.
4. **Une valeur n'est jamais du code** : les requêtes SQL prennent des
   paramètres, jamais des morceaux collés.
5. **Le moindre privilège** : le rôle de la base ne lit que ce dont le
   code a besoin ; s'il est trompé, il ne peut pas plus.

La suite le mesure : 300 portefeuilles, une adresse de confirmation, et
une recherche de membres.

---

Les leçons précédentes supposaient des appelants honnêtes, maladroits au
pire. L'application de tontine déplace de l'argent : certains appelants
chercheront ce qu'ils peuvent lire, payer ou confirmer sans y avoir droit.
Le problème de cette leçon :

> **Quelles décisions de conception empêchent un utilisateur connecté,
> un inconnu sur Internet, ou un champ de recherche, d'aller au-delà de
> ce qui lui revient ?**

Le module de la leçon est `l95`. Il utilise la bibliothèque standard, et
le PostgreSQL 17 du niveau 5 (`sd-pg`, port 55432) pour la section 4. Tout
ce qui suit est mesuré sur un module vert sous `gofmt -l`, `go vet ./...`
et `go test -race -count=1 ./...`.

## 1. Le jeton dit qui, pas quoi

Les membres se connectent ; un jeton signé (leçon 9.1) dit qui ils sont,
dans quelle tontine, avec quel rôle. L'API sert les portefeuilles :

```go
// Handler returns the routes.
func (a *API) Handler() http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /wallets/{member}", func(w http.ResponseWriter, r *http.Request) {
        c, ok := a.Tokens.Check(strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer "))
        if !ok {
            http.Error(w, "who are you?", http.StatusUnauthorized)
            return
        }
        wallet, found := a.Store[r.PathValue("member")]
        if a.CheckOwner && found && !May(c, wallet) {
            found = false // answer as if it did not exist: no hint for the curious
        }
        if !found {
            http.NotFound(w, r)
            return
        }
        json.NewEncoder(w).Encode(wallet)
    })
    return mux
}
```

## 2. Mesure : lire les portefeuilles des autres

`cmd/bola` crée 300 portefeuilles dans 10 tontines. Le membre `m007`, avec
un jeton parfaitement valide, demande `/wallets/m000` à `/wallets/m299` ;
puis la trésorière de la tontine `t3` fait de même :

```text
300 wallets in 10 tontines; each bearer asks for all 300

API                                  bearer                     wallets read
logged in is enough                  member m007 of t7                 300
logged in is enough                  treasurer m003 of t3              300
owner, or treasurer of its tontine   member m007 of t7                   1
owner, or treasurer of its tontine   treasurer m003 of t3               30
```

- **« Connecté suffit » : le membre lit les 300 portefeuilles**, avec le
  numéro de téléphone et le solde de chacun. Il n'a rien forcé : il a
  changé un nombre dans l'adresse.
- **Avec le contrôle par objet** : le membre lit le sien, la trésorière
  les 30 de sa tontine.

L'OWASP place cette faille en tête de son classement des risques des API
(*Broken Object Level Authorization*) : chaque route qui reçoit
l'identifiant d'un objet doit vérifier que l'utilisateur connecté a le
droit d'agir sur cet objet. Le contrôle ne se fait pas « à l'entrée de
l'API », mais **à chaque objet**, là où l'objet est chargé.

Un portefeuille interdit répond `404`, comme un portefeuille absent : un
`403` confirmerait au curieux que `m042` existe.

## 3. Mesure : l'appel qui dit venir de l'opérateur

L'opérateur Mobile Money confirme les paiements en appelant une adresse
de l'application. Cette adresse est publique : n'importe qui peut
l'appeler. `cmd/webhook` envoie, pour trois façons de vérifier, 100 vraies
confirmations, 100 confirmations forgées par quelqu'un qui a trouvé
l'adresse, puis une vraie confirmation capturée, renvoyée 50 fois tout de
suite et 50 fois le lendemain :

```text
receiver checks                      operator   forged replayed at once replayed a day later
nothing                               100/100  100/100            50/50                50/50
the signature                         100/100    0/100            50/50                50/50
signature, time, and id               100/100    0/100             1/50                 0/50
```

- **Sans vérification**, les 100 fausses confirmations sont acceptées :
  100 cotisations de 500 000 FCFA « payées », sans un franc reçu.
- **La signature seule** (un HMAC du contenu avec un secret partagé)
  arrête les fausses, mais **pas les copies** : une vraie confirmation
  capturée reste vraie, et se rejoue 100 fois.
- **Signature, horodatage et identifiant** : l'horodatage est signé avec
  le contenu et doit avoir moins de 5 minutes ; l'identifiant de la
  confirmation, signé lui aussi, n'est accepté qu'une fois. La copie
  passe une fois (c'est l'originale), puis plus jamais.

```go
// Sign returns the signature the operator puts in X-Signature: an HMAC of
// the timestamp and the body.
func Sign(secret []byte, timestamp string, body []byte) string {
    m := hmac.New(sha256.New, secret)
    m.Write([]byte(timestamp))
    m.Write([]byte("."))
    m.Write(body)
    return hex.EncodeToString(m.Sum(nil))
}
```

La comparaison des signatures passe par `hmac.Equal`, qui compare sans
révéler, par le temps qu'elle met, combien de caractères sont justes.

## 4. Mesure : le champ de recherche qui parle SQL

L'écran de la trésorière cherche les membres par nom. La première version
colle le texte tapé dans la requête :

```go
// Concatenated builds the query by pasting q into it.
func Concatenated(ctx context.Context, pool *pgxpool.Pool, q string) ([]Result, error) {
    rows, err := pool.Query(ctx, "SELECT id, name FROM members WHERE name ILIKE '%"+q+"%' ORDER BY id")
    if err != nil {
        return nil, err
    }
    return pgx.CollectRows(rows, pgx.RowToStructByPos[Result])
}
```

`cmd/inject` tape trois recherches, sur 200 membres, de trois façons : la
requête collée, exécutée par le propriétaire des tables ; la même,
exécutée par un rôle qui ne peut lire que l'identifiant et le nom ; la
requête avec un paramètre :

```text
200 members; three searches typed in the treasurer's screen

typed: Member 12
  pasted, as the owner            11 rows,   0 secrets leaked
  pasted, as a role for names     11 rows,   0 secrets leaked
  parameter, as the owner         11 rows,   0 secrets leaked
typed: x' UNION SELECT id, phone FROM members --
  pasted, as the owner           200 rows, 200 secrets leaked
  pasted, as a role for names    error: ERROR: permission denied for table members (SQLSTATE 42501)
  parameter, as the owner          0 rows,   0 secrets leaked
typed: x' UNION SELECT id, pin_hash FROM members --
  pasted, as the owner           200 rows, 200 secrets leaked
  pasted, as a role for names    error: ERROR: permission denied for table members (SQLSTATE 42501)
  parameter, as the owner          0 rows,   0 secrets leaked
```

- **Collée, en propriétaire : les 200 numéros de téléphone sortent**, puis
  les 200 empreintes de code PIN. Le texte tapé a fermé la chaîne,
  ajouté un `UNION`, et mis le reste en commentaire.
- **Collée, avec un rôle limité** : PostgreSQL refuse (`permission denied`).
  L'injection est toujours là, mais le rôle ne peut lire que ce qu'il
  doit afficher : c'est le **moindre privilège**, une seconde ligne de
  défense.
- **Avec un paramètre** : rien ne sort. Le texte est envoyé à part, comme
  une **valeur** ; il ne devient jamais du SQL. C'est la vraie
  correction ; elle traite aussi le membre qui s'appelle `O'Neil`.

L'aide-mémoire de l'OWASP sur les injections SQL met les requêtes
paramétrées en première défense, et le moindre privilège parmi les
défenses en profondeur, « pour limiter les dégâts » d'une injection
réussie.

## 5. La campagne

Neuf mutations, dans l'autorisation, la vérification des appels et la
recherche :

```text
pas de contrôle par objet                    tuee
trésorière de toutes les tontines            tuee
403 qui confirme l'existence                 tuee
jeton non vérifié                            tuee
horodatage non signé                         tuee
horodatage futur accepté                     tuee
pas de mémoire des identifiants              tuee
paramètre recollé                            tuee
rôle qui lit tout                            tuee
9/9 tuees
```

Toutes sont tuées. Deux méritent un mot : « 403 qui confirme
l'existence » est tuée par un test qui demande que l'objet d'un autre et
l'objet absent répondent pareil ; « horodatage futur accepté » par un test
qui envoie un horodatage six minutes dans le futur, qu'un attaquant
utiliserait pour prolonger la vie d'une copie.

## 6. La grille

| Pour chaque route et chaque appel | À vérifier |
|---|---|
| un identifiant d'objet dans la requête | une vérification d'autorisation sur cet objet, testée pour un autre utilisateur |
| la réponse à un objet interdit | `404`, comme un objet absent |
| un appel entrant (webhook) | signature HMAC sur le contenu et l'horodatage, fenêtre courte, identifiant accepté une fois, `hmac.Equal` |
| une requête SQL | des paramètres, jamais de texte collé ; même pour un tri ou un nom de colonne (liste fermée) |
| le rôle de la base | ne lit et n'écrit que ce dont le service a besoin ; jamais le propriétaire des tables |
| les secrets | dans un coffre, pas dans le code ni les journaux (leçon 9.4) |

## 7. Les trois erreurs qui restent

### « L'utilisateur est connecté, il a le droit »

300 portefeuilles lus par un membre honnête qui a changé un nombre. La
connexion dit **qui** ; seul le contrôle par objet dit **quoi**. Il se
teste comme le reste : un test par route, avec le jeton d'un autre
membre.

### « Personne ne connaît l'adresse du webhook »

Les adresses se devinent, se trouvent dans les journaux d'un serveur
intermédiaire, ou dans le code d'une application mobile. Une adresse
n'est pas un secret ; le secret partagé avec l'opérateur, si.

### « On échappe les guillemets »

Échapper, c'est écrire soi-même un analyseur SQL, et le tenir à jour
pour chaque encodage et chaque cas particulier. L'OWASP le décourage
fortement. Le paramètre ne demande rien de tout cela : la valeur ne passe
jamais par l'analyseur.

## 8. Le lien avec la production

- **Les tests d'autorisation** : une table route × rôle × propriétaire
  (le sien, celui d'un autre, celui d'une autre tontine), jouée dans la
  chaîne d'intégration. Une nouvelle route sans sa ligne fait échouer la
  chaîne.
- **Les secrets** du webhook et des jetons se renouvellent : accepter
  l'ancien et le nouveau pendant la bascule, puis retirer l'ancien.
- **Les rôles de la base** se déclarent avec les migrations (leçon 7.5 :
  un rôle par module) ; une revue refuse un `GRANT ALL`.
- **Les journaux** ne contiennent ni code PIN, ni jeton, ni pièce
  d'identité ; un filtre sur les champs sensibles est plus sûr que la
  discipline de chacun.

## 9. Ce qu'il faut retenir

1. Authentifier n'est pas autoriser : un contrôle par objet.
2. Un objet interdit répond comme un objet absent.
3. Un appel entrant : signé, daté, unique.
4. Une valeur n'est jamais du SQL.
5. Le moindre privilège limite ce qu'une erreur peut coûter.

## 10. Approfondissement

### Modéliser les menaces, simplement

Avant d'écrire une route, quatre questions suffisent souvent : qui peut
l'appeler ? avec quels identifiants d'objets ? que se passe-t-il si
l'appel est rejoué ? que peut faire ce code s'il est trompé ? Les trois
sections de mesure de cette leçon répondent chacune à l'une d'elles.

### L'autorisation dans la base

PostgreSQL sait filtrer les lignes par utilisateur (*row level
security*) : une politique qui ne laisse voir que les portefeuilles de la
tontine du rôle courant. C'est une seconde ligne de défense pour le
contrôle par objet, comme le rôle limité l'est pour l'injection ; elle
demande que chaque requête porte l'identité du membre jusqu'à la base.

## 11. Le réflexe à installer

Devant chaque route, demande-toi :

1. Quel identifiant d'objet reçoit-elle, et qui vérifie qu'il est au
   demandeur ?
2. Que répond-elle pour l'objet d'un autre ?
3. Si l'appel vient de l'extérieur, comment sait-on qui l'envoie, et
   qu'il n'est pas rejoué ?
4. Où un texte reçu pourrait-il devenir du code ?
5. Que pourrait faire ce code avec les droits qu'il a, s'il était trompé ?
