# Leçon 9.6 — Le temps et l'accord : des horloges qui mentent, des baux qui expirent, et des jetons qui protègent

## L'essentiel en deux minutes

**Le problème, en une phrase.** Plusieurs machines ne partagent ni la
même heure, ni la même idée de qui est « le chef » : une écriture
horodatée par une horloge en retard efface une écriture plus récente, et
un programme endormi quelques secondes se réveille en croyant tenir un
verrou qu'un autre a déjà pris.

**Trois images.**

- **Les montres des invités** : à une fête, chacun a sa montre ; « le
  dernier arrivé » selon les montres n'est pas forcément le dernier
  arrivé. Seul le portier, qui note les arrivées dans l'ordre, le sait.
- **La clé de la salle, prêtée pour une heure** : passé l'heure, le
  gardien la prête à un autre. Celui qui s'est endormi avec l'ancienne
  ne doit plus pouvoir entrer.
- **Le numéro de ticket** : le gardien numérote chaque prêt. La porte
  refuse un ticket plus petit que le dernier qu'elle a vu. C'est le
  **jeton de clôture**.

**Le code, en quelques lignes.** La passerelle des SMS refuse tout envoi
signé d'un jeton plus ancien que le plus récent qu'elle a vu :

```go
// Send sends the statement of member, on behalf of the holder of token.
func (g *Gateway) Send(token int64, member string) error {
    g.mu.Lock()
    defer g.mu.Unlock()
    if g.Fenced {
        if token < g.highest {
            return ErrFenced
        }
        g.highest = token
    }
    if g.sent == nil {
        g.sent = map[string]int{}
    }
    g.sent[member]++
    g.log = append(g.log, Delivery{token, member})
    return nil
}
```

**Les règles à retenir.**

1. **On ne compare pas des heures de machines différentes** pour décider
   d'un ordre : l'ordre se demande à un seul endroit (la base, une
   séquence, une version).
2. **Une durée se mesure à l'horloge monotone**, une date se lit à
   l'horloge murale ; les deux ne se mélangent pas.
3. **Un verrou distribué est un bail** : il expire, et son détenteur peut
   ne pas le savoir.
4. **Ce que protège un bail se protège aussi par un jeton de clôture** :
   un numéro qui grandit à chaque détenteur, vérifié par celui qui reçoit
   les écritures.
5. **Les expirations se lisent sur une seule horloge**, celle de la base.

La suite le mesure avec deux instances et un PostgreSQL 17.

## 1. Mesure : la dernière écriture selon qui ?

Un membre change son numéro de téléphone depuis deux appareils ;
l'application tourne sur deux instances, A et B. Deux façons de garder la
dernière valeur :

```go
// Write offers value, stamped at by the writer's clock.
func (r *LastWriteWins) Write(value string, at time.Time) {
    r.mu.Lock()
    defer r.mu.Unlock()
    if at.After(r.at) {
        r.value, r.at = value, at
    }
}
```

```go
// Write records value and returns its version.
func (r *Versioned) Write(value string) int64 {
    r.mu.Lock()
    defer r.mu.Unlock()
    r.version++
    r.value = value
    return r.version
}
```

`cmd/skew` envoie 1 000 mises à jour, une toutes les 500 ms, depuis l'une
ou l'autre instance au hasard ; l'horloge de A retarde de 0, 400 ms, puis
2 s :

```text
1,000 updates, one every 500 ms, from two instances at random

register                             updates lost  final value right
latest timestamp, A behind by 0s                0               true
latest timestamp, A behind by 400ms              0               true
latest timestamp, A behind by 2s              473               true
the store's order                               0               true
```

- **Un retard de 400 ms ne fait rien perdre** : les écritures sont
  espacées de 500 ms, plus que le décalage.
- **Un retard de 2 s fait perdre 473 mises à jour sur 1 000** : chaque
  écriture de A qui suit de moins de 2 s une écriture de B porte une heure
  plus ancienne, et la règle « la plus récente gagne » la jette. Le membre
  a changé de numéro ; l'application garde l'ancien.
- **L'ordre de la base** ne perd rien : elle numérote les écritures dans
  l'ordre où elle les reçoit.

Un décalage de deux secondes n'a rien d'exceptionnel : une machine
virtuelle qui redémarre, un service de synchronisation arrêté, un
conteneur dont l'hôte dérive. Leslie Lamport l'a posé dès 1978 : dans un
système réparti, il est parfois impossible de dire lequel de deux
événements s'est produit le premier ; « arrivé avant » n'est qu'un ordre
partiel. Un ordre total se **fabrique**, à un endroit qui voit tout passer.

## 2. Deux horloges dans chaque machine

Go le dit dans la documentation du paquet `time` : le système fournit une
horloge **murale**, qui peut être réglée (et sauter en avant ou en
arrière), et une horloge **monotone**, qui ne recule jamais. La première
sert à dire l'heure, la seconde à mesurer une durée. `time.Now()` porte
les deux ; `time.Since` et `Sub` utilisent la monotone. Une durée calculée
à partir d'heures **sérialisées** (écrites dans une base, envoyées sur le
réseau) a perdu la monotone : elle peut être négative après un réglage.

PostgreSQL a la même distinction : `now()` rend l'heure du **début de la
transaction**, la même pendant toute la transaction, et
`clock_timestamp()` l'heure réelle. Pour un bail, c'est `now()` qu'on
veut : une seule horloge, celle de la base, et une heure stable dans la
transaction.

## 3. Le bail

Le relevé mensuel est envoyé par un seul travailleur à la fois. Un bail
dans PostgreSQL dit qui le tient, jusqu'à quand, et avec quel **jeton** :

```go
// Acquire takes the lease name for holder for ttl, if it is free,
// expired, or already holder's, and returns the token of this holding: a
// new holder gets a greater token than every holder before.
func Acquire(ctx context.Context, pool *pgxpool.Pool, name, holder string, ttl time.Duration) (int64, error) {
    if _, err := pool.Exec(ctx, `INSERT INTO leases (name) VALUES ($1) ON CONFLICT DO NOTHING`, name); err != nil {
        return 0, err
    }
    var token int64
    err := pool.QueryRow(ctx, `
        UPDATE leases
        SET token = CASE WHEN holder = $2 AND expires_at > now() THEN token ELSE token + 1 END,
            holder = $2, expires_at = now() + $3::interval
        WHERE name = $1 AND (expires_at <= now() OR holder = $2)
        RETURNING token`, name, holder, ttl).Scan(&token)
    if errors.Is(err, pgx.ErrNoRows) {
        return 0, ErrHeld
    }
    return token, err
}
```

Le travailleur renouvelle son bail tous les 20 relevés, et le perd s'il
ne le renouvelle pas à temps. Un second travailleur attend en réserve, et
le prend quand il expire :

```go
// Run works until the job is done, the lease is lost, or the gateway
// refuses the worker's token.
func (w *Worker) Run(ctx context.Context) (sent int, err error) {
    token, err := lease.Acquire(ctx, w.Pool, "statements", w.Name, w.TTL)
    if err != nil {
        return 0, err
    }
    for n := 0; ; n++ {
        if n > 0 && n%w.RenewEvery == 0 {
            if token, err = lease.Acquire(ctx, w.Pool, "statements", w.Name, w.TTL); err != nil {
                return sent, err
            }
        }
        var next int
        if err := w.Pool.QueryRow(ctx, `SELECT next FROM job`).Scan(&next); err != nil {
            return sent, err
        }
        if next >= w.Members {
            return sent, nil
        }
        if next == w.PauseAt && w.Pause > 0 {
            time.Sleep(w.Pause)
            w.Pause = 0
        }
        if err := w.Gateway.Send(token, fmt.Sprintf("m%03d", next)); err != nil {
            return sent, err
        }
        sent++
        if _, err := w.Pool.Exec(ctx, `UPDATE job SET next = $1`, next+1); err != nil {
            return sent, err
        }
        time.Sleep(time.Millisecond)
    }
}
```

## 4. Mesure : le travailleur qui s'endort

`cmd/pause` envoie les relevés de 300 membres. A tient le bail (300 ms) ;
au membre 100, il s'arrête 600 ms (un ramasse-miettes très long, une
machine virtuelle déplacée, un portable refermé). B prend le bail expiré
et continue. A se réveille :

```text
300 statements; A pauses 600 ms at member 100; lease of 300 ms, renewed every 20 statements

gateway                  A sent   B sent    members   sent twice  A stopped by
sends whatever it gets      120      263        300           74  lease held by another worker
fenced by the token         100      200        300            0  stale token: a newer holder has taken over
```

- **Sans clôture : 74 membres reçoivent leur relevé deux fois** dans
  cette exécution ; d'autres exécutions en donnent entre 11 et 68, selon
  la façon dont A et B se croisent dans la table du travail. Ce qui ne
  varie pas : A se réveille, ne sait pas qu'il a perdu le bail, et envoie
  **20 relevés** jusqu'à son prochain renouvellement (la colonne
  « A sent » dit 120, soit 100 + 20), pendant que B travaille. Le bail a
  fait exactement ce qu'il devait : il a expiré. C'est A qui ne l'a pas
  su.
- **Avec un jeton de clôture : aucun double.** B a pris le bail avec le
  jeton 2 ; la passerelle a vu passer ce jeton ; le premier envoi de A,
  signé du jeton 1, est refusé, et A s'arrête aussitôt.

Martin Kleppmann décrit précisément ce scénario dans *How to do
distributed locking* : une pause du ramasse-miettes plus longue que le
bail, et un client qui ne se rend pas compte de l'expiration. Sa
correction est celle de la mesure : un jeton qui grandit à chaque
acquisition, joint à chaque écriture, et vérifié par le service qui
reçoit les écritures.

Le jeton déplace la vérification **là où l'écriture a lieu**. Vérifier le
bail avant d'écrire ne suffit pas : entre la vérification et l'écriture,
le programme peut encore s'endormir.

## 5. La campagne

Sept mutations, dans le bail, la passerelle, le registre et le
travailleur :

```text
jeton qui ne grandit pas                     tuee
bail pris de force                           tuee
renouvellement qui change le jeton           tuee
clôture d'un cran trop large                 tuee
plus haut jeton oublié                       tuee
dernier arrivé gagne                         tuee
jamais de renouvellement                     tuee
7/7 tuees
```

« Jamais de renouvellement » survivait au premier passage : avec la
clôture, un travailleur qui ne renouvelle pas est arrêté proprement, et
aucun test ne voyait la différence. Le test ajouté lance un travail plus
long que le bail, avec un second travailleur en réserve : celui qui
renouvelle garde le travail jusqu'au bout.

## 6. La grille

| Quand des machines doivent s'accorder | À vérifier |
|---|---|
| l'ordre des écritures | donné par un seul endroit (version, séquence, base), jamais par les horloges des écrivains |
| les durées | mesurées à l'horloge monotone ; jamais par différence d'heures sérialisées |
| les expirations | lues sur l'horloge de la base (`now()`), pas sur celle de chaque machine |
| un verrou entre machines | un bail avec une expiration, renouvelé bien avant elle |
| ce que le bail protège | un jeton de clôture joint à chaque écriture, vérifié par le récepteur |
| le pire cas | un détenteur qui s'endort plus longtemps que le bail : que se passe-t-il ? |

## 7. Les trois erreurs qui restent

### « Nos serveurs sont synchronisés par NTP »

Ils le sont, à quelques millisecondes près, la plupart du temps. Le jour
où le service s'arrête sur une machine, ou qu'une machine virtuelle
reprend après une pause, l'écart se compte en secondes, et la règle « la
plus récente gagne » perd des écritures sans erreur. La mesure en perd
473 sur 1 000 avec 2 s.

### « Le verrou est dans Redis (ou PostgreSQL), il est sûr »

Le verrou est sûr ; son **détenteur** ne l'est pas. Il peut s'endormir
après l'avoir vérifié. Aucun service de verrou ne peut empêcher un
programme endormi d'écrire en se réveillant ; seul le récepteur de
l'écriture le peut, avec un jeton.

### « On allonge le bail pour être tranquille »

Un bail d'une heure rend la pause rare, et la reprise lente : si le
détenteur meurt vraiment, le travail attend une heure. Et une pause plus
longue qu'une heure reste possible. On garde un bail court, renouvelé
souvent, et la clôture pour le cas rare.

## 8. Le lien avec la production

- **Le relais de l'outbox élu** (leçon 8.2) et le projecteur (leçon 8.4)
  sont des travailleurs uniques : un bail avec jeton, ou un verrou
  consultatif de PostgreSQL tenu par la session (`pg_try_advisory_lock`),
  libéré si la connexion tombe.
- **Le jeton dans les écritures** : une colonne `fence` dans la table
  écrite, et `UPDATE ... WHERE fence <= $token` ; un service externe qui
  ne connaît pas les jetons ne peut pas être protégé ainsi, et demande
  une clé d'idempotence (leçon 6.3) à la place.
- **Les heures dans les journaux** (leçon 9.4) viennent de chaque machine
  et peuvent être décalées : l'ordre d'une trace vient des liens entre
  étapes, pas des heures.
- **Une alerte sur le décalage d'horloge** de chaque machine (au-delà de
  100 ms) coûte peu et explique beaucoup d'incidents étranges.

## 9. Ce qu'il faut retenir

1. Un ordre se demande à un seul endroit, jamais aux horloges des
   écrivains.
2. Horloge monotone pour les durées, murale pour les dates.
3. Un verrou entre machines est un bail, qui expire sans prévenir.
4. Un jeton de clôture, vérifié là où l'on écrit.
5. Les expirations se lisent sur une seule horloge.

## 10. Approfondissement

### Les horloges logiques

Lamport propose de remplacer l'heure par un compteur : chaque machine
l'augmente à chaque événement, et le porte dans ses messages ; qui reçoit
un compteur plus grand que le sien saute à lui. On obtient un ordre
compatible avec « arrivé avant », sans aucune horloge. La version de la
section 1 en est le cas le plus simple : un compteur tenu par un seul
endroit.

### Le consensus

Élire un chef parmi plusieurs machines, sans point central, et sans
jamais en avoir deux, est le problème du **consensus** (Raft, Paxos).
Il est résolu par des outils éprouvés (etcd, ZooKeeper, et PostgreSQL
lui-même pour ses réplicas). Le bon réflexe est de s'appuyer sur l'un
d'eux, ici la base, plutôt que d'en écrire un : la leçon montre déjà ce
qu'il faut ajouter (le jeton) même quand l'outil est juste.

## 11. Le réflexe à installer

Devant chaque décision qui dépend du temps ou d'un chef, demande-toi :

1. Quelle horloge dit l'heure, et est-ce la même pour tous ?
2. Qui donne l'ordre des écritures ?
3. Si ce programme s'endort dix secondes ici, que se passe-t-il à son
   réveil ?
4. Qui reçoit l'écriture, et peut-il refuser un détenteur périmé ?
5. Que coûte un bail trop court, et un bail trop long ?
