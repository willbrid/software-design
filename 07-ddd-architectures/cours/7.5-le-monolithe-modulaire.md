# Leçon 7.5 — Le monolithe modulaire : des frontières tenues, dans un seul programme

## L'essentiel en deux minutes

**Le problème, en une phrase.** Les contextes de la leçon 7.2 sont des
frontières de sens ; si rien ne les tient, un développeur pressé finit
par importer le code interne d'un autre module, ou par lire ses tables
d'une requête, et la frontière n'existe plus que dans le schéma
d'architecture.

**Trois images.**

- **La maison et ses pièces** : une seule maison, un seul toit, une seule
  adresse ; mais chaque pièce a sa porte, et la cuisine ne passe pas par
  le mur de la chambre pour prendre une chaise.
- **Le guichet entre deux services** : le service des paiements répond à
  une question au guichet ; il ne laisse personne fouiller ses tiroirs.
- **La clé de chaque pièce** : la porte se ferme à clé ; ce n'est pas un
  panneau « prière de ne pas entrer ».

**Le code, en quelques lignes.** Le compilateur de Go refuse qu'un module
importe l'intérieur d'un autre :

```text
package example/modular75/modules/tontines
        modules/tontines/shortcut.go:6:2: use of internal package example/modular75/modules/payments/internal/ledger not allowed
```

**Les règles à retenir.**

1. **Un monolithe modulaire** est un seul programme, un seul déploiement,
   avec des frontières **imposées** entre ses modules.
2. **Chaque module a une face publique** (son paquet de premier niveau)
   et un intérieur (`internal/`) que le compilateur protège.
3. **Les dépendances entre modules sont déclarées et vérifiées** par un
   test ; le mieux est qu'un module déclare l'interface dont il a besoin,
   et que `main` branche.
4. **Chaque module a ses tables**, dans son schéma, avec son rôle
   PostgreSQL ; un autre module ne peut pas les lire.
5. **Commencer par un monolithe modulaire** : les frontières se testent
   et se déplacent à peu de frais ; un service se découpe le jour où une
   raison le demande (leçon 7.6).

La suite le mesure : ce qu'un changement touche, ce que le compilateur
refuse, ce que la base refuse.

---

Les leçons 7.2 à 7.4 ont dessiné des contextes, un hexagone, des cercles.
Tout cela vit dans un seul module Go, un seul binaire, une seule base.
Le problème de cette leçon :

> **Comment des frontières tiennent-elles dans un seul programme, sans
> devenir des microservices ?**

Le module de la leçon est `l75`, sur le même PostgreSQL 17. Il contient
deux versions de trois modules (tontines, paiements, prêts) : la
première, où tout se voit (`ball/`), et la version modulaire
(`modules/`). Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. La première version

Les paiements y exposent leur ligne de table et leur lecture :

```go
// LedgerRow is one row of payments.ledger.
type LedgerRow struct {
    Contribution string
    AmountFCFA   int64
    Outcome      string
}
```

Les tontines s'en servent, et ajoutent une jointure « plus rapide » sur
la table des paiements :

```go
// PaidThisRound counts the members of a round whose contribution is paid,
// with one query: faster than asking the payments one by one.
func PaidThisRound(ctx context.Context, pool *pgxpool.Pool, round int) (int, error) {
    var n int
    err := pool.QueryRow(ctx, `SELECT count(*) FROM tontines.contribution c
        JOIN payments.ledger l ON l.contribution = c.id
        WHERE c.round = $1 AND l.outcome = 'confirmed'`, round).Scan(&n)
    return n, err
}
```

Et les prêts lisent les paiements eux-mêmes, pour vérifier les
annulations :

```go
// MayBorrow reports whether a member may ask for a loan.
func MayBorrow(ctx context.Context, pool *pgxpool.Pool, lastContribution string) bool {
    if r, err := payments.Read(ctx, pool, lastContribution); err != nil || r.Outcome == "reversed" {
        return false
    }
    return tontines.UpToDate(ctx, pool, lastContribution)
}
```

Chaque ligne a une bonne raison. Ensemble, trois paquets connaissent la
table des paiements.

## 2. La version modulaire

Chaque module a une **face publique**, son paquet de premier niveau, et
un intérieur. Les paiements gardent leur registre dans `internal/` :

```go
// Schema is the table of the payments module, in the schema of its role:
// the pool of the module connects with search_path set to it.
const Schema = `
```

Et n'offrent que deux fonctions :

```go
// API is what the payments module offers.
type API struct{ ledger ledger.Ledger }
```

```go
// Confirmed reports whether a contribution is paid.
func (a *API) Confirmed(ctx context.Context, contribution string) (bool, error) {
    o, err := a.ledger.Outcome(ctx, contribution)
    return o == "confirmed", err
}
```

Les tontines ne connaissent pas les paiements : elles déclarent la
question dont elles ont besoin, comme dans la leçon 7.2.

```go
// Payments is what the tontines need of the payments module: one question.
// The interface is here, in the module that uses it; the payments module
// does not know the tontines exist.
type Payments interface {
    Confirmed(ctx context.Context, contribution string) (bool, error)
}
```

Seul `main` connaît tous les modules, et les branche :

```go
func main() {
    ctx := context.Background()
    pool, err := pg.Open(ctx, "public", 4)
    if err != nil {
        log.Fatal(err)
    }
    defer pool.Close()
    p := payments.New(pool)
    t := tontines.New(p)
    l := loans.New(t)
    fmt.Println(l != nil)
}
```

Shopify, qui a mené ce chantier sur l'un des plus gros codes Rails
existants, définit le monolithe modulaire ainsi : un système dont tout le
code fait tourner une seule application, avec des frontières **strictement
imposées** entre les domaines.

## 3. Mesure : ce qu'un changement du registre touche

Les paiements veulent changer leur registre : renommer une colonne,
séparer les annulations dans une table à part. `cmd/impact` demande à la
commande `go` quels paquets dépendent du code qui connaît la table, et
cherche les requêtes SQL qui la nomment :

```text
ball     depend on the ledger code: 3 [ball/loans ball/payments ball/tontines]
         write SQL on the ledger: 2 [ball/payments ball/tontines]
modules  depend on the ledger code: 3 [cmd/app modules/payments modules/payments/internal/ledger]
         write SQL on the ledger: 1 [modules/payments/internal/ledger]
```

- **Première version** : les **trois** modules dépendent du code du
  registre, et **deux** écrivent du SQL sur sa table. Renommer une colonne
  demande de changer les tontines, et de prévenir l'équipe des prêts.
- **Version modulaire** : seuls le module des paiements et `main` en
  dépendent, et **une seule** requête nomme la table, dans `internal/`.
  L'équipe des paiements change son registre seule, tant que `Record` et
  `Confirmed` gardent leur sens.

## 4. Mesure : ce que le compilateur refuse

Un développeur des tontines veut aller vite, et lit le registre
directement :

```text
import "example/modular75/modules/payments/internal/ledger"
```

`go build ./...` :

```text
package example/modular75/modules/tontines
        modules/tontines/shortcut.go:6:2: use of internal package example/modular75/modules/payments/internal/ledger not allowed
```

La documentation de la commande `go` le dit : le code d'un répertoire
`internal` ne peut être importé que par le code qui partage le chemin
au-dessus de `internal`. Ce n'est pas une convention : le programme ne
compile pas.

## 5. Mesure : ce que le test d'architecture refuse

`internal/` protège l'intérieur, pas la face publique. Les dépendances
entre modules se déclarent, et se vérifient en test :

```go
// allowed says which modules each module may import (its public package
// only: internal/ is kept by the compiler). The modules of the lesson
// import none: each declares the interface it needs, and main wires them.
var allowed = map[string][]string{
    "tontines": {},
    "payments": {},
    "loans":    {},
}
```

Un développeur des paiements veut rappeler aux membres de payer, et
demande aux tontines qui est à jour : les paiements importent les
tontines. Go accepte (il n'y a pas de cycle), le test non :

```text
--- FAIL: TestModulesImportOnlyWhatTheyAreAllowed (0.03s)
    arch_test.go:41: example/modular75/modules/payments imports example/modular75/modules/tontines: the module payments may not use the module tontines
FAIL
FAIL    example/modular75/modules       0.032s
FAIL
```

Le sens des dépendances entre modules est une décision d'architecture ;
le test la garde. Si la décision change, la table `allowed` change, dans
une revue de code, et pas au détour d'un import.

## 6. Mesure : ce que la base refuse

`cmd/schemas` crée une base neuve, donne à chaque module son schéma et
son rôle, et fait lire à chaque rôle la table de chaque module. La
dernière ligne est la première version : un seul rôle pour toute
l'application.

```text
reads      tontines.t payments.t loans.t   
tontines   yes        DENIED     DENIED    
           (ERROR: permission denied for schema payments (SQLSTATE 42501))
payments   DENIED     yes        DENIED    
loans      DENIED     DENIED     yes       
app        yes        yes        yes       
```

Chaque module ne lit que **son** schéma. La documentation de PostgreSQL
le dit : par défaut, un utilisateur ne peut accéder à aucun objet d'un
schéma qu'il ne possède pas, sauf si le propriétaire lui accorde le
privilège `USAGE`. La jointure « plus rapide » de la première version
échouerait avec `permission denied for schema payments` : pour savoir
qui a payé, les tontines doivent demander aux paiements.

Le pool de chaque module se connecte avec le rôle du module, et son
`search_path` vaut le schéma du module : les requêtes de `internal/`
nomment `ledger`, pas `payments.ledger`.

## 7. La campagne

Trois mutations dans le module des paiements :

```text
payé par exclusion                           tuee
pas de contrainte sur le résultat            tuee
le premier résultat reste                    tuee
3/3 tuees
```

Aucune survivante. La première, « payé par exclusion », est le défaut de
la leçon 7.2 ; elle est tuée ici par un test du **module seul**, qui ne
demande ni les tontines ni les prêts. C'est ce que la frontière rend
possible : chaque module se teste avec ses propres tables, son propre
schéma.

## 8. La grille

| Frontière | Comment la tenir | Ce qui la casse |
|---|---|---|
| l'intérieur d'un module | `internal/` : le compilateur refuse | rien, en Go |
| les dépendances entre modules | une table d'autorisations, un test qui lit les imports | un import non déclaré, que le test signale |
| les tables d'un module | un schéma et un rôle par module | une jointure entre schémas, que PostgreSQL refuse |
| ce qu'un module offre | sa face publique, petite, documentée | une fonction ajoutée « pour un autre module » sans revue |
| le câblage | `main`, seul à connaître tous les modules | un module qui en construit un autre |

## 9. Les trois erreurs qui restent

### « Des modules, c'est déjà des microservices »

Non : un seul binaire, un seul déploiement, des appels de fonction en
nanosecondes, et une transaction possible quand deux modules doivent
écrire ensemble. La frontière est dans le code et dans la base, pas sur
le réseau. Martin Fowler conseille même de ne pas commencer un projet
par des microservices, à cause de leur surcoût.

### « Une jointure entre deux modules, c'est plus rapide »

Plus rapide aujourd'hui, et le jour où les paiements changent leur
table, la requête des tontines casse, et personne aux paiements ne savait
qu'elle existait. Si les tontines ont vraiment besoin de compter les
paiements d'un tour, elles le **demandent** : une fonction
`ConfirmedAmong(ids)` dans la face publique des paiements, qui fait la
requête dans son schéma.

### « Les règles d'architecture, on les connaît »

L'équipe d'aujourd'hui les connaît. Le test de la section 5 les apprend à
la personne qui arrive dans six mois, au moment exact où elle s'apprête à
les enfreindre.

## 10. Le lien avec la production

- **Un rôle par module** : chaque pool a son rôle, avec ses droits sur
  son schéma ; les migrations (leçon 5.4) sont rangées par module, et
  appliquées par le rôle propriétaire du schéma.
- **Les journaux et les métriques portent le module** : un attribut
  `module=payments` sur chaque ligne, pour savoir qui ralentit quoi.
- **La CI** fait tourner le test d'architecture à chaque poussée, et les
  tests de chaque module en parallèle.
- **Un module qui devient service** (leçon 7.6) a déjà sa face publique,
  ses tables, son rôle : il reste à remplacer l'appel de fonction par un
  appel réseau, ce qui n'est pas rien, mais ne demande pas de démêler le
  code d'abord.

## 11. Ce qu'il faut retenir

1. Un monolithe modulaire : un programme, des frontières imposées.
2. `internal/` protège l'intérieur de chaque module ; le compilateur
   refuse le reste.
3. Les dépendances entre modules se déclarent et se testent.
4. Un schéma et un rôle par module : la base refuse les jointures entre
   modules.
5. On commence modulaire ; on découpe en services pour une raison.

## 12. Approfondissement

### Deux modules qui doivent écrire ensemble

Clore un tour (tontines) et enregistrer le versement (paiements) doivent
réussir ou échouer ensemble. Dans un monolithe, une transaction est
possible, mais elle franchit la frontière : le rôle d'une des deux parties
doit écrire dans le schéma de l'autre. Deux réponses : un module écrit un
**événement** dans sa table d'outbox (leçon 5.2), dans sa transaction, et
l'autre le traite ensuite (le niveau 8 le développe) ; ou les deux tables
appartiennent en fait au même module, et la frontière était mal placée.

### Les cycles

Go refuse les cycles d'import entre paquets. Entre modules, un cycle
apparaît souvent par les interfaces : les tontines demandent aux
paiements, et les paiements voudraient rappeler aux tontines. Le test de
la section 5 refuse la seconde dépendance ; la réponse est un
événement (« paiement confirmé ») que les tontines écoutent, au lieu
d'une question que les paiements posent.

## 13. Le réflexe à installer

Avant d'ajouter un import ou une requête qui franchit un module,
demande-toi :

1. Est-ce une question à poser à la face publique de l'autre module ?
2. Le compilateur, le test d'architecture et la base laisseraient-ils
   passer ce raccourci ?
3. Qui saura, dans l'autre équipe, que je dépends de ce que j'utilise ?
4. Si l'autre module devenait un service demain, ce code tiendrait-il ?
5. La frontière est-elle au bon endroit, si deux modules doivent écrire
   ensemble ?
