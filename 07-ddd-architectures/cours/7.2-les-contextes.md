# Leçon 7.2 — Le langage et les contextes délimités : un mot, un sens, une frontière

## L'essentiel en deux minutes

**Le problème, en une phrase.** « Membre » ne veut pas dire la même
chose pour la tontine (quelqu'un qui paie des tours), pour les paiements
(un numéro Mobile Money), pour le contrôle d'identité (une personne avec
une pièce d'identité). Un seul `Member` pour tous finit par porter tout,
et chaque changement de l'un casse les autres.

**Trois images.**

- **Le marché et ses étals** : au marché, « la mesure » veut dire un bol
  pour la vendeuse de riz et un mètre pour le tailleur. Personne ne
  s'en trouble : chaque étal a son langage. Le trouble commence quand on
  veut un seul mot pour tout le marché.
- **Le traducteur à la frontière** : quand on commerce avec un pays
  voisin, on ne se met pas à parler sa langue dans sa propre boutique.
  Un traducteur, à la frontière, convertit ses mots et ses unités dans
  les nôtres.
- **Le mot qu'on ne connaît pas** : un bon traducteur qui entend un mot
  nouveau ne devine pas ; il le note et demande.

**Le code, en quelques lignes.** Le seul paquet qui connaît les mots de
l'opérateur les traduit dans ceux des paiements, et refuse ce qu'il ne
connaît pas :

```go
    switch c.Status {
    case operator.Successful:
        outcome = payments.Confirmed
    case operator.Failed:
        outcome = payments.Failed
    case operator.Reversed:
        outcome = payments.Reversed
    case operator.Pending:
        outcome = payments.Waiting
    default:
        return payments.Event{}, fmt.Errorf("%w %q for %s", ErrUnknownStatus, c.Status, c.TxRef)
    }
```

**Les règles à retenir.**

1. **Un contexte délimité est une frontière où un modèle, et ses mots,
   ont un seul sens** : la tontine, les paiements, l'identité.
2. **Chaque contexte a son propre `Member`**, avec seulement ce dont il a
   besoin. Ce qu'ils partagent, c'est une clé (le numéro), pas un type.
3. **Le langage du domaine** (le *langage omniprésent*) se retrouve dans
   le code : `Confirmed`, `Reversed`, pas `SUCCESSFUL` ni `status == 2`.
4. **Une couche anti-corruption traduit un système extérieur** dans les
   mots du contexte, en un seul endroit, et refuse ce qu'elle ne
   comprend pas.

La suite le mesure avec la version 2 de l'API de l'opérateur Mobile
Money.

---

La leçon 7.1 a mis les règles d'un tour dans son agrégat. Mais une
application de tontines n'a pas qu'un modèle : elle paie par Mobile
Money, contrôle des identités, envoie des SMS. Le problème de cette
leçon :

> **Faut-il un seul modèle pour toute l'application, et que faire des
> mots d'un système qu'on ne contrôle pas ?**

Le module de la leçon est `l72`. Il n'a besoin que de la bibliothèque
standard ; il contient deux versions de la même application, l'une
autour d'un modèle partagé, l'autre découpée en contextes. Tout ce qui
suit est mesuré sur un module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. L'opérateur, et ses mots

Le paquet `operator` est le SDK de l'opérateur Mobile Money : ses noms,
ses formats, ses statuts. Les tontines ne les choisissent pas :

```go
// Callback is what the operator sends when a transaction changes.
type Callback struct {
    TxRef      string `json:"txRef"`
    ExternalID string `json:"externalId"` // the reference we gave: the contribution
    MSISDN     string `json:"msisdn"`     // 237677123456, no plus sign
    Amount     string `json:"amount"`     // "10000.00"
    Currency   string `json:"currency"`
    Status     Status `json:"status"`
}
```

Un numéro sans `+`, un montant en texte avec des centimes, des statuts en
capitales. En octobre 2026, la version 2 de son API ajoute un statut :

```go
// Reversed came with version 2 of the operator's API, in October 2026: a
// successful transaction was cancelled afterwards, and the money went back.
const Reversed Status = "REVERSED"
```

## 2. Le modèle partagé

La première version de l'application a un seul `Member`, partagé par
toutes ses parties. Chacune y a ajouté ce dont elle avait besoin :

```go
// Member is a member, for every part of the application.
type Member struct {
    ID          int64
    Phone       string // as the operator writes it: 237677123456
    Name        string
    Tontines    []int64
    Role        string // member, treasurer
    PaidRounds  map[int64]int
    LastPayment operator.Status // the status of the last Mobile Money payment
    IDCardNo    string          // for the KYC
    IDCardScan  []byte
    BirthDate   string
    KYCStatus   string
    SMSOptIn    bool
    Language    string
    PushToken   string
}
```

Le dernier statut de l'opérateur y est rangé tel quel. Les paiements
l'appliquent :

```go
// Apply records the callback on the member who paid. A payment that did not
// fail counts as paid.
func Apply(m *model.Member, round int64, c operator.Callback) {
    m.LastPayment = c.Status
    if c.Status != operator.Failed && c.Status != operator.Pending {
        m.PaidRounds[round]++
    }
}
```

Et la tontine décide qui est à jour, à sa façon, à partir du même
membre :

```go
// UpToDate reports whether m paid round, and the operator confirmed it.
func UpToDate(m model.Member, round int64) bool {
    return m.PaidRounds[round] > 0 && m.LastPayment == operator.Successful
}
```

Martin Fowler raconte la même histoire avec « client » et « produit » :
autrefois, on conseillait un modèle unifié de toute l'entreprise ; le DDD
reconnaît que ces mots ont plusieurs sens, et qu'il vaut mieux le dire
que le cacher.

## 3. Les contextes

La seconde version découpe l'application en **contextes délimités**.
Eric Evans le définit ainsi : définir explicitement le contexte dans
lequel un modèle s'applique, et ses frontières. Chaque contexte a son
propre membre, réduit à ce qu'il utilise :

```go
// Member is a member of a tontine.
type Member struct {
    Phone string
    Name  string
    Role  string // member, treasurer
}
```

```go
// Person is someone whose identity is checked.
type Person struct {
    Phone      string
    IDCardNo   string
    IDCardScan []byte
    BirthDate  string
    Status     string
}
```

Le contexte des paiements a ses propres mots : un paiement est
**confirmé**, **échoué**, **annulé** ou **en attente**, quoi qu'en dise
l'opérateur :

```go
// Outcome is what happened to a payment, in the words of the tontines.
type Outcome int
```

La tontine ne voit des paiements qu'une question, « cette cotisation
est-elle payée ? » :

```go
// Payments is what the tontines need to know of the payments context.
type Payments interface {
    Confirmed(contribution string) bool
}
```

Entre l'opérateur et les paiements, une **couche anti-corruption**
traduit :

```go
// Translate turns a callback of the operator into an event of the payments
// context.
func Translate(c operator.Callback) (payments.Event, error) {
    var outcome payments.Outcome
    switch c.Status {
    case operator.Successful:
        outcome = payments.Confirmed
    case operator.Failed:
        outcome = payments.Failed
    case operator.Reversed:
        outcome = payments.Reversed
    case operator.Pending:
        outcome = payments.Waiting
    default:
        return payments.Event{}, fmt.Errorf("%w %q for %s", ErrUnknownStatus, c.Status, c.TxRef)
    }
    if c.Currency != "XAF" {
        return payments.Event{}, fmt.Errorf("currency %q for %s", c.Currency, c.TxRef)
    }
    whole, cents, _ := strings.Cut(c.Amount, ".")
    amount, err := strconv.ParseInt(whole, 10, 64)
    if err != nil || strings.Trim(cents, "0") != "" {
        return payments.Event{}, fmt.Errorf("amount %q for %s", c.Amount, c.TxRef)
    }
    return payments.Event{Contribution: c.ExternalID, Phone: "+" + c.MSISDN, AmountFCFA: amount, Outcome: outcome}, nil
}
```

Evans la décrit comme une couche d'isolation qui donne à son système les
fonctions d'un système amont **dans les termes de son propre modèle**.
C'est le seul paquet qui importe `operator`.

## 4. Mesure : qui dépend de quoi

`cmd/coupling` demande à la commande `go` quels paquets dépendent du SDK
de l'opérateur, et de l'endroit où vit la pièce d'identité : ce sont les
paquets à recompiler, à retester, et peut-être à modifier, quand l'un
des deux change.

```text
shared/   depend on the operator's SDK: 5 [shared/kyc shared/model shared/notify shared/payments shared/tontine]
          change with the identity card: 5 [shared/model shared/kyc shared/notify shared/payments shared/tontine]
contexts/ depend on the operator's SDK: 1 [contexts/acl]
          change with the identity card: 1 [contexts/kyc]
```

- **Modèle partagé** : les **cinq** paquets dépendent du SDK de
  l'opérateur, y compris le contrôle d'identité, qui ne paie rien,
  simplement parce que `Member` contient un `operator.Status`. Et les
  cinq changent avec la pièce d'identité, y compris les SMS.
- **Contextes** : **un** seul paquet dépend de l'opérateur, la couche
  anti-corruption. **Un** seul change avec la pièce d'identité.

Un champ ajouté pour un besoin devient une dépendance pour tous. Quand
l'opérateur change son SDK, l'équipe du modèle partagé relit cinq
paquets ; l'équipe des contextes en relit un.

## 5. Mesure : l'annulation

`cmd/reversal` rejoue 1 000 cotisations payées par Mobile Money après la
version 2 : 1,5 % de paiements réussis sont **annulés** ensuite
(`REVERSED`), et un statut que personne n'a annoncé, `EXPIRED`, apparaît
pour 0,5 % d'entre elles.

```text
shared member      counted paid but not paid: 13  paid but not counted: 0  payments and tontines disagree: 13
payments context   counted paid but not paid:  0  paid but not counted: 0  kept aside: map[EXPIRED:6]
```

- **Modèle partagé** : **13 cotisations comptées payées alors que
  l'argent n'est pas là**. Les paiements comptent tout ce qui n'est ni
  `FAILED` ni `PENDING` : `REVERSED` et `EXPIRED` passent pour des
  paiements. Et la tontine, qui lit `LastPayment == SUCCESSFUL`, **n'est
  pas d'accord** avec les paiements sur ces 13 cotisations : le même
  champ du même membre a deux lectures, selon le paquet. La cagnotte
  compte 13 cotisations que l'écran « à jour » ne montre pas.
- **Contextes** : **aucune erreur**. `REVERSED` devient `Reversed`, que le
  registre des paiements sait traiter (l'argent est reparti). `EXPIRED`
  n'est pas deviné : les 6 rappels sont **mis de côté** pour une
  personne, et les cotisations restent non payées tant qu'on ne sait pas.

La couche anti-corruption ne connaissait pas `EXPIRED`, et c'est voulu.
Ce qui protège, c'est qu'elle **refuse l'inconnu** au lieu d'en faire un
succès par défaut, comme la ligne `c.Status != operator.Failed` du
modèle partagé.

## 6. La campagne

Huit mutations, dans la couche anti-corruption et le registre :

```text
annulation lue comme confirmée               tuee
statut inconnu deviné en attente             tuee
devise ignorée                               tuee
centimes ignorés                             tuee
numéro sans le +                             tuee
montant non comparé                          tuee
annulation ignorée                           tuee
cotisation inconnue acceptée                 tuee
8/8 tuees
```

Aucune survivante : chaque traduction a son test, et chaque refus aussi.
La couche anti-corruption est le paquet le plus facile à tester de
l'application : une fonction, des entrées venues d'ailleurs, des sorties
dans nos mots. C'est aussi celui qui protège le plus.

## 7. La grille

| Situation | Que faire |
|---|---|
| un mot a deux sens selon la partie de l'application | deux contextes, deux types |
| deux contextes parlent de la même personne | une clé partagée (le numéro), pas un type partagé |
| un contexte a besoin d'une information d'un autre | une question précise (une interface, une API), pas l'accès à son modèle |
| un système extérieur (opérateur, partenaire) | une couche anti-corruption, seule à importer son SDK |
| un statut, un format inconnu arrive de l'extérieur | refusé et mis de côté, jamais deviné |
| une petite application, une seule équipe | un seul contexte suffit souvent (leçon 4.6) ; la couche anti-corruption reste utile devant l'opérateur |

## 8. Les trois erreurs qui restent

### « Un seul modèle, c'est une seule vérité »

C'est une seule **structure**, avec plusieurs vérités dedans. La mesure
le montre : le même `LastPayment` est lu de deux façons par deux
paquets, et ils divergent sur 13 cotisations. Plusieurs modèles qui se
disent explicitement « je parle de paiements confirmés » sont plus
cohérents qu'un modèle commun que chacun interprète.

### « Les mots de l'opérateur, tout le monde les connaît »

Jusqu'à la version suivante de son API. `SUCCESSFUL` dans le code de la
tontine, c'est la tontine qui dépend d'un choix de l'opérateur.
`Confirmed` dans le code de la tontine, c'est un mot qui lui appartient,
et que la couche anti-corruption garde vrai.

### « Des contextes, c'est des microservices »

Non : les contextes de la leçon sont des **paquets Go**, dans un seul
programme. Un contexte est une frontière de **sens** ; il peut devenir
un service un jour (leçon 7.6), mais rien ne l'y oblige. La leçon 7.5
montre comment faire tenir les frontières dans un seul déploiement.

## 9. Le lien avec la production

- **Une carte des contextes** (*context map*) se dessine, et se garde à
  jour avec les diagrammes C4 de la leçon 4.5 : quels contextes, qui
  dépend de qui, où sont les couches anti-corruption.
- **Les rappels mis de côté** se surveillent : un compteur, une alerte
  au premier statut inconnu. C'est souvent ainsi qu'on apprend qu'un
  opérateur a changé son API sans prévenir.
- **Les équipes** suivent souvent les contextes : l'équipe des paiements
  possède le contexte des paiements et sa couche anti-corruption ; elle
  peut changer ses mots sans réunir toute l'entreprise.
- **La base** suit aussi : chaque contexte a ses tables, et un contexte
  ne lit pas les tables d'un autre (leçon 7.5).

## 10. Ce qu'il faut retenir

1. Un contexte délimité est une frontière où chaque mot a un seul sens.
2. Chaque contexte a son type, avec ce qu'il utilise ; ils partagent des
   clés, pas des structures.
3. Le code parle le langage du domaine, pas celui des systèmes voisins.
4. Une couche anti-corruption traduit l'extérieur, en un seul endroit.
5. Ce qu'elle ne comprend pas, elle le met de côté.

## 11. Approfondissement

### Les relations entre contextes

Evans nomme plusieurs relations : un contexte **client** et un
**fournisseur** qui négocient l'API ; un **conformiste** qui adopte le
modèle de l'autre tel quel, faute de pouvoir négocier ; un **noyau
partagé** que deux équipes possèdent ensemble ; la **couche
anti-corruption** quand on ne peut ni négocier ni accepter. Devant un
grand opérateur Mobile Money, on ne négocie pas : la couche
anti-corruption est la réponse habituelle.

### Le langage dans les noms

Le langage omniprésent n'est pas un glossaire à côté du code : c'est le
code. Si les trésorières disent « clore le tour » et que le code dit
`UpdateRoundStatus(3)`, la traduction se fait dans la tête de chaque
développeur, à chaque lecture. `round.Close()` dit la même chose que la
trésorière.

## 12. Le réflexe à installer

Devant chaque type qui grossit, demande-toi :

1. Ce mot a-t-il le même sens pour toutes les parties qui l'utilisent ?
2. Quels paquets dépendent de ce type, et pourquoi chacun ?
3. Les mots d'un système extérieur apparaissent-ils hors d'une couche de
   traduction ?
4. Que fait le code devant une valeur extérieure qu'il ne connaît pas ?
5. Ce que deux contextes partagent est-il une clé, ou un type entier ?
