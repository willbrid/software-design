# Leçon 7.3 — L'architecture hexagonale : des ports, des adaptateurs, et des faux fidèles

## L'essentiel en deux minutes

**Le problème, en une phrase.** Quand le code des règles appelle
directement PostgreSQL et la passerelle SMS, on ne peut le tester qu'avec
une base et une passerelle, on ne peut pas l'appeler depuis un autre
canal sans tout recopier, et changer de prestataire SMS touche aux
règles.

**Trois images.**

- **La prise électrique** : l'appareil ne sait pas si le courant vient
  d'un barrage ou d'un groupe électrogène ; il a une prise, et c'est au
  fournisseur de s'y conformer. Le port est la prise ; l'adaptateur, le
  fournisseur.
- **La maquette du guichet** : pour former une nouvelle caissière, on
  monte un faux guichet. Il doit se comporter comme le vrai, sinon elle
  apprend des gestes qui échoueront le premier jour.
- **La liste de contrôle commune** : le vrai guichet et la maquette
  passent la **même** liste de vérifications. C'est ce qui garantit que
  la maquette ne ment pas.

**Le code, en quelques lignes.** L'application dit ce dont elle a besoin,
dans ses propres mots, et ne connaît rien de ce qui le fournit :

```go
type Rounds interface {
    Create(ctx context.Context, id string, r *round.Round) error
    Load(ctx context.Context, id string) (*round.Round, int, error)
    Save(ctx context.Context, id string, r *round.Round, version int) error
}
```

**Les règles à retenir.**

1. **L'application et le domaine au centre, sans dépendance vers
   l'extérieur** : ni pilote de base, ni client HTTP.
2. **Un port est une interface définie par l'application**, dans son
   paquet, pour ce dont elle a besoin (stocker un tour, prévenir un
   membre).
3. **Un adaptateur implémente un port** pour une technologie : PostgreSQL,
   la mémoire, une passerelle SMS. D'autres adaptateurs **pilotent**
   l'application : HTTP, USSD, une ligne de commande.
4. **Un faux adaptateur doit être fidèle** : les mêmes tests de contrat
   tournent sur le faux et sur le vrai.
5. **Une règle d'architecture s'écrit en test** : le sens des dépendances
   se vérifie à chaque `go test`.

La suite le mesure : vitesse des tests, fidélité des faux, et sens des
dépendances.

---

La leçon 7.1 a mis les règles dans l'agrégat du tour. Il reste à
l'enregistrer, à prévenir les membres, à recevoir les requêtes. Le
problème de cette leçon :

> **Comment organiser le code autour des règles, pour qu'elles ne
> dépendent ni de la base, ni du réseau, ni du canal qui les appelle ?**

Le module de la leçon est `l73`, sur le même PostgreSQL 17 que le
niveau 5. Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. La première version

Le paquet `tangled` est la première version de la cotisation : un
gestionnaire qui décode, vérifie les règles, parle à PostgreSQL et à la
passerelle SMS, dans une seule fonction.

```go
// Handler serves POST /rounds/{id}/contributions.
func Handler(pool *pgxpool.Pool, smsURL string) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        var req struct {
            Member     string `json:"member"`
            AmountFCFA int64  `json:"amount_fcfa"`
        }
        if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
            http.Error(w, "malformed", http.StatusBadRequest)
            return
        }
        ctx := r.Context()
        err := pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
            var share int64
            var closed bool
            if err := tx.QueryRow(ctx, `SELECT share_fcfa, beneficiary <> '' FROM rounds WHERE id = $1 FOR UPDATE`,
                r.PathValue("id")).Scan(&share, &closed); err != nil {
                return err
            }
            if closed || req.AmountFCFA != share {
                return fmt.Errorf("refused")
            }
            _, err := tx.Exec(ctx, `INSERT INTO paid (round_id, member, amount_fcfa) VALUES ($1, $2, $3)`,
                r.PathValue("id"), req.Member, req.AmountFCFA)
            return err
        })
        if err != nil {
            http.Error(w, err.Error(), http.StatusUnprocessableEntity)
            return
        }
        form := url.Values{"to": {req.Member}, "text": {fmt.Sprintf("Cotisation de %d FCFA reçue", req.AmountFCFA)}}
        if resp, err := http.Post(smsURL, "application/x-www-form-urlencoded", strings.NewReader(form.Encode())); err == nil {
            resp.Body.Close()
        }
        w.WriteHeader(http.StatusCreated)
    })
}
```

Rien n'y est faux. Mais pour le tester, il faut une base avec les bonnes
tables et une passerelle SMS qui répond ; pour payer par USSD, il faut le
recopier ; pour changer de passerelle, il faut toucher le code qui
vérifie le montant.

## 2. L'hexagone

Alistair Cockburn a décrit l'architecture **hexagonale**, ou **ports et
adaptateurs** : une application au centre, qui communique avec
l'extérieur par des **ports** ; des **adaptateurs** propres à chaque
technologie convertissent ce qui arrive en appels de l'application. Son
but, dans ses mots : qu'une application puisse être pilotée aussi bien
par des personnes que par des programmes, des tests automatiques ou des
scripts, et être développée et testée **isolée** de ses bases de données
et de ses appareils.

Le module se découpe ainsi :

| Paquet | Rôle | Dépend de |
|---|---|---|
| `domain/round` | l'agrégat du tour (leçon 7.1) | rien |
| `app` | ce que l'application fait, et ses ports | `domain/round` |
| `adapters/pgstore` | le port `Rounds` sur PostgreSQL | `app`, `domain`, pgx |
| `adapters/memstore` | le port `Rounds` en mémoire | `app`, `domain` |
| `adapters/sms` | le port `Notifier` : une passerelle HTTP, et un enregistreur | — |
| `adapters/httpapi` | pilote l'application depuis HTTP | `app`, `domain` |

L'application déclare ses ports dans son propre paquet :

```go
// Rounds is the port to the stored rounds. Load returns a round of its own,
// that the caller may change, and the version it read; Save stores it if
// the version is still the current one, or returns ErrConflict.
type Rounds interface {
    Create(ctx context.Context, id string, r *round.Round) error
    Load(ctx context.Context, id string) (*round.Round, int, error)
    Save(ctx context.Context, id string, r *round.Round, version int) error
}
```

```go
// Notifier is the port to the messages sent to members.
type Notifier interface {
    Notify(ctx context.Context, phone, message string) error
}
```

C'est aussi la règle de Go : les *Go Code Review Comments* disent qu'une
interface appartient en général au paquet qui l'**utilise**, pas à celui
qui l'implémente. Le service ne voit que ses ports :

```go
// change loads round id, applies do, and saves it; again when another
// change came first, at most Tries times.
func (s *Service) change(ctx context.Context, id string, do func(*round.Round) error) error {
    for range Tries {
        r, version, err := s.Rounds.Load(ctx, id)
        if err != nil {
            return err
        }
        if err := do(r); err != nil {
            return err
        }
        err = s.Rounds.Save(ctx, id, r, version)
        if !errors.Is(err, ErrConflict) {
            return err
        }
    }
    return fmt.Errorf("round %s: %w, %d times", id, ErrConflict, Tries)
}
```

```go
// Contribute records the payment of member to round id, and thanks them.
func (s *Service) Contribute(ctx context.Context, id, member string, amount int64) error {
    if err := s.change(ctx, id, func(r *round.Round) error { return r.Contribute(member, amount) }); err != nil {
        return err
    }
    return s.Notify.Notify(ctx, member, fmt.Sprintf("Cotisation de %d FCFA reçue", amount))
}
```

L'adaptateur PostgreSQL implémente le port, avec la version de la leçon
5.3 dans la clause `WHERE` :

```go
// Save writes r if version is still the current one.
func (s Rounds) Save(ctx context.Context, id string, r *round.Round, version int) error {
    state, err := json.Marshal(r.Snapshot())
    if err != nil {
        return err
    }
    tag, err := s.Pool.Exec(ctx, `UPDATE round SET state = $3, version = version + 1 WHERE id = $1 AND version = $2`, id, version, state)
    if err != nil {
        return err
    }
    if tag.RowsAffected() == 0 {
        return app.ErrConflict
    }
    return nil
}
```

## 3. Mesure : le sens des dépendances

`cmd/deps` demande à la commande `go` de quoi dépend chaque paquet, hors
de la bibliothèque standard :

```text
./domain/round   0 packages outside the standard library; imported directly: []
./app            1 packages outside the standard library; imported directly: []
./tangled       29 packages outside the standard library; imported directly: [github.com/jackc/pgx/v5 github.com/jackc/pgx/v5/pgxpool]
```

Le domaine ne dépend de rien ; l'application, du seul domaine. La
première version entraîne **29 paquets** extérieurs, le pilote de base et
tout ce qu'il charge, dans le code des règles. Le sens se vérifie en
test :

```go
// The application and the domain depend on nothing outside themselves: not
// on an adapter, not on a driver. The adapters depend on them.
func TestTheDependenciesPointInwards(t *testing.T) {
    for _, pkg := range []string{"example/hex73/app", "example/hex73/domain/round"} {
        out, err := exec.Command("go", "list", "-deps", "-f", "{{if not .Standard}}{{.ImportPath}}{{end}}", pkg).Output()
        if err != nil {
            t.Fatal(err)
        }
        for _, d := range strings.Fields(string(out)) {
            if d != "example/hex73/app" && d != "example/hex73/domain/round" {
                t.Errorf("%s depends on %s", pkg, d)
            }
        }
    }
}
```

## 4. Mesure : la vitesse des tests

`cmd/speed` joue 300 fois le même scénario (ouvrir un tour de 20 membres,
un versement trop tôt refusé, 20 paiements, trois refus, un versement),
avec l'adaptateur mémoire, puis avec PostgreSQL :

```text
memstore   300 scenarios in 53ms
postgresql 300 scenarios in 23.931s
```

**53 ms contre 24 s**, plus de 400 fois plus vite. Les tests des règles
et de l'application tournent sur l'adaptateur mémoire, sans base, à
chaque sauvegarde de fichier ; ceux de l'adaptateur PostgreSQL tournent
sur PostgreSQL, et vérifient ce que seule la base peut vérifier.

## 5. Mesure : un faux doit être fidèle

Un faux adaptateur rapide n'est utile que s'il se comporte comme le vrai.
Le premier faux qui a été écrit garde les tours eux-mêmes, et enregistre
sans regarder la version :

```go
// Naive is the first fake that was written: it keeps the rounds
// themselves, and saves without looking at the version.
type Naive struct {
    mu     sync.Mutex
    rounds map[string]*round.Round
}
```

Les tests de l'application passaient avec lui. Le paquet `roundstest`
écrit le **contrat** du port `Rounds`, ce que tout adaptateur doit faire,
et le vérifie de la même façon sur chacun. Martin Fowler appelle ces
tests des **tests de contrat** : ils vérifient que les faux rendent les
mêmes résultats que le vrai.

```go
// Check runs the contract on stores made by fresh, and returns what an
// adapter breaks: nothing for a faithful one. With concurrent false, it
// leaves out the case of twenty changes at once.
func Check(fresh func() app.Rounds, concurrent bool) []string {
```

(Le corps, sept cas, est dans le module.) `cmd/fidelity` lance
le contrat sur les trois adaptateurs :

```text
memstore    0 broken
naive fake  3 broken
    a change that was not saved is in the store: Load does not return a copy
    a save from an old version is accepted: <nil>
    a change made after the save is in the store: the store shares the round's state
postgresql  0 broken
```

Le faux naïf casse **trois** clauses du contrat. Un test de
l'application qui modifie un tour sans l'enregistrer le voit modifié
quand même ; un test de conflit passe alors qu'en production, PostgreSQL
refuserait. Et le cas des vingt paiements simultanés, que `cmd/fidelity`
épargne au faux naïf, fait planter le programme :

```text
fatal error: concurrent map writes

goroutine 28 [running]:
internal/runtime/maps.fatal({0x585341?, 0x408ef0?})
```

Les vingt goroutines modifient **le même** tour, que le faux leur a
donné à toutes. Le faux fidèle rend une **copie** à chaque chargement,
comme la base, qui rend des lignes.

Le contrat a trouvé un défaut dans le vrai aussi. Avec cinq essais en
cas de conflit, les vingt paiements simultanés passaient en mémoire, et
échouaient sur PostgreSQL :


L'adaptateur mémoire répond en microsecondes : les fenêtres de conflit
sont minuscules, et cinq essais suffisent. PostgreSQL répond en
millisecondes : onze paiements sur vingt épuisent leurs essais. Le
service essaie maintenant jusqu'à 50 fois. Un faux, même fidèle, ne
reproduit pas les **délais** du vrai ; c'est pourquoi le contrat tourne
aussi sur PostgreSQL.

## 6. La campagne

Neuf mutations, dans les adaptateurs, le service et l'instantané du
tour :

```text
mémoire : version non comparée               tuee
mémoire : version jamais augmentée           tuee
pg : version non comparée                    tuee
pg : conflit ignoré                          tuee
pg : tour inconnu en erreur brute            tuee
pas de nouvel essai                          tuee
le bénéficiaire n'est pas rechargé           SURVIT
instantané partagé                           SURVIT
remerciement même refusé                     SURVIT
6/9 tuees
```

Trois survivantes, et deux disent ce que le contrat oubliait :

- **le bénéficiaire n'est pas rechargé** : un tour versé revenait
  **ouvert** de la base, et pouvait être versé une seconde fois. Aucun
  cas du contrat ne rechargeait un tour versé ;
- **l'instantané partagé** : `Snapshot` rendait la table des paiements de
  l'agrégat lui-même. Un appelant qui modifiait le tour **après**
  l'enregistrement modifiait le stockage en mémoire. Aucun cas ne
  modifiait un tour après l'avoir enregistré ;
- **le remerciement même refusé** : le service envoyait « cotisation
  reçue » pour un paiement refusé. Aucun test de l'application ne
  regardait les messages.

Les deux cas ajoutés au contrat :

```go
    // A round paid out stays paid out: the store keeps all of its state.
    s = fresh()
    one := round.New(1, 10_000, []string{"m00"})
    _ = one.Contribute("m00", 10_000)
    _ = one.PayOut("m00")
    _ = s.Create(ctx, "r1", one)
    if back, _, _ := s.Load(ctx, "r1"); back.Beneficiary() != "m00" || back.PayOut("m00") == nil {
        fail("a round paid out comes back open: it could be paid out twice")
    }

    // What the caller does after a save is not in the store.
    s = fresh()
    _ = s.Create(ctx, "r1", round.New(1, 10_000, members()))
    r, v, _ = s.Load(ctx, "r1")
    _ = s.Save(ctx, "r1", r, v)
    _ = r.Contribute("m05", 10_000) // after the save, never saved
    if again, _, _ := s.Load(ctx, "r1"); again.Pot() != 0 {
        fail("a change made after the save is in the store: the store shares the round's state")
    }
```

## 7. La grille

| Je veux… | Avec l'hexagone |
|---|---|
| tester une règle | sur le domaine seul, sans rien d'autre |
| tester ce que fait l'application | sur les adaptateurs en mémoire, en millisecondes |
| tester l'adaptateur PostgreSQL | le contrat du port, sur une vraie base |
| ajouter un canal (USSD, ligne de commande) | un adaptateur qui pilote le même service |
| changer de passerelle SMS | un nouvel adaptateur du port `Notifier` ; rien d'autre ne change |
| écrire un faux | qu'il passe le contrat du port, comme le vrai |

## 8. Les trois erreurs qui restent

### « Une interface pour chaque type, c'est l'hexagone »

Une interface par type ne sert à rien ; un port sert à **une frontière**
de l'application avec l'extérieur : le stockage, les messages, l'horloge,
l'opérateur. Le tour n'a pas d'interface : c'est le domaine, il n'y a
qu'une implémentation, et on la teste directement.

### « Les faux suffisent, la base est un détail »

Le contrat a trouvé un défaut que le faux fidèle ne montrait pas : cinq
essais suffisaient en mémoire, pas sur PostgreSQL. Les faux servent à
tester **vite** ; le contrat sur la vraie base sert à tester **juste**.
Les deux tournent.

### « Ports et adaptateurs, c'est beaucoup de fichiers pour une cotisation »

Six paquets au lieu d'un gestionnaire. Pour une application qui n'a qu'un
canal, qui n'est testée qu'avec une base, et dont les règles tiennent en
trois lignes, c'est trop, et la leçon 4.6 le disait. Le prix se paie dès
le deuxième canal, le premier changement de prestataire, ou la première
suite de tests qui dépasse la minute. La leçon 7.4 mesure ce que coûtent
les couches en trop.

## 9. Le lien avec la production

- **Le `main`** est le seul endroit qui connaît tout : il ouvre le pool
  PostgreSQL, construit `pgstore.Rounds`, `sms.Gateway`, le service, et
  l'adaptateur HTTP. C'est là que se choisissent les adaptateurs.
- **La CI** fait tourner les tests rapides à chaque poussée, et le
  contrat sur PostgreSQL avant chaque fusion.
- **Le test d'architecture** fait échouer la CI le jour où quelqu'un
  importe pgx dans `app`, au lieu qu'une revue le remarque, ou non.
- **Un incident** se reproduit souvent dans un test de l'application,
  avec les adaptateurs en mémoire, en quelques lignes ; puis dans le
  contrat, si l'adaptateur était en cause.

## 10. Ce qu'il faut retenir

1. Le domaine et l'application au centre, sans dépendance vers
   l'extérieur.
2. Un port est une interface de l'application, dans son paquet, pour une
   frontière.
3. Des adaptateurs pour chaque technologie, et pour chaque canal qui
   pilote l'application.
4. Un faux passe le même contrat que le vrai ; le contrat tourne aussi
   sur le vrai.
5. Le sens des dépendances se vérifie en test.

## 11. Approfondissement

### Les ports de sortie qu'on oublie

L'horloge (`time.Now`), le hasard, les identifiants générés sont aussi
des dépendances vers l'extérieur. Un service qui appelle `time.Now()` ne
peut pas être testé à minuit le 31 décembre. Un port `Clock` (ou un
champ `Now func() time.Time`, comme dans la leçon 6.5) le rend testable.

### Où mettre la transaction

Le port `Rounds` enregistre un agrégat, et la version protège des
écritures concurrentes. Quand un cas d'utilisation doit écrire **deux**
choses de façon atomique (le tour et un ordre dans l'outbox, leçon 5.2),
le port expose une unité de travail : une fonction qui reçoit les ports
liés à une même transaction. La leçon 7.4 y revient.

## 12. Le réflexe à installer

Devant chaque cas d'utilisation, demande-toi :

1. De quoi a-t-il besoin à l'extérieur, et quel port le dit dans ses
   mots ?
2. Le domaine et l'application importent-ils autre chose qu'eux-mêmes ?
3. Le faux de ce port passe-t-il le même contrat que le vrai ?
4. Le contrat tourne-t-il aussi sur la vraie base ?
5. Ajouter un canal demanderait-il de recopier une règle ?
