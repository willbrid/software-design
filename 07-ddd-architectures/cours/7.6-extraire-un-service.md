# Leçon 7.6 — Extraire un module en service : ce que coûte le réseau, et comment migrer sans sauter

## L'essentiel en deux minutes

**Le problème, en une phrase.** Un module bien découpé (leçon 7.5) peut
devenir un service, mais l'appel de fonction devient un appel réseau :
mille fois plus lent, et qui peut échouer, ou ne pas répondre. Et le
nouveau service, réécrit, ne répond pas forcément comme l'ancien module.

**Trois images.**

- **Le collègue qui déménage** : tant qu'il était dans le bureau d'à
  côté, on lui posait dix questions par heure. À l'autre bout de la
  ville, on les regroupe en un seul appel, et on prévoit le jour où il ne
  décroche pas.
- **Le figuier étrangleur** : il pousse autour d'un arbre, prend peu à peu
  sa place, et l'arbre finit par disparaître. On remplace un système de la
  même façon, morceau par morceau, jamais d'un coup.
- **Le nouveau caissier à côté de l'ancien** : pendant une semaine, les
  deux comptent chaque billet ; on ne garde que le compte de l'ancien, et
  on note chaque différence. Quand il n'y en a plus, le nouveau prend la
  caisse.

**Le code, en quelques lignes.** En ombre, l'ancien module répond, et le
nouveau service est seulement comparé :

```go
        for _, c := range contributions {
            if got[c] != old[c] {
                r.mismatches = append(r.mismatches, fmt.Sprintf("%s: module %v, service %v", c, old[c], got[c]))
            }
        }
        return old, nil
```

**Les règles à retenir.**

1. **Un service se justifie par une raison** (une équipe, une charge, une
   contrainte légale), pas par l'architecture : le réseau a un prix.
2. **Un appel réseau se regroupe** : une question pour vingt-cinq
   cotisations, pas vingt-cinq questions.
3. **Un appel réseau échoue** : un délai sur chaque appel, et aucune
   décision prise sur une absence de réponse.
4. **On migre par étapes** : d'abord en ombre, en comparant ; puis une
   part croissante des appels ; l'ancien module reste jusqu'à la fin.
5. **Une différence en ombre est un défaut trouvé avant les membres.**

La suite le mesure avec le module des paiements, extrait en service.

---

La leçon 7.5 a donné au module des paiements une face publique, ses
tables, son rôle. L'équipe des paiements veut maintenant le déployer à
part : l'opérateur Mobile Money impose des audits sur tout ce qui touche
l'argent, et l'équipe veut livrer sans attendre le reste de
l'application. Le problème de cette leçon :

> **Que change le passage d'un module à un service, et comment migrer
> sans casser les tontines un dimanche ?**

Le module de la leçon est `l76`. Il n'a besoin que de la bibliothèque
standard. Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Le module, et le service

Le module des paiements, dans le monolithe :

```go
// ConfirmedAmong reports, for each contribution, whether it is paid.
func (m *Module) ConfirmedAmong(ctx context.Context, contributions []string) (map[string]bool, error) {
    m.mu.Lock()
    defer m.mu.Unlock()
    out := make(map[string]bool, len(contributions))
    for _, c := range contributions {
        out[c] = m.outcome[c] == "confirmed"
    }
    return out, nil
}
```

Le service, réécrit par l'équipe des paiements, avec son propre stockage
rempli par une migration du registre, et une API HTTP :

```go
// Handler serves POST /confirmed-among: a JSON list of contributions in,
// a JSON object contribution -> paid out.
func (s *Service) Handler() http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("POST /confirmed-among", func(w http.ResponseWriter, r *http.Request) {
        var ids []string
        if err := json.NewDecoder(http.MaxBytesReader(w, r.Body, 64<<10)).Decode(&ids); err != nil {
            http.Error(w, "malformed", http.StatusBadRequest)
            return
        }
        s.mu.Lock()
        out := make(map[string]bool, len(ids))
        for _, id := range ids {
            out[id] = s.paid[id]
        }
        s.mu.Unlock()
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(out)
    })
    return mux
}
```

Et le client, que les tontines utilisent à la place du module. Il a la
même méthode, donc il satisfait la même interface `Payments` des
tontines (leçon 7.5) :

```go
// ConfirmedAmong asks for many contributions at once.
func (c Client) ConfirmedAmong(ctx context.Context, contributions []string) (map[string]bool, error) {
    ctx, cancel := context.WithTimeout(ctx, c.Timeout)
    defer cancel()
    body, _ := json.Marshal(contributions)
    req, err := http.NewRequestWithContext(ctx, http.MethodPost, c.URL+"/confirmed-among", bytes.NewReader(body))
    if err != nil {
        return nil, err
    }
    resp, err := c.HTTP.Do(req)
    if err != nil {
        return nil, fmt.Errorf("payments service: %w", err)
    }
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK {
        return nil, fmt.Errorf("payments service: %s", resp.Status)
    }
    var out map[string]bool
    if err := json.NewDecoder(resp.Body).Decode(&out); err != nil {
        return nil, fmt.Errorf("payments service: %w", err)
    }
    return out, nil
}
```

## 2. Mesure : le prix d'un appel

`cmd/latency` demande si les 25 cotisations d'un tour sont payées, 200
fois : au module, puis au service, à travers un réseau de 1 ms par
aller-retour (celui d'un centre de données), en une question pour les 25
et en 25 questions :

```text
module, the 25 at once              5µs per round
module, one by one                  5µs per round
service, the 25 at once         1.907ms per round
service, one by one            45.879ms per round
```

- **Le module répond en 5 µs**, que la question porte sur une cotisation
  ou sur vingt-cinq.
- **Le service répond en 1,9 ms** pour les 25 à la fois : environ 400 fois
  plus lent, et c'est le meilleur cas.
- **Un par un, 46 ms** : 25 allers-retours. Le code des tontines qui
  appelait `Confirmed` dans une boucle ne coûtait rien dans le monolithe ;
  à travers le réseau, c'est le N+1 de la leçon 5.5.

Avant d'extraire un module, on cherche chaque appel en boucle vers lui, et
on le remplace par une question groupée. C'est le travail de l'exercice 2
de la leçon 7.5, qui paie ici.

## 3. Mesure : la réponse qui ne vient pas

Le module ne tombait jamais en panne seul : s'il tombait, tout le
programme tombait avec lui. Le service, si. Les prêts décidaient ainsi :

```go
// MayBorrowNaive is the decision as it was written against the module,
// which never failed: an error reads as "not paid".
func MayBorrowNaive(ctx context.Context, p Payments, last string) (bool, error) {
    paid, _ := p.Confirmed(ctx, last)
    return paid, nil
}
```

`cmd/failure` demande 1 000 décisions de prêt pour des membres **à jour**,
pendant que le service répond `503` à 3 % des appels et met 2 s à 3 %
(le client abandonne après 300 ms) :

```text
naive                 up-to-date members refused: 58  told to try again:  0
no decision on error  up-to-date members refused:  0  told to try again: 62
```

**58 membres à jour se voient refuser un prêt** : l'erreur est lue comme
« pas payé ». La décision corrigée ne décide pas sans réponse :

```go
// MayBorrow takes no decision when the payments do not answer: the member
// is told to try again, and is not refused.
func MayBorrow(ctx context.Context, p Payments, last string) (bool, error) {
    paid, err := p.Confirmed(ctx, last)
    if err != nil {
        return false, ErrUnavailable
    }
    return paid, nil
}
```

62 membres lisent « réessayez », aucun n'est refusé à tort. Dans le
monolithe, la question « que faire si les paiements ne répondent pas ? »
n'existait pas ; après l'extraction, chaque appelant doit y répondre.

## 4. Migrer : le figuier étrangleur

Martin Fowler a nommé **figuier étrangleur** (*strangler fig*) la façon de
remplacer un système morceau par morceau : le nouveau pousse autour de
l'ancien, prend peu à peu ses fonctions, et l'ancien finit par
disparaître. Il note que le remplacement d'un coup, « le même système
dans une meilleure technologie », échoue la plupart du temps.

Le paquet `strangler` place un aiguillage entre les tontines et les
paiements :

```go
// Router answers with Old or New. In Shadow mode, Old answers, and New is
// asked the same question to compare; otherwise a share Share of the calls
// goes to New.
type Router struct {
    Old, New Payments
    Shadow   bool
    Share    float64
    Rand     func() float64

    mu         sync.Mutex
    asked      int
    toNew      int
    newErrors  int
    mismatches []string
}
```

```go
// ConfirmedAmong answers the question of the tontines.
func (r *Router) ConfirmedAmong(ctx context.Context, contributions []string) (map[string]bool, error) {
    if r.Shadow {
        old, err := r.Old.ConfirmedAmong(ctx, contributions)
        if err != nil {
            return nil, err
        }
        got, nerr := r.New.ConfirmedAmong(ctx, contributions)
        r.mu.Lock()
        defer r.mu.Unlock()
        r.asked++
        if nerr != nil {
            r.newErrors++
            return old, nil
        }
        for _, c := range contributions {
            if got[c] != old[c] {
                r.mismatches = append(r.mismatches, fmt.Sprintf("%s: module %v, service %v", c, old[c], got[c]))
            }
        }
        return old, nil
    }
    r.mu.Lock()
    r.asked++
    useNew := r.Rand() < r.Share
    if useNew {
        r.toNew++
    }
    r.mu.Unlock()
    if useNew {
        return r.New.ConfirmedAmong(ctx, contributions)
    }
    return r.Old.ConfirmedAmong(ctx, contributions)
}
```

En **ombre**, le module répond, et le service reçoit la même question :
les réponses sont comparées, chaque différence est notée, et une panne du
service ne touche personne. Ensuite, une **part** des appels va au
service, puis une part plus grande.

## 5. Mesure : ce que l'ombre trouve

`cmd/shadow` crée un registre de 2 000 cotisations (dont 3 % annulées,
2 % échouées, 5 % en attente), et pose 400 questions de 25 cotisations
par phase :

```text
shadow, first migration        questions 400  to the service   0  mismatches 339  first: c1081: module false, service true
shadow, fixed migration        questions 400  to the service   0  mismatches   0
10 % to the service            questions 400  to the service  42  mismatches   0
50 % to the service            questions 400  to the service 198  mismatches   0
100 % to the service           questions 400  to the service 400  mismatches   0
```

- **En ombre, avec la première migration : 339 réponses différentes.** La
  première : la cotisation `c1081`, non payée pour le module, payée pour
  le service. Le défaut est dans la migration :

```go
// MigrateFirstVersion is the first migration the payments team wrote, kept
// to replay the comparison that found its mistake: a payment that went
// through once counts as paid, even if it was reversed since.
func MigrateFirstVersion(ledger map[string]string) *Service {
    s := &Service{paid: map[string]bool{}}
    for c, outcome := range ledger {
        s.paid[c] = outcome == "confirmed" || strings.HasPrefix(outcome, "rev")
    }
    return s
}
```

  L'équipe a pensé « un paiement passé une fois est payé », et a compté
  les annulations comme des paiements : c'est l'incident de la leçon 7.2,
  recommencé par une autre équipe, et trouvé cette fois **avant** qu'un
  membre ne le voie. Les colonnes « to the service » restent à 0 en
  ombre : le service est interrogé à chaque question, mais ne répond à
  personne.
- **En ombre, avec la migration corrigée : aucune différence.**
- **10 %, puis 50 %, puis 100 %** des appels vont au service, sans
  différence. Le module reste en place jusqu'au bout : revenir en arrière
  est un réglage, pas un déploiement.

## 6. La campagne

Huit mutations, dans l'aiguillage, le service, le client et les prêts :

```text
l'ombre répond avec le service               tuee
réponses non comparées                       tuee
panne du service visible en ombre            tuee
part inversée                                SURVIT
migration par exclusion                      tuee
statut ignoré                                SURVIT
pas de délai                                 tuee
erreur lue comme refus                       tuee
6/8 tuees
```

Deux survivantes, deux tests trop faibles :

- **la part inversée** (`>` au lieu de `<`) : le test tirait deux nombres
  sous la part et deux au-dessus, et la mutation envoyait autant d'appels
  au service. Le test renforcé tire un nombre sous la part et trois
  au-dessus ;
- **le statut ignoré** : le test du client utilisait un `503` dont le
  corps n'était pas du JSON, et le décodage échouait de toute façon. Un
  service en panne peut répondre un corps qui se décode ; le test
  renforcé envoie un `500` avec `{"a":true}`.

```text
l'ombre répond avec le service               tuee
réponses non comparées                       tuee
panne du service visible en ombre            tuee
part inversée                                tuee
migration par exclusion                      tuee
statut ignoré                                tuee
pas de délai                                 tuee
erreur lue comme refus                       tuee
8/8 tuees
```

## 7. La grille

| Avant d'extraire | À vérifier |
|---|---|
| une raison | une équipe qui doit livrer seule, une charge différente, une contrainte d'audit ; sinon, rester modulaire |
| une face publique | le module n'est appelé que par elle (leçon 7.5) |
| les appels en boucle | remplacés par des questions groupées |
| chaque appelant | sait quoi faire sans réponse : réessayer, attendre, ne pas décider |
| les écritures communes | aucune transaction entre le module et les autres ; sinon, un ordre dans l'outbox |
| la migration des données | rejouée en ombre, comparée avec l'ancien module |
| le retour en arrière | l'ancien module reste branché jusqu'à 100 % sans différence |

## 8. Les trois erreurs qui restent

### « On découpe en services pour avoir une bonne architecture »

Martin Fowler, dans *MicroservicePremium*, le dit sans détour : ne pas
même envisager les microservices sans un système trop complexe pour être
géré en monolithe ; la plupart des systèmes devraient être une seule
application, avec une bonne modularité à l'intérieur. Les sections 2 et
3 montrent le prix : 400 fois plus lent au mieux, et 58 décisions
fausses si l'on oublie la panne.

### « Le service fait la même chose que le module, on bascule dimanche »

La première migration avait 339 réponses différentes sur 400 questions.
Sans l'ombre, la bascule du dimanche aurait versé des cagnottes avec des
annulations dedans. On ne sait pas qu'un nouveau code fait « la même
chose » : on le mesure, sur les vraies questions.

### « Une erreur réseau, c'est rare »

3 % de `503` et 3 % de lenteurs, c'est une mauvaise journée ordinaire. Le
monolithe n'avait pas de mauvaise journée partielle ; le service en aura.
Chaque appelant décide, dans son code, ce qu'il fait d'une absence de
réponse, et un test le vérifie.

## 9. Le lien avec la production

- **Les délais** se règlent par appel, plus courts que le budget de
  l'écran (leçon 6.6) : 300 ms pour une question des prêts dans un écran
  de 800 ms.
- **Les nouvelles tentatives** suivent la leçon 6.3 : seulement pour des
  questions, ou des écritures avec une clé d'idempotence.
- **L'ombre** coûte : chaque question est posée deux fois. Elle dure le
  temps de voir passer les cas rares (une fin de mois, un dimanche de
  versements), pas éternellement.
- **Les métriques de l'aiguillage** (part envoyée au service, différences,
  erreurs du service) sont le tableau de bord de la migration ; une
  différence qui apparaît à 50 % fait revenir à 10 %, pendant qu'on
  cherche.
- **Les données** : tant que le module et le service coexistent, une seule
  source écrit. Ici, le registre du module ; le service est rempli par la
  migration, puis tenu à jour par les événements du registre (le niveau 8
  le construit), jusqu'à ce que le service devienne la source.

## 10. Ce qu'il faut retenir

1. Un service se paie en latence et en pannes partielles ; il faut une
   raison.
2. Les appels se regroupent avant l'extraction.
3. Aucune décision sur une absence de réponse.
4. On migre en ombre, puis par parts croissantes, l'ancien module en place.
5. Chaque différence en ombre est un défaut trouvé avant les membres.

## 11. Approfondissement

### Les écritures pendant la migration

Cette leçon migre une **question**. Migrer une **écriture** (enregistrer un
paiement) demande une seule source à la fois : soit le module écrit et le
service suit, soit l'inverse, jamais les deux en même temps. La bascule
d'une écriture se fait d'un coup, une fois que l'ombre des lectures n'a
plus de différence, et avec un plan pour revenir en arrière qui dit ce que
deviennent les écritures faites entre-temps.

### Le réseau ment

L'appel réseau ajoute d'autres pannes que le délai : une réponse arrivée
deux fois, une connexion coupée après que le service a fait le travail
(leçon 6.3), une version du service plus récente que son client (leçons
6.4 et 6.5). Tout ce que le niveau 6 a construit pour l'API publique vaut
désormais **entre les modules** devenus services.

## 12. Le réflexe à installer

Avant d'extraire un module, demande-toi :

1. Quelle raison, qu'un monolithe modulaire ne satisfait pas ?
2. Quels appels vers lui sont dans une boucle ?
3. Que fait chaque appelant quand il ne répond pas ?
4. Comment comparer ses réponses à celles du module, avant d'y croire ?
5. Comment revenir en arrière, à chaque étape ?
