# Leçon 7.4 — Clean Architecture et les couches : ce qu'elles protègent, ce qu'elles coûtent

## L'essentiel en deux minutes

**Le problème, en une phrase.** Les cercles de la Clean Architecture
(entités, cas d'utilisation, adaptateurs, frameworks) protègent les
règles, mais chaque cercle ajoute des structures et des copies de champ
en champ. Pour une fonction qui n'a presque pas de règle, comme modifier
la ville d'un membre, on paie toute la protection sans rien protéger.

**Trois images.**

- **Le colis qui passe six frontières** : à chaque frontière, on déballe
  et on remballe dans un autre carton. Chaque remballage est une occasion
  d'oublier un objet, et personne ne s'en aperçoit avant l'arrivée.
- **Le coffre-fort pour le carnet d'adresses** : un coffre a du sens pour
  la caisse de la tontine. Pour la liste des numéros de téléphone, une
  étagère suffit.
- **Un plan pour chaque pièce** : on ne construit pas la cuisine comme la
  chambre forte. Une application a des parties qui méritent des cercles,
  et d'autres non.

**Le code, en quelques lignes.** Ajouter un champ « e-mail » au profil :
dans la version en cercles, il traverse six correspondances, et chacune
peut le perdre :

```go
func toEntity(r db.MemberRow) entity.Member {
    return entity.Member{ID: r.ID, Name: r.Name, Phone: r.Phone, Town: r.Town, Email: r.Email}
}
```

**Les règles à retenir.**

1. **La règle des dépendances** est ce qui compte : le code des règles ne
   dépend pas de l'extérieur. Les cercles en sont une façon, pas la seule.
2. **Chaque frontière qui copie des champs** est un endroit où un champ
   peut se perdre sans erreur. Un test doit suivre chaque champ à travers
   toutes les copies.
3. **Le coût des couches est dans le changement**, pas dans le
   processeur : quelques microsecondes de plus, et six fichiers à
   modifier au lieu d'un.
4. **On choisit l'architecture par partie** : des cercles là où les règles
   sont riches (les tours, les prêts), du code direct là où il n'y a
   presque rien à protéger (le profil).

La suite le mesure avec le même profil, écrit deux fois.

---

La leçon 7.3 a construit un hexagone autour des règles du tour. La
Clean Architecture de Robert C. Martin pousse plus loin la même idée :
des cercles concentriques, chacun avec ses structures, et des
dépendances qui ne pointent que vers l'intérieur. Le problème de cette
leçon :

> **Les couches valent-elles leur prix partout, et comment le savoir ?**

Le module de la leçon est `l74`. Il n'a besoin que de la bibliothèque
standard. Il contient le même profil d'un membre, écrit en cercles et
écrit directement, dans sa version d'origine (`v1`) et après l'ajout d'un
champ (`v2`). Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. La règle des dépendances

Robert C. Martin, dans *The Clean Architecture*, dessine quatre cercles :
les **entités** au centre, puis les **cas d'utilisation**, puis les
**adaptateurs** (contrôleurs, présentateurs, passerelles), puis les
**frameworks** (le web, la base). Sa règle : les dépendances du code
source ne peuvent pointer **que vers l'intérieur** ; rien dans un cercle
intérieur ne connaît le nom de quoi que ce soit d'un cercle extérieur. Il
ajoute que les données qui traversent une frontière sont de **simples
structures**, propres à la frontière : on ne passe ni les entités ni les
lignes de la base.

L'hexagone de la leçon 7.3 respecte déjà la règle. La Clean Architecture
ajoute des structures à chaque frontière : une requête et une réponse
pour le cas d'utilisation, une vue pour le présentateur, une ligne pour
la base.

## 2. Le profil en cercles

Le profil d'un membre : un nom, un numéro, une ville. Une règle : le nom
n'est pas vide. Dans la version en cercles, l'entité :

```go
// Member is a member of the tontines.
type Member struct {
    ID    string
    Name  string
    Phone string
    Town  string
}
```

Le cas d'utilisation, avec son port d'entrée, son port de sortie, ses
modèles de requête et de réponse :

```go
// UpdateProfile updates the profile of a member.
func (u *UpdateProfile) UpdateProfile(req UpdateProfileRequest) error {
    m, err := u.Members.Find(req.ID)
    if err != nil {
        u.Output.Fail(err)
        return err
    }
    if err := m.Rename(req.Name); err != nil {
        u.Output.Fail(err)
        return err
    }
    m.Phone = req.Phone
    m.Town = req.Town
    if err := u.Members.Store(m); err != nil {
        u.Output.Fail(err)
        return err
    }
    u.Output.Present(ProfileResponse{ID: m.ID, Name: m.Name, Phone: m.Phone, Town: m.Town})
    return nil
}
```

La passerelle, qui traduit l'entité en ligne et retour :

```go
func toEntity(r db.MemberRow) entity.Member {
    return entity.Member{ID: r.ID, Name: r.Name, Phone: r.Phone, Town: r.Town}
}
```

```go
func toRow(m entity.Member) db.MemberRow {
    return db.MemberRow{ID: m.ID, Name: m.Name, Phone: m.Phone, Town: m.Town}
}
```

Plus un contrôleur, un présentateur, une vue et une table : six paquets.

## 3. Le profil en direct

La version directe : un type, un stockage, un gestionnaire.

```go
// Handler serves PUT /members/{id}.
func Handler(s *Store) http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("PUT /members/{id}", func(w http.ResponseWriter, r *http.Request) {
        var p Profile
        if err := json.NewDecoder(r.Body).Decode(&p); err != nil {
            http.Error(w, "malformed", http.StatusBadRequest)
            return
        }
        p.ID = r.PathValue("id")
        if _, found := s.Get(p.ID); !found {
            http.NotFound(w, r)
            return
        }
        if p.Name == "" {
            http.Error(w, "a name is required", http.StatusUnprocessableEntity)
            return
        }
        s.Put(p)
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(p)
    })
    return mux
}
```

La règle « le nom n'est pas vide » y est aussi, en une ligne.

## 4. Mesure : la taille, et ce que coûte un champ

La taille des deux versions d'origine :

```text
layered: 6 250
direct: 1 66
```

**250 lignes en six fichiers**, contre **66 lignes en un**. Puis les
membres veulent recevoir leurs reçus par e-mail : un champ de plus.
`git diff --numstat` entre `v1` et `v2` compte les lignes ajoutées et
retirées dans chaque fichier :

```text
== layered
2       1       {before => after}/layered/controller/controller.go
1       0       {before => after}/layered/db/db.go
1       0       {before => after}/layered/entity/member.go
2       2       {before => after}/layered/gateway/members.go
2       1       {before => after}/layered/presenter/presenter.go
4       1       {before => after}/layered/usecase/profile.go
== direct
1       0       {before => after}/direct/profile/profile.go
```

En cercles : **six fichiers**, 12 lignes ajoutées et 5 modifiées. Le
champ entre dans la vue, la requête, l'entité, la ligne, la réponse, et
dans les six fonctions ou expressions qui copient de l'une à l'autre. En
direct : **une ligne**.

## 5. Mesure : où se perd un champ

Chaque copie de champ à champ est un endroit où l'e-mail peut se perdre.
Le module de `v2` avait les tests du profil d'origine (le nom, la ville)
quand le champ a été ajouté. Sept mutations, chacune oublie l'e-mail à
un endroit :

```text
contrôleur : requête sans e-mail             SURVIT
cas d'utilisation : e-mail non copié         SURVIT
réponse sans e-mail                          SURVIT
vue sans e-mail                              SURVIT
ligne lue sans e-mail                        SURVIT
ligne écrite sans e-mail                     SURVIT
corps : mauvais nom                          SURVIT
0/7 tuees
```

**Les sept survivent** : la requête réussit, la réponse est `200`, le
nom est juste, et l'e-mail disparaît en silence, à l'un des sept endroits.
Dans la version directe, il n'y a qu'un endroit, le type lui-même, et le
champ voyage avec lui.

Le test ajouté suit l'e-mail de la requête jusqu'à la ligne, et retour :

```go
// A field crosses six mappings between the request and the row: one test
// follows it through all of them, both ways.
func TestTheEmailCrossesEveryCircle(t *testing.T) {
    table := db.NewTable()
    table.Put(db.MemberRow{ID: "m1", Name: "Awa", Phone: "+237677123456", Town: "Douala"})
    code, v := put(t, table, `{"name":"Awa","phone":"+237677123456","town":"Douala","email":"awa@example.org"}`)
    if r, _ := table.Get("m1"); code != 200 || r.Email != "awa@example.org" || v["email"] != "awa@example.org" {
        t.Errorf("%d, stored %q, answered %q", code, r.Email, v["email"])
    }
    // read back from the row: the next update keeps the name, and answers the email
    _, v = put(t, table, `{"name":"Awa N.","phone":"+237677123456","town":"Douala","email":"awa@example.org"}`)
    if v["email"] != "awa@example.org" {
        t.Errorf("answered %q", v["email"])
    }
}
```

```text
contrôleur : requête sans e-mail             tuee
cas d'utilisation : e-mail non copié         tuee
réponse sans e-mail                          tuee
vue sans e-mail                              tuee
ligne lue sans e-mail                        SURVIT
ligne écrite sans e-mail                     tuee
corps : mauvais nom                          tuee
6/7 tuees
```

Une survivante encore : **la ligne lue sans e-mail**. Le seul cas
d'utilisation, la mise à jour, remplace tout le profil par la requête :
il ne lit jamais l'e-mail de la base. La correspondance qui le perd est
fausse, mais rien ne s'en sert **encore**. Le jour où l'envoi des reçus
lira l'e-mail du membre, il trouvera une chaîne vide. Seul un test de la
passerelle elle-même la voit :

```go
// No use case reads the email yet: only a test of the gateway sees a
// mapping that loses it.
func TestAMemberComesBackWhole(t *testing.T) {
    g := Members{db.NewTable()}
    m := entity.Member{ID: "m1", Name: "Awa", Phone: "+237677123456", Town: "Douala", Email: "awa@example.org"}
    _ = g.Store(m)
    if got, err := g.Find("m1"); err != nil || got != m {
        t.Errorf("%+v %v, want %+v", got, err, m)
    }
}
```

```text
contrôleur : requête sans e-mail             tuee
cas d'utilisation : e-mail non copié         tuee
réponse sans e-mail                          tuee
vue sans e-mail                              tuee
ligne lue sans e-mail                        tuee
ligne écrite sans e-mail                     tuee
corps : mauvais nom                          tuee
7/7 tuees
```

Chaque frontière qui copie des champs demande **son propre test** de
correspondance, en plus des tests du comportement.

## 6. Mesure : le coût au processeur

`cmd/cost` envoie 200 000 mises à jour à chaque version :

```text
layered 6.155µs per request   direct 6.219µs per request
layered 6.949µs per request   direct 6.036µs per request
```

**Environ 6 µs par requête dans les deux cas**, à quelques centaines de
nanosecondes près, d'une mesure à l'autre. Les structures et les copies
ne coûtent presque rien au processeur ; le décodage JSON et l'écriture de
la réponse dominent, et une requête à la base (leçon 5.5) coûte cent fois
plus. Le coût des couches n'est pas là : il est dans les fichiers qu'on
modifie à chaque changement, et dans les copies qu'on oublie.

## 7. Quand les cercles valent leur prix

Le tour de la leçon 7.1 a des règles qui comptent : un paiement par
membre, le montant exact, le versement quand tous ont payé, rien après.
Plusieurs canaux l'appellent, et la base a un adaptateur qui peut se
tromper (leçon 7.3, exercice 5). Là, le cercle des entités protège de
l'argent, et le port du stockage permet de tester vite et juste.

Le profil a une règle : le nom n'est pas vide. Un seul canal l'appelle,
et la base n'y garde rien de délicat. Les six cercles y protègent une
ligne de code, et coûtent six fichiers à chaque champ.

Martin Fowler fait la même remarque sur la séparation en couches
présentation, domaine et données : elle est courante, mais elle ne devrait
s'appliquer qu'à une granularité assez petite ; quand l'application
grandit, on découpe d'abord par sujet (les tours, les profils, les prêts),
puis en couches à l'intérieur de ceux qui en ont besoin. C'est le sujet
de la leçon 7.5.

## 8. La grille

| La partie… | Architecture |
|---|---|
| a des règles qui protègent de l'argent ou des droits | entités avec leurs règles, ports pour l'extérieur, contrat sur les adaptateurs |
| est appelée par plusieurs canaux | un service au centre, des adaptateurs qui le pilotent |
| lit et écrit des données presque sans règle (un profil, des préférences) | un type, un stockage, un gestionnaire ; la règle des dépendances quand même |
| ne fait que lire pour un écran | une requête et une vue (leçon 6.6), pas d'entité |
| hésite entre les deux | commencer direct ; ajouter un cercle le jour où une règle ou un second canal arrive |

## 9. Les trois erreurs qui restent

### « Toute l'application suit la même architecture, pour la cohérence »

La cohérence qui compte est celle de la **règle des dépendances** : rien
dans le domaine ne connaît la base ni HTTP. Le nombre de cercles, lui,
peut varier d'une partie à l'autre. Un profil en six paquets n'est pas
plus cohérent avec les tours, il est plus long.

### « Les couches rendent le code plus lent »

Pas mesurablement : 6 µs dans les deux cas. Le reproche est ailleurs, et
il est plus grave : chaque champ se modifie à six endroits, et peut se
perdre à sept.

### « Sans couches, le domaine dépendra de la base »

Pas si on garde la règle des dépendances. Le profil direct ne connaît
pas la base : son stockage est derrière son propre type. Le jour où il
passe sur PostgreSQL, on ajoute un adaptateur et un contrat, comme à la
leçon 7.3, sans rien changer au gestionnaire.

## 10. Le lien avec la production

- **La revue de code** regarde le nombre de fichiers qu'un petit
  changement touche. Un champ qui en touche six dans une partie sans
  règles est un signal : la partie a plus de cercles qu'il ne lui en faut.
- **Les tests de correspondance** (une structure en entrée, la même en
  sortie, à travers chaque copie) sont courts et rapides ; un générateur
  peut en écrire un par champ.
- **Les outils de copie automatique** (réflexion, génération de code)
  suppriment l'oubli, mais pas la dépendance entre les structures : un
  champ renommé d'un côté se perd de l'autre, en silence, si rien ne le
  teste.
- **Le proverbe de Go** : « un peu de copie vaut mieux qu'un peu de
  dépendance ». Il s'applique aux paquets ; à l'intérieur d'une partie
  simple, une seule structure vaut mieux que six copies.

## 11. Ce qu'il faut retenir

1. La règle des dépendances compte ; le nombre de cercles se choisit.
2. Chaque copie de champ est un endroit où le champ se perd sans erreur ;
   un test le suit partout.
3. Les couches coûtent en fichiers modifiés, pas en microsecondes.
4. Des cercles où les règles sont riches, du code direct ailleurs.
5. Une correspondance dont personne ne se sert encore n'est vérifiée que
   par son propre test.

## 12. Approfondissement

### L'unité de travail

Un cas d'utilisation qui écrit deux agrégats de façon atomique (un tour
et un ordre dans l'outbox) a besoin d'une transaction qui traverse les
ports. La Clean Architecture la place dans le cas d'utilisation, sans
nommer la base : une interface `UnitOfWork` avec une fonction
`Do(ctx, func(rounds Rounds, outbox Outbox) error)`, que l'adaptateur
PostgreSQL implémente avec `pgx.BeginFunc` (leçon 5.2). C'est un cercle
de plus qui se justifie, parce qu'il protège une règle : tout ou rien.

### Présentateur ou valeur de retour

Le présentateur (un port de sortie que le cas d'utilisation appelle) est
utile quand un même cas d'utilisation doit produire plusieurs formes de
sortie, au fil de son déroulement. Pour une requête qui rend une
réponse, une simple valeur de retour suffit, et économise une interface
et une structure.

## 13. Le réflexe à installer

Avant d'ajouter un cercle, demande-toi :

1. Quelle règle protège-t-il, et qu'arrive-t-il si elle est enfreinte ?
2. Combien de fichiers un nouveau champ touchera-t-il ?
3. Chaque copie de champ a-t-elle un test qui la suit ?
4. Combien de canaux, et combien d'adaptateurs, cette partie aura-t-elle
   vraiment ?
5. Le domaine dépend-il de l'extérieur, avec ou sans ce cercle ?
