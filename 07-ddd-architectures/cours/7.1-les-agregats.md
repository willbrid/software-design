# Leçon 7.1 — Le modèle dans le code : des agrégats qui gardent leurs règles

## L'essentiel en deux minutes

**Le problème, en une phrase.** Quand les règles d'un tour de tontine
vivent dans le code qui l'utilise, chaque nouveau point d'entrée (une
application, l'USSD, un import) les réécrit à sa façon, et en oublie
toujours une.

**Trois images.**

- **Le cahier ouvert sur la table** : n'importe qui peut y écrire, et
  chacun connaît une partie du règlement. Au bout de quelques mois, des
  lignes y sont fausses, et personne ne sait qui les a écrites.
- **La caisse et la trésorière** : on ne met pas l'argent dans la caisse
  soi-même ; on le donne à la trésorière, qui vérifie le montant, note le
  nom, et refuse un deuxième paiement. Elle seule touche à la caisse.
- **Une caisse par tour, pas une pour cinq ans** : si chaque paiement
  devait rouvrir le coffre des cinq dernières années, on attendrait à la
  porte, et deux membres ne pourraient jamais payer en même temps.

**Le code, en quelques lignes.** Les champs du tour sont cachés ; la
seule façon de payer passe par une méthode qui garde les règles :

```go
// Contribute records the payment of member.
func (r *Round) Contribute(member string, amount int64) error {
    switch {
    case r.beneficiary != "":
        return ErrClosed
    case !r.members[member]:
        return ErrNotMember
    case amount != r.share:
        return ErrBadAmount
    case r.paid[member] > 0:
        return ErrAlreadyPaid
    }
    r.paid[member] = amount
    return nil
}
```

**Les règles à retenir.**

1. **Un agrégat est un groupe d'objets qui changent ensemble**, sous des
   règles qui doivent toujours être vraies (ses *invariants*). On ne le
   modifie que par sa racine.
2. **Les règles vivent dans l'agrégat**, pas dans les points d'entrée :
   un nouveau canal appelle les mêmes méthodes, et ne peut rien oublier.
3. **Un agrégat est une frontière de cohérence** : on le charge, on le
   change, on l'enregistre en entier, dans une transaction.
4. **Petit** : seulement ce qu'une règle oblige à changer ensemble. Un
   agrégat trop gros est lent à charger, et fait se heurter des
   changements qui n'ont rien à voir.

La suite le mesure avec trois canaux de paiement, et une tontine de cinq
ans.

---

Le niveau 4 a construit le modèle du domaine sur le papier : tontines,
tours, cotisations, prêts, et leurs règles (leçon 4.3). Le niveau 5 a
mis les règles qui le pouvaient dans la base ; le niveau 6 a construit
les points d'entrée. Ce niveau 7 se demande **où vivent les règles dans
le code**, et comment le code s'organise autour d'elles. Le problème de
cette leçon :

> **Comment être sûr que les règles d'un tour sont respectées, quel que
> soit le code qui le modifie ?**

Le module de la leçon est `l71`. Il n'a besoin que de la bibliothèque
standard. Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Le modèle anémique

Le paquet `anemic` garde un tour comme on l'écrit souvent d'abord : une
structure aux champs publics.

```go
// Round is one round of a tontine.
type Round struct {
    Number      int
    ShareFCFA   int64
    Members     []string
    Paid        map[string]int64 // what each member paid
    Closed      bool
    Beneficiary string // who received the pot, once paid out
    PotFCFA     int64
}
```

Les règles sont dans les fonctions qui l'utilisent, une par point
d'entrée. L'application a été écrite la première, avec soin :

```go
// AppContribute is the entry point of the application, written first and
// with care: amount, second payment, closed round.
func AppContribute(r *Round, member string, amount int64) error {
    switch {
    case r.Closed:
        return ErrClosed
    case amount != r.ShareFCFA:
        return ErrBadAmount
    case r.Paid[member] > 0:
        return ErrAlreadyPaid
    }
    r.Paid[member] = amount
    r.PotFCFA += amount
    return nil
}
```

Le canal USSD est arrivé un an plus tard, écrit par une autre équipe à
partir des écrans de l'opérateur :

```go
// USSDContribute is the entry point of the USSD channel, written a year
// later by another team, from the screens of the operator: it checks the
// amount.
func USSDContribute(r *Round, member string, amount int64) error {
    if amount != r.ShareFCFA {
        return ErrBadAmount
    }
    r.Paid[member] += amount
    r.PotFCFA += amount
    return nil
}
```

Et l'import du cahier papier, pour les paiements en espèces, fait
confiance au cahier :

```go
// ImportPaid is the import of the paper notebook of a treasurer, for the
// payments made in cash: it trusts the notebook.
func ImportPaid(r *Round, member string, amount int64) {
    r.Paid[member] = amount
    r.PotFCFA += amount
}
```

Chaque fonction est raisonnable, prise seule. Martin Fowler appelle ce
style un **modèle de domaine anémique** : des objets qui portent les noms
du domaine, mais presque aucun comportement, des « sacs » de champs, avec
les règles ailleurs, dans des services.

## 2. L'agrégat

Le paquet `round` garde le même tour comme un **agrégat** : un groupe
d'objets (ici, le tour, ses membres et leurs paiements) traités comme un
seul tout, avec des règles écrites une fois.

```go
// Round is one round of a tontine. Its invariants:
//   - only members pay, each once, exactly the share;
//   - the pot is the sum of what was paid;
//   - the pot goes out once, to a member, when everyone has paid;
//   - nothing changes once it is out.
type Round struct {
    number      int
    share       int64
    members     map[string]bool
    paid        map[string]int64
    beneficiary string
}
```

Les champs sont en minuscules : hors du paquet, personne ne peut écrire
`r.paid["x"] = 1`. Le compilateur garde la porte. Les seules
modifications possibles sont `Contribute` (ci-dessus) et `PayOut` :

```go
// PayOut gives the pot to beneficiary, once everyone has paid.
func (r *Round) PayOut(beneficiary string) error {
    switch {
    case r.beneficiary != "":
        return ErrClosed
    case !r.members[beneficiary]:
        return ErrBeneficiary
    case len(r.paid) < len(r.members):
        return ErrNotAll
    }
    r.beneficiary = beneficiary
    return nil
}
```

La cagnotte n'est plus un champ qu'on additionne à côté des paiements :
elle **se calcule** à partir d'eux, et ne peut donc plus diverger.

```go
// Pot is what the round holds: the sum of what was paid.
func (r *Round) Pot() int64 {
    var sum int64
    for _, a := range r.paid {
        sum += a
    }
    return sum
}
```

Eric Evans, dans sa *DDD Reference*, résume la règle : regrouper les
entités et les objets-valeurs en agrégats, choisir une **racine**, ne
laisser l'extérieur tenir de référence que vers elle, et lui confier la
garde des invariants de l'ensemble.

## 3. Mesure : trois canaux, mille tours

`cmd/channels` fait vivre 1 000 tours de 20 membres, avec ce qui arrive
vraiment : des paiements par les trois canaux, quelques doubles appuis
(ou une ligne recopiée deux fois dans le cahier), quelques mauvais
montants, un numéro qui n'est pas celui d'un membre, des versements
demandés trop tôt, et un paiement tardif après le versement. Les mêmes
commandes vont au modèle anémique, puis à l'agrégat, par les mêmes
canaux. À la fin, on vérifie les règles de chaque tour :

```text
anemic    rounds with a broken rule: 726/1000  map[a stranger paid:324 not the share:513 paid after the payout:81 paid out before a member paid:146 pot is not the sum:152]
aggregate rounds with a broken rule:   0/1000  map[]
```

**726 tours sur 1 000** finissent avec au moins une règle cassée dans le
modèle anémique :

- **513** ont un paiement qui n'est pas la part : l'import ne vérifie
  rien, et l'USSD **ajoute** un deuxième paiement au premier ;
- **324** ont un paiement d'un inconnu : ni l'USSD ni l'import ne
  vérifient le numéro ;
- **152** ont une cagnotte qui n'est pas la somme des paiements : l'import
  **remplace** un paiement et **ajoute** à la cagnotte ;
- **146** ont été versés alors qu'un membre n'avait pas payé : un
  paiement d'inconnu compte dans `len(r.Paid)` ;
- **81** ont reçu un paiement après le versement, par l'USSD.

Avec l'agrégat : **aucun**. Les trois canaux appellent `Contribute`, et
c'est le tour qui refuse.

L'application, le seul canal écrit avec soin, ne casse rien **seule**.
Ce sont les deux autres, plus tardifs et plus simples, qui cassent les
règles, et ils cassent aussi les tours payés par l'application. Une règle
écrite dans un point d'entrée ne protège que ce point d'entrée.

## 4. Mesure : quelle taille pour un agrégat ?

Un agrégat se charge, se modifie et s'enregistre **en entier**, et deux
modifications d'un même agrégat se départagent par une version (leçon
5.3, et la leçon 6.6 pour les écrans). Le paquet `store` garde chaque
agrégat comme un document JSON avec sa version :

```go
// Change loads id into a fresh value made by fresh, applies change, and
// saves, again from the load when another save came first.
func Change[T any](s *Store, id string, fresh func() *T, change func(*T) error) error {
    for {
        v := fresh()
        read, err := s.Load(id, v)
        if err != nil {
            return err
        }
        if err := change(v); err != nil {
            return err
        }
        if err := s.Save(id, v, read); !errors.Is(err, ErrConflict) {
            return err
        }
    }
}
```

Une tontine a cinq ans d'histoire : 260 tours de 30 membres, et 10 prêts
en attente. Un soir, les 30 membres paient le tour en cours et la
trésorière décide les 10 prêts, tous en même temps. `cmd/size` compare
deux choix d'agrégat : **toute la tontine** (ses tours, ses membres, ses
prêts) en un seul, ou **un agrégat par tour et un par prêt** :

```text
one tontine     40 changes  conflicts  316  bytes moved 133205687  697ms
round and loans 40 changes  conflicts   98  bytes moved     98998  2ms
```

- **Toute la tontine** : chaque paiement charge et réécrit cinq ans de
  tours, **133 Mo** déplacés pour 40 changements de quelques octets. Et
  chaque changement se heurte à tous les autres : **316 conflits**, autant
  de rechargements complets. Une décision de prêt se heurte à un
  paiement, alors qu'aucune règle ne les lie.
- **Un tour et des prêts** : **99 ko** déplacés, 2 ms. Il reste 98
  conflits : les 30 paiements visent **le même tour**, et doivent se
  départager. C'est voulu : la règle « chacun paie une fois, et le
  versement attend que tous aient payé » lie ces paiements. Les prêts,
  eux, ne se heurtent plus à rien.

Vaughn Vernon, dans *Effective Aggregate Design*, en fait une règle :
concevoir de **petits agrégats**, et ne grouper que ce qu'un **vrai
invariant** oblige à garder cohérent dans une même transaction.

## 5. La campagne

Dix mutations, dans l'agrégat et dans le stockage :

```text
étranger accepté                             tuee
montant positif suffit                       tuee
deuxième paiement accepté                    tuee
paiement après le versement                  tuee
versement avant que tous paient              tuee
bénéficiaire étranger                        tuee
deux versements                              tuee
version non comparée                         tuee
pas de nouvel essai                          tuee
version jamais augmentée                     tuee
10/10 tuees
```

Aucune survivante : chaque règle du commentaire de `Round` a son test,
écrit avec la règle. C'est l'autre gain de l'agrégat : les règles sont
**à un seul endroit**, et un seul fichier de tests les couvre toutes. Dans
le modèle anémique, il faudrait les tester trois fois, une par canal, et
chaque nouveau canal en demanderait une quatrième.

## 6. La grille

| Question | Réponse |
|---|---|
| Qu'est-ce qui doit changer ensemble, sous une règle ? | c'est un agrégat : le tour et ses paiements |
| Qu'est-ce qui change seul ? | un autre agrégat : un prêt |
| Qui peut modifier l'agrégat ? | seulement ses méthodes ; ses champs sont cachés |
| Où vit une règle qui ne concerne qu'un agrégat ? | dans une méthode de sa racine |
| Une valeur se déduit d'autres (la cagnotte) ? | elle se calcule, elle n'est pas stockée à côté |
| Une transaction modifie combien d'agrégats ? | un seul, de préférence |
| Une règle lie deux agrégats ? | voir l'approfondissement |

## 7. Les trois erreurs qui restent

### « Une structure simple et des services, c'est plus clair »

Plus clair à lire, jusqu'au deuxième point d'entrée. La section 3 : trois
canaux raisonnables, 726 tours sur 1 000 avec une règle cassée. La
clarté d'un modèle anémique se paie à chaque nouvel appelant.

### « Un agrégat, c'est un gros objet qui contient tout »

C'est l'inverse : la section 4 montre ce que coûte un agrégat qui
contient tout, en octets et en conflits. Un agrégat est **aussi petit
que ses règles le permettent**.

### « Les règles sont dans la base, l'agrégat ne sert à rien »

La base garde ce qu'elle sait exprimer : une clé unique (un paiement par
membre et par tour), une contrainte `CHECK` (le montant). Elle ne sait
pas dire « le versement attend que tous aient payé » sans un déclencheur
difficile à maintenir. Les deux se complètent : l'agrégat garde toutes
les règles, la base reste le dernier garde-fou pour celles qu'elle peut
exprimer (leçon 5.1).

## 8. Le lien avec la production

- **Le chargement d'un agrégat** se mesure : si charger un tour lit des
  milliers de lignes, l'agrégat est trop gros, ou l'historique doit
  sortir de lui (les anciens tours sont des données en lecture, pas des
  objets qu'on modifie).
- **Les conflits de version** se comptent par type d'agrégat : un taux
  élevé dit que des changements sans rapport partagent un agrégat.
- **Les canaux** (application, USSD, import, administration) appellent
  tous le même agrégat. Un canal qui « a besoin » d'écrire directement
  dans la base, pour aller plus vite, est un canal qui contournera les
  règles.
- **L'agrégat en base** : une ligne pour le tour, une ligne par paiement,
  et une colonne `version` sur le tour, incrémentée à chaque
  enregistrement (leçon 5.3) ; ou un document JSON, comme dans la
  mesure.

## 9. Ce qu'il faut retenir

1. Un agrégat groupe ce qui change ensemble sous une règle, et se
   modifie par sa racine seule.
2. Les règles vivent dans l'agrégat : chaque canal les reçoit sans les
   réécrire.
3. Un agrégat se charge et s'enregistre en entier, avec une version.
4. Petit : seulement ce qu'un vrai invariant oblige à garder ensemble.
5. Une valeur qui se déduit se calcule, elle ne se stocke pas à côté.

## 10. Approfondissement

### La règle qui lie deux agrégats

« Un membre ne reçoit la cagnotte qu'une fois par cycle » concerne tous
les tours d'un cycle, pas un seul. Trois réponses, de la plus simple à la
plus lourde :

1. **une contrainte en base** : `UNIQUE (cycle, beneficiary)` sur les
   versements. La base départage, et l'agrégat du tour traduit l'erreur ;
2. **un petit agrégat de plus** : le *cycle*, qui ne contient que la
   liste des bénéficiaires déjà servis. `PayOut` passe par lui. Il est
   petit, et ne se heurte qu'aux versements ;
3. **une vérification après coup** : on verse, puis un contrôle signale
   un double bénéficiaire, qu'une personne corrige. Evans le dit ainsi :
   à l'intérieur d'un agrégat, les règles s'appliquent tout de suite ; à
   travers les agrégats, les mises à jour se font de façon asynchrone.
   Le niveau 8 y reviendra.

### Entités et objets-valeurs

Le tour a une **identité** (le tour 261 de la tontine du marché) : c'est
une entité. Un montant, un numéro de téléphone, une devise n'en ont pas :
deux montants de 10 000 FCFA sont le même montant. Ce sont des
**objets-valeurs**, immuables, comme le `Phone` et l'`Amount` de la
leçon 6.2. La leçon 2.1 a posé cette distinction ; dans un agrégat, les
valeurs sont ce qu'on peut copier et partager sans risque.

## 11. Le réflexe à installer

Devant chaque règle du domaine, demande-toi :

1. Quels objets doivent changer ensemble pour qu'elle reste vraie ?
2. Par quelle méthode, sur quelle racine, passe chaque modification ?
3. Un nouveau canal pourrait-il la contourner ? (Si oui, un champ est
   exposé.)
4. Que charge-t-on pour la vérifier, et combien de changements sans
   rapport se heurteraient ?
5. Si elle lie deux agrégats : contrainte, petit agrégat, ou contrôle
   après coup ?
