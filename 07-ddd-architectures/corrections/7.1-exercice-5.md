# Correction 7.1 — Exercice 5 : les cagnottes qui ne tombaient pas juste

> Rappel de l'énoncé : des tours d'octobre cassés par trois canaux ;
> auditer, rejouer par l'agrégat, réparer, rédiger.

L'audit, le rejeu et leurs tests sont dans `ex5` du module de
correction, verts sous `go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **124 tours sur 160 cassés** : 86 avec un paiement qui n'est pas la
  part, 63 avec un inconnu, 27 versés avant qu'un membre ait payé, 18
  avec une cagnotte qui n'est pas la somme (195 000 FCFA d'écart).
- **Rejouées par l'agrégat, les mêmes commandes ne cassent rien** : 737
  refus, chacun avec sa raison.
- **Seuls 31 tours sont versés** : l'agrégat n'autorise le versement que
  quand chaque membre a payé la part. Les autres attendent qu'une
  personne règle le paiement refusé, et c'est le comportement voulu.

## 1. L'audit

```go
func Audit(played []Played) Report {
    r := Report{Rounds: len(played)}
    for _, p := range played {
        members := map[string]bool{}
        for _, m := range p.Round.Members {
            members[m] = true
        }
        var sum int64
        stranger, wrong := false, false
        for m, a := range p.Round.Paid {
            sum += a
            stranger = stranger || !members[m]
            wrong = wrong || members[m] && a != p.Round.ShareFCFA
        }
        early := false
        for m := range members {
            early = early || p.Round.Beneficiary != "" && p.Round.Paid[m] == 0
        }
        gap := p.Round.PotFCFA - sum
        if stranger {
            r.Strangers++
        }
        if wrong {
            r.WrongAmount++
        }
        if gap != 0 {
            r.PotGap++
            r.GapFCFA += max(gap, -gap)
        }
        if early {
            r.PaidOutEarly++
        }
        if stranger || wrong || gap != 0 || early {
            r.Broken++
        }
    }
    return r
}
```

## 2. Les chiffres

`cmd/october` audite le mois, puis le rejoue par l'agrégat :

```text
{Rounds:160 Broken:124 Strangers:63 WrongAmount:86 PotGap:18 PaidOutEarly:27 GapFCFA:195000}
replayed through the aggregate: 31 rounds paid out, refused map[already paid this round:274 amount is not the share:155 not a member of the tontine:82 not everyone has paid:218 round closed:8]
```

Les tours cassés le sont souvent par plusieurs règles à la fois : un
inconnu qui paie compte pour un membre, ce qui permet le versement
alors qu'un vrai membre n'a pas payé.

## 3. Le rejeu par l'agrégat

```go
// Replay sends the commands of the month to the aggregate, through the same
// three channels, and counts what the aggregate refused, by reason: what
// the members and the treasurers would have been told.
func Replay(played []Played) (refused map[string]int, paidOut int) {
    refused = map[string]int{}
    for _, p := range played {
        r := round.New(p.Number, Share, Members())
        for _, c := range p.Commands {
            var err error
            if c.Channel == "payout" {
                err = r.PayOut(c.Member)
            } else {
                err = r.Contribute(c.Member, c.Amount)
            }
            if err != nil {
                refused[reason(err)]++
            }
        }
        if r.Beneficiary() != "" {
            paidOut++
        }
    }
    return refused, paidOut
}
```

Les refus disent ce que les membres et les trésorières auraient lu :
274 « déjà payé » (doubles appuis, lignes recopiées), 155 « pas la
part », 82 « pas membre », 218 « tout le monde n'a pas payé » (des
versements demandés trop tôt, ou des tours bloqués par un paiement
refusé), 8 « tour clos ».

Les 31 tours versés sur 160 ne sont pas une régression : dans le modèle
anémique, une partie des versements partaient **à tort**. Un tour où un
membre a payé 5 000 FCFA au lieu de 10 000 reste ouvert jusqu'à ce que
le paiement soit complété ; la trésorière le voit sur son écran, au lieu
de le découvrir au versement.

## 4. Réparer octobre

Les 160 tours ne se « corrigent » pas par un script : un paiement d'un
inconnu est peut-être un membre qui a changé de numéro, un paiement en
double est peut-être un acompte du tour suivant. Pour chaque tour cassé,
l'audit produit une fiche (règle cassée, paiements en cause, écart), et
la trésorière décide : rembourser, réaffecter, compléter. Les tours
réparés sont alors **rechargés dans l'agrégat**, qui refuse ceux qui
violent encore une règle.

## 5. Le compte rendu

1. **Quoi** : en octobre 2026, 124 tours sur 160 ont fini avec au moins
   une règle cassée : paiements qui ne sont pas la part (86), paiements
   d'inconnus (63), versements avant que tous aient payé (27), cagnottes
   fausses (18, 195 000 FCFA d'écart).
2. **Cause** : les règles d'un tour étaient écrites dans chaque point
   d'entrée ; le canal USSD et l'import du cahier en vérifiaient moins que
   l'application, et cassaient aussi les tours payés par elle.
3. **Détection** : par les trésorières, au versement. Aucun contrôle ne
   vérifiait l'état des tours.
4. **Correction** : les trois canaux appellent l'agrégat du tour ; les
   champs du tour ne sont plus accessibles hors de son paquet ; les tours
   d'octobre sont réparés un par un avec les trésorières.
5. **Prévention** : tout nouveau canal passe par l'agrégat (une revue de
   code refuse un accès direct au stockage) ; l'audit tourne chaque nuit
   comme contrôle ; la base ajoute ce qu'elle peut garder (un paiement par
   membre et par tour, le montant égal à la part).

## Ce qu'il faut retenir

- Un canal qui vérifie moins casse aussi le travail des autres.
- L'agrégat refuse, avec une raison : les erreurs deviennent visibles au
  moment où elles arrivent.
- Des données cassées se réparent avec des personnes, puis se rechargent
  dans l'agrégat.
