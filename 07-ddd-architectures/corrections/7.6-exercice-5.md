# Correction 7.6 — Exercice 5 : la bascule du dimanche

> Rappel de l'énoncé : une bascule à 100 % sans ombre, avec la première
> migration ; mesurer, rejouer en ombre, rédiger.

L'audit et le rejeu sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **27 cagnottes sur 40 versées en trop, 580 000 FCFA** : le service
  comptait les annulations comme des paiements.
- **En ombre, les mêmes 40 cagnottes partent justes**, et l'équipe des
  paiements voit **35 différences** dès la première heure.
- **La cause** : la migration ; **la cause de la cause** : la bascule
  d'un coup, sans comparer.

## 1. L'audit

```go
func Audit(pots []Pot) Report {
    r := Report{Pots: len(pots)}
    for _, p := range pots {
        if over := p.PaidOutFCFA - p.InLedgerFCFA; over > 0 {
            r.Overpaid++
            r.OverpaidFCFA += over
        }
    }
    return r
}
```

## 2. Les chiffres, et le rejeu

`cmd/sunday` rejoue la journée deux fois :

```text
all at once, first migration   {Pots:40 Overpaid:27 OverpaidFCFA:580000}
in shadow, first migration     {Pots:40 Overpaid:0 OverpaidFCFA:0}  questions 40  mismatches 35
    t01-c04: module false, service true
    t03-c21: module false, service true
    t05-c11: module false, service true
```

- **À 100 % d'un coup** : 27 cagnottes versées au-delà du registre, pour
  580 000 FCFA ;
- **en ombre** : le module répond, les 40 cagnottes partent justes, et
  l'aiguillage note **35 différences**, toutes de la même forme : « non
  payé pour le module, payé pour le service ». Les trois premières
  suffisent à trouver la cause : ce sont les cotisations annulées.

## 3. La cause

**En une phrase** : la première migration du service comptait comme
payée toute cotisation passée une fois, y compris celles que l'opérateur
avait annulées ensuite.

**La cause de la cause** : la bascule s'est faite **d'un coup**, à 100 %,
sans ombre. Le défaut de la migration n'était pas visible dans les tests
du service (ils n'avaient pas d'annulation), et la seule comparaison qui
l'aurait montré, celle des réponses du module et du service sur les
vraies questions, n'a jamais tourné.

## 4. Le compte rendu

1. **Quoi** : le dimanche 22 novembre 2026, 27 cagnottes sur 40 ont été
   versées en trop, pour 580 000 FCFA : des cotisations annulées par
   l'opérateur ont été comptées payées.
2. **Cause** : la question « payé ? » des tontines a été basculée à 100 %
   vers le nouveau service des paiements, dont la migration comptait les
   annulations comme des paiements.
3. **Détection** : par les trésorières, au rapprochement avec le compte de
   l'opérateur. Aucune comparaison avec l'ancien module n'avait tourné.
4. **Correction** : la part du service est remise à 0 (le module était
   toujours en place) ; la migration est corrigée ; les 580 000 FCFA sont
   repris sur les tours suivants.
5. **Prévention** : toute bascule commence par une ombre, assez longue
   pour voir passer un dimanche de versements et des annulations ; la
   part n'augmente qu'avec zéro différence ; le plan de bascule est relu
   comme une migration de base (leçon 5.4).

## Ce qu'il faut retenir

- Une migration de données se compare sur les vraies questions, avant
  d'y croire.
- Garder l'ancien module branché rend le retour en arrière immédiat.
- La bascule d'un coup transforme un défaut de migration en incident.
