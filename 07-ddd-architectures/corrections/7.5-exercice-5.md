# Correction 7.5 — Exercice 5 : la jointure du dimanche

> Rappel de l'énoncé : les paiements déplacent les annulations dans une
> table à part ; la jointure des tontines ne le sait pas ; mesurer,
> expliquer, empêcher.

L'audit et son test sont dans `ex5` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **24 tours sur 40 versés en trop, 725 000 FCFA**, le pire à 75 000 FCFA :
  la jointure compte 969 cotisations payées, il y en a 934.
- **La migration des paiements était juste**, et le module des paiements
  répondait juste. La jointure des tontines lisait une table qui ne lui
  appartenait pas.
- **Ce qui l'aurait empêché** : la question `ConfirmedAmong` de
  l'exercice 2, et un rôle par module, qui aurait refusé la jointure dès
  le premier jour.

## 1. L'audit

```go
func Audit(rounds []Round) Report {
    var r Report
    for _, round := range rounds {
        over := int64(round.Counted-round.Paid) * round.ShareFCFA
        if over <= 0 {
            continue
        }
        r.Rounds++
        r.OverpaidFCFA += over
        if over > r.WorstFCFA {
            r.Worst, r.WorstFCFA = round.Tontine, over
        }
    }
    return r
}
```

## 2. Les chiffres

`cmd/sunday` :

```text
40 rounds: 969 contributions counted by the join, 934 paid
{Rounds:24 OverpaidFCFA:725000 Worst:21 WorstFCFA:75000}
```

35 cotisations annulées par l'opérateur ont été comptées payées : leur
argent n'est plus là, et les cagnottes ont été versées comme s'il y
était.

## 3. La cause

La migration a changé le **sens** d'une colonne : `outcome = 'confirmed'`
voulait dire « payé » ; depuis samedi, il veut dire « l'opérateur a
d'abord confirmé », et une annulation est une ligne de
`payments.reversal`. L'équipe des paiements a mis à jour **son** module,
qui répond juste (la requête `AskThePayments`). Elle ne savait pas que
les tontines lisaient sa table : rien dans son code ne le disait, et la
première version donnait à toute l'application un seul rôle qui lisait
tout.

C'est la leçon 6.4 à l'intérieur d'un programme : un changement de sens
sans changement de forme. Entre deux modules qui partagent une table, il
n'y a même pas de contrat à vérifier.

## 4. Ce qui l'aurait empêché

- **Dans le code** : les tontines demandent `ConfirmedAmong` aux
  paiements (exercice 2). La réponse suit le sens que les paiements
  donnent à leurs tables, quel qu'il soit.
- **Dans la base** : un rôle par module, sans `USAGE` sur le schéma des
  autres. La jointure aurait échoué le jour où elle a été écrite, avec
  `permission denied for schema payments`, au lieu de réussir pendant des
  mois et de mentir un dimanche.
- **Dans les tests** : le test d'architecture ne voit pas une requête SQL ;
  c'est la base qui tient cette frontière-là.

## 5. Le compte rendu

1. **Quoi** : le dimanche 15 novembre 2026, 24 cagnottes sur 40 ont été
   versées en trop, pour 725 000 FCFA : 35 cotisations annulées par
   l'opérateur ont été comptées payées.
2. **Cause** : le samedi, le module des paiements a déplacé les
   annulations dans une table à part ; les tontines comptaient les
   paiements par une jointure directe sur la table du registre, qui
   comptait désormais les annulations comme des paiements.
3. **Détection** : par les trésorières, en rapprochant les versements du
   compte chez l'opérateur.
4. **Correction** : les tontines demandent `ConfirmedAmong` au module des
   paiements ; les 725 000 FCFA sont repris sur les prochains tours, avec
   l'accord des bureaux.
5. **Prévention** : un rôle PostgreSQL par module, sans accès aux schémas
   des autres ; toute lecture d'un autre module passe par sa face
   publique ; une migration d'un module ne peut plus casser que ce module.

## Ce qu'il faut retenir

- Une table lue par un autre module a deux propriétaires, dont un qui
  l'ignore.
- Une migration juste peut casser le lecteur que personne ne connaissait.
- Le rôle par module rend la frontière de la base aussi réelle que celle
  du code.
