# Correction 7.3 — Exercice 5 : l'« upsert » du mardi

> Rappel de l'énoncé : un enregistrement « simplifié » en une
> instruction ; des paiements annoncés reçus et perdus ; mesurer,
> expliquer, empêcher.

L'audit et le test qui l'aurait empêché sont dans `ex5` du module de
correction, verts sous `go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **945 paiements perdus sur 1 000**, dans les 50 tours : chaque membre a
  reçu « Cotisation reçue », et 55 paiements seulement sont dans la base.
- **La cause** : l'instruction ne compare plus la version. Chaque
  enregistrement écrase le précédent, avec l'état lu avant lui.
- **Le contrat du port**, lancé sur PostgreSQL dans la CI, échoue sur
  deux clauses et aurait arrêté le déploiement.

## 1. L'audit

```go
func Audit(answers []Answer, paid map[string][]string) Report {
    var r Report
    for _, ps := range paid {
        r.Stored += len(ps)
    }
    broken := map[string]bool{}
    for _, a := range answers {
        if !a.Accepted {
            continue
        }
        r.Accepted++
        if !slices.Contains(paid[a.Round], a.Member) {
            r.Lost++
            broken[a.Round] = true
        }
    }
    r.Rounds = len(broken)
    return r
}
```

## 2. Les chiffres

`cmd/evening` rejoue la soirée avec l'« upsert », puis avec l'adaptateur
de la leçon :

```text
upsert   {Accepted:1000 Stored:55 Lost:945 Rounds:50}
pgstore  {Accepted:1000 Stored:1000 Lost:0 Rounds:0}
```

Les vingt membres d'un tour paient presque en même temps. Chacun charge
le tour **vide**, y ajoute son paiement, et l'enregistre : le dernier
arrivé écrase les autres. Il reste en moyenne un peu plus d'un paiement
par tour.

## 3. La cause

```sql
INSERT INTO round (id, version, state) VALUES ($1, $2 + 1, $3)
ON CONFLICT (id) DO UPDATE SET state = EXCLUDED.state, version = round.version + 1
```

L'ancienne instruction disait `UPDATE ... WHERE id = $1 AND version = $2`,
et répondait « conflit » quand aucune ligne ne correspondait. La
nouvelle **augmente** la version, mais ne la **compare** plus : elle
réussit toujours. Le service ne voit jamais de conflit, ne recharge
jamais, et chaque enregistrement remplace l'état complet du tour par
celui qu'il avait lu. C'est la mise à jour perdue de la leçon 5.3, cachée
dans un adaptateur.

Les tests de l'application passaient, parce qu'ils tournent sur
`memstore`, qui n'avait pas changé. Le contrat du port existait ; une
explication probable, et la plus courante, est que la
CI ne le lançait que sur `memstore`, la tâche PostgreSQL ayant été
retirée « parce qu'elle était lente ».

## 4. Le test qui aurait arrêté le déploiement

```go
// The contract of the port, run on the upsert in CI, would have stopped
// the deploy.
func TestTheContractCatchesTheUpsert(t *testing.T) {
    broken := roundstest.Check(func() app.Rounds { return Upsert{pgstore.Rounds{Pool: pg.ForTest(t, pgstore.Schema)}} }, true)
    if len(broken) == 0 {
        t.Error("the contract passes on the upsert")
    }
    for _, b := range broken {
        t.Log(b)
    }
}
```

```text
=== RUN   TestTheContractCatchesTheUpsert
    audit_test.go:31: a save from an old version is accepted: <nil>
    audit_test.go:31: 20 members paid at once, the pot holds 30000 FCFA of 200000
--- PASS: TestTheContractCatchesTheUpsert (0.35s)
PASS
ok      example/hex73/ex5       0.354s
```

Deux clauses cassent : l'enregistrement d'une version périmée est
accepté, et vingt paiements simultanés ne laissent que 30 000 FCFA sur
200 000. Le contrat sur PostgreSQL tourne en moins d'une seconde : sa
lenteur était celle d'une ancienne tâche qui recréait la base à chaque
test, pas celle du contrat.

## 5. Le compte rendu

1. **Quoi** : le mardi 10 novembre 2026 au soir, 945 paiements sur 1 000
   ont été annoncés « reçus » aux membres et ne sont pas enregistrés ; les
   50 tours concernés montrent presque tous les membres comme non payés.
   L'argent, lui, est arrivé chez l'opérateur.
2. **Cause** : l'adaptateur PostgreSQL du stockage des tours a été réécrit
   en une instruction `INSERT ... ON CONFLICT DO UPDATE` qui ne compare
   plus la version : les enregistrements simultanés s'écrasent.
3. **Détection** : par les trésorières, le soir même. Les tests de
   l'application passaient sur l'adaptateur en mémoire ; le contrat ne
   tournait plus sur PostgreSQL dans la CI.
4. **Correction** : retour à l'instruction conditionnelle ; les 945
   paiements sont reconstitués à partir des rappels de l'opérateur, qui
   portent l'identifiant de chaque cotisation.
5. **Prévention** : le contrat du port tourne sur PostgreSQL à chaque
   fusion, et la CI refuse de fusionner sans lui ; un test de charge
   (vingt paiements simultanés sur un tour) fait partie du contrat ; une
   alerte compare chaque soir les paiements annoncés aux paiements
   enregistrés.

## Ce qu'il faut retenir

- Un adaptateur peut casser une règle que le domaine garde : la version
  est sa responsabilité.
- Les tests sur les faux ne voient que les faux ; le contrat doit tourner
  sur le vrai.
- Un test lent se répare ; un test retiré laisse passer l'incident
  suivant.
