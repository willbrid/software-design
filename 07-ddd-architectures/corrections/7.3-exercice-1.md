# Correction 7.3 — Exercice 1 : port, adaptateur, ou rien ?

> Rappel de l'énoncé : huit éléments à classer ; trois pourquoi ; un
> *mock* ou un faux pour le port `Rounds`.

## En bref

- **Un port est une interface de l'application**, un adaptateur une
  implémentation pour une technologie ou un canal.
- **Le domaine et l'assemblage ne sont ni l'un ni l'autre** : l'un est au
  centre, l'autre en dehors de tout.
- **Un faux qui passe le contrat vaut mieux qu'un mock** pour un port de
  stockage : il vérifie ce qu'on obtient, pas comment on l'a demandé.

## 1.a — Huit éléments

| # | Élément | Nature |
|---|---|---|
| 1 | `app.Rounds` | **port** (piloté) : ce dont l'application a besoin pour stocker |
| 2 | `pgstore.Rounds` | **adaptateur piloté** : le port sur PostgreSQL |
| 3 | `httpapi.New` | **adaptateur qui pilote** : HTTP vers le service |
| 4 | `round.Round` | **domaine** : ni port ni adaptateur |
| 5 | `sms.Recorder` | **adaptateur piloté**, de test, du port `Notifier` |
| 6 | `Clock` dans `app` | **port** (piloté) : l'heure vient de l'extérieur |
| 7 | `main` | **l'assemblage** : il choisit les adaptateurs et les branche |
| 8 | le gestionnaire des rappels de l'opérateur | **adaptateur qui pilote** : un système extérieur appelle l'application. Sa couche anti-corruption (leçon 7.2) en fait partie |

## 1.b — Trois pourquoi

1. **`Rounds` dans `app`** : c'est l'application qui sait ce dont elle a
   besoin (charger un tour, l'enregistrer avec sa version). Si
   l'interface était dans `pgstore`, `app` importerait `pgstore`, et
   dépendrait de pgx : le sens des dépendances serait inversé. Les *Go
   Code Review Comments* disent la même chose : l'interface appartient au
   paquet qui l'utilise.
2. **Le plantage** : le faux naïf rend **le même** `*round.Round` à
   chaque `Load`. Vingt goroutines modifient la même table de paiements en
   même temps ; le runtime de Go détecte des écritures concurrentes sur
   une table et arrête le programme. Le faux fidèle rend une copie, comme
   une base rend des lignes.
3. **Cinq essais** : en mémoire, un `Load` puis un `Save` prennent
   quelques microsecondes ; la fenêtre pendant laquelle un autre `Save`
   peut s'intercaler est minuscule. Sur PostgreSQL, chaque aller-retour
   prend des millisecondes, et vingt paiements simultanés se heurtent bien
   plus souvent. Un faux reproduit le **comportement**, pas les
   **délais**.

## 1.c — Mock ou faux ?

| | Mock généré | Faux en mémoire |
|---|---|---|
| ce qu'il vérifie | que `Save` a été appelé, avec tels arguments | que le tour chargé ensuite contient le paiement |
| après un changement d'implémentation (un `Save` en deux appels) | le test casse, alors que le comportement est le même | le test passe |
| la concurrence, la version | il faut la programmer à la main dans chaque test | elle est dans le faux, une fois, vérifiée par le contrat |
| la fidélité au vrai | rien ne la garantit | le contrat la vérifie sur le faux et sur PostgreSQL |

Pour un port de stockage, le faux est meilleur : on teste **l'état** qui
en résulte. Un mock reste utile pour un port dont on veut vérifier
**l'appel** lui-même, et qui n'a pas d'état à relire : « un SMS est parti
vers ce numéro » se vérifie très bien avec `sms.Recorder`, qui est un
enregistreur plus qu'un mock.

## Ce qu'il faut retenir

- Un port appartient à l'application, un adaptateur à une technologie.
- Un faux rend des copies, comme le vrai.
- On teste l'état obtenu ; un contrat garde le faux fidèle.
