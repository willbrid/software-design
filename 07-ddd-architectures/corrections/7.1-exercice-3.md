# Correction 7.1 — Exercice 3 : l'adhésion

> Rappel de l'énoncé : remplacer trois fonctions d'un service par
> l'agrégat `Membership`.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Les trois règles sont dans l'agrégat** : unicité et plafond dans
  `Add`, la trésorière qui reste dans `Remove`, une seule trésorière dans
  `NameTreasurer`.
- **« Exactement une trésorière » est dans la forme des données** : un
  seul champ `treasurer`, au lieu d'un booléen par membre qu'il faudrait
  garder cohérent.
- **`Phones` rend une copie** : sinon, l'appelant modifie l'agrégat sans
  passer par ses méthodes.

## 1. La solution

```go
// Add adds phone.
func (m *Membership) Add(phone string) error {
    switch {
    case slices.Contains(m.phones, phone):
        return ErrAlreadyMember
    case len(m.phones) >= MaxMembers:
        return ErrFull
    }
    m.phones = append(m.phones, phone)
    return nil
}
```

```go
// Remove removes phone.
func (m *Membership) Remove(phone string) error {
    i := slices.Index(m.phones, phone)
    switch {
    case i < 0:
        return ErrNotMember
    case phone == m.treasurer:
        return ErrTreasurerStays
    }
    m.phones = slices.Delete(m.phones, i, i+1)
    return nil
}
```

```go
// NameTreasurer makes phone the treasurer, in place of the one before:
// there is one treasurer, always.
func (m *Membership) NameTreasurer(phone string) error {
    if !slices.Contains(m.phones, phone) {
        return ErrNotMember
    }
    m.treasurer = phone
    return nil
}
```

Le service mettait un booléen `Treasurer` sur chaque membre : rien
n'empêchait d'en avoir deux, ou aucun. L'agrégat garde **un** nom de
trésorière. L'invariant « exactement une » n'a plus besoin d'être
vérifié : il ne peut pas être faux. C'est souvent le meilleur agrégat :
celui dont la représentation rend les états faux impossibles à écrire.

## 2. Migrer les tontines existantes

Les données d'aujourd'hui peuvent violer les règles que l'agrégat
garantit. Avant de basculer :

1. **un audit** liste les tontines en défaut : membres en double, aucune
   ou plusieurs trésorières, plus de 50 membres ;
2. **une décision humaine** pour chacune : le bureau dit qui est la
   trésorière ; les doublons se fusionnent ; une tontine de plus de 50
   membres est gardée telle quelle, mais `Add` refusera d'en ajouter ;
3. **le chargement** construit l'agrégat à partir des données réparées,
   et refuse (bruyamment) une tontine encore en défaut ;
4. **les trois fonctions du service** sont retirées, et leurs écrans
   appellent l'agrégat.

C'est le schéma `NOT VALID` puis `VALIDATE` de la leçon 5.4 : la règle
protège l'avenir tout de suite, on répare le passé, puis on l'impose au
passé aussi.

## Ce qu'il faut retenir

- Une représentation qui rend l'état faux impossible vaut mieux qu'une
  vérification.
- Un agrégat ne rend jamais ses parties modifiables : des copies.
- Les données existantes se réparent avant que l'agrégat ne les charge.
