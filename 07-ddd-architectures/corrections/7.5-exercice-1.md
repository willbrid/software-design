# Correction 7.5 — Exercice 1 : qui arrête quoi ?

> Rappel de l'énoncé : six raccourcis et ce qui les arrête ; trois
> pourquoi ; fusionner deux modules qui écrivent ensemble.

## En bref

- **Trois gardiens, trois frontières** : le compilateur pour l'intérieur,
  le test pour les dépendances entre modules, PostgreSQL pour les tables.
- **Copier du code ne contourne pas la base** : la requête copiée échoue
  avec le rôle du module.
- **Deux modules qui écrivent toujours ensemble sont peut-être un seul
  module**, ou un événement entre eux.

## 1.a — Six raccourcis

| # | Raccourci | Qui l'arrête |
|---|---|---|
| 1 | importer `payments/internal/ledger` | **le compilateur** : `use of internal package ... not allowed` |
| 2 | les paiements importent les tontines | **le test d'architecture** (section 5 de la leçon) ; Go l'accepte, faute de cycle |
| 3 | `SELECT ... FROM payments.ledger` avec le rôle des tontines | **PostgreSQL** : `permission denied for schema payments` |
| 4 | les prêts importent les tontines, non prévu | **le test d'architecture** |
| 5 | copier la requête du registre dans les tontines | **PostgreSQL**, à la première exécution : la copie lit le schéma des paiements avec le rôle des tontines. Le code, lui, compile |
| 6 | `main` importe les trois modules | **rien**, et c'est voulu : `main` est hors des modules, c'est lui qui assemble |

La ligne 5 montre pourquoi le rôle par module compte : le compilateur et
le test lisent les imports, pas le texte des requêtes. Sans rôle par
module, la requête copiée marche, et la frontière n'est plus tenue que
par la revue de code.

## 1.b — Trois pourquoi

1. **L'interface dans les tontines** : avec elle, les tontines ne
   dépendent pas du module des paiements, seulement de la question
   qu'elles posent. Elles se testent avec un faux d'une ligne, et le
   module des paiements peut changer tout ce qui n'est pas cette question.
   C'est la règle de Go de la leçon 7.3 : l'interface appartient à qui
   l'utilise.
2. **Trois paquets dans les deux versions** : le nombre est le même, pas
   les paquets. Dans la première version, ce sont les **trois modules**,
   tontines et prêts compris. Dans la version modulaire, ce sont **les
   paiements et `main`** : aucun autre module. Ce qui compte n'est pas le
   nombre de paquets à recompiler, c'est le nombre d'**équipes** à
   prévenir : une contre trois.
3. **Le `search_path`** : les requêtes de `internal/` nomment `ledger`,
   pas `payments.ledger`. Le module ne connaît pas le nom de son propre
   schéma ; les tests lui en donnent un aléatoire (leçon 5.1), la
   production lui donne `payments`, sans changer une ligne. Et une requête
   qui nommerait un autre schéma se repère d'un coup d'œil.

## 1.c — Fusionner ?

Ça dépend de **pourquoi** ils écrivent ensemble :

- si **chaque** clôture de tour écrit un versement, et qu'aucun des deux
  n'a de sens sans l'autre, la frontière est mal placée : le versement du
  tour appartient aux tontines, et le module des paiements ne garde que
  ce qui parle à l'opérateur. Déplacer une table vaut mieux que fusionner
  deux modules entiers ;
- si les paiements ont leur vie propre (opérateurs, annulations,
  réconciliation), la clôture écrit un **ordre** dans son outbox (leçon
  5.2), dans sa transaction, et les paiements le traitent ensuite. Les
  deux restent séparés, au prix d'un délai que le niveau 8 apprend à
  gérer.

Fusionner deux modules parce qu'une transaction les traverse, c'est
souvent perdre une frontière utile pour garder une atomicité qu'un ordre
dans l'outbox donnait aussi.

## Ce qu'il faut retenir

- Chaque frontière a son gardien ; sans rôle par module, les requêtes
  copiées passent.
- On compte les équipes à prévenir, pas les paquets à recompiler.
- Une transaction entre deux modules dit que la frontière est mal placée,
  ou qu'il faut un ordre dans l'outbox.
