# Correction 7.6 — Exercice 3 : verser sans réponse

> Rappel de l'énoncé : une décision de versement qui interroge cotisation
> par cotisation, et compte une erreur comme un paiement.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Une question pour tout le tour**, au lieu d'une par cotisation.
- **Une absence de réponse n'est ni oui ni non** : `ErrUnavailable`, et la
  cagnotte attend.
- **Le code d'avant n'était pas faux dans le monolithe** ; il l'est devenu
  le jour où l'appel a traversé le réseau.

## 1. La solution

```go
// Ready reports whether every contribution of a round is paid. It asks
// once for the whole round, and returns ErrUnavailable when the payments
// do not answer: the pot is never paid out on a missing answer.
func Ready(ctx context.Context, p Payments, round []string) (bool, error) {
    paid, err := p.ConfirmedAmong(ctx, round)
    if err != nil {
        return false, ErrUnavailable
    }
    for _, c := range round {
        if !paid[c] {
            return false, nil
        }
    }
    return true, nil
}
```

## 2. Était-il faux dans le monolithe ?

**Non**, en pratique : le module ne renvoyait jamais d'erreur, et
`err == nil` était toujours vrai. La condition `err == nil && !paid`
lisait comme « si ce n'est pas payé » ; personne n'avait à se demander ce
que voulait dire une erreur.

Mais le code contenait déjà une **décision** sur l'erreur, la pire : une
erreur compte comme un paiement, et la cagnotte part. Le monolithe la
cachait ; le réseau l'a rendue réelle. C'est pourquoi on relit chaque
appelant avant d'extraire un module : le comportement sur erreur est
souvent écrit, sans avoir été choisi.

## Ce qu'il faut retenir

- Un appelant écrit contre un module qui n'échoue pas a quand même une
  règle sur l'erreur : il faut la lire.
- Sans réponse, on ne décide pas.
- Une question par tour, pas une par cotisation.
