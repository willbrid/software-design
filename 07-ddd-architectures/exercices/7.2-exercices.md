## Exercice 2 — Code : un second opérateur

*Niveau 2. Écrire une couche anti-corruption ; les tests sont fournis.*

Un second opérateur, kash, arrive. Ses rappels ont leurs propres mots et
leurs propres unités :

```go
// KashCallback is what kash sends: its own words, its own units.
type KashCallback struct {
    Reference   string `json:"reference"`    // the contribution
    Phone       string `json:"phone"`        // +237677123456, or 677123456
    AmountMinor int64  `json:"amount_minor"` // in centimes of the currency
    Currency    string `json:"currency"`
    State       string `json:"state"` // OK, KO, WAIT, CANCELLED
}
```

```go
// Translate turns a kash callback into an event: OK is confirmed, KO
// failed, WAIT waiting, CANCELLED reversed. The phone is +237 and nine

// refused. Anything else is an error, and the callback is kept aside.
func Translate(c KashCallback) (payments.Event, error) {
    return payments.Event{Contribution: c.Reference, Phone: c.Phone, AmountFCFA: c.AmountMinor, Outcome: payments.Confirmed}, nil
}
```

## Exercice 3 — Refactoring : les SMS sans l'opérateur

*Niveau 3. Réécrire un paquet pour qu'il ne dépende plus de ce qui ne le
regarde pas ; les tests sont fournis.*

Les SMS envoyés après un paiement passent encore par le membre partagé et
les statuts de l'opérateur :

```go
// Message is the SMS after a payment whose outcome is o: in the member's
// language, one per outcome (confirmed, failed, reversed, waiting).
//
// Today it builds a shared member to call the code of before.
func Message(c Contact, o payments.Outcome) string {
    m := model.Member{Name: c.Name, Language: c.Language}
    switch o {
    case payments.Confirmed:
        m.LastPayment = operator.Successful
    case payments.Failed:
        m.LastPayment = operator.Failed
    }
    return messageOfBefore(m)
}
```

Les tests de `ex3/notify_test.go` vérifient les messages, et un test
d'architecture lit les imports du paquet :

## Exercice 4 — Design : la carte des contextes

*Niveau 4. Aucune ligne de code : une carte et ses relations.*

L'application des tontines a aujourd'hui : la gestion des tontines et des
tours ; les paiements par deux opérateurs ; le contrôle d'identité, fait
par un prestataire externe ; les SMS, envoyés par un agrégateur ; la
comptabilité, exportée chaque mois vers le logiciel d'un cabinet ; les
prêts.

Dessine la carte des contextes (un diagramme en texte suffit) : chaque
contexte, ce qu'il possède, les relations entre eux (qui fournit quoi à
qui), les couches anti-corruption, et la clé que deux contextes partagent
quand ils parlent de la même personne. Dis quelle équipe possède quoi,
pour une entreprise de huit développeurs.
