# Exercices 7.1 — Les agrégats

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 7.1](../cours/7.1-les-agregats.md) (`anemic`, `round`, `store`),
recopiés tels quels dans le module des exercices. Ils n'ont besoin que de
la bibliothèque standard. Tout le code ci-dessous compile et passe
`go vet` ; les tontines, les membres et l'incident sont **fictifs**.

## Exercice 1 — Compréhension : où vit la règle ?

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Six règles

Pour chaque règle, dis dans quel agrégat elle vit (le tour, le prêt,
l'adhésion, un autre), ou si elle lie plusieurs agrégats.

1. Un membre ne paie qu'une fois par tour.
2. Un prêt ne dépasse pas la limite de la tontine.
3. Une tontine a au plus trois prêts ouverts à la fois (leçon 5.3).
4. Le bénéficiaire d'un tour est un membre de la tontine.
5. Chaque membre reçoit la cagnotte une fois par cycle.
6. Une tontine a exactement une trésorière.

### 1.b — Trois pourquoi

1. Pourquoi l'application, le seul canal écrit avec soin, ne protège-t-elle
   pas les tours qu'elle a payés ?
2. Pourquoi la cagnotte de `round.Round` n'est-elle pas un champ ?
3. Pourquoi reste-t-il 98 conflits avec un agrégat par tour ?

### 1.c — Une proposition

Un développeur propose de garder le modèle anémique, et d'ajouter une
fonction `Validate(r *Round) error` que chaque canal appellerait avant
d'enregistrer. Qu'en penses-tu ?

## Exercice 3 — Refactoring : l'adhésion

*Niveau 3. Écrire l'agrégat qui remplace un service ; les tests sont
fournis.*

Les membres d'une tontine sont gérés aujourd'hui par trois fonctions
d'un service, chacune écrite pour un écran :

```go
// AddMember adds phone, as the application does.
func AddMember(t *Tontine, phone string) error {
    if len(t.Members) >= MaxMembers {
        return ErrFull
    }
    t.Members = append(t.Members, Member{Phone: phone})
    return nil
}
```

```go
// NameTreasurer makes phone the treasurer, as the bureau does.
func NameTreasurer(t *Tontine, phone string) error {
    for i := range t.Members {
        if t.Members[i].Phone == phone {
            t.Members[i].Treasurer = true
            return nil
        }
    }
    return ErrNotMember
}
```

## Exercice 4 — Design : les agrégats des prêts et des pénalités

*Niveau 4. Aucune ligne de code : une liste d'invariants et des
frontières.*

Les règles :

- un prêt est demandé, accordé ou refusé par la trésorière, puis
  remboursé ;
- une tontine a au plus trois prêts ouverts ;
- un membre qui a un prêt en retard ne peut pas en demander un autre ;
- une cotisation en retard coûte 500 FCFA par jour, plafonnés à 5 000 FCFA
  par tour (leçon 6.5) ;
- les pénalités d'un mois sont versées dans la caisse de la tontine ;
- le relevé d'un membre montre ses cotisations, ses pénalités et ses
  prêts.

Propose les agrégats, avec pour chacun ses invariants et ce qu'il
contient. Pour chaque règle qui lie deux agrégats, choisis entre une
contrainte en base, un petit agrégat de plus, et un contrôle après coup,
et justifie.

## Exercice 5 — Incident : les cagnottes qui ne tombaient pas juste

*Niveau 7. Un incident à mesurer avec les données, puis à corriger.*

Début novembre 2026, plusieurs trésorières signalent que la cagnotte
affichée ne correspond pas aux paiements, que des inconnus apparaissent
dans la liste, et qu'un tour a été versé alors qu'un membre n'avait pas
payé. Les tours d'octobre sont gérés par le modèle anémique de la leçon,
et ses trois canaux.

`ex5/month.go` rejoue octobre : 40 tontines, quatre tours chacune.

```go
// Played is one round of the month: its commands, and the round they left.
type Played struct {

}
```
