# Exercices 5.1 — Du modèle au schéma

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 5.1](../cours/5.1-du-modele-au-schema.md) (`schema`, `tontine`,
`loose`, `strict`, `internal/pg`), recopiés tels quels dans le module des
exercices. Ils demandent le même PostgreSQL 17 que la leçon. Tout le code
ci-dessous compile et passe `go vet` ; les tontines, les membres et
l'incident sont **fictifs**.

---

## Exercice 1 — Compréhension : où vit chaque règle ?

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Dix règles

Pour chaque règle, dis où elle vit : `NOT NULL`, `CHECK`, `UNIQUE`, clé
étrangère simple, clé étrangère composée, transaction, ou Go seul. Si
c'est une contrainte, écris-la en une ligne.

1. Une tontine a un nom.
2. Un membre tient au plus cinq parts.
3. Dans un même marché, deux tontines n'ont pas le même nom.
4. La cotisation d'un membre vaut son nombre de parts multiplié par la
   part de la tontine.
5. Un versement va à un membre de la même tontine.
6. Au cours d'un tour, chaque membre reçoit la cagnotte une seule fois.
7. Sur un tour complet, la somme des versements est égale à la somme des
   cotisations.
8. Le téléphone d'un membre est confirmé par SMS avant son premier
   versement.
9. Une réunion a lieu un dimanche.
10. Un membre qui a quitté la tontine ne cotise plus.

### 1.b — Trois pourquoi

1. Pourquoi `CHECK (name <> '')` laisse-t-il entrer un membre sans nom ?
   Que faut-il ajouter ?
2. Pourquoi la première version du test de concurrence passait-elle sur
   la version qui vérifie avant d'écrire ? Qu'est-ce que cela dit d'un
   test de concurrence vert ?
3. Pourquoi la version qui vérifie en Go est-elle **plus lente** que celle
   qui laisse faire les contraintes ?

### 1.c — Le total juste

Dans la reprise du cahier, la cagnotte de mars vaut 250 000 FCFA dans
les deux schémas. Pourquoi ce total juste ne prouve-t-il rien ? Quel
contrôle aurait montré le problème ?

## Exercice 2 — Code : la table des pénalités

*Niveau 2. Écrire un schéma et sa traduction ; les tests sont fournis.*

La tontine ajoute des pénalités : un membre qui paie en retard (`late`),
ou qui manque la réunion (`absent`). Le squelette donne la table sans
aucune règle :

```sql
-- Exercise 2: give this table its rules, with the constraint names of the
-- statement.
CREATE TABLE penalty (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    member_id   BIGINT,
    cycle       DATE,
    reason      TEXT,
    amount_fcfa BIGINT
);
```

Et un store qui écrit sans traduire :

```go
// Penalize records a penalty for reason "late" or "absent".
// TODO: translate the refusals of the schema into the errors of the domain.
func (s *Store) Penalize(ctx context.Context, memberID int64, cycle, reason string, amountFCFA int64) error {
    month, err := tontine.ParseCycle(cycle)
    if err != nil {
        return err
    }
    _, err = s.db.Exec(ctx,
        `INSERT INTO penalty (member_id, cycle, reason, amount_fcfa) VALUES ($1, $2, $3, $4)`,
        memberID, month, reason, amountFCFA)
    return err
}
```

Les règles :

| Règle | Nom de la contrainte |
|---|---|
| la pénalité vise un membre qui existe | `penalty_member` |
| le cycle est un mois (le 1er du mois) | `penalty_cycle_is_a_month` |
| le motif est `late` ou `absent` | `penalty_reason` |
| le montant est positif | `penalty_positive` |
| un membre n'a qu'une pénalité par cycle et par motif | `penalty_once` |
| aucune colonne n'est vide | `NOT NULL` |

Les tests sont dans `ex2/penalty_test.go`, et les deux échouent sur le
squelette. Le second :

```go
func TestPenalizeTranslatesTheRefusals(t *testing.T) {
    s := fixture(t)
    ctx := context.Background()
    for _, c := range []struct {
        member int64
        cycle  string

        {42, "2026-04", "late", 2500, tontine.ErrUnknownMember},
        {1, "2026-04", "sick", 2500, tontine.ErrInvalid},
        {1, "2026-04", "late", -2500, tontine.ErrInvalid},
    } {
        err := s.Penalize(ctx, c.member, c.cycle, c.reason, c.amount)
        if c.want == nil && err != nil || c.want != nil && !errors.Is(err, c.want) {
            t.Errorf("Penalize(%d, %s, %s, %d) = %v, want %v", c.member, c.cycle, c.reason, c.amount, err, c.want)
        }
    }
}
```

1. Écris les contraintes de `penalty.sql` et la traduction de `Penalize`
   pour que les tests passent sous `go test -race -count=1 ./ex2/...`.
2. Un membre peut-il avoir, le même mois, une pénalité `late` **et** une
   pénalité `absent` ? Quelle contrainte le décide ?
3. Pourquoi `penalty_reason` est-il un `CHECK` et pas une table des
   motifs avec une clé étrangère ? Quand changerais-tu d'avis ?

## Exercice 3 — Refactoring : la cagnotte qui dérive

*Niveau 3. Changer où vit une donnée ; les tests sont fournis.*

Pour que la page d'accueil s'affiche vite, une version de l'application
range la cagnotte de chaque mois dans une table `cycle_total`, que le
store met à jour à chaque cotisation :

```sql
-- The pot of each cycle, kept up to date by the store so that the home
-- page of the application does not have to add up the contributions.
CREATE TABLE cycle_total (
    tontine_id BIGINT NOT NULL REFERENCES tontine (id),
    cycle      DATE   NOT NULL,
    pot_fcfa   BIGINT NOT NULL,
    PRIMARY KEY (tontine_id, cycle)
);
```

```go
// Contribute records a contribution, then adds it to the pot of the cycle.
func (s *Store) Contribute(ctx context.Context, memberID int64, cycle string, amountFCFA int64) error {
    month, err := tontine.ParseCycle(cycle)
    if err != nil {
        return err
    }
    if _, err := s.db.Exec(ctx,
        `INSERT INTO contribution (member_id, cycle, amount_fcfa) VALUES ($1, $2, $3)`,
        memberID, month, amountFCFA); err != nil {
        return err
    }
    _, err = s.db.Exec(ctx, `
        INSERT INTO cycle_total (tontine_id, cycle, pot_fcfa)
        SELECT tontine_id, $2, $3 FROM member WHERE id = $1
        ON CONFLICT (tontine_id, cycle) DO UPDATE SET pot_fcfa = cycle_total.pot_fcfa + $3`,
        memberID, month, amountFCFA)
    return err
}
```

Les tests de `ex3/summary_test.go` en vérifient quatre aspects. Deux
passent, deux échouent :

1. Explique les deux échecs : qu'ont en commun le script de reprise et

## Exercice 4 — Conception : le schéma de la mutuelle

*Niveau 4. Écrire un schéma ; aucun test fourni.*

La mutuelle de santé du quartier (leçon 4.6, exercice 4) a ces règles :

1. une **famille** adhère, avec un nom et un téléphone ;
2. une famille inscrit des **personnes** ;
3. une personne apporte des **factures** d'une clinique ou d'une
   pharmacie : un fournisseur, un numéro, une date, un montant ;
4. une même facture (même fournisseur, même numéro) ne s'apporte qu'une
   fois ;
5. une facture est remboursée au plus une fois ;
6. le remboursement vaut au plus 70 % de la facture ;
7. au-delà de 20 000 FCFA, un remboursement demande l'accord du comité ;
8. une personne est remboursée d'au plus 50 000 FCFA par année civile ;
9. une famille en retard de deux mois de cotisation n'est plus
   remboursée.

Écris le schéma (les quatre tables, en SQL), en mettant dans le schéma
toutes les règles qui peuvent y être. Pour chaque règle qui reste dehors,
dis pourquoi, et où elle vivra.

*Indice pour la règle 6* : un `CHECK` ne lit pas une autre table, mais la
clé étrangère composée de la section 4 de la leçon peut **transporter**
une valeur d'une table à l'autre.

## Exercice 5 — Incident : les cagnottes de décembre

*Niveau 7. Un incident de production ; les tests de la réparation sont
fournis.*

L'application tourne depuis un an sur le schéma sans règle de la leçon,
avec la version qui vérifie avant d'écrire. Le 3 novembre 2026, la
trésorière de la tontine 9 signale qu'un membre a reçu la cagnotte de
décembre 2025 **trois fois**. L'équipe découvre que, quand l'opérateur
Mobile Money répondait lentement, l'application réessayait le versement
au bout de cinq secondes, pendant que le premier essai était encore en
cours.

Le module reproduit l'année de production : 40 tontines de 12 membres,
une cagnotte de 600 000 FCFA par mois (`ex5/incident.go`, fonction
`Load`). Le premier réflexe de l'équipe est d'ajouter la contrainte. Le
test qui le fait est fourni, et il **passe**, parce que la contrainte est
refusée :

```go
// The fix that comes to mind first: it fails, because the duplicates are there.
func TestTheConstraintCannotBeAddedToTheDirtyTable(t *testing.T) {
    db := loaded(t)
    _, err := db.Exec(context.Background(),
        `ALTER TABLE payout ADD CONSTRAINT payout_once_per_cycle UNIQUE (tontine_id, cycle)`)
    var pgErr *pgconn.PgError
    if !errors.As(err, &pgErr) || pgErr.Code != "23505" {
        t.Fatalf("got %v, want a unique violation", err)
    }
}
```

La réparation est à écrire :

```go
// Report says what the repair found.
type Report struct {

}

// Repair keeps the first payout of each cycle, moves the others to a new
// table payout_refund, and adds the constraint payout_once_per_cycle.
// Running it a second time changes nothing and reports zero.
func Repair(ctx context.Context, db *pgxpool.Pool) (Report, error) {
    return Report{}, errors.New("not implemented")
}
```

1. Explique l'incident avec la section 3 de la leçon. Pourquoi décembre ?
2. Écris la requête SQL qui liste les mois versés plus d'une fois, avec
   le nombre de versements et le membre.
3. Pourquoi l'`ALTER TABLE` échoue-t-il ? Pourquoi ne peut-on pas
   simplement supprimer les doublons à la main, puis l'ajouter ?
4. Écris `Repair` pour que les tests de `ex5/incident_test.go` passent.
   Le dernier, `TestRepairWaitsForAPayoutInProgress`, simule un versement
   de l'application en cours pendant la réparation : que doit faire
   `Repair` pour le passer ?
5. Combien de versements en trop, combien de FCFA, combien de membres ?
6. Écris le SMS envoyé aux membres qui ont reçu une cagnotte en trop.
7. Écris le **compte rendu** de l'incident en cinq lignes.
