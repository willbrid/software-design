# Exercices 5.3 — La concurrence

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 5.3](../cours/5.3-la-concurrence.md) (`deposit`, `loan`, `move`,
`retry`, `internal/pg`), recopiés tels quels dans le module des
exercices. Ils demandent le même PostgreSQL 17 que la leçon. Tout le code
ci-dessous compile et passe `go vet` ; les tontines, les membres et
l'incident sont **fictifs**.

## Exercice 1 — Compréhension : qui voit quoi, qui attend qui

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Six situations

Pour chaque situation, dis si un défaut est possible (mise à jour
perdue, règle violée, interblocage), et ce qui l'empêche.

1. Deux membres déposent au même instant sur la caisse avec
   `deposit.Atomic`.
2. Un membre corrige son nom pendant que la trésorière corrige son
   téléphone, chacun avec un formulaire qui réécrit **toute** la ligne
   lue cinq minutes plus tôt.
3. Deux demandes de prêt arrivent ensemble avec `loan.RepeatableRead`.
4. Un rapport long (`SELECT` de dix secondes sur toutes les cotisations)
   tourne pendant que les membres déposent.
5. Un transfert de A vers B et un transfert de B vers C tournent en même
   temps avec `move.InCallOrder`. Puis on ajoute un transfert de C vers A.
6. `deposit.Repeatable` envoie un SMS « dépôt reçu » dans sa fonction de
   transaction.

### 1.b — Trois pourquoi

1. Pourquoi la lecture-écriture ne perd-elle rien quand chaque
   travailleur a son propre compte ? Qu'est-ce que cela dit des tests de
   charge ?
2. Pourquoi `REPEATABLE READ` protège-t-il le dépôt, mais pas la limite
   de trois prêts ?
3. Pourquoi verrouille-t-on la ligne de la tontine, et pas les prêts,
   pour tenir la limite ?

### 1.c — La mutation qui survit

La campagne de la leçon laisse survivre « verrous dans l'ordre
décroissant ». Pourquoi ne faut-il pas écrire de test qui la tue ?
Donne un autre exemple de mutant équivalent dans le code de la leçon.

## Exercice 2 — Code : plusieurs envoyeurs pour une même outbox

*Niveau 2. Rendre une file sûre pour plusieurs travailleurs ; les tests
sont fournis.*

La leçon 5.2 n'avait qu'un envoyeur. Le soir de la cotisation, il y a
1 000 SMS « cotisation reçue » à envoyer, et l'équipe lance quatre
envoyeurs :

```go
// SendOne sends the oldest SMS not sent yet, and marks it sent. It returns
// false when there is nothing to send.
func (s *Sender) SendOne(ctx context.Context) (bool, error) {
    var id int64
    var phone, body string
    err := s.DB.QueryRow(ctx, `
        SELECT id, phone, body FROM sms_outbox
        WHERE sent_at IS NULL ORDER BY id LIMIT 1`).Scan(&id, &phone, &body)
    if errors.Is(err, pgx.ErrNoRows) {
        return false, nil
    }
    if err != nil {
        return false, err
    }
    if err := s.Gateway.Send(ctx, id, phone, body); err != nil {
        return false, err
    }
    _, err = s.DB.Exec(ctx, `UPDATE sms_outbox SET sent_at = now() WHERE id = $1`, id)
    return err == nil, err
}
```

Les deux tests de `ex2/sender_test.go` échouent :

```text
--- FAIL: TestFourSendersSendEachSMSOnce (1.79s)
    sender_test.go:68: SMS sent 200/200, sent more than once 198
--- FAIL: TestASenderDoesNotWaitForAnother (1.08s)
    sender_test.go:89: second sender: timeout: context deadline exceeded
FAIL
```

1. Explique les 198 SMS envoyés plusieurs fois.
2. Corrige `SendOne` pour que les deux tests passent. Le second
   (`TestASenderDoesNotWaitForAnother`) demande qu'un envoyeur ne reste
   pas bloqué derrière un autre.
3. Ta solution appelle-t-elle la passerelle SMS pendant une transaction ?
   Est-ce la faute de la section 6 de la leçon 5.2 ? Justifie.

## Exercice 3 — Refactoring : le retrait garanti

*Niveau 3. Corriger une règle entre deux tables ; les tests sont
fournis.*

L'épargne d'un membre garantit ses prêts ouverts : un retrait ne doit
jamais laisser moins que les prêts. Le code le vérifie, dans une
transaction :

```go
// Withdraw takes amountFCFA from the account, if what is left still covers
// the open loans of the member.
func Withdraw(ctx context.Context, db *pgxpool.Pool, account, amountFCFA int64) error {
    return pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        var balance, loans int64
        err := tx.QueryRow(ctx, `
            SELECT a.balance_fcfa,
                   (SELECT coalesce(sum(amount_fcfa), 0) FROM loan WHERE account_id = a.id AND open)
            FROM account a WHERE a.id = $1`, account).Scan(&balance, &loans)
        if err != nil {
            return err
        }
        if balance-amountFCFA < loans {
            return ErrGuarantee
        }
        _, err = tx.Exec(ctx, `UPDATE account SET balance_fcfa = $2 WHERE id = $1`, account, balance-amountFCFA)
        return err
    })
}
```

Le test de concurrence échoue :

```text
    withdraw_test.go:79: account 1: 20 paid, 0 refused, balance 80000; want 7, 13, 30000
    withdraw_test.go:79: account 2: 20 paid, 0 refused, balance 90000; want 7, 13, 30000
    withdraw_test.go:79: account 3: 20 paid, 0 refused, balance 90000; want 7, 13, 30000
    withdraw_test.go:79: account 4: 20 paid, 0 refused, balance 90000; want 7, 13, 30000
    withdraw_test.go:79: account 5: 20 paid, 0 refused, balance 90000; want 7, 13, 30000
FAIL
FAIL    example/conc53/ex3      0.430s
```

1. Lis le compte 1 : 20 retraits de 10 000 FCFA ont été payés, et il
   reste 80 000 FCFA sur un compte de 100 000. Combien d'argent est sorti
   de la caisse ? Combien en manque ?
2. Corrige `Withdraw` pour que les deux tests passent, sans changer sa
   signature.
3. Écris une seconde version en **une seule instruction SQL**. Laquelle
   préfères-tu, et quand l'autre devient-elle nécessaire ?
4. Un prêt peut aussi être accordé pendant un retrait. Ta correction
   protège-t-elle ce cas ? Que faudrait-il ?

## Exercice 4 — Conception : la carte de la concurrence

*Niveau 4. Analyser ; aucun test fourni.*

Pour chaque opération de l'application de la tontine, dis **quelles
autres opérations** peuvent la croiser, ce qui peut mal tourner, et la
technique que tu choisis (instruction atomique, `FOR UPDATE`, verrou du
parent, version, `SERIALIZABLE`, contrainte `UNIQUE`, rien).

1. Un membre paie sa cotisation du mois.
2. La trésorière clôture le mois et verse la cagnotte (leçon 5.2).
3. Un membre demande un prêt.
4. Un membre change son numéro de téléphone dans l'application, pendant
   que la trésorière le change aussi.
5. Le bureau change la part mensuelle de la tontine, le soir où les
   membres cotisent.
6. Un traitement de nuit calcule les intérêts de l'épargne de chaque
   membre et les ajoute au solde.

Termine par la question : sur quelle **ligne** de la base la tontine
aura-t-elle le plus de contention, et comment la réduire si elle devient
un problème ?

## Exercice 5 — Incident : les caisses qui ne tombent pas juste

*Niveau 7. Un incident de production ; les tests de l'audit et de la
réparation sont fournis.*

Le 20 septembre 2026, une nouvelle version passe en production. Pour
ajouter un plafond à la caisse, le dépôt a été réécrit : il lit le
solde, vérifie le plafond en Go, et écrit le nouveau solde, dans une
transaction. Le 26 octobre, la trésorière de la tontine 7 compte les
reçus de cotisation du mois et ne retrouve pas le solde de la caisse.

Le module reproduit les deux mois (`ex5/incident.go`, fonction `Load`) :
40 caisses de 25 membres, une cotisation de 25 000 FCFA chaque dimanche
soir. Chaque cotisation est écrite dans `contribution`, et le solde de
chaque caisse est copié chaque nuit :

```sql
-- The cash box of each tontine.
CREATE TABLE account (
    id           BIGINT PRIMARY KEY,
    balance_fcfa BIGINT NOT NULL CHECK (balance_fcfa >= 0)
);

-- Every contribution, as it was received. Nothing is ever updated here.
CREATE TABLE contribution (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account_id  BIGINT      NOT NULL REFERENCES account (id),
    member_id   BIGINT      NOT NULL,
    amount_fcfa BIGINT      NOT NULL CHECK (amount_fcfa > 0),
    paid_at     TIMESTAMPTZ NOT NULL
);

-- The balance of each cash box, copied every night at midnight.
CREATE TABLE balance_snapshot (
    account_id   BIGINT NOT NULL REFERENCES account (id),
    day          DATE   NOT NULL,
    balance_fcfa BIGINT NOT NULL,
    PRIMARY KEY (account_id, day)
);
```

L'audit et la réparation sont à écrire :

```go
// Report is what the audit finds.
type Report struct {
    Accounts    int       // cash boxes whose balance differs from their contributions
    MissingFCFA int64     // contributions received but absent from the balances
    FirstDay    time.Time // first night a snapshot differed from the contributions of the day
}
```

```go
// Repair sets each balance to the sum of its contributions, and says how
// many balances it changed. Deposits keep arriving while it runs.
func Repair(ctx context.Context, db *pgxpool.Pool) (int, error) {
    return 0, errors.New("not written yet")
}
```

1. Explique l'incident avec la section 2 de la leçon. Pourquoi le
   dimanche soir ?
2. Écris `Audit` : combien de caisses, combien de FCFA, depuis quelle
   nuit ?
3. Écris `Repair`. Le test `TestRepairDoesNotLoseADepositInProgress`
   simule un dépôt en cours pendant la réparation : que doit faire
   `Repair` pour le passer ?
4. L'argent manque-t-il vraiment ? Où est-il ?
5. Quelle correction du code empêche que cela recommence, **en gardant
   le plafond** ?
6. Écris le message aux trésoriers des 40 tontines.
7. Écris le **compte rendu** de l'incident en cinq lignes.
