# Exercices 5.5 — Lire vite

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 5.5](../cours/5.5-lire-vite.md) (`schema`, `page`, `history`,
`querycount`, `slownet`, `internal/pg`), recopiés tels quels dans le
module des exercices. `querycount` y gagne un second traceur, `Last`,
qui garde la dernière requête envoyée pour qu'un test puisse demander
son plan. Les exercices demandent le même PostgreSQL 17 que la leçon.
Tout le code ci-dessous compile et passe `go vet` ; les tontines, les
membres et l'incident sont **fictifs**.

## Exercice 1 — Compréhension : lire un plan, choisir un index

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Quatre plans

Pour chaque extrait de plan, dis ce que la base a fait, si c'est
normal, et ce que tu changerais.

1. `Parallel Seq Scan on contribution` … `Rows Removed by Filter: 666600`,
   pour une requête qui renvoie 20 lignes.
2. `Index Scan using contribution_by_member` … `Buffers: shared hit=23`,
   sous un `Limit`, pour 20 lignes.
3. `Sort (Sort Key: paid_at DESC)` au-dessus d'un `Bitmap Heap Scan`,
   sous un `Limit`.
4. `Seq Scan on tontine`, sur une table de 400 lignes.

### 1.b — L'ordre des colonnes

Pour chaque requête, écris l'index qui la sert le mieux, colonnes dans
l'ordre :

1. `WHERE tontine_id = $1 AND cycle = $2` (le versement d'un mois) ;
2. `WHERE tontine_id = $1 ORDER BY cycle DESC LIMIT 12` ;
3. `WHERE member_id = $1 AND paid_at >= $2 ORDER BY paid_at` ;
4. `WHERE lower(name) = lower($1)` ;
5. `WHERE open AND tontine_id = $1` (les prêts ouverts d'une tontine,
   1 % des prêts).

### 1.c — Trois pourquoi

1. Pourquoi le N+1 est-il presque gratuit sur le poste du développeur ?
2. Pourquoi un test qui compte les requêtes vaut-il mieux qu'un test qui
   mesure le temps de la page ?
3. Pourquoi la clé de pagination contient-elle l'`id` ?

## Exercice 2 — Code : le résumé d'une tontine

*Niveau 2. Supprimer un N+1 ; les tests sont fournis.*

Le résumé montre, pour chaque membre d'une tontine, ce qu'il a payé en
2026, combien de fois, et la date de son dernier paiement :

```go
// Summary returns the lines of the tontine's members, by member id.
func Summary(ctx context.Context, db *pgxpool.Pool, tontineID int64) ([]Line, error) {
    rows, err := db.Query(ctx, `SELECT id, name FROM member WHERE tontine_id = $1 ORDER BY id`, tontineID)
    if err != nil {
        return nil, err
    }
    var lines []Line
    for rows.Next() {
        var l Line
        if err := rows.Scan(&l.MemberID, &l.Name); err != nil {
            return nil, err
        }
        lines = append(lines, l)
    }
    if err := rows.Err(); err != nil {
        return nil, err
    }
    for i := range lines {
        err := db.QueryRow(ctx, `
            SELECT coalesce(sum(amount_fcfa), 0), count(*) FROM contribution
            WHERE member_id = $1 AND paid_at >= $2 AND paid_at < $3`,
            lines[i].MemberID, from, to).Scan(&lines[i].PaidFCFA, &lines[i].Payments)
        if err != nil {
            return nil, err
        }
        err = db.QueryRow(ctx, `SELECT max(paid_at) FROM contribution WHERE member_id = $1 AND paid_at < $2`,
            lines[i].MemberID, to).Scan(&lines[i].LastPaid)
        if err != nil {
            return nil, err
        }
    }
    return lines, nil
}
```


1. Combien de requêtes pour une tontine de 25 membres ? Combien de temps

## Exercice 3 — Refactoring : le journal de la caisse

*Niveau 3. Remplacer une pagination ; les tests sont fournis.*

L'application mobile affiche le journal de la caisse, page par page, avec
un curseur que le serveur donne et que l'application renvoie tel quel :

```go
// Page returns size lines of the tontine's journal, newest first, from
// cursor ("" for the first page), and the cursor of the next page ("" when
// there is none). The application treats the cursor as an opaque string.
func Page(ctx context.Context, db *pgxpool.Pool, tontineID int64, size int, cursor string) ([]Line, string, error) {
    skip := 0
    if cursor != "" {
        var err error
        if skip, err = strconv.Atoi(cursor); err != nil {
            return nil, "", ErrBadCursor
        }
    }
    rows, err := db.Query(ctx, `
        SELECT id, member_id, amount_fcfa, paid_at FROM journal
        WHERE tontine_id = $1
        ORDER BY paid_at DESC, id DESC
        LIMIT $2 OFFSET $3`, tontineID, size, skip)
    if err != nil {
        return nil, "", err
    }
    lines, err := pgx.CollectRows(rows, pgx.RowToStructByPos[Line])
    if err != nil || len(lines) < size {
        return lines, "", err
    }
    return lines, strconv.Itoa(skip + size), nil
}
```

Deux tests échouent :

```text
--- FAIL: TestANewPaymentDoesNotShiftThePages (0.08s)
    journal_test.go:106: page 2, line 0: id 3761, want 3561 (the line after the end of page 1)
--- FAIL: TestADeepPageReadsFewBlocks (8.76s)
    journal_test.go:142: page 400 reads 8557 blocks for 50 lines
FAIL
FAIL    example/read55/ex3      8.937s
FAIL
```

1. Explique le premier échec : que voit la trésorière qui fait défiler
   le journal pendant qu'un membre paie ?
2. Explique le second : pourquoi la page 400 lit-elle 8 557 blocs ?
3. Refactore `Page`, sans changer sa signature, pour que les quatre
   tests passent. Le curseur reste une chaîne **opaque** : l'application
   ne doit pas pouvoir en fabriquer un.
4. Ta pagination ne permet plus d'aller directement « à la page 37 ».
   Est-ce une perte pour un journal de caisse ? Pour quel écran en
   serait-ce une ?

## Exercice 4 — Conception : le tableau de bord de la trésorière

*Niveau 4. Concevoir les lectures ; aucun test fourni.*

La trésorière ouvre chaque soir un tableau de bord :

1. la caisse de chaque tontine dont elle s'occupe (12 tontines) ;
2. pour chacune, les membres en retard ce mois-ci ;
3. les 20 derniers paiements, toutes tontines confondues ;
4. le total versé par mois sur les 12 derniers mois ;
5. une recherche d'un membre par une partie de son nom.

Pour chaque bloc : écris la requête (ou dis combien de requêtes la page
envoie en tout), l'index qui la sert, et dis si le résultat doit être
**calculé à chaque affichage** ou **tenu à jour** dans une table. Puis
dis combien de requêtes envoie le tableau de bord entier, et ce que
coûte son affichage à 20 ms de la base.

## Exercice 5 — Incident : le relevé du 31 décembre

*Niveau 7. Un incident de production ; les tests de la réécriture sont
fournis.*

Le 31 décembre, une nouvelle fonction permet à chaque trésorière de
télécharger le relevé annuel de sa tontine : pour chaque membre, ce
qu'il a payé chaque mois. Le soir même, 400 trésorières essaient. La
base est hébergée dans une autre région que l'application, à 20 ms. Le
relevé ne s'affiche jamais : le répartiteur de charge coupe les
requêtes au bout de 5 secondes, et les trésorières réessaient.

```go
// Slow is the version that went live on December 31.
func Slow(ctx context.Context, db *pgxpool.Pool, tontineID int64, year int) ([]Row, error) {
    rows, err := db.Query(ctx, `SELECT id, name FROM member WHERE tontine_id = $1 ORDER BY id`, tontineID)
    if err != nil {
        return nil, err
    }
    var out []Row
    for rows.Next() {
        var r Row
        if err := rows.Scan(&r.MemberID, &r.Name); err != nil {
            return nil, err
        }
        out = append(out, r)
    }
    if err := rows.Err(); err != nil {
        return nil, err
    }
    for i := range out {
        for m := range 12 {
            err := db.QueryRow(ctx, `
                SELECT coalesce(sum(amount_fcfa), 0) FROM contribution
                WHERE member_id = $1
                  AND extract(year FROM paid_at AT TIME ZONE 'UTC') = $2
                  AND extract(month FROM paid_at AT TIME ZONE 'UTC') = $3`,
                out[i].MemberID, year, m+1).Scan(&out[i].Months[m])
            if err != nil {
                return nil, err
            }
            out[i].TotalFCFA += out[i].Months[m]
        }
    }
    return out, nil
}
```

La réécriture est à faire :

```go
// Statement returns what Slow returns.
func Statement(ctx context.Context, db *pgxpool.Pool, tontineID int64, year int) ([]Row, error) {
    return nil, errors.New("not written yet")
}
```

1. Combien de requêtes pour une tontine de 25 membres ? Combien de temps
   à 20 ms ? Pourquoi le relevé ne s'affiche-t-il jamais ?
2. Que deviennent les connexions du pool de l'application quand 400
   trésorières réessaient ?
3. Écris `Statement` pour que les trois tests de
   `ex5/statement_test.go` passent : le même relevé que `Slow`, en une
   requête, sans lire toute la table.
4. `Slow` filtre avec `extract(year FROM paid_at ...)`. Pourquoi est-ce
   un problème de plus ? Pourquoi n'empêche-t-il pas ici l'usage de
   l'index ?
5. Écris le message aux trésorières.
6. Écris le **compte rendu** de l'incident en cinq lignes.
