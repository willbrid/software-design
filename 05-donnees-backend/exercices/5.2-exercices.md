# Exercices 5.2 — Les transactions

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 5.2](../cours/5.2-les-transactions.md) (`closing`, `txn`, `leaky`,
`transfer`, `internal/pg`), recopiés tels quels dans le module des
exercices. Ils demandent le même PostgreSQL 17 que la leçon. Tout le code
ci-dessous compile et passe `go vet` ; les tontines, les membres et
l'incident sont **fictifs**.

---

## Exercice 1 — Compréhension : tout, rien, et le reste

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Que reste-t-il ?

Pour chaque scénario, dis ce que la trésorière trouve dans la base, et
ce qui s'est passé hors de la base.

1. La version `plain` est tuée juste après l'étape `debit`.
2. La version `txn` est tuée juste après l'étape `debit`.
3. La version `leaky` est tuée juste après l'étape `payout`.
4. La version `transfer.Inside` est tuée pendant que l'opérateur répond.
5. La version `transfer.Outbox` est tuée entre l'envoi à l'opérateur et
   le `UPDATE ... sent_at`.
6. La machine de la base de données redémarre pendant qu'une transaction
   `txn` attend la réponse de son `COMMIT`.

### 1.b — Trois pourquoi

1. Pourquoi le compilateur Go ne voit-il pas l'erreur de `leaky` ?
   Quelle habitude d'écriture la rend impossible ?
2. Pourquoi la clé `payout-<id>` ne protège-t-elle pas la version
   `Inside`, alors que la clé `outbox-<id>` protège la version `Outbox` ?
3. Pourquoi la transaction est-elle **plus rapide** que quatre écritures
   validées une par une ?

### 1.c — Au moins une fois, au plus une fois

Entre la base et l'opérateur, on doit choisir entre « peut-être
jamais » et « peut-être deux fois ». Écris les deux ordres possibles
(envoyer puis marquer, ou marquer puis envoyer), et dis pour chacun ce
qu'un arrêt au mauvais moment produit. Lequel choisit la leçon, et
qu'est-ce qui le rend acceptable ?

## Exercice 2 — Code : l'adhésion d'un membre

*Niveau 2. Rendre une opération atomique ; les tests sont fournis.*

L'adhésion d'un membre écrit trois choses : le membre, sa première
cotisation, et le SMS de bienvenue à envoyer (une outbox de SMS). Le
squelette écrit tout sur le pool :

```go
// Join registers the member, records the first contribution, and queues
// the welcome SMS.
func (s *Store) Join(ctx context.Context, tontineID int64, name, phone string, cycle time.Time, firstFCFA int64) (int64, error) {
    var id int64
    err := s.db.QueryRow(ctx,
        `INSERT INTO member (tontine_id, name, phone) VALUES ($1, $2, $3) RETURNING id`,
        tontineID, name, phone).Scan(&id)
    if err == nil {
        err = s.Fault.After("member")
    }
    if err == nil {
        _, err = s.db.Exec(ctx,
            `INSERT INTO contribution (member_id, cycle, amount_fcfa) VALUES ($1, $2, $3)`,
            id, cycle, firstFCFA)
    }
    if err == nil {
        err = s.Fault.After("contribution")
    }
    if err == nil {
        err = s.queueWelcome(ctx, name, phone)
    }
    if err == nil {
        err = s.Fault.After("sms")
    }
    if err != nil {
        return 0, err
    }
    return id, nil
}
```

```go
func (s *Store) queueWelcome(ctx context.Context, name, phone string) error {
    _, err := s.db.Exec(ctx, `INSERT INTO sms_outbox (phone, body) VALUES ($1, $2)`,
        phone, fmt.Sprintf("Bienvenue %s dans la tontine !", name))
    return err
}
```

## Exercice 3 — Refactoring : l'unité de travail

*Niveau 3. Déplacer la frontière de la transaction ; les tests sont
fournis.*

Un membre en retard reçoit la cagnotte moins la pénalité, et la pénalité
est enregistrée. Le cas d'usage est écrit sans PostgreSQL :

```go
// PayLate pays the pot less the penalty, and records the penalty.
func (s *Service) PayLate(ctx context.Context, tontineID int64, cycle time.Time, memberID, potFCFA, penaltyFCFA int64) error {
    if err := s.Payouts.Record(ctx, tontineID, cycle, memberID, potFCFA-penaltyFCFA); err != nil {
        return err
    }
    return s.Penalties.Add(ctx, memberID, cycle, penaltyFCFA, "late")
}
```

Chaque store ouvre sa propre transaction :

```go
// Record records a payout.
func (p *Payouts) Record(ctx context.Context, tontineID int64, cycle time.Time, memberID, amountFCFA int64) error {
    return pgx.BeginFunc(ctx, p.db, func(tx pgx.Tx) error {
        _, err := tx.Exec(ctx,
            `INSERT INTO payout (tontine_id, cycle, member_id, amount_fcfa) VALUES ($1, $2, $3, $4)`,
            tontineID, cycle, memberID, amountFCFA)
        return err
    })
}
```

Un test échoue :

```text
--- FAIL: TestARefusedPenaltyUndoesThePayout (0.05s)
    service_test.go:44: payouts 1, penalties 0; want nothing
FAIL
FAIL    example/tx52/ex3/postgres       0.211s
ok      example/tx52/ex3/service        0.002s
FAIL
```

1. Explique l'échec : chaque store utilise pourtant `pgx.BeginFunc`.
2. Refactore pour que le versement et la pénalité soient écrits **dans
   la même transaction**. Contraintes :
   - `ex3/service` n'importe pas `pgx` (un test le vérifie) ;
   - `postgres.NewService(db)` garde sa signature ;
   - les quatre tests de `ex3/postgres` passent, y compris sur un pool
     d'une connexion.
3. Écris un test du cas d'usage **sans base de données**. Qu'est-ce que
   ta conception a rendu possible ?

## Exercice 4 — Conception : le remboursement de la mutuelle

*Niveau 4. Concevoir ; aucun test fourni.*

La mutuelle de santé (exercice 4 de la leçon 5.1) rembourse une facture
ainsi :

1. le comité valide le remboursement ;
2. le plafond annuel de la personne diminue du montant remboursé ;
3. l'argent part par virement bancaire vers la clinique, par une API de
   la banque qui accepte un en-tête `Idempotency-Key` ;
4. la famille reçoit un SMS ;
5. la comptable reçoit, chaque fin de mois, un fichier des
   remboursements.

Dessine le découpage :

- quelles écritures vont dans **une** transaction, et laquelle ?
- qu'est-ce qui passe par une outbox, avec quelle clé ?
- que se passe-t-il si la banque répond « délai dépassé » ? Et si elle
  ne répond jamais ?
- que fait-on si la banque refuse le virement (compte de la clinique
  fermé) **après** que le plafond a été diminué ?
- quel rapprochement faut-il prévoir, et avec quelles données ?

## Exercice 5 — Incident : les virements en double

*Niveau 7. Un incident de production ; les tests du rapprochement sont
fournis.*

L'application de 30 tontines a tourné toute l'année 2026 avec la version
`transfer.Inside` de la leçon. Le 4 janvier 2027, en recevant le relevé
annuel de l'opérateur Mobile Money, la trésorière de la tontine 12 voit
deux virements de 300 000 FCFA au même membre, à dix secondes d'écart.

Le module reproduit l'année (`ex5/incident.go`, fonction `Load`) : les
versements de l'application, et le relevé de l'opérateur, une ligne par
virement, avec la clé donnée par l'application :

```sql
-- The payouts the application recorded.
CREATE TABLE payout (
    id          BIGINT PRIMARY KEY,
    tontine_id  BIGINT NOT NULL,
    cycle       DATE   NOT NULL,
    member_id   BIGINT NOT NULL,
    phone       TEXT   NOT NULL,
    amount_fcfa BIGINT NOT NULL,
    CONSTRAINT payout_once_per_cycle UNIQUE (tontine_id, cycle)
);

-- The statement of the Mobile Money operator: one line per transfer sent.
-- key is the key the application gave with the order.
CREATE TABLE statement (
    op_ref      TEXT        PRIMARY KEY,
    key         TEXT        NOT NULL,
    phone       TEXT        NOT NULL,
    amount_fcfa BIGINT      NOT NULL,
    sent_at     TIMESTAMPTZ NOT NULL
);
```

Le rapprochement est à écrire :

```go
// Report is what the reconciliation finds.
type Report struct {
    Extra      int   // transfers sent without a payout in the books
    ExtraFCFA  int64 // what they cost
    Members    int   // members who received money twice or more
    NotSent    int   // payouts in the books that the operator never sent
    Transfers  int   // lines of the statement
    PayoutRows int   // payouts in the books
}
```

1. Explique l'incident avec la section 6 de la leçon. Pourquoi les deux
   virements ont-ils des clés différentes ?
2. L'équipe a d'abord compté les téléphones payés plus d'une fois.
   Pourquoi ce chiffre est-il faux ? Dans quel sens ?
3. Écris `Reconcile` pour que les tests de `ex5/incident_test.go`
   passent.
4. Combien de virements en trop, combien de FCFA, combien de membres ?
   Les mois sont-ils touchés de la même façon ?
5. Quelle correction du code empêche que cela recommence ? Que faut-il
   demander à l'opérateur ?
6. Écris le SMS envoyé aux membres qui ont reçu la cagnotte deux fois.
7. Écris le **compte rendu** de l'incident en cinq lignes.
