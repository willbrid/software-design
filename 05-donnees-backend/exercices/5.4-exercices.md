# Exercices 5.4 — Les migrations

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 5.4](../cours/5.4-les-migrations.md) (`migrate`, `migrations`,
`phone`, `traffic`, `internal/pg`), recopiés tels quels dans le module
des exercices. Ils demandent le même PostgreSQL 17 que la leçon. Tout le
code ci-dessous compile et passe `go vet` ; les tontines, les membres et
l'incident sont **fictifs**.

---

## Exercice 1 — Compréhension : huit migrations à relire

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Bloque ou ne bloque pas

La table `contribution` a 50 millions de lignes, et les membres paient
en continu. Pour chaque migration, dis si elle bloque les écritures, à
peu près combien de temps, et ce que tu écrirais à la place.

1. `ALTER TABLE contribution ADD COLUMN note TEXT;`
2. `ALTER TABLE contribution ADD COLUMN channel TEXT NOT NULL DEFAULT 'momo';`
3. `ALTER TABLE contribution ADD COLUMN receipt UUID DEFAULT gen_random_uuid();`
4. `CREATE INDEX contribution_by_paid_at ON contribution (paid_at);`
5. `ALTER TABLE contribution ADD CONSTRAINT contribution_positive CHECK (amount_fcfa > 0);`
6. `ALTER TABLE contribution ALTER COLUMN member_id SET NOT NULL;`
7. `ALTER TABLE contribution RENAME COLUMN paid_at TO received_at;`
8. `DROP INDEX contribution_by_paid_at;`

### 1.b — Trois pourquoi

1. Pourquoi un `ALTER TABLE` de 9 ms peut-il arrêter l'application
   pendant trois secondes ?
2. Pourquoi `pg_advisory_lock` provoque-t-il un interblocage avec
   `CREATE INDEX CONCURRENTLY`, alors que `pg_try_advisory_lock` dans une
   boucle n'en provoque pas ?
3. Pourquoi le contract est-il livré **au déploiement suivant**, et pas
   avec l'expand ?

### 1.c — La migration corrigée

Une collègue a corrigé une faute de frappe dans la migration
`012_payout.sql`, déjà passée en production il y a trois mois. Que fait
`migrate.Up` au prochain démarrage ? Pourquoi est-ce le bon
comportement ? Que fallait-il faire ?

## Exercice 2 — Code : le relecteur de migrations

*Niveau 2. Écrire un vérificateur ; les tests sont fournis.*

On veut qu'une revue de code signale automatiquement les formes
dangereuses de la grille de la leçon. Le squelette :

```go
// Finding is one risk found in a migration.
type Finding string
```

```go
// Check returns the risks of sql, in the order of the constants above,
// each at most once. sql is the content of one migration file. The lock
// timeout is not its business: package migrate sets it.
func Check(sql string) []Finding {
    return nil
}
```

Les tests de `ex2/lint_test.go` décrivent ce qui est attendu, cas par
cas. Le début de leur sortie sur le squelette :

```text
--- FAIL: TestCheck (0.00s)
    lint_test.go:38: CREATE INDEX member_by_phone ON member (phone);
            got  []
            want ["CREATE INDEX without CONCURRENTLY blocks writes"]
    lint_test.go:38: create unique index member_by_phone on member (tontine_id, phone);
            got  []
            want ["CREATE INDEX without CONCURRENTLY blocks writes"]
```

1. Écris `Check` pour que `go test -race -count=1 ./ex2/...` passe.
   Lis bien tous les cas : la casse, les commentaires, `NOT VALID`, et
   `now()`, qui n'est **pas** volatile.
2. Pourquoi `DEFAULT now()` ne réécrit-il pas la table, alors que
   `DEFAULT clock_timestamp()` la réécrit ?
3. Ce vérificateur lit du texte. Donne un cas qu'il ne peut pas voir, et
   dis comment le rattraper.

## Exercice 3 — Refactoring : la recopie par lots

*Niveau 3. Découper une écriture trop grosse ; les tests sont fournis.*

Après l'expand de la leçon, il faut recopier `phone` dans `phone_e164`
pour tous les membres. Le squelette le fait en une instruction :

```go
// Backfill copies phone into phone_e164 where it is empty, batch rows at a
// time, and calls after with the number of rows filled so far once each
// batch is committed. An error from after stops it there; running it again
// carries on. It returns the number of rows it filled.
func Backfill(ctx context.Context, db *pgxpool.Pool, batch int, after func(filled int) error) (int, error) {
    tag, err := db.Exec(ctx, `UPDATE member SET phone_e164 = phone WHERE phone_e164 IS NULL`)
    if err != nil {
        return 0, err
    }
    n := int(tag.RowsAffected())
    return n, after(n)
}
```

Deux tests échouent :

```text
--- FAIL: TestEachBatchIsCommittedOnItsOwn (0.12s)
    backfill_test.go:58: batches seen [10000], want ten of 1000 rows
--- FAIL: TestAnInterruptedBackfillCarriesOn (0.11s)
    backfill_test.go:73: interrupted: deployment with 10000 rows filled; want the stop after 3000
FAIL
FAIL    example/mig54/ex3       0.345s
FAIL
```

1. Sur une table de 50 millions de membres, que coûte l'instruction
   unique : verrous, journal, durée, reprise après une coupure ?
2. Refactore `Backfill` pour que les trois tests passent, sans changer
   sa signature.
3. Que se passe-t-il si un membre change de téléphone (par v1) pendant
   la recopie ? Le résultat est-il juste ?

## Exercice 4 — Conception : plusieurs téléphones par membre

*Niveau 4. Planifier ; aucun test fourni.*

Les membres veulent enregistrer **plusieurs** numéros (un Orange, un
MTN), dont un principal. Aujourd'hui, `member.phone` contient un seul
numéro, et trois choses le lisent : l'application (v1), l'envoyeur de
SMS, et le rapprochement Mobile Money de la leçon 5.2.

Écris le plan de migration, déploiement par déploiement :

- la nouvelle table, et ses contraintes (un seul numéro principal par
  membre : comment le dire dans le schéma ?) ;
- ce que fait chaque version de l'application, et lesquelles tournent
  ensemble ;
- à quel moment la recopie se fait, et comment les deux représentations
  restent justes pendant la transition ;
- à quel moment chaque lecteur (SMS, rapprochement) bascule ;
- le contract, et le point au-delà duquel on ne peut plus revenir en
  arrière.

## Exercice 5 — Incident : le dimanche à 19 h 05

*Niveau 7. Un incident de production ; les tests de la correction sont
fournis.*

Pour imprimer des reçus, l'équipe ajoute un numéro de reçu unique à
chaque cotisation. La migration passe en production un dimanche à
19 h 05, en pleine soirée de cotisation :

```go
// Incident is the migration that went live on Sunday at 19:05.
var Incident = []migrate.Migration{{Version: 40, Name: "receipt", SQL: `
```

La table compte 30 millions de cotisations. Les paiements Mobile Money
restent bloqués pendant plus d'une minute. Les sondes de santé des
instances échouent, Kubernetes les redémarre, et chaque instance
redémarrée relance la migration. Le module rejoue la migration sur
1 000 000 de cotisations, pendant que dix membres paient :

```go
// The incident, replayed: the payments stop while the table is rewritten.
func TestTheIncidentMigrationStopsThePayments(t *testing.T) {
    db := contributions(t)
    stats := during(t, db, func(ctx context.Context) error {
        _, err := migrate.Up(ctx, db, ex5.Incident, migrate.Options{})
        return err
    })
    if stats.Max < time.Second {
        t.Errorf("slowest payment %v; the incident blocked them for seconds", stats.Max)
    }
}
```

La version sûre est à écrire :

```go
// Apply makes the same change without stopping the members' payments:
// in the end, every contribution, old or new, has a receipt_id, never
// NULL, unique.
func Apply(ctx context.Context, db *pgxpool.Pool) error {
    return errors.New("not written yet")
}
```

1. Explique l'incident avec les sections 3 et 4 de la leçon. Pourquoi
   la migration a-t-elle bloqué les **paiements**, et pas seulement les
   lectures de reçus ?
2. Pourquoi le redémarrage des instances a-t-il aggravé la situation ?
3. Écris `Apply` pour que `TestApplyKeepsThePaymentsFlowing` passe :
   aucun paiement en erreur, aucun paiement plus lent que 500 ms, et à
   la fin, chaque cotisation a un reçu unique, jamais `NULL`.
4. Ta version dure bien plus longtemps que la migration de l'incident.
   Est-ce un problème ?
5. Le test de latence a un seuil. Ta version pourrait-elle bloquer les
   paiements sur la vraie table de 30 millions de lignes, et passer
   quand même ce test ? Comment t'en assurer ?
6. Écris le message aux trésoriers.
7. Écris le **compte rendu** de l'incident en cinq lignes.
