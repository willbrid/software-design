# Exercices 5.6 — Le cache

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets de la
[leçon 5.6](../cours/5.6-le-cache.md) (`cache`, `account`, `slownet`,
`internal/pg`), recopiés tels quels dans le module des exercices. Ils
demandent le même PostgreSQL 17 que la leçon. Tout le code ci-dessous
compile et passe `go vet` ; les tontines, les membres et l'incident sont
**fictifs**.

## Exercice 1 — Compréhension : vrai, faux, ou ça dépend

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Six affirmations

Dis si chaque affirmation est vraie, fausse, ou vraie sous condition, et
justifie avec une mesure de la leçon.

1. « Notre cache a 99 % de réussite, les soldes affichés sont donc
   justes. »
2. « Supprimer la clé après chaque écriture rend le cache toujours
   juste. »
3. « Avec une durée de vie de 5 secondes, un solde est faux au plus
   5 secondes. »
4. « `NOTIFY` peut prévenir les autres instances d'un changement qui
   sera finalement annulé. »
5. « Un cache protège la base quand la charge monte. »
6. « Le cache est la cause des retraits acceptés à tort. »

### 1.b — Trois pourquoi

1. Pourquoi `Invalidate` retient-il une **version**, au lieu de
   simplement supprimer la clé ?
2. Pourquoi la durée de vie reste-t-elle utile quand on a `NOTIFY` ?
3. Pourquoi une lecture indexée à 0,1 ms ne gagne-t-elle presque rien à
   être mise en cache ?

### 1.c — Où mettre le cache ?

Pour chaque donnée, dis si tu la mets en cache, avec quelle durée de
vie, et comment tu l'invalides : le règlement d'une tontine ; le solde de
la caisse ; la liste des membres ; le classement des tontines du
quartier ; le montant qu'un membre peut emprunter.

## Exercice 2 — Code : un seul chargement pour tous

*Niveau 2. Écrire un chargeur partagé ; les tests sont fournis.*

Le règlement d'une tontine (ses parts, ses pénalités, son calendrier) se
calcule en 50 ms. Le squelette le garde en cache, mais chaque appelant
qui le trouve absent le recalcule :

```go
// Get returns the value of key, from the cache, or from load. Callers that
// ask for the same key at the same time share one load; an error is
// returned to them, and never kept.
func (l *Loader[V]) Get(ctx context.Context, key int64, load Load[V]) (V, error) {
    if v, ok := l.cache.Get(key); ok {
        return v, nil
    }
    v, version, err := load(ctx)
    if err != nil {
        var zero V
        return zero, err
    }
    l.cache.Put(key, v, version)
    return v, nil
}
```

Les tests de `ex2/loader_test.go` :

```text

    loader_test.go:43: a later call loaded again (100 loads, <nil>)

    loader_test.go:84: 0 patient callers failed, 21 loads
FAIL

```

1. Fais passer les trois tests sous `go test -race -count=1 ./ex2/...`.
2. Le troisième test, `TestACallerWhoGivesUpDoesNotFailTheOthers`,

   première correction avec `singleflight`, il échoue souvent autrement.
   Comment ? Que fait le premier appelant aux autres ?

## Exercice 5 — Incident : le samedi des avances

*Niveau 7. Un incident de production ; les tests de la correction sont
fournis.*

La tontine accorde des avances sur sa cagnotte. Pour aller vite,
l'écran des trésorières affiche la cagnotte disponible depuis le cache,
et la décision d'accorder se fait sur ce chiffre :

```go
// GrantFromCache is the version that was live on Saturday: it checks the
// pot shown on the treasurer's screen, from the cache.
func GrantFromCache(ctx context.Context, db *pgxpool.Pool, c *cache.Cache[int64], tontineID, memberID, amountFCFA int64) error {
    available, ok := c.Get(tontineID)
    if !ok {
        if err := db.QueryRow(ctx, `SELECT available_fcfa FROM pot WHERE tontine_id = $1`, tontineID).Scan(&available); err != nil {
            return err
        }
        c.Put(tontineID, available, 0)
    }
    if available < amountFCFA {
        return ErrPotTooSmall
    }
    err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        _, err := tx.Exec(ctx, `INSERT INTO advance (tontine_id, member_id, amount_fcfa) VALUES ($1, $2, $3)`,
            tontineID, memberID, amountFCFA)
        if err == nil {
            _, err = tx.Exec(ctx, `UPDATE pot SET available_fcfa = available_fcfa - $2 WHERE tontine_id = $1`,
                tontineID, amountFCFA)
        }
        return err
    })
    c.Delete(tontineID)
    return err
}
```

Le samedi 17 octobre 2026, jour de marché, les trésorières de 30
tontines accordent des avances toute la matinée. Le lundi, sept
cagnottes sont négatives. Le module reproduit ce samedi
(`ex5/incident.go`, fonction `Load`) :

```sql
CREATE TABLE pot (
    tontine_id     BIGINT PRIMARY KEY,
    available_fcfa BIGINT NOT NULL
);
CREATE TABLE advance (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tontine_id  BIGINT      NOT NULL REFERENCES pot (tontine_id),
    member_id   BIGINT      NOT NULL,
    amount_fcfa BIGINT      NOT NULL CHECK (amount_fcfa > 0),
    granted_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

1. Explique l'incident avec les sections 3 et 5 de la leçon. Le cache
