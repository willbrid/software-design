# Leçon 5.6 — Le cache : ce qu'il coûte, et quand il ment

## L'essentiel en deux minutes

**Le problème, en une phrase.** Un cache garde en mémoire une copie de
ce que dit la base, pour répondre sans la questionner. Il est des milliers
de fois plus rapide, mais c'est une **copie** : dès que la base change,
il peut montrer un solde qui n'existe plus.

**Trois images.**

- **Le tableau d'affichage du marché** : les prix y sont recopiés le
  matin. On les lit vite, mais si le prix change à midi, le tableau
  ment jusqu'à ce que quelqu'un le corrige.
- **L'affiche de concert collée deux fois** : on décolle l'ancienne
  affiche, mais un retardataire recolle par-dessus l'affiche qu'il
  tenait depuis le matin. Supprimer ne suffit pas, il faut savoir quelle
  affiche est la plus récente.
- **Le guichet qui ouvre** : quand le tableau est effacé, deux cents
  personnes viennent demander le prix au même guichet en même temps. Il
  vaut mieux qu'une seule demande, et que les autres l'écoutent.

**Le code, en quelques lignes.** Une valeur lue avant un changement ne
peut plus revenir dans le cache après lui :

```go
// Invalidate forgets key, and remembers that version exists: a value read
// before it can no longer be put back.
func (c *Cache[V]) Invalidate(key int64, version int64) {
    c.mu.Lock()
    defer c.mu.Unlock()
    if it, found := c.items[key]; found && it.version > version {
        return
    }
    var zero V
    c.items[key] = item[V]{zero, false, version, c.Now().Add(c.TTL)}
}
```

**Les règles à retenir.**

1. **Mesurer d'abord** : une lecture indexée coûte 0,1 ms sur la même
   machine, 1,2 ms à 1 ms de la base. Un cache ne se justifie que par un
   coût mesuré.
2. **Une durée de vie (TTL) seule montre des valeurs anciennes**, jusqu'à
   toute la durée de vie : c'est acceptable pour un affichage, pas pour
   un solde qui vient de changer.
3. **On invalide avec la version** de la ligne : supprimer la clé laisse
   un lecteur en retard y remettre une ancienne valeur.
4. **Plusieurs instances, plusieurs caches** : chaque instance doit
   apprendre le changement. PostgreSQL le dit avec `LISTEN`/`NOTIFY`,
   au moment du `COMMIT`.
5. **On ne décide jamais sur une valeur en cache** : un retrait, un
   prêt, un versement se décident dans la base, dans la transaction
   (leçon 5.3).

La suite le mesure avec des dépôts qui changent les soldes pendant qu'on
les lit.

---

La leçon 5.5 a rendu les lectures rapides avec des index et sans N+1.
Quand cela ne suffit plus, la tentation suivante est le cache. Le
problème de cette leçon :

> **Que gagne-t-on à garder les soldes en mémoire, et quand le solde
> affiché devient-il faux ?**

Le module de la leçon est `l56`, sur le même PostgreSQL 17. Le cache est
en mémoire, dans le processus ; les mêmes questions se posent avec un
cache partagé comme Redis. Tout ce qui suit est mesuré sur un module vert
sous `gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Ce que coûte une lecture, et ce qu'un cache fait gagner

Le programme `cmd/worth` lit 1 000 fois le solde d'un compte, depuis la
base sur la même machine, depuis la base à 1 ms (le proxy de la leçon
5.5), et depuis le cache :

```text
$ go run ./cmd/worth
database, same machine  median 108.129µs, 99th percentile 282.607µs
database, 1 ms away     median 1.225551ms, 99th percentile 1.908531ms
cache hit               median      87ns, 99th percentile     207ns
```

Le cache est **dix mille fois** plus rapide : une centaine de
nanosecondes contre une milliseconde. Mais en absolu, il fait gagner
**1,1 ms par lecture**, sur une page qui en coûte souvent 50 à cause du
reste (le réseau du membre, le rendu, les autres requêtes). Avant de
mettre un cache, on se demande :

- la lecture est-elle **coûteuse** (un calcul de 50 ms, section 4), ou
  seulement **fréquente** ?
- le N+1 et les index de la leçon 5.5 ont-ils été traités ? Un cache
  posé sur un N+1 cache cent requêtes au lieu d'en supprimer 99 ;
- combien de temps la valeur peut-elle être fausse sans dommage ?

## 2. Le cache de la leçon

Un cache qui garde chaque valeur avec sa date d'expiration et la
**version** de la ligne d'où elle vient :

```go
// Get returns the value of key, if it is there and has not expired.
func (c *Cache[V]) Get(key int64) (V, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()
    it, found := c.items[key]
    if found && it.ok && c.Now().Before(it.expires) {
        c.hits++
        return it.value, true
    }
    c.misses++
    var zero V
    return zero, false
}
```

```go
// Put stores value, read at version, unless the cache already knows a
// newer version of key, as a value or as an invalidation.
func (c *Cache[V]) Put(key int64, value V, version int64) {
    c.mu.Lock()
    defer c.mu.Unlock()
    if it, found := c.items[key]; found && it.version > version && c.Now().Before(it.expires) {
        return
    }
    c.items[key] = item[V]{value, true, version, c.Now().Add(c.TTL)}
}
```

La version vient de la base : chaque changement de solde l'augmente, dans
la même instruction que le solde :

```go
// Change adds amountFCFA (negative for a withdrawal) to the balance, and
// notifies the change. PostgreSQL delivers the notification at COMMIT,
// and never if the transaction is rolled back.
func Change(ctx context.Context, db *pgxpool.Pool, id, amountFCFA int64) (Balance, error) {
    var b Balance
    err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        err := tx.QueryRow(ctx, `
            UPDATE account SET balance_fcfa = balance_fcfa + $2, version = version + 1
            WHERE id = $1 RETURNING balance_fcfa, version`, id, amountFCFA).Scan(&b.FCFA, &b.Version)
        if err != nil {
            return err
        }
        _, err = tx.Exec(ctx, `SELECT pg_notify($1, $2)`, Channel, fmt.Sprintf("%d:%d", id, b.Version))
        return err
    })
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) && pgErr.Code == "23514" {
        return Balance{}, ErrInsufficient
    }
    return b, err
}
```

La lecture passe par le cache, et va à la base en cas d'absence (*cache
aside*) :

```go
// Get returns the balance of the account.
func (c *Cached) Get(ctx context.Context, id int64) (Balance, error) {
    if b, ok := c.Cache.Get(id); ok {
        return b, nil
    }
    if c.Group == nil {
        return c.load(ctx, id)
    }
    v, err, _ := c.Group.Do(strconv.FormatInt(id, 10), func() (any, error) { return c.load(ctx, id) })
    if err != nil {
        return Balance{}, err
    }
    return v.(Balance), nil
}
```

## 3. Mesure : combien de soldes faux ?

Le programme `cmd/stale` lit dix soldes pendant trois secondes, par 20
lecteurs, pendant que deux écrivains font des dépôts toutes les 2 ms.
Pour chaque lecture, il note si le solde rendu était **déjà remplacé**
dans la base au moment où la lecture a commencé, et depuis combien de
temps :

```text
$ go run ./cmd/stale
TTL 1s only                         reads  41549, hit rate  99.8%, old balance shown  97.0%, oldest 998ms
TTL 1s + delete on write            reads  39460, hit rate  94.8%, old balance shown   0.0%, oldest 0s
TTL 1s + invalidate(version)        reads  39578, hit rate  95.1%, old balance shown   0.0%, oldest 0s
delete on write, slow readers       reads  36859, hit rate  92.7%, old balance shown   3.3%, oldest 104ms
invalidate(version), slow readers   reads  36373, hit rate  92.2%, old balance shown   0.0%, oldest 0s
2 instances, invalidate A only      reads  40359, hit rate  99.8%, old balance shown  96.5%, oldest 996ms
2 instances + LISTEN/NOTIFY         reads  40077, hit rate  95.1%, old balance shown   0.9%, oldest 3ms
```

Ligne par ligne :

- **TTL seul** : 99,8 % de lectures servies par le cache, et **97 % de
  soldes faux**, jusqu'à une seconde de retard. Avec des dépôts toutes
  les 2 ms, presque chaque valeur en cache a déjà changé. Le taux de
  réussite du cache, qu'on surveille souvent, ne dit rien de cela.
- **TTL + suppression de la clé à chaque écriture** : plus aucun solde
  faux, et encore 95 % de réussite.
- **Avec des lecteurs ralentis** (une pause de 0 à 2 ms entre la lecture
  en base et la mise en cache, comme un ramasse-miettes ou une machine
  chargée) : la suppression laisse passer **3,3 % de soldes faux**,
  jusqu'à 104 ms. L'invalidation avec version, elle, n'en laisse passer
  aucun.
- **Deux instances** : l'écriture passe par A, qui invalide **son**
  cache ; le membre lit par B, dont le cache n'en sait rien : 96,5 % de
  soldes faux. C'est le cas de toute application qui tourne en plusieurs
  exemplaires.
- **Deux instances + `LISTEN`/`NOTIFY`** : B apprend chaque changement
  par PostgreSQL. 0,9 % de lectures faites dans les 3 ms entre le
  `COMMIT` et l'arrivée de la notification.

### La course de la suppression

| Instant | Lecteur | Écrivain |
|---|---|---|
| 1 | cache vide : lit la base, version 1 | |
| 2 | (ralenti) | change le solde, version 2, `COMMIT` |
| 3 | | supprime la clé |
| 4 | range la version 1 | |

Après l'instant 4, le cache garde la version 1 jusqu'à la fin de sa
durée de vie, ou jusqu'à la prochaine écriture. `Delete` ne peut pas
savoir que ce qu'on lui apporte est vieux. `Invalidate` retient que la
version 2 existe, et `Put` refuse tout ce qui est plus ancien :

```go
// A reader slowed down between its read and its Put cannot put back the
// balance it read before a deposit.
func TestASlowReaderCannotPutBackAnOldBalance(t *testing.T) {
    db := accounts(t)
    ctx := context.Background()
    c := &account.Cached{DB: db, Cache: cache.New[account.Balance](time.Hour)}
    read, resume := make(chan struct{}), make(chan struct{})
    c.AfterRead = func() { close(read); <-resume }
    done := make(chan account.Balance)
    go func() {
        b, err := c.Get(ctx, 1)
        if err != nil {
            t.Error(err)
        }
        done <- b
    }()
    <-read
    nb, err := account.Change(ctx, db, 1, 25000)
    if err != nil {
        t.Fatal(err)
    }
    c.Cache.Invalidate(1, nb.Version)
    close(resume)
    if old := <-done; old.Version != 1 {
        t.Fatalf("the slow reader read %+v, want version 1", old)
    }
    c.AfterRead = nil
    if got, err := c.Get(ctx, 1); err != nil || got.Version != 2 {
        t.Errorf("after the slow reader: %+v, %v; want version 2", got, err)
    }
}
```

### Le `NOTIFY` arrive au `COMMIT`

La notification part dans la **même transaction** que le changement de
solde. PostgreSQL ne la livre qu'au `COMMIT`, et jamais si la
transaction est annulée : aucune instance n'apprend un changement qui
n'a pas eu lieu. Chaque instance écoute :

```go
// Listen calls changed for each notified change, until ctx is done.
func Listen(ctx context.Context, db *pgxpool.Pool, ready chan<- struct{}, changed func(id, version int64)) error {
    conn, err := db.Acquire(ctx)
    if err != nil {
        return err
    }
    defer conn.Release()
    if _, err := conn.Exec(ctx, "LISTEN "+Channel); err != nil {
        return err
    }
    close(ready)
    for {
        n, err := conn.Conn().WaitForNotification(ctx)
        if err != nil {
            return err
        }
        idText, versionText, _ := strings.Cut(n.Payload, ":")
        id, err1 := strconv.ParseInt(idText, 10, 64)
        version, err2 := strconv.ParseInt(versionText, 10, 64)
        if err1 == nil && err2 == nil {
            changed(id, version)
        }
    }
}
```

Il reste une limite : une instance qui perd sa connexion d'écoute
manque les notifications de ce moment-là. La durée de vie reste donc
nécessaire, comme filet : elle borne le temps pendant lequel une
notification perdue peut tromper. Après une reconnexion, l'instance vide
son cache.

## 4. Mesure : deux cents membres à la fois

Le solde de la caisse d'une tontine se calcule à partir de ses
cotisations : 50 ms. Il est en cache pour une minute. Quand il expire, le
soir de la cotisation, 200 membres ouvrent la page en même temps. Le
programme `cmd/stampede` le reproduit, avec un pool de 32 connexions :

```text
$ go run ./cmd/stampede
without singleflight  200 members at once: 200 computations in the database, slowest page 394ms
with singleflight     200 members at once:   1 computations in the database, slowest page 52ms
```

Sans précaution, les 200 requêtes trouvent le cache vide **en même
temps**, et toutes lancent le calcul : **200 calculs de 50 ms**, qui font
la queue sur 32 connexions, et la page la plus lente attend 394 ms. Le
cache, conçu pour protéger la base, lui envoie au pire moment deux cents
fois la requête la plus chère.

Avec `singleflight`, la première requête calcule, et les 199 autres
**attendent son résultat** au lieu de recalculer : un seul calcul, 52 ms
pour tout le monde.

```go
func (c *Cached) load(ctx context.Context, id int64) (Balance, error) {
    c.Loads.Add(1)
    read := c.Read
    if read == nil {
        read = Read
    }
    b, err := read(ctx, c.DB, id)
    if c.AfterRead != nil {
        c.AfterRead()
    }
    if err == nil {
        c.Cache.Put(id, b, b.Version)
    }
    return b, err
}
```

`singleflight` ne regroupe que les requêtes **d'une même instance**.
Avec dix instances, on a au pire dix calculs au lieu de deux mille : cela
suffit presque toujours.

## 5. Mesure : décider sur le cache

Trente membres retirent 10 000 FCFA d'un compte qui en contient 100 000.
Le programme `cmd/decide` vérifie le solde dans le cache avant de lancer
le retrait (« retrait accepté » à l'écran), puis demande à la base. Dans
la dernière ligne, l'application ne vérifie rien elle-même et affiche la
réponse de la base :

```text
$ go run ./cmd/decide
cache, one after the other               accepted on screen 30, paid 10, refused by the application  0, refused by the database 20
cache + invalidate, one after the other  accepted on screen 10, paid 10, refused by the application 20, refused by the database  0
cache + invalidate, 30 at once           accepted on screen 30, paid 10, refused by the application  0, refused by the database 20
database decides, 30 at once             accepted on screen  0, paid 10, refused by the application  0, refused by the database 20
```

- **Avec le cache seul**, l'écran dit « accepté » 30 fois ; la base en
  paie 10 et refuse les 20 autres. Vingt membres ont vu un retrait
  accepté, puis un échec.
- **Avec l'invalidation**, les retraits faits un par un sont justes :
  chaque retrait invalide le solde, et le suivant lit la base.
- **Avec l'invalidation, mais 30 retraits en même temps** : de nouveau 30
  « accepté ». Les 30 lisent le même solde avant que le premier retrait
  ne soit validé. C'est la lecture puis l'écriture de la leçon 5.3 : le
  cache ne l'a pas créée, mais il l'élargit.
- **Quand la base décide**, 10 retraits payés et 20 refusés, sans
  promesse fausse.

Ce qui a protégé l'argent dans les trois premières lignes, c'est la
contrainte `CHECK (balance_fcfa >= 0)` : la base, dernier garde-fou
(leçon 5.1). Le cache sert à **afficher** ; une décision se prend dans la
base, dans la transaction qui écrit.

## 6. La campagne

```text
valeurs éternelles                           tuee
ancienne version acceptée                    tuee
invalidation réduite à Delete                tuee
invalidation lue comme une valeur            tuee
invalidation éternelle                       tuee
notification lue à l'envers                  tuee
singleflight ignoré                          tuee
valeur rangée sans sa version                SURVIT
version notifiée en retard                   tuee
8/9 tuees
```

La survivante : **une valeur rangée sans sa version** (`Put(id, b, 0)`).
Après une invalidation de la version 2, le cache refuse cette valeur
« version 0 » : chaque lecture va à la base, et rend quand même le bon
solde. Aucun test ne voyait de différence, puisque le solde affiché est
juste. Mais le cache ne sert plus à rien : chaque lecture après une
écriture devient une requête. Le test ajouté vérifie que la lecture
suivante est servie par le cache :

```go
    // The new balance is cached again: the next read is a hit.
    hits, _ := b.Cache.Stats()
    if _, err := b.Get(ctx, 1); err != nil {
        t.Fatal(err)
    }
    if after, _ := b.Cache.Stats(); after != hits+1 {
        t.Errorf("the read after the reload missed the cache")
    }
```

```text
valeurs éternelles                           tuee
ancienne version acceptée                    tuee
invalidation réduite à Delete                tuee
invalidation lue comme une valeur            tuee
invalidation éternelle                       tuee
notification lue à l'envers                  tuee
singleflight ignoré                          tuee
valeur rangée sans sa version                tuee
version notifiée en retard                   tuee
9/9 tuees
```

Un cache a deux façons d'être faux : rendre une valeur fausse, et ne plus
rien garder. La seconde ne casse aucun test de résultat ; elle se voit
dans le taux de réussite, et dans la charge de la base.

## 7. La grille

| Donnée | Cache ? | Comment |
|---|---|---|
| un solde affiché, qui change souvent | seulement si sa lecture est mesurée trop chère | invalidation avec version, `NOTIFY` entre instances, TTL court en filet |
| un calcul coûteux (total de l'année, classement) | oui | TTL, et `singleflight` contre les afflux simultanés |
| une donnée qui ne change presque jamais (le règlement d'une tontine, la liste des opérateurs) | oui | TTL long ; invalidation au changement si possible |
| une valeur qui sert à **décider** (retrait, prêt, versement) | **jamais** | lue dans la transaction qui écrit, avec un verrou ou une condition (leçon 5.3) |
| une page entière, la même pour tous | oui, souvent hors de l'application (CDN, proxy) | TTL de quelques secondes |

## 8. Les trois erreurs qui restent

### « Le taux de réussite est à 99 %, le cache marche »

La mesure de la section 3 montre 99,8 % de réussite et 97 % de soldes
faux. Le taux de réussite mesure ce que le cache fait gagner, pas ce
qu'il fait perdre. On mesure aussi l'**âge** des valeurs servies, ou du
moins on borne leur durée de vie par ce que le métier tolère.

### « On supprime la clé à chaque écriture, c'est donc toujours juste »

Juste sur une seule instance, avec des lecteurs qui ne sont jamais
ralentis. La section 3 montre 3,3 % de soldes faux dès que les lecteurs
le sont, et 96,5 % avec deux instances. Il faut la version, et un moyen
de prévenir toutes les instances.

### « On ajoute un cache, ce sera plus rapide »

Plus rapide en moyenne, et plus lent au pire moment : la section 4
envoie 200 calculs à la base à l'instant où le cache expire. Et chaque
cache ajoute une source de valeurs fausses, un mécanisme d'invalidation
à maintenir, et des incidents plus difficiles à comprendre (« sur mon
téléphone, le solde est bon »). Phil Karlton comptait l'invalidation
des caches parmi les deux choses les plus difficiles de l'informatique.

## 9. Le lien avec la production

- **Le taux de réussite et l'âge** : on expose les deux, par type de
  donnée. Une chute du taux de réussite après un déploiement signale un
  cache qui ne garde plus rien (la section 6).
- **Le redémarrage** : une instance qui démarre a un cache vide. Si
  toutes redémarrent ensemble (un déploiement), la base reçoit toute la
  charge d'un coup : c'est l'afflux de la section 4, à l'échelle du
  service. On redémarre progressivement.
- **`LISTEN`/`NOTIFY`** passe par une connexion dédiée par instance, à
  compter dans le nombre de connexions de la base ; avec un répartiteur
  de connexions comme PgBouncer en mode transaction, `LISTEN` ne marche
  pas, et l'écoute doit passer par une connexion directe.
- **Redis** remplace le cache en mémoire quand plusieurs instances
  doivent **partager** une valeur coûteuse. Les questions de cette leçon
  restent les mêmes : version, invalidation, afflux, et jamais de
  décision dessus.

## 10. Ce qu'il faut retenir

1. Un cache se justifie par un coût mesuré, après les index et la
   suppression des N+1.
2. Une durée de vie seule sert des valeurs anciennes ; on invalide à
   l'écriture, avec la version.
3. Plusieurs instances, plusieurs caches : `NOTIFY` au `COMMIT` les
   prévient toutes, et la durée de vie reste le filet.
4. Contre l'afflux sur une clé expirée, une seule requête calcule
   (`singleflight`).
5. On affiche depuis le cache ; on décide dans la base.

## 11. Approfondissement

### Écrire dans le cache plutôt qu'invalider

Au lieu d'invalider, l'écrivain peut ranger la nouvelle valeur
(`Put(id, nouveau, version)`), puisqu'il la connaît (*write-through*).
La lecture suivante est un succès. La version protège de la même façon
contre un lecteur en retard. Le risque : un écrivain qui range une
valeur, puis voit sa transaction échouer. On ne range qu'**après** le
`COMMIT`.

### Les caches en couches

Un navigateur, un CDN, l'application, Redis, et la base elle-même (ses
pages en mémoire) : chaque couche a sa durée de vie, et elles
s'additionnent. Un solde peut avoir trois caches entre la base et l'écran
du membre. La question de la section 1 se pose à chaque couche.

## 12. Le réflexe à installer

Avant d'ajouter un cache, demande-toi :

1. Combien coûte la lecture aujourd'hui, mesurée ? Qu'est-ce qui a déjà
   été fait (index, N+1) ?
2. Combien de temps la valeur peut-elle être fausse sans dommage ?
3. Qui écrit cette donnée, et comment chaque instance apprend-elle le
   changement ?
4. Que se passe-t-il quand la clé expire sous la charge ?
5. Cette valeur sert-elle à décider quelque chose ? Si oui, pas de cache.
