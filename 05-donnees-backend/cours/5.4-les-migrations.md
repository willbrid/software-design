# Leçon 5.4 — Faire évoluer un schéma sans coupure : les migrations

## L'essentiel en deux minutes

**Le problème, en une phrase.** Le schéma change avec l'application :
une colonne de plus, un index, une contrainte, un nom de colonne
corrigé. Chaque changement doit être appliqué **une fois**, sur une base
qui **sert pendant ce temps**, alors que l'ancienne et la nouvelle
version de l'application tournent côte à côte.

**Trois images.**

- **Le registre des travaux** : chaque migration est notée dans une
  table quand elle est faite. Ce qui est noté ne se refait pas, et ne se
  réécrit pas.
- **La file au guichet** : un `ALTER TABLE` qui attend son tour bloque
  tous ceux qui arrivent après lui, même ceux qui voulaient seulement
  lire.
- **Le pont provisoire** : pour remplacer un pont, on construit le
  nouveau à côté, on fait passer tout le monde, puis on démonte
  l'ancien. C'est *expand, migrate, contract*.

**Le code, en quelques lignes.** Une migration peut abandonner vite au
lieu de faire attendre tout le monde, et réessayer :

```go
// Options tune Up.
type Options struct {
    // LockTimeout bounds how long a migration waits for a lock; zero waits
    // forever. Past it, the migration gives up, and is tried again.
    LockTimeout time.Duration
    // Tries is the number of attempts of a migration that times out on a
    // lock; Pause separates them.
    Tries int
    Pause time.Duration
    // Unlocked skips the advisory lock. It exists only to measure what the
    // lock prevents.
    Unlocked bool
}
```

**Les règles à retenir.**

1. **Les migrations sont des fichiers numérotés**, appliqués dans
   l'ordre, une fois, et notés dans la base. Une migration appliquée ne
   se modifie plus : on en écrit une nouvelle.
2. **Plusieurs instances démarrent ensemble** : un verrou consultatif
   laisse une seule instance migrer.
3. **Chaque migration fixe un `lock_timeout`** : sinon, un `ALTER TABLE`
   coincé derrière un long rapport arrête toute l'application.
4. **Sur une grande table, on choisit la forme qui ne bloque pas** :
   `CREATE INDEX CONCURRENTLY`, une contrainte `NOT VALID` suivie de
   `VALIDATE`, une valeur par défaut constante.
5. **Un changement incompatible se fait en deux déploiements** :
   on ajoute (*expand*), les deux versions cohabitent, puis on retire
   (*contract*).

La suite le mesure avec des requêtes qui tournent pendant chaque
migration.

---

Les leçons 5.1 à 5.3 ont posé un schéma et protégé ses écritures. Mais
un schéma ne reste pas fixe : le modèle du niveau 4 évolue, et la base
doit suivre, sans arrêter le service. Le problème de cette leçon :

> **Comment changer le schéma d'une base qui sert, pendant que deux
> versions de l'application l'utilisent ?**

Le module de la leçon est `l54`, sur le même PostgreSQL 17. Tout ce qui
suit est mesuré sur un module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. Des fichiers numérotés, et un registre

Les migrations sont des fichiers SQL dans le dépôt, numérotés :

```text
migrations/001_member.sql
migrations/002_contribution.sql
migrations/003_contribution_by_member.sql
```

Elles sont intégrées au binaire avec `embed`, et appliquées au
démarrage. Le registre est une table, `schema_migrations`, qui note
chaque version appliquée et une **empreinte** (SHA-256) de son contenu :

```go
// Up applies the migrations not applied yet, and returns their versions.
// Several instances may call it at once: the advisory lock lets one work,
// and the others find nothing left to do.
func Up(ctx context.Context, db *pgxpool.Pool, ms []Migration, opt Options) ([]int, error) {
    conn, err := db.Acquire(ctx)
    if err != nil {
        return nil, err
    }
    defer conn.Release()
    if !opt.Unlocked {
        if err := lock(ctx, conn.Conn()); err != nil {
            return nil, err
        }
        defer conn.Exec(context.Background(), `SELECT pg_advisory_unlock($1)`, lockKey)
    }
    _, err = conn.Exec(ctx, `CREATE TABLE IF NOT EXISTS schema_migrations (
        version    INT PRIMARY KEY,
        name       TEXT NOT NULL,
        checksum   TEXT NOT NULL,
        applied_at TIMESTAMPTZ NOT NULL DEFAULT now())`)
    if err != nil {
        return nil, err
    }
    done := map[int]string{}
    rows, err := conn.Query(ctx, `SELECT version, checksum FROM schema_migrations`)
    if err != nil {
        return nil, err
    }
    for rows.Next() {
        var v int
        var sum string
        if err := rows.Scan(&v, &sum); err != nil {
            return nil, err
        }
        done[v] = sum
    }
    if err := rows.Err(); err != nil {
        return nil, err
    }
    var applied []int
    for _, m := range ms {
        if sum, ok := done[m.Version]; ok {
            if sum != m.checksum() {
                return applied, fmt.Errorf("%w: %03d_%s", ErrChanged, m.Version, m.Name)
            }
            continue
        }
        if err := apply(ctx, conn.Conn(), m, opt); err != nil {
            return applied, fmt.Errorf("%03d_%s: %w", m.Version, m.Name, err)
        }
        applied = append(applied, m.Version)
    }
    return applied, nil
}
```

Trois règles sont dans ce code :

- **une fois** : une version notée n'est pas rejouée ;
- **une migration appliquée ne change plus** : si son fichier a été
  modifié, l'empreinte diffère, et `Up` refuse (`ErrChanged`). Corriger
  une migration déjà passée en production, c'est créer une base de
  développement différente de la production. On écrit une nouvelle
  migration ;
- **tout ou rien** : chaque migration tourne dans une transaction avec
  l'écriture de sa ligne dans le registre (leçon 5.2). Une migration qui
  échoue au milieu ne laisse rien, et sera rejouée entière.

Sauf une : `CREATE INDEX CONCURRENTLY` refuse de tourner dans une
transaction. Le fichier le dit sur sa première ligne :

```sql
-- migrate: no-transaction
CREATE INDEX CONCURRENTLY IF NOT EXISTS contribution_by_member ON contribution (member_id);
```

Une telle migration n'est plus atomique : si elle échoue, elle peut
laisser un index invalide. Elle doit donc contenir **une seule**
instruction, et pouvoir être rejouée (`IF NOT EXISTS`).

## 2. Mesure : cinq instances qui démarrent ensemble

En production, l'application tourne en plusieurs exemplaires. Un
déploiement les démarre presque en même temps, et chacun applique les
migrations. Le programme `cmd/instances` démarre cinq instances sur une
base vide, vingt fois. La première version prenait le verrou avec
`pg_advisory_lock`, qui attend dans la base que le verrou se libère :

```text
$ go run ./cmd/instances
without a lock         starts with an instance in error: 20/20
     32 x 001_member: ERROR: duplicate key value violates unique constraint "pg_type_typname_nsp_index"
     17 x 001_member: ERROR: relation "member" already exists
      3 x 002_contribution: ERROR: type "contribution" already exists
     12 x 002_contribution: ERROR: relation "contribution" already exists
      1 x 002_contribution: ERROR: duplicate key value violates unique constraint "pg_class_relname_nsp_index"
     14 x 002_contribution: ERROR: duplicate key value violates unique constraint "pg_type_typname_nsp_index"
      1 x 001_member: ERROR: type "member" already exists
with the advisory lock starts with an instance in error: 20/20
     71 x ERROR: deadlock detected
      9 x 003_contribution_by_member: ERROR: deadlock detected
```

Sans verrou, **les vingt démarrages ont une instance en erreur** : deux
instances créent la même table au même moment. Le message le plus
fréquent est surprenant : `pg_type_typname_nsp_index`. Chaque table crée
aussi un type, et c'est l'unicité de son nom dans le catalogue qui
refuse la deuxième. `CREATE TABLE IF NOT EXISTS` ne protège pas non
plus : la vérification et la création ont le même intervalle que dans
la leçon 5.1.

**Avec `pg_advisory_lock`, c'est pire : les vingt démarrages finissent
en interblocage.** L'instance qui tient le verrou lance
`CREATE INDEX CONCURRENTLY`, qui attend que toutes les transactions en
cours se terminent. Or les quatre autres instances sont **dans** une
instruction (`SELECT pg_advisory_lock(...)`), donc dans une
transaction, et elles attendent le verrou. Chacune attend l'autre ;
PostgreSQL le détecte et en annule une.

La correction : ne pas attendre **dans** la base. On essaie le verrou
avec `pg_try_advisory_lock`, qui répond tout de suite, et on réessaie
toutes les 50 ms :

```go
// lock takes the advisory lock of the migrations, trying again every 50 ms.
// It does not wait inside pg_advisory_lock: a waiting statement holds a
// snapshot, and CREATE INDEX CONCURRENTLY, run by the instance that has
// the lock, waits for every snapshot to end. Each would wait for the other.
func lock(ctx context.Context, conn *pgx.Conn) error {
    for {
        var ok bool
        if err := conn.QueryRow(ctx, `SELECT pg_try_advisory_lock($1)`, lockKey).Scan(&ok); err != nil {
            return err
        }
        if ok {
            return nil
        }
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-time.After(50 * time.Millisecond):
        }
    }
}
```

      1 x 001_member: ERROR: duplicate key value violates unique constraint "pg_class_relname_nsp_index"
     23 x 001_member: ERROR: duplicate key value violates unique constraint "pg_type_typname_nsp_index"
     19 x 001_member: ERROR: relation "member" already exists
      1 x 001_member: ERROR: type "member" already exists

les trois migrations ont été appliquées trois fois au total, pas quinze.

## 3. Mesure : la file derrière un `ALTER TABLE`

Ajouter une colonne sans valeur par défaut ne touche aucune ligne : c'est
instantané. Mais `ALTER TABLE` demande le verrou le plus fort,
`ACCESS EXCLUSIVE`, qui exclut **même les lectures**. Il doit attendre
que les transactions en cours sur la table se terminent, et pendant
qu'il attend, **les nouvelles requêtes font la queue derrière lui**.

Le programme `cmd/queue` fait lire des membres par 20 travailleurs, en
continu, pendant qu'il ajoute une colonne à `member`. Dans le deuxième
cas, un rapport mensuel tient une transaction de trois secondes sur la
table au moment de la migration :

```text
$ go run ./cmd/queue
ALTER alone                migration    9ms | requests 13096, errors    0, slower than 100ms    0, slowest 24ms
ALTER behind a report      migration 2.856s | requests  4860, errors    0, slower than 100ms   20, slowest 2.855s
ALTER, lock_timeout 200ms  migration 3.045s | requests  9443, errors    0, slower than 100ms  120, slowest 203ms
ALTER, lock_timeout 50ms   migration 2.861s | requests 11807, errors    0, slower than 100ms    0, slowest 55ms
```

- **Seul**, l'`ALTER` prend 9 ms : aucun membre ne remarque rien.
- **Derrière le rapport**, l'`ALTER` attend 2,86 s, et **toute
  l'application attend avec lui** : chaque lecture a été bloquée jusqu'à
  2,86 s, et le nombre de requêtes servies a chuté de 13 096 à 4 860.
  Pendant près de trois secondes, l'application ne répond plus, alors
  qu'aucune requête n'a rien demandé d'autre que lire.
- **Avec `lock_timeout`**, l'`ALTER` abandonne au bout du délai, laisse
  passer la file, attend, et réessaie. À 200 ms, chaque essai bloque
  encore les lectures pendant 200 ms (120 requêtes lentes). À **50 ms**,
  aucune requête ne dépasse 100 ms, et la migration passe dès la fin du
  rapport.

Le code de l'essai :

```go
// apply runs one migration, again while it times out on a lock.
func apply(ctx context.Context, conn *pgx.Conn, m Migration, opt Options) error {
    timeout := fmt.Sprintf("SET lock_timeout = %d", opt.LockTimeout.Milliseconds())
    record := func(q interface {
        Exec(context.Context, string, ...any) (pgconn.CommandTag, error)
    }) error {
        _, err := q.Exec(ctx, `INSERT INTO schema_migrations (version, name, checksum) VALUES ($1, $2, $3)`,
            m.Version, m.Name, m.checksum())
        return err
    }
    var err error
    for try := 1; try <= max(opt.Tries, 1); try++ {
        if m.NoTx {
            if _, err = conn.Exec(ctx, timeout); err == nil {
                if _, err = conn.Exec(ctx, m.SQL); err == nil {
                    err = record(conn)
                }
                _, _ = conn.Exec(ctx, "RESET lock_timeout")
            }
        } else {
            err = pgx.BeginFunc(ctx, conn, func(tx pgx.Tx) error {
                if _, err := tx.Exec(ctx, "SET LOCAL "+strings.TrimPrefix(timeout, "SET ")); err != nil {
                    return err
                }
                if _, err := tx.Exec(ctx, m.SQL); err != nil {
                    return err
                }
                return record(tx)
            })
        }
        var pgErr *pgconn.PgError
        if !errors.As(err, &pgErr) || pgErr.Code != "55P03" { // lock_not_available
            return err
        }
        time.Sleep(opt.Pause)
    }
    return err
}
```

## 4. Mesure : changer une grande table

Le programme `cmd/bigtable` modifie une table de 2 000 000 de
cotisations pendant que dix travailleurs continuent d'enregistrer des
cotisations :

```text
$ go run ./cmd/bigtable
ADD COLUMN, constant default      15ms | requests   755, errors    0, slower than 100ms    0, slowest 20ms
ADD COLUMN, volatile default    3.273s | requests   806, errors    0, slower than 100ms   10, slowest 3.238s
CREATE INDEX                     862ms | requests   761, errors    0, slower than 100ms   10, slowest 858ms
CREATE INDEX CONCURRENTLY        820ms | requests  1756, errors    0, slower than 100ms    0, slowest 23ms
ADD CHECK                        221ms | requests   776, errors    0, slower than 100ms   10, slowest 215ms
ADD CHECK NOT VALID               14ms | requests   775, errors    0, slower than 100ms    0, slowest 10ms
VALIDATE CONSTRAINT              267ms | requests  1059, errors    0, slower than 100ms    0, slowest 8ms
```

| Changement | Ce qui se passe | Écritures bloquées |
|---|---|---|
| `ADD COLUMN ... DEFAULT 'momo'` | la valeur constante est notée une fois dans le catalogue ; aucune ligne n'est réécrite | non (15 ms) |
| `ADD COLUMN ... DEFAULT clock_timestamp()` | une valeur différente par ligne : **la table entière est réécrite** | **3,2 s** |
| `CREATE INDEX` | lit toute la table, et bloque les écritures pendant ce temps | **858 ms** |
| `CREATE INDEX CONCURRENTLY` | deux passages sur la table, sans bloquer les écritures | non (23 ms au plus) |
| `ADD CONSTRAINT ... CHECK` | vérifie toutes les lignes sous `ACCESS EXCLUSIVE` | **215 ms** |
| `... CHECK ... NOT VALID` | la règle vaut pour les nouvelles lignes ; les anciennes ne sont pas lues | non |
| `VALIDATE CONSTRAINT` | vérifie les anciennes lignes sans bloquer les écritures | non (8 ms au plus) |

Les durées grandissent avec la table. À 2 millions de lignes, 858 ms
d'écritures bloquées passent presque inaperçues ; à 200 millions, c'est
une coupure d'une minute et demie. La forme sûre coûte une ligne de
plus, et ne dépend pas de la taille.

Deux remarques :

- `CREATE INDEX CONCURRENTLY` attend toutes les transactions en cours :
  un rapport de deux heures le fait attendre deux heures (c'est
  l'interblocage de la section 2) ;
- `NOT VALID` puis `VALIDATE` sont deux migrations distinctes, ou deux
  instructions de la même migration. Dans les deux cas, le verrou fort
  ne dure que le temps de noter la contrainte.

## 5. Renommer une colonne pendant un déploiement

Le téléphone des membres s'appelle `phone`. On veut l'appeler
`phone_e164`, du nom de la norme du format `+237...`. La version 1 de
l'application lit et écrit `phone` ; la version 2, `phone_e164`.

Un déploiement progressif (*rolling update*) remplace les instances une
par une. Pendant un moment, **v1 et v2 tournent ensemble** sur la même
base. Le programme `cmd/rename` le reproduit : v1 seule pendant une
seconde, puis la migration et le démarrage de v2, les deux ensemble
pendant une seconde, puis v2 seule.

```text
$ go run ./cmd/rename
rename in one step:
  v1 requests  2857, errors 1427, slower than 100ms    0, slowest 69ms
  v2 requests  2831, errors    0, slower than 100ms    0, slowest 68ms
  members without phone_e164: 0
  last error: ERROR: column "phone" of relation "member" does not exist (SQLSTATE 42703)
expand, then contract:
  v1 requests  2706, errors    0, slower than 100ms    0, slowest 65ms
  v2 requests  2754, errors    0, slower than 100ms    0, slowest 61ms
  members without phone_e164: 0
```

**Renommer en une fois** casse v1 dès la migration : **1 427 requêtes en
erreur** en une seconde, toutes « column "phone" does not exist ». Et
l'inverse serait aussi vrai : migrer après le déploiement casserait v2.
Aucun ordre ne marche, parce que le changement est **incompatible** avec
l'une des deux versions.

**Expand, puis contract** : aucune erreur. Le changement est découpé.

**1. Expand** (avec le déploiement de v2) : ajouter la nouvelle colonne,
garder les deux colonnes égales quelle que soit la version qui écrit,
et recopier les lignes existantes.

```go
// Expand adds the new column, keeps both columns equal whichever version
// writes, and copies the existing rows. Both versions keep working.
var Expand = []migrate.Migration{{Version: 100, Name: "expand_phone", SQL: `
```

**2. Migrate** : v2 se déploie ; v1 et v2 écrivent chacune dans leur
colonne, et le déclencheur recopie dans l'autre.

**3. Contract** (au déploiement **suivant**, quand plus aucune v1 ne
tourne) : rendre la nouvelle colonne obligatoire, retirer le
déclencheur et l'ancienne colonne.

```go
// Contract runs once no v1 is left: the new column becomes mandatory, the
// old one goes.
var Contract = []migrate.Migration{{Version: 101, Name: "contract_phone", SQL: `
```

Le contrat est une **deuxième** migration, livrée plus tard. Si on la
livrait avec l'expand, elle retirerait `phone` pendant que v1 tourne
encore : on retrouverait les 1 427 erreurs.

Le test qui le garantit écrit avec chaque version et vérifie que l'autre
voit la même chose :

```go
func TestEachVersionSeesWhatTheOtherWrites(t *testing.T) {
    db := migrated(t, phone.Expand)
    ctx := context.Background()
    for _, sql := range []string{
        `INSERT INTO member (tontine_id, name, phone) VALUES (1, 'Ebai', '+237690000002')`,        // v1
        `INSERT INTO member (tontine_id, name, phone_e164) VALUES (1, 'Mbarga', '+237690000003')`, // v2
        `UPDATE member SET phone = '+237690000011' WHERE name = 'Ngo Biyong'`,                     // v1
        `UPDATE member SET phone_e164 = '+237690000022' WHERE name = 'Ebai'`,                      // v2
    } {
        if _, err := db.Exec(ctx, sql); err != nil {
            t.Fatalf("%s: %v", sql, err)
        }
    }
    for name, want := range map[string]string{
        "Ebai": "+237690000022", "Mbarga": "+237690000003", "Ngo Biyong": "+237690000011",
    } {
        if v1, v2 := phones(t, db, name); v1 != want || v2 != want {
            t.Errorf("%s: phone %q, phone_e164 %q; want %q in both", name, v1, v2, want)
        }
    }
}
```

Sur une grande table, la recopie (`UPDATE ... WHERE phone_e164 IS NULL`)
se fait **par lots**, de quelques milliers de lignes, dans une tâche à
part. Un seul `UPDATE` de 200 millions de lignes tiendrait des verrous
et grossirait le journal pendant des heures.

## 6. La campagne

```text
aucun verrou consultatif                     tuee
verrou attendu dans pg_advisory_lock         tuee
migration modifiée acceptée                  tuee
migration non enregistrée                    tuee
marque no-transaction ignorée                tuee
pas de nouvel essai sur un verrou            SURVIT
migrations dans le désordre                  tuee
changement de v1 non recopié                 tuee
lignes existantes non recopiées              tuee
nouvelle colonne facultative                 tuee
9/10 tuees
```

Une survivante : **les nouveaux essais ne sont jamais vérifiés**. Le
test de la section 3 vérifie que la migration abandonne vite derrière un
rapport, puis qu'elle passe une fois le rapport fini. Une migration qui
n'essaie qu'une fois passe ce test. Le test ajouté libère le rapport
**pendant** les essais, et demande que la migration passe :

```go
// A short report ends while the migration is trying again: the migration
// passes on a later try, without ever waiting more than its lock timeout.
func TestAMigrationTriesAgainUntilTheReportEnds(t *testing.T) {
    db, ms, ctx := empty(t), load(t), context.Background()
    if _, err := migrate.Up(ctx, db, ms, migrate.Options{}); err != nil {
        t.Fatal(err)
    }
    report, err := db.Begin(ctx)
    if err != nil {
        t.Fatal(err)
    }
    if _, err := report.Exec(ctx, `SELECT count(*) FROM member`); err != nil {
        t.Fatal(err)
    }
    ended := make(chan error, 1)
    go func() {
        time.Sleep(300 * time.Millisecond)
        ended <- report.Commit(ctx)
    }()
    more := append(ms, migrate.Migration{Version: 4, Name: "note", SQL: `ALTER TABLE member ADD COLUMN note TEXT`})
    opt := migrate.Options{LockTimeout: 50 * time.Millisecond, Tries: 50, Pause: 50 * time.Millisecond}
    if got, err := migrate.Up(ctx, db, more, opt); err != nil || len(got) != 1 {
        t.Errorf("got %v, %v; want migration 4 after a few tries", got, err)
    }
    if err := <-ended; err != nil {
        t.Fatal(err)
    }
}
```

## 7. La grille

| Changement voulu | Forme sans coupure |
|---|---|
| ajouter une colonne | `ADD COLUMN` sans valeur par défaut, ou avec une constante |
| ajouter une colonne obligatoire | l'ajouter facultative, remplir par lots, puis `CHECK (...) NOT VALID` et `VALIDATE` |
| ajouter un index | `CREATE INDEX CONCURRENTLY`, seul dans sa migration, hors transaction |
| ajouter une contrainte (`CHECK`, clé étrangère) | `NOT VALID`, puis `VALIDATE CONSTRAINT` |
| ajouter une unicité | `CREATE UNIQUE INDEX CONCURRENTLY`, puis `ADD CONSTRAINT ... UNIQUE USING INDEX` |
| renommer une colonne, une table | expand (nouvelle colonne + recopie) ; contract au déploiement suivant |
| changer le type d'une colonne | expand/contract, comme un renommage |
| supprimer une colonne | d'abord une version de l'application qui ne la lit plus ; puis `DROP COLUMN` |
| toute migration | un `lock_timeout` court et des essais répétés |

## 8. Les trois erreurs qui restent

### « Je corrige la migration 12, elle avait une faute »

Si la migration 12 est passée en production, la base de production a la
faute, et les nouvelles bases ne l'auront pas : les deux divergent sans
que personne le sache. L'empreinte du registre l'empêche. On écrit la
migration 13, qui corrige.

### « Une migration se teste en la lançant sur ma base »

Une base de développement a cent lignes et aucun trafic. La section 4
montre que la même instruction peut durer 15 ms ou bloquer 3 s selon sa
**forme**, et que ce qui compte est la taille de la table et ce qui
tourne en même temps. On relit chaque migration avec la grille, et l'on
teste les plus risquées sur une copie de la taille de la production.

### « On fera un retour arrière si ça se passe mal »

Une migration qui a supprimé une colonne ne se défait pas : les données
sont parties. Expand/contract rend le retour arrière possible tant que
le contract n'est pas passé : on redéploie v1, qui trouve sa colonne,
tenue à jour par le déclencheur. C'est une raison de plus pour livrer le
contract **séparément**, une fois la version stable.

## 9. Le lien avec la production

- **Une page qui s'arrête pendant trois secondes lors d'un déploiement**,
  sans erreur dans les journaux de l'application : c'est souvent la
  section 3. Dans PostgreSQL, `pg_stat_activity` montre alors des
  requêtes `wait_event_type = Lock` derrière un `ALTER TABLE`.
- **La sonde de démarrage** (*readiness probe*) d'une instance qui migre
  doit attendre la fin de la migration ; les autres instances, qui
  attendent le verrou, ne sont pas prêtes non plus.
- **Migrer avant ou après le déploiement ?** Avec expand/contract, la
  réponse est fixe : l'expand passe **avant** (ou au démarrage de) la
  nouvelle version ; le contract, **après** que l'ancienne a disparu.
- **`lock_timeout` et `statement_timeout`** se règlent pour
  l'utilisateur qui migre (`ALTER ROLE migrator SET lock_timeout =
  '50ms'`), pour qu'aucun outil, ni une commande tapée à la main dans
  `psql`, ne puisse l'oublier.

## 10. Ce qu'il faut retenir

1. Les migrations sont des fichiers numérotés, appliqués une fois,
   notés avec leur empreinte, et jamais modifiés après coup.
2. Plusieurs instances se départagent avec un verrou consultatif, essayé
   sans attendre dans la base.
3. Un `ALTER TABLE` qui attend bloque toutes les requêtes derrière lui :
   chaque migration a un `lock_timeout` court, et réessaie.
4. Sur une grande table, on choisit la forme qui ne bloque pas les
   écritures.
5. Un changement incompatible se fait en deux temps : expand avec la
   nouvelle version, contract quand l'ancienne a disparu.

## 11. Approfondissement

### Les outils

Des outils font ce que fait le paquet `migrate` de la leçon :
`golang-migrate`, `goose`, `atlas`, `tern` (de l'auteur de pgx). Le
paquet de la leçon est là pour montrer ce qu'il faut leur demander :
un verrou entre instances, un registre avec empreinte, une transaction
par migration, une marque pour les migrations hors transaction, et un
`lock_timeout`.

### Les migrations de données

Changer le **schéma** et changer les **données** (recopier, corriger,
calculer) sont deux choses différentes. Une migration de données sur une
grande table se fait par lots, se reprend là où elle s'est arrêtée, et
tourne souvent hors du démarrage de l'application, comme un travail à
part.

## 12. Le réflexe à installer

Avant de fusionner une migration, demande-toi :

1. Quel verrou prend-elle, et combien de temps, sur la taille de la
   production ?
2. Que se passe-t-il si un long rapport tient la table à ce moment ?
3. L'ancienne version de l'application marche-t-elle encore après elle ?
   Et la nouvelle, avant elle ?
4. Si elle échoue au milieu, peut-on la relancer ?
5. Comment revient-on en arrière ?
