# Leçon 5.1 — Du modèle au schéma : la base de données comme dernier garde-fou

## L'essentiel en deux minutes

**Le problème, en une phrase.** Les règles du modèle de la leçon 4.3
(« un membre tient au moins une part », « un mois n'est versé qu'une
fois ») sont souvent écrites seulement dans le code Go. Or l'application
n'est pas la seule à écrire dans la base : un script de reprise, une
correction tapée dans `psql`, une deuxième version de l'application, ou
deux requêtes qui arrivent au même instant passent à côté de ces
vérifications.

**Trois images.**

- **Le guichet et le coffre** : le guichetier vérifie la pièce
  d'identité, mais le coffre a sa propre serrure. Si quelqu'un passe par
  la porte de service, c'est la serrure qui le refuse.
- **Le cahier de la trésorière** : une page de cahier accepte tout,
  même « Fouda, téléphone : — » ou une cotisation de « −50 000 ». Une
  table sans contrainte est un cahier.
- **La place de parking numérotée** : deux voitures ne peuvent pas
  occuper la place 12. Personne n'a besoin de vérifier avant de se garer :
  la place elle-même l'empêche. Une contrainte `UNIQUE` est cette place.

**Le code, en quelques lignes.** La règle est dans le schéma, et le Go
traduit le refus de la base en erreur du domaine :

```sql
    CONSTRAINT payout_once_per_cycle UNIQUE (tontine_id, cycle)
```

```go
// rules maps each named constraint to the rule it protects.
var rules = map[string]error{
    "member_phone_unique":           tontine.ErrDuplicatePhone,
    "contribution_member":           tontine.ErrUnknownMember,
    "contribution_once_per_cycle":   tontine.ErrAlreadyContributed,
    "payout_beneficiary_in_tontine": tontine.ErrNotAMember,
    "payout_once_per_cycle":         tontine.ErrAlreadyPaid,
}
```

**Les règles à retenir.**

1. **La base de données est le dernier garde-fou** : toute règle qui
   porte sur une seule ligne ou sur l'unicité doit y être écrite, parce
   que tout ce qui écrit dans la base passe par elle.
2. **Vérifier puis écrire ne protège pas l'unicité** : entre le `SELECT`
   qui vérifie et l'`INSERT` qui écrit, une autre requête peut écrire. Une
   contrainte `UNIQUE` ne laisse pas cet intervalle.
3. **On nomme chaque contrainte**, et le code traduit le nom en erreur du
   domaine.
4. **Un `CHECK` laisse passer `NULL`** : une valeur obligatoire demande
   `NOT NULL`, en plus de son `CHECK`.
5. **On teste le schéma lui-même**, avec du SQL qui ne passe pas par
   l'application, comme le ferait un script.

La suite mesure tout cela sur un vrai PostgreSQL.

---

Le niveau 4 a appris à trouver les règles d'un domaine et à les écrire
dans un modèle conceptuel. Le niveau 5 descend vers les données : où ces
règles vivent quand le système tourne, et ce qui leur arrive quand
plusieurs choses se passent en même temps. Le problème de cette leçon :

> **Les règles du modèle sont vérifiées par l'application. Qu'est-ce qui
> les protège quand quelque chose écrit dans la base sans passer par
> elle, ou au même moment qu'elle ?**

Le module de la leçon est `l51` ; il demande un PostgreSQL 17, lancé
par exemple avec
`docker run -d --name sd-pg -p 55432:5432 -e POSTGRES_PASSWORD=dev postgres:17`.
Chaque test et chaque programme crée son propre schéma vide et le
supprime à la fin. Tout ce qui suit est mesuré sur un module vert sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Le point de départ : le cahier devenu tables

La première version de l'application de la tontine a repris le cahier
de la trésorière tel quel : les bonnes colonnes, et aucune règle.

```sql
CREATE TABLE contribution (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    member_id   BIGINT,
    cycle       TEXT,
    amount_fcfa BIGINT
);

CREATE TABLE payout (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tontine_id  BIGINT,
    cycle       TEXT,
    member_id   BIGINT,
    amount_fcfa BIGINT
);
```

Les règles sont toutes dans le Go. Chaque méthode vérifie avant
d'écrire, par exemple le versement :

```go
// Pay records that memberID received the pot of the cycle. It checks that
// the beneficiary belongs to the tontine and that the cycle is not paid yet.
func (s *Store) Pay(ctx context.Context, tontineID int64, cycle string, memberID, amountFCFA int64) error {
    month, err := tontine.ParseCycle(cycle)
    if err != nil || amountFCFA <= 0 {
        return tontine.ErrInvalid
    }
    t, err := s.tontineOf(ctx, memberID)
    if err != nil {
        return err
    }
    if t != tontineID {
        return tontine.ErrNotAMember
    }
    var paid bool
    err = s.db.QueryRow(ctx,
        `SELECT EXISTS (SELECT 1 FROM payout WHERE tontine_id = $1 AND cycle = $2)`,
        tontineID, month.Format("2006-01-02")).Scan(&paid)
    if err != nil {
        return err
    }
    if paid {
        return tontine.ErrAlreadyPaid
    }
    _, err = s.db.Exec(ctx,
        `INSERT INTO payout (tontine_id, cycle, member_id, amount_fcfa) VALUES ($1, $2, $3, $4)`,
        tontineID, month.Format("2006-01-02"), memberID, amountFCFA)
    return err
}
```

Ce code est soigné. Il vérifie le format, l'appartenance du bénéficiaire
à la tontine, et qu'aucun versement n'existe déjà pour ce mois. Ses neuf
tests passent :

```text
--- PASS: TestAPhoneIsRegisteredOncePerTontine (0.05s)
--- PASS: TestAMemberHoldsAtLeastOneShare (0.05s)
--- PASS: TestAPhoneHasTheCameroonianFormat (0.05s)
--- PASS: TestAMemberContributesOncePerCycle (0.05s)
--- PASS: TestAContributionIsPositive (0.06s)
--- PASS: TestAContributionNeedsAMember (0.10s)
--- PASS: TestACycleIsPaidOnce (0.10s)
--- PASS: TestTheBeneficiaryBelongsToTheTontine (0.09s)
--- PASS: TestThePotSumsTheCycleOfTheTontine (0.07s)
```

On va lui faire subir deux épreuves ordinaires : la reprise du cahier
papier, puis deux requêtes qui arrivent ensemble.

## 3. Mesure : deux requêtes au même instant

La reprise est passée à côté du Go. Mais même quand toutes les écritures
passent par le Go, il reste un trou. Le programme `cmd/race` envoie
plusieurs versements du même mois, avec un écart donné entre eux, et
recommence sur 50 tontines :

```text
$ go run ./cmd/race -requests 2 -gap 0
loose   2 requests 0s apart, cycles paid more than once: 49/50, extra payouts:  49 (12250000 FCFA), worst cycle: 2 payouts
strict  2 requests 0s apart, cycles paid more than once:  0/50, extra payouts:   0 (0 FCFA), worst cycle: 1 payouts
$ go run ./cmd/race -requests 2 -gap 1ms
loose   2 requests 1ms apart, cycles paid more than once: 39/50, extra payouts:  39 (9750000 FCFA), worst cycle: 2 payouts
strict  2 requests 1ms apart, cycles paid more than once:  0/50, extra payouts:   0 (0 FCFA), worst cycle: 1 payouts
$ go run ./cmd/race -requests 2 -gap 10ms
loose   2 requests 10ms apart, cycles paid more than once:  0/50, extra payouts:   0 (0 FCFA), worst cycle: 1 payouts
strict  2 requests 10ms apart, cycles paid more than once:  0/50, extra payouts:   0 (0 FCFA), worst cycle: 1 payouts
$ go run ./cmd/race -requests 20 -gap 0
loose  20 requests 0s apart, cycles paid more than once: 49/50, extra payouts: 904 (226000000 FCFA), worst cycle: 20 payouts
strict 20 requests 0s apart, cycles paid more than once:  0/50, extra payouts:   0 (0 FCFA), worst cycle: 1 payouts
```

Avec deux requêtes envoyées au même instant (un double clic, ou un
nouvel essai pendant que la première requête est encore en cours), la
version qui vérifie avant d'écrire paie le mois **deux fois dans 49
tontines sur 50**. Avec 1 ms d'écart, encore 39 sur 50. Avec 10 ms,
plus aucune.

Ce qui se passe est toujours la même chose :

| Instant | Requête A | Requête B |
|---|---|---|
| 1 | `SELECT EXISTS` : pas de versement | |
| 2 | | `SELECT EXISTS` : pas de versement |
| 3 | `INSERT` du versement | |
| 4 | | `INSERT` du versement |

Chaque requête a vérifié honnêtement, et chacune avait raison au moment
où elle a vérifié. L'intervalle entre la vérification et l'écriture dure
ici moins d'une milliseconde, parce que la base est sur la même machine.
En production, il dure au moins un aller-retour réseau vers la base, et
bien plus quand celle-ci est chargée : l'intervalle s'élargit exactement
quand le trafic monte.

Le schéma strict, lui, verse le mois une seule fois dans tous les cas.
La contrainte `UNIQUE (tontine_id, cycle)` n'a pas d'intervalle : c'est
la base qui décide, au moment de l'écriture, et la deuxième écriture est
refusée.

## 4. Le schéma qui porte les règles

Voici les deux tables les plus importantes du schéma strict :

```sql
CREATE TABLE member (
    id         BIGINT PRIMARY KEY,
    tontine_id BIGINT NOT NULL REFERENCES tontine (id),
    name       TEXT   NOT NULL CHECK (name <> ''),
    phone      TEXT   NOT NULL,
    shares     INT    NOT NULL,
    CONSTRAINT member_phone_format CHECK (phone ~ '^\+237[0-9]{9}$'),
    CONSTRAINT member_has_a_share CHECK (shares >= 1),
    CONSTRAINT member_phone_unique UNIQUE (tontine_id, phone),
    -- lets payout check that its beneficiary belongs to the same tontine
    CONSTRAINT member_in_tontine UNIQUE (id, tontine_id)
);
```

```sql
CREATE TABLE payout (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tontine_id  BIGINT NOT NULL,
    cycle       DATE   NOT NULL,
    member_id   BIGINT NOT NULL,
    amount_fcfa BIGINT NOT NULL,
    CONSTRAINT payout_beneficiary_in_tontine FOREIGN KEY (member_id, tontine_id)
        REFERENCES member (id, tontine_id),
    CONSTRAINT payout_cycle_is_a_month CHECK (extract(day FROM cycle) = 1),
    CONSTRAINT payout_positive CHECK (amount_fcfa > 0),
    CONSTRAINT payout_once_per_cycle UNIQUE (tontine_id, cycle)
);
```

Chaque règle du modèle trouve sa forme :

| Règle du modèle | Forme dans le schéma |
|---|---|
| une valeur est obligatoire | `NOT NULL` |
| une part, un montant sont positifs | `CHECK (shares >= 1)`, `CHECK (amount_fcfa > 0)` |
| un téléphone a le format camerounais | `CHECK (phone ~ '^\+237[0-9]{9}$')` |
| un cycle est un mois | une colonne `DATE`, et `CHECK (extract(day FROM cycle) = 1)` |
| un téléphone, une fois par tontine | `UNIQUE (tontine_id, phone)` |
| un mois, un seul versement | `UNIQUE (tontine_id, cycle)` |
| une cotisation vient d'un membre qui existe | clé étrangère vers `member (id)` |
| le bénéficiaire appartient à **cette** tontine | clé étrangère composée `(member_id, tontine_id)` |

La dernière ligne mérite qu'on s'y arrête. Une clé étrangère simple vers
`member (id)` vérifie que le bénéficiaire existe, mais il pourrait
appartenir à une autre tontine. La clé composée vérifie le couple : ce
membre, dans cette tontine. Pour qu'elle soit possible, `member` doit
déclarer ce couple unique (`member_in_tontine`), parce qu'une clé
étrangère ne peut viser que des colonnes uniques.

Les types font une partie du travail : une colonne `DATE` refuse
« mars 2026 », là où une colonne `TEXT` accepte « mars 2026 »,
« 2026-03 » et « 2026-03-01 » comme trois valeurs différentes. Les montants
en FCFA sont des entiers (`BIGINT`), parce que le franc CFA ne se
compte pas en centimes dans la tontine.

## 5. Le store qui traduit

Avec ce schéma, le store n'a plus à vérifier avant d'écrire. Il écrit, et
traduit un refus :

```go
// Pay records that memberID received the pot of the cycle. The schema
// refuses a second payout for the cycle, and a beneficiary from another
// tontine.
func (s *Store) Pay(ctx context.Context, tontineID int64, cycle string, memberID, amountFCFA int64) error {
    month, err := tontine.ParseCycle(cycle)
    if err != nil {
        return err
    }
    _, err = s.db.Exec(ctx,
        `INSERT INTO payout (tontine_id, cycle, member_id, amount_fcfa) VALUES ($1, $2, $3, $4)`,
        tontineID, month, memberID, amountFCFA)
    return translate(err)
}
```

```go
// translate turns a refusal of the database into a rule of the domain. Any
// other check, not-null or foreign key violation is an invalid value.
func translate(err error) error {
    var pgErr *pgconn.PgError
    if !errors.As(err, &pgErr) {
        return err
    }
    if rule, ok := rules[pgErr.ConstraintName]; ok {
        return fmt.Errorf("%w (%s)", rule, pgErr.ConstraintName)
    }
    switch pgErr.Code {
    case "23502", "23503", "23514": // not_null, foreign_key, check
        return fmt.Errorf("%w (%s)", tontine.ErrInvalid, pgErr.ConstraintName)
    }
    return err
}
```

C'est ici que les **noms** des contraintes servent : `payout_once_per_cycle`
devient `ErrAlreadyPaid`, que le handler HTTP pourra transformer en
« ce mois a déjà été versé ». Sans nom, PostgreSQL en choisit un
(`member_tontine_id_fkey`), qui marche, mais change si l'on renomme une
colonne.

Le Go garde deux rôles. Il lit les entrées (`ParseCycle` transforme
« 2026-03 » en date) et il donne des messages compréhensibles. Il peut
aussi vérifier tôt pour répondre mieux, par exemple le format du
téléphone dans un formulaire. Mais ce n'est plus lui qui **garantit** la
règle.

## 6. Tester le schéma lui-même

Les tests du store passent par le Go. Le schéma a donc ses propres
tests, avec du SQL brut, comme l'écrirait un script :

```go
// The schema is tested on its own, with SQL that does not go through the
// store: this is what a migration script or a hurried fix in psql does.
func TestTheSchemaRefusesWhatTheModelForbids(t *testing.T) {
    db := pg.ForTest(t, schema.Strict)
    ctx := context.Background()
    _, err := db.Exec(ctx, `
        INSERT INTO tontine VALUES (1, 'Quartier', 50000), (2, 'Commerçantes', 25000);
        INSERT INTO member VALUES (1, 1, 'Ngo Biyong', '+237690000001', 1),
                                  (8, 2, 'Bilong', '+237690000008', 1);
        INSERT INTO payout (tontine_id, cycle, member_id, amount_fcfa) VALUES (1, '2026-03-01', 1, 50000);
        INSERT INTO contribution (member_id, cycle, amount_fcfa) VALUES (1, '2026-03-01', 50000);`)
    if err != nil {
        t.Fatal(err)
    }
    for _, c := range []struct{ sql, constraint string }{
        {`INSERT INTO tontine VALUES (3, '', 50000)`, "tontine_name_check"},
        {`INSERT INTO tontine VALUES (3, 'Gare', 0)`, "tontine_share_fcfa_check"},
        {`INSERT INTO member VALUES (2, 3, 'Ebai', '+237690000002', 1)`, "member_tontine_id_fkey"},
        {`INSERT INTO member VALUES (2, 1, '', '+237690000002', 1)`, "member_name_check"},
        {`INSERT INTO member VALUES (2, 1, 'Fouda', '', 1)`, "member_phone_format"},
        {`INSERT INTO member VALUES (2, 1, 'Fouda', '+23769000005', 1)`, "member_phone_format"},
        {`INSERT INTO member VALUES (2, 1, 'Essomba', '+237690000007', 0)`, "member_has_a_share"},
        {`INSERT INTO member VALUES (2, 1, 'Ndzi', '+237690000001', 1)`, "member_phone_unique"},
        {`INSERT INTO contribution (member_id, cycle, amount_fcfa) VALUES (42, '2026-03-01', 50000)`, "contribution_member"},
        {`INSERT INTO contribution (member_id, cycle, amount_fcfa) VALUES (1, '2026-04-15', 50000)`, "contribution_cycle_is_a_month"},
        {`INSERT INTO contribution (member_id, cycle, amount_fcfa) VALUES (1, '2026-04-01', -50000)`, "contribution_positive"},
        {`INSERT INTO contribution (member_id, cycle, amount_fcfa) VALUES (1, '2026-03-01', 50000)`, "contribution_once_per_cycle"},
        {`INSERT INTO payout (tontine_id, cycle, member_id, amount_fcfa) VALUES (1, '2026-04-01', 8, 50000)`, "payout_beneficiary_in_tontine"},
        {`INSERT INTO payout (tontine_id, cycle, member_id, amount_fcfa) VALUES (1, '2026-04-15', 1, 50000)`, "payout_cycle_is_a_month"},
        {`INSERT INTO payout (tontine_id, cycle, member_id, amount_fcfa) VALUES (1, '2026-04-01', 1, 0)`, "payout_positive"},
        {`INSERT INTO payout (tontine_id, cycle, member_id, amount_fcfa) VALUES (1, '2026-03-01', 1, 50000)`, "payout_once_per_cycle"},
    } {
        _, err := db.Exec(ctx, c.sql)
        var pgErr *pgconn.PgError
        if !errors.As(err, &pgErr) || pgErr.ConstraintName != c.constraint {
            t.Errorf("%s\n    got %v, want a violation of %s", c.sql, err, c.constraint)
        }
    }
```

Chaque ligne essaie une donnée interdite, et vérifie que c'est la bonne
contrainte qui la refuse. Vérifier seulement « une erreur » serait le
piège de la leçon 4.6 : un test de refus qui accepte n'importe quel
refus.

Le test de concurrence demande une précaution. Sa première version
envoyait vingt versements une seule fois, et elle passait aussi sur la
version qui vérifie avant d'écrire. La raison : au premier tour, le
pool n'a pas encore de connexions ouvertes ; les ouvrir prend du temps,
et cela aligne les requêtes les unes derrière les autres. Le test fait
donc douze tours, un par mois. Sur la version qui vérifie avant
d'écrire, janvier passe, et février échoue :

```text
$ go test -count=1 -run Concurrent ./loose
--- FAIL: TestConcurrentPayoutsPayOnce (0.07s)
    race_test.go:49: 2026-02: won 20, refused 0, rows 20; want 1, 19, 1
FAIL
FAIL    example/schema51/loose  0.078s
FAIL
```

Un test de concurrence qui passe ne prouve pas grand-chose s'il n'a pas
d'abord été vu échouer sur le code fautif.

## 7. Ce que la base ne sait pas dire simplement

Certaines règles portent sur plusieurs lignes ou plusieurs tables :

- une cotisation vaut le nombre de parts du membre multiplié par la part
  de la tontine ;
- au cours d'un tour, chaque membre reçoit la cagnotte une fois et une
  seule ;
- le montant versé est égal à la cagnotte du mois.

La deuxième s'écrit encore comme une unicité, si le tour est une colonne :
`UNIQUE (tontine_id, round, member_id)`. Les deux autres comparent une
ligne à d'autres tables. Un `CHECK` ne peut pas lire une autre table. Il
reste trois solutions : un déclencheur (*trigger*), une vue calculée à la
place d'une colonne stockée, ou la règle dans le Go, **à l'intérieur
d'une transaction** qui empêche les autres d'écrire entre la lecture et
l'écriture. C'est le sujet des leçons 5.2 et 5.3.

La ligne de partage est donc simple : ce qui porte sur une ligne ou sur
l'unicité va dans le schéma ; ce qui compare plusieurs lignes demande une
transaction bien construite, ou une donnée calculée plutôt que stockée.

## 8. La campagne

La campagne modifie le schéma strict et la traduction des erreurs, une
mutation à la fois, et relance les tests du paquet `strict`. Premier
passage :

```text
tontine au nom vide                          tuee
part à 0 FCFA                                tuee
membre d'une tontine inconnue                tuee
téléphone à 8 chiffres                       SURVIT
téléphone absent (NULL)                      SURVIT
nom de membre absent (NULL)                  SURVIT
membre sans part                             tuee
même téléphone deux fois                     tuee
cotisation d'un membre inconnu               tuee
cotisation au 15 du mois                     tuee
cotisation négative                          tuee
deux cotisations le même mois                tuee
bénéficiaire d'une autre tontine             tuee
versement au 15 du mois                      tuee
versement de 0 FCFA                          tuee
versement sans montant (NULL)                tuee
deux bénéficiaires le même mois              tuee
double versement mal traduit                 tuee
membre inconnu mal traduit                   tuee
téléphone en double mal traduit              tuee
CHECK non traduit                            tuee
cagnotte de toutes les tontines              tuee
19/22 tuees
```

Trois mutations survivent, et elles disent deux choses différentes.

**Le téléphone à 8 chiffres** survit parce qu'aucun test n'essaie un
numéro qui commence bien par +237 mais auquel il manque un chiffre. Les
tests essayaient une chaîne vide et un numéro sans indicatif : des cas
faciles. C'est un cas limite manquant.

**Les deux `NULL`** survivent pour une raison plus surprenante. Retirer
`NOT NULL` de `name` ne change rien en apparence, puisque
`CHECK (name <> '')` est toujours là. Mais un `CHECK` laisse passer
`NULL` :

```text
$ psql -c "SELECT NULL <> '' AS name_check, NULL ~ '^\+237[0-9]{9}$' AS phone_check"
 name_check | phone_check 
------------+-------------
            | 
(1 row)
```

`NULL <> ''` ne vaut ni vrai ni faux : il vaut `NULL`, « inconnu ». Et la
documentation de PostgreSQL est explicite : une contrainte `CHECK` est
satisfaite si l'expression vaut vrai **ou `NULL`**. Sans `NOT NULL`, un
membre sans nom ni téléphone entre dans la table.

Les tests ajoutés : un numéro à 8 chiffres, un membre sans nom, un membre
sans téléphone. Campagne rejouée :


## 9. « Les contraintes ralentissent »

C'est l'objection la plus fréquente. Le programme `cmd/cost` enregistre
4 800 cotisations, une par une, comme le fait l'application, trois fois
de suite. `unchecked` écrit dans le schéma sans règle avec un simple
`INSERT`, sans aucune vérification :

```text
$ go run ./cmd/cost   # run 1
unchecked 4800 contributions in 8.823s, 1.838ms each
loose     4800 contributions in 16.317s, 3.399ms each
strict    4800 contributions in 9.691s, 2.019ms each
$ go run ./cmd/cost   # run 2
unchecked 4800 contributions in 11.337s, 2.362ms each
loose     4800 contributions in 14.102s, 2.938ms each
strict    4800 contributions in 10.481s, 2.184ms each
$ go run ./cmd/cost   # run 3
unchecked 4800 contributions in 8.981s, 1.871ms each
loose     4800 contributions in 20.113s, 4.19ms each
strict    4800 contributions in 9.698s, 2.02ms each
```

Les chiffres bougent d'une exécution à l'autre (la deuxième a été
dérangée par la machine), mais aux exécutions 1 et 3 les contraintes
coûtent entre 0,15 et 0,18 ms par écriture, presque rien à côté de la validation de
la transaction sur le disque. La version qui vérifie en Go coûte
**plus cher** que les contraintes : chaque vérification est une requête
de plus, avec son aller-retour. Elle est à la fois plus lente et moins
sûre.

Une contrainte a un vrai coût ailleurs : l'index qui sert à `UNIQUE`
occupe de la place, et l'ajout d'une contrainte à une grande table
existante demande des précautions. La leçon 5.4 les traite.

## 10. La grille

| Situation | Où vit la règle |
|---|---|
| une valeur obligatoire, un format, un intervalle | dans le schéma (`NOT NULL`, `CHECK`, type), et éventuellement aussi dans le Go pour un meilleur message |
| une unicité | dans le schéma, toujours : le Go ne peut pas la garantir |
| une référence à une autre ligne | une clé étrangère, composée si l'appartenance compte |
| une règle entre plusieurs lignes | une transaction (5.2, 5.3), un déclencheur, ou une valeur calculée |
| une règle qui dépend d'un service extérieur | dans le Go, avec ses cas d'erreur (leçon 4.4) |

## 11. Les trois erreurs qui restent

### « L'application valide déjà »

Elle valide ce qui passe par elle, une requête à la fois. La mesure de la
section 2 montre ce qui ne passe pas par elle, et celle de la section 3
montre deux requêtes à la fois. Une base de données sert presque toujours
plus longtemps que l'application qui l'a créée, et à plus de programmes
que prévu : Martin Fowler appelle *integration database* une base qui
sert de stockage à plusieurs applications.

### « On ajoutera les contraintes plus tard »

Plus tard, les données invalides sont déjà là. Ajouter
`UNIQUE (tontine_id, cycle)` à une table qui contient deux versements de
mars échoue : il faut d'abord décider lequel des deux était le bon, et
souvent rembourser l'autre. L'exercice 5 mesure ce que coûte ce
« plus tard ».

### « Une erreur de contrainte, c'est un bug »

C'est l'inverse : une violation de `payout_once_per_cycle` dans les
journaux est une règle qui fait son travail, et qui vient d'empêcher un
double versement. On la traduit, on la compte, et on regarde d'où elle
vient (un double clic ? un client qui réessaie trop vite ?). Ce qui est
un bug, c'est une erreur **non traduite**, qui remonte à l'utilisateur
sous la forme d'un « erreur interne ».

## 12. Le lien avec la production

Pour quelqu'un qui a fait de l'exploitation, cette leçon décrit des
choses vues en astreinte :

- **la correction à la main dans `psql`** pendant un incident : c'est le
  moment où personne ne passe par l'application, et où le schéma est la
  seule protection ;
- **le nouvel essai automatique** d'un client ou d'un répartiteur de
  charge après un délai dépassé : c'est exactement la mesure de la
  section 3 ;
- **le code SQLSTATE dans les journaux** : `23505` (unicité), `23503`
  (clé étrangère), `23514` (`CHECK`), `23502` (`NOT NULL`). Compter ces
  codes par nom de contrainte donne une métrique utile : une hausse
  soudaine de `payout_once_per_cycle` signale un client qui réessaie en
  boucle.

## 13. Ce qu'il faut retenir

1. La base de données est le dernier endroit par où passent toutes les
   écritures : les règles d'une ligne et les unicités y sont écrites.
2. Vérifier puis écrire laisse un intervalle ; l'unicité se garantit par
   une contrainte `UNIQUE`.
3. Chaque contrainte a un nom, que le code traduit en erreur du domaine.
4. `CHECK` laisse passer `NULL` ; une valeur obligatoire demande
   `NOT NULL`.
5. Le schéma se teste avec du SQL brut, et un test de concurrence se voit
   d'abord échouer.

## 14. Approfondissement

### Les formes normales, en une phrase

La normalisation dit qu'un fait est écrit **à un seul endroit**. Le
téléphone d'un membre est dans `member`, pas recopié dans chaque
cotisation. Quand on recopie un fait (pour aller plus vite en lecture),
il faut un mécanisme qui garde les copies justes ; l'exercice 3 mesure ce
qui arrive sans lui.

### Clé naturelle ou clé technique

Le téléphone pourrait servir de clé d'un membre. Mais un membre change de
téléphone (leçon 4.6, exercice 3), et une clé qui change oblige à
modifier toutes les lignes qui la référencent. On garde une clé technique
(`id`) et on déclare l'unicité métier à part (`member_phone_unique`).

## 15. Le réflexe à installer

Avant d'écrire une vérification dans le Go, demande-toi :

1. Est-ce qu'un script, une correction à la main ou une deuxième requête
   au même instant pourraient passer à côté ?
2. Si oui, quelle contrainte du schéma l'exprime ? Si aucune, quelle
   transaction (5.2, 5.3) ?
3. Quel nom lui donnes-tu, et en quelle erreur du domaine le Go le
   traduit-il ?
4. Quel test SQL brut prouve que la base la refuse ?
