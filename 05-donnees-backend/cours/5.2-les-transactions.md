# Leçon 5.2 — Les transactions : tout ou rien, et ce que « rien » veut dire

## L'essentiel en deux minutes

**Le problème, en une phrase.** Clôturer le mois d'une tontine demande
plusieurs écritures : marquer le mois clos, enregistrer le versement,
sortir l'argent de la caisse, le mettre sur le compte du membre. Si le
programme s'arrête entre deux écritures (un redémarrage, un `kill`, une
panne), les comptes restent à moitié écrits.

**Trois images.**

- **Le virement au guichet** : la banque ne débite pas votre compte sans
  créditer l'autre. Les deux mouvements arrivent ensemble, ou aucun.
- **Le brouillon et la page propre** : dans une transaction, on écrit au
  brouillon. `COMMIT` recopie tout sur la page propre d'un seul geste ;
  `ROLLBACK` jette le brouillon.
- **La lettre déjà postée** : le brouillon se jette, la lettre postée ne
  revient pas. Un virement Mobile Money envoyé pendant la transaction
  reste envoyé, même si la transaction est annulée.

**Le code, en quelques lignes.**

```go
// Close closes the cycle: the four statements are committed together, or
// not at all.
func (s *Store) Close(ctx context.Context, tontineID int64, month time.Time) error {
    return pgx.BeginFunc(ctx, s.db, func(tx pgx.Tx) error {
        _, err := closing.Write(ctx, tx, tontineID, month, s.Fault)
        return err
    })
}
```

**Les règles à retenir.**

1. **Les écritures qui forment un seul fait** (« le mois de mars est
   versé ») vont dans **une** transaction : toutes, ou aucune.
2. **Dans la transaction, chaque requête passe par `tx`**, jamais par le
   pool. Une requête sur le pool s'échappe de la transaction.
3. **« Rien » ne vaut que pour la base** : un appel réseau fait pendant
   la transaction n'est pas annulé par `ROLLBACK`.
4. **Ce qui doit partir dehors s'écrit d'abord dans la base** (une table
   *outbox*), dans la même transaction, puis part après le `COMMIT`, avec
   une clé qui permet au destinataire de refuser un doublon.
5. **Une transaction ne ralentit pas** : une écriture en quatre
   `COMMIT` coûte plus cher qu'une transaction de quatre écritures.

La suite mesure tout cela en tuant le programme au hasard, cinquante
fois.

---

La leçon 5.1 a mis dans le schéma les règles qui portent sur une ligne.
Il reste les faits qui demandent plusieurs lignes. Le problème de cette
leçon :

> **Une opération écrit quatre lignes. Que reste-t-il dans la base si le
> programme s'arrête après la deuxième ?**

Le module de la leçon est `l52`, sur le même PostgreSQL 17 que la leçon
5.1. Tout ce qui suit est mesuré sur un module vert sous `gofmt -l`,
`go vet ./...` et `go test -race -count=1 ./...`.

## 1. Clôturer un mois : quatre écritures

Le plan de la tontine est connu d'avance : chaque mois a son bénéficiaire
et sa cagnotte (table `cycle`). Clôturer un mois, c'est écrire quatre
choses :

| Étape | Écriture |
|---|---|
| `closed` | le mois passe à « clos » |
| `payout` | le versement est enregistré |
| `debit` | la cagnotte sort de la caisse (`pot:1`, −600 000) |
| `credit` | elle arrive sur le compte du membre (`member:100`, +600 000) |

Les deux dernières suivent la **partie double** de la comptabilité : un
versement s'écrit en deux lignes dont la somme vaut zéro. L'argent ne
disparaît pas et n'apparaît pas de nulle part.

```sql
-- A payout moves money twice: out of the pot, into the member's wallet.
-- The two entries of a payout add up to zero.
CREATE TABLE entry (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payout_id   BIGINT NOT NULL REFERENCES payout (id),
    account     TEXT   NOT NULL,
    amount_fcfa BIGINT NOT NULL CHECK (amount_fcfa <> 0)
);
```

Les quatre écritures sont codées une seule fois, contre une petite
interface :

```go
// DBTX is what a pool and a transaction both do. Code written against it
// runs the same way inside a transaction or outside.
type DBTX interface {
    Exec(ctx context.Context, sql string, args ...any) (pgconn.CommandTag, error)
    QueryRow(ctx context.Context, sql string, args ...any) pgx.Row
}
```

Un `*pgxpool.Pool` et une `pgx.Tx` ont tous deux ces deux méthodes. Le
même code peut donc tourner hors transaction, ou dedans :

```go
// Write closes the cycle with four statements on q.
func Write(ctx context.Context, q DBTX, tontineID int64, month time.Time, fault Fault) (Payout, error) {
    p, err := MarkClosed(ctx, q, tontineID, month)
    if err == nil {
        err = fault.After("closed")
    }
    if err != nil {
        return Payout{}, err
    }
    return Pay(ctx, q, tontineID, month, p, fault)
}
```

La première version de l'application l'appelle directement sur le pool.
Chaque instruction est alors validée seule (c'est le mode
*autocommit*, celui de toute requête envoyée hors transaction) :

```go
// Close closes the cycle: four statements, each one committed on its own.
func (s *Store) Close(ctx context.Context, tontineID int64, month time.Time) error {
    _, err := closing.Write(ctx, s.db, tontineID, month, s.Fault)
    return err
}
```

Ses tests passent : un mois se clôture, avec ses deux écritures
équilibrées, et une seconde clôture du même mois est refusée.

## 2. Mesure : le programme tué au milieu

Le programme `cmd/crash` lance un processus enfant qui clôture les mois
les uns après les autres. Au bout d'un temps tiré au hasard (entre 0 et
20 ms), il le tue avec `SIGKILL`, comme le ferait le noyau à court de
mémoire ou un `kill -9` pendant un déploiement : aucun `defer` ne
s'exécute. Puis il relance un enfant, cinquante fois. À la fin, il lit
les comptes comme le ferait la trésorière :

```text
$ go run ./cmd/crash -store plain -kills 50
plain 50 kills: closed 68, payouts 54, closed but unpaid 14, payouts without entries 12, money out of the pot but not in the wallet 11
$ go run ./cmd/crash -store txn -kills 50
txn   50 kills: closed 80, payouts 80, closed but unpaid 0, payouts without entries 0, money out of the pot but not in the wallet 0
```

Sans transaction, sur 50 arrêts, **37 mois sont cassés**, de trois
façons différentes :

- **14 mois clos mais jamais versés** : le programme est mort après
  `closed`. Le mois est marqué clos, donc personne ne le reprendra. Le
  membre attend une cagnotte qui ne viendra jamais ;
- **12 versements sans aucune écriture** : la base dit que le membre a
  été payé, mais aucun argent n'a bougé ;
- **11 versements à moitié écrits** : l'argent est sorti de la caisse,
  mais n'est arrivé nulle part. La caisse ne tombe plus juste.

Avec une transaction, **aucun** mois cassé. Un arrêt au milieu laisse le
mois ouvert, comme s'il n'avait jamais été touché, et l'enfant suivant
le clôture.

## 3. La transaction en Go

```go
// Close closes the cycle: the four statements are committed together, or
// not at all.
func (s *Store) Close(ctx context.Context, tontineID int64, month time.Time) error {
    return pgx.BeginFunc(ctx, s.db, func(tx pgx.Tx) error {
        _, err := closing.Write(ctx, tx, tontineID, month, s.Fault)
        return err
    })
}
```

`pgx.BeginFunc` ouvre la transaction, appelle la fonction, puis valide
(`COMMIT`) si elle ne renvoie pas d'erreur, et annule (`ROLLBACK`)
sinon. Écrite à la main, la même chose donne :

```go
// CloseByHand does what Close does, without pgx.BeginFunc.
func (s *Store) CloseByHand(ctx context.Context, tontineID int64, month time.Time) error {
    tx, err := s.db.Begin(ctx)
    if err != nil {
        return err
    }
    // Rollback after a Commit does nothing; on any early return, it undoes
    // everything and gives the connection back to the pool.
    defer tx.Rollback(ctx)
    if _, err := closing.Write(ctx, tx, tontineID, month, s.Fault); err != nil {
        return err
    }
    return tx.Commit(ctx)
}
```

Le `defer tx.Rollback(ctx)` est la ligne à ne jamais oublier. Il annule
la transaction à **chaque** sortie anticipée : une erreur, un `return`
ajouté plus tard, une panique. Après un `Commit` réussi, il ne fait rien.

Et si le processus est tué, comme dans la mesure ? Aucun `defer` ne
tourne. C'est PostgreSQL qui annule : quand la connexion se coupe au
milieu d'une transaction, il jette tout ce qui n'a pas été validé. Rien
n'est visible des autres connexions avant le `COMMIT`.

### Le test qui le prouve

Un test de chaque étape arrête la clôture juste après, avec une erreur,
comme le ferait une panne :

```go
// Atomic stops the closing after each step, as a crash would, and checks
// that nothing is left; then closes the month again.
func Atomic(t *testing.T, newStore New) {
    for _, step := range closing.Steps {
        t.Run("AFailureAfter_"+step+"_LeavesNothing", func(t *testing.T) {
            db := fresh(t)
            ctx := context.Background()
            crash := errors.New("crash after " + step)
            fault := func(s string) error {
                if s == step {
                    return crash
                }
                return nil
            }
            if err := newStore(db, fault).Close(ctx, 1, closing.January); !errors.Is(err, crash) {
                t.Fatalf("close: %v, want the crash", err)
            }
            if got := audit(t, db); got != (closing.Audit{}) {
                t.Errorf("after a crash after %s: %v\nwant nothing", step, got)
            }
            if err := newStore(db, nil).Close(ctx, 1, closing.January); err != nil {
                t.Errorf("closing again: %v", err)
            }
        })
    }
}
```

Le champ `Fault` est la seule trace de ce test dans le code de

## 4. L'instruction qui s'échappe

Un jour, quelqu'un range le code. L'étape `closed` part dans une petite
méthode du store :

```go
// Close looks like txn.Store.Close.
func (s *Store) Close(ctx context.Context, tontineID int64, month time.Time) error {
    return pgx.BeginFunc(ctx, s.db, func(tx pgx.Tx) error {
        p, err := s.markClosed(ctx, tontineID, month)
        if err == nil {
            err = s.Fault.After("closed")
        }
        if err != nil {
            return err
        }
        _, err = closing.Pay(ctx, tx, tontineID, month, p, s.Fault)
        return err
    })
}
```

```go
// markClosed runs on s.db, the pool: another connection, outside the
// transaction. Its UPDATE is committed at once.
func (s *Store) markClosed(ctx context.Context, tontineID int64, month time.Time) (closing.Payout, error) {
    return closing.MarkClosed(ctx, s.db, tontineID, month)
}
```

La différence avec la bonne version tient en un mot : `s.db` au lieu de
`tx`. La méthode passe par le **pool**, qui lui prête une **autre**
connexion. Son `UPDATE` est validé tout de suite, hors de la
transaction. Le compilateur ne dit rien : les deux ont le type `DBTX`.
Les tests ordinaires passent. La mesure, elle, le voit :

```text
$ go run ./cmd/crash -store leaky -kills 50
leaky 50 kills: closed 35, payouts 15, closed but unpaid 20, payouts without entries 0, money out of the pot but not in the wallet 0
```

**20 mois clos et jamais versés** sur 50 arrêts. Le versement et ses
écritures sont bien annulés ensemble, mais le mois, lui, reste clos.

Le même défaut a une deuxième conséquence, plus bruyante. Avec un pool
d'**une seule** connexion, la transaction tient cette connexion, et
`markClosed` attend qu'elle se libère. Elle ne se libérera jamais :

```text
$ go run ./cmd/onepool
txn   pool of 1 connection: <nil> after 4ms
leaky pool of 1 connection: context deadline exceeded after 2.001s
```

En production, avec un pool de 32 connexions, cela n'arrive que sous
charge, quand les 32 sont prises par des transactions qui attendent
chacune une 33ᵉ. Le service se fige d'un coup, et redémarrer le libère.
C'est un incident difficile à expliquer.

Le test d'atomicité de la section 3, lui, l'attrape : sur cette
version, il échoue aux quatre étapes, avec chaque fois
`closed but unpaid 1`. Deux habitudes évitent le défaut :

- dans une fonction de transaction, **les requêtes ne prennent que
  `tx`** ; une méthode d'aide reçoit le `DBTX` en paramètre, elle ne va
  pas le chercher dans le store ;
- les tests tournent parfois avec un **pool d'une connexion** : toute
  requête qui s'échappe d'une transaction s'y bloque aussitôt.

## 5. Qui ouvre la transaction ?

Dans cette leçon, le store ouvre la transaction, parce qu'une clôture
est une seule opération du store. Quand un cas d'usage touche deux
stores (enregistrer le versement **et** la pénalité du mois), c'est le
**cas d'usage** qui décide où la transaction commence et finit. Le
service ne doit pas pour autant importer `pgx` : on lui donne un port,
comme au niveau 3. Un `Transactor`, avec une seule méthode
`InTx(ctx, fn)`, exécute `fn` dans une transaction et lui passe des
stores qui écrivent dans cette transaction.

C'est l'unité de travail (*unit of work*) : le cas d'usage dit « ces
écritures vont ensemble », l'adaptateur PostgreSQL sait comment les
faire tenir ensemble. L'exercice 3 le construit et le teste.

## 6. Ce que « rien » veut dire

Il reste une étape : envoyer réellement la cagnotte sur le téléphone du
membre, par l'opérateur Mobile Money. La version la plus naturelle
l'appelle dans la transaction, juste avant le `COMMIT` : « si l'envoi
échoue, on annule tout ».

```go
// Close closes the cycle and sends the pot, then commits.
func (s *Inside) Close(ctx context.Context, tontineID int64, month time.Time) error {
    return pgx.BeginFunc(ctx, s.DB, func(tx pgx.Tx) error {
        p, err := closing.Write(ctx, tx, tontineID, month, nil)
        if err != nil {
            return err
        }
        return s.Op.Transfer(ctx, fmt.Sprintf("payout-%d", p.ID), p.Phone, p.AmountFCFA)
    })
}
```

Le programme `cmd/transfer` démarre un faux opérateur. Celui-ci envoie
l'argent dès qu'il reçoit l'ordre, puis met 20 ms à répondre, comme un
vrai opérateur. L'enfant est tué au hasard, cinquante fois :

```text
$ go run ./cmd/transfer -mode inside
inside      payouts in the books  59, transfers sent  95, members paid twice 26, orders refused as already done  0
```

**26 membres payés deux fois** (et 95 virements pour 59 versements). Le
programme meurt pendant que l'opérateur répond : l'argent est parti,
mais la transaction n'a pas été validée. PostgreSQL l'annule, le mois
redevient ouvert, l'enfant suivant le clôture à nouveau et renvoie
l'argent.

`ROLLBACK` a tenu sa promesse : **rien** n'a changé dans la base. Mais
« rien » ne vaut que pour la base. Le virement envoyé est une lettre
postée.

Une clé d'idempotence (leçon 4.4) ne sauve pas cette version :

```text
$ go run ./cmd/transfer -mode inside -keys
inside+keys payouts in the books  42, transfers sent  69, members paid twice 18, orders refused as already done  0
```

La clé `payout-<id>` vient d'un identifiant donné par la transaction
annulée. Au nouvel essai, le versement reçoit un **autre** identifiant,
donc une autre clé, et l'opérateur ne peut pas reconnaître le doublon.
Une clé ne protège que si elle vient de quelque chose de **validé**.

## 7. L'outbox : écrire d'abord, envoyer ensuite

La solution renverse l'ordre. La transaction n'envoie rien : elle
**écrit** l'ordre de virement dans une table `outbox`, avec la clôture.
Les deux sont validés ensemble, ou pas du tout :

```go
// Close closes the cycle and queues its transfer, in one transaction.
func (s *Outbox) Close(ctx context.Context, tontineID int64, month time.Time) error {
    return pgx.BeginFunc(ctx, s.DB, func(tx pgx.Tx) error {
        p, err := closing.Write(ctx, tx, tontineID, month, s.Fault)
        if err != nil {
            return err
        }
        _, err = tx.Exec(ctx,
            `INSERT INTO outbox (payout_id, phone, amount_fcfa) VALUES ($1, $2, $3)`,
            p.ID, p.Phone, p.AmountFCFA)
        return err
    })
}
```

Après le `COMMIT`, un envoyeur lit les ordres pas encore envoyés, les
envoie, et les marque envoyés :

```go
// SendOne sends the oldest transfer not sent yet, then marks it sent. A
// crash between the two sends it again, with the same key. It returns
// false when there is nothing to send.
func (s *Outbox) SendOne(ctx context.Context) (bool, error) {
    var id, amount int64
    var phone string
    err := s.DB.QueryRow(ctx, `
        SELECT id, phone, amount_fcfa FROM outbox
        WHERE sent_at IS NULL ORDER BY id LIMIT 1`).Scan(&id, &phone, &amount)
    if errors.Is(err, pgx.ErrNoRows) {
        return false, nil
    }
    if err != nil {
        return false, err
    }
    if err := s.Op.Transfer(ctx, fmt.Sprintf("outbox-%d", id), phone, amount); err != nil {
        return false, err
    }
    if err := s.Fault.After("sent"); err != nil {
        return false, err
    }
    _, err = s.DB.Exec(ctx, `UPDATE outbox SET sent_at = now() WHERE id = $1`, id)
    return err == nil, err
}
```

Ce n'est pas encore suffisant :

```text
$ go run ./cmd/transfer -mode outbox
outbox      payouts in the books  59, transfers sent  85, members paid twice 22, orders refused as already done  0
```

**22 membres payés deux fois.** Le programme meurt entre l'envoi et le
`UPDATE ... sent_at` : l'ordre est encore marqué « à envoyer », et il
repart. Entre la base et l'opérateur, aucun ordre des opérations ne
supprime cet intervalle. On peut seulement choisir de quel côté on se
trompe : perdre un virement, ou l'envoyer deux fois.

L'outbox choisit « deux fois », puis s'appuie sur la clé. Cette fois, la
clé `outbox-<id>` vient d'une ligne **validée** : elle est la même à
chaque nouvel envoi. Un opérateur qui honore les clés refuse les
doublons :

```text
$ go run ./cmd/transfer -mode outbox -keys
outbox+keys payouts in the books  42, transfers sent  42, members paid twice  0, orders refused as already done 25
```

**42 versements, 42 virements, aucun membre payé deux fois**, et 25
ordres refusés par l'opérateur parce qu'ils étaient déjà faits. C'est la
règle des deux moitiés :

- l'**outbox** garantit qu'un ordre validé finira par partir, **au moins
  une fois** ;
- la **clé** garantit que l'opérateur ne l'exécute **qu'une fois**.

Le test de la deuxième moitié :

```go
func TestACrashAfterSendingSendsAgainWithTheSameKey(t *testing.T) {
    db := fresh(t)
    ctx := context.Background()
    op := &transfer.Fake{HonourKeys: true}
    crashed := false
    s := &transfer.Outbox{DB: db, Op: op, Fault: func(step string) error {
        if step == "sent" && !crashed {
            crashed = true
            return errors.New("crash before marking it sent")
        }
        return nil
    }}
    if err := s.Close(ctx, 1, closing.January); err != nil {
        t.Fatal(err)
    }
    if _, err := s.SendOne(ctx); err == nil {
        t.Fatal("no crash")
    }
    if more, err := s.SendOne(ctx); !more || err != nil {
        t.Fatalf("second send: %v, %v", more, err)
    }
    if sent, twice, refused := op.Stats(); sent != 1 || twice != 0 || refused != 1 {
        t.Errorf("sent %d, paid twice %d, refused %d; want 1, 0, 1", sent, twice, refused)
    }
    if n := count(t, db, `SELECT count(*) FROM outbox WHERE sent_at IS NULL`); n != 0 {
        t.Errorf("still pending: %d", n)
    }
}
```

Si l'opérateur n'accepte pas de clé, il reste à le prévoir dans le
processus : rapprocher chaque jour les virements de l'opérateur avec
l'outbox, et traiter les écarts à la main. C'est le sujet de
l'exercice 5.

Un seul envoyeur tourne ici. Avec deux envoyeurs, chacun lirait la même
ligne : c'est un problème de concurrence, traité en 5.3
(`FOR UPDATE SKIP LOCKED`).

## 8. La campagne

La campagne modifie les stores, les écritures, l'outbox et l'audit, une
mutation à la fois, et relance tous les tests du module. Premier
passage :

```text
écritures sur le pool (BeginFunc)            tuee
écritures sur le pool (à la main)            tuee
COMMIT oublié                                tuee
erreur ignorée avant COMMIT                  tuee
mois clôturé deux fois                       tuee
débit de signe faux                          tuee
panne après clôture jamais simulée           tuee
échec de l'opérateur ignoré                  tuee
clé différente à chaque envoi                tuee
virements déjà envoyés relus                 tuee
virement jamais marqué envoyé                tuee
audit : demi-écriture non comptée            SURVIT
audit : mois impayés mal comptés             tuee
audit : versement sans écriture non compté   SURVIT
12/14 tuees
```

Les trois survivantes de l'**audit** disent la même chose : l'outil qui
compte les comptes cassés n'avait jamais vu de comptes cassés. Les tests
d'atomicité vérifient que l'audit ne trouve **rien**, et un audit qui ne
compte rien du tout passe ce test. C'est le piège du test de refus de la
leçon 4.6, sous une autre forme : un instrument de mesure se teste sur un
cas où il doit trouver quelque chose.

Le test ajouté casse les comptes à la main, une façon par tontine, et
vérifie que l'audit compte chacune :

```go
func TestTheAuditFindsEachKindOfBrokenBooks(t *testing.T) {
    db := pg.ForTest(t, schema.DDL)
    ctx := context.Background()
    if err := closing.Seed(ctx, db, 4, 1); err != nil {
        t.Fatal(err)
    }
    _, err := db.Exec(ctx, `
        UPDATE cycle SET closed = true;
        -- tontine 1: closed, never paid
        -- tontine 2: paid, no entry
        INSERT INTO payout (id, tontine_id, cycle, member_id, amount_fcfa)
            OVERRIDING SYSTEM VALUE VALUES (2, 2, '2026-01-01', 200, 600000);
        -- tontine 3: out of the pot, never in the wallet
        INSERT INTO payout (id, tontine_id, cycle, member_id, amount_fcfa)
            OVERRIDING SYSTEM VALUE VALUES (3, 3, '2026-01-01', 300, 600000);
        INSERT INTO entry (payout_id, account, amount_fcfa) VALUES (3, 'pot:3', -600000);
        -- tontine 4: as it should be
        INSERT INTO payout (id, tontine_id, cycle, member_id, amount_fcfa)
            OVERRIDING SYSTEM VALUE VALUES (4, 4, '2026-01-01', 400, 600000);
        INSERT INTO entry (payout_id, account, amount_fcfa)
            VALUES (4, 'pot:4', -600000), (4, 'member:400', 600000);`)
    if err != nil {
        t.Fatal(err)
    }
    got, err := closing.Check(ctx, db)
    if err != nil {
        t.Fatal(err)
    }
    want := closing.Audit{Closed: 4, Unpaid: 1, NoEntry: 1, HalfEntry: 1, Payouts: 3, Unbalanced: 1}
    if got != want {
        t.Errorf("audit: %+v\nwant   %+v", got, want)
    }
    if got.Broken() != 3 {
        t.Errorf("broken: %d, want 3", got.Broken())
    }
}
```

## 9. « Les transactions ralentissent »

Le programme `cmd/cost` clôture 2 000 mois l'un après l'autre, sans
transaction (quatre `COMMIT` par mois), puis avec (un seul) :

```text
$ go run ./cmd/cost   # run 1
plain 2000 closings in 15.846s, 7.923ms each
txn   2000 closings in 4.751s, 2.376ms each
$ go run ./cmd/cost   # run 2
plain 2000 closings in 13.558s, 6.779ms each
txn   2000 closings in 12.463s, 6.231ms each
$ go run ./cmd/cost   # run 3
plain 2000 closings in 18.001s, 9ms each
txn   2000 closings in 11.574s, 5.787ms each
```

Les chiffres bougent beaucoup d'une exécution à l'autre, parce que le
disque de la machine est partagé. Mais le sens ne change jamais : **la
transaction est plus rapide**, de 8 % à 70 % selon l'exécution. Elle fait pourtant
deux allers-retours de plus (`BEGIN` et `COMMIT`).

La raison est le disque. À chaque `COMMIT`, PostgreSQL attend que son
journal (le WAL) soit écrit sur un support permanent avant de répondre.
Sans transaction, chaque instruction est son propre `COMMIT` : quatre
attentes du disque par mois. Avec une transaction, une seule.

Le vrai coût d'une transaction est ailleurs : pendant qu'elle est
ouverte, elle **tient une connexion** et **les verrous** des lignes
qu'elle a modifiées. Une transaction courte ne coûte presque rien ; une
transaction qui attend un appel réseau de 20 ms bloque une connexion
pendant 20 ms, et les autres requêtes qui veulent les mêmes lignes
attendent aussi. C'est une deuxième raison de ne rien appeler au dehors
pendant une transaction. La leçon 5.3 mesure les verrous.

## 10. La grille

| Situation | Que faire |
|---|---|
| plusieurs écritures forment un seul fait | une transaction, ouverte par le store, ou par le cas d'usage s'il touche plusieurs stores |
| une fonction d'aide écrit pendant une transaction | elle reçoit le `DBTX` en paramètre ; jamais `s.db` |
| un effet hors de la base (virement, SMS, message) | une ligne dans l'outbox, dans la transaction ; l'envoi après le `COMMIT` |
| l'envoi peut être répété | une clé d'idempotence tirée d'une ligne validée |
| le destinataire ne connaît pas les clés | un rapprochement quotidien, et une procédure pour les écarts |
| une lecture seule | pas besoin de transaction, sauf pour lire plusieurs tables au même instant (5.3) |

## 11. Les trois erreurs qui restent

### « La transaction annule tout »

Elle annule tout **dans la base**. La section 6 a envoyé 95 virements
pour 59 versements avec une transaction parfaitement correcte. Tout ce
qui sort de la base (HTTP, SMS, fichier, message) n'est pas annulé.

### « Le `defer tx.Rollback` est inutile, puisque je fais `Commit` »

Il sert sur les chemins qu'on n'a pas écrits : l'erreur ajoutée l'année
prochaine, la panique dans une bibliothèque. Sans lui, la transaction
reste ouverte, avec sa connexion et ses verrous, jusqu'à ce que la
connexion soit fermée. `pgx.BeginFunc` le fait pour vous.

### « Tant que j'utilise `BeginFunc`, je suis protégé »

`BeginFunc` protège ce qui passe par `tx`. La version de la section 4
utilise `BeginFunc`, et casse 20 mois sur 50 arrêts. La transaction est
une propriété de la **connexion**, pas de la fonction Go.

## 12. Le lien avec la production

- **Le `kill -9` et le redémarrage du pod** sont exactement la mesure de
  la section 2. Kubernetes envoie `SIGTERM`, attend le délai de grâce,
  puis `SIGKILL` : un code qui n'est correct qu'en cas d'arrêt propre
  n'est pas correct.
- **`idle in transaction`** dans `pg_stat_activity` : une connexion qui
  a ouvert une transaction et ne fait rien. C'est souvent un appel réseau
  dans la transaction, ou un `Rollback` oublié. Le paramètre
  `idle_in_transaction_session_timeout` les coupe.
- **Le pool figé** de la section 4 ressemble, vu de l'extérieur, à une
  base lente. Le signe qui le distingue : la base ne fait rien, et le
  pool n'a plus de connexion libre.
- **Le rapprochement** avec l'opérateur est une tâche d'exploitation à
  part entière. Il faut l'outiller, avec une requête, une alerte sur les
  écarts et une procédure de remboursement.

## 13. Ce qu'il faut retenir

1. Les écritures d'un même fait vont dans une transaction : toutes, ou
   aucune, même si le processus est tué.
2. Dans la transaction, tout passe par `tx` ; une requête sur le pool
   s'échappe, et peut même bloquer le pool.
3. `ROLLBACK` n'annule que la base. Un effet extérieur s'écrit dans une
   outbox, et part après le `COMMIT`.
4. L'outbox envoie au moins une fois ; la clé, tirée d'une ligne validée,
   fait exécuter une seule fois.
5. Une transaction courte est plus rapide que des écritures validées une
   par une ; une transaction longue tient une connexion et des verrous.

## 14. Approfondissement

### Les points de sauvegarde

`SAVEPOINT` permet d'annuler une partie de la transaction sans la
perdre entière. Dans pgx, appeler `Begin` sur une `pgx.Tx` crée un point
de sauvegarde. C'est utile pour « essayer, et sinon faire autre chose »
dans une même transaction ; c'est rarement utile dans un service
ordinaire.

### Valider sans attendre le disque

`synchronous_commit = off` fait répondre au `COMMIT` sans attendre le
disque. Une panne du serveur peut alors perdre les dernières
transactions validées, mais **jamais** en casser une à moitié : la base
reste cohérente. C'est un choix possible pour des journaux d'activité ;
pas pour des versements.

### Les transactions distribuées

Le protocole de validation à deux phases (`PREPARE TRANSACTION`) peut
lier deux bases. Il ne lie pas une base et un opérateur Mobile Money, qui
ne le parle pas. Dans la pratique, entre services, on utilise l'outbox et
les clés d'idempotence.

## 15. Le réflexe à installer

Devant une opération qui écrit plus d'une ligne, demande-toi :

1. Si le processus meurt entre deux écritures, que voit la trésorière ?
2. Où commence et où finit la transaction ? Qui la décide, le store ou le
   cas d'usage ?
3. Est-ce que **chaque** requête de la fonction passe par `tx` ?
4. Qu'est-ce qui sort de la base pendant l'opération ? Passe-t-il par une
   outbox, avec une clé qui vient d'une ligne validée ?
5. Quel test arrête l'opération après chaque étape, et vérifie qu'il ne
   reste rien ?
