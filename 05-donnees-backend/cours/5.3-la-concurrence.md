# Leçon 5.3 — La concurrence : mises à jour perdues, isolation, verrous

## L'essentiel en deux minutes

**Le problème, en une phrase.** Une transaction garantit « tout ou
rien » (leçon 5.2), mais elle ne garantit pas, à elle seule, que deux
transactions qui tournent **en même temps** ne s'écrasent pas : lire un
solde, ajouter en Go, puis réécrire perd des dépôts, même dans une
transaction.

**Trois images.**

- **Le cahier passé de main en main** : deux trésorières recopient le
  même solde, ajoutent chacune leur dépôt, et réécrivent. La seconde
  efface la première.
- **La clé du coffre** : `SELECT ... FOR UPDATE` prend la clé. Les
  autres attendent qu'elle soit rendue, au `COMMIT`.
- **Le guichet qui refuse et fait recommencer** : en `SERIALIZABLE`, la
  base refuse une transaction qui aurait pu donner un résultat
  impossible en file indienne, et l'on recommence.

**Le code, en quelques lignes.** La base fait le calcul, en une seule
instruction :

```go
// Atomic lets the database add: one statement, no read in Go.
func Atomic(ctx context.Context, db *pgxpool.Pool, account, amountFCFA int64) (int, error) {
    _, err := db.Exec(ctx,
        `UPDATE account SET balance_fcfa = balance_fcfa + $2 WHERE id = $1`, account, amountFCFA)
    return 1, err
}
```

**Les règles à retenir.**

1. **Lire, calculer en Go, réécrire perd des mises à jour**, même dans
   une transaction, au niveau par défaut de PostgreSQL (`READ
   COMMITTED`).
2. **Le plus simple d'abord** : une instruction qui calcule dans la base
   (`balance = balance + $2`). Sinon, verrouiller ce qu'on lit
   (`FOR UPDATE`).
3. **Une règle sur plusieurs lignes** (« au plus 3 prêts ouverts ») ne se
   protège ni par `READ COMMITTED` ni par `REPEATABLE READ` : il faut
   verrouiller une ligne parente, ou `SERIALIZABLE` avec de nouveaux
   essais.
4. **Les verrous se prennent toujours dans le même ordre** ; sinon, deux
   transactions s'attendent l'une l'autre, et PostgreSQL en tue une au
   bout d'une seconde.
5. **Une transaction refusée pour conflit se rejoue entière**, et elle ne
   doit rien faire hors de la base (leçon 5.2).

La suite mesure tout cela avec 50 requêtes en même temps.

---

La leçon 5.2 a rendu les écritures atomiques. Il reste à savoir ce qui
se passe quand **plusieurs** transactions touchent les mêmes lignes au
même moment. Le problème de cette leçon :

> **Cinquante membres déposent en même temps sur la caisse de la
> tontine. Combien de dépôts arrivent vraiment ?**

Le module de la leçon est `l53`, sur le même PostgreSQL 17. Tout ce qui
suit est mesuré sur un module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. Le dépôt naturel

La caisse d'une tontine est une ligne de `account`, avec son solde. Le
dépôt le plus naturel lit le solde, ajoute le montant en Go, et écrit le
nouveau solde :

```go
func readWrite(ctx context.Context, q DBTX, account, amountFCFA int64) error {
    var balance int64
    err := q.QueryRow(ctx, `SELECT balance_fcfa FROM account WHERE id = $1`, account).Scan(&balance)
    if err != nil {
        return err
    }
    _, err = q.Exec(ctx, `UPDATE account SET balance_fcfa = $2 WHERE id = $1`, account, balance+amountFCFA)
    return err
}
```

Une version plus prudente le met dans une transaction :

```go
// ReadWriteTx does the same in a transaction, at the default isolation
// level of PostgreSQL, READ COMMITTED.
func ReadWriteTx(ctx context.Context, db *pgxpool.Pool, account, amountFCFA int64) (int, error) {
    return 1, pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        return readWrite(ctx, tx, account, amountFCFA)
    })
}
```

Le test d'un dépôt passe pour les deux : 5 000 + 1 500 donnent bien
6 500.

## 2. Mesure : cinquante dépôts à la fois

Le programme `cmd/deposits` envoie 1 000 dépôts de 1 000 FCFA, par 50
travailleurs en parallèle. Avec `-accounts 1`, tous vont sur la **même**
caisse ; avec `-accounts 50`, chaque travailleur a la sienne :

```text

```

Quand tous déposent sur la même caisse, la lecture-écriture **perd 975
dépôts sur 1 000**. Dans une transaction, elle en perd 980. Aucune
erreur n'est renvoyée : chaque dépôt a répondu « fait ».

Quand chacun a son compte, rien n'est perdu, quelle que soit la
méthode. C'est pour cela que le défaut passe les tests et la recette :
il ne se montre que lorsque plusieurs requêtes touchent **la même
ligne**. Dans une tontine, cela arrive le jour de la cotisation, quand
tout le monde paie la même caisse le même soir.

Ce qui se passe :

| Instant | Dépôt A | Dépôt B |
|---|---|---|
| 1 | lit 10 000 | |
| 2 | | lit 10 000 |
| 3 | écrit 11 000 | |
| 4 | | écrit 11 000 |

Le dépôt de A a disparu. C'est une **mise à jour perdue** (*lost
update*).

### Pourquoi la transaction ne suffit pas

Au niveau par défaut de PostgreSQL, `READ COMMITTED`, chaque instruction
voit les données validées **au moment où elle commence**. Le `SELECT`
de B, à l'instant 2, voit 10 000, puisque A n'a pas encore validé.
La transaction garantit que les deux écritures de A partent ensemble ;
elle ne dit rien de ce que B lit pendant ce temps.

## 3. Quatre façons de ne rien perdre

**Laisser la base calculer.** Une seule instruction lit et écrit la
ligne. PostgreSQL verrouille la ligne pendant l'`UPDATE`, et le second
`UPDATE` attend, puis repart de la valeur validée par le premier :

```go
// Atomic lets the database add: one statement, no read in Go.
func Atomic(ctx context.Context, db *pgxpool.Pool, account, amountFCFA int64) (int, error) {
    _, err := db.Exec(ctx,
        `UPDATE account SET balance_fcfa = balance_fcfa + $2 WHERE id = $1`, account, amountFCFA)
    return 1, err
}
```

C'est la plus rapide des méthodes correctes (1,38 s pour 1 000 dépôts
sur la même caisse). Elle suffit chaque fois que le calcul tient en SQL.

**Verrouiller ce qu'on lit.** Quand le calcul doit se faire en Go (une
règle compliquée, un appel à une autre table), on lit avec
`FOR UPDATE`. La ligne est verrouillée jusqu'à la fin de la
transaction ; un autre `FOR UPDATE` sur la même ligne attend :

```go
// ForUpdate locks the row when reading it: another ForUpdate on the same
// account waits until this transaction ends.
func ForUpdate(ctx context.Context, db *pgxpool.Pool, account, amountFCFA int64) (int, error) {
    return 1, pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        var balance int64
        err := tx.QueryRow(ctx,
            `SELECT balance_fcfa FROM account WHERE id = $1 FOR UPDATE`, account).Scan(&balance)
        if err != nil {
            return err
        }
        _, err = tx.Exec(ctx, `UPDATE account SET balance_fcfa = $2 WHERE id = $1`, account, balance+amountFCFA)
        return err
    })
}
```

**Demander à la base de refuser les conflits.** En `REPEATABLE READ`,
toute la transaction voit une photo prise à son début. Si une autre
transaction a modifié la ligne depuis, l'`UPDATE` est refusé
(`40001`, « could not serialize access due to concurrent update »), et
la transaction se rejoue :

```go
// Tx runs fn in a transaction with opts, again and again while it fails
// with a retryable error. fn must have no effect outside the transaction:
// it may run several times.
func Tx(ctx context.Context, db *pgxpool.Pool, opts pgx.TxOptions, fn func(pgx.Tx) error) (tries int, err error) {
    for tries = 1; ; tries++ {
        err = pgx.BeginTxFunc(ctx, db, opts, fn)
        if !Retryable(err) || tries == MaxTries {
            return tries, err
        }
    }
}
```

```go
// Repeatable reads and writes like ReadWrite, at REPEATABLE READ: PostgreSQL
// refuses to write a row changed since the transaction began, and the
// transaction runs again.
func Repeatable(ctx context.Context, db *pgxpool.Pool, account, amountFCFA int64) (int, error) {
    return retry.Tx(ctx, db, pgx.TxOptions{IsoLevel: pgx.RepeatableRead}, func(tx pgx.Tx) error {
        return readWrite(ctx, tx, account, amountFCFA)
    })
}
```

**Un numéro de version.** C'est le verrou optimiste, sans transaction :
on relit si la version a changé.

```go
// Versioned reads the balance and its version, and writes only if the
// version has not changed; otherwise it reads again.
func Versioned(ctx context.Context, db *pgxpool.Pool, account, amountFCFA int64) (int, error) {
    for tries := 1; tries <= retry.MaxTries; tries++ {
        var balance, version int64
        err := db.QueryRow(ctx,
            `SELECT balance_fcfa, version FROM account WHERE id = $1`, account).Scan(&balance, &version)
        if err != nil {
            return tries, err
        }
        tag, err := db.Exec(ctx, `
            UPDATE account SET balance_fcfa = $2, version = version + 1
            WHERE id = $1 AND version = $3`, account, balance+amountFCFA, version)
        if err != nil {
            return tries, err
        }
        if tag.RowsAffected() == 1 {
            return tries, nil
        }
    }
    return retry.MaxTries, ErrBusy
}
```

### Ce que la mesure dit de ces quatre méthodes

Sur 50 comptes, les quatre sont aussi rapides que la version fautive.
Sur une seule caisse, les différences sont fortes :

| Méthode | Dépôts perdus | Essais | Durée |
|---|---|---|---|
| `UPDATE ... + $2` | 0 | 1 000 | 1,4 s |
| `FOR UPDATE` | 0 | 1 000 | 2,2 s |
| `REPEATABLE READ` + nouvel essai | 0 perdu, **24 refusés** | 23 479 | 5,1 s |
| version + nouvel essai | 0 | 9 925 | 12,4 s |

Les deux méthodes **optimistes** (qui espèrent qu'il n'y aura pas de
conflit, et recommencent sinon) s'effondrent quand tout le monde écrit
la même ligne : 23 essais par dépôt en moyenne. Au-delà de 100 essais,
`retry.Tx` abandonne et renvoie l'erreur. Ces 24 dépôts ne sont pas
**perdus en silence** comme ceux de la section 2 : le client reçoit une
erreur, et peut réessayer plus tard. Mais l'expérience est mauvaise.

La règle qui en sort : **les méthodes optimistes conviennent quand les
conflits sont rares** (un membre modifie son propre profil). Quand
beaucoup écrivent la même ligne (la caisse), on calcule dans la base ou
on verrouille.

## 4. La règle sur plusieurs lignes

La tontine prête à ses membres, mais **au plus trois prêts ouverts à la
fois**. La règle porte sur plusieurs lignes : c'est le cas que la leçon
5.1 avait renvoyé ici. Le code compte, puis insère :

```go
// grant counts the open loans and inserts one if the limit allows it. With
// lockTontine, it locks the row of the tontine first.
func grant(ctx context.Context, tx pgx.Tx, tontineID, memberID, amountFCFA int64, lockTontine bool) error {
    read := `SELECT max_open_loans FROM tontine WHERE id = $1`
    if lockTontine {
        read += ` FOR UPDATE`
    }
    var limit, open int
    if err := tx.QueryRow(ctx, read, tontineID).Scan(&limit); err != nil {
        return err
    }
    err := tx.QueryRow(ctx,
        `SELECT count(*) FROM loan WHERE tontine_id = $1 AND open`, tontineID).Scan(&open)
    if err != nil {
        return err
    }
    if open >= limit {
        return ErrLimit
    }
    _, err = tx.Exec(ctx,
        `INSERT INTO loan (tontine_id, member_id, amount_fcfa) VALUES ($1, $2, $3)`,
        tontineID, memberID, amountFCFA)
    return err
}
```

Le programme `cmd/loans` fait demander un prêt par 20 membres en même
temps, dans 50 tontines :

```text
$ go run ./cmd/loans
read committed        loans 987 (want 150), tontines over the limit 50/50, worst 20, refused  13, failed 0, attempts 1000, 334ms
repeatable read       loans 1000 (want 150), tontines over the limit 50/50, worst 20, refused   0, failed 0, attempts 1000, 347ms
serializable + retry  loans 150 (want 150), tontines over the limit  0/50, worst  3, refused 850, failed 0, attempts 3537, 930ms
lock the tontine      loans 150 (want 150), tontines over the limit  0/50, worst  3, refused 850, failed 0, attempts 1000, 1.336s
```

En `READ COMMITTED`, **les 50 tontines dépassent la limite**, jusqu'à 20
prêts ouverts au lieu de 3. En `REPEATABLE READ`, c'est pire : les 1 000
demandes sont accordées. La photo du début de transaction ne montre
jamais les prêts des autres, et aucune ligne n'est modifiée deux fois :
chaque transaction **insère** une ligne nouvelle. `REPEATABLE READ` ne
voit pas de conflit, parce qu'il n'y en a pas sur une ligne. Le conflit
porte sur une **règle**, entre des lignes différentes. On l'appelle
*write skew*.

Deux méthodes tiennent la règle :

- **Verrouiller la ligne parente.** Toutes les demandes d'une tontine
  commencent par `SELECT ... FROM tontine WHERE id = $1 FOR UPDATE` :
  elles passent une par une. On ne peut pas verrouiller les prêts
  eux-mêmes, puisque celui qu'on va créer n'existe pas encore ;
- **`SERIALIZABLE`.** PostgreSQL surveille ce que chaque transaction a
  lu, et refuse celle dont le résultat serait impossible si les
  transactions avaient tourné l'une après l'autre. Il faut rejouer :
  3 537 essais pour 1 000 demandes.

Les deux accordent exactement 150 prêts. `SERIALIZABLE` protège
**toutes** les règles sans y penser, au prix de nouveaux essais.
Verrouiller le parent ne protège que les règles auxquelles on a pensé,
sans nouvel essai. Le code de la leçon les écrit avec la même fonction :

```go
func at(level pgx.TxIsoLevel, lock bool) Func {
    return func(ctx context.Context, db *pgxpool.Pool, tontineID, memberID, amountFCFA int64) (int, error) {
        return retry.Tx(ctx, db, pgx.TxOptions{IsoLevel: level}, func(tx pgx.Tx) error {
            return grant(ctx, tx, tontineID, memberID, amountFCFA, lock)
        })
    }
}
```

## 5. Mesure : l'interblocage

Un membre envoie de l'argent à un autre, pendant que l'autre lui en
envoie. Chaque transfert débite, puis crédite :

```go
// InCallOrder debits, then credits: the rows are locked in the order of
// the call.
func InCallOrder(ctx context.Context, db *pgxpool.Pool, from, to, amountFCFA int64) error {
    return pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        return debitCredit(ctx, tx, from, to, amountFCFA)
    })
}
```

Le premier transfert verrouille le compte 1, le second le compte 2.
Chacun attend ensuite le compte que l'autre tient. Aucun ne peut
avancer : c'est un **interblocage** (*deadlock*). PostgreSQL le
détecte au bout de `deadlock_timeout` (une seconde par défaut), et
annule l'une des deux transactions avec l'erreur `40P01`. Le programme
`cmd/deadlock` lance 20 paires de transferts croisés, cinq fois :

```text
$ go run ./cmd/deadlock
in the order of the call  moves 200, deadlocks 66, other errors 0, slowest move 1.056s, total 5.129s, money in the accounts 40000000 FCFA
in the order of the ids   moves 200, deadlocks  0, other errors 0, slowest move 73ms, total 118ms, money in the accounts 40000000 FCFA
```

**66 transferts sur 200 annulés**, et chaque interblocage coûte plus
d'une seconde à la transaction qui attend. L'argent est intact (le
total ne change pas) : l'interblocage est un problème de
**disponibilité**, pas de cohérence.

La correction verrouille les deux comptes **dans l'ordre de leurs
identifiants**, avant de les modifier :

```go
// InIDOrder locks both rows in the order of their ids, then debits and
// credits: two moves always lock in the same order.
func InIDOrder(ctx context.Context, db *pgxpool.Pool, from, to, amountFCFA int64) error {
    return pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        _, err := tx.Exec(ctx,
            `SELECT id FROM account WHERE id IN ($1, $2) ORDER BY id FOR UPDATE`, from, to)
        if err != nil {
            return err
        }
        return debitCredit(ctx, tx, from, to, amountFCFA)
    })
}
```

Plus aucun interblocage, et 118 ms au lieu de 5,1 s. Deux transactions
qui prennent leurs verrous dans le même ordre ne peuvent pas s'attendre
en cercle.

## 6. Les tests

Chaque méthode correcte a un test de concurrence : dix travailleurs,
dix dépôts chacun, sur le même compte, trois tours :

```go
// Ten workers deposit ten times each on the same account, three rounds:
// the first round runs on a cold pool, which lines requests up.
func noDepositIsLost(t *testing.T, f deposit.Func) {
    db := pg.ForTestConns(t, schema.DDL, 10)
    ctx := context.Background()
    for round := int64(1); round <= 3; round++ {
        if _, err := db.Exec(ctx, `INSERT INTO account (id) VALUES ($1)`, round); err != nil {
            t.Fatal(err)
        }
        var wg sync.WaitGroup
        for range 10 {
            wg.Go(func() {
                for range 10 {
                    if _, err := f(ctx, db, round, 1000); err != nil {
                        t.Error(err)
                    }
                }
            })
        }
        wg.Wait()
        var balance int64
        if err := db.QueryRow(ctx, `SELECT balance_fcfa FROM account WHERE id = $1`, round).Scan(&balance); err != nil {
            t.Fatal(err)
        }
        if balance != 100000 {
            t.Errorf("round %d: balance %d FCFA, want 100000: %d deposits lost", round, balance, (100000-balance)/1000)
        }
    }
}
```

## 7. La campagne

```text
dépôt sur plusieurs comptes                  tuee
lecture sans FOR UPDATE                      tuee
dépôt en READ COMMITTED                      tuee
version jamais incrémentée                   tuee
conflit de version ignoré                    tuee
interblocage non réessayé                    tuee
aucun nouvel essai                           tuee
prêt en REPEATABLE READ                      tuee
tontine non verrouillée                      tuee
un prêt de trop                              tuee
verrous dans l'ordre décroissant             SURVIT
aucun verrou préalable                       tuee
crédit sur le mauvais compte                 tuee
12/13 tuees
```

Une mutation survit, et c'est **normal**. Verrouiller les deux comptes
par ordre **décroissant** d'identifiant protège aussi bien : ce qui
compte, c'est que toutes les transactions suivent **le même** ordre, pas
lequel. Cette mutation ne change pas le comportement du programme ;
on l'appelle un mutant **équivalent**. Aucun test ne peut la tuer, et il
ne faut pas en écrire un qui le ferait : ce test figerait un détail sans
importance.

Une campagne ne vise donc pas 100 % à tout prix. Chaque survivante est
expliquée : un test manquant, ou un mutant équivalent.

## 8. Les niveaux d'isolation, en une table

| Niveau | Ce que voit une instruction | Mise à jour perdue (lire puis réécrire) | Règle sur plusieurs lignes |
|---|---|---|---|
| `READ COMMITTED` (défaut) | ce qui est validé au début de l'instruction | **perdue** | **violée** |
| `REPEATABLE READ` | une photo prise au début de la transaction | refusée (`40001`), à rejouer | **violée** |
| `SERIALIZABLE` | la même photo, et PostgreSQL vérifie l'ordre | refusée (`40001`), à rejouer | refusée (`40001`), à rejouer |

Monter le niveau d'isolation n'est pas gratuit : il faut un code qui
rejoue, et un code qui **peut** être rejoué (aucun effet hors de la
base, leçon 5.2).

## 9. La grille

| Situation | Que faire |
|---|---|
| un compteur, un solde, un stock | `UPDATE ... SET x = x + $1`, et un `CHECK (x >= 0)` pour la limite |
| un calcul en Go sur une ligne lue | `SELECT ... FOR UPDATE` dans la transaction |
| une ligne rarement disputée, éditée par une personne | un numéro de version (verrou optimiste) |
| une règle qui compte ou somme plusieurs lignes | verrouiller la ligne parente, ou `SERIALIZABLE` avec nouvel essai |
| deux lignes ou plus à verrouiller | toujours dans le même ordre (par identifiant) |
| des travailleurs qui se partagent une file | `FOR UPDATE SKIP LOCKED` (exercice 2) |

## 10. Les trois erreurs qui restent

### « C'est dans une transaction, donc c'est protégé »

La section 2 perd 980 dépôts sur 1 000 **dans une transaction**. La
transaction donne l'atomicité ; l'isolation dépend du niveau, et le
niveau par défaut laisse passer les mises à jour perdues.

### « Passons tout en `SERIALIZABLE` »

C'est défendable, à condition que **chaque** transaction soit écrite
pour être rejouée, et que l'on mesure le nombre d'essais. Sur une ligne
très disputée, la section 3 montre 23 essais par dépôt. Et un nouvel
essai qui renvoie un SMS ou rappelle l'opérateur refait la section 6 de
la leçon 5.2.

### « Les interblocages, c'est la base qui gère »

Elle les détecte, et en annule un. Sans nouvel essai, c'est une erreur
pour l'utilisateur ; avec, c'est une seconde d'attente à chaque fois. On
les **évite** par l'ordre des verrous, et on rejoue en dernier recours.

## 11. Le lien avec la production

- **`deadlock detected`** dans les journaux de PostgreSQL : le message
  donne les deux requêtes et les lignes en cause. Un interblocage
  régulier est presque toujours un ordre de verrouillage différent entre
  deux chemins du code.
- **`pg_locks`** joint à **`pg_stat_activity`** montre qui attend qui.
  Une longue file d'attente sur une même ligne (la caisse) est le signe
  d'une ligne trop disputée. Il faut alors raccourcir les transactions
  qui la tiennent, ou découper la donnée (une ligne par jour, sommée à
  la lecture).
- **Les erreurs `40001`** sont une métrique : leur taux dit si un niveau
  d'isolation élevé coûte trop cher.
- **Le test de charge** doit concentrer les écritures sur **une** ligne,
  comme le soir de la cotisation. Un test qui répartit tout sur des
  comptes différents ne montre aucun de ces défauts.

## 12. Ce qu'il faut retenir

1. Lire, calculer en Go et réécrire perd des mises à jour, même dans une
   transaction en `READ COMMITTED`.
2. On calcule dans la base quand c'est possible, sinon on verrouille ce
   qu'on lit.
3. Les méthodes optimistes conviennent quand les conflits sont rares ;
   elles s'effondrent sur une ligne très disputée.
4. Une règle sur plusieurs lignes demande un verrou sur la ligne parente,
   ou `SERIALIZABLE` avec nouvel essai.
5. Les verrous se prennent dans le même ordre partout ; une transaction
   refusée se rejoue entière.

## 13. Approfondissement

### MVCC, en une phrase

PostgreSQL garde plusieurs versions d'une ligne : un lecteur ne bloque
jamais un écrivain, et un écrivain ne bloque jamais un lecteur. Seuls
deux écrivains sur la même ligne s'attendent. C'est pour cela que le
`SELECT` de la section 2 ne voit pas l'écriture en cours, et ne
l'attend pas.

### Les verrous consultatifs

`pg_advisory_xact_lock(clé)` verrouille un **nombre** choisi par
l'application, pas une ligne. C'est utile pour sérialiser une opération
qui n'a pas de ligne naturelle à verrouiller. La leçon 5.4 s'en sert
pour qu'une seule instance applique les migrations.

## 14. Le réflexe à installer

Devant une écriture qui dépend d'une lecture, demande-toi :

1. Que se passe-t-il si deux requêtes font la même chose au même
   instant, sur **la même** ligne ?
2. Le calcul peut-il se faire dans une seule instruction SQL ?
3. Sinon, quelle ligne verrouiller, et dans quel ordre ?
4. La règle porte-t-elle sur plusieurs lignes ? Quel parent verrouiller,
   ou faut-il `SERIALIZABLE` ?
5. Quel test concentre les requêtes sur une seule ligne, sur plusieurs
   tours, et a été vu échouer ?
