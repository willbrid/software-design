# Correction 5.2 — Exercice 2 : l'adhésion d'un membre

> Rappel de l'énoncé : rendre `Join` atomique (le membre, la première
> cotisation, le SMS de bienvenue), traduire le téléphone déjà pris, et
> expliquer le test du pool d'une connexion.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Une transaction autour des trois écritures**, et chaque écriture
  passe par `tx`.
- **La fonction d'aide reçoit `tx` en paramètre** : elle ne peut plus
  s'échapper de la transaction.
- **Le test du pool d'une connexion** attrape la correction à moitié
  faite, celle qui oublie l'aide.

## 1. La solution

```go
// Join registers the member, records the first contribution, and queues
// the welcome SMS, in one transaction.
func (s *Store) Join(ctx context.Context, tontineID int64, name, phone string, cycle time.Time, firstFCFA int64) (int64, error) {
    var id int64
    err := pgx.BeginFunc(ctx, s.db, func(tx pgx.Tx) error {
        err := tx.QueryRow(ctx,
            `INSERT INTO member (tontine_id, name, phone) VALUES ($1, $2, $3) RETURNING id`,
            tontineID, name, phone).Scan(&id)
        if err == nil {
            err = s.Fault.After("member")
        }
        if err == nil {
            _, err = tx.Exec(ctx,
                `INSERT INTO contribution (member_id, cycle, amount_fcfa) VALUES ($1, $2, $3)`,
                id, cycle, firstFCFA)
        }
        if err == nil {
            err = s.Fault.After("contribution")
        }
        if err == nil {
            err = queueWelcome(ctx, tx, name, phone)
        }
        if err == nil {
            err = s.Fault.After("sms")
        }
        return err
    })
    if err != nil {
        return 0, translate(err)
    }
    return id, nil
}
```

```go
// queueWelcome takes the transaction as a parameter: it cannot escape it.
func queueWelcome(ctx context.Context, q closing.DBTX, name, phone string) error {
    _, err := q.Exec(ctx, `INSERT INTO sms_outbox (phone, body) VALUES ($1, $2)`,
        phone, fmt.Sprintf("Bienvenue %s dans la tontine !", name))
    return err
}
```

```go
func translate(err error) error {
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) && pgErr.ConstraintName == "member_phone_unique" {
        return fmt.Errorf("%w (%s)", ErrDuplicatePhone, pgErr.ConstraintName)
    }
    return err
}
```

`queueWelcome` n'est plus une méthode du store. Elle reçoit la connexion
sur laquelle écrire, et dans `Join` la seule variable disponible est
`tx`. L'erreur de `leaky` devient impossible à écrire par distraction.

La traduction se fait **après** la transaction : à ce moment, l'erreur
est celle de l'`INSERT` du membre, remontée par `BeginFunc` après le
`ROLLBACK`.

## 2. Le test qui paraît inutile

La correction la plus courante enveloppe le corps de `Join` dans
`pgx.BeginFunc`, remplace `s.db` par `tx` dans les deux premières
écritures… et garde `s.queueWelcome`, qui écrit toujours sur `s.db`. Les
trois premiers tests ont l'air de passer ? Voici ce que donne cette
version :

```text
--- FAIL: TestAFailedJoinLeavesNothing (0.14s)
    --- FAIL: TestAFailedJoinLeavesNothing/sms (0.06s)
        join_test.go:58: after a crash after sms: {members:0 contributions:0 sms:1}, want nothing
--- FAIL: TestJoinWorksOnAPoolOfOneConnection (2.06s)
    join_test.go:86: context deadline exceeded
FAIL
FAIL    example/corr52/ex2      2.317s
FAIL
```

Deux échecs :

- **après une panne à l'étape `sms`**, le membre et la cotisation sont
  annulés, mais le SMS est déjà validé : le futur membre recevra
  « Bienvenue » pour une adhésion qui n'existe pas ;
- **sur un pool d'une connexion**, la transaction tient la seule
  connexion, et `queueWelcome` en attend une deuxième jusqu'au délai de
  deux secondes.

Le second test est le plus utile des deux, parce qu'il ne dépend pas
d'une panne simulée. Toute requête qui s'échappe d'une transaction se
bloque sur un pool d'une connexion, quelle que soit l'étape. C'est un
filet bon marché pour tout le code transactionnel.

## 3. Pourquoi une table de SMS

Envoyer le SMS depuis `Join` reproduirait la section 6 de la leçon. Si
l'envoi part avant le `COMMIT` et que la transaction est annulée, la
personne reçoit « Bienvenue » sans être membre. Si l'envoi part après le
`COMMIT` et que le programme meurt entre les deux, le membre n'a jamais
de SMS. La table `sms_outbox` est écrite **avec** l'adhésion, et un
envoyeur la vide ensuite.

Un SMS de bienvenue envoyé deux fois est sans gravité : ici, une clé
d'idempotence n'est pas indispensable. Pour un virement, elle l'est.

## Ce qu'il faut retenir

- Une fonction d'aide qui écrit reçoit le `DBTX` en paramètre.
- Un test sur un pool d'une connexion détecte toute requête qui
  s'échappe de la transaction.
- Le coût d'un doublon décide si une clé est nécessaire : un SMS n'est
  pas un virement.
