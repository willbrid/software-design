# Correction 5.6 — Exercice 5 : le samedi des avances

> Rappel de l'énoncé : des avances accordées sur la cagnotte affichée
> depuis le cache ; le lundi, sept cagnottes sont négatives. Auditer,
> écrire la version sûre, ajouter la contrainte qui manquait, et rédiger
> le compte rendu.

L'audit et la version sûre sont dans `ex5` du module de correction,
verts sous `go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **La cause** : la décision se prenait sur une valeur lue (en cache), et
  la base n'avait aucune contrainte pour refuser.
- **7 cagnottes, 1 000 000 FCFA prêtés en trop, 20 avances**, la première
  à 12 h 16.
- **La version sûre** décide dans l'instruction qui écrit, avec une
  condition : rejouée en direct, elle accorde 50 avances sur 50
  possibles, là où la version de l'incident en accorde 150.

## 1. L'incident

C'est la section 5 de la leçon, avec une différence qui change tout :
**aucune contrainte** sur la cagnotte. Trente écrans demandent la
cagnotte en même temps ; le cache est vide ou vient d'être invalidé ;
tous lisent 500 000 FCFA, et tous accordent. L'invalidation après chaque
avance n'y peut rien : elle arrive **après** que les autres ont déjà lu
et décidé. Rejoué en direct par le module :

```text
$ go run ./cmd/ex5
GrantFromCache  advances granted 150 for 50 possible, lowest pot -1000000 FCFA
Grant           advances granted  50 for 50 possible, lowest pot        0 FCFA
```

150 avances accordées pour 50 possibles, et une cagnotte à
−1 000 000 FCFA.

## 2. Ce qui aurait limité les dégâts

La leçon 5.1 : **la base, dernier garde-fou**.
`CHECK (available_fcfa >= 0)` sur la cagnotte aurait refusé chaque avance
de trop au moment de l'`UPDATE`. Les écrans auraient affiché des refus
après des « accepté » (la section 5 de la leçon), ce qui reste un défaut,
mais aucun franc ne serait parti en trop.

## 3. L'audit et la version sûre

```go
// Audit finds the pots lent beyond what they held. The pot held, before
// the day, what is left plus what was lent; an advance is too many when
// the advances granted up to it exceed that.
func Audit(ctx context.Context, db *pgxpool.Pool) (Report, error) {
    var r Report
    var first *time.Time
    err := db.QueryRow(ctx, `
        WITH a AS (
            SELECT ad.granted_at,
                   p.available_fcfa + sum(ad.amount_fcfa) OVER (PARTITION BY ad.tontine_id) AS held,
                   sum(ad.amount_fcfa) OVER (PARTITION BY ad.tontine_id ORDER BY ad.granted_at, ad.id) AS lent
            FROM advance ad JOIN pot p USING (tontine_id))
        SELECT (SELECT count(*) FROM pot WHERE available_fcfa < 0),
               (SELECT coalesce(sum(-available_fcfa), 0) FROM pot WHERE available_fcfa < 0),
               count(*) FILTER (WHERE lent > held),
               min(granted_at) FILTER (WHERE lent > held)
        FROM a`).Scan(&r.Tontines, &r.OverFCFA, &r.TooMany, &first)
    if first != nil {
        r.FirstLate = *first
    }
    return r, err
}
```

L'audit reconstitue ce que chaque cagnotte contenait le matin (ce qui
reste, plus ce qui a été prêté), puis cumule les avances dans l'ordre où
elles ont été accordées. Une avance est de trop quand le cumul dépasse ce
que la cagnotte contenait. L'`id` départage deux avances de la même
seconde, comme la clé de pagination de la leçon 5.5.

```go
// Grant grants the advance if the pot covers it, whatever the screens show
// and however many treasurers grant at the same time: the pot decreases
// only if it still covers the advance when the row is updated.
func Grant(ctx context.Context, db *pgxpool.Pool, tontineID, memberID, amountFCFA int64) error {
    return pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        tag, err := tx.Exec(ctx, `
            UPDATE pot SET available_fcfa = available_fcfa - $2
            WHERE tontine_id = $1 AND available_fcfa >= $2`, tontineID, amountFCFA)
        if err != nil {
            return err
        }
        if tag.RowsAffected() == 0 {
            return ErrPotTooSmall
        }
        _, err = tx.Exec(ctx, `INSERT INTO advance (tontine_id, member_id, amount_fcfa) VALUES ($1, $2, $3)`,
            tontineID, memberID, amountFCFA)
        return err
    })
}
```

La décision et l'écriture sont **une seule instruction**. Quand trente
`UPDATE` visent la même cagnotte, ils passent l'un après l'autre, et
chacun réévalue `available_fcfa >= $2` sur la valeur laissée par le
précédent (leçon 5.3, exercice 3). Le cache n'intervient plus : l'écran
peut continuer à l'afficher, mais la décision ne le lit pas.

```text

--- PASS: TestGrantNeverLendsMoreThanThePot (0.35s)
--- PASS: TestTheSaturdayAddsUp (0.36s)
ok      example/corr56/ex5      0.749s
```

## 4. Les chiffres

```text
Saturday: 7 pots lent beyond what they held, 1000000 FCFA too much, 20 advances too many, the first at 12:16
```

- **7 cagnottes** sur 30 ont été prêtées au-delà de ce qu'elles
  contenaient ;
- **1 000 000 FCFA** prêtés en trop, soit **20 avances** de
  50 000 FCFA ;
- **la première à 12 h 16**, après trois heures de marché, au moment où
  les cagnottes les plus demandées arrivaient à leur fin.

## 5. Ajouter la contrainte malgré les cagnottes négatives

`ALTER TABLE pot ADD CONSTRAINT pot_not_negative CHECK (available_fcfa >= 0)`
échoue aujourd'hui : sept lignes la violent. La leçon 5.4 donne la
forme qui marche :

1. `... CHECK (available_fcfa >= 0) NOT VALID` : la règle protège dès
   maintenant **toutes les nouvelles écritures**, sans vérifier les
   lignes existantes ;
2. on règle les sept cagnottes (remboursement des avances de trop, ou
   apport du bureau), ce qui les ramène à zéro ou plus ;
3. `VALIDATE CONSTRAINT pot_not_negative`, quand plus aucune ligne ne la
   viole.

Le premier pas se fait **le jour même** : c'est lui qui empêche le
samedi suivant de recommencer, même si le code n'était pas encore
corrigé.

## 6. Le message aux trésorières

> Objet : avances accordées le samedi 17 octobre
>
> Samedi, l'application a accordé dans sept tontines plus d'avances que
> la cagnotte ne pouvait en couvrir : l'écran affichait une cagnotte qui
> n'était plus à jour. Les avances déjà versées restent valables : aucun
> membre n'a à rendre l'argent de son propre chef. Le bureau de chaque
> tontine concernée sera appelé cette semaine pour décider comment
> combler l'écart. Depuis lundi, une avance n'est accordée que si la
> cagnotte la couvre réellement, et l'écran peut afficher un refus
> même quand le montant semble disponible.

## 7. Le compte rendu

1. **Quoi** : le samedi 17 octobre 2026, 20 avances de trop ont été
   accordées dans 7 tontines, soit 1 000 000 FCFA au-delà des cagnottes,
   à partir de 12 h 16.
2. **Cause** : la décision d'accorder se prenait sur la cagnotte lue
   depuis le cache, et la table des cagnottes n'avait aucune contrainte.
   Des trésorières qui accordaient en même temps lisaient toutes la même
   cagnotte.
3. **Détection** : le lundi, par les cagnottes négatives. Rien ne
   surveillait le signe des cagnottes.
4. **Correction** : la décision se prend dans l'instruction qui écrit,
   avec une condition ; la contrainte `pot_not_negative` est ajoutée
   `NOT VALID` le jour même, puis validée après règlement.
5. **Prévention** : aucune décision ne lit le cache (règle de revue de
   code) ; un test accorde 30 avances simultanées sur une même cagnotte ;
   une alerte se déclenche dès qu'une cagnotte passe sous zéro.

## Ce qu'il faut retenir

- Le cache élargit la fenêtre entre la lecture et l'écriture ; il ne la
  crée pas, et l'invalidation ne la ferme pas.
- La contrainte de la base est la seule protection qui ne dépend pas du
  code qui écrit.
- Une contrainte qu'on ne peut pas valider aujourd'hui s'ajoute
  `NOT VALID` : elle protège l'avenir pendant qu'on répare le passé.
