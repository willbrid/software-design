# Correction 5.3 — Exercice 3 : le retrait garanti

> Rappel de l'énoncé : un retrait ne doit jamais laisser moins que les
> prêts ouverts du membre. Le test de concurrence montre 20 retraits
> payés sur un compte qui en permettait 7.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Le compte 1 a payé 200 000 FCFA** sur un solde de 100 000 et garde
  80 000 : **180 000 FCFA** sont sortis de la caisse sans être débités.
- **Verrouiller la ligne du compte** avant de lire fait passer les
  retraits un par un.
- **Une instruction conditionnelle** fait le même travail, sans
  transaction explicite, tant que la règle tient dans un `WHERE`.

## 1. Lire le compte 1

20 retraits de 10 000 FCFA ont répondu « payé » : 200 000 FCFA sont
partis. Le solde aurait dû baisser de 200 000, ce qui est impossible
avec 100 000. Il n'a baissé que de 20 000 : il reste 80 000. Les
retraits ont lu le même solde de 100 000, chacun a écrit 90 000, puis
quelques-uns ont relu 90 000 et écrit 80 000. **180 000 FCFA** ont été
payés sans être débités, et la garantie des prêts (30 000) a disparu
avec eux.

C'est la mise à jour perdue de la leçon, côté retrait : elle ne perd
plus des dépôts, elle **crée de l'argent**.

## 2. La correction

```go
// Withdraw takes amountFCFA from the account, if what is left still covers
// the open loans of the member. The account row is locked first: two
// withdrawals from the same account run one after the other.
func Withdraw(ctx context.Context, db *pgxpool.Pool, account, amountFCFA int64) error {
    return pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        var balance, loans int64
        err := tx.QueryRow(ctx,
            `SELECT balance_fcfa FROM account WHERE id = $1 FOR UPDATE`, account).Scan(&balance)
        if err != nil {
            return err
        }
        err = tx.QueryRow(ctx,
            `SELECT coalesce(sum(amount_fcfa), 0) FROM loan WHERE account_id = $1 AND open`,
            account).Scan(&loans)
        if err != nil {
            return err
        }
        if balance-amountFCFA < loans {
            return ErrGuarantee
        }
        _, err = tx.Exec(ctx, `UPDATE account SET balance_fcfa = $2 WHERE id = $1`, account, balance-amountFCFA)
        return err
    })
}
```

Le `FOR UPDATE` sur le compte fait attendre le deuxième retrait jusqu'au
`COMMIT` du premier. Il lit alors le solde déjà diminué. Sept retraits
passent, treize sont refusés, et le solde finit à 30 000 FCFA.

## 3. En une instruction

```go
// WithdrawInOneStatement does the same with one conditional UPDATE: it
// writes only if the guarantee still holds when the row is updated.
func WithdrawInOneStatement(ctx context.Context, db *pgxpool.Pool, account, amountFCFA int64) error {
    tag, err := db.Exec(ctx, `
        UPDATE account a SET balance_fcfa = balance_fcfa - $2
        WHERE id = $1 AND balance_fcfa - $2 >= (
            SELECT coalesce(sum(amount_fcfa), 0) FROM loan WHERE account_id = a.id AND open)`,
        account, amountFCFA)
    if err != nil {
        return err
    }
    if tag.RowsAffected() == 0 {
        return ErrGuarantee
    }
    return nil
}
```

```text
--- PASS: TestAWithdrawalKeepsTheGuarantee (0.05s)
--- PASS: TestConcurrentWithdrawalsKeepTheGuarantee (0.26s)
--- PASS: TestTheOneStatementWithdrawalKeepsTheGuarantee (0.16s)
ok      example/corr53/ex3      0.479s
```

Quand deux `UPDATE` visent la même ligne, le second attend le premier,
puis **réévalue sa condition `WHERE`** sur la ligne mise à jour. Le
solde vu par le `WHERE` est donc toujours le dernier. C'est ce que fait
`READ COMMITTED` pour un `UPDATE`, et c'est pour cela que l'instruction
unique est sûre.

Attention à la limite de ce mécanisme : seule **la ligne modifiée** est
relue. Les lignes d'une autre table jointe dans un `FROM` ne le sont
pas : l'exercice 5 tombe dans ce piège. Ici, les prêts ne changent pas
pendant le retrait, et la question 4 traite le cas où ils changent.

Je préfère l'instruction unique quand la règle tient dans le `WHERE` :
elle fait un aller-retour au lieu de cinq. La version avec
`FOR UPDATE` devient nécessaire dès que la décision a besoin de Go :
un message d'erreur qui dit combien on peut retirer, un plafond qui
dépend d'un calcul compliqué, ou plusieurs écritures après la
vérification.

## 4. Un prêt accordé pendant le retrait

Non, la correction ne protège pas ce cas. Le retrait verrouille le
**compte**, mais l'octroi du prêt n'y touche pas : il insère dans
`loan`. Un retrait et un prêt peuvent donc passer en même temps, et
chacun voir l'ancienne situation (*write skew*, section 4 de la leçon).

Pour le protéger, il faut que les deux opérations se rencontrent sur
**la même ligne** : l'octroi d'un prêt verrouille aussi le compte du
membre (`SELECT ... FROM account WHERE id = $1 FOR UPDATE`) avant de
vérifier la garantie. Le compte devient la ligne parente de la règle
« l'épargne couvre les prêts », comme la tontine l'était pour « au plus
trois prêts ».

## Ce qu'il faut retenir

- Une mise à jour perdue sur un retrait crée de l'argent.
- `FOR UPDATE` sur la ligne parente fait passer les opérations d'une
  même règle une par une.
- Toutes les opérations d'une règle doivent verrouiller **la même**
  ligne, sinon la règle reste ouverte.
