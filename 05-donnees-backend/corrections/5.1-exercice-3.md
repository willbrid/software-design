# Correction 5.1 — Exercice 3 : la cagnotte qui dérive

> Rappel de l'énoncé : expliquer les deux échecs, refactorer pour que la
> cagnotte ne dérive plus, mesurer le coût, dire quand garder un total
> stocké.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Le total stocké n'est juste que si tout passe par le store.** Le
  script et `psql` n'y passent pas.
- **La refactorisation remplace la table par une vue du même nom** : la
  cagnotte est calculée, elle ne peut plus dériver, et `Pot` ne change
  pas.
- **Le coût** : une lecture passe de 0,17 ms à 0,85 ms ; une cotisation
  passe de 4 ms à 2 ms.

## 1. Les deux échecs

Le total est un **deuxième exemplaire** d'un fait (la somme des
cotisations). Le store tient les deux à jour ensemble ; tout ce qui
écrit sans lui ne met à jour que le premier. Le script de reprise ajoute
une cotisation sans toucher au total ; la suppression dans `psql` en
retire une sans le toucher non plus. C'est la règle de normalisation de
la leçon : un fait écrit à deux endroits finit par avoir deux valeurs.

Il y a un troisième défaut, que les tests ne montrent pas : `Contribute`
fait deux écritures séparées. Si le programme s'arrête entre les deux, la
cotisation est enregistrée et le total ne l'est pas. La leçon 5.2 traite
ce cas.

## 2. La refactorisation

```sql
-- The pot of each cycle is computed from the contributions, never stored:
-- whatever writes a contribution, the pot sees it.
CREATE VIEW cycle_total AS
SELECT m.tontine_id, c.cycle, sum(c.amount_fcfa)::bigint AS pot_fcfa
FROM contribution c
JOIN member m ON m.id = c.member_id
GROUP BY m.tontine_id, c.cycle;
```

```go
// Contribute records a contribution. The pot follows by itself.
func (s *Store) Contribute(ctx context.Context, memberID int64, cycle string, amountFCFA int64) error {
    month, err := tontine.ParseCycle(cycle)
    if err != nil {
        return err
    }
    _, err = s.db.Exec(ctx,
        `INSERT INTO contribution (member_id, cycle, amount_fcfa) VALUES ($1, $2, $3)`,
        memberID, month, amountFCFA)
    return err
}
```

La vue garde le nom `cycle_total` et les mêmes colonnes : la requête de
`Pot` est inchangée, et la page d'accueil aussi. `Contribute` n'a plus
qu'une écriture. Les quatre tests passent.

## 3. Le coût

Le programme `cmd/ex3cost` enregistre 4 800 cotisations par chaque
version, puis lit une cagnotte 1 000 fois :

```text
stored contribution 3.968ms, pot read 167µs
view   contribution 2.03ms, pot read 856µs
stored contribution 3.974ms, pot read 168µs
view   contribution 2.03ms, pot read 849µs
stored contribution 3.951ms, pot read 186µs
view   contribution 1.918ms, pot read 850µs
```

La lecture coûte cinq fois plus cher : la vue additionne 400 cotisations
à chaque fois. Mais elle reste sous la milliseconde, et une cotisation
coûte **deux fois moins** cher, puisqu'il n'y a plus qu'une écriture à
valider. Pour une tontine, ce coût n'existe pas en pratique.

## 4. Quand garder un total stocké

Quand la somme devient chère : des millions de lignes, une page lue des
milliers de fois par seconde. Il faut alors que **la base** tienne le
total à jour, pas le store :

- un déclencheur sur `contribution` (`AFTER INSERT OR UPDATE OR DELETE`)
  qui met à jour le total dans la même transaction que l'écriture : le
  script et `psql` passent par lui ;
- ou une vue matérialisée rafraîchie à intervalles, si un total un peu
  en retard est acceptable (et on le dit sur la page) ;
- et dans les deux cas, un contrôle de rapprochement qui compare chaque
  nuit le total stocké à la somme calculée, avec une alerte.

## Ce qu'il faut retenir

1. Un fait écrit à deux endroits dérive dès qu'un programme n'écrit qu'à
   un endroit.
2. Calculer d'abord ; stocker quand la mesure le demande, et alors faire
   tenir le total par la base.
3. Une vue du même nom permet de refactorer le schéma sans toucher aux
   lecteurs.
