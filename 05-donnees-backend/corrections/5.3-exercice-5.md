# Correction 5.3 — Exercice 5 : les caisses qui ne tombent pas juste

> Rappel de l'énoncé : depuis une nouvelle version, le dépôt lit le
> solde, vérifie un plafond en Go, et réécrit. Deux mois plus tard, les
> caisses ne correspondent plus aux cotisations. Auditer, réparer
> pendant que les dépôts continuent, corriger, prévenir, et rédiger le
> compte rendu.

L'audit et la réparation sont dans `ex5` du module de correction, verts
sous `go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **La cause** : la mise à jour perdue de la section 2 de la leçon,
  mise en production pour ajouter un plafond.
- **Les 40 caisses sont touchées, et il manque 11 800 000 FCFA** dans les
  soldes, depuis la nuit du 20 septembre. L'argent n'est pas perdu : il
  est dans les cotisations, qui ont toutes été enregistrées.
- **La réparation verrouille les caisses avant de lire les cotisations**.
  Sans ce verrou, un dépôt en cours est perdu une deuxième fois, par la
  réparation elle-même.

## 1. L'incident

C'est la section 2 de la leçon : lire le solde, calculer en Go, réécrire.
Dans une transaction en `READ COMMITTED`, deux dépôts simultanés lisent
le même solde, et le second efface le premier. Le dimanche soir, 25
membres paient la même caisse en deux heures : c'est le seul moment où
deux dépôts tombent au même instant sur la même ligne. En semaine, il
n'y a presque aucun dépôt, et la recette n'en a fait qu'un à la fois.

## 2. L'audit

Le solde d'une caisse doit valoir la somme de ses cotisations. Chaque
copie de nuit doit valoir la somme des cotisations **reçues avant
minuit** :

```go
// Audit compares the balances with the contributions.
func Audit(ctx context.Context, db *pgxpool.Pool) (Report, error) {
    var r Report
    var first *time.Time
    err := db.QueryRow(ctx, audit).Scan(&r.Accounts, &r.MissingFCFA, &first)
    if first != nil {
        r.FirstDay = *first
    }
    return r, err
}
```

```text
audit: 40 cash boxes short, 11800000 FCFA missing, first night 2026-09-20
  2026-09-06  boxes short  0/40, missing since the start        0 FCFA
  2026-09-13  boxes short  0/40, missing since the start        0 FCFA
  2026-09-20  boxes short 35/40, missing since the start  1800000 FCFA
  2026-09-27  boxes short 40/40, missing since the start  4225000 FCFA
  2026-10-04  boxes short 40/40, missing since the start  6250000 FCFA
  2026-10-11  boxes short 40/40, missing since the start  8150000 FCFA
  2026-10-18  boxes short 40/40, missing since the start  9925000 FCFA
  2026-10-25  boxes short 40/40, missing since the start 11800000 FCFA
```

- **40 caisses sur 40**, et **11 800 000 FCFA** de cotisations absentes
  des soldes ;
- **la première nuit fausse est le 20 septembre**, le jour de la mise en
  production. Les nuits du 6 et du 13 septembre sont justes ;
- le manque grandit d'environ 2 000 000 FCFA chaque dimanche, sur
  25 000 000 FCFA de cotisations : le défaut efface près de 8 % des
  dépôts du soir.

## 3. La réparation

```go
// Repair sets each balance to the sum of its contributions, and says how
// many balances it changed. It locks the cash boxes first: a deposit in
// progress finishes before the sums are read, and the deposits that start
// later wait for the repair.
func Repair(ctx context.Context, db *pgxpool.Pool) (int, error) {
    changed := 0
    err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        if _, err := tx.Exec(ctx, `SELECT id FROM account ORDER BY id FOR UPDATE`); err != nil {
            return err
        }
        tag, err := tx.Exec(ctx, `
            UPDATE account a SET balance_fcfa = l.due
            FROM (SELECT account_id, sum(amount_fcfa) AS due FROM contribution GROUP BY account_id) l
            WHERE l.account_id = a.id AND a.balance_fcfa <> l.due`)
        changed = int(tag.RowsAffected())
        return err
    })
    return changed, err
}
```

Le premier `SELECT ... FOR UPDATE` est la ligne qui compte. Sans lui, la
réparation a l'air correcte : l'`UPDATE` attend lui aussi le dépôt en
cours, puisqu'il touche la même ligne. Mais il a calculé les sommes
**avant** d'attendre. Quand le dépôt valide, PostgreSQL réévalue la
condition `WHERE` sur le nouveau solde, mais **pas** la sous-requête
des sommes, déjà calculée. La réparation écrit l'ancienne somme
par-dessus le dépôt :

```text
--- FAIL: TestRepairDoesNotLoseADepositInProgress (0.10s)
    incident_test.go:109: after the repair: {Accounts:1 MissingFCFA:25000 FirstDay:2026-10-04 00:00:00 +0000 UTC}
FAIL
FAIL    example/corr53/ex5      0.105s
FAIL
```

Avec le verrou pris d'abord, la réparation attend que le dépôt en cours
valide, puis lit les sommes, qui l'incluent. Les dépôts qui arrivent
ensuite attendent la fin de la réparation, une fraction de seconde. Le
verrou est pris dans l'ordre des identifiants, comme les transferts de
la leçon, pour ne pas croiser un autre traitement qui verrouillerait
plusieurs caisses.

La réparation ne change que les soldes faux. Sur les deux mois, elle en
change 40, et l'audit ne trouve plus rien :

```text
repair: 40 balances changed; audit after: 0 boxes short, 0 FCFA missing
```

La relancer ne change plus rien : `TestRepairFixesTheBalancesOnce`
vérifie qu'un deuxième passage renvoie zéro solde modifié.

## 4. Où est l'argent ?

L'argent n'a pas disparu. Chaque cotisation a été payée par Mobile Money
et enregistrée dans `contribution`. C'est le **solde**, une copie
calculée, qui est faux. Les membres ne doivent rien, et personne n'a
pris d'argent. En revanche, toute décision prise d'après le solde
(plafond de la caisse, montant prêtable, rapport mensuel) a été prise
sur un chiffre trop bas.

C'est la leçon de l'exercice 3 de la leçon 5.1, vue de l'autre côté :
le fait (la cotisation) était écrit une fois, la copie (le solde) a
dérivé, et c'est le fait qui permet de réparer.

## 5. La correction, en gardant le plafond

Le plafond se vérifie dans l'instruction qui écrit :

```sql
UPDATE account SET balance_fcfa = balance_fcfa + $2
WHERE id = $1 AND balance_fcfa + $2 <= $3   -- $3 : le plafond
```

Si aucune ligne n'est modifiée, le plafond est atteint et le dépôt est
refusé. C'est la même idée que le retrait de l'exercice 3. Si le plafond
devait se calculer en Go, on lirait le solde avec `FOR UPDATE`. Dans
tous les cas, on ajoute un test qui envoie plusieurs dépôts **sur la
même caisse**, sur plusieurs tours, et on le voit échouer sur la version
fautive avant de le garder.

## 7. Le compte rendu

1. **Quoi** : du 20 septembre au 25 octobre 2026, les soldes des 40
   caisses ont été sous-évalués de 11 800 000 FCFA au total ; aucune
   cotisation n'a été perdue.
2. **Cause** : la version du 20 septembre lisait le solde, vérifiait le
   plafond en Go et réécrivait. Deux dépôts simultanés du dimanche soir
   s'écrasaient l'un l'autre.
3. **Détection** : par une trésorière, cinq semaines plus tard. Il n'y
   avait aucun contrôle automatique entre les soldes et les cotisations.
4. **Correction** : le dépôt calcule le solde et vérifie le plafond dans
   une seule instruction ; les soldes ont été recalculés par une
   réparation qui verrouille les caisses.
5. **Prévention** : l'audit de cet exercice tourne chaque nuit et alerte
   au premier écart, et un test concentre des dépôts simultanés sur une
   même caisse.

## Ce qu'il faut retenir

- Un fait écrit une fois (la cotisation) permet de réparer une copie qui
  a dérivé (le solde).
- Une réparation qui tourne pendant le trafic verrouille d'abord, puis
  lit : sinon elle commet elle-même la mise à jour perdue qu'elle
  répare.
- Un audit de nuit transforme un incident de cinq semaines en incident
  d'un jour.
