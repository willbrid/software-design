# Correction 5.5 — Exercice 2 : le résumé d'une tontine

> Rappel de l'énoncé : le résumé d'une tontine envoyait deux requêtes
> par membre. Le réécrire en une requête, sans changer son contenu.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **51 requêtes** pour 25 membres : 1 pour les membres, 2 par membre.
  À 20 ms de la base, plus d'une seconde.
- **Une requête** : une jointure externe et des agrégats filtrés.
- **Les pièges sont aux bords** : le membre qui n'a jamais payé, le
  paiement de 2027, celui de 2025 qui compte pour la date mais pas pour
  le total.

## 1. Le coût

1 + 2 × 25 = **51 requêtes**. À 20 ms par aller-retour, la page coûte
au moins **1,02 s**, pour un résultat de 25 lignes.

## 2. La solution

```go
// Summary returns the lines of the tontine's members, by member id, in one
// query: the database groups the contributions of each member.
func Summary(ctx context.Context, db *pgxpool.Pool, tontineID int64) ([]Line, error) {
    rows, err := db.Query(ctx, `
        SELECT m.id, m.name,
               coalesce(sum(c.amount_fcfa) FILTER (WHERE c.paid_at >= $2), 0),
               max(c.paid_at),
               count(c.id) FILTER (WHERE c.paid_at >= $2)
        FROM member m
        LEFT JOIN contribution c ON c.member_id = m.id AND c.paid_at < $3
        WHERE m.tontine_id = $1
        GROUP BY m.id
        ORDER BY m.id`, tontineID, from, to)
    if err != nil {
        return nil, err
    }
    return pgx.CollectRows(rows, pgx.RowToStructByPos[Line])
}
```

Chaque morceau répond à un cas du test :

- **`LEFT JOIN`** garde le membre 4, qui n'a jamais payé : sans lui, il
  disparaîtrait du résumé ;
- **`c.paid_at < $3` dans la jointure**, pas dans un `WHERE` : un
  `WHERE` sur une colonne de `c` éliminerait les membres sans
  cotisation, et le `LEFT JOIN` redeviendrait un `JOIN`. Cette borne
  écarte le paiement de 2027 du membre 3 ;
- **`FILTER (WHERE c.paid_at >= $2)`** sur la somme et le compte, mais
  **pas** sur `max(c.paid_at)` : le paiement de 2025 du membre 2 ne
  compte pas dans le total de 2026, mais c'est bien sa dernière date de
  paiement ;
- **`count(c.id)`** et pas `count(*)` : pour un membre sans cotisation,
  la jointure externe donne une ligne de `NULL`, que `count(*)`
  compterait.

La campagne des corrections a muté trois de ces points (le filtre sur
la somme, la jointure externe, la borne de 2027), et les tests les ont
tous attrapés.

## 3. L'index

`member_by_tontine (tontine_id)` trouve les 25 membres ; puis, pour
chacun, `contribution_by_member (member_id, paid_at DESC, id DESC)`
donne ses cotisations jusqu'à la borne `paid_at < $3`. Ce sont les deux
index de la leçon : une bonne requête réutilise souvent les index des
autres.

## Ce qu'il faut retenir

- Un N+1 se remplace par une jointure externe et des agrégats.
- Une condition sur la table de droite d'un `LEFT JOIN` va dans le `ON`,
  pas dans le `WHERE`.
- `FILTER` permet plusieurs agrégats sur des sous-ensembles différents,
  en une seule lecture.
