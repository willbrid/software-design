# Correction 5.3 — Exercice 2 : plusieurs envoyeurs pour une même outbox

> Rappel de l'énoncé : quatre envoyeurs vident la même outbox de SMS ;
> chaque SMS doit partir une fois, et un envoyeur ne doit pas attendre
> les autres.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Les quatre envoyeurs lisaient la même ligne** : celle qui n'est pas
  encore marquée envoyée. C'est une mise à jour perdue, sous la forme
  d'un travail fait quatre fois.
- **`FOR UPDATE SKIP LOCKED`** : chaque envoyeur prend la première ligne
  que personne ne tient, et saute les autres.
- **Envoyer pendant la transaction est acceptable ici** : la ligne est
  déjà validée, et c'est le verrou qu'on tient, pas la décision.

## 1. Les 198 SMS en double

Sans verrou, les quatre envoyeurs exécutent le même `SELECT` au même
moment, et la plus ancienne ligne non envoyée est la même pour tous. Les
quatre l'envoient, puis la marquent. Chaque SMS part jusqu'à quatre
fois ; 198 des 200 sont partis plus d'une fois.

## 2. La solution

```go
// SendOne locks the oldest SMS that no other sender holds, sends it, and
// marks it sent, in one transaction. It returns false when there is
// nothing left to take.
func (s *Sender) SendOne(ctx context.Context) (bool, error) {
    sent := false
    err := pgx.BeginFunc(ctx, s.DB, func(tx pgx.Tx) error {
        var id int64
        var phone, body string
        err := tx.QueryRow(ctx, `
            SELECT id, phone, body FROM sms_outbox
            WHERE sent_at IS NULL ORDER BY id LIMIT 1
            FOR UPDATE SKIP LOCKED`).Scan(&id, &phone, &body)
        if errors.Is(err, pgx.ErrNoRows) {
            return nil
        }
        if err != nil {
            return err
        }
        if err := s.Gateway.Send(ctx, id, phone, body); err != nil {
            return err
        }
        _, err = tx.Exec(ctx, `UPDATE sms_outbox SET sent_at = now() WHERE id = $1`, id)
        sent = err == nil
        return err
    })
    return sent, err
}
```

`FOR UPDATE` seul suffirait à empêcher les doublons : le deuxième
envoyeur attendrait que le premier valide, puis relirait la ligne, la
verrait envoyée, et l'ignorerait. Mais il **attendrait** :

```text
--- FAIL: TestASenderDoesNotWaitForAnother (1.06s)
    sender_test.go:89: second sender: timeout: context deadline exceeded
FAIL
FAIL    example/corr53/ex2      2.160s
FAIL
```

Avec `FOR UPDATE`, les quatre envoyeurs font la queue derrière la même
ligne : il y a quatre processus, mais un seul envoie à la fois.
`SKIP LOCKED` leur fait prendre **des lignes différentes** :

```text
--- PASS: TestFourSendersSendEachSMSOnce (0.35s)
--- PASS: TestASenderDoesNotWaitForAnother (0.08s)
ok      example/corr53/ex2      0.433s
```

## 3. Envoyer pendant la transaction

La section 6 de la leçon 5.2 reprochait à `transfer.Inside` d'appeler
l'opérateur **avant que la décision soit validée** : si la transaction
était annulée, l'argent était parti pour une clôture qui n'existait
pas.

Ici, la décision (« ce SMS doit partir ») est déjà validée, depuis
longtemps, dans l'outbox. La transaction de l'envoyeur ne sert qu'à
**tenir la ligne** pendant l'envoi. Si l'envoyeur meurt après l'envoi
et avant le `COMMIT`, la ligne redevient libre et le SMS repart : c'est
le « au moins une fois » de la leçon 5.2, avec la clé `id` passée à la
passerelle.

Le prix : chaque envoyeur garde une connexion pendant l'envoi. Avec
quatre envoyeurs, c'est quatre connexions, ce qui reste raisonnable. Si
l'envoi pouvait durer des minutes, on marquerait plutôt la ligne
« prise par l'envoyeur X à 21:04 » dans une transaction courte, et on
reprendrait les lignes prises depuis trop longtemps.

## Ce qu'il faut retenir

- Une file dans une table se partage entre travailleurs avec
  `FOR UPDATE SKIP LOCKED`.
- `FOR UPDATE` seul est correct, mais aligne les travailleurs les uns
  derrière les autres.
- Appeler l'extérieur pendant une transaction n'est une faute que si
  l'appel dépend d'une décision pas encore validée.
