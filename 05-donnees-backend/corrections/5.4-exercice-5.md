# Correction 5.4 — Exercice 5 : le dimanche à 19 h 05

> Rappel de l'énoncé : une migration ajoute un numéro de reçu unique à
> 30 millions de cotisations en pleine soirée de paiement ; les
> paiements s'arrêtent, les instances redémarrent en boucle. Expliquer,
> écrire la version sûre, et rédiger le compte rendu.

La version sûre est dans `ex5` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **La cause** : une valeur par défaut volatile réécrit toute la table,
  puis un index unique est construit sans `CONCURRENTLY`. Les deux
  opérations tiennent un verrou qui bloque les paiements.
- **La version sûre** découpe le changement en quatre migrations et une
  recopie par lots : 29 s au lieu de 2,35 s, sans qu'un paiement
  dépasse 112 ms.
- **Un test de latence ne suffit pas** : à un million de lignes, deux
  formes bloquantes restent sous son seuil. Le vérificateur de
  l'exercice 2 les attrape.

## 1. L'incident

`ADD COLUMN ... DEFAULT gen_random_uuid()` : `gen_random_uuid()` est
volatile, chaque ligne doit recevoir sa propre valeur, et PostgreSQL
**réécrit les 30 millions de lignes** sous `ACCESS EXCLUSIVE`. Ce verrou
exclut tout, y compris les `INSERT` des paiements, qui n'ont rien à voir
avec les reçus. Puis `CREATE UNIQUE INDEX` lit toute la table en
bloquant les écritures. Sur le million de lignes du module :

```text
$ go run ./cmd/ex5
incident migration    2.35s | requests   544, errors    0, slower than 100ms   10, slowest 2.327s
```

2,35 s de paiements bloqués pour un million de lignes ; à 30 millions,
plus d'une minute.

## 2. Les redémarrages

Les paiements bloqués font échouer les sondes de santé. Kubernetes
redémarre les instances, et chacune relance `migrate.Up`. Les nouvelles
instances attendent le verrou consultatif, donc **aucune** ne devient
prête. Pendant ce temps, les instances qui n'avaient pas été
redémarrées sont arrêtées à leur tour, faute de répondre. À la fin,
plus aucune instance ne sert, même pour les lectures que la migration ne
bloquait pas.

Si une instance redémarrée avait tué la connexion de la migration (en
mourant elle-même pendant qu'elle migrait), la transaction aurait été
annulée, et la migration aurait recommencé depuis le début, encore et
encore.

## 3. La version sûre

```go
// Change is the same change in four migrations that block nothing for
// long. The rows already there get their receipt from Apply, between
// migrations 41 and 42.
var Change = []migrate.Migration{
    {Version: 41, Name: "receipt_column", SQL: `
ALTER TABLE contribution ADD COLUMN receipt_id UUID;
ALTER TABLE contribution ALTER COLUMN receipt_id SET DEFAULT gen_random_uuid();`},
    {Version: 42, Name: "receipt_unique", NoTx: true, SQL: `-- migrate: no-transaction
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS contribution_receipt ON contribution (receipt_id);`},
    {Version: 43, Name: "receipt_present", SQL: `
ALTER TABLE contribution ADD CONSTRAINT contribution_receipt_present CHECK (receipt_id IS NOT NULL) NOT VALID;`},
    {Version: 44, Name: "receipt_present_validated", SQL: `
ALTER TABLE contribution VALIDATE CONSTRAINT contribution_receipt_present;`},
}
```

```go
// Apply makes the same change without stopping the members' payments:
// in the end, every contribution, old or new, has a receipt_id, never
// NULL, unique.
func Apply(ctx context.Context, db *pgxpool.Pool) error {
    opt := migrate.Options{LockTimeout: 50 * time.Millisecond, Tries: 100, Pause: 200 * time.Millisecond}
    if _, err := migrate.Up(ctx, db, Change[:1], opt); err != nil {
        return err
    }
    // The new rows get a receipt from the default; the old ones, by batches.
    for {
        tag, err := db.Exec(ctx, `
            UPDATE contribution SET receipt_id = gen_random_uuid()
            WHERE id IN (SELECT id FROM contribution WHERE receipt_id IS NULL ORDER BY id LIMIT 10000)`)
        if err != nil {
            return err
        }
        if tag.RowsAffected() == 0 {
            break
        }
    }
    _, err := migrate.Up(ctx, db, Change, opt)
    return err
}
```

Ce qui ne bloque plus :

- **la colonne** est ajoutée sans valeur (instantané). `SET DEFAULT`
  ne concerne que les lignes futures : c'est une écriture du catalogue,
  instantanée elle aussi ;
- **le passé** est rempli par lots de 10 000 lignes, chacun dans sa
  propre transaction (exercice 3) ;
- **l'unicité** passe par `CREATE UNIQUE INDEX CONCURRENTLY`, seul dans
  une migration hors transaction ;
- **« jamais `NULL` »** devient `CHECK ... NOT VALID`, puis `VALIDATE`.

```text
Apply               29.469s | requests 38286, errors    0, slower than 100ms    4, slowest 112ms
```

## 4. Plus long, et alors ?

29 s au lieu de 2,35 s : la version sûre est **douze fois plus
longue**. Mais pendant ces 29 s, 38 286 paiements ont été servis, et le
plus lent a pris 112 ms. Pendant les 2,35 s de l'incident, 544
seulement, dont dix bloqués plus de deux secondes. Ce qui compte pour
les membres, c'est que les paiements passent, pas que la migration soit
courte. La durée d'une migration sûre n'a d'importance que pour le
déploiement suivant, qui doit l'attendre.

## 5. Le seuil du test

Oui, c'est possible, et la campagne des corrections l'a montré. Deux
mutations rendaient la version sûre bloquante :

- `CREATE UNIQUE INDEX` sans `CONCURRENTLY` ;
- la contrainte vérifiée d'un coup, sans `NOT VALID`.

Toutes deux **survivaient** au premier passage. Sur un million de
lignes, elles bloquaient les paiements moins de 500 ms, sous le seuil du
test. Sur 30 millions, elles les auraient bloqués des secondes. Un test
de latence mesure un symptôme, à une taille donnée. Le test ajouté juge
la **forme** de chaque migration avec le vérificateur de l'exercice 2 :

```go
// The latency test has a threshold: on a million rows, a blocking form may
// stay under it. The linter of exercise 2 judges the form itself.
func TestTheChangePassesTheLinter(t *testing.T) {
    for _, m := range ex5.Change {
        if f := ex2.Check(m.SQL); len(f) != 0 {
            t.Errorf("%03d_%s: %q", m.Version, m.Name, f)
        }
    }
    if f := ex2.Check(ex5.Incident[0].SQL); len(f) != 2 {
        t.Errorf("the incident migration: %q, want two findings", f)
    }
}
```

## 7. Le compte rendu

1. **Quoi** : dimanche à 19 h 05, les paiements Mobile Money ont été
   bloqués, puis toutes les instances ont été redémarrées en boucle, en
   pleine soirée de cotisation.
2. **Cause** : la migration des reçus réécrivait les 30 millions de
   cotisations (valeur par défaut volatile) et construisait un index
   unique en bloquant les écritures.
3. **Aggravation** : les sondes de santé ont fait redémarrer les
   instances, qui attendaient toutes la migration pour démarrer.
4. **Correction** : la même évolution en quatre migrations et une
   recopie par lots, sans paiement plus lent que 112 ms dans la
   répétition.
5. **Prévention** : le vérificateur de migrations bloque la revue de
   code ; les migrations risquées sont répétées sur une copie de la
   taille de la production ; aucune migration le dimanche soir.

## Ce qu'il faut retenir

- Un verrou exclusif sur une table bloque toutes les opérations, même
  celles qui n'ont rien à voir avec le changement.
- La version sûre est plus longue, et c'est sans importance pour les
  membres.
- Un test de latence juge une taille ; un vérificateur juge une forme.
  Il faut les deux.
