# Correction 5.4 — Exercice 1 : huit migrations à relire

> Rappel de l'énoncé : dire si huit migrations bloquent les écritures
> sur une table de 50 millions de lignes ; trois pourquoi ; une
> migration corrigée après coup.

## En bref

- **Trois migrations sur huit sont sûres telles quelles** ; les cinq
  autres ont une forme qui ne bloque pas, ou demandent un expand/contract.
- **Ce qui arrête l'application**, c'est souvent l'attente du verrou,
  pas la durée de la migration.
- **Une migration appliquée ne se modifie pas** : `Up` refuse de
  démarrer, et c'est voulu.

## 1.a — Bloque ou ne bloque pas

| # | Bloque ? | Combien | À la place |
|---|---|---|---|
| 1 | non : le catalogue seul change | quelques ms (plus l'attente du verrou) | telle quelle, avec un `lock_timeout` |
| 2 | non : la constante est notée une fois | quelques ms | telle quelle |
| 3 | **oui** : valeur volatile, la table est réécrite | des dizaines de secondes à plusieurs minutes | colonne sans valeur ; `SET DEFAULT gen_random_uuid()` pour les nouvelles lignes ; recopie par lots |
| 4 | **oui** : les écritures attendent la fin de la lecture de la table | ~25 fois les 858 ms de la leçon, plus de 20 s | `CREATE INDEX CONCURRENTLY`, seule dans sa migration |
| 5 | **oui** : toutes les lignes sont vérifiées sous verrou exclusif | plusieurs secondes | `... NOT VALID`, puis `VALIDATE CONSTRAINT` |
| 6 | **oui** : toutes les lignes sont vérifiées sous verrou exclusif | plusieurs secondes | `CHECK (member_id IS NOT NULL) NOT VALID`, `VALIDATE` ; puis `SET NOT NULL` voit la contrainte validée et ne relit pas la table |
| 7 | pas longtemps, mais **casse** la version de l'application qui lit `paid_at` | — | expand/contract |
| 8 | **oui**, brièvement : `ACCESS EXCLUSIVE`, et la file derrière lui | quelques ms + l'attente | `DROP INDEX CONCURRENTLY` |

Pour la ligne 6 : depuis PostgreSQL 12, `SET NOT NULL` ne relit pas la
table si une contrainte `CHECK (... IS NOT NULL)` validée prouve déjà
qu'aucune valeur ne manque. La contrainte peut ensuite être supprimée.

## 1.b — Trois pourquoi

1. **9 ms qui arrêtent l'application** : l'`ALTER` demande
   `ACCESS EXCLUSIVE`, qui exclut aussi les lectures. Il **attend** que
   le rapport de trois secondes se termine, et pendant ce temps toutes
   les nouvelles requêtes se rangent derrière lui. L'`ALTER` ne travaille
   que 9 ms ; c'est son attente qui arrête tout. `lock_timeout` lui fait
   abandonner son tour au lieu d'attendre.
2. **L'interblocage** : une instance qui attend dans
   `SELECT pg_advisory_lock(...)` est dans une instruction en cours, donc
   dans une transaction avec un instantané. `CREATE INDEX CONCURRENTLY`,
   lancé par l'instance qui tient le verrou, attend la fin de toutes ces
   transactions. Chacune attend l'autre. Avec `pg_try_advisory_lock`,
   l'instruction répond tout de suite et se termine : entre deux essais,
   l'instance qui attend n'a **aucune** transaction ouverte.
3. **Le contract au déploiement suivant** : pendant le déploiement, v1
   tourne encore. Le contract retire `phone`, que v1 lit : la mesure de
   la leçon montre 1 427 erreurs en une seconde dans ce cas. Il faut
   aussi pouvoir revenir à v1 si v2 se comporte mal ; c'est possible
   tant que `phone` existe et que le déclencheur la tient à jour.

## 1.c — La migration corrigée

`Up` relit le registre, calcule l'empreinte du fichier `012_payout.sql`
modifié, la trouve différente de celle notée il y a trois mois, et
**refuse** de démarrer (`ErrChanged`).

C'est le bon comportement. La production a la version d'origine (avec
la faute), alors qu'une base neuve aurait la version corrigée : les deux
schémas divergent, et personne ne le saurait. Le refus rend la
divergence visible avant qu'elle ne fasse de dégâts.

Il fallait remettre `012` dans son état d'origine, et écrire
`027_fix_payout.sql`, qui corrige la faute en production comme dans les
bases neuves.

## Ce qu'il faut retenir

- La forme d'une migration décide si elle bloque ; la taille de la
  table décide combien de temps.
- L'attente du verrou bloque autant que le travail lui-même.
- Le registre et ses empreintes rendent les divergences de schéma
  impossibles à ignorer.

## Sources

- PostgreSQL 17, [ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html),
  `SET NOT NULL` : « if a valid CHECK constraint exists (and is not
  dropped in the same command) which proves no NULL can exist, then the
  table scan is skipped ».
- PostgreSQL 17, [DROP INDEX](https://www.postgresql.org/docs/17/sql-dropindex.html),
  `CONCURRENTLY` : « Drop the index without locking out concurrent
  selects, inserts, updates, and deletes on the index's table. »
