# Correction 5.2 — Exercice 3 : l'unité de travail

> Rappel de l'énoncé : le versement et la pénalité sont écrits par deux
> stores, chacun dans sa transaction. Les mettre dans la même, sans que
> le cas d'usage importe `pgx`.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Deux transactions ne font pas une transaction** : chaque store
  validait sa propre écriture.
- **Le cas d'usage dit ce qui va ensemble**, à travers un port
  `Transactor` ; l'adaptateur PostgreSQL sait comment.
- **Les stores écrivent sur un `DBTX`** qu'on leur donne, sans ouvrir de
  transaction eux-mêmes.

## 1. L'échec

`Payouts.Record` ouvre une transaction, écrit le versement, et la
**valide**. Puis `Penalties.Add` ouvre une autre transaction, qui échoue
sur le `CHECK` et s'annule. Mais il n'annule qu'elle-même : le versement
est déjà validé. Chaque store est atomique, le cas d'usage ne l'est pas.
La frontière de la transaction était au mauvais endroit : dans le store,
alors que c'est le cas d'usage qui sait ce qui forme un seul fait.

## 2. La solution

Le port, côté cas d'usage :

```go
// Stores are the stores of one unit of work: they all write in it.
type Stores struct {
    Payouts   Payouts
    Penalties Penalties
}
```

Le cas d'usage dit ce qui va ensemble :

```go
// PayLate pays the pot less the penalty, and records the penalty: both, or
// neither.
func (s *Service) PayLate(ctx context.Context, tontineID int64, cycle time.Time, memberID, potFCFA, penaltyFCFA int64) error {
    return s.tx.InTx(ctx, func(st Stores) error {
        if err := st.Payouts.Record(ctx, tontineID, cycle, memberID, potFCFA-penaltyFCFA); err != nil {
            return err
        }
        return st.Penalties.Add(ctx, memberID, cycle, penaltyFCFA, "late")
    })
}
```

Côté PostgreSQL, les stores n'ouvrent plus de transaction ; ils écrivent
sur ce qu'on leur donne :

```go
// Payouts records payouts on q: a pool, or a transaction.
type Payouts struct{ q closing.DBTX }
```

L'adaptateur de l'unité de travail ouvre la transaction et construit des
stores qui écrivent dedans :

```go
// Transactor opens one PostgreSQL transaction per unit of work, and gives
// fn stores that write in it.
type Transactor struct{ db *pgxpool.Pool }
```

`NewService(db)` garde sa signature, et les tests passent, y compris sur
un pool d'une connexion :


## 3. Le test sans base de données

Le port rend possible un faux `Transactor`, en mémoire, qui ne garde les
écritures que si `fn` réussit :

```go
// fake is a unit of work in memory: writes are kept only if fn succeeds.
type fake struct{ payouts, penalties []int64 }
```

```go
// The use case is tested without a database: the port is enough.
func TestPayLateKeepsBothOrNeither(t *testing.T) {
    f := &fake{}
    s := service.New(f)
    ctx := context.Background()
    march := time.Date(2026, time.March, 1, 0, 0, 0, 0, time.UTC)
    if err := s.PayLate(ctx, 1, march, 7, 600000, 5000); err != nil {
        t.Fatal(err)
    }
    if err := s.PayLate(ctx, 1, march, 8, 600000, 0); err == nil {
        t.Fatal("a penalty of 0 was accepted")
    }
    if len(f.payouts) != 1 || f.payouts[0] != 595000 || len(f.penalties) != 1 {
        t.Errorf("payouts %v, penalties %v; want [595000], [5000]", f.payouts, f.penalties)
    }
}
```

Ce test vérifie la **règle du cas d'usage** (« les deux, ou aucun ») en
quelques microsecondes. Le test PostgreSQL vérifie, lui, que
l'adaptateur tient la promesse du port. Les deux ensemble sont la
séparation du niveau 3, appliquée à la transaction.

## 4. Le piège à éviter

On voit souvent un `context.Context` qui transporte la transaction
(`ctx = context.WithValue(ctx, txKey, tx)`), et des stores qui la
cherchent dedans. Cela marche, mais la dépendance devient invisible : un
store appelé avec un contexte sans transaction écrit sur le pool, sans
erreur, et l'on retrouve `leaky`. Passer les stores à `fn` rend la
dépendance visible dans les types.

## Ce qu'il faut retenir

- Le cas d'usage décide de la frontière de la transaction ; les stores
  écrivent dedans.
- Le port `Transactor` garde le cas d'usage libre de `pgx`, et testable
  sans base.
- Une transaction cachée dans le contexte est une transaction qu'on peut
  oublier.
