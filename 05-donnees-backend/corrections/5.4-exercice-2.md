# Correction 5.4 — Exercice 2 : le relecteur de migrations

> Rappel de l'énoncé : écrire `Check`, qui signale dans une migration
> les formes qui bloquent sur une grande table.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Normaliser d'abord** : retirer les commentaires, passer en
  majuscules, découper en instructions. Ensuite, chaque règle est une
  ligne.
- **`now()` n'est pas volatile** : il vaut la même chose pour toute la
  transaction, et PostgreSQL le calcule une fois.
- **Un vérificateur de texte ne voit pas tout** : il complète la revue,
  il ne la remplace pas.

## 1. La solution

```go
// Check returns the risks of sql, in the order of the constants above,
// each at most once. sql is the content of one migration file. The lock
// timeout is not its business: package migrate sets it.
func Check(sql string) []Finding {
    found := map[Finding]bool{}
    for _, stmt := range statements(sql) {
        for _, r := range rules {
            if r.match(stmt) {
                found[r.finding] = true
            }
        }
    }
    var out []Finding
    for _, r := range rules {
        if found[r.finding] {
            out = append(out, r.finding)
        }
    }
    return out
}
```

```go
// statements returns the statements of sql, without comments, in upper
// case, with single spaces.
func statements(sql string) []string {
    sql = strings.ToUpper(comment.ReplaceAllString(sql, " "))
    var out []string
    for _, s := range strings.Split(sql, ";") {
        if s = strings.TrimSpace(spaces.ReplaceAllString(s, " ")); s != "" {
            out = append(out, s)
        }
    }
    return out
}
```

Les commentaires sont retirés **avant** tout le reste. Le cas de test
`ALTER TABLE member -- RENAME COLUMN phone later` le vérifie : sans
cela, le mot `RENAME` du commentaire serait signalé. Ce cas a été ajouté
après la campagne des corrections, où la mutation « commentaires lus
comme du SQL » survivait : le seul cas avec un commentaire le plaçait
en tête d'instruction, là où aucune règle ne regarde.

## 2. `now()` et `clock_timestamp()`

PostgreSQL classe ses fonctions : une fonction **volatile**
(`clock_timestamp()`, `random()`, `gen_random_uuid()`) peut donner une
valeur différente à chaque appel ; une fonction **stable** (`now()`)
donne la même valeur pendant toute la transaction. Pour
`ADD COLUMN ... DEFAULT now()`, PostgreSQL calcule la valeur une fois,
et la note dans le catalogue comme une constante : aucune ligne n'est
réécrite. Pour une fonction volatile, chaque ligne doit recevoir sa
propre valeur : la table est réécrite. C'est la mesure de la leçon :
15 ms contre 3,2 s.

## 3. Ce qu'il ne voit pas

- **Une migration de données** : `UPDATE contribution SET ...` sur 50
  millions de lignes, sans `WHERE` ni lot. Aucune règle ne la signale.
- **Une instruction dans du PL/pgSQL** (`DO $$ ... $$`) ou construite
  dynamiquement (`EXECUTE format(...)`).
- **La taille** : `CREATE INDEX` sur une table de dix lignes ne gêne
  personne, et le vérificateur le signale quand même.
- **Une instruction très lente sur une petite table**, à cause d'un
  verrou tenu par un autre programme.

On les rattrape par la revue humaine, avec la grille de la leçon, et par
une répétition de la migration sur une copie de la taille de la
production. Le vérificateur sert à ne pas dépendre de la mémoire du
relecteur pour les cas connus.

## Ce qu'il faut retenir

- Un vérificateur simple attrape les formes connues, à chaque revue,
  sans fatigue.
- Volatile, stable : la classe d'une fonction décide si la table est
  réécrite.
- Ce que le texte ne montre pas (la taille, les données, les autres
  programmes) reste l'affaire de la revue et de la répétition.
