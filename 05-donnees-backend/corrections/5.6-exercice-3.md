# Correction 5.6 — Exercice 3 : plusieurs instances

> Rappel de l'énoncé : un service qui sert les soldes depuis un cache de
> 30 secondes, en plusieurs instances ; il doit montrer un dépôt tout de
> suite sur l'instance qui l'a fait, en moins d'une seconde sur les
> autres, et survivre à la perte de sa connexion d'écoute.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **L'instance qui écrit invalide son cache** avec la version du dépôt.
- **Les autres l'apprennent par `NOTIFY`**, et invalident avec la même
  version.
- **Une instance qui a perdu l'écoute recommence à écouter, puis vide son
  cache** : elle a pu manquer des changements entre les deux.

## 1. La solution

```go
// Start lets the instance follow the changes made by the others, until
// ctx is done. It returns once the instance follows them. When the
// listening connection is lost, the instance listens again, then forgets
// its cache: it may have missed changes in between.
func (s *Service) Start(ctx context.Context) error {
    first := make(chan error, 1)
    go func() {
        started := false
        for ctx.Err() == nil {
            ready, done := make(chan struct{}), make(chan error, 1)
            go func() {
                done <- account.Listen(ctx, s.DB, ready, func(id, version int64) {
                    s.Reader.Cache.Invalidate(id, version)
                })
            }()
            select {
            case <-ready:
                s.Reader.Cache.Clear()
                if !started {
                    started = true
                    first <- nil
                }
                <-done
            case err := <-done:
                if !started {
                    first <- err
                    return
                }
            }
            time.Sleep(50 * time.Millisecond)
        }
    }()
    return <-first
}
```

```go
// Deposit adds amountFCFA to the cash box. This instance forgets the old
// balance at once; the others hear of it through the notification.
func (s *Service) Deposit(ctx context.Context, id, amountFCFA int64) (account.Balance, error) {
    b, err := account.Change(ctx, s.DB, id, amountFCFA)
    if err == nil {
        s.Reader.Cache.Invalidate(id, b.Version)
    }
    return b, err
}
```

## 2. Écouter, puis vider

Si l'instance vidait son cache **avant** de recommencer à écouter, un
dépôt fait entre les deux serait perdu :

| Instant | Instance B | Ailleurs |
|---|---|---|
| 1 | vide son cache | |
| 2 | un membre lit le solde : B le relit en base, version 5, et le range | |
| 3 | | un dépôt : version 6, `NOTIFY` |
| 4 | recommence à écouter : la notification de l'instant 3 est déjà passée | |

B garde la version 5 jusqu'à la fin de sa durée de vie. En vidant
**après** que `LISTEN` est actif, toute écriture validée ensuite sera
entendue, et tout ce qui a été rangé avant est jeté. Le `ready` de
`account.Listen` sert exactement à savoir quand `LISTEN` est actif.

## 3. Les connexions

Chaque instance tient **une connexion d'écoute** en permanence, en plus
de son pool : six instances, six connexions. C'est peu, mais il faut le
compter dans `max_connections`.

Avec PgBouncer en mode *transaction*, `LISTEN` ne marche pas : la
connexion au serveur change à chaque transaction, et l'écoute serait
perdue. La connexion d'écoute doit alors aller directement à PostgreSQL,
ou passer par un PgBouncer en mode *session*. Le reste du trafic peut
continuer par le répartiteur.

## Ce qu'il faut retenir

- L'écrivain invalide son propre cache tout de suite ; les autres
  l'apprennent par la base, au `COMMIT`.
- Après une coupure, on écoute d'abord, puis on oublie : dans l'autre
  ordre, un changement peut passer entre les deux.
- La connexion d'écoute se compte et se route à part.
