# Correction 5.1 — Exercice 2 : la table des pénalités

> Rappel de l'énoncé : écrire les contraintes de `penalty` et la
> traduction de `Penalize` ; dire si `late` et `absent` peuvent coexister
> le même mois ; justifier le `CHECK` du motif.

La solution est dans `ex2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Une contrainte par règle, chacune nommée**, et `NOT NULL` partout.
- **La traduction ne connaît que deux noms** : `penalty_member` et
  `penalty_once`. Les autres violations sont des valeurs invalides.
- **`late` et `absent` coexistent** le même mois : c'est le motif dans
  `UNIQUE (member_id, cycle, reason)` qui le permet.

## 1. La solution

```sql
CREATE TABLE penalty (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    member_id   BIGINT NOT NULL,
    cycle       DATE   NOT NULL,
    reason      TEXT   NOT NULL,
    amount_fcfa BIGINT NOT NULL,
    CONSTRAINT penalty_member FOREIGN KEY (member_id) REFERENCES member (id),
    CONSTRAINT penalty_cycle_is_a_month CHECK (extract(day FROM cycle) = 1),
    CONSTRAINT penalty_reason CHECK (reason IN ('late', 'absent')),
    CONSTRAINT penalty_positive CHECK (amount_fcfa > 0),
    CONSTRAINT penalty_once UNIQUE (member_id, cycle, reason)
);
```

```go
// Penalize records a penalty for reason "late" or "absent".
func (s *Store) Penalize(ctx context.Context, memberID int64, cycle, reason string, amountFCFA int64) error {
    month, err := tontine.ParseCycle(cycle)
    if err != nil {
        return err
    }
    _, err = s.db.Exec(ctx,
        `INSERT INTO penalty (member_id, cycle, reason, amount_fcfa) VALUES ($1, $2, $3, $4)`,
        memberID, month, reason, amountFCFA)
    return translate(err)
}
```

```go
var rules = map[string]error{
    "penalty_member": tontine.ErrUnknownMember,
    "penalty_once":   ErrAlreadyPenalized,
}
```

```go
func translate(err error) error {
    var pgErr *pgconn.PgError
    if !errors.As(err, &pgErr) {
        return err
    }
    if rule, ok := rules[pgErr.ConstraintName]; ok {
        return fmt.Errorf("%w (%s)", rule, pgErr.ConstraintName)
    }
    switch pgErr.Code {
    case "23502", "23514":
        return fmt.Errorf("%w (%s)", tontine.ErrInvalid, pgErr.ConstraintName)
    }
    return err
}
```

Deux remarques sur la traduction :

- le code `23503` (clé étrangère) n'est pas dans le `switch`, parce que la
  seule clé étrangère de la table a un nom, et donc une erreur précise ;
- une violation qu'on ne connaît pas remonte **telle quelle**. La
  transformer en `ErrInvalid` cacherait une erreur de programmation
  derrière un « valeur invalide ».

## 2. `late` et `absent` le même mois

Oui, et c'est voulu : un membre peut payer en retard **et** manquer la
réunion. La contrainte `penalty_once` porte sur
`(member_id, cycle, reason)`. Si elle portait sur `(member_id, cycle)`,
la deuxième pénalité serait refusée. La campagne contient cette mutation
(« un seul motif par mois ») : elle est tuée par le test qui enregistre
`absent` en mars alors que `late` y est déjà.

## 3. `CHECK` ou table des motifs

Deux motifs, fixés par le règlement de la tontine, qui changent quand le
règlement change : un `CHECK` suffit, et il se lit dans le schéma.

Une table `penalty_reason (code PRIMARY KEY, label, amount_fcfa)` avec
une clé étrangère devient meilleure quand :

- les motifs changent **sans** nouvelle version du code (le bureau de
  la tontine les gère lui-même) ;
- chaque motif porte des données (un libellé à afficher, un montant par
  défaut) ;
- chaque tontine a ses propres motifs : la clé devient alors
  `(tontine_id, code)`.

## 4. La campagne

Les mutations de l'exercice 2, tirées de la campagne sur les exercices 2
et 5 :

```text
pénalité d'un membre inconnu                 tuee
pénalité au 15 du mois                       tuee
motif quelconque                             tuee
pénalité de 0 FCFA                           tuee
deux pénalités identiques                    tuee
un seul motif par mois                       tuee
motif absent (NULL)                          tuee
montant absent (NULL)                        tuee
double pénalité mal traduite                 tuee
membre inconnu mal traduit                   tuee
CHECK non traduit                            tuee
```

Les deux mutations `NULL` sont tuées dès le premier passage : les tests
fournis insèrent une ligne sans chacune des colonnes. C'est la leçon de
la campagne 5.1 appliquée d'avance.

## Ce qu'il faut retenir

1. Chaque règle a un nom, et chaque nom qui compte pour le métier a son
   erreur.
2. Une violation inconnue remonte telle quelle.
3. Le choix des colonnes d'une contrainte `UNIQUE` est une décision
   métier : il dit ce qui peut coexister.
