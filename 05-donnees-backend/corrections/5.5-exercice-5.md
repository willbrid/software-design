# Correction 5.5 — Exercice 5 : le relevé du 31 décembre

> Rappel de l'énoncé : le relevé annuel envoie une requête par membre et
> par mois ; à 20 ms de la base, il dépasse le délai du répartiteur de
> charge, et les trésorières réessaient. Réécrire, expliquer, et rédiger
> le compte rendu.

La réécriture est dans `ex5` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **301 requêtes** pour 25 membres : 6,6 s à 20 ms de la base, au-delà
  des 5 s du répartiteur. Le relevé ne pouvait **jamais** s'afficher.
- **Une requête** suffit : 53 ms à la même distance.
- **Le test du plan a d'abord échoué sur la bonne requête** : sur un jeu
  de données trop petit, lire toute la table était le bon choix. Le test
  doit ressembler à la production.

## 1. Le relevé qui ne s'affiche jamais

1 + 25 × 12 = **301 requêtes**. Le module le mesure, avec le proxy de la
leçon à 20 ms :

```text
$ go run ./cmd/ex5
Slow      20 ms away: 301 queries, 6.575s, 25 members
Statement 20 ms away:   1 queries, 53ms, 25 members
```

6,6 s, plus que les 5 s du répartiteur de charge. Celui-ci coupe la
requête HTTP, mais le serveur, lui, continue à envoyer ses 301 requêtes
jusqu'au bout (sauf si le contexte de la requête est annulé et transmis
à pgx). Le relevé n'arrive **jamais** à la trésorière, quelle que soit
la charge : même seule, elle n'a aucune chance.

## 2. Le pool

Chaque relevé tient une connexion pendant 6,6 s. Avec un pool de 32
connexions, 32 relevés en cours suffisent à le remplir. Les trésorières
réessaient, ce qui ajoute d'autres relevés. Toutes les autres requêtes
de l'application (les paiements, les connexions) attendent alors une
connexion libre : **l'application entière** devient lente, pas seulement
le relevé. Et puisque chaque relevé est coupé au bout de 5 s, tout ce
travail est perdu.

## 3. La réécriture

```go
// Statement returns what Slow returns, in one query. The year becomes an
// interval on paid_at, so that the index on (member_id, paid_at) serves it;
// the database sums by member and by month.
func Statement(ctx context.Context, db *pgxpool.Pool, tontineID int64, year int) ([]Row, error) {
    from := time.Date(year, time.January, 1, 0, 0, 0, 0, time.UTC)
    rows, err := db.Query(ctx, `
        SELECT m.id, m.name, extract(month FROM c.paid_at AT TIME ZONE 'UTC')::int, sum(c.amount_fcfa)
        FROM member m
        LEFT JOIN contribution c ON c.member_id = m.id AND c.paid_at >= $2 AND c.paid_at < $3
        WHERE m.tontine_id = $1
        GROUP BY 1, 2, 3
        ORDER BY 1`, tontineID, from, from.AddDate(1, 0, 0))
    if err != nil {
        return nil, err
    }
    defer rows.Close()
    var out []Row
    for rows.Next() {
        var id int64
        var name string
        var month *int
        var sum *int64
        if err := rows.Scan(&id, &name, &month, &sum); err != nil {
            return nil, err
        }
        if len(out) == 0 || out[len(out)-1].MemberID != id {
            out = append(out, Row{MemberID: id, Name: name})
        }
        if month != nil {
            r := &out[len(out)-1]
            r.Months[*month-1] = *sum
            r.TotalFCFA += *sum
        }
    }
    return out, rows.Err()
}
```

```text
--- PASS: TestTheStatementIsTheSlowOne (1.23s)
--- PASS: TestTheStatementSendsOneQuery (0.92s)
--- PASS: TestTheStatementDoesNotScanTheTable (7.71s)
ok      example/corr55/ex5      9.861s
```

- **une requête**, qui groupe par membre et par mois ;
- **un intervalle** sur `paid_at` (du 1er janvier au 1er janvier
  suivant, borne haute exclue), dans le `ON` de la jointure externe ;
- **`LEFT JOIN`** : le membre qui n'a rien payé apparaît avec des zéros,
  comme dans `Slow`.

### Le test du plan, et le jeu de données

La première version du test remplissait 40 tontines. Sur ces données,
la bonne requête lisait **toute** la table :

```text

        GroupAggregate  (cost=10744.36..11044.30 rows=9998 width=54)

                      ->  Hash  (cost=8.59..8.59 rows=25 width=18)

```

Le planificateur avait raison : la tontine représentait 1/40 de la
table, soit 10 000 lignes réparties partout. Aller les chercher une à
une par l'index coûtait plus que lire toute la table d'un coup. Une
vraie base compte des centaines de tontines : le test en remplit
maintenant 400, la tontine ne pèse plus que 1/400 de la table, et le
plan passe par l'index. Le test d'un plan dépend des **proportions**
des données. On le construit avec des proportions réalistes.

## 4. `extract(year FROM paid_at ...)`

C'est une fonction sur la colonne (section 5 de la leçon) : un index
sur `paid_at` ne peut pas servir la condition. Ici, la condition qui
mène à l'index est `member_id = $1`, et l'année n'est qu'un filtre sur
les quelque 200 cotisations du membre. Le coût est donc faible. Mais
une requête qui chercherait « toutes les cotisations de 2026 » avec
`extract` lirait toute la table. On écrit un intervalle par habitude :
il marche dans les deux cas.

## 6. Le compte rendu

1. **Quoi** : le 31 décembre, le relevé annuel n'a jamais pu s'afficher,
   et l'application entière a ralenti pendant la soirée.
2. **Cause** : le relevé envoyait 301 requêtes (une par membre et par
   mois). À 20 ms de la base, il durait 6,6 s, au-delà du délai de 5 s
   du répartiteur ; les essais répétés ont rempli le pool de connexions.
3. **Détection** : par les trésorières, le soir même. Les tests locaux
   affichaient le relevé en moins de 100 ms.
4. **Correction** : une seule requête, qui groupe par membre et par mois
   sur un intervalle de dates : 53 ms à 20 ms de la base.
5. **Prévention** : chaque page a un test qui compte ses requêtes ; un
   test de plan sur des données aux proportions de la production ; un
   proxy de latence dans l'environnement de recette.

## Ce qu'il faut retenir

- Le N+1 multiplié par une distance réseau peut rendre une page
  impossible, pas seulement lente.
- Une requête lente tient une connexion : elle ralentit toute
  l'application, pas seulement sa page.
- Un test de plan se construit sur des données aux proportions de la
  production.
