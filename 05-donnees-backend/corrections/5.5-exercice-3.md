# Correction 5.5 — Exercice 3 : le journal de la caisse

> Rappel de l'énoncé : remplacer la pagination par `OFFSET` du journal
> de la caisse par une pagination par clé, avec un curseur opaque.

La solution est dans `ex3` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Avec `OFFSET`, un paiement décale les pages** : la trésorière revoit
  des lignes déjà vues, ou en saute.
- **Avec `OFFSET`, la page 400 relit les 399 pages qui précèdent** :
  8 557 blocs pour 50 lignes.
- **Le curseur contient la clé de la dernière ligne**, encodée pour que
  l'application ne la fabrique pas.

## 1. Le décalage

Le curseur de la page 2 dit « saute 10 lignes ». Entre les deux
appels, cinq paiements arrivent, plus récents que tout : ils prennent
les cinq premières places. Sauter 10 lignes ne mène plus à la fin de la
page 1, mais cinq lignes plus tôt : la trésorière revoit **cinq
paiements déjà vus**. Dans l'autre sens (une ligne supprimée), elle en
**sauterait**. Le test le voit : la page 2 commence par l'id 3761 au
lieu de 3561.

## 2. Les 8 557 blocs

`OFFSET 19950` oblige la base à produire, puis jeter, les 19 950 lignes
qui précèdent, en lisant l'index **et** la table pour chacune. La page
400 coûte 400 fois la page 1, et ce coût grandit avec l'ancienneté de
la caisse.

## 3. La solution

```go
// Page returns size lines of the tontine's journal, newest first, from
// cursor ("" for the first page), and the cursor of the next page ("" when
// there is none). The application treats the cursor as an opaque string.
func Page(ctx context.Context, db *pgxpool.Pool, tontineID int64, size int, cursor string) ([]Line, string, error) {
    var rows pgx.Rows
    var err error
    if cursor == "" {
        rows, err = db.Query(ctx, `
            SELECT id, member_id, amount_fcfa, paid_at FROM journal
            WHERE tontine_id = $1
            ORDER BY paid_at DESC, id DESC
            LIMIT $2`, tontineID, size)
    } else {
        k, kerr := decode(cursor)
        if kerr != nil {
            return nil, "", kerr
        }
        rows, err = db.Query(ctx, `
            SELECT id, member_id, amount_fcfa, paid_at FROM journal
            WHERE tontine_id = $1 AND (paid_at, id) < ($3, $4)
            ORDER BY paid_at DESC, id DESC
            LIMIT $2`, tontineID, size, k.PaidAt, k.ID)
    }
    if err != nil {
        return nil, "", err
    }
    lines, err := pgx.CollectRows(rows, pgx.RowToStructByPos[Line])
    if err != nil || len(lines) < size {
        return lines, "", err
    }
    last := lines[len(lines)-1]
    return lines, encode(key{last.PaidAt, last.ID}), nil
}
```

```go
// key is the place of a line in the journal: its date, and its id for the
// lines of the same date.
type key struct {
    PaidAt time.Time `json:"t"`
    ID     int64     `json:"i"`
}
```

```go
// encode makes the cursor opaque: the application must not build one, nor
// rely on what is inside.
func encode(k key) string {
    b, _ := json.Marshal(k)
    return base64.RawURLEncoding.EncodeToString(b)
}
```

- La page suivante commence **après la dernière ligne vue** : un
  paiement arrivé entre-temps se place avant, et ne décale rien ;
- la condition `(paid_at, id) < ($3, $4)` suit l'index
  `(tontine_id, paid_at DESC, id DESC)` : la base descend directement à
  la bonne place ;
- le curseur est du JSON encodé en base64 : l'application le renvoie
  sans le lire. Si demain la clé change (une colonne de plus), seul le
  serveur change.

La campagne des corrections a trouvé une faiblesse : un curseur `e30`
(`{}` en base64) se décodait sans erreur, avec une clé vide, et la page
renvoyait une liste vide au lieu de refuser. La vérification
`k.ID <= 0` le refuse, et le test des curseurs invalides essaie
maintenant aussi `e30`.

## 4. Plus de « page 37 »

Pour un journal de caisse, ce n'est pas une perte : on le lit en faisant
défiler, du plus récent au plus ancien, et on cherche une date, pas un
numéro de page. Pour aller « au 15 mars », on donne une date comme point
de départ : c'est une clé comme une autre.

Ce serait une perte pour un écran qui affiche « page 37 sur 120 » et
permet de sauter à une page, comme une liste de résultats triée par un
critère sans rapport avec le temps. Là, on garde `OFFSET` pour les
premières pages, et on limite la profondeur : personne ne lit la page
3 000 d'une recherche.

## Ce qu'il faut retenir

- `OFFSET` décale les pages quand les données changent, et relit tout ce
  qui précède.
- La clé de la dernière ligne vue donne des pages stables, au même coût
  partout.
- Un curseur opaque laisse le serveur libre de changer sa clé.
