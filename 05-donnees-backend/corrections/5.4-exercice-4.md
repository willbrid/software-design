# Correction 5.4 — Exercice 4 : plusieurs téléphones par membre

> Rappel de l'énoncé : passer de `member.phone` (un numéro) à plusieurs
> numéros par membre, dont un principal, avec trois lecteurs (v1, SMS,
> rapprochement), sans coupure et avec un retour arrière possible.

## En bref

- **Une table `member_phone`**, et un index unique partiel pour dire
  « un seul principal par membre ».
- **Quatre déploiements** : expand, bascule de l'écriture, bascule des
  lecteurs, contract.
- **Le point de non-retour** est le contract : avant lui, on peut
  toujours revenir à v1.

## 1. La nouvelle table

```sql
CREATE TABLE member_phone (
    member_id BIGINT  NOT NULL REFERENCES member (id),
    phone     TEXT    NOT NULL,
    principal BOOLEAN NOT NULL DEFAULT false,
    CONSTRAINT member_phone_format CHECK (phone ~ '^\+237[0-9]{9}$'),
    PRIMARY KEY (member_id, phone)
);

-- one principal number per member
CREATE UNIQUE INDEX member_phone_one_principal
    ON member_phone (member_id) WHERE principal;
```

L'index unique **partiel** ne porte que sur les lignes où `principal`
est vrai : deux numéros secondaires sont permis, deux principaux non.
La règle « au moins un principal » porte sur plusieurs lignes : elle
reste dans le code, dans la transaction qui ajoute ou retire un numéro,
avec un verrou sur la ligne du membre (leçon 5.3).

## 2. Le plan

| Étape | Schéma | Application | Lecteurs |
|---|---|---|---|
| **D1 : expand** | crée `member_phone` ; un déclencheur sur `member` recopie `phone` comme numéro principal à chaque écriture de v1 ; recopie par lots des membres existants | v1 (inchangée) | inchangés |
| **D2 : v2 écrit les deux** | — | v2 écrit dans `member_phone`, et met aussi à jour `member.phone` avec le principal ; v1 et v2 tournent ensemble pendant le déploiement | inchangés, ils lisent `member.phone`, toujours juste |
| **D3 : bascule des lecteurs** | — | v2 lit `member_phone` | l'envoyeur de SMS et le rapprochement lisent `member_phone` (le principal, ou tous les numéros pour le rapprochement) |
| **D4 : contract** | retire le déclencheur, puis la colonne `member.phone` | v3 n'écrit plus `member.phone` | — |

À chaque étape, ce qui tourne lit une donnée juste :

- après D1, `member_phone` est tenue à jour par le déclencheur, et la
  recopie remplit le passé ;
- pendant D2, v1 écrit `phone` (le déclencheur recopie) et v2 écrit les
  deux : les deux représentations restent égales ;
- D3 ne change que des lectures : on peut le faire lecteur par lecteur,
  et revenir en arrière pour chacun.

Le rapprochement Mobile Money gagne à basculer en dernier, et à lire
**tous** les numéros : un membre payé sur son numéro MTN doit être
retrouvé, même si son principal est Orange.

## 3. Le retour arrière

| Après | Revenir en arrière ? |
|---|---|
| D1 | oui : v1 n'a rien vu ; on peut même supprimer `member_phone` |
| D2 | oui : on redéploie v1 ; `member.phone` est juste (v2 l'écrivait), le déclencheur reprend |
| D3 | oui : on rebascule les lecteurs vers `member.phone`, toujours tenu à jour par v2 |
| D4 | **non** : `member.phone` n'existe plus. Revenir demanderait une nouvelle migration (recréer la colonne et la remplir depuis le principal) |

C'est pour cela que D4 attend : une ou deux semaines de D3 sans
incident, et l'accord de ceux qui lisent la base sans passer par
l'application (le rapprochement, un export comptable).

## Ce qu'il faut retenir

- Un index unique partiel exprime « un seul ... parmi ceux qui ... ».
- Un changement de forme se fait en déploiements dont chacun garde les
  deux représentations justes.
- Le contract est le point de non-retour : on le retarde, et on le
  prévient.
