# Correction 5.1 — Exercice 5 : les cagnottes de décembre

> Rappel de l'énoncé : une année de production sur le schéma sans règle ;
> des cagnottes versées deux ou trois fois quand l'opérateur répondait
> lentement. Expliquer, trouver, réparer, chiffrer, prévenir les membres,
> et rédiger le compte rendu.

La réparation est dans `ex5` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **La cause** : vérifier puis écrire, avec un nouvel essai lancé pendant
  que le premier était encore en cours. Décembre est le mois où
  l'opérateur était lent.
- **34 versements en trop, 20 400 000 FCFA, 30 membres**, dont 18
  versements en décembre.
- **La réparation tient en une transaction** : verrouiller la table,
  déplacer les doublons, ajouter la contrainte. Sans le verrou, un
  versement en cours la fait échouer.

## 1. L'incident

C'est la section 3 de la leçon, en production. Le premier essai vérifie
qu'aucun versement n'existe, puis appelle l'opérateur et attend. Au bout
de cinq secondes, l'application relance le versement : le second essai
vérifie à son tour, et ne voit toujours rien, puisque le premier n'a pas
encore écrit. Les deux écrivent. L'intervalle entre la vérification et
l'écriture, qui dure moins d'une milliseconde dans la mesure de la leçon,
dure ici **le temps de réponse de l'opérateur**.

Décembre est le mois des fêtes : beaucoup de transferts, un opérateur
lent, donc beaucoup de nouveaux essais. Le reste de l'année, les
doublons sont rares, mais ils existent.

## 2. Trouver les doublons

```go
// Duplicates lists the cycles paid more than once, with their beneficiaries.
const Duplicates = `
    SELECT tontine_id, to_char(cycle, 'YYYY-MM') AS cycle, count(*) AS payouts,
           string_agg(DISTINCT member_id::text, ', ') AS members
    FROM payout
    GROUP BY tontine_id, cycle
    HAVING count(*) > 1
    ORDER BY cycle, tontine_id`
```

## 3. Le premier réflexe, et pourquoi il échoue

`ALTER TABLE … ADD CONSTRAINT … UNIQUE` construit un index unique sur les
lignes **existantes**. Les doublons sont là, l'index ne peut pas être
construit, la commande échoue (`23505`), et rien ne change.

Supprimer les doublons à la main, puis ajouter la contrainte, a deux
défauts :

- **perdre la trace** : chaque doublon est un versement réel, de l'argent
  qui est parti. Il faut le garder pour savoir qui doit rembourser quoi ;
- **la fenêtre** : entre la suppression et l'ajout, l'application continue
  de verser. Un nouveau doublon peut arriver, et l'ajout échoue encore.

## 4. La réparation

```go
// Repair keeps the first payout of each cycle, moves the others to a new
// table payout_refund, and adds the constraint payout_once_per_cycle.
// Running it a second time changes nothing and reports zero.
func Repair(ctx context.Context, db *pgxpool.Pool) (Report, error) {
    var r Report
    err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
        // No payout may be written while the table is repaired.
        if _, err := tx.Exec(ctx, `LOCK TABLE payout IN EXCLUSIVE MODE`); err != nil {
            return err
        }
        var done bool
        if err := tx.QueryRow(ctx, `SELECT EXISTS (SELECT 1 FROM pg_constraint
            WHERE conrelid = 'payout'::regclass AND conname = 'payout_once_per_cycle')`).Scan(&done); err != nil {
            return err
        }
        if done {
            return nil
        }
        if _, err := tx.Exec(ctx, `
            CREATE TABLE payout_refund (LIKE payout);
            WITH ranked AS (
                SELECT id, row_number() OVER (PARTITION BY tontine_id, cycle ORDER BY paid_at, id) AS n
                FROM payout
            ), moved AS (
                DELETE FROM payout p USING ranked r WHERE p.id = r.id AND r.n > 1
                RETURNING p.*
            )
            INSERT INTO payout_refund SELECT * FROM moved;
            ALTER TABLE payout ADD CONSTRAINT payout_once_per_cycle UNIQUE (tontine_id, cycle);`); err != nil {
            return err
        }
        return tx.QueryRow(ctx, `SELECT count(*), coalesce(sum(amount_fcfa), 0), count(DISTINCT member_id)
            FROM payout_refund`).Scan(&r.Duplicates, &r.AmountFCFA, &r.Members)
    })
    return r, err
}
```

Les choix, un par un :

- **le premier versement est gardé** (`ORDER BY paid_at, id`) : c'est
  celui que le membre attendait ; les suivants sont les doublons ;
- **les doublons sont déplacés**, pas effacés : `payout_refund` est la
  liste de travail du trésorier ;
- **tout est dans une transaction** : si l'ajout de la contrainte échoue,
  rien n'a été déplacé. La leçon 5.2 détaille ce « tout ou rien » ;
- **la réparation est rejouable** : si la contrainte existe déjà, elle ne
  fait rien. Un script de réparation est souvent relancé, par erreur ou
  par prudence ;
- **le verrou** : `LOCK TABLE payout IN EXCLUSIVE MODE` laisse lire la
  table, mais fait attendre toute écriture jusqu'à la fin de la
  réparation.

Le dernier test montre pourquoi le verrou compte. Un versement de
l'application est en cours, pas encore validé, quand la réparation
démarre. Sans le verrou, la réparation déplace les doublons qu'elle voit,
puis l'ajout de la contrainte attend le versement en cours, qui se
valide… et apporte un nouveau doublon :

```text
$ go test -count=1 -run WaitsFor ./ex5/   # without LOCK TABLE
--- FAIL: TestRepairWaitsForAPayoutInProgress (0.12s)
    incident_test.go:157: repair: ERROR: could not create unique index "payout_once_per_cycle" (SQLSTATE 23505)
FAIL
FAIL    example/corr51/ex5      0.123s
FAIL
```

Avec le verrou, la réparation attend le versement **avant** de chercher
les doublons, le voit, et le déplace avec les autres. Ce résultat est
déterministe : le test attend que la réparation soit bloquée
(`pg_locks`) avant de valider le versement.

## Le compte rendu, en cinq lignes

1. **Quoi** : de novembre 2025 à octobre 2026, 34 cagnottes ont été
   versées en trop à 30 membres, pour 20 400 000 FCFA, dont 18 en
   décembre.
2. **Pourquoi** : le versement vérifiait avant d'écrire, et l'application
   relançait un versement au bout de cinq secondes quand l'opérateur
   tardait ; les deux essais passaient la vérification.
3. **Pourquoi personne ne l'a vu** : le schéma n'avait aucune contrainte
   d'unicité, et les tests n'envoyaient jamais deux versements en même
   temps.
4. **Correction** : la contrainte `payout_once_per_cycle` est en place ;
   les doublons sont dans `payout_refund` ; un test de concurrence
   protège la règle.
5. **Ce qui reste ouvert** : le remboursement des 30 membres ; un nouvel
   essai qui ne crée pas un nouveau versement (idempotence, niveau 6) ;
   les autres unicités du schéma, à vérifier une par une.

## Ce qu'il faut retenir

1. Une contrainte ajoutée tard rencontre les données déjà fausses : la
   réparation déplace, verrouille, et tient en une transaction.
2. Un script de réparation est rejouable.
3. Un test de concurrence déterministe attend l'état voulu (`pg_locks`)
   au lieu de dormir au hasard.
