# Correction 5.1 — Exercice 4 : le schéma de la mutuelle

> Rappel de l'énoncé : écrire les quatre tables de la mutuelle avec toutes
> les règles qui peuvent y vivre, et dire où vivent les autres.

Le schéma est dans `ex4/mutuelle.sql` du module de correction ; un test
l'applique sur PostgreSQL et vérifie ses contraintes.

## En bref

- **Sept règles sur neuf vivent dans le schéma**, dont le plafond de
  70 %, grâce à une clé étrangère composée qui transporte le montant de
  la facture.
- **Le plafond annuel et le retard de cotisation** portent sur plusieurs
  lignes : ils vivent dans une transaction.
- La confidentialité (leçon 4.6) se règle aussi dans la base, par les
  droits.

## 1. Le schéma

```sql
-- The mutual health fund of the neighbourhood (lesson 4.6, exercise 4).
CREATE TABLE family (
    id    BIGINT PRIMARY KEY,
    name  TEXT   NOT NULL CHECK (name <> ''),
    phone TEXT   NOT NULL CHECK (phone ~ '^\+237[0-9]{9}$')
);

CREATE TABLE person (
    id        BIGINT PRIMARY KEY,
    family_id BIGINT NOT NULL REFERENCES family (id),
    name      TEXT   NOT NULL CHECK (name <> '')
);

CREATE TABLE invoice (
    id          BIGINT PRIMARY KEY,
    person_id   BIGINT NOT NULL REFERENCES person (id),
    provider    TEXT   NOT NULL CHECK (provider <> ''),
    number      TEXT   NOT NULL CHECK (number <> ''),
    issued_on   DATE   NOT NULL,
    amount_fcfa BIGINT NOT NULL CHECK (amount_fcfa > 0),
    -- the same invoice of a clinic is never brought twice
    CONSTRAINT invoice_once UNIQUE (provider, number),
    -- lets a reimbursement read the amount of its invoice
    CONSTRAINT invoice_amount UNIQUE (id, amount_fcfa)
);

CREATE TABLE reimbursement (
    invoice_id     BIGINT NOT NULL,
    invoice_fcfa   BIGINT NOT NULL,
    amount_fcfa    BIGINT NOT NULL CHECK (amount_fcfa > 0),
    approved_by    TEXT,
    CONSTRAINT reimbursement_of_invoice FOREIGN KEY (invoice_id, invoice_fcfa)
        REFERENCES invoice (id, amount_fcfa),
    CONSTRAINT reimbursement_once UNIQUE (invoice_id),
    CONSTRAINT reimbursement_at_most_70_percent CHECK (amount_fcfa * 10 <= invoice_fcfa * 7),
    CONSTRAINT reimbursement_committee CHECK (amount_fcfa <= 20000 OR approved_by IS NOT NULL)
);
```

La règle 6 est la plus intéressante. Un `CHECK` ne lit pas la table
`invoice`. Mais le remboursement **recopie** le montant de la facture
dans `invoice_fcfa`, et la clé étrangère composée
`(invoice_id, invoice_fcfa)` vérifie que la copie est exacte : on ne
peut pas écrire un autre montant que celui de la facture. Le `CHECK`
compare ensuite deux colonnes de la même ligne. Le calcul
`amount_fcfa * 10 <= invoice_fcfa * 7` évite la division et ses
arrondis.

Le test, avec du SQL brut :

```go
func TestTheSchemaHoldsTheRulesOfARow(t *testing.T) {
    db := pg.ForTest(t, Schema)
    ctx := context.Background()
    _, err := db.Exec(ctx, `
        INSERT INTO family VALUES (1, 'Famille Ebai', '+237690000002');
        INSERT INTO person VALUES (1, 1, 'Ebai'), (2, 1, 'Ebai junior');
        INSERT INTO invoice VALUES (1, 2, 'Clinique de la gare', 'F-1042', '2026-03-12', 40000),
                                   (2, 2, 'Clinique de la gare', 'F-1043', '2026-03-20', 10000);
        INSERT INTO reimbursement VALUES (1, 40000, 28000, 'comité du 15 mars');
        INSERT INTO reimbursement (invoice_id, invoice_fcfa, amount_fcfa) VALUES (2, 10000, 7000);`)
    if err != nil {
        t.Fatal(err)
    }
    for _, c := range []struct{ sql, constraint string }{
        {`INSERT INTO invoice VALUES (3, 2, 'Clinique de la gare', 'F-1042', '2026-03-12', 40000)`, "invoice_once"},
        {`INSERT INTO reimbursement VALUES (1, 40000, 1000, 'comité')`, "reimbursement_once"},
        {`INSERT INTO invoice VALUES (3, 1, 'Pharmacie', 'P-7', '2026-04-02', 30000);
          INSERT INTO reimbursement VALUES (3, 30000, 21001, 'comité')`, "reimbursement_at_most_70_percent"},
        {`INSERT INTO invoice VALUES (4, 1, 'Pharmacie', 'P-8', '2026-04-02', 30000);
          INSERT INTO reimbursement (invoice_id, invoice_fcfa, amount_fcfa) VALUES (4, 30000, 21000)`, "reimbursement_committee"},
        {`INSERT INTO invoice VALUES (5, 1, 'Pharmacie', 'P-9', '2026-04-02', 30000);
          INSERT INTO reimbursement VALUES (5, 300000, 21000, 'comité')`, "reimbursement_of_invoice"},
    } {
        _, err := db.Exec(ctx, c.sql)
        var pgErr *pgconn.PgError
        if !errors.As(err, &pgErr) || pgErr.ConstraintName != c.constraint {
            t.Errorf("%s\n    got %v, want a violation of %s", c.sql, err, c.constraint)
        }
    }
}
```

La dernière ligne du test essaie de tricher : un remboursement qui
prétend que la facture vaut 300 000 au lieu de 30 000. La clé composée
le refuse.

## 2. Les règles qui restent dehors

| Règle | Pourquoi dehors | Où |
|---|---|---|
| 8. 50 000 FCFA par personne et par an | une somme sur plusieurs remboursements | une transaction qui lit la somme de l'année et écrit le remboursement sans qu'une autre écriture se glisse entre les deux (leçon 5.3). Une autre forme : une table `allowance (person_id, year, used_fcfa)` avec `CHECK (used_fcfa <= 50000)`, mise à jour par `UPDATE … SET used_fcfa = used_fcfa + $1` dans la même transaction que le remboursement : la base refuse alors le dépassement, même avec deux requêtes simultanées |
| 9. famille en retard de deux mois | dépend de l'historique des cotisations et de la date du jour | une transaction qui lit les cotisations de la famille ; la règle « deux mois » reste dans le Go, où elle se teste avec une horloge fixée |

## 3. La confidentialité

La leçon 4.6 a fait de la confidentialité la qualité la plus importante
de la mutuelle. Dans la base, cela se traduit par un **schéma PostgreSQL
séparé** (`mutuelle`) et un rôle de connexion propre à l'application de
la mutuelle. Le rôle de l'application de la tontine n'a aucun droit
dessus (`GRANT` seulement au rôle de la mutuelle). Une erreur dans le
code de la tontine ne peut alors pas lire une facture.

## Ce qu'il faut retenir

1. Une clé étrangère composée peut transporter une valeur d'une autre
   table, et rendre possible un `CHECK` qui la compare.
2. Une règle sur une somme de lignes vit dans une transaction, ou dans
   un compteur protégé par un `CHECK`.
3. La confidentialité se règle aussi par les droits de la base.
