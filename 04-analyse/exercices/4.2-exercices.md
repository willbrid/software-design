# Exercices 4.2 — Les exigences de qualité

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets `load`, `situation`, `upstream` et
`pin` de la [leçon 4.2](../cours/4.2-exigences-de-qualite.md), recopiés tels
quels dans le module des exercices. Tout le code ci-dessous compile et
passe `go vet` ; la tontine, l'opérateur et l'incident sont **fictifs**.

## Exercice 1 — Compréhension : lire des chiffres

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Vingt mesures

Le programme `ex1/predict` affiche le résumé de vingt latences, puis des
dix-neuf premières :

```go
func main() {
    ms := []int{48, 52, 55, 51, 47, 60, 58, 49, 53, 50, 62, 54, 57, 46, 59, 61, 45, 56, 52, 1900}
    lat := make([]time.Duration, len(ms))
    for i, m := range ms {
        lat[i] = time.Duration(m) * time.Millisecond
    }
    fmt.Println(load.Summary(lat))
    fmt.Println(load.Summary(lat[:19]))
}
```

**Prévois** les deux lignes (moyenne, p50, p90, p99, max), en utilisant la
définition de `load.Percentile` (rang le plus proche, arrondi vers le
haut). Puis réponds : une seule mesure lente sur vingt change-t-elle le
p99 ? la moyenne ? Que faudrait-il pour qu'un p99 « résiste » à une
mesure isolée ?

### 1.b — Ce qui manque

Pour chaque exigence, dis quelle(s) partie(s) du scénario manque(nt)
(source, stimulus, artefact, environnement, réponse, mesure), et réécris
la plus mauvaise :

1. « Le temps de réponse doit être inférieur à 200 ms. »
2. « L'application doit être disponible 24 h/24, 7 j/7. »
3. « 95 % des versements de cagnotte sont faits en moins de 2 minutes
   après la validation de la trésorière. »
4. « Le système doit supporter beaucoup d'utilisateurs. »
5. « Un membre qui perd son téléphone peut bloquer son compte. »

### 1.c — Le rapport de test

Une équipe joint ce rapport à sa demande de mise en production :

```text
Outil : 8 clients virtuels, chacun envoie sa requête suivante dès la réponse.
Durée : 10 minutes. Requêtes : 12 000.
Latence : moyenne 61 ms, p99 95 ms, max 3,1 s.
Conclusion : l'exigence « 99 % sous 350 ms » est tenue.
```

Qu'est-ce que le maximum à 3,1 s te dit ? Combien de requêtes de vrais
membres, arrivant au même rythme moyen, auraient attendu pendant ce
moment ? La conclusion est-elle justifiée ?


## Exercice 3 — Refactoring : un client qui réessaie

*Niveau 3. Garder ce que fait le client, et tenir le scénario.*

La semaine où l'opérateur a eu des problèmes, quelqu'un a écrit ce
client :

```go
// Client retries three times, with two seconds per try and half a second
// between tries, "because the operator is sometimes slow".
type Client struct{ API API }
```

Il passe ses tests (`ex3/balance/balance_test.go`). Contre un opérateur
dont un appel sur vingt ne répond jamais, à 50 demandes par seconde en
boucle ouverte (`go run ./ex3/cmd/measure`) :

```text
retry client   500 requests  mean  222ms  p50   53ms  p90   79ms  p99 2.571s  max 5.028s  errors 0
```

Le scénario de la leçon demande 99 % des réponses en moins de 350 ms.

1. Calcule le **pire cas** de ce client, en lisant son code : combien de
   temps un appel peut-il prendre ? Retrouve ce chiffre dans la mesure.
2. Trouve le défaut que le test `TestThreeFailuresAreAnError` affiche sans
   le signaler.
3. Refactore le client pour qu'il tienne le scénario : **un budget total**
   pour l'appel, des essais qui tiennent dans ce budget, aucune attente
   inutile. Ses trois tests doivent continuer de passer, à part ce que tu
   changes exprès (dis-le).
4. Mesure ta version de la même façon. Combien d'appels finissent en
   erreur, et qu'en fait l'écran de la leçon ?

## Exercice 5 — Incident : le 5 décembre à 20 h

*Niveau 7. Un incident réel, à expliquer et à corriger.*

**Les faits.** Le 5 décembre, entre 20 h 10 et 20 h 30, des membres se
plaignent sur le groupe : « l'appli met deux secondes à
répondre », « j'ai cru qu'elle avait planté ». Le tableau de bord, lui,
n'a rien vu. L'alerte se déclenche quand la ligne « p99 » dépasse 350 ms
pendant cinq minutes ; elle ne s'est pas déclenchée.

L'application tourne sur dix instances derrière un répartiteur de charge.
Chacune calcule son p99 de la minute, et l'envoie au tableau de bord :

```go
// P99 is the line "p99 latency" of the dashboard: the mean of the
// instances' p99.
func P99(ms []Minute) time.Duration {
    var sum time.Duration
    for _, m := range ms {
        sum += load.Percentile(m.Lat, 99)
    }
    return sum / time.Duration(len(ms))
}
```

La soirée, rejouée à partir des latences de chaque instance
(`go run ./ex5/cmd/evening`) :

```text
20:00  p99 90ms
20:05  p99 90ms
20:10  p99 299ms
20:15  p99 299ms
20:20  p99 300ms
20:25  p99 299ms
20:30  p99 90ms
20:35  p99 90ms
20:40  p99 90ms
20:45  p99 90ms
20:50  p99 90ms
20:55  p99 90ms
```

Le paquet `ex5/dash` contient aussi la fonction qui rejoue la soirée,
`Evening`.

1. **Explique** pourquoi la ligne « p99 » plafonne à 300 ms alors que des
   membres attendent deux secondes. Le calcul de chaque instance est
   juste : où est l'erreur ?
2. **Calcule** le vrai p99 de chaque minute, sur toutes les requêtes, et
   la part des requêtes de plus de 350 ms. Écris l'outil.
3. **Corrige** ce que le tableau de bord reçoit et calcule. Tu ne peux pas
   envoyer toutes les latences : chaque instance envoie au plus quelques
   dizaines de nombres par minute.
4. Avec ta correction, à quelle minute l'alerte se serait-elle
   déclenchée ?
5. Une meilleure question que « quel est le p99 ? » est « quelle part des
   demandes a raté l'objectif ? ». Pourquoi s'agrège-t-elle
   correctement, quand le p99 ne le fait pas ? Relie-la à l'exercice 2.
6. Écris le **compte rendu** de l'incident en cinq lignes.
