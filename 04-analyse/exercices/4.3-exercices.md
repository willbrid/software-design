# Exercices 4.3 — Modéliser le domaine sans code

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets `model`, `notebook` et `flat` de la
[leçon 4.3](../cours/4.3-modele-conceptuel.md), et sur le cahier de la
trésorière, recopiés tels quels dans le module des exercices. Tout le code
ci-dessous compile et passe `go vet` ; la tontine, ses membres et
l'incident sont **fictifs**.

## Exercice 1 — Compréhension : des mots aux concepts

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Souligner, puis trier

La présidente d'une **mutuelle de santé** de quartier décrit son
fonctionnement :

```text
Chaque famille adhérente paie une cotisation de 3 000 FCFA par mois et par
personne inscrite. Quand un membre de la famille est malade, le chef de
famille apporte la facture de la pharmacie ou du centre de santé ; la
mutuelle rembourse 70 % du montant, dans la limite de 50 000 FCFA par
personne et par an. Une famille en retard de deux mois n'est plus
remboursée jusqu'à ce qu'elle régularise. Le trésorier tient le registre
des factures, et le comité valide les remboursements au-dessus de
20 000 FCFA.
```

Souligne les noms, puis range chacun en **concept**, **rôle** ou
**attribut**. Justifie les cas difficiles avec la question de la leçon :
« ai-je besoin de me souvenir de chacun, séparément ? ».

### 1.b — Lire des multiplicités

Avec le modèle de la leçon, dis pour chaque situation si elle est
**permise**, **interdite**, ou si le modèle **ne dit rien** :

1. Ama tient deux parts entières.
2. Trois personnes tiennent chacune un tiers d'une part.
3. Une part est tenue aux trois quarts par Fon et au quart par son fils.
4. Le mois de mars est le tour de deux parts.
5. Une part n'a reçu aucune cagnotte à la fin du cycle.
6. Bih, qui ne tient aucune part, assiste aux réunions.

### 1.c — Un mot, deux sens

Dans ce message du groupe, trouve les mots qui désignent deux choses
différentes, et ceux qui désignent la même chose sous deux noms. Propose
la correction du glossaire.

```text
Le versement de Fon n'est pas arrivé, donc on ne peut pas faire le
versement de Kum. Divine a dit qu'elle mettait son nom pour Ebai ce mois,
elles partagent le même nom de toute façon. La cotisation de décembre est
de 600 000, il manque juste la cotisation de Fon.
```

## Exercice 2 — Code : chaque part paie son mois

*Niveau 2. Écrire une règle ; les tests sont fournis.*

Le contrôle de la leçon vérifie que chaque **titulaire** paie **sa
fraction**. Il ne vérifie pas que chaque **part**, au total, a payé
exactement son montant chaque mois : une demi-part dont une moitié manque
passe inaperçue. Le paquet `ex2/monthly` :

```go
// Check returns one violation per share and per month of c.Order where
// the contributions for that share do not add up to c.Amount: too little
// (the line is 0, the text says how much is missing) or too much (the line
// is the last contribution of that share that month). Months come in
// order, then shares in the order of c.Shares.
//
// To write: exercise 2.
func Check(c model.Cycle, cs []model.Contribution) []model.Violation {
    return nil
}
```

Les tests sont dans `ex2/monthly/monthly_test.go`. Sur le squelette, cinq
des six échouent. Deux d'entre eux :

```go
// A half share counts as paid when both halves are in.
func TestAHalfMissingIsReported(t *testing.T) {
    cs := slices.Delete(full(), 2, 3) // Ebai, November
    vs := monthly.Check(cycle(), cs)
    if got := texts(vs); !slices.Equal(got, []string{"cycle     monthly     P2 paid 25000 of 50000 in 2025-11"}) {
        t.Fatalf("%q", got)
    }
}
```

```go
// On the treasurer's notebook: only Ebai's whole share in December.
func TestTheNotebook(t *testing.T) {
    c, cs, _, err := notebook.Load("../../notebook/testdata", 50_000)
    if err != nil {
        t.Fatal(err)
    }
    got := texts(monthly.Check(c, cs))
    if !slices.Equal(got, []string{"line  21  monthly     P05 paid 75000 of 50000 in 2025-12"}) {
        t.Fatalf("%q", got)
    }
}
```

1. Écris `Check` pour que les six tests passent sous
   `go test -race -count=1 ./ex2/...`.
2. De quelle multiplicité, ou de quelle contrainte du diagramme, cette
   règle vient-elle ? Faut-il l'ajouter au diagramme ?
3. Sur le cahier, ta règle et celle de la leçon trouvent toutes deux la
   ligne 21. Donne un cas que **seule** ta règle voit, et un cas que
   **seule** celle de la leçon voit.

## Exercice 3 — Refactoring : qui paie, et pour qui

*Niveau 3. Changer le modèle sans casser ce qui marche.*

Le contrôle de la leçon signale « *Mme Fon is not a holder of P06* ». La
section 6 conclut que le modèle confondait **celui qui paie** et **celui
qui doit**. La trésorière accepte de noter, désormais, pour qui chaque
paiement est fait. Le cahier `notebook/testdata2/cahier.csv` a une
colonne de plus, vide quand on paie pour soi :

```text
date;kind;share;person;amount;for
2025-11-03;contribution;P01;Ama;50000;
2026-03-03;contribution;P06;Mme Fon;50000;Fon
```

1. Change le **modèle conceptuel** d'abord : redessine la partie du
   diagramme concernée, avec ses multiplicités, et ajoute les termes au
   glossaire.
2. Change ensuite `model` et `notebook` : une cotisation a un **payeur**
   et un **titulaire pour qui** elle est faite. Les règles de la leçon
   s'appliquent au titulaire.
3. Le **cahier d'origine**, sans la colonne `for`, doit toujours se lire,
   et donner les mêmes huit problèmes ; le nouveau cahier, sept.
   Explique pourquoi l'ancien cahier garde le problème de Mme Fon.
4. Les tests de la leçon doivent continuer de passer, à part ceux que tu
   changes exprès (dis lesquels, et pourquoi).

## Exercice 5 — Incident : la cagnotte de décembre

*Niveau 7. Un incident réel, à expliquer et à corriger.*

**Les faits.** Le nouveau cycle commence en novembre 2026, avec
l'application écrite d'après le modèle de la leçon. La part P05, toujours
tenue à moitié par Divine et Ebai, a son tour en décembre. Le 6 décembre,
Ebai écrit au groupe : « *La cagnotte de P05 est partie où ? Moi je n'ai
rien reçu.* » Divine ne répond pas.

Le code qui transforme un versement en transferts Mobile Money :

```go
// Transfer is one Mobile Money transfer.
type Transfer struct {
    To     string // a person: the operator needs a phone number, kept per person
    Amount int64
}
```

```go
// Transfers returns what to send for the pot of share s. The model says a
// payout "is received by" a share; the share's first holder is the one
// the treasurer knows.
func Transfers(s model.Share, pot int64) []Transfer {
    return []Transfer{{To: s.Holders[0].Person, Amount: pot}}
}
```

Les versements des six premiers mois, rejoués (`go run ./ex5/cmd/october`) :

```text
2026-11  P11  600000 to Kum
2026-12  P05  600000 to Divine
2027-01  P02  600000 to Ama
2027-02  P08  600000 to Hilda
2027-03  P03  600000 to Bih
2027-04  P10  600000 to Joyce
Divine received 600000, Ebai received 0
```

1. **Explique** l'incident. Le code a-t-il mal suivi le modèle, ou a-t-il
   suivi un modèle incomplet ? Montre l'association du diagramme de la
   leçon en cause.
2. **Corrige le modèle** : quelles questions faut-il poser au bureau, et
   quelle réponse proposes-tu par défaut ? Dessine la partie corrigée du
   diagramme.
3. **Corrige le code**, et écris le test qui manquait. Que fait ta
   correction d'une cagnotte impaire, par exemple 600 001 FCFA, sur une
   demi-part ?
4. Quelle règle de contrôle, ajoutée au contrôle de la leçon, aurait
   **refusé** de lancer ce versement ?
5. Écris le **compte rendu** de l'incident en cinq lignes.
