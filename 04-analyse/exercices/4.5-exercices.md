# Exercices 4.5 — Décrire une architecture

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur l'application, les outils `tools/arch`,
`tools/adrcheck` et les ADR de la [leçon 4.5](../cours/4.5-c4-adr.md),
recopiés dans le module des exercices. Une seule différence : la copie de
`arch.Tontine` ignore aussi les dossiers des exercices (`ex2/`, `ex3/`,
`ex5/`), qui ne font pas partie du produit. Tout le code ci-dessous
compile et passe `go vet` ; la tontine et l'incident sont **fictifs**.

## Exercice 1 — Compréhension : niveaux et décisions

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Quel niveau de C4 ?

Range chaque élément au niveau du contexte, des conteneurs, des composants
ou du code, et dis s'il est **dans** le système de la tontine ou à
l'extérieur :

1. la trésorière ;
2. la base de données des parts et des versements ;
3. le paquet `domain/payout` ;
4. Baobab Pay ;
5. la fonction `payout.Split` ;
6. l'application Android des membres ;
7. le paquet `adapter/mobilemoney` ;
8. la passerelle SMS.

### 1.b — Est-ce un ADR ?

Pour chaque sujet, dis s'il mérite un ADR, et pourquoi en une phrase :

1. « Nous utilisons `log/slog` pour les journaux. »
2. « Les montants sont des entiers de FCFA, jamais des nombres à
   virgule. »
3. « Les noms des tests sont en anglais. »
4. « Un délai dépassé chez l'opérateur mène à `Unknown`, jamais à un
   échec. »
5. « Nous passons de Kola Money seul à plusieurs opérateurs. »
6. « Le bouton de validation est vert. »

### 1.c — Une décision qui change

En mars, le bureau décide que la tontine paie elle-même les frais de
l'opérateur, au lieu de les retenir sur chaque virement. Une décision
précédente, l'ADR-0006 « Les frais de l'opérateur sont retenus sur chaque
virement », disait le contraire. Décris **exactement** ce qui change dans

```go
//

```

Les tests sont dans `ex2/layers/layers_test.go`. Sur le squelette, trois
des cinq échouent. Deux d'entre eux :

```go
func TestAThreeLayerCycleStartsAtTheFirstLayer(t *testing.T) {
    got := layers.Cycles(a, []arch.Edge{e("app/x", "adapter/y"), e("adapter/y", "cmd/z"), e("cmd/z", "app/w")})
    if !reflect.DeepEqual(got, [][]string{{"App", "Adapt", "Root"}}) {

```

```go

func TestCyclesAreSortedAndNotRepeated(t *testing.T) {
    got := layers.Cycles(a, []arch.Edge{
        e("domain/a", "app/b"), e("app/b", "domain/c"),

    })
    want := [][]string{{"Domaine", "App"}, {"App", "Adapt"}}
    if !reflect.DeepEqual(got, want) {
        t.Fatalf("%v, want %v", got, want)
    }
}
```

1. Écris `Cycles` pour que les cinq tests passent sous
   `go test -race -count=1 ./ex2/...`.
2. Les règles d'`arch.Tontine` interdisent-elles déjà tous les cycles
   entre couches ? Si oui, à quoi sert `Cycles` ?
3. Quel ADR écrirais-tu pour en faire une règle du projet ? Donne son

## Exercice 3 — Refactoring : défaire le raccourci

*Niveau 3. Garder le comportement, respecter l'ADR-0002.*

Le 3 mars, le bureau a décidé que les frais de l'opérateur seraient
retenus sur chaque virement. Le code a été écrit vite, dans le domaine :

```go
// Split gives each holder their part, less the operator's fee; the franc
// left by rounding goes to the first holder.
func Split(s tontine.Share, pot int64) []Transfer {
    out := make([]Transfer, len(s.Holders))
    var given int64
    for i, h := range s.Holders {
        part := pot * int64(h.Num) / int64(h.Den)
        out[i] = Transfer{To: h.Person, Amount: part}
        given += part
    }
    if len(out) > 0 {
        out[0].Amount += pot - given
    }
    for i := range out {
        out[i].Fee = mobilemoney.FeeOf(out[i].Amount)
        out[i].Amount -= out[i].Fee
    }
    return out
}
```

Ses tests passent. Le test d'architecture, lui :

## Exercice 5 — Incident : l'ADR qui disait vrai

*Niveau 7. Un incident réel, à expliquer et à corriger.*

**Les faits.** C'est la nuit du 14 janvier de l'exercice 5 de la leçon
4.4 : 37 versements bloqués parce que la version 2.3 répondait 204 avant
de vérifier les signatures. Pendant la revue de l'incident, quelqu'un
ouvre `docs/adr` et lit :

```text
# ADR-0005 — Vérifier une réponse de l'opérateur avant d'y répondre

- Statut : Acceptée
- Date : 2026-12-02
- Vérifiée par : TestABadSignatureIsRefusedBeforeAnswering

## Contexte

L'opérateur renvoie une réponse tant qu'il n'a pas reçu de 204. Un 204
promet donc que la banque a la réponse, et qu'elle est authentique.

## Décision

Nous vérifions la signature d'une réponse avant de répondre : 401 si elle
est fausse, pour que l'opérateur réessaie ; 204 sinon.

## Conséquences

Une réponse à la signature fausse n'est jamais perdue : l'opérateur la
renvoie. La vérification doit rester rapide, puisqu'elle a lieu avant la
réponse.
```

« Mais c'était décidé, et vérifié par un test ! » Le test de la version
2.3 :

```go
// Version 2.3: the operator gets its 204 at once. The test of ADR-0005,
// TestABadSignatureIsRefusedBeforeAnswering, was removed in the same pull
// request: "it tests the old behaviour".
func TestTheOperatorGetsItsAnswerAtOnce(t *testing.T) {
    p := &payouts{}
    h := &callback.Handler{Sig: anyKey{}, Payouts: p}
    if code := h.Receive(context.Background(), "r", nil, "k"); code != 204 {
        t.Fatalf("code %d", code)
    }
    h.Wait()
    if p.n != 1 {
        t.Fatalf("confirmed %d", p.n)
    }
}
```

Le contrôle du dossier, lancé après coup depuis `ex5`
(`go run example/exercises45/tools/adr docs/adr`) :

```text
docs/adr: 1 problems
   0005-verifier-avant-de-repondre.md: verified by TestABadSignatureIsRefusedBeforeAnswering, which is not a test of the code
```

1. **Explique** comment une décision « acceptée » et « vérifiée » a pu être
   défaite sans que personne ne le voie. Combien de garde-fous ont
   manqué ?
2. La version 2.3 avait une raison (leçon 4.4, exercice 5). Qu'aurait-il
   fallu faire du **dossier d'ADR** dans la revue de la version 2.3, si
   l'équipe voulait vraiment changer la décision ?
3. Où lancer `tools/adr`, et `tools/arch`, pour que ce scénario ne puisse
   plus se reproduire ? Écris la commande ou l'étape.
4. Le contrôle vérifie que le test **existe**. Est-ce suffisant ? Que
   faudrait-il de plus pour qu'un test cité vérifie **vraiment** la
   décision ?
5. Écris le **compte rendu** de ce que la revue a appris, en cinq lignes.
