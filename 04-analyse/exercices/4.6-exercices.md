# Exercices 4.6 — Combien d'analyse ?

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets `shared` et `contexts` de la
[leçon 4.6](../cours/4.6-combien-d-analyse.md), recopiés tels quels dans le
module des exercices. Tout le code ci-dessous compile et passe `go vet` ;
les projets, la tontine, la banque et l'incident sont **fictifs**.

---

## Exercice 1 — Compréhension : quel effort, pour quel projet ?

*Niveau 1. Aucune ligne de code à écrire.*

### 1.a — Six projets

Pour chacun, dis **qui perd quoi si c'est faux**, puis quels outils du
niveau tu appliquerais (critères, scénarios de qualité, modèle, diagrammes,
C4 et ADR, DDD stratégique), et lesquels tu laisserais de côté :

1. un script qui convertit une fois le cahier Excel de la trésorière en
   fichier CSV, lancé par toi ;
2. le même script, lancé chaque nuit par la plateforme pour les quarante
   tontines d'un marché ;
3. une page web qui affiche les horaires des réunions de la tontine ;
4. le calcul des pénalités de retard ;
5. l'intégration d'un troisième opérateur Mobile Money ;
6. un tableau de bord interne pour l'astreinte.

### 1.b — Le DDD couvre-t-il… ?

Vrai ou faux, et pourquoi en une phrase :

1. « Avec un bon langage omniprésent, on n'a plus besoin de critères
   d'acceptation. »
2. « Le DDD dit à quel p99 répondre. »
3. « Un contexte délimité peut avoir son propre sens du mot *membre*. »
4. « Une couche anti-corruption ne sert qu'avec des systèmes extérieurs. »
5. « Pour une équipe de deux personnes, le DDD stratégique est toujours
   inutile. »

### 1.c — Les deux tests restés verts

Dans la mesure de la section 6 de la leçon, deux tests de la tontine
restent verts avec la règle de la banque. Explique pourquoi c'est **pire**
qu'un échec, et ce qu'un test aurait dû vérifier pour ne pas passer.

## Exercice 2 — Code : traduire les mots de l'opérateur

*Niveau 2. Écrire une traduction ; les tests sont fournis.*

Les réponses de l'opérateur ont leurs propres mots : des codes de statut,
un montant écrit en texte. Ils ne doivent pas entrer tels quels dans le
cycle de vie du versement (leçon 3.5). Une couche anti-corruption les
traduit :

```go
// Answer is the operator's answer, in the operator's words.
type Answer struct {
    Ref    string // "P05/2027-03/Divine"
    Status string // "00" paid, "05" refused, "51" no money on the float, "91" operator busy, "96" error
    Amount string // "300000", in FCFA
}
```

```go
// Translate returns the event for answer a about a transfer of want FCFA.
// "00" with the right amount is Confirm; "05" and "51" are Decline; "91",
// "96" and every code we do not know are Unknown: only an explicit refusal
// gives the money back. "00" with another amount is an error, ErrAmount.
//
// To write: exercise 2.
func Translate(a Answer, want int64) (Event, error) {
    return 0, errors.New("not implemented")
}
```

Les tests sont dans `ex2/callback/callback_test.go` ; les cinq échouent
sur le squelette. Deux d'entre eux :

```go
// An unknown code is not a refusal: refunding on it pays twice if the
// operator paid (lesson 3.5).
func TestAnythingElseIsUnknown(t *testing.T) {
    for _, s := range []string{"91", "96", "99", "", "OK"} {
        if e, err := callback.Translate(callback.Answer{Status: s, Amount: "300000"}, 300_000); err != nil || e != callback.Unknown {
            t.Errorf("%q: %v, %v", s, e, err)
        }
    }
}
```

```go
func TestPaidWithAnotherAmountIsAnError(t *testing.T) {
    for _, amount := range []string{"299999", "3000000", "300000.00", "", "abc"} {
        if _, err := callback.Translate(callback.Answer{Status: "00", Amount: amount}, 300_000); !errors.Is(err, callback.ErrAmount) {
            t.Errorf("%q: %v", amount, err)
        }
    }
}
```

1. Écris `Translate` pour que les cinq tests passent sous
   `go test -race -count=1 ./ex2/...`.
2. Pourquoi un code inconnu est-il `Unknown` et pas `Decline` ? Relie ta
   réponse à l'exercice 5 de la leçon 3.5.
3. Pourquoi « 300000.00 » est-il refusé ? Qui doit décider s'il faut
   l'accepter ?

## Exercice 3 — Refactoring : séparer les contextes

*Niveau 3. Refaire, sur ton propre code, la séparation de la leçon.*

Reprends le paquet `shared` (copié dans le module) et fais-en deux
contextes, `tontine` et `kyc`, **sans regarder** ceux de la leçon :

1. Liste d'abord, champ par champ et fonction par fonction, à quel contexte
   appartient chaque élément de `shared.Member`.
2. Écris les deux contextes et la traduction, puis déplace les tests de la
   tontine. Ils doivent passer **avec et sans** `-tags kycrule`.
3. Une personne est membre de la tontine **et** cliente de la banque.
   Elle change de numéro de téléphone à la banque. Que doit-il se passer
   côté tontine ? Qui décide ? Propose un mécanisme (un événement, une
   synchronisation, rien du tout) et justifie-le.

## Exercice 4 — Conception : le plan d'analyse de la mutuelle

*Niveau 4. Un plan, sans code.*

La mutuelle de santé de l'exercice 1 de la leçon 4.3 veut une application :
inscription des familles, cotisations, factures, remboursements. Elle
partagera les membres avec la tontine du même quartier.

1. Qui perd quoi si c'est faux ? Classe le projet dans la grille de la
   leçon.
2. Écris le **plan d'analyse** : pour chaque outil du niveau, l'appliques-tu,
   sur quoi précisément, et combien de temps y consacres-tu ?
3. Quels mots ont deux sens entre la mutuelle et la tontine ? Faut-il des
   contextes séparés ? Dessine la carte des contextes en Mermaid.
4. Donne trois scénarios de qualité propres à la mutuelle, dont un de
   **confidentialité**.

## Exercice 5 — Incident : les cagnottes bloquées du printemps

*Niveau 7. Un incident réel, à expliquer et à corriger.*

**Les faits.** Le 1er mars, l'équipe de la banque ajoute sa règle (« pas
de pièce d'identité expirée ») au modèle partagé. La CI de la tontine
échoue ; l'équipe de la banque « répare » les tests de la tontine :

```go
// Changed by the bank team in the release of 1 March: "the tontine tests
// failed with the new rule; we gave the test members a valid document".
func TestABeneficiaryIsPaid(t *testing.T) {
    m := shared.Member{Name: "Ama", Phone: "237690000001", Shares: 1, IDNumber: "TEST", IDExpiry: now.AddDate(5, 0, 0)}
    if err := payday.Pay(m, now); err != nil {
        t.Fatal(err)
    }
}
```

Le code du versement, qui vérifie le bénéficiaire avec le modèle partagé
« par prudence » :

```go
// Pay returns whether the pot of the month may be sent to m.
func Pay(m shared.Member, now time.Time) error {
    if Rule && m.IDExpiry.Before(now) {
        return shared.ErrInvalid
    }
    return m.Validate(now)
}
```

Les versements de mars à décembre, rejoués sur les membres tels qu'ils
sont en base (`go run ./ex5/cmd/march`) :

```text
2027-04  Bih     refused: invalid member
2027-05  Che     refused: invalid member
2027-06  Divine  refused: invalid member
2027-08  Gwen    refused: invalid member
2027-09  Hilda   refused: invalid member
2027-10  Ismael  refused: invalid member
2027-12  Kum     refused: invalid member
7 pots of 600000 FCFA blocked out of 10
```

1. **Explique** l'incident, en trois causes.
2. Pourquoi la « réparation » des tests est-elle la cause la plus grave ?
   Qu'aurait dû faire l'équipe de la banque quand la CI de la tontine a
   échoué ?
3. **Corrige** : où doit vivre la règle de la banque, et que doit vérifier
   le versement de la tontine ? Écris le test qui aurait échoué, et qui
   n'aurait pas pu être « réparé » sans changer de sens.
4. Combien de FCFA de cagnottes ont été bloqués, et combien de membres
   touchés ? Que fallait-il faire pour eux, le jour où l'incident a été
   compris ?
5. Écris le **compte rendu** de l'incident en cinq lignes.
