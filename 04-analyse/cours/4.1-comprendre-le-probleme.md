# Leçon 4.1 — Comprendre le problème : cas d'utilisation, récits utilisateur, critères d'acceptation

## L'essentiel en deux minutes

**Le problème, en une phrase.** On code ce qu'on a **compris**, pas ce qui
a été **demandé**. Chaque ligne de code prend une décision métier : si
personne ne l'a prise avant, c'est le développeur qui la prend, seul, sans
le savoir. Et ses tests, verts, vérifient ce qu'il a compris.

**Trois images.**

- **Le tailleur.** Avant de couper le tissu, il prend les mesures, et il
  demande pour quelle occasion : un mariage ou le bureau, ce n'est pas la
  même coupe. Couper d'abord coûte le tissu.
- **La recette de grand-mère** : « un peu de sel, cuire le temps qu'il
  faut ». Elle sait ce qu'elle veut dire ; vous, non. Un **critère
  d'acceptation** remplace « un peu » par « une cuillère à café ».
- **Le dessin coté du menuisier**, signé par le client avant la
  fabrication : 1,80 m, trois tiroirs, poignées en laiton. En cas de
  désaccord, on regarde le dessin, pas les souvenirs.

**Le code, en dix lignes.** Une règle du métier, écrite comme un
exemple chiffré, devient un test :

```go
// AC4. When a share is still missing on the 10th, the pot is paid in full,
// and the emergency fund advances the missing 50 000.
func TestAC4OnTheTenthTheFundAdvancesWhatIsMissing(t *testing.T) {
    d := given(t)
    pay(t, d, nov(4), except(twelve, "Fon")...)
    p, _ := d.Settle(1, nov(10))
    if !p.Pay || p.Amount != 600_000 || p.Advanced != 50_000 {
        t.Fatalf("got %+v; want 600000 paid, 50000 advanced", p)
    }
}
```

**Les règles à retenir.**

1. **Chaque ligne de code prend une décision métier.** Liste-les avant
   d'écrire, et fais-les prendre par ceux à qui elles appartiennent.
2. **Un cas d'utilisation raconte un objectif de bout en bout**, puis tout
   ce qui peut mal tourner : les **extensions**. Chaque extension est une
   question à poser.
3. **Un récit utilisateur est une promesse de conversation**, pas une
   spécification : une carte, une conversation, une confirmation.
4. **Un critère d'acceptation est un exemple chiffré** (« le 10, il manque
   50 000 : la caisse les avance »), qu'on écrit en « étant donné, quand,
   alors », et qui devient un test.
5. **Les tests d'acceptation parlent la langue du métier**, à travers un
   pilote. Quand une campagne en laisse survivre, la cause est souvent une
   question que personne n'a posée.

La suite mesure tout cela sur un vrai module.

---

Les trois niveaux précédents partaient d'un problème **donné** : un
paiement, un barème, un opérateur. Le niveau 4 remonte d'un cran. Avant
de concevoir, il faut savoir ce qu'on conçoit, et c'est rarement écrit
quelque part. Le problème qui revient est

> **Le client décrit ce qu'il veut en quelques phrases, avec ses mots.
> Comment trouver tout ce que ces phrases ne disent pas, le faire décider
> par lui, et vérifier ensuite que le logiciel fait bien ce qui a été
> décidé ?**

Cette leçon change de terrain : une **tontine**. Douze personnes
cotisent chaque mois la même somme, et chaque mois l'une d'elles reçoit
toute la cagnotte. Au Cameroun, on dit qu'elle « bouffe » la tontine. Les
règles semblent simples, tout le monde les connaît, et c'est exactement ce
qui rend l'analyse difficile : chacun a les **siennes** en tête.

Tout ce qui suit est mesuré sur un module vert sous `gofmt -l`,
`go vet ./...` et `go test -race -count=1 ./...`. La tontine, ses membres
et sa présidente sont fictifs.

## 1. La demande

Le message reçu par le développeur, de la présidente de la tontine :

```text
Bonjour ! On voudrait une appli pour notre tontine. On est 12, chacun
cotise 50 000 par mois, le 5. Chaque mois quelqu'un bouffe. Il faut que
ça marche avec Mobile Money. Et il faut gérer les retards, il y a toujours
des gens en retard 😅
```

Cinq phrases. Le développeur connaît les tontines : sa mère en fait
partie de trois. Il commence à coder le soir même.

## 2. Le code écrit tout de suite

```go
// Tontine is twelve members who each put in Amount every month; each month
// one of them takes the pot.
type Tontine struct {
    Members []string
    Amount  int64
    Turn    int
    paid    map[string]bool
}
```

Et ses tests, qui passent :

```go
func TestThePotIsWhatTheOthersPay(t *testing.T) {
    tt := v1.New([]string{"Ama", "Bih", "Che"}, 50_000)
    if _, amount := tt.Payout(); amount != 100_000 {
        t.Fatalf("pot %d, want 100000", amount)
    }
}
```

```text
--- PASS: TestThePotGoesRoundTheMembers (0.00s)
--- PASS: TestThePotIsWhatTheOthersPay (0.00s)
--- PASS: TestThePenaltyIsAThousandADay (0.00s)
ok      example/tontine41/v1    0.002s
```

Trois tests, trois verts. Le code est court, lisible, testé. Il est aussi
**faux**, mais aucun de ses tests ne peut le dire : ils vérifient ce que
le développeur a compris, avec les chiffres qu'il a choisis.

## 3. Six décisions que personne n'a prises

Relis le code en te demandant, pour chaque ligne : **qui a décidé ça ?**

| Ligne | Décision prise par le code | Ce que dit le message |
|---|---|---|
| `t.Members[t.Turn%len(t.Members)]` | l'ordre des bénéficiaires est l'ordre de la liste | rien |
| `t.Amount * int64(len(t.Members)-1)` | le bénéficiaire ne cotise pas pour lui-même : 550 000 | rien |
| `Payout()` ne lit jamais `paid` | la cagnotte est versée même si des cotisations manquent | rien |
| `Payout()` n'a pas de date | on peut verser n'importe quel jour, même avant le 5 | « le 5 » |
| `Members []string` | une personne, une part | rien |
| `1000 * int64(daysLate)` | la pénalité est de 1 000 FCFA par jour | « gérer les retards » |

Six décisions métier, et le message n'en prend **aucune**. Le développeur
les a prises de bonne foi, d'après la tontine de sa mère. La deuxième
ligne enlève 50 000 FCFA à chaque bénéficiaire ; la troisième fait verser
de l'argent qui n'est pas encore arrivé. Aucune n'est une faute de
programmation : ce sont des **questions qui n'ont pas été posées**.

L'analyse, c'est l'art de trouver ces questions **avant** d'écrire le
code. La suite présente trois outils pour les trouver, et un pour vérifier
les réponses.

## 4. Le cas d'utilisation : raconter, puis chercher ce qui casse

Un **cas d'utilisation** raconte comment un **acteur** atteint un
**objectif** avec le système, de bout en bout. La forme la plus utile est
celle d'Alistair Cockburn (*Writing Effective Use Cases*, 2001) : du texte,
pas un dessin. Il range les cas par **niveau**, avec une image : le
niveau « nuage » pour un objectif d'entreprise (« faire tourner la
tontine pendant un an »), le niveau « mer » pour un objectif qu'un
utilisateur atteint en une séance (« verser la cagnotte du mois »), le
niveau « poisson » pour une sous-étape (« vérifier un numéro »). On écrit
surtout au niveau de la mer.

```text
Cas : Verser la cagnotte du mois
Acteur principal : la trésorière
Niveau : objectif utilisateur (mer)
Parties prenantes et intérêts :
  - le bénéficiaire du mois : recevoir toute la cagnotte, à la date prévue ;
  - les autres membres : que leur argent aille au bon bénéficiaire, et
    qu'un retardataire ne soit pas avantagé ;
  - la trésorière : ne jamais verser de l'argent qui n'est pas arrivé.
Préconditions : le cycle a commencé ; l'ordre des bénéficiaires est connu.
Garantie en cas de succès : le bénéficiaire a reçu la cagnotte, chaque
  membre voit le versement dans l'historique.

Scénario nominal :
  1. Le 5, la trésorière ouvre le mois en cours.
  2. Le système montre les cotisations reçues : toutes les parts sont là.
  3. Le système indique le bénéficiaire du mois et le montant.
  4. La trésorière valide.
  5. Le système envoie le montant au bénéficiaire par Mobile Money.
  6. Le système enregistre le versement, et prévient le groupe.

Extensions :
  2a. Une ou plusieurs parts manquent le 5.
  2b. Le bénéficiaire du mois n'a pas cotisé lui-même.
  2c. Une cotisation est arrivée en double.
  2d. Une personne qui n'est pas membre a envoyé de l'argent.
  3a. Un membre a deux parts : combien de fois bouffe-t-il ?
  3b. Le bénéficiaire veut céder son tour à un autre membre.
  5a. Mobile Money ne répond pas, ou répond plus tard (leçon 3.5).
  5b. Le numéro du bénéficiaire a changé.
  *a. Un membre veut quitter la tontine en cours de cycle.
```

Le scénario nominal tient en six lignes, et il est presque sans intérêt :
tout le monde le connaît. Le travail est dans les **extensions** : pour
chaque étape, « qu'est-ce qui peut se passer d'autre ? ». Neuf extensions,
et chacune est une question dont le message ne disait rien. La notation
`*a` désigne ce qui peut arriver à n'importe quelle étape.

Remarque aussi la ligne « parties prenantes et intérêts ». Elle oblige à
se demander qui perd quoi si le système se trompe. Le bénéficiaire perd
50 000 FCFA avec la v1, et la trésorière verse de l'argent qui n'existe
pas : deux intérêts que le code ignorait.

## 5. Les questions, et les réponses

Les extensions deviennent une liste de questions, apportée à la réunion
du bureau de la tontine. Le compte rendu, tel que la présidente l'a
envoyé au groupe :

```text
Réunion du 14 octobre, bureau de la tontine

R1. L'ordre des bénéficiaires est tiré au sort au début du cycle, devant
    tout le monde. Le tirage doit pouvoir être refait pour vérifier.
R2. Tout le monde cotise chaque mois, le bénéficiaire aussi. La cagnotte,
    c'est toutes les parts.
R3. On peut avoir deux parts (deux « noms ») : on cotise deux fois, on
    bouffe deux fois.
R4. On verse dès que tout est arrivé, mais jamais avant le 5. Si le 10 il
    manque encore des parts, la caisse de secours avance ce qui manque, et
    le retardataire rembourse la caisse.
R5. Pénalité : 5 % de la cotisation par semaine de retard commencée.
    Payer le 5 à n'importe quelle heure, c'est à l'heure.
R6. Départ en cours de cycle : on n'est pas d'accord. À revoir à la
    prochaine réunion.
```

Comparé à la v1 : l'ordre est tiré au sort, le bénéficiaire cotise, on ne
verse pas l'argent absent, une personne peut avoir deux parts, la
pénalité est hebdomadaire, et l'on ne verse jamais avant le 5. **Les six
décisions du code étaient fausses.**

Et R6 n'est pas décidée. C'est un résultat normal de l'analyse : certaines
questions n'ont pas encore de réponse. Le code ne doit pas en inventer
une. Il refuse le cas, ou le laisse à la main de la trésorière, et la
question reste sur la liste.

## 6. Les récits utilisateur : une carte, une conversation, une confirmation

Un **récit utilisateur** (*user story*) découpe le travail en morceaux
qu'on peut livrer un par un. La forme la plus répandue, popularisée par
Mike Cohn : « *As a [type of user], I [need/want/am required] to [do
something], so that [reason or benefit]* ». En français :

```text
En tant que trésorière,
je veux que la caisse avance les parts manquantes le 10,
afin que le bénéficiaire reçoive toute sa cagnotte même si quelqu'un est en retard.
```

Le récit ne dit **pas** combien avancer, ni comment le retardataire
rembourse. C'est voulu. Ron Jeffries, l'un des créateurs de l'*Extreme
Programming*, décrit les trois parties d'un récit : « *Card,
Conversation, and Confirmation* ». La **carte** ne contient pas toute
l'exigence : « *the card has just enough text to identify the requirement,
and to remind everyone what the story is* ». Le détail vient de la
**conversation** avec le métier, et la **confirmation**, ce sont les
tests d'acceptation de la section 7.

Bill Wake a résumé ce qu'est un bon récit par l'acronyme **INVEST** :
« *Independent, Negotiable, Valuable, Estimable, Small, Testable* ». Le
dernier critère est le plus utile au quotidien. Wake l'explique ainsi :
écrire un récit, c'est promettre « *I understand what I want well enough
that I could write a test for it* ».

Appliqué à la phrase du message, « il faut gérer les retards » n'est pas
un récit : impossible d'écrire un test, et c'est trop gros. Découpé :

| Récit | Testable ? |
|---|---|
| En tant que trésorière, je vois le 5 qui n'a pas cotisé, afin de relancer. | oui : la liste des manquants |
| En tant que trésorière, je veux que la caisse avance les parts manquantes le 10, afin que le bénéficiaire soit payé. | oui : le montant avancé |
| En tant que membre, je connais ma pénalité de retard, afin de ne pas être surpris. | oui : le montant dû à une date |
| ~~En tant que membre, je peux quitter la tontine.~~ | non : R6 n'est pas décidée, le récit attend |

Chacun de ces récits peut être livré seul, et chacun apporte quelque chose
à quelqu'un.

## 7. Les critères d'acceptation : des exemples chiffrés

Un **critère d'acceptation** dit quand un récit est fini. Le plus utile
n'est pas une règle générale (« la pénalité est de 5 % par semaine
commencée ») mais un **exemple**, avec des chiffres : « un jour de retard,
2 500 ; sept jours, 2 500 ; huit jours, 5 000 ». Martin Fowler appelle
cette pratique *Specification By Example* : la règle s'écrit par ses
exemples, et les exemples ne se discutent pas.

Dan North, qui a introduit le *Behaviour-Driven Development*, a donné aux
exemples une forme : « *Given some initial context (the givens), When an
event occurs, Then ensure some outcomes* ». En français : **étant
donné**, **quand**, **alors**.

Les critères de la tontine, écrits avec la présidente :

| # | Étant donné | Quand | Alors |
|---|---|---|---|
| AC1 | 12 parts de 50 000 | tout le monde a cotisé le 5 | le bénéficiaire reçoit 600 000 le 5 |
| AC2 | idem | tout le monde sauf le bénéficiaire a cotisé | rien n'est versé le 5 |
| AC3 | idem | Fon n'a pas cotisé le 5 | rien n'est versé, Fon est nommé |
| AC4 | idem | Fon n'a toujours pas cotisé le 10 | 600 000 versés, dont 50 000 avancés par la caisse |
| AC5 | Fon n'a pas cotisé le 5 | Fon cotise le 8 | 600 000 versés le 8, rien d'avancé |
| AC6 | tout le monde a cotisé le 2 | on est le 3 | rien n'est versé |
| AC7 | Fon cotise le 5 à 23 h 59 / le 6 / le 12 / le 13 | on calcule sa pénalité | 0 / 2 500 / 2 500 / 5 000 |
| AC8 | Fon n'a rien payé | on est le 20 | Fon doit 50 000 + 7 500 |
| AC9 | Ama a deux parts, onze autres une | on tire l'ordre, puis tout le monde cotise | Ama a 2 tours sur 13 ; la cagnotte est de 650 000 |
| AC10 | la graine publiée | on refait le tirage | même ordre, une part par tour, pas l'ordre de la liste |
| AC11 | — | Zacharie, qui n'est pas membre, envoie 50 000 | le paiement est refusé |

Écrire ce tableau avec la présidente a fait apparaître deux nouvelles
questions. « Le 5 à 23 h 59, c'est à l'heure ? » Oui (AC7). « Si tout
arrive le 8, on attend le 10 ? » Non, on verse le 8 (AC5). Un exemple
chiffré oblige à trancher ce qu'une phrase laisse flou.

## 8. Du critère au test : le pilote

Chaque ligne du tableau devient un test Go. Pour que les tests parlent la
langue du métier, et non celle d'une implémentation, ils passent par un
**pilote** (*driver*) : une interface qui dit ce que les critères
demandent à la tontine, rien de plus.

```go
// Driver is the tontine as the criteria see it.
type Driver interface {
    Start(members []Member, amount int64, firstDue time.Time, seed uint64) error
    Contribute(month int, member string, at time.Time) error
    Settle(month int, now time.Time) (Payout, error)
    Order() ([]string, error)
    Owed(member string, now time.Time) (int64, error)
}
```

Le « étant donné » commun à presque tous les critères :

```go
// given starts a tontine of twelve members with one share each, 50 000
// FCFA a month, the first due date on 5 November.
func given(t *testing.T) Driver {
    t.Helper()
    members := make([]Member, len(twelve))
    for i, n := range twelve {
        members[i] = Member{n, 1}
    }
    d := newDriver()
    if err := d.Start(members, 50_000, firstDue, 2026); err != nil {
        t.Fatal(err)
    }
    return d
}
```

Puis chaque critère, avec son numéro et sa phrase en commentaire :

```go
// AC7. A late share costs 5 % per started week: one day late, 2 500; seven
// days, 2 500; eight days, 5 000. Paying on the due date, at any hour, is on
// time.
func TestAC7APenaltyPerStartedWeek(t *testing.T) {
    for _, c := range []struct {
        at   time.Time
        want int64
    }{
        {time.Date(2026, 11, 5, 23, 59, 0, 0, douala), 0},
        {nov(6), 2_500},
        {nov(12), 2_500},
        {nov(13), 5_000},
    } {
        d := given(t)
        pay(t, d, c.at, "Fon")
        got, err := d.Owed("Fon", nov(20))
        if err != nil || got != c.want {
            t.Errorf("paid %s: owes %d, %v; want %d", c.at.Format("Jan 2 15:04"), got, err, c.want)
        }
    }
}
```

Le pilote a un autre avantage : les mêmes critères peuvent vérifier
**deux** implémentations. Le pilote de la v1 traduit les mêmes demandes
vers son API, et dit honnêtement ce qu'elle ne sait pas faire :

```go
// Settle pays whenever it is asked: v1 has no dates and does not look at who
// paid.
func (d *first) Settle(_ int, _ time.Time) (Payout, error) {
    who, amount := d.t.Payout()
    return Payout{Pay: true, Beneficiary: who, Amount: amount}, nil
}
```

La nouvelle version, `tontine`, applique R1 à R5. Sa décision sur la
cagnotte :

```go
// Settle decides about the pot of month m at now (R4).
func (c *Cycle) Settle(m int, now time.Time) (Settlement, error) {
    if m < 1 || m > c.Months() {
        return Settlement{}, fmt.Errorf("%w: %d", ErrMonth, m)
    }
    s := Settlement{Beneficiary: c.order[m-1]}
    var missing int64
    for name := range c.shares {
        if _, ok := c.paid[m][name]; !ok {
            s.Missing = append(s.Missing, name)
            missing += c.owes(name)
        }
    }
    slices.Sort(s.Missing)
    due := c.Due(m)
    switch {
    case now.Before(due):
        return s, nil // never before the due date
    case missing == 0:
        s.Pay, s.Amount = true, c.Pot()
    case daysLate(due, now) >= Grace:
        s.Pay, s.Amount, s.Advanced = true, c.Pot(), missing
    }
    return s, nil
}
```

```go
// Penalty is the cost of paying due daysLate days late (R5).
func Penalty(due int64, daysLate int) int64 {
    weeks := (daysLate + 6) / 7
    return int64(weeks) * due * PenaltyBP / 10_000
}
```

## 10. La campagne : un survivant est souvent une question

Les critères suffisent-ils à verrouiller la nouvelle version ? On
introduit une erreur à la fois dans `tontine`, avec **seulement** les tests
d'acceptation :

```text
cagnotte sans le bénéficiaire                tuee
versé avant l'échéance                       tuee
avance dès le 9                              SURVIT
avance seulement le 11                       tuee
```

Quatre erreurs survivent, et elles ne sont pas de la même nature :

- **« avance dès le 9 »** : un critère **manque**. Les critères disaient
  ce qui se passe le 5 et le 10, pas le 9. La règle « le 10 » n'était
  testée que d'un côté.
- **« double paiement accepté »** : une **question** que personne n'avait
  posée. Fon paie deux fois le même mois : on refuse ? on garde pour le
  mois suivant ? La présidente a répondu : on refuse, et la trésorière
  rembourse.
- **« manquants non triés »** : ce n'est pas une règle métier. Que la
  liste soit triée est une promesse du **code** (le même message de
  relance à chaque appel) : un test unitaire, pas un critère.
- **« tontine d'une part »** : une validation technique (une tontine à un
  seul membre n'a pas de sens). Un test unitaire aussi.

Deux critères ajoutés, après la réunion :

```go
// AC12, added after the campaign. On the 9th, a share is still missing:
```

## 11. Cas d'utilisation ou récit ?

Les deux ne s'opposent pas. Ils servent à des moments différents :

| | Cas d'utilisation | Récit utilisateur | Critère d'acceptation |
|---|---|---|---|
| sert à | **trouver** les questions | **découper** le travail | **vérifier** une réponse |
| unité | un objectif complet, avec ses extensions | un morceau livrable | un exemple chiffré |
| moment | avant de planifier | pour planifier | avant de coder, et pour toujours |
| qui l'écrit | l'analyste, avec le métier | l'équipe, avec le métier | le métier, avec l'équipe |
| ce qu'il rate | rien n'oblige à chiffrer | les cas d'erreur, si personne ne les cherche | ce que personne n'a pensé à demander |

Un projet de tontine peut se contenter de récits et de critères. Un
système de paiement qui touche à l'argent de milliers de personnes gagne à
écrire d'abord les cas d'utilisation des quelques objectifs principaux :
leurs extensions sont la liste la plus complète des questions à poser. La
leçon 4.6 revient sur « combien d'analyse » selon le projet.

## 13. Les trois erreurs qui restent

### « Le client sait ce qu'il veut, il suffit de l'écrire »

La présidente savait **parfaitement** ce qu'elle voulait. Mais elle ne
savait pas que « le bénéficiaire cotise-t-il ? » était une question : pour
elle, c'était évident, et ça l'était tout autant, dans l'autre sens, pour
le développeur. Le client connaît son métier, pas la liste des décisions
qu'un programme doit prendre. Cette liste, c'est le travail de
l'analyste.

### « On verra en recette »

En recette, la présidente aurait vu 550 000 au lieu de 600 000, et le
développeur aurait corrigé une ligne. Mais « verser avant le 5 », « pas
de caisse de secours », « une part par personne » touchent au modèle de
données : il aurait fallu reprendre la moitié du code, et les tests avec.
Une question coûte une phrase en réunion ; la même réponse trouvée en
recette coûte une réécriture.

### « Les critères d'acceptation, ce sont des tests d'interface »

Les critères de cette leçon ne cliquent sur rien. Ils parlent à la
tontine par un pilote, en millisecondes, et tournent à chaque `go test`.
Un critère vérifie une **règle**, pas un écran. Des tests d'interface
peuvent s'y ajouter, quelques-uns, pour le parcours principal ; ils ne
remplacent pas les exemples chiffrés.

## 14. Le lien avec la production

Tu as déjà vu ces incidents :

- « Le calcul est juste, mais ce n'est pas ce que le client voulait » :
  une décision métier prise dans le code, et des tests qui la
  confirment.
- « Ça marchait dans tous nos tests ; en production, il y avait des
  doublons » : une extension (2c, la cotisation en double) que personne
  n'a écrite.
- « Le client conteste un montant, et personne ne sait quelle était la
  règle » : pas de critère chiffré, ou un critère resté dans un courriel.
  Un test d'acceptation nommé `TestAC7APenaltyPerStartedWeek` **est** la
  règle, et il est versionné avec le code.

Le réflexe de diagnostic, devant un « ce n'est pas ce que je voulais » :
retrouver le critère. S'il n'existe pas, le défaut n'est pas dans le
code ; il est dans l'analyse, et la correction commence par un exemple
chiffré, validé par le métier.

## 15. Ce qu'il faut retenir

1. Chaque ligne de code prend une décision. Relis ton code en demandant
   « qui a décidé ça ? ».
2. Le cas d'utilisation sert à **trouver les questions** : un scénario
   nominal court, et des extensions pour chaque étape.
3. Le récit utilisateur sert à **découper** : une carte, une
   conversation, une confirmation. Il doit être testable.
4. Le critère d'acceptation sert à **vérifier** : un exemple chiffré, en
   étant donné / quand / alors, qui devient un test.
5. Les tests d'acceptation passent par un pilote, et une campagne de
   mutations dessus révèle les questions oubliées.

## 16. Approfondissement

### Le diagramme de cas d'utilisation

UML propose un diagramme : des bonshommes (les acteurs), des ovales (les
cas), des traits. Il dit **qui** fait **quoi**, et rien de ce qui compte :
ni les étapes, ni les extensions, ni les règles. Il sert de sommaire quand
les cas sont nombreux. La valeur est dans le texte.

### Les outils de BDD

Des outils lisent des critères écrits en langue naturelle (le format
Gherkin : `Given`, `When`, `Then`) et les relient à du code ; en Go,
`godog` en est un. Ils valent la peine quand le métier **lit** ou
**écrit** lui-même les critères. Sinon, un test Go bien nommé, avec la
phrase du critère en commentaire, fait le même travail avec un outil de
moins.

### Et le modèle du domaine ?

En écrivant les critères, des mots sont revenus sans cesse : part,
cagnotte, échéance, caisse de secours, retardataire. Ce vocabulaire est le
début d'un **modèle du domaine**, et c'est le sujet de la leçon 4.3.

## 17. Le réflexe à installer

Avant d'écrire la première ligne d'une fonctionnalité :

1. Écris le scénario nominal en six lignes, puis, pour chaque étape,
   « qu'est-ce qui peut se passer d'autre ? ».
2. Transforme chaque extension en question, et fais-la trancher par le
   métier. Note celles qui restent ouvertes.
3. Pour chaque réponse, écris un exemple chiffré : étant donné, quand,
   alors.
4. Après le code, lance une campagne sur les tests d'acceptation : chaque
   survivant est soit un test qui manque, soit une question qui manque.
