# Correction 4.4 — Exercice 2 : un diagramme bien formé

> Rappel de l'énoncé : écrire `check.Problems`, qui trouve ce qui ne va
> pas dans un diagramme d'activité écrit comme des données ; dire ce que
> la règle d'atteignabilité fait des boucles ; dire quel test de la leçon
> aurait dû s'en servir.

La solution est dans `ex2/check` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Deux parcours** suffisent pour l'essentiel : depuis le début en
  suivant les flèches (ce qui est atteignable), et depuis la fin en les
  remontant (ce qui mène à la fin). Le reste est un compte des flèches de
  chaque nœud.
- **Une boucle avec une sortie est acceptée** ; une boucle sans sortie est
  refusée, parce que la fin n'est atteignable depuis aucun de ses nœuds.
- La campagne a trouvé une faiblesse **des tests fournis** : chercher un
  problème qui « contient d » ne vérifie presque rien quand les nœuds
  s'appellent `a`, `b`, `d`.

## 1. La solution

```go
// Problems returns what is wrong with g, one sentence per problem, sorted.
func Problems(g activity.Graph) []string {
    var out []string
    nodes := map[string]activity.Node{}
    for _, n := range g.Nodes {
        nodes[n.ID] = n
    }
    outs := map[string][]activity.Edge{}
    ins := map[string][]string{}
    for _, e := range g.Edges {
        for _, id := range []string{e.From, e.To} {
            if _, ok := nodes[id]; !ok {
                out = append(out, fmt.Sprintf("edge %s -> %s: no node %s", e.From, e.To, id))
            }
        }
        outs[e.From] = append(outs[e.From], e)
        ins[e.To] = append(ins[e.To], e.From)
    }
    for _, n := range g.Nodes {
        es := outs[n.ID]
        switch {
        case n.Decision:
            if len(es) < 2 {
                out = append(out, fmt.Sprintf("decision %s: %d way out, want two or more", n.ID, len(es)))
            }
            guards := map[string]bool{}
            for _, e := range es {
                if e.Guard == "" {
                    out = append(out, fmt.Sprintf("decision %s: an edge to %s without a guard", n.ID, e.To))
                } else if guards[e.Guard] {
                    out = append(out, fmt.Sprintf("decision %s: guard %q twice", n.ID, e.Guard))
                }
                guards[e.Guard] = true
            }
        case n.ID == g.End:
            if len(es) > 0 {
                out = append(out, fmt.Sprintf("end %s: %d ways out, want none", n.ID, len(es)))
            }
        default:
            if len(es) != 1 {
                out = append(out, fmt.Sprintf("step %s: %d ways out, want one", n.ID, len(es)))
            }
            for _, e := range es {
                if e.Guard != "" {
                    out = append(out, fmt.Sprintf("step %s: guard %q on a step", n.ID, e.Guard))
                }
            }
        }
    }
    reach := func(from string, next func(string) []string) map[string]bool {
        seen := map[string]bool{from: true}
        todo := []string{from}
        for len(todo) > 0 {
            id := todo[0]
            todo = todo[1:]
            for _, n := range next(id) {
                if !seen[n] {
                    seen[n] = true
                    todo = append(todo, n)
                }
            }
        }
        return seen
    }
    forward := reach(g.Start, func(id string) []string {
        var ns []string
        for _, e := range outs[id] {
            ns = append(ns, e.To)
        }
        return ns
    })
    backward := reach(g.End, func(id string) []string { return ins[id] })
    for _, n := range g.Nodes {
        if !forward[n.ID] {
            out = append(out, fmt.Sprintf("node %s: cannot be reached from the start", n.ID))
        }
        if !backward[n.ID] {
            out = append(out, fmt.Sprintf("node %s: the end cannot be reached from it", n.ID))
        }
    }
    slices.Sort(out)
    return out
}
```

Les deux parcours sont le même code (`reach`), une fois en suivant les
flèches, une fois en les remontant. Un nœud qui manque au premier est
**isolé** ; un nœud qui manque au second est une **impasse**.

## 2. Les boucles

La boucle de la leçon, `send → d3 → fix → send`, a une sortie :
`d3 → wait`. En remontant depuis la fin, on atteint `wait`, puis `d3`,
puis `send` et `fix` : tous mènent à la fin, la règle l'accepte. Une
boucle **sans** sortie, comme `b → b` dans `TestEveryNodeLeadsToTheEnd`,
n'est jamais atteinte en remontant : chacun de ses nœuds est signalé
« *the end cannot be reached from it* ». La règle distingue donc
exactement les boucles qui finissent de celles qui ne finissent pas.

## 3. Le test de la leçon qui aurait dû s'en servir

`TestTheClosingHasTwelvePaths`, et surtout `cmd/paths`, énumèrent les
chemins **en supposant** que le diagramme est bien formé. Sur un
diagramme avec une impasse, l'énumération ne trouve simplement pas les
chemins qui y passent, sans rien dire ; sur une décision à une seule
sortie, elle compte une réponse fantôme. Le plan de test serait faux en
silence. La bonne place de `Problems` est **avant** `Paths`, dans le test
de référence du diagramme : un diagramme mal formé ne doit ni se dessiner,
ni se compter.

## 4. La campagne

Au premier passage :

```text
décision à une sortie acceptée               SURVIT
garde en double acceptée                     tuee
décision sans garde acceptée                 tuee
étape sans sortie acceptée                   SURVIT
fin avec sortie acceptée                     tuee
garde sur une étape acceptée                 tuee
nœud isolé accepté                           tuee
impasse acceptée                             tuee
problèmes non triés                          NE COMPILE PAS
nœud inexistant accepté                      tuee
7/10 tuees
```

Deux survivantes, dues aux tests fournis :

- **« décision à une sortie acceptée »** : le test supprime une sortie de
  `d` et cherche un problème qui contient « d ». La mutation ne signale
  plus la décision, mais le nœud `b`, devenu isolé, donne « *node b:
  cannot be reached from the start* », qui contient un « d » (dans
  *reached*). Le test passe pour une mauvaise raison.
- **« étape sans sortie acceptée »** : une étape sans flèche de sortie est
  aussi une impasse, signalée par l'autre règle. Le test qui cherche « b »
  et « end » la trouve, mutation ou pas.

Une troisième ne compilait pas (« problèmes non triés » rendait `slices`
inutilisé) ; elle a été réécrite. Deux tests ajoutés vérifient la phrase
exacte :

```go
// Added after the campaign: with one-letter names, "a problem that
// contains d" is almost always true ("cannot be reached" contains a d).
// These two tests check the exact sentence.
func TestADecisionWithOneWayOutIsNamedExactly(t *testing.T) {
    g := small()
    g.Edges = slices.Delete(g.Edges, 2, 3)
    if got := check.Problems(g); !slices.Contains(got, "decision d: 1 way out, want two or more") {
        t.Fatalf("%q", got)
    }
}
```

## Ce qu'il faut retenir

1. Un diagramme écrit comme des données se vérifie comme des données :
   des comptes, et deux parcours.
2. Les boucles se jugent à leur sortie : une boucle qui ne mène pas à la
   fin est une impasse.
3. Un plan de test tiré d'un diagramme suppose le diagramme bien formé :
   vérifie-le d'abord.
4. Un test qui cherche une sous-chaîne d'une lettre ne vérifie presque
   rien. Compare la phrase entière, ou au moins un mot qui ne peut venir
   que du bon message.
