# Correction 4.5 — Exercice 5 : l'ADR qui disait vrai

> Rappel de l'énoncé : l'ADR-0005 disait « vérifier avant de répondre,
> vérifiée par un test » ; la version 2.3 a défait la décision et supprimé
> le test dans la même revue. Expliquer, dire ce qu'il fallait faire du
> dossier, où lancer les contrôles, si « le test existe » suffit, et
> rédiger le compte rendu.

Cette correction s'appuie sur la sortie du contrôle donnée dans l'énoncé,
et sur les outils de la leçon ; elle n'ajoute pas de code.

## En bref

- **Trois garde-fous ont manqué** : la revue n'a pas ouvert les ADR, le
  test qui vérifiait la décision a été supprimé comme « test de l'ancien
  comportement », et le contrôle du dossier n'était lancé nulle part.
- **Changer une décision acceptée, c'est écrire un ADR qui la remplace**,
  dans la même revue que le code. La version 2.3 aurait alors dû
  expliquer pourquoi elle répondait avant de vérifier, et quelqu'un aurait
  demandé ce que devenaient les réponses refusées.
- **Les deux contrôles vont dans la CI**, à côté de `go test`.
- **« Le test existe » ne suffit pas** : il faut qu'il échoue si la
  décision est défaite. Une campagne de mutations sur la décision le
  vérifie.

## 1. Comment une décision vérifiée a été défaite

Trois choses devaient arrêter la version 2.3, et aucune ne l'a fait :

1. **La revue de code** a vu un test supprimé, avec une bonne raison en
   apparence : « *it tests the old behaviour* ». Personne n'a fait le lien
   avec l'ADR qui citait ce test. Un test qui vérifie une décision n'est pas
   un test comme les autres : le supprimer, c'est défaire la décision.
2. **Le test lui-même** a été supprimé dans la revue qui changeait le
   comportement. Un test qui échoue est une alarme ; un test supprimé n'en
   déclenche aucune.
3. **Le contrôle du dossier** aurait signalé, dès la revue, la phrase
   que l'énoncé a obtenue après coup : « *verified by
   TestABadSignatureIsRefusedBeforeAnswering, which is not a test of the
   code* ». Mais il n'était lancé ni en local, ni dans la CI.

L'ADR, lui, disait vrai **le jour où il a été écrit**. Il est devenu faux
sans changer une lettre.

## 2. Ce qu'il fallait faire du dossier

Si l'équipe voulait vraiment répondre avant de vérifier (pour ne jamais
faire attendre l'opérateur, leçon 4.4, exercice 5), la revue de la
version 2.3 devait contenir :

- un **ADR-0012** « Répondre à l'opérateur avant de vérifier », qui
  **remplace** l'ADR-0005, avec son contexte (les délais de l'opérateur),
  sa décision, et surtout ses **conséquences** : « une réponse à la
  signature fausse n'est plus renvoyée par l'opérateur ; elle doit être
  signalée par une alerte, et récupérée par le rapprochement » ;
- la ligne de statut de l'ADR-0005 changée en `Remplacée par ADR-0012` ;
- le test qui vérifie la **nouvelle** décision, nommé dans l'ADR-0012 :
  par exemple, qu'une signature fausse incrémente un compteur d'alerte.

Écrire les conséquences aurait suffi à faire apparaître le défaut : il est
difficile d'écrire « les réponses refusées ne sont plus renvoyées » sans
se demander ce qu'elles deviennent.

## 3. Où lancer les contrôles

Dans la CI, à chaque revue, comme `go test` :

```text
go vet ./...
go test -race -count=1 ./...
go run ./tools/adr docs/adr
go run ./tools/c4 .
```

Les deux derniers ne sont même pas nécessaires en plus si leurs règles
sont des tests, comme dans la leçon : `TestTheADRsOfTheProjectAreConsistent`
et `TestTheDomainDependsOnNoAdapter` tournent avec `go test ./...`. C'est
la meilleure forme : un contrôle qui fait partie de `go test` ne peut pas
être oublié dans un script. Les commandes `tools/adr` et `tools/c4`
restent utiles pour lire le détail en local.

## 4. « Le test existe », est-ce suffisant ?

Non. Le contrôle vérifie qu'une fonction de test porte ce nom ; il ne
vérifie pas qu'elle **teste la décision**. Un test renommé et vidé de son
contenu, ou un test qui vérifie autre chose, passerait le contrôle.

Ce qui vérifie qu'un test protège une décision, c'est la technique de tout
ce cours : **défaire la décision dans le code, et voir le test échouer**.
Pour l'ADR-0005, la mutation est simple : déplacer la vérification après
la réponse. Le test nommé doit être rouge. Une campagne de mutations par
ADR, une mutation par décision, le vérifie à chaque version.

## Le compte rendu, en cinq lignes

1. **Quoi** : la décision ADR-0005 (« vérifier avant de répondre ») a été
   défaite par la version 2.3 sans que personne ne le sache ; elle a mené
   aux 37 versements bloqués du 14 janvier.
2. **Pourquoi** : la revue a supprimé le test qui vérifiait la décision
   (« ancien comportement »), sans ouvrir l'ADR qui le citait.
3. **Pourquoi personne ne l'a vu** : le contrôle du dossier d'ADR, qui
   l'aurait signalé, n'était lancé nulle part.
4. **Correction** : les contrôles d'architecture et d'ADR sont des tests
   de `go test` ; une décision qui change passe par un ADR qui la
   remplace, dans la même revue ; chaque ADR vérifié a une mutation qui
   rend son test rouge.
5. **Ce qui reste ouvert** : reprendre les ADR existants pour ajouter
   « Vérifiée par » là où un test est possible, et corriger le contrôle
   pour qu'il ne vérifie les tests que des ADR acceptés (correction 1).

## Ce qu'il faut retenir

1. Supprimer le test d'une décision, c'est défaire la décision : la revue
   doit le voir comme tel.
2. Une décision acceptée change par un nouvel ADR, dans la même revue que
   le code, avec ses conséquences.
3. Les contrôles d'architecture et d'ADR sont des tests : ils tournent
   avec `go test`, partout.
4. Un test nommé dans un ADR doit échouer quand la décision est défaite :
   c'est ce que vérifie une mutation.
