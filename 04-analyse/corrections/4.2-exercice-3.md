# Correction 4.2 — Exercice 3 : un client qui réessaie

> Rappel de l'énoncé : calculer le pire cas du client à trois essais de
> 2 s ; trouver le défaut que montre son troisième test ; le refactorer
> autour d'un budget ; le mesurer.

La nouvelle version est dans `ex3/balance2` du module de correction,
verte sous `go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Pire cas du client d'origine : 7,5 s**, pour un scénario qui en
  accorde 0,35. Ses réglages (2 s, trois essais, une demi-seconde
  d'attente) ont été choisis sans le scénario.
- **Un défaut caché** : il dort une demi-seconde **après** le dernier
  échec, pour rien.
- **La nouvelle version** part du scénario : 300 ms pour tout l'appel, des
  essais de 120 ms au plus. p99 de 2,569 s à 196 ms, sans aucune erreur.
- La campagne a fait **supprimer** un réglage de plus, qui ne servait
  qu'à faire échouer des appels qui auraient réussi.

## 1. Le pire cas, et la mesure

Le client essaie trois fois. Chaque essai peut durer 2 s, et chaque échec
est suivi d'une attente de 500 ms, **y compris le dernier**. Pire cas :
3 × 2 s + 3 × 0,5 s = **7,5 s**.

La mesure de l'énoncé montrait un maximum de 5,028 s : deux essais sans
réponse (2 × 2 s + 2 × 0,5 s = 5 s), puis une réponse en une vingtaine de
millisecondes. Le p99 à 2,571 s correspond aux appels avec **un** essai
sans réponse : 2 s, la demi-seconde, puis la réponse. Avec un appel sur
vingt sans réponse, 5 % des appels sont dans ce cas, bien au-delà du 1 %
que le p99 tolère.

## 2. Le défaut que le test affiche

La ligne qu'affiche `go test -v ./ex3/balance` :

```text
    balance_test.go:43: three failures took 1.5s
```

Trois échecs instantanés prennent une seconde et demie : la boucle dort
après **chaque** échec, y compris le troisième, avant de rendre l'erreur.
Le test l'affiche avec `t.Logf`, et ne le vérifie pas. Une demi-seconde
perdue à chaque appel qui échoue, c'est autant de délai pour l'écran, qui
attend une erreur pour afficher le dernier solde connu.

## 3. La nouvelle version

```go
// Client tries at most Attempts times, each try at most Try long, and the
// whole call at most Budget long. The last try gets what is left of the
// budget, however short: the operator's normal answer takes 20 to 80 ms.
type Client struct {
    API      balance.API
    Budget   time.Duration // 300 ms: the scenario's 350, minus our own work
    Try      time.Duration // 120 ms: well above a normal answer
    Attempts int           // 3, as before
}
```

```go
func (c Client) Balance(ctx context.Context, wallet string) (int64, error) {
    ctx, cancel := context.WithTimeout(ctx, c.Budget) // the caller's deadline wins if shorter
    defer cancel()
    deadline, _ := ctx.Deadline()
    var errs []error
    for attempt := 1; attempt <= c.Attempts; attempt++ {
        left := time.Until(deadline)
        if left <= 0 {
            break
        }
        tctx, tcancel := context.WithTimeout(ctx, min(c.Try, left))
        b, err := c.API.Balance(tctx, wallet)
        tcancel()
        if err == nil {
            return b, nil
        }
        errs = append(errs, err)
    }
    return 0, errors.Join(append([]error{ErrBudget}, errs...)...)
}
```

Ce qui a changé, et pourquoi :

| Avant | Après | Raison |
|---|---|---|
| 2 s par essai | 120 ms par essai | une réponse normale prend 20 à 80 ms : au-delà de 120, elle ne viendra probablement pas |
| aucune limite totale | 300 ms pour tout l'appel | le scénario accorde 350 ms, et l'écran a son propre travail |
| 500 ms entre deux essais | aucune attente | l'opérateur ne répond pas, il n'est pas surchargé ; voir la remarque ci-dessous |
| attente après le dernier échec | aucune | le défaut de la section 2 |
| trois essais | trois essais | gardé |

Les trois tests d'origine sont gardés. Un seul change exprès, renommé
`TestThreeFailuresAreAnErrorAtOnce` : il vérifie maintenant que trois
échecs rendent l'erreur **tout de suite**. Trois tests s'ajoutent pour le
budget :

```go
func TestAHungOperatorCostsAtMostTheBudget(t *testing.T) {
    s := &script{steps: []string{"hang"}}
    start := time.Now()
    _, err := client(s).Balance(t.Context(), "w")
    took := time.Since(start)
    if !errors.Is(err, balance2.ErrBudget) || took > 330*time.Millisecond {
        t.Fatalf("%v after %v and %d calls", err, took, s.calls.Load())
    }
    if n := s.calls.Load(); n != 3 {
        t.Fatalf("%d tries, want 120 + 120 ms, then the 60 ms left", n)
    }
}
```

```go
func TestAShorterDeadlineOfTheCallerWins(t *testing.T) {
    s := &script{steps: []string{"hang"}}
    ctx, cancel := context.WithTimeout(t.Context(), 100*time.Millisecond)
    defer cancel()
    start := time.Now()
    if _, err := client(s).Balance(ctx, "w"); err == nil {
        t.Fatal("no error")
    }
    if took := time.Since(start); took > 130*time.Millisecond {
        t.Fatalf("took %v, the caller gave 100 ms", took)
    }
}
```

**Une remarque sur l'attente.** Supprimer l'attente entre deux essais est
juste **ici**, parce que l'opérateur perd des appels, il n'est pas
débordé. Si l'opérateur était surchargé, réessayer tout de suite
ajouterait de la charge au pire moment, et tous les clients
recommenceraient ensemble. Il faudrait alors une attente courte et
aléatoire, et un plafond sur la part des appels réessayés. Le bon réglage
dépend de **la façon dont la dépendance échoue** : une question à poser
avant de choisir les chiffres.

## 4. La mesure

Les deux clients, de la même façon, à 50 demandes par seconde en boucle
ouverte (`go run ./ex3/cmd/measure`) :

```text
retry client   500 requests  mean  222ms  p50   54ms  p90   79ms  p99 2.569s  max 2.581s  errors 0
budget client  500 requests  mean   60ms  p50   54ms  p90   79ms  p99  196ms  max  270ms  errors 0
```

Le p99 passe de 2,569 s à 196 ms, et le maximum de 2,6 s à 270 ms. Le
client d'origine a ici un maximum plus bas que dans l'énoncé (2,581 s
contre 5,028 s) : l'opérateur simulé tire ses pannes au hasard, et l'ordre
dans lequel les appels concurrents reçoivent leur tirage change d'une
exécution à l'autre. Cette fois, aucun appel n'a eu deux pannes de suite.

**Aucune erreur** avec le nouveau client : quand le premier essai ne
répond pas, le deuxième répond presque toujours. Si les deux échouent, le
troisième essai a les 60 ms restantes. Quand le client rend une erreur,
l'écran de la leçon affiche le dernier solde connu, avec sa date.

## 5. La campagne, et le réglage supprimé

La première version avait un réglage de plus, `MinTry` : ne pas commencer
un essai avec moins de 60 ms restantes. L'idée semblait prudente. La
campagne l'a trouvé inutile :

```text
budget total ignoré                          tuee
un essai prend tout le budget                tuee
essai commencé sans marge                    SURVIT
essais sans limite                           tuee
un essai de moins                            tuee
ErrBudget oubliée                            tuee
5/6 tuees
```

« essai commencé sans marge » survit : aucun test du scénario ne voit la
différence entre commencer ou non un essai avec 60 ms restantes. Et en y
regardant de près, la règle était **nuisible** : l'opérateur répond en 20
à 80 ms, donc un essai de 60 ms réussit souvent. La mesure avec cette
première version :

```text
budget client  500 requests  mean   59ms  p50   54ms  p90   78ms  p99  196ms  max  243ms  errors 3
```

Trois erreurs, que la version sans `MinTry` n'a pas : trois appels qui
auraient réussi avec le dernier essai. Le réglage a été supprimé, et la
campagne rejouée :

```text
budget total ignoré                          tuee
un essai prend tout le budget                tuee
essais sans limite                           tuee
un essai de moins                            tuee
ErrBudget oubliée                            tuee
5/5 tuees
```

C'est la deuxième fois dans ce cours qu'une mutation survivante désigne du
code à **supprimer** plutôt qu'un test à ajouter (la première était à
l'exercice 3 de la leçon 3.6). Un réglage qui n'est rattaché à aucun
scénario n'a pas de raison d'exister.

## Ce qu'il faut retenir

1. Un client avec des essais et des délais a un **pire cas** qu'on calcule
   en lisant le code : compare-le au scénario.
2. Les délais se déduisent du budget du scénario, de haut en bas : un
   délai total, des essais qui y tiennent, et l'échéance de l'appelant qui
   l'emporte si elle est plus courte.
3. La politique d'attente entre deux essais dépend de la façon dont la
   dépendance échoue : perte ou surcharge.
4. Un réglage qu'aucun scénario ne justifie, et qu'aucun test ne voit, se
   supprime.
