# Correction 4.2 — Exercice 2 : le budget d'erreur

> Rappel de l'énoncé : écrire `Remaining`, `BurnRate` et `Page` ;
> expliquer les deux fenêtres ; trouver le test qui passe sur le squelette.

La solution est dans `ex2/budget` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Le budget**, c'est la part de demandes qu'on a le droit de rater :
  0,1 % pour 99,9 %. Le **taux de consommation** (*burn rate*), c'est la
  part ratée divisée par cette part permise.
- **Deux fenêtres** : la longue dit que le budget brûle vraiment, la courte
  qu'il brûle **encore**. Sans la courte, on réveille quelqu'un pour un
  incident fini depuis quarante minutes.
- Un piège de calcul : en virgule flottante, 144 ratées sur 10 000 à
  99,9 % ne font pas 14,4, mais 14,399999999999986. Le test des seuils l'a
  trouvé.

## 1. La solution

```go
// Remaining is the share of the error budget still unspent: 1 - bad
// spent / budget, where the budget is (1 - slo) of the requests.
func Remaining(slo float64, w Window) (float64, error) {
    if err := check(slo); err != nil {
        return 0, err
    }
    if w.Total == 0 {
        return 1, nil
    }
    allowed := (1 - slo) * float64(w.Total)
    return 1 - float64(w.Bad)/allowed, nil
}
```

```go
// BurnRate is the share of bad requests over the share the SLO allows.
func BurnRate(slo float64, w Window) (float64, error) {
    if err := check(slo); err != nil {
        return 0, err
    }
    if w.Total == 0 {
        return 0, nil
    }
    return float64(w.Bad) / float64(w.Total) / (1 - slo), nil
}
```

```go
// Page applies the two pairs of windows of the SRE workbook: a long window
// says the budget is really burning, a short one says it still is.
func Page(slo float64, hour, fiveMin, sixHours, thirtyMin Window) (bool, error) {
    burns := make([]float64, 4)
    for i, w := range []Window{hour, fiveMin, sixHours, thirtyMin} {
        b, err := BurnRate(slo, w)
        if err != nil {
            return false, err
        }
        burns[i] = b
    }
    // In floating point, 144 bad of 10 000 at 99.9 % burns 14.399999999999986,
    // not 14.4: compare with a small tolerance.
    const eps = 1e-9
    fast := burns[0] >= 14.4-eps && burns[1] >= 14.4-eps
    slow := burns[2] >= 6-eps && burns[3] >= 6-eps
    return fast || slow, nil
}
```

Les seuils viennent du *Site Reliability Workbook* de Google, chapitre
*Alerting on SLOs*, qui définit le taux ainsi : « *Burn rate is how fast,
relative to the SLO, the service consumes the error budget* ». Il
recommande d'appeler quelqu'un quand 2 % du budget de trente jours brûle
en une heure (taux 14,4), ou 5 % en six heures (taux 6), et d'ouvrir un
ticket quand 10 % brûle en trois jours (taux 1).

**La tolérance.** `1 - 0.999` ne vaut pas exactement 0,001 en virgule
flottante, et le taux calculé pour 144 ratées sur 10 000 est
14,399999999999986. Une comparaison stricte `>= 14.4` dirait « pas
d'alerte » pile au seuil. Le test `TestTheThresholdsAreIncluded` le voit,
et la campagne le confirme (« seuil sans tolérance »). Une autre solution,
plus robuste encore : travailler en nombres entiers, en comparant
`bad * 1000` avec `total * 14.4`, ou en exprimant le SLO en
« pour cent mille ».

## 2. Pourquoi deux fenêtres

Imagine un incident de vingt minutes, à 10 % d'erreurs, qui s'arrête à
10 h 20. Avec la seule fenêtre d'une heure :

| Heure | Fenêtre d'une heure | Fenêtre de 5 minutes | Une heure seule | Les deux |
|---|---|---|---|---|
| 10 h 05 | 5 min à 10 % : taux 8,3 | taux 100 | pas d'alerte | pas d'alerte |
| 10 h 09 | taux 15 | taux 100 | **alerte** | **alerte** |
| 10 h 20 | taux 33 | taux 100 | alerte | alerte |
| 10 h 30 | taux 33 | taux 0 | **alerte**, alors que c'est fini | plus d'alerte |
| 11 h 05 | 15 min sur l'heure : taux 25 | taux 0 | alerte encore | plus d'alerte |

(Taux calculés pour 99,9 % : 10 % d'erreurs pendant 20 minutes d'une
heure font 3,3 % sur l'heure, soit un taux de 33.)

La fenêtre longue garde la mémoire de l'incident pendant une heure ; la
courte permet de **désarmer** l'alerte dès que le problème s'arrête. Le
*workbook* donne la règle de la fenêtre courte : un douzième de la longue,
cinq minutes pour une heure.

## 3. Le test qui passait sur le squelette

`TestAFastBurnThatIsOverDoesNotPage` vérifie qu'on **n'appelle pas** ; le
squelette rend `false` à tout, donc il passe. Il passait pour la mauvaise
raison : il ne vérifiait pas l'erreur. Pour qu'il échoue sur le squelette,
il suffit de la vérifier :

```text
if p, err := budget.Page(0.999, w(150), w(5), w(30), w(5)); err != nil || p {
```

Règle générale : un test qui vérifie une **absence** (pas d'alerte, pas
d'appel, rien d'envoyé) doit aussi vérifier que la fonction a vraiment
travaillé.

## 4. La campagne

```text
SLO de 0 ou 1 accepté                        tuee
budget dépensé au lieu de restant            tuee
fenêtre vide divisée                         tuee
divisé par le SLO                            tuee
fenêtre courte ignorée                       tuee
seuil sans tolérance                         tuee
seuil lent exclu                             tuee
brûlure lente oubliée                        tuee
8/8 tuees
```

Huit erreurs, toutes vues. Au premier passage, « brûlure lente oubliée »
ne compilait pas (la variable `slow` devenait inutilisée) ; elle a été
réécrite (`fast || (slow && false)`), puis rejouée.

## Ce qu'il faut retenir

1. Le budget d'erreur, c'est (1 − SLO) des demandes ; le taux de
   consommation, la part ratée sur la part permise.
2. On appelle quelqu'un quand une fenêtre longue **et** une fenêtre courte
   brûlent vite : la longue évite les fausses alertes, la courte les
   alertes d'un incident fini.
3. Les seuils en virgule flottante se comparent avec une tolérance, ou en
   entiers.
4. Un test d'absence doit vérifier que la fonction a travaillé.
