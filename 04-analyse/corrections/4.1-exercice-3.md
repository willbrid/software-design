# Correction 4.1 — Exercice 3 : des tests qui parlent la langue du métier

> Rappel de l'énoncé : dire pourquoi les tests du collègue cassent sur
> `tontine3b` ; les réécrire en paquet externe, dans la langue des critères ;
> vérifier qu'ils passent sur les deux versions ; comparer les campagnes.

La suite réécrite est dans `ex3/check3` du module de correction ; la même,
avec un autre chemin d'import, dans `ex3/check3b`. Les deux sont vertes
sous `go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- Les tests du collègue vérifiaient **comment** le code range ses données,
  pas **ce qu'il fait** pour les membres. Un rangement différent les casse,
  sans qu'une seule règle ait changé.
- Réécrits en paquet externe, une règle par test, avec des chiffres, ils
  passent sur les deux versions **sans changer une ligne**.
- Et ils voient **plus** d'erreurs : 10 sur 16 pour ceux du collègue, 13
  puis 16 pour la suite réécrite. Un test qui lit les champs n'est pas un
  test plus précis.

## 1. Pourquoi ils cassent

`TestNewCycleFillsTheMaps` vérifie que `c.order` a douze éléments et que
`c.paid` est vide. Pour un membre, ce qui compte est « chaque part a un
tour, et l'ordre est tiré ». Les deux disent presque la même chose, mais
le premier le dit **dans les mots du code**. Le jour où l'ordre devient une
liste d'indices, le test ne compile plus, alors que la règle tient
toujours.

`TestSettleReadsPaid` est pire : il **écrit** dans `c.paid` pour préparer
son scénario. Il ne vérifie pas que `Contribute` enregistre une
cotisation ; il le contourne. Si `Contribute` cessait d'enregistrer, ce
test passerait encore.

Ces tests vérifient l'**implémentation**. Ce qu'on attend d'eux, c'est
qu'ils vérifient le **comportement**, de façon qu'un refactoring qui garde
le comportement les laisse verts : c'est même la définition d'un
refactoring.

## 2. La suite réécrite

Chaque test énonce une règle du compte rendu, avec un exemple chiffré, et
n'utilise que l'API exportée :

```go
// R4: a missing share holds the pot until the grace day, then the fund
// advances it.
func TestAMissingShareHoldsThePotThenTheFundAdvancesIt(t *testing.T) {
    c := cycle(t)
    payAllBut(t, c, due, "Fon")
    if s, _ := c.Settle(1, due); s.Pay || !slices.Equal(s.Missing, []string{"Fon"}) {
        t.Fatalf("on the due date: %+v; want nothing paid, Fon missing", s)
    }
    // The days are written out, not computed from tontine.Grace: a test that
    // reads the constant of the code checks nothing about its value.
    if s, _ := c.Settle(1, due.AddDate(0, 0, 4)); s.Pay {
        t.Fatalf("on the 9th: %+v", s)
    }
    if s, _ := c.Settle(1, due.AddDate(0, 0, 5)); !s.Pay || s.Amount != 600_000 || s.Advanced != 50_000 {
        t.Fatalf("on the 10th: %+v; want 600000 paid, 50000 advanced", s)
    }
}
```

```go
// R5: paying on the due date, at any hour, is on time; then 5 % per
// started week.
func TestAPenaltyPerStartedWeek(t *testing.T) {
    for at, want := range map[time.Time]int64{
        due.Add(-time.Hour):     0,
        due.Add(23 * time.Hour): 0,
        due.AddDate(0, 0, 1):    2_500,
        due.AddDate(0, 0, 7):    2_500,
        due.AddDate(0, 0, 8):    5_000,
    } {
        c := cycle(t)
        c.Contribute(1, "Fon", at)
        if got, _ := c.Owed("Fon", due.AddDate(0, 0, 20)); got != want {
            t.Errorf("paid %s: owes %d, want %d", at.Format("Jan 2 15:04"), got, want)
        }
    }
}
```

```go
// R1: the draw can be done again by anybody, from the published seed.
func TestTheDrawCanBeDoneAgain(t *testing.T) {

        t.Fatalf("two draws with seed 7:\n%v\n%v", a, b)
    }
}
```

## 3. Sur les deux versions

La suite de `ex3/check3b` est la même, à deux lignes près
(`diff ex3/check3/rules_test.go ex3/check3b/rules_test.go`) :

```text
1c1

---
> package check3b_test
9c9
<       tontine "example/exercises41/ex3/tontine3"

```

```text
ok      example/corrections41/ex3/check3        1.019s
ok      example/corrections41/ex3/check3b       1.020s
```

L'alias d'import `tontine` est ce qui rend la copie triviale : le corps
des tests ne nomme jamais le paquet autrement.

Treize contre dix. La suite du collègue rate « versé avant l'échéance »
(il n'appelle jamais `Settle` avant le 5), « une part par membre » et
« tontine d'une part » (il ne crée jamais de membre à deux parts, ni de
tontine trop petite).

Trois erreurs survivent encore à la suite réécrite, et l'une est
instructive. **« avance dès le 9 »** change la constante `Grace` de 5 à 4.
Or le premier jet du test calculait ses dates avec `tontine.Grace - 1` et
`tontine.Grace` : la mutation déplaçait le code **et** le test, et le test
restait vert. Un test qui lit la constante du code ne vérifie rien sur sa
valeur. La règle du métier est « le 10 » ; le test doit écrire le 10 :

```go
    // The days are written out, not computed from tontine.Grace: a test that
    // reads the constant of the code checks nothing about its value.
    if s, _ := c.Settle(1, due.AddDate(0, 0, 4)); s.Pay {
        t.Fatalf("on the 9th: %+v", s)
    }
```

Les deux autres, « graine ignorée » et « manquants non triés », sont des
règles que la suite n'énonçait pas encore : deux tests de plus, et la
campagne rejouée :

## Ce qu'il faut retenir

1. Un test qui lit les champs, ou appelle les fonctions non exportées,
   vérifie l'implémentation. Il casse au premier refactoring, et ne voit
   pas forcément plus d'erreurs.
2. Un test externe, une règle, un exemple chiffré : c'est un critère
   d'acceptation, qui survit à tout refactoring qui garde le comportement.
3. Un test qui calcule ses valeurs attendues avec les constantes du code
   ne vérifie pas ces constantes. Écris les chiffres du métier.
