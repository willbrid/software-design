# Correction 4.1 — Exercice 2 : la règle R6

> Rappel de l'énoncé : écrire `Leave` et `Refund` pour que les neuf tests
> passent ; trouver les décisions que les tests ont prises sans le compte
> rendu ; repérer celle qui change l'ordre des autres, et écrire le message
> au groupe.

La solution est dans `ex2/tontine2` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Vingt lignes** pour `Leave` et `Refund`. Le code est facile ; ce qui
  ne l'est pas, ce sont les **six décisions** que les tests ont prises à la
  place du bureau.
- La plus lourde : retirer les tours d'un partant **avance d'un mois**
  tous les bénéficiaires qui venaient après lui. Des membres qui n'ont rien
  demandé bouffent plus tôt.
- La campagne a trouvé un **vrai défaut** dans la première version de la
  solution : une part payée d'avance pour le mois du départ était perdue.

## 1. La solution

```go
// month is the first month without member: they leave before its pot.
func (c *Cycle) Leave(member string, month int) error {
    if month < 1 || month > c.Months() {
        return fmt.Errorf("%w: %d", ErrMonth, month)
    }
    if c.shares[member] == 0 || !c.in(member, month) {
        return fmt.Errorf("%w: %q", ErrMember, member)
    }
    if slices.Contains(c.order[:month-1], member) {
        return fmt.Errorf("%w: %s", ErrEaten, member) // one turn taken is enough
    }
    // Their turns are all from month on: removing them moves every later
    // beneficiary one month earlier per turn removed.
    c.order = slices.DeleteFunc(c.order, func(n string) bool { return n == member })
    c.left[member] = month
    return nil
}
```

```go
var ErrStillIn = errors.New("has not left")
```

```go
// Refund is what is given back to member at the end of the cycle, once they
// have left: every share they paid, minus what they owe on the due date
// of the month they left. It is negative when they still owe the fund.
func (c *Cycle) Refund(member string) (int64, error) {
    l, gone := c.left[member]
    if !gone {
        return 0, fmt.Errorf("%w: %q", ErrStillIn, member)
    }
    var paid int64
    for _, byMember := range c.paid { // every month: a share paid in advance is given back too
        if _, ok := byMember[member]; ok {
            paid += c.owes(member)
        }
    }
    owed, err := c.Owed(member, c.Due(l))
    return paid - owed, err
}
```

Deux détails :

- **`slices.Contains(c.order[:month-1], member)`** : un seul tour pris
  avant le départ suffit à l'interdire. Avec deux parts, c'est la décision
  du test `TestTwoSharesAndOneTurnTakenCannotLeave`.
- **La boucle sur toutes les cotisations**, et pas seulement celles des
  mois avant le départ. Voir la campagne, section 4.

## 2. Les décisions des tests

Le compte rendu tient en cinq phrases. Les tests en ont tiré au moins six
décisions :

| # | Décision des tests | Le compte rendu | À faire valider ? |
|---|---|---|---|
| 1 | avec deux parts, **un** tour pris interdit de partir | « un membre qui a déjà bouffé » | **oui** : « a déjà bouffé » peut vouloir dire « a pris tous ses tours » |
| 2 | les autres gardent leur ordre, et **avancent** d'un mois par tour retiré | « ses tours sont retirés » | **oui**, impérativement : voir la section 3 |
| 3 | le mois de départ est « le premier mois sans lui », choisi par la trésorière | « à partir de son départ » | oui : qui fixe la date, et à partir de quand une demande compte-t-elle ? |
| 4 | une part jamais payée est due avec sa pénalité **arrêtée au départ** | « ses pénalités restent dues » | oui : sinon, la pénalité grossit chaque semaine jusqu'à la fin du cycle |
| 5 | le remboursement peut être **négatif** (le partant doit encore) | rien | oui : comment récupère-t-on l'argent ? |
| 6 | une part payée d'avance pour le mois du départ est **rendue** | rien | non : c'est la seule réponse honnête, l'argent n'est dans aucune cagnotte |

Aucune de ces décisions n'est absurde. Mais cinq sur six touchent à
l'argent ou à l'ordre des membres : c'est au bureau de les prendre. La
bonne pratique est de **présenter les tests** au bureau, traduits en
phrases : un test bien nommé se lit comme une règle.

## 3. Qui bouffe quand

La décision 2 est la plus lourde. Avec l'ordre tiré pour la leçon, si le
membre du dernier mois part au mois 4, rien ne change pour les autres :
son tour était le dernier. Mais s'il avait eu le tour de juin (le mois 8
d'un cycle qui commence en novembre), **tous** les bénéficiaires de juillet
à octobre auraient bouffé un mois plus tôt, et le cycle aurait fini en
septembre au lieu d'octobre. Le test
`TestTheirTurnsAreRemovedAndTheOthersKeepTheirOrder` le vérifie, et ne le
dit nulle part.

Avancer d'un mois arrange certains (l'argent arrive plus tôt) et en gêne
d'autres (celui qui comptait sur la cagnotte d'octobre pour la rentrée
scolaire). L'autre option, garder le calendrier et laisser un mois sans
bénéficiaire, a ses propres coûts. Le message au groupe :

```text
Bonjour à tous. Kum quitte la tontine à partir de février ; il n'avait pas
encore bouffé. Ce qu'il a cotisé lui sera rendu en fin de cycle, moins ses
pénalités.

Conséquence pour l'ordre : son tour (juin) est supprimé. Les bénéficiaires
de juillet à octobre bouffent un mois plus tôt (juin à septembre), et le
cycle se termine en septembre. La cagnotte passe à 550 000.

Si ce changement vous pose problème, dites-le avant le 20 : le bureau
peut aussi garder le calendrier et laisser juin sans bénéficiaire.
```

Le message dit **ce qui change pour chacun**, et laisse une porte. C'est
ce que le code ne peut pas faire.

## 4. La campagne

Au premier passage :

```text
mois non vérifié                             tuee
partir deux fois                             tuee
seul le premier mois compte                  tuee
tours gardés                                 NE COMPILE PAS
départ non noté                              tuee
mois du départ remboursé                     SURVIT
parts impayées remboursées                   tuee
pénalités non retenues                       NE COMPILE PAS
dette comptée à la fin du cycle              tuee
remboursement d'un présent                   tuee
7/10 tuees
```

Deux mutations ne compilaient pas (une fonction générique non instanciée,
une variable devenue inutile) : elles ont été réécrites. Et une a
survécu, « mois du départ remboursé » : la première version de `Refund`
ne parcourait que les mois **avant** le départ. La mutation, qui
incluait le mois du départ, n'était vue par aucun test.

En cherchant le test qui la tuerait, la question est apparue : que se
passe-t-il si le partant a **déjà payé** le mois de son départ, en
avance ? Sa part n'entre dans aucune cagnotte (il n'est plus là ce
mois-là), et la première version ne la rendait pas. La mutation
survivante était **plus juste que le code**. Le code a été corrigé, et un
test ajouté :

```go
// Added by the correction, after the campaign: a share paid in advance for
// the month of departure is not in any pot, so it is given back.
func TestASharePaidInAdvanceIsGivenBack(t *testing.T) {
    c := start(t, one(twelve))
    who := last(c)
    payAll(t, c, 3)
    c.Contribute(4, who, c.Due(4).AddDate(0, 0, -10))
    c.Leave(who, 4)
    if got, _ := c.Refund(who); got != 200_000 {
        t.Fatalf("refund %d, want 200000: four shares paid", got)
    }
}
```

Rejouée, avec les mutations réécrites :

```text
mois non vérifié                             tuee
partir deux fois                             tuee
seul le premier mois compte                  tuee
tours gardés                                 tuee
départ non noté                              tuee
aucune part remboursée                       tuee
part payée d'avance gardée                   tuee
pénalités non retenues                       tuee
dette comptée à la fin du cycle              tuee
remboursement d'un présent                   tuee
10/10 tuees
```

## Ce qu'il faut retenir

1. Des tests écrits avant le code prennent des décisions. Elles se
   valident comme des règles, avec le métier.
2. Une règle qui modifie un ordre ou un calendrier touche des gens qui
   n'ont rien demandé. Il faut le leur dire, avec ce qui change pour
   chacun.
3. Une mutation qui survit peut être plus juste que le code : avant
   d'écrire le test qui la tue, demande-toi laquelle des deux versions a
   raison.
