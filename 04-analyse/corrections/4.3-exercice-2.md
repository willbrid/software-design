# Correction 4.3 — Exercice 2 : chaque part paie son mois

> Rappel de l'énoncé : écrire `monthly.Check`, qui vérifie que les
> cotisations de chaque part font son montant chaque mois ; dire d'où vient
> la règle ; trouver un cas que seule elle voit, et un cas que seule la
> règle de la leçon voit.

La solution est dans `ex2/monthly` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Une somme par (mois, part)**, comparée au montant. Le seul piège est
  l'ordre : une `map` Go se parcourt dans un ordre aléatoire, et les mois
  doivent sortir triés.
- La règle vient d'une **contrainte** du diagramme, pas d'une
  multiplicité : « les cotisations d'une part pour un mois font son
  montant ». Elle mérite d'être écrite en note sur le diagramme.
- La campagne a montré qu'un test sur **deux** mois ne peut pas vérifier un
  ordre : il passe une fois sur deux par chance.

## 1. La solution

```go
func Check(c model.Cycle, cs []model.Contribution) []model.Violation {
    type key struct{ month, share string }
    paid, last := map[key]int64{}, map[key]int{}
    for _, ct := range cs {
        k := key{ct.Month, ct.Share}
        paid[k] += ct.Amount
        last[k] = max(last[k], ct.Line)
    }
    var out []model.Violation
    for _, m := range slices.Sorted(maps.Keys(c.Order)) {
        for _, s := range c.Shares {
            k := key{m, s.ID}
            if p := paid[k]; p != c.Amount {
                line := 0
                if p > c.Amount {
                    line = last[k]
                }
                out = append(out, model.Violation{Line: line, Rule: "monthly", Text: fmt.Sprintf("%s paid %d of %d in %s", s.ID, p, c.Amount, m)})
            }
        }
    }
    return out
}
```

## 2. D'où vient la règle

Ce n'est pas une multiplicité : `Cotisation "*" → "1" Part` dit qu'une
cotisation est pour une part, pas combien elles doivent faire ensemble.
C'est une **contrainte** qui relie plusieurs associations : les cotisations
d'une part, pour un mois, font le montant du cycle. En UML, une contrainte
s'écrit entre accolades, en note sur le diagramme :
`{la somme des cotisations d'une part pour un mois = le montant}`. Il faut
l'y ajouter : c'est une règle que le métier connaît, et que personne ne
voyait sur le dessin.

## 3. Ce que chaque règle voit seule

| Cas | Règle de la leçon (`part`) | Règle mensuelle |
|---|---|---|
| Ebai paie une part entière sur une demi-part (ligne 21) | vue | vue |
| Ebai ne paie rien en novembre | **pas vue** : il n'y a pas de ligne à contrôler | **vue** : P05 a 25 000 sur 50 000 |
| Divine paie 30 000 et Ebai 20 000 | **vue** : chacune a payé autre chose que sa moitié | **pas vue** : la part a bien 50 000 |

La règle de la leçon contrôle chaque **ligne** ; la règle mensuelle
contrôle chaque **part**, y compris quand il n'y a pas de ligne. Les deux
sont nécessaires : la première voit un mauvais partage, la seconde voit un
paiement qui manque.

## 4. La campagne

Au premier passage :

```text
trop payé ignoré                             tuee
pas assez ignoré                             tuee
dernière ligne lue, pas la plus grande       SURVIT
ligne du mauvais côté                        tuee
mois dans le désordre                        NE COMPILE PAS
3/5 tuees
```

- **« dernière ligne lue, pas la plus grande »** survit : tous les tests
  donnaient les lignes dans l'ordre du cahier. Un test les donne
  maintenant à l'envers.
- **« mois dans le désordre »** ne compilait pas ; réécrite avec
  `slices.Collect(maps.Keys(...))`, elle a **survécu** au passage suivant.
  Le test de l'ordre utilisait deux mois : une `map` de deux clés sort dans
  le bon ordre une fois sur deux, et le test passe par chance. Sur douze
  mois, la chance tombe à une sur 479 001 600 :

```go
// Added after the campaign: with two months, an unsorted map gives the
// right order one time in two, and the test above passes by luck. With
// twelve months, luck is one chance in 479 001 600.
func TestTwelveMonthsComeInOrder(t *testing.T) {
    c, _, _, err := notebook.Load("../../../e43/notebook/testdata", 50_000)
    if err != nil {
        t.Fatal(err)
    }
    c.Shares = c.Shares[:1] // P01, which pays nothing here
    vs := monthly.Check(c, nil)
    var months []string
    for _, v := range vs {
        months = append(months, v.Text[len(v.Text)-7:])
    }
    if len(months) != 12 || !slices.IsSorted(months) {
        t.Fatalf("%v", months)
    }
}
```

Rejouée avec les deux tests ajoutés :

```text
trop payé ignoré                             tuee
pas assez ignoré                             tuee
dernière ligne lue, pas la plus grande       tuee
ligne du mauvais côté                        tuee
mois dans le désordre                        tuee
5/5 tuees
```

## Ce qu'il faut retenir

1. Une règle sur un **ensemble** (une somme, un total) vient d'une
   contrainte, pas d'une multiplicité : écris-la en note sur le diagramme.
2. Contrôler les lignes et contrôler les totaux sont deux règles
   différentes, qui voient des erreurs différentes.
3. Un test d'ordre sur deux éléments est un pile ou face. Donne-lui assez
   d'éléments pour que le hasard ne puisse pas le faire passer.
