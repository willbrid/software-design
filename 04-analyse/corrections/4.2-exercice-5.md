# Correction 4.2 — Exercice 5 : le 5 décembre à 20 h

> Rappel de l'énoncé : le tableau de bord fait la moyenne des p99 des dix
> instances ; il plafonne à 300 ms pendant que des membres attendent deux
> secondes. Expliquer, calculer le vrai p99, corriger ce que les instances
> envoient, dater l'alerte, et rédiger le compte rendu.

La correction est dans `ex5/dash2` du module de correction, et l'outil
de vérification dans `ex5/cmd/truth` ; tout est vert sous `go vet ./...`
et `go test -race -count=1 ./...`.

## En bref

- **On ne fait pas la moyenne de percentiles.** Le p99 de i07 est de deux
  secondes, celui des neuf autres de 90 ms : la moyenne fait 300 ms, et ne
  correspond à aucune requête. Le vrai p99 de la soirée est de **2 s**.
- **Ce qui s'additionne, ce sont des comptes.** Chaque instance envoie le
  nombre de requêtes par tranche de latence (69 nombres par minute) ; le
  tableau de bord les additionne, puis calcule le percentile.
- Avec la correction, l'alerte se déclenche à **20 h 14**, au lieu de
  jamais.
- La meilleure ligne du tableau de bord est **la part de requêtes qui ont
  raté 350 ms** : 3,2 % pendant vingt minutes. Elle s'additionne, et elle
  se relie directement au budget d'erreur de l'exercice 2.

## 1. Pourquoi la ligne plafonne à 300 ms

Chaque instance calcule son p99 correctement. Pendant l'incident :

- i07 : trois requêtes sur dix prennent deux secondes, son p99 est de
  2 s ;
- les neuf autres : leur p99 est de 90 ms.

La moyenne des dix est (9 × 90 + 2 000) / 10 ≈ 300 ms. Mais le p99 de
**toutes** les requêtes est autre chose : 3 % des requêtes de la soirée
(un dixième des requêtes, dont trois sur dix sont lentes) prennent deux
secondes, soit plus que le 1 % que le p99 laisse au-dessus de lui. Le
vrai p99 est donc d'environ 2 s.

L'erreur n'est dans aucune instance : elle est dans l'**agrégation**. Un
percentile ne s'agrège pas par moyenne, ni par maximum, ni par aucune
opération sur les percentiles eux-mêmes. Il faut repartir des mesures, ou
de quelque chose qui les résume et s'additionne.

## 3. La correction : envoyer des comptes

Une instance ne peut pas envoyer toutes ses latences, mais elle peut
envoyer **combien** de requêtes sont tombées dans chaque tranche :

```go
// Bounds are the upper bounds of the buckets each instance counts into:
// every 10 ms up to 500 ms, then every 250 ms up to 5 s. With the bucket
// beyond 5 s, 69 counts per instance and per minute, plus the two counts of
// the objective.
var Bounds = func() []time.Duration {
    var b []time.Duration
    for ms := 10; ms <= 500; ms += 10 {
        b = append(b, time.Duration(ms)*time.Millisecond)
    }
    for ms := 750; ms <= 5000; ms += 250 {
        b = append(b, time.Duration(ms)*time.Millisecond)
    }
    return b
}()

// Report is what one instance sends for one minute.
type Report struct {
    Counts []int // Counts[i]: requests up to Bounds[i]; the last one, beyond
    Good   int   // requests within Objective
    Total  int
}
```

```go
// Report is what one instance sends for one minute.
type Report struct {
    Counts []int // Counts[i]: requests up to Bounds[i]; the last one, beyond
    Good   int   // requests within Objective
    Total  int
}
```

```go
// Merge adds the reports of all instances: counts add up.
func Merge(rs []Report) Report {
    m := Report{Counts: make([]int, len(Bounds)+1)}
    for _, r := range rs {
        for i, c := range r.Counts {
            m.Counts[i] += c
        }
        m.Good += r.Good
        m.Total += r.Total
    }
    return m
}
```

```go
// Percentile is the upper bound of the bucket that holds the p-th
// percentile: never below the true value, at most one bucket above.
func (r Report) Percentile(p float64) time.Duration {
    rank := int(float64(r.Total)*p/100 + 0.999999)
    seen := 0
    for i, c := range r.Counts {
        if seen += c; seen >= rank {
            if i == len(Bounds) {
                return Bounds[len(Bounds)-1] + time.Nanosecond // beyond the last bound
            }
            return Bounds[i]
        }
    }
    return 0
}
```

Deux propriétés, vérifiées par les tests :

- **la fusion est exacte** : additionner les comptes de deux instances
  donne exactement les comptes de toutes leurs requêtes ;
- **le percentile des tranches n'est jamais optimiste** : il rend la borne
  haute de la tranche, donc une valeur au moins égale au vrai p99, et au
  plus une tranche au-dessus. La colonne « merged p99 » affiche 2,25 s
  pour un vrai p99 de 2,07 s : c'est la tranche de 2 à 2,25 s.

C'est ce que font les histogrammes de Prometheus, par exemple : chaque
instance expose des compteurs par tranche, et le serveur les additionne
avant de calculer un quantile. La documentation de Prometheus le dit à
propos des quantiles calculés sur chaque instance : « *you cannot aggregate
quantiles (e.g. to calculate the total 90th percentile latency for a
service backed by multiple replicated workers)* »
([Histograms and summaries](https://prometheus.io/docs/practices/histograms/)). Le choix des tranches est une décision :
elles doivent être fines **autour de l'objectif** (ici, tous les 10 ms
jusqu'à 500 ms) pour que l'alerte soit précise.

## 4. L'alerte

Avec les comptes, la ligne « p99 » dépasse 350 ms dès 20 h 10, et l'alerte
(cinq minutes au-dessus du seuil) part à **20 h 14**. La ligne « part
ratée au-delà de 1 % » se déclenche à la même minute.

## 5. La part ratée, et le budget

La part des requêtes qui ont raté 350 ms se calcule avec deux nombres par
instance : celles qui ont tenu l'objectif, et le total. Ces deux nombres
**s'additionnent** d'une instance à l'autre, et d'une minute à l'autre :
la part ratée de la soirée entière est exactement (total − bonnes) /
total, toutes instances confondues.

C'est le SLI de l'exercice 2. L'objectif « 99 % des requêtes sous 350 ms »
laisse 1 % de requêtes ratées ; pendant l'incident, 3,2 % : un taux de
consommation de 3,2. Sur vingt minutes, c'est peu du budget du mois, ce
qui est la bonne nouvelle. La mauvaise est que la règle d'appel du
*workbook* demande un taux de 14,4 sur une heure : **elle n'aurait pas
appelé** pour cet incident non plus, à juste titre, puisque 97 % des
requêtes passaient. Ce qui manquait n'était pas une alerte qui réveille,
mais une ligne juste sur le tableau de bord, que l'équipe de garde aurait
vue en répondant aux membres.

## Le compte rendu, en cinq lignes

1. **Quoi** : le 5 décembre, de 20 h 10 à 20 h 30, l'instance i07 a
   répondu en deux secondes à trois requêtes sur dix ; 3,2 % de toutes les
   requêtes ont raté l'objectif de 350 ms, et des membres se sont plaints.
2. **Pourquoi** : un disque lent sur i07 (cause technique à part, à
   corriger par l'exploitation).
3. **Pourquoi personne ne l'a vu** : le tableau de bord faisait la moyenne
   des p99 des instances, ce qui donnait 300 ms au lieu de 2 s ; l'alerte
   à 350 ms ne pouvait pas se déclencher.
4. **Correction** : chaque instance envoie des comptes par tranche de
   latence et le nombre de requêtes sous l'objectif ; le tableau de bord
   les additionne avant de calculer le p99 et la part ratée ; l'alerte
   aurait sonné à 20 h 14.
5. **Ce qui reste ouvert** : retirer du répartiteur une instance dont la
   part ratée dépasse nettement celle des autres, et revoir les autres
   graphiques qui agrègent des percentiles.

## Ce qu'il faut retenir

1. Un percentile ne s'agrège pas : ni moyenne, ni maximum de percentiles.
2. Ce qui s'agrège, ce sont des comptes : des histogrammes à tranches
   fixes, ou le nombre de requêtes bonnes et totales.
3. Des tranches fines autour de l'objectif rendent le percentile des
   tranches précis là où il compte.
4. La part ratée est le meilleur indicateur d'un scénario de latence : elle
   s'additionne, et elle se compare au budget d'erreur.
