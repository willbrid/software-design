# Correction 3.4 — Exercice 5 : jamais lent, jamais perdu

> Rappel de l'énoncé : la version 2 du bus confie à une goroutine chaque
> événement qui trouve sa file pleine. Pendant une soirée où l'opérateur SMS
> ralentit, les goroutines montent, le déploiement plante sur
> `send on closed channel`, et des SMS manquent. Expliquer, chiffrer,
> corriger, et écrire le test qui manquait.

La simulation de la version 3 et le test de non-régression sont dans `ex5/`
du module de correction, vert sous `go vet ./...` et
`go test -race -count=1 ./...`.

## En bref

- Une seule ligne, `go func() { q.ch <- env }()`, produit les trois
  symptômes. La file n'est plus bornée par sa taille : elle continue dans
  des goroutines. Celles-ci meurent quand `Close` ferme le canal.
- **460 SMS** perdus dans la simulation, sans un mot dans les journaux : les
  64 de la file, environ 395 qui attendaient dans des goroutines, et celui
  que l'abonné traitait.
- « Jamais lent, jamais perdu » est **impossible** en mémoire dès que
  l'abonné traite moins vite qu'on ne publie. Il faut choisir, et mesurer
  ce qu'on a choisi. La version 3 est le bus de la leçon, réglé en `Drop`
  pour le SMS, avec deux métriques de plus.
- Le test qui manquait **bloque** un abonné et publie plus que sa file.

## 1. Trois symptômes, une ligne

La ligne en cause, dans le `Publish` de l'énoncé :

```text
select {
case q.ch <- env:
default:
    go func() { q.ch <- env }()
}
```

**Les goroutines qui montent.** Pendant l'incident, l'abonné traite environ
94 événements par seconde (141 entre t = 1 s et t = 2,5 s), et on en publie
400. La file de 64 est pleine en un quart de seconde. Ensuite, chaque
événement en trop crée **une goroutine bloquée** sur l'envoi. Leur nombre
monte de 300 par seconde environ : 15, 91, 168, 244, 321, 397 dans la
sortie. Chacune garde sa pile et son événement : 1 088 Kio de piles à
t = 2,5 s, contre 288 au départ. Sur une vraie soirée de trois heures,
c'est l'`OOMKilled`.

**Le `panic: send on closed channel`.** `Close` ferme chaque file. Or des
centaines de goroutines sont bloquées sur `q.ch <- env`. La spécification
du langage ([Send statements](https://go.dev/ref/spec#Send_statements)) est formelle : « *A send on a closed channel proceeds by causing
a run-time panic.* » Il y en
a une par goroutine en attente, dans une goroutine que personne ne
rattrape, et le processus s'arrête avec le code 2. Le verrou de `Publish`
ne protège plus rien : `Publish` a rendu la main depuis longtemps, c'est la
goroutine anonyme qui envoie.

**Les SMS manquants.** À t = 2,5 s : 1 000 publiés, 540 traités. Les 460
autres étaient dans la file (64), dans des goroutines en attente (397,
moins la goroutine du programme et celle de l'abonné, soit 395), ou en
cours de traitement (1). Le processus meurt avec eux. Aucun journal ne les mentionne : V2 ne compte rien, puisqu'elle
promet de ne rien perdre.

Et le tableau de bord est resté vert, parce qu'il suivait **la seule
mesure que V2 garantit** : `Publish` ne dépasse jamais 266 µs. C'est vrai,
et c'est ce qui cache tout le reste.

## 2. Pourquoi les tests sont restés verts

Le chiffre est `Size: 1024`, dans le test d'ordre de `ex5/notify` :

```text
b := &notify.Async[int]{Size: 1024}
```

Ce test publie 1 000 événements. Avec une file de 1 024, elle n'est
**jamais pleine**, et la branche `default` n'est jamais exécutée. Le test de
la leçon utilisait une file de 8 : sur V2, il échoue sous `-race` (course
entre `close` et l'envoi de la goroutine, puis panique). Quelqu'un a
« réparé » le test en agrandissant la file, au lieu de lire ce qu'il
disait. Aucun autre test ne remplit une file : le seul chemin nouveau de V2
n'a jamais été exécuté par la suite.

## 3. « Jamais lent, jamais perdu » : impossible en mémoire

Pendant l'incident :

| | par seconde |
|---|---|
| événements publiés | 400 |
| événements traités | environ 94 |
| retard qui s'accumule | environ 306 |

Sur 1,5 s, le retard atteint environ 460 événements, ce que la mesure
confirme (1 000 − 540). Une file de taille finie ne peut absorber qu'un
temps fini : 64 places, c'est 0,2 s. Au-delà, il ne reste que trois
choix :

1. **ralentir celui qui publie** (`Block`) : c'est « lent » ;
2. **jeter et compter** (`Drop`) : c'est « perdu » ;
3. **stocker ailleurs**, sans limite : la mémoire du processus, comme V2,
   et alors tout est perdu au premier arrêt. Ou un disque, dans une base,
   avec l'événement écrit dans la transaction du virement : l'outbox du
   niveau 8.

La demande était donc mal posée. Elle se reformule en une décision métier :
**pour le SMS « virement reçu »**, quand l'opérateur ralentit, préfère-t-on
des virements plus lents ou des SMS manquants ?

## 4. La version 3, mesurée

La version 3, c'est le bus de la leçon, avec sa politique explicite. Même
simulation, en `Drop` puis en `Block` (`ex5/cmd/sim drop`, `ex5/cmd/sim
block`).

En `Drop` :

```text
t=1000ms published  399 handled  398 out of order   0 goroutines    2 stacks   288 KiB slowest Publish 78µs
t=1250ms published  498 handled  421 out of order   0 goroutines    2 stacks   288 KiB slowest Publish 78µs
t=2500ms published  997 handled  540 out of order   0 goroutines    2 stacks   288 KiB slowest Publish 78µs
deploy: Close
t=3000ms published  997 handled  605 out of order   0 goroutines    1 stacks   288 KiB slowest Publish 78µs
Close took 658ms, dropped 392
```

En `Block` :

```text
t=1000ms published  398 handled  397 out of order   0 goroutines    2 stacks   288 KiB slowest Publish 158µs
t=1250ms published  486 handled  421 out of order   0 goroutines    2 stacks   288 KiB slowest Publish 10.334ms
t=1500ms published  510 handled  445 out of order   0 goroutines    2 stacks   288 KiB slowest Publish 12.111ms
t=2500ms published  607 handled  542 out of order   0 goroutines    2 stacks   288 KiB slowest Publish 12.395ms
deploy: Close
t=3000ms published  607 handled  607 out of order   0 goroutines    1 stacks   288 KiB slowest Publish 12.395ms
Close took 673ms, dropped 0
```

- **`Drop`** : deux goroutines, jamais plus ; 288 Kio de piles du début à la
  fin ; aucun plantage ; `Close` vide les 64 de la file en 658 ms et le
  programme sort avec le code 0. Le prix : 392 SMS jetés, mais **comptés**.
- **`Block`** : rien n'est jeté, mais le publieur avance au rythme de
  l'opérateur. `Publish` monte à 12 ms, et surtout, à t = 2,5 s, il n'y a eu
  que **607** virements au lieu de 1 000. Dans un vrai serveur, chaque
  requête de virement attendrait sa place : c'est la banque entière qui
  tourne à la vitesse de l'opérateur SMS.

La décision pour ce SMS : **`Drop`**. Un SMS « virement reçu » qui arrive
avec dix minutes de retard n'informe plus personne ; un virement ralenti
par un SMS est inacceptable. Mais `Drop` n'est honnête qu'avec ce que le
tableau de bord doit maintenant afficher :

- le **nombre d'événements jetés par seconde**, par abonné, avec une
  alerte dès qu'il n'est plus nul : c'est le signal que V2 cachait ;
- la **longueur de chaque file** : elle monte avant que quoi que ce soit ne
  soit jeté, et elle donne l'alerte plus tôt ;
- la **latence de l'opérateur**, vue par l'abonné : c'est la cause ;
- la durée de **`Close`** au déploiement, comparée au délai de grâce de
  l'orchestrateur : au-delà, le `SIGKILL` emporte la file.

Une variante raisonnable : attendre un peu (quelques millisecondes), puis
jeter. Elle absorbe les à-coups sans laisser l'opérateur dicter le rythme.
Elle se construit avec un `ctx` court passé à `Publish` en politique
`Block`, et se mesure comme le reste.

## 5. Le test qui aurait empêché la version 2 de partir

Un abonné **bloqué**, une file de 8, 500 événements publiés, puis `Close`.
Quelle que soit la politique, deux propriétés : le nombre de goroutines
reste borné, et `Close` ne panique pas et rend la main.

```go
// stuck fills the queue of a subscriber that does not move, publishes 500
// more events, then lets it go and closes the bus. Whatever the policy, the
// number of goroutines must stay bounded and Close must return.
func stuck(t *testing.T, b publisher, subscribe func(func(context.Context, int) error)) {
    t.Helper()
    gate := make(chan struct{})
    subscribe(func(context.Context, int) error { <-gate; return nil })
    before := runtime.NumGoroutine()
    for i := range 500 {
        _ = b.Publish(context.Background(), i)
    }
    if n := runtime.NumGoroutine(); n > before+10 {
        t.Errorf("goroutines went from %d to %d while one subscriber was stuck", before, n)
    }
    close(gate)
    b.Close() // must neither panic nor hang
}
```

```go
func TestAStuckSubscriberCostsABoundedAmount(t *testing.T) {
    b := &bus.Async[int]{Size: 8, Policy: bus.Drop}
    stuck(t, b, func(h func(context.Context, int) error) { _, _ = b.Subscribe(h) })
    if got := b.Dropped(); got < 490 {
        t.Fatalf("dropped %d, want the events that found the queue full counted", got)
    }
}
```

Sur la version 3 :

```text
--- PASS: TestAStuckSubscriberCostsABoundedAmount (0.00s)
ok      example/corrections34/ex5/regress       1.015s
```

Sur la version 2, par une sonde derrière une étiquette de compilation :

```text
=== RUN   TestV2AStuckSubscriberCostsABoundedAmount
    v2_probe_test.go:15: goroutines went from 3 to 494 while one subscriber was stuck
panic: send on closed channel
...
FAIL    example/corrections34/ex5/regress       0.029s
```

Le message dit le premier symptôme (494 goroutines pour un abonné bloqué),
la panique dit le deuxième. Le test tient en vingt lignes, et sans
`time.Sleep` : c'est l'abonné bloqué sur `gate`, ouvert quand le test le
décide, qui rend la situation certaine.

## Le compte rendu, en cinq lignes

1. **Quoi** : 460 SMS « virement reçu » jamais envoyés, et un plantage au
   déploiement, le jeudi soir.
2. **Pourquoi** : la V2 transformait chaque événement en trop en goroutine
   bloquée, sans limite et sans compteur ; `Close` les a fait paniquer.
3. **Pourquoi personne ne l'a vu** : le tableau de bord suivait la latence
   de `Publish`, que la V2 garantissait par construction, et le seul test
   qui remplissait une file avait été agrandi pour passer.
4. **Correction** : V3 = politique `Drop` explicite pour le SMS, file
   bornée, compteur `Dropped` et longueur de file sur le tableau de bord.
5. **Ce qui reste ouvert** : le webhook marchand et l'audit ne doivent pas
   passer par ce bus (exercice 4) ; l'outbox est à planifier.

## Ce qu'il faut retenir

1. Une file en mémoire a une taille. Quand elle est pleine, il faut
   ralentir ou jeter. Une goroutine par événement en trop, c'est une file
   sans taille qui finira dans le `OOMKilled`.
2. Ne mesure jamais seulement ce que ton code garantit par construction :
   mesure ce qu'il **abandonne** (événements jetés, files qui montent).
3. Un test qui échoue en remplissant une file a trouvé un bug ; agrandir la
   file pour le faire passer, c'est effacer le message.
4. Une exigence comme « jamais lent, jamais perdu » se discute avec des
   chiffres : rythme d'arrivée, rythme de traitement, taille de la file.
