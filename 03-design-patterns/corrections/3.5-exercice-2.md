# Correction 3.5 — Exercice 2 : le contrôle d'une table

> Rappel de l'énoncé : écrire `check.Problems`, qui trouve dans n'importe
> quelle table les couples ambigus, les fins qui ont une sortie, les statuts
> coincés et les statuts inatteignables ; puis expliquer deux des tests
> fournis.

Le module de correction est vert sous `go vet ./...` et
`go test -race -count=1 ./...`. Les huit tests de l'énoncé sont recopiés sans
changement ; la correction en ajoute deux, expliqués à la section 3.

## En bref

- Deux parcours suffisent : **en avant** depuis `start` (qui est
  atteignable ?), **en arrière** depuis les fins (qui peut finir ?). Un
  statut coincé, c'est un statut atteint, non final, que le parcours arrière
  n'a pas touché.
- Une implémentation plus simple, « coincé = sans sortie », passe sept tests
  sur huit. Seule la boucle `B ⇄ C` la démasque : on peut avoir des sorties
  et ne jamais finir.
- Les tests fournis laissaient passer deux erreurs : une sortie non triée
  (qui échoue **12 fois sur 100**), et un doublon répété. Deux tests de plus
  les ferment.

## 1. La solution

```go
func Problems(start string, finals []string, table []Transition) []string {
    var out []string
    next := map[string][]string{} // status -> statuses one event away
    prev := map[string][]string{} // status -> statuses one event before
    all := map[string]bool{start: true}
    seen := map[[2]string]bool{}
    for _, t := range table {
        pair := [2]string{t.From, t.On}
        if seen[pair] {
            out = append(out, fmt.Sprintf("ambiguous: %s on %s", t.From, t.On))
        }
        seen[pair] = true
        next[t.From] = append(next[t.From], t.To)
        prev[t.To] = append(prev[t.To], t.From)
        all[t.From], all[t.To] = true, true
    }
    final := map[string]bool{}
    for _, f := range finals {
        final[f], all[f] = true, true
        if len(next[f]) > 0 {
            out = append(out, "final with exit: "+f)
        }
    }

    reached := walk([]string{start}, next) // forward from start
    canEnd := walk(finals, prev)           // backward from the finals
    for s := range all {
        switch {
        case !reached[s]:
            out = append(out, "unreachable: "+s)
        case !final[s] && !canEnd[s]:
            out = append(out, "stuck: "+s)
        }
    }
    slices.Sort(out)
    return slices.Compact(out)
}
```

```go
// walk returns every status reachable from from through links.
func walk(from []string, links map[string][]string) map[string]bool {
    seen := map[string]bool{}
    todo := slices.Clone(from)
    for len(todo) > 0 {
        s := todo[len(todo)-1]
        todo = todo[:len(todo)-1]
        if seen[s] {
            continue
        }
        seen[s] = true
        todo = append(todo, links[s]...)
    }
    return seen
}
```

Ligne par ligne :

- `next` et `prev` sont le même graphe, dans les deux sens. Les construire
  ensemble, en une boucle sur la table, évite qu'ils divergent.
- `all` réunit tous les statuts cités : par la table, par les fins, et le
  départ. Une fin que **personne** n'atteint n'apparaît que dans `finals` :
  sans cet ajout, elle passerait inaperçue (c'est le cas de
  `TestAStatusNobodyReachesIsReported`).
- `walk` est un parcours en profondeur, avec une pile. Le même code sert aux
  deux sens : seul le graphe change.
- Le `switch` donne la priorité à « inatteignable » : un statut qu'on
  n'atteint pas n'est jamais aussi déclaré coincé.
- `slices.Sort` puis `slices.Compact` : la sortie ne dépend ni de l'ordre de
  la table, ni de l'ordre de parcours des `map`, et chaque problème n'y
  figure qu'une fois.

Appliquée à la table des paiements de la leçon : `nil`. Appliquée aux tables
des exercices 3 et 4, elle sert de garde avant la mise en production.

## 2. Les deux questions

**Pourquoi `TestALoopWithoutExitIsStuck` ?** La première idée pour
« coincé », c'est « un statut non final **sans sortie** » :
`len(next[s]) == 0`. Elle passe sept tests sur huit, dont
`TestAStatusWithNoWayToAFinalIsStuck`, où `Unknown` n'a plus aucune sortie.
La campagne le confirme : le seul test qui voit cette erreur est celui de la
boucle.

```text
coincé = sans sortie                     TestALoopWithoutExitIsStuck
```

`B` et `C` ont chacun une sortie, mais l'une mène à l'autre et réciproquement :
un dossier qui passe de « en révision » à « à compléter » et retour, sans
jamais pouvoir être accepté ni refusé. C'est le blocage le plus courant dans
une vraie table, et le plus difficile à voir à l'œil.

**Pourquoi un statut inatteignable n'est-il pas aussi « coincé » ?** Dans
`TestAnUnreachableStatusIsNotAlsoStuck`, `Archived` ne mène qu'à lui-même :
il ne peut pas finir. Le déclarer aussi « coincé » donnerait deux messages
pour **un** problème, et le second égarerait : on chercherait comment faire
sortir de `Archived` des paiements qui n'y entrent jamais. La vraie question
est « pourquoi personne n'y arrive ? ». C'est aussi ce que dit la
documentation de la fonction : *a **reachable** status that is not final*.

## 3. La campagne, et les deux tests ajoutés

Neuf erreurs plausibles, chacune seule, avec les huit tests de l'énoncé :

```text
coincé = sans sortie                         tuee
ambiguïtés ignorées                          tuee
fins avec sortie ignorées                    tuee
parcours avant à l'envers                    tuee
« peut finir » depuis start                  tuee
pas de tri                                   SURVIT
fins absentes de la liste des statuts        tuee
inatteignable aussi déclaré coincé           tuee
doublons gardés                              SURVIT
7/9 tuees
```

**« pas de tri » survit, mais pas toujours.** Sans `slices.Sort`, l'ordre des
statuts coincés ou inatteignables est celui du parcours de la `map` `all`,
que Go tire au hasard à chaque exécution. Le seul test qui en a deux à la fois
est celui de la boucle (`B` et `C`), et il tombe juste la plupart du temps :

```text
$ go test -count=100 -run TestALoopWithoutExitIsStuck ./ex2/check/ | grep -c -- "--- FAIL"
12
```

Douze échecs sur cent : la campagne a eu de la chance, et l'intégration
continue en aurait moins. Un test qui échoue **parfois** est pire qu'un test
qui échoue toujours : on le relance, il passe, et l'on conclut à un test
instable. Le test ajouté met six statuts inatteignables dans le désordre :
la probabilité de tomber juste par hasard est de 1 sur 720.

**« doublons gardés » survit toujours** : aucun test ne répète trois fois
la même ligne. Sans `Compact`, une table qui répète trois fois un couple
donne deux lignes « ambiguous » identiques.

```go
// Added by the correction: the order of a map must not reach the output.
func TestProblemsAreSortedWhateverTheTableOrder(t *testing.T) {
    table := slices.Clone(payout)
    for _, s := range []string{"F", "B", "E", "A", "D", "C"} {
        table = append(table, Transition{s, "noop", s})
    }
    expect(t, Problems("Requested", finals, table),
        "unreachable: A", "unreachable: B", "unreachable: C",
        "unreachable: D", "unreachable: E", "unreachable: F")
}
```

## Ce qu'il faut retenir

1. « Peut finir » se calcule **à l'envers**, depuis les fins. C'est plus
   simple et plus juste que de chercher les impasses.
2. Une boucle sans sortie vers une fin est un blocage, même si chaque
   statut a une sortie.
3. Une sortie qui passe par une `map` se trie, sinon elle dépend du hasard,
   et les tests aussi.
4. Un test qui échoue une fois sur dix n'est pas instable : il a trouvé un
   bogue qui dépend de l'ordre.
