# Correction 3.3 — Exercice 2 : deux middlewares, et l'ordre qui les lie

> Rappel de l'énoncé : écrire `RequireKey` (un proxy qui contrôle l'accès) et
> `Recover` (un décorateur qui transforme une panique en 500), puis trouver
> l'ordre qui satisfait trois exigences de journal.

Le code de cette correction vit dans un module vert sous `go vet ./...` et
`go test -race -count=1 ./...`. Le paquet `before` est le paquet `mw` de
l'énoncé augmenté des deux middlewares ; le paquet `mw` est la version
corrigée.

## En bref

- `RequireKey` refuse **avant** d'appeler la suite et ne la rappelle jamais
  après un refus. Il se méfie d'une clé vide, même présente dans sa propre
  configuration.
- `Recover` transforme une panique en 500 **seulement si rien n'est encore
  parti**, et laisse passer `http.ErrAbortHandler`, comme la documentation de
  `net/http` le demande.
- Aucun des six ordres ne satisfait les trois exigences : « journaliser le
  401 » veut le journal **au-dessus** du contrôle de clé, « journaliser le
  marchand » le veut **au-dessous**. L'information doit **remonter**, et
  l'ordre seul ne la fait pas remonter. Une case posée par le journal et
  remplie par le contrôle de clé le permet, sans toucher aux middlewares.

## 1. `RequireKey`

```go
// RequireKey lets a request through only with a known API key, and puts the
// key's merchant in the request's context.
func RequireKey(keys map[string]string) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, req *http.Request) {
            key, ok := strings.CutPrefix(req.Header.Get("Authorization"), "Bearer ")
            merchant, known := keys[key]
            if !ok || key == "" || !known {
                w.Header().Set("WWW-Authenticate", "Bearer")
                http.Error(w, "unauthorized", http.StatusUnauthorized)
                return
            }
            next.ServeHTTP(w, req.WithContext(WithMerchant(req.Context(), merchant)))
        })
    }
}
```

Trois détails, chacun tenu par un test :

- **Le schéma compte.** `strings.CutPrefix` dit si l'en-tête commence par
  `Bearer `. Sans ce contrôle, un en-tête `Authorization: k-1` passerait.
- **La clé vide est refusée explicitement.** Une clé lue dans une variable
  d'environnement absente vaut `""`, et `Authorization: Bearer ` (avec
  l'espace) donne une clé vide. Sans le `key == ""`, une configuration
  `{"": "m-0"}` ouvrirait l'API à quiconque envoie cet en-tête. La campagne
  ci-dessous a montré que le premier jeu de tests ne le vérifiait pas.
- **Le `return` après le refus.** `http.Error` n'arrête rien : sa
  documentation le dit (« It does not otherwise end the request »). Sans
  `return`, le handler suivant s'exécute quand même, sans marchand.

Dans un vrai service, on ne garderait pas les clés en clair dans une `map` :
on garderait leur empreinte, et on comparerait en temps constant
(`crypto/subtle`). La forme du middleware ne change pas.

## 2. `Recover`

```go
// started remembers whether the response has begun.
type started struct {
    http.ResponseWriter
    begun bool
}

func (s *started) WriteHeader(code int) {
    s.begun = true
    s.ResponseWriter.WriteHeader(code)
}

func (s *started) Write(p []byte) (int, error) {
    s.begun = true
    return s.ResponseWriter.Write(p)
}

func (s *started) Unwrap() http.ResponseWriter { return s.ResponseWriter }
```

```go
// Recover turns a panic of next into a 500 and a log line. It lets
// http.ErrAbortHandler go on, as net/http documents, and cannot change a
// status that is already sent.
func Recover(log *slog.Logger) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, req *http.Request) {
            s := &started{ResponseWriter: w}
            defer func() {
                v := recover()
                if v == nil {
                    return
                }
                if err, ok := v.(error); ok && errors.Is(err, http.ErrAbortHandler) {
                    panic(v)
                }
                log.Error("panic", "path", req.URL.Path, "value", v, "stack", string(debug.Stack()))
                if !s.begun {
                    http.Error(w, "internal error", http.StatusInternalServerError)
                }
            }()
            next.ServeHTTP(s, req)
        })
    }
}
```

Ce qu'il fait, et pourquoi :

- **`http.ErrAbortHandler` repart.** La documentation de
  [`http.Handler`](https://pkg.go.dev/net/http#Handler) le réserve à ceux qui
  veulent interrompre la réponse **sans** trace dans le journal : « panic with
  the value ErrAbortHandler ». Un `Recover` qui l'avalerait changerait une
  interruption voulue en 500. `errors.Is` plutôt que `==`, parce qu'une
  bibliothèque peut l'emballer.
- **Le statut ne se change qu'avant le début.** Une fois des octets partis,
  le statut 200 est sur le réseau ; écrire un 500 ajouterait seulement
  « internal error » à la fin d'un corps déjà commencé. `started` observe
  `WriteHeader` **et** `Write`, puisqu'un premier `Write` envoie un 200
  implicite.
- **La pile est journalisée.** `debug.Stack()` ; une ligne « panic » sans pile
  ne sert pas à grand-chose.
- **`started` a un `Unwrap`.** Leçon 3.3, section 7 : sans lui, un handler qui
  diffuse cesserait de marcher derrière `Recover`.

`net/http` récupère déjà les paniques d'un handler : il journalise la pile
et **coupe la connexion**. Le client ne reçoit aucun statut. `Recover`
existe pour répondre un vrai 500, et pour que la panique passe par **notre**
journal.

## 3. L'ordre : la mesure

Le programme `ex2/cmd/orders` essaie les six ordres, avec le paquet de
l'énoncé puis avec le paquet corrigé. Une colonne par exigence : le 401 est
journalisé, le 500 est journalisé par `AccessLog`, la ligne d'une requête
authentifiée porte le marchand.

```text
statement's package:
  order (outermost first)                401   500   merchant
  AccessLog > RequireKey > Recover       yes   yes   -
  AccessLog > Recover > RequireKey       yes   yes   -
  RequireKey > AccessLog > Recover       -     yes   yes
  RequireKey > Recover > AccessLog       -     -     yes
  Recover > AccessLog > RequireKey       yes   -     -
  Recover > RequireKey > AccessLog       -     -     yes
merchant slot:
  order (outermost first)                401   500   merchant
  AccessLog > RequireKey > Recover       yes   yes   yes
  AccessLog > Recover > RequireKey       yes   yes   yes
  RequireKey > AccessLog > Recover       -     yes   yes
  RequireKey > Recover > AccessLog       -     -     yes
  Recover > AccessLog > RequireKey       yes   -     yes
  Recover > RequireKey > AccessLog       -     -     yes
```

### Pourquoi aucun ordre ne marche avec le paquet de l'énoncé

Chaque exigence fixe une relation entre deux couches :

- **401 journalisé** : `AccessLog` doit être **au-dessus** de `RequireKey`.
  Sinon, `RequireKey` répond et rend la main sans que `AccessLog` ait été
  appelé.
- **500 journalisé par `AccessLog`** : `AccessLog` doit être **au-dessus**
  de `Recover`. Si `Recover` est au-dessus, la panique traverse `AccessLog`
  avant d'être rattrapée, et la ligne de journal, écrite **après**
  `next.ServeHTTP`, n'est jamais exécutée.
- **Le marchand dans la ligne** : `AccessLog` doit être **au-dessous** de
  `RequireKey`. `RequireKey` ne modifie pas la requête qu'il a reçue : il en
  passe une **nouvelle** à la couche suivante (`req.WithContext`). Une couche
  au-dessus garde l'ancienne, sans marchand.

La première et la troisième se contredisent. Aucune permutation ne peut
mettre `AccessLog` à la fois au-dessus et au-dessous de `RequireKey`. Ce
n'est pas un problème d'ordre : **un contexte ne descend que vers le bas**,
et l'information dont le journal a besoin naît plus bas que lui.

### La plus petite modification

Il faut un chemin qui remonte. Le journal pose, avant d'appeler la suite,
une **case vide** dans le contexte ; `WithMerchant` la remplit au passage :

```go
// slot is put in the context by AccessLog, before any other layer runs, so
// that a layer below can tell it who the merchant is.
type slot struct{ merchant string }

type slotKey struct{}

// WithMerchant returns a context that carries the merchant's ID, and fills
// the slot of an AccessLog above, if any.
func WithMerchant(ctx context.Context, merchant string) context.Context {
    if s, ok := ctx.Value(slotKey{}).(*slot); ok {
        s.merchant = merchant
    }
    return context.WithValue(ctx, merchantKey{}, merchant)
}

// MerchantFrom returns the merchant's ID carried by ctx, or the one a layer
// below put in the slot, or "".
func MerchantFrom(ctx context.Context) string {
    if m, ok := ctx.Value(merchantKey{}).(string); ok {
        return m
    }
    if s, ok := ctx.Value(slotKey{}).(*slot); ok {
        return s.merchant
    }
    return ""
}
```

et, dans `AccessLog`, une ligne de plus :

```go
// AccessLog logs method, path, merchant and status of every request.
func AccessLog(log *slog.Logger) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, req *http.Request) {
            rec := &recorder{ResponseWriter: w, status: http.StatusOK}
            req = req.WithContext(context.WithValue(req.Context(), slotKey{}, &slot{}))
            next.ServeHTTP(rec, req)
            log.Info("http", "method", req.Method, "path", req.URL.Path,
                "merchant", MerchantFrom(req.Context()), "status", rec.status)
        })
    }
}
```

`RequireKey` ne change pas : il appelle toujours `WithMerchant`. Le diff,
mesuré avec `diff` : vingt-trois lignes ajoutées et cinq supprimées dans
`mw.go`, commentaires compris, aucune dans les middlewares. Avec ce paquet, deux ordres satisfont tout ; on choisit
`AccessLog > Recover > RequireKey`, qui protège aussi d'une panique **dans**
`RequireKey`. Le test qui garde la composition livrée :

```go
// TestTheChosenOrderMeetsAllThree is the test that guards the composition
// shipped: AccessLog > Recover > RequireKey.
func TestTheChosenOrderMeetsAllThree(t *testing.T) {
    r := Orders(After)[1]
    if r.Order != "AccessLog > Recover > RequireKey" || !r.Logs401 || !r.Logs500 || !r.Merchant {
        t.Fatalf("%+v", r)
    }
}
```

### Ce que coûte la case

Elle est honnête sur un point : c'est une donnée **propre à la requête**, ce
que la documentation de `context` autorise (« Use context Values only for
request-scoped data that transits processes and APIs »). Chaque requête a sa
case ; `TestTheSlotDoesNotLeakBetweenRequests` envoie deux cents requêtes
concurrentes de deux marchands sous `-race` et vérifie chaque ligne.

Elle a un prix : une valeur de contexte **modifiable** est un canal caché
entre deux couches. `WithMerchant` sait maintenant qu'un journal existe
peut-être au-dessus. Les deux autres réponses défendables :

- **le 401 journalisé par `RequireKey` lui-même**, et `AccessLog` placé sous
  lui : pas de canal caché, mais deux formats de ligne pour le même
  journal ;
- **une structure de requête unique**, posée tout en haut et remplie par
  chaque couche (le statut, le marchand, la durée) : c'est ce que font la
  plupart des frameworks, et c'est la case de cette correction, généralisée.

## La campagne

Treize mutations sur `RequireKey`, `Recover` et la case. Premier passage :

```text

recover : ecrit apres le debut               tuee

recover : Write ne marque pas le debut       tuee
recover : debut jamais observe               tuee
case : AccessLog ne la pose plus             tuee
case : WithMerchant ne la remplit plus       tuee
9/13 tuees
```

Trois mutations ne compilaient pas — une variable devenue inutilisée
(`ok`, `merchant`) ou un import (`errors`). Elles sont rejouées sous une forme
qui compile : `if _ = ok; key == "" || !known`, `_ = merchant`, et
`err == http.ErrAbortHandler || errors.Is(nil, err)`, toujours faux pour la
seconde moitié.

La survivante, **« clé : clé vide acceptée »**, semblait équivalente : sans
entrée `""` dans la configuration, une clé vide n'est pas trouvée de toute
façon. Mais « sans entrée vide dans la configuration » est une hypothèse sur
**l'exploitation**, pas sur le code — et c'est exactement ce que produit une
variable d'environnement oubliée. Diagnostic : **réclame un test**.
`TestAnEmptyKeyInTheConfigOpensNothing` :

```go
// TestAnEmptyKeyInTheConfigOpensNothing: a key read from an unset variable
// is "", and "Authorization: Bearer " must not match it.
func TestAnEmptyKeyInTheConfigOpensNothing(t *testing.T) {
    h := RequireKey(map[string]string{"": "m-0"})(http.HandlerFunc(func(http.ResponseWriter, *http.Request) {
        t.Error("an empty key opened the API")
    }))
    req := httptest.NewRequest("GET", "/", nil)
    req.Header.Set("Authorization", "Bearer ")
    w := httptest.NewRecorder()
    h.ServeHTTP(w, req)
    if w.Code != http.StatusUnauthorized {
        t.Fatalf("code %d", w.Code)
    }
}
```

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Un proxy qui refuse doit **ne pas appeler** la suite : `http.Error` n'arrête rien, le `return` si. |
| ⚫ | Une clé vide est une clé : une variable d'environnement oubliée la met dans la configuration. |
| ⚫ | `Recover` ne change le statut qu'avant le premier octet, et laisse passer `http.ErrAbortHandler`. |
| ⚫ | Une couche au-dessus ne voit que la requête qu'elle a reçue : un contexte descend, il ne remonte pas. |
| ⚫ | Quand une exigence veut une couche à deux places à la fois, ce n'est plus un problème d'ordre : il faut un chemin qui remonte, et il se paie en couplage. |
| ⚫ | L'ordre livré se garde par un test qui construit la composition réelle. |
