# Correction 3.1 — Exercice 1 : quatre extraits

> Rappel de l'énoncé : un tri, un point de santé HTTP, un arrondi par devise,
> et un notifieur à une seule implémentation, tirés du même service.

Les quatre extraits tournent dans un module vert sous `go vet ./...` et
`go test -race -count=1 ./...`, avec les tests qui établissent les faits de
cette correction.

## 1. Lesquels sont des stratégies ?

| Extrait | Stratégie ? | La règle qui varie |
|---|---|---|
| **A** `sort.Slice` | **oui** | l'ordre : le squelette du tri est fixe, la comparaison est fournie |
| **B** `http.HandlerFunc` | **oui** | ce qu'on fait d'une requête : le serveur est fixe, le traitement est fourni |
| **C** `Round` | **oui** | la règle d'arrondi, choisie par la devise |
| **D** `Notifier` | **pas encore** | une seule façon de notifier existe ; l'interface annonce une variation qui n'a pas eu lieu |

Et une cinquième, que l'énoncé ne numérote pas : le champ `Gateway` de
`SMSNotifier` **est** une stratégie — c'est par lui que passe la seule
variation réelle de l'extrait D, la passerelle de production contre la fausse
passerelle des tests.

## 2. Les formes

| Extrait | Forme | Est-ce la bonne aujourd'hui ? |
|---|---|---|
| A | **fonction** | oui : une opération, aucune identité à porter, un usage local |
| B | **adaptateur** — interface `http.Handler` et type fonction `HandlerFunc` | oui : c'est la forme de référence de la leçon |
| C | **`switch`** | oui pour une opération ; c'est la question 5 qui dit pour combien de temps |
| D | **interface** sans deuxième implémentation, et un champ **fonction** dedans | l'interface non ; le champ fonction oui |

## 3. La faute de l'extrait C

Elle n'est pas dans la forme, elle est dans l'arithmétique, et il y en a
deux.

**Les négatifs.** `int64()` tronque **vers zéro**. Ajouter 0,5 puis tronquer
arrondit au plus proche pour un positif, et vers zéro pour un négatif :

```go
// TestRoundIsWrongBelowZero: int64() truncates toward zero, so adding 0.5
// rounds the negative amounts toward zero, not to the nearest.
func TestRoundIsWrongBelowZero(t *testing.T) {
    for _, c := range []struct {
        in, want float64
    }{
        {2.7, 3}, {2.2, 2}, {-2.2, -2}, {-2.7, -3},
    } {
        got := Round(c.in, "XAF")
        mark := "ok"
        if got != c.want {
            mark = "WRONG"
        }
        t.Logf("Round(%v, XAF) = %v, nearest is %v  %s", c.in, got, c.want, mark)
    }
}
```

```
Round(2.7, XAF) = 3, nearest is 3  ok
Round(2.2, XAF) = 2, nearest is 2  ok
Round(-2.2, XAF) = -1, nearest is -2  WRONG
Round(-2.7, XAF) = -2, nearest is -3  WRONG
```

Deux négatifs sur deux sont faux. Un remboursement de 2,7 XAF s'affiche −2 ;
sur un relevé, la somme des montants affichés ne fait plus le solde affiché.

**Le défaut.** Une devise inconnue repart **sans arrondi**, sans un mot :

```
Round(1234.567, NGN) = 1234.567
```

C'est la faute de la correction 2.3/5 en miniature : un repli silencieux. Le
naira arrivera un jour dans la liste des devises du service, et l'affichage
montrera trois décimales sur un reçu, sans qu'aucun test ni aucune alerte ne
le dise. La ligne de test qui la montre :
`if got := Round(1234.567, "NGN"); got != 1235 { t.Errorf(...) }` — et la
vraie réponse est que `Round` doit rendre une **erreur**.

Et une troisième faute, de signature celle-là : `float64` pour un montant.
L'exercice 2 y revient.

## 4. L'interface à une seule implémentation

La leçon 2.6 donne trois raisons légitimes à une interface : deux
implémentations, une doublure de test, ou une frontière que le graphe des
dépendances doit respecter. Ici :

- **deux implémentations** : non, `SMSNotifier` est la seule ;
- **une doublure** : non, et c'est l'énoncé qui le dit — *les tests
  l'utilisent avec une fausse passerelle*. La doublure remplace le **champ
  `Gateway`**, pas le `Notifier` :

```go
// TestTheNotifierIsNotWhatTheTestsDouble: the tests replace the GATEWAY, a
// function field, not the Notifier.
func TestTheNotifierIsNotWhatTheTestsDouble(t *testing.T) {
    var sent []string
    n := SMSNotifier{
        Gateway: func(number, text string) error { sent = append(sent, number+": "+text); return nil },
        Numbers: map[string]string{"CM-0001": "+237 6 99 00 00 01"},
    }
    if err := n.Notify("CM-0001", "Virement recu"); err != nil || len(sent) != 1 {
        t.Fatalf("%v %v", sent, err)
    }
    failing := SMSNotifier{Gateway: func(string, string) error { return errors.New("gateway down") }}
    if failing.Notify("CM-0001", "x") == nil {
        t.Fatal("the error is lost")
    }
}
```

- **une frontière** : seulement si l'interface est déclarée **chez
  l'appelant**, au bord du paquet des virements (leçon 2.5). Déclarée à côté
  de son unique implémentation, comme ici, elle n'est la frontière de
  personne.

Verdict : **elle n'est pas justifiée par ce qu'on voit.** En forme fonction,
le notifieur serait `type Notify func(accountID, text string) error`, et le
service des virements recevrait `SMSNotifier{...}.Notify` — une méthode
liée est une fonction. La leçon dit le prix de ce choix : le jour où il faut
**nommer** le canal de notification dans un journal, la fonction ne le peut
pas. Ce jour-là, l'interface reviendra, avec sa deuxième implémentation.

## 5. La prédiction

Mesurée sur une copie du module : on recopie le `switch` pour `Symbol`, puis
on ajoute `NGN` au `switch` de `Round` seulement.

```
Symbol recopie : 0 erreur(s), 0 test(s) rouge(s)
NGN dans Round seulement : 0 erreur(s), 0 test(s) rouge(s)
```

Zéro et zéro, les deux fois. Le naira a un arrondi et pas de symbole : le reçu
imprime « 1235 NGN » là où les autres devises impriment un symbole, et rien
ne l'a dit. C'est la mesure de la section 3 de la leçon, reproduite sur un
autre code : **à partir de la deuxième opération, un `switch` recopie la liste
des cas, et rien ne relie les copies.**

## 6. La question ouverte

Le collègue a raison sur `sort.Slice` : une opération, une règle locale,
jamais nommée, jamais comparée. La fonction est la forme la plus courte, et
rien ne la fera grandir.

Sa règle coûterait cher **sur l'extrait C** — précisément celui qui a déjà
deux opérations en vue (arrondir, et le symbole de la question 5) et une
identité à porter (l'exercice 2 demande d'imprimer la règle d'arrondi sur le
reçu). En fonction, la deuxième opération change le type et touche chaque
appelant ; et une fonction ne sait pas dire son nom.

> La forme ne se choisit pas sur l'exemple le plus connu. Elle se choisit sur
> le nombre d'opérations à venir et sur le besoin de désigner la règle.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Une stratégie se reconnaît à un squelette fixe et une règle fournie : `sort.Slice`, `http.HandlerFunc`, un `switch` sur la devise, un champ fonction. |
| ⚫ | La variation réelle n'est pas toujours là où est l'interface : ici, c'est le champ `Gateway` que les tests remplacent. |
| ⚫ | Une interface déclarée à côté de son unique implémentation, sans doublure, n'est la frontière de personne. |
| ⚫ | `int64(x + 0.5)` arrondit les négatifs vers zéro. Mesuré : −2,2 donne −1, −2,7 donne −2. |
| ⚫ | Un `default` qui rend l'entrée telle quelle est un repli silencieux (correction 2.3/5). |
| ⚫ | Copier un `switch` pour une deuxième opération, puis ajouter un cas à un seul : 0 erreur, 0 test rouge. Mesuré deux fois. |
