# Correction 3.2 — Exercice 2 : l'ouverture de compte

> Rappel de l'énoncé : un paquet `account` dont aucun compte invalide ne sort,
> sauf la valeur zéro ; une règle qui lie le découvert au niveau de
> vérification ; un découvert de zéro qui veut dire zéro.

Le paquet tourne dans un module vert sous `go vet ./...` et
`go test -race -count=1 ./...`.

## 1. La forme, et pourquoi

Les deux valeurs **requises** — l'identifiant, le titulaire — sont des
paramètres : on ne peut pas les oublier. Les trois **facultatives** — devise,
niveau, découvert — sont des options.

```go
type config struct {
    currency  string
    kyc       int
    overdraft int64
}

// Option changes one optional setting. It records; Open checks.
type Option func(*config)

// WithCurrency sets the currency: XAF or EUR. The default is XAF.
func WithCurrency(currency string) Option {
    return func(c *config) { c.currency = currency }
}
```

```go
// WithOverdraft sets the authorized overdraft, in minor units. The default
// is zero, and zero means zero.
func WithOverdraft(limit int64) Option {
    return func(c *config) { c.overdraft = limit }
}
```

La justification demande un peu d'honnêteté. **Pour ces trois réglages, une
structure de configuration aurait marché** : le zéro de chacun est soit le
défaut (découvert : zéro), soit invalide (niveau 0, devise vide) — donc « pas
renseigné » et « renseigné à zéro » ne se contredisent jamais. La deuxième
mesure de la leçon ne tire pas.

Elle tire à la question 6. Le plafond journalier est le premier réglage dont
le zéro **pourrait** avoir un sens métier, et une API de compte en gagnera
d'autres. Les options coûtent un type et une fonction par réglage
aujourd'hui ; elles évitent qu'un réglage futur ne puisse pas dire zéro. C'est
un pari sur la croissance de l'API, et il faut le dire comme tel : pour un
paquet interne qui n'en aura jamais d'autre, la structure serait plus courte.

## 2. La porte

```go
// Open returns an account, or the first rule its settings break. Every
// rule is checked here, once, after the last option.
func Open(id, owner string, opts ...Option) (*Account, error) {
    c := config{currency: "XAF", kyc: 1}
    for _, o := range opts {
        o(&c)
    }
    switch {
    case !idFormat.MatchString(id):
        return nil, fmt.Errorf("%w: id %q is not CM-NNNN", ErrInvalid, id)
    case strings.TrimSpace(owner) == "":
        return nil, fmt.Errorf("%w: no owner", ErrInvalid)
    case c.currency != "XAF" && c.currency != "EUR":
        return nil, fmt.Errorf("%w: currency %q", ErrInvalid, c.currency)
    case c.kyc < 1 || c.kyc > 3:
        return nil, fmt.Errorf("%w: kyc level %d", ErrInvalid, c.kyc)
    case c.overdraft < 0:
        return nil, fmt.Errorf("%w: overdraft %d", ErrInvalid, c.overdraft)
    case c.overdraft > 0 && c.kyc < 2:
        return nil, fmt.Errorf("%w: an overdraft of %d needs kyc level 2, not %d", ErrInvalid, c.overdraft, c.kyc)
    }
    return &Account{id: id, owner: owner, currency: c.currency, kyc: c.kyc, overdraft: c.overdraft}, nil
}
```

**Toutes** les règles sont dans le `switch` de `Open`, après la dernière
option. Les options ne contrôlent rien : elles enregistrent. C'est ce qui rend
l'ordre indifférent.

```go
// TestTheOrderDoesNotMatter: the rule that ties the overdraft to the kyc
// level, given in both orders.
func TestTheOrderDoesNotMatter(t *testing.T) {
    for _, opts := range [][]account.Option{
        {account.WithOverdraft(50_000), account.WithKYC(2)},
        {account.WithKYC(2), account.WithOverdraft(50_000)},
    } {
        a, err := account.Open("CM-0001", "Awa", opts...)
        if err != nil || a.Overdraft() != 50_000 || a.KYC() != 2 {
            t.Fatalf("%v, %v", a, err)
        }
    }
    for _, opts := range [][]account.Option{
        {account.WithOverdraft(50_000), account.WithKYC(1)},
        {account.WithKYC(1), account.WithOverdraft(50_000)},
    } {
        if _, err := account.Open("CM-0001", "Awa", opts...); !errors.Is(err, account.ErrInvalid) {
            t.Fatalf("overdraft at kyc 1: %v", err)
        }
    }
}
```

Deux détails du `switch` que la campagne a vérifiés : l'expression régulière
est **ancrée** (`^…$`), sinon `CM-12345` passe ; et le titulaire est contrôlé
après `strings.TrimSpace`, sinon un titulaire de deux espaces passe.

## 3. Le débit et la valeur zéro

```go
func (a *Account) opened() bool { return a.id != "" }
```

```go
// Debit takes amount from the account, within the overdraft.
func (a *Account) Debit(amount int64) error {
    switch {
    case !a.opened():
        return ErrNotOpened
    case amount <= 0:
        return fmt.Errorf("%w: debit of %d", ErrRefused, amount)
    case a.balance-amount < -a.overdraft:
        return fmt.Errorf("%w: debit of %d, balance %d, overdraft %d", ErrRefused, amount, a.balance, a.overdraft)
    }
    a.balance -= amount
    return nil
}
```

`opened` est la détection de la valeur zéro : un compte qui n'est pas passé
par `Open` n'a pas d'identifiant, puisque `Open` refuse l'identifiant vide.
C'est l'invariant qui rend la comparaison suffisante — comme `IsZero` dans la
leçon.

Le geste d'une minute, écrit en test :

```go
// TestTheZeroValue is the gesture of one minute: every exported method on
// the zero value, and none panics.
func TestTheZeroValue(t *testing.T) {
    var a account.Account
    for name, err := range map[string]error{"Debit": a.Debit(100), "Credit": a.Credit(100)} {
        if !errors.Is(err, account.ErrNotOpened) {
            t.Errorf("%s: %v", name, err)
        }
    }
    _, _, _, _, _, _ = a.ID(), a.Owner(), a.Currency(), a.KYC(), a.Overdraft(), a.Balance()
    if a.Balance() != 0 {
        t.Fatalf("balance %d", a.Balance())
    }
}
```

Les accesseurs sur la valeur zéro rendent des zéros, et c'est acceptable :
ils décrivent, ils n'agissent pas. Les deux méthodes qui **déplacent de
l'argent** refusent avec une erreur nommée.

Un trou reste, et il faut le nommer : `var p *account.Account` puis
`p.Balance()` panique. Un `*Account` nul ne sort que d'un appelant qui a
ignoré l'erreur de `Open` ; garder chaque accesseur contre `nil` coûterait
six gardes pour une faute que `errcheck` ou la revue voient avant. Le choix
est défendable ; il doit être fait exprès.

Le zéro qui veut dire zéro, fixé par un test, parce que la campagne devait
pouvoir le casser :

```go
// TestAZeroOverdraftIsZero: at kyc level 2, an overdraft explicitly set to
// zero allows no overdraft.
func TestAZeroOverdraftIsZero(t *testing.T) {
    a, err := account.Open("CM-0001", "Awa", account.WithKYC(2), account.WithOverdraft(0))
    if err != nil {
        t.Fatal(err)
    }
    if err := a.Debit(1); !errors.Is(err, account.ErrRefused) {
        t.Fatalf("debit on an empty account: %v", err)
    }
}
```

## 4. Un réglage de plus

Le plafond journalier, mesuré sur deux copies du module :

```
== plafond, zero = pas de plafond : 1 fichier(s) ['ex2/account/account.go'], +15 -1 lignes, 0 erreur(s), 0 test(s) rouge(s), appelants touches : 0
== plafond, zero = aucun retrait : 1 fichier(s) ['ex2/account/account.go'], +17 -1 lignes, 0 erreur(s), 0 test(s) rouge(s), appelants touches : 0
```

| | zéro = pas de plafond | zéro = aucun retrait |
|---|---|---|
| fichiers | 1 | 1 |
| lignes | +15 −1 | +17 −1 |
| appelants touchés | 0 | 0 |
| ce qui change | — | un booléen « donné », dans la configuration et dans le compte |

Avec les options, la différence entre les deux sens du zéro coûte **deux
lignes** : un champ `dailySet` qui retient que l'option a été donnée, comme
`burstSet` dans la correction de l'exercice 1. Aucun appelant ne le voit :
`WithDailyLimit(0)` veut dire zéro, l'absence de l'option veut dire « pas de
plafond ».

Avec une structure de configuration, le premier sens est gratuit — un champ
`DailyLimit int64` dont le zéro est le défaut. Le second ne peut pas
s'écrire sans changer de convention : un `*int64`, ou une sentinelle. C'est
exactement le réglage qui aurait fait regretter la structure, et la raison
du choix de la section 1.

## 5. La campagne

Quinze modifications, jouées sous `go test -race -count=1 -timeout=60s`.
Une, « titulaire en blancs accepté », ne compilait pas sous sa première forme
— retirer `strings.TrimSpace` laisse l'import inutilisé — et a été rejouée
sous la forme `strings.TrimSpace(owner) == "" && owner == ""`. Première passe :

```
decouvert controle dans le reglage             tuee
regle du decouvert retiree                     tuee
decouvert nul remplace par un defaut           tuee
Debit : plus de garde                          tuee
Credit : plus de garde                         tuee
CM-123 accepte                                 tuee
identifiant non ancre                          tuee
EUR refuse                                     tuee
niveau 4 accepte                               tuee
decouvert negatif accepte                      tuee
decouvert exige le niveau 3                    tuee
Debit : limite du decouvert exclue             tuee
Debit de zero accepte                          tuee
defaut : niveau 2                              tuee
titulaire en blancs accepte                    tuee
15/15 tuees
```

Aucun survivant. Les quatre modifications imposées par l'énoncé sont
tuées par quatre tests différents, et c'est le résultat à regarder :

| Modification imposée | Tuée par |
|---|---|
| découvert contrôlé dans le réglage | `TestTheOrderDoesNotMatter` : dans l'ordre découvert puis niveau, le découvert est perdu |
| découvert nul remplacé par un défaut | `TestAZeroOverdraftIsZero` |
| plus de garde de la valeur zéro | `TestTheZeroValue` : le débit rend « refusé » au lieu de « pas ouvert » |
| `CM-123` accepté | `TestOpenRefuses`, cas « short id » |

Le troisième mérite une ligne : sans la garde, le débit de la valeur zéro est
**quand même refusé** — solde 0, découvert 0 — mais pour la mauvaise raison.
Un test qui vérifiait seulement `err != nil` l'aurait laissé survivre. Le
test vérifie **quelle** erreur, et c'est ce qui le tue : la prochaine
modification du débit, elle, aurait pu accepter.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Les valeurs requises en paramètres, les facultatives en options ; toutes les règles dans `Open`, après la dernière option. |
| ⚫ | Une structure de configuration aurait marché pour ces trois réglages : chaque zéro y est le défaut ou invalide. Les options sont un pari sur les réglages à venir, et il faut le dire. |
| ⚫ | Le plafond journalier mesure le pari : avec les options, « zéro veut dire zéro » coûte deux lignes et zéro appelant. |
| ⚫ | La valeur zéro se détecte par l'invariant : un compte ouvert a toujours un identifiant. |
| ⚫ | Un test de refus vérifie **quelle** erreur. « Refusé pour la mauvaise raison » est une survie qui attend son heure. |
