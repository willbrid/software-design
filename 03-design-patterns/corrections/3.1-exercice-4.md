# Correction 3.1 — Exercice 4 : le moteur antifraude

> Rappel de l'énoncé : neuf règles, une par mois en plus, des paramètres par
> commerçant sans livraison, toutes les règles évaluées et la plus sévère qui
> gagne, un audit qui dit quelle règle, quelle version, quels paramètres, et
> deux versions d'une règle qui tournent en même temps.

C'est un exercice de conception, mais chaque réponse est un test vert. Le
moteur tient dans un paquet, `fraud`, vert sous `go vet ./...` et
`go test -race -count=1 ./...` — et c'est `-race` qui a trouvé la faute
de ma première version (section 4). Campagne de onze modifications, 11/11
après deux passes.

## 1. La forme d'une règle

**Une interface, pas une fonction**, et c'est la ligne « audit » du tableau
qui le décide : l'audit doit dire **quelle** règle, **quelle** version,
**quels** paramètres ont décidé. Une fonction ne sait rien dire d'elle-même
(leçon, section 4).

```go
// Rule is a fraud rule. It is an interface, not a function, because the
// audit must say WHICH rule, WHICH version and WHICH parameters decided.
type Rule interface {
    ID() string
    Version() string
    Params() string
    Evaluate(p Payment, f Facts) Verdict
}
```

Et une règle est une **valeur paramétrée** : la vélocité d'un commerçant et
celle d'un autre sont deux valeurs du même type, pas deux types.

```go
// Velocity: more than Max payments on the same card in the window. It
// receives the count; it keeps nothing.
type Velocity struct {
    Max int
    V   string
}

func (r Velocity) ID() string      { return "velocity" }
func (r Velocity) Version() string { return r.V }
func (r Velocity) Params() string  { return fmt.Sprintf("max=%d", r.Max) }
func (r Velocity) Evaluate(_ Payment, f Facts) Verdict {
    if f.RecentOnCard+1 > r.Max {
        return Block
    }
    return Pass
}
```

Ce que l'audit enregistre, pour un paiement à l'étranger :

```
decision review
velocity v1 max=5 -> pass
geography v1 threshold=500000 -> review
```

## 2. La vélocité ne garde rien

> **L'état de vélocité vit dans l'historique des paiements, pas dans la
> règle.** Une règle qui compte ses appels compte par instance, oublie tout
> au redémarrage, et court en concurrence — c'est la section 6 de la leçon,
> et l'exercice 5 en est l'incident.

La règle reçoit le compte en **argument**, calculé avant elle à partir de
l'historique — la même source pour toutes les instances :

```go
// Facts is what the rules need and do not keep: it is computed outside the
// rules, from the payment history, before the rules run.
type Facts struct {
    // RecentOnCard is the number of payments on the same card in the
    // velocity window, this one excluded.
    RecentOnCard int
}
```

Le test le dit en une boucle : les mêmes faits donnent le même verdict, quoi
qu'il se soit passé avant.

```go
// TestVelocityKeepsNothing: the same facts give the same verdict, whatever
// came before and on whichever instance.
func TestVelocityKeepsNothing(t *testing.T) {
    r := Velocity{Max: 5, V: "v1"}
    for range 3 {
        if r.Evaluate(abroad, Facts{RecentOnCard: 4}) != Pass || r.Evaluate(abroad, Facts{RecentOnCard: 5}) != Block {
            t.Fatal("velocity depends on something else than its facts")
        }
    }
}
```

## 3. Deux versions, une seule décide

La version B tourne en **ombre** : évaluée sur chaque paiement, enregistrée,
jamais combinée. Et ce qui l'empêche de décider n'est pas une précaution du
code, c'est un **type** :

```go
// ShadowResult is the result of a rule that runs without deciding. It is a
// DIFFERENT type: combine takes []Result, and a ShadowResult cannot be given
// to it by mistake.
type ShadowResult struct{ Result }
```

```go
// Decide evaluates every rule — not the first that blocks — and combines
// the active ones: the most severe verdict wins.
func (e Engine) Decide(p Payment, f Facts) Decision {
    var d Decision
    for _, r := range e.Active {
        d.Results = append(d.Results, e.run(r, p, f))
    }
    for _, r := range e.Shadow {
        d.Shadow = append(d.Shadow, ShadowResult{e.run(r, p, f)})
    }
    d.Verdict = combine(d.Results)
    return d
}
```

Donner les résultats de l'ombre à la combinaison ne compile pas :

```
ex4/fraud/misuse.go:3:50: cannot use d.Shadow (variable of type []ShadowResult) as []Result value in argument to combine
```

Et le test, avec une version 2 plus stricte qui bloque pendant que la
version 1 laisse passer :

```
decision pass; shadow velocity v2 max=2 -> block
```

L'audit enregistre pour B ce qu'il enregistre pour A — règle, version,
paramètres, verdict — dans une colonne à part. C'est ce qui permet de
comparer, sur une semaine de trafic réel, combien de paiements B aurait
bloqués que A a laissés passer, **avant** de la promouvoir.

## 4. La plus sévère gagne, et une règle cassée

Toutes les règles sont évaluées — pas la première qui bloque, sinon l'audit
ne dit plus pourquoi les autres n'ont pas bloqué — et la combinaison est un
maximum sur un verdict **ordonné** :

```go
// Verdict is ordered: the most severe wins.
type Verdict int

const (
    Pass Verdict = iota
    Review
    Block
)
```

**Une règle qui panique ou qui ne répond pas à temps envoie le paiement en
revue.** C'est un choix métier, et les deux autres sont pires :

| | Ce que ça coûte quand la règle est cassée |
|---|---|
| **laisser passer** | chaque fraude que cette règle aurait vue passe — et personne ne le sait, puisque le paiement a « réussi » |
| **bloquer** | chaque client légitime est refusé pour un défaut de la banque — et la règle cassée devient une panne de paiement |
| **revue** | un analyste regarde ; le coût est un délai et du temps humain, compté et visible |

```go
// run evaluates one rule. A rule that panics or does not answer in time
// sends the payment to REVIEW: passing it would let a fraud through,
// blocking it would refuse a customer for a bug of the bank.
func (e Engine) run(r Rule, p Payment, f Facts) Result {
    res := Result{Rule: r.ID(), Version: r.Version(), Params: r.Params()}
    ctx, cancel := context.WithTimeout(context.Background(), e.Timeout)
    defer cancel()
    // The goroutine gets its OWN copy of the result. On a timeout, run
    // returns while the abandoned rule is still running: whatever they share,
    // they race on — the first version of this function shared res, and
    // go test -race said so.
    done := make(chan Result, 1)
    go func(out Result) {
        defer func() {
            if x := recover(); x != nil {
                out.Verdict, out.Note = Review, fmt.Sprintf("panicked: %v", x)
                done <- out
            }
        }()
        out.Verdict = r.Evaluate(p, f)
        done <- out
    }(res)
    select {
    case out := <-done:
        return out
    case <-ctx.Done():
        res.Verdict, res.Note = Review, "timed out"
        return res
    }
}
```

```
broken: review (panicked: index out of range)
slow: review (timed out)
```

**Ma première version avait une course de données**, et c'est `go test
-race` qui l'a vue. La goroutine de la règle lisait la variable `res` pour
faire sa copie ; sur un dépassement de délai, `run` écrivait dans la même
variable et rendait la main — pendant que la règle abandonnée tournait
encore. Une règle abandonnée **continue de s'exécuter** : tout ce qu'elle
partage avec l'appelant, elle le partage en concurrence. La goroutine reçoit
maintenant sa propre copie, en argument.

Et la limite à dire : la règle trop lente n'est pas arrêtée, elle est
**abandonnée**. Si toutes les règles se mettent à dépasser leur délai, les
goroutines s'accumulent. La métrique à suivre est le nombre de verdicts
« timed out » par minute ; au-dessus d'un seuil, c'est la règle qu'il faut
retirer, pas le délai qu'il faut allonger.

## 5. Des paramètres sans livraison

Le chargement valide **tout le fichier avant d'en accepter une ligne**, et le
refus garde le jeu précédent — la réponse de la correction 2.4/4, pour la même
raison : un fichier à moitié chargé est un jeu de paramètres que personne n'a
écrit.

```go
// LoadParams validates the WHOLE file before accepting a line of it: one
// invalid merchant refuses the file, and the caller keeps the previous set.
// It is a list, not an object, so that a duplicate merchant shows.
func LoadParams(b []byte) (map[string]MerchantParams, error) {
    var list []MerchantParams
    if err := json.Unmarshal(b, &list); err != nil {
        return nil, err
    }
    out := map[string]MerchantParams{}
    var errs []error
    for i, p := range list {
        switch {
        case p.Merchant == "":
            errs = append(errs, fmt.Errorf("line %d: no merchant", i+1))
        case out[p.Merchant] != (MerchantParams{}):
            errs = append(errs, fmt.Errorf("line %d: %q twice", i+1, p.Merchant))
        case p.VelocityMax < 1:
            errs = append(errs, fmt.Errorf("line %d: %q: velocity_max %d < 1", i+1, p.Merchant, p.VelocityMax))
        case p.GeographyThreshold < 0:
            errs = append(errs, fmt.Errorf("line %d: %q: negative geography_threshold", i+1, p.Merchant))
        }
        out[p.Merchant] = p
    }
    if err := errors.Join(errs...); err != nil {
        return nil, err
    }
    return out, nil
}
```

```
line 2: "M-0002": velocity_max 0 < 1
line 3: "M-0001" twice
```

Pourquoi pas « ignorer la ligne invalide » : le commerçant dont la ligne est
ignorée garde l'ancien paramètre **ou** n'en a plus aucun, selon que la ligne
était une modification ou un ajout — et personne ne choisit lequel. Une liste
plutôt qu'un objet JSON, pour qu'un commerçant en double se voie (correction
2.4/4, proposition C).

## 6. Un petit langage

| | |
|---|---|
| **Ce que la banque gagne** | l'équipe fraude réagit en heures au lieu d'un cycle de livraison, sur une menace qui change en jours |
| **Ce qu'elle perd sur l'audit** | une règle écrite dans le langage a une identité — son nom, sa version — seulement si le langage l'exige ; sinon, l'audit redevient « bloqué » |
| **Ce qu'elle perd sur les tests** | les règles ne passent plus par `go test` ni par la revue de code : la batterie, la campagne, le `-race` ne les voient pas |
| **Ce qu'elle risque** | une règle qui boucle, qui panique ou qui bloque tout — exactement ce que la section 4 rattrape, à condition que le langage passe par `run` |

**La frontière : les faits sont du code, les règles sont des données** — la
coupe de la correction 2.4/4, au même endroit. L'équipe fraude **combine** des
faits existants (montant, pays, vélocité, commerçant) avec des seuils et des
opérateurs ; elle ne **calcule** rien de nouveau. Un fait nouveau — « nombre
de cartes distinctes sur ce commerçant en une heure » — est du code, revu,
testé, livré. Et une règle écrite par l'équipe fraude entre **d'abord en
ombre** : la section 3 donne gratuitement le mécanisme de mise en production
d'une règle que personne n'a testée.

## 7. La campagne

Onze modifications, jouées sous `go test -race -count=1 ./ex4/...`. Première
passe :

```
la derniere regle gagne                        SURVIT
l'ombre decide aussi                           tuee
une regle qui panique laisse passer            tuee
une regle trop lente laisse passer             tuee
plus de delai                                  tuee
velocite : un paiement de trop                 tuee
geographie sans le pays                        tuee

commercant en double accepte                   tuee

```

Le survivant réclame un test, et sa cause est instructive : **dans tous les
tests, la règle la plus sévère était la dernière de la liste.** « La dernière
gagne » et « la plus sévère gagne » donnaient le même verdict sur toutes les
données de test. Le test parcourt maintenant les deux ordres :

```go
// TestEveryRuleRunsAndTheMostSevereWins, in both orders: with the most
// severe rule always last, "the last one wins" passes too.
func TestEveryRuleRunsAndTheMostSevereWins(t *testing.T) {
    geo, vel := Geography{Threshold: 500_000, V: "v1"}, Velocity{Max: 5, V: "v1"}
    for _, rules := range [][]Rule{{geo, vel}, {vel, geo}} {
        d := engine(rules...).Decide(abroad, Facts{RecentOnCard: 5})
        if d.Verdict != Block || len(d.Results) != 2 {
            t.Fatalf("%s first: %+v", rules[0].ID(), d)
        }
    }
}
```

Deuxième passe :

```
11/11 tuees
```

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | L'audit décide de la forme : une règle qu'il faut nommer, versionner et paramétrer est une **interface**, et ses variantes sont des **valeurs**. |
| ⚫ | Une règle ne garde pas d'état : elle reçoit les faits en argument, calculés à partir d'une source commune à toutes les instances. |
| ⚫ | Une version en ombre ne doit pas pouvoir décider **par construction** : un type différent que la combinaison n'accepte pas. Mesuré : la confusion ne compile pas. |
| ⚫ | Une règle cassée envoie en revue : laisser passer cache la fraude, bloquer transforme un défaut en panne. C'est un choix métier. |
| ⚫ | Une règle abandonnée sur délai continue de tourner. Ce qu'elle partage avec l'appelant, elle le partage en concurrence — `-race` l'a vu ici. |
| ⚫ | Un fichier de paramètres se valide en entier, et le refus garde le jeu précédent. |
| ⚫ | Les faits sont du code, les règles sont des données, et une règle nouvelle entre en ombre. |
| ⚫ | Des données de test où le cas extrême est toujours en dernier ne distinguent pas « le dernier » de « le pire ». |
