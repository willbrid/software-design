# Correction 3.4 — Exercice 2 : attendre son propre événement

> Rappel de l'énoncé : écrire `wait.For`, qui attend sur un bus `Async` le
> premier événement qui correspond, abandonne avec le `ctx`, et se désabonne
> quoi qu'il arrive ; puis expliquer deux des cinq tests fournis.

Le module de correction est vert sous `go vet ./...` et
`go test -race -count=1 ./...`. Les cinq tests sont ceux de l'énoncé,
recopiés sans changement.

## En bref

- La fonction tient en vingt lignes. Trois décisions la rendent juste : un
  canal de **taille 1**, un envoi qui **ne bloque jamais**, et un
  `defer stop()` placé juste après un `Subscribe` réussi.
- Un envoi bloquant passe quatre tests sur cinq. Il ne casse que le jour où
  un deuxième événement correspond **après** le retour de `For` : la
  goroutine de l'abonné attend un lecteur qui est parti, et `Close` ne rend
  plus la main.
- Un désabonnement oublié ne se voit, de l'extérieur, que par les goroutines
  qui restent. Un bus qui veut qu'on le surveille doit exposer **son nombre
  d'abonnés**.

## La solution

```go
// For subscribes to b, returns the first event for which match is true,
// and is unsubscribed when it returns, whatever happens. It gives up when
// ctx ends.
func For[E any](ctx context.Context, b *bus.Async[E], match func(E) bool) (E, error) {
    var zero E
    found := make(chan E, 1)
    stop, err := b.Subscribe(func(_ context.Context, e E) error {
        if !match(e) {
            return nil
        }
        select {
        case found <- e:
        default: // one is already waiting, or For has returned: never block
        }
        return nil
    })
    if err != nil {
        return zero, err
    }
    defer stop()
    select {
    case e := <-found:
        return e, nil
    case <-ctx.Done():
        return zero, ctx.Err()
    }
}
```

Ligne par ligne :

- `found` a **une** place. Le premier événement qui correspond y entre sans
  attendre que `For` soit prêt à le lire.
- Le `select` avec `default` : si la place est déjà prise (un premier
  événement attend), ou si `For` a rendu la main et que personne ne lira
  plus jamais `found`, l'événement est **ignoré**. Le handler rend la main
  dans tous les cas. C'est la règle de la leçon : un handler ne bloque pas la
  goroutine de sa file.
- L'erreur de `Subscribe` est rendue **avant** le `defer` : sur un bus
  fermé, `stop` vaut `nil`, et `defer stop()` paniquerait au retour.
- `defer stop()` couvre les deux sorties, l'événement trouvé et l'abandon
  par le `ctx`. C'est ce qui empêche la fuite de la section 9.

## 2. Pourquoi un envoi ordinaire casse un seul test

Chaque erreur plausible, introduite seule, avec les tests qui la voient :

```text
envoi bloquant                           TestLateMatchesDoNotBlockClose 
pas de désabonnement                     TestForLeavesNoGoroutineBehind 
erreur de Subscribe ignorée              - panic: test timed out after 1m0s
filtre oublié                            TestForReturnsTheFirstMatchingEvent 
contexte ignoré                          - panic: test timed out after 1m0s
```

L'envoi bloquant (`found <- e` à la place du `select`) n'est vu que par
`TestLateMatchesDoNotBlockClose`. Le déroulé :

1. le test publie 2, 4, 6, 8, 10 d'un coup : les cinq entrent dans la file
   de l'abonné, qui a huit places ;
2. le handler envoie 2 dans `found`, et `For` le lit et rend la main. La
   place de `found` est de nouveau libre : le handler y met 4, que plus
   personne ne lira ;
3. le handler essaie d'envoyer 6 : `found` est plein, et plus personne ne le
   videra. **La goroutine de l'abonné attend pour toujours.** `stop()` ferme
   la file, mais la goroutine est coincée dans le handler et ne revient
   jamais à son `range` ;
4. `Close` attend cette goroutine (`wg.Wait`) : il ne rend pas la main, et
   le test échoue au bout d'une seconde.

Les quatre autres tests passent, parce qu'ils ne publient jamais un
**deuxième** événement qui correspond. C'est la leçon de la campagne :
l'erreur ne se voit que si un test **provoque** la situation.

Deux autres lignes de la sortie méritent un mot :

- « erreur de Subscribe ignorée » et « contexte ignoré » finissent en
  `test timed out` : `For` attend un événement qui ne viendra pas. Sur un bus
  fermé, rien n'arrive ; sans la branche `ctx.Done()`, rien ne l'interrompt.
  Un test qui ne finit jamais est un test rouge, mais un rouge **lent** et
  sans message. Un délai court dans le test lui-même (comme
  `time.After(time.Second)` dans `TestLateMatchesDoNotBlockClose`) donne un
  meilleur diagnostic.
- Pour faire compiler « erreur de Subscribe ignorée », il a fallu écrire
  `_ = err` : sans cela, Go refuse une variable inutilisée. Le compilateur
  attrape une partie de cette erreur, pas toute.

La campagne complète, cinq erreurs, toutes vues :

```text
envoi bloquant                               tuee
pas de désabonnement                         tuee
erreur de Subscribe ignorée                  tuee
filtre oublié                                tuee
contexte ignoré                              tuee
5/5 tuees
```

## 3. Pourquoi compter les goroutines

`TestForLeavesNoGoroutineBehind` est le seul test qui voit « pas de
désabonnement » : un abonné oublié ne fait **rien de faux**. Il reçoit les
événements suivants, ne trouve personne pour les lire, et les ignore grâce
au `default`. Ce qu'il laisse derrière lui, c'est une goroutine et une file
qui vivront jusqu'à `Close`. Le bus ne dit pas combien d'abonnés il a :
compter les goroutines du programme est la seule trace observable de
l'extérieur. C'est fragile : un autre test qui démarre une goroutine en
parallèle fausse le compte. D'où la boucle `settle`, qui laisse le temps aux
goroutines arrêtées de finir.

Ce qu'il faudrait au bus pour que le test, et la production, voient mieux :

```text
// Subscribers returns the number of subscribers that have not been
// stopped.
func (b *Async[E]) Subscribers() int
```

Le test vérifie alors `Subscribers()` avant et après, sans dépendre du
reste du programme. En production, c'est une **jauge** à exposer : un
nombre d'abonnés qui monte avec le trafic est le symptôme exact de la
section 9 de la leçon, visible avant que la mémoire ne le soit.

## Ce qu'il faut retenir

1. Un handler ne bloque jamais la goroutine de sa file : un envoi dans un
   canal depuis un handler se fait avec `select` et `default`, ou dans un
   canal dont on **sait** qu'il a de la place.
2. `defer stop()` se place juste après un `Subscribe` **réussi**.
3. Le test qui compte est celui qui provoque le cas rare : ici, un
   deuxième événement qui correspond après le retour.
4. Ce qui peut fuir doit pouvoir se compter : un bus expose son nombre
   d'abonnés.
