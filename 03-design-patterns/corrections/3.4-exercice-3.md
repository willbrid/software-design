# Correction 3.4 — Exercice 3 : l'ouverture de compte

> Rappel de l'énoncé : caractériser `signup.Service.Open`, défauts compris ;
> classer ses réactions ; la refactorer avec un événement `AccountOpened` et
> un bus ; refaire passer les tests et assumer chaque changement.

Tout ce qui suit est dans le module de correction, vert sous
`go vet ./...` et `go test -race -count=1 ./...`. Les tests de
caractérisation (`ex3/legacy`) visent le paquet **d'origine**, sans le
modifier ; la nouvelle forme est dans `ex3/opening`.

## En bref

- `Open` cache **cinq** défauts, tous épinglés par un test nommé : un faux
  échec quand l'e-mail échoue, un CRM appelé avec un contexte annulé, une
  prime perdue sans un mot, une prime payée « plus tard », et un compteur en
  course.
- La prime de parrainage **n'est pas** un abonné : c'est de l'argent promis
  au client. Elle reste un appel direct, dans `Open`, et son échec devient
  visible. Le reste devient des abonnés.
- La nouvelle forme ne connaît plus ni le mailer ni le CRM ; chacun des
  quatre tests de caractérisation change, et chaque changement est voulu.

## 1. Caractériser d'abord

Quatre tests, verts sur le code d'origine. Chacun **décrit un défaut** ; son
nom le dit, pour que personne ne le prenne pour une règle.

```go
// Flaw: the account exists, the caller is told it does not, and when the
// customer tries again the phone number is taken.
func TestAWelcomeFailureReportsAFailedOpeningOfAnAccountThatExists(t *testing.T) {
    down := errors.New("mail server down")
    s, _ := service(mailer{fail: down}, 100000)
    if _, err := s.Open(context.Background(), awa); !errors.Is(err, down) {
        t.Fatalf("err = %v, want %v", err, down)
    }
    if s.Accounts.Count() != 1 {
        t.Fatalf("accounts = %d, want 1: it was created anyway", s.Accounts.Count())
    }
    if _, err := s.Open(context.Background(), awa); !errors.Is(err, signup.ErrPhoneTaken) {
        t.Fatalf("retry err = %v, want ErrPhoneTaken", err)
    }
    if s.Opened != 0 {
        t.Fatalf("opened = %d, want 0: the dashboard does not count it", s.Opened)
    }
}
```

C'est le défaut de la leçon, en pire : le compte existe, l'application
mobile affiche « échec », le client réessaie, et on lui répond que son
numéro **a déjà un compte**. Le tableau de bord, lui, ne le compte pas
(`Opened` vaut 0).

```go
// Flaw: the CRM runs after the answer, with the request's context, which is
// canceled by then.
func TestTheCRMGetsACanceledContext(t *testing.T) {
    s, c := service(mailer{}, 100000)
    ctx, cancel := context.WithCancel(context.Background())
    if _, err := s.Open(ctx, awa); err != nil {
        t.Fatal(err)
    }
    cancel() // the HTTP server does this once the response is written
    if err := <-c.seen; !errors.Is(err, context.Canceled) {
        t.Fatalf("CRM saw %v, want context.Canceled", err)
    }
}
```

`go s.CRM.Push(ctx, a)` emporte le `ctx` de la requête dans une goroutine
qui lui survit. Dès que le serveur a répondu, ce contexte est annulé : un
vrai client HTTP de CRM abandonnerait sa requête.

```go
// Flaw: with an empty promo account, the bonus is not paid, and nobody is
// told: the error is dropped by the go statement.
func TestAnEmptyPromoAccountLosesTheBonusSilently(t *testing.T) {
    s, _ := service(mailer{}, 0)
    if _, err := s.Open(context.Background(), awa); err != nil {
        t.Fatalf("err = %v, want nil", err)
    }
    time.Sleep(20 * time.Millisecond)
    if got := s.Ledger.Balance("acc-ref"); got != 0 {
        t.Fatalf("referrer = %d, want 0", got)
    }
}
```

```go
// Flaw: the bonus is paid by a goroutine nobody waits for; right after Open
// returns, it may not be there yet.
func TestTheBonusIsPaidSometimeAfterOpenReturns(t *testing.T) {
    s, _ := service(mailer{}, 100000)
    if _, err := s.Open(context.Background(), awa); err != nil {
        t.Fatal(err)
    }
    deadline := time.Now().Add(time.Second)

        if time.Now().After(deadline) {
            t.Fatal("the bonus never arrived")

```

`go s.Ledger.Move(...)` jette **l'erreur** de `Move` : une prime qui ne peut
pas être payée disparaît sans trace. Et quand elle peut l'être, elle arrive
« un peu après » : un test qui vérifie le solde juste après `Open` est
instable.

Le cinquième défaut ne peut pas être un test vert : c'est une course. Une
sonde, derrière une étiquette de compilation pour ne pas casser la suite,
ouvre deux comptes en parallèle :

## 2. Classer

| Réaction | Peut-elle refuser l'ouverture ? | Peut-on la perdre ? | Forme |
|---|---|---|---|
| e-mail de bienvenue | non | oui, si on le compte | abonné |
| CRM | non | oui, rattrapable | abonné, avec **son propre** délai |
| prime de parrainage | non, mais c'est une **promesse d'argent** | **non** | appel direct, dans `Open`, erreur visible |
| compteur du tableau de bord | non | oui | abonné, sûr en concurrence |

La prime est le piège de l'exercice. Elle ne refuse rien, donc la table de
la leçon la classerait en abonné. Mais elle déplace de l'argent : la perdre
au plantage du processus, ou la laisser échouer en silence, c'est ne pas
tenir une promesse faite au client. Tant que la banque n'a pas d'outbox
(niveau 8), sa place est **dans** l'opération, avec un échec qu'on voit.

## 3. La nouvelle forme

```go
// AccountOpened says that an account exists, and whether the referral
// bonus was paid.
type AccountOpened struct {
    Account    signup.Account
    ReferredBy string
    BonusPaid  bool
}
```

```go
// Open creates the account and pays the referral bonus, then announces the
// opening. Once the account exists, Open succeeds: a bonus that cannot be
// paid is logged as an error, with what is needed to pay it by hand.
func (s *Service) Open(ctx context.Context, r signup.Request) (signup.Account, error) {
    a, err := s.Accounts.Create(r.Name, r.Phone)
    if err != nil {
        return signup.Account{}, err
    }
    paid := false
    if r.ReferredBy != "" {
        _, err := s.Ledger.Move("bonus-"+a.ID, "promo", r.ReferredBy, signup.ReferralBonus)
        if err != nil {
            s.Log.Error("referral bonus not paid", "account", a.ID, "referrer", r.ReferredBy, "err", err)
        }
        paid = err == nil
    }
    e := AccountOpened{Account: a, ReferredBy: r.ReferredBy, BonusPaid: paid}
    if err := s.Events.Publish(ctx, e); err != nil {
        s.Log.Warn("account opened, a reaction failed", "account", a.ID, "err", err)
    }
    return a, nil
}
```

Trois décisions :

- La prime est payée **avant** l'annonce, et l'événement dit si elle l'a été
  (`BonusPaid`). Un abonné peut ainsi envoyer « votre filleul a ouvert son
  compte, 2 000 FCFA vous ont été crédités » sans relire le grand livre, et
  ne pas l'envoyer quand c'est faux.
- Une prime impayée n'annule pas l'ouverture : le compte existe déjà, et il
  n'y a pas de transaction pour le défaire. Elle est journalisée au niveau
  **Error**, avec ce qu'il faut pour la payer à la main. C'est un compromis
  assumé, et il vaut mieux qu'une goroutine qui l'oublie.
- `Open` réussit dès que le compte existe, comme `Transfer` dans la leçon.

Les réactions sont des adaptateurs d'une ligne, qui traduisent l'événement
vers les interfaces existantes :

```go
// PushToCRM adapts a signup.CRM to the event. It gives the call its own
// deadline: it runs after the request is over.
func PushToCRM(c signup.CRM, timeout time.Duration) func(context.Context, AccountOpened) error {
    return func(ctx context.Context, e AccountOpened) error {
        ctx, cancel := context.WithTimeout(ctx, timeout)
        defer cancel()
        return c.Push(ctx, e.Account)
    }
}
```

Les imports confirment que le service ne connaît plus ni le mailer ni le
CRM. Il importe encore `signup` pour les types `Account`, `Request` et
`Accounts`, mais n'utilise plus ses interfaces `Mailer` et `CRM` :

```text
example/corrections34/ex3/opening: context example/exercises34/ex3/signup example/exercises34/ledger log/slog sync time
example/exercises34/ex3/signup: context errors example/exercises34/ledger fmt sync
```

L'assemblage branche les trois réactions sur un bus `Async` ; c'est le
`newWorld` des tests :

```go
func newWorld(m signup.Mailer, promo int64) *world {
    w := &world{crm: crm{seen: make(chan error, 10)}, opened: &opening.Opened{}, log: &bytes.Buffer{}}
    w.events = &bus.Async[opening.AccountOpened]{Size: 64, OnError: func(err error) {
        w.mu.Lock()
        defer w.mu.Unlock()
        w.failed = append(w.failed, err)
    }}
    for _, h := range []bus.Handler[opening.AccountOpened]{
        opening.Welcome(m), opening.PushToCRM(w.crm, time.Second), w.opened.Handle,
    } {
        if _, err := w.events.Subscribe(h); err != nil {
            panic(err)
        }
    }
    w.svc = &opening.Service{
        Accounts: &signup.Accounts{},
        Ledger:   ledger.New(map[string]int64{"promo": promo, "acc-ref": 0}),
        Events:   w.events,
        Log:      slog.New(slog.NewTextHandler(w.log, nil)),
    }
    return w
}
```

Une remarque d'honnêteté : dans la première version de ces tests, le faux
CRM envoyait dans un canal de 10 places **sans** `select`. Le test qui ouvre
vingt comptes a bloqué : la onzième réaction attendait une place, la
goroutine de l'abonné restait coincée, et `Close` ne rendait jamais la
main. C'est exactement le défaut de l'exercice 2, commis dans un faux de
test. Le faux ne bloque plus :

```go
// crm reports the state of the context it was given, once it gets to it.
// It never blocks: a handler that blocks would block Close.
type crm struct{ seen chan error }
```

## 4. Les tests, après

Chaque test de caractérisation a son pendant, **renommé** parce que le
comportement a changé exprès :

| Avant (défaut épinglé) | Après | Pourquoi le changement est voulu |
|---|---|---|
| `TestAWelcomeFailureReportsAFailedOpeningOfAnAccountThatExists` | `TestAWelcomeFailureNoLongerFailsTheOpening` | le compte existe : l'échec de l'e-mail est remonté par `OnError`, pas au client |
| `TestTheCRMGetsACanceledContext` | `TestTheCRMGetsItsOwnDeadline` | le CRM tourne après la requête, avec un délai qui lui appartient |
| `TestAnEmptyPromoAccountLosesTheBonusSilently` | `TestAnUnpaidBonusIsLoggedAndAnnounced` | une promesse non tenue doit se voir |
| `TestTheBonusIsPaidSometimeAfterOpenReturns` | `TestTheBonusIsPaidBeforeOpenReturns` | payée dans l'opération, donc avant la réponse |
| sonde de course | `TestOpeningsInParallelAreAllCounted`, `TestTheDashboardCanReadWhileAccountsOpen` | le compteur est un abonné sûr en concurrence |

```text

--- PASS: TestAnUnpaidBonusIsLoggedAndAnnounced (0.01s)
```

### La campagne

```text
prime payée dans une goroutine               tuee
prime toujours annoncée payée                tuee
prime manquée non journalisée                tuee
refus annoncé                                tuee
CRM sans délai propre                        tuee
compteur sans verrou                         SURVIT
```

Au premier passage, « compteur sans verrou » **survit**. Ce n'est pas un
hasard, c'est l'exercice 1.c : branché sur `Async`, `Opened.Handle` n'est
appelé que par **une** goroutine, et le test ne lisait `Count()` qu'après
`Close`. Sans verrou, rien ne se chevauche. Mais en production, le tableau
de bord lit le compteur **pendant** que les comptes s'ouvrent. Le test qui
manquait fait exactement cela :

```go
// The dashboard reads the counter while accounts are being opened: the
// reaction runs in the bus's goroutine, the reader in another.
func TestTheDashboardCanReadWhileAccountsOpen(t *testing.T) {
    w := newWorld(mailer{}, 100000)
    done := make(chan struct{})
    go func() {
        defer close(done)
        for range 100 {
            _ = w.opened.Count()
        }
    }()
    for i := range 20 {
        _, _ = w.svc.Open(context.Background(), signup.Request{Name: "n", Phone: fmt.Sprint("+2377", i)})
    }
    <-done
    w.events.Close()
}
```

Rejouée avec lui, la mutation est tuée :

```text

prime toujours annoncée payée                tuee
prime manquée non journalisée                tuee
refus annoncé                                tuee
CRM sans délai propre                        tuee
compteur sans verrou                         tuee
6/6 tuees
```

## Ce qu'il faut retenir

1. On caractérise avant de refactorer, défauts compris, et chaque défaut est
   un test **nommé**. Une course se caractérise par une sonde sous `-race`,
   pas par un test vert.
2. « Peut-elle refuser ? » ne suffit pas pour classer une réaction. Il faut
   aussi demander « peut-on la perdre ? ». Ce qui déplace de l'argent ne se
   perd pas.
3. Un événement peut porter le **résultat** de ce qui est resté dans
   l'opération (`BonusPaid`), pour que les abonnés n'aient pas à le
   redemander.
4. Chaque test de caractérisation qui change est un changement de
   comportement : on le renomme, et on écrit pourquoi.
