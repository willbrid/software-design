# Correction 3.2 — Exercice 1 : quatre extraits

> Rappel de l'énoncé : un constructeur qui recopie, une structure de
> configuration à défauts, un limiteur à options qui se contrôlent, un grand
> livre dont la valeur zéro est prête.

Les quatre extraits tournent dans un module vert sous `go vet ./...` et
`go test -race -count=1 ./...`, avec les tests qui établissent les faits de
cette correction.

## 1. Les chemins vers un objet invalide

| Extrait | Littéral | Après coup | Valeur zéro | Par la porte |
|---|---|---|---|---|
| **A** `Account` | **ouvert** | **ouvert** | ouvert | **ouvert** : `NewAccount` recopie |
| **C** `Limiter` | fermé | fermé | ouvert | **ouvert, deux fois** |
| **D** `Ledger` | sans objet | **ouvert** : la copie | prête | sans objet |

**A** n'a aucune porte : les champs sont exportés, et le constructeur
lui-même accepte tout.

```go
// TestAAcceptsEverything: the constructor of A copies its arguments.
func TestAAcceptsEverything(t *testing.T) {
    a := NewAccount("", "", -1_000_000)
    if a.ID != "" || a.Overdraft != -1_000_000 {
        t.Fatalf("%+v", a)
    }
    a.Overdraft = -5 // and the fields stay open after it
}
```

**C** est le cas instructif. Ses champs ne sont pas exportés : un autre paquet
ne peut écrire ni `Limiter{rate: 100, burst: 50}`, ni `l.burst = 50`. La porte
est donc la seule entrée — et **c'est elle qui laisse passer** :

```
rate then burst: limiter: burst below rate
burst then rate: accepted, rate 100, burst 50
WithRate(100) alone: accepted, rate 100, burst 10
```

Deux limiteurs invalides sortis de la porte, plus la valeur zéro. Fermer les
champs ne sert à rien si le constructeur ne contrôle pas la règle **après**
toutes les options.

**D** n'a qu'une règle — le verrou protège les entrées — et un seul moyen de
la violer : copier le grand livre. C'est la question 5.

## 2. Les valeurs zéro

| | Valeur zéro | Verdict |
|---|---|---|
| `Account` | un compte sans identifiant ni titulaire | **indiscernable** d'un compte saisi vide : rien ne peut la détecter, puisque `NewAccount("", "", 0)` donne la même |
| `Limiter` | débit 0, rafale 0 | **piège** : à détecter |
| `Ledger` | un grand livre vide, verrou ouvert | **utile**, et documentée comme telle |

Pour `Limiter`, tout dépend de la façon dont on écrit `Allow`. Avec un
intervalle calculé par division — la forme la plus courante :

```
interval of the zero Limiter: panic: runtime error: integer divide by zero
```

Avec un seau de jetons rempli à `rate × temps écoulé`, il ne panique pas : il
ne se remplit jamais, et **refuse tout, en silence**. Les deux sont pires
qu'une erreur nommée. La valeur zéro d'un limiteur ne peut pas être utile — un
débit de zéro n'a pas de sens —, donc elle doit être **détectée** : `Allow`
sur un limiteur non construit rend une erreur.

## 3. Extrait B : le zéro déjà pris

```
ServerConfig{MaxBody: 0}: MaxBody 1048576
```

Le point d'entrée qui devait refuser tout corps accepte un mébioctet. Le
commentaire de la structure le disait — « un champ à zéro prend son défaut » —,
et l'équipe a lu le nom du champ, pas le commentaire.

Trois réparations, et ce qu'elles coûtent aux **autres** équipes :

| Réparation | Ce qu'elle coûte |
|---|---|
| `MaxBody *int64` | **chaque équipe qui renseigne `MaxBody` casse** à la compilation, et écrit désormais `MaxBody: ptr(int64(4096))` |
| une sentinelle, `NoBody = -1` | rien à la compilation ; une convention à connaître, et `-1` devient une taille valide |
| un champ explicite, `RefuseBody bool` | rien : son zéro, `false`, est le comportement actuel |

Le champ explicite est la seule réparation dont le zéro **veut honnêtement dire
« le défaut »** — c'est la règle de la leçon, section 5. Il ajoute une règle
qui lie deux champs — `RefuseBody` avec un `MaxBody` non nul est
contradictoire — à contrôler une fois, dans le constructeur du serveur.

## 4. Extrait C : l'ordre décide

Les prédictions, mesurées :

```
rate then burst: limiter: burst below rate
burst then rate: accepted, rate 100, burst 50
WithRate(100) alone: accepted, rate 100, burst 10
```

Le même débit et la même rafale, refusés dans un ordre et acceptés dans
l'autre — et l'acceptation viole la règle que l'option prétendait contrôler.
La troisième ligne n'était pas demandée et elle est la plus grave : **une seule
option suffit**, parce que la règle n'est contrôlée que dans `WithBurst`, et
qu'un débit seul laisse la rafale par défaut au-dessous de lui.

La réécriture : les options enregistrent, `New` contrôle une fois.

```go
type config struct {
    rate, burst int
    burstSet    bool
}
```

```go
// WithBurst sets the size of a burst, which cannot be below the rate.
// Without it, the burst follows the rate.
func WithBurst(n int) Option {
    return func(c *config) { c.burst, c.burstSet = n, true }
}
```

```go
// New returns a limiter of 10 requests per second, bursts of 10, changed
// by the options, then checked once.
func New(opts ...Option) (*Limiter, error) {
    c := config{rate: 10}
    for _, o := range opts {
        o(&c)
    }
    if !c.burstSet {
        c.burst = c.rate
    }
    switch {
    case c.rate <= 0:
        return nil, fmt.Errorf("%w: rate %d", ErrConfig, c.rate)
    case c.burst < c.rate:
        return nil, fmt.Errorf("%w: burst %d below rate %d", ErrConfig, c.burst, c.rate)
    }
    return &Limiter{rate: c.rate, burst: c.burst}, nil
}
```

Le champ `burstSet` est le détail qui compte. Sans lui, « la rafale suit le
débit quand elle n'est pas donnée » s'écrirait `if c.burst == 0` — et
`WithBurst(0)` deviendrait « pas donnée ». C'est le zéro de l'extrait B,
recréé à l'intérieur des options. La campagne l'a vérifié.

```go
func TestTheOrderNoLongerMatters(t *testing.T) {
    for _, opts := range [][]Option{
        {WithRate(100), WithBurst(50)},
        {WithBurst(50), WithRate(100)},
    } {
        if _, err := New(opts...); !errors.Is(err, ErrConfig) {
            t.Fatalf("rate 100, burst 50: %v", err)
        }
    }
    for _, opts := range [][]Option{
        {WithRate(100), WithBurst(150)},
        {WithBurst(150), WithRate(100)},
    } {
        l, err := New(opts...)
        if err != nil || l.Rate() != 100 || l.Burst() != 150 {
            t.Fatalf("rate 100, burst 150: %v, %v", l, err)
        }
    }
}
```

## 5. Extrait D : le grand livre copié

**`NewLedger` ne sert à rien** : la valeur zéro est prête, le commentaire le
dit, et `var l ex1.Ledger` suffit. Il ne nuit pas non plus ; son seul défaut
est de laisser croire que la valeur zéro ne l'est pas. On le garde seulement
s'il doit un jour faire autre chose qu'allouer.

**`snapshot := *ledger`**, `go vet` le refuse, deux fois :

```
ex1/snap.go:5:14: assignment copies lock value to snapshot: example/c32/ex1.Ledger contains sync.Mutex
ex1/snap.go:6:9: return copies lock value: example/c32/ex1.Ledger contains sync.Mutex
```

Sans `go vet`, la copie emporte deux choses qu'elle ne devrait pas.

**Le verrou, dans l'état où il est.** Copié pendant qu'une écriture le tient,
il est verrouillé dans la copie, et personne ne le déverrouillera jamais :

```
copied while locked
fatal error: all goroutines are asleep - deadlock!
```

**Le tableau des entrées.** Une tranche copiée partage son tableau. Le test
écrit explicitement ce que `*ledger` copie, sans le verrou, pour que `go vet`
le laisse passer :

```go
// TestDTheCopySharesTheEntries: what `snapshot := *ledger` copies, without
// the lock: the slice header, so the same backing array.
func TestDTheCopySharesTheEntries(t *testing.T) {
    var l Ledger
    for _, a := range []string{"A", "B", "C"} {
        l.Add(Entry{Account: a, Amount: 100})
    }
    snapshot := Ledger{entries: l.entries}
    l.Add(Entry{Account: "D", Amount: 100})
    snapshot.Add(Entry{Account: "X", Amount: -999})
    if got := l.entries[3].Account; got != "X" {
        t.Fatalf("entry 4 of the ledger: %q", got)
    }
    t.Logf("entry 4 of the ledger after snapshot.Add: %+v", l.entries[3])
}
```

```
entry 4 of the ledger after snapshot.Add: {Account:X Amount:-999}
```

Une écriture dans l'**instantané** a remplacé la quatrième écriture du
**grand livre** : un crédit de 100 devenu un débit de 999, sans erreur et
sans course que `-race` puisse voir — tout s'est passé dans une seule
goroutine. La réparation est une méthode qui copie sous le verrou :

```go
// Snapshot returns a copy of the entries, taken under the lock: the
// export gets its own array, and the ledger keeps its own lock.
func (l *Ledger) Snapshot() []Entry {
    l.mu.Lock()
    defer l.mu.Unlock()
    return slices.Clone(l.entries)
}
```

> Un type qui contient un verrou ne se copie pas, et sa valeur zéro peut être
> prête : les deux vont ensemble. C'est pour ça que `sync.Mutex` est la
> valeur zéro utile la plus citée — et que `go vet` surveille sa copie.

## 6. La question ouverte

Aujourd'hui, `NewAccount` ne sert à rien : il fait ce que fait le littéral,
avec des arguments positionnels en plus.

Le jour où le découvert doit être positif ou nul, il devient la seule chose
utile de l'extrait — à condition de payer deux prix d'un coup. Sa signature
devient `(*Account, error)` : **chaque appelant casse**, c'est la première
mesure de la leçon. Et les champs doivent devenir non exportés, sinon la
porte a un mur à côté : **chaque lecture et chaque écriture de champ** casse
aussi. Un constructeur qui recopie des champs exportés n'est pas une porte ;
c'est un nom de plus pour le littéral. Son seul mérite est d'avoir habitué les
appelants à passer par une fonction, ce qui rendra la migration un peu moins
chère.

## 7. La campagne

Dix modifications sur le limiteur réécrit. Première passe :

```
rafale : ne suit plus le debit                 tuee
rafale egale au debit refusee                  tuee
debit nul accepte                              tuee
debit nul accepte (borne)                      tuee
WithBurst oublie burstSet                      tuee
WithRate sans effet                            tuee
defaut : 1 requete par seconde                 SURVIT
Burst rend le debit                            tuee
controle dans WithBurst                        tuee
zero : rafale non donnee                       SURVIT
8/10 tuees
```

**« Défaut : 1 requête par seconde ».** Aucun test ne construisait un
limiteur sans option : le défaut promis par l'extrait C n'était vérifié nulle
part.

**« Zéro : rafale non donnée ».** La modification annoncée à la question 4 :
`if c.burst == 0` à la place de `if !c.burstSet`. Aucun test ne donnait une
rafale de zéro — c'est-à-dire aucun test ne distinguait « pas donné » de
« donné à zéro ».

```go
// TestTheDefaults: without options, extract C promised 10 and 10.
func TestTheDefaults(t *testing.T) {
    l, err := New()
    if err != nil || l.Rate() != 10 || l.Burst() != 10 {
        t.Fatalf("%v, %v", l, err)
    }
}
```

```go
// TestABurstOfZeroIsABurstOfZero: given, zero is a value, and it breaks
// the rule. It is not "not given".
func TestABurstOfZeroIsABurstOfZero(t *testing.T) {
    if _, err := New(WithBurst(0)); !errors.Is(err, ErrConfig) {
        t.Fatalf("burst 0: %v", err)
    }
}
```

Deuxième passe :

```
10/10 tuees
```

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Fermer les champs ne sert que si la porte contrôle : le limiteur aux champs non exportés laissait sortir deux limiteurs invalides par son constructeur. |
| ⚫ | Une règle contrôlée dans une option ne voit pas les options suivantes. Mesuré : refusé dans un ordre, accepté dans l'autre, et accepté avec **une seule** option. |
| ⚫ | `ServerConfig{MaxBody: 0}` donne 1 048 576 octets. Le zéro d'une structure de configuration ne sait pas dire zéro. |
| ⚫ | Le même piège se recrée à l'intérieur des options dès qu'on écrit `if c.burst == 0` au lieu de garder « donné ou non ». |
| ⚫ | Une valeur zéro qui ne peut pas être utile se détecte : une division par un débit nul panique, un seau jamais rempli refuse tout en silence. |
| ⚫ | Copier un type qui contient un verrou copie aussi son état et ses tranches : interblocage mesuré, et une écriture de l'instantané qui remplace une écriture du grand livre. |
