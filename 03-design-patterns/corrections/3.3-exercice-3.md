# Correction 3.3 — Exercice 3 : démêler l'expéditeur de SMS

> Rappel de l'énoncé : un `sms.Sender` qui mêle journal, reprises et limite
> par numéro. Caractériser, découper en trois décorateurs, décider de
> l'ordre, et assumer chaque comportement changé.

Tout le code de cette correction est vert sous `go vet ./...` et
`go test -race -count=1 ./...`. Les tests de caractérisation tournent
**contre les deux versions** à la fois : l'ancienne (`sms.Sender` de
l'énoncé) et la nouvelle (`notify.New`).

## En bref

- L'ancien `Send` a deux comportements que personne n'a demandés : **un
  message entièrement raté bloque quand même le numéro** pendant 30 s, et
  **`Retries: -1` rend `nil` sans rien envoyer**. Il panique aussi sans
  horloge.
- La nouvelle forme : `Logging > Limiting > Retrying > fournisseur`. La
  limite compte des **messages**, pas des tentatives, et un message raté
  rend sa place.
- Cinq comportements sont identiques, quatre changent, et chacun des quatre
  a son test, qui dit ce que faisait l'ancienne version et pourquoi la
  nouvelle diffère.

## 1. Caractériser d'abord

Lire `Send` ligne à ligne, et noter **tout** ce qu'il fait, demandé ou non :

| # | Comportement de l'ancien `Send` | Voulu ? |
|---|---|---|
| 1 | réessaie sur `ErrUnavailable`, jusqu'à `Retries` fois, sans attendre | oui |
| 2 | ne réessaie pas une autre erreur | oui |
| 3 | un message par numéro et par période `Every` ; les numéros sont indépendants | oui |
| 4 | sous concurrence, un seul message passe pour un même numéro | oui |
| 5 | une ligne de journal **par tentative**, avec son numéro, et une ligne pour un refus | à décider |
| 6 | **la place est prise avant l'envoi et jamais rendue** : un message dont toutes les tentatives échouent bloque le numéro pendant `Every` | **non** |
| 7 | **`Retries` négatif saute la boucle** : `Send` rend `nil`, rien n'est envoyé | **non** |
| 8 | un `Sender` sans `Now` panique au premier message | non |
| 9 | les reprises ignorent l'annulation du contexte : c'est le fournisseur qui décide | à noter |

Le 6 est celui de l'énoncé. Imagine l'utilisateur pendant une panne de
quinze secondes du fournisseur : il demande son code, les trois tentatives
échouent, il redemande… et reçoit « too soon » pendant trente secondes, alors
qu'il n'a jamais rien reçu.

Le 7 est pire, parce qu'il est **silencieux** : `for attempt := 0; attempt <=
s.Retries; attempt++` ne s'exécute pas une seule fois quand `Retries` vaut
`-1`, `err` reste à `nil`, et l'appelant croit le code parti. Une
configuration qui met `-1` pour dire « pas de reprise » — c'est une
convention courante — désactive les SMS sans erreur.

Chaque ligne du tableau devient un test. Le harnais construit les deux
versions avec la même signature :

```go
// build makes a sender from a provider, a logger, retries, a period and a
// clock. Every characterization runs against both versions.
type build func(p func(context.Context, string, string) error, log *slog.Logger, retries int, every time.Duration, now func() time.Time) notify.Sender

var (
    before build = func(p func(context.Context, string, string) error, log *slog.Logger, retries int, every time.Duration, now func() time.Time) notify.Sender {
        return &sms.Sender{Provider: p, Log: log, Retries: retries, Every: every, Now: now}
    }
    after build = notify.New
)
```

## 2. La nouvelle forme

```go
// Sender sends one text message.
type Sender interface {
    Send(ctx context.Context, to, text string) error
}

// SenderFunc lets a provider function be a Sender.
type SenderFunc func(ctx context.Context, to, text string) error

// Send calls f.
func (f SenderFunc) Send(ctx context.Context, to, text string) error { return f(ctx, to, text) }
```

```go
// Logging writes one line per message, with its outcome.
type Logging struct {
    Next Sender
    Log  *slog.Logger
}

// Send logs the outcome of Next.Send.
func (l Logging) Send(ctx context.Context, to, text string) error {
    err := l.Next.Send(ctx, to, text)
    l.Log.Info("sms", "to", to, "err", err)
    return err
}
```

```go
// Retrying tries once, then up to Retries more times on
// sms.ErrUnavailable. A negative Retries means no retry.
type Retrying struct {
    Next    Sender
    Retries int
}

// Send retries temporary failures.
func (r Retrying) Send(ctx context.Context, to, text string) error {
    for attempt := 0; ; attempt++ {
        err := r.Next.Send(ctx, to, text)
        if err == nil || !errors.Is(err, sms.ErrUnavailable) || attempt >= r.Retries {
            return err
        }
    }
}
```

`attempt >= r.Retries` plutôt que `==` : avec `Retries: -1`, la première
tentative a lieu, puis la boucle s'arrête. Le comportement 7 disparaît.

```go
// Limiting lets at most one message per number through per Every. A
// message that fails gives its slot back. A nil Now means time.Now.
type Limiting struct {
    Next  Sender
    Every time.Duration
    Now   func() time.Time

    mu   sync.Mutex
    last map[string]time.Time
}

// Send reserves the number's slot, sends, and keeps the slot only if the
// message went out.
func (l *Limiting) Send(ctx context.Context, to, text string) error {
    now := time.Now
    if l.Now != nil {
        now = l.Now
    }
    l.mu.Lock()
    if prev, ok := l.last[to]; ok && now().Sub(prev) < l.Every {
        l.mu.Unlock()
        return sms.ErrTooSoon
    }
    if l.last == nil {
        l.last = map[string]time.Time{}
    }
    l.last[to] = now()
    l.mu.Unlock()

    err := l.Next.Send(ctx, to, text)
    if err != nil {
        l.mu.Lock()
        delete(l.last, to)
        l.mu.Unlock()
    }
    return err
}
```

```go
// New builds the chain: one log line per message, then the limit, then
// the retries, then the provider.
func New(provider func(ctx context.Context, to, text string) error, log *slog.Logger,
    retries int, every time.Duration, now func() time.Time) Sender {
    return Logging{Log: log, Next: &Limiting{Every: every, Now: now,
        Next: Retrying{Retries: retries, Next: SenderFunc(provider)}}}
}
```

## 3. L'ordre de la limite et des reprises

**La limite est au-dessus des reprises.** Ce que la limite protège, c'est le
**téléphone de l'utilisateur** — et la facture des SMS : un message par
période. Trois tentatives pour **un** message ne sont pas trois messages.
Au-dessus, la limite prend une place par message ; les reprises, dessous, ne
la voient pas.

**Un message raté rend sa place.** La place est **réservée avant** l'envoi —
c'est ce qui garantit qu'un seul message passe quand cinquante demandes
arrivent en même temps (`TestConcurrentSendsToOneNumber`, sous `-race`) —
puis **rendue** si l'envoi échoue. Le prix, assumé : une demande arrivée
pendant un envoi qui finira par échouer reçoit « too soon » pour rien. Elle
peut redemander aussitôt.

**Le journal est tout en haut**, une ligne par message, refus compris. C'est
ce que lit le support (« le client dit qu'il n'a rien reçu »). Une ligne par
tentative sert à enquêter sur le fournisseur ; elle s'obtient en ajoutant un
second `Logging` **sous** `Retrying`, une ligne dans `New`.

## 4. Les comportements changés, un par un

Les cinq premiers tests passent **à l'identique** sur les deux versions. Les
quatre suivants attendent une réponse différente selon la version, et le
disent dans leur commentaire. Le plus important :

```go
// TestAFailedMessageKeepsTheQuota: before, a message that failed on every
// attempt still blocked the number for Every; the user could not ask for a
// new code for 30 s after an outage. After, a failed message gives its slot
// back.
func TestAFailedMessageKeepsTheQuota(t *testing.T) {
    want := map[string]error{"before": sms.ErrTooSoon, "after": nil}
    for _, v := range versions {
        p, _ := script(3, sms.ErrUnavailable)
        c := newClock()
        s := v.build(p, quiet(), 2, 30*time.Second, c.now)
        s.Send(context.Background(), to, "code") // three attempts, all fail
        c.add(10 * time.Second)
        if err := s.Send(context.Background(), to, "code"); !errors.Is(err, want[v.name]) || (want[v.name] == nil) != (err == nil) {
            t.Errorf("%s: second message = %v, want %v", v.name, err, want[v.name])
        }
    }
}
```

Les trois autres suivent le même modèle : `TestNegativeRetries` (avant : zéro
appel et `nil` ; après : un appel), `TestLogLines` (avant : une ligne par
tentative ; après : une par message), `TestNilClock` (avant : panique ;
après : `time.Now`).

```go
// TestLogLines: before, one line per attempt with its index, and one line
// for a refusal. After, one line per message with its outcome; a line per
// attempt is one more Logging under Retrying, if someone needs it.
func TestLogLines(t *testing.T) {
    want := map[string]string{
        "before": "attempt=0 err=\"sms: provider unavailable\"|attempt=1 err=<nil>|err=\"sms: too soon for this number\"",
        "after":  "err=<nil>|err=\"sms: too soon for this number\"",
    }
    for _, v := range versions {
        var buf bytes.Buffer
        log := slog.New(slog.NewTextHandler(&buf, &slog.HandlerOptions{ReplaceAttr: func(_ []string, a slog.Attr) slog.Attr {
            if a.Key == "time" || a.Key == "level" || a.Key == "msg" || a.Key == "to" {
                return slog.Attr{}
            }
            return a
        }}))
        p, _ := script(1, sms.ErrUnavailable)
        s := v.build(p, log, 2, 30*time.Second, newClock().now)
        s.Send(context.Background(), to, "1")
        s.Send(context.Background(), to, "2")
        got := strings.ReplaceAll(strings.TrimSpace(buf.String()), "\n", "|")
        if got != want[v.name] {
            t.Errorf("%s:\n got  %s\n want %s", v.name, got, want[v.name])
        }
    }
}
```

C'est le geste qui rend un refactoring honnête : **un test qui change
d'attendu est un changement de comportement**, et il est écrit comme tel, avec
l'ancien attendu à côté du nouveau.

## La campagne

Onze mutations sur la nouvelle forme. Premier passage :

```text
journal : avale l'erreur                     tuee
journal : pas de ligne                       tuee
reprises : une de trop                       tuee
reprises : reprend tout                      tuee
limite : periode exacte refusee              tuee
limite : echec garde le quota                tuee
limite : succes rend le quota                tuee
limite : efface au lieu de restaurer         SURVIT
limite : lecture hors verrou                 tuee
limite : horloge nulle panique               tuee
chaine : reprises autour de la limite        SURVIT
9/11 tuees
```

**« limite : efface au lieu de restaurer »** survivait, et elle avait raison.
La première version de `Limiting` rendait la place en **restaurant** l'ancienne
date quand il y en avait une :

```go
    err := l.Next.Send(ctx, to, text)
    if err != nil {
        l.mu.Lock()
        if had {
            l.last[to] = prev
        } else {
            delete(l.last, to)
        }
        l.mu.Unlock()
    }
```

Mais si une ancienne date existait **et** que le message est passé, c'est
qu'elle était déjà expirée : la restaurer ou l'effacer donne le même résultat
au message suivant. Diagnostic : **suppression de branche**. La version
publiée efface simplement (section 2), et la mutation n'a plus d'objet.

**« chaîne : reprises autour de la limite »** survit aux deux passages.
Mettre `Retrying` au-dessus de `Limiting` fait réserver et rendre la place
**à chaque tentative**. Avec ce `Retrying`, qui réessaie sans attendre, la
fenêtre entre « rendre » et « réserver à nouveau » dure quelques
instructions : aucun test ne peut s'y glisser, et les résultats sont les
mêmes. Diagnostic : **rien, aujourd'hui**. Le jour où `Retrying` attendra
entre deux tentatives — ce que fait celui de la leçon —, un autre message
pourra prendre la place pendant l'attente, et la tentative suivante recevra
`ErrTooSoon`. L'ordre choisi ne dépend pas de ce détail ; c'est la raison de
le préférer.

Deuxième passage, après la suppression de la branche :

```text
journal : avale l'erreur                     tuee
journal : pas de ligne                       tuee
reprises : une de trop                       tuee
reprises : reprend tout                      tuee
limite : periode exacte refusee              tuee
limite : echec garde le quota                tuee
limite : succes rend le quota                tuee
limite : lecture hors verrou                 tuee
limite : horloge nulle panique               tuee
chaine : reprises autour de la limite        SURVIT
9/10 tuees
```

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Caractériser, c'est écrire **tout** ce que fait le code, y compris ce que personne n'a demandé : ici, un quota consommé par un échec et un `Retries: -1` qui n'envoie rien. |
| ⚫ | Faire tourner les mêmes tests contre l'ancienne et la nouvelle forme rend chaque différence visible et datée. |
| ⚫ | Un test qui change d'attendu est un changement de comportement : il garde l'ancien attendu à côté du nouveau, et dit pourquoi. |
| ⚫ | Une limite protège une unité métier — un message — : elle va au-dessus des reprises, qui ne sont qu'un détail de transport. |
| ⚫ | Réserver avant, rendre en cas d'échec : la seule façon d'avoir à la fois l'exclusivité sous concurrence et un échec qui ne pénalise pas. |
| ⚫ | Une mutation qui survit peut signaler une branche inutile : on la supprime au lieu de lui écrire un test. |
