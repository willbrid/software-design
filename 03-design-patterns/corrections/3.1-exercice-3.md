# Correction 3.1 — Exercice 3 : les canaux de paiement

> Rappel de l'énoncé : une liste de quatre canaux, trois `switch` dans deux
> fichiers — les frais, le plafond, le libellé —, des tests verts, et une
> faute à trouver sans lire les `switch` un par un.

Deux paquets, `before` (le code tel qu'il est, plus les tests de cette
correction) et `after` (le refactoring), verts sous `go vet ./...` et
`go test -race -count=1 ./...`. Campagne de dix modifications, 10/10 après deux
passes — et la deuxième passe a corrigé une faute de **mon** refactoring.

## 1. Le test qui parcourt la liste

```go
// walk asks the three functions about every channel of the list, instead of
// reading the switches one by one, and returns what is missing.
func walk() []string {
    var missing []string
    for _, c := range Channels {
        if _, err := Fee(c, 100_000); err != nil {
            missing = append(missing, c+": no fee")
        }
        if Limit(c) <= 0 {
            missing = append(missing, fmt.Sprintf("%s: limit %d", c, Limit(c)))
        }
        if Label(c) == c {
            missing = append(missing, c+": no label")
        }
    }
    return missing
}
```

```
walk: [cash: limit 0]
```

**Le plafond des espèces n'existe pas.** `Limit("cash")` tombe hors du
`switch` et rend 0. Ce que fait la production dépend de l'appelant, et les
deux lectures sont mauvaises :

- s'il refuse un paiement au-dessus du plafond, **tout paiement en espèces est
  refusé** — et l'incident arrive au premier guichet ;
- s'il lit 0 comme « pas de plafond », **les espèces n'ont aucune limite** —
  et l'incident arrive au premier contrôle de conformité.

Aucune des deux n'est un choix ; c'est une valeur zéro qui en tient lieu. Et
le plafond des espèces n'est écrit **nulle part** : le refactoring ne peut pas
le retrouver, il faut le demander au métier. J'ai mis 1 000 000 XAF, en
hypothèse déclarée dans le code.

## 2. Pourquoi aucun test ne l'a vue

> **La liste des canaux existe en quatre exemplaires — `Channels` et trois
> `switch` — et rien ne relie les copies.** Les tests interrogent chaque
> fonction sur les canaux auxquels leur auteur a pensé ; personne n'a pensé à
> demander le plafond des espèces, parce que personne ne lit les quatre listes
> ensemble.

C'est la mesure de la section 3 de la leçon, sur du vrai code : à partir de la
deuxième opération, un `switch` recopie la liste des cas.

## 3. Le refactoring

Les quatre canaux ne diffèrent pas par leur code, ils diffèrent par leurs
**valeurs** : un taux, un plafond de frais, des frais fixes, une limite, un
libellé. C'est le cas du type paramétré de la leçon et de l'exercice 2 — **une
table, une entrée par canal, tous les champs remplis** :

```go
// Channel is everything the bank knows about a payment channel. Its fields
// are data: a channel differs from another by its values, not by its code.
type Channel struct {
    Name  string
    Label string // on the receipt, in French
    Limit int64  // maximum amount of one payment, in XAF
    // The fee is Flat + Bps of the amount, capped at Cap when Cap > 0.
    Flat, Bps, Cap int64
}
```

```go
// Fee returns the fee of a payment, in XAF.
func (c Channel) Fee(amount int64) int64 {
    f := amount * c.Bps / 10_000
    if c.Cap > 0 {
        f = min(f, c.Cap)
    }
    return c.Flat + f
}
```

```go
// table is the only list of the channels.
var table = []Channel{
    {Name: "card", Label: "Carte bancaire", Limit: 2_000_000, Bps: 150},
    {Name: "mobile_money", Label: "Mobile money", Limit: 500_000, Bps: 100, Cap: 2_000},
    {Name: "transfer", Label: "Virement", Limit: 50_000_000, Flat: 500},
    // The limit of cash exists nowhere in the original code: it is a business
    // decision to ask for. 1,000,000 XAF is an assumption.
    {Name: "cash", Label: "Especes", Limit: 1_000_000},
}
```

Les trois fonctions publiques gardent leur signature, et les tests existants
passent **sans une ligne de changement** : ils sont recopiés tels quels dans
`after`. Le test de complétude remplace le compilateur sur la table :

```go
// TestEveryChannelIsComplete replaces the compiler on the table: a field
// added to Channel is a field every channel must fill.
func TestEveryChannelIsComplete(t *testing.T) {
    seen := map[string]bool{}
    for _, c := range table {
        if seen[c.Name] {
            t.Errorf("%s: twice in the table", c.Name)
        }
        seen[c.Name] = true
        if c.Name == "" || c.Label == "" || c.Limit <= 0 {
            t.Errorf("%q is incomplete: %+v", c.Name, c)
        }
    }
}
```

### Avant de refactoriser : fixer ce que personne n'a fixé

La première passe de la campagne a montré trois survivants, et **les trois
étaient des comportements du code d'origine qu'aucun test ne fixait** :

```
la table perd cash                             tuee
le plafond de frais du mobile money ignore     tuee
la carte au taux du mobile money               tuee
un canal inconnu a des frais nuls              SURVIT
les frais fixes oublies                        tuee
le plafond du virement divise par dix          tuee
Label rend vide pour un canal inconnu          SURVIT
find rend toujours le premier canal            tuee
le mobile money sans libelle                   tuee
Channels dans un autre ordre                   SURVIT
7/10 tuees
```

- un canal inconnu rend une erreur dans `Fee` ;
- un canal inconnu garde **son nom** sur le reçu, dans `Label` ;
- `Channels` est dans l'ordre de déclaration — et ma première version de
  `after` le **triait**. Un menu qui affiche les canaux dans cet ordre aurait
  changé à la mise en production de mon refactoring, et aucun test ne
  l'aurait dit.

D'où le test de caractérisation, écrit **sur le code d'origine** et passé
**aux deux** :

```go
// TestTheBehaviorsNoTestPinned: before refactoring, pin what the code does
// on the cases nobody asked about. Here, an unknown channel keeps its name
// on the receipt.
func TestTheBehaviorsNoTestPinned(t *testing.T) {
    if got := Label("no-such-channel"); got != "no-such-channel" {
        t.Fatalf("Label(unknown) = %q", got)
    }
    // The order of the list is an output too: a menu may display it.
    if want := []string{"card", "mobile_money", "transfer", "cash"}; !slices.Equal(Channels, want) {
        t.Fatalf("Channels = %v", Channels)
    }
    if _, err := Fee("no-such-channel", 1); err == nil {
        t.Fatal("Fee(unknown) has no error")
    }
}
```

> Un refactoring conserve **tous** les comportements observables, y compris
> ceux qu'aucun test ne fixait. Le test de caractérisation s'écrit avant de
> toucher au code, sur le code d'origine, et il passe aux deux versions.

Deuxième passe :

```
10/10 tuees
```

## 5. `Label` et `Limit` n'ont pas le même défaut

| | Ce qu'il rend pour un canal oublié | Qui le voit |
|---|---|---|
| `Label` | **le nom brut du canal** — « crypto » sur le reçu | le client, au premier reçu : la faute est **visible** |
| `Limit` | **0** | personne, jusqu'à ce que l'argent bouge : la faute est **silencieuse**, et elle porte sur un contrôle |

`Limit` est le plus dangereux, pour la raison de la correction 2.3/5 : un
défaut qui produit une valeur plausible ne déclenche rien. Le refactoring n'a
ni l'un ni l'autre, parce qu'un canal **est** une entrée de table, et qu'une
entrée incomplète fait tomber un test qui la nomme.

## 6. La langue

**Une donnée, pas une deuxième stratégie.** La langue ne change pas le calcul
d'un canal, elle change un texte : `Label` devient une carte langue → texte
dans chaque entrée de la table, et le test de complétude vérifie que chaque
canal a un libellé dans chaque langue de la banque.

Ce que coûte une troisième langue : **une ligne par canal**, soit quatre
aujourd'hui, et le test de complétude nomme celles qui manquent — c'est la
mesure de la correction 2.4/2 (onze gabarits manquants nommés un par un).
En deuxième stratégie, le même ajout serait un type ou une fonction par
langue, et la combinaison canal × langue reviendrait au code.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Une faute de `switch` se trouve en **parcourant la liste** et en interrogeant chaque fonction, pas en relisant les `switch`. |
| ⚫ | Trois `switch` et une liste sont quatre copies de la même liste. Rien ne les relie, et la copie oubliée rend une valeur zéro. |
| ⚫ | Des variantes qui ne diffèrent que par leurs valeurs sont **une table** : un canal de plus est une ligne. |
| ⚫ | Un champ ajouté à une table est optionnel pour le compilateur ; un test de complétude le rend obligatoire et nomme l'entrée qui manque. |
| ⚫ | Un refactoring conserve tous les comportements observables. Le test de caractérisation s'écrit avant, sur le code d'origine — ici il a attrapé mon propre tri. |
| ⚫ | Une valeur zéro sur un contrôle (un plafond) est plus dangereuse qu'une valeur zéro sur un affichage (un libellé) : l'une se voit, l'autre bouge de l'argent. |
| ⚫ | La langue est une donnée de la table, pas une deuxième stratégie : les deux axes s'additionnent au lieu de se multiplier. |
