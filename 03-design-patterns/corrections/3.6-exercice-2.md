# Correction 3.6 — Exercice 2 : `New` qui refuse un service incomplet

> Rappel de l'énoncé : écrire `deps.New(d Deps)`, qui rend une erreur
> listant **tous** les problèmes de `d` ; dire ce qu'elle fait d'un pointeur
> nul typé ; choisir entre paramètres positionnels et `struct` vérifiée.

La solution est dans `ex2/deps` du module de correction, verte sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- **Une vérification par champ, dans un ordre fixe**, chacune ajoutée à
  une liste ; `errors.Join` à la fin. Le lecteur du message corrige tout
  d'un coup.
- **Un pointeur nul typé passe la vérification**, et le service panique au
  premier transfert. Le détecter demande la réflexion ; mieux vaut ne pas
  le créer, ce que fait une racine de composition qui construit tout
  d'un bloc.
- **Positionnels jusqu'à cinq ou six dépendances**, parce que le
  compilateur vérifie tout. Au-delà, la `struct` vérifiée ; et d'abord, la
  question de savoir si le service fait trop de choses.

## 1. La solution

```go
// New returns the service, or an error that lists every problem of d, not
// only the first. The checks run in a fixed order, so the message is the
// same for the same Deps.
func New(d Deps) (*transfer.Service, error) {
    var errs []error
    missing := func(name string, absent bool) {
        if absent {
            errs = append(errs, fmt.Errorf("%w: %s", ErrMissing, name))
        }
    }
    missing("operator", d.Operator == nil)
    missing("ledger", d.Ledger == nil)
    missing("notifier", d.Notifier == nil)
    missing("clock", d.Now == nil)
    if d.Limit <= 0 {
        errs = append(errs, fmt.Errorf("%w: limit %d, want more than 0", ErrInvalid, d.Limit))
    }
    if d.Fees.RateBP < 0 || d.Fees.RateBP > 10_000 {
        errs = append(errs, fmt.Errorf("%w: rate %d bp, want 0 to 10000", ErrInvalid, d.Fees.RateBP))
    }
    if d.Fees.Min < 0 {
        errs = append(errs, fmt.Errorf("%w: minimum %d, want 0 or more", ErrInvalid, d.Fees.Min))
    }
    if err := errors.Join(errs...); err != nil {
        return nil, fmt.Errorf("transfer service: %w", err)
    }
    return transfer.New(d.Operator, d.Ledger, d.Notifier, d.Fees, d.Limit, d.Now), nil
}
```

Quatre choix méritent un mot :

- **Les vérifications sont écrites dans l'ordre**, pas parcourues dans une
  `map` : l'ordre de parcours d'une `map` change d'une exécution à l'autre,
  et le message aussi. C'est ce que vérifie
  `TestTheErrorListsTheProblemsInAFixedOrder`, qui passait sur le squelette
  pour la mauvaise raison (deux fois le même `not implemented`).
- **`%w` sur la sentinelle**, puis le détail : `errors.Is(err, ErrMissing)`
  marche à travers `errors.Join`, qui garde toutes les erreurs.
- **Un taux de 0 est valide.** Une semaine de transferts gratuits est une
  vraie offre ; la refuser obligerait le métier à tricher avec
  `RateBP: 1`. La vérification interdit ce qui est **absurde** (un taux
  négatif, plus de 100 %), pas ce qui est inhabituel.
- **Pas de service rendu avec une erreur.** Un appelant qui ignore
  l'erreur doit recevoir `nil`, et paniquer tout de suite, plutôt qu'un
  service à moitié construit qui panique plus tard.

vide :

## 2. Le pointeur nul typé

`var l *fake.Ledger`, puis `Deps{Ledger: l}`. Ce que fait la solution
(`go run ./ex2/cmd/typednil`) :

```text
New: <nil>
first Send: runtime error: invalid memory address or nil pointer dereference
```

`New` accepte, et le premier `Send` panique. La raison : une interface
contient **un type et une valeur**. `Ledger: l` y range le type
`*fake.Ledger` et la valeur `nil`. L'interface n'est pas nulle, puisqu'elle
a un type ; `d.Ledger == nil` est faux.

Faut-il le détecter ? On peut, avec le paquet `reflect`
(`reflect.ValueOf(d.Ledger).IsNil()` pour les types pointeurs). Mais c'est
traiter un symptôme. Un pointeur nul typé arrive quand une variable est
**déclarée** quelque part et **remplie** ailleurs, ou jamais. Une racine
de composition qui construit chaque dépendance juste avant de la passer
(`ledger := core.New(...)`, puis `Deps{Ledger: ledger}`) ne le produit
pas. La bonne réponse est donc : ne pas écrire de vérification par
réflexion, et garder la construction en un seul endroit, lu de haut en
bas.

## 3. Positionnels, ou `struct` vérifiée ?

| | Paramètres positionnels | `struct` vérifiée par `New` |
|---|---|---|
| un oubli | erreur de **compilation** | erreur au **démarrage** |
| l'appel | long, ordre à respecter | lisible, champs nommés |
| ajouter une dépendance | chaque appel casse : on les voit tous | aucun appel ne casse : `New` doit la vérifier |
| deux dépendances du même type | inversables sans erreur | nommées, pas d'inversion |

Pour `transfer`, avec six dépendances de types tous différents, les
paramètres positionnels sont le meilleur choix : le compilateur fait tout
le travail, et l'inversion est impossible (on ne peut pas passer un
`Ledger` là où il attend un `Notifier`).

Le point de bascule n'est pas un nombre, c'est **la ressemblance des
paramètres**. Deux `int64` côte à côte (`limit`, `min`), deux `string`
(`url`, `secret`) s'inversent sans qu'aucun outil ne le voie ; des champs
nommés l'empêchent. Et au-delà de sept ou huit dépendances, la vraie
question est celle de la leçon 1.2 : ce service a-t-il une seule raison de
changer ?

## Ce qu'il faut retenir

1. Une `struct` de dépendances déplace la vérification du compilateur vers
   `New`. Elle doit alors tout vérifier, et tout dire d'un coup.
2. Un message d'erreur stable s'écrit dans un ordre fixe, jamais en
   parcourant une `map`.
3. Une interface qui contient un pointeur nul n'est pas nulle. On s'en
   protège par la façon de construire, pas par la réflexion.
4. Positionnels quand les types diffèrent ; champs nommés quand ils se
   ressemblent ; découpage quand ils sont trop nombreux.
