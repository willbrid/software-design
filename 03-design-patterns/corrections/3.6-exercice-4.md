# Correction 3.6 — Exercice 4 : deux pays, un processus

> Rappel de l'énoncé : le même serveur sert le Cameroun (Kola, 1 %,
> 500 000 FCFA par jour) et le Gabon (Baobab, 0,8 %, 1 000 000 FCFA).
> Combien d'instances, quelle configuration, quel vérificateur pour les
> réponses, comment changer un taux sans redémarrer, et ce que coûte un
> troisième pays.

La conception ci-dessous est vérifiée par les paquets `ex4/countries`,
`ex4/transfer2` et `ex4/usage` du module de correction, verts sous
`go vet ./...` et `go test -race -count=1 ./...`. Ce code est une
**vérification** de la conception, pas un serveur de production.

## En bref

- **Un service par pays**, construits par la même racine de composition,
  rangés dans une `map` indexée par le code du pays. Le pays vient de la
  requête du client, que l'application connaît déjà.
- **Un fichier par pays**, et un seul fichier faux suffit à refuser le
  démarrage de **tous** les pays.
- **Le vérificateur est choisi par le chemin** (`/callbacks/ga`), que la
  banque a donné à chaque opérateur. Jamais par le corps de la réponse :
  n'importe qui peut l'écrire.
- **Changer un taux sans redémarrer**, c'est reconstruire la version
  entière et l'échanger d'un coup. Mais les compteurs du plafond ne
  doivent pas être dans ce qu'on reconstruit : la mesure le montre, un
  client passe de 900 000 à 1 900 000 FCFA dans la journée.

## 1. Combien d'instances, et qui choisit

```text
                 main (racine de composition)
                   │
   construit une fois :  http.Client, grand livre, SMS, compteurs
                   │
   pour chaque fichier cm.conf, ga.conf :
       famille de l'opérateur ─► encodeur + vérificateur
       barème, plafond
       ─► un transfer2.Service par pays
                   │
              Bank { services[pays], verifiers[pays] }
                   │
              Live (la version en cours, échangeable)
```

Une instance de `transfer.Service` par pays : chacune a **son** opérateur,
**son** barème et **son** plafond. Ce qui est commun (le grand livre, la
passerelle SMS, le client HTTP) est construit une fois par `main` et
**passé** à chacune.

Qui choisit ? Le pays est une donnée de la requête : le client est
authentifié, son compte appartient à un pays. Le choix est une recherche
dans une `map` :

```go
func (l *Live) Send(ctx context.Context, country, key, account, wallet string, amount int64) (int64, error) {
    svc, ok := l.cur.Load().services[country]
    if !ok {
        return 0, fmt.Errorf("%w %q", ErrCountry, country)
    }
    return svc.Send(ctx, key, account, wallet, amount)
}
```

Ce qu'il ne faut **pas** faire : un `if country == "ga"` dans
`transfer.Service`. Le service ne doit pas savoir qu'il existe plusieurs
pays ; c'est la racine de composition qui le sait.

Un détail que les tests ont vérifié : le même numéro de compte peut
exister dans les deux pays. La clé du plafond contient donc le pays :

```go
func (s *Service) Send(ctx context.Context, key, account, wallet string, amount int64) (int64, error) {
    // The country is in the key: the same account number may exist in both.
    day := s.country + "/" + account + "/" + s.now().Format("2006-01-02")
    if before, ok := s.usage.Reserve(day, amount, s.limit); !ok {
        return 0, fmt.Errorf("%w: %d FCFA already sent today", transfer.ErrLimit, before)
    }
    fee := s.fees.Fee(amount)
    if err := s.ledger.Hold(ctx, account, amount+fee); err != nil {
        s.usage.Undo(day, amount)
        return 0, err
    }
    if err := s.op.Send(ctx, key, wallet, amount); err != nil {
        s.usage.Undo(day, amount)
        return 0, errors.Join(err,
            s.ledger.Release(ctx, account, amount+fee),
            s.notify.Refused(ctx, account, amount))
    }
    return fee, nil
}
```

## 2. Un fichier par pays, et tous ou rien

Un fichier par pays : `cm.conf`, `ga.conf`. Ajouter un pays, c'est
déposer un fichier ; le modifier ne touche pas aux autres ; la revue d'un
changement du Gabon ne montre que le Gabon.

Et si celui du Gabon est faux au démarrage ? Deux réponses possibles :
démarrer le Cameroun seul, ou refuser tout. La seconde est la bonne. Un
serveur à moitié démarré est vu « en bonne santé » par l'orchestrateur,
tandis que tous les clients gabonais reçoivent une erreur. Un démarrage
refusé arrête le déploiement, et l'ancienne version continue de servir les
deux pays.

```go
// Load reads one file per country: cm.conf, ga.conf. Every bad file is
// reported, and one bad file is enough to refuse them all.
func Load(dir string) (map[string]config.Config, error) {
    paths, err := filepath.Glob(filepath.Join(dir, "*.conf"))
    if err != nil {
        return nil, err
    }
    cfgs := map[string]config.Config{}
    var errs []error
    for _, p := range paths {
        c, err := config.Load(p)
        if err != nil {
            errs = append(errs, fmt.Errorf("%s: %w", filepath.Base(p), err))
            continue
        }
        cfgs[strings.TrimSuffix(filepath.Base(p), ".conf")] = c
    }
    if err := errors.Join(errs...); err != nil {
        return nil, err
    }
    if len(cfgs) == 0 {
        return nil, fmt.Errorf("no *.conf in %s", dir)
    }
    return cfgs, nil
}
```

```go
// One bad file refuses them all, and names the file and the line.
```

## 3. Le vérificateur des réponses

```go
// Callbacks returns the handler of the operators' answers. The verifier is
// chosen by the country in the path, which the bank gave each operator, and
// never by the body, which anybody can write.
func (l *Live) Callbacks() http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("POST /callbacks/{country}", func(w http.ResponseWriter, r *http.Request) {
        ver, ok := l.cur.Load().verifiers[r.PathValue("country")]
        if !ok {
            http.NotFound(w, r)
            return
        }
        body, err := io.ReadAll(io.LimitReader(r.Body, 1<<20))
        if err != nil {
            http.Error(w, "read", http.StatusBadRequest)
            return
        }
        if ver.Verify(body, r.Header.Get("X-Signature")) != nil {
            http.Error(w, "signature", http.StatusUnauthorized)
            return
        }
        w.WriteHeader(http.StatusNoContent) // the status machine of lesson 3.5 takes over here
    })
    return mux
}
```

La banque donne à chaque opérateur **son** adresse de rappel :
`/callbacks/cm` à Kola, `/callbacks/ga` à Baobab. Le chemin dit donc qui
est censé avoir signé, et la signature vérifie qu'il l'a fait.

Pourquoi pas un champ `country=ga` du corps ? Parce que le corps n'est
pas encore vérifié quand on le lit pour choisir le vérificateur.
Quiconque détient le secret d'**un** opérateur (une fuite chez Baobab, ou
un employé de Baobab) écrirait `country=ga` dans un corps signé avec ce
secret, y mettrait la référence d'un paiement **camerounais**, et le
ferait confirmer : la vérification passerait, avec l'algorithme et le
secret qu'il a lui-même choisis. La règle générale : **rien de ce
qui n'est pas encore vérifié ne choisit la façon de le vérifier.** Le
test le joue, avec un corps qui dit `country=ga` envoyé sur le chemin du
Cameroun :

```go
// The verifier is chosen by the path. A Baobab answer posted on the
// Cameroon path is rejected, whatever its body says.
func TestACallbackIsVerifiedByThePathsCountry(t *testing.T) {
    t.Parallel()
    h := live(t, shared(t)).Callbacks()
    body := []byte("country=ga&status=paid&reference=CM-1")
    for _, c := range []struct {
        path, sig string
        want      int
    }{
        {"/callbacks/cm", kola.Sign("cm-secret", body), http.StatusNoContent},
        {"/callbacks/ga", baobab.Sign("ga-secret", body), http.StatusNoContent},
        {"/callbacks/cm", baobab.Sign("ga-secret", body), http.StatusUnauthorized},
        {"/callbacks/ga", kola.Sign("cm-secret", body), http.StatusUnauthorized},
        {"/callbacks/cm", kola.Sign("ga-secret", body), http.StatusUnauthorized},
        {"/callbacks/sn", kola.Sign("cm-secret", body), http.StatusNotFound},
    } {
        if got := post(h, c.path, body, c.sig); got != c.want {
            t.Errorf("%s with %.8s…: %d, want %d", c.path, c.sig, got, c.want)
        }
    }
}
```

## 4. Changer le taux sans redémarrer

Le mécanisme : à la réception d'un signal (ou d'un appel d'administration),
relire **tous** les fichiers, tout reconstruire avec la même fonction qu'au
démarrage, et, seulement si tout a réussi, échanger la version en cours
d'un coup :

```go
// Live is the current Bank. A reload swaps it whole: a request that started
// on the old one finishes on it.
type Live struct{ cur atomic.Pointer[Bank] }
```

```go
func (l *Live) Reload(b *Bank) { l.cur.Store(b) }
```

`atomic.Pointer` garantit qu'une requête voit l'ancienne version **ou** la
nouvelle, jamais un mélange (le taux du nouveau barème avec le plafond de
l'ancien). Une requête commencée sur l'ancienne version y finit. Un
fichier faux au rechargement laisse la version en cours intacte : on
journalise l'erreur, on ne remplace rien.

Ce n'est **pas** un singleton modifiable : personne ne change un réglage
dans l'objet partagé. On construit un nouvel objet complet, et l'on
remplace la référence.

### Le piège du plafond

Le service de la leçon garde ses compteurs du jour **dans** l'instance.
Reconstruire l'instance les remet à zéro. La mesure, au Gabon, avec un
client qui a envoyé 900 000 FCFA avant la promotion de 8 h
(`go run ./ex4/cmd/reload`) :

```text
counts inside the service: 900000, reload, 1000000 more: fee 4000, <nil>
counter shared across rebuilds: 900000, reload, 1000000 more: fee 0, daily limit reached: 900000 FCFA already sent today
```

Avec les compteurs dans le service, le rechargement autorise 1 000 000 FCFA
de plus : **1 900 000 FCFA** le même jour, presque deux fois le plafond.
Chaque rechargement est une remise à zéro, pour tous les clients.

La correction : ce qui doit **survivre** à une reconstruction n'est pas
dans ce qu'on reconstruit. Les compteurs deviennent une dépendance,
construite une fois par `main`, comme le grand livre :

```go
// Reserve adds amount to key if the total stays within limit. It returns
// what was sent before, and whether the amount was added.
func (c *Counter) Reserve(key string, amount, limit int64) (int64, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()
    before := c.sent[key]
    if before+amount > limit {
        return before, false
    }
    c.sent[key] = before + amount
    return before, true
}
```

C'est la règle qui sépare ce qu'une racine de composition construit :

| Construit **une fois** par `main` | Reconstruit à chaque version |
|---|---|
| le client HTTP, le grand livre, la passerelle SMS | les familles d'opérateurs (le secret peut changer) |
| les compteurs du plafond | les barèmes et les plafonds |
| | les services par pays |

En production, les compteurs seraient d'ailleurs dans une base partagée :
avec deux instances du serveur derrière un répartiteur, une `map` en
mémoire laisserait chaque client envoyer deux plafonds par jour. Le
paquet `usage` le cache derrière une interface, et cette question
appartient au niveau 5.

```go
// A reload changes the rate, and keeps what each customer sent today.
func TestAReloadChangesTheRateAndKeepsTheDailyUsage(t *testing.T) {
    t.Parallel()
    sh := shared(t)
    l := live(t, sh)
    ctx := t.Context()
    if _, err := l.Send(ctx, "ga", "k1", "ACC-1", "24106000000", 900_000); err != nil {
        t.Fatal(err)
    }
    b, err := countries.LoadAndBuild("testdata/promo", sh)
    if err != nil {
        t.Fatal(err)
    }
    l.Reload(b)
    if fee, err := l.Send(ctx, "ga", "k2", "ACC-1", "24106000000", 100_000); err != nil || fee != 400 {
        t.Errorf("after the promotion: %d, %v; want 400", fee, err)
    }
    if _, err := l.Send(ctx, "ga", "k3", "ACC-1", "24106000000", 1); !errors.Is(err, transfer.ErrLimit) {
        t.Fatalf("1 000 000 already sent before and after the reload, then 1 more: %v", err)
    }
}
```

## 5. Un troisième pays

Ce qui change :

- **un fichier** `sn.conf` ;
- **une famille** d'opérateur, si l'opérateur est nouveau : un paquet avec
  sa fonction `New`, et une ligne dans `wiring.Families` ;
- **une adresse** de rappel donnée à l'opérateur.

Ce qui ne change pas : `transfer2`, `usage`, `countries`, et tous leurs
tests. C'est le critère d'une bonne racine de composition : ajouter une
variante, c'est **ajouter**, pas modifier.

Trois trous, tous du même genre : **ce qui ne devrait jamais arriver
n'était pas testé.**

- **« aucun pays accepté »** : un répertoire vide démarrait un serveur sans
  pays, qui refuse toutes les requêtes en paraissant sain. C'est l'erreur
  de déploiement typique : un volume mal monté.
- **« opérateur inconnu sauté »** : `baobabpay` au lieu de `baobab`
  démarrait le Cameroun seul, contre la règle du « tous ou rien ».
- **« un refus compte dans le plafond »** : aucun test ne faisait refuser
  un transfert par l'opérateur.

## Ce que cette vérification ne couvre pas

- **Le signal de rechargement** lui-même (`SIGHUP`, ou un point d'entrée
  d'administration protégé) : il appelle `LoadAndBuild` puis `Reload`, et
  journalise l'erreur s'il y en a une.
- **Les compteurs partagés entre plusieurs instances du serveur** : une
  base, avec une écriture conditionnelle comme à la leçon 3.5.
- **La devise.** Le Cameroun et le Gabon partagent le franc CFA de
  l'Afrique centrale ; un pays d'une autre zone monétaire demanderait un
  type `Money` avec sa devise, et le niveau 5.

## Ce qu'il faut retenir

1. Plusieurs variantes dans un processus, c'est **plusieurs instances**,
   construites par la même racine et rangées dans une `map`. Le service ne
   sait pas qu'il a des frères.
2. Une configuration se valide **en entier** : un fichier faux refuse le
   démarrage de tous.
3. Rien de ce qui n'est pas encore vérifié ne choisit la façon de le
   vérifier.
4. Pour changer des réglages à chaud, reconstruis une version complète et
   échange-la d'un coup. Ce qui doit survivre au changement (les
   compteurs, les connexions) est construit une fois, à part.
