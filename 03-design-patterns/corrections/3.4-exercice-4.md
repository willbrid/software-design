# Correction 3.4 — Exercice 4 : une politique par abonné

> Rappel de l'énoncé : cinq abonnés de `TransferCompleted` à régler
> (synchrone ou non, politique, taille, perte au plantage, métrique) ; dire
> lesquels n'ont rien à faire dans un bus en mémoire ; ajouter une politique
> par abonné sans casser `Subscribe` ; garder l'ordre par compte avec quatre
> goroutines.

Le code de vérification est dans `ex4/` du module de correction, vert sous
`go vet ./...` et `go test -race -count=1 ./...`.

## En bref

- Deux abonnés sur cinq, le webhook marchand et l'audit, ne doivent **pas**
  passer par un bus en mémoire : leur perte au plantage n'est pas
  acceptable.
- Une **nouvelle méthode** `SubscribeWith(h, Options)` donne des réglages
  par abonné. `Subscribe` devient un appel de `SubscribeWith` avec les
  réglages du bus : aucun appel existant ne change, et les tests du bus
  passent sans modification.
- Quatre goroutines sur **une** file perdent l'ordre (571 inversions sur
  2 000 événements, les 50 comptes touchés). Répartir par compte, avec
  `ByKey`, le garde (0 inversion), aussi vite.

## 1. Réglage de chaque abonné

La taille d'une file se choisit avec une règle simple : **la durée de
dégradation qu'on veut absorber, multipliée par le débit**. À 400 virements
par seconde, une file de 4 000 absorbe 10 secondes d'un abonné arrêté ; au
delà, la politique décide.

| Abonné | Forme | Politique | Taille | Perte au plantage | Métrique |
|---|---|---|---|---|---|
| SMS « virement reçu » | asynchrone | **`Drop`** : un SMS en retard de 2 minutes ne sert plus à rien | quelques secondes de trafic | quelques SMS : acceptable, compté | `Dropped` par seconde, longueur de file |
| webhook marchand | **pas un bus en mémoire** | — | — | **inacceptable** : le marchand ne livre pas | — |
| score anti-fraude | asynchrone, **une** goroutine par compte (question 4) | **`Block`**, avec un délai court sur le `ctx` du publieur | petite : il traite 500 événements par seconde | un score en retard, rattrapable en relisant le grand livre | longueur de file, retard du dernier événement traité |
| statistiques | synchrone : 5 µs ne coûtent rien | sans objet | sans objet | une valeur approximative | aucune |
| audit réglementaire | **pas un bus en mémoire** | — | — | **inacceptable** : un trou dans l'audit | — |

Deux choix méritent d'être discutés :

- **Le score anti-fraude en `Block`.** S'il saute des virements, le score
  est faux, et c'est lui qui décide si **les virements suivants** passent.
  On préfère ralentir un peu l'émetteur à ce moment-là. Le délai sur le
  `ctx` borne ce ralentissement : au-delà, le virement réussit quand même, et
  l'événement manqué est une alerte.
- **Les statistiques en synchrone.** Un abonné asynchrone coûte une file,
  une goroutine et une métrique. Pour 5 µs, le synchrone suffit : c'est la
  règle de la leçon, « commence synchrone ».

## 2. Ceux qui n'ont rien à faire dans un bus en mémoire

Le webhook marchand et l'audit. La question de la section 10 de la leçon
tranche : si le processus meurt entre le virement et la réaction, est-ce
grave ? Pour eux, oui. Les régler en `Block` avec une grande file n'y
change rien : une file en mémoire meurt avec le processus, quelle que soit
sa taille. Il leur faut l'événement **écrit en base avec le virement**,
puis délivré depuis la base, avec reprise : l'outbox du niveau 8.

## 3. Une politique par abonné, sans rien casser

```text
// Options are the settings of one subscriber.
type Options struct {
    Size   int // queue length
    Policy Policy
}

// SubscribeWith is Subscribe with settings of its own for this subscriber.
func (b *Async[E]) SubscribeWith(h Handler[E], o Options) (unsubscribe func(), err error)
```

Le changement complet dans `async.go` : la file retient **sa** politique,
`Subscribe` délègue, et `Publish` lit `q.policy` au lieu de `b.Policy`.

```go
// Subscribe starts the goroutine of h and returns the function that stops
// it. The goroutine handles what is already queued before it ends. The
// subscriber gets the Size and Policy of the bus.
func (b *Async[E]) Subscribe(h Handler[E]) (unsubscribe func(), err error) {
    return b.SubscribeWith(h, Options{Size: b.Size, Policy: b.Policy})
}
```

```go
// SubscribeWith is Subscribe with settings of its own for this subscriber.
func (b *Async[E]) SubscribeWith(h Handler[E], o Options) (unsubscribe func(), err error) {
    b.mu.Lock()
    defer b.mu.Unlock()
    if b.closed {
        return nil, ErrClosed
    }
    q := &queue[E]{ch: make(chan envelope[E], o.Size), policy: o.Policy}
    b.subs = append(b.subs, q)
    b.wg.Go(func() { b.run(q, h) })
    return func() { b.remove(q) }, nil
}
```

Pourquoi une nouvelle méthode, et pas un paramètre de plus ? Ajouter
`opts ...Options` à `Subscribe` compilerait chez les appelants, mais
changerait le **type** de la méthode : une interface du code appelant qui
déclare `Subscribe(h Handler[E]) (func(), error)` ne serait plus
satisfaite. Une méthode de plus ne retire rien. Les champs `Size` et
`Policy` du bus gardent leur sens : ce sont les réglages par défaut.

La vérification : les tests du bus de la leçon, recopiés **sans
changement**, passent ; un test de plus fixe le nouveau contrat.

```go
func TestEachSubscriberKeepsItsOwnPolicy(t *testing.T) {
    b := &bus.Async[int]{Size: 1, Policy: bus.Block}
    started, gate := make(chan int, 10), make(chan struct{})
    _, _ = b.SubscribeWith(blocker(started, gate), bus.Options{Size: 2, Policy: bus.Drop})
    var c collector
    _, _ = b.Subscribe(c.handle) // the bus default: Block, 1
    _ = b.Publish(ctx, 1)
    <-started
    for i := 2; i <= 5; i++ {
        _ = b.Publish(ctx, i)
    }
    close(gate)
    b.Close()
    if b.Dropped() != 2 || len(c.get()) != 5 {
        t.Fatalf("dropped %d, the Block subscriber saw %d; want 2 and 5", b.Dropped(), len(c.get()))
    }
}
```

## 4. L'ordre par compte, avec quatre goroutines

Le programme `ex4/cmd/order` publie 2 000 mouvements sur 50 comptes, par
rafales de cinq mouvements du même compte (une entreprise qui paie
plusieurs salaires d'affilée). Le score met jusqu'à 300 µs par mouvement.

```text
1 goroutine                out of order for their account:    0, accounts hit:  0/50, took 2.04s
4 goroutines, one queue    out of order for their account:  571, accounts hit: 50/50, took 370ms
4 goroutines, ByKey        out of order for their account:    0, accounts hit:  0/50, took 370ms
```

- **Une goroutine** : l'ordre est garanti, mais c'est cinq fois plus lent.
- **Quatre goroutines sur une file** : quatre fois plus de débit, mais 571
  mouvements traités avant un mouvement **plus ancien du même compte**, et
  les 50 comptes touchés. Pour un score qui suit un solde ou une vitesse de
  dépense, c'est un score faux.
- **`ByKey`** : chaque compte a **sa** goroutine, toujours la même, choisie
  par un hachage de son identifiant. Les mouvements d'un compte passent un
  par un, dans l'ordre ; ceux de comptes différents passent en parallèle.

```go
// ByKey turns h into n handlers. Each one handles only the events whose key
// falls on it: events with the same key are handled by the same handler, so
// one at a time and in order; events with different keys may be handled in
// parallel. Subscribe each of them once.
//
// Every handler still receives every event and skips the others: each queue
// carries n times the events it handles.
func ByKey[E any](n int, key func(E) string, h Handler[E]) []Handler[E] {
    hs := make([]Handler[E], n)
    for i := range n {
        hs[i] = func(ctx context.Context, e E) error {
            if shard(key(e), n) != i {
                return nil
            }
            return h(ctx, e)
        }
    }
    return hs
}
```

`ByKey` ne touche pas au bus : il fabrique quatre handlers, et chacun ignore
les comptes qui ne sont pas les siens. Le prix est écrit dans sa
documentation : chaque file transporte **tous** les événements. Ici, c'est
gratuit (370 ms dans les deux cas). Pour un débit beaucoup plus fort, il
faudrait que le bus lui-même **route** chaque événement vers une seule file,
ce qui change son API.

C'est la même idée que les **partitions** d'un journal de messages
(niveau 8) : l'ordre est garanti à l'intérieur d'une clé, jamais entre les
clés.

### La campagne

```text
politique du bus pour tous                   tuee
taille du bus pour tous                      tuee
Subscribe sans réglages du bus               tuee
une seule goroutine travaille                SURVIT
filtre inversé                               tuee
sans filtre                                  tuee
```

« Une seule goroutine travaille » (`shard` qui rend toujours 0) **survit** au
premier passage : tous les comptes vont au même handler, l'ordre est gardé,
le total est juste. Le code est correct, mais il n'y a plus de
parallélisme, et le test d'ordre ne peut pas le voir. Il faut un test qui
vérifie la **répartition** :

```go
// Each key goes to exactly one handler, and the keys are spread: with ten
// keys and four handlers, more than one handler has work.
func TestByKeySpreadsTheKeys(t *testing.T) {
    var ran int
    hs := bus.ByKey(4, func(m move) string { return m.account }, func(context.Context, move) error { ran++; return nil })
    used := map[int]bool{}
    for k := range 10 {
        for i, h := range hs {
            before := ran
            _ = h(ctx, move{account: fmt.Sprint("acc-", k)})
            if ran > before {
                used[i] = true
            }
        }
        if ran != k+1 {
            t.Fatalf("key %d was handled %d times, want once", k, ran-k)
        }
    }
    if len(used) < 2 {
        t.Fatalf("handlers used: %d of 4", len(used))
    }
}
```

Rejouée avec lui :

```text
politique du bus pour tous                   tuee
taille du bus pour tous                      tuee
Subscribe sans réglages du bus               tuee
une seule goroutine travaille                tuee
filtre inversé                               tuee
sans filtre                                  tuee
6/6 tuees
```

## Ce qu'il faut retenir

1. La taille d'une file, c'est une durée de panne qu'on accepte d'absorber,
   multipliée par le débit. La politique dit ce qui se passe au-delà.
2. `Block` quand sauter un événement rend la suite fausse ; `Drop` quand un
   événement en retard ne sert plus à rien. Dans les deux cas, on mesure.
3. On étend une API par une **nouvelle méthode**, pas en changeant la
   signature d'une méthode existante.
4. Plus de goroutines, c'est moins d'ordre. Pour garder l'ordre par clé, on
   donne à chaque clé une seule goroutine.
