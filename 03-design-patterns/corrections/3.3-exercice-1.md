# Correction 3.3 — Exercice 1 : prévoir avant d'exécuter

> Rappel de l'énoncé : cinq chaînes de décorateurs à prévoir, deux compteurs
> d'octets sous `io.Copy`, sept éléments de la bibliothèque standard à ranger,
> et la matrice de diffusion de la leçon.

Chaque prévision est vérifiée en exécutant le code : les sorties citées
viennent de programmes du module de correction, et des tests les
verrouillent. Le module est vert sous `go vet ./...` et
`go test -race -count=1 ./...`.

## En bref

- **1.a** — L'ordre décide de tout : le journal à l'extérieur écrit une ligne
  par paiement, à l'intérieur une par tentative ; un délai sous les reprises
  laisse la deuxième tentative réussir ; sans `translate`, la reprise ne voit
  qu'un abandon et s'arrête.
- **1.b** — `count.File` ne compte **rien** : en embarquant `*os.File`, il
  hérite aussi de `ReadFrom`, et `io.Copy` passe par là, sans jamais appeler
  son `Write`.
- **1.c** — Cinq décorateurs (dont deux qui protègent, à la frontière du
  proxy), un adaptateur net, et un proxy au sens réseau.
- **1.d** — Une assertion de type ne suit pas `Unwrap`. Ajouter `Flush` au
  `recorder` fait passer l'assertion, mais l'emballage **ment** quand ce qu'il
  emballe ne sait pas vider son tampon.

## 1.a — Cinq chaînes

La sortie du programme `ex1/cmd/predict` :

```text
A  calls=3  log lines=1  err=payment: unavailable
B  calls=3  log lines=3  err=payment: unavailable
C  calls=2  log lines=0  err=<nil>
D  calls=1  log lines=0  err=payment: declined
E  calls=1  log lines=0  err=context deadline exceeded
```

**A et B : le même prestataire, le même nombre d'appels, pas le même
journal.** Trois pannes, deux reprises : trois appels dans les deux cas, et
l'erreur `payment: unavailable` remonte. Dans **A**, `Logging` est à
l'extérieur : il voit **un** appel, celui de l'appelant, qui a duré le temps
des trois tentatives — une ligne. Dans **B**, `Logging` est sous les
reprises : chaque tentative passe par lui — trois lignes.

**C : la reprise réussit.** Le délai est **sous** les reprises : chaque
tentative a ses 50 ms. La première ne répond jamais, son délai expire,
`translate` en fait une `payment.ErrUnavailable`, et `Retrying` réessaie. La
deuxième réussit : deux appels, pas d'erreur.

**D : un refus ne se réessaie pas.** `Retries: 5` ne change rien :
`Retrying` ne réessaie que `payment.ErrUnavailable`. Un appel.

**E : sans `translate`, la reprise abandonne.** Le délai expire de la même
façon, mais l'erreur reste `context.DeadlineExceeded`. Pour `Retrying`, ce
n'est pas une panne passagère : il rend l'erreur telle quelle après un seul
appel. C'est exactement pour cela que `translate` existe — et pour cela
qu'il ne traduit **que** notre délai : celui de l'appelant doit rester un
abandon.

Les cinq réponses sont verrouillées par un test :

```go
// TestPredictions locks the answers to question 1.a.

```

## 1.b — Deux compteurs

La sortie du programme `ex1/cmd/copy` :

```text
1. count.Writer, file -> file:          copied 1000, N = 1000
2. count.File,   file -> file:          copied 1000, N = 0
3. count.File,   strings.Reader -> file: copied  500, N = 0
4. count.File hidden behind struct{ io.Writer }: copied  500, N = 500
```

Les lignes 1 à 3 répondent à l'énoncé ; la ligne 4 est la réparation.

**Ligne 1 : `count.Writer` compte juste.** Il embarque l'**interface**
`io.Writer` : seule la méthode `Write` est promue, et c'est la sienne qui
la remplace. Il n'a rien d'autre que `io.Copy` puisse utiliser à sa place.

**Lignes 2 et 3 : `count.File` compte zéro, alors que les octets sont bien
écrits.** Il embarque le type **concret** `*os.File`, et un `*os.File` a bien
plus que `Write` : `ReadFrom`, `WriteString`, `WriteTo` et d'autres, tous
promus avec le reste. La
[documentation d'`io.Copy`](https://pkg.go.dev/io#Copy) dit l'ordre des
questions qu'il pose :

> If src implements WriterTo, the copy is implemented by calling
> src.WriteTo(dst). Otherwise, if dst implements ReaderFrom, the copy is
> implemented by calling dst.ReadFrom(src).

Le chemin exact, lu dans les sources de `os` (`os/file.go`) :

1. ligne 2, la source est un `*os.File`, qui a `WriteTo`. `io.Copy` l'appelle.
   Faute de raccourci noyau vers une destination qui n'est pas un fichier,
   `WriteTo` se replie sur `io.Copy(w, fileWithoutWriteTo{File: f})` ;
2. ce second `io.Copy` demande à la destination si elle a `ReadFrom`. Elle
   l'a, **promu** depuis le `*os.File` embarqué ;
3. ce `ReadFrom` a pour receveur le `*os.File` **intérieur**. Il écrit dans
   le fichier sans jamais passer par `count.File.Write`.

Ligne 3, la source est un `strings.Reader`, et le contournement passe par
**une autre** méthode promue. `strings.Reader` a `WriteTo`, donc `io.Copy`
l'appelle ; ce `WriteTo` écrit avec `io.WriteString(w, s)`, et
`io.WriteString` commence par demander si la destination a `WriteString`.
`*os.File` en a un, promu sur `count.File`, qui écrit directement dans le
fichier. Deux chemins différents, le même résultat : **une méthode promue
que tu n'as pas écrite court-circuite celle que tu as écrite**, et tu ne
choisis pas laquelle.

La bibliothèque standard connaît le piège et se protège elle-même : `os`
déclare des types `noReadFrom` et `noWriteTo` dont le seul rôle, dit leur
commentaire, est d'être embarqués « to hide the ReadFrom method of that
other type ». Ligne 4, on fait pareil depuis l'extérieur : `struct{
io.Writer }{f}` ne laisse voir que `Write`, et le compte redevient juste.

La leçon 3.3 mesurait une méthode **future** qui passe sans le comportement.
Ici, c'est une méthode **présente**, que personne n'a remarquée.

## 1.c — Ranger la bibliothèque standard

| | Forme | Pourquoi |
|---|---|---|
| `io.LimitReader(r, n)` | **décorateur** | prend un `io.Reader`, rend un `io.Reader` qui s'arrête après `n` octets |
| `http.HandlerFunc(f)` | **adaptateur** | fait entrer une fonction dans l'interface `http.Handler` ; sa documentation dit « an adapter » |
| `http.StripPrefix("/api", h)` | **décorateur** | même interface, et il **modifie la requête** avant de la passer ; il répond 404 si le préfixe manque |
| `http.TimeoutHandler(h, d, msg)` | **décorateur** | même interface ; il borne la durée et répond 503 au-delà |
| `io.NopCloser(r)` | **adaptateur** | change d'interface : un `io.Reader` devient un `io.ReadCloser` |
| `http.MaxBytesHandler(h, n)` | décorateur, **discutable** | même interface ; il emballe le corps avec un `MaxBytesReader`, ce qui en fait un contrôle d'accès à la ressource — un proxy de protection, si on regarde l'intention |
| `httputil.NewSingleHostReverseProxy(u)` | **proxy**, au sens du livre | il se tient à la place d'un serveur distant ; ce n'est pas un emballage d'un `http.Handler` local mais un représentant d'un objet distant |

La documentation d'`io.NopCloser` contient une phrase qui annonce la question
suivante : « If r implements WriterTo, the returned ReadCloser will implement
WriterTo by forwarding calls to r ». L'emballage le plus simple de la
bibliothèque standard doit déjà s'occuper des **interfaces facultatives** de
ce qu'il emballe.

## 1.d — La matrice de la section 7

**Pourquoi `EventsAssert` derrière `AccessLog` répond 500.** `Unwrap` n'est
qu'une méthode ordinaire. `http.NewResponseController` la **cherche et la
suit** ; une assertion de type `w.(http.Flusher)` ne fait rien de tel : elle
demande si **ce** type a `Flush`, et `recorder` ne l'a pas.

**Ce qu'il faudrait ajouter.** Une méthode `Flush` qui transmet :

```go
// Flush forwards to the wrapped ResponseWriter if it can flush. It has no
// way to say that it could not.
func (r *Recorder) Flush() {
    _ = http.NewResponseController(r.ResponseWriter).Flush()
}
```

Elle fait passer l'assertion. Mais deux tests montrent son prix :

```go
// plain hides every method but the three of http.ResponseWriter.
type plain struct{ http.ResponseWriter }

func TestFlushLiesOverAWriterThatCannotFlush(t *testing.T) {
    inner := plain{httptest.NewRecorder()}
    rec := &Recorder{ResponseWriter: inner}

    _, claims := any(rec).(http.Flusher)
    err := http.NewResponseController(inner).Flush()
    t.Logf("Recorder claims http.Flusher: %v; the writer it wraps: %v", claims, err)
    if !claims || !errors.Is(err, http.ErrNotSupported) {
        t.Fatalf("claims=%v err=%v", claims, err)
    }
    any(rec).(http.Flusher).Flush() // returns nothing: the handler believes it streamed
}
```

```text
--- PASS: TestFlushMakesTheAssertionPass (0.00s)
    flushrec_test.go:36: Recorder claims http.Flusher: true; the writer it wraps: feature not supported
--- PASS: TestFlushLiesOverAWriterThatCannotFlush (0.00s)
ok      example/corrections33/ex1/flushrec    1.019s
```

**Pourquoi il ne faut pas le généraliser.**

1. **L'emballage ment.** Il se dit `http.Flusher` quel que soit ce qu'il
   emballe. Au-dessus d'un écrivain qui ne sait pas vider son tampon, le
   handler croit diffuser, et rien ne part avant la fin. `Flush()` ne rend
   pas d'erreur : il n'a aucun moyen de le dire.
2. **La liste n'a pas de fin.** `Flusher` n'est qu'une des interfaces
   facultatives d'un `ResponseWriter` : il y a aussi `http.Hijacker` (pour
   les WebSockets), `io.ReaderFrom`, et chaque bibliothèque peut en ajouter.
   Pour être honnête, un emballage devrait exposer **exactement** celles de
   ce qu'il emballe — une combinaison de types par sous-ensemble possible.
3. **La bibliothèque standard a choisi l'autre voie** : `Unwrap` d'un côté,
   `http.ResponseController` de l'autre, qui rend une erreur `ErrNotSupported`
   au lieu de mentir. Le handler qui veut diffuser l'utilise ; c'est lui qu'il
   faut changer, pas l'emballage.

## La campagne

Neuf mutations, sur les décorateurs, les compteurs et `flushrec`, chacune
appliquée seule. Premier passage :

```text
reprises : une de trop                       tuee
journal : Charge sans ligne                  tuee
delai : ne traduit plus                      tuee
chaine : ordre inverse                       tuee
reprises : reprend un refus                  tuee
compteur : Writer embarque *os.File          NE COMPILE PAS
compteur : compte la moitie                  tuee
flushrec : Flush ne transmet plus            SURVIT
flushrec : plus de Flush                     NE COMPILE PAS
6/9 tuees
```

- **« compteur : Writer embarque `*os.File` »** ne compile pas : les tests
  construisent `count.Writer{Writer: out}`. La même intention se rejoue de
  l'autre côté — donner à `count.File` un `ReadFrom` qui passe par `Write`,
  ce qui **répare** le compteur ; si le test qui verrouille « compte zéro »
  ne rougit pas, il ne verrouille rien.
- **« flushrec : plus de `Flush` »** ne compile pas : un test appelait
  `rec.Flush()` directement. Il l'appelle désormais à travers l'interface,
  `any(rec).(http.Flusher).Flush()`, comme le ferait un handler.
- **« flushrec : `Flush` ne transmet plus »** survivait. Diagnostic :
  **réclame un test**. Les tests vérifiaient que l'emballage **se dit**
  `Flusher`, jamais qu'il **transmet**. `TestFlushForwardsToAWriterThatCanFlush`
  emballe un `httptest.ResponseRecorder` et vérifie son champ `Flushed`.

Deuxième passage :

```text
reprises : une de trop                       tuee
journal : Charge sans ligne                  tuee
delai : ne traduit plus                      tuee
chaine : ordre inverse                       tuee
reprises : reprend un refus                  tuee
compteur : File ne contourne plus Write      tuee

9/9 tuees
```

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Pour prévoir une chaîne, lis-la de l'extérieur vers l'intérieur : chaque couche voit ce que les couches au-dessous lui rendent, et seulement ça. |
| ⚫ | Un délai sous les reprises borne chaque tentative ; sans traduction en panne passagère, la reprise ne le voit que comme un abandon. |
| ⚫ | Embarquer un type **concret** promeut **toutes** ses méthodes, y compris celles qui court-circuitent la tienne : `count.File` ne compte rien sous `io.Copy`, par `ReadFrom` ou par `WriteString` selon la source. |
| ⚫ | `struct{ io.Writer }{x}` cache tout sauf `Write` : la bibliothèque standard utilise le même geste (`noReadFrom`, `noWriteTo`). |
| ⚫ | Une assertion de type ne suit pas `Unwrap` ; `http.ResponseController` le fait, et rend une erreur au lieu de mentir. |
| ⚫ | Un test qui vérifie qu'un emballage **se dit** capable ne vérifie pas qu'il **transmet**. |
