# Leçon 3.3 — Ajouter un comportement autour d'un autre : décorateur, middleware, adaptateur, proxy

## L'essentiel en deux minutes

**Le problème, en une phrase.** On veut ajouter un comportement — journaliser,
limiter le temps, réessayer, compter, interdire — **autour** d'un code qui
marche, sans le réécrire et sans le mélanger avec lui.

**L'image.** Entre la prise murale et ton ordinateur, tu peux brancher trois
objets différents :

- un **parafoudre** : même prise à l'entrée, même prise à la sortie, et il
  ajoute une protection. C'est un **décorateur** ;
- un **adaptateur de voyage** : il change la forme de la prise pour que ton
  appareil rentre dans un mur étranger. C'est un **adaptateur** ;
- une **minuterie** : même prise des deux côtés, mais elle décide **si** le
  courant passe. C'est un **proxy**.

Les trois se branchent *entre* les deux, et aucun n'oblige à ouvrir
l'ordinateur.

**Le code, en treize lignes.**

```go
// Logging writes one line per call, then returns what Next returned.
type Logging struct {
    Next payment.Gateway
    Log  *slog.Logger
}

// Charge logs the charge and its outcome.
func (l Logging) Charge(ctx context.Context, c payment.Charge) (payment.Receipt, error) {
    start := time.Now()
    r, err := l.Next.Charge(ctx, c)
    l.Log.Info("charge", "id", c.ID, "amount", c.Amount, "err", err, "took", time.Since(start))
    return r, err
}
```

`Logging` **est** une passerelle de paiement (elle a les mêmes méthodes) et
**contient** une passerelle (`Next`). Elle fait son travail, puis passe la
main. On les empile comme des poupées russes :

```text
deco.Chain(provider, deco.WithLogging(log), deco.WithRetries(2, wait), deco.WithTimeout(2*time.Second))
```

**Les règles à retenir.**

1. Un décorateur a **la même interface** que ce qu'il emballe : l'appelant ne
   voit pas la différence. Une préoccupation par décorateur.
2. **L'ordre compte** : un délai à l'intérieur des reprises limite chaque
   tentative ; à l'extérieur, il limite le tout. Ce n'est pas un détail,
   c'est un comportement à tester.
3. N'**embarque** pas l'interface dans un décorateur pour économiser des
   lignes : le jour où l'interface gagne une méthode, elle passera **sans**
   ton comportement, et le compilateur ne dira rien.
4. Un adaptateur **traduit** : les noms, les types, les erreurs. C'est le
   seul endroit qui connaît le vocabulaire de l'autre.
5. Décorateur et proxy ont la même forme. Le proxy contrôle **l'accès** ; ce
   qui compte, c'est que ses tests vérifient ce qu'il interdit.

La suite mesure tout cela sur un vrai module.

---

La leçon 3.2 a construit un client valide. Celle-ci s'occupe de ce qu'on
veut **autour** de lui. Le problème qui revient :

> **Un composant marche. On veut lui ajouter un comportement qui n'est pas
> son métier** — une ligne de journal par appel, un délai, des reprises, un
> compteur, une interdiction — **sans le réécrire, et sans que chaque ajout
> rende le suivant plus difficile.**

La banque parle à un prestataire de paiement à travers une interface :

```go
// Gateway is a payment provider seen from the bank.
type Gateway interface {
    // Charge takes the money. It is safe to repeat with the same Charge.ID.
    Charge(ctx context.Context, c Charge) (Receipt, error)
    // Status tells what became of a charge: "captured", "pending" or
    // "unknown".
    Status(ctx context.Context, chargeID string) (string, error)
}
```

```go
var (
    // ErrDeclined means the provider refused the charge: do not retry.
    ErrDeclined = errors.New("payment: declined")
    // ErrUnavailable means the provider did not answer: a retry may succeed.
    ErrUnavailable = errors.New("payment: unavailable")
    // ErrForbidden means the caller may not perform the operation.
    ErrForbidden = errors.New("payment: forbidden")
)
```

L'équipe veut, dans l'ordre où les demandes sont arrivées : une ligne de
journal par paiement, un délai par tentative, des reprises sur panne
passagère, puis un compteur des issues, un accès en lecture seule pour
l'outil du support, et enfin un nouveau prestataire dont le SDK ne parle pas
la même langue.

Tout ce qui suit est mesuré sur un module vert sous `gofmt -l`,
`go vet ./...` et `go test -race -count=1 ./...`. Le prestataire et son SDK
sont **fictifs** ; le faux prestataire des tests suit un script : `Hang`
appels qui ne répondent jamais, puis `Fail` appels en panne, puis des
réponses.

## 1. Les deux formes de départ

### Tout dans le client

La première idée est la plus naturelle : le client qui parle au prestataire
fait aussi le reste.

```go
// Charge sends the charge, with a timeout per attempt, retries and a log
// line per attempt.
func (c *Client) Charge(ctx context.Context, ch payment.Charge) (payment.Receipt, error) {
    for attempt := 0; ; attempt++ {
        start := time.Now()
        actx, cancel := context.WithTimeout(ctx, c.Timeout)
        r, err := c.Send(actx, ch)
        cancel()
        if errors.Is(err, context.DeadlineExceeded) && ctx.Err() == nil {
            err = fmt.Errorf("%w: no answer within %v", payment.ErrUnavailable, c.Timeout)
        }
        c.Log.Info("charge", "id", ch.ID, "attempt", attempt, "err", err, "took", time.Since(start))
        if err == nil || !errors.Is(err, payment.ErrUnavailable) || attempt == c.Retries {
            return r, err
        }
        select {
        case <-ctx.Done():
            return payment.Receipt{}, ctx.Err()
        case <-time.After(c.Wait):
        }
    }
}
```

C'est juste, et testé. Mais lis la boucle : quatre préoccupations sont
tressées dans les mêmes lignes — le délai (`WithTimeout`), la
traduction du délai en panne, le journal, les reprises. Et `Status` contient
**la même boucle**, recopiée, parce qu'il faut les mêmes
protections pour la lecture. Toute nouvelle préoccupation s'écrit deux fois,
au milieu des autres.

### Un décorateur par préoccupation

La seconde forme découpe : chaque préoccupation est un type qui **est** une
`payment.Gateway` et qui **en contient** une.

```go
// Timeout gives each call at most D. When its own deadline fires, it
// reports payment.ErrUnavailable, so that a retry above it may try again.
type Timeout struct {
    Next payment.Gateway
    D    time.Duration
}

// Charge calls Next with a deadline.
func (t Timeout) Charge(ctx context.Context, c payment.Charge) (payment.Receipt, error) {
    actx, cancel := context.WithTimeout(ctx, t.D)
    defer cancel()
    r, err := t.Next.Charge(actx, c)
    return r, t.translate(ctx, err)
}
```

```go
// translate turns our own deadline into ErrUnavailable; the caller's
// deadline stays what it is.
func (t Timeout) translate(ctx context.Context, err error) error {
    if errors.Is(err, context.DeadlineExceeded) && ctx.Err() == nil {
        return fmt.Errorf("%w: no answer within %v", payment.ErrUnavailable, t.D)
    }
    return err
}
```

`translate` est la seule subtilité : quand **notre** délai expire, c'est une
panne passagère, et un décorateur de reprise au-dessus a le droit de
réessayer. Quand c'est le délai **de l'appelant** qui expire, il a abandonné :
on ne déguise pas son abandon en panne.

```go
// Retrying calls Next again after payment.ErrUnavailable, at most Retries
// more times. It retries a Charge only because Charge.ID makes a repeat
// harmless.
type Retrying struct {
    Next    payment.Gateway
    Retries int
    Wait    time.Duration
}
```

```go
func (r Retrying) do(ctx context.Context, call func() error) error {
    for attempt := 0; ; attempt++ {
        err := call()
        if err == nil || !errors.Is(err, payment.ErrUnavailable) || attempt == r.Retries {
            return err
        }
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-time.After(r.Wait):
        }
    }
}
```

Réessayer un paiement n'est sûr que parce que `Charge.ID` est une clé
d'idempotence (leçon 1.1, et 3.2 exercice 4) : si la première tentative a
abouti sans que la réponse revienne, la deuxième rend le même reçu au lieu de
débiter deux fois.

### La chaîne

Empiler à la main (`Logging{Next: Retrying{Next: Timeout{...}}}`) se lit de
l'intérieur vers l'extérieur. Une petite fonction remet l'ordre de lecture à
l'endroit :

```go
// Middleware wraps a Gateway into another Gateway.
type Middleware func(payment.Gateway) payment.Gateway

// Chain wraps g so that the first middleware is the outermost: a call goes
// through mws[0], then mws[1], ..., then g.
func Chain(g payment.Gateway, mws ...Middleware) payment.Gateway {
    for i := len(mws) - 1; i >= 0; i-- {
        g = mws[i](g)
    }
    return g
}
```

```go
// WithLogging returns a Middleware that adds Logging.
func WithLogging(log *slog.Logger) Middleware {
    return func(next payment.Gateway) payment.Gateway { return Logging{Next: next, Log: log} }
}
```

Un `Middleware`, c'est le même mot que dans un serveur HTTP : une fonction qui
prend un composant et en rend un autre, de même type. Le test fixe le sens de
lecture :

```go
func TestChainPutsTheFirstMiddlewareOutside(t *testing.T) {
    var trail []string
    g := deco.Chain(&fake.Gateway{}, tag("A", &trail), tag("B", &trail), tag("C", &trail))
    if _, err := g.Charge(context.Background(), charge); err != nil {
        t.Fatal(err)
    }
    if got := strings.Join(trail, ">"); got != "A>B>C" {
        t.Fatalf("order = %s, want A>B>C", got)
    }
}
```

### Ce qui ne change pas

Les deux formes ont **les mêmes tests de comportement** : une reprise après un
délai, un arrêt au bout de `Retries`, aucune reprise sur un refus, l'abandon
de l'appelant respecté. Les deux sont vertes. La différence n'apparaît que
quand on change quelque chose.

## 2. Première mesure : une préoccupation de plus

Le support veut compter les issues des paiements : réussis, refusés, en
panne. Dans le client, on ajoute un champ, trois lignes avant le `return` et
une fonction qui classe l'erreur.
En décorateur, on écrit un type de plus :

```go
// Counting counts the outcomes of charges: "ok", "declined", "unavailable"
// or "other".
type Counting struct {
    Next payment.Gateway

    mu     sync.Mutex
    counts map[string]int
}

// Charge counts the outcome of Next.Charge.
func (c *Counting) Charge(ctx context.Context, ch payment.Charge) (payment.Receipt, error) {
    r, err := c.Next.Charge(ctx, ch)
    c.add(outcome(err))
    return r, err
}
```

La mesure, sur une copie du module :

```text
inline:    inline/inline.go +16 -0, vet exit 0, tests exit 0
decorator: deco/counting.go new, 58 lines; existing files changed: 0
```

Il faut le dire honnêtement : **le décorateur coûte plus de lignes**, 58
contre 16. Ce qu'il achète est ailleurs :

- il touche **zéro** ligne existante — le client, ses tests et les autres
  décorateurs ne bougent pas ;
- il se teste seul, contre le faux prestataire, sans journal ni délai ;
- il s'enlève en retirant une ligne de la chaîne, alors que dans le client il
  faut relire la boucle pour savoir ce qu'on peut supprimer sans rien casser.

Et le client, lui, en est maintenant à **cinq** préoccupations dans la même
boucle. Le coût d'une préoccupation « en ligne » n'est pas les seize lignes :
c'est que la sixième s'écrira au milieu des cinq autres.

## 3. Deuxième mesure : l'ordre des couches

Les mêmes décorateurs, dans deux ordres différents, contre le même
prestataire. Le programme `cmd/order` :

```text
provider: the first call never answers, the second one does
  Chain(g, retries, timeout)   calls=2  took=250ms  err=<nil>
  Chain(g, timeout, retries)   calls=1  took=200ms  err=payment: unavailable: no answer within 200ms
provider: two calls fail, the third one succeeds
  Chain(g, logging, retries)   err=<nil>, 1 log lines:
    id=c-1 amount=5000 err=<nil>
  Chain(g, retries, logging)   err=<nil>, 3 log lines:
    id=c-1 amount=5000 err="payment: unavailable"
    id=c-1 amount=5000 err="payment: unavailable"
    id=c-1 amount=5000 err=<nil>
```

Ce que disent ces quatre lignes :

- **Délai à l'intérieur des reprises** (`retries, timeout`) : chaque tentative
  a 200 ms. La première expire, la deuxième passe. Le paiement réussit en
  250 ms.
- **Délai autour des reprises** (`timeout, retries`) : les 200 ms couvrent
  **tout**. La première tentative les consomme, il ne reste rien pour la
  deuxième. Le paiement échoue.
- **Journal à l'extérieur** : une ligne par paiement, ce que veut un relevé
  d'activité.
- **Journal à l'intérieur** : une ligne par tentative, ce que veut celui qui
  enquête sur les pannes du prestataire.

Aucun de ces ordres n'est « le bon » dans l'absolu : un délai global a du sens
pour une requête d'un client qui attend derrière son écran. Mais chaque ordre
est un **comportement**, et il se teste — `TestTimeoutPerAttemptLetsTheRetrySucceed`
et `TestTimeoutAroundTheRetriesStopsEverything` dans le module.

Dans le client « tout en ligne », l'ordre est figé dans la boucle : avoir les
deux journaux, ou un délai global, c'est réécrire la boucle.

## 4. Le proxy : même forme, autre intention

L'outil du support doit pouvoir **consulter** un paiement, jamais en créer.
On lui donne une passerelle qui refuse :

```go
// ReadOnly lets a support tool look at charges, never move money. Every
// method of the Gateway is written out.
type ReadOnly struct {
    Next payment.Gateway
}

// Charge is refused.
func (p ReadOnly) Charge(context.Context, payment.Charge) (payment.Receipt, error) {
    return payment.Receipt{}, payment.ErrForbidden
}

// Status is passed on.
func (p ReadOnly) Status(ctx context.Context, chargeID string) (string, error) {
    return p.Next.Status(ctx, chargeID)
}
```

C'est la forme d'un décorateur — même interface, un `Next` à l'intérieur — et
pourtant l'intention est différente : un décorateur **ajoute** à ce qui se
passe, un proxy **décide si** ça se passe. Le livre de 1994 range dans les
proxies le contrôle d'accès, le chargement paresseux et l'objet distant.

Il existe une version plus courte, qui n'écrit que la méthode qu'elle refuse
et **embarque** l'interface pour le reste :

```go
// ReadOnlyEmbed does the same with an embedded Gateway: it writes only the
// method it refuses, and every other method is promoted from the Gateway.
type ReadOnlyEmbed struct {
    payment.Gateway
}

// Charge is refused.
func (p ReadOnlyEmbed) Charge(context.Context, payment.Charge) (payment.Receipt, error) {
    return payment.Receipt{}, payment.ErrForbidden
}
```

En Go, embarquer `payment.Gateway` dans une structure **promeut** ses
méthodes : `ReadOnlyEmbed` a un `Status` qu'on n'a pas écrit, qui appelle
celui de la passerelle embarquée. Aujourd'hui, les deux proxies passent les
mêmes tests. La mesure suivante les sépare.

## 5. Troisième mesure : l'interface gagne une méthode

Le métier demande les remboursements. L'interface gagne une méthode :

```go
    // Refund gives the money of a captured charge back.
    Refund(ctx context.Context, chargeID string) error
```

On l'écrit chez les deux prestataires, et **rien d'autre**. La mesure :


Lis-la en deux temps.

**Premier temps, huit erreurs de compilation.** Chaque décorateur écrit à la
main, et le proxy `ReadOnly`, ne sont plus des `Gateway` : il leur manque
`Refund`. Le compilateur dresse la liste et oblige à **décider**, pour chacun :
le journal journalise le remboursement, le délai le borne, les reprises le
réessaient, `ReadOnly` le **refuse**.

Cinq de ces erreurs viennent de vérifications écrites exprès — une dans
`proxy/proxy.go`, quatre dans ce fichier :

```go
package deco

import "example/bank33/payment"

// The compiler checks here, inside the package, that every decorator is a
// Gateway: a new method in the interface breaks this file first.
var (
    _ payment.Gateway = Logging{}
    _ payment.Gateway = Timeout{}
    _ payment.Gateway = Retrying{}
    _ payment.Gateway = (*Counting)(nil)
)
```

Sans elles, un décorateur que le paquet n'utilise jamais comme `Gateway`
(`Counting`, ici) ne serait signalé qu'au premier appelant, dans un autre
paquet. *Effective Go* décrit ce geste dans
[Interface checks](https://go.dev/doc/effective_go#blank_implements) : une
affectation à l'identifiant `_` pour que le compilateur vérifie, dans le
paquet même, qu'un type satisfait une interface.

**Second temps, zéro erreur pour `ReadOnlyEmbed`, et un trou de sécurité.**
`ReadOnlyEmbed` compile sans qu'on y touche : `Refund` a été promu depuis la
passerelle embarquée. Le test le dit en clair : **l'outil du support peut
rembourser**. Personne n'a écrit de code pour l'autoriser ; personne n'a eu à
décider.

C'est la mesure centrale de la leçon :

> **Un décorateur écrit à la main casse à la compilation quand l'interface
> grandit : c'est ce qu'on veut. Un décorateur qui embarque l'interface
> laisse passer chaque méthode future sans son comportement, en silence.**

L'embarquement reste un bon outil quand le comportement ajouté **doit**
s'appliquer à tout ce qui viendra sans y réfléchir — et c'est rarement le cas
d'un contrôle d'accès.

## 6. L'adaptateur : traduire un vocabulaire

Le nouveau prestataire fournit un SDK. Sa langue n'est pas celle de la
banque :

```go
func (c *Client) CreatePayment(token string, cents int, currency, idempotencyKey string) (*Payment, error) {
```

```go
// APIError is the SDK's only error type.
type APIError struct {
    Code      string // "card_declined", "rate_limited", "internal"
    Retryable bool
}
```

Pas de `context.Context`, un montant en `int`, des états en majuscules, et une
seule sorte d'erreur avec un code texte. L'adaptateur est le **seul paquet de
la banque qui importe le SDK** :

```go
// Charge translates the charge into the SDK's call, and its errors into the
// bank's.
func (g Gateway) Charge(ctx context.Context, c payment.Charge) (payment.Receipt, error) {
    if err := ctx.Err(); err != nil {
        return payment.Receipt{}, err
    }
    if c.Amount <= 0 || c.Amount > math.MaxInt32 {
        return payment.Receipt{}, fmt.Errorf("acme: amount %d out of range", c.Amount)
    }
    p, err := g.SDK.CreatePayment(c.Card, int(c.Amount), c.Currency, c.ID)
    if err != nil {
        return payment.Receipt{}, translate(err)
    }
    return payment.Receipt{ChargeID: c.ID, Ref: p.Reference}, nil
}
```

```go
func translate(err error) error {
    var api *acmepay.APIError
    switch {
    case !errors.As(err, &api):
        return err
    case api.Code == "card_declined":
        return fmt.Errorf("%w: %w", payment.ErrDeclined, err)
    case api.Retryable:
        return fmt.Errorf("%w: %w", payment.ErrUnavailable, err)
    }
    return err
}
```

Ce qu'il traduit, et pourquoi chaque ligne est là :

- **le montant** : `int64` vers `int`, avec un contrôle de bornes, parce
  qu'une conversion silencieuse tronquerait un grand montant ;
- **les erreurs** : `card_declined` devient `payment.ErrDeclined`, une erreur
  « réessayable » devient `payment.ErrUnavailable`. Le `%w: %w` garde **les
  deux** : le reste de la banque teste `errors.Is(err, payment.ErrDeclined)`,
  et celui qui enquête peut encore retrouver l'`*acmepay.APIError` avec
  `errors.As` ;
- **le contexte** : le SDK n'en prend pas, donc l'adaptateur vérifie au moins
  que l'appelant n'a pas déjà abandonné. Il ne peut **pas** interrompre un
  appel en cours : c'est une limite du SDK, et l'adaptateur ne la cache pas.

Parce que l'adaptateur rend une `payment.Gateway`, tous les décorateurs
s'appliquent à lui sans changement (`TestDecoratorsWorkOnTheAdapter`). Le
jour où le SDK change de version, un seul paquet s'ouvre.

`http.HandlerFunc`, vu en 3.1, est aussi un adaptateur : il fait entrer une
fonction dans l'interface `http.Handler`.

## 7. Le middleware HTTP, et l'embarquement qui cache

Côté serveur, la même idée s'appelle **middleware** : une fonction qui prend
un `http.Handler` et en rend un autre. Le classique est le journal d'accès,
qui doit connaître le code de statut écrit par le handler. Pour le
connaître, on emballe le `http.ResponseWriter` :

```go
// naiveRecorder remembers the status code a handler wrote.
type naiveRecorder struct {
    http.ResponseWriter
    status int
}

func (r *naiveRecorder) WriteHeader(code int) {
    r.status = code
    r.ResponseWriter.WriteHeader(code)
}
```

Et un handler qui diffuse des événements a besoin de vider son tampon après
chaque événement, avec `http.Flusher` :

```go
// EventsAssert streams three events, flushing each one, and finds the
// flusher with a type assertion.
func EventsAssert(w http.ResponseWriter, req *http.Request) {
    f, ok := w.(http.Flusher)
    if !ok {
        http.Error(w, "streaming unsupported", http.StatusInternalServerError)
        return
    }
    for i := 1; i <= 3; i++ {
        fmt.Fprintf(w, "event: %d\n", i)
        f.Flush()
    }
}
```

Le programme `cmd/stream` sert chaque handler nu, puis derrière chaque
journal d'accès :

```text
              bare            AccessLogNaive  AccessLog
EventsAssert  200             500             500
Events        200             500             200
```

Derrière `AccessLogNaive`, la diffusion **casse** : 500. Le mécanisme est
l'inverse de la section 5. Le champ embarqué est de type **interface**
`http.ResponseWriter`, donc seules ses trois méthodes sont promues — pas
`Flush`, que le `ResponseWriter` réel du serveur possède pourtant.
L'assertion `w.(http.Flusher)` échoue. La documentation de `net/http` le
prévient : « ResponseWriter wrappers may not » support Flusher.

La réparation officielle a deux moitiés, depuis Go 1.20. L'emballage expose ce
qu'il emballe :

```go
func (r *recorder) Unwrap() http.ResponseWriter { return r.ResponseWriter }
```

et le handler passe par `http.ResponseController`, qui suit les `Unwrap`
jusqu'au `ResponseWriter` d'origine :

```go
// Events streams three events, flushing each one, through
// http.ResponseController. The first Flush, before any write, checks that
// streaming is possible while an error status can still be sent.
func Events(w http.ResponseWriter, req *http.Request) {
    rc := http.NewResponseController(w)
    if err := rc.Flush(); err != nil {
        http.Error(w, "streaming unsupported", http.StatusInternalServerError)
        return
    }
    for i := 1; i <= 3; i++ {
        fmt.Fprintf(w, "event: %d\n", i)
        rc.Flush()
    }
}
```

La matrice montre qu'il faut **les deux** : `EventsAssert` derrière
`AccessLog` reste à 500, parce qu'une assertion de type ne suit pas
`Unwrap`.

## 9. La grille

| Si… | Alors |
|---|---|
| un comportement qui n'est pas le métier (journal, délai, reprise, mesure) | un **décorateur**, une préoccupation par type |
| plusieurs décorateurs | une **chaîne** dont l'ordre est lu dans le code et vérifié par un test |
| un délai et des reprises | décide si le délai borne **chaque tentative** ou **le tout** ; souvent les deux, à deux niveaux |
| des reprises sur une opération qui écrit | seulement avec une clé d'idempotence |
| contrôler **si** l'appel a lieu (droits, quota, paresse) | un **proxy**, chaque méthode écrite à la main |
| une interface qui va grandir | pas d'embarquement dans les décorateurs ; `var _ I = T{}` dans le paquet |
| un SDK ou un service qui ne parle pas ta langue | un **adaptateur**, le seul paquet qui l'importe, qui traduit aussi les erreurs |
| un emballage de `http.ResponseWriter` | une méthode `Unwrap`, et `http.ResponseController` dans les handlers |
| une seule préoccupation, un seul appelant, rien ne bouge | le code en ligne suffit (leçon 2.6) |

## 10. Les trois erreurs qui restent

### « Embarquer l'interface, c'est le décorateur sans le code répétitif »

C'est un décorateur **qui ne voit pas l'avenir**. La section 5 l'a mesuré :
huit erreurs de compilation d'un côté, un remboursement autorisé en silence de
l'autre. Les trois lignes de transmission qu'on économise sont précisément
les endroits où le compilateur t'aurait demandé de réfléchir.

### « L'ordre des middlewares, c'est de la plomberie »

La section 3 : le même délai, les mêmes reprises, et un paiement qui réussit
ou qui échoue selon l'ordre. Le journal donne une ligne par paiement ou une
par tentative. L'ordre est une spécification ; il mérite un test et un
commentaire.

### « Le décorateur, c'est un pattern objet ; en Go on fait des fonctions »

En Go, on fait **les deux**, et la bibliothèque standard le montre :
`bufio.NewReader`, `io.LimitReader` ou `gzip.NewReader` prennent un
`io.Reader` et en rendent un autre — ce sont des décorateurs. Le middleware
`func(http.Handler) http.Handler` est la forme fonction du même geste. La
forme importe moins que la règle : même interface en entrée et en sortie, une
préoccupation à la fois.

## 11. Le lien avec la production

| Ce que tu as déjà vu | Ce que c'est |
|---|---|
| des requêtes qui échouent toutes au bout de N secondes, alors que le prestataire répond en N+1 | un délai global autour des reprises (section 3) |
| un journal qui montre trois lignes pour un seul paiement, et une alerte « taux d'erreur » qui s'emballe | un journal à l'intérieur des reprises (section 3) |
| des événements serveur (SSE) qui n'arrivent qu'à la fin, ou une erreur « streaming unsupported » après l'ajout d'un middleware | un `ResponseWriter` emballé sans `Unwrap` (section 7) |
| un accès « lecture seule » qui a pu écrire après une mise à jour | un proxy qui embarque l'interface (section 5) |
| un double débit après une coupure réseau | des reprises sans clé d'idempotence (section 1) |
| un changement de SDK qui touche quarante fichiers | un SDK importé partout au lieu d'un adaptateur (section 6) |

## 12. Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Un décorateur a la même interface que ce qu'il emballe, et une seule préoccupation. |
| ⚫ | Une préoccupation de plus en décorateur coûte plus de lignes qu'en ligne, mais ne touche aucune ligne existante. |
| ⚫ | L'ordre des couches est un comportement : délai par tentative ou global, journal par paiement ou par tentative. |
| ⚫ | Un délai qui expire est une panne passagère seulement si c'est **le nôtre** ; celui de l'appelant est un abandon. |
| ⚫ | On ne réessaie une écriture qu'avec une clé d'idempotence. |
| ⚫ | Embarquer l'interface dans un décorateur fait passer chaque méthode future **sans** le comportement ; l'écrire à la main la fait casser à la compilation. |
| ⚫ | `var _ I = T{}` fait vérifier l'interface dans le paquet même. |
| ⚫ | Un adaptateur traduit noms, types et erreurs, et il est le seul à connaître l'autre vocabulaire. |
| ⚫ | Un emballage de `http.ResponseWriter` cache `Flush` ; `Unwrap` plus `http.ResponseController` le rendent. |

## 13. Approfondissement

### Les décorateurs de la bibliothèque standard

`io.Reader` est l'interface la plus décorée de Go. `io.LimitReader(r, n)`
s'arrête après `n` octets, `bufio.NewReader(r)` ajoute un tampon,
`gzip.NewReader(r)` décompresse, `io.TeeReader(r, w)` recopie ce qu'il lit.
Chacun prend un `io.Reader` et en rend un : on les empile exactement comme la
chaîne de la section 1.

### Le middleware côté client

Côté client HTTP, le point d'emballage est `http.RoundTripper` : un
`Transport` qui ajoute un en-tête, mesure une latence ou rejoue une requête
emballe le `http.DefaultTransport`. Les mêmes questions d'ordre se posent, et
la même règle d'idempotence : la documentation de `RoundTripper` demande de
ne pas modifier la requête reçue.

### `slog.Handler`

Un `slog.Handler` qui ajoute un attribut à chaque ligne, ou filtre un niveau,
emballe un autre `slog.Handler`. Il doit transmettre aussi `WithAttrs` et
`WithGroup` — c'est la section 5 à nouveau : une interface à plusieurs
méthodes, dont on oublie volontiers celles qui ne nous intéressent pas.

## 14. Le réflexe à installer

> **Devant un comportement à ajouter**
> Est-ce le métier de ce composant ? Si non, il va dans une couche autour,
> pas dans sa boucle.
>
> **Devant une pile de couches**
> Lis-la de l'extérieur vers l'intérieur et demande-toi, pour chaque paire :
> que se passe-t-il si je les échange ?
>
> **Devant une structure qui embarque une interface**
> Que fera-t-elle de la **prochaine** méthode de cette interface ?

Et le geste d'une minute :

> **Après avoir écrit un décorateur, ajoute `var _ I = T{}` à côté.** Le jour
> où l'interface grandit, c'est la ligne qui t'appellera.
