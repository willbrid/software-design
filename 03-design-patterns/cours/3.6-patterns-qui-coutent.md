# Leçon 3.6 — Les patterns qui coûtent : singleton, service locator, fabrique abstraite

## L'essentiel en deux minutes

**Le problème, en une phrase.** Certains objets servent à tout le
programme : la configuration, le client de l'opérateur, le grand livre,
l'horloge. La tentation est de les rendre **accessibles de partout**, par
une variable globale ou un annuaire. Ça marche, jusqu'au jour où il en faut
**deux versions** en même temps : deux tests, deux pays, deux opérateurs.
Ce jour-là arrive plus tôt qu'on ne le croit, souvent dès le premier test.

**Quatre images.**

- **La photocopieuse du service**, dont chacun change les réglages
  (recto-verso, agrandissement) et oublie de les remettre. La personne
  suivante reçoit les réglages de la précédente. C'est un **singleton
  modifiable**.
- **Le standard téléphonique** : « passez-moi la comptabilité ». On ne
  sait pas si quelqu'un répondra avant d'avoir appelé, et l'on ne le
  découvre qu'au moment où l'on en a besoin. C'est le **service locator**.
- **La mallette remise au technicien avant qu'il parte.** On voit ce
  qu'elle contient avant le départ ; s'il manque un outil, on le voit à
  l'atelier, pas chez le client. C'est l'**injection de dépendances**, et
  l'atelier est la **racine de composition**.
- **Le kit de raccordement d'un fabricant** : la prise et le câble viennent
  ensemble, et l'on ne branche pas le câble d'une marque sur la prise d'une
  autre. C'est la **fabrique abstraite**.

**Le code, en dix lignes.** Ce dont le service a besoin se lit dans `New`,
et `main` construit tout une fois.

```go
func New(op Operator, ledger Ledger, notify Notifier, sched fees.Schedule, limit int64, now func() time.Time) *Service {
    return &Service{op: op, ledger: ledger, notify: notify, fees: sched, limit: limit, now: now, sent: map[string]int64{}}
}
```

```go
    cfg, err := config.Load(*path)
    if err != nil {
        log.Fatalf("config: %v", err)
    }
```

**Les règles à retenir.**

1. **Une seule instance n'est pas un accès global.** `main` crée l'unique
   instance et la **passe** à ceux qui en ont besoin.
2. **Les dépendances se lisent dans la signature.** Le compilateur vérifie
   qu'il n'en manque aucune ; un annuaire ne le vérifie qu'à l'exécution.
3. **La configuration se lit une fois, au démarrage, dans `main`.** Une
   erreur arrête le programme avant le premier client, pas au milieu de la
   nuit.
4. **Une variable de paquet n'est acceptable que si elle ne change
   jamais** et ne fait aucune entrée-sortie : une erreur sentinelle, une
   expression régulière compilée.
5. **Une fabrique abstraite quand il existe vraiment plusieurs familles**
   qui ne doivent pas se mélanger. En Go, c'est une fonction qui rend la
   famille entière, choisie par **une seule** clé.

La suite mesure tout cela sur un vrai module.

---

Les cinq leçons précédentes présentaient des patterns qui **rapportent**,
à condition de les employer au bon moment. Celle-ci termine le niveau 3 par
trois patterns que l'on rencontre partout dans le code existant, et qui
coûtent souvent plus qu'ils ne rapportent. Le problème qui revient est

> **Un objet sert à tout le programme. Comment le rendre disponible partout
> où il sert, sans que chaque fonction en dépende en cachette, et sans
> s'interdire d'en avoir deux le jour où il en faut deux ?**

La banque de la leçon 3.5 facture ses transferts vers Mobile Money : 1 % du
montant, avec un minimum de 100 FCFA, et un plafond de 500 000 FCFA par
client et par jour. Les réglages sont dans un fichier `bank.conf` :

```text
# Test settings. The real file is on the server.
fee_bp      = 100
fee_min     = 100
daily_limit = 500000
operator    = kola
secret      = test-secret
```

La lecture du fichier (`config.Parse`) refuse une clé inconnue, une clé
manquante et un nombre illisible : une faute de frappe doit arrêter le
programme, pas le laisser facturer un tarif par défaut. Ce n'est pas le
sujet de la leçon ; la question est **qui lit ce fichier, quand, et comment
les réglages arrivent jusqu'au calcul des frais**.

Tout ce qui suit est mesuré sur un module vert sous `gofmt -l`,
`go vet ./...` et `go test -race -count=1 ./...`.

## 1. Le singleton : une configuration, partout

La première version fait ce que décrit le *Gang of Four* : « *Ensure a
class only has one instance, and provide a global point of access to it* »
(une seule instance, et un point d'accès global). En Go, une variable de
paquet et un `sync.Once` :

```go
// Path is where Get looks for the file.
var Path = "bank.conf"

var (
    once sync.Once
    cfg  *config.Config
)

// Get loads the configuration the first time it is called, and returns the
// same one ever after.
func Get() *config.Config {
    once.Do(func() {
        c, err := config.Load(Path)
        if err != nil {
            log.Printf("config: %v", err)
            return
        }
        cfg = &c
    })
    return cfg
}
```

Le calcul des frais s'en sert directement :

```go
// Fee reads the rate from the global configuration. Its signature does not
// say so.
func Fee(amount int64) int64 {
    c := global.Get()
    f := amount * c.FeeBP / 10_000
    if f < c.FeeMin {
        return c.FeeMin
    }
    return f
}
```

C'est court et ça marche. Tout le code peut appeler `legacy.Fee(150_000)`
sans rien préparer. Mais regarde la signature : `Fee(amount int64) int64`.
Rien n'y dit que la fonction **lit un fichier sur le disque**, qu'elle
dépend d'une variable `Path`, ni qu'elle plante si le fichier manquait au
premier appel. Le singleton mélange deux choses :

- **une seule instance** : c'est souvent une vraie contrainte (une seule
  configuration chargée, un seul pool de connexions) ;
- **un accès global** : c'est une commodité, et c'est elle qui coûte.

Les trois sections suivantes mesurent ce coût.

## 2. Mesure : `sync.Once` retient l'échec

Le serveur démarre à 7 h 58. Le fichier de configuration est déposé par le
déploiement à 8 h 00. Le premier transfert arrive à 7 h 59
(`go run ./cmd/once`) :

```text
config: open bank.conf: no such file or directory
07:59 first transfer, the file is not there yet: panic: runtime error: invalid memory address or nil pointer dereference
08:00 the file is there: panic: runtime error: invalid memory address or nil pointer dereference
08:00 global.Get() = <nil>
```

Le premier appel à `Get` a échoué. Le second **n'a même pas réessayé**,
alors que le fichier était là : `Once` a fait son travail, une fois. La
documentation le dit : « *If f panics, Do considers it to have returned;
future calls of Do return without calling f* ». Une erreur rendue, ou ici
seulement journalisée, compte de la même façon : `f` a été appelée, c'est
fini. `sync.OnceValues`, ajouté en Go 1.21, rend l'erreur proprement, mais
la **garde aussi** : il rendra la même erreur à chaque appel.

Le serveur ne s'arrête pas. Il répond, et chaque transfert plante, jusqu'à
ce que quelqu'un le redémarre. Le défaut n'est pas `sync.Once` : c'est de
lire la configuration **au premier usage**, au milieu d'une requête, là où
l'on ne peut plus rien faire d'une erreur. La section 7 la lit au
démarrage.

## 3. Mesure : les tests se partagent l'état

Le paquet n'a qu'**une** configuration, donc tous ses tests partagent la
même. `TestMain` la fait pointer vers le fichier de test :

```go
// TestMain points the singleton at the test file, for every test of the
// package: there is only one configuration.
func TestMain(m *testing.M) {
    global.Path = "testdata/bank.conf"
    os.Exit(m.Run())
}
```

Puis une développeuse ajoute le test d'une promotion, à 0,5 % :

```go
// The test changes the singleton, and forgets to put it back.
func TestAPromotionHalvesTheFee(t *testing.T) {
    global.Get().FeeBP = 50
    if got := legacy.Fee(150_000); got != 750 {
        t.Fatalf("Fee(150000) = %d, want 750", got)
    }
}
```

Il passe. Tous les tests passent, dans l'ordre où ils sont écrits. Mais
`go test -shuffle=N` les exécute dans un ordre tiré au hasard à partir de
la graine `N`. Sur vingt graines :

```text
singleton: ok FAIL ok FAIL FAIL FAIL FAIL FAIL FAIL ok FAIL ok FAIL ok FAIL ok ok FAIL ok FAIL
singleton: 12 failing runs out of 20
```

Douze fois sur vingt, un test qui n'a rien à voir avec la promotion
échoue :

```text
-test.shuffle 2
--- FAIL: TestTheFeeReadsTheGlobalConfiguration (0.00s)
    legacy_test.go:20: Fee(150000) = 750, want 1500
FAIL
FAIL    example/wiring36/legacy 0.002s
FAIL
```

Le test en échec n'est pas le fautif : c'est la promotion, exécutée
**avant**, qui a laissé le taux à 50. La photocopieuse est restée en
recto-verso. Ce genre d'échec coûte des heures, parce que le message
désigne le mauvais test et qu'il ne se reproduit qu'une fois sur deux.

« Il suffit de remettre la valeur. » Essayons, avec `t.Cleanup`, et des
tests parallèles pour que la CI aille plus vite :

```go
// This one puts the rate back. It still shares it with the test below.
func TestAPromotionInParallel(t *testing.T) {
    t.Parallel()
    c := global.Get()
    old := c.FeeBP
    c.FeeBP = 50
    t.Cleanup(func() { c.FeeBP = old })
    if got := legacy.Fee(150_000); got != 750 {
        t.Fatalf("Fee(150000) = %d, want 750", got)
    }
}
```

Sous `go test -race`, vingt fois de suite :

```text
20 runs of go test -race: 8 reported a race, 12 were green
```

Quand le détecteur la voit, la course est exactement celle qu'on attend :

```text
WARNING: DATA RACE
Write at 0x00c00001aac0 by goroutine 9:
  example/wiring36/legacy_test.TestAPromotionInParallel()
Previous read at 0x00c00001aac0 by goroutine 10:
  example/wiring36/legacy.Fee()
  example/wiring36/legacy_test.TestOnePercentInParallel()
  example/wiring36/legacy_test.TestMain()
  example/wiring36/legacy_test.TestMain()
--- FAIL: TestAPromotionInParallel (0.00s)
    testing.go:1867: race detected during execution of test
```

Huit fois sur vingt, le détecteur trouve l'écriture de la promotion et la
lecture de l'autre test sur **la même adresse**. Les douze autres fois,
les deux tests ne se sont pas chevauchés, et tout est vert. Remettre la
valeur ne suffit pas : deux tests qui tournent en même temps voient le
réglage de l'autre **pendant** qu'il est changé. Avec un singleton
modifiable, il n'existe que deux façons de faire des tests fiables : ne
jamais le modifier, ou ne jamais tester en parallèle.

## 4. L'horloge est un singleton aussi

Le plafond est « par jour ». Le code d'origine calcule le jour avec
`time.Now()` : la fonction lit l'horloge du système, que tout le programme
partage. Le test « le plafond repart le lendemain » demande alors
d'attendre minuit. Personne ne l'a écrit, et la campagne de la section 11
le montrera.

Le remède est le même que pour la configuration : l'horloge devient un
paramètre, `now func() time.Time`. En production, on passe `time.Now`. Dans
les tests, une horloge que le test avance à la main :

```go
// clock is a time the test moves by hand.
type clock struct{ t time.Time }
```

```go
// The clock is a dependency too: without it, this test would wait until
// midnight.
func TestTheLimitStartsAgainTheNextDay(t *testing.T) {
    t.Parallel()
    s, _, _, _, c := newService(standard, 500_000)
    ctx := t.Context()
    if _, err := s.Send(ctx, "k1", "ACC-1", "237690000001", 500_000); err != nil {
        t.Fatal(err)
    }
    c.t = c.t.Add(16 * time.Hour) // 00:00 the next day
    if _, err := s.Send(ctx, "k2", "ACC-1", "237690000001", 500_000); err != nil {
        t.Fatalf("next day: %v", err)
    }
}
```

Seize heures d'attente deviennent une affectation.

## 5. Le service locator : des dépendances qu'on ne voit qu'à l'exécution

La configuration n'est pas la seule chose partagée. Le service de transfert
a besoin d'un opérateur, d'un grand livre et d'un service de SMS. La
version d'origine les range dans un **annuaire** global, où chacun vient
chercher ce qu'il lui faut par son nom :

```go
// Register makes s available under name.
func Register(name string, s any) {
    mu.Lock()
    defer mu.Unlock()
    services[name] = s
}
```

```go
// Get returns the service registered under name. It panics if there is
// none, or if it is not a T: the compiler cannot check either.
func Get[T any](name string) T {
    mu.RLock()
    defer mu.RUnlock()
    s, ok := services[name]
    if !ok {
        panic(fmt.Sprintf("locator: no service named %q", name))
    }
    t, ok := s.(T)
    if !ok {
        panic(fmt.Sprintf("locator: %q is a %T", name, s))
    }
    return t
}
```

```go
// Service needs an operator, a ledger, a notifier, the configuration and a
// clock. Its type says none of it.
type Service struct {
    mu   sync.Mutex
    sent map[string]int64
}

func (s *Service) Send(ctx context.Context, key, account, wallet string, amount int64) (int64, error) {
    day := account + "/" + time.Now().Format("2006-01-02")
    s.mu.Lock()
    if s.sent == nil {
        s.sent = map[string]int64{}
    }
    if s.sent[day]+amount > global.Get().DailyLimit {
        s.mu.Unlock()
        return 0, transfer.ErrLimit
    }
    s.sent[day] += amount
    s.mu.Unlock()

    fee := Fee(amount)
    ledger := locator.Get[transfer.Ledger]("ledger")
    if err := ledger.Hold(ctx, account, amount+fee); err != nil {
        return 0, err
    }
    if err := locator.Get[transfer.Operator]("operator").Send(ctx, key, wallet, amount); err != nil {
        return 0, errors.Join(err,
            ledger.Release(ctx, account, amount+fee),
            locator.Get[transfer.Notifier]("sms").Refused(ctx, account, amount))
    }
    return fee, nil
}
```

Le serveur web enregistre les trois services au démarrage. Le traitement
de nuit, écrit plus tard pour payer 200 bénéficiaires, recopie ce qu'il
croit nécessaire :

```go
    locator.Register("ledger", &fake.Ledger{})
    locator.Register("operator", &fake.Operator{Refuse: map[string]bool{"237690000038": true}})
```

Le SMS de refus a été ajouté au service **après** l'écriture du
traitement de nuit, et personne n'a pensé à lui. Ce que disent le
compilateur, puis l'exécution (`go run ./cmd/locator`) :

```text
go build && go vet: exit 0
sent before the crash: 37
panic: locator: no service named "sms"
```

Le programme compile, `go vet` ne dit rien, et 37 paiements partent. Le
38e est refusé par l'opérateur : c'est le premier à passer par le chemin du
SMS, et le traitement s'arrête. Les 162 bénéficiaires suivants ne sont pas
payés cette nuit-là. Un test du traitement qui ne jouerait que des paiements
acceptés serait vert.

Mark Seemann résume le défaut en une phrase : « *the problem with Service
Locator is that it hides a class' dependencies, causing run-time errors
instead of compile-time errors* ». Le type `Service` est une `struct{}`
vide ; pour savoir de quoi il a besoin, il faut lire **tout** son code, et
celui de tout ce qu'il appelle.

Martin Fowler, qui a décrit les deux formes en 2004, est plus nuancé : pour
lui, « *the choice between Service Locator and Dependency Injection is less
important than the principle of separating service configuration from the
use of services* ». C'est juste : un annuaire rempli au démarrage et lu au
même endroit vaut mieux qu'un code qui construit ses dépendances un peu
partout. Mais en Go, l'injection ne coûte presque rien, comme le montre la
section suivante, et elle fait vérifier le câblage par le compilateur.

## 6. L'injection : tout passe par `New`

La nouvelle forme reçoit tout ce dont elle a besoin. Ses champs **sont**
ses dépendances :

```go
// Service is one transfer service. Its fields are its dependencies: reading
// New is enough to know what it needs.
type Service struct {
    op     Operator
    ledger Ledger
    notify Notifier
    fees   fees.Schedule
    limit  int64
    now    func() time.Time

    mu   sync.Mutex
    sent map[string]int64 // account/day -> FCFA sent
}

func New(op Operator, ledger Ledger, notify Notifier, sched fees.Schedule, limit int64, now func() time.Time) *Service {
    return &Service{op: op, ledger: ledger, notify: notify, fees: sched, limit: limit, now: now, sent: map[string]int64{}}
}
```

```go
// Send holds amount plus the fee, then asks the operator. A refusal releases
// the money and tells the customer. It returns the fee.
func (s *Service) Send(ctx context.Context, key, account, wallet string, amount int64) (int64, error) {
    day := account + "/" + s.now().Format("2006-01-02")
    s.mu.Lock()
    if s.sent[day]+amount > s.limit {
        s.mu.Unlock()
        return 0, fmt.Errorf("%w: %d FCFA already sent today", ErrLimit, s.sent[day])
    }
    s.sent[day] += amount
    s.mu.Unlock()

    fee := s.fees.Fee(amount)
    if err := s.ledger.Hold(ctx, account, amount+fee); err != nil {
        s.undo(day, amount)
        return 0, err
    }
    if err := s.op.Send(ctx, key, wallet, amount); err != nil {
        s.undo(day, amount)
        return 0, errors.Join(err,
            s.ledger.Release(ctx, account, amount+fee),
            s.notify.Refused(ctx, account, amount))
    }
    return fee, nil
}
```

Les frais ne lisent plus rien : un barème est une **valeur**, que chaque
test peut avoir à lui.

```go
// Schedule is a rate with a floor. It is a value: two tests can each have
// their own.
type Schedule struct {
    RateBP int64 // basis points: 100 is 1 %
    Min    int64 // FCFA
}

func (s Schedule) Fee(amount int64) int64 {
    f := amount * s.RateBP / 10_000
    if f < s.Min {
        return s.Min
    }
    return f
}
```

Le traitement de nuit, écrit avec `New`, avec le même oubli :

```go
    svc := transfer.New(&fake.Operator{}, &fake.Ledger{}, fees.Schedule{RateBP: 100, Min: 100}, 5_000_000, time.Now)
```

```text
# example/wiring36/cmd/forget
cmd/forget/main.go:15:105: not enough arguments in call to transfer.New
        have (*fake.Operator, *fake.Ledger, fees.Schedule, number, func() time.Time)
        want (transfer.Operator, transfer.Ledger, transfer.Notifier, fees.Schedule, int64, func() time.Time)
```

L'oubli est trouvé à la compilation, par la machine du développeur, avant
la nuit : la ligne `want` donne même la liste de ce qui manque. C'est la
mallette ouverte à l'atelier.

Et les tests ? Chacun construit son service avec **son** barème :

```go
// Each test has its own schedule: a promotion here changes nothing elsewhere.
func TestAPromotionHalvesTheFee(t *testing.T) {
    t.Parallel()
    s, _, _, _, _ := newService(fees.Schedule{RateBP: 50, Min: 100}, 500_000)
    if fee, _ := s.Send(t.Context(), "k1", "ACC-1", "237690000001", 150_000); fee != 750 {
        t.Fatalf("fee = %d, want 750", fee)
    }
}
```

Tous les tests du paquet sont marqués `t.Parallel()`. Sur vingt ordres
tirés au hasard, sous `-race` :

```text
explicit: ok ok ok ok ok ok ok ok ok ok ok ok ok ok ok ok ok ok ok ok
explicit: 0 failing runs out of 20
```

Aucun échec, aucune course : il n'y a plus rien à partager.

## 7. La racine de composition

Si plus personne ne va chercher ses dépendances, quelqu'un doit les
construire. Ce quelqu'un est **un seul** endroit du programme, au plus près
de `main` : la racine de composition. Seemann la définit ainsi : « *A
Composition Root is a (preferably) unique location in an application where
modules are composed together* ».

Ici, `wiring.Build` connaît tous les types concrets et assemble le service
à partir de la configuration :

```go
// Families maps the configuration's "operator" key to the function that
// builds the whole family. One key picks every part.
var Families = map[string]func(operator.Settings) operator.Family{
    "kola":   kola.New,
    "baobab": baobab.New,
}

// Build is called once, by main. An unknown operator stops the program
// before it serves anything.
func Build(cfg config.Config, url string, httpc *http.Client, ledger transfer.Ledger, sms transfer.Notifier, now func() time.Time) (*transfer.Service, operator.Verifier, error) {
    newFamily, ok := Families[cfg.Operator]
    if !ok {
        return nil, nil, fmt.Errorf("unknown operator %q", cfg.Operator)
    }
    fam := newFamily(operator.Settings{URL: url, Secret: cfg.Secret})
    op := operator.Client{Family: fam, URL: url, HTTP: httpc}
    sched := fees.Schedule{RateBP: cfg.FeeBP, Min: cfg.FeeMin}
    return transfer.New(op, ledger, sms, sched, cfg.DailyLimit, now), fam.Verifier, nil
}
```

Et `main` lit la configuration **une fois, au démarrage** :

```go
func main() {
    log.SetFlags(0)
    path := flag.String("config", "bank.conf", "settings file")
    flag.Parse()

    cfg, err := config.Load(*path)
    if err != nil {
        log.Fatalf("config: %v", err)
    }
    // Plays the operator, so that the demo needs no network.
    op := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusAccepted)
    }))
    defer op.Close()

    httpc := &http.Client{Timeout: 10 * time.Second} // this service's own client
    svc, _, err := wiring.Build(cfg, op.URL, httpc, &fake.Ledger{}, &fake.Notifier{}, time.Now)
    if err != nil {
        log.Fatalf("wiring: %v", err)
    }
    for i, amount := range []int64{150_000, 5_000, 400_000} {
        fee, err := svc.Send(context.Background(), fmt.Sprint("demo-", i), "ACC-1", "237690000001", amount)
        fmt.Printf("%7d FCFA: fee %5d, %v\n", amount, fee, err)
    }
}
```

Avec le fichier de test (`go run ./cmd/bank -config legacy/testdata/bank.conf`) :

```text
 150000 FCFA: fee  1500, <nil>
   5000 FCFA: fee   100, <nil>
 400000 FCFA: fee     0, daily limit reached: 155000 FCFA already sent today
```

Sans fichier :

```text
config: open bank.conf: no such file or directory
exit status 1
exit 1
```

Le programme s'arrête **avant** d'accepter le premier client, avec un code
de sortie non nul. L'orchestrateur (systemd, Kubernetes) voit le démarrage
échouer, le déploiement s'arrête, et l'ancienne version continue de servir.
Comparé à la section 2, c'est le même fichier manquant ; la différence est
**quand** on le découvre.

Remarque le `http.Client` créé dans `main` : le service a **son
propre** client, avec son propre délai. La section suivante dit pourquoi.

## 8. Un singleton de la bibliothèque standard : `http.DefaultClient`

La bibliothèque standard a ses variables globales, et l'une d'elles est
célèbre : « *DefaultClient is the default Client and is used by Get, Head,
and Post* ». C'est un `&Client{}`, sans délai : « *A Timeout of zero means
no timeout* ».

Le rapport quotidien au régulateur l'utilise, et l'envoi prend une seconde
et demie :

```go
func Export(url string) error {
    resp, err := http.DefaultClient.Get(url)
    if err != nil {
        return err
    }
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK {
        return fmt.Errorf("regulator: %s", resp.Status)
    }
    return nil
}
```

Une autre équipe, dans un autre paquet, corrige un blocage sur la page
d'état de l'opérateur :

```go
// Configure was the fix for the hang: a timeout on the client. On the
// default client, which is everybody's.
func Configure() {
    http.DefaultClient.Timeout = time.Second
}
```

Lundi, avant la correction ; mardi, après (`go run ./cmd/defaultclient`) :

```text
Monday: report after 1.5s: <nil>
Tuesday: report after 1s: Get "http://127.0.0.1:45909": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
```

Le rapport au régulateur ne part plus, et personne n'a touché au paquet
`report`. La revue de code de `opstatus` ne pouvait pas le voir : le lien
entre les deux paquets n'apparaît dans **aucun** import. C'est le défaut du
singleton modifiable, dans la bibliothèque standard : chacun peut changer
les réglages de tous.

La règle est simple : un service crée **son** `http.Client`, avec le délai
qui lui convient, et le passe à ceux qui en ont besoin.

## 9. Ce qu'une variable de paquet a le droit d'être

Dave Cheney a posé la question en 2017 : à quoi ressemblerait Go sans
variables de paquet ? Sa réponse : « *package scoped variables are
fundamentally singletons, used to smuggle state between unrelated concerns,
encourage tight coupling and makes the code that relies on them hard to
test* ». Il ne propose pas de les interdire, mais l'expérience donne une
grille :

| Variable de paquet | Acceptable ? | Pourquoi |
|---|---|---|
| `var ErrLimit = errors.New(...)` | oui | ne change jamais, sert à comparer |
| `var walletRE = regexp.MustCompile(...)` | oui | immuable une fois compilée, sans entrée-sortie |
| une table de correspondance jamais modifiée (`Families`) | oui, avec prudence | personne ne doit y écrire après le démarrage ; une fonction qui la rend serait plus sûre |
| la configuration chargée | **non** | dépend d'un fichier, change entre les tests |
| une connexion, un client HTTP, un grand livre | **non** | fait des entrées-sorties, a des réglages |
| `time.Now`, `rand` global | **non** dans le code métier | rendent les tests dépendants de l'heure et du hasard |

La question à poser n'est pas « est-ce global ? » mais « **un test, ou un
second client, en voudrait-il une autre ?** ». Si oui, c'est un paramètre.

## 10. La fabrique abstraite : des familles qui ne se mélangent pas

La banque ouvre au Gabon. L'opérateur là-bas n'est plus Kola Money mais
Baobab Pay, et presque tout change : le format des ordres (JSON chez Kola,
formulaire chez Baobab) et la signature des réponses (HMAC-SHA256 en
hexadécimal contre HMAC-SHA512 en base64). Le service a besoin de deux
choses d'un opérateur :

```go
// Encoder writes a payment order in the operator's format.
type Encoder interface {
    Encode(key, wallet string, amount int64) (contentType string, body []byte)
}

// Verifier checks that a callback was signed by the operator.
type Verifier interface {
    Verify(body []byte, signature string) error
}
```

### Le premier fichier : deux clés

La première configuration choisit l'encodeur et le vérificateur
**séparément**, par deux clés. Le fichier du Gabon a été copié de celui du
Cameroun, et l'une des deux clés n'a pas été changée. Les ordres partent
bien, au bon format. Mais chaque réponse de Baobab est vérifiée avec
l'algorithme de Kola. Mille réponses (`go run ./cmd/mixed`) :

```text
separate keys: 1000 callbacks rejected out of 1000
one family key: 0 callbacks rejected out of 1000
```

Mille rejets. Avec la leçon 3.5, on sait ce que ça donne : chaque paiement
reste `Sent`, puis passe en `Unknown`, et l'argent des clients reste
bloqué jusqu'au rapprochement.

### Une clé, une famille

Le défaut n'est pas une faute de frappe : c'est une configuration qui
**permet** une combinaison absurde. Encodeur et vérificateur forment une
**famille** ; on ne doit pas pouvoir les choisir l'un sans l'autre. Le
*Gang of Four* appelle fabrique abstraite l'objet qui crée **toute** une
famille : « *Provide an interface for creating families of related or
dependent objects without specifying their concrete classes* ». Dessinée
comme dans le livre :

```go
type Factory interface {
    Encoder() operator.Encoder
    Verifier() operator.Verifier
}
```

```go
type Kola struct{ Settings operator.Settings }

func (f Kola) Encoder() operator.Encoder   { return kola.New(f.Settings).Encoder }
func (f Kola) Verifier() operator.Verifier { return kola.New(f.Settings).Verifier }
```

En Go, il n'est pas besoin d'une interface de fabrique et d'un type par
famille. Une famille est une **valeur** :

```go
// Family is everything one operator needs. Its parts go together: the
// encoder of one operator with the verifier of another sends fine, and
// rejects every answer.
type Family struct {
    Name     string
    Encoder  Encoder
    Verifier Verifier
}
```

et la fabrique, une **fonction** qui la rend entière :

```go
// New returns the whole Kola family. Nothing else builds its parts.
func New(s operator.Settings) operator.Family {
    return operator.Family{Name: "kola", Encoder: encoder{}, Verifier: verifier{secret: s.Secret}}
}
```

Le choix se fait par une seule clé, `operator = baobab`, dans la table
`Families` de la section 7. Il n'existe plus de fichier qui associe
l'encodeur de l'un au vérificateur de l'autre. C'est la seconde ligne de
la mesure : zéro rejet.

### Quand la fabrique abstraite coûte

Elle coûte quand il n'existe **qu'une** famille. Avant l'ouverture au
Gabon, la banque ne parlait qu'à Kola. Une interface `Factory`, un type
`KolaFactory` et des interfaces pour chaque produit, c'était écrire
aujourd'hui la souplesse d'un deuxième opérateur qui n'existait pas, et
dont on ne connaissait pas les différences. Elles auraient été fausses :
personne n'avait prévu qu'un opérateur signerait en SHA-512. C'est
l'abstraction prématurée de la leçon 2.6. Avec un seul opérateur, le
paquet `kola` suffit ; la famille se dessine le jour où le second arrive,
à partir de ce que les deux ont **vraiment** en commun.

## 11. La campagne

Le module est-il vraiment testé ? On introduit une erreur à la fois dans la
nouvelle forme, et l'on relance `go vet` et `go test -race` :

```text
clé inconnue ignorée                         tuee
clé manquante acceptée                       tuee
nombre illisible ignoré                      tuee
ligne sans « = » sautée                      tuee
plancher oublié                              tuee
taux pour mille                              tuee
plafond exclu                                tuee
plafond sans le jour                         tuee
plafond sans le compte                       tuee
refus sans libération                        tuee
libération sans les frais                    tuee
refus sans SMS                               tuee
un refus compte dans le plafond              tuee
Kola accepte toute signature                 tuee
Baobab vérifie sans le secret                tuee
ordre Kola mal nommé                         tuee
type de contenu oublié                       tuee
refus de l'opérateur ignoré                  tuee
opérateur inconnu : Kola par défaut          tuee
secret non transmis                          tuee
plancher du fichier ignoré                   tuee
plafond codé en dur                          tuee
taux codé en dur                             tuee
23/23 tuees
```

Vingt-trois erreurs, toutes vues. Une précision d'honnêteté : au premier
passage, « opérateur inconnu : Kola par défaut » ne compilait pas (le
paquet `fmt` devenait inutilisé) ; elle a été réécrite pour compiler, puis
rejouée. Les erreurs de câblage (« secret non transmis », « plafond codé en
dur ») sont vues par les tests de `wiring` : la racine de composition se
teste comme le reste.

Et le code d'origine ? Les mêmes erreurs, dans `legacy`, contre ses
propres tests :

```text
plancher oublié                              SURVIT
taux pour mille                              tuee
plafond exclu                                SURVIT
plafond sans le jour                         SURVIT
refus sans libération                        SURVIT
refus sans SMS                               SURVIT
1/6 tuees
```

Une sur six. Ce n'est pas que l'auteur du code d'origine testait mal :
avec un singleton, un annuaire global et `time.Now`, chaque test demande
un fichier sur le disque, des services enregistrés dans l'annuaire, et
d'attendre minuit. Alors on ne les écrit pas. Le plafond, le minimum, la
libération des fonds et le SMS n'avaient aucun test, et cinq erreurs
sur six survivent. Le code difficile à tester n'est pas testé :
c'est la leçon 1.6, mesurée.

## 12. La grille

| | Singleton et annuaire | Injection par `New` |
|---|---|---|
| ce dont le service a besoin | à lire dans tout son code | la signature de `New` |
| une dépendance oubliée | panique à l'exécution, au 38e paiement | erreur de compilation |
| fichier de configuration absent | panique à chaque transfert, sans retour possible | arrêt au démarrage, code de sortie 1 |
| tests dans un ordre tiré au hasard | 12 échecs sur 20 | 0 sur 20 |
| tests en parallèle | course détectée 8 fois sur 20 | aucune course |
| le plafond du lendemain | test impossible sans attendre minuit | une affectation |
| erreurs vues par les tests | 1 sur 6 | 23 sur 23 |
| code à écrire au démarrage | aucun | une racine de composition |

| | Deux clés séparées | Une famille par clé |
|---|---|---|
| combinaison absurde possible | oui | non |
| réponses rejetées sur 1 000 | 1 000 | 0 |
| ajouter un opérateur | deux entrées, à garder cohérentes | une fonction `New` |

## 13. Les trois erreurs qui restent

### « Un constructeur à huit paramètres, c'est illisible : l'annuaire est plus simple »

Les huit paramètres ne sont pas créés par l'injection : ils étaient déjà
là, cachés dans le code. L'injection les **montre**. S'ils sont trop
nombreux, c'est que le service a trop de raisons de changer (leçon 1.2), et
le remède est de le découper. Quand ils sont nombreux pour une bonne
raison, on les regroupe dans une `struct` de dépendances, et `New` vérifie
qu'aucune ne manque : c'est l'exercice 2.

### « Il n'y aura jamais qu'une configuration »

Il y en a déjà deux : celle de la production et celle des tests. Puis la
promotion, le second pays, la version de démonstration pour un partenaire.
Le singleton ne coûte rien le jour où on l'écrit ; il coûte le jour où il
en faut deux, et ce jour-là, il faut toucher tous ceux qui l'appellent.

### « Le singleton est sûr en concurrence, grâce à `sync.Once` »

`Once` protège la **création**. Il ne protège pas l'usage : deux goroutines
qui lisent et modifient l'objet créé font une course de données ordinaire,
mesurée section 3. Et il protège si bien la création qu'il ne la refait
jamais, même après un échec (section 2).

## 14. Le lien avec la production

Tu as déjà vu ces pannes :

- « Le service a démarré, mais toutes les requêtes échouent » : une
  configuration lue au premier usage, dont le chargement a échoué une fois.
  Un service qui lit sa configuration au démarrage, et qui échoue s'il ne
  peut pas, est **redémarré** par l'orchestrateur, ou bloque le
  déploiement : c'est ce qu'on veut.
- « Le job de nuit a planté sur un service non enregistré » : un annuaire,
  et un chemin rarement emprunté. La pile d'appels montre `locator.Get`,
  jamais l'endroit où l'enregistrement manquait.
- « Les tests passent en local et échouent en CI, une fois sur deux » : un
  état global partagé entre tests, révélé par un ordre ou un parallélisme
  différents. `go test -shuffle=on` le trouve avant la CI, et il affiche la
  graine pour rejouer l'échec.
- « Depuis la mise en production d'hier, l'export expire » : un réglage
  changé sur un objet partagé, `http.DefaultClient` ou
  `http.DefaultTransport`, par un paquet qui n'avait rien à voir.

Le réflexe de diagnostic : quand un comportement change sans que le code
concerné ait changé, cherche **ce qu'il partage** avec le code qui, lui, a
changé.

## 15. Ce qu'il faut retenir

1. Le singleton mélange **une seule instance** (souvent utile) et **un
   accès global** (presque toujours coûteux). Garde la première, laisse la
   seconde : `main` crée l'instance et la passe.
2. Une dépendance se passe à `New`. Le compilateur vérifie le câblage, les
   tests construisent ce qu'ils veulent, et la signature documente le
   service.
3. La configuration se lit au démarrage, dans la racine de composition, et
   une erreur arrête le programme.
4. L'horloge, le hasard et le client HTTP sont des dépendances comme les
   autres.
5. La fabrique abstraite garantit qu'une famille ne se mélange pas. En Go,
   une fonction qui rend la famille entière suffit, et seulement quand il
   existe vraiment plus d'une famille.

## 16. Approfondissement

### Les conteneurs d'injection

Dans d'autres langages, un **conteneur** construit les objets à partir de
déclarations (annotations, fichiers XML). Go en a aussi, qui génèrent ou
exécutent la racine de composition à partir des constructeurs. Ils servent
quand le graphe compte des centaines de types. En dessous, une racine
écrite à la main se lit de haut en bas, et ses erreurs sont des erreurs de
compilation. Commence toujours par elle.

### L'enregistrement par `init`

`database/sql` utilise un annuaire : un pilote s'enregistre dans sa
fonction `init`, et le programme l'importe pour cet effet seul
(`import _ "pkg/driver"`). C'est un annuaire acceptable, parce qu'il n'est
rempli qu'au démarrage et ne contient que des **fabriques** de connexions,
pas des connexions. Mais il garde le défaut de la section 5 : supprimer
l'import ne casse pas la compilation, seulement l'ouverture de la base.

Et les fonctions `init` ont un piège à elles. La spécification dit que
l'initialisation des paquets « *happens in a single goroutine,
sequentially, one package at a time* », **avant** `main`. Une variable de
paquet ou un `init` qui appelle `global.Get()` lit donc la configuration
avant que `main` ait pu dire où elle se trouve. L'exercice 5 en tire un
incident.

### Le niveau 7

La racine de composition est le cœur des architectures du niveau 7
(hexagonale, *clean architecture*) : le domaine ne connaît que des
interfaces, et un seul endroit connaît les implémentations. Ce que cette
leçon a fait pour un service, le niveau 7 le fera pour une application
entière.

## 17. Le réflexe à installer

Devant une variable globale, un `Get()` sans paramètre, ou un annuaire,
pose trois questions :

1. Un test en voudrait-il une autre version ? Un deuxième pays, un
   deuxième client ? Si oui, c'est un paramètre.
2. Si elle manque ou si elle est fausse, quand le découvre-t-on : à la
   compilation, au démarrage, ou au milieu de la nuit ?
3. Qui d'autre peut la modifier, et le verrait-on dans un import ?

## Fin du niveau 3

Les six leçons de ce niveau ont suivi le même chemin : une contrainte qui
revient, plusieurs façons de la résoudre en Go, une mesure de ce que coûte
chacune le jour où la contrainte change, puis le nom du pattern. Ce qui
reste, au-delà des noms :

- une **fonction** suffit souvent là où le livre dessine une interface et
  plusieurs classes (stratégie, fabrique, commande) ;
- un pattern se justifie par un **changement qui revient**, jamais par un
  changement imaginé ;
- chaque pattern a une version qui coûte : celle qui cache ce dont le code
  dépend, ou ce qu'il a déjà fait.

Le niveau 4 change de question. Jusqu'ici, le problème était donné. Il
apprend à le **trouver** : ce que le système doit faire, à quel point il
doit bien le faire, et comment le montrer à d'autres avant d'écrire du
code.
