# Leçon 3.2 — Construire un objet valide : constructeurs, options, builder, fabrique

## L'essentiel en deux minutes

**Le problème, en une phrase.** Un objet ne doit exister que **valide**, mais
il a des valeurs obligatoires, des valeurs facultatives, et des règles qui
lient deux valeurs entre elles.

**L'image.** Un guichet de banque qui ouvre des comptes : on ne repart pas
avec un compte si un papier manque, on ne remplit que les cases qui nous
concernent, et le guichetier relit **tout le dossier à la fin**, pas case par
case — parce que certaines règles portent sur deux cases à la fois.

**Le piège propre à Go.** Go n'a pas de constructeur obligatoire. N'importe
qui peut écrire `var c Client` et obtenir la **valeur zéro** : tous les
champs à zéro, sans passer par le guichet. La
[spécification](https://go.dev/ref/spec#The_zero_value) le garantit pour tout
type.

**Le code, en une cinquantaine de lignes.**

```go
// Package e32 is the two-minute version of lesson 3.2.
package e32

import (
    "errors"
    "fmt"
    "time"
)

// ErrNotBuilt is returned by a Client that New did not build.
var ErrNotBuilt = errors.New("client not built with New")

// Client sends payments. Its fields are unexported: New is the only door.
type Client struct {
    endpoint string
    timeout  time.Duration
    retries  int
}

// Option records one setting; New checks them all at the end.
type Option func(*Client)

// WithTimeout sets the timeout of one attempt.
func WithTimeout(d time.Duration) Option { return func(c *Client) { c.timeout = d } }

// WithRetries sets the number of retries; zero means "never retry".
func WithRetries(n int) Option { return func(c *Client) { c.retries = n } }

// New builds a valid Client or returns an error.
func New(endpoint string, opts ...Option) (*Client, error) {
    c := &Client{endpoint: endpoint, timeout: 2 * time.Second, retries: 3}
    for _, opt := range opts {
        opt(c)
    }
    if c.endpoint == "" {
        return nil, errors.New("missing endpoint")
    }
    if total := c.timeout * time.Duration(c.retries+1); total > 30*time.Second {
        return nil, fmt.Errorf("worst case %v exceeds 30s", total)
    }
    return c, nil
}

// Send refuses the zero value instead of panicking three calls later.
func (c *Client) Send(amount int64) error {
    if c == nil || c.endpoint == "" {
        return ErrNotBuilt
    }
    return nil
}
```

Ce que fait chaque morceau :

- **Champs non exportés** : un autre paquet ne peut ni fabriquer un client
  incomplet, ni le modifier après contrôle. `New` est la seule porte.
- **Une option enregistre, `New` contrôle** : la règle « le pire cas ne
  dépasse pas 30 s » lie deux réglages. Contrôlée dans `WithTimeout`, elle
  dépendrait de l'ordre des options ; contrôlée à la fin, elle voit tout.
- **`WithRetries(0)` veut vraiment dire zéro** : avec une structure de
  configuration, `Retries: 0` serait confondu avec « pas renseigné » et
  remplacé par le défaut 3.
- **`Send` détecte la valeur zéro** et rend une erreur nommée au lieu de
  paniquer plus loin.

**Les règles à retenir.**

1. Champs non exportés plus **une** porte qui rend l'objet ou une erreur.
2. La valeur zéro se **rend utile** ou se **détecte**. *Effective Go*
   recommande la première quand c'est possible
   ([Allocation with new](https://go.dev/doc/effective_go#allocation_new)) :
   « the zero value for Buffer is an empty buffer ready to use ».
3. Deux ou trois valeurs obligatoires : des paramètres. Beaucoup de réglages
   facultatifs dont le zéro veut dire « défaut » : une structure de
   configuration. Un zéro qui a un sens, ou une API publique qui va grandir :
   des options fonctionnelles.
4. Une règle qui lie deux réglages se contrôle **une fois, à la fin**.
5. Les valeurs par défaut se **copient**, elles ne se partagent pas par
   pointeur.

La suite de la leçon mesure chaque forme sur trois changements réels : un
réglage de plus, un zéro qui veut dire zéro, une règle qui lie deux réglages.

La leçon 3.1 a fait varier une règle. Celle-ci s'occupe du moment qui la
précède : **la naissance d'un objet**. Le problème qui revient :

> **Un objet n'a le droit d'exister que valide.** Il a des valeurs
> **requises**, des valeurs **facultatives** avec un défaut, et des règles qui
> **lient deux valeurs** entre elles. Où écrire ces règles pour qu'aucun
> chemin ne les contourne, et comment laisser l'appelant ne dire que ce qui
> l'intéresse ?

Le catalogue a quatre réponses : le **constructeur**, la **structure de
configuration**, les **options fonctionnelles** et le **builder**. Il a aussi
la **fabrique**, qui répond à une autre question — *quel type* construire. Go
ajoute une contrainte que les autres langages n'ont pas : il n'existe pas de
constructeur obligatoire. **N'importe quel type a une valeur zéro, et
n'importe quel paquet peut la déclarer.** Toute la leçon tourne autour de ce
fait.

Tout ce qui suit est mesuré sur un module vert sous `gofmt -l`,
`go vet ./...` et `go test -race -count=1 ./...`. Le partenaire de
règlement, ses délais et son contrat de service sont **fictifs**.

## 1. L'invariant : une seule porte

### Des champs exportés

```go
// Transfer moves an amount between two accounts.
type Transfer struct {
    From, To string
    Amount   int64
    Currency string
}
```

```go
// Validate checks the rules of a transfer.
func (t Transfer) Validate() error {
    switch {
    case t.From == "" || t.To == "":
        return fmt.Errorf("%w: missing account", ErrInvalid)
    case t.From == t.To:
        return fmt.Errorf("%w: same account", ErrInvalid)
    case t.Amount <= 0:
        return fmt.Errorf("%w: amount %d", ErrInvalid, t.Amount)
    case !currencies[t.Currency]:
        return fmt.Errorf("%w: currency %q", ErrInvalid, t.Currency)
    }
    return nil
}
```

La règle existe, et elle est juste. Mais elle est **une méthode qu'on
appelle** : chaque consommateur doit s'en souvenir. Le paquet a deux
consommateurs, `Post` qui s'en souvient et `Receipt` qui l'oublie. Cinq
virements invalides, écrits en une ligne chacun depuis un autre paquet :

```go
var invalid = []open.Transfer{
    {From: "", To: "B", Amount: 1_000, Currency: "XAF"},
    {From: "A", To: "A", Amount: 1_000, Currency: "XAF"},
    {From: "A", To: "B", Amount: 0, Currency: "XAF"},
    {From: "A", To: "B", Amount: -500, Currency: "XAF"},
    {From: "A", To: "B", Amount: 1_000, Currency: "XAG"},
}
```

```
Post refused 5/5, Receipt printed 5/5, e.g. "you sent -500 XAF to B"
```

Et un virement **validé puis modifié** reste un virement : le test
`TestValidThenChanged` contrôle, puis écrit `tr.Amount = -1_000`, et le reçu
dit `you sent -1000 XAF to B`. Le contrôle a eu lieu ; il ne protège plus rien.

### Des champs non exportés et un constructeur

```go
// Transfer moves an amount between two accounts.
type Transfer struct {
    from, to string
    amount   int64
    currency string
}
```

```go
// New returns a valid transfer, or an error: there is no third outcome.
func New(from, to string, amount int64, currency string) (Transfer, error) {
    switch {
    case from == "" || to == "":
        return Transfer{}, fmt.Errorf("%w: missing account", ErrInvalid)
    case from == to:
        return Transfer{}, fmt.Errorf("%w: same account", ErrInvalid)
    case amount <= 0:
        return Transfer{}, fmt.Errorf("%w: amount %d", ErrInvalid, amount)
    case !currencies[currency]:
        return Transfer{}, fmt.Errorf("%w: currency %q", ErrInvalid, currency)
    }
    return Transfer{from: from, to: to, amount: amount, currency: currency}, nil
}
```

`New` est la **seule porte** : elle rend un virement valide ou une erreur,
il n'y a pas de troisième issue. Depuis un autre paquet, les deux
contournements ne compilent plus :

```
try/try.go:5:27: cannot refer to unexported field amount in struct literal of type sealed.Transfer
try/try.go:7:36: t.amount undefined (type sealed.Transfer has no field or method amount, but does have method Amount)
```

Pas de littéral, pas d'affectation après coup. Le virement est valide à sa
naissance, et rien ne peut le rendre invalide ensuite — sauf à le remplacer
par la valeur zéro.

### Le trou : la valeur zéro

Une ligne du même fichier compile pourtant sans erreur :

```
var zero = sealed.Transfer{}
```

C'est le seul virement que `New` n'a pas construit, et Go ne permet pas de
l'interdire : un type exporté a une valeur zéro, et tout paquet peut la
déclarer — dans une variable non initialisée, un champ de structure, une
carte qui ne trouve pas la clé. La différence avec la forme ouverte est
qu'**il n'y en a qu'une**, et qu'elle se reconnaît en une comparaison :

```go
// IsZero reports whether t is the zero value, the one Transfer that New
// did not build.
func (t Transfer) IsZero() bool { return t == Transfer{} }
```

```go
// Post books the transfer.
func Post(t Transfer) (string, error) {
    if t.IsZero() {
        return "", ErrZero
    }
    return fmt.Sprintf("debit %s, credit %s: %d %s", t.from, t.to, t.amount, t.currency), nil
}
```

`Post` la refuse. `Receipt`, comme dans la forme ouverte, ne contrôle rien :

```
Receipt of the zero value: "you sent 0  to "
```

| | champs exportés | champs non exportés et `New` |
|---|---|---|
| virements invalides qu'un autre paquet peut écrire | **tous** | **un** : la valeur zéro |
| ce que chaque consommateur doit contrôler | toutes les règles | `IsZero` |
| un virement modifié après contrôle | possible | ne compile pas |
| ce que ça coûte | rien | des accesseurs, et des tests qui passent par `New` |

> Un constructeur ne rend pas les objets invalides **impossibles** en Go. Il
> réduit l'ensemble des objets invalides à **un seul, connu d'avance** : la
> valeur zéro. Les consommateurs n'ont plus à se souvenir de cinq règles,
> seulement d'une comparaison.

## 2. La valeur zéro d'un client

Le même trou existe pour un objet qui fait quelque chose. Le client du
partenaire de règlement a des champs non exportés et un constructeur `New` ;
on peut quand même écrire `var c gateway.Client`. Sans garde, `Send` sur cette
valeur fait ce que fait n'importe quel appel de méthode sur une interface
nulle (chemin raccourci) :

```
panic: runtime error: invalid memory address or nil pointer dereference [recovered, repanicked]
[signal SIGSEGV: segmentation violation code=0x1 addr=0x18 pc=0x54fbd7]
...
    gateway/gateway.go:82 +0x77
```

La ligne 82 de cette copie est l'appel au transport. Avec une garde de trois lignes, la même
valeur rend une erreur qui dit ce qui s'est passé :

```go
// Send posts the payload, retrying on error, and returns the number of
// attempts made.
func (c *Client) Send(ctx context.Context, payload string) (int, error) {
    if c == nil || c.s.Transport == nil {
        return 0, ErrNotBuilt
    }
    for attempt := 1; ; attempt++ {
        actx, cancel := context.WithTimeout(ctx, c.s.Timeout)
        err := c.s.Transport.Post(actx, c.s.Endpoint, payload)
        cancel()
        if err == nil || attempt > c.s.Retries {
            return attempt, err
        }
    }
}
```

La garde couvre aussi le pointeur nul : `var c *gateway.Client` suivi de
`c.Send(…)` est un appel de méthode valide en Go, avec `c == nil`.

> Go laisse deux choix devant la valeur zéro : la **rendre utile** — un
> `sync.Mutex` ou un `bytes.Buffer` zéro sont prêts à servir — ou la
> **détecter** et le dire. Un client sans transport ne peut pas être utile ;
> il doit le dire. Ce qu'il ne doit jamais faire, c'est paniquer trois appels
> plus loin.

## 3. Les valeurs requises, les valeurs facultatives, et la règle qui en lie deux

Le client a deux valeurs requises — l'adresse du partenaire, le transport — et
deux facultatives — le délai d'une tentative, le nombre de reprises. Et une
règle qui lie les deux facultatives : **un virement est réglé ou échoue en
trente secondes au plus**, toutes tentatives comprises.

```go
// Settings are the values a Client is built from.
type Settings struct {
    Endpoint  string
    Transport Transport
    Timeout   time.Duration
    Retries   int
}

// ErrSettings is returned for settings that break a rule.
var ErrSettings = errors.New("gateway: invalid settings")

// Validate checks every rule, including the one that ties two fields: it
// runs once all the values are known.
func (s Settings) Validate() error {
    switch {
    case !strings.HasPrefix(s.Endpoint, "https://"):
        return fmt.Errorf("%w: endpoint %q is not https", ErrSettings, s.Endpoint)
    case s.Transport == nil:
        return fmt.Errorf("%w: no transport", ErrSettings)
    case s.Timeout <= 0:
        return fmt.Errorf("%w: timeout %v", ErrSettings, s.Timeout)
    case s.Retries < 0:
        return fmt.Errorf("%w: retries %d", ErrSettings, s.Retries)
    case time.Duration(s.Retries+1)*s.Timeout > MaxTotal:
        return fmt.Errorf("%w: %d attempts of %v exceed %v", ErrSettings, s.Retries+1, s.Timeout, MaxTotal)
    }
    return nil
}
```

Toutes les règles sont écrites **une fois**, dans `Validate`, et `New` les
applique. Les quatre formes qui suivent ne diffèrent que par **la façon dont
l'appelant exprime les réglages** ; toutes finissent dans `gateway.New`.

### Les paramètres positionnels

```go
// New returns a client.
func New(endpoint string, t gateway.Transport, timeout time.Duration, retries int) (*gateway.Client, error) {
    return gateway.New(gateway.Settings{Endpoint: endpoint, Transport: t, Timeout: timeout, Retries: retries})
}
```

Pas de défaut possible : l'appelant écrit tout, à chaque fois.

```go
func ExampleNew() {
    journal := provider.Journal{W: io.Discard}
    c, err := positional.New("https://partner.example/settle", journal, 2*time.Second, 3)
    if err != nil {
        panic(err)
    }
    fmt.Println(c.Settings().Timeout, c.Settings().Retries)
    // Output: 2s 3
}
```

Que veut dire le `3` ? Il faut ouvrir la signature pour le savoir.

### La structure de configuration

```go
// Config holds the settings of a client.
type Config struct {
    Endpoint  string
    Transport gateway.Transport
    Timeout   time.Duration // zero means gateway.DefaultTimeout
    Retries   int           // zero means gateway.DefaultRetries
}

// New returns a client.
func New(c Config) (*gateway.Client, error) {
    s := gateway.Settings{Endpoint: c.Endpoint, Transport: c.Transport, Timeout: c.Timeout, Retries: c.Retries}
    if s.Timeout == 0 {
        s.Timeout = gateway.DefaultTimeout
    }
    if s.Retries == 0 {
        s.Retries = gateway.DefaultRetries
    }
    return gateway.New(s)
}
```

L'appelant ne nomme que ce qu'il change :

```go
func ExampleNew() {
    journal := provider.Journal{W: io.Discard}
    c, err := byconfig.New(byconfig.Config{
        Endpoint:  "https://partner.example/settle",
        Transport: journal,
        Timeout:   2 * time.Second,
    })
    if err != nil {
        panic(err)
    }
    fmt.Println(c.Settings().Timeout, c.Settings().Retries)
    // Output: 2s 3
}
```

Chaque champ se lit, et ce qui n'est pas écrit prend son défaut. Retenez le
commentaire de `Retries` : « zéro veut dire le défaut ». La section 5 y revient.

### Les options fonctionnelles

```go
// config is unexported: outside this package, nobody can write an Option
// that this package did not write.
type config struct {
    s gateway.Settings
}

// Option changes one setting.
type Option func(*config)

// WithTimeout sets the timeout of one attempt.
func WithTimeout(d time.Duration) Option {
    return func(c *config) { c.s.Timeout = d }
}

// WithRetries sets the number of retries after the first attempt. Zero
// means zero.
func WithRetries(n int) Option {
    return func(c *config) { c.s.Retries = n }
}

// New returns a client. The required values are parameters; the rest are
// options, applied over the defaults, then checked once, together.
func New(endpoint string, t gateway.Transport, opts ...Option) (*gateway.Client, error) {
    c := config{s: gateway.Settings{
        Endpoint:  endpoint,
        Transport: t,
        Timeout:   gateway.DefaultTimeout,
        Retries:   gateway.DefaultRetries,
    }}
    for _, o := range opts {
        o(&c)
    }
    return gateway.New(c.s)
}
```

Les valeurs requises sont des paramètres, le reste est une liste d'options
appliquées par-dessus les défauts. Le type `config` n'est pas exporté : hors
du paquet, personne ne peut écrire une option que le paquet n'a pas écrite.

```go
func ExampleNew() {
    journal := provider.Journal{W: io.Discard}
    c, err := byoption.New("https://partner.example/settle", journal,
        byoption.WithTimeout(2*time.Second),
    )
    if err != nil {
        panic(err)
    }
    fmt.Println(c.Settings().Timeout, c.Settings().Retries)
    // Output: 2s 3
}
```

### Le builder

```go
// Builder accumulates the settings of a client.
type Builder struct {
    s gateway.Settings
}

// NewBuilder starts from the required values and the defaults.
func NewBuilder(endpoint string, t gateway.Transport) *Builder {
    return &Builder{s: gateway.Settings{
        Endpoint:  endpoint,
        Transport: t,
        Timeout:   gateway.DefaultTimeout,
        Retries:   gateway.DefaultRetries,
    }}
}

// Timeout sets the timeout of one attempt.
func (b *Builder) Timeout(d time.Duration) *Builder {
    b.s.Timeout = d
    return b
}

// Retries sets the number of retries after the first attempt.
func (b *Builder) Retries(n int) *Builder {
    b.s.Retries = n
    return b
}

// Build returns a client, or the first broken rule.
func (b *Builder) Build() (*gateway.Client, error) {
    return gateway.New(b.s)
}
```

```go
func ExampleBuilder() {
    journal := provider.Journal{W: io.Discard}
    c, err := bybuilder.NewBuilder("https://partner.example/settle", journal).
        Timeout(2 * time.Second).
        Build()
    if err != nil {
        panic(err)
    }
    fmt.Println(c.Settings().Timeout, c.Settings().Retries)
    // Output: 2s 3
}
```

### Ce qui ne change pas

La batterie est écrite **une fois**, et les quatre formes y passent. Chaque
forme a sa traduction de « ce que l'appelant demande » — et celle des
paramètres positionnels montre son défaut : **l'appelant écrit les défauts
lui-même**.

```go
// cases is written once: the four forms must build the same clients.
var cases = []struct {
    name    string
    s       spec
    timeout time.Duration
    retries int
    fails   bool
}{
    {"defaults", spec{}, 5 * time.Second, 3, false},
    {"timeout given", spec{timeout: dur(2 * time.Second)}, 2 * time.Second, 3, false},
    {"one retry", spec{retries: n(1)}, 5 * time.Second, 1, false},
    {"budget kept", spec{timeout: dur(2 * time.Second), retries: n(9)}, 2 * time.Second, 9, false},
    {"budget broken", spec{retries: n(9)}, 0, 0, true},
    {"negative timeout", spec{timeout: dur(-time.Second)}, 0, 0, true},
    {"plain http", spec{endpoint: "http://partner.example/settle"}, 0, 0, true},
}
```

## 4. Première mesure : un réglage de plus

L'équipe sécurité du partenaire veut un `User-Agent` dans chaque requête, avec
un défaut. Deux lignes dans `gateway` pour les quatre formes, puis, mesuré sur
une copie verte du module, dans chaque forme :

| | positionnel | configuration | options | builder |
|---|---|---|---|---|
| fichiers touchés | **3** | 1 | 1 | 1 |
| lignes | +4 −4 | +5 −1 | +6 | +7 |
| erreurs de compilation, avant les appelants | **2** | 0 | 0 | 0 |
| appelants touchés | **tous** | 0 | 0 | 0 |

Les deux erreurs sont les deux appels du module :

```
gateway/forms_test.go:43:67: not enough arguments in call to positional.New
positional/example_test.go:14:85: not enough arguments in call to positional.New
```

Le module a deux appelants ; un service a autant d'appelants que d'endroits
qui construisent un client, tests compris. Les trois autres formes ajoutent un
réglage **sans qu'aucun appelant ne le sache**. C'est la même mesure que la
deuxième opération de la leçon 3.1 : le coût d'un changement croît avec le
nombre d'appelants quand les appelants dépendent de la **forme** de l'appel.

## 5. Deuxième mesure : le zéro qui veut dire zéro

Un partenaire n'est pas idempotent : renvoyer un ordre de virement, c'est le
payer deux fois. Pour lui, **aucune reprise**. Une ligne dans la batterie :

```
{"no retry", spec{retries: n(0)}, 5 * time.Second, 0, false},
```

```
forms_test.go:111: config, no retry: timeout 5s retries 3, want 5s and 0
```

Une seule forme rouge. Dans une structure de configuration, le zéro est déjà
pris : il veut dire « pas renseigné ». Il ne peut pas aussi vouloir dire
« zéro ». L'exemple du paquet le fixe, pour qu'aucun lecteur ne l'ignore :

```go
// ExampleNew_zeroRetries: the caller asks for no retry, and gets three.
// Zero is the value "not given"; it cannot also mean zero.
func ExampleNew_zeroRetries() {
    journal := provider.Journal{W: io.Discard}
    c, err := byconfig.New(byconfig.Config{
        Endpoint:  "https://partner.example/settle",
        Transport: journal,
        Retries:   0,
    })
    if err != nil {
        panic(err)
    }
    fmt.Println(c.Settings().Retries)
    // Output: 3
}
```

Trois reprises pour un partenaire qui paie chaque reprise. Les options, elles,
distinguent « pas d'option » de « l'option avec zéro » :

```go
// ExampleWithRetries: zero means zero.
func ExampleWithRetries() {
    journal := provider.Journal{W: io.Discard}
    c, err := byoption.New("https://partner.example/settle", journal, byoption.WithRetries(0))
    if err != nil {
        panic(err)
    }
    fmt.Println(c.Settings().Retries)
    // Output: 0
}
```

La structure de configuration a deux réparations, et aucune n'est gratuite :
un champ `*int` — l'appelant écrit `Retries: ptr(0)`, et le lecteur se demande
pourquoi un entier est un pointeur — ou une valeur sentinelle,
`NoRetries = -1`, qui fait de `-1` un nombre de reprises valide et oblige à
documenter une convention. La règle utile : **une structure de configuration
convient quand le zéro de chaque champ peut honnêtement vouloir dire « le
défaut »**. Dès qu'un zéro a un sens métier — zéro reprise, zéro frais, délai
nul —, elle ment.

## 6. Troisième mesure : où contrôler la règle qui lie deux valeurs

La règle des trente secondes lie le délai et les reprises. Le réflexe, quand
on écrit des options qui peuvent échouer, est de la mettre dans l'option qui
est arrivée avec elle :

```go
// WithRetries checks the budget against the timeout known so far: the
// options that come after it are not applied yet.
func WithRetries(n int) Option {
    return func(c *config) error {
        if time.Duration(n+1)*c.s.Timeout > gateway.MaxTotal {
            return fmt.Errorf("%w: %d attempts of %v exceed %v", gateway.ErrSettings, n+1, c.s.Timeout, gateway.MaxTotal)
        }
        c.s.Retries = n
        return nil
    }
}
```

L'option contrôle le budget **avec le délai connu à ce moment-là**, et les
options suivantes ne sont pas encore appliquées. Les mêmes deux options, les
mêmes réglages finaux — dix tentatives de 2 s, 20 s en tout :

```
retries then timeout: gateway: invalid settings: 10 attempts of 5s exceed 30s
```

Acceptés dans un ordre, refusés dans l'autre. C'est le premier défaut : **un
refus à tort**. Le second se voit en retirant le contrôle final de
`gateway.New`, sur une copie : l'autre ordre de deux autres options passe.

```
retries then timeout: accepted, 6 attempts of 10s = 1m0s
```

Une minute pour un contrat de trente secondes. Dans le module publié, seul le
contrôle de `gateway.New` l'arrête — le contrôle dans l'option est donc au
mieux **inutile**, au pire **faux**.

> **Une option enregistre ; le constructeur contrôle.** Une règle qui lie deux
> valeurs ne peut être vérifiée qu'une fois toutes les valeurs connues : après
> la dernière option et le dernier défaut, juste avant de rendre l'objet. Le
> builder a le même piège s'il contrôle dans ses méthodes, et la même réponse :
> tout contrôler dans `Build`.

Une option peut quand même refuser **sa propre valeur** quand la règle ne
regarde qu'elle — un délai négatif, par exemple. Ce qu'elle ne peut pas
juger, c'est une relation avec une valeur qui n'est pas encore là.

## 7. Le builder, et ce qu'il apporte en Go

Dans les trois mesures, le builder a fait **exactement** ce que font les
options, avec un objet mutable de plus. C'est le résultat honnête : pour
construire un objet à partir de valeurs connues d'un coup, Go a les options,
et le builder du livre n'apporte rien.

Il paie dans deux cas. Quand **la construction est étalée** : les réglages
viennent du fichier de configuration, puis de l'environnement, puis des
drapeaux, et trois fonctions différentes complètent le même builder avant un
seul `Build`. Et quand **le produit s'assemble par morceaux** : c'est le sens
des seuls « builders » de la bibliothèque standard, `strings.Builder` et
`bytes.Buffer`, qui n'ont aucun réglage et servent à éviter de recopier une
chaîne à chaque ajout. Un builder qui n'est ni l'un ni l'autre est une
structure de configuration avec des méthodes autour.

## 8. La fabrique : choisir le type

Toutes les formes précédentes construisent **un** type. La fabrique répond à
une autre question : la configuration dit `transport: journal` en recette et
`transport: https` en production, et l'appelant ne doit pas savoir lequel.

```go
// New returns the transport named by kind. The caller does not choose the
// type: the configuration does, and the caller only sees the interface.
func New(kind string, journal io.Writer) (gateway.Transport, error) {
    switch kind {
    case "https":
        return HTTPS{Client: &http.Client{}}, nil
    case "journal":
        return Journal{W: journal}, nil
    }
    return nil, fmt.Errorf("%w: %q (known: https, journal)", ErrUnknownKind, kind)
}
```

```
provider: unknown kind: "smtp" (known: https, journal)
```

Deux remarques, qui relient cette section aux précédentes.

**Elle rend l'interface.** La leçon 2.5 déclare l'interface chez le
consommateur, et un constructeur y rend donc un type concret. La fabrique est
l'exception légitime :
l'appelant **ne choisit pas** le type, la configuration le fait. Rendre
`HTTPS` ou `Journal` n'aurait aucun sens.

**Elle contient un `switch`, et c'est très bien.** La leçon 3.1 a mesuré
qu'un `switch` coûte cher à partir de la deuxième opération. Une fabrique a
une seule opération — construire — et c'est l'endroit où le `switch` sur une
chaîne de configuration a sa place : un seul, à la frontière, qui traduit une
chaîne en type. Un type de transport de plus, mesuré :

```
== fabrique, un type de plus : 2 fichier(s) [provider/provider.go, provider/refuse.go], +16 -1 lignes, 0 erreur(s), 0 test(s) rouge(s)
```

Aucun appelant touché : ils ne voient que `gateway.Transport`.

## 9. Les défauts partagés

Une dernière forme, rencontrée dans de vrais dépôts. Les options sont
correctes, les défauts aussi, et il manque **une étoile** :

```go
// defaults are the settings every client starts from.
var defaults = &gateway.Settings{
    Timeout: gateway.DefaultTimeout,
    Retries: gateway.DefaultRetries,
}
```

```go
// New returns a client.
func New(endpoint string, t gateway.Transport, opts ...Option) (*gateway.Client, error) {
    s := defaults // a copy of the pointer, not of the settings
    s.Endpoint, s.Transport = endpoint, t
    for _, o := range opts {
        o(s)
    }
    return gateway.New(*s)
}
```

`s := defaults` copie le **pointeur**. Chaque option écrit donc dans les
défauts de tout le paquet, et le client suivant hérite des choix du
précédent :

```
second client, no option: timeout 1s
```

Le second client n'a rien demandé et reçoit le délai du premier. Et deux
constructions concurrentes écrivent la même structure :

```
WARNING: DATA RACE
```

La réparation est l'étoile — `s := *defaults` copie les réglages — plus les
deux ajustements qu'elle entraîne : `o(&s)` et `gateway.New(s)`. Mesurée :

```
== l'etoile ajoutee : 1 fichier(s) [leaky/leaky.go], +3 -3 lignes, 0 erreur(s), 2 test(s) rouge(s)
   --- FAIL: TestTheSecondClientInheritsTheFirst (0.00s)
   --- FAIL: TestConstructionRaces (1.85s)
```

Les deux tests rouges sont ceux qui **fixaient le défaut** : ils deviennent
rouges quand le défaut disparaît, c'est leur rôle. C'est le même défaut que la
stratégie qui se souvient de la leçon 3.1 — un état partagé là où chaque
instance croyait avoir le sien — rencontré à la construction au lieu de
l'exécution.

> Les défauts sont une **valeur**, pas un endroit. Une fonction qui les rend
> (`func defaults() Settings`) ou une variable copiée par valeur ne peuvent
> pas fuir ; un pointeur partagé le peut, et le compilateur ne dit rien.

## 10. La campagne

Dix-huit modifications, jouées sous `go test -race -count=1 -timeout=60s ./...`.
Première passe :

```
reglages : http accepte                        tuee
reglages : budget atteint refuse               tuee
reglages : premiere tentative hors budget      tuee
Send : une tentative de moins                  tuee
Send : plus de garde                           tuee
Send : plus de delai par tentative             SURVIT
positionnel : retries ignore                   tuee
config : pas de defaut pour retries            tuee
options : ignorees                             tuee
builder : Retries sans effet                   tuee
ouvert : meme compte accepte                   tuee
scelle : montant nul accepte                   tuee
scelle : devise inconnue acceptee              tuee
scelle : Post accepte la valeur zero           tuee
scelle : IsZero ne regarde que le montant      SURVIT
fabrique : type inconnu en journal             tuee
fabrique : https ignore le statut              SURVIT
naif : WithRetries ne controle plus            tuee
15/18 tuees
```

Trois survivants, deux tests à écrire et une modification qui ne change rien.

**« Send : plus de délai par tentative ».** Aucun test ne faisait attendre
`Send`. Le partenaire qui ne répond jamais est pourtant l'incident le plus
courant d'un client réseau :

```go
// TestEachAttemptHasItsOwnDeadline: a partner that never answers costs
// one timeout per attempt, not forever.
func TestEachAttemptHasItsOwnDeadline(t *testing.T) {
    s := settings(hangs{}, 1)
    s.Timeout = 50 * time.Millisecond
    cl, err := New(s)
    if err != nil {
        t.Fatal(err)
    }
    done := make(chan struct{})
    var attempts int
    go func() {
        attempts, err = cl.Send(context.Background(), "{}")
        close(done)
    }()
    select {
    case <-done:
    case <-time.After(5 * time.Second):
        t.Fatal("Send still waiting after 5s")
    }
    if attempts != 2 || !errors.Is(err, context.DeadlineExceeded) {
        t.Fatalf("%d attempts, %v", attempts, err)
    }
}
```

Le test garde sa propre limite de cinq secondes : sans elle, la modification
ne serait tuée que par le `-timeout` de `go test`, une minute plus tard, avec
un message qui ne dit pas quel test attend.

**« Fabrique : https ignore le statut ».** Le transport HTTPS n'avait aucun
test, parce qu'il parle au réseau. `httptest` fournit le réseau :

```go
// TestHTTPSReadsTheStatus: a partner that answers 503 has not settled.
func TestHTTPSReadsTheStatus(t *testing.T) {
    status := http.StatusOK
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, _ *http.Request) {
        w.WriteHeader(status)
    }))
    defer srv.Close()
    h := HTTPS{Client: srv.Client()}
    if err := h.Post(context.Background(), srv.URL, "{}"); err != nil {
        t.Fatalf("200: %v", err)
    }
    status = http.StatusServiceUnavailable
    err := h.Post(context.Background(), srv.URL, "{}")
    if err == nil {
        t.Fatal("503 accepted")
    }
    t.Log(err)
}
```

**« Scellé : IsZero ne regarde que le montant ».** Elle survit et elle doit
survivre. `t.amount == 0` et `t == Transfer{}` ne diffèrent que pour un
virement de montant nul **qui ne serait pas la valeur zéro** — et `New`
refuse le montant nul. L'invariant rend les deux expressions équivalentes ;
aucun test ne peut les séparer sans construire un virement que la porte
interdit. C'est la seule modification de la campagne dont la survie confirme
le code au lieu de l'accuser. La version écrite reste la comparaison
complète : elle ne dépend pas d'une règle écrite ailleurs.

Deuxième passe :

```
17/18 tuees
```

## 11. La grille

| Si… | Alors |
|---|---|
| un objet a des règles | champs non exportés, **une** porte qui rend l'objet ou une erreur |
| la valeur zéro peut servir | la rendre utile, et le documenter |
| la valeur zéro ne peut pas servir | la **détecter** dans chaque méthode qui en dépend, avec une erreur nommée |
| deux ou trois valeurs, toutes requises | des paramètres positionnels, de types différents si possible |
| beaucoup de réglages, et le zéro de **chacun** peut vouloir dire « défaut » | une structure de configuration |
| des réglages dont le zéro a un sens métier, ou une API publique qui va grandir | des options fonctionnelles, requis en paramètres |
| une règle qui lie deux réglages | contrôlée **une fois**, après le dernier défaut, dans le constructeur |
| des réglages complétés en plusieurs étapes, ou un produit assemblé par morceaux | un builder |
| le type à construire dépend de la configuration | une fabrique, qui rend l'interface |

## 12. Les trois erreurs qui restent

### « Les options fonctionnelles, c'est toujours mieux »

Elles coûtent un type, une fonction par réglage, et une indirection à la
lecture : `byoption.WithTimeout` ne dit pas à quoi ressemble le client final,
une structure le dit. Pour un paquet interne avec quatre réglages dont le
zéro veut dire « défaut », la structure de configuration est plus courte et
plus lisible. La mesure qui fait basculer est celle de la section 5 : **un
zéro qui a un sens**.

### « Un constructeur garantit que l'objet est valide »

Pas en Go : la section 1 l'a mesuré. Il garantit que l'objet est valide **ou
zéro**. Un constructeur sans détection de la valeur zéro déplace le trou au
lieu de le boucher.

### « Chaque option valide sa valeur, donc l'objet est valide »

La section 6 : une option ne voit pas les autres. Elle peut refuser sa propre
valeur ; elle ne peut pas juger une relation. Le seul contrôle qui voit tout
est celui qui passe en dernier.

## 13. Le lien avec la production

| Ce que tu as déjà vu | Ce que c'est |
|---|---|
| un `nil pointer dereference` dans une méthode, sur un objet « jamais construit » | une valeur zéro qu'aucune méthode ne détecte (section 2) |
| « j'ai mis `Retries: 0` et il réessaie quand même » | une structure de configuration dont le zéro est déjà pris (section 5) |
| une configuration refusée ou acceptée selon l'ordre des drapeaux | un contrôle de relation fait dans une option (section 6) |
| un client qui hérite du délai d'un autre client, seulement en production | des défauts partagés par pointeur (section 9) |
| un ordre de virement payé deux fois après une coupure réseau | des reprises sur un partenaire non idempotent : le zéro de la section 5 |
| un client réseau bloqué pendant des minutes sur un partenaire muet | une tentative sans délai propre (la campagne) |

## 14. Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | En Go, tout type a une valeur zéro et tout paquet peut la déclarer. Un constructeur ne l'interdit pas : il réduit les objets invalides à **celui-là**. |
| ⚫ | Champs non exportés plus une porte : les autres paquets ne peuvent ni écrire un objet invalide, ni le modifier après contrôle. |
| ⚫ | La valeur zéro se rend utile ou se détecte. Elle ne panique pas trois appels plus loin. |
| ⚫ | Un réglage de plus : les paramètres positionnels cassent chaque appelant ; configuration, options et builder n'en touchent aucun. |
| ⚫ | Une structure de configuration ne sait pas dire « zéro » quand zéro veut déjà dire « défaut ». |
| ⚫ | Une option enregistre, le constructeur contrôle : une règle qui lie deux valeurs se vérifie quand toutes sont connues. |
| ⚫ | Le builder ne paie en Go que si la construction est étalée ou le produit assemblé par morceaux. |
| ⚫ | Une fabrique rend une interface, parce que la configuration choisit le type ; c'est l'endroit où un `switch` sur une chaîne a sa place. |
| ⚫ | Les défauts sont une valeur : copiés, jamais partagés par pointeur. |

## 15. Approfondissement

### D'où viennent les options fonctionnelles

Le motif a été décrit par Rob Pike en 2014 (« Self-referential functions and
the design of options ») et popularisé la même année par Dave Cheney
(« Functional options for friendly APIs »). La version de Pike rend aussi
l'ancienne valeur, pour pouvoir annuler une option ; presque personne ne s'en
sert, et la forme de cette leçon est celle qu'on rencontre.

### Les options en interface

gRPC déclare ses options comme une **interface** à méthode non exportée
(`DialOption` avec `apply(*dialOptions)`) plutôt que comme un type fonction.
C'est la leçon 3.1 appliquée aux options : une interface peut gagner une
méthode — une description, pour journaliser la configuration effective — sans
casser les appelants, et la méthode non exportée ferme la liste aussi bien
que le type `config` non exporté de cette leçon.

### `cmp.Or` et les défauts

La batterie écrit `cmp.Or(s.endpoint, endpoint)` : la première valeur non
nulle. C'est la forme la plus courte de « zéro veut dire défaut », et elle a
exactement le défaut de la section 5 : elle ne sait pas rendre zéro quand on
le demande.

### La fabrique abstraite

Une fabrique de **familles** d'objets — un transport, un journal et une
horloge qui vont ensemble, une famille pour la recette, une pour la
production. La leçon 3.6 la mesure parmi les patterns qui coûtent.

## 16. Le réflexe à installer

> **Devant un objet qui a des règles**
> Combien de chemins mènent à un objet de ce type sans passer par la règle ?
> S'il y en a plus d'un — la valeur zéro —, ferme-les.
>
> **Devant un réglage facultatif**
> Son zéro a-t-il un sens métier ? Si oui, une structure de configuration
> mentira tôt ou tard.
>
> **Devant une règle qui lie deux réglages**
> Est-elle contrôlée après le dernier défaut, une seule fois ?

Et le geste d'une minute :

> **Avant de publier un type, écris `var x T` dans un test et appelle chacune
> de ses méthodes.** Celles qui paniquent sont celles qu'un appelant
> rencontrera un jour.
