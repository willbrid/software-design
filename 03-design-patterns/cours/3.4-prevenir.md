# Leçon 3.4 — Prévenir sans coupler : observateur, bus en mémoire, et la concurrence

## L'essentiel en deux minutes

**Le problème, en une phrase.** Quand quelque chose arrive — un virement est
passé —, plusieurs parties du système doivent réagir : envoyer un SMS,
écrire une ligne d'audit, créditer des points de fidélité. Si le code du
virement appelle chacune par son nom, il doit toutes les connaître, et chaque
nouvelle réaction l'oblige à changer.

**L'image.** Un bébé vient de naître. Tu peux appeler chaque membre de la
famille un par un : tu sais que chacun a reçu la nouvelle, mais il faut
connaître tout le monde, et tu restes au téléphone jusqu'au dernier. Ou tu
postes un message dans le **groupe de la famille** : tu ne sais pas qui le
lira ni quand, mais tu as fini tout de suite, et un cousin qui rejoint le
groupe demain recevra les nouvelles suivantes sans que tu changes quoi que ce
soit. Le groupe, c'est un **observateur** : celui qui annonce ne connaît pas
ceux qui écoutent.

**Le code, en quinze lignes.**

```go
// Publish runs every handler, even after one fails, and returns their
// errors joined. A handler that panics is reported as an error: it stops
// neither the others nor the publisher.
func (b *Sync[E]) Publish(ctx context.Context, e E) error {
    b.mu.Lock()
    hs := slices.Clone(b.handlers)
    b.mu.Unlock()
    var errs []error
    for _, x := range hs {
        if err := call(ctx, x.h, e); err != nil {
            errs = append(errs, err)
        }
    }
    return errors.Join(errs...)
}
```

Le service de virement appelle `Publish` ; le SMS, l'audit et la fidélité se
sont abonnés avec `Subscribe`. Le service ne connaît que l'**événement**
(`TransferCompleted`), jamais les réactions.

**Les règles à retenir.**

1. Un événement est un **fait accompli** : « le virement est passé ». Une
   réaction peut échouer, elle ne peut pas annuler le fait. Ce qui doit
   pouvoir dire **non** (un contrôle anti-fraude) n'est pas un abonné : c'est
   un appel direct, **avant**.
2. **Synchrone** d'abord : chaque réaction s'exécute dans l'appel, dans
   l'ordre. C'est simple, mais la réaction la plus lente fixe la durée du
   virement.
3. `go handler(e)` n'est pas un bus asynchrone : on perd l'ordre, on perd
   les événements à l'arrêt, une panique tue le programme, et la réaction
   tourne en concurrence avec elle-même.
4. Un bus asynchrone honnête donne à chaque abonné **une file et une
   goroutine**, décide quoi faire quand la file est pleine (attendre ou
   jeter, et compter), et sait **se fermer** en vidant les files.
5. Un bus en mémoire **oublie tout** si le processus meurt. Quand une
   réaction ne doit jamais être perdue, l'événement doit être écrit en base
   avec le virement : c'est l'*outbox*, au niveau 8.

La suite mesure tout cela sur un vrai module.

---

La leçon 3.3 a ajouté des comportements **autour** d'un appel. Celle-ci
s'occupe de ce qui doit se passer **après** : le problème qui revient est

> **Un composant fait son travail. D'autres doivent le savoir et réagir.
> Comment le leur dire sans qu'il dépende d'eux, et sans que leur lenteur,
> leurs pannes ou leurs bogues deviennent les siens ?**

La banque a un grand livre en mémoire. `Move` débite, crédite, et rend le
**fait** qui vient de se produire :

```go
// TransferCompleted says that a transfer has been written to the ledger.
// It is a fact: by the time anyone reads it, the money has moved.
type TransferCompleted struct {
    ID     string
    Seq    int // position in the ledger, increasing by one per transfer
    From   string
    To     string
    Amount int64 // XAF, which has no minor unit
    At     time.Time
}
```

Trois réactions existent déjà : un SMS au destinataire, une ligne d'audit,
des points de fidélité pour l'émetteur (un point par tranche complète de
1 000 FCFA). Chacune est une méthode `Handle(ctx, e) error`.

Tout ce qui suit est mesuré sur un module vert sous `gofmt -l`,
`go vet ./...` et `go test -race -count=1 ./...`. L'opérateur SMS est un
faux qui peut attendre (`Delay`) ou échouer (`Fail`).

## 1. Les deux formes de départ

### Le service qui appelle tout le monde

```go
// Service knows every reaction to a transfer by name.
type Service struct {
    Ledger  *ledger.Ledger
    SMS     react.SMS
    Audit   *react.Audit
    Loyalty *react.Loyalty
}
```

```go
// Transfer moves the money, then sends the SMS, records the audit line and
// credits the points, in that order.
func (s *Service) Transfer(ctx context.Context, id, from, to string, amount int64) error {
    e, err := s.Ledger.Move(id, from, to, amount)
    if err != nil {
        return err
    }
    if err := s.SMS.Handle(ctx, e); err != nil {
        return fmt.Errorf("transfer %s: %w", id, err)
    }
    if err := s.Audit.Handle(ctx, e); err != nil {
        return fmt.Errorf("transfer %s: %w", id, err)
    }
    if err := s.Loyalty.Handle(ctx, e); err != nil {
        return fmt.Errorf("transfer %s: %w", id, err)
    }
    return nil
}
```

C'est lisible : en une page, on voit tout ce qui se passe après un virement.
Mais regarde les dépendances : le paquet `direct` importe `react`, donc il
connaît le SMS, l'audit et la fidélité **par leur nom**.

### Le service qui annonce

```go
// Publisher announces a completed transfer.
type Publisher interface {
    Publish(ctx context.Context, e event.TransferCompleted) error
}
```

```go
// Transfer moves the money, then publishes TransferCompleted. Once the
// money has moved, the transfer has succeeded: a reaction that fails is
// logged, it does not turn the answer into an error.
func (s *Service) Transfer(ctx context.Context, id, from, to string, amount int64) error {
    e, err := s.Ledger.Move(id, from, to, amount)
    if err != nil {
        return err
    }
    if err := s.Events.Publish(ctx, e); err != nil {
        s.Log.Warn("transfer done, a reaction failed", "id", id, "err", err)
    }
    return nil
}
```

Le service ne connaît qu'une interface d'une méthode et le type de
l'événement. Qui écoute ? Ça se décide **ailleurs**, à l'endroit où l'on
assemble le programme :

```go
    events := &bus.Async[event.TransferCompleted]{Size: 1024, OnError: func(err error) {
        log.Warn("reaction failed", "err", err)
    }}
    subscribe(events, react.SMS{Sender: sender, Phones: map[string]string{"ben": "+237600000002"}}.Handle)
    subscribe(events, audit.Handle)
    subscribe(events, loyalty.Handle)
```

C'est le seul fichier qui connaît les deux côtés. On retrouve l'idée de la
leçon 2.5 (inversion des dépendances) : le métier ne dépend pas des détails,
c'est l'assemblage qui les branche.

## 2. Première mesure : une réaction de plus

Le support veut un tableau de bord : le nombre de virements et leur volume.
On écrit `react.Stats` (32 lignes, identiques pour les deux formes), puis on
le branche. La mesure, sur deux copies du module :

```text

vet+tests exit 1
  --- FAIL: TestTransferCallsEveryReaction (0.00s)

  FAIL  example/bank34/direct   0.004s
  FAIL

```

Ce qu'il faut lire :

- **Forme directe** : il faut ouvrir le service (4 lignes : un champ et un
  appel). Et si l'on oublie son test, le test **panique** : le champ `Stats`
  vaut `nil`, et `Transfer` l'appelle. Chaque nouvelle réaction touche le
  code et les tests de quelqu'un qui n'a rien demandé.
- **Forme observée** : une ligne dans l'assemblage. Le service, ses tests et
  les autres réactions ne bougent pas.
- **Les imports** disent la même chose en une ligne : `direct` dépend de
  `react` ; `observed` ne dépend que de `event`.

Il faut aussi dire ce que la forme observée **coûte** : pour savoir ce qui se
passe après un virement, on ne lit plus une fonction, on cherche les
`Subscribe`. Martin Fowler le formule ainsi à propos des notifications
d'événements : « *it can be hard to see such a flow as it's not explicit in
any program text* » — le flux n'est écrit nulle part dans le code. C'est
supportable tant que les abonnements sont tous au même endroit, dans
l'assemblage, et que chaque réaction est **indépendante** des autres.

### Le défaut caché de la forme directe

Le test suivant ne décrit pas un comportement voulu : il **épingle** un
défaut, pour que personne ne le prenne pour une règle.

```go
// The flaw of this form, pinned so that nobody mistakes it for a feature:
// the money has moved, yet the caller is told the transfer failed, and the
// reactions after the SMS never run.
func TestAnSMSFailureMakesADoneTransferLookFailed(t *testing.T) {
    down := errors.New("operator down")
    s := newService(&fake.Sender{Fail: down})
    err := s.Transfer(context.Background(), "t1", "awa", "ben", 25000)
    if !errors.Is(err, down) {
        t.Fatalf("err = %v, want %v", err, down)
    }
    if s.Ledger.Balance("ben") != 25000 {
        t.Fatalf("ben = %d, want 25000: the money moved anyway", s.Ledger.Balance("ben"))
    }
    if len(s.Audit.Lines()) != 0 || s.Loyalty.Of("awa") != 0 {
        t.Fatalf("audit %d, points %d: the later reactions were skipped", len(s.Audit.Lines()), s.Loyalty.Of("awa"))
    }
}
```

L'argent est parti, mais l'appelant reçoit une erreur. Une application
mobile qui voit « échec » propose de réessayer : le client envoie le virement
**deux fois**. Et l'audit n'a rien écrit, parce que la réaction suivante n'a
jamais été appelée. La panne d'un opérateur SMS est devenue un faux échec de
virement et un trou dans l'audit.

## 3. Un événement est un fait : qui a le droit de dire non ?

La forme observée tranche la question dans sa documentation : une fois
l'argent déplacé, **le virement a réussi**. Le test le fixe :

```go
func TestAFailedReactionIsLoggedAndTheTransferStillSucceeds(t *testing.T) {
    w := newWorld(&fake.Sender{Fail: errors.New("operator down")})
    if err := w.svc.Transfer(context.Background(), "t1", "awa", "ben", 25000); err != nil {
        t.Fatalf("err = %v, want nil: the money has moved", err)
    }
    if len(w.audit.Lines()) != 1 || w.loyalty.Of("awa") != 25 {
        t.Fatal("the reactions after the failed one did not run")
    }
    if !strings.Contains(w.log.String(), "operator down") {
        t.Fatalf("log = %q, want the failure", w.log.String())
    }
}
```

Cela demande une décision claire sur chaque réaction :

| Si la réaction échoue… | …le virement doit-il échouer ? | Alors c'est |
|---|---|---|
| contrôle anti-fraude | **oui**, il doit pouvoir l'empêcher | un appel direct, **avant** `Move` |
| SMS, audit, fidélité, statistiques | non, l'argent a bougé | un abonné, **après** |

Un abonné qui voudrait « annuler » un virement arrive trop tard : le fait
est écrit. S'il faut vraiment défaire quelque chose après coup, c'est une
**nouvelle** opération (un virement inverse), pas une erreur rendue à
l'appelant ; c'est la logique des sagas, au niveau 8.

### Le bus synchrone

La version la plus simple appelle les abonnés un par un, dans la goroutine
de celui qui publie :

```go
// Sync calls every handler in the publisher's goroutine, one after the
// other, in the order they subscribed. Publish returns once all have run.
type Sync[E any] struct {
    mu       sync.Mutex
    lastID   int
    handlers []entry[E]
}
```

```go
// call runs h and turns its panic into an error.
func call[E any](ctx context.Context, h Handler[E], e E) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("%w: %v", ErrPanic, r)
        }
    }()
    return h(ctx, e)
}
```

Trois détails font la différence entre un bus qui marche et un bus qui
marche **le jour de la démo** :

- **Toutes** les réactions sont appelées, même après un échec ; les erreurs
  sont réunies par `errors.Join`, qui « *returns an error that wraps the
  given errors* » : `errors.Is` les retrouve toutes.
- Une **panique** devient une erreur. Mesuré avec une réaction qui écrit
  dans une `map` nil :

  ```text
  publish: handler panicked: assignment to entry in nil map
  still serving
  ```

- Le verrou est **relâché** avant d'appeler les réactions, et `Publish`
  travaille sur une **copie** de la liste. Sans cela, une réaction qui
  s'abonne ou se désabonne pendant une publication bloquerait le programme
  (le verrou n'est pas réentrant), ou modifierait la liste sous les pieds de
  la boucle. Le test qui le fixe :

```go
// Publish works on a copy of the handlers: an unsubscribe made while an
// event is being published takes effect from the next event.
func TestSyncAnUnsubscribeDuringPublishTakesEffectOnTheNextEvent(t *testing.T) {
    var b bus.Sync[int]
    var trail []string
    var stopB func()
    b.Subscribe(func(context.Context, int) error { stopB(); return nil })
    stopB = b.Subscribe(recorder("B", &trail))
    b.Subscribe(recorder("C", &trail))
    if err := b.Publish(ctx, 1); err != nil {
        t.Fatal(err)
    }
    _ = b.Publish(ctx, 2)
    if got := strings.Join(trail, ">"); got != "B>C>C" {
        t.Fatalf("trail = %s, want B>C>C", got)
    }
}
```

## 4. Deuxième mesure : la réaction lente

L'opérateur SMS met 150 ms à répondre. Vingt virements à la suite, avec le
bus synchrone puis avec le bus asynchrone de la section 6 (programme
`cmd/latency`) :

```text
sync : 150.44ms per transfer; SMS sent when the transfers return: 20/20, after closing the bus: 20/20 (Close took 0s)
async: 2µs per transfer; SMS sent when the transfers return: 0/20, after closing the bus: 20/20 (Close took 3.01s)
```

En synchrone, **chaque virement attend le SMS** : 150 ms au lieu de quelques
microsecondes. Le client paie la lenteur d'une réaction dont il ne voit même
pas le résultat. En asynchrone, le virement rend la main en 2 µs.

Mais lis la fin de la deuxième ligne : quand les virements rendent la main,
**aucun** SMS n'est parti, et `Close` a attendu **3 secondes** (20 × 150 ms)
pour tous les envoyer. Le travail n'a pas disparu : il a été **déplacé**. Il
faudra donc répondre à trois questions que la version synchrone n'avait
pas : dans quel ordre, avec combien de mémoire, et que devient le travail en
attente si le programme s'arrête.

## 5. La première idée asynchrone : une goroutine par réaction

```go
// Publish starts the handlers and does not wait for them.
func (b *GoEach[E]) Publish(ctx context.Context, e E) error {
    b.mu.Lock()
    hs := slices.Clone(b.handlers)
    b.mu.Unlock()
    for _, h := range hs {
        go h(ctx, e)
    }
    return nil
}
```

C'est la version qu'on écrit en cinq minutes. Le programme `cmd/naive`
publie 1 000 événements numérotés à un abonné qui travaille 1 ms par
événement, et compte :

```text
GoEach handled when publishing returns:  282/1000, after waiting: 1000/1000, out of order: 418, peak goroutines: 790
Async  handled when publishing returns:    0/1000, after waiting: 1000/1000, out of order:   0, peak goroutines: 2
```

Sur la ligne `GoEach`, quatre défauts, tous mesurés :

1. **L'ordre est perdu** : 418 fois, un événement a été traité avant un
   événement publié plus tôt. Pour un relevé de compte ou des notifications
   « solde : … », c'est un client qui voit son solde reculer.
2. **Les événements en vol meurent avec le programme** : quand la boucle de
   publication se termine, seuls 282 événements sur 1 000 sont traités. Si
   `main` s'arrête là, 718 réactions n'auront jamais lieu, et rien ne le
   signale.
3. **Les goroutines s'accumulent** : jusqu'à 790 en même temps, une par
   événement pas encore traité. Avec un SMS à 150 ms et un pic de trafic,
   c'est autant de connexions ouvertes vers l'opérateur.
4. **Une panique arrête tout le programme**. Dans une goroutine lancée par
   `go`, personne n'est là pour la rattraper ; la spécification du langage
   dit qu'à ce stade « *the program is terminated* ». La même réaction
   qu'à la section 3 :

   ```text
   panic: assignment to entry in nil map
   exit status 2
   ```

Et un cinquième, plus sournois. Le programme abonne une deuxième réaction
écrite « comme si elle tournait seule » : un compteur `count++`. Avec le bus
synchrone, c'est correct, car une publication appelle les réactions l'une
après l'autre. Avec `GoEach`, la **même** réaction tourne dans des centaines
de goroutines à la fois. Le détecteur de courses (`go run -race`) le voit :

```text
WARNING: DATA RACE
Read at 0x00c000018138 by goroutine 17:
  main.main.func1()
      cmd/naive/main.go:64 +0x2e

Previous write at 0x00c000018138 by goroutine 13:
  main.main.func1()
      cmd/naive/main.go:64 +0x44
...
Found 2 data race(s)
exit status 66
```

Le modèle mémoire de Go est sans ambiguïté : « *Programs that modify data
being simultaneously accessed by multiple goroutines must serialize such
access.* » Passer en asynchrone **change le contrat** de chaque réaction :
elle doit maintenant être sûre en concurrence. Et le détecteur « *only finds
races that happen at runtime* » : il ne voit que les courses que les tests
font vraiment se produire.

## 6. Une file par abonné

La réponse classique : chaque abonné reçoit **sa propre file** (un canal
bufferisé) et **sa propre goroutine**, qui traite les événements un par un,
dans l'ordre.

```go
// Async gives each subscriber its own queue and its own goroutine. A
// subscriber sees the events one at a time, in the order they were
// published, and a slow subscriber slows nobody until its queue is full.
type Async[E any] struct {
    Size    int // queue length per subscriber
    Policy  Policy
    OnError func(error) // called from the subscriber's goroutine; may be nil

    mu      sync.RWMutex
    subs    []*queue[E]
    closed  bool
    wg      sync.WaitGroup
    dropped atomic.Int64
}
```

```go
// Subscribe starts the goroutine of h and returns the function that stops
// it. The goroutine handles what is already queued before it ends.
func (b *Async[E]) Subscribe(h Handler[E]) (unsubscribe func(), err error) {
    b.mu.Lock()
    defer b.mu.Unlock()
    if b.closed {
        return nil, ErrClosed
    }
    q := &queue[E]{ch: make(chan envelope[E], b.Size)}
    b.subs = append(b.subs, q)
    b.wg.Go(func() { b.run(q, h) })
    return func() { b.remove(q) }, nil
}
```

```go
func (b *Async[E]) run(q *queue[E], h Handler[E]) {
    for env := range q.ch {
        if err := call(env.ctx, h, env.e); err != nil && b.OnError != nil {
            b.OnError(err)
        }
    }
}
```

Lis ce que cela garantit, ligne `Async` de la mesure précédente : **0**
inversion, **1 000/1 000** traités après `Close`, et **2** goroutines au plus
fort (le programme et l'abonné), quel que soit le nombre d'événements.

- **L'ordre** vient de la file : une seule goroutine lit le canal d'un
  abonné, donc il voit les événements dans l'ordre où ils ont été publiés.
- **La sécurité de la réaction** aussi : une réaction n'est jamais appelée
  en même temps qu'elle-même. Le compteur `count++` de la section 5 serait
  correct ici, tant qu'une seule goroutine le touche.
- **Une panique** est rattrapée par `call`, comme en synchrone, et remise à
  `OnError`. C'est indispensable : `sync.WaitGroup.Go`, qui lance la
  goroutine, précise que « *The function f must not panic* ».

C'est la maxime d'*Effective Go* appliquée : « *Do not communicate by
sharing memory; instead, share memory by communicating* ». Chaque événement
passe par un canal, et une seule goroutine le traite.

### Fermer, et vider

```go
// Close refuses new events, lets every subscriber finish its queue, and
// returns when all have.
func (b *Async[E]) Close() {
    b.mu.Lock()
    if !b.closed {
        b.closed = true
        for _, q := range b.subs {
            close(q.ch)
        }
        b.subs = nil
    }
    b.mu.Unlock()
    b.wg.Wait()
}
```

`Close` est ce qui sépare un bus jouet d'un bus utilisable : il refuse les
nouveaux événements, ferme chaque file, et **attend** que chaque abonné ait
fini la sienne. `range q.ch` dans `run` s'arrête quand le canal est fermé
**et vide** : rien n'est jeté. Le programme d'assemblage `cmd/bank`
l'appelle juste avant de sortir.

## 7. Troisième mesure : publier plus vite qu'on ne traite

Une file a une taille. Que fait `Publish` quand elle est pleine ? Il n'y a
que deux réponses honnêtes, et le bus oblige à en choisir une :

```go
// Publish queues e for every subscriber. The handlers get a context that
// keeps the values of ctx but not its cancellation: the request that
// published the event may be over long before the event is handled.
func (b *Async[E]) Publish(ctx context.Context, e E) error {
    b.mu.RLock()
    defer b.mu.RUnlock()
    if b.closed {
        return ErrClosed
    }
    env := envelope[E]{ctx: context.WithoutCancel(ctx), e: e}
    for _, q := range b.subs {
        if b.Policy == Drop {
            select {
            case q.ch <- env:
            default:
                b.dropped.Add(1)
            }
            continue
        }
        select {
        case q.ch <- env:
        case <-ctx.Done():
            return ctx.Err()
        }
    }
    return nil
}
```

Mesure avec une file de 16 et un abonné qui traite environ 1 000 événements
par seconde, face à 500 événements publiés d'un coup (`cmd/pressure`) :

```text
Block publishing 500 events took    554ms; handled 500, dropped   0
Drop  publishing 500 events took       0s; handled  17, dropped 483
```

- **`Block`** : rien n'est perdu, mais le publieur **ralentit** au rythme du
  plus lent des abonnés (554 ms). C'est la contre-pression : la lenteur
  remonte jusqu'à l'appelant, comme en synchrone, mais seulement quand la
  file déborde. Le `ctx` du publieur borne cette attente.
- **`Drop`** : le publieur ne ralentit jamais, mais 483 événements sur 500
  n'ont pas été traités. C'est acceptable pour des statistiques
  approximatives, pas pour l'audit.

Le choix dépend de **la réaction**, pas du bus. La bibliothèque standard a
fait le choix `Drop` pour les signaux : la documentation de
`signal.Notify` dit « *Package signal will not block sending to c: the
caller must ensure that c has sufficient buffer space* ». Elle l'écrit en
toutes lettres ; ton bus doit faire pareil, et **compter** ce qu'il jette
(`Dropped`), sinon la perte est invisible.

Une file **sans** limite n'est pas une troisième réponse : c'est `Block`
repoussé jusqu'à ce que la mémoire du processus soit pleine.

## 8. Le contexte de la requête ne doit pas suivre l'événement

Le `ctx` passé à `Publish` est celui de la requête HTTP qui a fait le
virement. Il porte des valeurs utiles (l'identifiant de trace), et une
**annulation** : il est annulé dès que la réponse est partie. Or en
asynchrone, la réaction tourne **après** la réponse. Si on lui passait ce
`ctx` tel quel, le SMS partirait avec un contexte déjà annulé, et le faux
opérateur rendrait `context canceled`.

D'où la ligne `context.WithoutCancel(ctx)` dans `Publish`. La documentation
de `context` : `WithoutCancel` « *returns a derived context that points to
the parent context and is not canceled when parent is canceled* ». Les
valeurs restent, l'annulation non. Le test :

```go
func TestAsyncHandlersKeepContextValuesButNotCancellation(t *testing.T) {
    b := &bus.Async[int]{Size: 1}
    gate := make(chan struct{})
    type seen struct {
        v   any
        err error
    }
    out := make(chan seen, 1)
    _, _ = b.Subscribe(func(ctx context.Context, _ int) error {
        <-gate
        out <- seen{ctx.Value(key{}), ctx.Err()}
        return nil
    })
    req, cancel := context.WithCancel(context.WithValue(ctx, key{}, "trace-42"))
    _ = b.Publish(req, 1)
    cancel() // the request is over before the handler runs
    close(gate)
    b.Close()
    if s := <-out; s.v != "trace-42" || s.err != nil {
        t.Fatalf("handler saw value %v and err %v; want trace-42 and nil", s.v, s.err)
    }
}
```

Une réaction asynchrone qui doit être bornée dans le temps se donne
**son propre** délai (`context.WithTimeout` à l'intérieur de `Handle`), qui
ne dépend pas de la durée de la requête d'origine.

## 9. Se désabonner, ou fuir

`Subscribe` rend une fonction. Si personne ne l'appelle, l'abonné vit pour
toujours, avec sa goroutine. Le cas typique : un gestionnaire HTTP qui
s'abonne pour attendre « son » événement, et qui oublie de se désabonner.
Mesure sur 1 000 requêtes (`cmd/leak`) :

```text
forget=true  goroutines before: 1, after 1000 requests: 1001
forget=false goroutines before: 1, after 1000 requests: 1
```

Mille goroutines de plus, une par requête, qui ne finiront jamais. Le
billet de l'équipe Go sur les pipelines le dit en une phrase :
« *Goroutines are not garbage collected; they must exit on their own.* »
La règle d'usage est celle de `context.WithCancel` : ce qui est ouvert dans
une fonction est fermé dans la même, avec `defer stop()`.

## 10. Ce que la mémoire ne garde pas

Dernière mesure, la plus importante. Cinquante virements passent par le bus
asynchrone, avec un SMS à 20 ms, puis le processus s'arrête **sans**
`Close`, comme lors d'un plantage, d'un `kill -9` ou d'un conteneur tué par
manque de mémoire (`cmd/crash`) :

```text
ledger: ben received 50000 XAF in 50 transfers; SMS sent before the stop: 4/50
```

Le grand livre dit que l'argent est parti cinquante fois. Quarante-six
destinataires ne recevront jamais leur SMS, et **aucune trace** ne le dira :
les événements étaient dans un canal, en mémoire, et la mémoire est partie
avec le processus. `Close` protège contre un arrêt **propre** ; rien dans un
bus en mémoire ne protège contre un arrêt **brutal**.

Pour un SMS de courtoisie, c'est peut-être acceptable. Pour l'audit, ou pour
la notification d'un marchand qui attend son paiement, non. La solution
connue est l'*outbox transactionnelle* : écrire l'événement **dans la même
transaction** que le virement, puis le publier depuis la base. Le catalogue
de Chris Richardson pose le problème ainsi : « *If the database transaction
commits then the messages must be sent. Conversely, if the database rolls
back, the messages must not be sent* ». Ce sera le cœur du niveau 8 ;
retiens dès maintenant la question à poser : **si le processus meurt entre
le virement et la réaction, est-ce grave ?**

## 11. La campagne

Une réaction qui « marche » ne prouve rien sur un bus : ses défauts
apparaissent sous la concurrence, à l'arrêt ou à la panne. Les tests sont-ils
assez précis pour voir chacun d'eux ? On introduit une erreur à la fois, et
on relance `go vet` et `go test -race` :

```text
Sync s'arrête à la première erreur           tuee
plus de recover                              tuee
verrou tenu pendant les handlers             tuee
pas de copie des handlers                    tuee
désabonnement inversé                        tuee
contexte de la requête transmis              tuee
abandon non compté                           tuee
Block ignore le contexte                     tuee
Close n'attend pas                           tuee
Close ne ferme pas les files                 tuee
file sans recover                            tuee
désabonnement sans fermer la file            tuee
Publish accepté après Close                  tuee
Subscribe accepté après Close                tuee
taille de file ignorée                       tuee
Drop retombe dans Block                      tuee
l'échec d'une réaction fait échouer le virement tuee
annonce même un virement refusé              tuee
numéro de séquence figé                      tuee
points au destinataire                       tuee
SMS à l'émetteur                             tuee
21/21 tuees
```

Vingt et une erreurs, toutes vues. Une précision d'honnêteté : au premier
passage, la mutation « annonce même un virement refusé » ne compilait pas
(une variable `err` devenue inutilisée) ; elle a été réécrite avec
`_ = err` pour qu'elle compile, puis rejouée seule.

Les tests qui tuent les mutations les plus sournoises sont ceux qui
**provoquent** la situation au lieu d'espérer la rencontrer :

- « pas de copie des handlers » n'est vue que par le test qui désabonne
  pendant une publication (section 3). Sans copie, `slices.DeleteFunc`
  décale les éléments **dans le même tableau** et met à zéro la fin ; la
  boucle en cours appelle alors un handler nil, ce qui panique.
- « Close n'attend pas » et « Close ne ferme pas les files » sont vues par
  le test qui publie 1 000 événements puis vérifie, juste après `Close`,
  qu'ils sont **tous** là.
- « Block ignore le contexte » et « taille de file ignorée » sont vues par
  des tests qui **remplissent** la file exprès, avec un abonné bloqué sur un
  canal que le test ouvre quand il le décide : aucun `time.Sleep` n'y
  décide de l'ordre.

## 12. La grille

| | Appels directs | Bus synchrone | `go` par réaction | File par abonné |
|---|---|---|---|---|
| le service connaît les réactions | **oui**, par leur nom | non | non | non |
| ajouter une réaction | le service et ses tests | une ligne d'assemblage | idem | idem |
| on lit le flux dans le code | **oui** | dans l'assemblage | idem | idem |
| la réaction lente ralentit le virement | oui | oui | non | non, sauf file pleine (`Block`) |
| ordre des événements | oui | oui | **non** | oui, par abonné |
| une panique de réaction | erreur ou plantage | erreur | **plantage** | erreur, via `OnError` |
| la réaction doit être sûre en concurrence | non | non | **oui, avec elle-même** | non |
| événements perdus à l'arrêt propre | aucun | aucun | **oui** | aucun, avec `Close` |
| événements perdus au plantage | aucun | aucun | oui | **oui** : il faut une outbox |

Lecture : le bus synchrone est le bon point de départ ; il découple le code
sans rien changer à l'exécution. On ne passe à la file par abonné que
lorsqu'une réaction lente coûte vraiment quelque chose au client, et on
n'écrit jamais `go handler(e)`.

## 13. Les trois erreurs qui restent

### « Avec un bus, tout est découplé »

Le code est découplé, pas le **comportement**. Si la fidélité lit une donnée
que l'audit vient d'écrire, l'ordre des abonnements est devenu une règle
métier, et elle n'est écrite nulle part. Un abonné ne doit dépendre ni de
l'ordre des autres, ni de leur succès. Quand une réaction a besoin du
résultat d'une autre, c'est un enchaînement : on l'écrit comme un appel, ou
comme un deuxième événement publié par la première réaction.

### « Asynchrone, c'est plus rapide »

C'est plus rapide **pour celui qui publie**. Le travail total est le même
(la mesure de la section 4 : 3 secondes de SMS dans les deux cas), et
s'y ajoutent une file, une goroutine, une politique de débordement, une
fermeture et une perte possible au plantage. On paie tout cela pour une
seule chose : que la lenteur d'une réaction ne soit plus celle du virement.

### « Je publie l'événement, puis j'écris en base »

Si l'on publie **avant** que le fait soit vrai, un abonné peut envoyer un
SMS pour un virement qui finira refusé ou annulé par la base. Un événement
se publie **après** le fait, au passé : `TransferCompleted`, pas
`TransferRequested`. Le test `TestARefusedTransferIsNotAnnounced` fixe la
version en mémoire de cette règle ; la version avec base de données, c'est
encore l'outbox.

## 14. Le lien avec la production

Tu as déjà vu ces pannes, sous d'autres noms :

- « La latence de l'API de paiement a doublé » : quelqu'un a ajouté une
  réaction synchrone qui appelle un service externe.
- « Les goroutines montent sans redescendre » sur le tableau de bord : un
  abonnement par requête jamais fermé (section 9), ou un `go handler(e)` face
  à un pic de trafic (section 5).
- « Après le déploiement, des clients n'ont pas reçu leur SMS » : le
  processus a été arrêté sans `Close`, ou tué pendant que la file était
  pleine (section 10). Un `SIGTERM` doit déclencher `Close` avant la sortie.
- « Les notifications arrivent dans le désordre » : un bus sans file par
  abonné.

Les métriques à exposer pour un bus en mémoire tiennent en quatre lignes :
la longueur de chaque file, le nombre d'événements jetés (`Dropped`), le
nombre d'erreurs remontées par `OnError`, et la durée de `Close` à l'arrêt.

## 15. Ce qu'il faut retenir

1. L'observateur sert quand **celui qui sait** ne doit pas dépendre de
   **ceux qui réagissent**. Le gain se mesure : ajouter une réaction ne
   touche plus le service.
2. Un événement est un fait au passé ; une réaction ne peut pas l'annuler.
   Ce qui doit pouvoir refuser passe **avant**, par un appel direct.
3. Commence synchrone. Le bus synchrone découple le code sans ajouter un
   seul problème de concurrence.
4. Passer en asynchrone, c'est accepter un nouveau contrat : ordre, mémoire,
   débordement, fermeture, contexte. Une file et une goroutine par abonné y
   répondent ; `go handler(e)` n'y répond pas.
5. Ce qui est en mémoire meurt avec le processus. Pose toujours la
   question : « si le processus s'arrête maintenant, qu'est-ce qu'on perd ? »

## 16. Approfondissement

### L'observateur chez le *Gang of Four*

Dans *Design Patterns*, le sujet garde une liste d'observateurs et les
prévient d'un changement d'état. Le livre distingue le modèle *push* (le
sujet envoie le détail du changement) et le modèle *pull* (il prévient
seulement, et l'observateur relit l'état). Ici, l'événement porte tout ce
dont la réaction a besoin : c'est du *push*, et c'est ce qui permet à la
réaction de tourner plus tard, sans relire un grand livre qui a peut-être
changé entre-temps.

### Événement de domaine

`TransferCompleted` n'est pas un détail technique : c'est un **mot du
métier**, au passé, que le support et la conformité comprennent. Le DDD
l'appelle un *événement de domaine*, et l'on y reviendra au niveau 7. Un bon
test de nommage : un expert métier dirait-il « quand un virement est passé,
alors… » ?

### Canaux ou fonctions ?

On aurait pu exposer aux abonnés un canal (`Subscribe() <-chan E`) plutôt
que d'accepter une fonction. C'est idiomatique, mais chaque abonné doit
alors écrire sa boucle, gérer la fermeture, et un abonné qui ne lit plus
bloque ou fait perdre des événements sans que le bus le sache. Accepter une
fonction garde la boucle, la fermeture et la récupération des paniques en un
seul endroit, testé une fois.

## 17. Le réflexe à installer

Avant d'ajouter un appel « après » dans une fonction métier, pose quatre
questions :

1. Si cette réaction échoue, l'opération doit-elle échouer ? Si oui, ce n'est
   pas un abonné.
2. Combien de temps prend-elle, et le client doit-il attendre ? Si non, et
   si c'est long, asynchrone — avec une file par abonné.
3. Quand sa file est pleine : attendre ou jeter ? Et qui regarde le compteur
   des événements jetés ?
4. Si le processus meurt maintenant, qu'est-ce qu'on perd ? Si la réponse
   est « quelque chose d'important », il faut une outbox, pas un bus en
   mémoire.
