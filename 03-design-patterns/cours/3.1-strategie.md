# Leçon 3.1 — Faire varier une règle : la stratégie, et quand une fonction suffit

Le niveau 2 a appris à mesurer ce qu'un principe rapporte et ce qu'il coûte.
Le niveau 3 applique la même discipline aux **patterns de conception**, et il
commence par renverser l'ordre habituel :

> On n'apprend pas un pattern pour le placer. On part d'un **problème qui
> revient**, on écrit les deux ou trois façons de le résoudre, et on mesure
> ce que chacune coûte le jour où le problème change. Le nom du pattern
> arrive à la fin, comme une étiquette sur une solution qu'on a déjà jugée.

Un pattern, au sens du livre de 1994, c'est exactement ça : un nom donné à une
solution récurrente **à une contrainte récurrente**. Sans la contrainte, le
nom ne sert à rien — c'est la leçon 2.6 appliquée au catalogue.

Et Go change le catalogue. Le livre a été écrit pour C++ et Smalltalk, deux
langages où une fonction n'est pas une valeur qu'on passe facilement. En Go,
elle l'est. Plusieurs patterns du livre — Stratégie, Commande, Patron de
méthode — se réduisent alors **parfois** à une fonction en paramètre. Cette
leçon mesure le « parfois ».

Le problème de la leçon :

> **La même opération, plusieurs règles, choisies à l'exécution.** Les frais
> d'un virement dépendent du segment du client — standard, premium,
> association — et le segment n'est connu qu'au moment du virement.

C'est le problème que le pattern **Stratégie** résout. En Go, il a trois
formes, et une quatrième qui combine les deux meilleures. Tout ce qui suit
est mesuré sur un module vert sous `gofmt -l`, `go vet ./...` et
`go test -race -count=1 ./...`. Les règles de frais sont **fictives**.

## 1. Les trois formes

### Un `switch`

```go
// Fee returns the fee of a transfer for a customer segment.
func Fee(t fees.Transfer, segment string) (int64, error) {
    switch segment {
    case "standard":
        if !t.International {
            return 500, nil
        }
        return fees.Percent(t.Amount, 100, 2_500), nil
    case "premium":
        if !t.International {
            return 0, nil
        }
        return fees.Percent(t.Amount, 50, 1_000), nil
    case "nonprofit":
        if !t.International {
            return 0, nil
        }
        return 1_000, nil
    }
    return 0, fmt.Errorf("%w: %q", ErrUnknownSegment, segment)
}
```

Toutes les règles dans une fonction. C'est la forme qu'on écrit d'abord, et
elle n'a rien de honteux : trois segments, quinze lignes, tout se lit d'un
coup d'œil.

### Une interface

```go
// Policy is a fee rule.
type Policy interface {
    Fee(t fees.Transfer) int64
}
```

```go
// Premium is the rule of premium accounts.
type Premium struct{}

func (Premium) Fee(t fees.Transfer) int64 {
    if !t.International {
        return 0
    }
    return fees.Percent(t.Amount, 50, 1_000)
}
```

Un type par règle, une méthode par type. C'est la forme du livre.

### Une fonction

```go
// Policy is a fee rule.
type Policy func(t fees.Transfer) int64
```

```go
// Premium is the rule of premium accounts.
func Premium(t fees.Transfer) int64 {
    if !t.International {
        return 0
    }
    return fees.Percent(t.Amount, 50, 1_000)
}
```

La même chose sans type par règle : une règle **est** une fonction. Le
registre range des fonctions, et l'appelant écrit `p(t)` au lieu de
`p.Fee(t)`.

### Ce qui ne change pas

Le barème est écrit **une fois**, et les trois formes y passent :

```go
// cases is the fee schedule, written once: the three forms must give the
// same fees, or one of them is wrong.
var cases = []struct {
    segment string
    t       fees.Transfer
    want    int64
}{
    {"standard", fees.Transfer{Amount: 100_000}, 500},
    {"standard", fees.Transfer{Amount: 100_000, International: true}, 2_500},
    {"standard", fees.Transfer{Amount: 1_000_000, International: true}, 10_000},
    {"premium", fees.Transfer{Amount: 100_000}, 0},
    {"premium", fees.Transfer{Amount: 100_000, International: true}, 1_000},
    {"premium", fees.Transfer{Amount: 1_000_000, International: true}, 5_000},
    {"nonprofit", fees.Transfer{Amount: 100_000}, 0},
    {"nonprofit", fees.Transfer{Amount: 1_000_000, International: true}, 1_000},
}
```

C'est la leçon 2.4 appliquée tout de suite : trois implémentations du même
contrat, une seule batterie. Et le registre refuse un segment inconnu — pas
de règle par défaut, pour la raison de la correction 2.3/5 :

```
fees: unknown segment: "no-such-segment" (known: [nonprofit premium standard])
```

## 2. Première mesure : une règle de plus

Le segment « personnel » arrive : domestique gratuit, international à moitié
du tarif standard. Mesuré sur une copie verte du module, dans chaque forme :

| | `switch` | interface | fonction |
|---|---|---|---|
| fichiers touchés | 1 | 1 neuf + 1 (le registre) | 1 neuf + 1 (le registre) |
| lignes | **+5** | +14 | +12 |
| erreurs de compilation | 0 | 0 | 0 |
| tests rouges | **0** | 1 — la liste des segments | 1 — la liste des segments |

Sur l'axe des règles, les trois formes sont **ouvertes** au sens de la
leçon 2.4, et la fonction est la moins chère des deux formes à registre.

Le chiffre qui compte est le zéro de la première colonne. Le `switch` n'a
**pas de liste** : il n'y a rien à compter, donc aucun test ne peut dire
« un segment est apparu sans décision ». Un registre est une donnée qu'on
peut parcourir ; un `switch` est du code qu'on ne peut que lire.

## 3. Deuxième mesure : une opération de plus

Le reçu doit maintenant **expliquer** les frais : « premium : domestique
gratuit, international 0,5 % (min 1 000 XAF) ». Une deuxième opération sur
chaque règle.

### L'interface : le compilateur dresse la liste

Une ligne dans l'interface, et le compilateur nomme les trois endroits :

```
byiface/policies.go:38:16: cannot use Standard{} (value of struct type Standard) as Policy value in map literal: Standard does not implement Policy (missing method Explain)
byiface/policies.go:39:16: cannot use Premium{} (value of struct type Premium) as Policy value in map literal: Premium does not implement Policy (missing method Explain)
byiface/policies.go:40:16: cannot use NonProfit{} (value of struct type NonProfit) as Policy value in map literal: NonProfit does not implement Policy (missing method Explain)
```

Migration finie : **+13 lignes, zéro
ligne retirée, zéro appelant touché.** Les appelants écrivaient `p.Fee(t)` ;
ils l'écrivent toujours.

### La fonction : le type lui-même change

Une fonction ne gagne pas de méthode que chaque règle renseigne. Il faut
changer le **type** — ici en une structure qui porte la fonction et son
explication — et les erreurs arrivent par vagues, parce que chaque correction
débloque la compilation suivante :

```
vague 1 :
byfunc/byfunc.go:34:10: cannot use nil as Policy value in return statement
byfunc/policies.go:32:16: cannot use Standard (value of type func(t fees.Transfer) int64) as Policy value in map literal
byfunc/policies.go:33:16: cannot use Premium (value of type func(t fees.Transfer) int64) as Policy value in map literal
byfunc/policies.go:34:16: cannot use NonProfit (value of type func(t fees.Transfer) int64) as Policy value in map literal
vague 2, registre repris :
byfunc/byfunc.go:34:10: cannot use nil as Policy value in return statement
vague 3, nil repris :
byfunc/identity_test.go:20:47: invalid operation: f != nil (mismatched types byfunc.Policy and untyped nil)
fees/fees_test.go:41:20: invalid operation: cannot call f (variable of struct type byfunc.Policy): byfunc.Policy is not a function
```

Migration finie : **+10 −7 lignes, dans trois fichiers**, dont
le test du barème — parce que chaque **appelant** écrivait `f(t)` et doit
maintenant écrire `f.Fee(t)`. Le test d'identité de la section 4, lui, n'a
plus d'objet : la règle n'est plus une fonction, et il disparaît.

> Avec l'interface, le coût d'une opération nouvelle croît avec le nombre de
> **règles**. Avec la fonction, il croît aussi avec le nombre d'**appelants**,
> parce que les appelants dépendaient de la forme « appelable ». C'est la
> mesure qui décide entre les deux, et elle se fait avant d'écrire la
> deuxième opération : combien d'opérations une règle aura-t-elle ?

### Le `switch` : un deuxième `switch`, et rien ne les lie

Ajouter `Explain` au `switch`, c'est écrire un deuxième `switch` sur les
mêmes segments : +13 lignes, zéro erreur. Puis la mesure qui compte :
**ajouter un segment au premier `switch` et l'oublier dans le second.**

```
== puis un segment ajoute a Fee et oublie dans Explain : 0 erreur(s), 0 test(s) rouge(s)
```

Zéro erreur, zéro test rouge. Le segment « personnel » a des frais et pas
d'explication, et la première personne à le savoir sera un client. C'est le
défaut du `switch` à partir de la deuxième opération : **la liste des cas est
recopiée, et les copies divergent sans bruit** — c'est le problème de
l'expression de la leçon 2.2, vu du côté des opérations.

## 4. Ce que la fonction ne sait pas faire

Trois choses, et les trois se rencontrent en production avant la deuxième
opération.

**La comparer.** « Ce client est-il au tarif premium ? » ne compile pas :

```
try.go:5:47: invalid operation: p == byfunc.Premium (func can only be compared to nil)
```

**La nommer.** Le reçu, le journal et l'audit veulent dire **quelle** règle a
été appliquée. Un type le dit ; une fonction ne peut montrer que son adresse :

```
func:      %p = 0x54f400, %T = byfunc.Policy
interface: %v = {}, %T = byiface.Premium
```

Et `go vet` refuse même qu'on essaie de l'imprimer avec `%v` :

```
vet.go:9:42: fmt.Sprintf format %v arg byfunc.Standard is a func value, not called
```

**La mettre en clé de carte**, pour la même raison qu'on ne peut pas la
comparer.

> Une fonction n'a **pas d'identité**. Tant que la règle n'a besoin que d'être
> appelée, c'est un avantage : il n'y a rien à nommer. Dès qu'il faut la
> désigner — dans un reçu, une métrique, un test — la fonction ne suffit plus.

## 5. La quatrième forme : l'adaptateur de `net/http`

La bibliothèque standard a tranché ce dilemme il y a quinze ans, avec
`http.Handler` et `http.HandlerFunc` : une **interface** pour les appelants,
et un **type fonction qui la satisfait** pour les variantes qui ne sont
qu'une fonction.

```go
// Policy is a fee rule.
type Policy interface {
    Fee(t fees.Transfer) int64
}

// PolicyFunc lets an ordinary function be a Policy, as http.HandlerFunc lets
// a function be an http.Handler.
type PolicyFunc func(t fees.Transfer) int64

// Fee calls f.
func (f PolicyFunc) Fee(t fees.Transfer) int64 { return f(t) }
```

```go
// Tiered is a variant with parameters, and a name: it is a type.
type Tiered struct {
    Name     string
    Domestic int64
    Bps, Min int64
}

func (p Tiered) Fee(t fees.Transfer) int64 {
    if !t.International {
        return p.Domestic
    }
    return fees.Percent(t.Amount, p.Bps, p.Min)
}
```

```go
// Default returns the registry of the bank: two variants are values of a
// type, one is a function.
func Default() map[string]Policy {
    return map[string]Policy{
        "standard": Tiered{Name: "standard", Domestic: 500, Bps: 100, Min: 2_500},
        "premium":  Tiered{Name: "premium", Domestic: 0, Bps: 50, Min: 1_000},
        "nonprofit": PolicyFunc(func(t fees.Transfer) int64 {
            if !t.International {
                return 0
            }
            return 1_000
        }),
    }
}
```

Les appelants dépendent de l'interface : une opération nouvelle ne les touche
pas. Les variantes paramétrées et nommées sont des valeurs d'un type —
`Tiered` sert deux segments avec deux jeux de paramètres, ce que ni la forme
interface « un type par règle » ni la forme fonction n'exprimaient. Et la
variante qui n'est qu'un calcul reste une fonction, emballée en une ligne.

Une doublure de test aussi tient en une ligne :

```go
// TestADoubleIsOneLine: with the adapter, a test double is a function
// literal, as with the func form.
func TestADoubleIsOneLine(t *testing.T) {
    var p Policy = PolicyFunc(func(fees.Transfer) int64 { return 42 })
    if p.Fee(fees.Transfer{}) != 42 {
        t.Fatal("the double does not answer")
    }
}
```

Le prix existe : le jour où l'interface gagne `Explain`, `PolicyFunc` ne la
satisfait plus, et la variante emballée devra devenir un type. C'est le même
compte que la section 3 — mais il ne touche que **cette** variante, pas les
appelants.

## 6. La stratégie qui se souvient

« Les trois premiers virements internationaux du mois sont gratuits. » La
tentation est d'écrire une stratégie qui compte :

```go
// FirstFree wraps a rule: the first n international transfers are free. The
// counter lives in the closure — so in this process, in this registry, and
// without a lock.
func FirstFree(n int, then Policy) Policy {
    used := 0
    return func(t fees.Transfer) int64 {
        if t.International && used < n {
            used++
            return 0
        }
        return then(t)
    }
}
```

Elle compile, elle passe un test écrit sur une instance. Elle a trois
défauts, et deux se mesurent.

**Elle n'est pas sûre en concurrence.** Le compteur vit dans la fermeture,
sans verrou ; un service HTTP l'appelle depuis plusieurs goroutines :

```
WARNING: DATA RACE
```

**Elle compte par processus.** Deux instances du service derrière un
répartiteur ont chacune leur registre, donc leur compteur :

```
two instances, 6 free transfers for a month that allows 3
```

**Elle oublie tout au redémarrage**, et le mois recommence à chaque
déploiement.

Le verrou corrigerait le premier défaut et laisserait les deux autres. La
vraie correction est de **sortir l'état** : l'usage du mois devient une
entrée de la règle, lue là où il est vraiment tenu — la base, le grand livre.

```go
// Usage is what the rule needs to know about the month: it is an INPUT, not
// a memory.
type Usage struct {
    FreeUsed int
}
```

```go
// PureFirstFree is FirstFree with the state outside: the same input gives
// the same fee, in any process, at any time.
func PureFirstFree(n int, then func(fees.Transfer) int64) PurePolicy {
    return func(t fees.Transfer, u Usage) int64 {
        if t.International && u.FreeUsed < n {
            return 0
        }
        return then(t)
    }
}
```

```
free used 0..4: 0 0 0 2500 2500
```

> Une stratégie qui garde de l'état n'est plus une stratégie : c'est un
> service, avec sa concurrence, sa persistance et son cycle de vie. Une règle
> reçoit ce qu'elle doit savoir en **argument**. C'est la leçon 1.1 — la
> propriété des données — appliquée à un pattern.

## 7. La campagne

Onze modifications, jouées sous `go test -race -count=1 -timeout=120s ./...`.
Première passe :

```
Percent sans minimum                           tuee
switch : premium au taux standard              tuee
switch : segment inconnu au tarif standard     tuee
interface : premium sans minimum               tuee
interface : segment inconnu au tarif standard  tuee
fonction : association payante en domestique   tuee
fonction : segment inconnu au tarif standard   tuee
adaptateur : PolicyFunc n'appelle plus f       tuee
adaptateur : Tiered ignore le domestique       SURVIT
pure : un transfert gratuit de trop            tuee
fermeture : gratuit sans limite                SURVIT
9/11 tuees
```

Deux survivants, et les deux réclament un test.

**« Tiered ignore le domestique ».** Le test de l'adaptateur ne reprenait que
des cas internationaux : il avait été écrit pour vérifier l'emballage, pas les
règles. Un cas domestique de plus.

**« Gratuit sans limite ».** Le seul test de `FirstFree` comptait six
virements gratuits sur **deux** instances — et une fermeture qui a oublié la
limite donne aussi six virements gratuits. Le test vérifiait le défaut qu'il
voulait montrer, pas la règle elle-même :

```go
// TestTheFourthTransferPays: on ONE instance, the limit holds. The test
// below, with two instances, gives six free transfers whether the limit
// exists or not: alone, it could not see a closure that forgot it.
func TestTheFourthTransferPays(t *testing.T) {
    p := FirstFree(3, Policy(byfunc.Standard))
    var got []string
    for range 4 {
        got = append(got, strconv.FormatInt(p(intl), 10))
    }
    if s := strings.Join(got, " "); s != "0 0 0 2500" {
        t.Fatalf("fees = %s", s)
    }
}
```

C'est la faute de la correction 2.4/3, clause 7, vue d'un autre côté : un test
écrit pour montrer un effet ne vérifie pas le comportement normal.

Deuxième passe :

```
11/11 tuees
```

## 8. La grille

| Si… | Alors |
|---|---|
| une seule règle, ou des règles qui changent toujours ensemble | pas de stratégie : du code direct (leçon 2.6) |
| peu de règles, **une** opération, aucun besoin de les nommer | un `switch`, tant qu'il n'y a pas de deuxième opération |
| une opération, des règles choisies par une donnée, rien à nommer | une **fonction** et un registre |
| des règles qu'il faut nommer, comparer, paramétrer, ou plusieurs opérations | une **interface** |
| les deux à la fois | l'interface, plus un **type fonction adaptateur** pour les règles qui ne sont qu'un calcul |
| la règle doit se souvenir de quelque chose | ce n'est pas une règle : sors l'état, passe-le en argument |

## 9. Les trois erreurs qui restent

### « En Go, une stratégie, c'est une fonction »

Souvent, et c'est une bonne première forme. Mais la mesure de la section 3
est le prix de l'erreur : si la règle gagne une deuxième opération, la
migration touche chaque appelant. La question à poser avant de choisir n'est
pas « est-ce plus court ? », c'est **« combien d'opérations, et faut-il la
nommer ? »**.

### « Un `switch` n'est pas extensible, il faut une stratégie »

Un `switch` à une opération s'étend en une ligne, et la mesure de la section 2
dit qu'il coûte moins que les deux autres. Son défaut n'est pas l'extension :
c'est **la deuxième opération**, et l'absence de liste qu'un test pourrait
parcourir.

### « Le pattern Stratégie veut une interface, c'est sa définition »

Le livre définit le pattern par son **intention** — encapsuler une famille de
règles interchangeables — pas par sa syntaxe. Une fonction en paramètre de
`sort.Slice` est une stratégie de comparaison ; personne n'écrirait une
interface `Less` pour trier une tranche une fois.

## 10. Le lien avec la production

| Ce que tu as déjà vu | Ce que c'est |
|---|---|
| un `switch` sur le type de client recopié dans quatre fichiers, dont un oublié | deux opérations en `switch`, sans liste commune (section 3) |
| « quel tarif a été appliqué à ce client ? » et personne ne peut répondre | une règle sans identité (section 4) |
| une promotion « les N premiers gratuits » qui en donne 2N après la mise à l'échelle | une stratégie qui garde l'état par instance (section 6) |
| des frais différents après chaque redémarrage | le même état, perdu au déploiement |
| un refactoring « fonction vers interface » qui touche quarante fichiers | une deuxième opération sur une stratégie en fonction : le coût est chez les appelants |

## 11. Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Un pattern est un nom donné à une solution **à une contrainte qui revient**. On part de la contrainte, jamais du nom. |
| ⚫ | En Go, la Stratégie a quatre formes : `switch`, interface, fonction, et interface plus type fonction adaptateur. |
| ⚫ | Une règle de plus coûte peu dans les quatre. Le `switch` n'a pas de liste : aucun test ne voit un cas apparaître. |
| ⚫ | Une opération de plus : l'interface touche les règles, la fonction touche aussi **les appelants**, le `switch` recopie la liste des cas sans que rien ne relie les copies. |
| ⚫ | Une fonction n'a pas d'identité : on ne la compare pas, on ne la nomme pas, `go vet` refuse de l'imprimer. Dès qu'il faut désigner la règle, elle ne suffit plus. |
| ⚫ | `http.HandlerFunc` est la réponse de la bibliothèque standard : l'interface pour les appelants, une fonction emballée pour les variantes qui ne sont qu'un calcul. |
| ⚫ | Une stratégie qui garde de l'état n'est plus une stratégie : elle compte par processus, perd tout au redémarrage, et court en concurrence. L'état est une **entrée**. |
| ⚫ | Un test écrit pour montrer un défaut ne vérifie pas le comportement normal : il faut les deux. |

## 12. Approfondissement

### Le patron de méthode, et pourquoi il disparaît

Le *Template Method* du livre fixe le squelette d'un algorithme dans une
classe de base et laisse des sous-classes remplir des étapes. Go n'a pas
d'héritage (leçon 2.3), et le pattern y devient **une fonction qui prend des
stratégies** : le squelette est la fonction, les étapes sont ses paramètres.
`sort.Sort` en est la forme la plus connue — le squelette du tri, et une
interface de trois méthodes pour les étapes.

### La Commande, cousine de la Stratégie

Une stratégie répond à « **comment** faire ». Une commande répond à « **quoi**
faire, et quand » : elle se range dans une file, se rejoue, s'annule. Les
deux ont la même forme en Go — une fonction ou une interface à une méthode — et
c'est leur usage qui les distingue. La leçon 3.5 y revient, avec les états.

### Pourquoi `go vet` refuse d'imprimer une fonction

Parce que c'est presque toujours une faute : `fmt.Println(user.Name)` au lieu
de `fmt.Println(user.Name())`. Le refus a un effet de bord utile ici : il
rappelle qu'une fonction n'a rien d'imprimable à dire sur elle-même.

## 13. Le réflexe à installer

> **Devant une règle qui varie**
> Combien de variantes aujourd'hui, et combien d'**opérations** par variante
> demain ? Faut-il **désigner** la règle appliquée — dans un reçu, une
> métrique, un audit ? La forme découle des deux réponses.
>
> **Devant une stratégie qui compte, cache ou retient**
> Où vit cet état quand il y a deux instances, et que devient-il au
> redémarrage ? Si la réponse est « dans la fermeture », sors-le.

Et le geste d'une minute :

> **Avant d'écrire la deuxième opération sur une stratégie, compte ses
> appelants.** C'est le prix de la migration si la stratégie est une fonction,
> et c'est zéro si elle est une interface.
