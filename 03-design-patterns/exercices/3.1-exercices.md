# Exercices 3.1 — Faire varier une règle

**Règles.** Réponds avant d'ouvrir la correction. La question n'est jamais
*« quel pattern est-ce ? »* mais **« quelle contrainte revient, et que coûte
chaque forme le jour où elle change ? »**

Quatre obligations de méthode, valables pour tout le niveau 3 :

1. **Avant de lancer quoi que ce soit, écris ta prédiction.** Puis lance, et
   compare. L'écart est l'enseignement.
2. **Une forme se juge sur les deux changements de la leçon** : une variante
   de plus, une opération de plus. Pour chacun : fichiers touchés, lignes,
   erreurs de compilation, tests rouges.
3. **Dis si la règle doit être désignée** — comparée, nommée, journalisée,
   auditée. C'est ce qui sépare une fonction d'un type.
4. **Chaque chiffre que tu avances doit venir d'une commande.** `go test`,
   `go test -race`, `go vet`, un `diff` — pas d'estimation à vue.

Écris tes réponses dans `03-design-patterns/mes-reponses/3.1.md` (dossier
local, ignoré par Git).

## Exercice 1 — Compréhension

Quatre extraits, tirés du même service bancaire.

```go
// A — sorting the accounts for the statement.
func SortForStatement(accounts []Account) {
    sort.Slice(accounts, func(i, j int) bool {
        return accounts[i].Opened.Before(accounts[j].Opened)
    })
}
```

```go
// B — the health endpoint.
func Health() http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusNoContent)
    })
}
```

```go
// C — rounding an amount for display.
func Round(amount float64, currency string) float64 {
    switch currency {
    case "XAF", "XOF":
        return float64(int64(amount + 0.5))
    case "EUR", "USD":
        return float64(int64(amount*100+0.5)) / 100
    }
    return amount
}
```

```go
// D — the notifier of the transfer service.
type Notifier interface {
    Notify(accountID, text string) error
}
```

```go
// SMSNotifier is the only implementation, and the tests use it with a fake
// gateway.
type SMSNotifier struct {
    Gateway func(number, text string) error
    Numbers map[string]string
}

func (n SMSNotifier) Notify(accountID, text string) error {
    return n.Gateway(n.Numbers[accountID], text)
}
```

1. **Lesquels sont des stratégies ?** Pour chacun, dis oui ou non, et nomme
   la règle qui varie — ou dis pourquoi il n'y en a pas.

2. **Nomme la forme** de chaque stratégie parmi les quatre de la leçon, et
   dis si elle est la bonne pour ce qu'elle fait aujourd'hui.

3. **L'extrait C a une faute qui n'est pas une faute de forme.** Trouve-la,
   écris la ligne de test qui la montre, et dis à quelle correction du
   niveau 2 elle ressemble.

4. **L'extrait D est une interface à une seule implémentation.** La leçon 2.6
   dit de s'en méfier. Dis si elle est justifiée ici, en citant ce que
   l'énoncé dit des tests, et ce qu'elle serait en forme fonction.

5. **Prédiction.** On ajoute à l'extrait C une deuxième opération — le
   symbole de la devise pour le reçu — en recopiant le `switch`. Combien
   d'erreurs de compilation, combien de tests rouges ? Puis on ajoute la
   devise `NGN` au premier `switch` seulement. Même question.

6. **Question ouverte.** Un collègue dit : *« `sort.Slice` prouve que la
   bonne forme de la stratégie en Go est la fonction »*. Dis sur quoi il a
   raison, et donne le cas — tiré de cette page — où sa règle coûterait cher.

## Exercice 2 — Code

La banque affiche ses montants dans cinq devises : XAF et XOF (sans
subdivision), EUR et USD (au centime), et NGN, qui s'arrondit au naira entier
pour l'affichage mais au kobo pour la comptabilité.

**Écris le paquet d'arrondi**, et il doit vérifier tout ce qui suit :

1. **Les montants sont des entiers** dans la plus petite unité comptable de la
   devise. Pas de `float64` dans une signature exportée — dis pourquoi en une
   phrase.

2. **Chaque règle d'arrondi est désignable** : le reçu imprime
   « arrondi : XAF, à l'unité, au plus proche, demi vers le haut ». Choisis la
   forme en conséquence, et justifie-la par la règle 3 de méthode.

3. **Une devise inconnue est une erreur**, avec la liste des devises connues.
   Pas d'arrondi par défaut.

4. **Une seule batterie** pour toutes les règles : chaque cas du barème est
   écrit une fois, et une règle qui n'y passe pas fait tomber un test qui la
   nomme.

5. **Mesure les deux changements.** Ajoute le franc guinéen (GNF, sans
   subdivision) : fichiers, lignes, erreurs, tests rouges. Puis ajoute une
   opération `Symbol() string` : mêmes chiffres. Publie le `diff` des deux.

6. **Le demi.** Pour 2,5 XAF affichés à l'unité : 2 ou 3 ? Pour −2,5 ?
   Choisis une règle, écris les quatre cas de test qui la fixent (positif,
   négatif, juste au-dessous, juste au-dessus), et dis ce qu'un arrondi
   « au plus proche » sans règle pour le demi produit sur un relevé de mille
   lignes.

Puis :

7. **Campagne de modifications**, au moins dix, dont une qui retire une
   devise du registre, une qui inverse le sens du demi, une qui fait arrondir
   NGN au kobo pour l'affichage, et une qui rend une règle par défaut. Publie
   le relevé, et pour chaque survivant : un test, une suppression de branche,
   ou rien.

## Exercice 3 — Refactoring

Le code des canaux de paiement, tel qu'il est en production :

```go
// Channels lists the channels the bank offers.
var Channels = []string{"card", "mobile_money", "transfer", "cash"}
```

```go
// Fee returns the fee of a payment, in XAF.
func Fee(channel string, amount int64) (int64, error) {
    switch channel {
    case "card":
        return amount * 150 / 10_000, nil
    case "mobile_money":
        return min(amount*100/10_000, 2_000), nil
    case "transfer":
        return 500, nil
    case "cash":
        return 0, nil
    }
    return 0, fmt.Errorf("unknown channel %q", channel)
}
```

```go
// Limit returns the maximum amount of one payment, in XAF.
func Limit(channel string) int64 {
    switch channel {
    case "card":
        return 2_000_000
    case "mobile_money":
        return 500_000
    case "transfer":
        return 50_000_000
    }
    return 0
}
```

```go
// Label returns the name of the channel on the receipt, in French.
func Label(channel string) string {
    switch channel {
    case "card":
        return "Carte bancaire"
    case "mobile_money":
        return "Mobile money"
    case "transfer":
        return "Virement"
    case "cash":
        return "Especes"
    default:
        return channel
    }
}
```

Les tests passent :

```go
func TestFee(t *testing.T) {
    for _, c := range []struct {
        channel string
        amount  int64
        want    int64
    }{
        {"card", 100_000, 1_500},
        {"mobile_money", 100_000, 1_000},
        {"mobile_money", 1_000_000, 2_000},
        {"transfer", 100_000, 500},
        {"cash", 100_000, 0},
    } {
        if got, err := Fee(c.channel, c.amount); err != nil || got != c.want {
            t.Errorf("%s %d: %d, %v", c.channel, c.amount, got, err)
        }
    }
}
```

1. **Il y a une faute.** Trouve-la sans lire les `switch` un par un : écris
   **un** test qui parcourt `Channels` et interroge les trois fonctions. Dis
   ce qu'il trouve, et ce que fait la production avec cette faute.

2. **Pourquoi aucun test ne l'a vue**, en une phrase qui parle de la forme du
   code, pas des tests.

3. **Refactorise.** Choisis la forme, écris-la, et fais repasser les tests
   existants sans les modifier — sinon dis lequel tu modifies et pourquoi.

4. **Mesure avant et après.** Ajoute le canal `crypto` (frais 2 %, plafond
   100 000 XAF, libellé « Crypto-actifs ») dans le code d'origine puis dans le
   tien : fichiers, lignes, erreurs de compilation, tests rouges. Puis oublie
   volontairement le plafond de `crypto` dans les deux : qui le voit ?

5. **Le défaut de `Label`** n'est pas le même que celui de `Limit`. Dis
   lequel est le plus dangereux, et pourquoi le tien n'a ni l'un ni l'autre.

6. **Question ouverte.** La comptabilité demande que le libellé dépende aussi
   de la **langue** du client. Dis si la langue devient une deuxième
   stratégie, une donnée, ou un paramètre de la première — et mesure ce que
   ton choix coûte pour une troisième langue.

## Exercice 4 — Design

Le moteur antifraude de la banque décide, pour chaque paiement, s'il passe,
s'il est bloqué, ou s'il part en revue manuelle. Les règles :

| | Aujourd'hui | Demandé |
|---|---|---|
| règles | 9, écrites par l'équipe fraude | une nouvelle par mois, en moyenne |
| paramètres | seuils codés en dur | par commerçant, modifiables sans livraison |
| décision | la première règle qui bloque | toutes les règles, et la plus sévère gagne |
| audit | « bloqué » | **quelle règle, quelle version, quels paramètres** |
| expérimentation | aucune | faire tourner deux versions d'une règle en même temps, une seule décide |

Et deux règles particulières : la **vélocité** (« plus de 5 paiements en
10 minutes sur la même carte ») et la **géographie** (« pays du commerçant
différent du pays de la carte, et montant au-dessus d'un seuil »).

1. **La forme d'une règle.** Écris la signature — type, interface, ou
   fonction — et justifie-la par la ligne « audit » du tableau.

2. **La vélocité garde de l'état.** Dis où vit cet état, et pourquoi pas dans
   la règle. Écris ce que la règle reçoit en argument.

3. **Deux versions en même temps.** Écris comment la version B tourne sans
   décider, et ce que l'audit enregistre pour elle. Dis ce qui empêche, par
   construction, que B décide par erreur.

4. **« La plus sévère gagne. »** Écris la combinaison. Puis dis ce qui se
   passe quand une règle **panique** ou **dépasse son délai** : le paiement
   passe, est bloqué, ou part en revue ? Justifie par le métier, pas par la
   technique.

5. **Paramètres sans livraison.** Ils arrivent d'un fichier ou d'une base.
   Dis ce qui est validé au chargement, et ce qui se passe quand un paramètre
   d'un commerçant est invalide : on refuse le fichier entier, on garde
   l'ancien jeu, ou on ignore la ligne ? (La correction 2.4/4 a une réponse
   pour un cas voisin.)

6. **Question ouverte.** L'équipe fraude veut écrire ses règles elle-même,
   « dans un petit langage », sans passer par les développeurs. Dis ce que la
   banque gagne, ce qu'elle perd — en particulier sur l'audit et les tests —,
   et où tu places la frontière.

## Exercice 5 — Incident de production

Banque en ligne, 180 000 virements par jour. Extrait du post-mortem.

```
lun. 03/11 08:00  lancement de la campagne « vos 5 premiers virements de
                  novembre offerts ». Le service de frais tourne sur 2
                  instances
mar. 04/11 14:00  le service passe a 6 instances, pour la paie de fin de
                  mois annoncee
mer. 05/11 11:20  deploiement d'un correctif sans rapport ; les 6
                  instances redemarrent
jeu. 06/11 09:15  la comptabilite signale que les frais de virement de
                  novembre sont a 31 % de la prevision
jeu. 06/11 16:00  reconstitution : 41 % des clients actifs ont eu plus de
                  5 virements gratuits ; le maximum observe est 30
```

Le code de la campagne :

```go
// FirstFiveFree makes the first five transfers of each account free during
// the campaign. "Simple and self-contained: no database change."
func FirstFiveFree(then Rule) Rule {
    var mu sync.Mutex
    used := map[string]int{}
    return func(t Transfer) int64 {
        mu.Lock()
        defer mu.Unlock()
        if used[t.Account] < 5 {
            used[t.Account]++
            return 0
        }
        return then(t)
    }
}
```

```go
// Rules is built once at startup, by each instance of the service.
func Rules() map[string]Rule {
    return map[string]Rule{
        "standard":  Standard,
        "promo-nov": FirstFiveFree(Standard),
    }
}
```

Le test, vert depuis le premier jour :

```go
func TestTheFirstFiveAreFree(t *testing.T) {
    r := Rules()["promo-nov"]
    var fees []int64
    for range 7 {
        fees = append(fees, r(Transfer{Account: "CM-0001", Amount: 100_000}))
    }
    for i, f := range fees {
        want := int64(0)
        if i >= 5 {
            want = 500
        }
        if f != want {
            t.Fatalf("transfer %d: fee %d, want %d", i+1, f, want)
        }
    }
}
```

Établi après coup :

- La revue a approuvé avec le commentaire *« simple et autonome, pas de
  changement de base : parfait pour une campagne d'un mois »*.
- Le verrou a été ajouté pendant la revue, après qu'un relecteur a lancé
  `go test -race`.
- Le répartiteur de charge envoie chaque requête à une instance au hasard.

### Les questions

1. **Explique le mécanisme en trois phrases**, sans employer le mot
   « instance ».

2. **Le maximum observé est 30.** Calcule, à partir de la chronologie, le
   nombre maximal de virements gratuits qu'un client pouvait obtenir à chaque
   étape — lundi, mardi après 14:00, mercredi après 11:20. Puis dis pourquoi
   le maximum observé est plus bas que le tien, et pourquoi 41 % des clients
   et pas tous.

3. **Le verrou a corrigé un défaut et en a caché deux.** Nomme le défaut
   corrigé et les deux défauts qu'il ne pouvait pas corriger.

4. **Le test était vert.** Dis ce qu'il vérifiait exactement, et écris le
   test qui aurait échoué avant la mise en production — sans réseau, sans
   base, en moins de vingt lignes.

5. **Trois jours de détection.** Décompose-les. Dis quel indicateur aurait
   tiré le mardi après-midi, avec son seuil et son plancher de bruit.

6. **« Simple et autonome. »** Dis ce que « autonome » voulait dire pour
   l'auteur, et ce que ça voulait dire pour le système. La question que la
   revue aurait dû poser tient en une ligne.

7. **La correction.** Quatre propositions :

   | | Proposition |
   |---|---|
   | A | une instance unique pour le service de frais pendant la campagne |
   | B | le compteur dans Redis, incrémenté par la règle |
   | C | la règle reçoit en argument le nombre de virements gratuits déjà consommés, lu dans le grand livre |
   | D | supprimer les campagnes de gratuité |

   Pour chacune : ce qu'elle empêche, ce qu'elle n'empêche pas, ce qu'elle
   coûte, et **ce qui se passe au prochain redémarrage**. Laquelle choisis-tu ?

8. **Question ouverte.** La direction demande une garantie : *« plus jamais
   une règle de frais dont le résultat dépend de l'instance qui la calcule »*.
   Propose une propriété du code qui la tient, dis à quel moment elle tire
   — revue, compilation, test, production —, ce qu'elle interdit, et réponds
   à la question qui décide : **ta propriété attrape-t-elle une règle qui lit
   l'heure ?**
