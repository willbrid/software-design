# Exercices 3.6 — Les patterns qui coûtent

Cinq exercices, du plus simple au plus ouvert. Traite-les **dans l'ordre** et
écris tes réponses dans `mes-reponses/` avant d'ouvrir les corrections.

Les exercices s'appuient sur les paquets `config`, `fees`, `global`,
`locator`, `legacy`, `transfer`, `operator`, `wiring` et `fake` de la
[leçon 3.6](../cours/3.6-patterns-qui-coutent.md), recopiés tels quels dans
le module des exercices. Tout le code ci-dessous compile et passe
`go vet` ; la banque, les opérateurs Kola Money et Baobab Pay, et l'incident
sont **fictifs**.

## Exercice 2 — Code : `New` qui refuse un service incomplet

*Niveau 2. Écrire une fonction ; les tests sont fournis.*

`transfer.New` a six paramètres positionnels. Une équipe préfère une
`struct` de dépendances, plus lisible à l'appel. Mais un champ oublié dans
une `struct` est une valeur zéro, et **le compilateur ne dit rien** : c'est
le défaut du service locator, déplacé. `New` doit donc vérifier elle-même.

```go
// Deps is everything a transfer service needs. A field left out is a zero
// value: the compiler does not see it, so New must.
type Deps struct {
    Operator transfer.Operator
    Ledger   transfer.Ledger
    Notifier transfer.Notifier
    Fees     fees.Schedule
    Limit    int64
    Now      func() time.Time
}
```

```go
var (
    ErrMissing = errors.New("missing dependency")
    ErrInvalid = errors.New("invalid setting")
)
```

```go
// New returns the service, or an error that lists every problem of d, not
// only the first. Each problem wraps ErrMissing or ErrInvalid.
//
// To write: exercise 2.
func New(d Deps) (*transfer.Service, error) {
    return nil, errors.New("not implemented")
}
```

Les tests sont dans `ex2/deps/deps_test.go`. Sur le squelette, sept des
huit échouent : c'est voulu. Le huitième vérifie que deux appels donnent le
même message, et passe déjà, pour la mauvaise raison.

```go
func TestAMissingDependencyIsNamed(t *testing.T) {
    for name, clear := range map[string]func(*deps.Deps){
        "operator": func(d *deps.Deps) { d.Operator = nil },
        "ledger":   func(d *deps.Deps) { d.Ledger = nil },
        "notifier": func(d *deps.Deps) { d.Notifier = nil },
        "clock":    func(d *deps.Deps) { d.Now = nil },
    } {
        d := complete()
        clear(&d)
        svc, err := deps.New(d)
        if svc != nil || !errors.Is(err, deps.ErrMissing) || !strings.Contains(err.Error(), name) {
            t.Errorf("without %s: %v, %v; want ErrMissing naming %q", name, svc, err, name)
        }
    }
}
```

```go
// Every problem is reported at once: the person who reads the error fixes
// the file once, not four times.
func TestEveryProblemIsReportedAtOnce(t *testing.T) {
    _, err := deps.New(deps.Deps{Fees: fees.Schedule{RateBP: -5}})
    if err == nil {
        t.Fatal("no error")
    }
    for _, name := range []string{"operator", "ledger", "notifier", "clock", "limit", "rate"} {
        if !strings.Contains(err.Error(), name) {
            t.Errorf("%q not in %q", name, err)
        }
    }
    if !errors.Is(err, deps.ErrMissing) || !errors.Is(err, deps.ErrInvalid) {
        t.Errorf("err should wrap both ErrMissing and ErrInvalid: %v", err)
    }
}
```

1. Écris `New` pour que les huit tests passent sous
   `go test -race -count=1 ./ex2/...`.
2. Que fait ton `New` avec `var l *fake.Ledger` puis
   `Deps{Ledger: l, ...}` ? Prévois, puis vérifie. Faut-il le détecter ?
3. Six paramètres positionnels, ou une `struct` vérifiée : laquelle
   choisirais-tu pour `transfer`, et à partir de combien de dépendances
   changerais-tu d'avis ?

## Exercice 3 — Refactoring : les alertes SMS

*Niveau 3. Caractériser, puis refactorer sans casser les appelants.*

Quand un gros transfert part d'un compte, le client reçoit un SMS : s'il
n'en est pas l'auteur, il appelle la banque dans les minutes qui suivent.
Le paquet `ex3/alerts` fait ce travail depuis trois ans :

```go
// Threshold is the amount, in FCFA, from which a transfer is alerted.
var Threshold int64 = 1_000_000
```

```go
var gateway = sms.Gateway{URL: os.Getenv("SMS_URL"), HTTP: &http.Client{Timeout: 5 * time.Second}}
```

```go
var (
    mu   sync.Mutex
    last = map[string]time.Time{} // account -> time of the last alert
)
```

```go
// Notify sends at most one alert per account and per hour, and none at
// night, from 22:00 to 07:00, so as not to wake the customer.
func Notify(ctx context.Context, account, phone string, amount int64) error {
    if amount <= Threshold {
        return nil
    }
    now := time.Now()
    if h := now.Hour(); h >= 22 || h < 7 {
        return nil
    }
    mu.Lock()
    if t, ok := last[account]; ok && now.Sub(t) < time.Hour {
        mu.Unlock()
        return nil
    }
    last[account] = now
    mu.Unlock()
    text := fmt.Sprintf("Transfert de %d FCFA depuis votre compte. Ce n'est pas vous ? Appelez le 8000.", amount)
    return gateway.Send(ctx, phone, text)
}
```

Il a deux appelants : le paquet `ex3/payroll` (ci-dessous), et le serveur
web, qui appartient à une autre équipe et ne changera pas avant deux mois.

```go
// Alert warns each account of the batch. A failed SMS does not stop the
// batch.
func Alert(ctx context.Context, lines []Line) {
    for _, l := range lines {
        if err := alerts.Notify(ctx, l.Account, l.Phone, l.Amount); err != nil {
            log.Printf("alert %s: %v", l.Account, err)
        }
    }
}
```

Les serveurs tournent en UTC. Les clients sont à Douala, en UTC+1.

1. **Pourquoi ne peut-on pas tester `Notify` aujourd'hui ?** Liste chaque
   obstacle, et ce qu'il faudrait pour le lever.
2. **Caractérise.** Introduis le **plus petit** changement qui permette de
   tester, sans changer aucun comportement, puis écris les tests qui
   épinglent ce que fait `Notify`, défauts compris. Chaque défaut a un test
   dont le nom commence par `TestFlaw`. Il y en a au moins quatre.
3. **Refactore** vers un type `Alerter`, construit par `New`, qui reçoit
   tout ce dont il a besoin. Le serveur web doit continuer de compiler et
   de fonctionner sans changer une ligne : que devient la fonction
   `Notify` du paquet ?
4. **Un seul défaut est à corriger dans ce refactoring** : un SMS qui n'est
   pas parti ne doit pas compter comme envoyé. Corrige-le, et dis ce que tu
   ferais des autres.
5. Lance une campagne sur ta nouvelle forme : quelles erreurs tes tests
   voient-ils ?

## Exercice 4 — Conception : deux pays, un processus

*Niveau 4. Pas de code imposé : une conception argumentée.*

La banque ouvre au Gabon. Le même serveur sert les deux pays :

| | Cameroun | Gabon |
|---|---|---|
| opérateur | Kola Money | Baobab Pay |
| frais | 1 %, minimum 100 FCFA | 0,8 %, minimum 150 FCFA |
| plafond par client et par jour | 500 000 FCFA | 1 000 000 FCFA |

Le grand livre et la passerelle SMS sont communs. Les réponses des deux
opérateurs arrivent sur le même serveur.

1. **Combien d'instances** de `transfer.Service` ? Qui choisit celle qui
   traite une requête, et à partir de quelle information ?
2. **La configuration** : un fichier par pays, ou un seul ? Que se passe-t-il
   au démarrage si celui du Gabon contient une erreur ?
3. **Les réponses des opérateurs** : comment le serveur choisit-il le
   vérificateur de signature ? Pourquoi ne faut-il **pas** le choisir à
   partir d'un champ du corps de la réponse ?
4. **Le métier veut changer le taux du Gabon sans redémarrer** (une
   promotion qui commence lundi à 8 h). Propose un mécanisme. Que
   devient le plafond journalier d'un client qui a déjà envoyé 900 000 FCFA
   ce jour-là, au moment du changement ?
5. **Un troisième pays** l'an prochain : qu'est-ce qui change dans le code,
   et qu'est-ce qui ne change pas ?

Réponds par un texte d'une page au plus, avec un schéma de la racine de
composition si tu le juges utile.

## Exercice 5 — Incident : la promotion que personne n'avait lancée

*Niveau 7. Un incident réel, à expliquer et à corriger.*

**Les faits.** La version 4.12 du serveur de transferts est déployée un
lundi. Le jeudi, la finance signale que les frais encaissés depuis lundi
sont **la moitié** de ce qu'ils devraient être, et le service de la
conformité remarque des clients qui ont envoyé plus de 500 000 FCFA dans la
journée. La configuration de production, montée par la plateforme dans
`/etc/bank`, est juste :

```text
# Production settings, mounted by the platform at /etc/bank.
fee_bp      = 100
fee_min     = 100
daily_limit = 500000
operator    = kola
secret      = prod-secret
```

La version 4.12 a ajouté un paquet `pricing`, pour éviter de relire la
configuration à chaque transfert :

```go
var schedule = load()
```

Le programme principal, qui rejoue ici le trafic au lieu d'écouter sur un
port :

```go
func main() {
    log.SetFlags(0)
    global.Path = "etc/bank.conf" // the production file
    log.Printf("bankd 4.12 starting, config %s", global.Path)

    limit := global.Get().DailyLimit
    r := rand.New(rand.NewPCG(4, 12))
    for day := 1; day <= 3; day++ {
        sent := map[int]int64{}
        var n, overLimit, amounts, charged int64
        for range 40_000 {
            account := r.IntN(25_000)
            amount := 2_000 + r.Int64N(r.Int64N(300_000)+1)
            if r.IntN(100) == 0 {
                amount = 300_000 + r.Int64N(600_000) // a few large ones
            }
            if sent[account]+amount > limit {
                continue
            }
            if sent[account]+amount > 500_000 {
                overLimit++
            }
            sent[account] += amount
            n++
            amounts += amount
            charged += pricing.Fee(amount)
        }
        fmt.Printf("day %d: %d transfers, %d FCFA sent, %d FCFA of fees, %d took the account past 500000\n", day, n, amounts, charged, overLimit)
    }
}
```

L'image du conteneur est construite par un `COPY . .` depuis la machine du
développeur. Le répertoire de travail de l'image (`ex5/image` dans le
module) contient, en plus de `etc/` :

```text
# Local settings for the promotion tests. Do not commit.
fee_bp      = 50
fee_min     = 100
daily_limit = 5000000
operator    = kola
secret      = dev
```

La rejouée de trois jours de trafic (voir le commentaire en tête de
`bankd`) :

```text
bankd 4.12 starting, config etc/bank.conf
day 1: 40000 transfers, 3287973527 FCFA sent, 16889244 FCFA of fees, 1042 took the account past 500000
day 2: 40000 transfers, 3275874134 FCFA sent, 16824085 FCFA of fees, 984 took the account past 500000
day 3: 40000 transfers, 3320297072 FCFA sent, 17037459 FCFA of fees, 1068 took the account past 500000
```

Le journal dit `config etc/bank.conf`. Personne n'a vu le problème pendant
trois jours.

1. **Explique** pourquoi la version 4.12 a facturé 0,5 % et appliqué un
   plafond de 5 000 000 FCFA, alors que `main` désigne le bon fichier.
   Appuie-toi sur l'ordre d'initialisation de Go.
2. **Pourquoi le journal ment-il ?** Qu'aurait-il dû afficher ?
3. **Combien** la banque a-t-elle perdu en frais, sur les trois jours
   rejoués ? Donne un chiffre, et la méthode.
4. **Corrige** : écris la version 4.13 de façon que ce défaut ne puisse pas
   revenir, même si quelqu'un recopie un fichier de développement dans
   l'image.
5. **Le test qui manquait** : écris un test qui aurait échoué sur la 4.12.
6. **Le tableau de bord** : quelle métrique aurait montré le problème le
   lundi, et avec quel seuil ?
7. Écris le **compte rendu** de l'incident en cinq lignes.
