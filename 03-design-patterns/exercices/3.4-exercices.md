*Niveau 2. Une fonction de vingt lignes, qui doit passer cinq tests.*

## Exercice 4 — Design : une politique par abonné

*Niveau 4. Des signatures, une table, des décisions ; un peu de code pour

## Exercice 5 — Incident : jamais lent, jamais perdu

*Niveau 7. Un incident réel dans sa forme, fictif dans ses chiffres.*

Deux semaines après le passage au bus asynchrone, l'équipe a reçu cette
demande : « un virement ne doit **jamais** attendre une notification, et une
notification ne doit **jamais** être perdue ». La version 2 du bus
(`ex5/notify`) a été livrée pour cela. Voici sa seule différence avec le bus
de la leçon, qui n'a plus de `Policy` :

```go
// Publish queues e for every subscriber. The handlers get a context that
// keeps the values of ctx but not its cancellation: the request that
// published the event may be over long before the event is handled.
//
// V2: a full queue must never slow a transfer down, and an event must never
// be dropped. When a queue is full, the event waits for room in a goroutine
// of its own, and Publish returns at once.
func (b *Async[E]) Publish(ctx context.Context, e E) error {
    b.mu.RLock()
    defer b.mu.RUnlock()
    if b.closed {
        return ErrClosed
    }
    env := envelope[E]{ctx: context.WithoutCancel(ctx), e: e}
    for _, q := range b.subs {
        select {
        case q.ch <- env:
        default:
            go func() { q.ch <- env }()
        }
    }
    return nil
}
```

Ses tests sont verts sous `-race`. Le jeudi soir, l'opérateur SMS ralentit :
il répond en 10 ms au lieu de 1 ms. Le programme `ex5/cmd/sim` rejoue la
soirée en accéléré : 400 virements par seconde, l'opérateur ralentit à
t = 1 s, et un déploiement arrête le service à t = 2,5 s.
