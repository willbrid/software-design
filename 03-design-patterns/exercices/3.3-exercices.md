### 1.b — Deux compteurs

```go
// Package count wraps writers to count the bytes written through them.
package count

import (
    "io"
    "os"
)

// Writer counts the bytes written through an io.Writer.
type Writer struct {
    io.Writer
    N int64
}

// Write counts, then writes.
func (w *Writer) Write(p []byte) (int, error) {
    n, err := w.Writer.Write(p)
    w.N += int64(n)
    return n, err
}

// File counts the bytes written to a file.
type File struct {
    *os.File
    N int64
}

// Write counts, then writes.
func (f *File) Write(p []byte) (int, error) {
    n, err := f.File.Write(p)
    f.N += int64(n)
    return n, err
}
```

On copie un fichier de 1 000 octets avec `io.Copy(dst, src)`, où `src` est un

2. quand `dst` est `&count.File{File: out}` ?
3. quand `dst` est `&count.File{File: out}` et que `src` est un

Explique le mécanisme. Indice : lis la documentation de
[`io.Copy`](https://pkg.go.dev/io#Copy), et cherche quelles méthodes possède
un `*os.File`.

## Exercice 2 — Code : deux middlewares, et l'ordre qui les lie

*Niveau 2. Écrire du code et ses tests.*

L'API des marchands a déjà un journal d'accès et un handler qui peut
paniquer :

```go
// Package mw holds the HTTP middlewares of the merchant API.
package mw

import (
    "context"
    "fmt"
    "log/slog"
    "net/http"
)

type merchantKey struct{}

// WithMerchant returns a context that carries the merchant's ID.
func WithMerchant(ctx context.Context, merchant string) context.Context {
    return context.WithValue(ctx, merchantKey{}, merchant)
}

// MerchantFrom returns the merchant's ID carried by ctx, or "".
func MerchantFrom(ctx context.Context) string {
    m, _ := ctx.Value(merchantKey{}).(string)
    return m
}

type recorder struct {
    http.ResponseWriter
    status int
}

func (r *recorder) WriteHeader(code int) {
    r.status = code
    r.ResponseWriter.WriteHeader(code)
}

func (r *recorder) Unwrap() http.ResponseWriter { return r.ResponseWriter }

// AccessLog logs method, path, merchant and status of every request.
func AccessLog(log *slog.Logger) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, req *http.Request) {
            rec := &recorder{ResponseWriter: w, status: http.StatusOK}
            next.ServeHTTP(rec, req)
            log.Info("http", "method", req.Method, "path", req.URL.Path,
                "merchant", MerchantFrom(req.Context()), "status", rec.status)
        })
    }
}

// Balance answers the merchant's balance. It panics when the ledger is
// missing, as the real one did in incident INC-207.
func Balance(ledger map[string]int64) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, req *http.Request) {
        if ledger == nil {
            panic("ledger not loaded")
        }
        fmt.Fprintf(w, "%d\n", ledger[MerchantFrom(req.Context())])
    })
}
```

Écris dans le paquet `mw` :

1. **`RequireKey(keys map[string]string) func(http.Handler) http.Handler`** —
   la clé arrive dans l'en-tête `Authorization: Bearer <clé>` ; `keys` associe
   une clé à un identifiant de marchand. Clé absente ou inconnue : réponse
   401, en-tête `WWW-Authenticate: Bearer`, et le handler suivant **n'est pas
   appelé**. Clé connue : le handler suivant reçoit une requête dont le
   contexte porte le marchand (`WithMerchant`).
2. **`Recover(log *slog.Logger) func(http.Handler) http.Handler`** — si le
   handler suivant panique, répondre 500 et écrire une ligne de journal avec
   la valeur de la panique ; le serveur continue de servir. Lis ce que la
   documentation de [`http.Handler`](https://pkg.go.dev/net/http#Handler) dit
   des paniques et de `http.ErrAbortHandler`, et respecte-le.
3. **L'ordre.** Trouve une composition de `AccessLog`, `RequireKey` et
   `Recover` autour de `Balance` telle que :
   - une requête avec une mauvaise clé est journalisée avec `status=401` ;
   - une panique de `Balance` est journalisée par `AccessLog` avec
     `status=500` ;
   - chaque ligne de `AccessLog` d'une requête authentifiée porte le
     `merchant`.

   Tu vas découvrir qu'une de ces trois exigences résiste à toutes les
   permutations. Explique pourquoi, et modifie **le moins de code possible**
   pour la satisfaire.
4. Des tests pour chaque exigence, avec `httptest`.

## Exercice 3 — Refactoring : démêler l'expéditeur de SMS

*Niveau 3. Changer la forme sans changer le comportement — ou en le disant.*

Le service de notifications envoie les codes de connexion par SMS :

```go
// Package sms sends text messages through a provider.
package sms

import (
    "context"
    "errors"
    "log/slog"
    "sync"
    "time"
)

var (
    // ErrUnavailable is returned by a provider that did not answer.
    ErrUnavailable = errors.New("sms: provider unavailable")
    // ErrTooSoon means the number already got a message less than Every ago.
    ErrTooSoon = errors.New("sms: too soon for this number")
)

// Sender sends messages, with a log line per attempt, retries on
// ErrUnavailable, and at most one message per number per Every.
type Sender struct {
    Provider func(ctx context.Context, to, text string) error
    Log      *slog.Logger
    Retries  int
    Every    time.Duration
    Now      func() time.Time

    mu   sync.Mutex
    last map[string]time.Time
}

// Send sends text to the number to.
func (s *Sender) Send(ctx context.Context, to, text string) error {
    s.mu.Lock()
    if t, ok := s.last[to]; ok && s.Now().Sub(t) < s.Every {
        s.mu.Unlock()
        s.Log.Info("sms", "to", to, "err", ErrTooSoon)
        return ErrTooSoon
    }
    if s.last == nil {
        s.last = map[string]time.Time{}
    }
    s.last[to] = s.Now()
    s.mu.Unlock()

    var err error
    for attempt := 0; attempt <= s.Retries; attempt++ {
        err = s.Provider(ctx, to, text)
        s.Log.Info("sms", "to", to, "attempt", attempt, "err", err)
        if err == nil || !errors.Is(err, ErrUnavailable) {
            break
        }
    }
    return err
}
```

Son seul test :

```go
package sms

import (
    "bytes"
    "context"
    "errors"
    "log/slog"
    "testing"
    "time"
)

type clock struct{ t time.Time }

func (c *clock) now() time.Time { return c.t }

func TestSendRetriesThenLimits(t *testing.T) {
    var calls int
    provider := func(context.Context, string, string) error {
        calls++
        if calls == 1 {
            return ErrUnavailable
        }
        return nil
    }
    var buf bytes.Buffer
    c := &clock{t: time.Date(2026, 11, 7, 9, 0, 0, 0, time.UTC)}
    s := &Sender{Provider: provider, Log: slog.New(slog.NewTextHandler(&buf, nil)),
        Retries: 2, Every: 30 * time.Second, Now: c.now}

    if err := s.Send(context.Background(), "+237600000001", "code 1234"); err != nil || calls != 2 {
        t.Fatalf("err = %v after %d calls", err, calls)
    }
    c.t = c.t.Add(10 * time.Second)
    if err := s.Send(context.Background(), "+237600000001", "code 5678"); !errors.Is(err, ErrTooSoon) {
        t.Fatalf("second message 10s later: %v", err)
    }
    c.t = c.t.Add(30 * time.Second)
    if err := s.Send(context.Background(), "+237600000001", "code 9012"); err != nil {
        t.Fatalf("third message 40s later: %v", err)
    }
}
```

1. **Caractérise d'abord.** Dresse la liste de **tous** les comportements de
   `Send`, y compris ceux que personne n'a demandés. Il y en a au moins un qui
   surprend : que devient le quota d'un numéro quand toutes les tentatives
   échouent ? Écris un test pour chacun, contre le code actuel.
2. **Découpe** en une interface `Sender` et trois décorateurs : journal,
   reprises, limite par numéro. Le fournisseur devient l'implémentation de
   base.
3. **Décide de l'ordre** de la limite et des reprises, et justifie-le pour
   l'utilisateur qui attend son code : une reprise doit-elle consommer le
   quota ? Un échec complet doit-il le consommer ?
4. Fais passer tes tests de caractérisation sur la nouvelle forme. Pour
   chaque test que tu modifies, écris **pourquoi** : c'est un changement de
   comportement, il doit être assumé.

## Exercice 4 — Design : l'adaptateur d'un prestataire asynchrone

*Niveau 4. Pas de code attendu : des signatures, une table, des décisions.*

La banque ajoute un second prestataire, BetaPay (fictif). Son API, telle que
sa documentation la décrit :

- `POST /v2/payments` avec `{"amount": "125.00", "currency": "EUR",
  "source": "<jeton>"}` et un en-tête `Idempotency-Key`. Le montant est une
  **chaîne décimale** ; pour une devise sans décimales comme le franc CFA,
  `"125"` veut dire 125 XAF.
- La réponse est `202 Accepted` avec `{"id": "pay_…", "status":
  "processing"}`. Le résultat arrive **plus tard**, par un webhook
  `payment.succeeded` ou `payment.failed`, ou en interrogeant
  `GET /v2/payments/{id}`.
- Les erreurs : `402` avec `{"error": {"type": "card_error", "code":
  "insufficient_funds"}}` ; `409` si la même clé d'idempotence est réutilisée
  avec un corps **différent** ; `429` avec un en-tête `Retry-After` ; `5xx`.

L'interface de la banque est `payment.Gateway` (leçon 3.3) : `Charge` rend un
`Receipt` ou une erreur, `Status` rend `"captured"`, `"pending"` ou
`"unknown"`.

1. Que doit rendre `Charge` quand BetaPay répond `202` ? Envisage au moins
   deux réponses, et dis laquelle **ment** à l'appelant.
2. Ce que l'adaptateur **ne peut pas cacher** : l'asynchronisme. Propose la
   plus petite modification de `payment.Gateway` et de `Receipt` qui le rende
   visible, et dis ce qu'elle casse chez le prestataire existant et dans les
   décorateurs de la leçon.
3. La table de traduction des erreurs : pour chaque réponse de BetaPay,
   l'erreur de la banque, et si le décorateur `Retrying` doit réessayer. Que
   faire du `Retry-After` ?
4. La conversion du montant : écris la règle, cite la source qui donne le
   nombre de décimales de chaque devise, et donne trois cas de test.
5. Le `409` : dans quelle situation la banque peut-elle le provoquer
   elle-même, et qu'est-ce que ça dit d'un bug chez elle ?

## Exercice 5 — Incident : le p99 qui s'améliore

*Niveau 7. Un incident réel dans sa forme, fictif dans ses chiffres.*

Le service de paiement construit sa chaîne ainsi :

```go
// Package pay builds the payment chain of the checkout service.
package pay

import (
    "log/slog"
    "time"

    "example/exercises33/deco"
    "example/exercises33/payment"
)

// V37 is the chain shipped in release 3.7.
func V37(g payment.Gateway, log *slog.Logger) payment.Gateway {
    return deco.Chain(g,
        deco.WithLogging(log),
        deco.WithRetries(2, 200*time.Millisecond),
        deco.WithTimeout(2*time.Second),
    )
}

// V38 is the chain shipped in release 3.8, for ticket PAY-412: "the
// checkout page must answer within one second".
func V38(g payment.Gateway, log *slog.Logger) payment.Gateway {
    return deco.Chain(g,
        deco.WithTimeout(time.Second),
        deco.WithLogging(log),
        deco.WithRetries(2, 200*time.Millisecond),
    )
}
```

La version 3.8 a été livrée le lundi pour le ticket PAY-412, ouvert par
l'équipe de la page de paiement : « le p99 dépasse 2 s, la page doit répondre
en moins d'une seconde ». Le jeudi, le tableau de bord, sur une journée de
48 000 paiements :

| | 3.7 (semaine précédente) | 3.8 |
|---|---|---|
| paiements en échec | 1 sur 48 000 | 1 444 sur 48 000 (3,0 %) |
| latence p50 | 120 ms | 120 ms |
| latence p99 | 2,32 s | 1,00 s |

Le ticket PAY-412 a été fermé le mardi, avec la mention « p99 divisé par
deux ». Le support a ouvert le jeudi le ticket PAY-431 : « des clients disent
que le paiement échoue, puis passe quand ils recommencent ».

Les statistiques du prestataire, inchangées sur les deux semaines : 90 % des
appels répondent en 120 ms environ, 7 % en 600 ms environ, et 3 % ne
répondent jamais (son répartiteur les perd). Chaque tentative est
indépendante des précédentes.

Le journal d'un paiement dont la première tentative est perdue, avant et
après :

```text
release 3.7:
level=INFO msg=charge id=c-31337 amount=12500 err=<nil> took=2.2s
  returned to checkout: <nil>
release 3.8:
level=INFO msg=charge id=c-31337 amount=12500 err="context deadline exceeded" took=1s
  returned to checkout: payment: unavailable: no answer within 1s
```

1. Explique, mécanisme à l'appui, pourquoi les échecs passent de 1 à 1 444
   **et** pourquoi le p99 s'améliore. Calcule, à partir des statistiques du
   prestataire, le taux d'échec attendu de chaque version.
2. Pourquoi le journal dit `context deadline exceeded` alors que la page de
   paiement reçoit `payment: unavailable: no answer within 1s` ?
3. Propose une chaîne qui respecte PAY-412 (réponse en moins d'une seconde)
   avec le taux d'échec le plus bas possible. Calcule son taux d'échec et son
   p99 attendus, puis vérifie-les par une simulation.
4. Écris le test qui aurait empêché la 3.8 de partir.
5. Quel indicateur manquait au tableau de bord pour que PAY-412 ne soit pas
   fermé alors que les échecs étaient devenus plus de mille fois plus
   fréquents ?
