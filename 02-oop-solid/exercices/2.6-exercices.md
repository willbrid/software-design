# Exercices 2.6 — Les limites

**Règles.** Réponds avant d'ouvrir la correction. La question n'est jamais
*« est-ce que c'est trop abstrait ? »* mais **« quel changement ce principe
prépare-t-il, est-il arrivé, et combien a coûté son absence ? »**

Cinq obligations de méthode, valables partout dans ce chapitre :

1. **Avant de lancer quoi que ce soit, écris ta prédiction.** Puis lance, et
   compare. L'écart est l'enseignement.
2. **Une abstraction se juge sur la variante suivante.** Chaque fois que tu
   défends ou attaques une abstraction, ajoute la variante qui vient et donne
   les fichiers existants touchés.
3. **Une découpe se juge sur la co-variation.** Chaque fois que tu défends ou
   attaques une découpe, donne le dernier changement réel et les fichiers
   qu'il a touchés.
4. **Une interface se juge sur ce qu'il y a derrière** : deux
   implémentations, une doublure, ou une frontière que le graphe doit
   respecter. Donne le relevé du sondage.
5. **Chaque chiffre que tu avances doit venir d'une commande.** `go test`,
   `go test -bench`, `go build -gcflags=-m`, `go list`, `git log` — pas
   d'estimation à vue.

Écris tes réponses dans `02-oop-solid/mes-reponses/2.6.md` (dossier local,
ignoré par Git).

## Exercice 1 — Compréhension

Un module de virements. Le sondage des implémentations de la leçon, lancé
sur ses quatre paquets, rend :

```
export.Exporter          production 4 [export.CSV export.CentralBank export.Partner export.Text], tests 0 []
fees.Calculator          production 1 [fees.Schedule], tests 0 []
notification.Notifier    production 1 [notification.SMS], tests 1 [notification.outbox]
storage.Accounts         production 1 [storage.Postgres], tests 0 []
```

Les quatre interfaces :

```go
// Calculator computes the fees.
type Calculator interface {
    Fees(cents int64, international bool) int64
}

// Schedule is the implementation.
type Schedule struct{}

func (Schedule) Fees(cents int64, international bool) int64 {
    if international {
        return 1500 + cents/1000
    }
    return 0
}

// Service applies the calculator.
type Service struct{ C Calculator }

func (s Service) Total(cents int64, international bool) int64 {
    return cents + s.C.Fees(cents, international)
}
```

```go
// Exporter writes lines. The options were added for the central bank's
// format, which needs an issuer code and a separator.
type Exporter interface {
    Export(w io.Writer, lines []Line, options map[string]string) error

```

```go
// Accounts is declared by the business; a single implementation, on
// PostgreSQL. The module's architecture test forbids the business from

type Accounts interface {
    Balance(id string) (int64, error)
}

type Postgres struct{ DB *sql.DB }

func (p Postgres) Balance(id string) (b int64, err error) {
    err = p.DB.QueryRow(`SELECT balance FROM accounts WHERE id = $1`, id).Scan(&b)
    return b, err
```

Et `notification.Notifier`, une méthode `Send(customer, message string)
error`, implémentée par `SMS` et par une doublure dans les tests.

Les quatre implémentations d'`Exporter` : `CSV`, `Text` et `Partner`
écrivent `_ map[string]string` ; `CentralBank` lit `o["issuer"]` et

1. **Avant de lire le relevé** : pour chacune des quatre interfaces, garde,
   supprime, ou transforme ? Écris ta prédiction.

2. **Deux interfaces ont une seule implémentation de production.** L'une doit
   partir, l'autre doit rester. Lesquelles, et quelle est la phrase du
   commentaire qui décide ?

3. **`Notifier` a une implémentation et une doublure.** Est-ce suffisant pour
   la garder ? Donne le critère de la leçon, et dis ce qu'il faudrait pour
   qu'elle soit de trop.

4. **`Exporter` a quatre implémentations**, le sondage n'a rien à dire. Et
   pourtant trois sur quatre ignorent un paramètre. Qu'est-ce que ça mesure ?
   Nomme la section de la leçon, et propose ce que tu fais de `options`.

5. **Supprime `Calculator`.** Combien de fichiers changent, combien de lignes,

6. **Le jour où un deuxième calculateur arrive** — un barème promotionnel —,

7. **Question ouverte.** Un collègue dit : *« le sondage est trop grossier :
   il compte des homonymes, il ne voit pas les interfaces incorporées. On ne
   peut rien décider avec. »* Dis dans quel sens il se trompe, et dans quel
   sens il a raison, en nommant le sens de l'erreur du sondage.

## Exercice 2 — Code

Le calcul des frais d'un virement. L'abstraction a été posée à la deuxième
règle ; voici ce qu'elle est devenue cinq règles plus tard :

```go
// Context is everything a rule may want to know. Each rule that was added
// added what it needed to it.
type Context struct {
    Amount             int64
    Currency           string
    DestCountry        string
    Instant            bool
    PremiumCustomer    bool
    TransfersThisMonth int
    Channel            string // "branch", "web", "mobile"
    Hour               int
    Holiday            bool
}

// Rule adds or removes fees.
type Rule interface {
    Fees(c Context, current int64) int64
}

type Base struct{}

func (Base) Fees(c Context, current int64) int64 { return current + 50 }

type International struct{}

func (International) Fees(c Context, current int64) int64 {
    if c.DestCountry != "FR" {
        return current + 500 + c.Amount/1000
    }
    return current
}

type Instant struct{}

func (Instant) Fees(c Context, current int64) int64 {
    if c.Instant {
        if c.Holiday || c.Hour < 8 || c.Hour >= 20 {
            return current + 150
        }
        return current + 100
    }
    return current
}

type Premium struct{}

func (Premium) Fees(c Context, current int64) int64 {
    if c.PremiumCustomer {
        return current / 2
    }
    return current
}

type Free struct{}

func (Free) Fees(c Context, current int64) int64 {
    if c.Channel != "branch" && c.TransfersThisMonth < 5 && c.DestCountry == "FR" && !c.Instant {
        return 0
    }
    return current
}

// Chain is the order of application. Order matters: Premium halves what the
// previous rules accumulated, Free cancels everything.
var Chain = []Rule{Base{}, International{}, Instant{}, Premium{}, Free{}}

// Compute applies the chain.
func Compute(c Context) int64 {
    var f int64
    for _, r := range Chain {
        f = r.Fees(c, f)
    }
    return f
}
```

Le métier annonce une sixième règle : **un plafond de frais à 20 EUR pour
les virements internationaux des clients premium**, appliqué après la remise
premium.

**Défais l'abstraction, puis décide**, en suivant la procédure de la leçon
(section 10, « la mauvaise abstraction ») :

1. **Mesure l'état actuel.** Pour chaque règle, quels champs du `Context`
   lit-elle ? Donne la matrice règles × champs. Combien de cases remplies sur
   quarante-cinq ? Et `current` : quelles règles le lisent, et pour quoi
   faire ?

2. **Ajoute la sixième règle dans l'abstraction telle quelle.** Fichiers
   touchés, lignes, erreurs de compilation. Puis dis ce que la règle t'a
   obligé à savoir de la **position** des autres dans `Chain`.

3. **Défais.** Remplace la chaîne par une fonction qui calcule les frais
   directement, avec les `if` qu'il faut. Les tests existants restent verts
   **sans être modifiés**.

4. **Ajoute la sixième règle dans la version défaite.** Mêmes trois chiffres.
   Compare.

5. **Faut-il ré-abstraire ?** Dis ce que les six règles ont **vraiment** en
   commun, une fois défaites. Si tu proposes une nouvelle abstraction, donne
   ce qu'elle unit et ce qu'elle laisse dehors ; si tu n'en proposes pas,
   dis quel signal te ferait changer d'avis, et comment tu le mesures.

6. **L'ordre.** Le commentaire de `Chain` affirme que l'ordre compte, et
   nomme `Premium` et `Free`. Vérifie-le avant de le croire : permute
   chaque paire de règles et compte les cas où le résultat change. Puis écris
   le test qui échoue si l'on permute deux règles **dont l'ordre compte
   vraiment** — et dis lesquelles.

7. **Campagne de modifications**, au moins dix sur la version défaite, dont
   une qui permute deux règles, une qui oublie le cas férié, et une qui
   applique le plafond avant la remise. Publie le relevé, nomme les
   survivants, et dis pour chacun s'il réclame un test, une suppression de
   branche, ou rien.

## Exercice 3 — Refactoring

Le plafond d'une carte bancaire, exposé en HTTP : lire, modifier, avec une
règle — entre 100 et 500 000 EUR. Six paquets :

```
ex3/controller/controller.go              47
ex3/dto/dto.go                             7
ex3/entity/entity.go                       8
ex3/mapping/mapping.go                    24
ex3/service/service.go                    41
ex3/store/store.go                        41
```

Le service, typique :

```go
// Package service holds the rule: a limit is between 100 and 500,000 EUR.
package service

import (
    "errors"

    "example/e26/ex3/dto"
    "example/e26/ex3/mapping"
    "example/e26/ex3/store"
)

var ErrOutOfBounds = errors.New("service: limit out of bounds")

type CardLimitService interface {
    Read(card string) (dto.CardLimit, error)
    Update(d dto.CardLimit) error
}

type cardLimitServiceImpl struct {
    store  store.CardLimitStore
    mapper mapping.Mapper
}

func NewCardLimitService(s store.CardLimitStore, m mapping.Mapper) CardLimitService {
    return cardLimitServiceImpl{store: s, mapper: m}
}

func (s cardLimitServiceImpl) Read(card string) (dto.CardLimit, error) {
    e, err := s.store.Read(card)
    if err != nil {
        return dto.CardLimit{}, err
    }
    return s.mapper.ToDTO(e), nil
}

func (s cardLimitServiceImpl) Update(d dto.CardLimit) error {
    if d.Amount < 10_000 || d.Amount > 50_000_000 {
        return ErrOutOfBounds
    }
    return s.store.Write(s.mapper.ToEntity(d))
}
```

Le sondage des implémentations :

```
mapping.Mapper                         production 1, tests 0
service.CardLimitService               production 1, tests 0
store.CardLimitStore                   production 1, tests 0
```

1. **Lis le relevé.** Trois interfaces, une implémentation chacune, aucune
   doublure. Le sondage en oublie une quatrième : laquelle, et pourquoi ne la
   voit-il pas ?

2. **Mesure la co-variation.** Ajoute un champ — la **date d'expiration** du
   plafond, exposée en JSON et stockée. Combien de fichiers ? Puis oublie la
   correspondance (`mapping`), et dis ce qui se passe.

3. **Effondre.** Un seul paquet, `cardlimit`, avec la règle, le stockage et le
   gestionnaire HTTP. Le test du contrôleur reste vert **sans être modifié**,
   au chemin d'import près. Donne les lignes avant et après.

4. **Refais la mesure de la question 2** sur la version effondrée.

5. **Qu'est-ce qui doit rester séparé ?** Le stockage est en mémoire
   aujourd'hui ; demain il sera sur PostgreSQL. Dis ce que tu sépares **ce
   jour-là**, pas avant, et ce que tu mesures pour savoir que c'est le jour.
   Cite la leçon 2.5.

6. **`Version`** est un champ de l'entité qui n'existe pas dans le DTO. Le
   dépôt l'incrémente à chaque écriture, et personne ne le lit. Supprime-le
   ou donne-lui un usage, et justifie par une mesure.

7. **Question ouverte.** L'équipe objecte : *« c'est l'architecture standard
   de l'entreprise, tous les services sont faits comme ça, un développeur qui
   change de service s'y retrouve tout de suite. »* L'argument est réel.
   Chiffre ce qu'il rapporte et ce qu'il coûte sur ce service, et dis ce que
   tu proposes à l'échelle de l'entreprise — pas seulement de ce service.

## Exercice 4 — Design

## Exercice 5 — Incident de production

Prestataire de paiement par carte, 4 200 transactions par seconde à la
pointe. Extrait du post-mortem.

```
lun. 02/03  mise en production du refactoring du moteur de tarification,
            « pour respecter OCP et DIP » : chaque regle de frais devient un
            type, enregistre dans un registre, construit depuis la
            configuration. 412 tests verts, revue approuvee
lun. 02/03 -> ven. 06/03   trafic normal, aucune alerte
ven. 06/03 18:40  pointe du vendredi soir. p99 de l'autorisation :
                  38 ms (habituel : 17 ms). Temps CPU du ramasse-miettes :
                  21 % (habituel : 4 %)
ven. 06/03 18:52  premier depassement du delai de 50 ms impose par le
                  reseau de cartes : 0,4 % des autorisations refusees
                  par expiration
ven. 06/03 19:30  retour arriere du refactoring ; p99 a 16 ms
```

Le code, avant :

```go
// Schedule is loaded at startup; its tiers are sorted once.
type Schedule struct {
    FixedFee        int64
    Tiers           []Tier
    CountryDiscount map[string]int64
}

func NewSchedule(fixed int64, tiers []Tier, discounts map[string]int64) *Schedule {
    t := append([]Tier(nil), tiers...)
    sort.Slice(t, func(i, j int) bool { return t[i].Threshold < t[j].Threshold })
    return &Schedule{FixedFee: fixed, Tiers: t, CountryDiscount: discounts}
}

// Price applies the three rules, in order.
func (s *Schedule) Price(t *Transaction) {
    t.Fees += s.FixedFee
    var rate int64
    for _, tr := range s.Tiers {
        if t.Amount >= tr.Threshold {
            rate = tr.Rate
        }
    }
    t.Fees += t.Amount * rate / 10_000
    t.Fees -= t.Fees * s.CountryDiscount[t.Country] / 10_000
}
```

Et après :

```go
// Factory builds a rule from its configuration parameters.
type Factory func(p Params) Rule

// Params is a rule's configuration.
type Params struct {
    Values map[string]int64
}

var registry = map[string]Factory{
    "commission": func(p Params) Rule { return &commission{fixed: p.Values["fixed"]} },
    "tiers":      newTiers,
    "discount":   func(p Params) Rule { return &discount{byCountry: p.Values} },
}

type commission struct{ fixed int64 }

func (c *commission) Apply(t *Transaction) { t.Fees += c.fixed }

type tier struct{ threshold, rate int64 }

type tiers struct{ t []tier }

// newTiers reads the "threshold:rate" tiers from the parameters.
func newTiers(p Params) Rule {
    r := &tiers{}
    for key, rate := range p.Values {
        var threshold int64
        for _, c := range key {
            threshold = threshold*10 + int64(c-'0')
        }
        r.t = append(r.t, tier{threshold, rate})
    }
    sort.Slice(r.t, func(i, j int) bool { return r.t[i].threshold < r.t[j].threshold })
    return r
}

func (r *tiers) Apply(t *Transaction) {
    var rate int64
    for _, tr := range r.t {
        if t.Amount >= tr.threshold {
            rate = tr.rate
        }
    }
    t.Fees += t.Amount * rate / 10_000
}

type discount struct{ byCountry map[string]int64 }

func (d *discount) Apply(t *Transaction) { t.Fees -= t.Fees * d.byCountry[t.Country] / 10_000 }

// Step is a rule named in the configuration.
type Step struct {
    Name   string
    Params Params
}

// Engine re-reads its configuration on every transaction: a configuration
// change applies without a restart.
type Engine struct{ Steps func() []Step }

func (e Engine) Price(t *Transaction) {
    for _, s := range e.Steps() {
        registry[s.Name](s.Params).Apply(t)
    }
}
```

Établi après coup :

- La configuration de production a **12 étapes**, dont 5 de type
  `tiers` avec chacune une dizaine de tranches.
- Les 412 tests vérifient les montants, et ils sont identiques avant et
  après. Aucun banc de performance n'existe.
- Le tableau de bord suit le p99 et le taux d'erreur. Il ne suit ni les
  allocations, ni le temps du ramasse-miettes.
- La revue a écrit : *« beaucoup plus extensible »*.

### Les questions

1. **Explique le mécanisme en trois phrases**, sans employer le mot
   « interface ».

2. **Mesure-le.** Écris le banc qui compare les deux versions sur la
   configuration de production — douze étapes —, avec `-benchmem`. Donne
   ns/op, B/op et allocations par transaction. Puis `-gcflags=-m` : quelles
   valeurs s'échappent ?

3. **Ramène à la pointe.** À 4 200 transactions par seconde, combien
   d'allocations et d'octets par seconde la version d'après produit-elle ? Le
   chiffre suffit-il à expliquer 21 % de CPU dans le ramasse-miettes ? Dis ce
   que tu sais et ce que tu ne sais pas.

4. **Pourquoi lundi, mardi, mercredi et jeudi n'ont rien montré ?**

5. **Le refactoring visait OCP et DIP. A-t-il eu tort ?** Sépare ce qui coûte
   — l'interface, le registre, la construction par transaction — et mesure
   chaque part. Lequel des trois est la faute ?

6. **Corrige sans revenir en arrière.** Garde les règles comme types et le
   registre, et fais disparaître les allocations du chemin chaud. Mesure.
   Puis dis ce que devient l'exigence « une modification de configuration
   s'applique sans redémarrage ».

7. **La garantie.** Écris le test qui échoue si le chemin chaud de la
   tarification alloue — avec quelle fonction de la bibliothèque standard, et
   quel seuil. Dis ce qu'il ne couvre pas.

8. **« Beaucoup plus extensible. »** Dis ce qui manquait à la demande de
   fusion pour que les relecteurs puissent juger le coût, en une question
   qu'ils auraient dû poser.

9. **Question ouverte.** La direction technique demande : *« plus jamais un
   refactoring de conception qui dégrade la latence »*. Propose la mesure qui
   tire **avant** la production, dis où elle tourne et avec quel seuil, et
   réponds à la question qui décide : **ta mesure aurait-elle vu cet incident
   un lundi matin, à trafic normal ?**
