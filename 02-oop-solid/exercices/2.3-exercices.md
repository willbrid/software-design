# Exercices 2.3 — Composition contre héritage, et pourquoi Go a tranché

**Règles.** Réponds avant d'ouvrir la correction. Pour tous les exercices, la
question n'est jamais *« composition ou héritage ? »* mais **« de laquelle des
trois ai-je besoin : la réutilisation, le sous-typage, ou la spécialisation
ouverte ? »**

Quatre obligations de méthode, valables partout dans ce chapitre :

1. **Avant de lancer quoi que ce soit, écris ta prédiction.** Puis lance, et
   compare. Cette leçon est pleine de cas où la prédiction est fausse, et
   l'écart est l'enseignement.
2. **Chaque fois que tu incorpores un type, applique le critère** : est-ce
   qu'une de ses méthodes appelle une autre de ses méthodes sur son propre
   récepteur ? Si oui, ne surcharge rien.
3. **Chaque fois que tu incorpores un type, compte les méthodes exportées que
   ça ajoute.** Si le nombre n'est pas zéro et que tu ne les voulais pas,
   nomme le champ.
4. **Chaque chiffre que tu avances doit venir d'une commande.** `go test`,
   `go list`, `reflect.Type.NumMethod` — pas d'estimation à vue.

Écris tes réponses dans `02-oop-solid/mes-reponses/2.3.md` (dossier local,
ignoré par Git).

## Exercice 1 — Compréhension

Une plateforme de notification, portée depuis une base Java par une équipe
qui a fait de son mieux. Voilà le code tel qu'il est en production.

```go
// Package notification est l'enonce de l'exercice 1 : la hierarchie telle
// qu'elle a ete portee depuis Java.
package notification

import (
    "errors"
    "strings"
    "time"
)

var ErrEnvoiRefuse = errors.New("notification : envoi refuse")

// Base porte le squelette et les valeurs par defaut.
type Base struct {
    Expediteur string
    Horloge    func() time.Time
}

func (b Base) destinataireValide(d string) bool { return strings.Contains(d, "@") }

func (b Base) sujet(objet string) string { return "[NOTIF] " + objet }

func (b Base) corps(message string) string { return message }

func (b Base) entete() string { return "De: " + b.Expediteur }

// Envoyer est la « methode modele ».
func (b Base) Envoyer(destinataire, objet, message string) (string, error) {
    if !b.destinataireValide(destinataire) {
        return "", ErrEnvoiRefuse
    }
    var sb strings.Builder
    sb.WriteString(b.entete())
    sb.WriteString("\nA: ")
    sb.WriteString(destinataire)
    sb.WriteString("\nSujet: ")
    sb.WriteString(b.sujet(objet))
    sb.WriteString("\n\n")
    sb.WriteString(b.corps(message))
    return sb.String(), nil
}

// SMS « surcharge » trois des quatre morceaux.
type SMS struct {
    Base
    Operateur string
}

func (SMS) destinataireValide(d string) bool { return len(d) == 9 }

func (SMS) sujet(objet string) string { return "" }

func (s SMS) corps(message string) string {
    if len(message) > 160 {
        return message[:157] + "..."
    }
    return message
}

// Courrier « surcharge » l'entete et le corps.
type Courrier struct {
    Base
    CodePostal string
}

func (c Courrier) entete() string { return "Expediteur: " + c.Expediteur + " (courrier)" }

func (c Courrier) corps(message string) string {
    return strings.ToUpper(message) + "\n\nFait a Douala, le " + c.Horloge().Format("2006-01-02")
}
```

1. **Avant de compiler : écris ce que rend chacun de ces trois appels.**
   Donne le texte exact, ligne par ligne.

   ```
   a := SMS{Base: Base{Expediteur: "BANQUE", Horloge: time.Now}, Operateur: "MTN"}
   a.Envoyer("677123456", "Solde", "Votre solde est de 12 400 FCFA")

   b := Courrier{Base: Base{Expediteur: "BANQUE", Horloge: time.Now}, CodePostal: "BP 1234"}
   b.Envoyer("client@example.cm", "Releve", "Votre releve est disponible")

   c := Base{Expediteur: "BANQUE", Horloge: time.Now}
   c.Envoyer("client@example.cm", "Solde", "Votre solde est de 12 400 FCFA")
   ```

   Puis compile et lance. Combien des trois avais-tu prédits juste ?

2. **Le premier appel.** `SMS` surcharge `destinataireValide` pour accepter un
   numéro à neuf chiffres. Que renvoie `a.Envoyer("677123456", ...)` et
   pourquoi ? Quelle erreur un client reçoit-il, et quelle erreur un
   développeur verrait-il dans les journaux ?

3. **Applique le critère** à `Base`. Combien de ses méthodes appellent une
   autre de ses méthodes sur son propre récepteur ? Nomme-les. Et dis ce que
   ça implique pour `SMS` et `Courrier`.

4. **Compte les méthodes exportées** de `Base`, de `SMS` et de `Courrier`. Les
   trois nombres sont-ils ceux que tu attendais ? Et le champ `Horloge func()
   time.Time` : qu'est-ce qu'il ajoute à l'interface publique de `SMS` ?

5. **Le champ `Operateur` de `SMS` et `CodePostal` de `Courrier` ne sont
   utilisés nulle part.** Ce n'est pas un hasard — explique pourquoi la forme
   du code les a rendus inutilisables depuis `Envoyer`.

6. **Propose la correction**, et donne le diff conceptuel : qu'est-ce qui
   devient une fonction, qu'est-ce qui devient une interface, combien de
   méthodes a cette interface, et où est-elle déclarée ?

7. **Question ouverte.** L'équipe a 23 tests sur ce paquet, tous verts, et
   94 % de couverture. Décris précisément la forme qu'ont forcément ces tests
   pour être verts alors que le code est faux. Puis donne **un** test, en une
   phrase, qui aurait été rouge dès le premier jour.

## Exercice 2 — Code

Chaîne de traitement de virements internationaux pour une banque. Chaque
virement passe par cinq étapes, toujours dans le même ordre :

| Étape | Ce qu'elle fait | Varie selon le corridor ? |
|---|---|---|
| **1. valider** | format de l'IBAN ou du numéro de compte, montant plafonné | **oui** |
| **2. convertir** | passage de la devise source à la devise cible | **oui** |
| **3. tarifer** | frais fixes et variables | **oui** |
| **4. consigner** | écriture au journal des opérations | non |
| **5. notifier** | message au donneur d'ordre | non |

Trois corridors sont en production : `FCFA→EUR` (zone CEMAC vers SEPA),
`FCFA→USD` (vers correspondant américain), `FCFA→FCFA` (interne, sans
conversion). Un quatrième — `FCFA→NGN` — est annoncé pour le trimestre
prochain.

**Écris le paquet**, et il doit vérifier tout ce qui suit :

1. **Le squelette est une fonction**, et les cinq étapes sont appelées dans
   l'ordre. Un test doit vérifier l'ordre, et il doit s'observer **depuis le
   point intermédiaire** — tu as la raison depuis la leçon 2.2.
2. **Les trois étapes variables sont derrière une interface déclarée par le
   squelette**, et sa signature ne doit nommer que des types du domaine.
   Prouve-le par `go list`.
3. **Les deux étapes fixes ne sont pas dans l'interface.** Justifie-le avec le
   critère de la leçon 2.2 sur ce qui appartient à la variante.
4. **Un corridor absent est une erreur**, pas un corridor par défaut. Dis
   pourquoi, en une phrase, en citant l'incident de la correction 2.2/5.
5. **Aucun type du paquet n'incorpore un type qui a des appels internes.**
   Vérifie-le avec un sondage `go/ast`, ou explique pourquoi tu peux t'en
   passer.
6. **Le journal des opérations enregistre le corridor retenu AVANT la
   conversion**, et un test le prouve.

Puis les mesures :

7. **Ajoute le quatrième corridor.** Combien de fichiers de production
   faut-il toucher ? Le compilateur en trouve-t-il un seul ? Lesquels de tes
   tests tombent, et dans quel ordre ?
8. **Ajoute une sixième étape** (« vérifier la liste des personnes
   sanctionnées », qui ne varie pas par corridor). Combien de fichiers ?
   Combien de corridors ont changé ?
9. **Écris volontairement la version avec incorporation et méthode-modèle**,
   dans un paquet `avant`, et mesure que les trois corridors rendent le même
   résultat. Garde ce paquet : c'est ta démonstration.
10. **Campagne de modifications**, au moins dix, dont une qui retire une étape
    du squelette, une qui inverse deux étapes, une qui remplace un champ nommé
    par une incorporation, et une qui ajoute une méthode `String()` à un type
    incorporé. Publie le relevé, nomme les survivants, et dis pour chacun s'il
    réclame un test, une suppression de branche, ou rien.

## Exercice 3 — Refactoring

Voilà du code réel, simplifié mais pas déformé. C'est la passerelle d'appel
d'un service interne, et son auteur a incorporé quatre choses pour pouvoir
écrire `s.Maintenant()` au lieu de `s.horloge.Maintenant()`.

```go
// Service est le type de l'exercice.
//
// Il incorpore quatre choses, et son auteur l'a fait pour pouvoir ecrire
// s.Maintenant() plutot que s.horloge.Maintenant().
type Service struct {
    Horloge
    *Compteur
    *log.Logger
    sync.Mutex
    URL string
}

func (s *Service) Appeler(chemin string) (string, error) {
    s.Lock()
    defer s.Unlock()
    s.Incrementer(chemin)
    s.Printf("appel de %s a %s", chemin, s.Maintenant().Format(time.RFC3339))
    if s.URL == "" {
        return "", ErrIndisponible
    }
    return s.URL + chemin, nil
}
```

1. **Compte l'interface publique.** Combien de méthodes `*Service` exporte-t-il ?
   Combien son auteur en a-t-il déclaré ? Donne la liste de l'écart, obtenue
   par `reflect`, pas à la main.

2. **Trouve les trois interfaces de la bibliothèque standard** que `*Service`
   satisfait sans que personne ne l'ait voulu. Pour chacune, dis ce qu'un code
   générique pourrait en faire.

3. **Il y a un interblocage latent dans `Appeler`.** Trouve-le. Indice : lis la
   première ligne et la troisième, et demande-toi combien de mutex sont en jeu.

4. **Il y a un deuxième défaut, de concurrence, et il ne vient pas d'un
   mutex.** Trouve-le, et dis comment tu le prouverais — `go test -race`
   suffit-il ?

5. **`s.Printf` est appelé sur un `*log.Logger` incorporé.** Que se passe-t-il
   si ce champ est nul ? Compare avec ce qui se passe si `*Compteur` est nul.
   Les deux modes de panne sont-ils les mêmes ?

6. **Refactore.** Donne la nouvelle déclaration de `Service`, et compte à
   nouveau les méthodes exportées. Puis dis combien de caractères par appel ta
   correction coûte, et combien de lignes elle supprime.

7. **La question qui compte.** Un développeur de l'équipe objecte : *« avec
   des champs nommés, il faut écrire `s.horloge.Maintenant()` partout, c'est
   verbeux et ça n'apporte rien »*. Réponds-lui en trois phrases, dont une
   qui chiffre.

8. **Question ouverte.** La version suivante de Go — ou de l'une des
   bibliothèques utilisées — ajoute une méthode à l'un des quatre types
   incorporés. Décris les **trois** choses différentes qui peuvent arriver à
   ton code, de la plus visible à la plus silencieuse. Puis propose un test
   qui attrape la troisième.

## Exercice 4 — Design

Chaîne de traitement HTTP pour une API bancaire. Six préoccupations
transverses doivent s'appliquer à chaque requête, et elles sont composables :

| Préoccupation | Ce qu'elle fait |
|---|---|
| journalisation | une ligne par requête, avec la durée |
| authentification | rejette si le jeton est absent ou expiré |
| limitation de débit | rejette au-delà de N requêtes par minute et par client |
| trace distribuée | propage et génère un identifiant de corrélation |
| récupération de panique | transforme une panique en réponse 500 |
| compression | compresse la réponse si le client l'accepte |

Trois exigences du métier :

- l'ordre d'application est **significatif** et doit être explicite ;
- certaines routes n'ont **pas** d'authentification (la page de santé) et
  d'autres **pas** de limitation (les appels internes) ;
- une équipe partenaire doit pouvoir ajouter sa propre préoccupation, dans
  son propre dépôt.

1. **Choisis le mécanisme**, et justifie-le par la question des trois. Est-ce
   que l'incorporation a un rôle ici ? Lequel, exactement, et pour laquelle
   des six ?

2. **Écris l'interface**, et dis combien de méthodes elle a et pourquoi. Puis
   dis où elle est déclarée, et montre par `go list` que les préoccupations
   n'importent pas leur appelant.

3. **La composition.** Écris le mécanisme qui enchaîne les préoccupations.
   Deux formes sont possibles — une enveloppe qui incorpore l'interface, et
   une fonction qui prend une liste. Écris **les deux**, et donne trois
   critères mesurables pour choisir.

4. **La récupération de panique doit être la première ou la dernière ?**
   Réponds, puis écris le test qui prouve ta réponse — et ce test doit
   échouer si on inverse l'ordre.

5. **L'ordre.** Donne l'ordre que tu retiens pour les six, et pour chaque
   paire adjacente dis ce qui se casse si on l'inverse. Au moins deux de ces
   inversions doivent être attrapées par un test.

6. **Les routes sans authentification.** Trois propositions arrivent :

   | | Proposition |
   |---|---|
   | A | une liste de chemins exemptés dans la préoccupation d'authentification |
   | B | une chaîne différente par groupe de routes |
   | C | une méthode `Exempte(chemin string) bool` sur l'interface |

   Pour chacune : ce qu'elle permet, ce qu'elle coûte, et ce qui se passe le
   jour où une septième préoccupation a aussi des exemptions. Laquelle
   choisis-tu ?

7. **L'équipe partenaire.** Qu'est-ce qu'elle doit importer de chez toi ?
   Qu'est-ce qu'elle ne doit surtout pas avoir à importer ? Et si elle
   incorpore ton type d'enveloppe pour « hériter du comportement par défaut »,
   qu'est-ce qui va mal se passer ?

8. **Question ouverte.** La direction technique veut une garantie : *« qu'une
   requête ne puisse plus jamais traverser la chaîne sans être tracée »*.

   Propose :
   - **une propriété du modèle** qui rend la classe entière du problème
     impossible — et dis honnêtement ce qu'elle ne couvre pas ;
   - **ce qu'elle interdit**, chiffré ;
   - **une mesure** pour le reste, avec son seuil et son plancher de bruit ;
   - et la question de ce chapitre : **à quelle condition ta propriété survit-elle
     au prochain développeur qui ajoutera une préoccupation ?**

## Exercice 5 — Incident de production

API de consultation de comptes d'une banque, 180 000 requêtes par jour.
Extrait du post-mortem.

```
mer. 03/06 14:20  deploiement de la version 4.12.0. Rien de notable au
                  tableau de bord : latence stable, taux d'erreur a 2 pour mille
mer. 03/06 -> dim. 14/06   rien
dim. 14/06 09:15  un client entreprise appelle : « votre API nous renvoie des
                  erreurs 500 depuis une semaine, on a basculé sur l'export CSV »
dim. 14/06 11:40  reconstitution : depuis le 03/06, 100 % des reponses de
                  /comptes/{id}/operations sont des 500. 214 000 requetes.
                  Zero client n'avait signale avant le 14
lun. 15/06 09:00  reunion de crise. La question posee est « comment le
                  tableau de bord a pu rester vert »
```

Le code de la version 4.12.0, pour la partie qui compte :

```go
// Package reponse est l'enonce de l'exercice 5 : le code du jour de
// l'incident, reproduit.
package reponse

import "fmt"

// Incident est la trace d'un probleme rencontre pendant le traitement.
//
// Elle porte une methode Error() parce que le code interne la remonte parfois
// comme une erreur, et c'est legitime.
type Incident struct {
    Code     string
    Detail   string
    Bloquant bool
}

func (i Incident) Error() string {
    return fmt.Sprintf("incident %s : %s", i.Code, i.Detail)
}

// Reponse est ce que le gestionnaire HTTP rend.
//
// Elle incorpore Incident pour que le code puisse ecrire r.Code plutot que
// r.incident.Code. Les trois champs utiles sont Donnees, Total et Page.
type Reponse struct {
    Incident
    Donnees []string
    Total   int
    Page    int
}

// Traiter rend une reponse. Elle ne rend JAMAIS d'erreur : les problemes
// non bloquants sont dans l'incident incorpore.
func Traiter(page int) Reponse {
    return Reponse{
        Donnees: []string{"a", "b", "c"},
        Total:   3,
        Page:    page,
    }
}
```

Et l'intergiciel qui écrit la réponse HTTP, inchangé depuis deux ans :

```
func ecrire(w http.ResponseWriter, v any) {
    if err, ok := v.(error); ok {
        w.WriteHeader(http.StatusInternalServerError)
        _ = json.NewEncoder(w).Encode(map[string]string{"erreur": err.Error()})
        return
    }
    w.WriteHeader(http.StatusOK)
    _ = json.NewEncoder(w).Encode(v)
}
```

Établi après coup :

- La version 4.11.0 déclarait `type Reponse struct { incident Incident; Donnees []string; ... }`
  — avec un champ **nommé**.
- La version 4.12.0 a renommé le champ en l'incorporant, dans un commit
  intitulé « simplifie l'accès aux champs de l'incident ».
- Le commit a été relu et approuvé par deux personnes.
- Les tests du paquet `reponse` : 41 tests, 97 % de couverture, tous verts
  avant comme après.
- Les tests de l'intergiciel : 12 tests, tous verts.
- Le tableau de bord suit le **taux d'erreur applicatif** : le nombre de fois
  où un gestionnaire rend une erreur non nulle, divisé par le nombre de
  requêtes. Il est resté à 2 pour mille.
- Les journaux d'accès du serveur contiennent bien 214 000 lignes avec le code
  500.

### Les questions

1. **Explique le mécanisme en trois phrases**, sans employer le mot
   « héritage ».

2. **Les 41 tests du paquet `reponse` et les 12 de l'intergiciel étaient tous
   verts.** Explique précisément pourquoi aucun des 53 ne pouvait voir le
   problème. Il y a deux raisons différentes, une par paquet.

3. **Écris le test**, en une phrase puis en code, qui aurait été rouge le
   03/06. Il doit porter sur le paquet `reponse` et ne rien savoir de
   l'intergiciel.

4. **Onze jours.** Décompose-les : détection, qualification, diagnostic.
   Lequel des trois la conception pouvait-elle réduire, et de combien ?

5. **Le tableau de bord est resté à 2 pour mille.** Explique pourquoi cet
   indicateur ne pouvait pas bouger, et dis ce qu'il mesurait réellement.
   Puis propose l'indicateur qui aurait tiré, avec son seuil, et dis à quelle
   heure il aurait tiré le 03/06.

6. **« Zéro client n'avait signalé avant le 14 ».** C'est l'information la
   plus inquiétante du post-mortem, et elle ne concerne pas le code. Dis
   pourquoi, et ce que ça change à tes priorités de correction.

7. **La correction.** Quatre propositions arrivent :

   | | Proposition |
   |---|---|
   | A | revenir au champ nommé |
   | B | renommer `Incident.Error()` en `Incident.Message()` |
   | C | dans l'intergiciel, remplacer l'assertion de type par un champ explicite dans la réponse |
   | D | ajouter à l'intergiciel une liste de types qui ne doivent pas être traités comme des erreurs |

   Pour chacune : ce qu'elle empêche, ce qu'elle n'empêche pas, ce qu'elle
   coûte, et **ce qui se passe le jour où un deuxième type incorpore
   `Incident`**. Laquelle choisis-tu, et dans quel ordre déploies-tu ?

8. **Le commit a été relu par deux personnes.** Qu'est-ce qu'une relecture
   aurait dû chercher pour l'attraper ? Formule-le comme une question à poser
   sur **tout** commit qui transforme un champ nommé en champ incorporé.

9. **Question ouverte.** La direction demande une garantie : *« qu'une méthode
   promue ne puisse plus jamais changer le comportement d'un type sans qu'on
   le sache »*.

   « On fera attention » est faux. « On n'incorporera plus rien » est faux
   aussi, et tu dois pouvoir dire pourquoi en deux phrases.

   Propose donc :
   - **une propriété ou un contrôle** qui rend la classe entière de ce bug
     visible, et dis à quel moment il tire — relecture, compilation, test,
     ou production ;
   - **l'endroit exact** où il vit, et pourquoi pas un autre — tu as un
     critère depuis la 2.1 sur le niveau le plus bas qui puisse porter un
     garde-fou, et un autre depuis la 2.2/4 sur la racine de composition ;
   - **ce qu'il coûte**, chiffré en ce qu'il interdit ;
   - **une mesure** pour ce qu'il ne couvre pas, avec son seuil ;
   - et la question qui décide de tout : **ton contrôle attrape-t-il le cas où
     c'est la bibliothèque, et non ton code, qui ajoute la méthode ?** Si non,
     dis ce qu'il faut en plus.
