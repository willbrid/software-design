# Leçon 2.4 — SOLID : SRP, OCP, LSP

## L'essentiel en deux minutes

**Le problème, en une phrase.** SOLID est répété partout et appliqué
nulle part, parce que ses principes sont flous ; cette leçon donne à trois
d'entre eux un **test** qu'on peut faire sur du code.

**L'image.** Une prise électrique murale.

- **SRP** (responsabilité unique) : le compteur, les prises et l'éclairage
  sont sur des circuits séparés, parce que ce ne sont pas les mêmes
  personnes qui les font changer.
- **OCP** (ouvert/fermé) : brancher un **nouvel appareil** ne demande pas de
  refaire l'installation. Passer du 220 V au 110 V, si. Un système est
  ouvert sur un **axe**, jamais sur tous.
- **LSP** (substitution de Liskov) : un appareil qui a la bonne prise mais
  consomme dix fois trop « rentre » dans le mur et fait sauter le compteur.
  Avoir la bonne **forme** ne suffit pas : il faut tenir la **promesse**.

**Le code, en une cinquantaine de lignes.**

```go
// Package e24 is the two-minute version of lesson 2.4.
package e24

import (
    "errors"
    "strings"
)

// ErrNotFound is part of the contract of Store.
var ErrNotFound = errors.New("not found")

// Store keeps values by key. Contract: Get after Put returns the value;
// Get of an unknown key returns ErrNotFound; keys are case-sensitive.
type Store interface {
    Put(key, value string)
    Get(key string) (string, error)
}

// Memory keeps the contract.
type Memory map[string]string

func (m Memory) Put(key, value string) { m[key] = value }

func (m Memory) Get(key string) (string, error) {
    v, ok := m[key]
    if !ok {
        return "", ErrNotFound
    }
    return v, nil
}

// Upper compiles as a Store, and breaks the contract: it folds the case.
type Upper map[string]string

func (u Upper) Put(key, value string) { u[strings.ToUpper(key)] = value }

func (u Upper) Get(key string) (string, error) {
    v, ok := u[strings.ToUpper(key)]
    if !ok {
        return "", ErrNotFound
    }
    return v, nil
}

// Check is the contract written once, run against any implementation. It
// returns the clauses the store breaks.
func Check(s Store) []string {
    var broken []string
    s.Put("a", "1")
    if v, err := s.Get("a"); v != "1" || err != nil {
        broken = append(broken, "Get after Put")
    }
    if _, err := s.Get("missing"); !errors.Is(err, ErrNotFound) {
        broken = append(broken, "unknown key gives ErrNotFound")
    }
    if _, err := s.Get("A"); !errors.Is(err, ErrNotFound) {
        broken = append(broken, "keys are case-sensitive")
    }
    return broken
}
```

`Upper` compile comme un `Store` : le compilateur Go ne vérifie que les
**signatures**. Mais il range `"a"` et `"A"` au même endroit, alors que le
contrat dit que les clés distinguent les majuscules. `Check` est le contrat
écrit une fois, en code, et passé à chaque implémentation : il trouve
exactement la clause que `Upper` viole.

**Les règles à retenir.**

1. SRP se **sonde** : regroupe les méthodes selon les champs qu'elles
   touchent ; deux groupes séparés, deux types.
2. OCP se **compte** : « fermé » veut dire « le compilateur se tait » quand on
   ajoute une variante. Ajouter une opération, elle, casse — c'est l'autre
   axe.
3. LSP se **teste** : une batterie de contrat, écrite une fois et passée à
   toutes les implémentations, comme `testing/fstest.TestFS` le fait pour
   les systèmes de fichiers.
4. Les erreurs sentinelles (`ErrNotFound`) font partie du contrat de
   l'interface.
5. Une violation de Liskov typique en Go : refuser une entrée que les autres
   acceptent, rendre moins que promis, paniquer là où les autres rendent une
   erreur.

SOLID a trente ans. Les cinq principes sont dans tous les entretiens
d'embauche, et dans à peu près aucune revue de code — parce qu'on ne sait pas
quoi en faire. *« Une classe, une responsabilité »* : combien de
responsabilités a `UserService` ? Personne ne sait, et deux développeurs
compétents répondent deux choses différentes.

Cette leçon ne va pas répéter les énoncés. Elle va faire une seule chose,
trois fois :

> Prendre un principe, montrer que sa formulation courante **n'est pas
> mesurable**, en donner une qui l'est, et **la mesurer** — avec du code qui
> compile et une commande qu'on peut lancer.

Les trois principes de cette leçon ne sont pas de même nature, et il faut le
dire tout de suite, parce que c'est ce qui décide de ce qu'on peut en faire :

| | Ce que le principe décide | Qui peut le vérifier |
|---|---|---|
| **SRP** | où **couper** | un sondage sur le code — mécanique, avec un faux négatif connu |
| **OCP** | sur quel **axe** on est ouvert | un **diff** : on ajoute la variante et on compte les fichiers |
| **LSP** | ce qu'une implémentation **promet** | une **batterie de tests**, parce que le compilateur ne vérifie que les signatures |

Tout ce qui suit est mesuré sur un module de douze paquets qui passe sous
`gofmt -l`, `go vet ./...` et `go test -race -count=1 ./...`.

## 1. Les trois énoncés, et les trois reformulations

### SRP — Single Responsibility Principle

> *« Un module ne doit avoir qu'une seule raison de changer. »*

C'est la formulation de Robert Martin, et c'est déjà mieux que « une seule
responsabilité » : elle parle de **changement**, donc de temps, donc de
quelque chose qu'on peut observer. Sa version la plus précise, du même auteur,
parle d'**acteurs** : un module ne doit répondre qu'à un seul acteur — un
service de l'entreprise, un rôle, une personne qui demande des modifications.

Elle reste inutilisable telle quelle devant un fichier : on ne lit pas les
acteurs dans le code.

La reformulation mesurable :

> **Partitionne les méthodes d'un type par l'ensemble des champs du récepteur
> qu'elles touchent. Deux méthodes sont reliées si elles partagent un champ.
> S'il y a deux composantes connexes, il y a deux types.**

Cette mesure porte un nom : c'est une variante de **LCOM4** (*Lack of
Cohesion of Methods*, quatrième formulation, Hitz et Montazeri, 1995). Elle a
un faux négatif, elle a un faux positif, et les deux sont mesurés en
section 2.

### OCP — Open/Closed Principle

> *« Un module doit être ouvert à l'extension et fermé à la modification. »*

Pris littéralement, c'est contradictoire : étendre un module, c'est le
modifier. La leçon 2.2 a déjà donné la clé — l'ouverture est **un choix
d'axe**, et un module ouvert aux nouvelles variantes est fermé aux nouvelles
opérations. La reformulation mesurable :

> **Un module est ouvert sur un axe si ajouter une variante sur cet axe ne
> modifie aucun fichier existant. La mesure est un `diff` : on ajoute la
> variante, et on compte les fichiers touchés, les erreurs de compilation et
> les tests rouges.**

Les trois chiffres comptent, et le deuxième est le moins intuitif : **sur
l'axe ouvert, le compilateur se taira**. C'est le prix de l'ouverture, et la
section 3 le chiffre.

### LSP — Liskov Substitution Principle

> *« Si S est un sous-type de T, un objet de type T peut être remplacé par un
> objet de type S sans altérer la correction du programme. »*

C'est l'énoncé de Barbara Liskov, 1987, et c'est le seul des trois qui soit
un théorème plutôt qu'un conseil. En Go, il n'y a pas de sous-classes : il
s'applique aux **implémentations d'une interface**. Et il s'y applique
durement, pour une raison précise :

> Le compilateur Go vérifie qu'une implémentation a les bonnes
> **signatures**. Il ne vérifie rien d'autre. Tout ce que le contrat dit en
> plus — les erreurs rendues, le traitement du cas absent, l'ordre, la
> copie, la sûreté en concurrence — **n'est vérifié par personne**.

La reformulation mesurable :

> **Une implémentation respecte LSP si et seulement si elle passe la batterie
> de contrat de l'interface : un test écrit une fois, paramétré par
> l'implémentation.**

Ce n'est pas une invention de cette leçon. La bibliothèque standard fait
exactement ça depuis Go 1.16 : `testing/fstest.TestFS` est la batterie de
contrat de `fs.FS`, et elle existe parce que `fs.FS` promet des choses que sa
signature ne dit pas.

## 2. SRP : couper là où le sondage coupe

### Le sujet

```go
// StatementService does everything about statements.
//
// Six fields, five methods, and the question is: how many types?
type StatementService struct {
    entries    map[string][]Entry
    clock      func() time.Time
    fixedFee   int64
    feePerLine int64
    currency   string
    log        io.Writer
}
```

Six champs, cinq méthodes. Combien de types ? La question « combien de
responsabilités » n'a pas de réponse ; la question « combien de composantes »
en a une.

### Le sondage

```go
func touchedFields(fn *ast.FuncDecl, receiver string, fields []string) []string {
    known := map[string]bool{}
    for _, f := range fields {
        known[f] = true
    }
    seen := map[string]bool{}
    ast.Inspect(fn, func(n ast.Node) bool {
        sel, ok := n.(*ast.SelectorExpr)
        if !ok {
            return true
        }
        id, ok := sel.X.(*ast.Ident)
        if !ok || id.Name != receiver {
            return true
        }
        if known[sel.Sel.Name] {
            seen[sel.Sel.Name] = true
        }
        return true
    })
    var list []string
    for f := range seen {
        list = append(list, f)
    }
    sort.Strings(list)
    return list
}
```

```go
// components returns the groups of methods linked by a common field, and the
// list of the methods that touch no field.
func components(methods []Method) ([][]string, []string) {
    var isolated []string
    var useful []Method
    for _, m := range methods {
        if len(m.Fields) == 0 {
            isolated = append(isolated, m.Name)
            continue
        }
        useful = append(useful, m)
    }
    parent := make([]int, len(useful))
    for i := range parent {
        parent[i] = i
    }
    var root func(int) int
    root = func(i int) int {
        for parent[i] != i {
            parent[i] = parent[parent[i]]
            i = parent[i]
        }
        return i
    }
    for i := range useful {
        for j := i + 1; j < len(useful); j++ {
            if share(useful[i].Fields, useful[j].Fields) {
                parent[root(i)] = root(j)
            }
        }
    }
    groups := map[int][]string{}
    for i, m := range useful {
        r := root(i)
        groups[r] = append(groups[r], m.Name)
    }
    var list [][]string
    for _, g := range groups {
        sort.Strings(g)
        list = append(list, g)
    }
    sort.Slice(list, func(i, j int) bool { return list[i][0] < list[j][0] })
    return list, isolated
}
```

**Une composante.** `Add` et `Bill` partagent le journal, donc tout

> Un champ **transverse** — un journal, une horloge, un compteur, une

> nommément, et **la liste des exclusions est elle-même une information** :
> c'est la liste de ce qui traverse le type sans lui appartenir.

Deux composantes, et elles ont un **sens métier** qu'on n'a pas eu à chercher :

| Composante | Acteur | Ce qu'il demande |
|---|---|---|
| `Add`, `Generate` | la comptabilité | des changements de **contenu et de format** du relevé |
| `Bill`, `Price` | la direction commerciale | des changements de **montant et de devise** |

Le sondage ne connaît pas les acteurs. Il a trouvé la coupe qui les sépare,
en lisant uniquement quels champs quelles méthodes touchent. C'est ça que SRP
veut dire, et c'est pour ça qu'il est mesurable : **deux acteurs qui ne
parlent pas des mêmes données laissent une trace dans la structure du code.**

Et `Format` est **isolée** : elle ne touche aucun champ du service. Une
méthode qui ne lit que ses arguments n'est pas une méthode.

### Après la coupe

```go
// Ledger is the general ledger: it keeps the entries and draws statements
// from them.
//
// Its actor is accounting. It asks for changes of FORMAT and CONTENT of the
// statement.
type Ledger struct {
    entries map[string][]Entry
    clock   func() time.Time
    log     io.Writer
}

// NewLedger builds the general ledger.
func NewLedger(clock func() time.Time, log io.Writer) *Ledger {
    return &Ledger{entries: map[string][]Entry{}, clock: clock, log: log}
}

// Add posts an entry.
func (l *Ledger) Add(e Entry) {
    l.entries[e.Account] = append(l.entries[e.Account], e)
    fmt.Fprintf(l.log, "entry added on %s\n", e.Account)
}

// Generate builds the statement of an account.
func (l *Ledger) Generate(account string) (Statement, error) {
    lines, known := l.entries[account]
    if !known {
        return Statement{}, fmt.Errorf("%w: %q", ErrUnknownAccount, account)
    }
    sorted := make([]Entry, len(lines))
    copy(sorted, lines)
    sort.Slice(sorted, func(i, j int) bool { return sorted[i].Instant.Before(sorted[j].Instant) })
    var balance int64
    for _, e := range sorted {
        balance += e.Cents
    }
    return Statement{Account: account, Lines: sorted, Balance: balance, Issued: l.clock()}, nil
}
```

```go
// Tariff is the fee schedule of the statements.
//
// Its actor is the sales department. It asks for changes of AMOUNT and
// CURRENCY, and it has never asked for a change of statement format.
type Tariff struct {
    fixed    int64
    perLine  int64
    currency string
    log      io.Writer
}

// NewTariff builds the schedule.
func NewTariff(fixed, perLine int64, currency string, log io.Writer) *Tariff {
    return &Tariff{fixed: fixed, perLine: perLine, currency: currency, log: log}
}

// Price computes the fees of a statement.
//
// Note the argument: the schedule does not take a Statement, it takes the
// number of lines. It is what the cut revealed — pricing never needed the
// statement, only its size — and it is what allows pricing without having
// generated.
func (t *Tariff) Price(lines int) int64 {
    return t.fixed + int64(lines)*t.perLine
}

// Bill builds the invoice.
func (t *Tariff) Bill(account string, lines int) Invoice {
    amount := t.Price(lines)
    fmt.Fprintf(t.log, "invoice issued for %s: %d %s\n", account, amount, t.currency)
    return Invoice{
        Account:  account,
        Cents:    amount,
        Currency: t.currency,
        Detail: fmt.Sprintf("%d %s fixed fees + %d lines at %d %s",
            t.fixed, t.currency, lines, t.perLine, t.currency),
    }
}
```

```go
// the service. A method that only reads its arguments is not a method.

    fmt.Fprintf(&sb, "Statement of account %s at %s\n", s.Account, s.Issued.Format("2006-01-02"))
    for _, e := range s.Lines {
        fmt.Fprintf(&sb, "  %s  %-20s %10d\n", e.Instant.Format("2006-01-02"), e.Label, e.Cents)
    }
    fmt.Fprintf(&sb, "Balance: %d\n", s.Balance)

}
```

`Price` ne prend plus un `Statement` : elle prend un **nombre de lignes**. Elle
n'a jamais eu besoin du relevé, seulement de sa taille — et on ne pouvait pas
le voir tant que les deux vivaient dans le même type.

> Couper un type ne déplace pas seulement du code : ça **révèle les
> dépendances que la cohabitation cachait**. Ici, une facturation qui n'a
> jamais eu besoin d'un relevé.

Avec, bien sûr, l'épreuve de non-régression :

```
same statement, same formatting, same fees (55000 cents) — and two types instead of one
```

### Le faux négatif, mesuré

Une mesure dont on ne connaît pas les faux négatifs ne sert à rien.

```go
// Package limit holds the false negative of the cohesion probe.
package limit

import (
    "strings"
    "unicode"
)

// Account holds an IBAN, and two responsibilities on it.
type Account struct {
    iban string
}

// NewAccount builds an account.
func NewAccount(iban string) *Account { return &Account{iban: iban} }

// Valid checks that the IBAN has the expected shape.
//
// Its actor is regulatory compliance. When the BEAC changes the length of an
// IBAN, it is this method that changes.
func (a *Account) Valid() bool {
    s := strings.ToUpper(strings.ReplaceAll(a.iban, " ", ""))
    if len(s) < 15 || len(s) > 34 {
        return false
    }
    for i, r := range s {
        if i < 2 && !unicode.IsLetter(r) {
            return false
        }
        if i >= 2 && !(unicode.IsLetter(r) || unicode.IsDigit(r)) {
            return false
        }
    }
    return true
}

// Masked returns the IBAN for display, with the middle digits hidden.
//
// Its actor is customer service. When customer service wants to show four
// digits instead of two, it is this method that changes.
func (a *Account) Masked() string {
    s := strings.ToUpper(strings.ReplaceAll(a.iban, " ", ""))
    if len(s) <= 8 {
        return strings.Repeat("*", len(s))
    }
    return s[:4] + strings.Repeat("*", len(s)-8) + s[len(s)-4:]
}
```

```go
// TestTheProbeDoesNotSeeTwoResponsibilitiesOnTheSameFields is the LIMIT of
// the measure, measured.
//
// Checking an IBAN and formatting it are two responsibilities, two actors —
// compliance and customer service — and they touch the same field. The
// probe returns a single component, and it is wrong.
//
// A measure whose false negative one does not know is useless. This one is:
// two responsibilities on the same data.
func TestTheProbeDoesNotSeeTwoResponsibilitiesOnTheSameFields(t *testing.T) {
    r := report(t, "limit", "Account", nil)
    if len(r.Components) != 1 {
        t.Fatalf("%d components, want 1:\n%s", len(r.Components), describe(r))
    }
    t.Logf("%s", describe(r))
    t.Log("two actors — compliance and customer service — and a single" +
        " component: it is the false negative of the measure")
}
```

```
Account: 1 fields, 2 methods, 1 component(s)
  Masked [iban]
  Valid  [iban]
  component 1: [Masked Valid]
two actors — compliance and customer service — and a single component: it is the false negative of the measure
```

Vérifier un IBAN et le masquer pour l'affichage sont **deux responsabilités,
deux acteurs** — la conformité réglementaire et le service client — et elles
touchent le même champ. Le sondage rend une composante, et il a tort.

> Le sondage de cohésion voit les responsabilités qui se partagent des
> **données différentes**. Il est aveugle à deux responsabilités sur **la
> même donnée**. C'est son faux négatif, et il n'y a pas de sondage pour
> celui-là : il faut connaître les acteurs.

Et son faux positif est l'autre face de `Format` : une méthode qui ne touche
aucun champ forme sa propre composante, ce qui gonfle le compte. C'est pour ça
que le rapport les sépare dans une liste `Isolated` au lieu de les compter.

### Le test que la campagne a imposé

```go
// Package trap holds the case that made a modification survive.
//
// The campaign removed the qualification by the receiver in the cohesion
// probe — in other words, the probe counted any "x.field" as an access to
// the receiver — and NO test saw it. It is exactly the fault of the probe of
// lesson 2.3, which confused two homonymous types.
//
// This package exists so that it no longer survives: it holds a method that
// reads the field of ANOTHER instance of the same type.
package trap

// Log is a log of lines.
type Log struct {
    lines []string
    size  int
}

// NewLog builds a log.
func NewLog(size int) *Log { return &Log{size: size} }

// Merge appends the lines of another log.
//
// It touches l.lines — the receiver — and other.lines, which is not the
// receiver.
func (l *Log) Merge(other *Log) {
    l.lines = append(l.lines, other.lines...)
}

// Size returns the size of the log.
func (l *Log) Size() int { return l.size }

// SizeOf returns the size of ANOTHER log.
//
// It touches no field of the receiver. A probe that does not qualify by the
// receiver will think it linked to Size, and it will return one component
// less.
func (l *Log) SizeOf(other *Log) int { return other.size }
```

```go
// TestAnAccessOnAnotherInstanceIsNotAnAccessToTheReceiver is the NEGATIVE
// test of the probe, and it was born of a modification that survived.
//
// Without the qualification by the receiver, SizeOf counts as touching
// "size", so it links to Size: the probe returns two components and zero
// isolated methods, instead of two components and one isolated. The count
// of components is therefore not enough: one must check THE COMPOSITION.
func TestAnAccessOnAnotherInstanceIsNotAnAccessToTheReceiver(t *testing.T) {
    r := report(t, "trap", "Log", nil)
    if len(r.Components) != 2 {
        t.Fatalf("%d components, want 2:\n%s", len(r.Components), describe(r))
    }
    want := [][]string{{"Merge"}, {"Size"}}
    for i, c := range want {
        if strings.Join(r.Components[i], ",") != strings.Join(c, ",") {
            t.Errorf("component %d = %v, want %v", i+1, r.Components[i], c)
        }
    }
    if len(r.Isolated) != 1 || r.Isolated[0] != "SizeOf" {
        t.Fatalf("isolated = %v, want [SizeOf]: the probe credits"+
            " SizeOf with a field it reads on another instance", r.Isolated)
    }
    t.Logf("%s", describe(r))
}
```

Ce fichier existe parce qu'une modification a **survécu** : retirer la
qualification par le récepteur dans le sondage — autrement dit, compter
n'importe quel `x.field` comme un accès au récepteur — et aucun test ne le
voyait.

C'est, au mot près, la faute du sondage de la leçon 2.3, qui confondait deux
types homonymes. Deux leçons de suite, le même défaut, dans le même genre
d'outil.

> Un sondage sur du code a toujours besoin de son **test négatif** : un cas
> où il doit trouver quelque chose, et un cas où il doit ne rien trouver. Et
> le compte de composantes ne suffit pas : il faut vérifier **leur
> composition**.

## 3. OCP : l'axe, et son prix

### Le module

```go
// Format is the axis on which the module is OPEN.
//
// Two methods. Each method added here is a modification of all the
// implementations, present and future: it is the price of the axis, and
// section 5 of the lesson puts a figure on it.
type Format interface {
    Extension() string
    Encode(s model.Statement) ([]byte, error)
}
```

```go
// Export encodes the statement in the requested format and returns the file
// name and the content.
//
// It is the only code that changes when the export changes; it does not
// change when a format is added.
func Export(reg Registry, name string, s model.Statement) (file string, content []byte, err error) {
    f, err := reg.For(name)
    if err != nil {
        return "", nil, err
    }
    content, err = f.Encode(s)
    if err != nil {
        return "", nil, fmt.Errorf("export: encoding %s: %w", name, err)
    }
    return s.Account + "-" + s.Issued.Format("2006-01") + f.Extension(), content, nil
}
```

```go
// Package formats holds one format per file.
//
// It imports model, the vocabulary. It does NOT import export: none of its
// types names the interface it satisfies.
package formats

import (
    "bytes"
    "encoding/csv"
    "strconv"

    "example/bank24/model"
)

// CSV encodes the statement as comma-separated values.
type CSV struct{ Separator rune }

// Extension returns the file extension.
func (CSV) Extension() string { return ".csv" }

// Encode returns the statement as CSV.
func (c CSV) Encode(s model.Statement) ([]byte, error) {
    var buf bytes.Buffer
    w := csv.NewWriter(&buf)
    if c.Separator != 0 {
        w.Comma = c.Separator
    }
    if err := w.Write([]string{"date", "label", "cents"}); err != nil {
        return nil, err
    }
    for _, l := range s.Lines {
        line := []string{
            l.Instant.Format("2006-01-02"),
            l.Label,
            strconv.FormatInt(l.Cents, 10),
        }
        if err := w.Write(line); err != nil {
            return nil, err
        }
    }
    w.Flush()
    return buf.Bytes(), w.Error()
}
```

### Ce que les deux mesures disent ensemble

| | Axe **ouvert** (variante) | Axe **fermé** (opération) |
|---|---|---|
| fichiers existants touchés | 1 (la racine) | N (toutes les implémentations) |
| le compilateur t'aide ? | **non, zéro erreur** | **oui, N erreurs** |
| qui te protège ? | un test sur la liste | le compilateur |

C'est la même symétrie que le *problème de l'expression* de la leçon 2.2,
vue du côté de l'outillage. Et elle a une conséquence pratique qu'on n'énonce
presque jamais :

> **« Fermé à la modification » veut dire « le compilateur se taira ».** Sur
> l'axe ouvert, l'ajout est facile et invisible : c'est un test sur la liste
> des variantes qui remplace le compilateur. Sans ce test, un quatrième
> format part en production sans que personne ne l'ait décidé.

Et la conclusion sur le principe lui-même :

> OCP n'est pas une propriété d'un module. C'est une propriété d'un module
> **par rapport à un axe**. « Est-ce que ce code respecte OCP ? » n'a pas de
> réponse ; « sur quel axe est-il ouvert, et combien coûte l'autre ? » en a
> deux, chiffrées.

## 4. LSP : le compilateur ne vérifie que les signatures

### Le port, et ce que sa signature ne dit pas

```go
// Store is the document storage port.
//
// Its signature says four things. Its CONTRACT says ten, and the other six
// are nowhere in the code: they are in the battery.
type Store interface {
    Save(key string, content []byte) error
    Read(key string) ([]byte, error)
    List(prefix string) ([]string, error)
    Delete(key string) error
}
```

Quatre méthodes. Le contrat en dit **dix**, et les six autres ne sont nulle
part dans le code :

```
1. read what was saved
2. an absent key returns ErrNotFound
3. saving twice replaces
4. deleting an absent key returns ErrNotFound
5. list returns the keys sorted
6. listing a nonexistent prefix returns zero keys
7. the returned content is a copy
8. an empty key is refused with ErrInvalidKey
9. a key with several segments is accepted
10. a hundred concurrent saves lose nothing
```

Aucune de ces dix clauses n'est vérifiable par le compilateur. Les quatre
signatures, oui.

### Les sentinelles d'erreur font partie du vocabulaire

```go
// The errors of the contract.
//
// They are here, with the interface, and it is an exception to the rule of
// lessons 2.2 and 2.3 — "an implementation does not import its caller". A
// caller that writes errors.Is(err, contract.ErrNotFound) requires that the
// implementation return THIS value: the sentinels are part of the
// vocabulary, so the implementations import this package.
var (
    // ErrNotFound: the requested key does not exist.
    ErrNotFound = errors.New("contract: key not found")
    // ErrInvalidKey: the key does not have the expected shape.
    ErrInvalidKey = errors.New("contract: invalid key")
)
```


C'est une **exception** à la règle des leçons 2.2 et 2.3 — *« une
implémentation n'importe pas son appelant »* — et il faut la nommer, parce
qu'elle est systématique :

> Dès qu'un appelant écrit `errors.Is(err, ErrNotFound)`, il exige de
> l'implémentation **cette valeur précise**. Les sentinelles d'erreur font
> donc partie du vocabulaire de l'interface, et les implémentations doivent
> importer le paquet qui les déclare.

### La batterie

```go
// Check puts the implementation through the ten clauses of the contract and
// returns the failures.
//
// It returns failures instead of calling t.Errorf, for two reasons. The
// first is that it also serves as a MEASUREMENT: the lesson publishes, for
// each faulty implementation, the exact list of the clauses it breaks. The
// second is that a battery that takes *testing.T cannot itself be tested.
func Check(newOne func() Store) []Failure {
    var failures []Failure
    for _, c := range clauses() {
        finding := protectedCall(c, newOne)
        if finding != "" {
            failures = append(failures, Failure{Clause: c.name, Finding: finding})
        }
    }
    return failures
}

// protectedCall runs a clause, catching panics.
//
// An implementation that panics where the others return an error is a
// violation of the contract, not a crash of the battery.
func protectedCall(c clause, newOne func() Store) (finding string) {
    defer func() {
        if p := recover(); p != nil {
            finding = fmt.Sprintf("panicked instead of answering: %v", p)
        }
    }()
    return c.check(newOne())
}
```

Deux décisions de forme, et les deux sont mesurées par la campagne :

- **elle rend des échecs au lieu d'appeler `t.Errorf`** — ce qui permet de
  publier, pour chaque implémentation fautive, la liste exacte des clauses
  qu'elle casse, et de **tester la batterie elle-même** ;
- **elle rattrape les paniques par clause** — parce qu'une implémentation qui
  panique là où les autres rendent une erreur est une violation du contrat,
  pas un plantage de la batterie.

### Les trois implémentations conformes

```go
// TestTheThreeCompliantImplementations puts the three through the ten
// clauses.
//
// One battery, three implementations, one of them on disk and a decorator.
// It is what LSP means in Go: the battery IS the contract.
func TestTheThreeCompliantImplementations(t *testing.T) {
    cases := map[string]func() contract.Store{
        "Memory": func() contract.Store { return stores.NewMemory() },
        "File":   func() contract.Store { return stores.NewFile(t.TempDir()) },
        "Prefix": func() contract.Store {
            return stores.Prefix{Next: stores.NewMemory(), Head: "bank/"}
        },
    }
    for name, newOne := range cases {
        t.Run(name, func(t *testing.T) {
            failures := contract.Check(newOne)
            for _, f := range failures {
                t.Errorf("%s", f)
            }
            if len(failures) == 0 {
                t.Logf("%s: 10/10 clauses held", name)
            }
        })
    }
}
```

```
Memory: 10/10 clauses held
File: 10/10 clauses held
Prefix: 10/10 clauses held
```

Une batterie, trois implémentations, dont une sur disque et **un
décorateur** :

```go
// Prefix is a decorator: it prefixes all the keys.
//
// It is the third case of the battery, and it is there for a precise
// reason: a decorator is the easiest implementation to break, because it
// must translate the keys IN BOTH DIRECTIONS. This one also translates the
// output of List, and clause 5 does not forgive the omission.
type Prefix struct {
    Next contract.Store
    Head string
}

// Save prefixes the key.
func (p Prefix) Save(key string, content []byte) error {
    if err := validate(key); err != nil {
        return err
    }
    return p.Next.Save(p.Head+key, content)
}

// Read prefixes the key.
func (p Prefix) Read(key string) ([]byte, error) { return p.Next.Read(p.Head + key) }

// List prefixes the prefix, then REMOVES the head from the keys returned.
func (p Prefix) List(prefix string) ([]string, error) {
    raw, err := p.Next.List(p.Head + prefix)
    if err != nil {
        return nil, err
    }
    keys := make([]string, 0, len(raw))
    for _, k := range raw {
        keys = append(keys, strings.TrimPrefix(k, p.Head))
    }
    return keys, nil
}
```

Le décorateur est l'implémentation la plus facile à casser, parce qu'il doit
traduire les clés **dans les deux sens**. Celui-ci retire la tête des clés que
`List` rend, et la clause 5 ne pardonne pas l'oubli — la campagne le
confirme : retirer ce `TrimPrefix` fait tomber le test.

### Les cinq implémentations qui compilent et violent le contrat

```go
// TestTheFourNaivesEachBreakTheirClause is the MEASUREMENT of the section on
// LSP. The fifth naive, Loser, has its own test: it triggers a race, so it
// must run in a subprocess.
//
// The four compile. The four satisfy the interface. The compiler has nothing
// to say about any of the four, because it only checks the signatures.
func TestTheFourNaivesEachBreakTheirClause(t *testing.T) {
    cases := []struct {
        name    string
        newOne  func() contract.Store
        clauses []string
    }{
        {"NoCopy", func() contract.Store { return naive.NewNoCopy() },
            []string{"7"}},
        {"Panicky", func() contract.Store { return naive.NewPanicky() },
            []string{"2", "4"}},
        {"Unsorted", func() contract.Store { return naive.NewUnsorted() },
            []string{"5"}},
        {"Strict", func() contract.Store { return naive.NewStrict() },
            []string{"9"}},
    }
    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            var _ contract.Store = c.newOne() // the compiler is happy
            failures := contract.Check(c.newOne)
            var numbers []string
            for _, f := range failures {
                numbers = append(numbers, strings.SplitN(f.Clause, ".", 2)[0])
                t.Logf("  %s", f)
            }
            if strings.Join(numbers, ",") != strings.Join(c.clauses, ",") {
                t.Fatalf("broken clauses = %v, want %v", numbers, c.clauses)
            }
            t.Logf("%s: breaks %d clause(s) out of 10, and compiles without a word",
                c.name, len(failures))
        })
    }
}
```

```
NoCopy:   7. the returned content is a copy: after modifying the returned
            slice, the store holds "Xello"
          breaks 1 clause(s) out of 10, and compiles without a word

Panicky:  2. an absent key returns ErrNotFound: panicked instead of
            answering: store: absent key never-written
          4. deleting an absent key returns ErrNotFound: panicked ...
          breaks 2 clause(s) out of 10, and compiles without a word

Unsorted: 5. list returns the keys sorted: List returns [c.txt b.txt a.txt],
            want [a.txt b.txt c.txt]
          breaks 1 clause(s) out of 10, and compiles without a word

Strict:   9. a key with several segments is accepted:
            Save("2026/06/CM-0001.json"): contract: invalid key: the key
            contains a slash
          breaks 1 clause(s) out of 10, and compiles without a word
```

Aucune n'est absurde. Chacune est une façon d'écrire un dépôt quand on lit la
signature et qu'on ne lit pas le contrat :

| | Ce que son auteur a pensé | La violation de Liskov |
|---|---|---|
| `NoCopy` | « pourquoi copier, c'est la même donnée » | **postcondition affaiblie** : la valeur rendue n'est plus indépendante |
| `Panicky` | « une clé absente est un bug de l'appelant » | **changement de mode d'échec** : l'appelant ne peut plus récupérer |
| `Unsorted` | « l'ordre n'est pas spécifié » — il l'est | **postcondition affaiblie** |
| `Strict` | « je stocke à plat, j'interdis la barre oblique » | **précondition renforcée**, la forme canonique de la violation |

Et le cinquième, qui a besoin d'un sous-processus :

```go
// TestTheLoserInASubprocess is the fifth naive, and it needs a subprocess
// for two different reasons.
//
// Under -race, it triggers a race that fails the whole suite. Without -race,
// it loses writes without any message: it is the most important half of the
// measurement, and it only shows if one observes it.
func TestTheLoserInASubprocess(t *testing.T) {
    if os.Getenv("LOSER") != "" {
        failures := contract.Check(func() contract.Store { return naive.NewLoser() })
        for _, f := range failures {
            t.Errorf("%s", f)
        }
        return
    }
    for _, c := range []struct {
        name string
        args []string
        want string
    }{
        {"without the race detector",
            []string{"test", "-count=1", "-run", "TestTheLoserInASubprocess", "."},
            "writes were lost"},
        {"with the race detector",
            []string{"test", "-race", "-count=1", "-run", "TestTheLoserInASubprocess", "."},
            "DATA RACE"},
    } {
        t.Run(c.name, func(t *testing.T) {
            cmd := exec.Command("go", c.args...)
            cmd.Env = append(os.Environ(), "LOSER=1")
            out, err := cmd.CombinedOutput()
            if err == nil {
                t.Fatalf("the subprocess succeeded: the measurement changed\n%s", out)
            }
            if !strings.Contains(string(out), c.want) {
                t.Fatalf("output without %q:\n%s", c.want, out)
            }
            for _, l := range strings.Split(string(out), "\n") {
                if strings.Contains(l, c.want) {
                    t.Logf("%s", strings.TrimSpace(l))
                    break
                }
            }
        })
    }
    t.Log("an implementation that loses writes satisfies the interface," +
        " passes nine clauses out of ten, and says nothing at all in production")
}
```


```
without the race detector: 10. a hundred concurrent saves lose
  nothing: 51 keys out of 100: writes were lost
with the race detector: WARNING: DATA RACE
```

`Loser` écrit par copie-sur-écriture **sans verrou** : c'est un cache
concurrent écrit de mémoire. Il n'y a pas de `fatal error: concurrent map
writes`, parce qu'aucune carte n'est écrite deux fois — il y a seulement
**49 écritures perdues sur 100**, sans un message — et un autre nombre à
l'exécution suivante : la perte dépend de l'entrelacement.

> Une implémentation qui perd des écritures satisfait l'interface, passe neuf
> clauses sur dix, et ne dit **rien du tout** en production. Le détecteur de
> course la voit — à condition qu'un test la provoque, et c'est la leçon de
> la correction 2.3/3.

### Ce que la batterie a attrapé pendant son écriture

`Panicky` ne devait casser que les clauses 2 et 4. Elle en cassait
**trois** : en réécrivant `Read` pour y mettre la panique, j'avais recopié le
corps de la méthode d'origine et **oublié la copie** de la tranche.

```
Panicky: broken clauses = [2 4 7], want [2 4]
```

```go
// Read panics if the key is absent.
//
// The copy on the next line was FORGOTTEN in the first version of this file.
// Panicky was only to break clauses 2 and 4; it broke three, and it is the
// battery that said so. Rewriting a method to change only part of it is
// copying the rest, and what one copies, one damages.
func (d Panicky) Read(key string) ([]byte, error) {
    d.mu.RLock()
    defer d.mu.RUnlock()
    c, known := d.contents[key]
    if !known {
        panic("store: absent key " + key)
    }
    cp := make([]byte, len(c))
    copy(cp, c)
    return cp, nil
}
```


> Réécrire une méthode pour n'en changer qu'une partie, c'est recopier le
> reste — et ce qu'on recopie, on l'abîme. La batterie l'a dit en une ligne,
> et c'est précisément le genre de faute qu'aucune relecture ne voit, parce
> que le diff est « correct ».

## 5. Ce que ça donne, et ce que ça coûte

| | Ce qu'on gagne | Ce qu'on paye |
|---|---|---|
| **SRP** par le sondage | une coupe qui a un sens métier, trouvée sans connaître le métier ; des dépendances révélées (`Price` sans relevé) | un type de plus, un constructeur de plus, et une liste d'exclusions à tenir |
| **OCP** par l'axe | ajouter un format : 1 fichier neuf, 1 ligne, 0 implémentation touchée | ajouter une opération : 3 implémentations, et **le compilateur muet** sur l'axe ouvert |
| **LSP** par la batterie | dix clauses vérifiées sur trois implémentations conformes et cinq fautives, par un test écrit **une fois** | la batterie est du code à écrire et à maintenir : 150 lignes pour une interface de 4 méthodes |

Ce dernier chiffre mérite qu'on s'y arrête : **150 lignes de batterie pour 4
signatures**. C'est le coût réel de LSP en Go, et il n'est pas négociable —
c'est exactement le coût de ce que le compilateur ne vérifie pas. La
bibliothèque standard paye le même : `testing/fstest` fait plus de mille
lignes pour une interface d'une seule méthode.

Et la contrepartie se chiffre aussi : cette batterie a été écrite une fois, et
elle a validé trois implémentations et diagnostiqué cinq fautes — dont une
dans mon propre code, pendant que je l'écrivais.

## 6. Les trois erreurs qui restent

### « SRP veut dire des petites classes »

Non. `Ledger` a deux méthodes, `Tariff` en a deux ; mais `Memory` en a quatre
et la batterie en a dix clauses, et aucune ne doit être coupée. La taille
n'est pas le critère : **la partition des champs** l'est. Un type de six
méthodes qui touchent tous les mêmes champs est cohésif ; un type de deux
méthodes qui n'en partagent aucun est deux types.

### « OCP veut dire qu'il faut une interface partout »

Non, et le coût est mesuré : chaque méthode d'une interface est **N
modifications** le jour où elle change, N étant le nombre
d'implémentations — y compris celles qui sont dans d'autres dépôts.
L'ouverture sur un axe est un investissement, et un investissement se fait
quand on a une **raison de croire que l'axe est le bon**. La leçon 2.2 donne
la raison : le relevé des changements passés.

### « LSP, en Go, ça ne s'applique pas, il n'y a pas d'héritage »

C'est l'erreur la plus coûteuse des trois, et elle est fréquente. LSP ne parle
pas d'héritage, il parle de **substituabilité** — et Go en fait un usage plus
intensif que les langages à classes, parce qu'une interface Go est satisfaite
**implicitement**. Personne n'écrit `implements Store`. Personne ne relit donc
la liste de ce que `Store` promet. Les cinq implémentations fautives de la
section 4 compilent toutes, et aucune n'a eu à déclarer quoi que ce soit.

> En Go, LSP s'applique **plus** qu'ailleurs, et il est vérifié **moins**
> qu'ailleurs. C'est ce différentiel que la batterie paye.

## 7. Le lien avec la production

| Ce que tu as déjà vu en production | Le principe, et sa mesure |
|---|---|
| un fichier de 2 000 lignes que trois équipes modifient, et un conflit de fusion par semaine | SRP. Le sondage donne la coupe, et l'historique git donne les acteurs : regarde qui a touché quelles méthodes |
| un `switch` sur le type de canal qu'il faut modifier à chaque nouveau canal | OCP, axe des variantes. Mesure le diff du dernier ajout |
| une méthode ajoutée à une interface, et 14 fichiers à reprendre dans la même journée | OCP, axe des opérations. Ce n'est pas un échec : c'est le prix de l'axe que tu as choisi. La question est de savoir si tu l'as choisi |
| un bouchon de test qui passe tous les tests, et une panne le jour où on branche le vrai | LSP. Le bouchon et le vrai n'ont jamais été passés dans la **même** batterie |
| un cache qui perd des écritures sous charge, et rien dans les journaux | LSP, clause de concurrence. Mesuré ici : 51 clés sur 100, sans un message |
| un décorateur qui marche sauf sur `List` | LSP. Un décorateur traduit dans les deux sens, et l'oubli est toujours dans le sens retour |

Et la règle d'usage, celle qui vaut dans une revue :

> Quand quelqu'un écrit une **deuxième** implémentation d'une interface, la
> question n'est pas « est-ce qu'elle compile ». C'est : **où est la batterie,
> et est-ce que la première y passe aussi ?**

## 8. Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Les trois principes ne sont pas de même nature : SRP décide d'une **coupe**, OCP d'un **axe**, LSP d'un **contrat**. Le premier se sonde, le deuxième se diffe, le troisième se teste. |
| ⚫ | SRP mesurable : partitionne les méthodes par les champs du récepteur qu'elles touchent. Deux composantes, deux types. C'est une variante de LCOM4. |
| ⚫ | Un champ **transverse** relie tout à tout et annule la mesure. La liste des exclusions est une information : c'est ce qui traverse le type sans lui appartenir. |
| ⚫ | Le faux négatif du sondage : **deux responsabilités sur la même donnée**. Il n'y a pas de sondage pour celui-là. Son faux positif : une méthode qui ne touche aucun champ — et c'est le signal qu'elle doit être une fonction. |
| ⚫ | Couper un type **révèle les dépendances que la cohabitation cachait**. Mesuré : une facturation qui n'a jamais eu besoin d'un relevé, seulement de sa taille. |
| ⚫ | OCP n'est pas une propriété d'un module, c'est une propriété d'un module **par rapport à un axe**. La question « est-ce que ça respecte OCP » n'a pas de réponse. |
| ⚫ | « Fermé à la modification » veut dire **« le compilateur se taira »**. Mesuré : 0 erreur de compilation pour une variante ajoutée, 3 pour une opération ajoutée. |
| ⚫ | Sur l'axe ouvert, c'est un **test sur la liste des variantes** qui remplace le compilateur. Sans lui, une variante part en production sans décision. |
| ⚫ | En Go, le compilateur vérifie les **signatures** d'une implémentation et rien d'autre. Les dix clauses du contrat de cette leçon ne sont nulle part dans le code. |
| ⚫ | La réponse à LSP en Go est une **batterie de contrat** : un test écrit une fois, paramétré par l'implémentation. La bibliothèque standard fait ça avec `testing/fstest.TestFS`. |
| ⚫ | Les **sentinelles d'erreur** font partie du vocabulaire de l'interface. C'est la seule raison légitime pour qu'une implémentation importe le paquet qui déclare l'interface. |
| ⚫ | Une batterie doit rattraper les paniques par clause : une implémentation qui panique là où les autres rendent une erreur viole le contrat, elle ne casse pas la batterie. |
| ⚫ | Les violations canoniques de Liskov en Go : **précondition renforcée** (une clé refusée que les autres acceptent), **postcondition affaiblie** (une liste non triée, une tranche partagée), **mode d'échec changé** (une panique au lieu d'une erreur), **garantie de concurrence perdue**. |
| ⚫ | 150 lignes de batterie pour 4 signatures. C'est le coût de ce que le compilateur ne vérifie pas, et il n'est pas négociable. |
| ⚫ | Réécrire une méthode pour n'en changer qu'une partie, c'est recopier le reste — et ce qu'on recopie, on l'abîme. |
| ⚫ | Un sondage sur du code a toujours besoin de son **test négatif**, et vérifier le nombre de composantes ne suffit pas : il faut vérifier leur composition. |

## 9. Approfondissement

### Pourquoi le sondage de cohésion n'est pas un outil de décision

Il est un outil d'**attention**. Deux composantes ne veulent pas dire « coupe
maintenant » : elles veulent dire « demande-toi qui demande les changements de
chaque composante ». Si c'est le même acteur, ne coupe pas — tu obtiendrais
deux types qui changent toujours ensemble, ce qui est la faute inverse et elle
coûte plus cher (deux fichiers à garder cohérents, un constructeur de plus,
une dépendance explicite à écrire).

Le sondage te donne les **candidats**. L'historique git te donne la réponse :
regarde, sur les douze derniers mois, si les commits qui touchent la
composante 1 touchent aussi la composante 2. Si oui, c'est un seul acteur. La
mesure du code et la mesure du temps ne disent pas la même chose, et c'est la
seconde qui décide.

### La version faible et la version forte d'OCP

La version faible : *« je peux ajouter une variante sans modifier les autres
variantes »*. C'est ce que mesure la section 3, et ça suffit presque toujours.

La version forte : *« je peux ajouter une variante sans modifier **aucun**
fichier existant »*. Elle demande un chargement dynamique — un registre
peuplé par des `init()`, un plugin, une table lue dans un fichier de
configuration. Et elle coûte exactement ce qu'elle promet : le registre n'est
plus lisible dans un seul endroit, donc plus vérifiable par un test, donc on
revient au problème de la section 3 en pire. La version faible — une ligne
dans une racine de composition, plus un test sur la liste — est le bon point
d'arrêt dans à peu près tous les cas.

### Ce que LSP dit des interfaces larges

Les cinq implémentations fautives de la section 4 cassent chacune une clause
différente. Si l'interface avait eu dix méthodes au lieu de quatre, la
batterie aurait eu vingt-cinq clauses, et la probabilité qu'une implémentation
en casse une aurait monté avec. Ce n'est pas une intuition, c'est de
l'arithmétique :

> Le coût de LSP croît avec la **largeur** de l'interface, et le nombre de
> ses implémentations multiplie ce coût.

C'est le pont vers la leçon 2.5 : ISP — *Interface Segregation Principle* —
n'est pas un principe d'élégance. C'est **la façon de rendre LSP abordable**.

## 10. Le réflexe à installer

Trois questions, une par principe, dans l'ordre où elles se posent dans une
vraie journée de travail.

> **Devant un type qui grossit** (SRP)
> Quels champs touche chaque méthode ? S'il y a deux groupes disjoints — en
> excluant les champs transverses — demande qui demande les changements de
> chaque groupe. Deux acteurs → coupe. Un seul acteur → laisse, et note la
> mesure dans un commentaire.
>
> **Devant une interface qu'on te demande d'ajouter** (OCP)
> Sur quel axe est-ce que je m'ouvre, et qu'est-ce que je ferme ? Puis :
> est-ce que le relevé des douze derniers mois dit que c'est le bon axe ? Et
> enfin : **où est le test qui remplace le compilateur sur l'axe ouvert ?**
>
> **Devant une deuxième implémentation d'une interface** (LSP)
> Où est la batterie de contrat ? Si elle n'existe pas, écris-la **avant**
> l'implémentation, et fais-y passer la première. Les clauses que tu
> découvriras en l'écrivant sont exactement ce que la première implémentation
> promettait sans le dire.

Et le geste d'une minute, devant n'importe quelle interface :

> **Compte ses méthodes, puis compte les choses que son contrat promet et que
> sa signature ne dit pas.** Si le second nombre est plus grand que le
> premier — et il l'est presque toujours — tu viens de mesurer la taille de
> la batterie qui te manque.
