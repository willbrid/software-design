# Leçon 2.2 — Polymorphisme : à quoi il sert vraiment

## L'essentiel en deux minutes

**Le problème, en une phrase.** Un même nom désigne plusieurs
comportements, et quelque chose doit choisir lequel s'exécute : **qui
choisit, et quand ?**

**L'image.** Un moule à gâteau et une télécommande universelle. Le moule
fait toujours la même recette, avec la farine que tu y mets : c'est le
polymorphisme **paramétrique** (les génériques), décidé avant de cuisiner.
La télécommande a un seul bouton « marche », et chaque appareil réagit à
sa façon : c'est le polymorphisme **par interface**, décidé au moment où tu
appuies.

**Le code, en une quarantaine de lignes.**

```go
// Package e22 is the two-minute version of lesson 2.2.
package e22

import (
    "cmp"
    "fmt"
)

// Max is parametric: one algorithm for any ordered type, chosen when the
// program compiles.
func Max[T cmp.Ordered](first T, rest ...T) T {
    m := first
    for _, x := range rest {
        m = max(m, x)
    }
    return m
}

// Notifier is subtyping: one call, and the behavior is chosen while the
// program runs, by the value behind the interface.
type Notifier interface {
    Notify(to, msg string) string
}

// SMS sends a text message.
type SMS struct{}

// Notify formats an SMS.
func (SMS) Notify(to, msg string) string { return fmt.Sprintf("sms %s: %s", to, msg) }

// Email sends a mail from a sender: an implementation with state.
type Email struct{ From string }

// Notify formats a mail.
func (e Email) Notify(to, msg string) string {
    return fmt.Sprintf("mail %s -> %s: %s", e.From, to, msg)
}

// Broadcast does not know which notifiers it calls.
func Broadcast(ns []Notifier, to, msg string) []string {
    var out []string
    for _, n := range ns {
        out = append(out, n.Notify(to, msg))
    }
    return out
}
```

`Max` est le moule : le même algorithme pour des entiers ou des chaînes, et
le compilateur vérifie tout. `Broadcast` est la télécommande : il ne sait
pas ce qu'il appelle, et ajouter un `Push` ne le touche pas. `Email` a un
état (`From`) : c'est ce qui justifie une interface plutôt qu'une simple
fonction.

**Les règles à retenir.**

1. Générique : l'algorithme est le même, **le type** change, tout est décidé
   à la compilation. Interface : le type est le même, **le comportement**
   change, et c'est décidé à l'exécution.
2. Go n'a pas de surcharge (deux fonctions de même nom) : un conseil écrit
   pour Java ou C++ ne s'applique pas tel quel.
3. Une interface à une méthode et un type fonction sont le même
   polymorphisme ; l'interface se justifie quand l'implémentation a un état.
4. Le coût d'un appel par interface est de l'ordre de la nanoseconde : ce
   n'est presque jamais l'argument qui décide.
5. La vraie question : **qu'est-ce qui arrive le plus souvent**, de nouvelles
   variantes ou de nouvelles opérations ? `git log` répond mieux qu'une
   intuition.

La leçon 2.1 s'est terminée sur un aveu : on n'y a écrit aucune interface. Ce
n'était pas un oubli. Il n'y avait pas deux implémentations de quoi que ce
soit, et une interface sans deux implémentations n'est pas du polymorphisme,
c'est un alias.

On commence donc par poser le mot : ce qu'il désigne, ses quatre formes, ce
que Go fait de chacune, et ce que chacune coûte — avec du code qui compile et
des chiffres mesurés. Puis on arrive à la seule question qui décide s'il faut
en mettre, et à quel endroit.

> Le polymorphisme n'est pas un outil, c'est un **choix d'axe d'extension**.
> La question n'est jamais *« faut-il une interface ici ? »*. Elle est :
> **qui va ajouter le cas suivant, et de quel côté va-t-il arriver ?**

Et il y a une surprise au bout, spécifique à Go, qui change la façon de
compter le coût. On la mesurera.

## 1. Le polymorphisme, défini

### La définition

> **Polymorphisme** : un même nom d'opération désigne plusieurs
> implémentations, et le choix de l'implémentation se fait **ailleurs** que là
> où le nom est écrit.

« Poly-morphe » : plusieurs formes. Le mot vient du grec, la pratique vient de
Simula, et la définition ci-dessus est volontairement pauvre — elle ne dit
rien de bien, rien de propre, rien de souhaitable. Elle dit seulement
*plusieurs implémentations* et *le choix est ailleurs*.

Et c'est ce « ailleurs » qui porte tout. Deux questions en découlent, et elles
suffisent à classer toutes les formes de polymorphisme qui existent :

> **Qui choisit l'implémentation, et à quel moment ?**

### Les quatre formes, et ce que Go fait de chacune

| Forme | Autre nom | Qui choisit | Quand | En Go |
|---|---|---|---|---|
| **par surcharge** | *ad hoc*, overloading | le compilateur, d'après les types des arguments | compilation | **absent**, et c'est un choix |
| **paramétrique** | généricité | le compilateur, d'après le paramètre de type | compilation | `[T any]`, depuis Go 1.18 |
| **de sous-typage** | par inclusion, dynamique | l'exécution, d'après le type réel de la valeur | exécution | les **interfaces** |
| **par table** | dispatch par donnée | le programme, en lisant une table | exécution | une `map` de fonctions |

Les trois dernières existent en Go. La première n'existe pas, et ce n'est pas
un oubli : le compilateur le dit, et c'est un des cas du test de
non-compilation de ce module.

```
./main.go:8:6: Ajouter redeclared in this block
```

Deux fonctions de même nom et de signatures différentes ne cohabitent pas.
Quand tu liras « polymorphisme » dans un livre écrit pour Java ou C++, vérifie
toujours si l'auteur parle de la surcharge : la moitié des conseils qui en
découlent ne s'applique pas ici.

Le reste de cette leçon ne parlera **que du polymorphisme de sous-typage** —
celui des interfaces — parce que c'est le seul des quatre qui pose une
question de conception. Les trois autres posent des questions de notation.

### Forme 1 — le sous-typage, et où le choix a lieu

```go
// --- 1. SUBTYPING polymorphism: the choice happens at run time ---

// Formatter formats a label before display.
type Formatter interface {
    Format(s string) string
}

// Upper turns everything to capitals.
type Upper struct{}

func (Upper) Format(s string) string { return strings.ToUpper(s) }

// Truncate cuts beyond a width, marking the cut.
type Truncate struct{ Width int }

func (t Truncate) Format(s string) string {
    if t.Width <= 0 || len(s) <= t.Width {
        return s
    }
    if t.Width <= 3 {
        return s[:t.Width]
    }
    return s[:t.Width-3] + "..."
}

// Apply is where polymorphism shows: this function does not
// does not know, and CANNOT know, which code will run. The decision is
// in the value it is given, not in its text.
func Apply(f Formatter, s string) string { return f.Format(s) }
```

Regarde `Apply`. Trois mots de corps, et une propriété que rien dans son
texte ne révèle : **cette fonction ne sait pas, et ne peut pas savoir, quel
code va s'exécuter**. La décision est dans la valeur qu'on lui passe.

C'est ça, et seulement ça, le polymorphisme de sous-typage. Le test le dit en
quatre lignes — même appel, quatre résultats :

```go
// TestTheCallerDoesNotKnowWhichCodeRuns: the same call line produces two
// different results, and it is the operational definition of
// subtyping polymorphism.
func TestTheCallerDoesNotKnowWhichCodeRuns(t *testing.T) {
    tc := []struct {
        f     bases.Formatter
        input string
        want  string
    }{
        {bases.Upper{}, "orange invoice", "ORANGE INVOICE"},
        {bases.Truncate{Width: 8}, "orange invoice", "factu..."},
        {bases.Truncate{Width: 0}, "orange invoice", "orange invoice"},
        {bases.Truncate{Width: 2}, "orange invoice", "fa"},
    }
    for _, c := range tc {
        if got := bases.Apply(c.f, c.input); got != c.want {
            t.Errorf("Apply(%s, %q) = %q, want %q",
                bases.WhoIsIt(c.f), c.input, got, c.want)
        }
    }
}
```

Trois notions à poser au passage, parce qu'on va s'en servir pendant toute la
leçon et pendant tout le niveau 2.

**Le dispatch.** C'est le nom du mécanisme qui choisit. *Statique* quand le
compilateur choisit, *dynamique* quand l'exécution choisit. `Apply` fait
un dispatch dynamique ; `ApplyUpper`, juste au-dessus, fait un
dispatch statique sur exactement le même code.

**La valeur d'interface.** En Go, une variable de type interface n'est pas un
pointeur : c'est une **paire** *(type réel, valeur)*. Les deux cases sont
remplies au moment de l'affectation, et c'est la première case qui permet au
dispatch dynamique de fonctionner. Cette représentation explique à elle seule
deux comportements qui surprennent tout le monde — elle revient en section 9.

**La substituabilité.** Si `Apply` accepte n'importe quel `Formatter`,
alors tout `Formatter` doit pouvoir être passé **sans que l'appelant change
de comportement attendu**. La signature l'exige du compilateur ; le contrat,
lui, n'est écrit nulle part. Un `Formatter` qui renverrait une chaîne vide, ou
qui paniquerait, satisferait l'interface et casserait tous ses appelants.
C'est le sujet de la leçon 2.4, et ça porte un nom : le principe de
substitution de Liskov.

### Ce que le dispatch dynamique efface, et qu'on peut récupérer

```go
// ApplyUpper does the same thing WITHOUT polymorphism: the type is
// known at compile time, the call is direct, and the compiler can
// inline it. It is the benchmark's witness.
func ApplyUpper(m Upper, s string) string { return m.Format(s) }

// WhoIsIt returns the real type behind an interface value.
//
// It is the information polymorphism hides from the caller, and it is
// exactly the one missing during an incident. It can be recovered,
// but only if someone bothered to write it somewhere.
func WhoIsIt(f Formatter) string { return fmt.Sprintf("%T", f) }
```

`WhoIsIt` récupère le type réel. Retiens cette fonction : **l'information
que le polymorphisme cache à l'appelant n'est pas perdue, elle est seulement
non écrite.** La section 7 raconte un incident de production qui tient tout
entier dans cette phrase.

### Forme 2 — le paramétrique, qui ne répond pas à la même question

```go
// --- 2. PARAMETRIC polymorphism: the choice happens at compile time ---

// ErrEmpty: the slice is empty, there is no first element.
var ErrEmpty = errors.New("bases: empty slice")

// First returns the first element of a slice of anything.
//
// What varies here is not the BEHAVIOR, it is the TYPE. The algorithm is
// the same for every T, and the compiler produces distinct code per
// instantiation. Nothing is decided at run time.
func First[T any](s []T) (T, error) {
    var zero T
    if len(s) == 0 {
        return zero, ErrEmpty
    }
    return s[0], nil
}

// Largest requires T to be ordered. The constraint is an
// interface, but it serves at COMPILE time: it says which types are
// accepted, not which code will run.
func Largest[T int | int64 | string](s []T) (T, error) {
    var zero T
    if len(s) == 0 {
        return zero, ErrEmpty
    }
    max := s[0]
    for _, v := range s[1:] {
        if v > max {
            max = v
        }
    }
    return max, nil
}
```

La différence avec la forme 1 est nette, et la confondre fait écrire du code
inutile :

| | ce qui varie | ce qui est connu à la compilation |
|---|---|---|
| **sous-typage** (interface) | le **comportement** | rien : le type réel arrive au dernier moment |
| **paramétrique** (générique) | le **type** | tout : chaque instanciation est un code distinct |

Un générique sert quand **l'algorithme est le même et le type change** —
`First` fait la même chose sur des `int` et sur des `string`. Une interface
sert quand **le type est le même et le comportement change** — `Apply`
reçoit toujours une chaîne et en rend toujours une.

Note au passage que la contrainte `[T int | int64 | string]` de `Largest`
*ressemble* à un ensemble fermé de variantes. Elle n'en est pas un : elle dit
quels types sont **acceptés à la compilation**, pas quel code s'exécutera. Il
n'y a aucun dispatch là-dedans.

### Forme 3 — la table, et son mode de panne

```go
// --- 3. TABLE polymorphism: the choice happens at run time, through data ---

// ErrUnknownFormatter: the key names no formatter.
var ErrUnknownFormatter = errors.New("bases: unknown formatter")

// byName is a table dispatch. An interface with ONE method and a
// function are the same polymorphism: here the function is enough, because
// no implementation has state.
var byName = map[string]func(string) string{
    "upper": strings.ToUpper,
    "lower": strings.ToLower,
    "title": func(s string) string { return strings.ToUpper(s[:1]) + s[1:] },
}

// ApplyByName picks from the table. Note the failure mode: the key is
// a string, so the typo passes compilation. It is the flaw
// that the incident of exercise 5 tells at scale.
func ApplyByName(name, s string) (string, error) {
    f, ok := byName[name]
    if !ok {
        return "", fmt.Errorf("%w: %q", ErrUnknownFormatter, name)
    }
    if s == "" {
        return "", nil
    }
    return f(s), nil
}
```

C'est du polymorphisme en règle : plusieurs implémentations, et le choix a
lieu ailleurs — ici dans une donnée. La bibliothèque standard en est pleine,
et `http.HandlerFunc` dit à voix haute ce que cette table suggère :

> Une interface à **une** méthode et un **type fonction** sont le même
> polymorphisme. L'interface se mérite quand l'implémentation a besoin d'un
> état, ou quand on veut nommer l'ensemble ; sinon une fonction suffit.

Et le mode de panne est visible à l'œil nu : **la clé est une chaîne**. Une
faute de frappe passe la compilation et devient une erreur d'exécution — ou,
bien pire, tombe dans une valeur par défaut qui ne dit rien. C'est exactement
l'incident de l'exercice 5, raconté en grand.

### Combien ça coûte, et pourquoi la réponse courante est fausse

« Les interfaces, c'est lent. » C'est l'objection qu'on entend, et elle mérite
un chiffre plutôt qu'une opinion. J'ai écrit deux bancs d'essai sur le même
travail — mettre une chaîne en majuscules — l'un en appel direct, l'autre par
interface :

```
BenchmarkAppelDirect-8         59142405    62.78 ns/op
BenchmarkAppelParInterface-8   53994928    62.73 ns/op
```

Aucune différence. Le corps de la fonction coûte soixante nanosecondes, et le
dispatch disparaît dedans. J'ai donc réduit le corps au strict minimum —
`return n + 1` — pour mesurer l'appel et rien d'autre :

```
BenchmarkCorpsTrivialEnDirect-8          0.5708 ns/op
BenchmarkCorpsTrivialParInterface-8      0.4364 ns/op
```

**L'appel « lent » est plus rapide que l'appel direct.** Mon banc d'essai ne
mesurait pas ce qu'il prétendait, et voilà pourquoi : le compilateur voyait
le type concret affecté juste au-dessus, et il remplaçait l'appel indirect par
un appel direct. Ça s'appelle la **dévirtualisation**, Go la fait, et elle
avait vidé la mesure de son sens.

```go
// --- 4. The material of the trivial-body benchmark ---

// Incrementer has the simplest possible method, so that the
// benchmark measures the COST OF THE CALL and nothing else.
type Incrementer interface {
    Plus1(n int) int
}

// Counter is the trivial implementation.
type Counter struct{}

func (Counter) Plus1(n int) int { return n + 1 }

// ViaInterface goes through the indirect call: the compiler does not know which
// code to call, so it cannot inline it.
func ViaInterface(i Incrementer, n int) int { return i.Plus1(n) }

// Direct goes through a static call, which the compiler inlines.
func Direct(c Counter, n int) int { return c.Plus1(n) }

// Doubler is a second implementation, and it exists for only one
// reason: without it, the compiler has a single candidate and devirtualizes.
type Doubler struct{}

func (Doubler) Plus1(n int) int { return n + 2 }

// Choose returns an implementation the compiler cannot guess.
//
// The noinline directive is not a whim: without it, the compiler
// inlines Choose, sees the constant argument, deduces the concrete type and
// replaces the indirect call with a direct call. It is DEVIRTUALIZATION,
// and it made the first benchmark of this lesson wrong: the
// "slow" was faster than the direct call there.
//
//go:noinline
func Choose(second bool) Incrementer {
    if second {
        return Doubler{}
    }
    return Counter{}
}
```

Avec une implémentation que le compilateur ne peut pas deviner :

```
BenchmarkCorpsTrivialEnDirect-8                       0.5708 ns/op
BenchmarkCorpsTrivialParInterfaceNonDevirtualisee-8   1.760  ns/op
```

Voilà le chiffre vrai : **1,2 nanoseconde de plus par appel**, sur un corps
qui ne fait rien. Sur le corps réel à 62 nanosecondes, ça fait **2 %**, et
c'est pour ça que le premier banc d'essai ne voyait rien.

Deux choses à emporter, et la seconde vaut plus que la première.

> Le coût du dispatch dynamique est de l'ordre de la nanoseconde. Si ta
> fonction fait quoi que ce soit de réel — une allocation, un accès mémoire
> non caché, un appel système — il est invisible. L'argument de performance
> contre les interfaces est, dans la quasi-totalité des cas, du bruit.

> **Un banc d'essai se vérifie comme un test.** Le mien donnait un résultat
> plausible — « c'est pareil » — pour une raison qui n'avait rien à voir avec
> ce qu'il croyait mesurer. Un chiffre qui confirme ce que tu espérais est le
> plus dangereux de tous.

### Ce que le polymorphisme ne fait pas

Trois croyances qu'il faut poser par terre avant la suite, parce qu'elles
mènent à des décisions de conception fausses.

| Ce qu'on dit | Pourquoi c'est faux ou inutile |
|---|---|
| « ça remplace les `if` par des types » | remplacer un `if` n'est pas un gain en soi, et la section 4 montre un cas où c'en est un coût |
| « ça permet d'étendre sans modifier » | d'étendre **sur un axe**, en figeant l'autre. La phrase est à moitié dite, et la moitié manquante est le sujet de la leçon |
| « ça découple » | ça déplace le couplage. Il ne disparaît pas : il va chez quelqu'un, et la section 4 mesure chez qui |

Et une quatrième, qui est la plus coûteuse :

> Une interface avec **une seule** implémentation n'est pas du polymorphisme,
> c'est un alias. Le test : nomme la deuxième implémentation, et dis qui l'a
> demandée. Si la seule que tu trouves est un double de test, relis la
> leçon 1.6 — *on n'injecte pas pour tester, on injecte quand le remplaçant a
> un demandeur en production*.

Voilà pour les définitions. Maintenant la question qui occupe le reste de la
leçon, et à laquelle les quatre formes ne répondent pas.

## 2. Le concept, simplement

### Qui ajoute le cas suivant

La question qui décide se formule en une phrase, et elle ne parle ni
d'élégance ni d'extensibilité. Un programme traite un **ensemble de
variantes** avec un **ensemble d'opérations** — quatre moyens de
paiement et cinq choses à leur demander, six formats de fichier et trois
traitements, huit types d'événement et quatre abonnés. Ça fait un tableau.

| | opération A | opération B | opération C |
|---|---|---|---|
| **variante 1** | ✓ | ✓ | ✓ |
| **variante 2** | ✓ | ✓ | ✓ |
| **variante 3** | ✓ | ✓ | ✓ |

Le code doit remplir toutes les cases. Il y a deux manières de le découper :
**par ligne** ou **par colonne**. Et ce choix décide de ce qui sera facile à
ajouter.

### Les deux axes, et ce que chacun coûte

| | découpage **par ligne** (interface) | découpage **par colonne** (type somme) |
|---|---|---|
| chaque unité de code est | une variante, avec toutes ses opérations | une opération, avec toutes ses variantes |
| **ajouter une variante** coûte | **1 fichier** | **N fichiers** (un par opération) |
| **ajouter une opération** coûte | **N fichiers** (un par variante) | **1 fichier** |
| convient quand | les variantes arrivent souvent, les opérations sont figées | les opérations arrivent souvent, les variantes sont figées |

Ce tableau est le cœur de la leçon, et il a un nom dans la littérature : le
**problème de l'expression**. Il n'a pas de solution. Les deux découpages sont
exacts, chacun paie sur l'axe que l'autre rend gratuit, et aucun langage
courant ne rend les deux gratuits en même temps.

> Il n'y a pas de bonne réponse. Il y a la réponse qui correspond à l'axe sur
> lequel le changement arrive. Et cet axe n'est pas une question de goût :
> c'est une question qu'on peut **mesurer** dans l'historique du dépôt.

### Le test décisif

Devant un ensemble de variantes, une seule question, et elle se répond avec
des faits, pas avec une intuition :

> **Sur les douze derniers mois, qu'est-ce qui est arrivé le plus souvent :
> une nouvelle variante, ou une nouvelle question posée aux variantes
> existantes ?**

Trois réponses, trois conséquences :

| La réponse | L'outil | Ce qu'il faut acheter en plus |
|---|---|---|
| **des variantes** — un prestataire par trimestre | une **interface**, déclarée chez l'appelant | une assertion de conformité par implémentation |
| **des opérations** — une question nouvelle par sprint | un **ensemble fermé** et des `switch` chez les appelants | un test d'exhaustivité |
| **les deux, autant** | tu n'as pas un ensemble, tu en as deux — sépare-les | |

La troisième réponse est la plus intéressante et la plus fréquente, et c'est
tout l'objet de la section 4 : **le même programme contient les deux formes,
dans deux sens opposés**, et ce n'est pas une incohérence.

### Et le cas où la réponse est « aucun des deux »

Il reste un cas, et c'est le plus courant de tous dans le code qu'on hérite :

> Quand deux implémentations ne diffèrent que par des **constantes**, le
> polymorphisme est un **tableau** qui s'ignore.

Trois types, trois méthodes, trois jeux de tests, une interface — qui se
ramènent à une `struct` de trois champs. Ce n'est pas une question d'élégance,
et on ne le règle pas au jugé : on l'établit par un **test d'équivalence**, et
c'est fait en section 4.

## 3. L'intuition

Prends une plateforme de commerce en ligne, à Douala. Elle encaisse par carte,
par mobile money, par virement reçu, et par bon d'achat qu'elle a elle-même
émis.

Maintenant pose-toi les deux questions, séparément.

**Combien de moyens de paiement a-t-on ajoutés l'an dernier ?** Zéro. En
ajouter un, ce n'est pas écrire du code : c'est signer un contrat, ouvrir un
compte de cantonnement, passer une certification. Ça se décide un trimestre à
l'avance, en comité. L'ensemble est **fermé**, et il est fermé par le métier,
pas par le programme.

**Combien de questions nouvelles a-t-on posées à un moyen de paiement ?**
Sept. La comptabilité a voulu une ligne d'écriture. Le service client a voulu
un libellé lisible. Le juridique a voulu savoir ce qui est remboursable. Le
trésorier a voulu la date de disponibilité. La lutte anti-fraude a voulu un
plafond. Et ainsi de suite.

Quatre variantes figées, sept opérations qui arrivent une par une : l'axe est
sans ambiguïté. Et pourtant le code d'origine fait l'inverse — une interface
avec les sept méthodes, et quatre types qui les implémentent toutes. Chaque
nouvelle question a coûté **quatre modifications**, et le métier n'a jamais
rien demandé de ce qui aurait rendu ces quatre modifications utiles.

Même plateforme, autre endroit. L'autorisation d'un paiement par carte passe
par une **passerelle** : la monétique du groupement bancaire, l'API Orange
Money, celle de MTN, et deux agrégateurs qu'on évalue.

**Combien de passerelles a-t-on ajoutées l'an dernier ?** Quatre. Celle de
l'an prochain n'est pas encore choisie.

**Combien d'opérations nouvelles leur a-t-on demandées ?** Zéro. Autoriser,
capturer, rembourser : c'est le protocole d'un paiement, il est stable depuis
vingt ans, et aucun prestataire n'inventera une quatrième étape.

L'axe est inversé, et donc la réponse aussi. Dans le même programme.

> Les deux mécanismes coexistent, dans deux sens opposés, et c'est l'axe du
> changement qui a décidé — jamais le goût, jamais la règle apprise.

Et puisque c'est l'axe qui décide, il faut pouvoir le lire. Dans un dépôt
réel, ça se mesure : `git log` par fichier, sur douze mois, et on compte les
commits qui ajoutent une variante contre ceux qui ajoutent une question. La
leçon 1.4 avait déjà utilisé ce genre de relevé pour autre chose ; ici il
répond à la question de la conception, directement.

## 4. Le mécanisme

Tout ce qui suit est dans un module qui compile, dont les tests passent, et
dont les chiffres cités sont des sorties de commande.

### Le modèle d'origine : une interface, sept méthodes

```go
// PaymentMeans is the original interface: seven methods.
// Seven methods are seven questions EACH variant must be able to
// answer, including those that have no opinion. And as the interface
// is not sealed, any package can add a fifth
// without anyone knowing.
type PaymentMeans interface {
    Label() string
    Fees(amountFCFA int64) int64
    LedgerLine() string
    AvailabilityDelayDays() int
    IsRefundable() bool
    CapFCFA() int64
    Authorize(amountFCFA int64) (string, error)
}
```

Sept méthodes. Lis-les comme sept **questions**, et demande-toi à qui chacune
est posée.

```go
// Card must now know: the tariff grid, the chart of accounts,
// the bank calendar and the gateway's address.
type Card struct {
    Network    string
    LastFour   string
    Grid       tariff.Grid
    GatewayURL string
    Client     *http.Client
}
```

Une carte bancaire porte maintenant une grille tarifaire, l'adresse d'une
passerelle et un client HTTP. Elle a quatre numéros de téléphone et un
camion. Ce n'est pas du mauvais goût, c'est une **conséquence mécanique** :
l'interface a exigé sept réponses, et une variante qui doit répondre doit
d'abord savoir.

> Le polymorphisme déplace la connaissance, il ne la supprime pas. Chaque
> méthode ajoutée à une interface est un **impôt prélevé sur chaque
> implémentation** : elle doit désormais connaître ce qu'il faut pour
> répondre.

### Cinq défauts, démontrés

Je ne les affirme pas. Chacun est une mesure ou une sortie de compilateur.

**Défaut 1 — la variante importe le monde.** La liste des imports est la
mesure, et elle ne demande aucune interprétation :

```
$ go list -f '{{join .Imports " "}}' ./avant
errors exemple/paiement/plan exemple/paiement/tarif fmt net/http net/url strings

$ go list -f '{{join .Imports " "}}' ./means
errors fmt strings
```

Sept imports contre trois. Et parmi les sept : `net/http`, parce qu'une
variante autorise ; `plan`, parce qu'une variante connaît le plan comptable ;
`tariff`, parce qu'une variante calcule des frais. Chacun de ces trois imports
est une question mal adressée.

**Défaut 2 — aucun test ne s'écrit.**

```go
// Authorize makes a network call from a payment means variant.
// Immediate consequence: no test of this package can be written without a
// double, and it is exactly what lesson 1.6 called a difficulty
// write a test that measures the design.
func (c Card) Authorize(amountFCFA int64) (string, error) {
    rep, err := c.Client.PostForm(c.GatewayURL, url.Values{
        "network": {c.Network},
        "amount":  {fmt.Sprint(amountFCFA)},
    })
    if err != nil {
        return "", err
    }
    defer rep.Body.Close()
    if rep.StatusCode != http.StatusOK {
        return "", fmt.Errorf("%w: status %d", ErrRefused, rep.StatusCode)
    }
    return rep.Header.Get("X-Autorisation"), nil
}
```

Un appel réseau depuis une variante de moyen de paiement. Essaie d'écrire le
test de `Fees` : tu construis une `Card`, et tu dois lui donner un
`*http.Client` dont ce test n'a rien à faire. La leçon 1.6 l'avait formulé
ainsi : *la difficulté d'écrire un test n'est pas une propriété du test, c'est
une mesure de la conception.* Ici l'étape qui fait mal est la première —
**construire**.

**Défaut 3 — deux sens pour une valeur.**

```go
// AvailabilityDelayDays for a voucher: the question makes no sense,
// no money ever reaches a bank account. The method returns 0, and
// 0 means "not applicable" here while it means "immediate" for
// MobileMoney. Two meanings for the same value, in the same type.
func (b Voucher) AvailabilityDelayDays() int { return 0 }
```

`MobileMoney.AvailabilityDelayDays()` rend `0` pour *immédiat*.
`Voucher.AvailabilityDelayDays()` rend `0` pour *la question n'a pas de
sens*. Le même type, la même signature, la même valeur, deux sens opposés, et
**aucun appelant capable de les distinguer**. L'interface a forcé une réponse
là où la bonne réponse était « cette question ne m'est pas posée ».

**Défaut 4 — l'ensemble est ouvert alors que le métier l'a fermé.** N'importe
quel paquet peut déclarer un cinquième moyen de paiement, et le routeur
l'acceptera. Le métier a mis un trimestre et un comité pour fermer cet
ensemble ; le code l'a rouvert gratuitement.

**Défaut 5 — et c'est celui qui coûte le plus cher** — rien n'est une valeur.
`Card` contient un `*http.Client`. Elle n'est donc pas comparable, pas une
clé de map, pas partageable entre goroutines sans réflexion. Tout ce que la
leçon 2.1 avait gagné en déclarant un moyen de paiement comme une valeur, les
sept méthodes l'ont repris.

### Première forme : l'ensemble fermé, et le ⚫ qui le ferme

```go
// Package means defines the payment means the platform accepts.
//
// The set of variants is CLOSED. There are only four, and a
// fifth is not added by surprise: it is added by a contract
// signed, one quarter ahead. This package tells the compiler rather
// than to the reader, with an unexported method: see PaymentMeans.
//
// The variants are VALUES in the sense of lesson 2.1: two cards whose
// fields are all equal are the same payment means. So they are
// comparable, immutable, and built by a constructor that refuses what
// is not canonical.
package means
```

L'interface, maintenant :

```go
// PaymentMeans is the closed set of accepted payment means.
// The method means() is NOT exported. Consequence: no type declared
// in another package can satisfy this interface, even by declaring
// a method named means() too: the name of an unexported method
// includes its package path, and the two will never be the same name.
// So the set of implementations is known at compile time, and it fits
// in this file.
//
// It is a ⚫: the state "a payment means variant this package does not
// does not know" cannot be represented.
//
// Label is the ONLY operation carried by the variants themselves, and the
// criterion has a single line: a method belongs to the variant if and
// only if it is answered with the variant's fields. Label
// answers. Fees needs a tariff grid, LedgerLine a chart of
// accounts, AvailabilityDelay a bank calendar: none of the three is
// is answered with them. So they live at their callers, and the proof that nothing
// leaked is the import list of this file.
type PaymentMeans interface {
    means()
    Label() string
}
```

Deux choses à y voir.

**`means()` n'est pas exportée, et ça scelle l'ensemble.** Aucun type d'un
autre paquet ne peut satisfaire `PaymentMeans` — pas même en déclarant lui
aussi une méthode nommée `means()`, parce que le nom d'une méthode non
exportée **inclut le chemin de son paquet**. C'est un ⚫ : l'état « une
variante de moyen de paiement que ce paquet ne connaît pas » n'est pas
représentable.

Et ce n'est pas une affirmation. Le compilateur donne **deux messages
différents** selon la façon de s'y prendre, et la différence est la preuve du
mécanisme :

```
# sans methode means() du tout
Crypto does not implement means.PaymentMeans (missing method means)

# avec une methode means() declaree dans un autre paquet
Crypto does not implement means.PaymentMeans (unexported method means)
```

« *missing* » dans un cas, « *unexported* » dans l'autre. Le compilateur la
voit, et il la refuse parce que ce n'est pas la même méthode.

**`Label` est la seule opération que les variantes portent**, et le critère
qui l'a décidé tient en une ligne :

> Une méthode appartient à la variante **si et seulement si elle se répond
> avec les champs de la variante**.

`Label` s'y répond. `Fees` a besoin d'une grille tarifaire.
`LedgerLine` d'un plan comptable. `DelaiDisponibilite` d'un calendrier
bancaire. Aucune des trois ne s'y répond, donc aucune des trois n'y est. Et la
preuve que rien n'a fui, c'est la liste des trois imports de ce fichier :
`errors`, `fmt`, `strings`.

Une variante, en entier :

```go
// Card is a payment by bank card.
type Card struct {
    reseau Network
    four   string
}

// NewCard builds a card. lastFour is what the platform
// is allowed to keep: four digits, and nothing else.
func NewCard(reseau Network, lastFour string) (Card, error) {
    if reseau != Visa && reseau != Mastercard {
        return Card{}, fmt.Errorf("%w: %d", ErrUnknownNetwork, reseau)
    }
    if !digits(lastFour, 4) {
        return Card{}, fmt.Errorf("%w: last four %q", ErrFormat, lastFour)
    }
    return Card{reseau: reseau, four: lastFour}, nil
}

func (c Card) means()           {}
func (c Card) Network() Network { return c.reseau }
func (c Card) Label() string    { return c.reseau.String() + " ****" + c.four }
```

C'est une **valeur**, au sens exact de la leçon 2.1 : champs privés,
constructeur qui refuse le non-canonique, immuable, comparable. Et cette fois
`==` est la **bonne** égalité — l'inverse exact du choix fait pour l'entité de
la 2.1, pour la même raison retournée : deux cartes aux mêmes champs *sont* le
même moyen de paiement.

Le gain est concret et il tient en un test : une variante est une clé de map.

### Ce que Go donne, et les deux choses qu'il ne donne pas

Voilà où la leçon devient spécifique à Go, et où la plupart des explications
du polymorphisme s'arrêtent trop tôt.

| | Go le donne ? |
|---|---|
| la **clôture de l'ensemble des implémentations** | **oui**, gratuitement, par la méthode non exportée |
| l'**exhaustivité du traitement** | **non**. Un `switch` à trois cas plus un `default` compile parfaitement |
| la **clôture de l'ensemble des valeurs** | **non**. `nil` satisfait toute interface, toujours |

Les deux « non » coûtent, et il faut les payer explicitement.

**Le deuxième « non » m'a coûté un défaut, et le test l'a trouvé.** La
première version de `accounting.Entry` construisait sa ligne avant le
`switch`, donc appelait `m.Label()` avant de savoir ce qu'était `m` :

```
--- FAIL: TestLeDefautRendUneErreurEtNonUnePanique (0.00s)
panic: runtime error: invalid memory address or nil pointer dereference
exemple/paiement/accounting.Entry({0x0, 0x0}, {0x0?})
    comptable/accounting.go:51
```

> Le scellement ferme l'ensemble des **implémentations**. Il ne ferme pas
> l'ensemble des **valeurs**. L'ensemble n'a pas quatre variantes, il en a
> cinq, et la cinquième ne se déclare nulle part.

La correction, et le `case nil` en premier :

```go
// Entry returns the accounting entry of a collection.
// The type switch is HERE, at the caller. It is here for a reason that is
// not taste: putting a method on a variant is giving it a
// dependency. LedgerLine() on Card would force package means to
// know the chart of accounts, that is to change when the chart changes:
// while a bank card does not change when an accountant
// renumbers an account.
//
// Polymorphism moves knowledge, it does not remove it. The only
// question is where it must land.
func Entry(m means.PaymentMeans, sum amount.Amount) (Line, error) {
    // The type switch comes BEFORE any method call on m, and the first
    // case is nil.
    //
    // It is not caution, it is the repair of a flaw that the
    // test found. The first version built the Line first, so
    // called m.Label() before knowing what m was, and panicked on
    // a nil interface.
    //
    // The seal closes the set of IMPLEMENTATIONS. It does not close
    // the set of VALUES: nil satisfies every interface, always, and
    // no unexported method changes anything. So the set does not have
    // four variants, it has five, and the fifth is declared nowhere
    // place.
    l := Line{Counterpart: plan.ActiveClients, Sum: sum}
    switch v := m.(type) {
    case nil:
        return Line{}, fmt.Errorf("%w: nil interface", ErrMeansNotHandled)
    case means.Card:
        // Mastercard collections go through a dedicated account since
        // the March amendment. Exactly the kind of rule that has no business
        // do in package means: it comes from the chart of accounts, it
        // will change with it, and a bank card has nothing to do with it.
        l.Account = plan.BankCard
        if v.Network() == means.Mastercard {
            l.Account = plan.BankCardMC
        }
    case means.MobileMoney:
        l.Account = plan.MobileMoney
    case means.Transfer:
        l.Account = plan.BankTransfer
    case means.Voucher:
        // A voucher collects nothing: it settles a debt the
        // platform already had towards the client. The counterpart changes.
        l.Account = plan.VouchersIssued
        l.Counterpart = plan.ActiveClients
    default:
        return Line{}, fmt.Errorf("%w: %T", ErrMeansNotHandled, m)
    }
    l.Label = m.Label()
    return l, nil
}
```

### Les deux tests qui achètent l'exhaustivité

```go
// Package exhaustiveness_test buys what Go does not give.
//
// Go gives the CLOSURE of the set of IMPLEMENTATIONS: the unexported
// unexported means() makes any implementation outside the package impossible, and
// it is free. It does not give two other things.
//
// It does not give EXHAUSTIVENESS of handling: no compiler
// will check that a type switch handles the four variants, and a switch with
// three cases plus a default compiles perfectly.
//
// And it does not give the closure of the set of VALUES: nil satisfies
// every interface, always. So the set has a fifth variant that
// nothing declares, and this package requires it in each switch.
//
// Closure is free, exhaustiveness is paid for in tests. There are two
// here, and they do not replace each other:
//
//   - by REPETITION: walk means.Variants() and require that no
//     operation falls into its default. It is simple, and it is worth something only if
//     Variants() is complete.
//   - by READING THE SOURCE: read means/*.go with go/ast to establish
//     the true list of variants, then read the module's type switches. It is
//     that test that guards the other.
//
// They are two of the three mechanisms of lesson 1.6: by value, by
// repetition, by reading the source: and it is the second time they
// are used.
package exhaustiveness_test
```

Le premier établit la **liste vraie** des variantes en lisant la source — tout
type du paquet qui porte la méthode de scellement. C'est la définition exacte
de « appartenir à l'ensemble », et elle ne dépend d'aucune liste écrite à la
main :

```go
// variantsFromSource establishes the TRUE list of variants: every type of the
// package means that carries the unexported method means().
//
// It is the exact definition of "belonging to the sealed set". It does not
// depend on any hand-written list, and that is the whole point.
func variantsFromSource(t *testing.T) []string {
    t.Helper()
    fset := token.NewFileSet()
    pkgs, err := parser.ParseDir(fset, sealedPkg, nil, 0)
    if err != nil {
        t.Fatalf("reading %s: %v", sealedPkg, err)
    }
    var names []string
    for _, p := range pkgs {
        for _, f := range p.Files {
            for _, d := range f.Decls {
                fn, ok := d.(*ast.FuncDecl)
                if !ok || fn.Recv == nil || fn.Name.Name != "means" {
                    continue
                }
                if n := receiverName(fn.Recv); n != "" {
                    names = append(names, n)
                }
            }
        }
    }
    slices.Sort(names)
    if len(names) == 0 {
        t.Fatal("no variant found: the seal method changed its name")
    }
    return names
}
```

Le second parcourt les fichiers de production, retient ceux qui importent le
paquet scellé, et exige de chaque `switch` les quatre variantes **plus le cas
`nil`** :

```go
// TestEachTypeSwitchOnAMeansIsExhaustive is the test that pays back the
// debt of the default.
//
// It walks every production file of the module, keeps those that
// import the sealed package, and for each type switch where at least one case
// names a variant, requires that all four be there.
//
// NOT GUARANTEED, and it must be said: the criterion "at least one case names a
// variant" is a heuristic. A type switch that named no
// known variant would not be examined, and handling written with
// if/else instead of a switch would escape entirely. This test catches the case
// by far the most frequent (the variant added and the switch forgotten), and not
// every case.
func TestEachTypeSwitchOnAMeansIsExhaustive(t *testing.T) {
    variants := variantsFromSource(t)
    examined := 0
    err := filepath.WalkDir(root, func(path string, d fs.DirEntry, err error) error {
        if err != nil {
            return err
        }
        if d.IsDir() || !strings.HasSuffix(path, ".go") || strings.HasSuffix(path, "_test.go") {
            return nil
        }
        fset := token.NewFileSet()
        f, err := parser.ParseFile(fset, path, nil, 0)
        if err != nil {
            return fmt.Errorf("%s: %w", path, err)
        }
        if !imported(f, importPath) {
            return nil
        }
        ast.Inspect(f, func(n ast.Node) bool {
            sw, ok := n.(*ast.TypeSwitchStmt)
            if !ok {
                return true
            }
            handled := casesOfATypeSwitch(sw, variants)
            if len(handled) == 0 {
                return true
            }
            examined++
            pos := fset.Position(sw.Pos())
            for _, v := range variants {
                if !slices.Contains(handled, v) {
                    t.Errorf("%s:%d: the type switch does not handle means.%s (handled: %v)",
                        path, pos.Line, v, handled)
                }
            }
            // The fifth variant. nil satisfies every interface, the
            // seal changes nothing about it, and a switch that does not name it
            // lets it fall into its default, or worse, lets
            // a method on it before getting there. It is the flaw that a
            // test found in accounting.Entry, and this requirement is
            // there so that it does not come back.
            if !handlesNilCase(sw) {
                t.Errorf("%s:%d: the type switch does not handle the nil case", path, pos.Line)
            }
            return true
        })
        return nil
    })
    if err != nil {
        t.Fatalf("walking the module: %v", err)
    }
    if examined == 0 {
        t.Fatal("no type switch examined: the test watches nothing any more")
    }
    t.Logf("%d production type switches examined: %d variants required in each, plus the nil case",
        examined, len(variants))
}
```

Note la clause **NON GARANTI** dans la documentation du test. Le critère « au
moins un cas nomme une variante » est une heuristique : un traitement écrit en
`if`/`else` y échappe entièrement. Ce test attrape le cas de très loin le plus
fréquent — la variante ajoutée, le `switch` oublié — et pas tous les cas. Le
dire fait partie du test.

### L'expérience : on ajoute une cinquième variante

C'est la mesure centrale de la leçon. J'ajoute `ALaLivraison` au paquet
scellé, et j'observe, par étapes.

**Étape 1 — la variante existe, et rien d'autre n'a bougé.**

```
$ go build ./...
COMPILE : OUI — le compilateur n'a rien a dire

$ go test -count=1 ./...
--- FAIL: TestLaListeVariantesEstComplete
    variantes declarees dans la source : [ALaLivraison Voucher Card MobileMoney Transfer]
    variantes rendues par Variants()  : [Voucher Card MobileMoney Transfer]
--- FAIL: TestEachTypeSwitchOnAMeansIsExhaustive
    ../comptable/accounting.go:52     : ne traite pas means.ALaLivraison
    ../disponibilite/disponibilite.go:51 : ne traite pas means.ALaLivraison
```

Le compilateur n'a rien dit. **Deux tests** l'ont dit, et ils ont nommé les

Mais regarde le troisième test, celui par la répétition, lancé seul :

```
$ go test -count=1 -run TestNoOperationFallsIntoItsDefault ./exhaustivite/
```

Il passe. Il parcourt `Variants()`, et `Variants()` est incomplète. C'est

**Étape 2 — `Variants()` est complétée, les `switch` ne bougent pas.**

```
--- PASS: TestLaListeVariantesEstComplete

```

Le relais s'est fait : le garde est vert, et les deux tests qu'il gardait
tombent ensemble.

**Étape 3 — les deux `switch` sont complétés.** Tout est vert. Bilan :
**quatre fichiers de production touchés** — le paquet scellé, les deux
appelants, et le plan comptable pour le nouveau compte.

### La deuxième expérience : on ajoute une opération

`disponibilite` **est** cette expérience. Il répond à une question nouvelle —
à partir de quand l'argent est disponible — et il a coûté :

- **un paquet nouveau**, et rien d'autre ;
- **zéro** modification du paquet scellé ;
- **zéro** méthode ajoutée aux quatre variantes ;
- aucune variante n'a appris ce qu'est un jour ouvré.

```go
// Delay returns the number of BUSINESS days before availability.
// The delay is not a method of the variant, because it is not answered
// with the variant's fields: it needs a calendar. And a calendar
// is data that changes (decreed holidays, bank closures),
// while a bank card does not change.
func Delay(m means.PaymentMeans) (int, error) {
    switch m.(type) {
    case nil:
        // nil is the fifth variant the seal does not close: a
        // nil interface satisfies every interface. The case is explicit here
        // so that the message says so, and so that it is not confused with
        // a forgotten variant.
        return 0, fmt.Errorf("%w: nil interface", ErrMeansNotHandled)
    case means.Card:
        return 2, nil
    case means.MobileMoney:
        return 0, nil
    case means.Transfer:
        return 3, nil
    case means.Voucher:
        // A voucher makes no money available: it settles a
        // debt. The question does not arise, and saying so is a more
        // useful one than zero.
        return 0, fmt.Errorf("%w: %T", ErrNotApplicable, m)
    default:
        return 0, fmt.Errorf("%w: %T", ErrMeansNotHandled, m)
    }
}
```

Le tableau de la section 2, rempli avec les chiffres mesurés sur ce module :

| | ajouter une variante | ajouter une opération |
|---|---|---|
| **ensemble fermé** (`means`) | 4 fichiers | **1 fichier** |
| **interface à 7 méthodes** (`before`) | **1 fichier** | 1 fichier, 5 endroits — et voir plus bas |

### L'asymétrie que je croyais trouver, et celle qui est vraie

Avant de mesurer, j'étais sûr de la conclusion. Dans un langage à typage
nominal — Java, C#, Rust — ajouter une méthode à une interface **casse la
compilation de chaque implémentation**, et le compilateur te donne la liste
des endroits à corriger. Je m'attendais donc à une asymétrie nette : le
compilateur aide sur l'axe des opérations, il abandonne sur l'axe des
variantes.

J'ai ajouté une huitième méthode à l'interface de `before`. Résultat :

```
$ go build ./avant/
$ echo $?
0
```

**Zéro erreur.** Quatre types qui n'implémentent plus l'interface, et le
compilateur ne dit rien — parce que Go n'a pas de déclaration `implements`, et
que personne n'avait écrit qu'une `Card` était un `PaymentMeans`. Le
typage structurel, qui rend les interfaces si légères à déclarer, retire en
même temps la seule chose que le typage nominal donnait gratuitement : **la
liste des sites à corriger**.

Alors j'ai ajouté les quatre lignes que presque personne n'écrit :

```go
// The four conformance assertions.
// They are NOT decorative, and it is measured in the lesson: without them,
// adding a method to PaymentMeans compiles without a single error, because
// because Go has no "implements" declaration and so has nothing to check.
// With them, the four sites to fix appear immediately.
//
// These four lines are Go's "implements" declaration, written by
// hand. It is the only place in the language where it is found, and almost nobody
// writes it.
var (
    _ PaymentMeans = Card{}
    _ PaymentMeans = MobileMoney{}
    _ PaymentMeans = Transfer{}
    _ PaymentMeans = Voucher{}
)
```

Et la huitième méthode, à nouveau :

```
$ go build ./avant/
avant/before.go:171:22: Card does not implement PaymentMeans (missing method EstContestable)
avant/before.go:172:22: MobileMoney does not implement PaymentMeans (missing method EstContestable)
avant/before.go:173:22: Transfer does not implement PaymentMeans (missing method EstContestable)
avant/before.go:174:22: Voucher does not implement PaymentMeans (missing method EstContestable)
```

**Zéro erreur sans les assertions, quatre avec.** La vraie conclusion n'est
donc pas une asymétrie, c'est une symétrie désagréable :

> En Go, le compilateur n'aide sur **aucun** des deux axes, par défaut.
> Ajouter une variante ne casse aucun `switch`. Ajouter une méthode ne casse
> aucune implémentation. Chaque garantie se **déclare** : une assertion de
> conformité d'un côté, un test qui lit la source de l'autre.

Un détail qui a son charme : du côté de l'ensemble scellé, la garantie existe
déjà **sans qu'on l'ait écrite pour ça**. `Variants()` assigne les quatre
variantes à `PaymentMeans` dans un littéral de slice, ce qui est une
assertion de conformité qui ne se présente pas comme telle. Ajouter une
méthode à l'interface scellée donne immédiatement quatre erreurs.

```go
// Variants returns one instance of each variant.
// This function exists for a single reason: to let a test
// walk the closed set without copying it. It has the flaw of every
// hand-written list: it can be incomplete. It is exactly what
// that package exhaustiveness watches, by reading this file.
func Variants() []PaymentMeans {
    return []PaymentMeans{
        Card{reseau: Visa, four: "4242"},
        MobileMoney{operator: Orange, number: "699000001"},
        Transfer{bank: "AFRIBQXX", reference: "VIR-1"},
        Voucher{code: "BONJANVIER24"},
    }
}
```

### Deuxième forme : l'ensemble ouvert, et l'interface de l'appelant

On change de côté du programme et d'axe.

```go
// Package routing picks the gateway that will handle an authorization.
//
// It is the SECOND form of polymorphism of the lesson, and it goes the
// opposite way of the first. The set of gateways is OPEN: one
// comes one per quarter, each with its contract, and next year's
// is not chosen yet. The set of operations is CLOSED:
// authorize, capture, refund: it is the protocol of a card payment,
// card payment, it has been fixed for twenty years.
//
// Open on variants, closed on operations: it is exactly the
// case where the interface is the right tool, and where the sum type would be the wrong one.
// So the same program holds both mechanisms, in two opposite
// directions, and it is not an inconsistency: it is the axis of change that
// decides, not taste.
package routing
```

L'interface :

```go
// Gateway is THIS PACKAGE's interface.
// It is declared here, at its user, and not in the package that
// implements it. Its signature names only types of package operation,
// that is of the shared vocabulary: it is on this condition, and on this
// condition only, that the gateway need not import its caller.
//
// It is Go's structural typing that allows it, and it is not a
// convenience: it is what makes the interface's size a property of
// the CALLER. The router needs two things from a
// gateway: knowing its name, and asking it for an
// authorization. So it declares two methods.
//
// Real gateways have five or six. No caller sees them
// all, and it is the subject of lesson 2.5.
type Gateway interface {
    Name() string
    Authorize(d operation.Request) (operation.Authorization, error)
}

// Journal records what the router does.
//
// TWO methods, and the second is the lesson of the incident: Selection is
// called at the moment of CHOICE, before knowing whether it works. A journal that
// records only the result does not let one attribute an outage to a
// gateway, because whoever writes the result line does not know who
// was chosen.
type Journal interface {
    Selection(reference, rule, gateway string)
    Result(reference string, err error)
}
```

**Elle est déclarée chez celui qui s'en sert.** C'est le typage structurel de
Go qui le permet, et ce n'est pas une commodité :

> Déclarer l'interface chez l'appelant fait de la **taille de l'interface une
> propriété de l'appelant**, et non de l'implémentation.

Le routeur a besoin de deux choses d'une passerelle. Il déclare deux méthodes.
Les passerelles réelles en ont trois. Et un troisième appelant n'en veut
qu'une :

```go
// Package refund refunds a payment already captured.
//
// It declares its own interface, with ONE method, and it is the second half
// of the demonstration: the gateways carry three methods, the router
// declares two, this package declares one. Three interface sizes for one
// same implementation, each the size of its caller's need.
//
// Practical consequence, and it is not aesthetic: the double this
// package needs for its tests has ONE method to write. The router's has
// has two. A double of the original model's seven-method interface
// had seven, five of them empty.
package refund

import (
    "errors"
    "fmt"

    "example/payment/amount"
)

// ErrRefundRefused: the gateway refused the refund.
var ErrRefundRefused = errors.New("refund: refused")

// Refunder is this package's interface. One method, because this package
// does one thing only.
type Refunder interface {
    Refund(reference string, sum amount.Amount) error
}

// Refund refunds, and returns what was given back.
func Refund(r Refunder, reference string, sum amount.Amount) (amount.Amount, error) {
    if sum.IsZero() {
        return amount.Zero, fmt.Errorf("%w: zero sum for %s", ErrRefundRefused, reference)
    }
    if err := r.Refund(reference, sum); err != nil {
        return amount.Zero, fmt.Errorf("%w: %s: %w", ErrRefundRefused, reference, err)
    }
    return sum, nil
}
```

Trois tailles d'interface pour la même implémentation, chacune à la taille du
besoin de son appelant. La conséquence pratique n'est pas esthétique, elle est
chiffrable : **le double dont `refund` a besoin pour ses tests a une
méthode à écrire.** Celui du routeur en a deux. Un double de l'interface à
sept méthodes du modèle d'origine en aurait sept, dont six vides — et six
méthodes vides dans un test, c'est six endroits où une future méthode ira se
cacher.

C'est le fil qui mène à la leçon 2.5. On n'y est pas encore.

### Le piège, mesuré

J'ai écrit la première version de `Gateway` avec `routing.Request` et
`routing.Authorization` dans sa signature. Puis j'ai mesuré :

```
$ go list -f '{{join .Imports " "}}' ./passerelles
exemple/paiement/routage fmt
```

**La passerelle importait son appelant.** La flèche n'avait pas été inversée,
elle avait été déguisée : l'interface était bien déclarée chez l'appelant,
mais sa signature nommait des types de l'appelant, donc l'implémentation
devait l'importer quand même.

```go
// Package operation holds the vocabulary shared between a router and the
// gateways it calls.
//
// This package exists because of a measure. The Gateway interface is declared
// by the router, which is the right rule; but the first version of its
// signature named routing.Request and routing.Authorization, and the result
// was:
//
//    $ go list -f '{{join .Imports " "}}' ./gateways
//    example/payment/routing fmt
//
// The gateway imported its caller. The arrow had not been reversed,
// it had only been disguised.
//
// The rule it gives: declaring an interface at the caller decouples
// only if its signature names only SHARED types. Otherwise the dependency
// comes back through the arguments. Decoupling by interface moves the
// dependency to the vocabulary; if the vocabulary has no package, it
// falls back on the caller.
package operation
```

Après correction :

```
$ for p in operation routage passerelles remboursement; do
>   printf '%-16s : ' $p; go list -f '{{join .Imports " "}}' ./$p
> done
operation        : example/payment/amount exemple/paiement/means
routage          : errors exemple/paiement/operation fmt
passerelles      : errors example/payment/amount exemple/paiement/operation fmt math/rand
remboursement    : errors example/payment/amount fmt
```

`gateways` n'importe plus `routing`. `refund` n'importe ni l'un ni
l'autre — son interface à une méthode ne nomme que `string` et
`amount.Amount`.

> Déclarer une interface chez l'appelant ne découple **que si sa signature ne
> nomme que des types partagés**. Le découplage par interface déplace la
> dépendance vers le **vocabulaire** ; si le vocabulaire n'a pas de paquet,
> elle retombe sur l'appelant.

Et le corollaire, qui explique pourquoi `io.Writer` a traversé quinze ans sans
bouger : une interface dont la signature ne nomme que des types primitifs ou
universels est la seule qui découple vraiment. `Write([]byte) (int, error)` ne
nomme rien que tout le monde n'ait déjà.

### Le routeur, et la décision séparée de l'effet

```go
// Choose returns the chosen gateway and the name of the rule that chose it.
// It is exported apart from Authorize for a test reason: the choice
// is a DECISION, the authorization is an EFFECT, and lesson 1.6 says to
// separate them so as to observe the first without triggering the second.
func (r *Router) Choose(d operation.Request) (Gateway, string, error) {
    for _, rule := range r.rules {
        if rule.Fits(d) {
            return rule.Gateway, rule.Name, nil
        }
    }
    if r.fallback != nil {
        return r.fallback, "fallback", nil
    }
    return nil, "", fmt.Errorf("%w: %s", ErrNoGateway, d.Reference)
}

// Authorize chooses, logs the choice, then calls.
func (r *Router) Authorize(d operation.Request) (operation.Authorization, error) {
    p, rule, err := r.Choose(d)
    if err != nil {
        r.journal.Result(d.Reference, err)
        return operation.Authorization{}, err
    }
    // The choice is logged BEFORE the call. If the call times out after
    // thirty seconds and the process is then killed, the selection line
    // already exists, and it is the only one that will tell who did not
    // did not answer.
    r.journal.Selection(d.Reference, rule, p.Name())
    a, err := p.Authorize(d)
    r.journal.Result(d.Reference, err)
    if err != nil {
        return operation.Authorization{}, err
    }
    return a, nil
}
```

Deux choses, dont une qui vient de la leçon 1.6 et une qui vient de
l'incident.

`Choose` est exportée séparément de `Authorize` parce que **le choix est une
décision et l'autorisation est un effet**, et qu'on veut observer la première
sans déclencher la seconde. Le test tient en quinze lignes et il ne touche pas
le réseau.

Et `Selection` est journalisée **avant** l'appel. Si l'appel part en timeout
de trente secondes puis que le processus est tué, la ligne de sélection existe
déjà. C'est la seule qui permettra de savoir qui ne répondait pas, et la
section 7 montre ce que ça coûte de ne pas l'avoir.

### Le polymorphisme qui ne décide rien

Dernier cas, et c'est celui que tu rencontreras le plus souvent dans du code
hérité. Trois types, une interface, et un calcul de frais :

```go
package fees

import "example/payment/amount"

// Calc is the original interface of fee computation, with its three
// implementations. It is kept in this file for a single reason:
// the equivalence test of fees_test.go compares its results with those of the
// scale, and it is this comparison that decides.
type Calc interface {
    Fees(m amount.Amount) (amount.Amount, error)
}

// Fixed always returns the same amount.
type Fixed struct {
    Share amount.Amount
}

// Fees ignores its argument. An implementation that does not use the
// parameter the interface imposes is the first hint that the interface
// describes the caller's need and not a family of behaviors.
func (f Fixed) Fees(m amount.Amount) (amount.Amount, error) {
    return f.Share, nil
}

// Proportional returns a fraction of the amount, per mille.
type Proportional struct {
    PerMille int64
}

func (p Proportional) Fees(m amount.Amount) (amount.Amount, error) {
    return m.PerMille(p.PerMille)
}

// Capped returns a fraction of the amount, without exceeding a cap.
type Capped struct {
    PerMille int64
    Cap      amount.Amount
}

func (p Capped) Fees(m amount.Amount) (amount.Amount, error) {
    f, err := m.PerMille(p.PerMille)
    if err != nil {
        return amount.Zero, err
    }
    if f.Exceeds(p.Cap) {
        return p.Cap, nil
    }
    return f, nil
}
```

Ça a l'air d'un polymorphisme en règle : une interface, trois implémentations,
chacune avec son calcul. Un premier indice qu'il n'en est pas un est dans le
commentaire de `Fixed.Fees` — **elle n'utilise pas son argument**. Une
implémentation qui ignore le paramètre que l'interface lui impose dit que
l'interface décrit le besoin de l'appelant et non une famille de
comportements.

Mais l'indice ne prouve rien. Ce qui prouve, c'est un **test d'équivalence** :

```go
// Scale is the standard scale: a proportional share per mille,
// a fixed share, and an optional cap.
//
// These three fields cover exactly the three types of polymorphic.go:
//
//    Fixed{X}                -> Scale{Fixed: X}
//    Proportional{P}         -> Scale{PerMille: P}
//    Capped{P, C}            -> Scale{PerMille: P, Cap: C}
//
// Three types, three methods, three test sets replaced by three
// fields. The three implementations did not differ by their SHAPE of
// computation, they differed by constants: and a polymorphism that
// tells only constants apart is a table that does not know itself.
type Scale struct {
    PerMille int64
    Fixed    amount.Amount
    // Cap at zero means "no cap". It is the zero value as
    // sensible default, in the sense of lesson 2.1: a scale without a cap
    // is the common case.
    Cap amount.Amount
}

func (b Scale) Fees(m amount.Amount) (amount.Amount, error) {
    share, err := m.PerMille(b.PerMille)
    if err != nil {
        return amount.Zero, err
    }
    total, err := share.Plus(b.Fixed)
    if err != nil {
        return amount.Zero, err
    }
    if !b.Cap.IsZero() && total.Exceeds(b.Cap) {
        return b.Cap, nil
    }
    return total, nil
}
```

```go
// TestTheThreeTypesReduceToAScale is the test that decides.
// It does not say the table is "cleaner". It says that for every
// witness amount, the three implementations and the scale return the SAME
// result. If it is true, the three types told nothing apart: three
// methods, three test sets and an interface replaced by three fields.
func TestTheThreeTypesReduceToAScale(t *testing.T) {
    tc := []struct {
        name        string
        polymorphic fees.Calc
        table       fees.Scale
    }{
        {
            "fixed fees of 100 FCFA",
            fees.Fixed{Share: m(100)},
            fees.Scale{Fixed: m(100)},
        },
        {
            "proportional fees of 25 per mille",
            fees.Proportional{PerMille: 25},
            fees.Scale{PerMille: 25},
        },
        {
            "fees of 25 per mille capped at 5 000 FCFA",
            fees.Capped{PerMille: 25, Cap: m(5_000)},
            fees.Scale{PerMille: 25, Cap: m(5_000)},
        },
    }
    for _, c := range tc {
        t.Run(c.name, func(t *testing.T) {
            for _, v := range witnessAmounts {
                want, err1 := c.polymorphic.Fees(m(v))
                got, err2 := c.table.Fees(m(v))
                if (err1 == nil) != (err2 == nil) {
                    t.Fatalf("at %d FCFA: different errors, polymorphic=%v table=%v", v, err1, err2)
                }
                if want != got {
                    t.Errorf("at %d FCFA: polymorphic returns %s, table returns %s", v, want, got)
                }
            }
        })
    }
}
```

Le test ne dit pas que la table est « plus propre ». Il dit que **pour tout
montant témoin, les trois implémentations et le barème rendent le même
résultat**. Si c'est vrai, les trois types ne distinguaient rien.

> Quand deux implémentations ne diffèrent que par des **constantes**, le
> polymorphisme est un tableau. Trois types, trois méthodes, trois jeux de
> tests et une interface remplacés par trois champs.

### Le seuil exact où le polymorphisme se paie

La question suivante est la seule qui compte : **à partir de quand
l'interface redevient-elle justifiée ?**

Au quatrième trimestre, un avenant apporte un barème dégressif : le taux
baisse par palier. Et là, il faut être précis, parce que la réponse n'est pas
« dès qu'il y a un cas de plus ».

Le barème dégressif **ne se ramène pas** à un `Scale`. Et ce n'est pas une
affirmation : un `Scale` est toujours croissant — quelles que soient ses
trois constantes, les frais ne descendent jamais quand le montant monte, et
un balayage de 400 barèmes sur 379 montants chacun le vérifie. Une grille à
taux global, elle, peut descendre. Donc aucun `Scale` ne la reproduit.

**Deux formes de calcul, c'est le seuil.** L'interface `Calc` reprend son
sens, avec une méthode et deux implémentations qui en ont toutes les deux
besoin.

Sauf que la mesure a donné autre chose en route, et c'est le sujet de la
section suivante.

### Le test qui a changé la conclusion

Pour admettre la grille dégressive, j'ai écrit un constructeur qui refuse une
grille **non monotone** — une grille où il existe un montant tel que payer un
franc de plus coûte **moins** de frais. Une tarification non monotone est
arbitrable : le client découpe ou arrondit, et la plateforme perd la
différence.

```go
// NewBrackets builds a sliding grid, or refuses to
// build it.
//
// It refuses two things. First a grid that does not start at zero: the
// amounts below the first tier would have no rate. Then, and it is
// the refusal that matters: a NON-MONOTONIC grid, that is a grid where
// there is an amount such that paying one franc more costs less in
// fee computation. A global rate per tier almost always produces this step.
//
// So this constructor will refuse the grid as it was negotiated. It is
// reason, and the test that shows it gives the figure to take to the meeting.
func NewBrackets(tiers []Bracket) (Brackets, error) {
    if len(tiers) == 0 {
        return Brackets{}, fmt.Errorf("%w: empty list", ErrMissingTier)
    }
    cp := make([]Bracket, len(tiers))
    copy(cp, tiers)
    slices.SortFunc(cp, func(a, b Bracket) int {
        return cmp.Compare(a.Since.Value(), b.Since.Value())
    })
    if !cp[0].Since.IsZero() {
        return Brackets{}, fmt.Errorf("%w: the lowest starts at %s",
            ErrMissingTier, cp[0].Since)
    }
    t := Brackets{tiers: cp}
    for _, p := range cp[1:] {
        if p.Since.IsZero() {
            continue
        }
        right, err := amount.FCFA(p.Since.Value() - 1)
        if err != nil {
            return Brackets{}, err
        }
        before, err := t.Fees(right)
        if err != nil {
            return Brackets{}, err
        }
        after, err := t.Fees(p.Since)
        if err != nil {
            return Brackets{}, err
        }
        if before.Exceeds(after) {
            missing, _ := before.Minus(after)
            return Brackets{}, fmt.Errorf(
                "%w: at %s the fees go from %s to %s, that is %s less for one franc more",
                ErrGridNotMonotone, p.Since, before, after, missing)
        }
    }
    return t, nil
}
```

Le constructeur refuse la grille telle que l'avenant l'écrit, et il donne le
chiffre :

```
frais : grille non monotone : a 500000 FCFA les frais passent de 12499 FCFA
a 7500 FCFA, soit 4999 FCFA de moins pour un franc de plus
```

À ce moment-là j'ai écrit, dans la documentation du type, que la **forme
entière** était non monotone : qu'aucune grille à taux global décroissant ne
pouvait tenir, pour n'importe quelles valeurs. C'était faux, et un balayage
l'a dit :

```
plancher      1000 FCFA :  220 refusees,  59 acceptees
plancher     50000 FCFA :  279 refusees,   0 acceptees
plancher    500000 FCFA :  279 refusees,   0 acceptees
plancher   2000000 FCFA :  279 refusees,   0 acceptees
```

Cinquante-neuf grilles passent, toutes à un plancher de 1 000 FCFA avec une
baisse de 1 pour mille. La raison est la **troncature** : les frais sont des
entiers, et quand la marche théorique vaut moins d'un franc, elle disparaît à
l'arrondi. `(999 × 26) / 1000 = 25` et `(1000 × 25) / 1000 = 25`.

Le test n'affirme donc plus un théorème. Il vérifie que la décision du
constructeur coïncide **exactement** avec un critère arithmétique calculé à
part, sur tout le balayage :

```
(D-1) × haut / 1000  >  D × bas / 1000      (divisions entieres)
```

Deux choses à emporter de cet épisode, et la deuxième vaut plus que la
première.

> **Le domaine d'un balayage décide de sa conclusion.** Je ne sais que la
> troncature absorbe la marche parce que mon balayage incluait un plancher de
> 1 000 FCFA. Un balayage parti à 50 000 aurait conclu au théorème, et le
> théorème aurait été publié.

> Et la conclusion métier n'est pas « cette grille est mal réglée ». C'est :
> la forme à taux global ne tient que là où les frais valent quelques francs.
> **On ne corrige pas un réglage, on change de forme.**

La forme qui tient est marginale, comme un barème d'impôt sur le revenu : le
taux ne s'applique qu'à la portion du montant tombant dans sa tranche.

```go
// MarginalBrackets is the sliding grid that does hold.
// It exists because the Brackets constructor refuses the grid
// as negotiated. The sweep in fees_test.go shows how far this refusal goes: with a
// floor of 1 000 FCFA, 59 decreasing grids out of 279 pass, because
// the theoretical step is worth less than one franc and disappears at truncation
// started. From 50 000 FCFA, none passes: 279 out of 279 refused, for
// every pair of rates tried.
//
// So the conclusion is not "this grid is badly tuned". It is: the
// global-rate shape holds only where the fees are worth a few francs.
// We do not fix a setting, we change the shape.
//
// Here the rate applies only to the PORTION of the amount falling in its
// bracket, like an income tax scale. Monotony is then a
// consequence of the shape and not a check: each term of the sum
// grows with the amount, so the sum grows.
type MarginalBrackets struct {
    tiers []Bracket
}

// NewMarginalBrackets builds a marginal grid. It no longer has
// need to check monotony: the shape guarantees it. It checks what
// remains checkable: coverage from zero, no duplicates, and the
// positivity of the rates.
func NewMarginalBrackets(tiers []Bracket) (MarginalBrackets, error) {
    if len(tiers) == 0 {
        return MarginalBrackets{}, fmt.Errorf("%w: empty list", ErrMissingTier)
    }
    cp := slices.Clone(tiers)
    slices.SortFunc(cp, func(a, b Bracket) int {
        return cmp.Compare(a.Since.Value(), b.Since.Value())
    })
    if !cp[0].Since.IsZero() {
        return MarginalBrackets{}, fmt.Errorf("%w: the lowest starts at %s",
            ErrMissingTier, cp[0].Since)
    }
    for i, p := range cp {
        if p.PerMille < 0 {
            return MarginalBrackets{}, fmt.Errorf("%w: rate %d per mille",
                ErrNegativeRate, p.PerMille)
        }
        if i > 0 && cp[i-1].Since == p.Since {
            return MarginalBrackets{}, fmt.Errorf("%w: two tiers at %s",
                ErrDuplicateTier, p.Since)
        }
    }
    return MarginalBrackets{tiers: cp}, nil
}

func (t MarginalBrackets) Tiers() []Bracket { return slices.Clone(t.tiers) }

func (t MarginalBrackets) Fees(m amount.Amount) (amount.Amount, error) {
    total := amount.Zero
    for i, p := range t.tiers {
        if p.Since.Exceeds(m) {
            break
        }
        // The top of the bracket is the floor of the next tier, or the
        // amount itself for the last bracket reached.
        top := m
        if i+1 < len(t.tiers) && !t.tiers[i+1].Since.Exceeds(m) {
            top = t.tiers[i+1].Since
        }
        portion, err := top.Minus(p.Since)
        if err != nil {
            return amount.Zero, err
        }
        share, err := portion.PerMille(p.PerMille)
        if err != nil {
            return amount.Zero, err
        }
        total, err = total.Plus(share)
        if err != nil {
            return amount.Zero, err
        }
    }
    return total, nil
}
```

Et la monotonie n'est plus vérifiée par le constructeur, parce qu'elle
**découle de la forme** : chaque terme de la somme croît avec le montant, donc
la somme croît. Un test le confirme sur cinq millions de valeurs entières au
lieu de l'affirmer.

> Le meilleur garde-fou est celui qu'on peut **supprimer** parce que la forme
> le rend inutile. La leçon 2.1 l'avait dit du plafond qui devient une
> fonction du niveau ; c'est le même mouvement.

Au bout du compte, l'interface `Calc` existe, elle a **une** méthode, et
elle a **deux** implémentations qui diffèrent par la forme du calcul. C'est le
plus petit polymorphisme qui se paie, et il a fallu tout ce chemin pour
savoir qu'il était justifié.

## 5. Ce que ça donne, et ce que ça coûte

### Les cinq défauts, repris un par un

| Défaut du modèle d'origine | Ce qui l'a corrigé | Vérifié par |
|---|---|---|
| la variante importe le monde | les opérations chez leurs appelants | `go list` : 3 imports contre 7 |
| aucun test ne s'écrit | plus d'appel réseau dans une variante | les tests existent, et ils n'ont pas de double |
| deux sens pour une valeur | `ErrNotApplicable` au lieu de `0` | `TestUnBonDAchatNeRendPasZeroMaisUneErreur` |
| l'ensemble est ouvert | méthode non exportée | 4 programmes qui ne compilent pas |
| rien n'est une valeur | champs privés, pas de client HTTP | une variante est une clé de map |

### Le coût, compté honnêtement

Ce n'est pas gratuit, et il faut pouvoir le dire en réunion.

| Ce que ça coûte | Combien |
|---|---|
| le paquet `exhaustivite` | 267 lignes de test, dont 90 de `go/ast` |
| le paquet `guard` | 192 lignes, dont un sous-processus `go build` par cas |
| le paquet `operation` | 38 lignes dont le seul rôle est de porter deux `struct` |
| ajouter une variante | 4 fichiers au lieu d'1 |
| le `default` de chaque `switch` | une erreur à écrire, un cas à tester, dans chaque appelant |

Et le coût qu'on ne compte jamais : **il faut connaître l'astuce**. La méthode
non exportée pour sceller, l'assertion de conformité, le `case nil`, le test
qui lit la source — rien de tout ça n'est dans un tutoriel Go. Un développeur
qui arrive sur ce code et qui n'a pas lu cette leçon va supprimer le `_
[0]func()` de la 2.1, retirer le `moyen()` « qui ne sert à rien », et enlever
les quatre assertions de conformité « qui ne font rien ».

> Une garantie que le prochain développeur ne comprend pas est une garantie
> qui a une date d'expiration. Les quatre tests de ce module existent pour que
> cette date soit **le jour où il essaie**, et pas six mois plus tard en
> production.

### Quand ne rien faire est la bonne réponse

Trois cas où tout ce chapitre ne s'applique pas :

1. **Deux variantes, et le métier n'en prévoit pas de troisième.** Un `if`.
   Pas un `switch`, pas une interface, un `if`. Et si la troisième arrive, tu
   la verras arriver.
2. **Les variantes ne diffèrent que par une constante.** C'est un tableau, et
   la section 4 l'a démontré au lieu de l'affirmer.
3. **Le programme a six mois à vivre.** Le coût des quatre tests ne sera
   jamais amorti, et l'écrire est une faute professionnelle de l'autre sens.

## 6. Les trois erreurs qui restent, après tout ça

### L'interface déclarée par le mauvais côté

Le réflexe hérité de Java : un paquet `gateways` qui déclare
`gateways.Gateway`, et tous les appelants qui l'importent. Ça compile,
ça marche, et ça produit l'interface la plus grosse possible — l'union des
besoins de tous les appelants — donc le double de test le plus gros possible.

Le signe : **ton interface a plus de méthodes que le plus exigeant de ses
appelants n'en utilise.** Compte-les.

### Le `switch` déguisé en polymorphisme

```go
// Handle is the switch disguised as polymorphism.
// Three methods written as one method with a string parameter. The
// compiler checks nothing any more: neither the number of arguments of each
// action, nor the type of its return, nor whether the action exists. We moved
// a switch from COMPILE time to RUN time, which is the opposite of what
// we wanted.
func (c Card) Handle(action string) (string, error) {
    switch action {
    case "authorize":
        return "AUT-" + c.Network, nil
    case "capture":
        return "CAP-" + c.Network, nil
    case "refund":
        return "REM-" + c.Network, nil
    default:
        return "", fmt.Errorf("%w: %q", ErrUnknownAction, action)
    }
}
```

Trois méthodes écrites comme une méthode avec un paramètre `string`. Le
compilateur ne vérifie plus rien : ni le nombre d'arguments, ni le type du
retour, ni l'existence de l'action. On a déplacé un `switch` **de la
compilation vers l'exécution**, ce qui est exactement l'inverse de ce qu'on
voulait.

### Le double qui prouve que l'interface est trop grosse

Si écrire le double de test d'une interface demande d'implémenter des méthodes
que le test n'appellera jamais, l'interface n'est pas à la taille de son
appelant. C'est mesurable, et la mesure est : **combien de méthodes de ce
double rendent une valeur que personne ne lit ?** Au-delà de zéro, découpe.

C'est la leçon 2.5 qui en fait une règle. Ici c'est juste un symptôme, et il
est chiffrable.

## 7. Le lien avec la production

### L'incident de la passerelle dégradée

Post-mortem, reconstitué dans le module et mesuré sur dix mille demandes.

Un samedi, la passerelle MTN se dégrade : quatre demandes sur dix partent en
timeout. Le tableau de bord a **un** indicateur, le taux d'échec global, et
**un** seuil d'alerte, fixé à 100 pour mille — le double du taux observé en
régime normal, arrondi. Personne n'a eu tort de le choisir ainsi.

Voilà les deux indicateurs, sur le même trafic :

```
AVANT   : taux d'echec global 42 pour mille (seuil 100)
          ORANGE-MONEY     pannes  11, refus   0 (pour mille)
          MTN-MOMO         pannes  12, refus   0 (pour mille)
          MONETIQUE-CEMAC  pannes   9, refus  78 (pour mille)
PENDANT : taux d'echec global 75 pour mille (seuil 100)
          ORANGE-MONEY     pannes  11, refus   0 (pour mille)
          MTN-MOMO         pannes 410, refus   0 (pour mille)
          MONETIQUE-CEMAC  pannes   9, refus  78 (pour mille)
```

Le taux de panne de MTN passe de 12 à **410 pour mille** — il multiplie par
34. Le taux global passe de 42 à 75, et **ne franchit pas le seuil**. Aucune
alerte. L'incident a été découvert par les appels au service client.

Deux raisons, et elles sont différentes.

**La première est la dilution.** MTN traite 8 % du trafic. Une panne à 40 %
sur 8 % du trafic fait 3,2 points sur le global. Rien ne la distingue du
bruit.

**La seconde est le plancher de bruit, et c'est la plus intéressante.** La
monétique **refuse** 78 pour mille des demandes — ce sont les paiements
au-dessus du plafond unitaire. Ce n'est pas une panne, c'est une **réponse
métier**, et c'est parfaitement normal. Mais l'indicateur global les compte
comme des échecs. Le régime normal est donc à 42 pour mille, et c'est ce 42
qui a fixé le seuil à 100.

> Un indicateur qui mélange les **refus** et les **pannes** a un plancher de
> bruit, et le plancher de bruit est exactement ce qui empêche de voir la
> panne. Le seuil n'était pas trop haut : il était calculé sur un indicateur
> qui ne mesurait pas ce qu'on croyait.

C'est la même leçon que l'incident de la 1.6, retrouvée par un autre chemin :
un indicateur candidat qui ne se déclenche pas est une information, et il faut
la mesurer avant de le mettre au tableau de bord.

### Et le rapport avec le polymorphisme

Direct, et c'est le point de cette section.

Le routeur choisit parmi quatre implémentations d'une interface. Celui qui
écrit la ligne de journal après l'autorisation connaît la référence et
l'erreur — **il ne connaît pas l'implémentation qui a été choisie**. C'est
précisément ce que le polymorphisme a rendu transparent, et c'est précisément
l'information qui manque à trois heures du matin.

> Le polymorphisme efface l'information qui te manquera pendant l'incident :
> **laquelle**. Toute sélection dynamique doit être journalisée **au point de
> sélection**, pas au point d'usage.

Et « au point de sélection » veut dire **avant** l'appel, pas après : une
passerelle qui part en timeout de trente secondes puis un processus tué, et
la seule ligne qui aurait permis d'attribuer la panne n'a jamais été écrite.

### Le test d'ordre qui ne testait pas l'ordre

J'avais écrit ce test, et il était vert :

```
attendu := []string{"selection:QUI-TOMBE:tout", "resultat:echec"}
```

La campagne de modifications l'a mis à nu. En déplaçant l'appel à `Selection`
**après** `p.Authorize(d)`, le test reste vert : la suite du journal est
toujours *sélection puis résultat*, parce que `Result` vient après
`Selection` dans les deux cas. Le test a survécu à la modification qu'il était
censé attraper.

```go
// failingGateway always fails, records that it was called, and,
// that is the point: writes its own call INTO the ordered journal sequence.
//
// The first version of this double wrote nothing to the journal, and the
// order test compared only "selection" then "result". A
// change of the campaign laid it bare: by moving the call to
// Selection AFTER p.Authorize(r), the journal's sequence stays the same:
// selection then result, because Result comes after Selection in
// both cases. The test survived the change it was supposed to
// catch.
//
//    An order test must be observed from the INTERMEDIATE point, not
//    from the end of the chain. The journal sees A then B in both
//    way round; only the gateway can say whether A happened before we
//    calls it.
type failingGateway struct {
    name    string
    called  *bool
    journal *orderedJournal
}

func (p failingGateway) Name() string { return p.name }

func (p failingGateway) Authorize(d operation.Request) (operation.Authorization, error) {
    *p.called = true
    if p.journal != nil {
        p.journal.rest = append(p.journal.rest, "call:"+p.name)
    }
    return operation.Authorization{}, errors.New("timeout")
}

var _ routing.Gateway = failingGateway{}
```

> **Un test d'ordre doit s'observer depuis le point intermédiaire**, pas
> depuis le bout de la chaîne. Le journal voit A puis B dans les deux sens ;
> seule la passerelle peut dire si A a eu lieu avant qu'on l'appelle.

### Le relevé de la campagne

Quatorze modifications, sur un module à huit paquets de test.

```
modification                                                       | tests qui tombent
-------------------------------------------------------------------+------------------
 1. ParseReseau n'uniformise plus la casse                         | 1
 2. NewCard ne verifie plus le network                        | 1
 3. Variants() oublie le bon d'achat                              | 2
 4. Scale n'applique plus le plafond                              | 2
 5. NewBrackets ne verifie plus la monotonie                 | 2
 6. le calcul marginal ignore le haut de tranche                   | 1
 7. Tiers() rend la tranche interne au lieu d'une copie          | 1
 8. la selection est journalisee APRES l'appel                     | 1
 9. Choose rend la DERNIERE regle qui convient                    | 1
10. Entry perd son cas nil                                      | 1
11. Entry perd le cas du virement                               | 4
12. un bon d'achat rend un delai de zero au lieu d'une erreur      | 2
13. remboursement accepte une somme nulle                          | 1
14. le Mastercard retombe sur le compte carte generique            | 4

14/14 modifications detectees
```

Trois remarques de méthode, parce que le relevé final cache le chemin.

**La modification 8 a d'abord survécu.** C'est elle qui a révélé le test
d'ordre défectueux. Une modification qui survit ne réclame pas toujours un
test de plus : ici elle réclamait un **point d'observation** différent.

**Les modifications 6 et 14 n'ont d'abord pas compilé** — une variable
devenait inutilisée. Une modification qui ne compile pas n'est ni détectée ni
survivante : elle n'a pas été jouée. Les rejouer sous une forme qui compile a
pris trois minutes, et les deux tombent.

**La modification 10 ne fait tomber qu'un test, et ce n'est pas celui qu'on
croit.** Retirer le `case nil` de `Entry` ne fait pas tomber le test qui
passe `nil` — il passe toujours, parce que le `default` l'attrape. Il fait
tomber le test d'exhaustivité, qui exige le cas `nil` dans chaque `switch`.
Autrement dit : le garde-fou qui tient, c'est celui qui lit la source.

## 8. Ce qu'il faut retenir

1. **Polymorphisme** : un même nom désigne plusieurs implémentations, et le
   choix se fait ailleurs. Tout tient dans ce « ailleurs » — **qui choisit, et
   quand ?**
2. **Quatre formes, trois en Go.** La surcharge n'existe pas, et le
   compilateur le dit : `Ajouter redeclared in this block`. Méfie-toi de tout
   conseil sur le polymorphisme écrit pour un langage qui l'a.
3. **Paramétrique et sous-typage ne répondent pas à la même question.** Le
   générique : l'algorithme est le même, le type change, tout est décidé à la
   compilation. L'interface : le type est le même, le comportement change,
   rien n'est décidé avant l'exécution.
4. **Une interface à une méthode et un type fonction sont le même
   polymorphisme.** L'interface se mérite quand l'implémentation a un état.
5. **Le coût du dispatch dynamique est de 1,2 nanoseconde par appel** sur un
   corps qui ne fait rien, soit 2 % sur un corps réel. L'argument de
   performance contre les interfaces est du bruit.
6. **Un banc d'essai se vérifie comme un test.** Le mien disait « c'est
   pareil » parce que le compilateur dévirtualisait, pas parce que le dispatch
   est gratuit. Un chiffre qui confirme ce que tu espérais est le plus
   dangereux de tous.
7. **Le polymorphisme n'est pas un outil, c'est un choix d'axe d'extension.**
   La question est : qui ajoute le cas suivant, et de quel côté ?
8. **Le test décisif se répond avec `git log`**, pas avec une intuition : sur
   douze mois, qu'est-ce qui est arrivé le plus — des variantes ou des
   opérations ?
9. **Les deux formes coexistent dans un même programme**, dans deux sens
   opposés, et ce n'est pas une incohérence.
10. **Une méthode appartient à la variante si et seulement si elle se répond
   avec les champs de la variante.** Sinon elle est chez son appelant.
11. **Chaque méthode d'une interface est un impôt prélevé sur chaque
   implémentation** : elle doit désormais connaître ce qu'il faut pour
   répondre. Le polymorphisme déplace la connaissance, il ne la supprime pas.
12. **Une méthode non exportée scelle un ensemble**, gratuitement. Et les deux
   messages du compilateur — `missing method` contre `unexported method` —
   sont la preuve du mécanisme.
13. **Clôture n'est pas exhaustivité.** Go donne la première gratuitement et
   ne donne pas la seconde. Elle s'achète en deux tests : par la répétition,
   et par la lecture de la source — et c'est le second qui garde le premier.
14. **`nil` est la variante que rien ne déclare.** Le scellement ferme
   l'ensemble des implémentations, pas celui des valeurs.
15. **En Go, le compilateur n'aide sur aucun des deux axes par défaut** : zéro
   erreur sans assertion de conformité, quatre avec. Chaque garantie se
   déclare.
16. **Une interface se déclare chez son appelant**, et sa signature ne doit
    nommer que des types partagés — sinon la dépendance revient par les
    arguments.
17. **Trois appelants, trois tailles d'interface**, pour une même
    implémentation. Et la taille du double de test est la mesure.
18. **Quand deux implémentations ne diffèrent que par des constantes, le
    polymorphisme est un tableau**, et un test d'équivalence le démontre.
19. **Deux formes de calcul est le seuil** à partir duquel le polymorphisme
    se paie. Pas deux cas, deux formes.
20. **Le domaine d'un balayage décide de sa conclusion.** Un balayage trop
    étroit produit un théorème faux, et un théorème faux se publie.
21. **Le polymorphisme efface « laquelle ».** Journalise la sélection au
    point de sélection, et avant l'appel.
22. **Un indicateur qui mélange refus et pannes a un plancher de bruit**, et
    ce plancher est ce qui empêche de voir la panne.
23. **Un test d'ordre s'observe depuis le point intermédiaire**, jamais depuis
    le bout de la chaîne.

## 9. Approfondissement

### Une interface à une méthode est une fonction

Dans ce module, `Regle.Fits` est un `func(operation.Request) bool` et non
une interface à une méthode. Les deux sont **le même polymorphisme** : en Go,
un type fonction et une interface à une méthode sont interchangeables, et la
bibliothèque standard le dit à voix haute avec `http.HandlerFunc`, qui est un
type fonction portant la méthode de l'interface.

Le choix entre les deux :

| Prends une **fonction** quand | Prends une **interface** quand |
|---|---|
| l'implémentation n'a pas d'état | l'implémentation a besoin d'un état (une connexion, un cache) |
| il n'y a rien à nommer | tu veux nommer l'ensemble, le documenter, l'assertionner |
| une seule opération, pour toujours | une deuxième opération est plausible |

Et le piège : une fonction ne peut pas porter d'assertion de conformité. Si tu
veux que le compilateur vérifie quelque chose, il faut un type.

### Pourquoi Go n'a pas de types sommes, et ce que ça coûte

Un type somme — `enum` de Rust, `sealed` de Kotlin, union discriminée de
TypeScript — déclare l'ensemble fermé **et** fait vérifier l'exhaustivité par
le compilateur. Go n'en a pas, et ce n'est pas un oubli : la proposition
existe, elle est discutée depuis dix ans, et elle n'est pas passée.

Ce que ça coûte, exactement, est ce que la section 4 a mesuré : la clôture est
gratuite (une méthode non exportée), l'exhaustivité coûte 267 lignes de test
dont 90 de `go/ast`. Dans un langage à types sommes, ces 267 lignes sont une
ligne — l'absence de branche `default`.

Ce n'est pas rien, et il est honnête de le reconnaître plutôt que de prétendre
que l'idiome Go est équivalent. Il ne l'est pas. Il est suffisant, et il se
paie.

Une solution intermédiaire existe et mérite d'être connue : des analyseurs
externes (`go-check-sumtype`, `exhaustive` de `golangci-lint`) font cette
vérification dans l'outillage plutôt que dans un test. L'avantage est qu'ils
sont génériques ; l'inconvénient est qu'ils vivent dans la configuration de
l'intégration continue, donc **hors du dépôt du code qu'ils gardent**, et
qu'un développeur pressé désactive une règle de linter plus facilement qu'il
ne supprime un test. À toi de choisir où tu veux que la garantie habite.

### Le signe qu'on s'est trompé de forme

La section 1 a posé la différence entre le sous-typage et le paramétrique. Le
signe qu'on a pris le mauvais des deux, dans un sens comme dans l'autre :

- **un paramètre de type contraint par une interface à méthodes, et une seule
  implémentation** : l'interface seule suffit, le générique n'ajoute qu'une
  signature plus longue ;
- **une interface dont toutes les implémentations ont le même corps à un type
  près** : c'est un générique qui s'ignore, et tu l'as écrit N fois.

Le second cas se détecte exactement comme le polymorphisme qui ne décide
rien, et par le même outil : un test d'équivalence.

### La valeur zéro d'une interface, et pourquoi elle n'est pas `nil`

Un piège Go classique, et il appartient à cette leçon puisqu'il concerne les
valeurs d'interface.

```go
// InterfaceFromNilPointer returns an interface built from a
// nil pointer, and that is the whole trap: it is NOT nil.
//
// An interface value is a pair (type, value). It is nil only if
// BOTH are nil. Assigning a nil pointer to an interface gives a
// non-nil interface holding a nil pointer, and the next method call
// panics.
func InterfaceFromNilPointer() Authorizer {
    var p *Gateway = nil
    var i Authorizer = p
    return i
}
```

Une valeur d'interface est une paire *(type, valeur)*. Elle est `nil`
seulement si **les deux** sont nuls. Assigner un pointeur nul à une interface
donne une interface non nulle qui contient un pointeur nul — et le prochain
appel de méthode panique.

La conséquence pratique, dans le vocabulaire de cette leçon : **ne rends
jamais un type concret là où ta signature promet une interface.** Rends
l'interface, et rends `nil` littéralement. C'est aussi pourquoi les variantes
de `means` ont des récepteurs par valeur et non par pointeur : il n'y a pas de
pointeur nul possible.

### Ce que cette leçon n'a pas traité

- **L'héritage**, et pourquoi Go l'a remplacé par l'incorporation. C'est la
  leçon 2.3, et le polymorphisme y revient par une autre porte : celle de la
  substituabilité.
- **La taille des interfaces comme principe**, au lieu d'une observation.
  C'est l'ISP, leçon 2.5.
- **L'inversion de dépendance.** On l'a pratiquée sans la nommer en déclarant
  l'interface chez l'appelant ; la 2.5 en fait une règle et dit où elle
  s'arrête.
- **Le polymorphisme à l'exécution par registre** — une `map[string]Gateway`
  peuplée au démarrage. Il a ses propres modes de panne, et ils appartiennent
  au niveau 6.

## 10. Le réflexe à installer

Devant un ensemble de variantes, trois questions, dans cet ordre :

> 1. **Les variantes diffèrent-elles par leur forme de calcul, ou seulement
>    par des constantes ?**
>    Par des constantes → c'est un tableau. Écris le test d'équivalence, il
>    prend dix minutes et il tranche.
>    Par la forme → continue.
> 2. **Sur les douze derniers mois, qu'est-ce qui est arrivé le plus souvent :
>    une variante de plus, ou une question de plus ?**
>    Des variantes → interface, déclarée chez l'appelant, signature en
>    vocabulaire partagé, une assertion de conformité par implémentation.
>    Des questions → ensemble scellé par une méthode non exportée, `switch`
>    chez les appelants, et les deux tests d'exhaustivité.
>    Les deux autant → tu as deux ensembles, pas un. Sépare-les.
> 3. **Qu'est-ce que le compilateur vérifie, et qu'est-ce que j'ai déclaré
>    pour qu'il le vérifie ?**
>    Rien n'est vérifié par défaut. Si tu n'as écrit ni assertion de
>    conformité ni test qui lit la source, ta garantie est un commentaire.

Et devant une interface qui existe déjà, un seul geste, qui prend une minute :

> **Compte les méthodes de l'interface, puis compte celles que son appelant le
> plus exigeant utilise réellement.** Si les deux nombres diffèrent,
> l'interface n'appartient pas à son appelant — elle appartient à son
> implémentation, et elle lui ressemble. Et pour chaque méthode de l'écart,
> demande : *celle-là, se répond-elle avec les champs de la variante ?*
