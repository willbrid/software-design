# Leçon 2.3 — Composition contre héritage, et pourquoi Go a tranché

Tu as sûrement déjà lu la formule : *« préférer la composition à
l'héritage »*. Elle a quarante ans, elle est dans le livre du Gang of Four,
et elle est répétée si souvent qu'elle ne veut plus rien dire.

Cette leçon ne va pas la répéter. Elle va faire deux choses : poser ce que
l'héritage **fait**, mécanisme par mécanisme, et montrer que Go n'en a gardé
qu'une partie — puis mesurer ce qui arrive quand on écrit du Go en croyant
avoir le reste.

> Go n'a pas d'héritage. Il a l'**incorporation**, qui ressemble à l'héritage
> jusqu'au moment où ça compte, et c'est précisément à ce moment-là que le
> programme devient faux **sans que rien ne le signale**.

On commence par les définitions et par quatre faits mesurés, avec du code qui
compile.

## 1. L'héritage et l'incorporation, définis

### Ce que l'héritage fait, et ce sont trois choses

Quand un langage dit *« `Derive` hérite de `Base` »*, il accorde **trois
choses à la fois**, et presque personne ne les sépare :

| | Ce que l'héritage accorde | En une phrase |
|---|---|---|
| **1** | la **réutilisation de code** | je veux les méthodes de `Base` sans les réécrire |
| **2** | le **sous-typage** | je veux être accepté partout où un `Base` est accepté |
| **3** | la **spécialisation ouverte** | je veux remplacer une partie du comportement de `Base`, **y compris quand c'est `Base` qui l'appelle** |

Le troisième est le seul qui soit vraiment propre à l'héritage, et c'est celui
qui porte un nom : le **dispatch dynamique**, ou dispatch virtuel. Quand une
méthode de `Base` appelle `this.quelqueChose()`, l'appel est résolu **à
l'exécution**, sur le type réel de l'objet. C'est ce qui fait marcher le
patron de la méthode-modèle, et c'est ce qui fait que `super` existe.

> La question qui décide n'est pas *« héritage ou composition ? »*. C'est :
> **de laquelle des trois ai-je besoin ?** Parce qu'un langage à héritage te
> donne les trois même quand tu n'en voulais qu'une, et les deux autres sont
> des engagements que tu n'as pas pris exprès.

### Ce que Go accorde, et séparément

| Je veux… | En Go |
|---|---|
| la **réutilisation** | l'**incorporation** : un champ anonyme, dont les méthodes sont promues |
| le **sous-typage** | une **interface**, satisfaite structurellement, sans déclaration |
| la **spécialisation ouverte** | **rien.** Elle n'existe pas, et c'est le sujet de cette leçon |

Trois mécanismes séparés pour trois besoins séparés, et le troisième manque.
Ce n'est pas un oubli : c'est une décision des auteurs du langage, et la
section 9 dit ce qu'elle a coûté et rapporté.

### FAIT 1 — la promotion, et la preuve que c'est un champ

```go
// --- FAIT 1 : la promotion de methodes ---

// Horodatage est un type incorporable.
type Horodatage struct {
    Annee int
    Mois  int
}

func (h Horodatage) Periode() string {
    return pad4(h.Annee) + "-" + pad2(h.Mois)
}

// Evenement incorpore Horodatage. Il n'y a pas d'heritage ici : Horodatage est
// un CHAMP, dont le nom est le nom de son type, et dont les methodes sont
// PROMUES au niveau d'Evenement.
//
// La preuve que c'est un champ et non un parent : on peut l'atteindre par son
// nom, e.Horodatage, et on peut le remplacer entier.
type Evenement struct {
    Horodatage
    Type string
}
```

```go
package mecanique_test

import (
    "errors"
    "testing"

    "exemple/banque/mecanique"
)

// TestLaPromotionDonneAccesAuxMethodesEtAuChamp est le FAIT 1.
//
// Elle donne les deux faces du mecanisme : la methode est appelable au niveau
// du type englobant, ET le type incorpore reste atteignable par son nom. La
// seconde face est la preuve que c'est un champ et non un parent.
func TestLaPromotionDonneAccesAuxMethodesEtAuChamp(t *testing.T) {
    e := mecanique.Evenement{
        Horodatage: mecanique.Horodatage{Annee: 2026, Mois: 3},
        Type:       "PAIEMENT",
    }
    if got := e.Periode(); got != "2026-03" {
        t.Errorf("methode promue : e.Periode() = %q", got)
    }
    if got := e.Horodatage.Periode(); got != "2026-03" {
        t.Errorf("acces par le nom du champ : e.Horodatage.Periode() = %q", got)
    }
    // Et le champ se remplace en entier, ce qu'aucun heritage ne permet.
    e.Horodatage = mecanique.Horodatage{Annee: 2027, Mois: 12}
    if got := e.Periode(); got != "2027-12" {
        t.Errorf("apres remplacement du champ : %q", got)
    }
}
```

Deux faces, et la seconde est la plus importante.

`e.Periode()` marche : la méthode est **promue** au niveau du type englobant,
comme si `Evenement` l'avait déclarée. C'est la réutilisation, et c'est
gratuit.

Mais `e.Horodatage` marche aussi. Le type incorporé est **atteignable par son
nom**, et il se **remplace en entier** : `e.Horodatage = ...`. Aucun héritage
ne permet ça, parce qu'un parent n'est pas un champ.

> L'incorporation n'est pas une relation entre deux types, c'est un **champ
> dont le nom est le nom de son type**. Tout le reste en découle.

### FAIT 2 — il n'y a pas de dispatch virtuel

C'est le fait central de la leçon. Lis-le lentement.

```go
// --- FAIT 2 : l'absence de dispatch virtuel ---
//
// C'est le fait central de la lecon, et celui qui surprend tout le monde.

// Base a deux methodes, et l'une appelle l'autre.
type Base struct{}

func (Base) Nom() string { return "base" }

// Saluer appelle b.Nom(). Le recepteur b est de type Base, et Base ne sait
// rien de ce qui pourrait l'incorporer. L'appel est donc resolu A LA
// COMPILATION vers Base.Nom, definitivement.
func (b Base) Saluer() string { return "bonjour " + b.Nom() }

// Derive incorpore Base et declare sa propre methode Nom.
//
// En Java, en C# ou en Python, Derive{}.Saluer() rendrait « bonjour derive ».
// En Go il rend « bonjour base », et le test de ce paquet le mesure.
//
//    L'incorporation n'est pas de l'heritage : c'est de la DELEGATION avec
//    du sucre syntaxique. Il n'y a pas de table virtuelle, pas de super, et
//    pas de patron de methode-modele.
type Derive struct{ Base }

func (Derive) Nom() string { return "derive" }
```

```go
// TestIlNyAPasDeDispatchVirtuel est le FAIT 2, et c'est le fait central de
// toute la lecon.
//
// Base.Saluer appelle b.Nom() avec un recepteur de type Base. Derive declare
// sa propre methode Nom. En Java, en C#, en Python, Derive{}.Saluer() rendrait
// « bonjour derive ». En Go il rend « bonjour base ».
//
// Ce test n'est pas la pour verifier un comportement : il est la pour que ce
// fait ne puisse pas etre oublie, et pour qu'il tombe si une version de Go le
// changeait.
func TestIlNyAPasDeDispatchVirtuel(t *testing.T) {
    d := mecanique.Derive{}

    // La surcharge existe et elle marche, quand on l'appelle directement.
    if got := d.Nom(); got != "derive" {
        t.Fatalf("d.Nom() = %q, attendu « derive »", got)
    }

    // Mais la methode heritee ne la voit pas.
    if got := d.Saluer(); got != "bonjour base" {
        t.Fatalf("d.Saluer() = %q, attendu « bonjour base » — "+
            "si ce test echoue, Go a acquis le dispatch virtuel et la lecon 2.3 est a reecrire", got)
    }
    t.Logf("d.Nom() = %q mais d.Saluer() = %q", d.Nom(), d.Saluer())
}
```

```
d.Nom() = "derive" mais d.Saluer() = "bonjour base"
```

En Java, en C#, en Python, en Ruby, `d.Saluer()` rendrait **« bonjour
derive »**. En Go il rend **« bonjour base »**, et il le rendra toujours.

La raison est dans la signature : `func (b Base) Saluer()`. Le récepteur `b`
est de type `Base`. `Base` ne sait rien de ce qui pourrait l'incorporer, et
l'appel `b.Nom()` est résolu **à la compilation** vers `Base.Nom`,
définitivement.

> **L'incorporation est de la délégation avec du sucre syntaxique.** Il n'y a
> pas de table virtuelle, pas de `super`, et pas de patron de
> méthode-modèle. La surcharge existe — `d.Nom()` rend bien « derive » — mais
> **personne, à l'intérieur de `Base`, ne la verra jamais.**

### FAIT 3 — l'ambiguïté se déclare mais ne s'utilise pas

```go
// --- FAIT 3 : l'ambiguite se declare mais ne s'utilise pas ---

type Gauche struct{}
type Droite struct{}

func (Gauche) Etiquette() string { return "gauche" }
func (Droite) Etiquette() string { return "droite" }

// Losange incorpore les deux. Ce type COMPILE : Go accepte la declaration.
//
// C'est l'appel losange.Etiquette() qui ne compile pas — « ambiguous
// selector » — et le test de non-compilation du paquet garde le montre.
// Consequence pratique : une bibliotheque qui AJOUTE une methode a un type
// que tu incorpores peut casser ton code a un endroit que tu n'as pas ecrit.
type Losange struct {
    Gauche
    Droite
}

// EtiquetteExplicite est la sortie : nommer le champ leve l'ambiguite.
func (l Losange) EtiquetteExplicite() string { return l.Gauche.Etiquette() }
```

Le type `Losange` **compile**. Go accepte qu'on incorpore deux types portant
la même méthode. C'est l'appel qui est refusé :

```
./main.go:15:26: ambiguous selector mecanique.Losange{}.Etiquette
```

Deux choses à en tirer.

La sortie est de **nommer le champ** : `l.Gauche.Etiquette()`. L'ambiguïté
n'est pas une erreur de conception en soi, c'est une information manquante.

Et la conséquence qui fait mal : **une bibliothèque qui ajoute une méthode à
un type que tu incorpores peut casser ton code à un endroit que tu n'as pas
écrit.** Tu n'as rien changé, ta version mineure est compatible, et un appel
devient ambigu.

### FAIT 4 — l'interface incorporée, et sa panique

```go
// --- FAIT 4 : l'incorporation d'une interface, et son mode de panne ---

// Formateur met en forme une chaine.
type Formateur interface {
    Formater(s string) string
}

// Majuscules est une implementation.
type Majuscules struct{}

func (Majuscules) Formater(s string) string { return strings.ToUpper(s) }

// Enveloppe incorpore l'INTERFACE et non une implementation.
//
// C'est l'idiome du remplacement partiel : l'enveloppe delegue tout ce qu'elle
// ne surcharge pas. Et son mode de panne est brutal : si le champ est laisse
// nul, le premier appel delegue panique sur un pointeur nul. Rien ne
// l'empeche a la compilation, parce que la valeur zero d'une interface est
// une valeur valide du type.
type Enveloppe struct {
    Formateur
    Prefixe string
}

// NouvelleEnveloppe est le remede : un constructeur qui refuse le nil.
//
// Il ne rend pas le probleme non representable — Enveloppe{} reste
// declarable — mais il ferme le chemin que tout le monde emprunte.
func NouvelleEnveloppe(f Formateur, prefixe string) (Enveloppe, error) {
    if f == nil {
        return Enveloppe{}, ErrFormateurNul
    }
    return Enveloppe{Formateur: f, Prefixe: prefixe}, nil
}

// FormaterAvecPrefixe surcharge en appelant explicitement la delegation.
//
// Noter l'appel : e.Formateur.Formater(s), et non e.Formater(s). Le second
// serait une recursion infinie si la methode portait le meme nom — c'est le
// piege de l'enveloppe, et il n'est pas theorique.
func (e Enveloppe) FormaterAvecPrefixe(s string) string {
    return e.Prefixe + e.Formateur.Formater(s)
}
```

Incorporer une **interface** plutôt qu'une implémentation est l'idiome du
remplacement partiel : l'enveloppe délègue tout ce qu'elle ne surcharge pas.
Il est utile, et il a un mode de panne brutal :

```
panique attendue : runtime error: invalid memory address or nil pointer dereference
```

La valeur zéro d'une interface est `nil`, et `nil` est une valeur **valide**
du type. Rien n'empêche à la compilation de construire une `Enveloppe` sans
formateur ; le premier appel délégué panique.

Le remède est un constructeur qui refuse le `nil`. Il ne rend pas l'état non
représentable — `Enveloppe{}` reste déclarable — mais il **ferme le chemin que
tout le monde emprunte**, et c'est la différence entre un ⚫ et un garde-fou.

Et un piège dans le piège, qu'il faut avoir vu une fois : la surcharge écrit
`e.Formateur.Formater(s)` et non `e.Formater(s)`. Si la méthode portait le
même nom que celle de l'interface, la seconde forme serait une **récursion
infinie** — l'appel se résoudrait vers elle-même.

### Le vocabulaire, pour finir

| Le mot | Ce qu'il désigne en Go |
|---|---|
| **incorporation** (*embedding*) | un champ anonyme ; le mot « hérite » ne s'applique pas |
| **promotion** | le fait que les méthodes du champ anonyme deviennent appelables sur le type englobant |
| **délégation** | ce que la promotion fait réellement : un appel transféré à un champ |
| **dispatch statique** | l'appel est résolu à la compilation — c'est le cas de tous les appels à l'intérieur d'un type incorporé |
| **dispatch dynamique** | l'appel est résolu à l'exécution — en Go, **seulement** par une interface |

## 2. L'intuition

Une banque, à Douala, et une exigence banale : exporter un relevé de compte
dans trois formats. Texte lisible pour le client, CSV pour son tableur, XML
pour l'échange interbancaire.

Le squelette est le même pour les trois — un en-tête, les lignes, un pied — et
seule la mise en forme change. Dans n'importe quel langage à héritage, c'est
l'exercice du premier chapitre : une classe abstraite avec une méthode
`exporter()` qui appelle `entete()`, `ligne()` et `pied()`, puis trois
sous-classes qui surchargent les morceaux.

Un développeur qui arrive de Java écrit donc ceci, et il a raison de penser
que ça marche. Les quatre blocs sans étiquette `go` de cette leçon sont des
**esquisses** et non du code du module : tout ce qui porte l'étiquette est
extrait d'un paquet qui compile et dont les tests passent.

```
type Base struct{}
func (b Base) Exporter(r Releve) string  { ... b.entete(r) ... b.ligne(l) ... }
func (Base) ligne(l Ligne) string        { /* format texte */ }

type CSV struct{ Base }
func (CSV) ligne(l Ligne) string         { /* format CSV */ }
```

Ça compile. Les tests qu'il écrit — s'il appelle `CSV{}.ligne(...)`
directement — passent. Et le fichier qui part chez le client est au format
texte.

> Il n'y a pas d'erreur de compilation, pas de panique, pas de test rouge. Il
> y a un fichier CSV avec des espaces au lieu de points-virgules, et un client
> qui appellera dans trois semaines.

## 3. Le mécanisme

### Le modèle d'origine, et la mesure de son défaut

```go
// Package avant est la tentative qui echoue, et elle echoue en silence.
//
// L'exigence est banale : trois formats d'export d'un releve, un squelette
// commun — entete, lignes, pied — et un morceau qui change par format. Dans
// un langage a heritage on ecrit une classe abstraite avec une methode
// modele, on surcharge ligne() dans trois sous-classes, et c'est fini.
//
// Ce fichier fait exactement ca, avec l'incorporation. Il COMPILE. Et il
// produit le mauvais format pour les trois, parce que l'incorporation n'est
// pas de l'heritage.
package avant

import (
    "strconv"
    "strings"

    "exemple/banque/releve"
)
```

```go
// Base porte le squelette et les valeurs par defaut.
type Base struct{}

// entete, ligne et pied sont les trois morceaux. Non exportes, parce que
// seules les sous-structures du paquet sont censees les remplacer.
func (Base) entete(r releve.Releve) string { return "RELEVE " + r.Iban() + " " + r.Periode() }

func (Base) ligne(l releve.Ligne) string {
    return l.Jour().Format("2006-01-02") + " " + l.Libelle() + " " + l.Montant().String()
}

func (Base) pied(total string) string { return "SOLDE " + total }

// Exporter est la « methode modele ».
//
// Elle appelle b.entete, b.ligne et b.pied. Le recepteur b est de type Base,
// et Base ne sait rien de ce qui l'incorpore : les trois appels sont resolus
// A LA COMPILATION vers les methodes de Base.
//
// Aucune surcharge ne sera jamais appelee d'ici. Jamais.
func (b Base) Exporter(r releve.Releve) (string, error) {
    final, err := r.SoldeFinal()
    if err != nil {
        return "", err
    }
    var sb strings.Builder
    sb.WriteString(b.entete(r))
    sb.WriteString("\n")
    for _, l := range r.Lignes() {
        sb.WriteString(b.ligne(l))
        sb.WriteString("\n")
    }
    sb.WriteString(b.pied(final.String()))
    return sb.String(), nil
}
```

```go
// CSV « surcharge » ligne. La methode existe, elle est correcte, et elle n'est
// appelee par personne.
type CSV struct{ Base }

func (CSV) ligne(l releve.Ligne) string {
    return l.Jour().Format("2006-01-02") + ";" + l.Libelle() + ";" +
        strconv.FormatInt(l.Montant().Valeur(), 10)
}
```

La mesure :

```go
// TestLesTroisFormatsRendentLeMemeTexte est le test qui mesure le defaut.
//
// Les trois types declarent des methodes entete et ligne differentes. Les
// trois exports sont IDENTIQUES, et ils sont tous au format par defaut de
// Base.
//
// Ce n'est pas une erreur de compilation, ce n'est pas une panique, ce n'est
// pas un test rouge : c'est un fichier CSV qui part chez le client avec des
// espaces au lieu de points-virgules.
func TestLesTroisFormatsRendentLeMemeTexte(t *testing.T) {
    r := releveTemoin(t)

    base, err := (avant.Base{}).Exporter(r)
    if err != nil {
        t.Fatal(err)
    }
    csv, err := (avant.CSV{}).Exporter(r)
    if err != nil {
        t.Fatal(err)
    }
    xml, err := (avant.XML{}).Exporter(r)
    if err != nil {
        t.Fatal(err)
    }

    if csv != base {
        t.Error("l'export CSV differe du defaut : le dispatch virtuel est apparu")
    }
    if xml != base {
        t.Error("l'export XML differe du defaut : le dispatch virtuel est apparu")
    }
    // Et la preuve que les surcharges existent bien : appelees directement,
    // elles fonctionnent.
    if !strings.Contains(csvDirect(t, r), ";") {
        t.Error("CSV.ligne ne produit pas de point-virgule")
    }
    if strings.Contains(csv, ";") {
        t.Error("l'export CSV contient un point-virgule : la surcharge a ete appelee")
    }
    t.Logf("les trois exports font %d octets et sont identiques", len(base))
}
```

```
les trois exports font 132 octets et sont identiques
```

**Trois formats, trois types, trois jeux de méthodes, et un seul résultat.**
Les surcharges existent, elles sont correctes, et elles ne sont appelées par
personne.

### La demi-correction que tout le monde essaie ensuite

Quand on découvre le problème, le premier réflexe est de passer « soi-même »
au squelette :

```go
// --- La demi-correction que tout le monde essaie ensuite ---

// morceaux est l'interface des trois morceaux, extraite pour pouvoir passer
// « soi-meme » au squelette.
type morceaux interface {
    entete(releve.Releve) string
    ligne(releve.Ligne) string
    pied(string) string
}

// ExporterAvecSoi est la demi-correction : on passe explicitement l'objet
// dont on veut les morceaux.
//
// Elle MARCHE, et c'est le probleme : elle marche en recopiant a la main ce
// qu'une table virtuelle ferait toute seule, et chaque appelant doit se
// souvenir de se passer lui-meme. Oublier l'argument ne produit aucune erreur
// de compilation — il produit le format par defaut.
//
// Et surtout : si on passe deja l'interface en argument, l'incorporation
// n'apporte plus rien. C'est la conclusion de la lecon.
func (b Base) ExporterAvecSoi(r releve.Releve, soi morceaux) (string, error) {
    final, err := r.SoldeFinal()
    if err != nil {
        return "", err
    }
    var sb strings.Builder
    sb.WriteString(soi.entete(r))
    sb.WriteString("\n")
    for _, l := range r.Lignes() {
        sb.WriteString(soi.ligne(l))
        sb.WriteString("\n")
    }
    sb.WriteString(soi.pied(final.String()))
    return sb.String(), nil
}
```

Et **ça marche**. C'est le problème.

Ça marche en recopiant à la main ce qu'une table virtuelle ferait toute seule,
et chaque appelant doit se souvenir de se passer lui-même. Se passer la
mauvaise valeur produit un format valide et faux, sans aucun signal :

```
(avant.Base{}).ExporterAvecSoi(r, avant.XML{})   // du XML, demande ou pas
```

Regarde cet appel. On construit une `Base` pour rien, on lui passe un `XML`,
et le `XML` incorpore déjà une `Base`. Et surtout :

> **Si on passe déjà l'interface en argument, l'incorporation n'apporte plus
> rien.** C'est tout le chemin de cette leçon, et il s'arrête ici.

### La correction, et elle tient en un mot

```go
// Package export assemble un releve selon un format.
//
// C'est la correction, et elle tient en une phrase : le squelette est une
// FONCTION, pas une methode d'un type a incorporer.
//
// Consequence immediate : il n'y a plus de « parent », donc plus rien a
// surcharger, donc plus de dispatch a esperer. Le squelette recoit son
// formateur en argument, et le compilateur verifie qu'il en a un.
package export

import (
    "errors"
    "fmt"
    "strings"

    "exemple/banque/releve"
    "exemple/banque/somme"
)
```

```go
// Formateur rend les morceaux. TROIS methodes, et ce sont les trois que le
// squelette appelle.
//
// Elle est declaree ici, chez l'appelant. Sa signature ne nomme que des types
// du domaine — releve et somme — donc une implementation n'a pas a importer
// ce paquet.
type Formateur interface {
    Entete(r releve.Releve) string
    Ligne(l releve.Ligne) string
    Pied(soldeFinal somme.Somme) string
}

// Exporter assemble le releve. C'est le squelette, et c'est une fonction.
//
// Compare-la a avant.Base.Exporter : c'est le meme code, au recepteur pres.
// Et c'est tout ce qu'il fallait changer.
func Exporter(r releve.Releve, f Formateur) (string, error) {
    if f == nil {
        return "", ErrFormateurNul
    }
    final, err := r.SoldeFinal()
    if err != nil {
        return "", err
    }
    var sb strings.Builder
    sb.WriteString(f.Entete(r))
    sb.WriteString("\n")
    for i, l := range r.Lignes() {
        ligne := f.Ligne(l)
        if strings.TrimSpace(ligne) == "" {
            return "", fmt.Errorf("%w : rang %d, libelle %q", ErrLigneVide, i, l.Libelle())
        }
        sb.WriteString(ligne)
        sb.WriteString("\n")
    }
    sb.WriteString(f.Pied(final))
    return sb.String(), nil
}
```

Le squelette est devenu une **fonction**. C'est tout ce qui a changé — le
corps est le même, à la ligne de signature près.

Et les conséquences sont immédiates :

| | Avant | Après |
|---|---|---|
| le squelette est | une méthode d'un type à incorporer | une **fonction** |
| le formateur arrive | par le récepteur, en espérant | par un **argument**, vérifié par le compilateur |
| un formateur absent donne | le format par défaut, en silence | `ErrFormateurNul` |
| les trois formats rendent | le même texte | trois textes |

```go
// Les assertions de conformite. Sans elles, ajouter une methode a Formateur
// ne produit aucune erreur de compilation.
var (
```

## 4. Le critère, et son contrôle mécanique

Tout ce qui précède tient dans une phrase, et elle est vérifiable :

> **Un type est sûr à incorporer-et-surcharger si et seulement si aucune de
> ses méthodes n'appelle une autre de ses méthodes sur son propre récepteur.**

La raison est le FAIT 2. Si une méthode de `T` appelle `t.Autre()`, cet appel
est gelé vers `T.Autre` à la compilation, et il le restera quel que soit le
type qui incorpore `T`.

Et ce critère se **lit dans la source**. C'est le troisième mécanisme de la
leçon 1.6 — par la lecture de la source — et c'est sa troisième utilisation
dans ce cours.

```go
// Package sondage repond mecaniquement a la seule question qui decide si une
// incorporation est sure.
//
// Le critere de la lecon :
//
//    Un type est sur a incorporer-et-surcharger si et seulement si AUCUNE de
//    ses methodes n'appelle une autre de ses methodes sur son propre
//    recepteur.
//
// La raison est l'absence de dispatch virtuel. Si une methode de T appelle
// t.Autre(), cet appel est resolu a la compilation vers T.Autre, et il le
// restera quel que soit le type qui incorpore T. Une surcharge d'Autre dans
// le type englobant ne sera jamais appelee depuis T — et c'est exactement le
// defaut du paquet avant.
//
// Ce paquet lit la source avec go/ast et rend la liste des appels internes.
// C'est le troisieme mecanisme de la lecon 1.6 — par la lecture de la source
// — et c'est sa troisieme utilisation dans le cours.
package sondage
```

Deux fonctions exportées : l'une rend les appels internes, l'autre rend les
types incorporés **de façon anonyme** — un champ nommé ne promeut rien, donc
il ne pose aucun des problèmes de cette leçon. La différence entre
`sync.Mutex` et `mu sync.Mutex` est un mot, et c'est toute la différence.

```go
// AppelInterne est un appel d'une methode d'un type a une autre methode du
// meme type, sur son propre recepteur.
//
// Type est QUALIFIE par son paquet, et ce n'est pas cosmetique : la premiere
// version de ce sondage rendait des noms courts, et elle confondait
// mecanique.Base avec avant.Base. Le rapport paraissait juste parce que les
// deux types etaient deroges — une erreur masquee par une coincidence.
//
//    Un sondage qui identifie les types par leur nom court confond les
//    homonymes de paquets differents, et il le fait en silence.
type AppelInterne struct {
    Fichier string
    Ligne   int
    Type    string
    Depuis  string
    Vers    string
}
```

Le test applique le critère à tout le module :

```go

// correction 2.2/3 sur le compte des champs. Une derogation nommee et
// justifiee est relisible ; une regle qu'on desactive ne l'est pas.
var derogations = map[string]string{
    "mecanique.Base": "type de demonstration : son appel interne EST le fait " +
        "que la lecon mesure. Il n'existe que pour etre incorpore a tort.",
    "avant.Base": "type de demonstration : le paquet avant montre le defaut, " +
        "il ne le corrige pas. Son remplacant est export.Exporter, qui est " +
        "une fonction et n'incorpore rien.",
    "sync.Mutex": "type de la bibliotheque standard, non analysable par ce " +
```

### Ce que le sondage m'a appris sur lui-même

Deux fois, et les deux valent plus que le sondage.

**Il confondait les homonymes.** Sa première version identifiait les types par
leur **nom court**, donc `mecanique.Base` et `avant.Base` étaient le même
type. Le rapport paraissait juste — parce que les deux étaient dérogés. Une
erreur masquée par une coïncidence.

> Un sondage qui identifie les types par leur nom court confond les homonymes
> de paquets différents, et il le fait en silence.

**Il manquait son propre test négatif.** Une modification de la campagne —
retirer la comparaison du nom du récepteur — a **survécu**. Elle faisait
compter `soi.entete(...)` comme un appel interne, et aucun test ne s'en
apercevait, parce que le seul type concerné était dérogé.

```go

// du sondage, et il manquait.
//
// avant.Base a deux methodes qui assemblent un releve. Exporter appelle
// b.entete(...) sur son RECEPTEUR : c'est un appel interne, et le sondage
// doit le voir. ExporterAvecSoi appelle soi.entete(...) sur un ARGUMENT :
// ce n'est pas un appel interne, et le sondage ne doit pas le voir.
//
// Sans ce test, une modification de la campagne survivait : retirer la
// comparaison du nom du recepteur faisait compter les appels sur soi comme
// des appels internes, et aucun test ne s'en apercevait — parce que le seul
// type concerne etait deroge.
//
//    Un sondage qui surveille les autres a besoin de ses propres tests, et
//    notamment du test de ce qu'il ne doit PAS trouver.
func TestUnAppelSurUnAutreIdentifiantNEstPasUnAppelInterne(t *testing.T) {
    appels, err := sondage.AppelsInternes(racine)
    if err != nil {
        t.Fatal(err)
    }
    interne, surSoi := 0, 0
    for _, a := range appels {
        if a.Type != "avant.Base" {
            continue
        }
        switch a.Depuis {
        case "Exporter":
            interne++
        case "ExporterAvecSoi":
            surSoi++
        }
    }

    }
    if surSoi != 0 {
        t.Errorf("%d appels comptes depuis ExporterAvecSoi, attendu 0 :"+
            " le sondage confond le recepteur avec un argument", surSoi)
    }
    t.Logf("Exporter : %d appels internes ; ExporterAvecSoi : %d", interne, surSoi)
}
```

> notamment du test de ce qu'il ne doit **pas** trouver.

## 5. Ce que ça donne, et ce que ça coûte

### Quand l'incorporation est le bon outil

Elle l'est souvent, et la leçon n'est pas « n'incorpore jamais ». Trois cas où
elle est exactement ce qu'il faut :

| Cas | Pourquoi c'est sûr |
|---|---|
| **état partagé sans surcharge** — un champ `base` que trois types se partagent, dont personne ne remplace les méthodes | le critère est satisfait : aucun appel interne à surcharger |
| **composition d'interfaces** — `type ReadWriter interface { Reader; Writer }` | une interface n'a pas de corps, donc pas d'appel interne possible |
| **décoration** — une enveloppe qui transfère tout et remplace une méthode que rien n'appelle en interne | le critère, encore |

Et le troisième cas a une variante qu'on rencontre tous les jours : une
enveloppe d'interface qui surcharge **une** méthode. `registre.Connecteur`, de
la correction 2.2/4, est exactement ça : trois interfaces incorporées pour
n'en faire qu'une, sans un seul corps de méthode.

### Le coût de la correction, compté

| | Avant | Après |
|---|---|---|
| lignes du squelette | 22 (méthode) | 22 (fonction) |
| types à déclarer | 1 `Base` + 3 sous-types | 0 + 3 formateurs |
| le paquet `sondage` | — | **216 lignes** de `go/ast` |
| le test du critère | — | **273 lignes** |
| ce que le compilateur vérifie | que `Base` existe | que le formateur **est** un formateur |

Les 489 lignes de sondage et de test sont le vrai coût, et il faut être
honnête sur ce qu'elles achètent : **elles n'achètent rien pour ce
module-là**. Le module est correct sans elles. Elles achètent la garantie que
le prochain développeur ne réintroduise pas le défaut — et elles ne la
rendent que si quelqu'un lit leur rapport.

> Un sondage qui lit la source est le dernier recours, pas le premier. Avant
> lui il y a le critère, qui tient en une phrase, et qui s'applique en
> relecture pour zéro ligne de code.

### Quand ne rien faire est la bonne réponse

- **Un seul format, pour toujours.** Pas d'interface, pas de squelette : une
  fonction qui écrit le texte. Et si le deuxième format arrive, tu auras le
  premier sous les yeux pour extraire l'interface.
- **Le type incorporé n'a qu'une méthode et personne ne la surcharge.**
  L'incorporation est gratuite et correcte.
- **Le programme a six mois à vivre.** Les 489 lignes ne seront jamais
  amorties.

## 6. Les trois erreurs qui restent

### L'incorporation qui exporte ce qu'on ne voulait pas

C'est l'erreur la plus fréquente, et elle est dans la section 7 parce qu'elle
produit un incident. Résumé : incorporer `sync.Mutex` exporte `Lock`,
`Unlock` **et `TryLock`**, et le chiffre n'est pas celui qu'on croit.

### L'enveloppe qui s'appelle elle-même

```
func (e Enveloppe) Formater(s string) string {
    return e.Prefixe + e.Formater(s)   // recursion infinie
}
```

La méthode surchargée porte le même nom que celle de l'interface incorporée.
`e.Formater` se résout vers la méthode de l'enveloppe, pas vers celle du
champ. Il faut écrire `e.Formateur.Formater(s)`, et c'est ce que fait le
FAIT 4.

Le signe : une pile d'appel de dix mille lignes identiques, et un
`stack overflow` au lieu d'un résultat.

### L'incorporation comme raccourci de nommage

```
type Service struct {
    *sql.DB            // pour ecrire s.Query(...) au lieu de s.db.Query(...)
    *redis.Client
    *log.Logger
}
```

Trois caractères économisés par appel, et en échange : toutes les méthodes des
trois types exportées par `Service`, un risque d'ambiguïté à chaque mise à
jour, et un `Service` qui satisfait `io.Closer` — donc que n'importe quel
code générique fermera.

> L'incorporation n'est pas un raccourci de nommage. Elle a un **prix
> d'interface publique**, et ce prix se paie à chaque mise à jour des types
> incorporés.

## 7. Le lien avec la production

Deux incidents, et les deux viennent de la **promotion** — pas du dispatch.

### Incident 1 — le cache bloqué par un verrou posé ailleurs

```go
// CacheIncorpore est le cache tel qu'on l'ecrit d'instinct.
//
// Il incorpore sync.Mutex, ce qui est l'idiome le plus repandu de la
// bibliotheque standard. Et il expose du coup DEUX methodes publiques de plus
// que son auteur n'en a declare : Lock et Unlock.
//
// Consequence : n'importe quel appelant peut verrouiller le mutex interne de
// ce cache depuis l'exterieur. Et le jour ou il le fait et oublie de
// deverrouiller, le cache est mort pour tout le processus — avec une pile
// d'appel qui ne montrera jamais ce paquet.
type CacheIncorpore struct {
    sync.Mutex
    entrees map[string]string
}
```

```go
// CacheNomme est la correction, et elle tient en un nom de champ.
//
// Le mutex devient un champ nomme, prive. Les methodes Lock et Unlock ne sont
// plus promues, donc elles ne sont plus exportees, donc l'etat « un appelant
// exterieur verrouille le mutex de ce cache » n'est plus representable.
//
// Le cout est d'un mot : « mu sync.Mutex » au lieu de « sync.Mutex ».
type CacheNomme struct {
    mu      sync.Mutex
    entrees map[string]string
}
```

La mesure d'abord, parce qu'elle ne donne pas le chiffre attendu :

```go
// TestLeMutexIncorporeExporteTroisMethodesDeTrop est la MESURE de la fuite.
//
// J'avais ecrit « deux methodes de trop » — Lock et Unlock — et le test a
// repondu TROIS. La troisieme est TryLock, ajoutee a sync.Mutex par Go 1.18.
//
//    On ne sait pas combien de methodes on exporte quand on incorpore un
//    type qu'on ne possede pas : son jeu de methodes peut grandir. Un cache
//    ecrit avant Go 1.18 a gagne une methode publique a la mise a jour de
//    la chaine d'outils, sans qu'une ligne de son code change.
//
// C'est le meme mecanisme que l'incident du paquet incident, avec la
// bibliotheque standard dans le role de la bibliotheque tierce.
func TestLeMutexIncorporeExporteTroisMethodesDeTrop(t *testing.T) {
    incorpore := methodesExportees(reflect.TypeOf(fuite.NouveauCacheIncorpore()))
    nomme := methodesExportees(reflect.TypeOf(fuite.NouveauCacheNomme()))

    t.Logf("CacheIncorpore : %d methodes exportees %v", len(incorpore), incorpore)
    t.Logf("CacheNomme     : %d methodes exportees %v", len(nomme), nomme)

    if len(incorpore)-len(nomme) != 3 {
        t.Fatalf("ecart de %d methodes, attendu 3 (Lock, TryLock et Unlock)."+
            " Si l'ecart change, c'est que sync.Mutex a gagne ou perdu une"+
            " methode — et c'est precisement le point du test",
            len(incorpore)-len(nomme))
    }
    for _, attendue := range []string{"Lock", "TryLock", "Unlock"} {
        if !contient(incorpore, attendue) {
            t.Errorf("%s n'est pas exportee par CacheIncorpore", attendue)
        }
        if contient(nomme, attendue) {
            t.Errorf("%s est encore exportee par CacheNomme", attendue)
        }
    }
}
```

```
CacheIncorpore : 5 methodes exportees [Lire Lock Mettre TryLock Unlock]
CacheNomme     : 2 methodes exportees [Lire Mettre]
```

J'avais écrit « deux méthodes de trop » — `Lock` et `Unlock`. Le test a
répondu **trois**. La troisième est `TryLock`, ajoutée à `sync.Mutex` par
Go 1.18.

> On ne sait pas combien de méthodes on exporte quand on incorpore un type
> qu'on ne possède pas : **son jeu de méthodes peut grandir**. Un cache écrit
> avant Go 1.18 a gagné une méthode publique à la mise à jour de la chaîne
> d'outils, sans qu'une ligne de son code change.

Et l'incident lui-même, reproduit :

```go
// TestUnAppelantExterieurPeutBloquerLeCacheIncorpore reproduit l'incident.
//
// Un appelant verrouille le mutex promu depuis l'exterieur du paquet et
// oublie de deverrouiller. Le cache est alors mort pour tout le processus, et
// la pile d'appel du blocage ne montrera jamais le paquet fuite.
//
// Le test utilise un delai parce qu'un vrai interblocage bloque pour
// toujours, et qu'un test qui bloque pour toujours n'est pas un test.
func TestUnAppelantExterieurPeutBloquerLeCacheIncorpore(t *testing.T) {
    c := fuite.NouveauCacheIncorpore()
    c.Mettre("cle", "valeur")

    // Le cache repond normalement.
    if err := fuite.EssaiAvecDelai(func() error {
        _, err := c.Lire("cle")
        return err
    }, 200*time.Millisecond); err != nil {
        t.Fatalf("lecture normale : %v", err)
    }

    // Un appelant exterieur verrouille, et oublie de deverrouiller.
    c.Lock()
    err := fuite.EssaiAvecDelai(func() error {
        _, err := c.Lire("cle")
        return err
    }, 200*time.Millisecond)
    if !errors.Is(err, fuite.ErrInterblocage) {
        t.Fatalf("attendu un interblocage, obtenu %v", err)
    }
    t.Log("le cache est bloque par un verrou pose hors du paquet qui le declare")
    c.Unlock()

    // Et il repart.
    if err := fuite.EssaiAvecDelai(func() error {
        _, err := c.Lire("cle")
        return err
    }, 200*time.Millisecond); err != nil {
        t.Fatalf("apres deverrouillage : %v", err)
    }
}
```

```
le cache est bloque par un verrou pose hors du paquet qui le declare
```

Un appelant extérieur verrouille le mutex promu et oublie de déverrouiller. Le
cache est mort pour tout le processus, et la pile d'appel du blocage ne
montrera **jamais** le paquet qui déclare le cache. Le temps de diagnostic
d'un incident comme celui-là se compte en heures.

La correction tient en un mot : `mu sync.Mutex` au lieu de `sync.Mutex`. Un
champ nommé ne promeut rien, donc `Lock` n'est plus exportée, donc l'état
« un appelant extérieur verrouille le mutex de ce cache » n'est plus
représentable — et un programme qui l'essaie ne compile pas :

```
./main.go:15:28: fuite.NouveauCacheNomme().Lock undefined
    (type *fuite.CacheNomme has no field or method Lock)
```

### Incident 2 — l'API qui a arrêté d'envoyer la moitié de ses champs

Celui-là est le plus coûteux, parce qu'il est **silencieux et à distance**.

Une API expose des événements en JSON. Le type `Evenement` incorpore un
`Horodatage` fourni par une bibliothèque interne. Un jour, l'auteur de cette
bibliothèque ajoute trois lignes :

```go
// --- APRES la mise a jour ---

// HorodatageV2 est le meme type, plus une methode.
//
// L'ajout est raisonnable, et l'auteur de la bibliotheque a bien fait : il
// voulait que son horodatage se serialise en RFC 3339 plutot qu'en objet. Il
// a publie ca en version mineure, parce que ca n'enleve rien et ne change
// aucune signature.
type HorodatageV2 struct {
    Instant time.Time `json:"instant"`
}

// MarshalJSON est la methode ajoutee. Trois lignes.
func (h HorodatageV2) MarshalJSON() ([]byte, error) {
    return []byte(`"` + h.Instant.UTC().Format(time.RFC3339) + `"`), nil
}

// EvenementV2 est le MEME code que EvenementV1. Pas une ligne n'a change.
//
// Et son JSON n'est plus un objet : c'est la chaine rendue par
// HorodatageV2.MarshalJSON. Type et Ref ont disparu.
//
// La raison est la promotion : MarshalJSON est promue au niveau
// d'EvenementV2, donc EvenementV2 satisfait json.Marshaler, donc
// encoding/json n'inspecte plus ses champs et appelle la methode.
type EvenementV2 struct {
    HorodatageV2
    Type string `json:"type"`
    Ref  string `json:"ref"`
}
```

L'ajout est raisonnable. Il voulait que son horodatage se sérialise en
RFC 3339 plutôt qu'en objet. Il a publié ça en **version mineure**, parce que
ça n'enlève rien et ne change aucune signature.

Et voilà ce que l'API envoie, avant et après — sans qu'une ligne de son code
change :

```
avant : {"instant":"2026-03-01T08:00:00Z","type":"PAIEMENT","ref":"R-1"}
apres : "2026-03-01T08:00:00Z"
```

**`type` et `ref` ont disparu.** Le JSON n'est même plus un objet.

Le mécanisme est la promotion : `MarshalJSON` est promue au niveau
d'`Evenement`, donc `Evenement` satisfait `json.Marshaler`, donc
`encoding/json` n'inspecte plus ses champs et appelle la méthode.

> Une méthode promue fait satisfaire au type englobant une interface que
> personne n'a voulue. Et quand cette interface est un point d'extension de la
> bibliothèque standard, le comportement du type change **entièrement**.

La correction tient, encore, en un nom de champ :

```go
// --- La correction ---

// EvenementV3 est la correction, et elle tient en un nom de champ.
//
// L'horodatage devient un champ NOMME. Sa methode MarshalJSON n'est plus
// promue, donc EvenementV3 ne satisfait pas json.Marshaler, donc
// encoding/json inspecte ses champs comme avant.
//
// Cout : un mot, et une etiquette json pour garder la meme forme de sortie.
type EvenementV3 struct {
    Horodatage HorodatageV2 `json:"horodatage"`
    Type       string       `json:"type"`
    Ref        string       `json:"ref"`
}
```

```
corrige : {"horodatage":"2026-03-01T08:00:00Z","type":"PAIEMENT","ref":"R-1"}
```

### Le garde-fou, et pourquoi les tests habituels ne l'attrapent pas

Un test qui compare le JSON produit à un JSON attendu écrit à la main **ne
voit rien**, parce que le développeur qui casse la forme met à jour l'attendu
dans le même commit. C'est le mode de panne de tout test écrit comme un
instantané.

Ce qu'il faut est un test qui ne connaît pas la forme, mais **le contrat** :
la liste des champs que l'API promet.

```go
// VerifierChamps est le garde-fou generique : il dit si une serialisation
// contient tous les champs attendus.
//
// Il existe parce que la classe entiere de ce bug est invisible a la
// compilation ET aux tests qui comparent un JSON a un JSON attendu ecrit a la
// main — ceux-la sont mis a jour par le developpeur qui casse la forme.
func VerifierChamps(brut []byte, attendus ...string) error {
    var manquants []string
    for _, champ := range attendus {
        if !contientClef(brut, champ) {
            manquants = append(manquants, champ)
        }
    }
    if len(manquants) > 0 {
        return fmt.Errorf("%w : %v absents de %s", ErrChampsPerdus, manquants, brut)
    }
    return nil
}

func contientClef(brut []byte, champ string) bool {
    return strings.Contains(string(brut), `"`+champ+`":`)
}
```

```
champs perdus : incident : champs perdus a la serialisation :
                [instant type ref] absents de "2026-03-01T08:00:00Z"
```

> Un test d'instantané est mis à jour par celui qui casse le contrat. Un test
> qui énumère les **engagements** ne l'est pas, parce qu'il faudrait retirer
> un engagement — et retirer un engagement se voit en revue.

### Le relevé de la campagne

Dix-huit modifications, dix paquets de test.

```
modification                                                       | tests qui tombent
-------------------------------------------------------------------+------------------
 1. releve.Nouveau ne trie plus les lignes                         | 1
 2. Lignes() rend la tranche interne                               | 1
 3. une ligne hors periode est acceptee                            | 1
 4. un libelle vide est accepte                                    | 1
 5. NouvelleLigne garde l'heure                                    | 1
 6. somme.Plus ne verifie plus le depassement par le bas           | 1
 7. Exporter accepte un formateur nul                              | 1
 8. Exporter accepte une ligne vide                                | 1
 9. Exporter ecrit l'entete au lieu du pied                        | 3
10. CSV.sep() rend la chaine vide                                  | 1
11. CSV.Ligne n'echappe plus le libelle                            | 1
12. l'echappement XML traite & en dernier                          | 1
13. mecanique.Derive perd sa surcharge                             | 2
14. CacheNomme incorpore son mutex au lieu de le nommer            | 3
15. HorodatageV2 perd son MarshalJSON                              | 4
16. VerifierChamps ne verifie plus rien                            | 4
17. le sondage ne qualifie plus les types par leur paquet          | 4
18. le sondage ne verifie plus le nom du recepteur                 | 1

18/18 modifications detectees
```

Trois remarques.

**Six modifications n'ont d'abord pas compilé** — une variable ou un import
devenu inutilisé à chaque fois. C'est le taux le plus élevé de ce cours, et la
raison est mécanique : le module a beaucoup de garde-fous d'une seule ligne,
et retirer une ligne de garde laisse souvent son message d'erreur orphelin.
Une modification qui ne compile pas n'a pas été jouée ; il faut la rejouer, et
`if false && ...` suffit.

**La modification 18 a survécu**, et c'est elle qui a produit le test
manquant du sondage. Un survivant ne réclame pas toujours un test de plus :
celui-là en réclamait un, et c'était un test de ce que le sondage ne doit
**pas** trouver.

**La modification 12 est la plus discrète.** Faire échapper `&` en dernier au
lieu d'en premier produit `&amp;lt;` au lieu de `&lt;` — un XML qui s'ouvre
dans un navigateur, qui passe la validation de forme, et qui affiche
`&lt;` littéralement chez le destinataire. C'est le même genre de
non-commutativité que l'ordre des normalisations de la correction 2.2/1.

## 8. Ce qu'il faut retenir

1. **L'héritage accorde trois choses** — réutilisation, sous-typage,
   spécialisation ouverte — et on n'en voulait presque jamais les trois.
2. **Go les a séparées** : incorporation pour la première, interface pour la
   deuxième, **rien** pour la troisième.
3. **L'incorporation est un champ**, dont le nom est le nom de son type. Il
   est atteignable, et il se remplace en entier.
4. **Il n'y a pas de dispatch virtuel.** `Derive{}.Saluer()` rend « bonjour
   base », et le rendra toujours. La surcharge existe ; personne à l'intérieur
   du type incorporé ne la verra.
5. **Le patron de la méthode-modèle ne marche pas** avec l'incorporation. Il
   compile, et il produit le format par défaut pour tout le monde.
6. **Le critère** : un type est sûr à incorporer-et-surcharger si et seulement
   si aucune de ses méthodes n'appelle une autre de ses méthodes sur son
   propre récepteur.
7. **La correction est de transformer la méthode-squelette en fonction.** Le
   corps ne change pas ; le formateur devient un argument que le compilateur
   vérifie.
8. **Si tu passes déjà l'interface en argument, l'incorporation n'apporte
   plus rien.**
9. **L'ambiguïté se déclare mais ne s'utilise pas** — et une bibliothèque qui
   ajoute une méthode peut casser ton code à un endroit que tu n'as pas écrit.
10. **Une interface incorporée nulle panique**, parce que `nil` est une valeur
    valide d'un type interface. Un constructeur ferme le chemin qu'on emprunte.
11. **L'incorporation a un prix d'interface publique.** Incorporer
    `sync.Mutex` exporte trois méthodes, pas deux, et le nombre peut grandir
    à la prochaine mise à jour du langage.
12. **Une méthode promue fait satisfaire une interface que personne n'a
    voulue.** Avec `json.Marshaler`, les champs du type englobant disparaissent
    de la sérialisation.
13. **Un champ nommé ne promeut rien.** La différence entre `sync.Mutex` et
    `mu sync.Mutex` est un mot, et c'est toute la différence.
14. **Un test d'instantané est mis à jour par celui qui casse le contrat.**
    Un test qui énumère les engagements ne l'est pas.
15. **Un sondage qui surveille les autres a besoin de ses propres tests**, et
    notamment du test de ce qu'il ne doit pas trouver.

## 9. Approfondissement

### Pourquoi Go a tranché comme ça, et ce que ça a coûté

Les auteurs de Go ont écarté l'héritage explicitement, et leur argument tient
en une observation : **une hiérarchie de classes mélange deux graphes
différents**. Celui de la réutilisation de code, et celui de la
substituabilité. Dans un langage à héritage simple, les deux sont le même
graphe, et il faut choisir lequel on optimise.

Ce que la décision a rapporté :

- les interfaces sont **satisfaites structurellement**, donc on peut en
  déclarer une pour un type qu'on ne possède pas, après coup. C'est ce qui
  rend possible « l'interface déclarée chez l'appelant » de la leçon 2.2, et
  aucun langage à sous-typage nominal ne le permet ;
- il n'y a **pas de hiérarchie à concevoir**, donc pas de refonte de
  hiérarchie à faire quand le métier change de forme ;
- la question *« de laquelle des trois ai-je besoin ? »* est **forcée** : les
  trois mécanismes étant séparés, il faut en nommer un.

Ce que la décision a coûté :

- le patron de la méthode-modèle n'existe pas, et il est **remplaçable** — ce
  module le montre — mais il faut le savoir, et l'incorporation ressemble
  assez à l'héritage pour qu'on ne le sache qu'après l'avoir essayé ;
- il n'y a pas de `super`, donc une enveloppe qui veut « faire comme le
  délégué, plus une chose » doit nommer le délégué explicitement ;
- la promotion est **tout ou rien** : on ne peut pas incorporer un type et
  masquer une de ses méthodes. On nomme le champ, ou on les prend toutes.

### Les quatre formes de réutilisation, et quand chacune sert

| La forme | Ce qu'elle donne | Quand |
|---|---|---|
| **une fonction libre** | rien de plus que le code | par défaut, et c'est le cas le plus fréquent |
| **l'incorporation** | les méthodes, promues | état partagé que personne ne surcharge |
| **un champ nommé** | les méthodes, non promues | tout le reste — et c'est ce qu'il faut préférer |
| **une interface en argument** | le dispatch dynamique | quand le comportement doit varier |

La ligne qui manque dans la plupart des discussions est la troisième. Entre
« incorporer » et « réécrire », il y a **nommer le champ**, et c'est presque
toujours la bonne réponse. Elle coûte un mot par appel.

### La promotion traverse les niveaux, et ça se mesure

Une subtilité qu'il faut avoir vue : la promotion est **transitive**. Si `A`
incorpore `B` qui incorpore `C`, les méthodes de `C` sont appelables sur `A`.
Et la résolution se fait par **profondeur** : la méthode la moins profonde
gagne, sans ambiguïté.

Conséquence pratique : un type qui incorpore un type d'une bibliothèque hérite
de l'interface publique de **tout ce que cette bibliothèque incorpore**, y
compris ce qu'elle a incorporé dans une version mineure. Le compte des
méthodes exportées de la section 7 n'est donc pas une curiosité : c'est une
mesure à refaire à chaque mise à jour.

### Le cas de `context.Context` et des interfaces qu'on incorpore pour étendre

Un idiome qu'on voit souvent, et qui est correct :

```
type Journalise interface {
    io.Writer
    Niveau() string
}
```

Incorporer des interfaces dans une interface est la seule forme
d'incorporation qui n'a **aucun** des problèmes de cette leçon : pas de corps,
donc pas d'appel interne, donc pas de dispatch à espérer. L'ambiguïté reste
possible si deux interfaces déclarent la même méthode avec des signatures
différentes — et depuis Go 1.14 c'est accepté si les signatures sont
**identiques**, refusé sinon.

### Ce que cette leçon n'a pas traité

- **La substituabilité comme contrat**, et ce qui se passe quand une
  implémentation satisfait une signature sans satisfaire ses promesses. C'est
  Liskov, et c'est la leçon 2.4.
- **Quand une interface a trop de méthodes**, et pourquoi la taille est une
  propriété de l'appelant. La leçon 2.2 l'a observé ; la 2.5 en fait une règle.
- **Le patron décorateur**, qui est l'usage le plus légitime de
  l'incorporation d'interface, et qui a ses propres modes de panne — ils
  appartiennent au niveau 3.
- **Les génériques comme forme de réutilisation.** Ils n'ont pas été évoqués
  ici parce qu'ils ne répondent pas à la question : ils font varier le type,
  pas le comportement. La leçon 2.2 a posé la distinction.

## 10. Le réflexe à installer

Devant une incorporation que tu t'apprêtes à écrire, trois questions, dans cet
ordre :

> 1. **De laquelle des trois ai-je besoin ?**
>    La réutilisation → un champ, et probablement **nommé**.
>    Le sous-typage → une interface, déclarée chez l'appelant.
>    La spécialisation ouverte → elle n'existe pas. Passe l'interface en
>    argument, et transforme la méthode en fonction.
> 2. **Le type que j'incorpore appelle-t-il une de ses propres méthodes ?**
>    Oui → ne le surcharge pas. L'appel ne te verra jamais.
>    Non → l'incorporation est sûre, aujourd'hui, pour cette version.
> 3. **Combien de méthodes est-ce que j'exporte en plus ?**
>    Compte-les. Si la réponse n'est pas zéro et que tu ne les voulais pas,
>    **nomme le champ**. Ça coûte un mot par appel.

Et devant une incorporation qui existe déjà, un seul geste, qui prend une
minute :

> **Compte les méthodes exportées du type englobant, et barre celles qu'il a
> déclarées lui-même.** Ce qui reste est son interface publique accidentelle.
> Pour chacune, demande : *un appelant qui l'utilise aurait-il dû pouvoir ?*
> Et : *que se passe-t-il si la bibliothèque en ajoute une au prochain
> trimestre ?*
