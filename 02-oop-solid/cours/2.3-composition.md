# Leçon 2.3 — Composition contre héritage, et pourquoi Go a tranché

## L'essentiel en deux minutes

**Le problème, en une phrase.** Réutiliser le code d'un type dans un autre
sans hériter de ce qu'on ne voulait pas — et Go ne propose pas l'héritage.

**L'image.** Une voiture **a** un GPS ; elle n'**est** pas un GPS. Si le
GPS a un bouton « annoncer la destination », c'est le GPS qui parle, avec
sa propre voix, même si la voiture a un autre haut-parleur. En Go,
**incorporer** un type, c'est poser un GPS dans la voiture : un champ, dont
les méthodes sont accessibles directement — mais qui reste un GPS.

**Le code, en une vingtaine de lignes.**

```go
// Package e23 is the two-minute version of lesson 2.3.
package e23

// Base greets with its name.
type Base struct{}

// Name is Base's name.
func (Base) Name() string { return "base" }

// Greet calls Name on its own receiver: always Base.Name.
func (b Base) Greet() string { return "hello " + b.Name() }

// Derived embeds Base and redefines Name.
type Derived struct{ Base }

// Name is Derived's name. Base.Greet will never see it.
func (Derived) Name() string { return "derived" }

// Greet, as a function, takes the name giver as an argument: the compile
// checks it, and Derived's Name is used.
func Greet(n interface{ Name() string }) string { return "hello " + n.Name() }
```

`Derived{}.Greet()` rend `"hello base"`, pas `"hello derived"`. `Greet` est
une méthode de `Base` : elle appelle `Name` sur **son** receveur, qui est un
`Base`. Il n'y a pas de « méthode virtuelle » en Go : la méthode redéfinie
dans `Derived` n'est vue que par ceux qui appellent `Derived` directement.
La fonction `Greet`, qui reçoit l'interface en argument, fait ce qu'on
voulait, et le compilateur vérifie l'argument.

**Les règles à retenir.**

1. L'héritage donne trois choses à la fois : réutiliser du code, être
   accepté à la place d'un autre type, et redéfinir un comportement. Go les
   sépare : l'incorporation pour la première, l'interface pour la deuxième,
   rien pour la troisième.
2. Un type incorporé est **un champ**, qui porte le nom de son type. Ses
   méthodes sont promues, pas redéfinissables de l'intérieur.
3. Un type est sûr à incorporer puis « surcharger » seulement si aucune de
   ses méthodes n'en appelle une autre sur son propre receveur.
4. Pour un comportement à faire varier, passe une interface ou une fonction
   **en argument**.
5. Incorporer exporte les méthodes promues : `sync.Mutex` incorporé rend
   `Lock` et `Unlock` publics sur ton type.

Tu as sûrement déjà lu la formule : *« préférer la composition à
l'héritage »*. Elle a quarante ans, elle est dans le livre du Gang of Four,
et elle est répétée si souvent qu'elle ne veut plus rien dire.

Cette leçon ne va pas la répéter. Elle va faire deux choses : poser ce que
l'héritage **fait**, mécanisme par mécanisme, et montrer que Go n'en a gardé
qu'une partie — puis mesurer ce qui arrive quand on écrit du Go en croyant
avoir le reste.

> Go n'a pas d'héritage. Il a l'**incorporation**, qui ressemble à l'héritage
> jusqu'au moment où ça compte, et c'est précisément à ce moment-là que le
> programme devient faux **sans que rien ne le signale**.

On commence par les définitions et par quatre faits mesurés, avec du code qui
compile.

## 1. L'héritage et l'incorporation, définis

### Ce que l'héritage fait, et ce sont trois choses

Quand un langage dit *« `Derived` hérite de `Base` »*, il accorde **trois
choses à la fois**, et presque personne ne les sépare :

| | Ce que l'héritage accorde | En une phrase |
|---|---|---|
| **1** | la **réutilisation de code** | je veux les méthodes de `Base` sans les réécrire |
| **2** | le **sous-typage** | je veux être accepté partout où un `Base` est accepté |
| **3** | la **spécialisation ouverte** | je veux remplacer une partie du comportement de `Base`, **y compris quand c'est `Base` qui l'appelle** |

Le troisième est le seul qui soit vraiment propre à l'héritage, et c'est celui
qui porte un nom : le **dispatch dynamique**, ou dispatch virtuel. Quand une
méthode de `Base` appelle `this.quelqueChose()`, l'appel est résolu **à
l'exécution**, sur le type réel de l'objet. C'est ce qui fait marcher le
patron de la méthode-modèle, et c'est ce qui fait que `super` existe.

> La question qui décide n'est pas *« héritage ou composition ? »*. C'est :
> **de laquelle des trois ai-je besoin ?** Parce qu'un langage à héritage te
> donne les trois même quand tu n'en voulais qu'une, et les deux autres sont
> des engagements que tu n'as pas pris exprès.

### Ce que Go accorde, et séparément

| Je veux… | En Go |
|---|---|
| la **réutilisation** | l'**incorporation** : un champ anonyme, dont les méthodes sont promues |
| le **sous-typage** | une **interface**, satisfaite structurellement, sans déclaration |
| la **spécialisation ouverte** | **rien.** Elle n'existe pas, et c'est le sujet de cette leçon |

Trois mécanismes séparés pour trois besoins séparés, et le troisième manque.
Ce n'est pas un oubli : c'est une décision des auteurs du langage, et la
section 9 dit ce qu'elle a coûté et rapporté.

### FAIT 1 — la promotion, et la preuve que c'est un champ

```go
// --- FACT 1: method promotion ---

// Timestamp is an embeddable type.
type Timestamp struct {
    Year  int
    Month int
}

func (h Timestamp) Period() string {
    return pad4(h.Year) + "-" + pad2(h.Month)
}

// Event embeds Timestamp. There is no inheritance here: Timestamp is
// a FIELD, whose name is the name of its type, and whose methods are
// PROMOTED to Event's level.
//
// The proof that it is a field and not a parent: it can be reached by its
// name, e.Timestamp, and it can be replaced whole.
type Event struct {
    Timestamp
    Type string
}
```

```go
package mechanics_test

import (
    "errors"
    "testing"

    "example/bank/mechanics"
)

// TestPromotionGivesAccessToMethodsAndField is FACT 1.
//
// It gives both sides of the mechanism: the method can be called at the level
// of the outer type, AND the embedded type stays reachable by its name. The
// second side is the proof that it is a field and not a parent.
func TestPromotionGivesAccessToMethodsAndField(t *testing.T) {
    e := mechanics.Event{
        Timestamp: mechanics.Timestamp{Year: 2026, Month: 3},
        Type:      "PAIEMENT",
    }
    if got := e.Period(); got != "2026-03" {
        t.Errorf("promoted method: e.Period() = %q", got)
    }
    if got := e.Timestamp.Period(); got != "2026-03" {
        t.Errorf("access by field name: e.Timestamp.Period() = %q", got)
    }
    // And the field can be replaced whole, which no inheritance allows.
    e.Timestamp = mechanics.Timestamp{Year: 2027, Month: 12}
    if got := e.Period(); got != "2027-12" {
        t.Errorf("after replacing the field: %q", got)
    }
}
```

Deux faces, et la seconde est la plus importante.

`e.Period()` marche : la méthode est **promue** au niveau du type englobant,
comme si `Event` l'avait déclarée. C'est la réutilisation, et c'est
gratuit.

Mais `e.Timestamp` marche aussi. Le type incorporé est **atteignable par son
nom**, et il se **remplace en entier** : `e.Timestamp = ...`. Aucun héritage
ne permet ça, parce qu'un parent n'est pas un champ.

> L'incorporation n'est pas une relation entre deux types, c'est un **champ
> dont le nom est le nom de son type**. Tout le reste en découle.

### FAIT 2 — il n'y a pas de dispatch virtuel

C'est le fait central de la leçon. Lis-le lentement.

```go
// --- FACT 2: no virtual dispatch ---
//
// It is the central fact of the lesson, and the one that surprises everyone.

// Base has two methods, and one calls the other.
type Base struct{}

func (Base) Name() string { return "base" }

// Greet calls b.Name(). The receiver b is of type Base, and Base knows
// nothing of what could embed it. So the call is resolved AT
// COMPILE time to Base.Name, for good.
func (b Base) Greet() string { return "hello " + b.Name() }

// Derived embeds Base and declares its own Name method.
//
// In Java, C# or Python, Derived{}.Greet() would return "hello derived".
// In Go it returns "hello base", and this package's test measures it.
//
//    Embedding is not inheritance: it is DELEGATION with
//    syntactic sugar. There is no virtual table, no super, and
//    no template method pattern.
type Derived struct{ Base }

func (Derived) Name() string { return "derived" }
```

```go
// TestThereIsNoVirtualDispatch is FACT 2, and it is the central fact of
// the whole lesson.
//
// Base.Greet calls b.Name() with a receiver of type Base. Derived declares
// its own Name method. In Java, C#, Python, Derived{}.Greet() would return
// "hello derived". In Go it returns "hello base".
//
// This test is not there to check a behavior: it is there so that this
// fact cannot be forgotten, and so that it fails if a Go version
// changed.
func TestThereIsNoVirtualDispatch(t *testing.T) {
    d := mechanics.Derived{}

    // The override exists and it works, when called directly.
    if got := d.Name(); got != "derived" {
        t.Fatalf("d.Name() = %q, want \"derived\"", got)
    }

    // But the inherited method does not see it.
    if got := d.Greet(); got != "hello base" {
        t.Fatalf("d.Greet() = %q, want \"hello base\": "+
            "if this test fails, Go has gained virtual dispatch and lesson 2.3 must be rewritten", got)
    }
    t.Logf("d.Name() = %q but d.Greet() = %q", d.Name(), d.Greet())
}
```

```
d.Name() = "derived" mais d.Greet() = "hello base"
```

En Java, en C#, en Python, en Ruby, `d.Greet()` rendrait **« bonjour
derive »**. En Go il rend **« hello base »**, et il le rendra toujours.

La raison est dans la signature : `func (b Base) Greet()`. Le récepteur `b`
est de type `Base`. `Base` ne sait rien de ce qui pourrait l'incorporer, et
l'appel `b.Name()` est résolu **à la compilation** vers `Base.Name`,
définitivement.

> **L'incorporation est de la délégation avec du sucre syntaxique.** Il n'y a
> pas de table virtuelle, pas de `super`, et pas de patron de
> méthode-modèle. La surcharge existe — `d.Name()` rend bien « derived » — mais
> **personne, à l'intérieur de `Base`, ne la verra jamais.**

### FAIT 3 — l'ambiguïté se déclare mais ne s'utilise pas

```go
// --- FACT 3: ambiguity can be declared but not used ---

type Left struct{}
type Right struct{}

func (Left) Tag() string  { return "left" }
func (Right) Tag() string { return "right" }

// Diamond embeds both. This type COMPILES: Go accepts the declaration.
//
// It is the call diamond.Tag() that does not compile: "ambiguous
// selector", and the non-compilation test of package guard shows it.
// Practical consequence: a library that ADDS a method to a type
// you embed can break your code at a place you did not write.
type Diamond struct {
    Left
    Right
}

// ExplicitTag is the way out: naming the field lifts the ambiguity.
func (l Diamond) ExplicitTag() string { return l.Left.Tag() }
```

Le type `Diamond` **compile**. Go accepte qu'on incorpore deux types portant
la même méthode. C'est l'appel qui est refusé :

```
./main.go:15:26: ambiguous selector mechanics.Diamond{}.Tag
```

Deux choses à en tirer.

La sortie est de **nommer le champ** : `l.Left.Tag()`. L'ambiguïté
n'est pas une erreur de conception en soi, c'est une information manquante.

Et la conséquence qui fait mal : **une bibliothèque qui ajoute une méthode à
un type que tu incorpores peut casser ton code à un endroit que tu n'as pas
écrit.** Tu n'as rien changé, ta version mineure est compatible, et un appel
devient ambigu.

### FAIT 4 — l'interface incorporée, et sa panique

```go
// --- FACT 4: embedding an interface, and its failure mode ---

// Formatter formats a string.
type Formatter interface {
    Format(s string) string
}

// Upper is an implementation.
type Upper struct{}

func (Upper) Format(s string) string { return strings.ToUpper(s) }

// Wrapper embeds the INTERFACE and not an implementation.
//
// It is the partial replacement idiom: the wrapper delegates everything it
// does not override. And its failure mode is brutal: if the field is left
// nil, the first delegated call panics on a nil pointer. Nothing
// prevents it at compile time, because the zero value of an interface is
// a valid value of the type.
type Wrapper struct {
    Formatter
    Prefix string
}

// NewWrapper is the remedy: a constructor that refuses nil.
//
// It does not make the problem non-representable (Wrapper{} can still be
// declared), but it closes the path everyone takes.
func NewWrapper(f Formatter, prefix string) (Wrapper, error) {
    if f == nil {
        return Wrapper{}, ErrNilFormatter
    }
    return Wrapper{Formatter: f, Prefix: prefix}, nil
}

// FormatWithPrefix overrides by calling the delegation explicitly.
//
// Note the call: e.Formatter.Format(s), and not e.Format(s). The second
// would be an infinite recursion if the method had the same name: it is the
// wrapper's trap, and it is not theoretical.
func (e Wrapper) FormatWithPrefix(s string) string {
    return e.Prefix + e.Formatter.Format(s)
}
```

Incorporer une **interface** plutôt qu'une implémentation est l'idiome du
remplacement partiel : l'enveloppe délègue tout ce qu'elle ne surcharge pas.
Il est utile, et il a un mode de panne brutal :

```
panique attendue : runtime error: invalid memory address or nil pointer dereference
```

La valeur zéro d'une interface est `nil`, et `nil` est une valeur **valide**
du type. Rien n'empêche à la compilation de construire une `Wrapper` sans
formateur ; le premier appel délégué panique.

Le remède est un constructeur qui refuse le `nil`. Il ne rend pas l'état non
représentable — `Wrapper{}` reste déclarable — mais il **ferme le chemin que
tout le monde emprunte**, et c'est la différence entre un ⚫ et un garde-fou.

Et un piège dans le piège, qu'il faut avoir vu une fois : la surcharge écrit
`e.Formatter.Format(s)` et non `e.Format(s)`. Si la méthode portait le
même nom que celle de l'interface, la seconde forme serait une **récursion
infinie** — l'appel se résoudrait vers elle-même.

### Le vocabulaire, pour finir

| Le mot | Ce qu'il désigne en Go |
|---|---|
| **incorporation** (*embedding*) | un champ anonyme ; le mot « hérite » ne s'applique pas |
| **promotion** | le fait que les méthodes du champ anonyme deviennent appelables sur le type englobant |
| **délégation** | ce que la promotion fait réellement : un appel transféré à un champ |
| **dispatch statique** | l'appel est résolu à la compilation — c'est le cas de tous les appels à l'intérieur d'un type incorporé |
| **dispatch dynamique** | l'appel est résolu à l'exécution — en Go, **seulement** par une interface |

## 2. L'intuition

Une banque, à Douala, et une exigence banale : exporter un relevé de compte
dans trois formats. Texte lisible pour le client, CSV pour son tableur, XML
pour l'échange interbancaire.

Le squelette est le même pour les trois — un en-tête, les lignes, un pied — et
seule la mise en forme change. Dans n'importe quel langage à héritage, c'est
l'exercice du premier chapitre : une classe abstraite avec une méthode
`exporter()` qui appelle `header()`, `line()` et `footer()`, puis trois
sous-classes qui surchargent les morceaux.

Un développeur qui arrive de Java écrit donc ceci, et il a raison de penser
que ça marche. Les quatre blocs sans étiquette `go` de cette leçon sont des
**esquisses** et non du code du module : tout ce qui porte l'étiquette est
extrait d'un paquet qui compile et dont les tests passent.

```
type Base struct{}
func (b Base) Export(r Statement) string  { ... b.header(r) ... b.line(l) ... }
func (Base) line(l Line) string        { /* format texte */ }

type CSV struct{ Base }
func (CSV) line(l Line) string         { /* format CSV */ }
```

Ça compile. Les tests qu'il écrit — s'il appelle `CSV{}.line(...)`
directement — passent. Et le fichier qui part chez le client est au format
texte.

> Il n'y a pas d'erreur de compilation, pas de panique, pas de test rouge. Il
> y a un fichier CSV avec des espaces au lieu de points-virgules, et un client
> qui appellera dans trois semaines.

## 3. Le mécanisme

### Le modèle d'origine, et la mesure de son défaut

```go
// Package before is the attempt that fails, and it fails silently.
//
// The requirement is ordinary: three export formats of a statement, a common
// skeleton (header, lines, footer) and one piece that changes by format. In
// a language with inheritance one writes an abstract class with a template
// method, one overrides line() in three subclasses, and it is done.
//
// This file does exactly that, with embedding. It COMPILES. And it
// produces the wrong format for the three, because embedding is
// not inheritance.
package before

import (
    "strconv"
    "strings"

    "example/bank/statement"
)
```

```go
// Base holds the skeleton and the defaults.
type Base struct{}

// header, line and footer are the three pieces. Unexported, because
// only the package's substructures are meant to replace them.
func (Base) header(r statement.Statement) string { return "RELEVE " + r.Iban() + " " + r.Period() }

func (Base) line(l statement.Line) string {
    return l.Day().Format("2006-01-02") + " " + l.Label() + " " + l.Amount().String()
}

func (Base) footer(total string) string { return "SOLDE " + total }

// Export is the "template method".
//
// It calls b.header, b.line and b.footer. The receiver b is of type Base,
// and Base knows nothing of what embeds it: the three calls are resolved
// AT COMPILE TIME to Base's methods.
//
// No override will ever be called from here. Never.
func (b Base) Export(r statement.Statement) (string, error) {
    final, err := r.FinalBalance()
    if err != nil {
        return "", err
    }
    var sb strings.Builder
    sb.WriteString(b.header(r))
    sb.WriteString("\n")
    for _, l := range r.Lines() {
        sb.WriteString(b.line(l))
        sb.WriteString("\n")
    }
    sb.WriteString(b.footer(final.String()))
    return sb.String(), nil
}
```

```go
// CSV "overrides" line. The method exists, it is correct, and it is
// called by nobody.
type CSV struct{ Base }

func (CSV) line(l statement.Line) string {
    return l.Day().Format("2006-01-02") + ";" + l.Label() + ";" +
        strconv.FormatInt(l.Amount().Value(), 10)
}
```

La mesure :

```go
// TestTheThreeFormatsReturnTheSameText is the test that measures the flaw.
// The three types declare different header and line methods. The
// three exports are IDENTICAL, and they are all in the default format of
// Base.
//
// It is not a compile error, it is not a panic, it is
// not a red test: it is a CSV file that goes to the client with
// spaces instead of semicolons.
func TestTheThreeFormatsReturnTheSameText(t *testing.T) {
    r := witnessStatement(t)

    base, err := (before.Base{}).Export(r)
    if err != nil {
        t.Fatal(err)
    }
    csv, err := (before.CSV{}).Export(r)
    if err != nil {
        t.Fatal(err)
    }
    xml, err := (before.XML{}).Export(r)
    if err != nil {
        t.Fatal(err)
    }

    if csv != base {
        t.Error("the CSV export differs from the default: virtual dispatch appeared")
    }
    if xml != base {
        t.Error("the XML export differs from the default: virtual dispatch appeared")
    }
    // And the proof that the overrides do exist: called directly,
    // they work.
    if !strings.Contains(csvDirect(t, r), ";") {
        t.Error("CSV.line produces no semicolon")
    }
    if strings.Contains(csv, ";") {
        t.Error("the CSV export contains a semicolon: the override was called")
    }
    t.Logf("the three exports are %d bytes and identical", len(base))
}
```

```
les trois exports font 132 octets et sont identiques
```

**Trois formats, trois types, trois jeux de méthodes, et un seul résultat.**
Les surcharges existent, elles sont correctes, et elles ne sont appelées par
personne.

### La demi-correction que tout le monde essaie ensuite

Quand on découvre le problème, le premier réflexe est de passer « soi-même »
au squelette :

```go
// --- The half-fix everyone tries next ---

// pieces is the interface of the three pieces, extracted to be able to pass
// "itself" to the skeleton.
type pieces interface {
    header(statement.Statement) string
    line(statement.Line) string
    footer(string) string
}

// ExportWithSelf is the half-fix: we explicitly pass the object
// whose pieces we want.
//
// It WORKS, and that is the problem: it works by copying by hand what
// a virtual table would do by itself, and each caller must
// remember to pass itself. Forgetting the argument produces no
// compile error: it produces the default format.
//
// And above all: if the interface is already passed as an argument, embedding
// brings nothing more. It is the conclusion of the lesson.
func (b Base) ExportWithSelf(r statement.Statement, self pieces) (string, error) {
    final, err := r.FinalBalance()
    if err != nil {
        return "", err
    }
    var sb strings.Builder
    sb.WriteString(self.header(r))
    sb.WriteString("\n")
    for _, l := range r.Lines() {
        sb.WriteString(self.line(l))
        sb.WriteString("\n")
    }
    sb.WriteString(self.footer(final.String()))
    return sb.String(), nil
}
```

Et **ça marche**. C'est le problème.

Ça marche en recopiant à la main ce qu'une table virtuelle ferait toute seule,
et chaque appelant doit se souvenir de se passer lui-même. Se passer la
mauvaise valeur produit un format valide et faux, sans aucun signal :

```
(before.Base{}).ExportWithSelf(r, before.XML{})   // du XML, demande ou pas
```

Regarde cet appel. On construit une `Base` pour rien, on lui passe un `XML`,
et le `XML` incorpore déjà une `Base`. Et surtout :

> **Si on passe déjà l'interface en argument, l'incorporation n'apporte plus
> rien.** C'est tout le chemin de cette leçon, et il s'arrête ici.

### La correction, et elle tient en un mot

```go
// Package export assembles a statement in a format.
//
// It is the fix, and it fits in one sentence: the skeleton is a
// FUNCTION, not a method of a type to embed.
//
// Immediate consequence: there is no "parent" any more, so nothing left to
// override, so no more dispatch to hope for. The skeleton receives its
// formatter as an argument, and the compiler checks it has one.
package export

import (
    "errors"
    "fmt"
    "strings"

    "example/bank/statement"
    "example/bank/sum"
)
```

```go
// Formatter returns the pieces. THREE methods, and they are the three the
// skeleton calls.
//
// It is declared here, at the caller. Its signature names only types
// of the domain (statement and sum), so an implementation need not import
// this package.
type Formatter interface {
    Header(r statement.Statement) string
    Line(l statement.Line) string
    Footer(finalBalance sum.Sum) string
}

// Export assembles the statement. It is the skeleton, and it is a function.
//
// Compare it with before.Base.Export: it is the same code, but for the receiver.
// And it is all that had to change.
func Export(r statement.Statement, f Formatter) (string, error) {
    if f == nil {
        return "", ErrNilFormatter
    }
    final, err := r.FinalBalance()
    if err != nil {
        return "", err
    }
    var sb strings.Builder
    sb.WriteString(f.Header(r))
    sb.WriteString("\n")
    for i, l := range r.Lines() {
        line := f.Line(l)
        if strings.TrimSpace(line) == "" {
            return "", fmt.Errorf("%w: rank %d, label %q", ErrEmptyLine, i, l.Label())
        }
        sb.WriteString(line)
        sb.WriteString("\n")
    }
    sb.WriteString(f.Footer(final))
    return sb.String(), nil
}
```

Le squelette est devenu une **fonction**. C'est tout ce qui a changé — le
corps est le même, à la ligne de signature près.

Et les conséquences sont immédiates :

| | Avant | Après |
|---|---|---|
| le squelette est | une méthode d'un type à incorporer | une **fonction** |
| le formateur arrive | par le récepteur, en espérant | par un **argument**, vérifié par le compilateur |
| un formateur absent donne | le format par défaut, en silence | `ErrNilFormatter` |
| les trois formats rendent | le même texte | trois textes |

```go
// The conformance assertions. Without them, adding a method to Formatter
// produces no compile error.
var (
    _ export.Formatter = formats.Text{}
    _ export.Formatter = formats.CSV{}
    _ export.Formatter = formats.XML{}
)

// TestTheThreeFormatsReturnThreeDifferentTexts is the exact opposite of the test
// of package before.

func TestTheThreeFormatsReturnThreeDifferentTexts(t *testing.T) {
```

## 4. Le critère, et son contrôle mécanique

Tout ce qui précède tient dans une phrase, et elle est vérifiable :

> **Un type est sûr à incorporer-et-surcharger si et seulement si aucune de
> ses méthodes n'appelle une autre de ses méthodes sur son propre récepteur.**

La raison est le FAIT 2. Si une méthode de `T` appelle `t.Autre()`, cet appel
est gelé vers `T.Autre` à la compilation, et il le restera quel que soit le
type qui incorpore `T`.

Et ce critère se **lit dans la source**. C'est le troisième mécanisme de la
leçon 1.6 — par la lecture de la source — et c'est sa troisième utilisation
dans ce cours.

```go
// Package survey answers mechanically the only question that decides whether an
// embedding is safe.
//
// The lesson's criterion:
//
//    A type is safe to embed-and-override if and only if NONE of
//    its methods calls another of its methods on its own
//    receiver.
//
// The reason is the lack of virtual dispatch. If a method of T calls
// t.Other(), this call is resolved at compile time to T.Other, and it
// will stay whatever type embeds T. An override of Other in
// the outer type will never be called from T, and it is exactly the
// flaw of package before.
//
// This package reads the source with go/ast and returns the list of internal calls.
// It is the third mechanism of lesson 1.6, by reading the source,
// : and it is its third use in the course.
package survey
```

Deux fonctions exportées : l'une rend les appels internes, l'autre rend les
types incorporés **de façon anonyme** — un champ nommé ne promeut rien, donc
il ne pose aucun des problèmes de cette leçon. La différence entre
`sync.Mutex` et `mu sync.Mutex` est un mot, et c'est toute la différence.

```go
// InternalCall is a call from a method of a type to another method of the
// same type, on its own receiver.
//
// Type is QUALIFIED by its package, and it is not cosmetic: the first
// version of this survey returned short names, and it mixed up
// mechanics.Base with before.Base. The report looked right because the
// two types were waived: an error hidden by a coincidence.
//
//    A survey that identifies types by their short name mixes up
//    namesakes from different packages, and it does so silently.
type InternalCall struct {
    File  string
    Line  int
    Type  string
    Since string
    To    string
}
```

Le test applique le critère à tout le module :

```go
// waivers lists the embeddings this module allows itself DESPITE the
// criterion, and each entry carries its reason.
//
// The mechanical criterion has false positives, exactly like the one of
// correction 2.2/3 on the count of fields. A named and justified
// waiver can be reread; a rule that is switched off cannot.
var waivers = map[string]string{
    "mechanics.Base": "demonstration type: its internal call IS the fact " +
        "that the lesson measures. It exists only to be embedded wrongly.",
    "before.Base": "demonstration type: package before shows the flaw, " +
        "it does not fix it. Its replacement is export.Export, which is " +
        "a function and embeds nothing.",
    "sync.Mutex": "standard library type, not parsable by this " +
        "survey. It is embedded by leak.EmbeddedCache, which is itself " +
        "also a demonstration type, and its fix names the field.",
}
```

```
9 types incorpores dans 9 structs
before.Base             3 appel(s) internal(s), derogation : type de demonstration...
mechanics.Base         1 appel(s) internal(s), derogation : type de demonstration...
sync.Mutex             non analysable, derogation : type de la bibliotheque standard...
```

Trois dérogations, trois raisons écrites. Et une clause **NON GARANTI** dans
la documentation du test : le sondage ne voit que les appels de la forme
`récepteur.Méthode()`. Un appel indirect — par une valeur de fonction, par une
interface — lui échappe.

### Ce que le sondage m'a appris sur lui-même

Deux fois, et les deux valent plus que le sondage.

**Il confondait les homonymes.** Sa première version identifiait les types par
leur **nom court**, donc `mechanics.Base` et `before.Base` étaient le même
type. Le rapport paraissait juste — parce que les deux étaient dérogés. Une
erreur masquée par une coïncidence.

> Un sondage qui identifie les types par leur nom court confond les homonymes
> de paquets différents, et il le fait en silence.

**Il manquait son propre test négatif.** Une modification de la campagne —
retirer la comparaison du nom du récepteur — a **survécu**. Elle faisait
compter `self.header(...)` comme un appel interne, et aucun test ne s'en
apercevait, parce que le seul type concerné était dérogé.

```go
// TestACallOnAnotherIdentifierIsNotAnInternalCall pins the fix
// of the survey, and it was missing.
//
// before.Base has two methods that assemble a statement. Export calls
// b.header(...) on its RECEIVER: it is an internal call, and the survey
// must see it. ExportWithSelf calls self.header(...) on an ARGUMENT:
// it is not an internal call, and the survey must not see it.
//
// Without this test, a change of the campaign survived: removing the
// comparison of the receiver's name made calls on self count as
// internal calls, and no test noticed, because the only
// type concerned was waived.
//
//    A survey that watches others needs its own tests, and
//    in particular a test of what it must NOT find.
func TestACallOnAnotherIdentifierIsNotAnInternalCall(t *testing.T) {
    calls, err := survey.InternalCalls(root)
    if err != nil {
        t.Fatal(err)
    }
    internal, onSelf := 0, 0
    for _, a := range calls {
        if a.Type != "before.Base" {
            continue
        }
        switch a.Since {
        case "Export":
            internal++
        case "ExportWithSelf":
            onSelf++
        }
    }
    if internal != 3 {
        t.Errorf("%d internal calls from Export, want 3", internal)
    }
    if onSelf != 0 {
        t.Errorf("%d calls counted from ExportWithSelf, want 0:"+
            " the survey mistakes the receiver for an argument", onSelf)
    }
    t.Logf("Export: %d internal calls; ExportWithSelf: %d", internal, onSelf)
}
```

```
Export : 3 appels internes ; ExportWithSelf : 0
```

> Un sondage qui surveille les autres a besoin de ses propres tests, et
> notamment du test de ce qu'il ne doit **pas** trouver.

## 5. Ce que ça donne, et ce que ça coûte

### Quand l'incorporation est le bon outil

Elle l'est souvent, et la leçon n'est pas « n'incorpore jamais ». Trois cas où
elle est exactement ce qu'il faut :

| Cas | Pourquoi c'est sûr |
|---|---|
| **état partagé sans surcharge** — un champ `base` que trois types se partagent, dont personne ne remplace les méthodes | le critère est satisfait : aucun appel interne à surcharger |
| **composition d'interfaces** — `type ReadWriter interface { Reader; Writer }` | une interface n'a pas de corps, donc pas d'appel interne possible |
| **décoration** — une enveloppe qui transfère tout et remplace une méthode que rien n'appelle en interne | le critère, encore |

Et le troisième cas a une variante qu'on rencontre tous les jours : une
enveloppe d'interface qui surcharge **une** méthode. `registre.Connecteur`, de
la correction 2.2/4, est exactement ça : trois interfaces incorporées pour
n'en faire qu'une, sans un seul corps de méthode.

### Le coût de la correction, compté

| | Avant | Après |
|---|---|---|
| lignes du squelette | 22 (méthode) | 22 (fonction) |
| types à déclarer | 1 `Base` + 3 sous-types | 0 + 3 formateurs |
| le paquet `survey` | — | **216 lignes** de `go/ast` |
| le test du critère | — | **273 lignes** |
| ce que le compilateur vérifie | que `Base` existe | que le formateur **est** un formateur |

Les 489 lignes de sondage et de test sont le vrai coût, et il faut être
honnête sur ce qu'elles achètent : **elles n'achètent rien pour ce
module-là**. Le module est correct sans elles. Elles achètent la garantie que
le prochain développeur ne réintroduise pas le défaut — et elles ne la
rendent que si quelqu'un lit leur rapport.

> Un sondage qui lit la source est le dernier recours, pas le premier. Avant
> lui il y a le critère, qui tient en une phrase, et qui s'applique en
> relecture pour zéro ligne de code.

### Quand ne rien faire est la bonne réponse

- **Un seul format, pour toujours.** Pas d'interface, pas de squelette : une
  fonction qui écrit le texte. Et si le deuxième format arrive, tu auras le
  premier sous les yeux pour extraire l'interface.
- **Le type incorporé n'a qu'une méthode et personne ne la surcharge.**
  L'incorporation est gratuite et correcte.
- **Le programme a six mois à vivre.** Les 489 lignes ne seront jamais
  amorties.

## 6. Les trois erreurs qui restent

### L'incorporation qui exporte ce qu'on ne voulait pas

C'est l'erreur la plus fréquente, et elle est dans la section 7 parce qu'elle
produit un incident. Résumé : incorporer `sync.Mutex` exporte `Lock`,
`Unlock` **et `TryLock`**, et le chiffre n'est pas celui qu'on croit.

### L'enveloppe qui s'appelle elle-même

```
func (e Wrapper) Format(s string) string {
    return e.Prefix + e.Format(s)   // recursion infinie
}
```

La méthode surchargée porte le même nom que celle de l'interface incorporée.
`e.Format` se résout vers la méthode de l'enveloppe, pas vers celle du
champ. Il faut écrire `e.Formatter.Format(s)`, et c'est ce que fait le
FAIT 4.

Le signe : une pile d'appel de dix mille lignes identiques, et un
`stack overflow` au lieu d'un résultat.

### L'incorporation comme raccourci de nommage

```
type Service struct {
    *sql.DB            // pour ecrire s.Query(...) au lieu de s.db.Query(...)
    *redis.Client
    *log.Logger
}
```

Trois caractères économisés par appel, et en échange : toutes les méthodes des
trois types exportées par `Service`, un risque d'ambiguïté à chaque mise à
jour, et un `Service` qui satisfait `io.Closer` — donc que n'importe quel
code générique fermera.

> L'incorporation n'est pas un raccourci de nommage. Elle a un **prix
> d'interface publique**, et ce prix se paie à chaque mise à jour des types
> incorporés.

## 7. Le lien avec la production

Deux incidents, et les deux viennent de la **promotion** — pas du dispatch.

### Incident 1 — le cache bloqué par un verrou posé ailleurs

```go
// EmbeddedCache is the cache as one writes it by instinct.
// It embeds sync.Mutex, which is the most widespread idiom of the
// standard library. And so it exposes TWO more public methods
// than its author declared: Lock and Unlock.
//
// Consequence: any caller can lock the internal mutex of
// this cache from outside. And the day it does and forgets to
// unlock, the cache is dead for the whole process, with a call
// stack that will never show this package.
type EmbeddedCache struct {
    sync.Mutex
    entries map[string]string
}
```

```go
// NamedCache is the fix, and it fits in one field name.
// The mutex becomes a named, private field. The Lock and Unlock methods are
// no longer promoted, so they are no longer exported, so the state "an outside caller
// outside locks this cache's mutex" can no longer be represented.
//
// The cost is one word: "mu sync.Mutex" instead of "sync.Mutex".
type NamedCache struct {
    mu      sync.Mutex
    entries map[string]string
}
```

La mesure d'abord, parce qu'elle ne donne pas le chiffre attendu :

```go
// TestTheEmbeddedMutexExportsThreeMethodsTooMany is the MEASURE of the leak.
// I had written "two methods too many" (Lock and Unlock), and the test
// answered THREE. The third is TryLock, added to sync.Mutex by Go 1.18.
//
//    We do not know how many methods we export when we embed a
//    type one does not own: its method set can grow. A cache
//    written before Go 1.18 gained a public method when updating
//    the toolchain, without a line of its code changing.
//
// It is the same mechanism as the incident of package incident, with the
// standard library in the role of the third-party library.
func TestTheEmbeddedMutexExportsThreeMethodsTooMany(t *testing.T) {
    embedded := exportedMethods(reflect.TypeOf(leak.NewEmbeddedCache()))
    named := exportedMethods(reflect.TypeOf(leak.NewNamedCache()))

    t.Logf("EmbeddedCache: %d exported methods %v", len(embedded), embedded)
    t.Logf("NamedCache   : %d exported methods %v", len(named), named)

    if len(embedded)-len(named) != 3 {
        t.Fatalf("gap of %d methods, want 3 (Lock, TryLock and Unlock)."+
            " If the gap changes, sync.Mutex gained or lost a"+
            " method, and that is precisely the point of the test",
            len(embedded)-len(named))
    }
    for _, wanted := range []string{"Lock", "TryLock", "Unlock"} {
        if !contains(embedded, wanted) {
            t.Errorf("%s is not exported by EmbeddedCache", wanted)
        }
        if contains(named, wanted) {
            t.Errorf("%s is still exported by NamedCache", wanted)
        }
    }
}
```

```
EmbeddedCache : 5 methodes exportees [Read Lock Put TryLock Unlock]
NamedCache     : 2 methodes exportees [Read Put]
```

J'avais écrit « deux méthodes de trop » — `Lock` et `Unlock`. Le test a
répondu **trois**. La troisième est `TryLock`, ajoutée à `sync.Mutex` par
Go 1.18.

> On ne sait pas combien de méthodes on exporte quand on incorpore un type
> qu'on ne possède pas : **son jeu de méthodes peut grandir**. Un cache écrit
> avant Go 1.18 a gagné une méthode publique à la mise à jour de la chaîne
> d'outils, sans qu'une ligne de son code change.

Et l'incident lui-même, reproduit :

```go
// TestAnOutsideCallerCanBlockTheEmbeddedCache reproduces the incident.
// A caller locks the promoted mutex from outside the package and
// forgets to unlock. The cache is then dead for the whole process, and
// the blocking call stack will never show package leak.
//
// The test uses a timeout because a real deadlock blocks
// forever, and a test that blocks forever is not a test.
func TestAnOutsideCallerCanBlockTheEmbeddedCache(t *testing.T) {
    c := leak.NewEmbeddedCache()
    c.Put("cle", "value")

    // The cache answers normally.
    if err := leak.TryWithTimeout(func() error {
        _, err := c.Read("cle")
        return err
    }, 200*time.Millisecond); err != nil {
        t.Fatalf("normal read: %v", err)
    }

    // An outside caller locks, and forgets to unlock.
    c.Lock()
    err := leak.TryWithTimeout(func() error {
        _, err := c.Read("cle")
        return err
    }, 200*time.Millisecond)
    if !errors.Is(err, leak.ErrDeadlock) {
        t.Fatalf("want a deadlock, got %v", err)
    }
    t.Log("the cache is blocked by a lock taken outside the package that declares it")
    c.Unlock()

    // And it starts again.
    if err := leak.TryWithTimeout(func() error {
        _, err := c.Read("cle")
        return err
    }, 200*time.Millisecond); err != nil {
        t.Fatalf("after unlocking: %v", err)
    }
}
```

```
the cache is blocked by a lock taken outside the package that declares it
```

Un appelant extérieur verrouille le mutex promu et oublie de déverrouiller. Le
cache est mort pour tout le processus, et la pile d'appel du blocage ne
montrera **jamais** le paquet qui déclare le cache. Le temps de diagnostic
d'un incident comme celui-là se compte en heures.

La correction tient en un mot : `mu sync.Mutex` au lieu de `sync.Mutex`. Un
champ nommé ne promeut rien, donc `Lock` n'est plus exportée, donc l'état
« un appelant extérieur verrouille le mutex de ce cache » n'est plus
représentable — et un programme qui l'essaie ne compile pas :

```
./main.go:15:28: leak.NewNamedCache().Lock undefined
    (type *leak.NamedCache has no field or method Lock)
```

### Incident 2 — l'API qui a arrêté d'envoyer la moitié de ses champs

Celui-là est le plus coûteux, parce qu'il est **silencieux et à distance**.

Une API expose des événements en JSON. Le type `Event` incorpore un
`Timestamp` fourni par une bibliothèque interne. Un jour, l'auteur de cette
bibliothèque ajoute trois lignes :

```go
// --- AFTER the update ---

// TimestampV2 is the same type, plus one method.
//
// The addition is reasonable, and the library's author did well: they
// wanted its timestamp to serialize as RFC 3339 rather than as an object. It
// published it as a minor version, because it removes nothing and changes
// no signature.
type TimestampV2 struct {
    Instant time.Time `json:"instant"`
}

// MarshalJSON is the added method. Three lines.
func (h TimestampV2) MarshalJSON() ([]byte, error) {
    return []byte(`"` + h.Instant.UTC().Format(time.RFC3339) + `"`), nil
}

// EventV2 is the SAME code as EventV1. Not one line changed.
//
// And its JSON is no longer an object: it is the string returned by
// TimestampV2.MarshalJSON. Type and Ref are gone.
//
// The reason is promotion: MarshalJSON is promoted to the level
// of EventV2, so EventV2 satisfies json.Marshaler, so
// encoding/json no longer inspects its fields and calls the method.
type EventV2 struct {
    TimestampV2
    Type string `json:"type"`
    Ref  string `json:"ref"`
}
```

L'ajout est raisonnable. Il voulait que son horodatage se sérialise en
RFC 3339 plutôt qu'en objet. Il a publié ça en **version mineure**, parce que
ça n'enlève rien et ne change aucune signature.

Et voilà ce que l'API envoie, avant et après — sans qu'une ligne de son code
change :

```
avant : {"instant":"2026-03-01T08:00:00Z","type":"PAIEMENT","ref":"R-1"}
apres : "2026-03-01T08:00:00Z"
```

**`type` et `ref` ont disparu.** Le JSON n'est même plus un objet.

Le mécanisme est la promotion : `MarshalJSON` est promue au niveau
d'`Event`, donc `Event` satisfait `json.Marshaler`, donc
`encoding/json` n'inspecte plus ses champs et appelle la méthode.

> Une méthode promue fait satisfaire au type englobant une interface que
> personne n'a voulue. Et quand cette interface est un point d'extension de la
> bibliothèque standard, le comportement du type change **entièrement**.

La correction tient, encore, en un nom de champ :

```go
// --- The fix ---

// EventV3 is the fix, and it fits in one field name.
//
// The timestamp becomes a NAMED field. Its MarshalJSON method is no longer
// promoted, so EventV3 does not satisfy json.Marshaler, so
// encoding/json inspects its fields as before.
//
// Cost: one word, and a json tag to keep the same output shape.
type EventV3 struct {
    Timestamp TimestampV2 `json:"timestamp"`
    Type      string      `json:"type"`
    Ref       string      `json:"ref"`
}
```

```
corrige : {"timestamp":"2026-03-01T08:00:00Z","type":"PAIEMENT","ref":"R-1"}
```

### Le garde-fou, et pourquoi les tests habituels ne l'attrapent pas

Un test qui compare le JSON produit à un JSON attendu écrit à la main **ne
voit rien**, parce que le développeur qui casse la forme met à jour l'attendu
dans le même commit. C'est le mode de panne de tout test écrit comme un
instantané.

Ce qu'il faut est un test qui ne connaît pas la forme, mais **le contrat** :
la liste des champs que l'API promet.

```go
// CheckFields is the generic safeguard: it says whether a serialization
// contains all the expected fields.
//
// It exists because the whole class of this bug is invisible to
// compilation AND to tests that compare a JSON with an expected JSON written by
// hand: those are updated by the developer who breaks the shape.
func CheckFields(raw []byte, wanted ...string) error {
    var missing []string
    for _, field := range wanted {
        if !containsKey(raw, field) {
            missing = append(missing, field)
        }
    }
    if len(missing) > 0 {
        return fmt.Errorf("%w: %v missing from %s", ErrLostFields, missing, raw)
    }
    return nil
}

func containsKey(raw []byte, field string) bool {
    return strings.Contains(string(raw), `"`+field+`":`)
}
```

```
champs perdus : incident : champs perdus a la serialisation :
                [instant type ref] absents de "2026-03-01T08:00:00Z"
```

> Un test d'instantané est mis à jour par celui qui casse le contrat. Un test
> qui énumère les **engagements** ne l'est pas, parce qu'il faudrait retirer
> un engagement — et retirer un engagement se voit en revue.

Dix-huit modifications, dix paquets de test.

`&lt;` littéralement chez le destinataire. C'est le même genre de
non-commutativité que l'ordre des normalisations de la correction 2.2/1.

## 8. Ce qu'il faut retenir

1. **L'héritage accorde trois choses** — réutilisation, sous-typage,
   spécialisation ouverte — et on n'en voulait presque jamais les trois.
2. **Go les a séparées** : incorporation pour la première, interface pour la
   deuxième, **rien** pour la troisième.
3. **L'incorporation est un champ**, dont le nom est le nom de son type. Il
   est atteignable, et il se remplace en entier.
4. **Il n'y a pas de dispatch virtuel.** `Derived{}.Greet()` rend « bonjour
   base », et le rendra toujours. La surcharge existe ; personne à l'intérieur
   du type incorporé ne la verra.
5. **Le patron de la méthode-modèle ne marche pas** avec l'incorporation. Il
   compile, et il produit le format par défaut pour tout le monde.
6. **Le critère** : un type est sûr à incorporer-et-surcharger si et seulement
   si aucune de ses méthodes n'appelle une autre de ses méthodes sur son
   propre récepteur.
7. **La correction est de transformer la méthode-squelette en fonction.** Le
   corps ne change pas ; le formateur devient un argument que le compilateur
   vérifie.
8. **Si tu passes déjà l'interface en argument, l'incorporation n'apporte
   plus rien.**
9. **L'ambiguïté se déclare mais ne s'utilise pas** — et une bibliothèque qui
   ajoute une méthode peut casser ton code à un endroit que tu n'as pas écrit.
10. **Une interface incorporée nulle panique**, parce que `nil` est une valeur
    valide d'un type interface. Un constructeur ferme le chemin qu'on emprunte.
11. **L'incorporation a un prix d'interface publique.** Incorporer
    `sync.Mutex` exporte trois méthodes, pas deux, et le nombre peut grandir
    à la prochaine mise à jour du langage.
12. **Une méthode promue fait satisfaire une interface que personne n'a
    voulue.** Avec `json.Marshaler`, les champs du type englobant disparaissent
    de la sérialisation.
13. **Un champ nommé ne promeut rien.** La différence entre `sync.Mutex` et
    `mu sync.Mutex` est un mot, et c'est toute la différence.
14. **Un test d'instantané est mis à jour par celui qui casse le contrat.**
    Un test qui énumère les engagements ne l'est pas.
15. **Un sondage qui surveille les autres a besoin de ses propres tests**, et
    notamment du test de ce qu'il ne doit pas trouver.

## 9. Approfondissement

### Pourquoi Go a tranché comme ça, et ce que ça a coûté

Les auteurs de Go ont écarté l'héritage explicitement, et leur argument tient
en une observation : **une hiérarchie de classes mélange deux graphes
différents**. Celui de la réutilisation de code, et celui de la
substituabilité. Dans un langage à héritage simple, les deux sont le même
graphe, et il faut choisir lequel on optimise.

Ce que la décision a rapporté :

- les interfaces sont **satisfaites structurellement**, donc on peut en
  déclarer une pour un type qu'on ne possède pas, après coup. C'est ce qui
  rend possible « l'interface déclarée chez l'appelant » de la leçon 2.2, et
  aucun langage à sous-typage nominal ne le permet ;
- il n'y a **pas de hiérarchie à concevoir**, donc pas de refonte de
  hiérarchie à faire quand le métier change de forme ;
- la question *« de laquelle des trois ai-je besoin ? »* est **forcée** : les
  trois mécanismes étant séparés, il faut en nommer un.

Ce que la décision a coûté :

- le patron de la méthode-modèle n'existe pas, et il est **remplaçable** — ce
  module le montre — mais il faut le savoir, et l'incorporation ressemble
  assez à l'héritage pour qu'on ne le sache qu'après l'avoir essayé ;
- il n'y a pas de `super`, donc une enveloppe qui veut « faire comme le
  délégué, plus une chose » doit nommer le délégué explicitement ;
- la promotion est **tout ou rien** : on ne peut pas incorporer un type et
  masquer une de ses méthodes. On nomme le champ, ou on les prend toutes.

### Les quatre formes de réutilisation, et quand chacune sert

| La forme | Ce qu'elle donne | Quand |
|---|---|---|
| **une fonction libre** | rien de plus que le code | par défaut, et c'est le cas le plus fréquent |
| **l'incorporation** | les méthodes, promues | état partagé que personne ne surcharge |
| **un champ nommé** | les méthodes, non promues | tout le reste — et c'est ce qu'il faut préférer |
| **une interface en argument** | le dispatch dynamique | quand le comportement doit varier |

La ligne qui manque dans la plupart des discussions est la troisième. Entre
« incorporer » et « réécrire », il y a **nommer le champ**, et c'est presque
toujours la bonne réponse. Elle coûte un mot par appel.

### La promotion traverse les niveaux, et ça se mesure

Une subtilité qu'il faut avoir vue : la promotion est **transitive**. Si `A`
incorpore `B` qui incorpore `C`, les méthodes de `C` sont appelables sur `A`.
Et la résolution se fait par **profondeur** : la méthode la moins profonde
gagne, sans ambiguïté.

Conséquence pratique : un type qui incorpore un type d'une bibliothèque hérite
de l'interface publique de **tout ce que cette bibliothèque incorpore**, y
compris ce qu'elle a incorporé dans une version mineure. Le compte des
méthodes exportées de la section 7 n'est donc pas une curiosité : c'est une
mesure à refaire à chaque mise à jour.

### Le cas de `context.Context` et des interfaces qu'on incorpore pour étendre

Un idiome qu'on voit souvent, et qui est correct :

```
type Journalise interface {
    io.Writer
    Niveau() string
}
```

Incorporer des interfaces dans une interface est la seule forme
d'incorporation qui n'a **aucun** des problèmes de cette leçon : pas de corps,
donc pas d'appel interne, donc pas de dispatch à espérer. L'ambiguïté reste
possible si deux interfaces déclarent la même méthode avec des signatures
différentes — et depuis Go 1.14 c'est accepté si les signatures sont
**identiques**, refusé sinon.

### Ce que cette leçon n'a pas traité

- **La substituabilité comme contrat**, et ce qui se passe quand une
  implémentation satisfait une signature sans satisfaire ses promesses. C'est
  Liskov, et c'est la leçon 2.4.
- **Quand une interface a trop de méthodes**, et pourquoi la taille est une
  propriété de l'appelant. La leçon 2.2 l'a observé ; la 2.5 en fait une règle.
- **Le patron décorateur**, qui est l'usage le plus légitime de
  l'incorporation d'interface, et qui a ses propres modes de panne — ils
  appartiennent au niveau 3.
- **Les génériques comme forme de réutilisation.** Ils n'ont pas été évoqués
  ici parce qu'ils ne répondent pas à la question : ils font varier le type,
  pas le comportement. La leçon 2.2 a posé la distinction.

## 10. Le réflexe à installer

Devant une incorporation que tu t'apprêtes à écrire, trois questions, dans cet
ordre :

> 1. **De laquelle des trois ai-je besoin ?**
>    La réutilisation → un champ, et probablement **nommé**.
>    Le sous-typage → une interface, déclarée chez l'appelant.
>    La spécialisation ouverte → elle n'existe pas. Passe l'interface en
>    argument, et transforme la méthode en fonction.
> 2. **Le type que j'incorpore appelle-t-il une de ses propres méthodes ?**
>    Oui → ne le surcharge pas. L'appel ne te verra jamais.
>    Non → l'incorporation est sûre, aujourd'hui, pour cette version.
> 3. **Combien de méthodes est-ce que j'exporte en plus ?**
>    Compte-les. Si la réponse n'est pas zéro et que tu ne les voulais pas,
>    **nomme le champ**. Ça coûte un mot par appel.

Et devant une incorporation qui existe déjà, un seul geste, qui prend une
minute :

> **Compte les méthodes exportées du type englobant, et barre celles qu'il a
> déclarées lui-même.** Ce qui reste est son interface publique accidentelle.
> Pour chacune, demande : *un appelant qui l'utilise aurait-il dû pouvoir ?*
> Et : *que se passe-t-il si la bibliothèque en ajoute une au prochain
> trimestre ?*
