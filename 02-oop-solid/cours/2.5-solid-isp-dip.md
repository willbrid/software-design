# Leçon 2.5 — SOLID : ISP, DIP

La leçon 2.4 s'est arrêtée sur une arithmétique : *le coût de LSP croît avec
la largeur de l'interface, et le nombre de ses implémentations multiplie ce
coût.* Les deux derniers principes de SOLID sont la réponse à cette phrase —
l'un sur la **largeur** des interfaces, l'autre sur leur **place**.

Même méthode que la leçon précédente :

> Prendre un principe, montrer que sa formulation courante **n'est pas
> mesurable**, en donner une qui l'est, et **la mesurer** — avec du code qui
> compile et une commande qu'on peut lancer.

| | Ce que le principe décide | Ce qui le vérifie |
|---|---|---|
| **ISP** | la **largeur** d'une interface | un **sondage** des appels, puis un **diff** : on change une méthode et on compte les paquets qui cassent sans l'appeler |
| **DIP** | le **sens des flèches** d'importation | le **graphe** que rend `go list`, et un test qui le relit à chaque exécution |

Tout ce qui suit est mesuré sur un module en trois instantanés du même code
bancaire — `avant`, `isp`, `dip` —, plus un sondage et un test
d'architecture, verts sous `gofmt -l`, `go vet ./...` et `go test -race
-count=1 ./...`.

## 1. Les deux énoncés, et les deux reformulations

### ISP — Interface Segregation Principle

L'énoncé courant :

> *« Aucun client ne doit être forcé de dépendre de méthodes qu'il
> n'utilise pas. »*

« Dépendre » n'est pas défini, et c'est tout le problème. Un paquet qui reçoit
une interface de neuf méthodes et en appelle deux, en « dépend-il » des sept
autres ? Il ne les appelle pas ; son code ne les nomme pas. On peut répondre
non, et l'énoncé n'a plus d'objet.

La reformulation qui se mesure :

> **Quand une méthode change, aucun paquet qui ne l'appelle pas ne doit
> cesser de compiler.**

Elle donne deux mesures. Une **matrice d'usage** — pour chaque consommateur,
les méthodes qu'il appelle vraiment —, qu'un sondage lit dans le code. Et un
**diff** : on change une méthode, on compte les paquets qui cassent, et on
regarde lesquels l'appelaient.

### DIP — Dependency Inversion Principle

L'énoncé courant :

> *« Les modules de haut niveau ne doivent pas dépendre des modules de bas
> niveau. Les deux doivent dépendre d'abstractions. »*

« Haut niveau », « bas niveau », « abstraction » : trois mots que deux
développeurs placeront différemment sur le même code. Et l'énoncé laisse
croire qu'il suffit d'ajouter une interface — alors qu'une interface déclarée
au mauvais endroit ne change rien au sens des flèches, et la section 3 le
mesure.

La reformulation qui se mesure :

> **Le paquet qui porte les règles métier compile, se teste et se lit sans
> que l'infrastructure soit dans ses dépendances — ni directement, ni
> transitivement.**

`go list -deps` la vérifie en une commande. Et un test qui la relance à
chaque exécution est le **compilateur de l'axe des importations** : Go refuse
un cycle, il ne refuse pas une flèche dans le mauvais sens.

## 2. ISP : mesurer la largeur

### Le sujet

Une banque. Un paquet `stockage` — l'infrastructure, avec une
implémentation en mémoire et une sur PostgreSQL — déclare son interface à côté
de ses implémentations, comme on le fait en venant de Java :

```go
// Depot est le port de stockage. Neuf methodes : tout ce que la base sait
// faire.
type Depot interface {
    Charger(id string) (Compte, error)
    Enregistrer(c Compte) error
    Verrouiller(id string) (func(), error)
    Mouvements(id string, depuis time.Time) ([]Mouvement, error)
    AjouterMouvement(m Mouvement) error
    Rechercher(titulaire string) ([]Compte, error)
    Exporter(w io.Writer, jour time.Time) error
    Compter() (int, error)
    Encours() (int64, error)
}
```

Quatre consommateurs la reçoivent : le **virement**, le **relevé**,
l'**export** comptable, le **tableau** de bord. Chacun prend un
`stockage.Depot`.

### Le sondage

Il lit la syntaxe, comme celui de la leçon 2.4 : pour chaque paquet, il trouve
les paramètres et les champs dont le type est écrit `stockage.Depot`, puis les
appels de méthodes sur eux.

```go
// appels rend les methodes appelees, dans les fichiers d'un paquet, sur un
// parametre ou un champ de type pkg.nom.
func appels(fs []*ast.File, chemin, nom string) map[string]bool {
    vus := map[string]bool{}
    champs := map[string]bool{}
    for _, f := range fs {
        a := alias(f, chemin)
        if a == "" {
            continue
        }
        ast.Inspect(f, func(n ast.Node) bool {
            if st, ok := n.(*ast.StructType); ok {
                for _, c := range st.Fields.List {
                    if estLeType(c.Type, a, nom) {
                        for _, nm := range c.Names {
                            champs[nm.Name] = true
                        }
                    }
                }
            }
            return true
        })
    }
    for _, f := range fs {
        a := alias(f, chemin)
        if a == "" {
            continue
        }
        for _, d := range f.Decls {
            fn, ok := d.(*ast.FuncDecl)
            if !ok || fn.Body == nil {
                continue
            }
            params := map[string]bool{}
            for _, p := range fn.Type.Params.List {
                if estLeType(p.Type, a, nom) {
                    for _, nm := range p.Names {
                        params[nm.Name] = true
                    }
                }
            }
            ast.Inspect(fn.Body, func(n ast.Node) bool {
                call, ok := n.(*ast.CallExpr)
                if !ok {
                    return true
                }
                sel, ok := call.Fun.(*ast.SelectorExpr)
                if !ok {
                    return true
                }
                switch x := sel.X.(type) {
                case *ast.Ident:
                    if params[x.Name] {
                        vus[sel.Sel.Name] = true
                    }
                case *ast.SelectorExpr:
                    if champs[x.Sel.Name] {
                        vus[sel.Sel.Name] = true
                    }
                }
                return true
            })
        }
    }
    return vus
}
```

La matrice d'usage :

```
export    1/9  [Exporter]
releve    2/9  [Charger Mouvements]
tableau   2/9  [Compter Encours]
virement  4/9  [AjouterMouvement Charger Enregistrer Verrouiller]
aucun consommateur : [Rechercher]
```

Quatre consommateurs, neuf méthodes : **36 cases, 9 remplies**. Aucun
consommateur n'utilise plus de la moitié de l'interface, et une méthode,
`Rechercher`, n'est appelée par personne — elle existe parce que la base sait
le faire, pas parce que quelqu'un l'a demandé. C'est la première chose qu'un
sondage d'usage apprend sur une interface déclarée par son producteur :
**elle décrit ce que l'implémentation sait faire, pas ce dont les
consommateurs ont besoin.**

### Ce que le sondage ne voit pas

Il voit `d.Charger(…)` et `s.depot.Charger(…)`. Il ne voit pas une valeur
recopiée dans une autre variable, une méthode prise comme valeur, ni une
interface passée à une autre fonction. Le test négatif le fige :

```go
// TestCeQueLeSondageNeVoitPas : le test negatif. Trois appels reels, zero vu.
// Le jour ou ce test echoue, le sondage a appris quelque chose, et la lecon
// doit le dire.
func TestCeQueLeSondageNeVoitPas(t *testing.T) {
    vus := appels(mustFichiers(t, "testdata/piege"), chemin, "Depot")
    if len(vus) != 0 {
        t.Fatalf("le sondage voit maintenant %v", vus)
    }
}
```

Les trois appels du fichier piégé sont réels ; le sondage en voit zéro. Son
erreur est donc toujours dans le même sens : il **sous-estime** l'usage. Une
méthode qu'il déclare inutilisée doit être vérifiée à la main avant d'être
supprimée ; une méthode qu'il déclare utilisée l'est.

### Mesure A : une méthode change, qui casse ?

Le relevé comptable demande un `context.Context` sur `Exporter`, pour
annuler un export trop long. On change la signature **dans `stockage`
seulement**, et on compte.

```

   avant/export/export.go:13:23: not enough arguments in call to d.Exporter
   avant/releve/releve_test.go:29:19: cannot use doublure{} (value of struct type doublure) as stockage.Depot value in argument to Releve: doublure does not implement stockage.Depot (wrong type for method Exporter)

   avant/virement/virement_test.go:50:20: cannot use d (variable of type *doublure) as stockage.Depot value in argument to Nouveau: *doublure does not implement stockage.Depot (wrong type for method Exporter)
```

Six paquets. `export` appelle `Exporter`, c'est normal. `montage` importe
`export`, c'est la conséquence. Mais **`releve`, `tableau` et `virement`
n'appellent pas `Exporter`** — la matrice le dit —, et ils cassent quand même,
par leurs doublures de test. Trois paquets, trois équipes peut-être, qui
reçoivent une erreur de compilation pour une méthode qu'ils n'ont jamais
appelée. Le sixième, `replique`, est une implémentation de lecture qu'on
retrouvera à la mesure C : elle n'appelle `Exporter` que pour le transmettre,
parce que l'interface large l'oblige à l'avoir, et aucun de ses
consommateurs ne s'en sert.

C'est la mesure de l'énoncé d'ISP. *« Dépendre d'une méthode qu'on n'utilise
pas »*, ça veut dire ça : **casser quand elle change**.

### La correction : l'interface chez le consommateur

Chaque consommateur déclare ce dont il a besoin, chez lui :

```go
// Comptes est ce dont le virement a besoin. Quatre methodes, declarees ICI,
// chez celui qui les appelle. Le stockage n'en sait rien, et n'a pas besoin
// d'en savoir quelque chose : en Go, satisfaire une interface ne s'ecrit pas.
type Comptes interface {
    Verrouiller(id string) (func(), error)
    Charger(id string) (stockage.Compte, error)
    Enregistrer(c stockage.Compte) error
    AjouterMouvement(m stockage.Mouvement) error
}

type Service struct{ depot Comptes }

func Nouveau(d Comptes) Service { return Service{depot: d} }
```

```go
// Package export produit le journal comptable du jour.
package export

import (
    "io"
    "time"
)

// Exportateur est ce dont l'export a besoin. Il n'importe plus stockage du
// tout : sa seule methode ne parle que de types de la bibliotheque standard.
type Exportateur interface {
    Exporter(w io.Writer, jour time.Time) error
}

// Journal ecrit le journal du jour dans w.
func Journal(d Exportateur, w io.Writer, jour time.Time) error {
    return d.Exporter(w, jour)
}
```

L'export n'importe même plus `stockage` : sa seule méthode ne parle que de
types de la bibliothèque standard.

Et voici le chiffre qui rend ISP presque gratuit en Go :

```
$ diff -r avant/stockage isp/stockage
$
```

**Zéro ligne modifiée dans l'implémentation.** En Go, satisfaire une interface
ne s'écrit pas : `*stockage.Memoire` satisfait `virement.Comptes` sans le
savoir. En Java, la même coupe oblige chaque implémentation à déclarer les
interfaces qu'elle implémente — l'implémentation doit connaître ses
consommateurs, ce qui est exactement la dépendance qu'on voulait éviter. Go a
tranché pour l'inverse, et c'est la conséquence la plus utile de la
satisfaction implicite.

La même mesure A, sur l'instantané `isp` :

```
== isp : 1 paquet(s) casse(s) : montage
   isp/montage/montage.go:29:80: cannot use d (variable of interface type stockage.Depot) as export.Exportateur value in argument to export.Journal: stockage.Depot does not implement export.Exportateur (wrong type for method Exporter)
```

Un paquet, et c'est le bon : la **racine de composition**, le seul endroit
qui connaît à la fois l'implémentation et le consommateur, et l'erreur nomme
exactement le désaccord. Aucun paquet qui n'appelle pas `Exporter` n'a cassé.

| | avant | isp |
|---|---|---|
| paquets qui cassent | 6 | **1** |
| dont paquets qui n'appellent pas `Exporter` | **3** — et la réplique, qui ne l'a que pour satisfaire l'interface | **0** |
| où l'erreur est signalée | dans les doublures de trois consommateurs, et dans la réplique | dans la racine de composition |

Ce n'est pas un hasard que l'erreur se déplace là. La racine de composition
est câblée **une fois**, pour les quatre consommateurs :

```go
// Assembler branche les quatre consommateurs sur un depot.
func Assembler(d stockage.Depot) Application {
    return Application{
        Virement:    virement.Nouveau(d),
        Releve:      func(id string, depuis time.Time) (string, error) { return releve.Releve(d, id, depuis) },
        Journal:     func(w io.Writer, jour time.Time) error { return export.Journal(d, w, jour) },
        Indicateurs: func() (string, error) { return tableau.Indicateurs(d) },
    }
}
```

Sans elle, rien ne vérifierait jamais que `stockage` satisfait encore
`export.Exportateur` — chaque paquet compilerait seul, et le désaccord
attendrait l'exécution. **Avec des interfaces côté consommateur, c'est la
racine de composition qui joue le rôle de vérification.** Elle doit exister,
et elle doit câbler tout le monde.

### Mesure B : ce que coûtent les doublures

Chaque test de consommateur a besoin d'une doublure. Avec l'interface large,
une doublure doit avoir les neuf méthodes :

```go
package tableau

import (
    "io"
    "testing"
    "time"

    "exemple/l25/avant/stockage"
)

type doublure struct{}

func (doublure) Compter() (int, error)                                      { return 2, nil }
func (doublure) Encours() (int64, error)                                    { return 1000, nil }
func (doublure) Charger(string) (stockage.Compte, error)                    { panic("non utilise") }
func (doublure) Enregistrer(stockage.Compte) error                          { panic("non utilise") }
func (doublure) Verrouiller(string) (func(), error)                         { panic("non utilise") }
func (doublure) Mouvements(string, time.Time) ([]stockage.Mouvement, error) { panic("non utilise") }
func (doublure) AjouterMouvement(stockage.Mouvement) error                  { panic("non utilise") }
func (doublure) Rechercher(string) ([]stockage.Compte, error)               { panic("non utilise") }
func (doublure) Exporter(io.Writer, time.Time) error                        { panic("non utilise") }

func TestIndicateurs(t *testing.T) {
    if s, err := Indicateurs(doublure{}); err != nil || s != "2 comptes, encours 1000" {
        t.Fatalf("%q, %v", s, err)
    }
}
```

Le tableau de bord appelle deux méthodes. Sa doublure en a neuf, dont sept
`panic("non utilise")` — et son fichier de test importe `io`, `time` et
`stockage` **uniquement pour écrire ces sept méthodes**. Après la coupe :

```go
package tableau

import "testing"

type doublure struct{}

func (doublure) Compter() (int, error)   { return 2, nil }
func (doublure) Encours() (int64, error) { return 1000, nil }

func TestIndicateurs(t *testing.T) {
    if s, err := Indicateurs(doublure{}); err != nil || s != "2 comptes, encours 1000" {
        t.Fatalf("%q, %v", s, err)
    }
}
```

| | avant | isp |
|---|---|---|
| méthodes de doublure, quatre consommateurs | 36 | **9** |
| dont `panic("non utilise")` | **27** | 0 |
| lignes des quatre fichiers de test | 145 | 105 |
| imports qui ne servaient qu'aux méthodes inutilisées | 6 | 0 |

Les 27 `panic` ne sont pas seulement du bruit. Ce sont 27 endroits où une
doublure **promet** une méthode qu'elle ne tient pas — 27 petites violations
de Liskov qu'on écrit pour faire plaisir au compilateur.

### Mesure C : la réplique, ou le lien avec LSP

Un jour arrive une réplique de lecture, pour soulager la base : le relevé et
le tableau de bord liront sur elle. Avec l'interface large, pour être passée au
relevé, elle doit être un `stockage.Depot` — **neuf méthodes, dont trois qui
écrivent** :

```go
// Replique lit depuis une source. Pour etre passee au releve et au tableau,
// qui prennent un stockage.Depot, elle doit avoir les NEUF methodes — y
// compris les trois qui ecrivent, et qu'elle ne peut que refuser.
type Replique struct{ source *stockage.Memoire }

func Nouvelle(source *stockage.Memoire) Replique { return Replique{source: source} }

func (r Replique) Charger(id string) (stockage.Compte, error) { return r.source.Charger(id) }
func (r Replique) Mouvements(id string, depuis time.Time) ([]stockage.Mouvement, error) {
    return r.source.Mouvements(id, depuis)
}
func (r Replique) Rechercher(t string) ([]stockage.Compte, error) { return r.source.Rechercher(t) }
func (r Replique) Exporter(w io.Writer, jour time.Time) error     { return r.source.Exporter(w, jour) }
func (r Replique) Compter() (int, error)                          { return r.source.Compter() }
func (r Replique) Encours() (int64, error)                        { return r.source.Encours() }
func (r Replique) Enregistrer(stockage.Compte) error              { return ErrLectureSeule }
func (r Replique) AjouterMouvement(stockage.Mouvement) error      { return ErrLectureSeule }
func (r Replique) Verrouiller(string) (func(), error)             { return nil, ErrLectureSeule }

var _ stockage.Depot = Replique{}
```

Elle ne peut que refuser les écritures. Passée à la batterie de `Depot` — une
clause par méthode, sur le modèle de la leçon 2.4 :

```
clause 2 : Enregistrer : replique : lecture seule
clause 3 : Verrouiller : replique : lecture seule
clause 5 : AjouterMouvement : replique : lecture seule
```

Trois clauses cassées sur neuf. Et le compilateur la laisse passer partout où
un `Depot` est attendu — y compris au virement, qui échoue **à l'exécution**,
au premier virement, avec `replique : lecture seule`.

> **Une interface trop large force la violation de Liskov.** Une
> implémentation qui ne peut honnêtement tenir qu'une partie du contrat n'a
> que deux choix : mentir (une méthode qui ne fait rien) ou refuser (une
> méthode qui rend une erreur que les autres ne rendent pas). Les deux cassent
> des clauses.

Avec les interfaces côté consommateur, la réplique a les quatre méthodes que
ses deux consommateurs appellent, et aucune autre :

```go
// Replique a les quatre methodes que le releve et le tableau appellent, et
// aucune autre.
type Replique struct{ source *stockage.Memoire }

func Nouvelle(source *stockage.Memoire) Replique { return Replique{source: source} }

func (r Replique) Charger(id string) (stockage.Compte, error) { return r.source.Charger(id) }
func (r Replique) Mouvements(id string, depuis time.Time) ([]stockage.Mouvement, error) {
    return r.source.Mouvements(id, depuis)
}
func (r Replique) Compter() (int, error)   { return r.source.Compter() }
func (r Replique) Encours() (int64, error) { return r.source.Encours() }
```

Elle tient les contrats de ses deux consommateurs — cinq clauses, zéro
cassée —, et la violation qui était possible est devenue une erreur de
compilation :

```go
// TestDonnerLaRepliqueAuVirementNeCompilePas : la violation de Liskov que
// l'interface large rendait possible est devenue une erreur de compilation.
func TestDonnerLaRepliqueAuVirementNeCompilePas(t *testing.T) {
    d, err := os.MkdirTemp(".", "_essai")
    if err != nil {
        t.Fatal(err)
    }
    t.Cleanup(func() { os.RemoveAll(d) })
    src := `package essai

import (
    "exemple/l25/isp/replique"
    "exemple/l25/isp/stockage"
    "exemple/l25/isp/virement"
)

var _ = virement.Nouveau(replique.Nouvelle(stockage.NouvelleMemoire()))
`
    if err := os.WriteFile(filepath.Join(d, "essai.go"), []byte(src), 0o644); err != nil {
        t.Fatal(err)
    }
    sortie, err := exec.Command("go", "build", "./"+d).CombinedOutput()
    if err == nil {
        t.Fatal("la replique a ete acceptee par le virement")
    }
    const attendu = "replique.Replique does not implement virement.Comptes (missing method AjouterMouvement)"
    if !strings.Contains(string(sortie), attendu) {
        t.Fatalf("echec pour une autre raison :\n%s", sortie)
    }
    t.Logf("%s", strings.TrimSpace(string(sortie)))
}
```

```
cannot use replique.Nouvelle(stockage.NouvelleMemoire()) (value of struct type replique.Replique) as virement.Comptes value in argument to virement.Nouveau: replique.Replique does not implement virement.Comptes (missing method AjouterMouvement)
```

C'est la phrase de la leçon 2.4, vérifiée : **ISP rend LSP abordable**. Il ne
diminue pas seulement la taille des batteries ; il supprime les clauses qu'une
implémentation ne pouvait pas tenir, en supprimant les méthodes qui les
portaient.

### Qui écrit la batterie d'une interface côté consommateur ?

Le consommateur. Il déclare ce dont il a besoin ; il dit aussi ce qu'il en
attend :

```go
// Jeu est ce que la batterie de Source demande. La batterie vit ICI, avec
// l'interface : celui qui declare ce dont il a besoin dit aussi ce qu'il en
// attend.
type Jeu struct {
    Nouveau   func() Source
    Alimenter func(s Source, cs []stockage.Compte, ms []stockage.Mouvement)
}

var jour = time.Date(2026, time.March, 2, 10, 0, 0, 0, time.UTC)

func pret(j Jeu) Source {
    s := j.Nouveau()
    j.Alimenter(s, []stockage.Compte{{ID: "A", Titulaire: "Awa", Solde: 1000}},
        []stockage.Mouvement{
            {Compte: "A", Date: jour.Add(-time.Hour), Montant: -50, Libelle: "frais"},
            {Compte: "A", Date: jour, Montant: -300, Libelle: "loyer"},
        })
    return s
}

// Verifier passe les trois clauses de Source.
func Verifier(j Jeu) []string {
    var out []string
    if c, err := pret(j).Charger("A"); err != nil || c.Solde != 1000 {
        out = append(out, fmt.Sprintf("clause 1 : Charger(A) = %+v, %v", c, err))
    }
    if _, err := pret(j).Charger("Z"); !errors.Is(err, stockage.ErrInconnu) {
        out = append(out, fmt.Sprintf("clause 2 : Charger(Z) : %v", err))
    }
    if ms, err := pret(j).Mouvements("A", jour); err != nil || len(ms) != 1 || ms[0].Libelle != "loyer" {
        out = append(out, fmt.Sprintf("clause 3 : Mouvements(A, depuis 10 h) = %v, %v", ms, err))
    }
    return out
}
```

C'est la conséquence logique, et elle a un coût qu'il faut dire : une
implémentation qui sert quatre consommateurs passe **quatre** batteries
petites au lieu d'une grande. Le total des clauses ne baisse pas forcément.
Ce qui baisse, c'est le nombre de clauses qu'une implémentation **partielle**
— la réplique — doit tenir sans pouvoir.

## 3. DIP : mesurer les flèches

### ISP ne suffit pas

L'instantané `isp` a des interfaces justes. Regardons ses flèches :

```
instantane paquet     database/sql ? stockage ? dependances
avant      virement   oui            oui        107
avant      releve     oui            oui        107
avant      export     oui            oui        107
avant      tableau    oui            oui        107
isp        virement   oui            oui        107
isp        releve     oui            oui        107
isp        export     non            non        45
isp        tableau    non            non        60
dip        virement   non            non        45
dip        releve     non            non        62
dip        export     non            non        45
dip        tableau    non            non        60
```

Dans `isp`, l'export et le tableau sont libérés — leurs interfaces ne parlent
que de types standards. Mais **le virement et le relevé tirent encore
`database/sql`**, et 107 paquets avec. Leur interface est déclarée chez eux,
mais elle parle de `stockage.Compte` et de `stockage.Mouvement` : pour nommer
un compte, le virement doit importer l'infrastructure.

> **Une interface déclarée au bon endroit ne suffit pas si les types qu'elle
> mentionne sont au mauvais endroit.** Le sens d'une flèche se décide sur
> tout ce que le paquet nomme, pas seulement sur ses interfaces.

### Le domaine

L'instantané `dip` déplace les types du métier dans un paquet qui n'importe
rien du module :

```go
// Package banque est le domaine : ce qu'est un compte et un mouvement, pour
// le metier. Il n'importe rien du module — et c'est la seule ligne de ce
// fichier qui compte.
package banque

import (
    "errors"
    "time"
)

var ErrInconnu = errors.New("banque : compte inconnu")

type Compte struct {
    ID        string
    Titulaire string
    Solde     int64
    Bloque    bool
}

type Mouvement struct {
    Compte  string
    Date    time.Time
    Montant int64
    Libelle string
}
```

Et l'infrastructure importe le domaine — la flèche s'inverse, c'est le nom du
principe :

```go
// Package stockage est l'infrastructure : il range les comptes et leurs
// mouvements. Il importe le domaine — la fleche va de l'infrastructure vers
// le metier, et plus l'inverse.
package stockage

import (
    "io"
    "time"

    "exemple/l25/dip/banque"
)

// Depot est le port de stockage. Neuf methodes : tout ce que la base sait
// faire.
type Depot interface {
    Charger(id string) (banque.Compte, error)
    Enregistrer(c banque.Compte) error
    Verrouiller(id string) (func(), error)
    Mouvements(id string, depuis time.Time) ([]banque.Mouvement, error)
    AjouterMouvement(m banque.Mouvement) error
    Rechercher(titulaire string) ([]banque.Compte, error)
    Exporter(w io.Writer, jour time.Time) error
    Compter() (int, error)
    Encours() (int64, error)
}
```

Le virement de `dip` n'importe plus que `banque`. Il compile, se teste et se
lit sans base de données : 45 dépendances au lieu de 107, et `database/sql`
n'en fait plus partie.

### La métrique qui certifie la violation

Robert Martin propose une mesure d'**instabilité** par paquet :
I = Ce / (Ca + Ce), où Ce compte les paquets qu'il importe et Ca ceux qui
l'importent. Un paquet à I = 0 est « stable » : tout le monde dépend de lui, il
ne dépend de personne. La règle associée — *dépendre dans le sens de la
stabilité* — est souvent présentée comme la forme mesurable de DIP.

Je l'ai calculée sur les deux instantanés, avec `go list`, en ne comptant que
les paquets du module :

```
== avant
   export     Ca=1 Ce=1 I=0.50   importe : stockage
   montage    Ca=0 Ce=5 I=1.00   importe : export, releve, stockage, tableau, virement
   releve     Ca=1 Ce=1 I=0.50   importe : stockage
   replique   Ca=0 Ce=1 I=1.00   importe : stockage
   stockage   Ca=6 Ce=0 I=0.00   importe : -
   tableau    Ca=1 Ce=1 I=0.50   importe : stockage
   virement   Ca=1 Ce=1 I=0.50   importe : stockage
== dip
   archi      Ca=0 Ce=0 I=  -    importe : -
   banque     Ca=4 Ce=0 I=0.00   importe : -
   export     Ca=1 Ce=0 I=0.00   importe : -
   montage    Ca=0 Ce=5 I=1.00   importe : export, releve, stockage, tableau, virement
   releve     Ca=1 Ce=1 I=0.50   importe : banque
   replique   Ca=0 Ce=2 I=1.00   importe : banque, stockage
   stockage   Ca=2 Ce=1 I=0.33   importe : banque
   tableau    Ca=1 Ce=0 I=0.00   importe : -
   virement   Ca=1 Ce=1 I=0.50   importe : banque
```

(`archi` ne contient que le test d'architecture : il n'importe ni n'est importé par aucun paquet du module, et I n'y est pas défini.)

Dans `avant`, **`stockage` a I = 0,00** : le paquet le plus « stable » du
module. Et toutes les flèches vont vers lui — la règle de stabilité est
**respectée**. La métrique certifie exactement la violation qu'on cherche.

Elle n'est pas fausse ; elle mesure autre chose que ce qu'on croit. I mesure
la **difficulté** de changer un paquet — combien d'autres il faut reprendre —,
pas la **probabilité** qu'il change. Un paquet d'infrastructure dont tout
dépend a I = 0 *parce que* tout en dépend, et il change quand même : un pilote
qui monte de version, un index, une migration de schéma. La métrique est
circulaire : un paquet devient « stable » parce qu'on a pris l'habitude d'en
dépendre.

> **La probabilité de changer ne se lit pas dans le code. Elle se lit dans
> l'historique.** La forme mesurable de DIP est : *les flèches vont du paquet
> qui change le plus souvent vers celui qui change le moins souvent* — et
> « le plus souvent » se compte avec `git log`.

```
git log --since=12.months --name-only --format= -- . \
  | grep . | xargs -n1 dirname | sort | uniq -c | sort -rn
```

Sur un vrai dépôt bancaire, le paquet qui porte le pilote de la base et le
paquet qui définit ce qu'est un compte ne sortent pas au même rang. C'est ce
rang, et pas I, qui dit dans quel sens la flèche doit aller.

### Le test d'architecture

Le compilateur de Go refuse un cycle d'importation. Il ne refuse pas une
flèche dans le mauvais sens : rien n'empêche demain le virement d'importer à
nouveau `stockage`. Il faut donc un test qui relise le graphe à chaque
exécution :

```go
const module = "exemple/l25/dip/"

// interdits dit, pour chaque paquet du metier, ce qu'il ne doit jamais
// tirer dans ses dependances — directement OU transitivement. C'est le
// compilateur de l'axe des importations : Go refuse un cycle, il ne refuse
// pas une fleche dans le mauvais sens.
var interdits = map[string][]string{
    "banque":   {module + "stockage", "database/sql", "net/http"},
    "virement": {module + "stockage", "database/sql", "net/http"},
    "releve":   {module + "stockage", "database/sql", "net/http"},
    "export":   {module + "stockage", "database/sql", "net/http"},
    "tableau":  {module + "stockage", "database/sql", "net/http"},
}

// violations rend ce que paquet tire parmi refus.
func violations(t *testing.T, paquet string, refus []string) []string {
    t.Helper()
    sortie, err := exec.Command("go", "list", "-deps", paquet).Output()
    if err != nil {
        t.Fatalf("go list %s : %v", paquet, err)
    }
    deps := map[string]bool{}
    for _, d := range strings.Fields(string(sortie)) {
        deps[d] = true
    }
    var out []string
    for _, r := range refus {
        if deps[r] {
            out = append(out, r)
        }
    }
    return out
}

func TestLesFlechesVontVersLeMetier(t *testing.T) {
    for paquet, refus := range interdits {
        for _, v := range violations(t, "../"+paquet, refus) {
            t.Errorf("%s depend de %s", paquet, v)
        }
    }
}

// TestLeTestVoitUneFlecheALEnvers : le test negatif. Le virement de l'instantane
// « avant » importe le stockage ; le test doit le dire.
func TestLeTestVoitUneFlecheALEnvers(t *testing.T) {
    got := violations(t, "../../avant/virement",
        []string{"exemple/l25/avant/stockage", "database/sql", "net/http"})
    if strings.Join(got, " ") != "exemple/l25/avant/stockage database/sql" {
        t.Fatalf("violations %v", got)
    }
}

// TestLaListeCouvreToutLeMetier : un paquet de metier ajoute sans etre inscrit
// ci-dessus echapperait au test. La liste est l'axe ouvert, et elle a son
// propre garde.
func TestLaListeCouvreToutLeMetier(t *testing.T) {
    sortie, err := exec.Command("go", "list", "../...").Output()
    if err != nil {
        t.Fatal(err)
    }
    infrastructure := map[string]bool{"stockage": true, "replique": true, "montage": true, "archi": true}
    for _, p := range strings.Fields(string(sortie)) {
        nom := strings.TrimPrefix(p, module)
        if !infrastructure[nom] && interdits[nom] == nil {
            t.Errorf("%s n'est ni de l'infrastructure, ni dans la liste du metier", nom)
        }
    }
}
```

Trois remarques sur ce test.

1. **Il vérifie les dépendances transitives**, avec `go list -deps`. Un
   paquet qui importe un intermédiaire qui importe `database/sql` viole la
   règle aussi sûrement qu'un import direct.
2. **Il a un test négatif.** Sans `TestLeTestVoitUneFlecheALEnvers`, la
   modification qui supprime la vérification — `if false && deps[r]` —
   survivait : le test n'avait jamais été vu en train de tirer. Il tire
   maintenant sur le virement de l'instantané `avant`, et c'est ce qui prouve
   qu'il sait tirer.
3. **La liste des paquets du métier est un axe ouvert**, avec son propre
   garde. Un paquet de métier ajouté sans être inscrit échapperait au test —
   c'est exactement la leçon 2.4 : *sur l'axe ouvert, un test sur la liste
   remplace le compilateur*.

## 4. Ce que ça donne, et ce que ça coûte

| | Ce qu'on gagne | Ce qu'on paye |
|---|---|---|
| **ISP** | une méthode change : **0** paquet qui ne l'appelle pas ne casse (contre 3, plus la réplique) ; 27 méthodes de doublure en moins ; une réplique partielle qui ne peut plus être donnée au virement | la même méthode est déclarée à plusieurs endroits ; une batterie par interface de consommateur ; la racine de composition devient le seul endroit qui vérifie la compatibilité |
| **DIP** | le métier compile et se teste sans l'infrastructure : 45 dépendances au lieu de 107, `database/sql` absent | un paquet de domaine de plus ; l'infrastructure parle les types du domaine, et chaque champ ajouté au domaine touche ses requêtes ; un test d'architecture à tenir |

Et une limite de chacun, à dire avant qu'on la découvre :

- **ISP côté consommateur ne protège pas la racine de composition.** Elle
  câble tout, donc elle casse à chaque changement — c'est son rôle. Une
  racine de composition qui ne câble pas tout le monde laisse des
  désaccords passer jusqu'à l'exécution.
- **DIP n'a de valeur que vers ce qui change moins souvent.** Inverser une
  dépendance vers `time`, `strings` ou `encoding/json` ne protège de rien : ces
  paquets ne changent pas, et une interface devant eux n'est qu'un détour. La
  question n'est jamais « est-ce une dépendance concrète ? », c'est « est-ce
  une dépendance **qui bouge** ? ».

## 5. Les trois erreurs qui restent

### « ISP veut dire des interfaces à une méthode »

Non. La matrice d'usage du virement est **quatre** méthodes, et elles vont
ensemble : verrouiller, charger, enregistrer, tracer. Les couper en quatre
interfaces d'une méthode donnerait un constructeur à quatre paramètres que
l'appelant remplirait avec le même objet quatre fois. Le critère n'est pas la
taille, c'est **l'usage** : une interface par groupe de méthodes que les
mêmes consommateurs appellent ensemble. `io.ReadWriter` existe parce que des
consommateurs lisent et écrivent sur la même chose.

### « DIP veut dire injection de dépendances »

Non. L'injection est une **technique** — passer ses dépendances par le
constructeur plutôt que de les fabriquer. DIP est une propriété du **graphe**.
On peut injecter un `*stockage.Postgres` concret dans le virement : c'est de
l'injection, et la flèche va du métier vers l'infrastructure. L'instantané
`isp` injecte une interface, et `virement` dépend encore de `database/sql`.
L'injection rend DIP possible ; elle ne le garantit pas. Seul `go list -deps`
le dit.

### « Il faut une interface devant chaque type »

Non, et c'est l'inverse de ce que mesure la section 2. Une interface déclarée
à côté de son implémentation, qui reprend ses méthodes une à une — l'interface
« en-tête », héritée de Java —, est exactement `stockage.Depot` : elle décrit
le producteur, elle est trop large pour chaque consommateur, et elle place
l'abstraction du côté du détail. En Go, **une interface naît chez celui qui
l'appelle**, au moment où il en a besoin — souvent au moment où arrive la
deuxième implémentation, ou le premier test.

## 6. Le lien avec la production

| Ce que tu as déjà vu en production | Le principe, et sa mesure |
|---|---|
| une méthode ajoutée au dépôt, et quatre équipes qui doivent reprendre leurs doublures dans la journée | ISP. La mesure A : compte les paquets qui cassent et qui n'appellent pas la méthode |
| des doublures de test pleines de `panic("not implemented")` | ISP. Chaque `panic` est une méthode que le consommateur n'appelle pas — et une promesse que la doublure ne tient pas |
| une réplique de lecture qui renvoie « read-only » au premier service qui essaie d'écrire | ISP et LSP ensemble. L'interface l'obligeait à avoir des méthodes d'écriture |
| un service métier dont les tests unitaires demandent une base PostgreSQL | DIP. `go list -deps ./metier/... \| grep database/sql` |
| une montée de version du pilote SQL qui recompile tout le dépôt | DIP. Le pilote est dans les dépendances transitives de paquets qui n'ont rien à faire de lui |
| un graphe d'architecture dessiné en 2022, que le code ne respecte plus | DIP sans test. Une règle de flèches qui n'est pas relue par un test n'est respectée que par chance |

Et la règle d'usage, celle qui vaut dans une revue :

> Devant une interface ajoutée, deux questions. **Qui l'appelle ?** — elle doit
> être déclarée chez lui. **Qu'est-ce qu'elle nomme ?** — chaque type de sa
> signature doit venir d'un paquet qui change moins souvent que celui qui
> l'appelle.

## 7. Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | ISP mesurable : **quand une méthode change, aucun paquet qui ne l'appelle pas ne doit cesser de compiler.** Mesuré : 3 paquets avant (plus une implémentation forcée de la porter), 0 après. |
| ⚫ | Un sondage d'usage donne la matrice consommateurs × méthodes. Ici, 36 cases, 9 remplies, et une méthode que personne n'appelle. Il sous-estime toujours, et son test négatif le dit. |
| ⚫ | Une interface déclarée par son producteur décrit ce qu'il sait faire, pas ce dont ses consommateurs ont besoin. |

| ⚫ | Avec des interfaces côté consommateur, la **racine de composition** est le seul endroit qui vérifie la compatibilité. Elle doit câbler tout le monde. |

## 8. Approfondissement

### Pourquoi `io.Reader` a une seule méthode

La bibliothèque standard est la meilleure démonstration d'ISP qui existe, et
elle n'a jamais cité le principe. `io.Reader`, `io.Writer`, `io.Closer` ont
une méthode chacune ; `io.ReadWriter`, `io.ReadCloser` les composent. Chaque
consommateur prend exactement ce qu'il appelle : `io.Copy` prend un `Writer`
et un `Reader`, pas un `*os.File`. Le résultat se mesure en implémentations :
des centaines de types satisfont `io.Reader` — fichiers, connexions, tampons,
décompresseurs, chiffreurs —, parce qu'une seule méthode est un contrat que
presque tout peut tenir.

La règle qu'on en tire : **plus une interface est étroite, plus elle a
d'implémentations possibles**, et plus chacune est facile à passer dans une
batterie. C'est le même calcul que la leçon 2.4, lu dans l'autre sens.

### Quand l'interface doit vivre chez le producteur

Il y a une exception, et la leçon 2.4 l'a nommée : les **sentinelles
d'erreur**, et plus largement le **vocabulaire** partagé. Quand plusieurs
consommateurs doivent parler de la même chose — `io.EOF`, `fs.ErrNotExist`,
`banque.ErrInconnu` —, ce vocabulaire ne peut pas être redéclaré chez chacun.
Il vit dans un paquet que tous importent, et ce paquet doit être **plus
stable** que tous ses consommateurs : c'est pourquoi `banque` n'importe rien.

L'autre cas est l'interface de **greffon** : un programme qui accepte des
implémentations écrites par d'autres, après coup — `database/sql/driver`,
`http.Handler`. L'interface y est déclarée par le consommateur aussi — c'est
`database/sql` qui déclare `driver.Driver`, pas les pilotes —, mais elle est
publiée pour être implémentée. Elle devient alors un contrat public, avec le
coût de tout contrat public : on ne la change plus.

### Le test d'architecture comme documentation

Le dessin d'architecture d'une équipe vieillit dès qu'il est exporté en PNG.
La table `interdits` du test, elle, ne peut pas mentir : si le code ne la
respecte plus, le test est rouge. C'est le meilleur endroit pour **écrire**
l'architecture — une ligne par règle, relue par la machine à chaque
exécution. Le schéma peut ensuite être généré à partir du graphe réel, au lieu
d'être dessiné à partir du graphe souhaité.

## 9. Le réflexe à installer

> **Devant une interface large** (ISP)
> Lance le sondage, ou fais-le à la main : pour chaque consommateur, quelles
> méthodes appelle-t-il ? S'il y a des groupes, chaque groupe devient une
> interface **chez son consommateur**. Puis vérifie que la racine de
> composition câble tout le monde.
>
> **Devant un paquet métier** (DIP)
> `go list -deps` : l'infrastructure est-elle dedans ? Si oui, cherche le
> **type** qui la tire — c'est presque toujours un type de données, pas une
> interface. Puis écris la règle dans un test d'architecture, avec son test
> négatif.

Et le geste d'une minute, devant n'importe quelle interface :

> **Compte ses consommateurs, puis compte, pour chacun, les méthodes qu'il
> appelle.** Si aucun n'en appelle plus de la moitié, l'interface décrit son
> producteur. Si le paquet qui la déclare est celui qui l'implémente, elle est
> au mauvais endroit — et l'implémentation n'aura pas une ligne à changer pour
> la déplacer.
