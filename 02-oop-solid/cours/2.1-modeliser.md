# Leçon 2.1 — Modéliser : ce qui a une identité, ce qui n'en a pas

## L'essentiel en deux minutes

**Le problème, en une phrase.** Avant de choisir les champs d'un type, il faut
répondre à une question : deux de ces choses, avec les mêmes valeurs,
sont-elles **la même chose** ?

**L'image.** Deux billets de 10 000 F sont interchangeables : tu te moques
de savoir lequel on te rend. C'est une **valeur**. Ton compte en banque, lui,
reste **ton** compte quand son solde change, et deux comptes au même solde
ne sont pas le même compte. C'est une **entité** : elle a une identité qui
survit à ses changements.

**Le code, en une trentaine de lignes.**

```go
// Package e21 is the two-minute version of lesson 2.1.
package e21

// Money is a value: two equal amounts are the same thing, and == says so.
type Money struct {
    Cents    int64
    Currency string
}

// Add returns a new amount; a value is never changed in place.
func (m Money) Add(o Money) Money { return Money{Cents: m.Cents + o.Cents, Currency: m.Currency} }

// Account is an entity: it stays the same account when its balance
// changes. Its identity is its ID, not its fields.
type Account struct {
    _       [0]func() // makes == refused to compile: comparing fields would be wrong
    id      string
    balance Money
}

// Open creates an account with its identity.
func Open(id, currency string) *Account {
    return &Account{id: id, balance: Money{Currency: currency}}
}

// Deposit changes the balance; the account stays the same account.
func (a *Account) Deposit(m Money) { a.balance = a.balance.Add(m) }

// SameAs compares identities.
func (a *Account) SameAs(b *Account) bool { return a.id == b.id }
```

`Money` se compare avec `==`, se copie sans danger, et `Add` en rend une
nouvelle. `Account` refuse `==` : le compilateur répond `invalid operation:
a == b (struct containing [0]func() cannot be compared)`. Comparer deux
comptes champ par champ serait une erreur — deux comptes au même solde
seraient « égaux ». On compare leur identité avec `SameAs`.

**Les règles à retenir.**

1. Le test décisif : *si je change un champ, est-ce toujours la même
   chose ?* Oui : entité. Non : valeur.
2. Cette réponse décide de l'égalité, de la copie, du cache, de la
   concurrence et du schéma de la base. Ce n'est pas une question de style.
3. Quand le métier a deux mots, il a deux types : un seul type pour deux
   notions perd une information.
4. Une méthode existe pour protéger une règle (un invariant). Sinon, c'est
   une fonction rangée au mauvais endroit.
5. L'identité métier (le numéro de compte) n'est pas la clé primaire de la
   base : deux identifiants, deux usages.

Le niveau 1 s'est terminé sur une question : *qu'est-ce que ce code me force à
savoir, et qui a le droit de l'exiger ?* Le niveau 2 commence par celle qui la
précède, et que presque personne ne pose.

On croit que modéliser, c'est choisir des champs. On ouvre un éditeur, on écrit
`type Book struct {`, et on liste ce qu'on sait du livre. Ça donne un
programme qui marche, et un modèle qui ne tient pas — pas parce que les champs
sont faux, mais parce qu'une question n'a pas été posée.

> La première question de toute modélisation n'est pas *« quels champs ? »*.
> C'est : **deux de ces choses sont-elles la même chose, et comment le
> sais-tu ?**

Cette leçon n'est pas une leçon sur la POO. Il n'y aura pas de classes, pas
d'héritage, et le mot « objet » servira peu — Go n'en a pas, et c'est une
chance : on va parler de ce que les objets servent à faire plutôt que de la
syntaxe pour les écrire.

## 1. Le concept, simplement

### Trois réponses possibles, trois sortes de types

| La réponse | Le nom | Exemple |
|---|---|---|
| **par la valeur** — si tous les champs sont égaux | une **valeur** | 1 000 FCFA, un ISBN, une durée, une cote |
| **par l'identité** — si l'identifiant est égal, *même si tout le reste diffère* | une **entité** | un adhérent, un exemplaire, un prêt |
| **par rien** — la chose n'a pas d'identité parce que ce n'est pas une chose | une **opération** | « calculer la pénalité », « synchroniser l'annuaire » |

### Le test décisif

Il tient en une phrase, il se pose en dix secondes, et il décide de tout le
reste :

> **Si je change un champ, est-ce toujours la même chose ?**
>
> Oui → **entité**. Non → **valeur**.

Applique-le, et regarde ce qui se passe :

- Je corrige une faute de frappe dans le titre d'un livre. **Est-ce le même
  livre ?** Évidemment. → entité.
- Je change un chiffre dans un ISBN. **Est-ce le même ISBN ?** Non, c'est un
  autre ISBN. → valeur.
- Une adhérente se marie et change de nom. **Est-ce la même adhérente ?** Oui,
  elle a la même carte. → entité.
- Je change le montant d'une somme d'argent. **Est-ce la même somme ?** Non. →
  valeur.

Dix secondes par type. Et pourtant ce test décide de l'égalité, de la mutabilité,
de la copie, du cache, de la concurrence, du schéma de base, de la forme de
l'API et de la façon d'écrire les tests. Voici la facture complète.

### Ce que la réponse décide

| | valeur | entité |
|---|---|---|
| **égalité** | tous les champs | l'identifiant **seul** |
| **modification** | jamais : on en fabrique une autre | dans le temps, par son propriétaire |
| **copie** | libre, gratuite, sans danger | dangereuse : deux copies divergent |
| **cache** | libre, sans invalidation | avec une invalidation, donc avec un bug en puissance |
| **concurrence** | aucun problème, jamais | un seul écrivain à la fois |
| **en base** | des colonnes, ou du JSON | une ligne, une clé primaire |
| **dans une API** | intégrée dans la réponse | référencée par son identifiant |
| **dans un test** | comparaison directe | comparaison de l'identité, **puis** des attributs |

Lis la colonne de droite et compte ce qui devient faux si tu te trompes. Ce
n'est pas une question de style.

### Et la troisième erreur, qui est la plus fréquente

Les deux premières erreurs sont connues : faire une entité d'une valeur — donner
un identifiant à une somme d'argent, ce qui est absurde — et faire une valeur
d'une entité, c'est-à-dire comparer deux adhérents avec `==` et être surpris.

La troisième ne porte pas de nom, et elle est partout :

> **Un type dont certains champs portent l'identité et d'autres non, sans qu'on
> puisse savoir lesquels.**

C'est le `Book` qui contient à la fois l'ISBN — l'œuvre — et la cote de
rangement — l'objet physique. Ce n'est ni une valeur ni une entité : c'est le
sac de la leçon 1.2, sous un autre nom.

## 2. L'intuition

Va dans une bibliothèque municipale et demande *« Les Soleils des
indépendances »*.

L'agent ne te donne pas « le livre ». Il regarde un écran, et il te dit : *« il
y en a quatre, trois sont sortis, le quatrième est au rayon romans, cote
ROM-KOU-03. »*

Il vient de manipuler **deux choses différentes** sans y penser :

- **l'ouvrage** — l'œuvre d'Ahmadou Kourouma, publiée en 1968. Il y en a **un**.
  Son identité est son ISBN. Son titre peut être corrigé dans le catalogue sans
  que l'ouvrage change.
- **l'exemplaire** — l'objet physique, avec une couverture cornée et un tampon.
  Il y en a **quatre**. Chacun a une identité propre, sa cote. Deux exemplaires
  du même ouvrage sont deux choses distinctes.

Tu **cherches** un ouvrage. Tu **empruntes** un exemplaire.

Personne, dans une bibliothèque, ne confond les deux. C'est le vocabulaire du
métier, il est précis, et il existe depuis plus longtemps que l'informatique.
Pourtant la première version du logiciel aura un seul type, `Book`, et il
mélangera les deux — parce qu'on n'a pas demandé à l'agent, on a regardé le
tableau Excel.

> Quand un métier a deux mots, il a presque toujours deux types. Et quand ton
> modèle n'en a qu'un, ce n'est pas une simplification : c'est une information
> perdue, et elle manquera au moment d'emprunter.

## 3. Le mécanisme

### Le modèle d'origine

```go
// Package before is the original model of the library.
//
// A single type, public fields, and all the logic in a service. This
// is not a straw man: it is the shape a model takes when one
// starts from the database schema, and there is one in every repository.
package before

import (
    "errors"
    "time"
)

var (
    ErrUnavailable  = errors.New("library: book unavailable")
    ErrQuotaReached = errors.New("library: quota reached")
    ErrUnknown      = errors.New("library: unknown book")
)

// Book mixes the work and the physical object. ISBN, title and author describe
// the work; Shelfmark, OnLoan and Borrower describe an object on a shelf.
type Book struct {
    ISBN      string
    Title     string
    Author    string
    Year      int
    Shelfmark string
    OnLoan    bool
    Borrower  string
    Due       time.Time
}

// Member, same form.
type Member struct {
    Number    string
    Name      string
    Quota     int
    Suspended bool
}

// Service holds every rule. The two types above have no
// method: they are bags of fields, and the service knows what is
// allowed.
type Service struct {
    Books        []Book
    Members      []Member
    DurationDays int
}

// Borrow looks for a book by its ISBN and lends it.
func (s *Service) Borrow(isbn, memberNumber string, now time.Time) error {
    var member *Member
    for i := range s.Members {
        if s.Members[i].Number == memberNumber {
            member = &s.Members[i]
            break
        }
    }
    if member == nil || member.Suspended {
        return ErrQuotaReached
    }

    ongoing := 0
    for _, l := range s.Books {
        if l.OnLoan && l.Borrower == memberNumber {
            ongoing++
        }
    }
    if ongoing >= member.Quota {
        return ErrQuotaReached
    }

    // The first book found with this ISBN. Which one? The one the loop
    // meets first.
    for i := range s.Books {
        if s.Books[i].ISBN != isbn {
            continue
        }
        if s.Books[i].OnLoan {
            continue
        }
        s.Books[i].OnLoan = true
        s.Books[i].Borrower = memberNumber
        s.Books[i].Due = now.AddDate(0, 0, s.DurationDays)
        return nil
    }
    return ErrUnavailable
}

// Return returns a book, given by its ISBN.
func (s *Service) Return(isbn string) error {
    for i := range s.Books {
        if s.Books[i].ISBN == isbn && s.Books[i].OnLoan {
            s.Books[i].OnLoan = false
            s.Books[i].Borrower = ""
            s.Books[i].Due = time.Time{}
            return nil
        }
    }
    return ErrUnknown
}

// FixTitle fixes a typo in a title.
func (s *Service) FixTitle(isbn, title string) error {
    found := false
    for i := range s.Books {
        if s.Books[i].ISBN == isbn {
            s.Books[i].Title = title
            found = true
        }
    }
    if !found {
        return ErrUnknown
    }
    return nil
}

// SameBook is the comparison function as it was written.
func SameBook(a, b Book) bool { return a == b }
```

Ce n'est pas un homme de paille. C'est la forme que prend un modèle quand on
part du schéma de base de données : une table `livres`, donc un type `Book`.
Il y en a dans tous les dépôts, y compris les bons.

Et il marche. C'est ça qu'il faut comprendre avant de continuer : ce code
fonctionne, il est en production, il rend service. Les défauts ne sont pas des
bugs qu'un test attraperait — ce sont des **conséquences**, et il faut les
provoquer pour les voir.

### Cinq défauts, démontrés

J'ai écrit cinq tests sur ce modèle. Tous passent. Aucun n'est un test de
régression : chacun constate un comportement et le nomme.

**1 et 2 — le titre est stocké trois fois.**

```
$ go test -v ./avant/
    avant_test.go:48: un attribut d'oeuvre corrige sur 3 lignes d'exemplaire
    avant_test.go:66: un ouvrage, 2 titres : map[Les Soleil des independances:2 Les Soleils des independances:1]
```

`FixTitle` parcourt la collection et modifie chaque ligne portant l'ISBN.
Ça marche — et ça dit tout. Un attribut de l'**œuvre** est stocké sur chaque
**exemplaire**, donc toute correction est une migration, et toute migration
interrompue laisse un ouvrage avec deux titres.

> Il n'existe aucun état de ce modèle où « le titre de l'ouvrage » soit une
> seule donnée. La cohérence est donc une propriété de la **boucle**, pas du
> modèle. Et une propriété de boucle s'oublie.

**3 et 4 — l'égalité répond faux, dans les deux sens.**

```go
// 3. SameBook compares field by field, so the same copy before and after
// a loan is no longer "the same book".
func TestTheSameCopyIsNoLongerTheSameAfterALoan(t *testing.T) {
    s := service()
    beforeLoan := s.Books[0]

    if err := s.Borrow(suns, "AD0042", now); err != nil {
        t.Fatalf("Borrow: %v", err)
    }
    afterLoan := s.Books[0]

    if before.SameBook(beforeLoan, afterLoan) {
        t.Fatal("the two should differ: it is the flaw we demonstrate")
    }
    if beforeLoan.Shelfmark != afterLoan.Shelfmark {
        t.Fatal("yet it is the same physical object, same shelfmark")
    }
    t.Logf("same shelfmark %q, SameBook = %v: structural equality on an entity"+
        " answers wrong", afterLoan.Shelfmark, before.SameBook(beforeLoan, afterLoan))
}

// 4. Two copies of the same work, not on loan, are EQUAL in the sense of
// SameBook... except by their shelfmark. Change the shelfmark, and two distinct objects
// can no longer be told apart.
//
// It is the most dangerous of the four flaws: it is silent, and it
// appears as soon as the shelfmark is missing: an import, a quick entry, a
// field not yet assigned.
func TestTwoCopiesWithoutShelfmarkCannotBeToldApart(t *testing.T) {
    a := before.Book{ISBN: suns, Title: "T", Author: "K", Year: 1968}
    b := before.Book{ISBN: suns, Title: "T", Author: "K", Year: 1968}

    if !before.SameBook(a, b) {
        t.Fatal("the two should be equal: it is the flaw we demonstrate")
    }
    t.Log("two distinct physical copies, SameBook = true." +
        " A deduplication would merge them, and the library would lose a book")
}
```

```

    avant_test.go:104: two distinct physical copies, SameBook = true. A deduplication would merge them, and the library would lose a book
```

Le même exemplaire physique, avant et après un prêt, n'est plus « le même
livre ». Et deux exemplaires distincts dont la cote n'est pas renseignée — un
import, une saisie rapide, un champ pas encore attribué — sont **égaux**.

Le second est le plus dangereux des cinq, parce qu'il est silencieux : un
dédoublonnage les fusionne, et la bibliothèque perd un livre sans qu'aucune
ligne de log ne le dise.

**5 — et la conséquence qui arrive au guichet.**



`Return` prend un ISBN. Il rend donc **n'importe lequel** des exemplaires
prêtés — pas celui qu'on a dans la main. Deux adhérents, deux exemplaires du
même ouvrage : Boubacar rend le sien, et le prêt d'Awa est clos. Awa recevra la
lettre de retard, elle viendra se plaindre, et personne ne comprendra.

Remonte la chaîne : la signature `Return(isbn string)` est fausse parce que le
**modèle** ne distingue pas l'ouvrage de l'exemplaire. On ne rend pas un ISBN.
On rend un objet.

> Les cinq défauts n'en font qu'un. Deux concepts du métier partagent un type,
> donc leurs identités se mélangent, donc chaque opération doit deviner de
> laquelle on parle. Et elle devine mal.

### Première correction : la valeur

Commençons par le plus simple, et par ce qui n'a pas d'identité.

```go
// Package isbn defines the international identifier of a work.
//
// It is a VALUE. Two ISBNs are the same ISBN if and only if their
// thirteen digits are the same. An ISBN has no state, no life cycle,
// no owner: it is not modified, we make another.
package isbn

import (
    "errors"
    "fmt"
    "strings"
)

var (
    // ErrLength: an ISBN-13 has thirteen digits.
    ErrLength = errors.New("isbn: invalid length")
    // ErrCharacter: an ISBN holds only digits, dashes and
    // spaces.
    ErrCharacter = errors.New("isbn: invalid character")
    // ErrCheckDigit: the first twelve digits do not match the
    // thirteenth.
    //
    // It is the interesting invariant of this package: it cannot be checked by
    // the compiler, it can be checked by a computation, and that computation must therefore
    // happen exactly once: at construction.
    ErrCheckDigit = errors.New("isbn: invalid check digit")
)

// ISBN is an identifier whose check digit is verified, and it cannot
// be anything else.
//
// The field is private for a single reason: to prevent ISBN{"anything"}.
// It is not ceremony, it is the difference between an invariant checked
// once and an invariant checked at each read, or more often, never.
//
// NOT GUARANTEED, and it is the clause that matters:
//
//    That the ISBN points to an existing work. The check digit is an
//    arithmetic check, not a directory.
//
//    That every typo is detected. The ISBN-13 check digit
//    does NOT see the transposition of two adjacent digits that differ by
//    5: swapping a 6 and a 1 changes the weighted sum by 10, so changes
//    nothing modulo 10. It is a property of the algorithm, not a flaw of this
//    code, and the test TestTranspositionIsDetectedButForOneCase marks it
//    precisely.
//
// So the type's name lies a little, and one must know it: ISBN means
// "passed a check whose holes I know", not "is right".
type ISBN struct {
    digits string // exactly 13 digits, no separator
}

// Parse accepts the forms humans write, with dashes, with
// spaces, and returns either a valid ISBN or an error. Never anything else.
func Parse(input string) (ISBN, error) {
    var b strings.Builder
    for _, r := range input {
        switch {
        case r >= '0' && r <= '9':
            b.WriteRune(r)
        case r == '-' || r == ' ':
            // Separators are a writing convenience, not data.
        default:
            return ISBN{}, fmt.Errorf("%w: %q in %q", ErrCharacter, r, input)
        }
    }

    digits := b.String()
    if len(digits) != 13 {
        return ISBN{}, fmt.Errorf("%w: %d digits in %q", ErrLength, len(digits), input)
    }
    if sum(digits)%10 != 0 {
        return ISBN{}, fmt.Errorf("%w: %s", ErrCheckDigit, digits)
    }
    return ISBN{digits: digits}, nil
}

// MustParse panics on invalid input. For literals written
// in the code: a wrong ISBN written by hand is a programming bug.
func MustParse(input string) ISBN {
    i, err := Parse(input)
    if err != nil {
        panic(err)
    }
    return i
}

// sum applies the alternating weights 1 and 3, thirteenth digit included. A valid
// ISBN has a sum that is a multiple of ten.
func sum(digits string) int {
    total := 0
    for i := 0; i < len(digits); i++ {
        weight := 1
        if i%2 == 1 {
            weight = 3
        }
        total += int(digits[i]-'0') * weight
    }
    return total
}

// IsZero tells the zero ISBN, which nobody builds, from a real ISBN.
func (i ISBN) IsZero() bool { return i.digits == "" }

// String returns the canonical form: thirteen digits, no separator. A single
// written form, so a single cache key, a single map key, a single
// database column.
func (i ISBN) String() string {
    if i.IsZero() {
        return "zero isbn"
    }
    return i.digits
}
```

Trois choses à relever.

**Le champ est privé.** Ce n'est pas de la cérémonie : c'est la différence entre
un invariant vérifié **une fois**, à la construction, et un invariant vérifié à
chaque lecture — ou, plus souvent, jamais. `ISBN{"n'importe quoi"}` ne compile
pas depuis l'extérieur du paquet.

**Trois écritures, une valeur.** Les tirets et les espaces sont une commodité
d'écriture humaine, pas une donnée. Après `Parse`, il existe **une seule
forme** : treize chiffres. Donc une seule clé de map, une seule clé de cache,
une seule colonne de base.

```go
// TestTwoSpellingsOfOneISBNAreTheSameISBN is the test that defines "value".
// Three different inputs, one value. It is the whole property of a
// value object: equality is structural, and it can be used with ==,
// so as a map key, so as a cache key.
func TestTwoSpellingsOfOneISBNAreTheSameISBN(t *testing.T) {
    spellings := []string{
        "978-0-306-40615-7",
        "9780306406157",
        "978 0 306 40615 7",
    }

    first := isbn.MustParse(spellings[0])
    for _, e := range spellings[1:] {
        other, err := isbn.Parse(e)
        if err != nil {
            t.Fatalf("Parse(%q): %v", e, err)
        }
        if other != first {
            t.Fatalf("%q and %q should be the same ISBN", spellings[0], e)
        }
    }

    // Usable as a map key, without a hash function to write.
    seen := map[isbn.ISBN]int{}
    for _, e := range spellings {
        seen[isbn.MustParse(e)]++
    }
    if len(seen) != 1 || seen[first] != 3 {
        t.Fatalf("map = %v, want a single key seen 3 times", seen)
    }
}
```

Et remarque la fin du test : `map[isbn.ISBN]int` fonctionne sans écrire une
seule fonction de hachage. C'est le bénéfice concret d'une valeur comparable, et
on le perd dès qu'on met une tranche ou une map dans le type.

**L'invariant a une portée, et la portée fait partie du contrat.**

Les poids alternés 1 et 3 de la clé de contrôle existent pour attraper les
**transpositions**, qui sont la faute de saisie la plus fréquente. J'ai écrit un
test pour le prouver. Il a échoué.

```go
// TestTranspositionIsDetectedButForOneCase marks the reach of the invariant.
// The alternating weights 1 and 3 exist to catch transpositions, which are
// the most frequent typo. Swapping two adjacent digits a and b
// changes the weighted sum by 2(a-b): the typo is therefore detected unless
// 2(a-b) is a multiple of 10, that is unless |a-b| is 5.
//
// This test found this hole when I wrote it: it first asserted
// that the twelve transpositions were detected, and the eleventh was not.
// I did not fix it by removing the awkward case: I wrote it as it
// is, because an invariant whose reach we do not know is an invariant
// we trust too much.
func TestTranspositionIsDetectedButForOneCase(t *testing.T) {
    const valid = "9780306406157"

    detected, blind := 0, 0
    for i := 0; i < len(valid)-1; i++ {
        a, b := int(valid[i]-'0'), int(valid[i+1]-'0')
        if a == b {
            continue // swapping two equal digits changes nothing
        }
        bytes := []byte(valid)
        bytes[i], bytes[i+1] = bytes[i+1], bytes[i]
        _, err := isbn.Parse(string(bytes))

        gap := a - b
        if gap < 0 {
            gap = -gap
        }
        if gap == 5 {
            // The hole, and it is proved here rather than assumed.
            if err != nil {
                t.Errorf("transposition %d<->%d at %d: err = %v, want nil."+
                    " If this test fails, the algorithm changed", a, b, i, err)
            }
            blind++
            continue
        }
        if !errors.Is(err, isbn.ErrCheckDigit) {
            t.Errorf("transposition %d<->%d at %d (%s) not detected: %v",
                a, b, i, string(bytes), err)
        }
        detected++
    }

    if detected == 0 || blind == 0 {
        t.Fatalf("%d detected, %d blind: this test must exercise both cases",
            detected, blind)
    }
    t.Logf("%d transpositions detected, %d invisible (gap of 5)", detected, blind)
}
```

### Deuxième correction : l'entité, et l'égalité qu'on lui interdit

```go
// Work is an ENTITY, identified by its ISBN.
// The test that classified it: "if I change a field, is it still the same
// thing?" Fixing a typo in the title does not change the work. So
// equality cannot be structural, so Work is not a value.
type Work struct {
    // noCompare makes o1 == o2 impossible AT COMPILE TIME.
    //
    // [0]func() costs no byte: a struct with and without it has the same
    // size, and makes the type not comparable. The compiler then refuses
    // the easiest mistake to make on an entity: comparing it field
    // by field. Two descriptions of the same work, one of which has a title
    // fixed are the SAME work, and == would have said the opposite without
    // report it.
    //
    // It is a ⚫: the state "I compared two entities by their fields" is
    // no longer representable.
    _ [0]func()

    isbn   isbn.ISBN
    title  string
    author string
    year   int
}

func NewWork(i isbn.ISBN, title, author string, year int) (Work, error) {
    if i.IsZero() {
        return Work{}, ErrZeroISBN
    }
    title = strings.TrimSpace(title)
    if title == "" {
        return Work{}, fmt.Errorf("%w: %s", ErrNoTitle, i)
    }
    return Work{isbn: i, title: title, author: strings.TrimSpace(author), year: year}, nil
}

// ISBN is the identity of the work.
func (o Work) ISBN() isbn.ISBN { return o.isbn }

// Title is an attribute. It can change.
func (o Work) Title() string { return o.title }

// Author is an attribute.
func (o Work) Author() string { return o.author }

// SameAs is an entity's equality: it looks only at identity.
//
// It is the method that replaces ==, and it exists because == was made
// impossible. The order of the two decisions matters: forbid first, provide
// then.
func (o Work) SameAs(other Work) bool { return o.isbn == other.isbn }

// WithTitle returns a copy with the fixed title. The work stays the same work:
// SameAs confirms it, and it is exactly what a test must check.
func (o Work) WithTitle(title string) (Work, error) {
    title = strings.TrimSpace(title)
    if title == "" {
        return Work{}, fmt.Errorf("%w: %s", ErrNoTitle, o.isbn)
    }
    o.title = title
    return o, nil
}

func (o Work) String() string {
    return fmt.Sprintf("%s (%s, %d) [%s]", o.title, o.author, o.year, o.isbn)
}
```

Le champ qui ne sert à rien est le plus important du fichier :

```
_ [0]func()
```

Un tableau de **zéro** fonction. Il n'occupe aucun octet — une structure avec et
sans fait exactement la même taille, 24 octets dans les deux cas, c'est
mesurable — et il rend le type **non comparable**. Le compilateur refuse alors
l'erreur la plus facile à commettre sur une entité :

```
invalid operation: a == b (struct containing [0]func() cannot be compared)
```

C'est un ⚫ au sens de la leçon 1.1 : l'état *« j'ai comparé deux entités par
leurs champs »* n'est plus représentable. Et l'ordre des deux décisions compte :
**interdire d'abord, fournir ensuite.** `SameAs` existe parce que `==` a été
rendu impossible, pas l'inverse — sinon personne ne l'appellerait.

Le test qui définit l'identité :

```go
// TestFixingTheTitleKeepsTheWork is THE test of this lesson.
// It answers the question "if I change a field, is it still the same
// thing?" and makes it executable. If this test fails, it is not a code
// bug: it is that the model changed its mind about what a work is.
func TestFixingTheTitleKeepsTheWork(t *testing.T) {
    before := work(t, "Les Soleil des independances") // typo
    after, err := before.WithTitle("Les Soleils des independances")
    if err != nil {
        t.Fatalf("WithTitle: %v", err)
    }

    if after.Title() == before.Title() {
        t.Fatal("the title did not change")
    }
    if !after.SameAs(before) {
        t.Fatal("fixing a typo changed the work")
    }
    // And the original did not move: WithTitle returns a copy.
    if before.Title() != "Les Soleil des independances" {
        t.Fatalf("the original was modified: %q", before.Title())
    }
}
```

Si ce test échoue un jour, ce ne sera pas un bug de code. Ce sera que le modèle
a changé d'avis sur ce qu'est un ouvrage, et c'est exactement ce qu'un test doit
signaler.

### Le test qui garde le ⚫

Un `[0]func()` ne sert à rien, il a l'air bizarre, et il sera retiré. Par
quelqu'un qui nettoie, de bonne foi, un vendredi. Ce jour-là, `==` redevient
possible et compare le titre.

Il faut donc un gardien, et il est d'un genre nouveau :

```go
// Package guard holds only decision tests.

    "os"
    "os/exec"
    "path/filepath"

    // it DEPENDS on changes. A test that checks by running "go build" in a
    // subprocess depends on nothing in the compiler's sense: so Go has the
    // right to return a stale result, and it does.
    //
    // Measured, not assumed. Removing the [0]func() field from Work:
    //

    //    $ go test -count=1 ./guard/     FAIL

//
// It is a special kind of test: it does not assert that a program gives
// a certain result, it asserts that a program DOES NOT COMPILE. It is the
// strongest of tests, because a compile failure cannot be disabled, is not
// marked "flaky" and is not ignored.
//
// It guards a decision no behavior test can guard: the day
// someone removes the [0]func() field from Work (it serves no purpose, it
// looks odd, it will be removed), == becomes possible again and compares the title.
//
// Each case carries the FRAGMENT of the expected compile message, and it is
// no luxury: without it, any error satisfies the test. An unused
// import is enough to make it green forever.
func TestComparingTwoEntitiesDoesNotCompile(t *testing.T) {
    tc := []struct {
        name string
        code string
        want string
    }{
        {
            name: "two works",

    a, _ := catalog.NewWork(isbn.MustParse("9780306406157"), "T", "A", 1968)
    b, _ := catalog.NewWork(isbn.MustParse("9780306406157"), "T fixed", "A", 1968)

`,

    a, _ := catalog.NewCopy(catalog.MustShelfmark("ROM-01"), isbn.MustParse("9780306406157"))

                    " expected. Wanted a message holding %q, got:\n%s",

            t.Logf("%s", firstUsefulLine(output))

// Two reasons not to put it through the compiler like the others:

//     same time as it;
//  2. in process, it creates the compile dependency that invalidates the cache.

func compile(t *testing.T, body string) (string, error) {
    t.Helper()

    root, err := filepath.Abs("..")
    if err != nil {
        t.Fatalf("root: %v", err)
    }
    records, err := os.MkdirTemp(root, "trial")
    if err != nil {
        t.Fatalf("records: %v", err)

    t.Cleanup(func() { _ = os.RemoveAll(records) })

    cmd.Dir = records
```

Ce test est fort, et il a **trois modes de panne qui lui sont propres**. Les
trois sont dans le fichier, et aucun n'est évident.

**1. Il peut passer parce que tout est cassé.** D'où le témoin,
`TestComparisonByIdentityAnswers`. Sans lui, le premier test passerait aussi

> Un test qui attend un échec a besoin d'un **témoin** qui réussit.

**2. Il peut passer pour la mauvaise raison.** D'où le champ `want` : chaque
cas porte un fragment du message de compilation qu'il exige. En écrivant la

> Un test qui attend un échec doit vérifier **la raison** de l'échec. Sinon
> n'importe quelle erreur le satisfait, et la première faute de frappe le rend
> définitivement vert.

**3. Et le plus sournois : il peut passer parce qu'il est en cache.**

Ce test valide en lançant `go build` dans un sous-processus. Il ne dépend donc
de **rien** au sens du compilateur, et le cache de tests de Go — qui invalide un
résultat quand un paquet dont il dépend change — a parfaitement le droit de
rendre une réponse périmée.

```

$ go test -count=1 ./garde/     FAIL  exemple/bibliotheque/garde
```

Le ⚫ venait de disparaître, et le test disait *« tout va bien »*.

Le remède par `-count=1` est fragile : il vit dans la commande, pas dans le
code, et le premier `go test ./...` le contourne. Le remède robuste est dans les
imports du fichier — et c'est pour ça qu'ils sont là, avec un long commentaire :

> **Un test de décision doit dépendre, au sens du compilateur, de ce qu'il
> surveille.** Sinon il surveille une version qui n'existe plus.

C'est une règle générale, et elle vaut pour tous les tests de décision du
niveau 1 : celui qui lit la source avec `go/ast`, celui qui interroge `go list`,
celui qui compile un programme. Les trois valident **par un sous-processus**, et
les trois sont donc hors du graphe de dépendances que Go connaît. Le test de
graphe d'imports de la correction 1.6/2 a le même défaut, et le même remède.

### Les invariants, et la seule raison d'avoir une méthode

Un exemplaire a trois états et des transitions. Voici la garde, et l'histoire
qui l'a écrite :

```go
// Lend moves the copy to the on-loan state.
// Here is the only legitimate reason to have a method rather than a function:
// it PRESERVES AN INVARIANT nothing else guards: a copy on loan
// is not lent twice, a withdrawn copy is no longer lent.
//
// A method that preserves no invariant is a misplaced function.
//
// Note the form of the guard. The first version of this file was written the
// wrong way round: it refused OnLoan and Withdrawn, and let everything else through.
// A test caught it on the first run: Copy{} has a zero
// state, which is neither OnLoan nor Withdrawn, so the zero value could be lent. A
// non-existent copy could leave the library.
//
// Hence the rule, and it holds for every state machine:
//
//    A transition is written by the ALLOWED starting state, never by the list
//    of forbidden states. The list of forbidden states always forgets the zero value,
//    and it will forget the fourth state the day we add it.
func (e Copy) Lend() (Copy, error) {
    if err := e.requireState(Available); err != nil {
        return e, err
    }
    e.state = OnLoan
    return e, nil
}

// Return puts the copy back on the shelf.
func (e Copy) Return() (Copy, error) {
    if err := e.requireState(OnLoan); err != nil {
        return e, err
    }
    e.state = Available
    return e, nil
}

// Withdraw takes the copy out of the collection. A one-way transition: it is the only
// of this type, and it is a business decision, not a convenience.
func (e Copy) Withdraw() (Copy, error) {
    if err := e.requireState(Available); err != nil {
        return e, err
    }
    e.state = Withdrawn
    return e, nil
}

// requireState is the single guard of the three transitions. A single place where the
// list of allowed states is written, so a single place to reread the day
// a fourth state appears.
func (e Copy) requireState(required State) error {
    if e.state == required {
        return nil
    }
    switch e.state {
    case Available, OnLoan, Withdrawn:
        return fmt.Errorf("%w: %s is %s, but %s is required",
            ErrUnexpectedState, e.shelfmark, e.state, required)
    default:
        // Including State(0): the zero value is not a copy.
        return fmt.Errorf("%w: %s", ErrNoSuchCopy, e.shelfmark)
    }
}
```

La première version de ce fichier était écrite **à l'envers**. Elle refusait
`OnLoan` et `Withdrawn`, et laissait passer tout le reste :

```
switch e.state {
case OnLoan:
    return e, ErrDejaPrete
case Withdrawn:
    return e, ErrRetire
}
e.state = OnLoan
```

Un test l'a prise en défaut au premier lancement : `Copy{}` a un état nul,
qui n'est ni `OnLoan` ni `Withdrawn`, donc la valeur zéro était **prêtable**. Un
exemplaire inexistant pouvait sortir de la bibliothèque.

> **Une transition s'écrit par l'état de départ autorisé, jamais par la liste
> des états interdits.** La liste des interdits oublie toujours la valeur zéro,
> et elle oubliera le quatrième état le jour où on l'ajoutera.

Et la règle qui justifie l'existence de ces méthodes, parce qu'il faut pouvoir
répondre à *« pourquoi une méthode plutôt qu'une fonction ? »* :

> Une méthode existe pour **préserver un invariant** que rien d'autre ne garde.
> Une méthode qui ne préserve aucun invariant est une fonction mal rangée.

Ce critère tranche. `Lend` préserve « un exemplaire n'est prêté qu'une fois ».
`Title()` ne préserve rien — c'est un accesseur, et il n'est là que parce que le
champ est privé. La différence entre un modèle riche et un modèle décoratif est
dans ce rapport.

### La valeur zéro : la question, pas la réponse

En Go, `Copy{}` existe. On ne peut pas l'empêcher. La question de
modélisation n'est donc pas *comment l'interdire*, c'est :

> **La valeur zéro est-elle un état valide de ce type ?**

Et la réponse change d'un type à l'autre, dans le même paquet :

| Type | Valeur zéro valide ? | Comment on le sait, et ce qu'on fait |
|---|---|---|
| `State` | **non** | `State(0)` ne vaut ni `Available`, ni `OnLoan`, ni `Withdrawn`. L'énumération commence à `iota + 1`, et `String()` rend « etat inconnu » |
| `Copy` | **non** | son état nul le trahit, sans champ supplémentaire |
| `Quota` | **oui** | un quota de 0 a un sens métier : inscrit, consulte sur place, n'emprunte pas. C'est un cas réel |
| `Member` | **non** | mais rien ne le trahit — un quota de 0 est légitime. Il faut donc un champ `built` dédié |

La dernière ligne est la moins élégante et la plus honnête. Quand aucun champ ne
trahit la valeur zéro, il faut un drapeau explicite. C'est laid, c'est
indispensable, et ça vaut mieux qu'un type dont la valeur zéro se comporte comme
un objet valide.

### L'invariant qui n'a pas de foyer

Voici la question la plus difficile de la leçon, et celle que la plupart des
cours escamotent.

L'invariant *« un adhérent a au plus `quota` emprunts simultanés »* porte sur un
adhérent **et** sur l'ensemble de ses prêts. Il n'a donc **aucun foyer naturel**
dans le système de types :

- le mettre dans `Member` oblige l'adhérent à contenir ses prêts, donc à les
  charger tous pour l'inscrire, pour changer son nom, pour l'afficher ;
- le mettre dans `Loan` oblige le prêt à connaître tous les autres prêts ;
- le mettre dans un service le sort du modèle, et c'est précisément le modèle
  anémique qu'on essaie d'éviter.

La sortie n'est pas de choisir le moins mauvais. Elle est de **séparer la règle
de sa mesure** :

```go
// Loans is a member's number of ongoing loans, AT A GIVEN
// GIVEN. VALUE: it is a snapshot, not a state.
//
// This type is the answer to the hardest question of this lesson:
// the invariant "at most Quota simultaneous loans" is about a member AND
// on all of their loans. So it has no natural home in the type
// of types: putting loans in the member would force loading them all
// to enroll someone.
//
// The way out is not to give up, it is to SEPARATE THE RULE FROM ITS MEASURE.
// The member keeps the rule; the count is passed as an argument. It is the
// same solution as "time is not a dependency, it is data to
// pass down": here, the count.
type Loans struct {
    n int
}

func NewLoans(n int) (Loans, error) {
    if n < 0 {
        return Loans{}, fmt.Errorf("%w: %d loans", ErrInvalidQuota, n)
    }
    return Loans{n: n}, nil
}

func (e Loans) Count() int { return e.n }

// Member is an ENTITY, identified by its number.
type Member struct {
    _ [0]func()

    number    Number
    name      string
    quota     Quota
    suspended bool
    built     bool
}

func New(n Number, name string, q Quota) (Member, error) {
    if n.IsZero() {
        return Member{}, fmt.Errorf("%w: zero number", ErrInvalidNumber)
    }
    name = strings.TrimSpace(name)
    if name == "" {
        return Member{}, fmt.Errorf("%w: %s", ErrNoName, n)
    }
    return Member{number: n, name: name, quota: q, built: true}, nil
}

func (a Member) Number() Number { return a.number }
func (a Member) Name() string   { return a.name }
func (a Member) Quota() Quota   { return a.quota }

// SameAs: an entity's equality.
func (a Member) SameAs(other Member) bool { return a.number == other.number }

// WithName returns a copy with the fixed name. A marriage does not change the member.
func (a Member) WithName(name string) (Member, error) {
    if err := a.exist(); err != nil {
        return a, err
    }
    name = strings.TrimSpace(name)
    if name == "" {
        return a, fmt.Errorf("%w: %s", ErrNoName, a.number)
    }
    a.name = name
    return a, nil
}

// Suspend and Reactivate are the two transitions of membership.
func (a Member) Suspend() (Member, error) {
    if err := a.exist(); err != nil {
        return a, err
    }
    a.suspended = true
    return a, nil
}

func (a Member) Reactivate() (Member, error) {
    if err := a.exist(); err != nil {
        return a, err
    }
    a.suspended = false
    return a, nil
}

// CanBorrow is the RULE, and it lives in the entity.
//
// It receives the count because it does not hold it. What the member knows
// (its quota, its suspension) stays with it; what it does not know is
// INSTANT. The caller who reads the count is responsible for reading it at the right time,
// and it is a different responsibility.
//
// NOT GUARANTEED: that the count is still right when the caller acts. Read
// then acting is a check-then-act, and only a transaction closes it. This
// method decides; it does not protect.
func (a Member) CanBorrow(e Loans) error {
    if err := a.exist(); err != nil {
        return err
    }
    if a.suspended {
        return fmt.Errorf("%w: %s", ErrSuspended, a.number)
    }
    if e.n >= a.quota.max {
        return fmt.Errorf("%w: %s has %d loans out of %d",
            ErrQuotaReached, a.number, e.n, a.quota.max)
    }
    return nil
}
```

L'adhérent garde la **règle** — son quota, sa suspension, la décision. Le
**compte** lui est passé en argument, parce qu'il ne le détient pas.

C'est exactement la solution de la leçon 1.6 sur le temps : *« le temps n'est
pas une dépendance à injecter, c'est une donnée à faire descendre »*. Ici, c'est
le compte.

Et la clause `NON GARANTI` dit la limite sans la farder : lire le compte puis
agir est un `check-then-act`, et seule une transaction le ferme. **Cette méthode
décide ; elle ne protège pas.** Le ⚫ est hors d'atteinte, et le dire vaut mieux
que de laisser croire.

> Quand un invariant porte sur plusieurs entités, il n'a pas de foyer dans les
> types. Mets la **décision** dans l'entité qui porte la règle, et fais
> descendre ce qu'elle ne sait pas. Ce qui reste — lire au bon moment, dans la
> bonne transaction — est une responsabilité différente, et elle a un autre
> demandeur.

### L'identité composée d'attributs

Dernier cas, et il revient sans arrêt dans la vraie vie. Un prêt : faut-il lui
donner un numéro propre, ou l'identifier par le couple (exemplaire, date de
début) ?

```go
// Loan is an ENTITY, and its identity is a number of its OWN.
// We could have identified it by the pair (copy, start date). Two
// reasons not to, and the second is the general rule:
//
//  1. the same copy may be lent again to the same member later. The shelfmark
//     alone is not enough, and the date is part of the key;
//  2. a start date gets FIXED: the clerk got the day wrong. If it is
//     part of the identity, fixing the date creates another loan, and the original
//     stays open in the database.
//
// Hence: an identity made of changeable attributes is not an identity.
type Loan struct {
    _ [0]func()

    number   Number
    copy     catalog.Shelfmark
    borrower member.Number
    start    day.Day
    due      day.Day
    renewals int
    returned bool
    built    bool
}
```

Deux raisons, et la seconde est la règle générale :

1. le même exemplaire peut être reprêté au même adhérent plus tard ;
2. une date de début **se corrige** — l'agent s'est trompé de jour. Si elle fait
   partie de l'identité, corriger la date crée un **autre** prêt, et le prêt
   d'origine reste ouvert dans la base, pour toujours.

> **Une identité composée d'attributs modifiables n'est pas une identité.**

Le corollaire est utile au moment de choisir une clé primaire : si tu hésites
entre une clé naturelle composée et un identifiant technique, demande-toi
laquelle des colonnes de ta clé peut être corrigée un jour. S'il y en a une,
tu as ta réponse.

## 4. Ce que ça donne, et ce que ça coûte

### Les cinq défauts, repris un par un

| # | Le défaut d'origine | Ce qui l'a supprimé |
|---|---|---|
| 1 | le titre stocké trois fois | le titre est sur `Work`, pas sur `Copy` |
| 2 | correction partielle, deux titres | il n'y a plus qu'une seule donnée à corriger |
| 3 | `==` répond faux sur une entité | `==` ne compile plus ; `SameAs` existe |
| 4 | deux exemplaires sans cote sont égaux | la cote est obligatoire à la construction, et `==` est interdit |
| 5 | `Return(isbn)` clôt le prêt de quelqu'un d'autre | `Loan.Return()` est une méthode du prêt qu'on a en main |

Le cinquième mérite une phrase, parce que c'est le plus instructif : il n'a pas
été corrigé par un `if`. Il a disparu **parce que la signature est devenue
impossible à écrire de travers**. On ne rend pas un ISBN ; on clôt un prêt.

### Le coût, compté honnêtement

| Ce qu'on paie | Combien |
|---|---|
| lignes de modèle | 118 → 761, dont les trois quarts sont de la documentation et des constructeurs |
| accesseurs à écrire | une vingtaine, qui ne préservent rien |
| conversions aux frontières | tout ce qui entre et sort — base, HTTP, CSV — doit passer par un constructeur |
| rigidité | ajouter un champ à `Work` demande de toucher le constructeur, et c'est voulu |

C'est beaucoup. Et ça ne se justifie pas partout : un type qui traverse le
programme sans jamais porter d'invariant n'a pas besoin de ça, et le lui
imposer est une cérémonie. On reviendra sur ce critère au §6, et la leçon 2.6
en fera son sujet.

Ce qu'il faut retenir du calcul : **le coût est fixe et payé une fois, les
défauts sont récurrents et payés au guichet.** Ce n'est pas un argument
universel, c'est un argument chiffrable, et il se chiffre par type.

## 5. Les trois erreurs qui restent, après tout ça

Même avec des entités propres et des valeurs immuables, trois fautes
subsistent. Elles sont plus discrètes.

### L'entité qui voyage

Une entité passée par valeur est **copiée**. Les deux copies divergent, et rien
ne le signale :

```
e, _ := catalog.NewCopy(cote, isbn)
prete, _ := e.Lend()
// e est toujours disponible. prete est prete. Laquelle est la verite ?
```

Ce code compile et il est faux. C'est pour ça que toutes les méthodes de ce
chapitre rendent une **nouvelle valeur** plutôt que de muter un pointeur : le
résultat est dans la valeur de retour, et l'ignorer se voit.

Ça ne supprime pas le problème — ça le rend visible. La vraie question est :
**qui est le propriétaire de l'état courant de cet exemplaire ?** La réponse est
le dépôt, et c'est le sujet du niveau 5.

### La valeur qui grossit

Une valeur immuable, comparable, sans identité — et douze champs. Elle est
correcte, et elle est devenue un sac. Le test de la leçon 1.3 s'applique sans
changement : **est-ce que ces douze champs changent pour la même raison ?**

Une valeur n'est pas dispensée des règles de cohésion. Elle est seulement
dispensée de celles de l'identité.

### L'accesseur qui rouvre ce que le constructeur a fermé

```
func (o Work) Champs() (isbn.ISBN, string, string, int)
```

Un accesseur par champ, puis un constructeur qui les reprend tous : les champs
sont privés, et le type est aussi malléable qu'avant. L'encapsulation n'est pas
dans le mot-clé, elle est dans ce que les méthodes **n'offrent pas**.

Le critère : chaque accesseur doit répondre à une question qu'un appelant pose
vraiment. `Title()` sert à afficher. `Year()` — qui la lit ? Si personne, elle
n'a pas à être exposée.

## 6. Le lien avec la production

### Ce que le modèle décide de l'incident

Reprends le défaut 5 — `Return(isbn)` clôt le prêt de quelqu'un d'autre — et
imagine l'incident. Un lundi matin, douze réclamations : des lettres de retard
envoyées à des adhérents qui ont rendu leurs livres.

Les questions de l'astreinte sont :

- **quel exemplaire a été rendu ?** Le modèle ne le sait pas : `Return` a reçu
  un ISBN.
- **quel prêt a été clos ?** Il n'y a pas de prêt, il y a un booléen sur une
  ligne de livre.
- **combien de fois est-ce arrivé ?** Impossible à dire : l'information n'a
  jamais existé.

Aucune de ces questions n'est une question de test ou d'outillage. **Ce sont des
questions de modèle**, et le modèle a décidé qu'elles n'auraient pas de réponse.

> Un modèle qui perd une distinction du métier ne perd pas seulement la
> correction : il perd la capacité de **raconter ce qui s'est passé**. Et c'est
> ce qu'on cherche à 3 h du matin.

### L'identité métier n'est pas la clé primaire

Distinction qui coûte cher quand on l'ignore, et qui se voit en production.

| | identité métier | clé de stockage |
|---|---|---|
| exemple | la cote `ROM-KOU-03`, l'ISBN, le numéro d'adhérent | un `BIGSERIAL`, un UUID |
| qui l'attribue | le métier, parfois avant l'informatique | la base, à l'insertion |
| qui peut la changer | personne, en principe — et pourtant ça arrive | personne |
| visible du client | **oui**, elle est imprimée sur la carte | non, jamais |

Deux identifiants, deux demandeurs. Et une conséquence pratique qui structure
tout le chemin d'écriture : **une entité créée mais pas encore stockée a-t-elle
une identité ?**

- Si l'identité est métier, **oui** : on peut la construire, la valider, la
  manipuler, et décider ensuite de l'enregistrer. C'est le choix de ce chapitre.
- Si l'identité est la clé de la base, **non** : il existe un état « entité sans
  identité », qu'il faut représenter — un pointeur nul, un entier à zéro, un
  booléen `enregistre`. C'est un état de plus, et il contaminera toutes les
  signatures.

Le second choix n'est pas faux ; il est plus cher, et il faut le prendre en
connaissance de cause plutôt que par défaut parce que l'ORM le fait comme ça.

### Le cache, et pourquoi la distinction s'y paie cash

C'est ici que l'erreur de modélisation devient une panne.

- **Une valeur se met en cache sans réfléchir.** Immuable, comparable : la clé
  est la valeur elle-même, et il n'y a **aucune invalidation**. Le catalogue
  peut mettre tous les ISBN qu'il veut en mémoire, pour toujours.
- **Une entité mise en cache a besoin d'une invalidation.** Son état change. Et
  la question « quand invalider ? » n'a pas de réponse locale : elle dépend de
  qui écrit, et d'où.

Donc : un type dont on n'a pas décidé s'il est valeur ou entité est un type
qu'on va mettre en cache **comme une valeur** — c'est plus simple — et qui va
servir des données périmées. Le bug arrive six mois plus tard, il est
intermittent, et personne ne le relie au modèle.

> Chaque fois que tu mets quelque chose en cache sans invalidation, tu déclares
> que c'est une valeur. Si ce n'en est pas une, tu viens d'écrire un bug avec
> une date d'échéance.

### Le critère de proportion

Le §4 a compté le coût. Voilà quand il se justifie, et c'est mesurable :

| Fais-en un type avec invariants quand… | Reste sur une structure simple quand… |
|---|---|
| un invariant existe et n'est vérifié nulle part | le type ne porte aucun invariant |
| plus d'un appelant construit la chose | un seul endroit la construit, et il la valide |
| une erreur de construction se paie chez le client | une erreur se voit immédiatement, en développement |
| le métier a un mot pour ça | c'est un détail de transport |

La dernière ligne est la plus rapide à appliquer. **Le métier a-t-il un mot ?**
S'il dit « exemplaire », fais un type. S'il dit « la ligne du fichier », c'est
une structure de transport, et l'appeler autrement serait mentir.

## 7. Ce qu'il faut retenir

1. **La première question n'est pas « quels champs » mais « deux de ces choses
   sont-elles la même chose ».**
2. **Le test décisif** : si je change un champ, est-ce toujours la même chose ?
   Oui → entité. Non → valeur.
3. **La réponse décide** de l'égalité, de la copie, du cache, de la
   concurrence, du schéma, de l'API et des tests. Pas du style.
4. **La troisième erreur, la plus fréquente** : un type dont certains champs
   portent l'identité et d'autres non.
5. **Quand le métier a deux mots, il a deux types.** Un seul type n'est pas une
   simplification, c'est une information perdue.
6. **`_ [0]func()` rend une entité non comparable**, sans coûter un octet.
   Interdire d'abord, fournir `SameAs` ensuite.
7. **Un test qui affirme qu'un programme ne compile pas est le plus fort des
   tests** — et il a trois modes de panne : passer parce que tout est cassé
   (d'où le témoin), passer pour la mauvaise raison (d'où le fragment de message
   attendu), et passer parce qu'il est en cache (d'où l'import de ce qu'il
   surveille).
8. **Une méthode existe pour préserver un invariant.** Sinon c'est une fonction
   mal rangée.
9. **Une transition s'écrit par l'état de départ autorisé**, jamais par la liste
   des interdits.
10. **La valeur zéro est une question, pas une réponse.** Elle se pose type par
    type, et elle n'a pas la même réponse deux fois de suite.
11. **Un invariant qui porte sur plusieurs entités n'a pas de foyer.** Mets la
    règle dans l'entité, fais descendre la mesure.
12. **Une identité composée d'attributs modifiables n'est pas une identité.**
13. **L'identité métier n'est pas la clé primaire.** Deux identifiants, deux
    demandeurs.
14. **Mettre en cache sans invalidation, c'est déclarer que c'est une valeur.**
15. **Un invariant dont on ne connaît pas la portée est un invariant auquel on
    fait trop confiance.**

## 8. Approfondissement

### Les trois égalités, et pourquoi Go n'en a qu'une

| L'égalité | Ce qu'elle demande | En Go |
|---|---|---|
| **structurelle** | tous les champs égaux | `==`, pour les types comparables |
| **d'identité** | le même identifiant | une méthode, à écrire |
| **référentielle** | le même emplacement mémoire | `p1 == p2` sur deux pointeurs |

Go donne la première gratuitement, ne donne pas la deuxième, et donne la
troisième par accident — comparer deux `*Work` compare les adresses, ce qui
est presque toujours une erreur, et le compilateur ne dira rien.

C'est pourquoi `[0]func()` compte double : il ferme l'égalité structurelle **et**
il rend l'égalité référentielle visible, puisque comparer deux pointeurs devient
le seul `==` qui compile encore, et qu'il saute aux yeux.

### Ce qu'un objet-valeur permet et qu'on n'exploite jamais

Une valeur immuable et comparable donne gratuitement cinq choses :

- une **clé de map**, sans fonction de hachage ;
- une **clé de cache**, sans invalidation ;
- un **partage entre goroutines**, sans verrou ;
- une **comparaison dans les tests**, sans comparateur ;
- une **sérialisation stable**, puisqu'il n'y a qu'une forme canonique.

Les cinq sont perdues dès qu'on met une tranche, une map ou une fonction dans le
type. C'est le vrai critère pour choisir entre `[]string` et une chaîne avec un
séparateur dans un objet-valeur : la tranche coûte la comparabilité, et la
comparabilité coûte cher à retrouver.

### L'anémie n'est pas un péché, c'est un symptôme

Le « modèle anémique » est souvent présenté comme une faute de goût. C'est
inexact, et la formulation utile est :

> Un modèle anémique n'est pas un défaut de style. C'est **un invariant sans
> adresse**.

D'où deux conséquences pratiques :

- **Un type sans invariant a le droit d'être anémique.** Une structure qui
  transporte les champs d'une requête HTTP n'a rien à préserver. La nommer
  `RequeteCreationOuvrage` plutôt que `Work` suffit, et c'est tout ce qu'il
  faut faire.
- **Un type avec un invariant qui vit ailleurs est un problème**, et le problème
  n'est pas l'anémie : c'est que l'invariant est vérifié dans un endroit, deux
  endroits, ou aucun, et que personne ne sait lequel.

Le test, encore une fois, est opérationnel : **cite l'invariant, puis demande où
il est vérifié.** Si la réponse est « dans le service », vérifie qu'il n'y a
qu'un seul service. Si la réponse est « ça dépend », tu as trouvé le bug avant
qu'il arrive.

### Ce que cette leçon n'a pas traité

Trois choses, pour qu'on sache ce qui manque :

- **La frontière d'un agrégat** — quelles entités se modifient ensemble, dans
  une transaction. Le quota en est un cas, et on a choisi de le contourner. La
  réponse complète est au niveau 7.
- **La persistance** — comment une entité avec des champs privés se lit et
  s'écrit en base sans rouvrir le type. C'est le niveau 5, et c'est une vraie
  difficulté, pas un détail.
- **Le polymorphisme** — on n'a écrit aucune interface dans ce chapitre, et ce
  n'est pas un oubli. Il n'y avait pas deux implémentations de quoi que ce soit.
  C'est la leçon 2.2.

## 9. Le réflexe à installer

Devant chaque type que tu t'apprêtes à écrire, trois questions, dans cet ordre :

> 1. **Si je change un champ, est-ce toujours la même chose ?**
>    Non → valeur : champs privés, constructeur, immuable, comparable.
>    Oui → entité : identité explicite, `==` interdit, `SameAs` fourni.
> 2. **La valeur zéro est-elle un état valide ?**
>    Oui → fais-en le défaut raisonnable. Non → fais en sorte qu'elle ne se
>    comporte comme aucun état valide.
> 3. **Quel invariant ce type préserve-t-il, et où est-il vérifié ?**
>    Aucun → c'est une structure de transport, nomme-la comme telle.
>    Un ou plusieurs → chaque méthode qui n'en préserve aucun est une fonction
>    mal rangée.

Et devant un type qui existe déjà, un seul geste, qui prend une minute :

> **Écris la liste de ses champs, et barre ceux qui peuvent changer sans que la
> chose change.** Ce qui reste est l'identité. S'il ne reste rien, c'est une
> valeur. S'il reste tout, tu n'as pas encore compris le type. Et si ce qui
> reste et ce qui est barré décrivent **deux choses différentes**, tu viens de
> trouver les deux types que le métier avait déjà nommés.
