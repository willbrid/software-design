# Leçon 2.6 — Les limites : quand ces principes coûtent plus qu'ils ne rapportent

Les deux leçons précédentes ont mesuré ce que rapportent les cinq principes :
une méthode changée qui ne casse plus aucun paquet qui ne l'appelle pas, un
métier qui passe de 107 dépendances à 45, une violation de Liskov devenue
erreur de compilation. Elles ont aussi, en passant, mesuré ce qu'ils
**coûtent** : 238 lignes de batterie pour quatre signatures, un paquet de
domaine de plus, une racine de composition à tenir, un test d'architecture.

Cette leçon prend le second chiffre au sérieux. Elle ne dit pas « il ne faut
pas abuser » — tout le monde le dit, et personne ne sait où est l'abus. Elle
fait la même chose que les deux précédentes :

> Prendre un principe, construire le cas où il est appliqué **trop tôt** ou
> **au mauvais endroit**, et **mesurer** ce que ça coûte — avec du code qui
> compile et une commande qu'on peut lancer.

Quatre mesures :

| | Ce qu'on applique trop | Ce qu'on mesure |
|---|---|---|
| 1 | une abstraction dès la deuxième variante | le diff de la **troisième** variante, qui ne rentre pas |
| 2 | SRP lu comme « un type par rôle technique » | le nombre de fichiers touchés par **un champ** ajouté — et ce que le compilateur laisse passer |
| 3 | une interface partout | le prix à l'exécution d'un appel à travers une interface |
| 4 | une interface devant chaque type | le nombre d'interfaces qui n'ont **qu'une** implémentation, et aucune doublure |

Tout ce qui suit est mesuré sur un module vert sous `gofmt -l`,
`go vet ./...` et `go test -race -count=1 ./...`.

## 1. La mauvaise abstraction

### Le sujet

Deux exports d'opérations bancaires : CSV et JSON. Deux variantes, et la
tentation de factoriser est immédiate — même boucle, même gestion d'erreur.
J'ai écrit les deux versions.

**L'abstraite**, une interface dessinée pour les deux formats connus :

```go
// Format is what CSV and JSON have in common: a beginning, one line per
// operation, an end. JSON needs to know whether the line is the first one,
// for the comma: hence the index.
type Format interface {
    Header() string
    Line(i int, o operation.Operation) string
    Footer() string
}

// Export writes the operations in the given format.
func Export(w io.Writer, f Format, ops []operation.Operation) error {
    if _, err := io.WriteString(w, f.Header()); err != nil {
        return err
    }
    for i, o := range ops {
        if _, err := io.WriteString(w, f.Line(i, o)); err != nil {
            return err
        }
    }
    _, err := io.WriteString(w, f.Footer())
    return err
}
```

Déjà, l'interface porte la trace de ses deux premiers clients : `Line`
reçoit un indice, **parce que JSON a besoin de savoir s'il doit écrire une
virgule**. CSV l'ignore.

```go
type JSON struct{}

func (JSON) Header() string { return "[" }
func (JSON) Line(i int, o operation.Operation) string {
    sep := ","
    if i == 0 {
        sep = ""
    }
    return fmt.Sprintf("%s{\"date\":%q,\"label\":%q,\"amount\":%d}", sep, o.Date.Format(time.DateOnly), o.Label, o.Amount)
}
func (JSON) Footer() string { return "]\n" }
```

**La dupliquée**, une fonction par format, sans rien en commun :

```go
// JSON writes the operations as a JSON array.
func JSON(w io.Writer, ops []operation.Operation) error {
    if _, err := io.WriteString(w, "["); err != nil {
        return err
    }
    for i, o := range ops {
        sep := ","
        if i == 0 {
            sep = ""
        }
        if _, err := fmt.Fprintf(w, "%s{\"date\":%q,\"label\":%q,\"amount\":%d}", sep, o.Date.Format(time.DateOnly), o.Label, o.Amount); err != nil {
            return err
        }
    }
    _, err := io.WriteString(w, "]\n")
    return err
}
```

La boucle et la gestion d'erreur sont écrites deux fois. C'est le prix, et il
est visible.

### La troisième variante

Le métier demande un **relevé imprimable** dont l'entête annonce le nombre
d'opérations et le total — avant la première ligne. L'entête a besoin de
**toutes** les opérations. `Header()` n'en reçoit aucune.

Mesuré, en partant de l'état vert, sur des copies jetables :

```
== duplicated : 0 error(s), tests green, files: statement.go (new)
== abstracted, interface changed : 2 error(s)
   abstraction/abstracted/format_test.go:18:3: cannot use CSV{} (value of struct type CSV) as Format value in map literal: CSV does not implement Format (wrong type for method Header)
   abstraction/abstracted/format_test.go:19:3: cannot use JSON{} (value of struct type JSON) as Format value in map literal: JSON does not implement Format (wrong type for method Header)
== abstracted, full change : 0 error(s), tests green, files: csv.go, format.go, json.go, statement.go (new)
```

| | dupliquée | abstraite |
|---|---|---|
| fichiers existants modifiés | **0** | **3** — l'interface et les deux formats qui n'avaient rien demandé |
| fichiers neufs | 1 | 1 |
| erreurs de compilation au premier pas | 0 | 2 — CSV et JSON ne satisfont plus `Format` |

L'abstraction n'a pas rendu la troisième variante moins chère : elle l'a
rendue **plus** chère, et elle a fait toucher deux formats qui marchaient. Et
elle a encore empiré : `Header` reçoit maintenant des opérations que CSV et
JSON ignorent, comme `Line` reçoit un indice que CSV ignore. Chaque variante
qui ne rentre pas laisse un paramètre que les autres doivent porter.

L'autre réponse habituelle — une interface optionnelle,
`if r, ok := f.(WithSummary); ok` dans `Export` — évite de toucher CSV et
JSON, mais fait d'`Export` un aiguillage sur les cas particuliers. À la
cinquième variante, l'abstraction est un `switch` qui ne dit pas son nom.

> **Une abstraction faite sur deux variantes encode ce que deux variantes ont
> en commun. La troisième paie la différence.** Deux copies coûtent ce qu'elles
> coûtent, et ce coût est visible ; une mauvaise abstraction coûte à chaque
> variante qui ne rentre pas, et ce coût se répartit sur des fichiers qui
> n'avaient rien demandé.

La règle de décision n'est pas « attendre la troisième variante » par
superstition. C'est celle de la leçon 2.2 : **le relevé**. Une abstraction se
justifie quand l'historique montre que les variantes arrivent, et qu'elles se
ressemblent **là où l'abstraction les fait se ressembler**. Deux variantes ne
disent ni l'un ni l'autre.

## 2. Découper par rôle technique

### Le sujet

Le bénéficiaire d'un virement : un nom, un IBAN, une règle de validation, un
carnet qui les range, une forme JSON. Deux versions.

**La cohérente** — un paquet, 47 lignes :

```go
// Package payee is the payee of a transfer: a piece of data, its rules, and
// the address book that stores them. A single actor asks for its changes —
// the transfers business —, so a single package.
package payee

import (
    "errors"
    "strings"
)

var ErrInvalid = errors.New("payee: invalid")

// Payee is the data, as it is stored and exposed in JSON.
type Payee struct {
    Name string `json:"name"`
    IBAN string `json:"iban"`
}

// Validate applies the business rules.
func (p Payee) Validate() error {
    if strings.TrimSpace(p.Name) == "" {
        return errors.Join(ErrInvalid, errors.New("empty name"))
    }
    if len(p.IBAN) != 27 || !strings.HasPrefix(p.IBAN, "FR") {
        return errors.Join(ErrInvalid, errors.New("French IBAN expected"))
    }
    return nil
}
```

**L'éclatée** — six paquets, un par rôle technique, 101 lignes : un DTO, un
modèle, une validation, une conversion, un dépôt derrière une interface, un
service derrière une interface. Un découpage qu'on trouve partout, et qu'on
justifie au nom de SRP : *chaque type n'a qu'une responsabilité*.

```go
// Package mapping converts from one form to the other.
package mapping

import (
    "example/l26/split/layered/dto"
    "example/l26/split/layered/model"
)

func ToModel(d dto.Payee) model.Payee {
    return model.Payee{Name: d.Name, IBAN: d.IBAN}
}

func ToDTO(m model.Payee) dto.Payee {
    return dto.Payee{Name: m.Name, IBAN: m.IBAN}
}
```

### Un champ de plus

Le métier ajoute un **plafond** par bénéficiaire : validé (strictement
positif), rangé, exposé en JSON.

```
== cohesive : compiles True, tests green, production files: payee/payee.go
== layered : compiles True, tests green, production files: dto/dto.go, mapping/mapping.go, model/model.go, validation/validation.go
== layered, mapping forgotten : compiles True, tests RED, production files: dto/dto.go, model/model.go, validation/validation.go
   --- FAIL: TestRoundTrip (0.00s)
   service_test.go:22: validation: invalid payee
   --- FAIL: TestTheLimitRoundTrips (0.00s)
   service_test.go:39: validation: invalid payee
== layered, optional field, mapping forgotten : compiles True, tests green, production files: dto/dto.go, model/model.go
   probe_test.go:14: nickname sent "mum", nickname read back ""
```

Trois chiffres :

1. **Un fichier contre quatre.** Le même changement, demandé par le même
   acteur, touche le DTO, le modèle, la validation et la conversion. Ces
   quatre types n'ont pas quatre raisons de changer ; ils en ont **une**, et
   ils changent toujours ensemble.
2. **La conversion oubliée compile.** Avec des littéraux à champs nommés, un
   champ absent vaut zéro, et le compilateur ne dit rien. Les tests ne sont
   rouges ici que **par chance** : la nouvelle règle refuse le plafond zéro
   que la conversion oubliée produit.
3. **Sans cette chance, rien.** Un champ facultatif — un surnom, sans règle —
   ajouté au DTO et au modèle, conversion oubliée : **ça compile, les tests
   sont verts, et le surnom est perdu**. Le client l'envoie, le service ne le
   rend pas.

C'est SRP **lu à l'envers**. La leçon 2.4 l'a défini par les **acteurs** : une
responsabilité, c'est une source de changements. Le DTO, le modèle, la
validation et la conversion d'un bénéficiaire ont la même source — le métier
des virements. Les couper, c'est créer quatre endroits à garder cohérents
pour un seul changement, et le compilateur ne garde pas cette cohérence.

> **Le critère de SRP est la co-variation, pas le rôle technique.** Des types
> qui changent toujours ensemble sont une seule responsabilité écrite en
> plusieurs fichiers. Le sondage de la leçon 2.4 le dirait de l'autre côté :
> la cohésion se mesure dans le temps, avec `git log`.

## 3. Le prix d'une interface à l'exécution

On entend souvent qu'une interface « coûte cher » en Go : appel indirect,
pas d'inlining, allocation. Je l'ai mesuré, sur un appel trivial — appliquer
un taux à un montant —, mille fois par itération, par le type concret et par
une interface :

```go
// Rate applies a rate in basis points.
type Rate interface {
    Apply(cents int64) int64
}

// Fixed is the only implementation.
type Fixed struct{ BasisPoints int64 }

func (f Fixed) Apply(c int64) int64 { return c * f.BasisPoints / 10_000 }

// SumConcrete applies the rate to each amount, through the concrete type.
func SumConcrete(f Fixed, amounts []int64) int64 {
    var s int64
    for _, a := range amounts {
        s += f.Apply(a)
    }
    return s
}

// SumInterface does the same through the interface.
func SumInterface(r Rate, amounts []int64) int64 {
    var s int64
    for _, a := range amounts {
        s += r.Apply(a)
    }
    return s
}

// NewConcrete returns a value.
func NewConcrete(bp int64) Fixed { return Fixed{BasisPoints: bp} }

// NewInterface returns the same value, converted to an interface.
func NewInterface(bp int64) Rate { return Fixed{BasisPoints: bp} }

// NewOpaque is NewInterface when the compiler cannot see through: a factory
// in another package, chosen at run time, or too big to be inlined.
// go:noinline simulates that case.
//
//go:noinline
func NewOpaque(bp int64) Rate { return Fixed{BasisPoints: bp} }
```

Ce qu'il faut lire :

- **L'appel à travers l'interface coûte environ 7 % de plus** dans la boucle —
  1 300 ns environ contre 1 230 pour mille appels, soit **moins d'un dixième
  de nanoseconde par appel**. C'est l'appel indirect qui empêche d'inliner
  `Apply` dans `SumInterface`.
- **Construire à travers une interface ne coûte rien** quand le compilateur
  voit le type concret : `NewInterface` est inlinée, et la valeur ne
  quitte pas la pile — 1,4 ns, comme le concret, une fois passées les deux
  premières exécutions, que la machine a ralenties (2,0 et 1,7 ns : c'est du
  bruit, et c'est pour ça qu'on lance cinq fois).
- **Quand il ne le voit pas** — une fabrique dans un autre paquet, choisie à
  l'exécution, ou trop grosse pour être inlinée, que `//go:noinline` simule
  ici —, la valeur **s'échappe sur le tas** : dix fois plus lent, 15 à 17 ns.

Un détail de mesure, qu'il faut dire parce qu'il m'a arrêté : le banc de la
fabrique opaque affiche `8 B/op` et `0 allocs/op`. Huit octets sans
allocation, ce n'est pas possible. J'ai compté directement, avec
`runtime.MemStats` sur un million d'appels :

```
opaque : 1.000 allocation(s), 8.0 byte(s) per call
inlined: 0.000 allocation(s), 0.0 byte(s) per call
```

Une allocation de huit octets par appel. Je n'ai pas d'explication certaine de
l'affichage du banc ; la mesure directe fait foi, et elle est maintenant un
test.

> **La performance n'est presque jamais l'argument contre une interface.**
> Moins d'un dixième de nanoseconde par appel, rien du tout à la
> construction quand le compilateur voit à travers. Elle le devient sur un
> chemin chaud qui fabrique ses valeurs à travers une fabrique opaque — et
> là, la mesure le dira, pas l'intuition.

Le vrai coût d'une interface n'est pas à l'exécution. Il est à la **lecture** :
un appel `s.store.Save(m)` ne dit plus où va le code, et il faut
chercher l'implémentation. C'est la quatrième mesure.

## 4. L'interface à une seule implémentation

Une interface a une raison d'être quand il y a **plus d'une chose** derrière :
deux implémentations, ou une implémentation et une doublure de test, ou une
frontière qu'on veut protéger (leçon 2.5). Sans aucune des trois, elle est une
indirection sans bénéficiaire : le lecteur cherche l'implémentation, il n'y en
a qu'une, et il a perdu le temps de la chercher.

Le sondage compte, pour chaque interface d'un module, ses implémentations de
production et ses doublures de test. Sur le module de cette leçon :

```
abstraction/abstracted.Format      production 2 [abstraction/abstracted.CSV abstraction/abstracted.JSON], tests 0
indirection.Rate                   production 1 [indirection.Fixed], tests 0
probe/testdata/double.Clock        production 1 [probe/testdata/double.System], tests 1
split/layered/service.Service      production 2 [split/cohesive/payee.AddressBook split/layered/service.service], tests 0
split/layered/store.Store          production 1 [split/layered/store.Memory], tests 0
```

Deux interfaces n'ont **qu'une implémentation et aucune doublure** :
`store.Store` et `indirection.Rate`. La seconde existe pour la mesure 3 ;
la première est une indirection pure — personne ne la double, personne ne
l'implémente une deuxième fois.

Et le sondage dit aussi ce qu'il ne sait pas faire : il compte
`payee.AddressBook` comme une implémentation de `service.Service`, parce
que `AddressBook` a des méthodes `Add` et `Read` — avec d'autres signatures. Il
ne lit que les noms :

```go
// TestTheProbesFalsePositive: AddressBook has Add and Read methods, like
// service.Service, with other signatures. The probe only reads names and
// counts it as an implementation. It therefore overestimates
// implementations — and can hide an interface that has only one, like
// Service here.
func TestTheProbesFalsePositive(t *testing.T) {
    s := measure(t)["split/layered/service.Service"]
    if !slices.Contains(s.Production, "split/cohesive/payee.AddressBook") {
        t.Fatalf("the false positive is gone: %v", s.Production)
    }
}
```

Son erreur va toujours dans le même sens : il **surestime** les
implémentations. Il peut donc **cacher** une interface à une seule
implémentation — c'est le cas de `service.Service`, qui n'en a qu'une — mais
jamais en inventer une. Une interface qu'il signale est vraiment seule.

**Ce qu'on fait d'une interface seule** : on la supprime, et le consommateur
prend le type concret. Le jour où une deuxième implémentation ou un test en
aura besoin, l'interface reviendra — déclarée chez le consommateur, à
l'endroit où elle sert, avec les seules méthodes qu'il appelle (leçon 2.5).
Le coût de la réintroduire est connu : zéro ligne dans l'implémentation, une
racine de composition à mettre à jour.

Il y a une exception, et elle compte : **la frontière d'infrastructure**. Le
`Store` de la leçon 2.5 n'avait qu'une implémentation de production, mais il
séparait le métier de `database/sql`, et le test d'architecture le gardait.
Une interface seule **à une frontière que le graphe d'imports doit
respecter** a un bénéficiaire : le graphe.

## 5. La grille

Chaque ligne est une décision, et chaque colonne une mesure qu'on sait
maintenant faire.

| Principe | Appliquer quand… | S'abstenir quand… | La mesure qui tranche |
|---|---|---|---|
| **une abstraction** (OCP) | le relevé montre que les variantes arrivent, et qu'elles se ressemblent là où l'abstraction les unit | il n'y a que deux variantes, ou la troisième ne ressemble pas aux deux premières | le diff de la variante suivante : fichiers existants touchés |
| **une coupe** (SRP) | les deux morceaux changent pour des raisons différentes, demandées par des acteurs différents | les morceaux changent toujours ensemble | `git log` : les commits qui touchent l'un touchent-ils l'autre ? |
| **une interface** (ISP, DIP) | il y a deux implémentations, ou une doublure, ou une frontière à garder | il n'y a qu'une chose derrière, et aucune frontière | le sondage des implémentations, et `go list -deps` |
| **une batterie** (LSP) | il y a — ou il y aura — une deuxième implémentation | l'interface n'a qu'une implémentation et n'en aura pas | le nombre d'implémentations, encore |
| **une indirection pour la performance** | jamais par principe | toujours par principe | `go test -bench` et `-gcflags=-m`, sur le chemin chaud réel |

Une remarque sur la dernière ligne : les principes
n'ont pas de « coût en performance » qui mérite une ligne à part. Ce qui en
a un, c'est une fabrique opaque sur un chemin chaud, et ça se mesure.

## 6. Ce que coûte de ne pas les appliquer

Il faut être honnête dans l'autre sens. La version dupliquée de la section 1
écrit deux fois la boucle et la gestion d'erreur. Le jour où cette gestion
d'erreur a un défaut, il faut le corriger **deux fois**, et le compilateur ne
dira pas qu'on a oublié la seconde copie. La cohérente de la section 2 met la
validation, le stockage et la forme JSON dans un seul paquet : le jour où le
stockage passe sur PostgreSQL, ce paquet tirera `database/sql` — et il faudra
alors le couper, au bon endroit, celui que la leçon 2.5 a mesuré.

Ce n'est pas un argument pour appliquer les principes d'avance. C'est
l'argument pour les appliquer **au moment où le coût de ne pas les appliquer
devient mesurable** : la deuxième copie d'un défaut, la première dépendance
d'infrastructure, la deuxième implémentation. Avant, on paie pour un
changement qui n'arrivera peut-être pas ; après, on paie le changement réel,
une fois.

## 7. Les trois erreurs qui restent

### « SOLID est une liste de bonnes pratiques, plus on en applique mieux c'est »

Non. Chaque principe a un coût mesuré dans ces trois leçons, et un bénéfice
qui dépend d'un changement **à venir** : une variante, une deuxième
implémentation, une frontière. Sans ce changement, il ne reste que le coût. Les
principes sont des **paris** sur l'avenir du code, et le relevé dit lesquels
gagner.

### « YAGNI veut dire ne jamais abstraire »

Non plus. YAGNI dit de ne pas construire pour un changement **supposé**. Il ne
dit rien contre un changement **mesuré** : onze types de notification en
dix-huit mois (correction 2.4/2), c'est un axe qui bouge, et l'ouvrir n'est pas
spéculer. La règle n'est pas « jamais », c'est « pas avant le relevé ».

### « Les interfaces coûtent cher en Go »

Mesuré : moins d'un dixième de nanoseconde par appel, rien à la construction
quand le compilateur voit à travers. L'argument de performance contre une
interface est presque toujours faux, et quand il est vrai, c'est un banc qui
le montre, sur le chemin chaud, pas une règle générale.

## 8. Le lien avec la production

| Ce que tu as déjà vu en production | La limite, et sa mesure |
|---|---|
| une interface `Export` avec des paramètres que la moitié des implémentations ignorent | la mauvaise abstraction. Compte les paramètres ignorés : chacun est une variante qui ne rentrait pas |
| un champ ajouté à l'API, et absent de la base trois semaines plus tard | le découpage par rôle technique. La conversion oubliée compile |
| un « `UserServiceImpl` » derrière un « `UserService` », sans autre implémentation ni doublure | l'interface seule. Le sondage la trouve |
| une revue qui refuse une interface « pour la performance » | mesure-le : `go test -bench`, `-gcflags=-m` |
| une correction appliquée dans une copie et pas dans l'autre | le coût de la duplication. C'est le signal pour factoriser — à partir de ce que les copies ont **vraiment** en commun |

## 9. Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Une abstraction faite sur deux variantes encode leur ressemblance ; la troisième paie la différence. Mesuré : 3 fichiers existants touchés contre 0, et 2 erreurs de compilation dans des formats qui n'avaient rien demandé. |
| ⚫ | Chaque variante qui ne rentre pas laisse un paramètre que les autres doivent porter. |
| ⚫ | SRP se lit par les acteurs, pas par les rôles techniques. Mesuré : un champ ajouté touche 1 fichier contre 4. |
| ⚫ | Entre des types découpés par rôle, le compilateur ne garde pas la cohérence. Mesuré : une conversion oubliée compile, les tests restent verts, la donnée est perdue. |
| ⚫ | Un appel à travers une interface coûte moins d'un dixième de nanoseconde de plus. La construction ne coûte rien quand le compilateur voit le type ; une fabrique opaque alloue, et coûte dix fois plus. |
| ⚫ | Un banc peut afficher un chiffre incohérent. Quand il le fait, on compte autrement, et la mesure directe devient un test. |
| ⚫ | Une interface à une seule implémentation, sans doublure et sans frontière à garder, est une indirection sans bénéficiaire. Le sondage la trouve ; son erreur va toujours dans le sens de la surestimation. |
| ⚫ | Les principes sont des paris sur un changement à venir. Le relevé dit lesquels gagner ; sans lui, il ne reste que le coût. |
| ⚫ | Ne pas appliquer un principe a aussi un coût. On l'applique au moment où ce coût devient mesurable : la deuxième copie d'un défaut, la première dépendance d'infrastructure, la deuxième implémentation. |

## 10. Approfondissement

### « La mauvaise abstraction »

Sandi Metz a nommé le phénomène de la section 1 : *la duplication coûte bien
moins cher que la mauvaise abstraction*. Son conseil pratique est celui qu'on
oublie : quand une abstraction s'est remplie de paramètres et de cas
particuliers, **la défaire** — réintroduire la duplication en recopiant
l'abstraction dans chaque appelant, simplifier chaque copie pour ce dont elle a
vraiment besoin, et seulement ensuite chercher la bonne abstraction. Ce n'est
pas un échec ; c'est la mesure qui a enfin assez de variantes pour dire où est
la ressemblance.

### « Un peu de copie vaut mieux qu'un peu de dépendance »

Les proverbes de Go le disent ainsi, et c'est la même idée appliquée aux
paquets : importer un paquet pour une fonction de trois lignes, c'est prendre
toutes ses dépendances et tous ses changements. La leçon 2.5 l'a mesuré du
côté des types : `fraud` passait de 200 dépendances à une en ne nommant plus
aucun type du prestataire.

### La dévirtualisation guidée par profil

Depuis Go 1.21, la compilation guidée par profil (`-pgo`) peut
**dévirtualiser** un appel d'interface sur un chemin chaud : si le profil
montre qu'une interface pointe presque toujours vers le même type concret, le
compilateur ajoute un test de type et un appel direct inlinable. La mesure 3
change alors encore en faveur de l'interface. Ce n'est pas une raison d'en
mettre partout ; c'est une raison de plus de ne pas en retirer pour la
performance sans profil.

## 11. Le réflexe à installer

> **Devant une abstraction qu'on te propose**
> Combien de variantes existent, et que dit le relevé de celles qui
> viennent ? Si la réponse est « deux, et on ne sait pas », écris les deux, et
> laisse la duplication visible.
>
> **Devant une découpe**
> Prends le dernier changement réel, et compte les fichiers qu'il a touchés.
> Si chaque changement touche les mêmes N fichiers, ces N fichiers sont une
> seule responsabilité.
>
> **Devant une interface**
> Qu'y a-t-il derrière ? Deux implémentations, une doublure, ou une frontière
> que le graphe doit respecter. Sinon, le type concret.

Et le geste d'une minute, devant n'importe quel principe qu'on te cite :

> **Demande quel changement il prépare, et quand ce changement est arrivé
> pour la dernière fois.** S'il n'est jamais arrivé, le principe n'a encore
> rien rapporté — et il a déjà coûté.
