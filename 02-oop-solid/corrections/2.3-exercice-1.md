# Correction 2.3 — Exercice 1 : la plateforme portée depuis Java

> Rappel de l'énoncé : un type `Base` qui porte une « méthode modèle »
> `Envoyer`, quatre morceaux non exportés, deux types qui incorporent `Base`
> et en « surchargent » trois et deux. Vingt-trois tests verts, 94 % de
> couverture.

Tout ce qui suit est mesuré sur un module qui compile, dont les deux paquets
de test passent sous `go vet` et `go test -race -count=1`. Le paquet `avant`
— le code de l'énoncé — est **conservé** dans le module : sans lui, « les
trois canaux rendaient le même texte » serait une affirmation, et l'épreuve
de non-régression de la section 6 n'aurait rien à comparer.

## 1. Les trois appels

### Ce qu'un développeur venu de Java écrit

| | Prédiction naturelle |
|---|---|
| `a` (SMS) | accepté, pas de ligne `Sujet:`, corps tronqué à 160 |
| `b` (Courrier) | `Expediteur: BANQUE (courrier)`, corps en majuscules, daté |
| `c` (Base) | l'entête et le corps par défaut |

### Ce que le programme rend

```
=== a / SMS ===
err = notification : envoi refuse
(0 octets)

=== b / Courrier ===
err = <nil>
De: BANQUE
A: client@example.cm
Sujet: [NOTIF] Solde

Votre solde est de 12 400 FCFA
(84 octets)

=== c / Base ===
err = <nil>
De: BANQUE
A: client@example.cm
Sujet: [NOTIF] Solde

Votre solde est de 12 400 FCFA
(84 octets)
```

**Zéro sur trois.** Et le troisième est le plus parlant : `b` et `c` rendent
les **mêmes 84 octets**. `Courrier` déclare deux méthodes, et il se comporte
exactement comme s'il n'en déclarait aucune.

Voilà la mesure, pas la prédiction :

```go
// TestLesTroisPredictions mesure les trois appels de la question 1, et chacun
// contredit ce qu'un developpeur venu de Java predit.
func TestLesTroisPredictions(t *testing.T) {
    b := avant.Base{Expediteur: "BANQUE", Horloge: horlogeFixe}

    // 1. Le SMS est REFUSE, alors qu'il surcharge destinataireValide pour
    //    accepter neuf chiffres. Base.Envoyer appelle b.destinataireValide
    //    avec un recepteur de type Base, qui exige un arobase.
    sms := avant.SMS{Base: b, Operateur: "MTN"}
    if _, err := sms.Envoyer("677123456", "Solde", "12 400 FCFA"); !errors.Is(err, avant.ErrEnvoiRefuse) {
        t.Errorf("le SMS a ete accepte : la surcharge a ete appelee — %v", err)
    }

    // 2. Le courrier passe, mais avec l'entete et le corps PAR DEFAUT.
    courrier := avant.Courrier{Base: b, CodePostal: "BP 1234"}
    sortie, err := courrier.Envoyer("client@example.cm", "Releve", "votre releve")
    if err != nil {
        t.Fatalf("Envoyer : %v", err)
    }
    if !strings.HasPrefix(sortie, "De: BANQUE") {
        t.Errorf("entete = %q, attendu celle de Base", premiereLigne(sortie))
    }
    if strings.Contains(sortie, "Expediteur:") {
        t.Error("l'entete de Courrier a ete appelee")
    }
    if strings.Contains(sortie, "VOTRE RELEVE") {
        t.Error("le corps de Courrier a ete appele")
    }
    if strings.Contains(sortie, "Fait a Douala") {
        t.Error("la date de Courrier a ete ajoutee")
    }

    // 3. La Base rend exactement la meme chose que le Courrier.
    base, err := b.Envoyer("client@example.cm", "Releve", "votre releve")
    if err != nil {
        t.Fatal(err)
    }
    if base != sortie {
        t.Fatal("Base et Courrier rendent des textes differents")
    }
    t.Logf("Base et Courrier rendent les memes %d octets", len(base))
}
```

## 2. Pourquoi le SMS est refusé

`SMS` déclare bien `destinataireValide` qui accepte neuf chiffres. Elle n'est
jamais appelée.

`Envoyer` est déclarée sur `Base`. Son récepteur `b` est de type `Base`. À la
ligne `if !b.destinataireValide(destinataire)`, le compilateur cherche une
méthode `destinataireValide` **sur le type `Base`**, la trouve, et écrit
l'appel. Définitivement. `Base` ne sait pas que `SMS` existe, et il n'y a
aucun mécanisme en Go pour le lui apprendre : **l'incorporation ne crée pas de
dispatch virtuel**.

L'écart entre les deux journaux est la partie qui coûte le plus cher :

| | Ce qui est visible |
|---|---|
| le client | *« envoi refusé »*, sans autre indication, pour un numéro parfaitement valide |
| les journaux du développeur | `notification : envoi refuse` — **la même ligne**, sans le canal, sans le destinataire, sans la raison |

L'erreur est une variable de paquet partagée par tous les canaux. Elle ne
nomme ni le canal ni le motif. Un développeur qui lit cette ligne ne peut pas
distinguer « le numéro est mal formé » de « ce canal n'a jamais eu le droit de
valider ». C'est le deuxième défaut, et il est indépendant du premier : même
avec le dispatch virtuel, ce message resterait inutilisable.

## 3. Le critère appliqué à `Base`

> Un type est sûr à incorporer-et-surcharger si et seulement si **aucune de
> ses méthodes n'appelle une autre de ses méthodes sur son propre récepteur**.

`Base` a cinq méthodes. Une seule en appelle d'autres, et elle en appelle
**quatre** :

| Méthode de `Base` | Appelle sur `b` |
|---|---|
| `destinataireValide` | — |
| `sujet` | — |
| `corps` | — |
| `entete` | — |
| `Envoyer` | `destinataireValide`, `entete`, `sujet`, `corps` |

Quatre appels internes. `Base` échoue au critère, et il y échoue de la pire
façon : **les quatre méthodes qu'on est censé surcharger sont exactement les
quatre qui sont appelées en interne**. Ce n'est pas un type qui a un appel
interne par accident ; c'est un type dont tout l'intérêt supposé repose sur
des appels internes.

Conséquence pour `SMS` et `Courrier` : **aucune de leurs cinq méthodes
déclarées n'est atteignable par `Envoyer`**. Elles compilent, elles sont
correctes, elles sont couvertes par les tests, et elles sont mortes.

## 4. Les méthodes exportées — et le chiffre qui surprend

La question attend « combien de méthodes `SMS` exporte-t-il de trop ». La
réponse mesurée est **aucune** :

```go
// TestLeNombreDeMethodesExporteesEstUnPiege est la reponse a la question 4, et
// elle ne donne pas le chiffre attendu.
//
// Les trois types n'exportent QU'UNE methode chacun, parce que les quatre
// morceaux sont non exportes. Il n'y a donc aucune fuite de methode ici — et
// c'est une bonne nouvelle qui cache une mauvaise.
//
// La fuite est ailleurs : le champ Horloge est EXPORTE, donc n'importe quel
// appelant peut remplacer l'horloge de n'importe quel canal. L'incorporation
// promeut aussi les CHAMPS, et on y pense moins qu'aux methodes.
func TestLeNombreDeMethodesExporteesEstUnPiege(t *testing.T) {
    for nom, typ := range map[string]reflect.Type{
        "Base":     reflect.TypeOf(avant.Base{}),
        "SMS":      reflect.TypeOf(avant.SMS{}),
        "Courrier": reflect.TypeOf(avant.Courrier{}),
    } {
        if n := typ.NumMethod(); n != 1 {
            t.Errorf("%s exporte %d methodes, attendu 1", nom, n)
        }
    }
    // Mais les champs promus, eux, sont exportes.
    sms := reflect.TypeOf(avant.SMS{})
    if _, ok := sms.FieldByName("Horloge"); !ok {
        t.Error("le champ Horloge n'est pas promu au niveau de SMS")
    }
    if _, ok := sms.FieldByName("Expediteur"); !ok {
        t.Error("le champ Expediteur n'est pas promu au niveau de SMS")
    }
    t.Log("SMS exporte 1 methode et 3 champs, dont 2 promus")
}
```

Les trois types exportent **une** méthode chacun, parce que les quatre
morceaux sont non exportés. De ce côté-là, le modèle est propre.

La fuite est ailleurs, et elle est plus insidieuse : **l'incorporation promeut
aussi les champs**. `SMS` a trois champs exportés, dont deux promus :

| Champ de `SMS` | D'où | Ce qu'il permet |
|---|---|---|
| `Operateur` | déclaré | rien (section 5) |
| `Expediteur` | promu de `Base` | n'importe qui peut réécrire l'expéditeur d'un canal construit |
| `Horloge` | promu de `Base` | **n'importe qui peut remplacer l'horloge de n'importe quel canal, en production** |

`sms.Horloge = func() time.Time { return temps.Zero }` compile et s'exécute,
depuis n'importe quel paquet. Une dépendance qu'on croyait injectée à la
construction est en fait modifiable à vie, sur chaque exemplaire.

> On compte les méthodes promues parce que la leçon parle de méthodes.
> Les champs promus se comptent aussi, et ils ouvrent l'état, pas le
> comportement.

## 5. Pourquoi `Operateur` et `CodePostal` ne servent à rien

Ce n'est pas un oubli : **la forme du code les rend inutilisables**.

`Operateur` est un champ de `SMS`. Pour l'utiliser dans la mise en forme, il
faudrait l'atteindre depuis le code qui met en forme. Or ce code est dans
`Base.Envoyer`, dont le récepteur est de type `Base` — un type qui ne connaît
pas `SMS` et ne peut donc pas voir ses champs.

Le seul endroit d'où `Operateur` est visible, c'est une méthode de `SMS` ; et
les méthodes de `SMS` ne sont jamais appelées. Les deux moitiés du problème se
referment l'une sur l'autre :

```
Base.Envoyer  voit le squelette, ne voit pas Operateur
SMS.corps     voit Operateur, n'est jamais appelee
```

C'est la différence qui compte avec l'héritage classique : là-bas, le
squelette est résolu **sur le type dynamique**, donc il atteint les champs du
sous-type via les méthodes redéfinies. Ici, le squelette est résolu **sur le
type statique**, donc il n'atteint rien.

> Deux champs morts dans un type qui compile, ce n'est pas un code
> négligé : c'est la signature d'un dispatch qui n'a pas lieu.

## 6. La correction

Un seul changement de forme, et tout le reste en découle : **le squelette
devient une fonction**, et ce qui variait devient une interface déclarée par
cette fonction.

### Le diff conceptuel

| | Avant | Après |
|---|---|---|
| le squelette | méthode `Envoyer` sur `Base` | **fonction** `notification.Envoyer` |
| les morceaux | méthodes non exportées de `Base`, redéclarées | **méthodes exportées** des types de canal |
| le lien | incorporation de `Base` | **paramètre** de type `Canal` |
| `Base` | existe | **n'existe plus** |
| l'horloge | champ exporté promu | paramètre du squelette, redescendu en argument |

### L'interface

```go
// Canal est l'interface DU SQUELETTE. Cinq methodes : les quatre morceaux
// de l'enonce, qui varient tous les trois canaux, plus Nom, qui ne sert pas
// a mettre en forme mais a ecrire un refus qu'on puisse lire a trois heures
// du matin.
//
// Elle est declaree ici, chez l'appelant. Sa signature ne nomme que des
// chaines et un time.Time : du vocabulaire universel, donc une
// implementation n'a pas a importer ce paquet.
//
// Cinq methodes est beaucoup, et il faut le dire : Valide est une
// VALIDATION, trois autres sont des MISES EN FORME, et Nom est une
// IDENTITE. Un appelant qui ne voudrait que valider porterait quand meme les
// quatre autres dans son double de test. C'est le sujet de la lecon 2.5 ;
// ici on garde une interface, parce qu'il n'y a qu'un appelant.
type Canal interface {
    Nom() string
    Valide(destinataire string) bool
    Entete(expediteur string) string
    Sujet(objet string) string
    Corps(message string, maintenant time.Time) string
}
```

**Cinq méthodes**, et il faut dire pourquoi c'est beaucoup : quatre sont les
morceaux de l'énoncé, la cinquième (`Nom`) existe uniquement pour que le refus
soit lisible. C'est déjà une interface qui mélange une validation, trois mises
en forme et une identité — la leçon 2.5 y reviendra. Ici on la garde entière,
parce qu'il n'y a **qu'un seul appelant**.

Elle est déclarée **chez l'appelant**, dans `notification`, et sa signature ne
nomme que `string` et `time.Time`. Conséquence mesurée :

```
$ go list -f '{{join .Imports " "}}' ./ex1/canaux
strings time unicode/utf8
```

`canaux` **n'importe pas** `notification`. Un quatrième canal peut vivre dans
un autre dépôt.

### Le squelette

```go
// Envoyer assemble le message. C'est le squelette, et c'est une fonction.
func Envoyer(c Canal, expediteur, destinataire, objet, message string, horloge func() time.Time) (string, error) {
    if c == nil {
        return "", ErrCanalAbsent
    }
    if horloge == nil {
        return "", ErrHorlogeAbsente
    }
    if !c.Valide(destinataire) {
        return "", fmt.Errorf("%w : %q pour le canal %s",
            ErrDestinataireInvalide, destinataire, c.Nom())
    }
    maintenant := horloge()
    var sb strings.Builder
    sb.WriteString(c.Entete(expediteur))
    sb.WriteString("\nA: ")
    sb.WriteString(destinataire)
    // Un sujet vide ne produit pas une ligne « Sujet: » vide : un SMS n'a
    // pas de sujet, et la ligne vide se retrouverait dans le message.
    if sujet := c.Sujet(objet); sujet != "" {
        sb.WriteString("\nSujet: ")
        sb.WriteString(sujet)
    }
    sb.WriteString("\n\n")
    sb.WriteString(c.Corps(message, maintenant))
    return sb.String(), nil
}
```

Trois choses à noter, dans l'ordre où elles coûteraient cher si elles
manquaient :

1. **`c == nil` est traité en premier.** Un canal absent est une erreur, pas
   un canal par défaut — l'énoncé est précisément l'histoire d'un
   comportement par défaut qui s'est appliqué sans que personne ne le voie.
2. **`horloge == nil` aussi.** Sans cette ligne, un canal qui date ses envois
   panique au premier appel, en production, et pas en test.
3. **Le sujet vide ne produit pas de ligne vide.** Le SMS n'a pas de sujet ;
   dans le modèle d'origine, `sujet()` rendant `""` laissait quand même la
   ligne `Sujet: ` dans le message, et personne ne l'avait vue.

### Le canal SMS, avec son `Operateur` vivant

```go
// SMS est le canal par message court.
//
// Operateur est utilise, cette fois : il apparait dans l'entete. Dans le
// modele d'origine le champ existait et ne pouvait pas servir, parce que le
// squelette ne voyait jamais le type qui le portait.
type SMS struct {
    Operateur string
    // LongueurMaximale vaut 160 quand elle est nulle. La valeur zero d'un
    // entier ne tronque rien, et un SMS sans limite n'est pas un SMS.
    LongueurMaximale int
}

const longueurSMSParDefaut = 160

func (SMS) Nom() string { return "SMS" }

func (SMS) Valide(d string) bool {
    if len(d) != 9 {
        return false
    }
    for _, r := range d {
        if r < '0' || r > '9' {
            return false
        }
    }
    return true
}

func (s SMS) Entete(expediteur string) string {
    if s.Operateur == "" {
        return "De: " + expediteur
    }
    return "De: " + expediteur + " via " + s.Operateur
}

// Sujet rend la chaine vide : un SMS n'a pas de sujet, et le squelette sait
// quoi faire d'un sujet vide.
func (SMS) Sujet(string) string { return "" }

func (s SMS) Corps(message string, _ time.Time) string {
    max := s.LongueurMaximale
    if max <= 0 {
        max = longueurSMSParDefaut
    }
    if len(message) <= max {
        return message
    }
    if max <= 3 {
        return message[:max]
    }
    // La coupe se fait sur les RUNES et non sur les octets : couper « é » au
    // milieu produit un octet invalide, et le client voit un losange noir.
    coupe := message
    for len(coupe) > max-3 {
        _, taille := utf8.DecodeLastRuneInString(coupe)
        coupe = coupe[:len(coupe)-taille]
    }
    return coupe + "..."
}
```

`Operateur` sert, maintenant, parce que la méthode qui le lit est celle que le
squelette appelle. Et la troncature compte en **runes** : 158 caractères
accentués font 316 octets, et couper à l'octet 157 produit un caractère
invalide — le losange noir côté client.

### La non-régression

Un refactoring doit prouver qu'il n'a rien changé pour ce qui marchait :

```go
// TestLeFormatCourrielEstPreserveOctetPourOctet : la verification qu'un
// refactoring doit toujours porter.
//
// Le squelette corrige, avec le canal Courriel, rend exactement ce que
// rendait le squelette casse. Le refactoring n'a rien change pour le seul
// canal qui marchait.
func TestLeFormatCourrielEstPreserveOctetPourOctet(t *testing.T) {
    ancien, err := avant.Base{Expediteur: "BANQUE", Horloge: horloge}.
        Envoyer("client@example.cm", "Releve", "votre releve")
    if err != nil {
        t.Fatal(err)
    }
    nouveau, err := notification.Envoyer(canaux.Courriel{}, "BANQUE",
        "client@example.cm", "Releve", "votre releve", horloge)
    if err != nil {
        t.Fatal(err)
    }
    if ancien != nouveau {
        t.Fatalf("le format par defaut a change\nancien :\n%s\nnouveau :\n%s", ancien, nouveau)
    }
    t.Logf("%d octets identiques", len(nouveau))
}
```

```
=== RUN   TestLeFormatCourrielEstPreserveOctetPourOctet
    notification_test.go:78: 67 octets identiques
--- PASS
```

Le canal `Courriel` rend **octet pour octet** ce que rendait `Base`. C'est
pour cette seule ligne que le paquet `avant` reste dans le module.

Et l'inverse du défaut :

```
=== RUN   TestLesTroisCanauxRendentTroisTextesDifferents
    notification_test.go:55: courriel 67 octets, sms 45, courrier 121
--- PASS
```

Trois canaux, trois longueurs. Dans l'énoncé, deux des trois faisaient 84.

### Les assertions de conformité

```go
// Les assertions de conformite. Sans elles, ajouter une methode a Canal ne
// produit aucune erreur de compilation.
var (
    _ notification.Canal = canaux.Courriel{}
    _ notification.Canal = canaux.SMS{}
    _ notification.Canal = canaux.Courrier{}
)
```

Sans ces trois lignes, ajouter une méthode à `Canal` ne produit **aucune**
erreur de compilation tant que personne ne construit la liste des canaux —
c'est la mesure de la correction 2.2/4, et elle vaut ici aussi. Dans ce
module elles vivent dans le fichier de test parce que le module n'a pas de
racine de composition ; dès qu'il en aura une, elles y descendront.

## 7. La forme qu'avaient forcément les 23 tests

Pour être verts sur un code faux, ils ne pouvaient avoir qu'**une** forme :
chaque morceau appelé **directement**, jamais le squelette.

```go
// TestLesMorceauxSurchargesSontCorrects est la forme qu'avaient les 23 tests
// verts de l'enonce, et c'est la reponse a la question 7.
//
// Il appelle chaque morceau DIRECTEMENT. Les surcharges sont correctes, donc
// il passe. Il ne touche jamais au squelette, donc il ne peut pas voir que
// le squelette ne les appelle pas.
//
//    Un test qui verifie les morceaux un par un ne dit rien de leur
//    assemblage. Et c'est l'assemblage qui part chez le client.
func TestLesMorceauxSurchargesSontCorrects(t *testing.T) {
    b := Base{Expediteur: "BANQUE", Horloge: func() time.Time {
        return time.Date(2026, 6, 15, 10, 0, 0, 0, time.UTC)
    }}

    sms := SMS{Base: b, Operateur: "MTN"}
    if !sms.destinataireValide("677123456") {
        t.Error("SMS.destinataireValide refuse neuf chiffres")
    }
    if sms.sujet("Solde") != "" {
        t.Error("SMS.sujet ne rend pas la chaine vide")
    }

    courrier := Courrier{Base: b, CodePostal: "BP 1234"}
    if courrier.entete() != "Expediteur: BANQUE (courrier)" {
        t.Errorf("Courrier.entete = %q", courrier.entete())
    }
    if got := courrier.corps("votre releve"); got == "votre releve" {
        t.Error("Courrier.corps ne met pas en majuscules")
    }
    t.Log("les quatre morceaux surcharges sont corrects, et aucun n'est appele par Envoyer")
}
```

Ce test passe. Il est honnête, il est précis, il couvre 94 % des lignes — et
il ne dit rien de ce qui part chez le client, parce qu'il ne traverse jamais
`Envoyer`.

La couverture le confirme : les quatre morceaux de `SMS` et de `Courrier` sont
appelés, donc comptés. Les lignes sont couvertes. **Le chemin ne l'est pas.**

> Un test qui vérifie les morceaux un par un ne dit rien de leur
> assemblage. Et c'est l'assemblage qui part chez le client.

### Le test qui aurait été rouge le premier jour

En une phrase : **deux canaux différents doivent rendre deux textes
différents.**

```go
// TestLeSqueletteNAppelleQueSesPropresMorceaux est le test qui aurait ete
// rouge le premier jour, et il tient en quatre lignes.
//
// Il ne verifie aucun format : il verifie que DEUX canaux differents rendent
// des textes differents. C'est la propriete que le metier demandait, et c'est
// la seule qu'aucun des 23 tests ne verifiait.
func TestLeSqueletteNAppelleQueSesPropresMorceaux(t *testing.T) {
    b := Base{Expediteur: "BANQUE", Horloge: time.Now}
    courrier, err := Courrier{Base: b, CodePostal: "BP 1234"}.
        Envoyer("client@example.cm", "Releve", "votre releve")
    if err != nil {
        t.Fatal(err)
    }
    base, err := b.Envoyer("client@example.cm", "Releve", "votre releve")
    if err != nil {
        t.Fatal(err)
    }
    if courrier == base {
        t.Log("le squelette rend le meme texte pour Courrier et pour Base :" +
            " c'est le defaut que la correction supprime")
        return
    }
    t.Fatal("les deux textes differents : le dispatch virtuel est apparu")
}
```

Quatre lignes utiles. Il ne vérifie **aucun format** — c'est ce qui le rend
robuste : il n'a pas à être mis à jour quand l'entête change. Il vérifie la
seule propriété que le métier demandait et qu'aucun des 23 tests ne touchait.

Noter sa forme : il est écrit à l'envers, il **réussit quand le défaut est
là**, et il échouerait si le dispatch virtuel apparaissait. C'est un test de
l'énoncé, pas de la correction ; il documente le défaut dans le module qui le
porte.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Une méthode d'un type est résolue **sur le type du récepteur**, pas sur ce qui l'incorpore. Il n'y a pas de dispatch virtuel en Go. |
| ⚫ | Un squelette qui doit appeler des morceaux variables ne peut pas être une méthode du type qui porte les morceaux par défaut. **C'est une fonction**, et les morceaux sont une interface. |
| ⚫ | `Base` échoue au critère de façon maximale : les quatre méthodes à surcharger sont les quatre appelées en interne. |
| ⚫ | L'incorporation promeut aussi les **champs**. Ici, `Horloge` exporté rend l'horloge de tout canal modifiable depuis n'importe où. |
| ⚫ | Un champ de sous-type inutilisable depuis le squelette est le **symptôme visible** d'un dispatch qui n'a pas lieu. |
| ⚫ | 94 % de couverture et 23 tests verts sont compatibles avec un code entièrement faux, si les tests appellent les morceaux et jamais l'assemblage. |
