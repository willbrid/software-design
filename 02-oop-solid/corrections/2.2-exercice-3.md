# Correction 2.2 — Exercice 3 : les barèmes de pénalité

> Rappel de l'énoncé : cinq implémentations d'une interface `Penalite`, un
> refactoring à mesurer, un défaut à trouver, un sixième barème qui arrive, et
> une règle à laisser à l'équipe.

L'ordre des questions n'est pas arbitraire : **on mesure avant de refactorer**.
Le reste de la correction suit cet ordre, et chaque chiffre vient d'une sortie
de test.

## 1. Le test qui tranche (question 1)

### Ce qu'il faut comparer

Les cinq implémentations ont toutes la même forme :

```
penalite = min(jours_facturables x taux, valeur / diviseur)
```

Elles diffèrent par **trois constantes** : le taux journalier, le diviseur du
plafond, et — pour une seule d'entre elles — un nombre de jours de franchise.

Mais ça, c'est ce que la lecture suggère. Ce qui tranche est un test.

```go
// TestLesCinqTypesSeRamenentALaTable est le test qui tranche.
//
// Il ne dit pas que la table est « plus propre ». Il dit que pour chaque
// bareme et chaque couple temoin, l'implementation d'origine et la ligne de
// table rendent le MEME resultat. Si c'est vrai, les cinq types ne
// distinguaient rien.
//
// Les entrees negatives sont exclues de ce test, et la raison est le test
// suivant : sur les entrees negatives, les deux ne rendent PAS la meme chose,
// et c'est volontaire.
func TestLesCinqTypesSeRamenentALaTable(t *testing.T) {
    compare := 0
    for nom, origine := range avant.Tous() {
        ligne, ok := bareme.Table[nom]
        if !ok {
            t.Fatalf("%q absent de la table", nom)
        }
        for _, j := range joursTemoins {
            for _, v := range valeursTemoins {
                attendu := origine.Calculer(j, v)
                obtenu, err := ligne.Frais(j, v)
                if err != nil {
                    t.Fatalf("%s(%d j, %d FCFA) : %v", nom, j, v, err)
                }
                if obtenu != attendu {
                    t.Errorf("%s(%d j, %d FCFA) : origine %d, table %d",
                        nom, j, v, attendu, obtenu)
                }
                compare++
            }
        }
    }
    attendu := len(avant.Tous()) * len(joursTemoins) * len(valeursTemoins)
    if compare != attendu {
        t.Fatalf("%d comparaisons, attendu %d", compare, attendu)
    }
    t.Logf("%d comparaisons sur %d baremes : les cinq types et la table rendent la meme chose",
        compare, len(avant.Tous()))
}
```

```
420 comparaisons sur 5 baremes : les cinq types et la table rendent la meme chose
```

Quatorze nombres de jours × six valeurs de matériel × cinq barèmes. Les jours
témoins ne sont pas pris au hasard : `0, 1, 2, 3, 4, 6, 7, 8, 13, 14, 15, 30,
100, 1 000` encadrent la franchise de trois jours (2, 3, 4), les bords de
semaine (6, 7, 8 puis 13, 14, 15) et les grandes valeurs où le plafond mord.

> Les voisins immédiats d'une frontière sont la seule façon de voir une
> marche. Un tableau qui teste 1, 10 et 100 ne voit aucune frontière.

### La réponse à « la réponse n'est pas la même pour les cinq »

Elle l'est. Les cinq se ramènent à la table, y compris les deux qui *ont l'air*
différentes :

| L'implémentation | Pourquoi elle a l'air différente | Pourquoi elle ne l'est pas |
|---|---|---|
| `PenaliteAdministration` | son plafond est la valeur entière, pas la moitié | `DiviseurPlafond: 1` |
| `PenaliteFranchise` | elle a un `if` de sortie anticipée | `FranchiseJours: 3`, et `max(0, j - 3) × taux` rend exactement la même chose, y compris à `j = 3` |

C'est le piège de l'exercice, et il n'y a qu'un moyen de ne pas y tomber :
**ne pas décider à l'œil**.

## 2. La table (question 2)

```go
// Bareme est le bareme journalier, et il couvre les cinq cas d'origine.
//
//    PenaliteStandard       -> {ParJourFCFA: 5000, DiviseurPlafond: 2}
//    PenaliteGrosCompte     -> {ParJourFCFA: 2000, DiviseurPlafond: 2}
//    PenaliteAssociation    -> {ParJourFCFA: 1000, DiviseurPlafond: 4}
//    PenaliteAdministration -> {ParJourFCFA: 5000, DiviseurPlafond: 1}
//    PenaliteFranchise      -> {ParJourFCFA: 5000, DiviseurPlafond: 2, FranchiseJours: 3}
//
// Trois champs pour cinq types, cinq methodes et cinq jeux de tests.
type Bareme struct {
    // ParJourFCFA est la penalite par jour de retard facturable.
    ParJourFCFA int
    // FranchiseJours est le nombre de jours de retard non facturables. Zero
    // signifie « pas de franchise », qui est le cas de quatre des cinq
    // baremes — la valeur zero est donc le defaut raisonnable.
    FranchiseJours int
    // DiviseurPlafond : la penalite ne depasse pas valeur / DiviseurPlafond.
    // Un diviseur de 1 plafonne a la valeur du materiel, ce qui est le cas de
    // l'administration. Il n'y a PAS de valeur signifiant « sans plafond » :
    // une penalite superieure a la valeur du materiel n'a aucun sens, donc
    // l'etat n'est pas representable.
    DiviseurPlafond int
}
```

Trois champs. Les cinq lignes :

```go
// Table est la grille des baremes journaliers.
//
// C'est une DONNEE : elle change par avenant commercial, et on ne redeploie
// pas pour un avenant.
var Table = map[string]Bareme{
    "standard":       {ParJourFCFA: 5_000, DiviseurPlafond: 2},
    "gros compte":    {ParJourFCFA: 2_000, DiviseurPlafond: 2},
    "association":    {ParJourFCFA: 1_000, DiviseurPlafond: 4},
    "administration": {ParJourFCFA: 5_000, DiviseurPlafond: 1},
    "franchise":      {ParJourFCFA: 5_000, DiviseurPlafond: 2, FranchiseJours: 3},
}
```

Deux décisions dans cette `struct` qui méritent un mot.

**`FranchiseJours` à zéro signifie « pas de franchise »**, et c'est le cas de
quatre barèmes sur cinq. La valeur zéro est donc le défaut raisonnable, au sens
de la leçon 2.1.

**Il n'y a pas de valeur de `DiviseurPlafond` signifiant « sans plafond ».**
Une pénalité supérieure à la valeur du matériel n'a aucun sens, donc l'état
n'est pas représentable : le minimum est `1`, qui plafonne à la valeur
complète. Un diviseur nul est refusé par une erreur nommée, parce qu'il
produirait une division par zéro — c'est une entrée invalide, pas un cas
limite.

## 3. Le compte (question 3)

| | Avant | Après |
|---|---|---|
| lignes de code non vides | **72** | **147** |
| types | 5 + 1 interface | 1 `struct` + 1 interface + 1 seconde forme |
| méthodes `Calculer` | 5 | 2 |
| fichiers à toucher pour un sixième **barème journalier** | **1 fichier, 1 type, 1 méthode, 1 jeu de tests** | **1 ligne de table** |

Il faut regarder le premier chiffre en face : **le code a grossi.** 72 lignes
deviennent 147.

Et il faut dire pourquoi, honnêtement : les 75 lignes de plus ne sont pas la
table. Ce sont la vérification des entrées, les quatre erreurs nommées, la
seconde forme de calcul et la documentation des choix. Si on ne comptait que
le remplacement des cinq types par la table, on passerait de 72 à environ 50.

> Un refactoring qui raccourcit le code n'est pas forcément un bon
> refactoring, et un refactoring qui l'allonge n'est pas forcément mauvais. Le
> chiffre qui décide est celui de la dernière ligne du tableau : **ce que coûte
> le changement suivant.**

Un sixième barème journalier, avant : un type, une méthode, cinq tests, et une
assertion de conformité à ajouter. Après : une ligne dans une `map`. Et dans
un vrai système, la table viendrait de la configuration — donc **zéro ligne de
code et zéro déploiement**.

## 4. Le défaut, et ce que la table en fait (question 4)

### Ce que les cinq implémentations font d'un retard négatif

```go
// TestLeDefautQueLaTableNeReproduitPas est la reponse a la question 4.
//
// Quatre des cinq implementations d'origine rendent une penalite NEGATIVE
// pour un retard negatif, et les cinq en rendent une pour une valeur de
// materiel negative. Une penalite negative, c'est la plateforme qui doit de
// l'argent au client pour un materiel rendu en retard.
//
// La table ne le reproduit pas : elle refuse l'entree. Ce n'est pas une
// infidelite au comportement d'origine, c'est la lecon 2.1 appliquee — un
// etat invalide qu'on rend non representable au lieu de le propager.
func TestLeDefautQueLaTableNeReproduitPas(t *testing.T) {
    negatives := 0
    for nom, origine := range avant.Tous() {
        got := origine.Calculer(-2, 1_000_000)
        if got < 0 {
            negatives++
            t.Logf("%-15s Calculer(-2 j, 1 000 000 FCFA) = %d FCFA", nom, got)
        }
        if _, err := bareme.Table[nom].Frais(-2, 1_000_000); !errors.Is(err, bareme.ErrJoursNegatifs) {
            t.Errorf("%s : la table accepte un retard negatif (%v)", nom, err)
        }
        if _, err := bareme.Table[nom].Frais(10, -500); !errors.Is(err, bareme.ErrValeurNegative) {
            t.Errorf("%s : la table accepte une valeur negative (%v)", nom, err)
        }
    }
    if negatives != 4 {
        t.Fatalf("%d implementations rendent une penalite negative, attendu 4", negatives)
    }
    // La cinquieme est la franchise : son « if j <= 3 » attrape les negatifs
    // par accident. Un garde-fou accidentel reste un garde-fou absent.
    if got := (avant.PenaliteFranchise{}).Calculer(-2, 1_000_000); got != 0 {
        t.Errorf("la franchise rend %d pour un retard negatif", got)
    }
}
```

```
standard        Calculer(-2 j, 1 000 000 FCFA) = -10000 FCFA
gros compte     Calculer(-2 j, 1 000 000 FCFA) = -4000 FCFA
association     Calculer(-2 j, 1 000 000 FCFA) = -2000 FCFA
administration  Calculer(-2 j, 1 000 000 FCFA) = -10000 FCFA
```

Quatre sur cinq rendent une **pénalité négative**. Une pénalité négative, c'est
la plateforme qui doit de l'argent au client pour un matériel rendu en retard.

Et avec une valeur de matériel négative, les cinq la rendent : `v/4` d'un
nombre négatif est négatif, et le plafond devient un plancher.

La cinquième — `PenaliteFranchise` — rend `0`, mais pas pour une bonne raison :
son `if j <= 3` attrape les négatifs **par accident**. C'est le cas de figure
de la correction 2.1 sur les données sales :

> Un garde-fou accidentel reste un garde-fou absent. Celui-ci disparaîtra le
> jour où quelqu'un ramènera la franchise à zéro.

### Faut-il que la table le reproduise ?

**Non**, et il faut pouvoir le défendre. La règle générale d'un refactoring est
de préserver le comportement — mais « préserver » ne s'applique qu'à un
comportement dont quelqu'un dépend. Ici :

- aucun appelant ne peut dépendre d'une pénalité négative : elle produirait une
  facture à montant négatif, que le système de facturation refuserait ;
- le comportement n'est pas documenté, pas testé, et ne figure dans aucune
  spécification ;
- il est **la conséquence d'un type trop large** — un `int` pour un nombre de
  jours de retard — et pas d'une décision.

La table refuse donc l'entrée, par deux erreurs nommées. Et la vraie
correction, celle de la leçon 2.1, va un cran plus loin : `joursDeRetard` et
`valeurMaterielFCFA` devraient être des types dont la valeur négative n'est pas
représentable. Je ne l'ai pas fait ici, et il faut dire pourquoi : ça
changerait la signature de `Calculer`, donc l'énoncé de l'exercice. **La
vérification au constructeur est le deuxième choix, et on le sait.**

Avant de déployer ce refus, il reste une chose à faire, et c'est la leçon 1.4 :

> Avant de transformer un comportement silencieux en erreur, **mesure combien
> d'appelants le déclenchent**. Journalise pendant une semaine, compte, puis
> décide. Si la réponse est zéro, le refus est gratuit. Si c'est quatre mille,
> tu viens de trouver un deuxième incident.

## 5. Le sixième barème, et le seuil exact (question 5)

### Pourquoi il ne se ramène pas à la table

La règle : 3 % de la valeur du matériel **par semaine entamée**, plafonné à la
valeur, avec une remise de 50 % sous conditions.

Laissons la remise de côté — c'est la question 6. Le cœur du calcul :

```go
// ContratCadre est le sixieme bareme, arrive six mois plus tard.
//
// Il ne se ramene PAS a un Bareme, et la raison est precise : il ne differe
// pas par la valeur de ses constantes, il differe par la FORME de son calcul.
//
//    Bareme       : penalite = f(jours) — un montant absolu par jour
//    ContratCadre : penalite = f(jours, valeur) — un pourcentage de la valeur,
//                   par semaine entamee
//
// La penalite d'un Bareme ne depend de la valeur que par son plafond. Celle
// d'un ContratCadre en depend directement, et par palier hebdomadaire. Un
// test le demontre par exhaustion plutot que de l'affirmer.
type ContratCadre struct {
    // ParSemainePourmilleValeur : 30 pour mille, soit 3 %, de la valeur du
    // materiel par semaine ENTAMEE.
    ParSemainePourmilleValeur int
}

func (c ContratCadre) Frais(joursDeRetard, valeurMaterielFCFA int) (int, error) {
    if err := verifierEntrees(joursDeRetard, valeurMaterielFCFA); err != nil {
        return 0, err
    }
    if joursDeRetard == 0 {
        return 0, nil
    }
    // « Semaine entamee » : un jour de retard est une semaine, huit jours en
    // sont deux. La division entiere arrondit vers le bas, donc on ajoute six.
    semaines := (joursDeRetard + 6) / 7
    p := semaines * valeurMaterielFCFA * c.ParSemainePourmilleValeur / 1000
    return min(p, valeurMaterielFCFA), nil
}
```

Il ne se ramène pas à un `Bareme`, et ce n'est pas une impression. La
démonstration tient en deux tests et une propriété :

> Pour un nombre de jours donné, la pénalité d'un `Bareme` **ne dépend pas de
> la valeur du matériel** tant qu'on reste sous le plafond — elle vaut
> `jours × taux`, et le taux est un montant absolu. Celle d'un `ContratCadre`
> en dépend **proportionnellement**.

```go
// TestUnBaremeNeDependPasDeLaValeurSousLePlafond : pour un nombre de jours
// donne, la penalite d'un Bareme est la MEME quelle que soit la valeur du
// materiel, tant qu'on reste sous le plafond.
func TestUnBaremeNeDependPasDeLaValeurSousLePlafond(t *testing.T) {
    alea := rand.New(rand.NewSource(3))
    for i := 0; i < 500; i++ {
        b := bareme.Bareme{
            ParJourFCFA:     alea.Intn(10_000),
            FranchiseJours:  alea.Intn(10),
            DiviseurPlafond: 1 + alea.Intn(4),
        }
        // Deux valeurs tres au-dessus de ce que dix jours peuvent couter :
        // le plafond ne mord ni pour l'une ni pour l'autre.
        a, err := b.Frais(10, 1_000_000_000)
        if err != nil {
            t.Fatal(err)
        }
        c, err := b.Frais(10, 2_000_000_000)
        if err != nil {
            t.Fatal(err)
        }
        if a != c {
            t.Fatalf("bareme %+v : la penalite depend de la valeur (%d puis %d)", b, a, c)
        }
    }
}
```

```go
// TestUnContratCadreDependDeLaValeur : la meme mesure sur le sixieme bareme
// donne le contraire. Les deux tests ensemble prouvent qu'AUCUN Bareme ne
// reproduit un ContratCadre — pas « aucun de ceux qu'on a essayes ».
func TestUnContratCadreDependDeLaValeur(t *testing.T) {
    c := bareme.ContratCadre{ParSemainePourmilleValeur: 30}
    a, err := c.Frais(10, 1_000_000)
    if err != nil {
        t.Fatal(err)
    }
    b, err := c.Frais(10, 2_000_000)
    if err != nil {
        t.Fatal(err)
    }
    if a == b {
        t.Fatal("la penalite du contrat-cadre ne depend pas de la valeur : la preuve tombe")
    }
    // 10 jours = 2 semaines entamees, 3 % par semaine.
    if a != 60_000 || b != 120_000 {
        t.Fatalf("Frais(10 j) = %d puis %d FCFA, attendu 60 000 puis 120 000", a, b)
    }
}
```

Cinq cents barèmes tirés au hasard, deux valeurs de matériel chacun : le
résultat est identique à chaque fois. Le `ContratCadre`, lui, rend 60 000 puis
120 000 FCFA.

C'est une preuve **générale** et non une exhaustion : elle ne dit pas « aucun
des barèmes essayés ne marche », elle dit « aucun barème ne peut marcher,
parce qu'ils n'ont pas la même dépendance à la valeur ».

> Pour montrer que deux formes diffèrent, cherche une **propriété** que
> l'une a et l'autre pas. Un balayage dit seulement que tu n'as pas trouvé de
> contre-exemple dans ce que tu as essayé — et la leçon 2.2 raconte comment
> ça m'a fait publier un théorème faux.

### Le seuil, formulé précisément

Ce n'est pas « dès qu'il y a un cas de plus ». Ce n'est pas non plus « dès que
le calcul est compliqué ».

> **Le polymorphisme se paie quand il y a deux formes de calcul, c'est-à-dire
> deux dépendances différentes aux mêmes entrées.** Pas deux jeux de
> constantes : deux manières dont le résultat dépend des arguments.

Et la frontière a un symptôme observable dans la table, qui est la question 7.

## 6. La remise (question 6)

Trois propositions dans l'énoncé. La réponse est **C**, et les deux autres ont
des défauts nommables.

| | Proposition | Ce qu'elle coûte |
|---|---|---|
| A | un champ `NombreDeRetards` dans la table | la table est un **contrat commercial**, pas un fichier client. Ce champ obligerait une ligne de table **par client** — soit quelques milliers de lignes pour une grille qui en a six |
| B | un argument de plus à `Calculer` | cinq implémentations sur six l'**ignoreraient**. Et la leçon le dit : *une implémentation qui n'utilise pas le paramètre que l'interface lui impose est le premier indice que l'interface décrit le besoin de l'appelant* |
| **C** | un deuxième calcul, chez l'appelant, appliqué au résultat | **la bonne**, pour la raison du critère : la remise ne se répond pas avec les champs du barème, il faut l'historique du client |

```go
// Package remise applique la remise de fidelite au resultat d'un calcul de
// penalite.
//
// Ce paquet EST la reponse a la question 6 de l'enonce, et il repond
// « proposition C ». La remise depend du nombre de retards du CLIENT sur
// douze mois ; elle ne depend pas du bareme. Elle n'a donc rien a faire ni
// dans la table — qui est un contrat commercial, pas un fichier client — ni
// dans la signature de Calcul.Frais, qui serait un argument que cinq des six
// implementations ignoreraient.
package remise
```

```go
// Historique dit combien de retards un client a eus sur douze mois.
//
// Interface d'UNE methode, declaree par celui qui s'en sert. Son double de
// test est une ligne.
type Historique interface {
    RetardsSurDouzeMois(client string) (int, error)
}

// Appliquer rend la penalite apres remise, et la raison.
//
// La raison n'est pas decorative : une penalite remisee apparait sur une
// facture, et un client qui appelle pour demander pourquoi doit obtenir une
// phrase et non un chiffre.
func Appliquer(penaliteFCFA int, client string, h Historique) (int, string, error) {
    if penaliteFCFA < 0 {
        return 0, "", fmt.Errorf("%w : %d FCFA", ErrPenaliteNegative, penaliteFCFA)
    }
    retards, err := h.RetardsSurDouzeMois(client)
    if err != nil {
        // On ne remise PAS par defaut, et on ne facture pas plein tarif en
        // silence non plus : on rend l'erreur. Decider a la place du client
        // sans savoir est le mode de panne de tout calcul qui depend d'un
        // service distant.
        return 0, "", fmt.Errorf("%w : %s : %w", ErrHistoriqueIndisponible, client, err)
    }
    if retards < 0 {
        return 0, "", fmt.Errorf("%w : %d retards", ErrPenaliteNegative, retards)
    }
    if retards >= SeuilRetards {
        return penaliteFCFA, fmt.Sprintf("plein tarif : %d retards sur douze mois", retards), nil
    }
    remisee := penaliteFCFA * (1000 - PourmilleRemise) / 1000
    return remisee, fmt.Sprintf("remise de fidelite : %d retard(s) sur douze mois", retards), nil
}
```

Trois décisions dans ce paquet, et chacune répond à une leçon antérieure.

**L'interface `Historique` a une méthode**, elle est déclarée par celui qui
s'en sert, et son double de test est une ligne.

**`Appliquer` rend la raison**, pas seulement le montant. Une pénalité remisée
apparaît sur une facture, et un client qui appelle pour demander pourquoi doit
obtenir une phrase.

**Un historique indisponible rend une erreur**, et c'est la décision la plus
importante du fichier. Ni remise par défaut — on offrirait de l'argent à cause
d'un timeout — ni plein tarif en silence — on facturerait trop à un bon client.

> Décider à la place de quelqu'un sans savoir est le mode de panne de tout
> calcul qui dépend d'un service distant. Le seul comportement défendable est
> de dire qu'on ne sait pas.

## 7. La règle laissée à l'équipe (question 7)

L'énoncé demandait une règle d'une phrase, vérifiable par quelqu'un qui n'a
pas lu la leçon, et tenue par un test. Voilà la phrase :

> **Un barème va dans la table si et seulement s'il se décrit avec les champs
> qui existent déjà. S'il lui faut un champ que lui seul utilise, c'est une
> implémentation.**

Et voilà le test qui la tient — en comptant, pour chaque champ de la `struct`,
combien de lignes de la table lui donnent une valeur non nulle :

```go
// TestChaqueChampDeLaTableSertAPlusieursLignes rend la regle mecanique.
//
// Pour chaque champ de Bareme, il compte les lignes de la table qui lui
// donnent une valeur non nulle. En dessous de deux, le champ doit figurer
// dans les derogations — sinon c'est le signe que ce champ decrit UN cas, et
// qu'un cas qui a besoin de son propre champ est une implementation.
func TestChaqueChampDeLaTableSertAPlusieursLignes(t *testing.T) {
    typ := reflect.TypeOf(bareme.Bareme{})
    for i := 0; i < typ.NumField(); i++ {
        champ := typ.Field(i).Name
        utilisations := 0
        for _, ligne := range bareme.Table {
            if reflect.ValueOf(ligne).Field(i).Int() != 0 {
                utilisations++
            }
        }
        t.Logf("%-16s : %d ligne(s) sur %d", champ, utilisations, len(bareme.Table))
        if utilisations >= 2 {
            continue
        }
        raison, derogue := champsAUsageUnique[champ]
        if !derogue {
            t.Errorf("le champ %s ne sert qu'a %d ligne(s) et n'a pas de derogation :"+
                " soit il decrit un cas qui merite sa propre implementation,"+
                " soit il merite une derogation ecrite", champ, utilisations)
            continue
        }
        t.Logf("%-16s   derogation : %s", "", raison)
    }
}
```

### Ce qui s'est passé quand je l'ai lancé

```
ParJourFCFA      : 5 ligne(s) sur 5
FranchiseJours   : 1 ligne(s) sur 5
DiviseurPlafond  : 5 ligne(s) sur 5
```

**La règle a rejeté la table que le test d'équivalence venait de valider.**
`FranchiseJours` ne sert qu'à une ligne sur cinq, et pourtant les 420
comparaisons disent que la franchise se ramène parfaitement à la table.

Donc la règle est fausse. Ou plutôt : elle est une **approximation** de la
vraie règle, qui est celle de la forme, et elle a un faux positif connu.

### Ce qu'on en fait

Il y avait trois sorties possibles :

| | Sortie | Pourquoi je ne l'ai pas prise |
|---|---|---|
| a | abaisser le seuil à une ligne | la règle devient vide : tout champ sert à au moins une ligne |
| b | sortir la franchise dans une implémentation | on casserait un refactoring démontré correct pour satisfaire une heuristique |
| **c** | garder la règle comme **déclencheur de relecture**, avec une dérogation nommée et justifiée par champ | retenue |

```go
// champsAUsageUnique est une liste de DEROGATIONS, et chaque entree porte sa
// raison.
//
// Elle existe parce que la regle « un champ de la table doit servir a au
// moins deux lignes » a un FAUX POSITIF, et que je l'ai decouvert en
// l'implementant : FranchiseJours ne sert qu'a une ligne sur cinq. La regle
// aurait donc rejete une table que le test d'equivalence venait de valider.
//
// La vraie regle est celle de la forme, pas celle du compte. Mais la regle de
// la forme n'est pas verifiable par une machine, alors que celle du compte
// l'est — donc on garde le compte comme DECLENCHEUR DE RELECTURE, avec une
// derogation nommee et justifiee par champ. Une derogation justifiee est
// relisible ; une regle qu'on desactive ne l'est pas.
var champsAUsageUnique = map[string]string{
    "FranchiseJours": "un seul bareme a une franchise, mais elle ne change pas la " +
        "forme du calcul : penalite = max(0, jours - franchise) x taux. Le test " +
        "d'equivalence le demontre sur 84 couples par bareme.",
}
```

```
FranchiseJours   : 1 ligne(s) sur 5
                   derogation : un seul bareme a une franchise, mais elle ne
                   change pas la forme du calcul : penalite =
                   max(0, jours - franchise) x taux. Le test d'equivalence le
                   demontre sur 84 couples par bareme.
```

Et la règle vraie, celle qu'on donne à l'équipe avec son outillage :

> La règle **vérifiable par une machine** est celle du compte de champs. Elle
> a un faux positif, donc elle n'est pas un verrou : c'est un **déclencheur de
> relecture**. Chaque dérogation porte son nom et sa raison dans le code, et
> une dérogation justifiée est relisible — alors qu'une règle qu'on désactive
> ne l'est pas.

C'est la différence qui compte entre un linter et un test : un linter se
désactive par une ligne de configuration que personne ne relit. Une dérogation
dans un test porte une phrase que la prochaine revue lira.

## 8. La campagne de modifications

Treize modifications, deux paquets de test.

```
modification                                                  | tests qui tombent
--------------------------------------------------------------+------------------
 1. la franchise n'est plus retiree des jours facturables     | 1
 2. la franchise peut rendre un nombre de jours negatif       | 1
 3. le plafond journalier n'est plus applique                 | 1
 4. les entrees negatives ne sont plus refusees               | 1
 5. la semaine devient revolue au lieu d'entamee              | 2
 6. le contrat-cadre depasse la valeur du materiel            | 1
 7. la ligne « franchise » perd sa franchise                  | 1
 8. l'administration retombe sur le plafond de moitie         | 1
 9. Pour rend un bareme pour le contrat-cadre                 | 1
10. le plafond journalier devient un plancher (min -> max)    | 2
11. le seuil de remise devient inclusif                       | 2
12. un historique indisponible accorde la remise              | 1
13. la remise ne rend plus de raison                          | 1

13/13 modifications detectees
```

### Le survivant, et ce qu'il a changé dans le code

Il y en avait un, et c'est le plus instructif de ce chapitre.

La première version de `Bareme.Frais` s'écrivait :

```
p := facturables * b.ParJourFCFA
if plafond := valeurMaterielFCFA / b.DiviseurPlafond; p > plafond {
    return plafond, nil
}
return p, nil
```

La modification « remplacer `p > plafond` par `p >= plafond` » a **survécu**.
Et avant de chercher quel test manquait, il faut se demander autre chose :

> À `p == plafond`, la branche rend `plafond` et l'autre rend `p`. **C'est le
> même nombre.** Les deux versions du programme calculent exactement la même
> fonction, pour toutes les entrées.

C'est un **mutant équivalent**. Il ne manque aucun test, et en écrire un
serait écrire un test qui n'affirme rien.

La leçon 1.6 avait déjà rencontré un survivant équivalent, et elle en avait
tiré une conclusion que je peux maintenant généraliser :

> **Avant d'écrire un test pour un survivant, vérifie si le mutant est
> équivalent.** Et quand il l'est, demande-toi pourquoi la frontière était
> exprimée : un mutant équivalent désigne souvent une branche qui n'avait pas
> besoin d'exister.

Ici elle n'en avait pas besoin :

```go
func (b Bareme) Frais(joursDeRetard, valeurMaterielFCFA int) (int, error) {
    if err := verifierEntrees(joursDeRetard, valeurMaterielFCFA); err != nil {
        return 0, err
    }
    if b.DiviseurPlafond <= 0 {
        return 0, fmt.Errorf("%w : %d", ErrDiviseurNul, b.DiviseurPlafond)
    }
    facturables := joursDeRetard - b.FranchiseJours
    if facturables < 0 {
        facturables = 0
    }
    // min plutot qu'un if, et ce n'est pas une coquetterie.
    //
    // La campagne de modifications a produit ici un mutant SURVIVANT :
    // remplacer « p > plafond » par « p >= plafond » ne change aucun
    // resultat, parce qu'a p == plafond les deux branches rendent le meme
    // nombre. C'est un mutant EQUIVALENT, et ecrire un test pour l'attraper
    // serait ecrire un test qui n'affirme rien.
    //
    //    Un mutant equivalent ne reclame pas un test de plus : il designe
    //    une branche qui n'avait pas besoin d'exister.
    //
    // Sans le if, la frontiere n'est plus exprimee, donc elle n'est plus
    // deplacable.
    return min(facturables*b.ParJourFCFA, valeurMaterielFCFA/b.DiviseurPlafond), nil
}
```

Un `min` au lieu d'un `if`. La frontière n'est plus écrite nulle part, donc
elle n'est plus déplaçable, donc la modification n'est **plus exprimable**.
Elle a été remplacée dans la campagne par `min` → `max`, qui fait tomber deux
tests.

> Le meilleur sort d'une modification qui survit n'est pas un test de plus.
> C'est parfois de rendre la modification impossible à écrire.

## 9. Ce que cet exercice devait faire comprendre

1. **On mesure avant de refactorer.** Le test d'équivalence tranche en 420
   comparaisons ; la lecture, elle, se trompe sur deux des cinq.
2. **Les voisins immédiats d'une frontière** sont la seule façon de voir une
   marche.
3. **Un refactoring qui allonge le code peut être le bon.** Le chiffre qui
   décide est le coût du changement suivant.
4. **Quatre implémentations sur cinq rendaient une pénalité négative**, et la
   cinquième s'en sortait par accident.
5. **Ne transforme pas un comportement silencieux en erreur sans avoir mesuré
   combien d'appelants le déclenchent.**
6. **Deux formes de calcul se démontrent par une propriété**, pas par un
   balayage. Ici : la dépendance à la valeur du matériel.
7. **La remise va chez l'appelant**, parce qu'elle ne se répond pas avec les
   champs du barème — et parce qu'un argument que cinq implémentations sur six
   ignorent est un argument mal placé.
8. **Décider à la place de quelqu'un sans savoir** est le mode de panne de
   tout calcul distant. Dis que tu ne sais pas.
9. **Une règle vérifiable par une machine a le droit d'avoir un faux positif**,
   à condition que la dérogation porte son nom et sa raison dans le code.
10. **Un mutant équivalent ne réclame pas un test de plus.** Il désigne une
    branche qui n'avait pas besoin d'exister.
