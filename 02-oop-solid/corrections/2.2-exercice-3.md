# Correction 2.2 — Exercice 3 : les barèmes de pénalité

> Rappel de l'énoncé : cinq implémentations d'une interface `Penalty`, un
> refactoring à mesurer, un défaut à trouver, un sixième barème qui arrive, et
> une règle à laisser à l'équipe.

L'ordre des questions n'est pas arbitraire : **on mesure avant de refactorer**.
Le reste de la correction suit cet ordre, et chaque chiffre vient d'une sortie
de test.

## 1. Le test qui tranche (question 1)

### Ce qu'il faut comparer

Les cinq implémentations ont toutes la même forme :

```
penalite = min(jours_facturables x taux, valeur / diviseur)
```

Elles diffèrent par **trois constantes** : le taux journalier, le diviseur du
plafond, et — pour une seule d'entre elles — un nombre de jours de franchise.

Mais ça, c'est ce que la lecture suggère. Ce qui tranche est un test.

```go
// TestTheFiveTypesReduceToTheTable is the test that decides.
// It does not say the table is "cleaner". It says that for each
// scale and each witness pair, the original implementation and the row of the
// table return the SAME result. If it is true, the five types
// told nothing apart.
//
// Negative inputs are excluded from this test, and the reason is the
// next one: on negative inputs, the two do NOT return the same thing,
// and it is on purpose.
func TestTheFiveTypesReduceToTheTable(t *testing.T) {
    compare := 0
    for name, origin := range before.All() {
        line, ok := scale.Table[name]
        if !ok {
            t.Fatalf("%q missing from the table", name)
        }
        for _, j := range witnessDays {
            for _, v := range witnessValues {
                want := origin.Compute(j, v)
                got, err := line.Fees(j, v)
                if err != nil {
                    t.Fatalf("%s(%d d, %d FCFA): %v", name, j, v, err)
                }
                if got != want {
                    t.Errorf("%s(%d d, %d FCFA): original %d, table %d",
                        name, j, v, want, got)
                }
                compare++
            }
        }
    }
    want := len(before.All()) * len(witnessDays) * len(witnessValues)
    if compare != want {
        t.Fatalf("%d comparisons, want %d", compare, want)
    }
    t.Logf("%d comparisons over %d scales: the five types and the table return the same thing",
        compare, len(before.All()))
}
```

```
420 comparaisons sur 5 baremes : les cinq types et la table rendent la meme chose
```

Quatorze nombres de jours × six valeurs de matériel × cinq barèmes. Les jours
témoins ne sont pas pris au hasard : `0, 1, 2, 3, 4, 6, 7, 8, 13, 14, 15, 30,
100, 1 000` encadrent la franchise de trois jours (2, 3, 4), les bords de
semaine (6, 7, 8 puis 13, 14, 15) et les grandes valeurs où le plafond mord.

> Les voisins immédiats d'une frontière sont la seule façon de voir une
> marche. Un tableau qui teste 1, 10 et 100 ne voit aucune frontière.

### La réponse à « la réponse n'est pas la même pour les cinq »

Elle l'est. Les cinq se ramènent à la table, y compris les deux qui *ont l'air*
différentes :

| L'implémentation | Pourquoi elle a l'air différente | Pourquoi elle ne l'est pas |
|---|---|---|
| `PenaltyAdministration` | son plafond est la valeur entière, pas la moitié | `CapDivisor: 1` |
| `PenaltyGrace` | elle a un `if` de sortie anticipée | `GraceDays: 3`, et `max(0, j - 3) × rate` rend exactement la même chose, y compris à `j = 3` |

C'est le piège de l'exercice, et il n'y a qu'un moyen de ne pas y tomber :
**ne pas décider à l'œil**.

## 2. La table (question 2)

```go
// Scale is the daily scale, and it covers the five original cases.
//    PenaltyStandard       -> {PerDayFCFA: 5000, CapDivisor: 2}
//    PenaltyLargeAccount   -> {PerDayFCFA: 2000, CapDivisor: 2}
//    PenaltyAssociation    -> {PerDayFCFA: 1000, CapDivisor: 4}
//    PenaltyAdministration -> {PerDayFCFA: 5000, CapDivisor: 1}
//    PenaltyGrace          -> {PerDayFCFA: 5000, CapDivisor: 2, GraceDays: 3}
//
// Three fields for five types, five methods and five test sets.
type Scale struct {
    // PerDayFCFA is the penalty per billable late day.
    PerDayFCFA int
    // GraceDays is the number of late days not billed. Zero
    // means "no grace period", which is the case for four of the five
    // scales: so the zero value is the sensible default.
    GraceDays int
    // CapDivisor: the penalty does not exceed value / CapDivisor.
    // A divisor of 1 caps at the equipment's value, which is the case of
    // administration. There is NO value meaning "no cap":
    // a penalty above the equipment's value makes no sense, so
    // the state cannot be represented.
    CapDivisor int
}
```

Trois champs. Les cinq lignes :

```go
// Table is the grid of daily scales.
// It is DATA: it changes by commercial amendment, and we do not redeploy
// not for an amendment.
var Table = map[string]Scale{
    "standard":       {PerDayFCFA: 5_000, CapDivisor: 2},
    "large account":  {PerDayFCFA: 2_000, CapDivisor: 2},
    "association":    {PerDayFCFA: 1_000, CapDivisor: 4},
    "administration": {PerDayFCFA: 5_000, CapDivisor: 1},
    "grace":          {PerDayFCFA: 5_000, CapDivisor: 2, GraceDays: 3},
}
```

Deux décisions dans cette `struct` qui méritent un mot.

**`GraceDays` à zéro signifie « pas de franchise »**, et c'est le cas de
quatre barèmes sur cinq. La valeur zéro est donc le défaut raisonnable, au sens
de la leçon 2.1.

**Il n'y a pas de valeur de `CapDivisor` signifiant « sans plafond ».**
Une pénalité supérieure à la valeur du matériel n'a aucun sens, donc l'état
n'est pas représentable : le minimum est `1`, qui plafonne à la valeur
complète. Un diviseur nul est refusé par une erreur nommée, parce qu'il
produirait une division par zéro — c'est une entrée invalide, pas un cas
limite.

## 3. Le compte (question 3)

| | Avant | Après |
|---|---|---|
| lignes de code non vides | **72** | **147** |
| types | 5 + 1 interface | 1 `struct` + 1 interface + 1 seconde forme |
| méthodes `Compute` | 5 | 2 |
| fichiers à toucher pour un sixième **barème journalier** | **1 fichier, 1 type, 1 méthode, 1 jeu de tests** | **1 ligne de table** |

Il faut regarder le premier chiffre en face : **le code a grossi.** 72 lignes
deviennent 147.

Et il faut dire pourquoi, honnêtement : les 75 lignes de plus ne sont pas la
table. Ce sont la vérification des entrées, les quatre erreurs nommées, la
seconde forme de calcul et la documentation des choix. Si on ne comptait que
le remplacement des cinq types par la table, on passerait de 72 à environ 50.

> Un refactoring qui raccourcit le code n'est pas forcément un bon
> refactoring, et un refactoring qui l'allonge n'est pas forcément mauvais. Le
> chiffre qui décide est celui de la dernière ligne du tableau : **ce que coûte
> le changement suivant.**

Un sixième barème journalier, avant : un type, une méthode, cinq tests, et une
assertion de conformité à ajouter. Après : une ligne dans une `map`. Et dans
un vrai système, la table viendrait de la configuration — donc **zéro ligne de
code et zéro déploiement**.

## 4. Le défaut, et ce que la table en fait (question 4)

### Ce que les cinq implémentations font d'un retard négatif

```go
// TestTheFlawTheTableDoesNotReproduce is the answer to question 4.
// Four of the five original implementations return a NEGATIVE penalty
// for a negative delay, and all five return one for an equipment
// equipment value. A negative penalty means the platform owes
// money to the client for equipment returned late.
//
// The table does not reproduce it: it refuses the input. It is not an
// infidelity to the original behavior, it is lesson 2.1 applied: an
// invalid state made non-representable instead of propagated.
func TestTheFlawTheTableDoesNotReproduce(t *testing.T) {
    negatives := 0
    for name, origin := range before.All() {
        got := origin.Compute(-2, 1_000_000)
        if got < 0 {
            negatives++
            t.Logf("%-15s Compute(-2 d, 1 000 000 FCFA) = %d FCFA", name, got)
        }
        if _, err := scale.Table[name].Fees(-2, 1_000_000); !errors.Is(err, scale.ErrNegativeDays) {
            t.Errorf("%s: the table accepts a negative delay (%v)", name, err)
        }
        if _, err := scale.Table[name].Fees(10, -500); !errors.Is(err, scale.ErrNegativeValue) {
            t.Errorf("%s: the table accepts a negative value (%v)", name, err)
        }
    }
    if negatives != 4 {
        t.Fatalf("%d implementations return a negative penalty, want 4", negatives)
    }
    // The fifth is the grace one: its "if d <= 3" catches negatives
    // by accident. An accidental safeguard is still a missing safeguard.
    if got := (before.PenaltyGrace{}).Compute(-2, 1_000_000); got != 0 {
        t.Errorf("the grace scale returns %d for a negative delay", got)
    }
}
```

```
standard        Compute(-2 j, 1 000 000 FCFA) = -10000 FCFA
large account     Compute(-2 j, 1 000 000 FCFA) = -4000 FCFA
association     Compute(-2 j, 1 000 000 FCFA) = -2000 FCFA
administration  Compute(-2 j, 1 000 000 FCFA) = -10000 FCFA
```

Quatre sur cinq rendent une **pénalité négative**. Une pénalité négative, c'est
la plateforme qui doit de l'argent au client pour un matériel rendu en retard.

Et avec une valeur de matériel négative, les cinq la rendent : `v/4` d'un
nombre négatif est négatif, et le plafond devient un plancher.

La cinquième — `PenaltyGrace` — rend `0`, mais pas pour une bonne raison :
son `if j <= 3` attrape les négatifs **par accident**. C'est le cas de figure
de la correction 2.1 sur les données sales :

> Un garde-fou accidentel reste un garde-fou absent. Celui-ci disparaîtra le
> jour où quelqu'un ramènera la franchise à zéro.

### Faut-il que la table le reproduise ?

**Non**, et il faut pouvoir le défendre. La règle générale d'un refactoring est
de préserver le comportement — mais « préserver » ne s'applique qu'à un
comportement dont quelqu'un dépend. Ici :

- aucun appelant ne peut dépendre d'une pénalité négative : elle produirait une
  facture à montant négatif, que le système de facturation refuserait ;
- le comportement n'est pas documenté, pas testé, et ne figure dans aucune
  spécification ;
- il est **la conséquence d'un type trop large** — un `int` pour un nombre de
  jours de retard — et pas d'une décision.

La table refuse donc l'entrée, par deux erreurs nommées. Et la vraie
correction, celle de la leçon 2.1, va un cran plus loin : `lateDays` et
`equipmentValueFCFA` devraient être des types dont la valeur négative n'est pas
représentable. Je ne l'ai pas fait ici, et il faut dire pourquoi : ça
changerait la signature de `Compute`, donc l'énoncé de l'exercice. **La
vérification au constructeur est le deuxième choix, et on le sait.**

Avant de déployer ce refus, il reste une chose à faire, et c'est la leçon 1.4 :

> Avant de transformer un comportement silencieux en erreur, **mesure combien
> d'appelants le déclenchent**. Journalise pendant une semaine, compte, puis
> décide. Si la réponse est zéro, le refus est gratuit. Si c'est quatre mille,
> tu viens de trouver un deuxième incident.

## 5. Le sixième barème, et le seuil exact (question 5)

### Pourquoi il ne se ramène pas à la table

La règle : 3 % de la valeur du matériel **par semaine entamée**, plafonné à la
valeur, avec une remise de 50 % sous conditions.

Laissons la remise de côté — c'est la question 6. Le cœur du calcul :

```go
// FrameworkContract is the sixth scale, which arrived six months later.
// It does NOT reduce to a Scale, and the reason is precise: it does not differ
// by the value of its constants, it differs by the SHAPE of its computation.
//
//    Scale            : penalty = f(days): an absolute amount per day
//    FrameworkContract: penalty = f(days, value): a percentage of the value,
//                   per week started
//
// A Scale's penalty depends on the value only through its cap. That
// of a FrameworkContract depends on it directly, by weekly step. A
// test shows it by exhaustion rather than asserting it.
type FrameworkContract struct {
    // PerWeekPerMilleValue: 30 per mille, that is 3 %, of the equipment's
    // value per week STARTED.
    PerWeekPerMilleValue int
}

func (c FrameworkContract) Fees(lateDays, equipmentValueFCFA int) (int, error) {
    if err := checkInputs(lateDays, equipmentValueFCFA); err != nil {
        return 0, err
    }
    if lateDays == 0 {
        return 0, nil
    }
    // "Week started": one late day is a week, eight days
    // are two. Integer division rounds down, so we add six.
    weeks := (lateDays + 6) / 7
    p := weeks * equipmentValueFCFA * c.PerWeekPerMilleValue / 1000
    return min(p, equipmentValueFCFA), nil
}
```

Il ne se ramène pas à un `Scale`, et ce n'est pas une impression. La
démonstration tient en deux tests et une propriété :

> Pour un nombre de jours donné, la pénalité d'un `Scale` **ne dépend pas de
> la valeur du matériel** tant qu'on reste sous le plafond — elle vaut
> `jours × rate`, et le taux est un montant absolu. Celle d'un `FrameworkContract`
> en dépend **proportionnellement**.

```go
// TestAScaleDoesNotDependOnTheValueBelowTheCap: for a given number of days,
// a Scale's penalty is the SAME whatever the value of the
// equipment, as long as we stay below the cap.
func TestAScaleDoesNotDependOnTheValueBelowTheCap(t *testing.T) {
    rnd := rand.New(rand.NewSource(3))
    for i := 0; i < 500; i++ {
        b := scale.Scale{
            PerDayFCFA: rnd.Intn(10_000),
            GraceDays:  rnd.Intn(10),
            CapDivisor: 1 + rnd.Intn(4),
        }
        // Two values well above what ten days can cost:
        // the cap bites for neither.
        a, err := b.Fees(10, 1_000_000_000)
        if err != nil {
            t.Fatal(err)
        }
        c, err := b.Fees(10, 2_000_000_000)
        if err != nil {
            t.Fatal(err)
        }
        if a != c {
            t.Fatalf("scale %+v: the penalty depends on the value (%d then %d)", b, a, c)
        }
    }
}
```

```go
// TestAFrameworkContractDependsOnTheValue: the same measure on the sixth scale
// shows the opposite. Both tests together prove that NO Scale
// reproduces a FrameworkContract, not "none of those we tried".
func TestAFrameworkContractDependsOnTheValue(t *testing.T) {
    c := scale.FrameworkContract{PerWeekPerMilleValue: 30}
    a, err := c.Fees(10, 1_000_000)
    if err != nil {
        t.Fatal(err)
    }
    b, err := c.Fees(10, 2_000_000)
    if err != nil {
        t.Fatal(err)
    }
    if a == b {
        t.Fatal("the framework contract's penalty does not depend on the value: the proof falls")
    }
    // 10 days = 2 weeks started, 3 % per week.
    if a != 60_000 || b != 120_000 {
        t.Fatalf("Fees(10 d) = %d then %d FCFA, want 60 000 then 120 000", a, b)
    }
}
```

Cinq cents barèmes tirés au hasard, deux valeurs de matériel chacun : le
résultat est identique à chaque fois. Le `FrameworkContract`, lui, rend 60 000 puis
120 000 FCFA.

C'est une preuve **générale** et non une exhaustion : elle ne dit pas « aucun
des barèmes essayés ne marche », elle dit « aucun barème ne peut marcher,
parce qu'ils n'ont pas la même dépendance à la valeur ».

> Pour montrer que deux formes diffèrent, cherche une **propriété** que
> l'une a et l'autre pas. Un balayage dit seulement que tu n'as pas trouvé de
> contre-exemple dans ce que tu as essayé — et la leçon 2.2 raconte comment
> ça m'a fait publier un théorème faux.

### Le seuil, formulé précisément

Ce n'est pas « dès qu'il y a un cas de plus ». Ce n'est pas non plus « dès que
le calcul est compliqué ».

> **Le polymorphisme se paie quand il y a deux formes de calcul, c'est-à-dire
> deux dépendances différentes aux mêmes entrées.** Pas deux jeux de
> constantes : deux manières dont le résultat dépend des arguments.

Et la frontière a un symptôme observable dans la table, qui est la question 7.

## 6. La remise (question 6)

Trois propositions dans l'énoncé. La réponse est **C**, et les deux autres ont
des défauts nommables.

| | Proposition | Ce qu'elle coûte |
|---|---|---|
| A | un champ `NombreDeRetards` dans la table | la table est un **contrat commercial**, pas un fichier client. Ce champ obligerait une ligne de table **par client** — soit quelques milliers de lignes pour une grille qui en a six |
| B | un argument de plus à `Compute` | cinq implémentations sur six l'**ignoreraient**. Et la leçon le dit : *une implémentation qui n'utilise pas le paramètre que l'interface lui impose est le premier indice que l'interface décrit le besoin de l'appelant* |
| **C** | un deuxième calcul, chez l'appelant, appliqué au résultat | **la bonne**, pour la raison du critère : la remise ne se répond pas avec les champs du barème, il faut l'historique du client |

```go
// Package discount applies the loyalty discount to the result of a
// penalty.
//
// This package IS the answer to question 6 of the statement, and it answers
// "proposal C". The discount depends on the number of the CLIENT's lates over
// twelve months; it does not depend on the scale. So it has no business either
// in the table (which is a commercial contract, not a client file), nor
// in the signature of Calc.Fees, which would be an argument that five of the six
// implementations would ignore.
package discount
```

```go
// History says how many lates a client had over twelve months.
// Interface with ONE method, declared by its user. Its test double
// test is a line.
type History interface {
    LatesOverTwelveMonths(client string) (int, error)
}

// Apply returns the penalty after discount, and the reason.
//
// The reason is not decorative: a discounted penalty appears on an
// invoice, and a client who calls to ask why must get a
// sentence and not a figure.
func Apply(penaltyFCFA int, client string, h History) (int, string, error) {
    if penaltyFCFA < 0 {
        return 0, "", fmt.Errorf("%w: %d FCFA", ErrNegativePenalty, penaltyFCFA)
    }
    lates, err := h.LatesOverTwelveMonths(client)
    if err != nil {
        // We do NOT discount by default, and we do not bill full rate
        // silently either: we return the error. Deciding for the client
        // without knowing is the failure mode of every computation that depends on a
        // remote service.
        return 0, "", fmt.Errorf("%w: %s: %w", ErrHistoryUnavailable, client, err)
    }
    if lates < 0 {
        return 0, "", fmt.Errorf("%w: %d lates", ErrNegativePenalty, lates)
    }
    if lates >= LateThreshold {
        return penaltyFCFA, fmt.Sprintf("full rate: %d lates over twelve months", lates), nil
    }
    discounted := penaltyFCFA * (1000 - DiscountPerMille) / 1000
    return discounted, fmt.Sprintf("loyalty discount: %d late(s) over twelve months", lates), nil
}
```

Trois décisions dans ce paquet, et chacune répond à une leçon antérieure.

**L'interface `History` a une méthode**, elle est déclarée par celui qui
s'en sert, et son double de test est une ligne.

**`Apply` rend la raison**, pas seulement le montant. Une pénalité remisée
apparaît sur une facture, et un client qui appelle pour demander pourquoi doit
obtenir une phrase.

**Un historique indisponible rend une erreur**, et c'est la décision la plus
importante du fichier. Ni remise par défaut — on offrirait de l'argent à cause
d'un timeout — ni plein tarif en silence — on facturerait trop à un bon client.

> Décider à la place de quelqu'un sans savoir est le mode de panne de tout
> calcul qui dépend d'un service distant. Le seul comportement défendable est
> de dire qu'on ne sait pas.

## 7. La règle laissée à l'équipe (question 7)

L'énoncé demandait une règle d'une phrase, vérifiable par quelqu'un qui n'a
pas lu la leçon, et tenue par un test. Voilà la phrase :

> **Un barème va dans la table si et seulement s'il se décrit avec les champs
> qui existent déjà. S'il lui faut un champ que lui seul utilise, c'est une
> implémentation.**

Et voilà le test qui la tient — en comptant, pour chaque champ de la `struct`,
combien de lignes de la table lui donnent une valeur non nulle :

```go
// TestEachTableFieldServesSeveralRows makes the rule mechanical.
// For each Scale field, it counts the table rows that give it
// a non-zero value. Below two, the field must appear
// in the waivers; otherwise it is the sign that this field describes ONE case, and
// that a case that needs its own field is an implementation.
func TestEachTableFieldServesSeveralRows(t *testing.T) {
    typ := reflect.TypeOf(scale.Scale{})
    for i := 0; i < typ.NumField(); i++ {
        field := typ.Field(i).Name
        uses := 0
        for _, line := range scale.Table {
            if reflect.ValueOf(line).Field(i).Int() != 0 {
                uses++
            }
        }
        t.Logf("%-16s: %d row(s) out of %d", field, uses, len(scale.Table))
        if uses >= 2 {
            continue
        }
        reason, waived := singleUseFields[field]
        if !waived {
            t.Errorf("field %s serves only %d row(s) and has no waiver:"+
                " either it describes a case that deserves its own implementation,"+
                " or it deserves a written waiver", field, uses)
            continue
        }
        t.Logf("%-16s   waiver: %s", "", reason)
    }
}
```

### Ce qui s'est passé quand je l'ai lancé

```
PerDayFCFA      : 5 line(s) sur 5
GraceDays   : 1 line(s) sur 5
CapDivisor  : 5 line(s) sur 5
```

**La règle a rejeté la table que le test d'équivalence venait de valider.**
`GraceDays` ne sert qu'à une ligne sur cinq, et pourtant les 420
comparaisons disent que la franchise se ramène parfaitement à la table.

Donc la règle est fausse. Ou plutôt : elle est une **approximation** de la
vraie règle, qui est celle de la forme, et elle a un faux positif connu.

### Ce qu'on en fait

Il y avait trois sorties possibles :

| | Sortie | Pourquoi je ne l'ai pas prise |
|---|---|---|
| a | abaisser le seuil à une ligne | la règle devient vide : tout champ sert à au moins une ligne |
| b | sortir la franchise dans une implémentation | on casserait un refactoring démontré correct pour satisfaire une heuristique |
| **c** | garder la règle comme **déclencheur de relecture**, avec une dérogation nommée et justifiée par champ | retenue |

```go
// singleUseFields is a list of WAIVERS, and each entry carries its
// reason.
//
// It exists because the rule "a table field must serve at
// least two rows" has a FALSE POSITIVE, and that I found it by
// implementing it: GraceDays serves only one row out of five. The rule
// would therefore have rejected a table the equivalence test had just validated.
//
// The real rule is the one about shape, not about count. But the rule of
// of shape cannot be checked by a machine, while the one of count
// is; so we keep the count as a REVIEW TRIGGER, with a
// named and justified waiver per field. A justified waiver is
// can be reread; a rule that is switched off cannot.
var singleUseFields = map[string]string{
    "GraceDays": "only one scale has a grace period, but it does not change the " +
        "shape of the computation: penalty = max(0, days - grace) x rate. The " +
        "equivalence test shows it on 84 pairs per scale.",
}
```

```
GraceDays   : 1 line(s) sur 5
                   derogation : un seul bareme a une grace, mais elle ne
                   change pas la forme du calcul : penalite =
                   max(0, jours - grace) x rate. Le test d'equivalence le
                   demontre sur 84 couples par scale.
```

Et la règle vraie, celle qu'on donne à l'équipe avec son outillage :

> La règle **vérifiable par une machine** est celle du compte de champs. Elle
> a un faux positif, donc elle n'est pas un verrou : c'est un **déclencheur de
> relecture**. Chaque dérogation porte son nom et sa raison dans le code, et
> une dérogation justifiée est relisible — alors qu'une règle qu'on désactive
> ne l'est pas.

C'est la différence qui compte entre un linter et un test : un linter se
désactive par une ligne de configuration que personne ne relit. Une dérogation
dans un test porte une phrase que la prochaine revue lira.

```
 5. la semaine devient revolue au lieu d'entamee              | 2
 6. le contrat-cadre depasse la valeur du materiel            | 1
 7. la ligne « grace » perd sa grace                  | 1
 8. l'administration retombe sur le plafond de moitie         | 1
 9. For rend un bareme pour le contrat-cadre                 | 1
10. le plafond journalier devient un plancher (min -> max)    | 2
11. le seuil de remise devient inclusif                       | 2
12. un historique indisponible accorde la remise              | 1
13. la remise ne rend plus de raison                          | 1

13/13 modifications detectees
```

### Le survivant, et ce qu'il a changé dans le code

Il y en avait un, et c'est le plus instructif de ce chapitre.

La première version de `Scale.Fees` s'écrivait :

```
p := facturables * b.PerDayFCFA
if plafond := equipmentValueFCFA / b.CapDivisor; p > plafond {
    return plafond, nil
}
return p, nil
```

La modification « remplacer `p > plafond` par `p >= plafond` » a **survécu**.
Et avant de chercher quel test manquait, il faut se demander autre chose :

> À `p == plafond`, la branche rend `plafond` et l'autre rend `p`. **C'est le
> même nombre.** Les deux versions du programme calculent exactement la même
> fonction, pour toutes les entrées.

C'est un **mutant équivalent**. Il ne manque aucun test, et en écrire un
serait écrire un test qui n'affirme rien.

La leçon 1.6 avait déjà rencontré un survivant équivalent, et elle en avait
tiré une conclusion que je peux maintenant généraliser :

> **Avant d'écrire un test pour un survivant, vérifie si le mutant est
> équivalent.** Et quand il l'est, demande-toi pourquoi la frontière était
> exprimée : un mutant équivalent désigne souvent une branche qui n'avait pas
> besoin d'exister.

Ici elle n'en avait pas besoin :

```go
func (b Scale) Fees(lateDays, equipmentValueFCFA int) (int, error) {
    if err := checkInputs(lateDays, equipmentValueFCFA); err != nil {
        return 0, err
    }
    if b.CapDivisor <= 0 {
        return 0, fmt.Errorf("%w: %d", ErrZeroDivisor, b.CapDivisor)
    }
    billable := lateDays - b.GraceDays
    if billable < 0 {
        billable = 0
    }
    // min rather than an if, and it is not a whim.
    //
    // The change campaign produced a SURVIVING mutant here:
    // replacing "p > cap" with "p >= cap" changes no
    // result, because at p == cap both branches return the same
    // number. It is an EQUIVALENT mutant, and writing a test to catch it
    // would be writing a test that asserts nothing.
    //
    //    An equivalent mutant does not call for one more test: it points to
    //    a branch that did not need to exist.
    //
    // Without the if, the boundary is no longer expressed, so it is no longer
    // movable.
    return min(billable*b.PerDayFCFA, equipmentValueFCFA/b.CapDivisor), nil
}
```

Un `min` au lieu d'un `if`. La frontière n'est plus écrite nulle part, donc
elle n'est plus déplaçable, donc la modification n'est **plus exprimable**.
Elle a été remplacée dans la campagne par `min` → `max`, qui fait tomber deux
tests.

> Le meilleur sort d'une modification qui survit n'est pas un test de plus.
> C'est parfois de rendre la modification impossible à écrire.

## 9. Ce que cet exercice devait faire comprendre

1. **On mesure avant de refactorer.** Le test d'équivalence tranche en 420
   comparaisons ; la lecture, elle, se trompe sur deux des cinq.
2. **Les voisins immédiats d'une frontière** sont la seule façon de voir une
   marche.
3. **Un refactoring qui allonge le code peut être le bon.** Le chiffre qui
   décide est le coût du changement suivant.
4. **Quatre implémentations sur cinq rendaient une pénalité négative**, et la
   cinquième s'en sortait par accident.
5. **Ne transforme pas un comportement silencieux en erreur sans avoir mesuré
   combien d'appelants le déclenchent.**
6. **Deux formes de calcul se démontrent par une propriété**, pas par un
   balayage. Ici : la dépendance à la valeur du matériel.
7. **La remise va chez l'appelant**, parce qu'elle ne se répond pas avec les
   champs du barème — et parce qu'un argument que cinq implémentations sur six
   ignorent est un argument mal placé.
8. **Décider à la place de quelqu'un sans savoir** est le mode de panne de
   tout calcul distant. Dis que tu ne sais pas.
9. **Une règle vérifiable par une machine a le droit d'avoir un faux positif**,
   à condition que la dérogation porte son nom et sa raison dans le code.
10. **Un mutant équivalent ne réclame pas un test de plus.** Il désigne une
    branche qui n'avait pas besoin d'exister.
