# Correction 2.4 — Exercice 4 : la plateforme de règlement interbancaire

> Rappel de l'énoncé : un moteur de règlement qui doit accueillir de nouveaux
> instruments **et** de nouvelles questions sur chaque instrument, trois
> équipes dans le même dépôt, et une direction des risques qui veut ajouter un
> contrôle sans attendre un cycle de livraison.

C'est un exercice de conception, mais chacune de ses questions a une réponse
qu'on peut mesurer. J'ai donc construit le modèle — quatre instruments, quatre
questions, un cinquième instrument écrit « par une autre équipe », les trois
registres proposés, et le contrôle de risque scellé de la question 8 —, et
chaque affirmation de ce corrigé est un test vert sous `go vet ./...` et
`go test -race -count=1 ./...`. Campagne de vingt modifications, 19/19 après
deux passes et une branche supprimée.

Les règles métier du modèle (délais, seuils, catégories fiscales) sont
**fictives et simplifiées** ; le calendrier de fermeture est celui de TARGET2
pour 2026.

## 1. Le relevé qui n'existe pas encore

On ne choisit pas un axe sans relevé — leçon 2.2. Ici il n'y en a pas, donc la
première décision porte sur **ce qu'on mesure**, et la seconde sur ce qu'on
fait en attendant.

**Ce que je mesure pendant six mois**, sur chaque demande de fusion qui touche
le moteur, avec une étiquette posée à la revue :

| Étiquette | Ce qu'elle compte |
|---|---|
| `+instrument` | un instrument nouveau |
| `+question` | une méthode ajoutée à l'interface `Instrument` |
| `+fonction` | une question ajoutée **hors** de l'interface, calculée à partir des réponses existantes |
| `+contrôle` | un contrôle de risque ajouté — et s'il a exigé un **fait** nouveau (question 4) |
| `multi-équipe` | la fusion touche des paquets de plus d'une équipe |

Et deux chiffres dérivés, qui décident :

- **le rapport `+question` / `+instrument`** — c'est le problème de
  l'expression (question 2) ; au-delà de 3 pour 1 sur six mois, la découpe se
  réexamine ;
- **la part des `+contrôle` qui ont exigé un fait nouveau** — c'est la
  contradiction de la question 4 ; au-delà d'un tiers, le vocabulaire des
  faits est trop pauvre et la direction des risques attend des livraisons.

L'étiquette `multi-équipe` mesure la question 3 : une découpe en paquets qui
marche produit des fusions qui restent chez une équipe. Si plus d'une fusion
sur cinq en touche deux, la découpe ne suit pas la propriété.

**La décision en attendant** : la découpe par ligne — une interface,
une implémentation par instrument —, pour une raison qui ne dépend pas du
relevé et que la question 2 mesure : en Go, c'est la seule des deux découpes
où **le compilateur parle sur un des deux axes**.

## 2. Le problème de l'expression, avec les chiffres du cas

Quatre instruments, quatre questions : **N = 4, M = 4, seize cases**. Le code
doit toutes les remplir, et il y a deux façons de le découper.

Par ligne, l'interface :

```go
// Instrument is a payment order, as the engine sees it.
type Instrument interface {
    // Code identifies the kind of instrument: "transfer", "cheque"...
    Code() string
    // Amount is in euro cents.
    Amount() int64
    // ValueDate is the day, in Paris, on which the order is settled.
    ValueDate() time.Time
    // Clearable says whether the order goes through clearing; otherwise, it
    // is settled gross, and the reason says why.
    Clearable() (bool, string)
    // Tax returns the tax category of the order.
    Tax() Treatment
}
```

Par colonne, un type somme et un aiguillage par question :

```go
func ValueDate(o Order) time.Time {
    switch o.Kind {
    case Transfer:
        return calendar.Value(o.Received, 0)
    case DirectDebit, Cheque:
        return calendar.Value(o.Received, 1)
    case Bill:
        return calendar.Value(o.Received, 2)
    }
    panic(unknown(o.Kind))
}
```

Plutôt que de recopier le tableau de la leçon 2.2, j'ai **mesuré** les deux
ajouts dans les deux découpes, sur des copies jetables du module : on part
d'un état vert, on fait le changement, on compte.

| | ajouter un instrument | ajouter une question |
|---|---|---|
| **par ligne** | 1 fichier neuf + 1 entrée au registre · **0 erreur** · 1 test rouge (la liste des instruments) | 1 ligne dans l'interface · **17 erreurs de compilation**, à chaque usage d'une des six implémentations |
| **par colonne** | 1 constante + 1 entrée dans `Kinds` · **0 erreur** · 1 test rouge (l'exhaustivité) | 1 fichier neuf · **0 erreur · 0 test rouge** |

Les dix-sept erreurs de la question ajoutée par ligne : les six du registre et
de son test, telles que le compilateur les donne (les cinq dernières
abrégées), et onze autres dans les tests de `engine`, `instruments` et
`risk` :

```
ex4/wiring/wiring.go:20:10: cannot use instruments.Transfer{…} (value of struct type instruments.Transfer) as instrument.Instrument value in return statement: instruments.Transfer does not implement instrument.Instrument (missing method Currency)
ex4/wiring/wiring.go:23:10: ... instruments.DirectDebit ... (missing method Currency)
ex4/wiring/wiring.go:26:10: ... instruments.Cheque ... (missing method Currency)
ex4/wiring/wiring.go:29:10: ... instruments.Bill ... (missing method Currency)
ex4/wiring/wiring.go:32:10: ... treasury.Treasury ... (missing method Currency)
ex4/wiring/wiring_test.go:41:11: ... treasury.Naive ... (missing method Currency)
```

La première version de ce corrigé en comptait six : la mesure avait été
faite avant que les tests de `engine`, `instruments` et `risk` existent. Le
compilateur ne s'arrête pas une fois par type, mais à **chaque endroit** où un
des six types est utilisé comme `Instrument` — et c'est tant mieux : l'erreur
arrive là où le code dépend de la promesse.

Deux mesures de plus, et ce sont elles qui comptent :

| | 0 erreur, 0 test rouge |
|---|---|
| par ligne : un instrument écrit **mais pas inscrit** au registre | oui |
| par colonne : un genre ajouté **mais pas inscrit** dans `Kinds` | oui |

Sur l'axe ouvert, dans les deux découpes, l'oubli de l'inscription est
invisible. C'est la leçon 2.4 : *« fermé à la modification » veut dire « le
compilateur se taira »*.

Et la mesure m'a appris une chose que je n'avais pas prévue. Pour le scénario
« par colonne, ajouter une question », j'ai écrit la fonction `Currency` vite,
et je l'ai écrite **sans le cas `Bill`**. Je ne l'ai pas fait exprès. La
mesure dit : 0 erreur, 0 test rouge. La fonction panique sur un effet de
commerce, et rien ne le voit — parce que le test d'exhaustivité ne parcourt
que les questions qu'on a pensé à y inscrire :

```go
// TestEachQuestionAnswersForEachKind is the exhaustive switch Go does not
// have. It walks Kinds, so it only sees a kind if it is listed there.
func TestEachQuestionAnswersForEachKind(t *testing.T) {
    received := time.Date(2026, time.April, 1, 10, 0, 0, 0, time.UTC)
    questions := map[string]func(Order){
        "ValueDate": func(o Order) { ValueDate(o) },
        "Clearable": func(o Order) { Clearable(o) },
        "Tax":       func(o Order) { Tax(o) },
    }
    for _, k := range Kinds {
        for name, q := range questions {
            func() {
                defer func() {
                    if r := recover(); r != nil {
                        t.Errorf("%s on kind %d: %v", name, k, fmt.Sprint(r))
                    }
                }()
                q(Order{Kind: k, Cents: 100, Received: received})
            }()
        }
    }
}
```

> **En Go, la découpe par colonne n'a le compilateur sur aucun des deux
> axes.** Il n'y a pas de `switch` exhaustif : un genre nouveau et une
> question nouvelle sont tous deux gardés par des listes qu'un humain doit
> tenir. La découpe par ligne a le compilateur sur l'axe des questions —
> dix-sept erreurs, toutes au bon endroit.

**Le coût que je choisis de payer** : N fichiers par question nouvelle. Le
compilateur rend ce coût **sûr** — on ne peut pas oublier un instrument — et
la question 6 le rend **juste** — la batterie vérifie ce que chacun répond.

Et je le borne, pour que le rapport `+question` / `+instrument` ne devienne
pas une taxe : **une question n'entre dans l'interface que si sa réponse
diffère par instrument d'une façon qu'aucune autre question ne permet de
calculer.** « Le plafond réglementaire » se calcule à partir de `Amount` et
de `Code` : c'est une fonction qui prend un `Instrument`, pas une méthode. Ce
tri est l'étiquette `+fonction` du relevé.

## 3. La troisième demande est du SRP

> OCP dit **quel changement est bon marché** ; SRP dit **qui demande le
> changement**. Trois équipes dans le même dépôt, c'est trois sources de
> changement, et la découpe en paquets doit faire qu'une demande d'une équipe
> ne touche que les paquets de cette équipe.

La découpe :

| Paquet | Propriétaire | Ce qu'il contient |
|---|---|---|
| `instrument` | **équipe moteur** | l'interface, `Treatment`, la batterie de contrat |
| `calendar` | équipe moteur | jours de place, heure limite |
| `engine` | équipe moteur | le règlement ; n'accepte qu'un `risk.Control` |
| `instruments` | **équipe moyens de paiement** | virement, prélèvement, chèque, effet |
| `treasury` | **équipe trésorerie** | le virement de trésorerie |
| `risk` | **direction des risques** | le vocabulaire des faits, le chargement des règles, `Control` |
| `wiring` | équipe moteur | **la** racine de composition : le registre |

**Une racine de composition**, pas trois. Le registre est le seul endroit qui
connaît tous les instruments, et une équipe qui ajoute un instrument y ajoute
**une** entrée — c'est la seule fusion `multi-équipe` attendue, et elle est
d'une ligne :

```go
// Instruments is the registry: a literal table. A duplicate key does not
// compile.
var Instruments = map[string]Factory{
    "transfer": func(c int64, r time.Time) instrument.Instrument {
        return instruments.Transfer{Cents: c, Received: r}
    },
    "directdebit": func(c int64, r time.Time) instrument.Instrument {
        return instruments.DirectDebit{Cents: c, Received: r}
    },
    "cheque": func(c int64, r time.Time) instrument.Instrument {
        return instruments.Cheque{Cents: c, Received: r}
    },
    "bill": func(c int64, r time.Time) instrument.Instrument {
        return instruments.Bill{Cents: c, Received: r}
    },
    "treasury": func(c int64, r time.Time) instrument.Instrument {
        return treasury.Treasury{Cents: c, Received: r}
    },
}
```

Trois racines — une par équipe —, ce serait trois façons d'assembler le moteur,
et le jour où elles divergent, le moteur de production n'est celui d'aucune
équipe.

## 4. La quatrième demande contredit la deuxième

Un contrôle de risque **est une question posée à un instrument** :
« ce chèque dépasse-t-il le plafond ? ». La deuxième demande, telle que la
question 2 l'a satisfaite, fait des questions du **code** — une méthode, une
livraison. La quatrième demande veut des questions sans livraison. Les deux ne
tiennent pas ensemble au même endroit.

« On fera les deux » voudrait dire un moteur de règles capable d'exprimer
n'importe quelle question : un langage, un interprète, et la batterie de la
question 6 qui ne vérifie plus rien, puisque les réponses ne sont plus dans le
code. Ce que je fais à la place, c'est **couper la question en deux** :

> **Un fait est du code ; un contrôle est une donnée.** Les faits sont un
> vocabulaire fermé, livré, testé. Un contrôle est une combinaison de faits
> existants, chargée sans livraison. Ajouter un contrôle ne livre rien ;
> ajouter un fait livre.

```go
// Fact is a word of the controls' vocabulary. The vocabulary is CODE: the
// risk department combines facts without a release, but a new fact is
// released.
type Fact string

const (
    FactAmount    Fact = "amount"    // cents
    FactClearable Fact = "clearable" // 1 if clearable, 0 otherwise
)

// vocabulary is the table of facts: one fact, one way to read it on an
// instrument. Adding a fact is one line here — and a release.
var vocabulary = map[Fact]func(instrument.Instrument) int64{
    FactAmount: func(i instrument.Instrument) int64 { return i.Amount() },
    FactClearable: func(i instrument.Instrument) int64 {
        if ok, _ := i.Clearable(); ok {
            return 1
        }
        return 0
    },
}
```

Le chargement refuse le fichier **entier** à la première ligne qu'il ne
comprend pas, et la direction des risques garde alors le jeu précédent :

```go
// Load validates the WHOLE file before accepting a line of it. An unknown
// fact, an unknown operator or a duplicate name refuse the whole file: the
// caller then keeps the previous set. The rules are a list, not an object, so
// that a duplicate name shows (see question 5).
func Load(b []byte, version int) (*Rules, error) {
    var rs []Rule
    if err := json.Unmarshal(b, &rs); err != nil {
        return nil, err
    }
    seen := map[string]bool{}
    var errs []error
    for i, r := range rs {
        if r.Name == "" || seen[r.Name] {
            errs = append(errs, fmt.Errorf("rule %d: name %q empty or duplicated", i+1, r.Name))
        }
        seen[r.Name] = true
        if vocabulary[r.Fact] == nil {
            errs = append(errs, fmt.Errorf("rule %q: fact %q unknown", r.Name, r.Fact))
        }
        if ops[r.Op] == nil {
            errs = append(errs, fmt.Errorf("rule %q: operator %q unknown", r.Name, r.Op))
        }
    }
    if err := errors.Join(errs...); err != nil {
        return nil, err
    }
    return &Rules{version: version, rules: rs}, nil
}
```

```
rule "b": fact "beneficiary_country" unknown
rule "c": operator "~" unknown
rule 4: name "a" empty or duplicated
```

Ce que la direction des risques perd, il faut le lui dire tel quel : **un
contrôle qui a besoin d'un fait qui n'existe pas attend une livraison.** Le
contrôle sur le pays du bénéficiaire, ci-dessus, est refusé. C'est la
deuxième étiquette du relevé, et c'est le chiffre qu'on lui présentera dans
six mois.

## 5. Le registre : ce qui se passe quand un instrument est inscrit deux fois

J'ai fait les trois. Le cas qui départage est celui de l'énoncé : deux équipes
inscrivent le même code, `cheque`, sans le savoir.

**A — la table littérale.** Elle ne compile pas :

```go
// TestADuplicateDoesNotCompile: proposal A, a literal table. We build a
// throwaway module whose table registers "cheque" twice.
func TestADuplicateDoesNotCompile(t *testing.T) {
    d := t.TempDir()
    write := func(name, content string) {
        if err := os.WriteFile(filepath.Join(d, name), []byte(content), 0o644); err != nil {
            t.Fatal(err)
        }
    }
    write("go.mod", "module throwaway\n\ngo 1.22\n")
    write("wiring.go", `package wiring

var Instruments = map[string]int{
    "transfer": 0,
    "cheque":   1,
    "bill":     2,
    "cheque":   3,
}
`)
    cmd := exec.Command("go", "build", "./...")
    cmd.Dir = d
    out, err := cmd.CombinedOutput()
    if err == nil {
        t.Fatal("the duplicate table compiled")
    }
    if !strings.Contains(string(out), `duplicate key "cheque" in map literal`) {
        t.Fatalf("failed for another reason:\n%s", out)
    }
    t.Logf("%s", strings.TrimSpace(string(out)))
}
```

```
./wiring.go:7:2: duplicate key "cheque" in map literal
```

**B — les `init()`.** Le registre panique sur un doublon, ce qui est le mieux
qu'un `init()` puisse faire, puisqu'il ne peut rien rendre :

```go
// Register refuses a duplicate registration — by panicking, since an init()
// cannot return anything.
func Register(code, author string) {
    if already, ok := registered[code]; ok {
        panic(fmt.Sprintf("registry: %q registered twice (%s, then %s)", code, already, author))
    }
    registered[code] = author
}

// Registered returns what is registered IN THIS BINARY: which depends on the
// packages the binary imports, and on nothing else.
func Registered() map[string]string { return registered }
```

Les tests des deux paquets d'instrument **passent**, chacun chez lui, parce
que chacun n'importe que lui-même. Le doublon n'existe que dans le binaire qui
importe les deux :

```
$ go test -count=1 ./ex4/registry/b/cheque ./ex4/registry/b/papercheque
ok      example/c24/ex4/registry/b/cheque
ok      example/c24/ex4/registry/b/papercheque
$ go run ./ex4/registry/b/cmd/engine
panic: registry: "cheque" registered twice (payments team, then paper remittance team)
```

Et sans le `panic` — un registre qui écrit simplement `registered[code] = f` —,
c'est l'ordre d'initialisation des paquets qui choisit le gagnant, sans un mot.

**C — le fichier de configuration.** `encoding/json` garde la **dernière**
valeur d'une clé en double, sans erreur :

```go
// TestADuplicateKeyWinsSilently: encoding/json keeps the LAST value of a
// duplicate key, without an error. The cheque registered twice is registered
// once — with the second team's delay.
func TestADuplicateKeyWinsSilently(t *testing.T) {
    t2, err := Load([]byte(`{
        "cheque": {"delay": 1, "active": true},
        "cheque": {"delay": 3, "active": true}
    }`))
    if err != nil {
        t.Fatalf("error: %v", err)
    }
    if len(t2) != 1 || t2["cheque"].Delay != 3 {
        t.Fatalf("table %v", t2)
    }
}
```

| | Ce qu'elle permet | Ce qu'elle coûte | Doublon | Ce qu'un test vérifie encore |
|---|---|---|---|---|
| **A** table littérale | tout le registre lisible en un écran ; la batterie passe **sur le registre** | une ligne par instrument dans un fichier de l'équipe moteur | **ne compile pas** | tout : la liste, et chaque instrument inscrit contre la batterie |
| **B** `init()` | aucun fichier partagé | l'inscription dépend des importations du binaire ; un import oublié est un instrument absent | panique **au démarrage du binaire**, jamais dans les tests des paquets | seulement ce que le paquet de test importe |
| **C** configuration | activer ou désactiver sans livraison | elle ne peut nommer que des instruments **compilés** : il faut A de toute façon | **la dernière gagne, en silence** | rien de ce qui sera lu en production |

**Je choisis A.** C'est le seul des trois où le doublon est une erreur avant
la fusion, et le seul où un test peut parcourir *exactement* ce que la
production assemble :

```go
// TestEachRegisteredInstrumentHoldsTheContract: the battery runs on the
// REGISTRY, not on a list written next to it. A registered instrument is a
// checked instrument, without anyone having to remember it.
func TestEachRegisteredInstrumentHoldsTheContract(t *testing.T) {
    for code, f := range Instruments {
        for _, e := range instrument.Check(instrument.Harness{Code: code, Make: f}) {
            t.Errorf("%s: %v", code, e)
        }
    }
}

// TestTheListOfInstruments is the compiler of the open axis: it is updated
// on purpose, never to go back to green.
func TestTheListOfInstruments(t *testing.T) {
    var codes []string
    for c := range Instruments {
        codes = append(codes, c)
    }
    slices.Sort(codes)
    want := []string{"bill", "cheque", "directdebit", "transfer", "treasury"}
    if !slices.Equal(codes, want) {
        t.Fatalf("instruments %v, want %v", codes, want)
    }
}
```

Et C n'est pas une alternative à A, c'est une couche au-dessus : si on veut
activer un instrument sans livraison, c'est une liste d'**activation** lue au
démarrage, validée contre la table A, en **liste** et pas en objet — pour que
le doublon se voie. C'est ce que fait `risk.Load` pour les règles.

## 6. La batterie de contrat des instruments

Neuf clauses. Quatre sont techniques, cinq sont métier.

| # | Clause | Nature |
|---|---|---|
| 1 | `Code` rend le code sous lequel l'instrument est inscrit | technique |
| 2 | `Amount` rend les centimes de l'ordre | technique |
| 3 | deux appels rendent la même réponse | technique |
| 4 | `ValueDate` rend minuit, heure de Paris | technique |
| 5 | la date de valeur est un jour où la place règle | **métier** |
| 6 | la date de valeur n'est jamais avant le jour de réception, **à Paris** | **métier** |
| 7 | un ordre reçu à l'heure limite est réglé plus tard que le même ordre reçu une minute avant | **métier** |
| 8 | non compensable ⇔ une raison est donnée | **métier** |
| 9 | `Tax` rend une catégorie déclarée, jamais la valeur zéro | **métier** |

Le jeu de données porte la moitié du travail. Six réceptions, chacune choisie
pour casser une implémentation plausible :

```go
// receptions covers what breaks a value date: an ordinary day, the eve of a
// Good Friday, a Saturday, an Easter Monday, the cut-off, and a reception at
// 0:30 in Paris, which is still the day before in UTC.
var receptions = []time.Time{
    at(1, 10, 0),  // Wednesday
    at(2, 17, 0),  // Thursday after the cut-off, before Good Friday
    at(4, 11, 0),  // Saturday
    at(6, 9, 0),   // Easter Monday, closed
    at(8, 16, 0),  // Wednesday, exactly at the cut-off
    at(14, 0, 30), // Tuesday 0:30 in Paris = Monday 22:30 UTC
}
```

Noter que la batterie **ne réutilise pas** le paquet `calendar` pour juger
les dates : elle a sa propre table des jours fermés. Une batterie qui jugerait
les dates avec le calendrier qu'elle doit vérifier ne verrait aucune faute du
calendrier — *deux valeurs calculées par la même fonction fautive restent
égales* (correction 2.4/2).

### Les clauses qu'une équipe ne devinerait pas

La preuve est la première version de l'équipe trésorerie. Elle compile, elle
satisfait l'interface, et elle a été écrite par des gens compétents qui
savaient ce qu'est un virement de trésorerie :

```go
// Naive is the team's first version. It compiles, it satisfies the
// interface, and its own tests pass: they check what the team understood of
// the instrument, not what the engine expects of an instrument.
type Naive struct {
    Cents    int64
    Received time.Time
}

func (n Naive) Code() string  { return "treasury" }
func (n Naive) Amount() int64 { return n.Cents }

// ValueDate: "the same day". In UTC, without a calendar, without a cut-off.
func (n Naive) ValueDate() time.Time {
    r := n.Received.UTC()
    return time.Date(r.Year(), r.Month(), r.Day(), 0, 0, 0, 0, time.UTC)
}

// Clearable: never. The reason goes without saying for the team.
func (n Naive) Clearable() (bool, string) { return false, "" }

// Tax was added when the interface gained the method. The compiler required
// a method; it did not require an answer.
func (n Naive) Tax() instrument.Treatment { return 0 }
```

```
clause 4 [technical]: value date 2026-04-01 00:00:00 +0000 UTC: not midnight Paris time
clause 5 [business]: received Sat 4 11:00, value 2026-04-04: the market is closed
clause 6 [business]: received on 2026-04-14 in Paris, value on 2026-04-13: before the reception
clause 7 [business]: received at 15:59: 2026-04-08; at 16:00: 2026-04-08 — the cut-off changed nothing
clause 8 [business]: not clearable at 1 cents, without a reason
clause 9 [business]: Tax() returns the zero value: no category declared
```

Six clauses sur neuf, dont les cinq métier. Les quatre qu'aucune équipe ne
devine :

1. **Le fuseau (clause 6).** Un ordre reçu à 0 h 30 à Paris est encore la
   veille en UTC. Une date de valeur calculée en UTC tombe **avant** la
   réception. L'équipe a écrit « le jour même », et c'était juste — dans le
   mauvais fuseau.
2. **L'heure limite (clause 7).** Elle n'est dans aucune signature. Une
   équipe qui ne la connaît pas ne peut pas la tenir. La clause vérifie
   **les deux côtés** du seuil — 15 h 59 et 16 h 00 —, parce qu'un seuil
   qu'on ne teste que d'un côté peut être n'importe où.
3. **La raison du refus de compensation (clause 8).** Pour l'équipe, « la
   trésorerie se règle en brut » va de soi. Pour l'auditeur qui lit le
   journal de règlement dans deux ans, une ligne `gross` sans raison est une
   anomalie.
4. **La valeur zéro de `Treatment` (clause 9).** Quand l'interface a gagné
   `Tax`, le compilateur a exigé une méthode ; il n'a pas exigé une
   réponse. `return 0` compile. C'est pourquoi la valeur zéro de
   `Treatment` est **`TreatmentUnknown`** — une énumération dont la valeur
   zéro est une réponse valide rend cet oubli indétectable :

```go
// Treatment is the tax category of an instrument. Its zero value is NOT a
// category: an instrument that forgets to answer returns TreatmentUnknown,
// and the battery sees it.
type Treatment int

const (
    TreatmentUnknown Treatment = iota
    Neutral
    Commission
    Stamp
)
```

La remarque qui relie cette question à la question 2 : les erreurs de
compilation de la question ajoutée par ligne désignent **six types, donc six
occasions d'écrire `return 0` pour que ça compile**. Le compilateur garantit que les N
instruments répondent ; la batterie garantit qu'ils répondent quelque chose.

### Le coût

167 lignes pour 5 signatures : **33 lignes par signature**, contre quarante
à soixante pour les batteries de la leçon et de l'exercice 3. La différence
s'explique : les clauses d'un instrument portent sur des **fonctions pures**.
Pas d'état, pas de mode d'échec, pas de concurrence — aucune des trois clauses
qui exigeaient un traitement à part à l'exercice 3.

## 7. Les deux règles de revue

> **Pour une implémentation ajoutée :** *montre-moi le test qui passe cette
> implémentation dans la batterie de l'interface — et si une clause casse,
> montre-moi pourquoi c'est la clause qui a tort.*

> **Pour une méthode ajoutée à une interface :** *écris d'abord la clause qui
> dit ce que cette méthode promet, puis montre-moi pourquoi ce n'est pas une
> fonction qui prend l'interface.*

La seconde moitié de la première règle n'est pas une formule : une clause
peut avoir tort. Le jour où le virement instantané arrive — réglé vingt-quatre
heures sur vingt-quatre, sept jours sur sept —, la clause 5 (« la date de
valeur est un jour où la place règle ») est fausse **pour lui**, et c'est la
clause qui doit changer, devant l'équipe moteur, pas l'instrument qui doit la
contourner.

## 8. La garantie : aucun instrument réglé sans contrôle de risque

### La propriété du modèle

> **Le moteur n'accepte pas un instrument. Il accepte un `risk.Control`,
> et seul le paquet `risk` peut en fabriquer un qui ne soit pas vide.**

```go
// Control is the proof that an instrument passed a rule set. Its fields are
// unexported: outside this package, the only way to get a non-zero one is
// Pass.
type Control struct {
    i       instrument.Instrument
    version int
}

// Refusal says which rule refused the order.
type Refusal struct{ Rule string }

func (r Refusal) Error() string { return fmt.Sprintf("risk: refused by %q", r.Rule) }

// Pass evaluates all the rules and returns a Control, or the first refusal.
func (r *Rules) Pass(i instrument.Instrument) (Control, error) {
    for _, g := range r.rules {
        if g.Instrument != "" && g.Instrument != i.Code() {
            continue
        }
        if ops[g.Op](vocabulary[g.Fact](i), g.Threshold) {
            return Control{}, Refusal{Rule: g.Name}
        }
    }
    return Control{i: i, version: r.version}, nil
}

// Instrument returns the controlled instrument, nil for the zero value.
func (c Control) Instrument() instrument.Instrument { return c.i }

// Version returns the version of the rules the instrument passed.
func (c Control) Version() int { return c.version }
```

```go
// ErrUncontrolled: the Control received is the zero value. It is the only
// hole in the guarantee the compiler leaves open, and it closes here, at run
// time.
var ErrUncontrolled = errors.New("engine: order without a risk control")

type Settlement struct {
    Code    string
    Amount  int64
    Value   time.Time
    Gross   bool
    Version int
}

type Engine struct {
    // Current returns the version of the rules in force.
    Current func() int

    stale atomic.Int64
}

// Settle settles a controlled order. An order controlled under a rule
// version that is no longer the current one is settled anyway, and counted:
// it is the measurement of the rest, not a guarantee.
func (e *Engine) Settle(c risk.Control) (Settlement, error) {
    i := c.Instrument()
    if i == nil {
        return Settlement{}, ErrUncontrolled
    }
    if c.Version() < e.Current() {
        e.stale.Add(1)
    }
    ok, _ := i.Clearable()
    return Settlement{
        Code:    i.Code(),
        Amount:  i.Amount(),
        Value:   i.ValueDate(),
        Gross:   !ok,
        Version: c.Version(),
    }, nil
}
```

`engine` n'importe même pas le paquet `instrument` : son seul chemin vers un
instrument passe par `Control.Instrument()`.

```
$ go list -f '{{join .Imports " "}}' ./ex4/engine
errors example/c24/ex4/risk sync/atomic time
```

La garantie est vérifiée **à la compilation**, par un test qui compile des
appels interdits dans un paquet jetable et vérifie la **raison** de l'échec :

```go
func TestTheGuaranteeAtCompileTime(t *testing.T) {
    for _, c := range []struct {
        name string
        body string
        want string // empty: must compile
    }{
        {"a raw instrument", `    e.Settle(instruments.Transfer{Cents: 1})`,
            "cannot use instruments.Transfer{…} (value of struct type instruments.Transfer) as risk.Control value in argument to e.Settle"},
        {"a forged control", `    e.Settle(risk.Control{i: instruments.Transfer{}, version: 1})`,
            "cannot refer to unexported field i in struct literal of type risk.Control"},
        {"the zero value", `    e.Settle(risk.Control{})`, ""},
    } {
        t.Run(c.name, func(t *testing.T) {
            out, err := build(t, c.body)
            if c.want == "" {
                if err != nil {
                    t.Fatalf("does not compile:\n%s", out)
                }
                return
            }
            if err == nil {
                t.Fatal("compiled")
            }
            if !strings.Contains(out, c.want) {
                t.Fatalf("failed for another reason:\n%s", out)
            }
        })
    }
}
```

Et ce test m'a repris sur la faute exacte que la correction 2.3/4 avait
publiée. J'attendais `unknown field i in struct literal` ; le compilateur dit :

```
cannot refer to unexported field i in struct literal of type risk.Control
cannot refer to unexported field version in struct literal of type risk.Control
```

Le test échouait, et il échouait **pour la bonne raison** : il vérifie la
raison de l'échec, pas l'échec. Un test qui aurait accepté n'importe quelle
erreur de compilation aurait passé — et il passerait encore le jour où le
fichier jetable ne compile plus pour une faute de frappe.

### Ce qu'elle ne couvre pas

Trois choses, et il faut les dire avant que quelqu'un les trouve :

1. **La valeur zéro.** Des champs non exportés empêchent de **remplir** la
   structure hors du paquet, pas de la **déclarer**. `risk.Control{}`
   compile partout — c'est le troisième cas du test ci-dessus, et il est
   attendu vert. Le trou se ferme à l'exécution, dans `Settle`, et un test le
   vérifie :

```go
// TestTheZeroValueCompilesAndIsRefused: it is the hole the compiler leaves.
// Any package can write risk.Control{} — unexported fields prevent FILLING
// the struct, not declaring it.
func TestTheZeroValueCompilesAndIsRefused(t *testing.T) {
    e := &Engine{Current: func() int { return 1 }}
    var zero risk.Control
    if _, err := e.Settle(zero); !errors.Is(err, ErrUncontrolled) {
        t.Fatalf("zero value: %v", err)
    }
}
```

2. **La fraîcheur.** Un `Control` prouve que l'instrument a passé **un** jeu
   de règles. Pas qu'il a passé celui qui est en vigueur au moment du
   règlement. Entre les deux, la direction des risques a pu recharger.
3. **Le paquet `risk` lui-même**, et `reflect` / `unsafe`. Le code de
   `risk` peut fabriquer un `Control` sans évaluer les règles ; une revue
   le voit, pas le compilateur.

### Ce qu'elle interdit, chiffré

| | |
|---|---|
| fonctions exportées de `engine` qui acceptent un `instrument.Instrument` | **0** |
| façons de fabriquer un `Control` non vide hors de `risk` | **0** — mesuré par compilation |
| appels à `Settle` dans le module | 3, dans les tests : deux derrière un `Pass`, un sur la valeur zéro, exprès |
| ce que chaque test du moteur paie en plus | un jeu de règles chargé (`rules(t, v)`, 8 lignes) |

Le dernier chiffre est le coût réel : on ne peut plus tester le moteur « juste
avec un virement ». C'est voulu ; c'est aussi le premier argument qu'on
entendra contre la garantie.

### Où elle vit

Dans **la signature de `engine.Settle`** et dans **le constructeur de
`risk`** — nulle part ailleurs. Pas dans `engine` : un moteur qui
appellerait lui-même les contrôles pourrait aussi ne pas les appeler. Pas dans
un décorateur devant le moteur : la classe du problème est précisément « un
chemin qui contourne », et un décorateur se contourne. La garantie doit être
dans le **type** que le moteur exige, parce que c'est la seule chose que
personne ne peut contourner sans que le compilateur le dise.

### La mesure pour le reste

La fraîcheur n'est pas une propriété du type. Elle se mesure : chaque
`Control` porte la version des règles qu'il a passées, et le moteur compte
les ordres réglés sous une version qui n'est plus la courante.

```go
// TestAStaleOrderIsSettledAndCounted: controlled under version 1, settled
// after the switch to version 2.
func TestAStaleOrderIsSettledAndCounted(t *testing.T) {
    v1 := rules(t, 1)
    current := 1
    e := &Engine{Current: func() int { return current }}
    c, _ := v1.Pass(instruments.Transfer{Cents: 125_000, Received: received})
    current = 2
    if _, err := e.Settle(c); err != nil {
        t.Fatal(err)
    }
    if e.Stale() != 1 {
        t.Fatalf("stale = %d", e.Stale())
    }
}
```

- **Le seuil** : zéro ordre réglé sous une version **antérieure à la
  précédente**. Un ordre qui a passé la version N−2 a traversé deux
  rechargements : il est resté coincé quelque part, et c'est un incident.
- **Le plancher de bruit** : à chaque rechargement, les ordres en vol entre
  `Pass` et `Settle` sont réglés sous la version N−1, légitimement. Leur
  nombre attendu est **débit × délai entre contrôle et règlement** — à 200
  ordres par seconde et 50 ms de délai, une dizaine par rechargement. En
  dessous de ce plancher, le compteur ne dit rien ; au-dessus, il dit qu'un
  rechargement a été suivi d'un afflux d'ordres contrôlés sous l'ancien jeu.

### La garantie survit-elle à la quatrième demande ?

**Oui pour les contrôles qui combinent des faits existants, non pour les
autres** — et c'est la coupe de la question 4 qui le permet. Un contrôle
chargé hors cycle est une donnée évaluée par `risk.Pass` : il passe par
le seul constructeur de `Control`, et la garantie tient. Un contrôle qui
aurait besoin d'un fait nouveau ne peut pas être chargé : `Load` le refuse.

Si la direction des risques exige plus — des contrôles arbitraires, écrits
par elle, branchés sans livraison —, alors il faut choisir, parce qu'un code
branché sans livraison est un code que le compilateur n'a pas vu, et la
garantie est une garantie **du compilateur**.

> **Je sacrifie l'expressivité des contrôles hors cycle, pas la garantie.** Et
> je le justifie **devant la direction des risques**, pas devant l'équipe
> technique : c'est elle qui perd quelque chose, et c'est elle qui a le plus
> à perdre d'un ordre réglé sans contrôle. Avec le chiffre du relevé — la
> part des contrôles qui ont exigé un fait nouveau — en main.

**La batterie dit ce qu'est un instrument, pas ce qu'est un effet (4).**
« Noël oublié » survit parce que les six réceptions de la batterie sont en
avril. « Seuil chèque exclu », « effet sans timbre », « prélèvement à J+2 »
survivent parce que la batterie vérifie qu'un instrument répond **une**
catégorie fiscale déclarée, pas **la bonne**. Ce n'est pas un trou de la
batterie, c'est sa définition : elle dit ce que **tout** instrument doit
tenir. Ce que **chaque** instrument répond est une fiche, tenue par l'équipe
qui le possède, seuils compris :

```go
// TestTheSheetOfEachInstrument: the battery says what an instrument IS. It
// does not say what a bill is. What each instrument answers, in particular at
// its thresholds, is one sheet per instrument — and the team that owns it
// keeps it.
func TestTheSheetOfEachInstrument(t *testing.T) {
    wednesday := time.Date(2026, time.April, 8, 10, 0, 0, 0, calendar.Paris)
    day := func(d int) time.Time { return time.Date(2026, time.April, d, 0, 0, 0, 0, calendar.Paris) }
    for _, c := range []struct {
        i         instrument.Instrument
        value     time.Time
        clearable bool
        tax       instrument.Treatment

        {Transfer{ClearingThreshold - 1, wednesday}, day(8), true, instrument.Neutral},
        {Transfer{ClearingThreshold, wednesday}, day(8), false, instrument.Neutral},
        {DirectDebit{1, wednesday}, day(9), true, instrument.Neutral},
        {Cheque{ChequeImageThreshold - 1, wednesday}, day(9), true, instrument.Neutral},
        {Cheque{ChequeImageThreshold, wednesday}, day(9), false, instrument.Neutral},
        {Bill{1, wednesday}, day(10), true, instrument.Stamp},
    } {
        ok, _ := c.i.Clearable()
        if !c.i.ValueDate().Equal(c.value) || ok != c.clearable || c.i.Tax() != c.tax {
            t.Errorf("%s at %d: value %s, clearable %v, tax %v",
                c.i.Code(), c.i.Amount(), c.i.ValueDate().Format(time.DateOnly), ok, c.i.Tax())
        }
    }
}
```

Et le calendrier gagne la sienne — une recopie du calendrier publié, assumée
comme telle :

```go
// TestThe2026Calendar copies the published closing calendar. A copy, yes: it
// is the specification, and the instruments' battery only covers April. The
// open days listed are the NEIGHBORS of the closed days, so that a table
// shifted by one day does not pass.
func TestThe2026Calendar(t *testing.T) {
    closedDays := []string{"2026-01-01", "2026-04-03", "2026-04-06", "2026-05-01", "2026-12-25", "2026-12-26"}
    openDays := []string{"2025-12-31", "2026-01-02", "2026-04-02", "2026-04-07",
        "2026-04-30", "2026-05-04", "2026-12-24", "2026-12-28"}
    for _, list := range []struct {
        days []string
        open bool
    }{{closedDays, false}, {openDays, true}} {
        for _, d := range list.days {
            day, err := time.ParseInLocation(time.DateOnly, d, Paris)
            if err != nil {
                t.Fatal(err)
            }
            if IsOpen(day) != list.open {
                t.Errorf("%s: IsOpen = %v", d, !list.open)
            }
        }
    }

```

**Une clause qui exigeait plus que le contrat (1) — suppression de branche.**
« Clause 4 sans le fuseau » retirait de la batterie une comparaison du
**fuseau** de la date rendue. Elle survit, et c'est la comparaison qui avait
tort : un minuit de Paris exprimé en UTC est **le même instant**, et le
contrat parle d'instants. La comparaison est supprimée ; la clause compare
l'heure à Paris, et rien d'autre.

**Un compteur jamais lu à zéro (1).** « Périmé à version égale » survit parce
qu'aucun test ne vérifiait que le compteur **reste** à zéro quand il doit.
`TestSettleAControlledOrder` le vérifie maintenant — c'est la même faute que la
clause 7 de l'exercice 3 : un test d'effet doit aussi regarder ce qui ne doit
pas changer.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Sans relevé, on décide **ce qu'on mesure** : une étiquette par fusion, deux rapports, deux seuils. |
| ⚫ | Le problème de l'expression, mesuré : par ligne, une question nouvelle donne N erreurs de compilation ; par colonne, **zéro, sur les deux axes**. Go n'a pas de `switch` exhaustif. |
| ⚫ | Sur l'axe ouvert, dans les deux découpes, l'oubli d'inscription est invisible — 0 erreur, 0 test rouge. Mesuré. |
| ⚫ | Une question n'entre dans l'interface que si sa réponse ne se calcule pas à partir des autres. Sinon, c'est une fonction. |
| ⚫ | OCP dit quel changement est bon marché ; SRP dit **qui** le demande. Une équipe, des paquets ; une seule racine de composition. |
| ⚫ | Un fait est du code, un contrôle est une donnée. C'est la coupe qui rend la quatrième demande compatible avec la deuxième, et elle a un coût qu'on dit à la direction des risques. |
| ⚫ | Doublon au registre : la table littérale ne compile pas ; les `init()` paniquent au démarrage du binaire et jamais dans les tests ; le JSON garde le dernier **en silence**. |
| ⚫ | La batterie dit ce qu'est **un** instrument ; la fiche dit ce qu'est **cet** instrument. Les deux sont nécessaires. |
| ⚫ | Le compilateur exige une méthode, pas une réponse. La valeur zéro d'une énumération ne doit jamais être une réponse valide. |
| ⚫ | Une batterie ne juge pas avec le code qu'elle vérifie. |
| ⚫ | Une clause peut avoir tort. Le virement instantané casse la clause 5, et c'est la clause qui change. |
| ⚫ | La garantie vit dans le **type** que le moteur exige. Un décorateur se contourne ; une signature, non. |
| ⚫ | Des champs non exportés empêchent de remplir une structure, pas de la déclarer : la valeur zéro est le trou, et il se ferme à l'exécution. |
| ⚫ | Un test qui attend un échec de compilation vérifie la **raison**. J'ai refait l'erreur de la correction 2.3/4, et c'est ce test qui l'a vue. |
| ⚫ | Ce que le type ne garantit pas se mesure : seuil, et plancher de bruit = débit × délai. |
