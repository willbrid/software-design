# Correction 2.2 — Exercice 1 : la plateforme de notification

> Rappel de l'énoncé : une interface `Canal` à huit méthodes, cinq
> implémentations, trois appelants aux besoins différents, et un relevé de
> quatorze mois qui donne un canal ajouté contre quatre méthodes ajoutées.

La réponse n'est ni « une interface » ni « un ensemble scellé ». C'est qu'il
**n'y a pas un seul ensemble**, et que cinq des huit méthodes n'ont jamais été
du polymorphisme. Tout ce qui suit est mesuré sur un module qui compile, dont
les cinq paquets de test passent sous `go vet` et `go test -race -count=1`.

## 1. L'axe du changement

### Ce que dit le relevé

| | Sur quatorze mois |
|---|---|
| canaux ajoutés | **1** |
| méthodes ajoutées à `Canal` | **4** |
| modifications d'implémentations existantes | **31** |

Les deux premières lignes donnent l'axe sans ambiguïté : **les opérations
arrivent, les variantes non**. Un canal tous les quatorze mois, une question
nouvelle tous les trois mois et demi. Avec l'interface actuelle, chaque
question nouvelle a coûté **cinq modifications** — une par implémentation — et
le métier n'a jamais rien demandé de ce qui aurait rendu ces cinq
modifications utiles.

### Ce que la troisième ligne ajoute, et que la plupart des réponses oublient

Trente-et-une modifications d'implémentations existantes, c'est **plus de deux
par mois**. Ce chiffre ne s'explique pas par les quatre méthodes ajoutées : il
faut aller voir ce qu'elles changeaient.

Et quand on va voir, on trouve des tarifs, des plafonds, des numéros de
compte. `CoutUnitaireFCFA` qui passe de 14 à 15 FCFA. `LongueurMaximale` d'un
canal WhatsApp qui passe de 1 024 à 4 096. Une ligne de refacturation
renumérotée par le cabinet comptable.

> Trente-et-une modifications de code pour trente-et-un changements de
> **données**. Le relevé ne dit pas seulement sur quel axe le changement
> arrive : il dit aussi que **la moitié de cette interface n'aurait jamais dû
> être du code**.

C'est le fil à tirer, et il mène à la vraie réponse.

## 2. Les huit méthodes, une par une

Le critère de la leçon : *une méthode appartient à la variante si et seulement
si elle se répond avec les champs de la variante*. Appliqué aux huit, il donne
trois groupes et non deux.

| Méthode | Se répond avec les champs ? | Verdict |
|---|---|---|
| `Nom()` | oui | identité du canal — **reste** |
| `Envoyer()` | oui, avec son transport | comportement — **reste** |
| `EstDisponible()` | oui, avec son transport | comportement — **reste** |
| `CoutUnitaireFCFA()` | elle rend **une constante** | ce n'est pas une méthode, c'est une **donnée** |
| `LongueurMaximale()` | elle rend **une constante** | donnée |
| `LigneDeFacturation()` | elle rend **une constante** | donnée |
| `DelaiMoyenSecondes()` | elle rend **une constante** | donnée |
| `SupporteAccuseDeReception()` | elle rend **une constante** | donnée |

Cinq des huit rendent une constante différente par implémentation. C'est mot
pour mot le cas de la leçon :

> Quand deux implémentations ne diffèrent que par des **constantes**, le
> polymorphisme est un tableau qui s'ignore.

Et on ne s'arrête pas à l'affirmation.

## 3. Le test qui tranche

```go
// TestCinqMethodesSurHuitSeRamenentALaTable est le test qui tranche.
//
// Il ne dit pas que la table est « plus propre ». Il dit que pour chacune des
// cinq implementations, les cinq methodes constantes rendent exactement ce
// que rend la fiche de catalogue. Si c'est vrai, ces cinq methodes ne
// distinguaient rien : vingt-cinq methodes remplacees par cinq champs.
//
// Les trois methodes restantes — Nom, EstDisponible, Envoyer — ne s'y
// ramenent pas : la premiere identifie, les deux autres sont du comportement.
func TestCinqMethodesSurHuitSeRamenentALaTable(t *testing.T) {
    compare := 0
    for _, c := range avant.Tous() {
        nom, err := catalogue.Analyser(c.Nom())
        if err != nil {
            t.Fatalf("%s absent du catalogue : %v", c.Nom(), err)
        }
        fiche, err := catalogue.Lire(nom)
        if err != nil {
            t.Fatal(err)
        }
        if got, want := c.CoutUnitaireFCFA(), fiche.CoutUnitaireFCFA; got != want {
            t.Errorf("%s : cout %d, table %d", c.Nom(), got, want)
        }
        if got, want := c.LongueurMaximale(), fiche.LongueurMaximale; got != want {
            t.Errorf("%s : longueur max %d, table %d", c.Nom(), got, want)
        }
        if got, want := c.LigneDeFacturation(), fiche.LigneFacturation; got != want {
            t.Errorf("%s : ligne %q, table %q", c.Nom(), got, want)
        }
        if got, want := c.DelaiMoyenSecondes(), fiche.DelaiMoyenSecondes; got != want {
            t.Errorf("%s : delai %d, table %d", c.Nom(), got, want)
        }
        if got, want := c.SupporteAccuseDeReception(), fiche.AccuseDeReception; got != want {
            t.Errorf("%s : accuse %v, table %v", c.Nom(), got, want)
        }
        compare += 5
    }
    if compare != 25 {
        t.Fatalf("%d comparaisons, attendu 25", compare)
    }
    t.Logf("%d comparaisons sur 5 canaux : les 5 methodes constantes et la table rendent la meme chose",
        compare)
}
```

```
25 comparaisons sur 5 canaux : les 5 methodes constantes et la table rendent la meme chose
```

Vingt-cinq comparaisons, vingt-cinq égalités. Les cinq méthodes ne
distinguaient rien : **vingt-cinq méthodes remplacées par cinq champs.**

Les trois autres ne s'y ramènent pas, et c'est aussi important : `Nom`
identifie, `EstDisponible` et `Envoyer` sont du comportement réel qui dépend
d'un réseau. Le test ne les compare pas, parce qu'il n'y a rien à comparer.

## 4. La conception qui en découle

### Le catalogue — ce qui n'était jamais du polymorphisme

```go
// Fiche est la ligne de catalogue d'un canal.
//
// Cinq champs, qui remplacent cinq methodes. Noter qu'aucun n'est un
// comportement : ce sont des faits contractuels, ils changent par avenant, et
// ils n'ont jamais eu besoin d'etre du code.
type Fiche struct {
    // CoutUnitaireFCFA est le cout d'un envoi, refacture au client.
    CoutUnitaireFCFA int
    // LongueurMaximale est le nombre d'octets au-dela duquel le message est
    // refuse. Zero signifie « sans limite », et c'est la correction du
    // defaut de l'enonce : CourrierPostal rendait 0 pour « pas de limite »
    // alors que SMS rendait 160 pour « 160 ».
    LongueurMaximale int
    // LigneFacturation est le compte de refacturation.
    LigneFacturation string
    // DelaiMoyenSecondes est le delai de remise observe, pas promis.
    DelaiMoyenSecondes int
    // AccuseDeReception dit si le canal sait confirmer la remise.
    AccuseDeReception bool
}
```

Deux détails qui règlent la question 3 de l'énoncé.

**`LongueurMaximale` à zéro signifie « sans limite »**, et c'est écrit dans la
documentation du champ. Dans le modèle d'origine, `CourrierPostal` rendait `0`
pour « pas de limite » et `SMS` rendait `160` pour « 160 octets » — la même
signature, deux sens incompatibles, et aucun appelant capable de les
distinguer. Ici le sens est décidé **à un seul endroit**, et un test le garde.

**`Lire` rend une erreur et non une fiche vide.** Une fiche vide signifierait
« gratuit, sans limite, remise instantanée » : exactement le contraire du
choix le plus restrictif, qui est la règle de la leçon 2.1 sur la valeur zéro.

```go
// Lire rend la fiche d'un canal, ou dit qu'elle n'existe pas.
//
// Elle rend une erreur et non une fiche vide : une fiche vide signifierait
// « gratuit, sans limite, remise instantanee », c'est-a-dire le contraire du
// choix le plus restrictif.
func Lire(n Nom) (Fiche, error) {
    f, ok := fiches[n]
    if !ok {
        return Fiche{}, fmt.Errorf("%w : %q", ErrCanalInconnu, n)
    }
    return f, nil
}

// Analyser canonise un nom venu de la configuration.
//
// L'ORDRE des trois normalisations n'est pas commutatif, et un test l'a
// montre. Ma premiere version remplacait les espaces par des tirets bas
// AVANT de couper ceux du bord : "  WhatsApp  " devenait "__WHATSAPP__", et
// le canal n'etait pas trouve. Il faut couper les bords d'abord.
func Analyser(s string) (Nom, error) {
    n := Nom(strings.ReplaceAll(strings.ToUpper(strings.TrimSpace(s)), " ", "_"))
    if _, ok := fiches[n]; !ok {
        return "", fmt.Errorf("%w : %q", ErrCanalInconnu, s)
    }
    return n, nil
}
```

Et une chose que je n'avais pas vue en écrivant `Analyser` :

> **L'ordre des normalisations n'est pas commutatif.** Ma première version
> remplaçait les espaces par des tirets bas **avant** de couper ceux du bord :
> `"  WhatsApp  "` devenait `"__WHATSAPP__"`, et le canal n'était pas trouvé.
> Un test l'a dit, pas une relecture.

### L'interface, et elle n'a que trois méthodes

```go
// Expediteur est l'interface DE CE PAQUET. Trois methodes, parce que ce
// paquet en appelle trois — et pas huit.
//
// Elle est declaree ici et non aux cotes des implementations. Sa signature ne
// nomme que des types partages — string et catalogue.Nom — donc une
// implementation n'a pas a importer ce paquet.
type Expediteur interface {
    Canal() catalogue.Nom
    EstDisponible() bool
    Envoyer(destinataire, corps string) (identifiant string, err error)
}

// Journal enregistre ce que fait l'expedition.
//
// Selection est appelee au moment du CHOIX, avant de savoir si ca marche :
// sans cette ligne, une panne de canal n'est pas attribuable, parce que celui
// qui ecrit la ligne de resultat ne sait pas quel canal a ete retenu.
type Journal interface {
    Selection(reference string, canal catalogue.Nom)
    Resultat(reference string, canal catalogue.Nom, err error)
}
```

Elle est déclarée chez `expedition`, parce que c'est `expedition` qui s'en
sert. Elle a trois méthodes parce que `expedition` en appelle trois. Et sa
signature ne nomme que `string` et `catalogue.Nom` — du vocabulaire partagé —
donc une implémentation n'a pas à importer son appelant. La mesure :

```
$ for p in catalogue expedition canaux redaction facturation; do
>   printf '%-14s : ' $p; go list -f '{{join .Imports " "}}' ./$p
> done
catalogue      : errors fmt strings
expedition     : errors exemple/notification/catalogue fmt
canaux         : errors exemple/notification/catalogue fmt
redaction      : exemple/notification/catalogue strings unicode/utf8
facturation    : exemple/notification/catalogue fmt
```

`canaux` n'importe pas `expedition`. Et `catalogue` n'importe rien du module :
c'est le vocabulaire, il est en bas.

### Les deux autres appelants ne déclarent aucune interface

C'est le résultat de l'exercice, et c'est celui qui surprend.

```go
// Package redaction tronque et met en forme un message.
//
// Il ne declare AUCUNE interface, et c'est le resultat de l'exercice.
//
// L'enonce dit qu'il n'appelle que LongueurMaximale(). Une longueur maximale
// n'est pas un comportement, c'est un nombre : ce paquet n'a donc pas besoin
// d'un canal, il a besoin d'une fiche. Il ne declare pas d'interface, il n'a
// pas de double a ecrire, et aucun de ses tests n'a besoin d'un faux canal.
package redaction

import (
    "strings"
    "unicode/utf8"

    "exemple/notification/catalogue"
)

// Marque est ce qu'on ajoute quand on coupe.
const Marque = "..."
```

L'énoncé dit que `redaction` n'appelle que `LongueurMaximale()`. Une longueur
maximale n'est pas un comportement, c'est un nombre. Ce paquet n'a donc pas
besoin d'un canal : **il a besoin d'une fiche**. Il ne déclare pas
d'interface, il n'a pas de double à écrire, et aucun de ses tests n'a besoin
d'un faux canal.

Même chose pour `facturation`, qui n'appelait que `CoutUnitaireFCFA` et
`LigneDeFacturation`.

| Appelant | Interface déclarée | Méthodes | Double de test |
|---|---|---|---|
| `expedition` | `Expediteur` | 3 | 3 méthodes, toutes lues |
| `redaction` | **aucune** | — | **aucun** |
| `facturation` | **aucune** | — | **aucun** |

> Deux appelants sur trois n'avaient pas besoin de polymorphisme. Ils avaient
> besoin d'une donnée, et on leur avait donné une interface à huit méthodes.

## 5. Les doubles, comptés (question 4)

L'énoncé demandait le compte. Il est dans le code, pas dans une estimation.

### Avant

Trois appelants, chacun avec son double de l'interface à huit méthodes. Voilà
celui d'`expedition`, écrit en entier et conservé dans le dépôt pour être
compté :

```go
// --- Le double qu'il aurait fallu avec l'interface d'origine ---

// doubleAHuitMethodes n'est utilise par aucun test. Il est ici pour etre
// COMPTE : c'est ce qu'il aurait fallu ecrire, dans chacun des trois
// appelants, avec l'interface a huit methodes de l'enonce.
//
// Cinq de ses huit methodes ne sont jamais lues par le code d'expedition. Et
// cinq methodes inutiles dans un double, ce ne sont pas cinq lignes de trop :
// ce sont cinq endroits ou une future methode ira se cacher, et cinq valeurs
// que personne ne verifie.
type doubleAHuitMethodes struct{ disponible bool }

func (doubleAHuitMethodes) Nom() string                         { return "SMS" }
func (d doubleAHuitMethodes) EstDisponible() bool               { return d.disponible }
func (doubleAHuitMethodes) Envoyer(d, c string) (string, error) { return "SMS-1", nil }
func (doubleAHuitMethodes) CoutUnitaireFCFA() int               { return 0 }     // jamais lue ici
func (doubleAHuitMethodes) LongueurMaximale() int               { return 0 }     // jamais lue ici
func (doubleAHuitMethodes) SupporteAccuseDeReception() bool     { return false } // jamais lue ici
func (doubleAHuitMethodes) DelaiMoyenSecondes() int             { return 0 }     // jamais lue ici
func (doubleAHuitMethodes) LigneDeFacturation() string          { return "" }    // jamais lue ici
```

| Appelant | Méthodes à écrire | Méthodes réellement lues | **Vides** |
|---|---|---|---|
| `expedition` | 8 | `Nom`, `EstDisponible`, `Envoyer` → 3 | **5** |
| `facturation` | 8 | `Nom`, `CoutUnitaireFCFA`, `LigneDeFacturation` → 3 | **5** |
| `redaction` | 8 | `LongueurMaximale` → 1 | **7** |
| **total** | **24** | **7** | **17** |

### Après

```go
// --- Le double dont ce paquet a besoin : TROIS methodes ---

// doubleATroisMethodes est le double de l'interface declaree par expedition.
//
// Trois methodes, et les trois sont appelees par le code teste. Zero methode
// vide. C'est la mesure de l'exercice, et elle se compare au double de la
// section suivante.
type doubleATroisMethodes struct {
    canal      catalogue.Nom
    disponible bool
    erreur     error
    appels     []string
    // journal n'est pas une commodite : c'est le point d'observation.
    //
    // Ma premiere version de ce double n'ecrivait rien dans le journal, et le
    // test d'ordre comparait seulement « selection » puis « resultat ». Une
    // modification de la campagne l'a mis a nu : en deplacant l'appel a
    // Selection APRES e.Envoyer(...), la suite du journal reste identique,
    // parce que Resultat vient apres Selection dans les deux cas. Le test a
    // survecu a la modification qu'il etait cense attraper — et c'est la
    // DEUXIEME fois dans ce chapitre, apres la lecon elle-meme.
    //
    //    Un test d'ordre doit s'observer depuis le point INTERMEDIAIRE, pas
    //    depuis le bout de la chaine. Connaitre la regle ne suffit pas : il
    //    faut le test qui l'applique.
    journal *journalOrdonne
}

func (d *doubleATroisMethodes) Canal() catalogue.Nom { return d.canal }
func (d *doubleATroisMethodes) EstDisponible() bool  { return d.disponible }
func (d *doubleATroisMethodes) Envoyer(dest, corps string) (string, error) {
    d.appels = append(d.appels, dest+"/"+corps)
    if d.journal != nil {
        d.journal.suite = append(d.journal.suite, "appel:"+string(d.canal))
    }
    if d.erreur != nil {
        return "", d.erreur
    }
    return string(d.canal) + "-1", nil
}
```

| Appelant | Méthodes à écrire | Vides |
|---|---|---|
| `expedition` | 3 | 0 |
| `facturation` | 0 | 0 |
| `redaction` | 0 | 0 |
| **total** | **3** | **0** |

**Vingt-quatre méthodes de double devenues trois, dix-sept méthodes vides
devenues zéro.** Et le chiffre qui compte le plus est le dix-sept :

> Cinq méthodes inutiles dans un double, ce ne sont pas cinq lignes de trop :
> ce sont cinq endroits où une future méthode ira se cacher, et cinq valeurs
> que personne ne vérifie.

## 6. Les deux questions difficiles

### Question 5 — `CourrierPostal.Envoyer` et `SMS.Envoyer` sont-ils la même opération ?

**Oui pour la signature, non pour le contrat.** Et c'est la seule réponse
honnête.

Les deux acceptent un destinataire et un corps, et rendent un identifiant ou
une erreur. C'est la même opération au sens de l'interface, et le type switch
serait ici une erreur.

Mais l'identifiant ne garantit pas la même chose. Pour le SMS, il dit « la
passerelle a accepté ». Pour le courrier postal, il dit « le fichier est
écrit », et la remise aura lieu douze heures plus tard — ou pas.

```go
// CourrierPostal depose un fichier qu'un prestataire releve deux fois par
// jour.
//
// C'est la reponse a la question 5 : Envoyer est bien la meme OPERATION que
// celle de SMS — accepter un message et rendre un identifiant — mais
// l'identifiant ne garantit PAS la meme chose. Pour SMS il dit « la
// passerelle a accepte ». Ici il dit « le fichier est ecrit », et la remise
// aura lieu douze heures plus tard.
//
// La difference n'est donc pas dans l'interface, elle est dans le CONTRAT de
// l'interface, et c'est pour ca qu'il est ecrit ici.
type CourrierPostal struct {
    Depot Passerelle
}

func (CourrierPostal) Canal() catalogue.Nom { return catalogue.CourrierPostal }

func (c CourrierPostal) EstDisponible() bool { return c.Depot != nil }

func (c CourrierPostal) Envoyer(destinataire, corps string) (string, error) {
    if c.Depot == nil {
        return "", fmt.Errorf("%w : aucun depot configure", ErrPasserelle)
    }
    ref, err := c.Depot.Remettre(destinataire, corps)
    if err != nil {
        return "", fmt.Errorf("%w : depot : %w", ErrPasserelle, err)
    }
    // Le prefixe dit ce que l'identifiant garantit, et ce qu'il ne garantit
    // pas. Un appelant qui le lit sait qu'il n'a pas une remise.
    return "DEPOSE:" + ref, nil
}
```

La différence n'est donc pas dans l'interface, elle est dans le **contrat** de
l'interface. Et puisqu'un contrat non écrit n'est pas un contrat, il est
écrit : le préfixe `DEPOSE:` dit ce que l'identifiant ne garantit pas, et un
test le vérifie.

> Deux implémentations qui satisfont la même signature avec des garanties
> différentes ne sont pas substituables. L'interface ne le voit pas ; c'est le
> sujet de la leçon 2.4.

### Question 6 — pourquoi « sceller `Canal` et mettre les quatre dernières méthodes dans des `switch` » est la mauvaise réponse

Deux raisons, et elles sont indépendantes.

**La première : quatre de ces questions ne sont pas des questions.** Mettre
`CoutUnitaireFCFA` dans un `switch` chez `facturation`, c'est déplacer une
table de tarifs du code vers… du code. On garde les trente-et-une
modifications de code pour trente-et-un changements de données, et on ajoute
un test d'exhaustivité pour les surveiller. Le scellement est l'outil juste
pour un ensemble fermé de variantes avec des opérations ouvertes ; il n'est
pas l'outil pour des constantes.

**La seconde : l'ensemble n'est pas fermé, il est en train de s'ouvrir** — et
c'est la question 7 qui le dit.

### Question 7 — les trois agrégateurs SMS en A/B

Le marketing veut tester trois agrégateurs sur le trafic réel, et pouvoir en
changer sans redéploiement. Ça change la réponse à la question 1, mais **pas
partout** :

| | Avant la demande | Après |
|---|---|---|
| l'ensemble des **canaux** | fermé (1 en 14 mois) | toujours fermé |
| l'ensemble des **transports d'un canal** | 1 par canal | **ouvert**, et il bouge à la semaine |

C'est un deuxième ensemble, et il s'ouvre **sur une branche** du premier. La
réponse de la leçon s'applique telle quelle : *les deux autant → tu as deux
ensembles, pas un. Sépare-les.*

```go
// SMS envoie par un agregateur SMS.
//
// Noter le champ Agregateur : c'est la reponse a la question 7 de l'enonce.
// Le jour ou le marketing veut tester trois agregateurs en A/B, l'ensemble
// des variantes s'ouvre SUR CETTE BRANCHE et sur elle seule — et c'est deja
// une interface, donc il n'y a rien a refaire.
type SMS struct {
    Agregateur string
    Passerelle Passerelle
}

func (SMS) Canal() catalogue.Nom { return catalogue.SMS }

func (s SMS) EstDisponible() bool { return s.Passerelle != nil }

func (s SMS) Envoyer(destinataire, corps string) (string, error) {
    if s.Passerelle == nil {
        return "", fmt.Errorf("%w : %s sans passerelle", ErrPasserelle, s.Agregateur)
    }
    id, err := s.Passerelle.Remettre(destinataire, corps)
    if err != nil {
        return "", fmt.Errorf("%w : %s : %w", ErrPasserelle, s.Agregateur, err)
    }
    return s.Agregateur + ":" + id, nil
}
```

L'interface `Passerelle` a **une** méthode, elle est déclarée par `canaux`, et
le champ `Agregateur` nomme celui qui a été retenu. Le découpage fait que cet
ajout ne touche à rien d'autre : ni au catalogue, ni à `expedition`, ni aux
quatre autres canaux.

Et ce que la leçon dit d'indispensable, et qui est le vrai sujet de la
question 7 :

> Toute sélection dynamique doit être journalisée **au point de sélection**,
> et **avant** l'appel. Sans ça, le jour où l'agrégateur B se dégrade, le taux
> d'échec global monte de deux points et personne ne sait lequel des trois en
> est la cause.

C'est pour ça que `Journal` a deux méthodes et que `Selection` est appelée
avant `Envoyer` :

```go
// Envoyer essaie les expediteurs dans l'ordre et rend le premier qui aboutit.
func Envoyer(j Journal, reference, destinataire, corps string, candidats ...Expediteur) (string, error) {
    if len(candidats) == 0 {
        return "", fmt.Errorf("%w : %s", ErrAucunCanal, reference)
    }
    var derniere error
    for _, e := range candidats {
        fiche, err := catalogue.Lire(e.Canal())
        if err != nil {
            derniere = err
            continue
        }
        if fiche.LongueurMaximale > 0 && len(corps) > fiche.LongueurMaximale {
            derniere = fmt.Errorf("%w : %d octets pour %s qui en accepte %d",
                ErrTropLong, len(corps), e.Canal(), fiche.LongueurMaximale)
            continue
        }
        if !e.EstDisponible() {
            derniere = fmt.Errorf("%w : %s", ErrIndisponible, e.Canal())
            continue
        }
        // Le choix est journalise AVANT l'appel : si l'envoi part en timeout
        // puis que le processus est tue, la ligne de selection existe deja.
        j.Selection(reference, e.Canal())
        id, err := e.Envoyer(destinataire, corps)
        j.Resultat(reference, e.Canal(), err)
        if err == nil {
            return id, nil
        }
        derniere = err
    }
    return "", derniere
}
```

## 7. Les assertions de conformité

Le modèle d'origine n'en avait aucune. Mesure, sur l'ajout d'une neuvième
méthode à `Canal` :

```
Une neuvieme methode est ajoutee a avant.Canal.
  avec les 5 assertions : 10 erreur(s) de compilation
  sans les assertions   :  5 erreur(s) de compilation
```

Les cinq du bas viennent du littéral de `Tous()`, qui assigne les cinq
implémentations à `Canal` — une assertion de conformité qui ne se présente pas
comme telle. Les cinq du haut sont les lignes explicites.

Sans `Tous()` **et** sans les assertions, il y en aurait zéro : Go n'a pas de
déclaration `implements`, donc le compilateur n'a rien à vérifier.

## 8. La campagne de modifications

Onze modifications, cinq paquets de test.

```
modification                                                  | tests qui tombent
--------------------------------------------------------------+------------------
 1. le catalogue perd la fiche du courrier postal             | 7
 2. Lire rend une fiche vide au lieu d'une erreur             | 3
 3. Analyser ne coupe plus les espaces du bord                | 1
 4. une longueur maximale nulle devient un refus              | 1
 5. la selection est journalisee APRES l'appel                | 2
 6. la disponibilite est verifiee apres l'envoi               | 2
 7. la coupe se fait sur les octets et non les runes          | 1
 8. Preparer ne dit plus qu'il a tronque                      | 2
 9. la refacturation oublie la quantite                       | 4
10. le SMS n'enveloppe plus l'erreur de sa passerelle         | 1
11. l'identifiant du courrier ne dit plus ce qu'il garantit   | 1

11/11 modifications detectees
```

Et l'aveu qui va avec, parce qu'il vaut plus que le relevé.

**La modification 5 a d'abord survécu.** Exactement comme dans la leçon, pour
exactement la même raison : mon `journalOrdonne` n'enregistrait que les appels
au journal, donc déplacer `Selection` après `Envoyer` laissait la suite
inchangée — *sélection* puis *résultat* dans les deux cas.

J'avais écrit la règle dans la leçon 2.2 une heure plus tôt. Je l'ai refaite.

> **Connaître la règle ne suffit pas : il faut le test qui l'applique.** Un
> test d'ordre s'observe depuis le point intermédiaire, et le seul moyen de s'y
> tenir est que le double lui-même écrive son passage dans la suite observée.

La modification 7 mérite un mot aussi. Couper un message sur les **octets**
plutôt que sur les **runes** casse un caractère accentué en deux, et le client
reçoit un losange noir à la place. Le test qui l'attrape utilise 81 fois « é »
— 162 octets sur un canal à 160, donc la coupe tombe pile au milieu du dernier
caractère. Sans ce cas limite, la modification survivait.

## 9. Ce que cet exercice devait faire comprendre

1. **Le relevé a trois colonnes, pas deux.** Les deux premières donnent l'axe,
   la troisième dit si l'interface contient des données déguisées en code.
2. **Cinq méthodes sur huit n'étaient pas du polymorphisme**, et un test
   d'équivalence le démontre en vingt-cinq comparaisons.
3. **La bonne réponse n'était ni l'interface ni le type somme** : c'était une
   table plus une interface à trois méthodes.
4. **Deux appelants sur trois n'avaient besoin d'aucune interface.** Ils
   avaient besoin d'un nombre.
5. **Le compte des doubles est la mesure**, et il passe de 24 méthodes dont 17
   vides à 3 méthodes dont 0 vide.
6. **Deux implémentations peuvent satisfaire la même signature avec des
   garanties différentes.** L'interface ne le voit pas, le contrat doit le
   dire, et c'est la leçon 2.4.
7. **Un ensemble peut s'ouvrir sur une seule de ses branches.** Deux
   ensembles, deux mécanismes, et le découpage fait que l'ouverture ne coûte
   rien ailleurs.
