# Correction 2.1 — Exercice 5 : incident de production

## Le fait qui change tout, et qui n'est pas dans le post-mortem

Avant toute analyse, il faut corriger une phrase du post-mortem. Celle-ci :

> *Il tourne depuis quatorze mois et avait fusionné 11 comptes au total, tous
> légitimement.*

Lue telle quelle, elle dit *« le travail marchait, et quelque chose l'a
cassé »*. C'est faux, et c'est l'erreur d'analyse qui ferait choisir la mauvaise
correction.

> **Le travail de dédoublonnage ne marchait pas depuis quatorze mois. Il ne
> faisait presque rien, parce que les données étaient trop sales pour qu'il
> trouve deux lignes égales. La campagne de nettoyage l'a mis en marche.**

Ce n'est pas une interprétation. C'est mesurable, et voici la mesure.

## L'incident, reproduit et mesuré

```go
// Compte est le type d'origine, reduit aux champs que MemeCompte regarde.
type Compte struct {
    Numero    string
    Nom       string
    Prenom    string
    DateNais  time.Time
    NumeroCNI string
    SoldeFCFA int64
}

// MemeCompte est la fonction de l'incident, reprise telle quelle.
func MemeCompte(a, b Compte) bool {
    return a.Nom == b.Nom && a.Prenom == b.Prenom &&
        a.DateNais.Equal(b.DateNais) && a.NumeroCNI == b.NumeroCNI
}
```

Le parc, avec les proportions du post-mortem — une part vérifiée avec CNI,
60 % sans date de naissance, et des noms écrits **salement**, comme dans un
parc constitué par saisie manuelle pendant des années :

```go
// Les noms sont tires de listes courtes, pour que les homonymes apparaissent
// naturellement — comme dans un vrai parc.
var (
    noms    = []string{"NDIAYE", "MBARGA", "FOTSO", "NJOYA", "ESSOMBA", "TCHOUTA", "BIYA", "ABEGA"}
    prenoms = []string{"Awa", "Boubacar", "Marie", "Jean", "Fatou", "Paul", "Aisha", "Eric"}
)

// Parc fabrique un parc de n comptes, avec les proportions du post-mortem :
// une part verifiee avec CNI, et 60 % sans date de naissance.
//
// Les noms sont ecrits SALEMENT : casse variable, accents, espaces en trop.
// C'est l'etat reel d'un parc constitue par saisie manuelle pendant des annees,
// et c'est cette salete qui a protege les donnees pendant quatorze mois.
func Parc(n int, partVerifiee float64, graine int64) []Compte {
    alea := rand.New(rand.NewSource(graine))
    parc := make([]Compte, 0, n)

    for i := 0; i < n; i++ {
        nom := noms[alea.Intn(len(noms))]
        prenom := prenoms[alea.Intn(len(prenoms))]

        c := Compte{
            Numero:    "2376" + pad(alea.Intn(100000000), 8),
            Nom:       salir(nom, alea),
            Prenom:    salir(prenom, alea),
            SoldeFCFA: int64(alea.Intn(200000)),
        }
        // 40 % ont une date de naissance.
        if alea.Float64() < 0.40 {
            c.DateNais = time.Date(1970+alea.Intn(40), time.Month(1+alea.Intn(12)), 1+alea.Intn(28), 0, 0, 0, 0, time.UTC)
        }
        // La part verifiee a une CNI, unique par abonne.
        if alea.Float64() < partVerifiee {
            c.NumeroCNI = "CNI" + pad(i, 9)
        }
        parc = append(parc, c)
    }
    return parc
}

// Normaliser est ce que la campagne de verification a fait aux noms :
// majuscules, sans accents, espaces reduits.
//
// C'est un nettoyage. Il est correct, il etait demande, et c'est lui qui a
// declenche l'incident.
func Normaliser(parc []Compte) []Compte {
    sortie := make([]Compte, len(parc))
    for i, c := range parc {
        c.Nom = canoniser(c.Nom)
        c.Prenom = canoniser(c.Prenom)
        sortie[i] = c
    }
    return sortie
}
```

Et la mesure :

```go
// TestLaCampagneDeNettoyageADeclencheLIncident est le test central de cette
// correction.
//
// Il ne verifie pas un comportement : il MESURE un ecart. Le meme parc, le meme
// travail de dedoublonnage, et la seule difference est que les noms ont ete
// normalises — un nettoyage correct, demande, et parfaitement innocent en
// apparence.
func TestLaCampagneDeNettoyageADeclencheLIncident(t *testing.T) {
    const comptes = 2000
    const partVerifiee = 0.17 // 340 000 sur 2 000 000

    avant := fusion.Parc(comptes, partVerifiee, 1)
    apres := fusion.Normaliser(avant)

    pairesAvant, groupeAvant := fusion.Collisions(avant)
    pairesApres, groupeApres := fusion.Collisions(apres)
    argentAvant := fusion.FCFAEnJeu(avant)
    argentApres := fusion.FCFAEnJeu(apres)

    t.Logf("AVANT la campagne : %d paires declarees identiques, plus gros groupe %d comptes, %d FCFA en jeu",
        pairesAvant, groupeAvant, argentAvant)
    t.Logf("APRES la campagne : %d paires declarees identiques, plus gros groupe %d comptes, %d FCFA en jeu",
        pairesApres, groupeApres, argentApres)
    if pairesAvant > 0 {
        t.Logf("multiplication des collisions : x%.1f", float64(pairesApres)/float64(pairesAvant))
    }

    if pairesApres <= pairesAvant {
        t.Fatalf("la normalisation devrait AUGMENTER les collisions : %d -> %d",
            pairesAvant, pairesApres)
    }
}
```

```

    AVANT la campagne : 461 paires declarees identiques, plus gros groupe 6 comptes, 54405127 FCFA en jeu
    APRES la campagne : 7684 paires declarees identiques, plus gros groupe 25 comptes, 98656400 FCFA en jeu
    multiplication des collisions : x16.7
```

Sur deux mille comptes. **Le nettoyage a multiplié les collisions par
seize**, et le plus gros groupe de comptes mutuellement « identiques » est
passé de six à **vingt-cinq**.

> La saleté des données était un garde-fou. Personne ne l'avait choisi,
> personne ne le savait, et c'est pour ça que le nettoyer a été dangereux.
> **Un garde-fou accidentel est un garde-fou qu'on retire sans s'en apercevoir.**

### Et l'asymétrie que personne n'avait vue

```go
// TestLaVerificationProtegeCeuxQuElleTouche montre l'asymetrie que personne
// n'avait vue.
//
// La campagne a enregistre 340 000 CNI. Ces comptes-la sont devenus
// INFUSIONNABLES, parce que leur CNI est unique. La campagne a donc protege
// ceux qu'elle a touches et rendu les autres indistinguables.
func TestLaVerificationProtegeCeuxQuElleTouche(t *testing.T) {
    const comptes = 2000

    for _, part := range []float64{0.0, 0.17, 0.50, 1.0} {
        parc := fusion.Normaliser(fusion.Parc(comptes, part, 1))
        paires, groupe := fusion.Collisions(parc)
        t.Logf("%3.0f %% du parc verifie : %6d paires, plus gros groupe %3d comptes",
            part*100, paires, groupe)

        if part == 1.0 && paires != 0 {
            t.Fatalf("un parc entierement verifie ne devrait avoir aucune"+
                " collision, obtenu %d", paires)
        }
    }
}
```

```

      0 % du parc verifie :  11303 paires, plus gros groupe  28 comptes
     17 % du parc verifie :   7684 paires, plus gros groupe  25 comptes
     50 % du parc verifie :   2653 paires, plus gros groupe  17 comptes

```

**La campagne a protégé exactement ceux qu'elle a touchés.** Un compte avec une
CNI enregistrée est infusionnable, puisque sa CNI est unique. Les 340 000
vérifiés étaient en sécurité ; les 1 660 000 autres ont été rendus
indistinguables par la normalisation de leurs noms.

Et la conclusion qui ne se devine pas : **plus la campagne de vérification
avançait, plus le risque augmentait pour ceux qui n'étaient pas encore
vérifiés.** Au moment où elle a atteint 17 %, le travail nocturne a trouvé de
quoi fusionner.

## Question 1 — les quatre décisions de modélisation

### 1. L'identité du compte est son numéro, et la comparaison porte sur autre chose

L'identité de `Compte` est `Numero`. `MemeCompte` compare `Nom`, `Prenom`,
`DateNais` et `NumeroCNI` — **aucun des quatre n'est l'identité**.

C'est la leçon 2.1 dans sa forme la plus coûteuse : *l'égalité structurelle sur
une entité se trompe dans les deux sens*, et le code la pratique sous un nom
rassurant.

Le ⚫ de la leçon — `_ [0]func()`, et `==` qui ne compile plus — n'aurait pas
suffi ici, parce que `MemeCompte` n'utilise pas `==`. Mais il aurait forcé la
question : *si je dois écrire ma propre fonction d'égalité, sur quels champs ?*
Et la réponse, posée explicitement, est `Numero`.

### 2. L'égalité porte sur des attributs facultatifs

`Nom`, `Prenom`, `DateNais`, `NumeroCNI` sont tous les quatre **optionnels**
dans ce modèle. Rien ne les exige.

Donc la comparaison est faite sur des champs qui peuvent tous être à leur valeur
zéro **en même temps** — et `time.Time{}.Equal(time.Time{})` rend `true`.

```go
// TestDeuxComptesVidesSontDeclaresIdentiques est le mecanisme, isole.
//
// Aucune donnee aleatoire, aucune proportion : deux comptes ouverts par USSD,
// ou l'on ne saisit que le numero. Quatre champs vides, et time.Time{} qui est
// egal a lui-meme.
func TestDeuxComptesVidesSontDeclaresIdentiques(t *testing.T) {
    a := fusion.Compte{Numero: "237691234567", SoldeFCFA: 12_400}
    b := fusion.Compte{Numero: "237698765432", SoldeFCFA: 3_100}

    if !fusion.MemeCompte(a, b) {
        t.Fatal("les deux devraient etre declares identiques : c'est le defaut")
    }
    t.Logf("deux abonnes sans rapport, declares identiques. La fusion verse"+
        " %d FCFA sur un compte qui n'est pas le leur", b.SoldeFCFA)
}
```

```
    deux abonnes sans rapport, declares identiques. La fusion verse 3100 FCFA sur un compte qui n'est pas le leur
```

> Une comparaison sur des attributs facultatifs n'est pas une comparaison
> imparfaite : c'est une comparaison qui déclare identiques **tous les objets
> non renseignés**. Et un parc en contient toujours une majorité.

### 3. Les quatre concepts sont dans un seul type

C'est la question 2 de l'exercice 1 : `Compte` porte l'abonné, l'identification,
le portefeuille et la ligne téléphonique.

Conséquence directe ici : **`MemeCompte` compare l'abonné et conclut sur le
portefeuille.** Les deux concepts ayant le même type, rien dans le code ne
signale le glissement. Avec deux types distincts, la signature
`MemeAbonne(a, b Abonne) bool` ne pourrait pas être appliquée à des
portefeuilles.

> Deux concepts dans un seul type, c'est une fonction qui compare l'un et
> décide pour l'autre — sans que le compilateur puisse le voir.

### 4. La fusion est destructive, et rien ne l'en empêche

*« il additionne les soldes et supprime le second compte »*.

Le modèle autorise :

- d'additionner deux soldes, parce que `SoldeFCFA` est un `int64` public ;
- de supprimer un compte, parce qu'aucun invariant ne s'y oppose ;
- et de faire les deux **sans trace**, parce qu'il n'y a pas de notion
  d'opération.

Le solde est stocké comme une **donnée modifiable** plutôt que comme la
**conséquence d'un journal**. C'est la décision la plus grave des quatre, et
c'est elle qui a rendu l'argent destructible. La question 5 y revient.

## Question 2 — le calcul

L'énoncé demandait le raisonnement. Le voici, en trois étapes — et la troisième
est celle qui compte.

### Étape 1 — qui est fusionnable

Un compte est fusionnable avec un autre si leurs quatre champs coïncident. Après
la normalisation des noms, deux comptes coïncident s'ils sont **homonymes**, tous
deux **sans date de naissance** et tous deux **sans CNI**.

| | |
|---|---|
| parc total | 2 000 000 |
| sans CNI (non vérifiés) | 2 000 000 − 340 000 = **1 660 000** |
| sans date de naissance | 60 % des comptes ouverts avant 2022 |
| homonymes après normalisation | tous ceux qui partagent nom **et** prénom |

### Étape 2 — l'ordre de grandeur des paires

Le nombre de **paires** fusionnables croît comme le **carré** de la taille de
chaque groupe d'homonymes. Sur l'échantillon mesuré, 2 000 comptes donnent
7 684 paires. Mettre à l'échelle n'est donc pas une multiplication par mille :

> Le nombre de paires est **quadratique**. Mille fois plus de comptes, c'est de
> l'ordre d'un **million** de fois plus de paires.

Et le chiffre exact n'est pas calculable à partir du post-mortem — la
distribution des noms n'y est pas. C'est à dire, et c'est la réponse honnête à
la question.

### Étape 3 — et voilà ce que le chiffre du post-mortem mesure vraiment

> *02h41 : il termine — « 1 843 doublons fusionnés »*

**1 843 n'est pas une mesure du problème. C'est une mesure de la fenêtre de
traitement.** Le travail a fusionné tout ce qu'il a eu le temps de fusionner en
quarante et une minutes. Il aurait pu tourner quatre heures.

C'est la conclusion la plus importante de cette question :

> Le rayon d'explosion de cet incident a été borné par **la durée du cron**, et
> par rien d'autre. Aucun garde-fou, aucune limite, aucun seuil n'est intervenu.
> Le travail s'est arrêté parce qu'il avait fini sa passe.

Et le corollaire, qui est la bonne question à poser en réunion de crise :
*« qu'est-ce qui l'aurait arrêté s'il avait trouvé cent mille paires ? »* La
réponse est : rien.

## Question 3 — 23 tests, 96 % de couverture, et rien

### La propriété du modèle qui rendait ce scénario inobservable

Elle tient en une phrase, et ce n'est pas « les tests étaient mauvais » :

> Les tests construisaient les comptes **en les renseignant**.

Un développeur qui écrit un test de dédoublonnage écrit ceci, naturellement :

```
a := Compte{Numero: "...", Nom: "NDIAYE", Prenom: "Awa",
            DateNais: unJour, NumeroCNI: "CNI123"}
```

Il remplit les champs, parce qu'un test se lit mieux avec des valeurs, et parce
qu'il teste la logique de fusion — pas la logique des champs vides. Les 23 tests
couvraient donc l'espace des comptes **renseignés**, qui est une fraction
minuscule de l'espace réel.

Et le modèle ne l'interdisait pas. **`Compte{}` est un compte valide**, et aucun
constructeur ne force le développeur à décider ce qu'il met dans les quatre
champs.

> Un type dont la valeur zéro est constructible produit des tests qui n'exercent
> jamais la valeur zéro — parce qu'il faut y **penser**, et qu'on ne pense pas à
> ce que le type ne demande pas.

C'est le lien exact avec la leçon : le champ `construit` et les constructeurs
obligatoires ne servent pas seulement à interdire un état en production. **Ils
obligent le développeur de test à se poser la question**, parce qu'il doit passer
par le constructeur.

### Le test qui l'aurait attrapé

Il tient en une phrase, et il n'a pas besoin du parc :

> *Deux comptes vides doivent être déclarés différents.*

C'est trois lignes :

```
if MemeCompte(Compte{Numero: "A"}, Compte{Numero: "B"}) {
    t.Fatal("deux comptes non renseignes ne sont pas le meme compte")
}
```

Trois lignes contre 12,4 millions FCFA. Et il n'aurait demandé aucune
sophistication : juste la discipline de la leçon 1.6, *« la valeur zéro est-elle
un état valide ? »*, posée à `Compte` au lieu d'à `Posologie`.

### Et le test qui l'aurait vu venir une semaine avant

Celui-là est plus intéressant, parce qu'il aurait sonné **avant** la nuit du
samedi :

> *Le nombre de paires que `MemeCompte` déclare identiques ne doit pas augmenter
> après une migration de données.*

C'est `TestLaCampagneDeNettoyageADeclencheLIncident`. Lancé sur un échantillon de
la base avant et après la campagne, il aurait montré le ×16,7 — **le mardi,
pendant l'import, et pas le samedi à 2 h du matin.**

> Une campagne de nettoyage de données doit être testée sur ce qu'elle rend
> **possible**, pas seulement sur ce qu'elle corrige.

## Question 4 — les deux durées

### Six heures et douze minutes jusqu'au premier appel

De 02h41 — fin du travail — à 08h12.

Le modèle en est entièrement responsable, et la cause est **l'absence
d'observable** :

| La question qu'on aurait pu se poser | Pourquoi elle n'a pas de réponse |
|---|---|
| combien de comptes ont été supprimés cette nuit ? | aucune trace : la suppression est un `DELETE` |
| de combien la somme des soldes a-t-elle varié ? | personne ne la mesure |
| quels comptes ont été fusionnés et dans lesquels ? | le journal ne retient que le nombre, 1 843 |
| le travail a-t-il fusionné **plus** que d'habitude ? | 11 en quatorze mois, puis 1 843 en une nuit — **l'information était là** |

La dernière ligne est la plus dure à lire. **Le chiffre anormal était dans le
journal, à 02h41.** Passer de 11 fusions en quatorze mois à 1 843 en une nuit est
un facteur de deux mille. Personne ne regardait, parce que personne n'avait
jamais eu de raison de regarder cette ligne.

> Un travail périodique dont le volume de sortie varie de deux mille fois d'une
> exécution à l'autre n'a pas besoin d'une alerte sophistiquée. Il a besoin
> qu'**on compare à la dernière fois**.

### Une heure et dix-huit minutes de plus jusqu'à la désactivation

De 08h12 — premier appel — à 09h30, et il a fallu **47 appels**.

C'est le premier terme du MTTR de la leçon 1.2 : *le temps de former la bonne
hypothèse*. Et il a été long pour une raison de modèle :

> Un client qui appelle en disant « mon solde est à zéro » ne désigne pas une
> cause. Avec un solde stocké comme une donnée, **il n'y a aucun moyen de savoir
> pourquoi il est à zéro.** Il peut avoir dépensé, avoir été débité à tort, ou
> avoir été fusionné.

Il a fallu 47 appels pour que quelqu'un remarque que les 47 avaient quelque chose
en commun. Avec un journal faisant foi, le premier appel aurait suffi : on lit
les mouvements du compte, et on voit une ligne « fusionné dans X » à 02h17.

### Le lien avec les deux termes

| Terme du MTTR | Durée | La décision de modèle responsable |
|---|---|---|
| former la bonne hypothèse | **7 h 30** | le solde est une donnée, pas une projection : rien ne dit *pourquoi* il vaut ce qu'il vaut |
| agir | 18 min | rien à reprocher — désactiver un cron est rapide |

Tout s'est joué sur le premier terme, et le premier terme est une propriété du
modèle.

## Question 5 — ce que la reconstitution révèle

> *14h00 : reconstitution à partir du journal des opérations*

Cette phrase contient toute l'architecture du système, et elle le dit par
accident.

### Ce qu'elle dit du journal

**Le journal des opérations est la source de vérité.** On a pu reconstituer
l'état d'avant, compte par compte, six heures après — donc le journal contenait
assez d'information pour recalculer 12,4 millions de francs répartis sur 1 790
comptes.

### Ce qu'elle dit des soldes

**`SoldeFCFA` est un cache.** Un cache non nommé, non documenté, et traité par
le code comme s'il était la vérité.

> Si on peut recalculer une donnée à partir d'une autre, la première est une
> **projection** et la seconde est la **source**. Peu importe laquelle est dans
> la colonne qu'on lit tous les jours.

### La distinction, en termes de la leçon

| | Le journal | Les soldes |
|---|---|---|
| nature | une suite d'**événements** | un **état** |
| modifiable | **non** — on ajoute, on ne change pas | oui, par n'importe qui |
| perd-on de l'information en le modifiant ? | on ne peut pas le modifier | **oui, tout** |
| en termes de 2.1 | une collection de **valeurs** immuables | un attribut d'entité |

Et la conséquence qui est le cœur de la question :

> Le travail de dédoublonnage a modifié le **cache** et pas la **source**. C'est
> pour ça que la reconstitution a été possible — et c'est aussi pour ça que
> personne ne s'est aperçu de rien pendant six heures : la source était intacte,
> et personne ne la regardait.

### Et la leçon de modélisation, qui n'est pas celle qu'on attend

On pourrait conclure *« il faut toujours un journal d'événements »*. C'est trop
large, et ce n'est pas le niveau 2.

La conclusion exacte est plus utile :

> Quand une donnée est **dérivable**, le modèle doit dire laquelle des deux fait
> foi — et le code doit empêcher d'écrire la projection directement. Sinon on a
> deux vérités, et c'est celle qu'on peut modifier qui finit par gagner.

Le mécanisme, dans le vocabulaire de cette leçon : `SoldeFCFA` ne devrait pas
être un champ public assignable. Il devrait être le résultat d'une méthode, comme
`Niveau.Plafond()` dans la correction 2 — et si c'est trop coûteux à recalculer,
alors c'est un cache, et il doit être **nommé** comme tel et reconstruit, jamais
écrit à la main.

## Question 6 — les trois corrections

| | Ce qu'elle empêche | Ce qu'elle n'empêche pas | Ce qu'elle coûte |
|---|---|---|---|
| **A** `&& a.NumeroCNI != ""` | la fusion des comptes sans CNI — c'est-à-dire **exactement cet incident** | la fusion de deux homonymes qui ont la **même** CNI mal saisie ; la fusion d'un abonné avec lui-même après un mariage, toujours ratée ; et tout futur champ facultatif ajouté à la comparaison | une ligne. C'est le point. |
| **B** validation humaine | toute fusion non voulue, **si** le valideur regarde | rien, le jour où il y a 1 843 fusions à valider : on clique « tout valider » | un poste de travail, et une file qui grossit. Et la validation devient un tampon dès la deuxième semaine |
| **C** fusion impossible | la destruction d'argent par ce mécanisme, **définitivement** | les doublons de continuer d'exister — il faut les traiter autrement | une procédure métier à écrire, et le refus de résoudre un problème réel |

### Ce que je choisis : C, avec A tout de suite

Deux temps, et il faut les deux.

**Tout de suite, A**, parce que l'incident peut se reproduire cette nuit. Une
ligne, déployée dans l'heure. Ce n'est pas la bonne correction, c'est l'arrêt de
l'hémorragie — et il faut savoir faire la différence sans se raconter d'histoire.

**Et ensuite C**, parce que A et B laissent intacte la décision de modélisation
n° 4 : **la fusion est destructive.**

Le mécanisme de C, et il n'est pas « on ne fait rien » :

| Au lieu de | On fait |
|---|---|
| additionner les soldes et supprimer un compte | **marquer** les deux comptes comme *doublons suspectés*, liés entre eux |
| décider automatiquement | laisser les deux comptes **vivants et utilisables** |
| détruire l'information | produire une liste, qu'un agent traite au guichet, **avec l'abonné présent** |

Ce que ça change : un doublon suspecté est une **information**, pas une action.
Personne ne perd d'argent en se trompant sur une information. Et la fusion
réelle, quand elle a lieu, est un **transfert** — une opération dans le journal,
réversible, traçable, avec un auteur.

> Quand une automatisation peut détruire quelque chose d'irremplaçable, la bonne
> conception n'est pas de la rendre prudente : c'est de lui retirer le pouvoir de
> détruire, et de lui laisser celui de **signaler**.

### Et les 1 790 fusions déjà faites

C'est la partie de la question qu'on ne peut pas éluder, et elle a quatre
morceaux.

**1. Reconstituer, pas « rembourser ».** Le journal fait foi. On recalcule les
1 790 soldes à partir de la source, on les réécrit, et on recrée les comptes
supprimés avec leur numéro. Ce n'est pas un geste commercial, c'est une
correction d'état — et la distinction compte pour le régulateur.

**2. Les 53 fusions légitimes doivent être retrouvées, pas annulées en bloc.**
1 843 − 1 790 = 53 fusions correctes, celles où la CNI coïncidait. Les annuler
recréerait 53 vrais doublons. Il faut donc rejouer le critère de A sur les 1 843,
et ne défaire que celles qui ne le passent pas.

**3. Le trou de six heures.** Entre 02h41 et 09h30, des abonnés ont utilisé des
comptes fusionnés. Certains ont dépensé l'argent de quelqu'un d'autre ; d'autres
se sont vu refuser une opération pour solde insuffisant. Les premiers ne se
plaindront pas, et il faut quand même les traiter — c'est une décision de
direction, pas de développeur, et le rôle de la technique est de **produire la
liste** et de dire ce qu'elle contient.

**4. Prévenir ceux qui n'ont pas appelé.** 47 appels pour 1 790 comptes touchés.
Mille sept cent quarante-trois abonnés n'ont rien dit — ils ne s'en sont pas
aperçus, ou ils ne savent pas à qui parler. Ne rien leur dire, c'est espérer
qu'ils ne regardent jamais.

## Question 7 — la garantie demandée

> *« Que plus jamais un travail automatique ne puisse détruire de l'argent
> client. »*

### Pourquoi « on va faire plus attention » est faux, en deux phrases

L'attention n'est pas une propriété du système : c'est une propriété de la
personne qui écrivait le code ce jour-là, et elle ne survit ni au départ de cette
personne ni à une astreinte de nuit. Et dans cet incident précis, **personne n'a
été inattentif** : le travail était correct depuis quatorze mois, et c'est une
campagne de nettoyage irréprochable qui l'a rendu dangereux.

### Pourquoi « on va rendre ça impossible » est faux aussi

Parce qu'un programme qui peut écrire un solde peut écrire un mauvais solde. On
ne peut rendre non représentable que ce qui est dans notre mémoire — et le solde
y est. **La seule façon de rendre la destruction impossible serait de retirer au
programme le droit d'écrire les soldes**, ce qui le rend inutile.

### La propriété du modèle qui ferme la classe entière

> **Un solde n'est pas écrit. Il est calculé à partir d'un journal d'opérations en
> ajout seul.**

Ce n'est pas « ce bug devient impossible ». C'est **la classe entière** :

| Ce qui devient impossible | Pourquoi |
|---|---|
| détruire un solde | il n'y a pas de solde à détruire, il y a des opérations |
| perdre de l'argent sans trace | toute variation est une ligne, avec un auteur et une cause |
| un écart comptable non explicable | l'invariant de l'exercice 4 est vérifiable par construction |
| un incident non reconstituable | la reconstitution devient une relecture, pas une enquête |

Et le mécanisme, dans le vocabulaire de la leçon : les opérations sont des
**valeurs immuables** ; le solde est une **projection**. Un travail automatique ne
peut écrire que des opérations — donc, au pire, il ajoute une opération fausse,
qui est visible, attribuable et compensable par une autre opération.

> On ne supprime pas le droit de se tromper. On supprime le droit de se tromper
> **sans laisser de trace**.

### Ce que ça coûte, chiffré en ce que ça interdit

Il faut être précis, parce que c'est cher :

| Ce qu'on ne peut plus faire | Ce que ça implique |
|---|---|
| lire un solde en une requête | il faut une projection matérialisée, donc un cache **nommé**, donc une reconstruction à surveiller |
| corriger un solde à la main | toute correction est une opération d'ajustement, avec un motif et un auteur. Le support n'aime pas |
| supprimer les données anciennes | un journal en ajout seul ne se purge pas sans perdre la capacité de reconstituer. Il faut une politique d'archivage, et elle est réglementée |
| déployer en deux semaines | c'est un chantier de plusieurs mois, et il touche les quatre services |

Et le coût qu'on oublie : **la projection peut dériver.** On remplace « un solde
faux » par « une projection désynchronisée », qui est moins grave — la source est
intacte — mais qui n'est pas rien, et qui demande sa propre mesure.

### La mesure pour ce que la propriété ne couvre pas

| | |
|---|---|
| **Grandeur** | *écart = (somme des soldes projetés) − (somme calculée depuis le journal)*, à une séquence donnée |
| **Référence** | **0**, exactement |
| **Seuil** | tout écart non nul |
| **Fréquence** | à chaque heure sur le jour courant, une fois par nuit sur la totalité |

C'est la mesure de l'exercice 4, et elle couvre précisément le risque résiduel :
la propriété garantit que la **source** est intacte, la mesure garantit que la
**projection** lui correspond.

Et une seconde, spécifique aux travaux automatiques, parce que c'est elle qui
aurait sonné à 02h41 :

| | |
|---|---|
| **Grandeur** | *volume de sortie de chaque travail périodique, rapporté à sa médiane sur trente exécutions* |
| **Référence** | **1** |
| **Seuil** | **3** — au-delà, le travail s'arrête de lui-même et attend un humain |
| Sur cet incident | 1 843 / 11 ≈ **167**. L'arrêt aurait eu lieu à la première fusion anormale |

Noter que le seuil est sur un **rapport**, pas sur un nombre absolu. Un seuil
absolu demande de connaître le volume normal de chaque travail — personne ne le
fera pour quarante travaux. Un rapport à la médiane se calcule tout seul, pour
tous.

> Un travail automatique qui modifie des données doit avoir un **plafond de
> volume relatif**, et s'arrêter quand il le dépasse. Ce n'est pas une alerte :
> c'est un frein.

### Et la question qui compte : survivre au prochain développeur pressé

Deux outils, et ils viennent des deux leçons.

**De la 2.1 : rendre la faute non représentable, pas interdite.**

Le journal est en **ajout seul**, et ça ne se garde pas par une convention. Ça se
garde par un type sans mutateur et par des droits de base de données :

```
REVOKE UPDATE, DELETE ON operations FROM application;
```

Un développeur pressé qui écrit un `UPDATE operations` obtient une erreur de la
base, pas une revue de code qu'il peut contourner. **Le garde-fou est au niveau
le plus bas qui puisse le porter**, et c'est le seul qui survit à tout le monde.

**De la 1.6 : le test de décision, et ses trois modes de panne.**

Un test qui vérifie qu'aucun paquet applicatif ne contient `UPDATE operations`
ni `DELETE FROM operations`. Avec les trois gardes que la correction 2 a établies
à ses dépens :

| La garde | Ici |
|---|---|
| un **témoin** qui réussit | un test qui vérifie qu'un `INSERT INTO operations` est bien accepté |
| la **raison** de l'échec vérifiée | le message doit nommer la table et l'ordre SQL, pas juste « erreur » |
| **dépendre** de ce qu'on surveille | le test importe les paquets qu'il inspecte, pour que le cache s'invalide |

Et un dernier, qui est propre à cette classe de risque et qui ne coûte presque
rien :

> **Faire tourner chaque travail automatique en lecture seule d'abord**, et
> comparer ce qu'il aurait fait à ce qu'il a fait la fois précédente. Le travail
> de dédoublonnage en mode « liste ce que tu fusionnerais » aurait produit 1 843
> lignes le samedi à 02h41 — et personne n'aurait eu à s'en apercevoir, parce
> qu'il n'aurait rien fusionné.

C'est le périmètre E de la correction 1.6/4, retourné : **un mode qui décide et
compare sans exécuter.** Il coûte un drapeau et une requête, il attrape cette
classe entière, et c'est la correction la moins chère de toute cette page.

## Ce qu'il faut retenir

1. **La saleté des données était un garde-fou accidentel.** Le nettoyer a mis en
   marche un travail qui ne faisait rien depuis quatorze mois.
2. **Mesuré** : la normalisation des noms a multiplié les collisions par 16,7, et
   le plus gros groupe de comptes « identiques » est passé de 6 à 25.
3. **La campagne a protégé exactement ceux qu'elle a touchés** — et plus elle
   avançait, plus les autres devenaient fusionnables.
4. **Une comparaison sur des attributs facultatifs déclare identiques tous les
   objets non renseignés.** Et un parc en contient toujours une majorité.
5. **Deux concepts dans un seul type**, c'est une fonction qui compare l'un et
   décide pour l'autre, sans que le compilateur puisse le voir.
6. **Un type dont la valeur zéro est constructible produit des tests qui ne
   l'exercent jamais.** Le constructeur obligatoire force la question.
7. **1 843 n'est pas une mesure du problème, c'est une mesure de la fenêtre du
   cron.** Le rayon d'explosion n'était borné par rien d'autre.
8. **Le chiffre anormal était dans le journal à 02h41** : 11 fusions en quatorze
   mois, puis 1 843 en une nuit. Comparer à la dernière fois suffisait.
9. **Si une donnée est dérivable, le modèle doit dire laquelle fait foi** — et
   empêcher d'écrire la projection. Sinon c'est celle qu'on peut modifier qui
   gagne.
10. **Une campagne de nettoyage se teste sur ce qu'elle rend possible**, pas
    seulement sur ce qu'elle corrige.
11. **Quand une automatisation peut détruire de l'irremplaçable**, on ne la rend
    pas prudente : on lui retire le pouvoir de détruire et on lui laisse celui de
    signaler.
12. **On ne supprime pas le droit de se tromper, on supprime le droit de se
    tromper sans laisser de trace.**
13. **Un travail automatique qui modifie des données doit avoir un plafond de
    volume relatif**, et s'arrêter — pas alerter.
14. **Le garde-fou doit être au niveau le plus bas qui puisse le porter.** Un
    `REVOKE UPDATE` survit à tout le monde.
