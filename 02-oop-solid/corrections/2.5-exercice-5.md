# Correction 2.5 — Exercice 5 : la bascule qui branchait les virements sur une réplique

> Rappel de l'énoncé : la principale tombe à 02:14, `Failover` rebranche toute
> l'application sur le premier candidat qui répond — une réplique —, et
> pendant 47 minutes les relevés marchent et les 2 318 virements échouent.

Pour rejouer l'incident au lieu de le raconter, j'ai écrit un pilote
`database/sql` en mémoire : chaque DSN est un serveur qui peut tomber ou
refuser les écritures, avec le message exact de PostgreSQL —
`cannot execute UPDATE in a read-only transaction (SQLSTATE 25006)`. Le code
de l'énoncé et le code corrigé tournent dessus, verts sous `go vet ./...` et
`go test -race -count=1 ./...`. Campagne de dix modifications, 9/9 après trois
passes et une branche supprimée.

## 1. Le mécanisme, en trois phrases

> Quand la principale a cessé de répondre, la bascule a pris la première base
> qui répondait, sans demander si elle acceptait les écritures. Elle a branché
> **toute** l'application dessus, parce que l'application ne recevait qu'une
> seule base pour tout faire. Les lectures ont marché, chaque écriture a été
> refusée par la base, et aucun composant ne savait que c'était le cas
> général et pas un accident.

## 2. Pourquoi le compilateur n'a rien vu — même après une coupe ISP

Le compilateur voit des types. La principale et la réplique sont **le même
type**, `*storage.Postgres` : *seul le DSN diffère*, dit le commentaire.
Rien, dans le système de types, ne distingue une base qui écrit d'une base
qui lit.

Une coupe ISP seule — un `Reader` pour le relevé, un `Writer` pour le
virement — ne change rien à ce code : `*Postgres` a les quatre méthodes, il
satisfait les deux interfaces, et `Failover` peut le donner au virement quel
que soit son DSN. **ISP sépare des méthodes ; ici, il fallait séparer des
bases.** Ce que la coupe doit séparer, c'est ce qui **construit** la valeur.

## 3. La propriété du modèle

> **Un service d'écriture ne reçoit qu'un `storage.Writer`, et un
> `Writer` ne se construit que par `OpenWriter`, qui vérifie que la
> base accepte les écritures.**

```go
// Writer reads and writes. Its field is unexported: outside this package,
// the only way to get a non-empty one is OpenWriter, which checks the
// database. The first version embedded *Reader — and an embedded field is
// named after its type, so it was exported: storage.Writer{Reader: r}
// compiled everywhere. The compile test caught it.
type Writer struct{ r *Reader }

// OpenWriter refuses a database that refuses writes. This is the model's
// property: a writing service cannot be built on a replica, because it only
// receives a Writer, and a Writer does not exist for a replica.
func OpenWriter(driver, dsn string) (*Writer, error) {
    r, err := OpenReader(driver, dsn)
    if err != nil {
        return nil, err
    }
    var readOnly string
    if err := r.db.QueryRow(`SHOW transaction_read_only`).Scan(&readOnly); err != nil {
        return nil, err
    }
    if readOnly != "off" {
        return nil, fmt.Errorf("%w: %s (transaction_read_only = %s)", ErrReadOnly, dsn, readOnly)
    }
    return &Writer{r: r}, nil
}

// translate covers what the constructor cannot: a database that becomes
// read-only AFTER being opened — a demotion by the orchestrator. SQLSTATE
// 25006 is read_only_sql_transaction.
func translate(err error) error {
    if err != nil && strings.Contains(err.Error(), "SQLSTATE 25006") {
        return fmt.Errorf("%w: %v", ErrReadOnly, err)
    }
    return err
}

func (w *Writer) Load(id string) (Account, error) { return w.r.Load(id) }

func (w *Writer) Movements(id string, since time.Time) ([]Movement, error) {
    return w.r.Movements(id, since)
}

func (w *Writer) Save(a Account) error {
    _, err := w.r.db.Exec(`UPDATE accounts SET balance = $2 WHERE id = $1`, a.ID, a.Balance)
    return translate(err)
}

func (w *Writer) AddMovement(m Movement) error {
    _, err := w.r.db.Exec(`INSERT INTO movements VALUES ($1, $2, $3)`, m.Account, m.Date, m.Amount)
    return translate(err)
}
```

Et le virement déclare un port qui écrit — un `*storage.Reader` ne le
satisfait pas. La garantie se vérifie à la compilation, par un test qui
compile les appels interdits et vérifie la raison de l'échec :

```go
func TestTheGuaranteeAtCompileTime(t *testing.T) {
    for _, c := range []struct {
        name, body, want string
    }{
        {"a reader given to the transfer",
            "func f(r *storage.Reader) transfer.Service { return transfer.Service{S: r} }",
            "*storage.Reader does not implement transfer.Accounts (missing method AddMovement)"},
        {"a forged writer",
            "var _ = transfer.Service{S: &storage.Writer{Reader: &storage.Reader{}}}",
            "unknown field Reader in struct literal of type storage.Writer"},
        // The hole: the zero value can be declared anywhere. It compiles, and
        // it panics on the first call.
        {"the zero value", "var _ = transfer.Service{S: &storage.Writer{}}", ""},
    } {
        t.Run(c.name, func(t *testing.T) {
            out, err := build(t, c.body)
            if c.want == "" {
                if err != nil {
                    t.Fatalf("does not compile:\n%s", out)
                }
                return
            }
            if err == nil || !strings.Contains(out, c.want) {
                t.Fatalf("%v:\n%s", err, out)
            }
        })
    }
}
```

Ce test m'a repris en tirant. Ma première version de `Writer` incorporait
`*Reader` — `type Writer struct{ *Reader }` —, avec un commentaire qui
disait « ses champs ne sont pas exportés ». C'était faux : **un champ
incorporé porte le nom de son type**, et `Reader` est exporté. Le cas « une
écriture fabriquée » **compilait** — n'importe quel paquet pouvait envelopper
une lecture sur une réplique dans un `Writer`. C'est la leçon 2.3 —
l'incorporation promeut aussi les champs —, retrouvée sur mon propre code.
Le champ est maintenant nommé et non exporté, et le test attend
`unknown field Reader in struct literal`.

**Ce que la propriété ne couvre pas**, honnêtement :

1. **La valeur zéro** : `storage.Writer{}` se déclare partout — c'est le
   troisième cas du test, attendu vert. Elle panique au premier appel au lieu
   d'écrire sur une réplique : une faute bruyante, pas silencieuse.
2. **Une base qui devient en lecture seule après la construction** : le
   constructeur vérifie une fois. La question 9 y revient, et la traduction
   de SQLSTATE 25006, dans le code ci-dessus, est la réponse d'exécution.

## 4. `Failover` après la coupe

Le nouveau contrat, en une phrase :

> **`Failover` choisit séparément une base pour lire et une base pour
> écrire ; si aucune n'accepte les écritures — ou si plus d'une les
> accepte —, les relevés continuent et les virements sont suspendus
> explicitement.**

```go
// Mode says what the failover obtained. An empty Writer means "transfers
// suspended": it is the indicator that fires the second it happens.
type Mode struct {
    Reader string
    Writer string
    // Writable lists every database that accepts writes. More than one is a
    // split brain: the orchestrator did not fence the old primary, and
    // picking one of the two loses the writes made on the other.
    Writable []string
}

// Failover picks, SEPARATELY, a database to read from and a database to
// write to. Contract: if no database accepts writes — or if MORE THAN ONE
// does —, statements go on and transfers are explicitly suspended.
func Failover(app *Application, driver string, candidates []Candidate) (Mode, error) {
    var m Mode
    var reader *storage.Reader
    var writer *storage.Writer
    for _, c := range candidates {
        if c.Responds() != nil {
            continue
        }
        if reader == nil {
            if r, err := storage.OpenReader(driver, c.DSN); err == nil {
                reader, m.Reader = r, c.DSN
            }
        }
        if w, err := storage.OpenWriter(driver, c.DSN); err == nil {
            m.Writable = append(m.Writable, c.DSN)
            writer, m.Writer = w, c.DSN
        }
    }
    if len(m.Writable) > 1 {
        writer, m.Writer = nil, ""
    }
    if reader == nil {
        return m, errors.New("wiring: no candidate answers")
    }
    app.mu.Lock()
    defer app.mu.Unlock()
    app.statement = statement.Service{S: reader}
    app.transfer = nil
    if writer != nil {
        app.transfer = &transfer.Service{S: writer}
    }
    return m, nil
}

// Transfer executes a transfer, or returns ErrTransfersSuspended. A database
// that becomes read-only along the way suspends transfers at the first
// refusal.
func (a *Application) Transfer(from, to string, amount int64, when time.Time) error {
    a.mu.RLock()
    t := a.transfer
    a.mu.RUnlock()
    if t == nil {
        return ErrTransfersSuspended
    }
    err := t.Execute(from, to, amount, when)
    if errors.Is(err, storage.ErrReadOnly) {
        a.mu.Lock()
        a.transfer = nil
        a.mu.Unlock()
    }
    return err
}
```

Ce que voit un client qui tente un virement pendant ce temps :
`ErrTransfersSuspended`, immédiatement, **sans qu'aucune requête SQL ne
parte** — le test vérifie que le solde de la réplique n'a pas bougé. C'est
mieux que 2 318 erreurs SQL pour trois raisons : l'erreur dit **ce qui se
passe** (« aucune base n'accepte les écritures ») au lieu d'un symptôme ;
elle est **classable** — un ordonnanceur de virements de salaire peut la
traiter comme « réessayer plus tard », ce qu'il ne pouvait pas faire d'un
message PostgreSQL ; et elle est **comptée** au lieu d'être diluée dans un
taux d'erreur.

```go
// TestTheIncidentDoesNotHappen: the primary goes down, only a replica
// answers. Statements go on, transfers are suspended, and no write query is
// sent.
func TestTheIncidentDoesNotHappen(t *testing.T) {
    app, f := setUp(t)
    f.p.Set(true, false)
    m, err := Failover(app, "fake", f.cs)
    if err != nil || m.Reader != "replica-1" || m.Writer != "" {
        t.Fatalf("failover: %+v, %v", m, err)
    }
    if app.WritesAvailable() {
        t.Fatal("the indicator does not fire")
    }
    if _, err := app.Statement("A", time.Time{}); err != nil {
        t.Fatalf("statement: %v", err)
    }
    if err := app.Transfer("A", "B", 300, time.Now()); !errors.Is(err, ErrTransfersSuspended) {
        t.Fatalf("transfer: %v", err)
    }
    if f.r1.Balance("A") != 1000 {
        t.Fatal("a write went to the replica")
    }
}
```

## 5. Les 340 tests et le test de bascule

J'ai réécrit le test de bascule tel que le post-mortem le décrit, sur le code
de l'énoncé, et l'incident juste à côté :

```go
// TestThePostMortemFailoverTest: the test as it existed. It passes.
func TestThePostMortemFailoverTest(t *testing.T) {
    app, p, cs := setUp(t)
    p.Set(true, false)
    if err := Failover(app, "fake", cs); err != nil {
        t.Fatal(err)
    }
    if _, err := app.Statement.Movements("A", time.Time{}); err != nil {
        t.Fatalf("the statement no longer answers: %v", err)
    }
}

// TestTheIncidentReplayed: the same failover, and a transfer.
func TestTheIncidentReplayed(t *testing.T) {
    app, p, cs := setUp(t)
    if err := app.Transfer.Execute("A", "B", 300, time.Now()); err != nil {
        t.Fatalf("before the outage: %v", err)
    }
    p.Set(true, false)
    if err := Failover(app, "fake", cs); err != nil {
        t.Fatal(err)
    }
    err := app.Transfer.Execute("A", "B", 300, time.Now())
    if err == nil {
        t.Fatal("the transfer went through on the replica")
    }
    t.Logf("transfer after the failover: %v", err)
}
```

```
--- PASS: TestThePostMortemFailoverTest (0.00s)
    incident_test.go:60: transfer after the failover: ERROR: cannot execute UPDATE in a read-only transaction (SQLSTATE 25006)
--- PASS: TestTheIncidentReplayed (0.00s)
```

Le test de bascule **passe**, et la même bascule casse tous les virements.
Les 340 tests étaient verts parce que le dépôt en mémoire des tests du
virement accepte toujours les écritures : aucun test n'a jamais vu une base
qui refuse.

Le test de bascule aurait dû vérifier **chacun des services**, et en
particulier celui qui écrit. Il a choisi le relevé, et ce n'est pas un hasard :
avec une seule base pour toute l'application, « l'application répond encore »
se vérifie naturellement par le chemin le plus simple — une lecture. Et le
contrat que `Failover` promettait était exactement « un candidat qui
répond » : le test a vérifié la promesse. C'est la promesse qui était
fausse, et le test ne pouvait pas le voir sans un type qui la rende fausse.

## 6. Quarante-sept minutes

| Phase | De | À | Durée |
|---|---|---|---|
| bascule | 02:14:00 | 02:14:21 | 21 s |
| **détection** | 02:14:21 | 02:29, alerte « > 5 % d'erreurs depuis 15 min » | **14 min 39 s** |
| diagnostic et remédiation | 02:29 | 03:01, promotion de replica-1 | 32 min |

L'alerte a mis quinze minutes par construction : un taux d'erreur moyenné sur
quinze minutes ne peut pas tirer avant quinze minutes. La conception réduit
**la détection et le diagnostic** à la fois.

**L'indicateur qui aurait tiré à 02:14:22** : `WritesAvailable()`, publié
comme une jauge — 1 quand un virement peut partir, 0 sinon. Il passe à 0 à la
fin de la bascule, sans attendre qu'un seul virement échoue.

- **Seuil** : à 0 pendant plus de 30 secondes.
- **Plancher de bruit** : une bascule **planifiée** suspend les écritures
  quelques secondes, légitimement. Les 30 secondes du seuil sont là pour
  elle ; au-delà, ce n'est plus une bascule, c'est une panne.

Et le diagnostic tombe avec lui : le `Mode` rendu par `Failover` dit en
toutes lettres « lecture sur replica-1, aucune base en écriture ». Les
32 minutes de l'astreinte se réduisent à la décision de promouvoir une
réplique — qui reste une décision humaine, et doit le rester.

## 7. « Simple et robuste »

Le code est simple. « Robuste » ne se juge qu'en connaissant les cas
d'échec, et la demande de fusion n'en listait aucun. La question que les
relecteurs devaient poser :

> **« Que fait `Failover` si le premier candidat qui répond est une
> réplique ? »**

La réponse était dans le code, en trois lignes. Personne ne l'a lue comme
une réponse à cette question, parce que personne ne l'a posée.

## 8. La correction

| | Ce qu'elle empêche | Ce qu'elle n'empêche pas | Ce qu'elle coûte | Quand l'export comptable, en lecture seule, est branché |
|---|---|---|---|---|
| **A** principale en premier | rien, ici : la principale est **en panne**, c'est le cas de l'incident | tout l'incident | rien | inchangé |
| **B** `pg_is_in_recovery()` dans `Failover` | de brancher l'application sur une réplique | que l'application, qui n'a qu'une base, perde **aussi** ses relevés quand seule une réplique répond | une requête par candidat | l'export perd sa base comme les autres : avec une seule base pour tout le monde, il est coupé alors qu'il pourrait lire |
| **C** `Reader` / `Writer`, constructeur vérifiant | qu'un service d'écriture soit **construit** sur une base qui refuse — par le type | une rétrogradation après construction ; la valeur zéro | deux types, une bascule qui choisit deux fois | il prend un `Reader` : branché sur la réplique, il continue pendant la panne |
| **D** pas de bascule automatique | toute bascule fautive | la panne elle-même, qui dure jusqu'à l'astreinte | relevés **et** virements coupés pendant toute la durée | coupé aussi |

**Je choisis C**, avec la traduction d'exécution de SQLSTATE 25006 et
l'indicateur. Dans cet ordre :

1. **L'indicateur d'abord**, même sur le code actuel : une jauge « une base
   accepte les écritures », vérifiée par `SHOW transaction_read_only` après
   chaque bascule. C'est une demi-journée, et c'est ce qui aurait ramené la
   détection de 15 minutes à une seconde.
2. **C ensuite** : les deux types, le constructeur vérifiant, la bascule qui
   choisit deux fois.
3. **B devient inutile** : c'est exactement ce que fait `OpenWriter`, mais
   au bon endroit — dans le seul constructeur d'un `Writer`, au lieu d'une
   précaution dans une fonction que le prochain développeur réécrira.

## 9. La garantie demandée

> *« Plus jamais un service d'écriture branché sur une base qui refuse les
> écritures. »*

**La propriété** : celle de la question 3 — un `Writer` ne se construit
que sur une base qui accepte les écritures, et le service d'écriture ne
prend qu'un `Writer`. Elle tire à **deux** moments : à la **compilation**
(on ne peut pas donner un `Reader` au virement, ni fabriquer un
`Writer`) et à la **construction** (on ne peut pas ouvrir un `Writer` sur
une réplique).

**Ce qu'elle interdit, chiffré** : zéro façon, hors du paquet `storage`, de
donner au virement une base non vérifiée — mesuré par le test de
compilation, trois cas. Et une chose qu'on payait sans le savoir : **le
virement n'est plus disponible pendant une fenêtre où seule une réplique
répond**. Le 03/03, c'est 47 minutes de virements indisponibles au lieu de 47
minutes de virements en échec — le même service rendu, mais dit.

**La mesure pour le reste** : le nombre d'erreurs `ErrReadOnly` à
l'exécution. **Seuil : une seule.** Le plancher de bruit est zéro : une base
qu'on a vérifiée inscriptible ne doit jamais refuser une écriture, et la
première qui le fait est un événement, pas une statistique.

**La garantie survit-elle à une rétrogradation pendant l'exécution ?**

**Non, pas entièrement.** Le type prouve que la base acceptait les écritures
**quand on l'a ouverte**. Une rétrogradation par l'orchestrateur, après,
échappe au type. Ce qui la rattrape est à l'exécution : la traduction de
SQLSTATE 25006, qui suspend les virements au premier refus — le test le
montre : le premier virement échoue avec `ErrReadOnly`, le suivant est
suspendu sans toucher la base.

```go
// TestADemotionMidway: the primary becomes read-only AFTER the failover. The
// constructor cannot see it; the translation of SQLSTATE 25006 sees it at
// the first transfer, and suspends the next ones.
func TestADemotionMidway(t *testing.T) {
    app, f := setUp(t)
    f.p.Set(false, true)
    err := app.Transfer("A", "B", 300, time.Now())
    if !errors.Is(err, storage.ErrReadOnly) {
        t.Fatalf("first transfer: %v", err)
    }
    if app.WritesAvailable() {
        t.Fatal("transfers are not suspended")
    }
    if err := app.Transfer("A", "B", 300, time.Now()); !errors.Is(err, ErrTransfersSuspended) {
        t.Fatalf("second transfer: %v", err)
    }
}
```

**Ce qui reste**, et où ça vit : **ce premier virement**. Et il y a pire, que
l'exercice ne demandait pas mais qu'il faut dire : le virement de l'énoncé
écrit le débit, puis le crédit, puis le mouvement, **en trois requêtes
séparées**, sans transaction. Une rétrogradation entre le débit et le crédit
laisse un compte débité et l'autre jamais crédité. Aucun type, aucun
constructeur, aucune bascule ne protège de ça : **ça vit dans la base**, dans
une transaction `BEGIN … COMMIT` qui rend les trois écritures atomiques. C'est
le prochain incident de ce code, et il est déjà écrit.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Le compilateur distingue des types. Une principale et une réplique du même type sont indistinguables, même après une coupe ISP : ISP sépare des méthodes, il fallait séparer des bases. |
| ⚫ | La garantie vit dans le **constructeur** : un `Writer` ne se construit que sur une base vérifiée, et le service d'écriture ne prend qu'un `Writer`. |
| ⚫ | Un champ incorporé porte le nom de son type : `struct{ *Reader }` exporte un champ `Reader`. Mon sceau était ouvert, et le test de compilation l'a vu. |
| ⚫ | Un mode dégradé explicite vaut mieux qu'un taux d'erreur : `ErrTransfersSuspended` se classe, se réessaie, et se compte. |
| ⚫ | Le test de bascule vérifiait la promesse de `Failover` — « un candidat qui répond ». La promesse était fausse ; aucun test ne pouvait le voir sans un type qui la rende fausse. |
| ⚫ | Un taux moyenné sur quinze minutes ne tire pas avant quinze minutes. Une jauge d'état tire à la seconde : ici, 02:14:22. |
| ⚫ | La campagne peut réclamer une **décision**, pas seulement un test : deux bases inscriptibles sont un cerveau divisé, et choisir l'une, c'est perdre l'autre. |
| ⚫ | Ce que le type ne couvre pas — une rétrogradation après construction — se rattrape à l'exécution, au premier refus, avec un seuil à un. |
| ⚫ | Ce qu'aucun type ne couvre — trois écritures sans transaction — vit dans la base. |
