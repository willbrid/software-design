# Correction 2.5 — Exercice 5 : la bascule qui branchait les virements sur une réplique

> Rappel de l'énoncé : la principale tombe à 02:14, `Basculer` rebranche toute
> l'application sur le premier candidat qui répond — une réplique —, et
> pendant 47 minutes les relevés marchent et les 2 318 virements échouent.

Pour rejouer l'incident au lieu de le raconter, j'ai écrit un pilote
`database/sql` en mémoire : chaque DSN est un serveur qui peut tomber ou
refuser les écritures, avec le message exact de PostgreSQL —
`cannot execute UPDATE in a read-only transaction (SQLSTATE 25006)`. Le code
de l'énoncé et le code corrigé tournent dessus, verts sous `go vet ./...` et
`go test -race -count=1 ./...`. Campagne de dix modifications, 9/9 après trois
passes et une branche supprimée.

## 1. Le mécanisme, en trois phrases

> Quand la principale a cessé de répondre, la bascule a pris la première base
> qui répondait, sans demander si elle acceptait les écritures. Elle a branché
> **toute** l'application dessus, parce que l'application ne recevait qu'une
> seule base pour tout faire. Les lectures ont marché, chaque écriture a été
> refusée par la base, et aucun composant ne savait que c'était le cas
> général et pas un accident.

## 2. Pourquoi le compilateur n'a rien vu — même après une coupe ISP

Le compilateur voit des types. La principale et la réplique sont **le même
type**, `*stockage.Postgres` : *seul le DSN diffère*, dit le commentaire.
Rien, dans le système de types, ne distingue une base qui écrit d'une base
qui lit.

Une coupe ISP seule — un `Lecteur` pour le relevé, un `Ecrivain` pour le
virement — ne change rien à ce code : `*Postgres` a les quatre méthodes, il
satisfait les deux interfaces, et `Basculer` peut le donner au virement quel
que soit son DSN. **ISP sépare des méthodes ; ici, il fallait séparer des
bases.** Ce que la coupe doit séparer, c'est ce qui **construit** la valeur.

## 3. La propriété du modèle

> **Un service d'écriture ne reçoit qu'une `stockage.Ecriture`, et une
> `Ecriture` ne se construit que par `OuvrirEcriture`, qui vérifie que la
> base accepte les écritures.**

```go
// Ecriture lit et ecrit. Son champ n'est pas exporte : hors de ce paquet, la
// seule facon d'en obtenir une non vide est OuvrirEcriture, qui verifie la
// base. La premiere version incorporait *Lecture — et un champ incorpore porte
// le nom de son type, donc il etait exporte : stockage.Ecriture{Lecture: l}
// compilait partout. Le test de compilation l'a vu.
type Ecriture struct{ l *Lecture }

// OuvrirEcriture refuse une base qui refuse les ecritures. C'est la propriete
// du modele : un service d'ecriture ne peut pas etre construit sur une
// replique, parce qu'il ne recoit qu'une Ecriture, et qu'une Ecriture n'existe
// pas pour une replique.
func OuvrirEcriture(pilote, dsn string) (*Ecriture, error) {
    l, err := OuvrirLecture(pilote, dsn)
    if err != nil {
        return nil, err
    }
    var lectureSeule string
    if err := l.db.QueryRow(`SHOW transaction_read_only`).Scan(&lectureSeule); err != nil {
        return nil, err
    }
    if lectureSeule != "off" {
        return nil, fmt.Errorf("%w : %s (transaction_read_only = %s)", ErrLectureSeule, dsn, lectureSeule)
    }
    return &Ecriture{l: l}, nil
}

// traduire couvre ce que le constructeur ne peut pas couvrir : une base qui
// devient en lecture seule APRES l'ouverture — une retrogradation par
// l'orchestrateur. SQLSTATE 25006 est read_only_sql_transaction.
func traduire(err error) error {
    if err != nil && strings.Contains(err.Error(), "SQLSTATE 25006") {
        return fmt.Errorf("%w : %v", ErrLectureSeule, err)
    }
    return err
}

func (e *Ecriture) Charger(id string) (Compte, error) { return e.l.Charger(id) }

func (e *Ecriture) Mouvements(id string, depuis time.Time) ([]Mouvement, error) {
    return e.l.Mouvements(id, depuis)
}

func (e *Ecriture) Enregistrer(c Compte) error {
    _, err := e.l.db.Exec(`UPDATE comptes SET solde = $2 WHERE id = $1`, c.ID, c.Solde)
    return traduire(err)
}

func (e *Ecriture) AjouterMouvement(m Mouvement) error {
    _, err := e.l.db.Exec(`INSERT INTO mouvements VALUES ($1, $2, $3)`, m.Compte, m.Date, m.Montant)
    return traduire(err)
}
```

Et le virement déclare un port qui écrit — un `*stockage.Lecture` ne le
satisfait pas. La garantie se vérifie à la compilation, par un test qui
compile les appels interdits et vérifie la raison de l'échec :

```go
func TestLaGarantieALaCompilation(t *testing.T) {

    } {

```

Ce test m'a repris en tirant. Ma première version de `Ecriture` incorporait
`*Lecture` — `type Ecriture struct{ *Lecture }` —, avec un commentaire qui
disait « ses champs ne sont pas exportés ». C'était faux : **un champ
incorporé porte le nom de son type**, et `Lecture` est exporté. Le cas « une
écriture fabriquée » **compilait** — n'importe quel paquet pouvait envelopper
une lecture sur une réplique dans une `Ecriture`. C'est la leçon 2.3 —
l'incorporation promeut aussi les champs —, retrouvée sur mon propre code.
Le champ est maintenant nommé et non exporté, et le test attend
`unknown field Lecture in struct literal`.

**Ce que la propriété ne couvre pas**, honnêtement :

1. **La valeur zéro** : `stockage.Ecriture{}` se déclare partout — c'est le
   troisième cas du test, attendu vert. Elle panique au premier appel au lieu
   d'écrire sur une réplique : une faute bruyante, pas silencieuse.
2. **Une base qui devient en lecture seule après la construction** : le
   constructeur vérifie une fois. La question 9 y revient, et la traduction
   de SQLSTATE 25006, dans le code ci-dessus, est la réponse d'exécution.

## 4. `Basculer` après la coupe

Le nouveau contrat, en une phrase :

> **`Basculer` choisit séparément une base pour lire et une base pour
> écrire ; si aucune n'accepte les écritures — ou si plus d'une les
> accepte —, les relevés continuent et les virements sont suspendus
> explicitement.**

```go
// Mode dit ce que la bascule a obtenu. Ecriture vide veut dire « virements
// suspendus » : c'est l'indicateur qui tire a la seconde ou ca arrive.
type Mode struct {
    Lecture  string
    Ecriture string
    // Inscriptibles liste toutes les bases qui acceptent les ecritures. Plus
    // d'une, c'est un cerveau divise : l'orchestrateur n'a pas isole
    // l'ancienne principale, et choisir l'une des deux, c'est perdre les
    // ecritures faites sur l'autre.
    Inscriptibles []string
}

// Basculer choisit, SEPAREMENT, une base pour lire et une base pour ecrire.
// Contrat : si aucune base n'accepte les ecritures — ou si PLUS D'UNE les
// accepte —, les releves continuent et les virements sont suspendus
// explicitement.
func Basculer(app *Application, pilote string, candidats []Candidat) (Mode, error) {
    var m Mode
    var lecture *stockage.Lecture
    var ecriture *stockage.Ecriture
    for _, c := range candidats {
        if c.Repond() != nil {
            continue
        }
        if lecture == nil {
            if l, err := stockage.OuvrirLecture(pilote, c.DSN); err == nil {
                lecture, m.Lecture = l, c.DSN
            }
        }
        if e, err := stockage.OuvrirEcriture(pilote, c.DSN); err == nil {
            m.Inscriptibles = append(m.Inscriptibles, c.DSN)
            ecriture, m.Ecriture = e, c.DSN
        }
    }
    if len(m.Inscriptibles) > 1 {
        ecriture, m.Ecriture = nil, ""
    }
    if lecture == nil {
        return m, errors.New("montage : aucun candidat ne repond")
    }
    app.mu.Lock()
    defer app.mu.Unlock()
    app.releve = releve.Service{D: lecture}
    app.virement = nil
    if ecriture != nil {
        app.virement = &virement.Service{D: ecriture}
    }
    return m, nil
}

// Virer execute un virement, ou rend ErrVirementsSuspendus. Une base qui
// devient en lecture seule en cours de route suspend les virements au premier
// refus.
func (a *Application) Virer(de, vers string, montant int64, quand time.Time) error {
    a.mu.RLock()
    v := a.virement
    a.mu.RUnlock()
    if v == nil {
        return ErrVirementsSuspendus
    }
    err := v.Executer(de, vers, montant, quand)
    if errors.Is(err, stockage.ErrLectureSeule) {
        a.mu.Lock()
        a.virement = nil
        a.mu.Unlock()
    }
    return err
}
```

Ce que voit un client qui tente un virement pendant ce temps :
`ErrVirementsSuspendus`, immédiatement, **sans qu'aucune requête SQL ne
parte** — le test vérifie que le solde de la réplique n'a pas bougé. C'est
mieux que 2 318 erreurs SQL pour trois raisons : l'erreur dit **ce qui se
passe** (« aucune base n'accepte les écritures ») au lieu d'un symptôme ;
elle est **classable** — un ordonnanceur de virements de salaire peut la
traiter comme « réessayer plus tard », ce qu'il ne pouvait pas faire d'un
message PostgreSQL ; et elle est **comptée** au lieu d'être diluée dans un
taux d'erreur.

```go
// TestLIncidentNeSeReproduitPas : la principale tombe, seule une replique
// repond. Les releves continuent, les virements sont suspendus, et aucune
// requete d'ecriture ne part.
func TestLIncidentNeSeReproduitPas(t *testing.T) {
    app, x := installer(t)
    x.p.Regler(true, false)
    m, err := Basculer(app, "faux", x.cs)
    if err != nil || m.Lecture != "replique-1" || m.Ecriture != "" {
        t.Fatalf("bascule : %+v, %v", m, err)
    }
    if app.EcrituresDisponibles() {
        t.Fatal("l'indicateur ne tire pas")
    }
    if _, err := app.Releve("A", time.Time{}); err != nil {
        t.Fatalf("releve : %v", err)
    }
    if err := app.Virer("A", "B", 300, time.Now()); !errors.Is(err, ErrVirementsSuspendus) {
        t.Fatalf("virement : %v", err)
    }
    if x.r1.Solde("A") != 1000 {
        t.Fatal("une ecriture est partie sur la replique")
    }
}
```

## 5. Les 340 tests et le test de bascule

J'ai réécrit le test de bascule tel que le post-mortem le décrit, sur le code
de l'énoncé, et l'incident juste à côté :

Le test de bascule **passe**, et la même bascule casse tous les virements.
Les 340 tests étaient verts parce que le dépôt en mémoire des tests du
virement accepte toujours les écritures : aucun test n'a jamais vu une base
qui refuse.

Le test de bascule aurait dû vérifier **chacun des services**, et en
particulier celui qui écrit. Il a choisi le relevé, et ce n'est pas un hasard :
avec une seule base pour toute l'application, « l'application répond encore »
se vérifie naturellement par le chemin le plus simple — une lecture. Et le
contrat que `Basculer` promettait était exactement « un candidat qui
répond » : le test a vérifié la promesse. C'est la promesse qui était
fausse, et le test ne pouvait pas le voir sans un type qui la rende fausse.

## 6. Quarante-sept minutes

| Phase | De | À | Durée |
|---|---|---|---|
| bascule | 02:14:00 | 02:14:21 | 21 s |
| **détection** | 02:14:21 | 02:29, alerte « > 5 % d'erreurs depuis 15 min » | **14 min 39 s** |
| diagnostic et remédiation | 02:29 | 03:01, promotion de replique-1 | 32 min |

L'alerte a mis quinze minutes par construction : un taux d'erreur moyenné sur
quinze minutes ne peut pas tirer avant quinze minutes. La conception réduit
**la détection et le diagnostic** à la fois.

**L'indicateur qui aurait tiré à 02:14:22** : `EcrituresDisponibles()`, publié
comme une jauge — 1 quand un virement peut partir, 0 sinon. Il passe à 0 à la
fin de la bascule, sans attendre qu'un seul virement échoue.

- **Seuil** : à 0 pendant plus de 30 secondes.
- **Plancher de bruit** : une bascule **planifiée** suspend les écritures
  quelques secondes, légitimement. Les 30 secondes du seuil sont là pour
  elle ; au-delà, ce n'est plus une bascule, c'est une panne.

Et le diagnostic tombe avec lui : le `Mode` rendu par `Basculer` dit en
toutes lettres « lecture sur replique-1, aucune base en écriture ». Les
32 minutes de l'astreinte se réduisent à la décision de promouvoir une
réplique — qui reste une décision humaine, et doit le rester.

## 7. « Simple et robuste »

Le code est simple. « Robuste » ne se juge qu'en connaissant les cas
d'échec, et la demande de fusion n'en listait aucun. La question que les
relecteurs devaient poser :

> **« Que fait `Basculer` si le premier candidat qui répond est une
> réplique ? »**

La réponse était dans le code, en trois lignes. Personne ne l'a lue comme
une réponse à cette question, parce que personne ne l'a posée.

## 8. La correction

| | Ce qu'elle empêche | Ce qu'elle n'empêche pas | Ce qu'elle coûte | Quand l'export comptable, en lecture seule, est branché |
|---|---|---|---|---|
| **A** principale en premier | rien, ici : la principale est **en panne**, c'est le cas de l'incident | tout l'incident | rien | inchangé |
| **B** `pg_is_in_recovery()` dans `Basculer` | de brancher l'application sur une réplique | que l'application, qui n'a qu'une base, perde **aussi** ses relevés quand seule une réplique répond | une requête par candidat | l'export perd sa base comme les autres : avec une seule base pour tout le monde, il est coupé alors qu'il pourrait lire |
| **C** `Lecture` / `Ecriture`, constructeur vérifiant | qu'un service d'écriture soit **construit** sur une base qui refuse — par le type | une rétrogradation après construction ; la valeur zéro | deux types, une bascule qui choisit deux fois | il prend une `Lecture` : branché sur la réplique, il continue pendant la panne |
| **D** pas de bascule automatique | toute bascule fautive | la panne elle-même, qui dure jusqu'à l'astreinte | relevés **et** virements coupés pendant toute la durée | coupé aussi |

**Je choisis C**, avec la traduction d'exécution de SQLSTATE 25006 et
l'indicateur. Dans cet ordre :

1. **L'indicateur d'abord**, même sur le code actuel : une jauge « une base
   accepte les écritures », vérifiée par `SHOW transaction_read_only` après
   chaque bascule. C'est une demi-journée, et c'est ce qui aurait ramené la
   détection de 15 minutes à une seconde.
2. **C ensuite** : les deux types, le constructeur vérifiant, la bascule qui
   choisit deux fois.
3. **B devient inutile** : c'est exactement ce que fait `OuvrirEcriture`, mais
   au bon endroit — dans le seul constructeur d'une `Ecriture`, au lieu d'une
   précaution dans une fonction que le prochain développeur réécrira.

## 9. La garantie demandée

> *« Plus jamais un service d'écriture branché sur une base qui refuse les
> écritures. »*

**La propriété** : celle de la question 3 — une `Ecriture` ne se construit
que sur une base qui accepte les écritures, et le service d'écriture ne
prend qu'une `Ecriture`. Elle tire à **deux** moments : à la **compilation**
(on ne peut pas donner une `Lecture` au virement, ni fabriquer une
`Ecriture`) et à la **construction** (on ne peut pas ouvrir une `Ecriture` sur
une réplique).

**Ce qu'elle interdit, chiffré** : zéro façon, hors du paquet `stockage`, de
donner au virement une base non vérifiée — mesuré par le test de
compilation, trois cas. Et une chose qu'on payait sans le savoir : **le
virement n'est plus disponible pendant une fenêtre où seule une réplique
répond**. Le 03/03, c'est 47 minutes de virements indisponibles au lieu de 47
minutes de virements en échec — le même service rendu, mais dit.

**La mesure pour le reste** : le nombre d'erreurs `ErrLectureSeule` à
l'exécution. **Seuil : une seule.** Le plancher de bruit est zéro : une base
qu'on a vérifiée inscriptible ne doit jamais refuser une écriture, et la
première qui le fait est un événement, pas une statistique.

**La garantie survit-elle à une rétrogradation pendant l'exécution ?**

**Non, pas entièrement.** Le type prouve que la base acceptait les écritures
**quand on l'a ouverte**. Une rétrogradation par l'orchestrateur, après,
échappe au type. Ce qui la rattrape est à l'exécution : la traduction de
SQLSTATE 25006, qui suspend les virements au premier refus — le test le
montre : le premier virement échoue avec `ErrLectureSeule`, le suivant est
suspendu sans toucher la base.

```go
// TestUneRetrogradationEnCoursDeRoute : la principale devient en lecture
// seule APRES la bascule. Le constructeur ne peut pas le voir ; la traduction
// de SQLSTATE 25006 le voit au premier virement, et suspend les suivants.
func TestUneRetrogradationEnCoursDeRoute(t *testing.T) {
    app, x := installer(t)
    x.p.Regler(false, true)
    err := app.Virer("A", "B", 300, time.Now())
    if !errors.Is(err, stockage.ErrLectureSeule) {
        t.Fatalf("premier virement : %v", err)
    }
    if app.EcrituresDisponibles() {
        t.Fatal("les virements ne sont pas suspendus")
    }
    if err := app.Virer("A", "B", 300, time.Now()); !errors.Is(err, ErrVirementsSuspendus) {
        t.Fatalf("deuxieme virement : %v", err)
    }
}
```

**Ce qui reste**, et où ça vit : **ce premier virement**. Et il y a pire, que
l'exercice ne demandait pas mais qu'il faut dire : le virement de l'énoncé
écrit le débit, puis le crédit, puis le mouvement, **en trois requêtes
séparées**, sans transaction. Une rétrogradation entre le débit et le crédit
laisse un compte débité et l'autre jamais crédité. Aucun type, aucun
constructeur, aucune bascule ne protège de ça : **ça vit dans la base**, dans
une transaction `BEGIN … COMMIT` qui rend les trois écritures atomiques. C'est
le prochain incident de ce code, et il est déjà écrit.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Le compilateur distingue des types. Une principale et une réplique du même type sont indistinguables, même après une coupe ISP : ISP sépare des méthodes, il fallait séparer des bases. |
| ⚫ | La garantie vit dans le **constructeur** : une `Ecriture` ne se construit que sur une base vérifiée, et le service d'écriture ne prend qu'une `Ecriture`. |
| ⚫ | Un champ incorporé porte le nom de son type : `struct{ *Lecture }` exporte un champ `Lecture`. Mon sceau était ouvert, et le test de compilation l'a vu. |
| ⚫ | Un mode dégradé explicite vaut mieux qu'un taux d'erreur : `ErrVirementsSuspendus` se classe, se réessaie, et se compte. |
| ⚫ | Le test de bascule vérifiait la promesse de `Basculer` — « un candidat qui répond ». La promesse était fausse ; aucun test ne pouvait le voir sans un type qui la rende fausse. |
| ⚫ | Un taux moyenné sur quinze minutes ne tire pas avant quinze minutes. Une jauge d'état tire à la seconde : ici, 02:14:22. |
| ⚫ | La campagne peut réclamer une **décision**, pas seulement un test : deux bases inscriptibles sont un cerveau divisé, et choisir l'une, c'est perdre l'autre. |
| ⚫ | Ce que le type ne couvre pas — une rétrogradation après construction — se rattrape à l'exécution, au premier refus, avec un seuil à un. |
| ⚫ | Ce qu'aucun type ne couvre — trois écritures sans transaction — vit dans la base. |
