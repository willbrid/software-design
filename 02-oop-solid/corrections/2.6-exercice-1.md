# Correction 2.6 — Exercice 1 : quatre interfaces, quatre verdicts

> Rappel de l'énoncé : un module de virements, quatre interfaces, et le
> relevé du sondage des implémentations — `Calculateur` et `Comptes` en ont
> une seule, `Notifieur` une et une doublure, `Exporteur` quatre.

J'ai fait les deux transformations proposées et toutes les mesures sur des
copies du module, vertes sous `go vet ./...` et `go test -race -count=1 ./...`.
Campagne de sept modifications, 7/7 après deux passes.

## 1. La prédiction

| Interface | Verdict | Pourquoi, en une ligne |
|---|---|---|
| `frais.Calculateur` | **supprimer** | une implémentation, pas de doublure, pas de frontière |
| `stockage.Comptes` | **garder** | une implémentation, mais une frontière que le test d'architecture garde |
| `notification.Notifieur` | **garder** | une implémentation et une doublure : il y a deux choses derrière |
| `export.Exporteur` | **transformer** | quatre implémentations, mais un paramètre que trois ignorent |

## 2. Les deux interfaces seules

`Calculateur` part. `Comptes` reste. Ce qui les sépare n'est pas dans le
relevé — les deux lignes disent « production 1, tests 0 » —, c'est la phrase
du commentaire de `Comptes` :

> *Le test d'architecture du module interdit au métier d'importer
> `database/sql`.*

`Comptes` est une **frontière** : sans elle, le paquet métier qui demande un
solde devrait nommer `stockage.Postgres`, et tirerait `database/sql` dans ses
dépendances (leçon 2.5). Son bénéficiaire n'est ni une deuxième
implémentation ni une doublure, c'est **le graphe d'imports**. `Calculateur`
n'en a aucun : il est déclaré dans le même paquet que son unique
implémentation, et son consommateur, `Service`, est dans ce paquet aussi.

## 3. `Notifieur`

Il reste : derrière lui, il y a deux choses — l'envoi par SMS, et le carnet
du test qui vérifie le texte du message. Le critère de la leçon est rempli
par la doublure.

Il serait de trop **le jour où la doublure ne servirait plus** — par exemple
si `SMS` acceptait une passerelle de test et que le test pouvait vérifier le
message à travers elle. Une interface qui n'existe que pour une doublure dont
on peut se passer est une interface seule qui s'ignore.

## 4. `Exporteur` et son paramètre ignoré

Le sondage n'a rien à dire : quatre implémentations, l'interface a des
bénéficiaires. Mais trois sur quatre écrivent `_ map[string]string`. C'est la
**mesure 1 de la leçon**, lue après coup : une variante qui ne rentrait pas —
la banque centrale, qui a besoin d'un émetteur et d'un séparateur — a laissé
un paramètre que les trois autres portent sans s'en servir. Et elle l'a laissé
sous la forme la plus faible possible : une carte de chaînes, dont les clés
ne sont vérifiées par rien.

Ce que j'en fais : **la configuration d'un format va dans le format**.

```go
// Exporteur ecrit des lignes. Ce dont un format a besoin pour se configurer
// est dans le format, pas dans la signature commune.
type Exporteur interface {
    Exporter(w io.Writer, lignes []Ligne) error
}
```

```go
// BanqueCentrale porte sa configuration. Un champ mal orthographie ne compile
// plus ; un emetteur absent, lui, donne encore une colonne vide.
type BanqueCentrale struct {
    Emetteur   string
    Separateur string
}

func (b BanqueCentrale) Exporter(w io.Writer, ls []Ligne) error {
    sep := b.Separateur
    if sep == "" {
        sep = "|"
    }
    for _, l := range ls {
        if _, err := fmt.Fprintf(w, "%s%s%s%s%d\n", b.Emetteur, sep, l.Compte, sep, l.Montant); err != nil {
            return err
        }
    }
    return nil
}
```

Un seul fichier change, −10 +15 lignes. Les trois formats perdent un
paramètre qu'ils ignoraient, et `BanqueCentrale{Emetteur: "BEAC01"}` remplace
`map[string]string{"emetteur": "BEAC01"}` : une faute de frappe dans
`"emeteur"` passait sans bruit, une faute de frappe dans `Emeteur` ne compile
pas. Ce que la structure ne règle pas, et il faut le dire : un émetteur
**absent** — `BanqueCentrale{}` — compile toujours, et donne une colonne vide.
Si c'est une faute, elle se ferme par un constructeur qui le refuse.

## 5. Supprimer `Calculateur`

Ma prédiction : un fichier, cinq lignes de moins, une erreur au premier pas.
Mesuré :

```
== suppression, premier pas : 1 erreur(s)
   ex1/avant/frais/frais.go:15:24: undefined: Calculateur
== suppression, complete : 0 erreur(s), tests verts, fichiers : ex1/avant/frais/frais.go (-6 +1)
```

Un fichier, −6 +1, une erreur. La sixième ligne retirée est le champ du
service, qui prend le type concret :

```go
// Package frais calcule les frais d'un virement.
package frais

// Bareme est l'implementation.
type Bareme struct{}

func (Bareme) Frais(centimes int64, international bool) int64 {
    if international {
        return 1500 + centimes/1000
    }
    return 0
}

// Service applique le calculateur.
type Service struct{ C Bareme }

func (s Service) Total(centimes int64, international bool) int64 {
    return centimes + s.C.Frais(centimes, international)
}
```

## 6. Le jour où un deuxième calculateur arrive

Un barème promotionnel. Mesuré, à partir de la version sans interface :

```
== reintroduction : 0 erreur(s), tests verts, fichiers : ex1/avant/frais/frais.go (-1 +11)
```

Un fichier, −1 +11 — dont quatre lignes pour le barème promotionnel
lui-même. **Réintroduire l'interface coûte sept lignes, une fois, dans le
paquet qui en a besoin.** L'avoir gardée un an ne coûtait aucune ligne de
plus : le coût d'une interface seule n'est pas dans les lignes, il est dans
la **lecture** — chaque développeur qui suit `s.C.Frais` cherche une
implémentation, pendant un an, pour en trouver une seule.

La comparaison honnête est donc : sept lignes, le jour où le besoin arrive,
contre un an de détours pour un besoin qui n'arrivera peut-être pas. Et la
mesure dit que le premier coût est connu et petit.

## 7. Le sondage « trop grossier »

Le collègue **a raison** sur les deux limites : le sondage compte des
homonymes, et il ne voit pas une interface qui n'est faite que
d'interfaces incorporées.

Il **se trompe** sur la conséquence. Les homonymes font **surestimer** les
implémentations : le sondage peut cacher une interface seule, il ne peut pas
en inventer une. Une interface qu'il signale avec une seule implémentation
**en a vraiment une seule** au plus — le signal est fiable, c'est l'absence de
signal qui ne prouve rien. On ne décide pas « tout va bien » avec lui ; on
décide « celle-ci est à regarder », et c'est exactement ce dont on a besoin.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Le relevé dit combien de choses il y a derrière une interface ; il ne dit pas si une **frontière** en a besoin. `Comptes` et `Calculateur` ont la même ligne, et deux verdicts. |
| ⚫ | Une interface seule dont le consommateur est dans le même paquet est une indirection sans bénéficiaire. |
| ⚫ | Une doublure justifie une interface tant qu'on ne peut pas s'en passer. |
| ⚫ | Un paramètre que la plupart des implémentations ignorent est la trace d'une variante qui ne rentrait pas. La configuration d'une variante va dans la variante. |
| ⚫ | Supprimer une interface seule : un fichier, −6 +1. La réintroduire le jour venu : sept lignes. Le coût de la garder n'est pas en lignes, il est en lecture. |
| ⚫ | Le sondage surestime les implémentations : ce qu'il signale est vrai, ce qu'il ne signale pas ne prouve rien. |
