# Correction 2.5 — Exercice 3 : le cache Redis et ses doublures générées

> Rappel de l'énoncé : une interface `cache.Cache` qui reprend Redis méthode
> pour méthode, un paquet `mocks` généré, trois consommateurs — sessions,
> limiteur de requêtes, verrou de tâche planifiée.

Deux instantanés, `avant` et `apres`, verts sous `go vet ./...` et
`go test -race -count=1 ./...`. Campagne de dix modifications : neuf tuées,
une survivante diagnostiquée « rien ».

## 1. La matrice

```
limiteur  2/7  [Expirer Incrementer]
session   3/7  [Ecrire Lire Supprimer]
tache     2/7  [Supprimer Verrouiller]
aucun consommateur : [Vider]
```

Trois consommateurs, sept méthodes, **sept cases remplies sur vingt et une**.
`Vider` n'est appelée par personne — ni par le code, ni par aucun test : son
champ `ViderFn` n'est configuré nulle part. `Supprimer` est appelée par deux
consommateurs, et pas pour la même chose : la question 5 y revient.

## 2. La mesure A, avec la doublure régénérée

Un paramètre ajouté à `Expirer`, dans `cache`, et `mocks` remis à jour :

```
ex3/avant/limiteur/limiteur.go:25:30: not enough arguments in call to l.c.Expirer
ex3/avant/limiteur/limiteur_test.go:14:18: cannot use func(string, time.Duration) error {…} (value of type func(string, time.Duration) error) as func(cle string, ttl time.Duration, glissant bool) error value in struct literal
FAIL    exemple/c25/ex3/avant/limiteur [build failed]
```

**Un paquet**, le seul qui appelle `Expirer`. C'est le chiffre que la leçon
obtient **après** la coupe ISP — et on l'obtient ici avec l'interface large
intacte. L'écart s'explique en une ligne : les doublures des trois
consommateurs ne sont pas dans leurs paquets, elles sont dans `mocks`, et
`mocks` a été régénéré. Le changement a cassé **un fichier de 80 lignes
qu'on ne lit pas**, au lieu de trois tests qu'on lit.

## 3. La mesure B

| | |
|---|---|
| méthodes de la doublure générée | 7, toutes avec un `panic` si elles ne sont pas configurées |
| méthodes configurées par au moins un test | 6 — `Vider` jamais |
| méthodes de doublure écrites dans les trois paquets consommateurs | **0** |
| lignes du paquet `mocks` | 80 |

Zéro ligne de doublure dans les consommateurs : la mesure B de la leçon —
« combien de méthodes de doublure un consommateur doit-il écrire pour des
méthodes qu'il n'appelle pas » — ne trouve rien à compter.

## 4. Pourquoi les deux mesures sont muettes, et où le coût est passé

**Les mesures A et B comptent ce que chaque consommateur doit écrire.** Un
générateur écrit à leur place, une fois pour tous : il ne supprime pas le coût
de l'interface large, il le **concentre** dans un paquet que personne ne
relit.

Le coût est toujours là, sous trois formes :

1. **Un fichier régénéré à chaque changement de l'interface**, quel que soit le
   consommateur concerné — 80 lignes ici, des milliers dans un vrai dépôt.
2. **Une doublure qui permet tout.** Le test des sessions peut configurer
   `VerrouillerFn` ; le compilateur ne dira rien. Une doublure côté
   consommateur, elle, n'a que les méthodes que le consommateur a le droit
   d'appeler : elle est **une** vérification du périmètre du consommateur. La
   doublure générée n'en est aucune.
3. **Une deuxième implémentation qui doit tout implémenter** — et c'est la
   question 5.

La mesure de la leçon qui voit encore l'interface large, c'est **le
sondage** : il lit le code de production, pas les tests, et la matrice de la
question 1 est la même avec ou sans générateur. **Le générateur efface les
mesures A et B ; il n'efface pas la matrice.**

## 5. La dépendance de `tache`

`tache` libère son verrou avec `Supprimer("verrou:" + nom)`. Il sait donc
**comment Redis range ses verrous** : une clé préfixée par `verrou:`, posée par
`Verrouiller`. Ni le sondage — qui voit un appel à `Supprimer`, rien de plus
— ni le compilateur — qui voit une chaîne — ne le voient. Il manque à
l'interface une méthode, **`Deverrouiller`**, et `tache` l'a remplacée par une
connaissance de l'implémentation.

J'ai écrit la deuxième implémentation que l'énoncé évoque — des verrous à la
façon d'etcd, rangés sous `/verrous/`. Pour être donnée à `tache`, qui prend
un `cache.Cache`, elle doit avoir les sept méthodes :

```go
// Package etcd est une deuxieme implementation des verrous, sur le modele
// d'etcd : les verrous sont des cles sous /verrous/. Ici en memoire.
//
// Pour etre passee a tache.Executer, qui prend un cache.Cache, elle doit
// avoir les SEPT methodes — dont cinq qu'un service de verrous n'a aucune
// raison d'avoir.
package etcd

import (
    "sync"
    "time"
)

type Etcd struct {
    mu sync.Mutex
    v  map[string]bool
}

func Nouveau() *Etcd { return &Etcd{v: map[string]bool{}} }

func (e *Etcd) Verrouiller(cle string, _ time.Duration) (bool, error) {
    e.mu.Lock()
    defer e.mu.Unlock()
    if e.v["/verrous/"+cle] {
        return false, nil
    }
    e.v["/verrous/"+cle] = true
    return true, nil
}

func (e *Etcd) Supprimer(cle string) error {
    e.mu.Lock()
    defer e.mu.Unlock()
    delete(e.v, cle)
    return nil
}

func (e *Etcd) Lire(string) ([]byte, bool, error)          { panic("etcd : non supporte") }
func (e *Etcd) Ecrire(string, []byte, time.Duration) error { panic("etcd : non supporte") }
func (e *Etcd) Incrementer(string, int64) (int64, error)   { panic("etcd : non supporte") }
func (e *Etcd) Expirer(string, time.Duration) error        { panic("etcd : non supporte") }
func (e *Etcd) Vider() error                               { panic("etcd : non supporte") }
```

Cinq `panic` pour satisfaire une interface dont un service de verrous n'a que
faire — l'interface large force la violation de Liskov, comme la réplique de
la leçon. Et le défaut de `tache` se mesure :

```go
// TestAvecEtcdLeVerrouNeSeLibereJamais fige le defaut : tache libere le verrou
// en supprimant « verrou:rapport », la cle que Redis utilise. Etcd range son
// verrou ailleurs ; la suppression ne touche rien, et la deuxieme execution
// est refusee.
func TestAvecEtcdLeVerrouNeSeLibereJamais(t *testing.T) {
    for _, c := range []struct {
        nom  string
        impl cache.Cache
        deux bool
    }{
        {"Redis", cache.NouveauRedis(), true},
        {"etcd", etcd.Nouveau(), false},
    } {
        f := func() error { return nil }
        _, _ = Executer(c.impl, "rapport", f)
        if ok, _ := Executer(c.impl, "rapport", f); ok != c.deux {
            t.Errorf("%s : deuxieme execution %v, attendu %v", c.nom, ok, c.deux)
        }
    }
}
```

Le test passe, c'est-à-dire que **le défaut est réel** : sur etcd, la
deuxième exécution est refusée, parce que la suppression de `verrou:rapport`
n'a rien supprimé. En production, la tâche planifiée ne tourne plus jusqu'à
l'expiration du verrou — cinq minutes, à chaque exécution.

C'est la leçon 2.4 : **un contrat que la signature ne dit pas**. Ici, le
contrat implicite de `Verrouiller` était « le verrou est une clé
`verrou:<nom>` que tu peux supprimer », et une seule implémentation le tenait.

## 6. La coupe

Trois interfaces, chez les trois consommateurs :

```go
// Sessions est ce dont le magasin de sessions a besoin.
type Sessions interface {
    Lire(cle string) ([]byte, bool, error)
    Ecrire(cle string, v []byte, ttl time.Duration) error
    Supprimer(cle string) error
}

type Magasin struct{ c Sessions }

func Nouveau(c Sessions) Magasin { return Magasin{c: c} }
```

```go
// Compteurs est ce dont le limiteur a besoin.
type Compteurs interface {
    Incrementer(cle string, n int64) (int64, error)
    Expirer(cle string, ttl time.Duration) error
}

type Limiteur struct {
    c     Compteurs
    Seuil int64
}

func Nouveau(c Compteurs, seuil int64) Limiteur { return Limiteur{c: c, Seuil: seuil} }
```

```go
// Package tache execute une tache planifiee sur une seule instance a la fois.
package tache

import "time"

// Verrous est ce dont la tache a besoin : prendre un verrou, et le rendre.
// Deverrouiller n'existait pas dans cache.Cache ; tache le remplacait par
// Supprimer("verrou:" + nom), c'est-a-dire par la connaissance de la cle que
// Redis utilise.
//
// Contrat : une erreur de Verrouiller s'accompagne toujours de false.
type Verrous interface {
    Verrouiller(cle string, ttl time.Duration) (bool, error)
    Deverrouiller(cle string) error
}

// Executer prend le verrou, lance f, et rend le verrou. Si une autre instance
// a le verrou, f n'est pas lancee.
func Executer(v Verrous, nom string, f func() error) (bool, error) {
    ok, err := v.Verrouiller(nom, 5*time.Minute)
    if err != nil || !ok {
        return false, err
    }
    defer v.Deverrouiller(nom)
    return true, f()
}
```

Le paquet `mocks` est supprimé. Le diff de `cache` :

```
71a72,75
> // Deverrouiller rend le verrou pris par Verrouiller. Il sait ou Redis range
> // ses verrous ; ses appelants n'ont plus a le savoir.
> func (r *Redis) Deverrouiller(cle string) error { return r.Supprimer("verrou:" + cle) }
>
```

Une méthode, et c'est la correction de la question 5, pas la coupe : **la
coupe ISP seule ne change aucune ligne de `cache`**, comme dans la leçon. La
connaissance de la clé `verrou:` est revenue là où elle appartient, chez
l'implémentation qui la choisit. `cache.Cache` existe toujours, sans plus aucun
consommateur : le sondage la signale entière, et elle peut partir dans un
second temps.

Et la racine de composition, sans laquelle rien ne vérifierait que Redis
satisfait encore les trois interfaces (correction 2.5/1) :

```go
// Ports regroupe ce que chaque consommateur recoit.
type Ports struct {
    Sessions  session.Sessions
    Compteurs limiteur.Compteurs
    Verrous   tache.Verrous
}

// Cabler branche un seul Redis sur les trois ports.
func Cabler(r *cache.Redis) Ports {
    return Ports{Sessions: r, Compteurs: r, Verrous: r}
}
```

La mesure A refaite sur `apres` :

```
ex3/apres/montage/montage.go:20:39: cannot use r (variable of type *cache.Redis) as limiteur.Compteurs value in struct literal: *cache.Redis does not implement limiteur.Compteurs (wrong type for method Expirer)
FAIL    exemple/c25/ex3/apres/montage [build failed]
```

Un paquet, la racine, avec une erreur qui nomme le consommateur. Le même
chiffre qu'avant — mais l'erreur est maintenant **à l'endroit où l'on câble**,
lisible, et aucun fichier généré n'a eu à changer.

Les doublures écrites à la main :

| Consommateur | lignes du test | méthodes de doublure |
|---|---|---|
| `session` | 28 | 3 |
| `limiteur` | 40 | 2 |
| `tache` | 54 | 0 — il teste sur les deux vraies implémentations, Redis et etcd |

## 7. `m.Appels`, et ce qu'il vérifiait

`[]string{"Ecrire", "Lire"}` vérifiait **l'ordre des appels que le magasin
passe pour faire son travail**. C'est un détail d'implémentation : un magasin
qui lirait d'abord pour vérifier qu'une session n'existe pas déjà ferait un
test rouge sans être faux. Ce que le test doit vérifier, c'est ce que le
magasin fait — ouvrir, lire, fermer — et le nouveau test le fait, y compris
`Fermer`, que l'ancien ne testait pas.

Il y a un cas où l'appel lui-même est la propriété : l'expiration de la clé
du limiteur. « La clé de la minute reçoit **une** expiration, d'**une**
minute » n'est pas un détail, c'est ce qui empêche le compteur de vivre
toujours. La doublure à la main l'enregistre, et le test le dit comme une
propriété :

```go
func TestLeTroisiemeEstRefuseEtLaCleExpireUneFois(t *testing.T) {
    c := &compteurs{n: map[string]int64{}, expirances: map[string][]time.Duration{}}
    l := Nouveau(c, 2)
    quand := time.Date(2026, 3, 2, 10, 0, 0, 0, time.UTC)
    var got []bool
    for range 3 {
        ok, _ := l.Autoriser("c1", quand)
        got = append(got, ok)
    }
    if got[0] != true || got[1] != true || got[2] != false {
        t.Fatalf("%v", got)
    }
    // Ce que vérifiait m.Appels, dit comme une propriété : la clé de la minute
    // reçoit UNE expiration, d'une minute. Pas une par requête.
    e := c.expirances["limite:c1:202603021000"]
    if len(e) != 1 || e[0] != time.Minute {
        t.Fatalf("expirations %v", e)
    }
}
```

Donc : **perte nulle**. Ce que vérifiait `m.Appels` se range en deux tas —
ce qui était un détail, et disparaît ; ce qui était une propriété, et devient
une assertion nommée.

## 8. Le générateur

Il fait gagner **le temps d'écrire les doublures** : 80 lignes générées
contre 5 méthodes écrites à la main ici, et dans un dépôt réel, des centaines.

Il fait perdre **la mesure** : avec lui, changer une méthode casse un paquet
généré que personne ne lit, et aucun consommateur n'écrit une ligne pour une
méthode qu'il n'appelle pas. L'interface large devient **gratuite à
l'usage**, donc elle grossit — sept méthodes ici, `Vider` comprise, que
personne n'appelle et que le générateur entretient quand même.

La règle qui garde le générateur sans perdre la mesure :

> **Générer les doublures depuis l'interface du consommateur, jamais depuis
> celle du producteur.** Un générateur accepte n'importe quelle interface :
> pointé sur `tache.Verrous`, il produit une doublure de deux méthodes, dans
> le paquet de `tache`. Une doublure générée qui a plus de méthodes que son
> consommateur n'en appelle est le signal qu'elle est générée au mauvais
> endroit.

## 9. La campagne

### Première passe

```
session : Fermer ne fait rien              tuee
limiteur : une expiration par requete      tuee
limiteur : expiration de deux minutes      tuee
limiteur : seuil exclu                     tuee
tache : ne deverrouille plus               tuee
tache : deverrouille avant de lancer       tuee
tache : erreur du verrou avalee            SURVIT
etcd : mauvaise cle au deverrouillage      tuee
Redis : mauvaise cle au deverrouillage     tuee
montage : un port non cable                tuee
9/10 tuees
```

`tache` prenait `if err != nil || !ok`. Remplacé par `if !ok`, la
modification survit — et elle survit encore après l'ajout d'un test où le
verrou est injoignable. La raison : quand `Verrouiller` échoue, toutes les
implémentations rendent `false` **et** l'erreur, et `return false, err` la
transmet de toute façon. La modification n'est observable qu'avec une
implémentation qui rendrait `true` et une erreur — ce qui n'a pas de sens.

C'est un mutant **équivalent sous le contrat**, et le diagnostic est
« rien » — à une condition : que le contrat soit écrit. Il l'est maintenant,
sur l'interface : *une erreur de Verrouiller s'accompagne toujours de false.*
Le test du verrou injoignable reste : il vérifie un comportement réel, même
s'il ne distingue pas ce mutant.

```
9/10 tuees
```

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Un générateur de doublures **concentre** le coût d'une interface large dans un paquet que personne ne lit. Mesuré : la mesure A donne 1, comme après une coupe ISP, avec l'interface intacte. |
| ⚫ | Le sondage lit le code de production : la matrice ne change pas avec ou sans générateur. C'est la mesure qui reste. |
| ⚫ | Une doublure côté consommateur vérifie son périmètre ; une doublure générée depuis le producteur permet tout. |
| ⚫ | Un consommateur qui supprime une clé « que l'implémentation a posée » dépend de l'implémentation. Il manque une méthode à l'interface. Mesuré : sur etcd, le verrou ne se libère jamais. |
| ⚫ | Une interface large force la deuxième implémentation à paniquer sur ce qu'elle ne sait pas faire : cinq `panic` pour un service de verrous. |
| ⚫ | Vérifier l'ordre des appels teste l'implémentation. Ce qui, dans cet ordre, est une propriété devient une assertion nommée. |
| ⚫ | Générer depuis l'interface du consommateur, jamais depuis celle du producteur. |
| ⚫ | Un mutant équivalent sous un contrat non écrit est un trou ; sous un contrat écrit, c'est « rien ». |
