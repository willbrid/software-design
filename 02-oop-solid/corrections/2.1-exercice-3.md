# Correction 2.1 — Exercice 3 : refactoring

## Question 1 — combien de concepts dans `Record`

Les trois commentaires du code annoncent trois sections : patient, consultation,
ordonnance. **Il y en a cinq**, et le piège annoncé par l'énoncé est le
quatrième.

| Concept | Le mot du métier | Son identité | Les champs |
|---|---|---|---|
| **le patient** | « le patient », « le dossier » | un identifiant propre | `PatientID`, `PatientName`, `BirthDate`, `Phone`, `BloodGroup`, `Allergies` |
| **la consultation** | « la consultation », « la visite » | un identifiant propre | `VisitDate`, `Practitioner`, `Reason` |
| **les constantes vitales** | « les constantes », « la tension » | aucune — elles appartiennent à la consultation | `SystolicBP`, `DiastolicBP`, `WeightKg` |
| **la ligne de prescription** | « la ligne », « le médicament prescrit » | un identifiant propre | `Drug`, `DosageMg`, `PerDay`, `DurationDays`, `Renewable` |
| **la délivrance** | « la délivrance », « la dispensation » | aucune — elle appartient à la ligne | `Dispensed`, `DispensedAt` |

### Le quatrième, celui que les commentaires ratent

Le commentaire dit `// Prescription`. Mais les champs qu'il annonce
— `Drug`, `DosageMg`, `PerDay`, `DurationDays` — ne décrivent **pas** une
ordonnance : ils décrivent **une ligne** d'ordonnance.

Une ordonnance porte trois médicaments. Dans ce modèle, elle n'existe pas : il y
a trois `Record` qui portent chacune un médicament et **répètent** le patient, la
consultation et les constantes. L'ordonnance comme document — celui que le
patient emporte, celui que le pharmacien lit, celui qui se renouvelle — n'a
aucune représentation.

> Quand un concept du métier n'a aucune représentation, il n'est pas « implicite ».
> Il est **réparti** dans toutes les lignes qui le mentionnent, et chaque
> opération doit le reconstituer. C'est pour ça que les trois méthodes du
> service font des boucles.

### Et les deux concepts sans identité propre

Les constantes vitales et la délivrance n'ont pas d'identité : elles
appartiennent entièrement à leur porteur. Ce sont donc des **valeurs** — ou, pour
la délivrance, un **état** de la ligne.

C'est utile à savoir pour la question 5, parce que c'est exactement là qu'on
fabrique des entités en trop.

## Question 2 — les trois bugs, racontés côté patient

### `Dispense` — la mauvaise boîte

```
for _, f := range fiches {
    if f.Drug == medicament && !f.Dispensed {
        f.Dispensed = true
```

La recherche se fait sur **le nom du médicament** et sur l'état *non délivré*.
Elle prend **la première** qui correspond.

> **Scénario patient.** Awa a reçu de l'amoxicilline 500 mg en janvier, et n'est
> jamais passée la chercher. En mars, le médecin lui prescrit de l'amoxicilline
> **250 mg** — dose réduite, parce qu'un bilan rénal est revenu anormal. Le
> pharmacien saisit « amoxicilline » et délivre. Le système clôt la ligne de
> **janvier**.
>
> Awa part avec une boîte de 500 mg. La ligne de mars reste ouverte, donc elle
> pourra revenir en chercher une autre. Et le dossier dit que la prescription de
> janvier a été honorée.

La cause n'est pas la boucle : c'est que **`Dispense` ne reçoit pas d'identité de
ligne**, parce que les lignes n'ont pas d'identité. La signature ne pouvait que
deviner.

### `UpdatePhone` — le SMS qui part à l'ancien numéro

```
for _, f := range fiches {
    f.Phone = telephone
    if err := s.repo.Save(f); err != nil {
        return err
    }
}
```

Le téléphone est stocké sur **chaque** fiche. Le corriger est donc une boucle
d'écritures, et la boucle s'arrête au premier échec.

> **Scénario patient.** Boubacar a douze lignes dans son dossier — quatre
> consultations, trois médicaments chacune. Il change de numéro. L'écriture
> réussit pour les sept premières, puis la base bascule. Boubacar a maintenant
> **deux numéros de téléphone** dans son dossier.
>
> Le rappel de son rendez-vous part sur l'ancien. Il ne vient pas. On le note
> comme absent.

Et une seconde fois le même mécanisme qu'en 1.6 : **la cohérence est une
propriété de la boucle, pas du modèle.** Il n'existe aucun état de ce modèle où
« le téléphone du patient » soit une seule donnée.

### `Prescribe` — l'écrasement silencieux

```
func (s *Service) Prescribe(f Record) error {
    if f.DosageMg <= 0 || ... { return errors.New("posologie invalid") }
    return s.repo.Save(f)
}
```

`Prescribe` reçoit une **fiche entière** — trente champs — pour en valider trois
et en enregistrer trente.

> **Scénario patient.** L'interface du cabinet charge la fiche d'Awa pour
> afficher ses allergies, puis l'opérateur passe à la consultation de Boubacar
> sans que l'objet en mémoire soit rechargé. Il prescrit. La fiche enregistrée
> porte le médicament de Boubacar **et le groupe sanguin d'Awa**.
>
> Six mois plus tard, Boubacar arrive aux urgences. Son dossier dit O+. Il est
> A−.

C'est le bug le plus grave des trois, et il n'est pas détectable : les deux
valeurs sont valides, aucune contrainte n'est violée, et il n'y a pas de trace.

> Une fonction qui reçoit plus de données qu'elle n'en a besoin ne se contente
> pas d'être imprécise : elle **enregistre** tout ce qu'elle a reçu. Le périmètre
> d'un paramètre est le périmètre de ce qu'il peut détruire.

### Et le quatrième, que l'énoncé ne demandait pas

`Prescribe` valide la posologie. **Et c'est le seul endroit.** Un import, une
reprise de données, un autre service, un `UPDATE` SQL : tous contournent la
validation. L'invariant *« une posologie est positive »* n'a pas d'adresse, c'est
la question 6 de l'exercice 1 sous un autre nom.

## Question 3 — `DailyDose`

```
func DailyDose(f Record) float64 { return f.DosageMg * float64(f.PerDay) }
```

### Sur quel concept porte-t-elle vraiment

Sur la **posologie**, et sur rien d'autre. Elle prend trente champs pour en lire
deux. La bonne signature est une méthode :

```
func (p Dosage) Daily() (Dose, error)
```

C'est le critère de la leçon : *une méthode existe pour préserver un invariant*.
Ici, elle calcule — mais elle calcule sur un type dont les trois champs ont été
validés ensemble, et c'est ce qui la rend sûre.

### Ce que `float64` autorise qu'une posologie interdit

| Ce que `float64` permet | Pourquoi c'est inacceptable ici |
|---|---|
| `NaN` | une dose « non définie » qui passe tous les tests `> 0` — car `NaN > 0` est **faux**, donc la garde `DosageMg <= 0` est **aussi** fausse, et `NaN` passe |
| `+Inf` | une dose infinie |
| `-0.0` | une dose négative qui n'est pas `< 0` |
| `0.1 + 0.2 = 0.30000000000000004` | une dose de 0,3 mg qui n'est pas égale à 0,3 mg |
| `2.5 * 3 = 7.5` puis `/3 = 2.4999999999999996` | une dose qui dérive à chaque calcul |

La première ligne est la plus grave et la moins connue. Relis la garde du
service :

```
if f.DosageMg <= 0 || f.PerDay <= 0 || f.DurationDays <= 0 {
```

Si `DosageMg` vaut `NaN`, alors `NaN <= 0` rend **faux**. La garde ne déclenche
pas. **Une prescription de `NaN` milligrammes est enregistrée.**

> En flottant, une comparaison n'est pas une partition. `x <= 0` et `x > 0`
> peuvent être faux tous les deux, et toute garde écrite avec un seul des deux
> a un trou.

### La réponse

Un entier, en microgrammes. C'est l'unité la plus fine utilisée en prescription
— la lévothyroxine se prescrit en microgrammes — et `int64` en microgrammes
couvre jusqu'à neuf mille tonnes : la borne n'est pas le problème.

```go
// Bounds of the dosage. They are here, once, and nowhere else.
const (
    MinIntakes = 1
    MaxIntakes = 6
    MinDays    = 1
    MaxDays    = 90
)

// Dose is an amount of active ingredient, in whole MICROGRAMS.
//
// No float64, and it is the most important decision of this file. A
// float64 allows NaN, +Inf, -0, 0.1 + 0.2 = 0.30000000000000004, and a dose
// of 2.5 mg that becomes 2.4999999999999996 at the third computation. In medicine,
// precision is not a preference.
//
// The microgram is the finest unit used in prescriptions: the
// levothyroxine is prescribed in micrograms. Int64 in micrograms covers
// up to nine thousand tonnes: the bound is not the problem.
type Dose struct {
    ug int64
}

// Micrograms builds a dose.
func Micrograms(ug int64) (Dose, error) {
    if ug < 0 {
        return Dose{}, fmt.Errorf("%w: %d ug", ErrNegativeDose, ug)
    }
    return Dose{ug: ug}, nil
}

// Milligrams builds a dose from milligrams expressed in
// tenths: 25 means 2.5 mg.
//
// Two constructors rather than one, because both units really
// come in: prescriptions speak in milligrams, leaflets in
// micrograms. Converting in the wrong place is a factor-of-a-thousand error.
func Milligrams(tenths int64) (Dose, error) {
    if tenths < 0 {
        return Dose{}, fmt.Errorf("%w: %d tenths of mg", ErrNegativeDose, tenths)
    }
    return Dose{ug: tenths * 100}, nil
}

func MustMilligrams(tenths int64) Dose {
    d, err := Milligrams(tenths)
    if err != nil {
        panic(err)
    }
    return d
}

func (d Dose) Micrograms() int64 { return d.ug }
func (d Dose) IsZero() bool      { return d.ug == 0 }

// Times multiplies the dose. Returns an error rather than a wrong result.
func (d Dose) Times(n int) (Dose, error) {
    if n < 0 {
        return Dose{}, fmt.Errorf("%w: x%d", ErrNegativeDose, n)
    }
    if n != 0 && d.ug > (1<<62)/int64(n) {
        return Dose{}, fmt.Errorf("%w: %d ug x %d", ErrDoseNotRepresentable, d.ug, n)
    }
    return Dose{ug: d.ug * int64(n)}, nil
}

func (d Dose) Exceeds(other Dose) bool { return d.ug > other.ug }

// String shows milligrams when it reads well, micrograms otherwise.
// A single form per dose, so that one log can be compared with another.
func (d Dose) String() string {
    if d.ug%1000 == 0 && d.ug != 0 {
        return strconv.FormatInt(d.ug/1000, 10) + " mg"
    }
    if d.ug%100 == 0 && d.ug != 0 {
        return strconv.FormatInt(d.ug/1000, 10) + "," + strconv.FormatInt((d.ug%1000)/100, 10) + " mg"
    }
    return strconv.FormatInt(d.ug, 10) + " ug"
}
```

Noter les **deux constructeurs**. Les ordonnances parlent en milligrammes, les
notices en microgrammes, et les deux arrivent. Convertir au mauvais endroit est
une erreur de facteur mille — en médecine, c'est un facteur mille sur une dose.
Un test garde la jonction :

```go
// TestTheTwoUnitsMeet guards the decision of two constructors: a
// factor-of-a-thousand error would be silent with only one.
func TestTheTwoUnitsMeet(t *testing.T) {
    perMg := dosage.MustMilligrams(25)    // 2,5 mg
    perUg, err := dosage.Micrograms(2500) // 2 500 ug
    if err != nil {
        t.Fatalf("Micrograms: %v", err)
    }
    if perMg != perUg {
        t.Fatalf("2.5 mg = %s but 2500 ug = %s", perMg, perUg)
    }
    if perMg.Micrograms() != 2500 {
        t.Fatalf("Micrograms() = %d", perMg.Micrograms())
    }
}
```

## Question 4 — la découpe

### Les valeurs

| Type | Identité | Invariants | Raison de changer |
|---|---|---|---|
| `Dose` | aucune — valeur | positive, en microgrammes entiers | la liste des unités utilisées en prescription |
| `Dosage` | aucune — valeur | dose non nulle, 1 à 6 prises, 1 à 90 jours | les bornes réglementaires de prescription |
| `Phone` | aucune — valeur | neuf chiffres, une seule forme canonique | le plan de numérotation de l'opérateur |
| `GroupeSanguin` | aucune — valeur | huit valeurs, pas une neuvième | rien : la biologie ne change pas |
| `PatientID`, `VisitID`, `LineID` | aucune — valeurs | strictement positives | la politique d'attribution des identifiants |

### Les entités

| Type | Identité | Invariants | Raison de changer |
|---|---|---|---|
| `Patient` | `PatientID` | nom non vide, naissance renseignée, allergies non modifiables de l'extérieur | ce que l'administration du cabinet doit connaître d'une personne |
| `Visit` | `VisitID` | patient et praticien désignés, date renseignée | ce qu'une visite doit tracer |
| `Line` | `LineID` | médicament nommé, posologie non nulle, délivrable une seule fois, rattachée à une ordonnance et à une seule | la règle de dispensation |

### Le type qui n'est pas dans la liste

`Prescription` manque, et c'est volontaire. Dans cette correction, une ligne porte
l'identifiant de sa consultation, et l'ordonnance est l'ensemble des lignes d'une
consultation.

C'est un **choix contestable**, et il faut dire pourquoi plutôt que de le cacher :
une ordonnance a des attributs propres dans la vraie vie — une date de validité,
un nombre de renouvellements, une signature. Dès que l'un des trois est demandé,
`Prescription` devient une entité à part entière. Je ne l'ai pas créée parce
qu'aucun des trois n'apparaît dans l'énoncé, et créer une entité pour un concept
dont on ne sait rien, c'est le piège de la question 5.

### Le code de la posologie, en entier

```go
// Dosage is "how much, how many times, for how long".
// The three fields together, because they change together: nobody
// changes the number of intakes without reconsidering the dose. Apart, they
// would allow a half-modified dosage.
type Dosage struct {
    dose    Dose
    intakes int
    days    int
}

// New builds a valid dosage, or nothing.
func New(d Dose, intakes, days int) (Dosage, error) {
    if d.IsZero() {
        return Dosage{}, ErrZeroDose
    }
    if intakes < MinIntakes || intakes > MaxIntakes {
        return Dosage{}, fmt.Errorf("%w: %d intakes (want %d to %d)",
            ErrInvalidIntakes, intakes, MinIntakes, MaxIntakes)
    }
    if days < MinDays || days > MaxDays {
        return Dosage{}, fmt.Errorf("%w: %d days (want %d to %d)",
            ErrInvalidDuration, days, MinDays, MaxDays)
    }
    return Dosage{dose: d, intakes: intakes, days: days}, nil
}

func (p Dosage) Dose() Dose   { return p.dose }
func (p Dosage) Intakes() int { return p.intakes }
func (p Dosage) Days() int    { return p.days }

// IsZero tells the zero value from a real dosage. The zero value of
// this type IS NOT a valid state: "0 mg, 0 times a day, for 0 days"
// is not a light prescription, it is no prescription.
func (p Dosage) IsZero() bool { return p == Dosage{} }

// Daily is the question the exercise asked: it is a method of the
// DOSAGE, not a function that takes a whole record.
//
// The original signature, DailyDose(f Record) float64, took thirty
// fields to read two, and returned a type that allows NaN.
func (p Dosage) Daily() (Dose, error) {
    if p.IsZero() {
        return Dose{}, ErrZeroDose
    }
    return p.dose.Times(p.intakes)
}

// Total is the quantity to dispense. It is what the pharmacist reads.
func (p Dosage) Total() (Dose, error) {
    daily, err := p.Daily()
    if err != nil {
        return Dose{}, err
    }
    return daily.Times(p.days)
}

// CheckAgainst compares the daily dose with the drug's maximum.
//
// The maximum is an ARGUMENT, not a field: it belongs to the drug, not to
// the dosage. Same mechanism as the lesson's quota: the rule is here, the
// data comes down.
//
// NOT GUARANTEED: that the dosage suits the patient. Age, weight,
// kidney function and interactions are not here, and no type will
// replace them. This method checks a bound; it does not prescribe.
func (p Dosage) CheckAgainst(maxDaily Dose) error {
    daily, err := p.Daily()
    if err != nil {
        return err
    }
    if daily.Exceeds(maxDaily) {
        return fmt.Errorf("%w: %s per day for a maximum of %s",
            ErrDailyDoseExceeded, daily, maxDaily)
    }
    return nil
}

func (p Dosage) String() string {
    if p.IsZero() {
        return "zero dosage"
    }
    return fmt.Sprintf("%s, %d times a day, for %d days", p.dose, p.intakes, p.days)
}
```

Deux points.

**Les trois champs sont ensemble parce qu'ils changent ensemble.** Personne ne
modifie le nombre de prises sans reconsidérer la dose. Séparés, ils
permettraient une posologie à moitié modifiée.

**`CheckAgainst` reçoit le maximum en argument.** Le maximum journalier
appartient au **médicament**, pas à la posologie. Même mécanique que le quota de
la leçon et que le cumulé de l'exercice 2 : la règle est ici, la donnée descend.

Et la clause `NON GARANTI` dit ce qu'aucun type ne remplacera :

> Que la posologie soit adaptée **au patient**. L'âge, le poids, la fonction
> rénale et les interactions ne sont pas ici. Cette méthode vérifie une borne ;
> elle ne prescrit pas.

## Question 5 — les deux pièges

### Celui que j'ai rencontré : trop de types

J'ai failli faire une entité de la **délivrance**. Elle a une date, elle a un
état, elle a un agent qui la réalise — tout pour ressembler à une entité.

Elle n'en est pas une, et le test de la leçon le dit en dix secondes : *si je
change un champ de la délivrance, est-ce toujours la même délivrance ?* La
question n'a pas de sens, parce qu'une délivrance **n'a pas de cycle de vie
propre** : elle arrive une fois, et elle ne change plus. C'est un **état** de la
ligne, pas une chose.

### Le critère qui tranche, et il ne tient pas en « ça dépend »

> Une chose est une entité si et seulement si elle peut **changer en gardant son
> identité**. Autrement dit : s'il existe au moins une opération qui la modifie
> et après laquelle on dit encore *« c'est la même »*.

Applique-le :

| Candidat | Une opération qui le modifie ? | Verdict |
|---|---|---|
| `Patient` | corriger le téléphone, ajouter une allergie | **entité** |
| `Visit` | corriger la date, corriger le motif | **entité** |
| `Line` | la délivrer | **entité** |
| la délivrance | aucune — elle est, ou elle n'est pas | **état**, pas entité |
| les constantes vitales | aucune — on ne corrige pas une tension passée, on en relève une autre | **valeur** |
| `Dosage` | aucune — on en prescrit une autre | **valeur** |

Le critère marche aussi à l'envers, et c'est là qu'il est le plus utile : **si
aucune opération ne modifie le candidat, en faire une entité ajoute un
identifiant, une table, une jointure et un cycle de vie — pour rien.**

### Et l'autre piège, qu'il faut savoir repérer chez soi

**Trop peu de types** : garder le patient et la consultation ensemble, parce que
« de toute façon une consultation appartient à un patient ». C'est le modèle
d'origine, et la conséquence est le bug n° 3 — prescrire écrase le groupe
sanguin.

Le test est le même, lu dans l'autre sens : les deux ont-ils **la même
identité** ? Un patient a quatre consultations. Donc non. Donc deux types.

## Question 6 — le type le plus chargé, et sa campagne

`Dosage` porte le plus d'invariants : six, dont trois bornes et un calcul.
Ses tests :

```go
func TestNewRefusesWhatMedicineRefuses(t *testing.T) {
    fiveHundred := dosage.MustMilligrams(5000) // 500,0 mg

    tc := []struct {
        name    string
        dose    dosage.Dose
        intakes int
        days    int
        want    error
        why     string
    }{
        {"valid", fiveHundred, 3, 7, nil, ""},
        {"one intake", fiveHundred, 1, 1, nil, "the minimum is a legitimate prescription"},
        {"six intakes", fiveHundred, 6, 90, nil, "both upper bounds can be reached"},
        {"zero dose", dosage.Dose{}, 3, 7, dosage.ErrZeroDose,
            "0 mg is not a light prescription, it is no prescription"},
        {"zero intakes", fiveHundred, 0, 7, dosage.ErrInvalidIntakes,
            "a drug one does not take has no dosage"},
        {"seven intakes", fiveHundred, 7, 7, dosage.ErrInvalidIntakes, "over the bound"},
        {"zero days", fiveHundred, 3, 0, dosage.ErrInvalidDuration, ""},
        {"91 days", fiveHundred, 3, 91, dosage.ErrInvalidDuration,
            "beyond 90 days, it is a long-term treatment, not a prescription"},
        {"negative intakes", fiveHundred, -1, 7, dosage.ErrInvalidIntakes, ""},
    }

    for _, c := range tc {
        t.Run(c.name, func(t *testing.T) {
            p, err := dosage.New(c.dose, c.intakes, c.days)
            if !errors.Is(err, c.want) {
                t.Fatalf("err = %v, want %v (%s)", err, c.want, c.why)
            }
            if err != nil && !p.IsZero() {
                t.Fatalf("a dosage %s is returned with the error", p)
            }
        })
    }
}
```

Noter les trois premiers cas — « valide », « une prise », « six prises ». Ils ne
cherchent pas de bug : ils **figent les bornes comme atteignables**. Une prise
par jour est une prescription légitime, six aussi. Sans ces cas, un `<` glissé à
la place d'un `<=` passerait inaperçu.

Et le tableau des calculs, qui est la raison d'être du type entier :

```go
// TestComputationsAreExact is the reason for the integer type.
// The cases are chosen to be the ones a float64 gets wrong. 0.1 + 0.2 is not
// 0.3 in binary; neither is 2.5 x 3 x 7, as soon as a division is involved.
func TestComputationsAreExact(t *testing.T) {
    tc := []struct {
        name          string
        tenthsMg      int64
        intakes, days int
        dailyUg       int64
        totalUg       int64
    }{
        {"500 mg x 3 x 7", 5000, 3, 7, 1_500_000, 10_500_000},
        {"2,5 mg x 3 x 7", 25, 3, 7, 7_500, 52_500},
        {"0,1 mg x 3 x 1", 1, 3, 1, 300, 300},
        {"0,1 mg x 2 x 1", 1, 2, 1, 200, 200},
    }

    for _, c := range tc {
        t.Run(c.name, func(t *testing.T) {
            p, err := dosage.New(dosage.MustMilligrams(c.tenthsMg), c.intakes, c.days)
            if err != nil {
                t.Fatalf("New: %v", err)
            }
            j, err := p.Daily()
            if err != nil {
                t.Fatalf("Daily: %v", err)
            }
            if j.Micrograms() != c.dailyUg {
                t.Errorf("daily = %d ug, want %d", j.Micrograms(), c.dailyUg)
            }
            total, err := p.Total()
            if err != nil {
                t.Fatalf("Total: %v", err)
            }
            if total.Micrograms() != c.totalUg {
                t.Errorf("total = %d ug, want %d", total.Micrograms(), c.totalUg)
            }
        })
    }

    // The pure microgram case: levothyroxine, 25 ug once a day.
    dose, err := dosage.Micrograms(25)
    if err != nil {
        t.Fatalf("Micrograms: %v", err)
    }
    p, err := dosage.New(dose, 1, 90)
    if err != nil {
        t.Fatalf("New: %v", err)
    }
    total, err := p.Total()
    if err != nil {
        t.Fatalf("Total: %v", err)
    }
    if total.Micrograms() != 2250 {
        t.Fatalf("total = %d ug, want 2250", total.Micrograms())
    }
}
```

Les cas sont choisis pour être **ceux qu'un flottant rate** : 2,5 mg et 0,1 mg.
Le dernier bloc — 25 µg une fois par jour pendant 90 jours — est la
lévothyroxine, et il vérifie que l'unité la plus fine survit à la multiplication.

### Le relevé des huit modifications

| # | La modification | Qui crie |
|---|---|---|
| 1 | `MaxIntakes` passe de 6 à 7 | « sept prises » |
| 2 | la borne des prises devient stricte (`<=` au lieu de `<`) | « une prise » **et** le tableau des calculs |
| 3 | `Milligrams` convertit par 10 au lieu de 100 | **3 tests**, dans deux paquets |
| 4 | la dose nulle est acceptée | « dose nulle » |
| 5 | `Exceeds` devient `>=` | « pile sur le maximum » |
| 6 | `Total` oublie de multiplier par les jours | le tableau des calculs |
| 7 | `Daily` multiplie par les jours au lieu des prises | le tableau des calculs |
| 8 | `MaxDays` passe de 90 à 365 | « 91 jours » |

**Huit sur huit.** Aucune survivante — et il faut le dire sans se féliciter : ce
type est petit, entièrement pur, et sans dépendance. C'est le cas le plus
facile. Les survivantes apparaissent sur les types qui orchestrent, pas sur ceux
qui calculent.

Deux remarques sur le relevé.

**La n° 3 fait tomber trois tests dans deux paquets**, dont un test du `records`.
C'est la signature d'un type **utilisé** : quand il casse, il casse chez ses
appelants. Un type dont une modification ne fait tomber que ses propres tests est
un type que personne n'utilise.

**Les n° 6 et 7 sont attrapées par le même tableau**, et par les mêmes deux cas.
C'est le bénéfice d'avoir choisi `3 intakes × 7 days` plutôt que `1 × 1` : avec
`1 × 1`, les deux modifications seraient invisibles, parce que `×1` et `×1`
donnent le même résultat.

> Un cas de test où tous les facteurs valent 1 ne distingue aucun facteur.
> Choisis des nombres **différents et premiers entre eux** : 3 et 7 attrapent ce
> que 1 et 1 laissent passer.

## Question 7 — le compteur, et les types qui ne valaient pas le coup

Types créés uniquement pour remplacer une chaîne ou un nombre : **six**.

| Type | Remplace | Verdict |
|---|---|---|
| `Dose` | `float64` | **indispensable** — `NaN` passait la garde |
| `Phone` | `string` | **justifié** — une seule forme canonique, un seul SMS |
| `GroupeSanguin` | `string` | **justifié** — énumération fermée de huit valeurs, et une faute de saisie est refusée au lieu de devenir un groupe inconnu |
| `PatientID` | `int64` | **justifié de justesse** — voir ci-dessous |
| `VisitID`, `LineID` | `int64` | **justifiés par le même argument**, et c'est le même argument qui les justifie tous les trois ou aucun |
| `Allergies` comme type | `string` | **non fait, et c'est la bonne décision** |

### Les trois identifiants : un seul argument, et il est bon

Pris séparément, `type PatientID struct{ n int64 }` ressemble à de la cérémonie.
Pris ensemble, les trois empêchent **une faute précise** :

```
Prescribe(MustLineID(42), MustVisitID(42), "Amoxicilline", p)
```

Avec trois `int64`, inverser deux arguments compile et produit une ligne
rattachée à la mauvaise ordonnance. Avec trois types distincts, l'inversion ne
compile pas.

Le critère est donc : **y a-t-il, dans une signature du programme, deux
identifiants du même type côte à côte ?** Ici oui — `Prescribe` en prend deux, et
`Dispense(patientID, drug)` en prenait déjà deux dans le modèle d'origine.
S'il n'y en avait eu qu'un, les trois types seraient de la cérémonie.

### `Allergies` : pourquoi je m'arrête à `[]string`

L'allergie est **du texte libre écrit par un praticien**. Il n'y a pas
d'énumération fermée, pas de forme canonique, pas d'invariant — sauf « non
vide ». En faire un type n'apporterait rien et coûterait un constructeur à
chaque saisie.

Mais il y avait quelque chose à corriger quand même, et ce n'était pas le type :

```go
// TestAllergiesCannotBeChangedFromOutside guards lesson 1.1 on a
// type that looks immutable.
func TestAllergiesCannotBeChangedFromOutside(t *testing.T) {
    p, err := patient(t, 42).WithAllergy("penicillin")
    if err != nil {
        t.Fatalf("WithAllergy: %v", err)
    }

    read := p.Allergies()
    if len(read) != 1 || read[0] != "penicillin" {
        t.Fatalf("allergies = %v", read)
    }

    // The caller modifies what it received.
    read[0] = "none"

    if reread := p.Allergies(); reread[0] != "penicillin" {
        t.Fatalf("allergies = %v: the internal slice was modified from"+
            " outside, and the medical record now says \"none\"", reread)
    }
}
```

`Allergies()` rend une **copie**. Sans elle, l'appelant recevrait la tranche
interne et pourrait la modifier — et le dossier médical dirait « aucune ». C'est
la leçon 1.1 sur un type qui a l'air immuable, et c'est la vraie correction à
faire sur ce champ.

> Le réflexe « j'en fais un type » n'est pas la réponse à tout. Sur une tranche
> dans une entité, la question n'est pas le type de ses éléments : c'est **qui
> peut la modifier**.

### Et le type que je n'ai pas fait, à tort

`Practitioner` est une chaîne. Il devrait être une entité — il a une identité, un
numéro d'ordre, une spécialité, et il change de nom en se mariant comme tout le
monde. Je l'ai laissé en chaîne parce que l'énoncé n'en dit rien, et c'est une
**dette assumée** : le jour où le cabinet voudra la liste des consultations par
praticien, la chaîne « Dr Mbarga » et la chaîne « Dr. Mbarga » seront deux
praticiens.

// LineID is the identity of a prescription line.
// It is the fourth concept, the one the three comments of the original model
// did not name. A prescription has several lines; a line has
// its own life cycle: it is dispensed, or not. So an entity.
type LineID struct{ n int64 }

func NewLineID(n int64) (LineID, error) {
    if n <= 0 {
        return LineID{}, fmt.Errorf("%w: line id %d", ErrNoID, n)
    }
    return LineID{n: n}, nil
}

func MustLineID(n int64) LineID {
    i, err := NewLineID(n)
    if err != nil {
        panic(err)
    }
    return i
}

func (i LineID) IsZero() bool   { return i.n == 0 }
func (i LineID) String() string { return fmt.Sprintf("L%06d", i.n) }

// Line is an ENTITY: a drug, its dosage, and its dispensing
// state.
type Line struct {
    _ [0]func()

    id           LineID
    prescription VisitID
    drug         string
    dosage       dosage.Dosage
    dispensed    bool
    dispensedAt  time.Time
    built        bool
}

// Prescribe creates a line. It receives ONLY what concerns it: no more
// record of thirty fields, so no more way to overwrite a
// patient's data while prescribing.
func Prescribe(id LineID, prescription VisitID, drug string, p dosage.Dosage) (Line, error) {
    if id.IsZero() {
        return Line{}, ErrNoID
    }
    if prescription.IsZero() {
        return Line{}, fmt.Errorf("%w: prescription of line %s", ErrNoID, id)
    }
    if drug = strings.TrimSpace(drug); drug == "" {
        return Line{}, fmt.Errorf("%w: line %s", ErrNoDrug, id)
    }
    if p.IsZero() {
        return Line{}, fmt.Errorf("records: line %s without dosage", id)
    }
    return Line{
        id: id, prescription: prescription, drug: drug,
        dosage: p, built: true,
    }, nil
}

func (l Line) ID() LineID             { return l.id }
func (l Line) Prescription() VisitID  { return l.prescription }
func (l Line) Drug() string           { return l.drug }
func (l Line) Dosage() dosage.Dosage  { return l.dosage }
func (l Line) Dispensed() bool        { return l.dispensed }
func (l Line) SameAs(other Line) bool { return l.id == other.id }

// Dispense marks the line as dispensed.
//
// Here is the fix of the first bug: we dispense ONE LINE, given by its
// identity. Not "the first undispensed drug with this name". The original
// signature, Dispense(patientID, drug), could not do otherwise
// than guess, and it guessed wrong.
func (l Line) Dispense(when time.Time) (Line, error) {
    if err := l.exist(); err != nil {
        return l, err
    }
    if l.dispensed {
        return l, fmt.Errorf("%w: %s (%s)", ErrAlreadyDispensed, l.id, l.drug)
    }
    if when.IsZero() {
        return l, fmt.Errorf("%w: dispensing %s", ErrMissingDate, l.id)
    }
    l.dispensed = true
    l.dispensedAt = when
    return l, nil
}

// BelongsTo checks the link before any prescription operation.
func (l Line) BelongsTo(prescription VisitID) error {
    if err := l.exist(); err != nil {
        return err
    }
    if l.prescription != prescription {
        return fmt.Errorf("%w: %s belongs to %s, not to %s",
            ErrOtherPrescription, l.id, l.prescription, prescription)
    }
    return nil
}

func (l Line) exist() error {
    if !l.built {
        return ErrNotFound
    }
    return nil
}

func (l Line) String() string {
    state := "to dispense"
    if l.dispensed {
        state = "dispensed"
    }
    return fmt.Sprintf("%s: %s, %s (%s)", l.id, l.drug, l.dosage, state)
}

// TestPrescribeGetsOnlyWhatConcernsTheLine fixes the third bug.
// The original signature took a whole Record: prescribing for one patient
// allowed overwriting someone else's blood group. Here, Prescribe receives
// no patient, no blood group, no allergy. There is nothing to overwrite.
//
// It is a SIGNATURE test: it cannot fail at run time, it
// will fail to compile the day someone adds one parameter too many.
func TestPrescribeGetsOnlyWhatConcernsTheLine(t *testing.T) {
    p := patient(t, 42)
    group, err := records.ParseGroup("O+")
    if err != nil {
        t.Fatalf("ParseGroup: %v", err)
    }
    p, err = p.WithGroup(group)
    if err != nil {
        t.Fatalf("WithGroup: %v", err)
    }

    // Prescribe, then check that the patient is intact.
    _ = line(t, 1, 10, "Amoxicilline", 5000)

    if p.Group() != group {
        t.Fatalf("group = %s after a prescription", p.Group())

    if len(p.Allergies()) != 0 {
        t.Fatalf("allergies = %v", p.Allergies())
    }
}

Il ne peut pas échouer à l'exécution. Il échouera **à la compilation** le jour où
quelqu'un ajoutera un paramètre de trop à `Prescribe`. C'est le seul genre de
test qui garde un périmètre d'argument, et c'est aussi la raison pour laquelle le
bug n° 3 est devenu impossible : `Prescribe` ne reçoit ni patient, ni groupe
sanguin, ni allergie. **Il n'y a rien à écraser.**

## Ce que ça ne règle pas

**`Prescription` n'existe pas**, et c'est une dette nommée. Dès qu'une date de
validité, un nombre de renouvellements ou une signature apparaît, il faut
l'entité.

**Le lien entre une ligne et sa consultation est un `VisitID`**, pas une
référence. Rien ne garantit que la consultation existe. Cette garantie est une
contrainte de clé étrangère, donc un ⚫ côté base, et le modèle ne peut que la
supposer. Il faut l'écrire dans le contrat du dépôt plutôt que de l'espérer.

**L'invariant « on ne prescrit pas un médicament auquel le patient est
allergique » n'a pas de foyer.** Il porte sur le patient, la ligne et une base de
connaissance médicamenteuse. Même mécanique que le quota : la règle peut vivre
dans une fonction qui reçoit les trois, et sa clause `NON GARANTI` doit dire
qu'elle ne couvre que les allergies **déclarées**.

**`Dosage` ne connaît pas la voie d'administration.** 500 mg par voie orale et
500 mg en intraveineuse ne sont pas la même prescription. Le type est donc
incomplet pour un usage hospitalier, et il faut le savoir avant de le réutiliser.

**La couverture de `records` est de 65,1 %.** Les parties non couvertes sont les
constructeurs d'identifiants et les accesseurs. Je les laisse, pour la raison du
niveau 1 : les couvrir ajouterait des tests qui vérifient qu'un `return` rend ce
qu'on lui a donné.

## Ce qu'il faut retenir

1. **Cinq concepts dans un type, et le commentaire n'en annonçait que trois.**
   Celui qui manque est celui dont le métier a un mot et le code n'a pas de nom.
2. **Un concept sans représentation est réparti partout**, et chaque opération
   doit le reconstituer. C'est pour ça que les trois méthodes faisaient des
   boucles.
3. **Le périmètre d'un paramètre est le périmètre de ce qu'il peut détruire.**
   `Prescribe(f Record)` pouvait écraser un groupe sanguin.
4. **En flottant, une comparaison n'est pas une partition.** `NaN <= 0` est faux,
   donc la garde a un trou, donc une dose `NaN` était enregistrable.
5. **Une chose est une entité si et seulement si une opération peut la modifier
   en lui gardant son identité.** Sinon c'est une valeur ou un état.
6. **Si aucune opération ne modifie le candidat**, en faire une entité ajoute un
   identifiant, une table, une jointure et un cycle de vie pour rien.
7. **Des types d'identifiants distincts se justifient par une signature**, celle
   qui en prend deux côte à côte. Pas par principe.
8. **Un cas de test où tous les facteurs valent 1 ne distingue aucun facteur.**
   3 et 7 attrapent ce que 1 et 1 laissent passer.
9. **Une modification qui ne fait tomber que les tests de son propre paquet
   signale un type que personne n'utilise.**
10. **Sur une tranche dans une entité, la question n'est pas le type des
    éléments : c'est qui peut la modifier.**
11. **Un test de signature échoue à la compilation**, et c'est le seul genre de
    test qui garde un périmètre d'argument.
