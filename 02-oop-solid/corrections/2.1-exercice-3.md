# Correction 2.1 — Exercice 3 : refactoring

## Question 1 — combien de concepts dans `Fiche`

Les trois commentaires du code annoncent trois sections : patient, consultation,
ordonnance. **Il y en a cinq**, et le piège annoncé par l'énoncé est le
quatrième.

| Concept | Le mot du métier | Son identité | Les champs |
|---|---|---|---|
| **le patient** | « le patient », « le dossier » | un identifiant propre | `IDPatient`, `NomPatient`, `DateNais`, `Telephone`, `GroupeSang`, `Allergies` |
| **la consultation** | « la consultation », « la visite » | un identifiant propre | `DateConsult`, `Praticien`, `Motif` |
| **les constantes vitales** | « les constantes », « la tension » | aucune — elles appartiennent à la consultation | `TensionSys`, `TensionDia`, `PoidsKg` |
| **la ligne de prescription** | « la ligne », « le médicament prescrit » | un identifiant propre | `Medicament`, `DosageMg`, `ParJour`, `DureeJours`, `Renouvelable` |
| **la délivrance** | « la délivrance », « la dispensation » | aucune — elle appartient à la ligne | `Delivree`, `DelivreeLe` |

### Le quatrième, celui que les commentaires ratent

Le commentaire dit `// Ordonnance`. Mais les champs qu'il annonce
— `Medicament`, `DosageMg`, `ParJour`, `DureeJours` — ne décrivent **pas** une
ordonnance : ils décrivent **une ligne** d'ordonnance.

Une ordonnance porte trois médicaments. Dans ce modèle, elle n'existe pas : il y
a trois `Fiche` qui portent chacune un médicament et **répètent** le patient, la
consultation et les constantes. L'ordonnance comme document — celui que le
patient emporte, celui que le pharmacien lit, celui qui se renouvelle — n'a
aucune représentation.

> Quand un concept du métier n'a aucune représentation, il n'est pas « implicite ».
> Il est **réparti** dans toutes les lignes qui le mentionnent, et chaque
> opération doit le reconstituer. C'est pour ça que les trois méthodes du
> service font des boucles.

### Et les deux concepts sans identité propre

Les constantes vitales et la délivrance n'ont pas d'identité : elles
appartiennent entièrement à leur porteur. Ce sont donc des **valeurs** — ou, pour
la délivrance, un **état** de la ligne.

C'est utile à savoir pour la question 5, parce que c'est exactement là qu'on
fabrique des entités en trop.

## Question 2 — les trois bugs, racontés côté patient

### `Delivrer` — la mauvaise boîte

```
for _, f := range fiches {
    if f.Medicament == medicament && !f.Delivree {
        f.Delivree = true
```

La recherche se fait sur **le nom du médicament** et sur l'état *non délivré*.
Elle prend **la première** qui correspond.

> **Scénario patient.** Awa a reçu de l'amoxicilline 500 mg en janvier, et n'est
> jamais passée la chercher. En mars, le médecin lui prescrit de l'amoxicilline
> **250 mg** — dose réduite, parce qu'un bilan rénal est revenu anormal. Le
> pharmacien saisit « amoxicilline » et délivre. Le système clôt la ligne de
> **janvier**.
>
> Awa part avec une boîte de 500 mg. La ligne de mars reste ouverte, donc elle
> pourra revenir en chercher une autre. Et le dossier dit que la prescription de
> janvier a été honorée.

La cause n'est pas la boucle : c'est que **`Delivrer` ne reçoit pas d'identité de
ligne**, parce que les lignes n'ont pas d'identité. La signature ne pouvait que
deviner.

### `MettreAJourTelephone` — le SMS qui part à l'ancien numéro

```
for _, f := range fiches {
    f.Telephone = telephone
    if err := s.depot.Enregistrer(f); err != nil {
        return err
    }
}
```

Le téléphone est stocké sur **chaque** fiche. Le corriger est donc une boucle
d'écritures, et la boucle s'arrête au premier échec.

> **Scénario patient.** Boubacar a douze lignes dans son dossier — quatre
> consultations, trois médicaments chacune. Il change de numéro. L'écriture
> réussit pour les sept premières, puis la base bascule. Boubacar a maintenant
> **deux numéros de téléphone** dans son dossier.
>
> Le rappel de son rendez-vous part sur l'ancien. Il ne vient pas. On le note
> comme absent.

Et une seconde fois le même mécanisme qu'en 1.6 : **la cohérence est une
propriété de la boucle, pas du modèle.** Il n'existe aucun état de ce modèle où
« le téléphone du patient » soit une seule donnée.

### `Prescrire` — l'écrasement silencieux

```
func (s *Service) Prescrire(f Fiche) error {
    if f.DosageMg <= 0 || ... { return errors.New("posologie invalide") }
    return s.depot.Enregistrer(f)
}
```

`Prescrire` reçoit une **fiche entière** — trente champs — pour en valider trois
et en enregistrer trente.

> **Scénario patient.** L'interface du cabinet charge la fiche d'Awa pour
> afficher ses allergies, puis l'opérateur passe à la consultation de Boubacar
> sans que l'objet en mémoire soit rechargé. Il prescrit. La fiche enregistrée
> porte le médicament de Boubacar **et le groupe sanguin d'Awa**.
>
> Six mois plus tard, Boubacar arrive aux urgences. Son dossier dit O+. Il est
> A−.

C'est le bug le plus grave des trois, et il n'est pas détectable : les deux
valeurs sont valides, aucune contrainte n'est violée, et il n'y a pas de trace.

> Une fonction qui reçoit plus de données qu'elle n'en a besoin ne se contente
> pas d'être imprécise : elle **enregistre** tout ce qu'elle a reçu. Le périmètre
> d'un paramètre est le périmètre de ce qu'il peut détruire.

### Et le quatrième, que l'énoncé ne demandait pas

`Prescrire` valide la posologie. **Et c'est le seul endroit.** Un import, une
reprise de données, un autre service, un `UPDATE` SQL : tous contournent la
validation. L'invariant *« une posologie est positive »* n'a pas d'adresse, c'est
la question 6 de l'exercice 1 sous un autre nom.

## Question 3 — `DoseJournaliere`

```
func DoseJournaliere(f Fiche) float64 { return f.DosageMg * float64(f.ParJour) }
```

### Sur quel concept porte-t-elle vraiment

Sur la **posologie**, et sur rien d'autre. Elle prend trente champs pour en lire
deux. La bonne signature est une méthode :

```
func (p Posologie) Journaliere() (Dose, error)
```

C'est le critère de la leçon : *une méthode existe pour préserver un invariant*.
Ici, elle calcule — mais elle calcule sur un type dont les trois champs ont été
validés ensemble, et c'est ce qui la rend sûre.

### Ce que `float64` autorise qu'une posologie interdit

| Ce que `float64` permet | Pourquoi c'est inacceptable ici |
|---|---|
| `NaN` | une dose « non définie » qui passe tous les tests `> 0` — car `NaN > 0` est **faux**, donc la garde `DosageMg <= 0` est **aussi** fausse, et `NaN` passe |
| `+Inf` | une dose infinie |
| `-0.0` | une dose négative qui n'est pas `< 0` |
| `0.1 + 0.2 = 0.30000000000000004` | une dose de 0,3 mg qui n'est pas égale à 0,3 mg |
| `2.5 * 3 = 7.5` puis `/3 = 2.4999999999999996` | une dose qui dérive à chaque calcul |

La première ligne est la plus grave et la moins connue. Relis la garde du
service :

```
if f.DosageMg <= 0 || f.ParJour <= 0 || f.DureeJours <= 0 {
```

Si `DosageMg` vaut `NaN`, alors `NaN <= 0` rend **faux**. La garde ne déclenche
pas. **Une prescription de `NaN` milligrammes est enregistrée.**

> En flottant, une comparaison n'est pas une partition. `x <= 0` et `x > 0`
> peuvent être faux tous les deux, et toute garde écrite avec un seul des deux
> a un trou.

### La réponse

Un entier, en microgrammes. C'est l'unité la plus fine utilisée en prescription
— la lévothyroxine se prescrit en microgrammes — et `int64` en microgrammes
couvre jusqu'à neuf mille tonnes : la borne n'est pas le problème.

```go
// Bornes de la posologie. Elles sont ici, une fois, et nulle part ailleurs.
const (
    PrisesMin = 1
    PrisesMax = 6
    JoursMin  = 1
    JoursMax  = 90
)

// Dose est une quantite de principe actif, en MICROGRAMMES entiers.
//
// Pas de float64, et c'est la decision la plus importante de ce fichier. Un
// float64 autorise NaN, +Inf, -0, 0,1 + 0,2 = 0,30000000000000004, et une dose
// de 2,5 mg qui devient 2,4999999999999996 au troisieme calcul. En medecine, la
// precision n'est pas une preference.
//
// Le microgramme est l'unite la plus fine utilisee en prescription — la
// levothyroxine se prescrit en microgrammes. Int64 en microgrammes couvre
// jusqu'a neuf mille tonnes : la borne n'est pas le probleme.
type Dose struct {
    ug int64
}

// Microgrammes construit une dose.
func Microgrammes(ug int64) (Dose, error) {
    if ug < 0 {
        return Dose{}, fmt.Errorf("%w : %d ug", ErrDoseNegative, ug)
    }
    return Dose{ug: ug}, nil
}

// Milligrammes construit une dose a partir de milligrammes exprimes en
// dixiemes — 25 veut dire 2,5 mg.
//
// Deux constructeurs plutot qu'un, parce que les deux unites arrivent
// vraiment : les ordonnances parlent en milligrammes, les notices en
// microgrammes. Convertir au mauvais endroit est une erreur de facteur mille.
func Milligrammes(dixiemes int64) (Dose, error) {
    if dixiemes < 0 {
        return Dose{}, fmt.Errorf("%w : %d dixiemes de mg", ErrDoseNegative, dixiemes)
    }
    return Dose{ug: dixiemes * 100}, nil
}

func MustMilligrammes(dixiemes int64) Dose {
    d, err := Milligrammes(dixiemes)
    if err != nil {
        panic(err)
    }
    return d
}

func (d Dose) Microgrammes() int64 { return d.ug }
func (d Dose) EstNulle() bool      { return d.ug == 0 }

// Fois multiplie la dose. Rend une erreur plutot qu'un resultat faux.
func (d Dose) Fois(n int) (Dose, error) {
    if n < 0 {
        return Dose{}, fmt.Errorf("%w : x%d", ErrDoseNegative, n)
    }
    if n != 0 && d.ug > (1<<62)/int64(n) {
        return Dose{}, fmt.Errorf("%w : %d ug x %d", ErrDoseNonRepresentable, d.ug, n)
    }
    return Dose{ug: d.ug * int64(n)}, nil
}

func (d Dose) Depasse(autre Dose) bool { return d.ug > autre.ug }

// String affiche en milligrammes quand c'est lisible, en microgrammes sinon.
// Une seule forme par dose, pour qu'un journal soit comparable a un autre.
func (d Dose) String() string {
    if d.ug%1000 == 0 && d.ug != 0 {
        return strconv.FormatInt(d.ug/1000, 10) + " mg"
    }
    if d.ug%100 == 0 && d.ug != 0 {
        return strconv.FormatInt(d.ug/1000, 10) + "," + strconv.FormatInt((d.ug%1000)/100, 10) + " mg"
    }
    return strconv.FormatInt(d.ug, 10) + " ug"
}
```

Noter les **deux constructeurs**. Les ordonnances parlent en milligrammes, les
notices en microgrammes, et les deux arrivent. Convertir au mauvais endroit est
une erreur de facteur mille — en médecine, c'est un facteur mille sur une dose.
Un test garde la jonction :

```go
// TestLesDeuxUnitesSeRejoignent garde la decision des deux constructeurs : une
// erreur de facteur mille serait silencieuse avec un seul.
func TestLesDeuxUnitesSeRejoignent(t *testing.T) {
    parMg := posologie.MustMilligrammes(25)    // 2,5 mg
    parUg, err := posologie.Microgrammes(2500) // 2 500 ug
    if err != nil {
        t.Fatalf("Microgrammes : %v", err)
    }
    if parMg != parUg {
        t.Fatalf("2,5 mg = %s mais 2500 ug = %s", parMg, parUg)
    }
    if parMg.Microgrammes() != 2500 {
        t.Fatalf("Microgrammes() = %d", parMg.Microgrammes())
    }
}
```

## Question 4 — la découpe

### Les valeurs

| Type | Identité | Invariants | Raison de changer |
|---|---|---|---|
| `Dose` | aucune — valeur | positive, en microgrammes entiers | la liste des unités utilisées en prescription |
| `Posologie` | aucune — valeur | dose non nulle, 1 à 6 prises, 1 à 90 jours | les bornes réglementaires de prescription |
| `Telephone` | aucune — valeur | neuf chiffres, une seule forme canonique | le plan de numérotation de l'opérateur |
| `GroupeSanguin` | aucune — valeur | huit valeurs, pas une neuvième | rien : la biologie ne change pas |
| `IDPatient`, `IDConsultation`, `IDLigne` | aucune — valeurs | strictement positives | la politique d'attribution des identifiants |

### Les entités

| Type | Identité | Invariants | Raison de changer |
|---|---|---|---|
| `Patient` | `IDPatient` | nom non vide, naissance renseignée, allergies non modifiables de l'extérieur | ce que l'administration du cabinet doit connaître d'une personne |
| `Consultation` | `IDConsultation` | patient et praticien désignés, date renseignée | ce qu'une visite doit tracer |
| `Ligne` | `IDLigne` | médicament nommé, posologie non nulle, délivrable une seule fois, rattachée à une ordonnance et à une seule | la règle de dispensation |

### Le type qui n'est pas dans la liste

`Ordonnance` manque, et c'est volontaire. Dans cette correction, une ligne porte
l'identifiant de sa consultation, et l'ordonnance est l'ensemble des lignes d'une
consultation.

C'est un **choix contestable**, et il faut dire pourquoi plutôt que de le cacher :
une ordonnance a des attributs propres dans la vraie vie — une date de validité,
un nombre de renouvellements, une signature. Dès que l'un des trois est demandé,
`Ordonnance` devient une entité à part entière. Je ne l'ai pas créée parce
qu'aucun des trois n'apparaît dans l'énoncé, et créer une entité pour un concept
dont on ne sait rien, c'est le piège de la question 5.

### Le code de la posologie, en entier

```go
// Posologie est « combien, combien de fois, pendant combien de temps ».
//
// Les trois champs ensemble, parce qu'ils changent ensemble : personne ne
// modifie le nombre de prises sans reconsiderer la dose. Separes, ils
// permettraient une posologie a moitie modifiee.
type Posologie struct {
    dose   Dose
    prises int
    jours  int
}

// Nouvelle construit une posologie valide, ou rien.
func Nouvelle(d Dose, prises, jours int) (Posologie, error) {
    if d.EstNulle() {
        return Posologie{}, ErrDoseNulle
    }
    if prises < PrisesMin || prises > PrisesMax {
        return Posologie{}, fmt.Errorf("%w : %d prises (attendu %d a %d)",
            ErrPrisesInvalides, prises, PrisesMin, PrisesMax)
    }
    if jours < JoursMin || jours > JoursMax {
        return Posologie{}, fmt.Errorf("%w : %d jours (attendu %d a %d)",
            ErrDureeInvalide, jours, JoursMin, JoursMax)
    }
    return Posologie{dose: d, prises: prises, jours: jours}, nil
}

func (p Posologie) Dose() Dose  { return p.dose }
func (p Posologie) Prises() int { return p.prises }
func (p Posologie) Jours() int  { return p.jours }

// EstNulle distingue la valeur zero d'une posologie reelle. La valeur zero de
// ce type N'EST PAS un etat valide — « 0 mg, 0 fois par jour, pendant 0 jour »
// n'est pas une prescription legere, c'est l'absence de prescription.
func (p Posologie) EstNulle() bool { return p == Posologie{} }

// Journaliere est la question que l'exercice posait : c'est une methode de la
// POSOLOGIE, pas une fonction qui prend une fiche entiere.
//
// La signature d'origine, DoseJournaliere(f Fiche) float64, prenait trente
// champs pour en lire deux, et rendait un type qui autorise NaN.
func (p Posologie) Journaliere() (Dose, error) {
    if p.EstNulle() {
        return Dose{}, ErrDoseNulle
    }
    return p.dose.Fois(p.prises)
}

// Totale est la quantite a delivrer. C'est elle que le pharmacien lit.
func (p Posologie) Totale() (Dose, error) {
    journaliere, err := p.Journaliere()
    if err != nil {
        return Dose{}, err
    }
    return journaliere.Fois(p.jours)
}

// VerifierContre compare la dose journaliere au maximum du medicament.
//
// Le maximum est un ARGUMENT, pas un champ : il appartient au medicament, pas a
// la posologie. Meme mecanique que le quota de la lecon — la regle est ici, la
// donnee descend.
//
// NON GARANTI : que la posologie soit adaptee au patient. L'age, le poids, la
// fonction renale et les interactions ne sont pas ici, et aucun type ne les
// remplacera. Cette methode verifie une borne ; elle ne prescrit pas.
func (p Posologie) VerifierContre(maxJournalier Dose) error {
    journaliere, err := p.Journaliere()
    if err != nil {
        return err
    }
    if journaliere.Depasse(maxJournalier) {
        return fmt.Errorf("%w : %s par jour pour un maximum de %s",
            ErrDoseJournaliereDepassee, journaliere, maxJournalier)
    }
    return nil
}

func (p Posologie) String() string {
    if p.EstNulle() {
        return "posologie nulle"
    }
    return fmt.Sprintf("%s, %d fois par jour, pendant %d jours", p.dose, p.prises, p.jours)
}
```

Deux points.

**Les trois champs sont ensemble parce qu'ils changent ensemble.** Personne ne
modifie le nombre de prises sans reconsidérer la dose. Séparés, ils
permettraient une posologie à moitié modifiée.

**`VerifierContre` reçoit le maximum en argument.** Le maximum journalier
appartient au **médicament**, pas à la posologie. Même mécanique que le quota de
la leçon et que le cumulé de l'exercice 2 : la règle est ici, la donnée descend.

Et la clause `NON GARANTI` dit ce qu'aucun type ne remplacera :

> Que la posologie soit adaptée **au patient**. L'âge, le poids, la fonction
> rénale et les interactions ne sont pas ici. Cette méthode vérifie une borne ;
> elle ne prescrit pas.

## Question 5 — les deux pièges

### Celui que j'ai rencontré : trop de types

J'ai failli faire une entité de la **délivrance**. Elle a une date, elle a un
état, elle a un agent qui la réalise — tout pour ressembler à une entité.

Elle n'en est pas une, et le test de la leçon le dit en dix secondes : *si je
change un champ de la délivrance, est-ce toujours la même délivrance ?* La
question n'a pas de sens, parce qu'une délivrance **n'a pas de cycle de vie
propre** : elle arrive une fois, et elle ne change plus. C'est un **état** de la
ligne, pas une chose.

### Le critère qui tranche, et il ne tient pas en « ça dépend »

> Une chose est une entité si et seulement si elle peut **changer en gardant son
> identité**. Autrement dit : s'il existe au moins une opération qui la modifie
> et après laquelle on dit encore *« c'est la même »*.

Applique-le :

| Candidat | Une opération qui le modifie ? | Verdict |
|---|---|---|
| `Patient` | corriger le téléphone, ajouter une allergie | **entité** |
| `Consultation` | corriger la date, corriger le motif | **entité** |
| `Ligne` | la délivrer | **entité** |
| la délivrance | aucune — elle est, ou elle n'est pas | **état**, pas entité |
| les constantes vitales | aucune — on ne corrige pas une tension passée, on en relève une autre | **valeur** |
| `Posologie` | aucune — on en prescrit une autre | **valeur** |

Le critère marche aussi à l'envers, et c'est là qu'il est le plus utile : **si
aucune opération ne modifie le candidat, en faire une entité ajoute un
identifiant, une table, une jointure et un cycle de vie — pour rien.**

### Et l'autre piège, qu'il faut savoir repérer chez soi

**Trop peu de types** : garder le patient et la consultation ensemble, parce que
« de toute façon une consultation appartient à un patient ». C'est le modèle
d'origine, et la conséquence est le bug n° 3 — prescrire écrase le groupe
sanguin.

Le test est le même, lu dans l'autre sens : les deux ont-ils **la même
identité** ? Un patient a quatre consultations. Donc non. Donc deux types.

## Question 6 — le type le plus chargé, et sa campagne

`Posologie` porte le plus d'invariants : six, dont trois bornes et un calcul.
Ses tests :

```go
func TestNouvelleRefuseCeQueLaMedecineRefuse(t *testing.T) {
    cinqCents := posologie.MustMilligrammes(5000) // 500,0 mg

    cas := []struct {
        nom      string
        dose     posologie.Dose
        prises   int
        jours    int
        attendu  error
        pourquoi string
    }{
        {"valide", cinqCents, 3, 7, nil, ""},
        {"une prise", cinqCents, 1, 1, nil, "le minimum est une prescription legitime"},
        {"six prises", cinqCents, 6, 90, nil, "les deux bornes hautes sont atteignables"},
        {"dose nulle", posologie.Dose{}, 3, 7, posologie.ErrDoseNulle,
            "0 mg n'est pas une prescription legere, c'est l'absence de prescription"},
        {"zero prise", cinqCents, 0, 7, posologie.ErrPrisesInvalides,
            "un medicament qu'on ne prend pas n'a pas de posologie"},
        {"sept prises", cinqCents, 7, 7, posologie.ErrPrisesInvalides, "au-dela de la borne"},
        {"zero jour", cinqCents, 3, 0, posologie.ErrDureeInvalide, ""},
        {"91 jours", cinqCents, 3, 91, posologie.ErrDureeInvalide,
            "au-dela de 90 jours, c'est un traitement de fond, pas une ordonnance"},
        {"prises negatives", cinqCents, -1, 7, posologie.ErrPrisesInvalides, ""},
    }

    for _, c := range cas {
        t.Run(c.nom, func(t *testing.T) {
            p, err := posologie.Nouvelle(c.dose, c.prises, c.jours)
            if !errors.Is(err, c.attendu) {
                t.Fatalf("err = %v, attendu %v (%s)", err, c.attendu, c.pourquoi)
            }
            if err != nil && !p.EstNulle() {
                t.Fatalf("une posologie %s est rendue avec l'erreur", p)
            }
        })
    }
}
```

Noter les trois premiers cas — « valide », « une prise », « six prises ». Ils ne
cherchent pas de bug : ils **figent les bornes comme atteignables**. Une prise
par jour est une prescription légitime, six aussi. Sans ces cas, un `<` glissé à
la place d'un `<=` passerait inaperçu.

Et le tableau des calculs, qui est la raison d'être du type entier :

```go
// TestLesCalculsSontExacts est la raison d'etre du type entier.
//
// Les cas sont choisis pour etre ceux qu'un float64 rate. 0,1 + 0,2 n'est pas
// 0,3 en binaire ; 2,5 x 3 x 7 non plus, des qu'on passe par une division.
func TestLesCalculsSontExacts(t *testing.T) {
    cas := []struct {
        nom           string
        dixiemesMg    int64
        prises, jours int
        journaliereUg int64
        totaleUg      int64
    }{
        {"500 mg x 3 x 7", 5000, 3, 7, 1_500_000, 10_500_000},
        {"2,5 mg x 3 x 7", 25, 3, 7, 7_500, 52_500},
        {"0,1 mg x 3 x 1", 1, 3, 1, 300, 300},
        {"0,1 mg x 2 x 1", 1, 2, 1, 200, 200},
    }

    for _, c := range cas {
        t.Run(c.nom, func(t *testing.T) {
            p, err := posologie.Nouvelle(posologie.MustMilligrammes(c.dixiemesMg), c.prises, c.jours)
            if err != nil {
                t.Fatalf("Nouvelle : %v", err)
            }
            j, err := p.Journaliere()
            if err != nil {
                t.Fatalf("Journaliere : %v", err)
            }
            if j.Microgrammes() != c.journaliereUg {
                t.Errorf("journaliere = %d ug, attendu %d", j.Microgrammes(), c.journaliereUg)
            }
            total, err := p.Totale()
            if err != nil {
                t.Fatalf("Totale : %v", err)
            }
            if total.Microgrammes() != c.totaleUg {
                t.Errorf("totale = %d ug, attendu %d", total.Microgrammes(), c.totaleUg)
            }
        })
    }

    // Le cas des microgrammes purs : la levothyroxine, 25 ug une fois par jour.
    dose, err := posologie.Microgrammes(25)
    if err != nil {
        t.Fatalf("Microgrammes : %v", err)
    }
    p, err := posologie.Nouvelle(dose, 1, 90)
    if err != nil {
        t.Fatalf("Nouvelle : %v", err)
    }
    total, err := p.Totale()
    if err != nil {
        t.Fatalf("Totale : %v", err)
    }
    if total.Microgrammes() != 2250 {
        t.Fatalf("totale = %d ug, attendu 2250", total.Microgrammes())
    }
}
```

Les cas sont choisis pour être **ceux qu'un flottant rate** : 2,5 mg et 0,1 mg.
Le dernier bloc — 25 µg une fois par jour pendant 90 jours — est la
lévothyroxine, et il vérifie que l'unité la plus fine survit à la multiplication.

### Le relevé des huit modifications

| # | La modification | Qui crie |
|---|---|---|
| 1 | `PrisesMax` passe de 6 à 7 | « sept prises » |
| 2 | la borne des prises devient stricte (`<=` au lieu de `<`) | « une prise » **et** le tableau des calculs |
| 3 | `Milligrammes` convertit par 10 au lieu de 100 | **3 tests**, dans deux paquets |
| 4 | la dose nulle est acceptée | « dose nulle » |
| 5 | `Depasse` devient `>=` | « pile sur le maximum » |
| 6 | `Totale` oublie de multiplier par les jours | le tableau des calculs |
| 7 | `Journaliere` multiplie par les jours au lieu des prises | le tableau des calculs |
| 8 | `JoursMax` passe de 90 à 365 | « 91 jours » |

**Huit sur huit.** Aucune survivante — et il faut le dire sans se féliciter : ce
type est petit, entièrement pur, et sans dépendance. C'est le cas le plus
facile. Les survivantes apparaissent sur les types qui orchestrent, pas sur ceux
qui calculent.

Deux remarques sur le relevé.

**La n° 3 fait tomber trois tests dans deux paquets**, dont un test du `dossier`.
C'est la signature d'un type **utilisé** : quand il casse, il casse chez ses
appelants. Un type dont une modification ne fait tomber que ses propres tests est
un type que personne n'utilise.

**Les n° 6 et 7 sont attrapées par le même tableau**, et par les mêmes deux cas.
C'est le bénéfice d'avoir choisi `3 prises × 7 jours` plutôt que `1 × 1` : avec
`1 × 1`, les deux modifications seraient invisibles, parce que `×1` et `×1`
donnent le même résultat.

> Un cas de test où tous les facteurs valent 1 ne distingue aucun facteur.
> Choisis des nombres **différents et premiers entre eux** : 3 et 7 attrapent ce
> que 1 et 1 laissent passer.

## Question 7 — le compteur, et les types qui ne valaient pas le coup

Types créés uniquement pour remplacer une chaîne ou un nombre : **six**.

| Type | Remplace | Verdict |
|---|---|---|
| `Dose` | `float64` | **indispensable** — `NaN` passait la garde |
| `Telephone` | `string` | **justifié** — une seule forme canonique, un seul SMS |
| `GroupeSanguin` | `string` | **justifié** — énumération fermée de huit valeurs, et une faute de saisie est refusée au lieu de devenir un groupe inconnu |
| `IDPatient` | `int64` | **justifié de justesse** — voir ci-dessous |
| `IDConsultation`, `IDLigne` | `int64` | **justifiés par le même argument**, et c'est le même argument qui les justifie tous les trois ou aucun |
| `Allergies` comme type | `string` | **non fait, et c'est la bonne décision** |

### Les trois identifiants : un seul argument, et il est bon

Pris séparément, `type IDPatient struct{ n int64 }` ressemble à de la cérémonie.
Pris ensemble, les trois empêchent **une faute précise** :

```
Prescrire(MustIDLigne(42), MustIDConsultation(42), "Amoxicilline", p)
```

Avec trois `int64`, inverser deux arguments compile et produit une ligne
rattachée à la mauvaise ordonnance. Avec trois types distincts, l'inversion ne
compile pas.

Le critère est donc : **y a-t-il, dans une signature du programme, deux
identifiants du même type côte à côte ?** Ici oui — `Prescrire` en prend deux, et
`Delivrer(idPatient, medicament)` en prenait déjà deux dans le modèle d'origine.
S'il n'y en avait eu qu'un, les trois types seraient de la cérémonie.

### `Allergies` : pourquoi je m'arrête à `[]string`

L'allergie est **du texte libre écrit par un praticien**. Il n'y a pas
d'énumération fermée, pas de forme canonique, pas d'invariant — sauf « non
vide ». En faire un type n'apporterait rien et coûterait un constructeur à
chaque saisie.

Mais il y avait quelque chose à corriger quand même, et ce n'était pas le type :

```go
// TestLesAllergiesNeSontPasModifiablesDeLExterieur garde la lecon 1.1 sur un
// type qui a l'air immuable.
func TestLesAllergiesNeSontPasModifiablesDeLExterieur(t *testing.T) {
    p, err := patient(t, 42).AvecAllergie("penicilline")
    if err != nil {
        t.Fatalf("AvecAllergie : %v", err)
    }

    lues := p.Allergies()
    if len(lues) != 1 || lues[0] != "penicilline" {
        t.Fatalf("allergies = %v", lues)
    }

    // L'appelant modifie ce qu'il a recu.
    lues[0] = "aucune"

    if relues := p.Allergies(); relues[0] != "penicilline" {
        t.Fatalf("allergies = %v : la tranche interne a ete modifiee de"+
            " l'exterieur, et le dossier medical dit maintenant « aucune »", relues)
    }
}
```

`Allergies()` rend une **copie**. Sans elle, l'appelant recevrait la tranche
interne et pourrait la modifier — et le dossier médical dirait « aucune ». C'est
la leçon 1.1 sur un type qui a l'air immuable, et c'est la vraie correction à
faire sur ce champ.

> Le réflexe « j'en fais un type » n'est pas la réponse à tout. Sur une tranche
> dans une entité, la question n'est pas le type de ses éléments : c'est **qui
> peut la modifier**.

### Et le type que je n'ai pas fait, à tort

`Praticien` est une chaîne. Il devrait être une entité — il a une identité, un
numéro d'ordre, une spécialité, et il change de nom en se mariant comme tout le
monde. Je l'ai laissé en chaîne parce que l'énoncé n'en dit rien, et c'est une
**dette assumée** : le jour où le cabinet voudra la liste des consultations par
praticien, la chaîne « Dr Mbarga » et la chaîne « Dr. Mbarga » seront deux
praticiens.

## La découpe, en code

```go
// Package dossier porte les entites du cabinet.
//
// Quatre entites, et le metier avait un mot pour chacune. Le modele d'origine
// n'en avait qu'un, « fiche », qui n'est le mot de personne.
package dossier

import (
    "errors"
    "fmt"
    "strings"
    "time"

    "exemple/cabinet/posologie"
)

var (
    ErrSansIdentifiant = errors.New("dossier : identifiant absent")
    ErrSansNom         = errors.New("dossier : nom absent")
    ErrSansPraticien   = errors.New("dossier : praticien absent")
    ErrSansMedicament  = errors.New("dossier : medicament absent")
    ErrDateAbsente     = errors.New("dossier : date absente")
    ErrDejaDelivree    = errors.New("dossier : ligne deja delivree")
    ErrInexistant      = errors.New("dossier : non construit")
    // ErrAutreOrdonnance : la ligne n'appartient pas a cette ordonnance. C'est
    // le bug de Delivrer, devenu impossible a ignorer.
    ErrAutreOrdonnance = errors.New("dossier : la ligne appartient a une autre ordonnance")
)
```

Les deux corrections qui comptent :

```go
// IDLigne est l'identite d'une ligne de prescription.
//
// C'est le quatrieme concept, celui que les trois commentaires du modele
// d'origine ne nommaient pas. Une ordonnance a plusieurs lignes ; une ligne a
// un cycle de vie propre — elle est delivree, ou pas. Donc une entite.
type IDLigne struct{ n int64 }

func NouvelIDLigne(n int64) (IDLigne, error) {
    if n <= 0 {
        return IDLigne{}, fmt.Errorf("%w : id ligne %d", ErrSansIdentifiant, n)
    }
    return IDLigne{n: n}, nil
}

func MustIDLigne(n int64) IDLigne {
    i, err := NouvelIDLigne(n)
    if err != nil {
        panic(err)
    }
    return i
}

func (i IDLigne) EstNul() bool   { return i.n == 0 }
func (i IDLigne) String() string { return fmt.Sprintf("L%06d", i.n) }

// Ligne est une ENTITE : un medicament, sa posologie, et son etat de
// delivrance.
type Ligne struct {
    _ [0]func()

    id         IDLigne
    ordonnance IDConsultation
    medicament string
    posologie  posologie.Posologie
    delivree   bool
    delivreeLe time.Time
    construit  bool
}

// Prescrire cree une ligne. Elle ne recoit QUE ce qui la concerne : plus de
// fiche de trente champs, donc plus de possibilite d'ecraser les donnees d'un
// patient en prescrivant.
func Prescrire(id IDLigne, ordonnance IDConsultation, medicament string, p posologie.Posologie) (Ligne, error) {
    if id.EstNul() {
        return Ligne{}, ErrSansIdentifiant
    }
    if ordonnance.EstNul() {
        return Ligne{}, fmt.Errorf("%w : ordonnance de la ligne %s", ErrSansIdentifiant, id)
    }
    if medicament = strings.TrimSpace(medicament); medicament == "" {
        return Ligne{}, fmt.Errorf("%w : ligne %s", ErrSansMedicament, id)
    }
    if p.EstNulle() {
        return Ligne{}, fmt.Errorf("dossier : ligne %s sans posologie", id)
    }
    return Ligne{
        id: id, ordonnance: ordonnance, medicament: medicament,
        posologie: p, construit: true,
    }, nil
}

func (l Ligne) ID() IDLigne                    { return l.id }
func (l Ligne) Ordonnance() IDConsultation     { return l.ordonnance }
func (l Ligne) Medicament() string             { return l.medicament }
func (l Ligne) Posologie() posologie.Posologie { return l.posologie }
func (l Ligne) Delivree() bool                 { return l.delivree }
func (l Ligne) MemeQue(autre Ligne) bool       { return l.id == autre.id }

// Delivrer marque la ligne comme delivree.
//
// Voila la correction du premier bug : on delivre UNE LIGNE, designee par son
// identite. Pas « le premier medicament de ce nom non delivre ». La signature
// d'origine, Delivrer(idPatient, medicament), ne pouvait pas faire autrement
// que de deviner — et elle devinait mal.
func (l Ligne) Delivrer(quand time.Time) (Ligne, error) {
    if err := l.exister(); err != nil {
        return l, err
    }
    if l.delivree {
        return l, fmt.Errorf("%w : %s (%s)", ErrDejaDelivree, l.id, l.medicament)
    }
    if quand.IsZero() {
        return l, fmt.Errorf("%w : delivrance de %s", ErrDateAbsente, l.id)
    }
    l.delivree = true
    l.delivreeLe = quand
    return l, nil
}

// AppartientA verifie le rattachement avant toute operation d'ordonnance.
func (l Ligne) AppartientA(ordonnance IDConsultation) error {
    if err := l.exister(); err != nil {
        return err
    }
    if l.ordonnance != ordonnance {
        return fmt.Errorf("%w : %s est rattachee a %s, pas a %s",
            ErrAutreOrdonnance, l.id, l.ordonnance, ordonnance)
    }
    return nil
}

func (l Ligne) exister() error {
    if !l.construit {
        return ErrInexistant
    }
    return nil
}

func (l Ligne) String() string {
    etat := "a delivrer"
    if l.delivree {
        etat = "delivree"
    }
    return fmt.Sprintf("%s : %s, %s (%s)", l.id, l.medicament, l.posologie, etat)
}
```

// TestDelivrerDesigneUneLigneEtPasUnNomDeMedicament corrige le premier bug.

// Deux lignes du meme medicament, deux posologies differentes, deux
// ordonnances differentes — la situation exacte qui faisait delivrer la
// mauvaise boite. Ici, chaque ligne se delivre separement, et la seconde reste

Et la troisième, qui est un test de **signature** :

```go
// TestPrescrireNeRecoitQueCeQuiConcerneLaLigne corrige le troisieme bug.
//
// La signature d'origine prenait une Fiche entiere : prescrire pour un patient
// permettait d'ecraser le groupe sanguin d'un autre. Ici, Prescrire ne recoit
// ni patient, ni groupe sanguin, ni allergie. Il n'y a rien a ecraser.
//
// C'est un test de SIGNATURE : il ne peut pas echouer a l'execution, il
// echouera a la compilation le jour ou quelqu'un ajoutera un parametre de trop.
func TestPrescrireNeRecoitQueCeQuiConcerneLaLigne(t *testing.T) {
    p := patient(t, 42)
    groupe, err := dossier.AnalyserGroupe("O+")
    if err != nil {
        t.Fatalf("AnalyserGroupe : %v", err)
    }
    p, err = p.AvecGroupe(groupe)
    if err != nil {
        t.Fatalf("AvecGroupe : %v", err)
    }

    // Prescrire, puis verifier que le patient est intact.
    _ = ligne(t, 1, 10, "Amoxicilline", 5000)

    if p.Groupe() != groupe {
        t.Fatalf("groupe = %s apres une prescription", p.Groupe())
    }
    if len(p.Allergies()) != 0 {
        t.Fatalf("allergies = %v", p.Allergies())
    }
}
```

Il ne peut pas échouer à l'exécution. Il échouera **à la compilation** le jour où
quelqu'un ajoutera un paramètre de trop à `Prescrire`. C'est le seul genre de
test qui garde un périmètre d'argument, et c'est aussi la raison pour laquelle le
bug n° 3 est devenu impossible : `Prescrire` ne reçoit ni patient, ni groupe
sanguin, ni allergie. **Il n'y a rien à écraser.**

## Ce que ça ne règle pas

**`Ordonnance` n'existe pas**, et c'est une dette nommée. Dès qu'une date de
validité, un nombre de renouvellements ou une signature apparaît, il faut
l'entité.

**Le lien entre une ligne et sa consultation est un `IDConsultation`**, pas une
référence. Rien ne garantit que la consultation existe. Cette garantie est une
contrainte de clé étrangère, donc un ⚫ côté base, et le modèle ne peut que la
supposer. Il faut l'écrire dans le contrat du dépôt plutôt que de l'espérer.

**L'invariant « on ne prescrit pas un médicament auquel le patient est
allergique » n'a pas de foyer.** Il porte sur le patient, la ligne et une base de
connaissance médicamenteuse. Même mécanique que le quota : la règle peut vivre
dans une fonction qui reçoit les trois, et sa clause `NON GARANTI` doit dire
qu'elle ne couvre que les allergies **déclarées**.

**`Posologie` ne connaît pas la voie d'administration.** 500 mg par voie orale et
500 mg en intraveineuse ne sont pas la même prescription. Le type est donc
incomplet pour un usage hospitalier, et il faut le savoir avant de le réutiliser.

**La couverture de `dossier` est de 65,1 %.** Les parties non couvertes sont les
constructeurs d'identifiants et les accesseurs. Je les laisse, pour la raison du
niveau 1 : les couvrir ajouterait des tests qui vérifient qu'un `return` rend ce
qu'on lui a donné.

## Ce qu'il faut retenir

1. **Cinq concepts dans un type, et le commentaire n'en annonçait que trois.**
   Celui qui manque est celui dont le métier a un mot et le code n'a pas de nom.
2. **Un concept sans représentation est réparti partout**, et chaque opération
   doit le reconstituer. C'est pour ça que les trois méthodes faisaient des
   boucles.
3. **Le périmètre d'un paramètre est le périmètre de ce qu'il peut détruire.**
   `Prescrire(f Fiche)` pouvait écraser un groupe sanguin.
4. **En flottant, une comparaison n'est pas une partition.** `NaN <= 0` est faux,
   donc la garde a un trou, donc une dose `NaN` était enregistrable.
5. **Une chose est une entité si et seulement si une opération peut la modifier
   en lui gardant son identité.** Sinon c'est une valeur ou un état.
6. **Si aucune opération ne modifie le candidat**, en faire une entité ajoute un
   identifiant, une table, une jointure et un cycle de vie pour rien.
7. **Des types d'identifiants distincts se justifient par une signature**, celle
   qui en prend deux côte à côte. Pas par principe.
8. **Un cas de test où tous les facteurs valent 1 ne distingue aucun facteur.**
   3 et 7 attrapent ce que 1 et 1 laissent passer.
9. **Une modification qui ne fait tomber que les tests de son propre paquet
   signale un type que personne n'utilise.**
10. **Sur une tranche dans une entité, la question n'est pas le type des
    éléments : c'est qui peut la modifier.**
11. **Un test de signature échoue à la compilation**, et c'est le seul genre de
    test qui garde un périmètre d'argument.
