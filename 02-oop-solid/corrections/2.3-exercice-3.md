# Correction 2.3 — Exercice 3 : la passerelle à quatre incorporations

> Rappel de l'énoncé : un `Service` qui incorpore `Horloge`, `*Compteur`,
> `*log.Logger` et `sync.Mutex`, « pour pouvoir écrire `s.Maintenant()` plutôt
> que `s.horloge.Maintenant()` ». Une méthode déclarée, huit questions.

Le module a quatre paquets. Le code de l'énoncé est dans `avant`, tel quel ;
le service refactoré dans `apres` ; l'horloge et le compteur dans `pieces`,
partagés par les deux, pour que la comparaison porte sur la **forme** du
service et sur rien d'autre. Tout passe sous `go vet ./...` et `go test -race
-count=1 ./...`.

```go
// ErrIndisponible est rendue quand le service n'a pas d'adresse.
var ErrIndisponible = errors.New("avant : service indisponible")

// Service est le type de l'exercice.
type Service struct {
    pieces.Horloge
    *pieces.Compteur
    *log.Logger
    sync.Mutex
    URL string
}

// Appeler est la seule methode que l'auteur a ecrite.
func (s *Service) Appeler(chemin string) (string, error) {
    s.Lock()
    defer s.Unlock()
    s.Incrementer(chemin)
    s.Printf("appel de %s a %s", chemin, s.Maintenant().Format(time.RFC3339))
    if s.URL == "" {
        return "", ErrIndisponible
    }
    return s.URL + chemin, nil
}
```

## 1. L'interface publique : 26 méthodes pour 1 déclarée

Comptée par `reflect`, pas à la main — écrite à la main elle aurait été
fausse, parce que personne ne connaît par cœur l'ensemble des méthodes de
`*log.Logger` :

```go
// TestLInventaireDesMethodesExportees repond a la question 1, par reflect et
// non a la main.
//
// L'auteur a declare UNE methode. Le type en expose beaucoup plus, et la
// liste est obtenue, pas supposee : ecrite a la main elle aurait ete fausse,
// parce que personne ne connait par coeur l'ensemble des methodes de
// *log.Logger.
func TestLInventaireDesMethodesExportees(t *testing.T) {
    ty := reflect.TypeOf(monter())
    parOrigine := map[string][]string{}
    for i := 0; i < ty.NumMethod(); i++ {
        nom := ty.Method(i).Name
        switch {
        case nom == "Appeler":
            parOrigine["declaree"] = append(parOrigine["declaree"], nom)
        case nom == "Maintenant":
            parOrigine["Horloge"] = append(parOrigine["Horloge"], nom)
        case nom == "Lock" || nom == "Unlock" || nom == "TryLock":
            parOrigine["sync.Mutex"] = append(parOrigine["sync.Mutex"], nom)
        default:
            if _, est := reflect.TypeOf(pieces.NouveauCompteur()).MethodByName(nom); est {
                parOrigine["*Compteur"] = append(parOrigine["*Compteur"], nom)
            } else {
                parOrigine["*log.Logger"] = append(parOrigine["*log.Logger"], nom)
            }
        }
    }
    total := ty.NumMethod()
    if n := len(parOrigine["declaree"]); n != 1 {
        t.Fatalf("%d methode declaree, attendu 1", n)
    }
    for _, origine := range []string{"declaree", "Horloge", "*Compteur", "sync.Mutex", "*log.Logger"} {
        t.Logf("%-12s %2d : %s", origine, len(parOrigine[origine]),
            strings.Join(parOrigine[origine], " "))
    }
    t.Logf("TOTAL        %2d methodes exportees pour 1 declaree, soit %d promues",
        total, total-1)
    if total <= 1 {
        t.Fatal("aucune promotion mesuree : le test ne mesure rien")
    }
}
```

```
declaree      1 : Appeler
Horloge       1 : Maintenant
*Compteur     5 : Incrementer MarshalJSON String Total Valeur
sync.Mutex    3 : Lock TryLock Unlock
*log.Logger  16 : Fatal Fatalf Fatalln Flags Output Panic Panicf Panicln
                  Prefix Print Printf Println SetFlags SetOutput SetPrefix Writer
TOTAL        26 methodes exportees pour 1 declaree, soit 25 promues
```

**Vingt-cinq méthodes que personne n'a décidées.** Dont trois qui peuvent tuer
le processus : `Fatal`, `Fatalf`, `Fatalln` appellent `os.Exit(1)`. N'importe
quel paquet qui tient un `*Service` peut arrêter le serveur, et la signature
qui le permet n'apparaît nulle part dans le code de l'équipe.

Ce qu'un code générique peut en faire, dans l'ordre croissant de dégâts :

| Interface | Ce que du code générique en fait |
|---|---|
| `sync.Locker` | un utilitaire de section critique (`avecVerrou(l sync.Locker, f func())`) prend le verrou du service puis appelle le service — **interblocage**, section 3 |
| `fmt.Stringer` | une ligne de journal `log.Printf("service=%v", s)` imprime l'état du compteur, c'est-à-dire **la liste des chemins appelés**, là où l'auteur croyait imprimer une adresse |
| `json.Marshaler` | un gestionnaire de diagnostic `json.NewEncoder(w).Encode(s)` publie le compteur et **perd l'URL** |

## 3. L'interblocage, et combien de mutex sont en jeu

Il y a **un** mutex pour le service, et c'est le problème : `Lock` et `Unlock`
sont promues, donc publiques. Un appelant qui verrouille le service — pour
enchaîner deux appels « de façon atomique », par exemple — s'interbloque avec
`Appeler`, qui verrouille le même mutex.

```go
// TestLInterblocageEstAtteignableDepuisLExterieur repond a la question 3.
//
// Il n'y a qu'UN mutex en jeu, et c'est le probleme. Lock et Unlock sont
// promues, donc publiques. Un appelant qui verrouille le service — pour
// faire deux appels « de facon atomique », par exemple — s'interbloque avec
// Appeler, qui verrouille le meme mutex.
//
// Le test ne peut pas attendre l'interblocage : il le constate par un delai.
// Un test qui attendrait vraiment ferait tomber la suite entiere sur le
// « all goroutines are asleep » du runtime.
func TestLInterblocageEstAtteignableDepuisLExterieur(t *testing.T) {
    s := monter()

    // Sans verrou exterieur : l'appel rend tout de suite.
    fini := make(chan struct{})
    go func() { _, _ = s.Appeler("/sain"); close(fini) }()
    select {
    case <-fini:
    case <-time.After(2 * time.Second):
        t.Fatal("un appel sans verrou exterieur ne rend pas : le test est faux")
    }

    // Avec le verrou exterieur, pris parce que Lock est publique.
    s.Lock()
    bloque := make(chan struct{})
    go func() { _, _ = s.Appeler("/bloque"); close(bloque) }()
    select {
    case <-bloque:
        s.Unlock()
        t.Fatal("l'appel a rendu : le mutex n'est pas partage, la mesure a change")
    case <-time.After(200 * time.Millisecond):
        t.Log("interblocage : Appeler attend un mutex que son appelant tient," +
            " et son appelant l'a pris par une methode promue")
    }
    // La goroutine reste bloquee jusqu'a la fin du processus de test. On ne
    // deverrouille pas : ce serait debloquer le defaut qu'on mesure, et le
    // compteur du service serait incremente apres la fin du test.
}
```

```
interblocage : Appeler attend un mutex que son appelant tient,
               et son appelant l'a pris par une methode promue
```

Le test ne peut pas *attendre* l'interblocage : il le constate par un délai.
Un test qui attendrait vraiment ferait tomber la suite entière sur le
`all goroutines are asleep` du runtime.

### La deuxième moitié de la question : combien de mutex, vraiment

**Deux, et c'est pire qu'un.** Celui du service protège `URL` ; le compteur a
le sien, en champ nommé.

```go
// TestLeMutexNEstPasCeluiDuCompteur est la reponse a la deuxieme moitie de
// la question 3 : combien de mutex sont en jeu.
//
// Deux, et c'est pire qu'un. Celui du service protege URL ; celui du
// compteur protege sa table. Un lecteur de Appeler croit que le s.Lock() de
// la premiere ligne protege l'increment de la troisieme : il ne protege rien
// de ce que le compteur fait.
func TestLeMutexNEstPasCeluiDuCompteur(t *testing.T) {
    s := monter()
    var attente sync.WaitGroup
    // Le compteur est appele en parallele, et le mutex du service n'y est
    // pour rien : c'est le champ nomme du compteur qui le protege.
    for i := 0; i < 100; i++ {
        attente.Add(1)
        go func() { defer attente.Done(); s.Incrementer("/parallele") }()
    }
    attente.Wait()
    if n := s.Valeur("/parallele"); n != 100 {
        t.Fatalf("%d increments sur 100 : le compteur n'est pas sur", n)
    }
    t.Log("100 increments concurrents sans passer par Appeler, sans perte :" +
        " le compteur se protege seul, et Lock() du service n'y sert a rien")
}
```

```
100 increments concurrents sans passer par Appeler, sans perte :
le compteur se protege seul, et Lock() du service n'y sert a rien
```

Un lecteur d'`Appeler` voit `s.Lock()` ligne 1 et `s.Incrementer(chemin)` ligne
3, et conclut que le premier protège le second. Il ne protège rien de ce que
le compteur fait. Les deux lignes ont la même forme — `s.quelquechose()` — et
elles portent sur deux objets différents. **C'est l'incorporation qui rend les
deux lignes indiscernables.**

> Un champ nommé aurait écrit `s.mu.Lock()` et `s.compteur.Incrementer()`.
> Trois caractères et neuf caractères de plus, et la question ne se posait
> pas.

## 4. Le deuxième défaut de concurrence, qui ne vient pas d'un mutex

L'incorporation promeut aussi les **champs**. `Horloge` et `URL` sont des
champs publics de `*Service`, modifiables par n'importe quel paquet, à
n'importe quel moment, **pendant** qu'un appel est en cours.

```go
// Package course repond a la question 4 : le deuxieme defaut de concurrence,
// celui qui ne vient pas d'un mutex.
//
// L'incorporation promeut les CHAMPS. Horloge et URL sont donc des champs
// publics de *Service, modifiables par n'importe quel paquet, a n'importe
// quel moment, pendant qu'un appel est en cours. Le mutex ne protege rien de
// ca : Appeler le prend pour lui-meme, pas pour ses appelants.
package course

import (
    "io"
    "log"
    "os"
    "os/exec"
    "strings"
    "sync"
    "testing"
    "time"

    "exemple/c23/ex3/avant"
    "exemple/c23/ex3/pieces"
)

// TestLaCourseSurLHorlogePromue provoque la course. Elle ne tourne que dans
// le sous-processus lance par le test suivant, parce qu'un test qui declenche
// une course fait echouer la suite entiere sous -race.
func TestLaCourseSurLHorlogePromue(t *testing.T) {
    if os.Getenv("COURSE_EX3") == "" {
        t.Skip("tourne dans le sous-processus de TestLeDetecteurNeLaVoitQueSiUnTestLaProvoque")
    }
    s := &avant.Service{
        Horloge:  pieces.Fixe{Instant: time.Date(2026, 6, 15, 10, 0, 0, 0, time.UTC)},
        Compteur: pieces.NouveauCompteur(),
        Logger:   log.New(io.Discard, "", 0),
        URL:      "https://interne.example.cm",
    }
    var attente sync.WaitGroup
    attente.Add(2)
    go func() {
        defer attente.Done()
        for i := 0; i < 1_000; i++ {
            _, _ = s.Appeler("/comptes")
        }
    }()
    go func() {
        defer attente.Done()
        // Un seul affectation suffit a la course. Mille, pour ne pas
        // dependre de l'ordonnancement.
        for i := 0; i < 1_000; i++ {
            s.Horloge = pieces.Systeme{}
        }
    }()
    attente.Wait()
}
```

```
Previous read at 0x00c000040a40 by goroutine 8:
```

### `go test -race` suffit-il ?

**Non**, et c'est la partie de la question qui compte.

```go
// TestLeDetecteurNeLaVoitQueSiUnTestLaProvoque est la reponse a « go test
// -race suffit-il ? ».
//
// Non. Le detecteur de course de Go est DYNAMIQUE : il ne signale que les
// acces qu'il observe pendant l'execution. Tant qu'aucun test n'ecrit le
// champ promu en parallele d'un appel, il ne voit rien et il rend un
// resultat vert — et seul quelqu'un qui sait deja que le champ est public
// peut ecrire ce test.
//
//    Un outil dynamique ne trouve pas les defauts : il confirme ceux
//    qu'un test a su reproduire.
func TestLeDetecteurNeLaVoitQueSiUnTestLaProvoque(t *testing.T) {
    if os.Getenv("COURSE_EX3") != "" {
        t.Skip("on est dans le sous-processus")
    }
    cmd := exec.Command("go", "test", "-race", "-count=1",
        "-run", "TestLaCourseSurLHorlogePromue", ".")
    cmd.Env = append(os.Environ(), "COURSE_EX3=1")
    sortie, err := cmd.CombinedOutput()
    if err == nil {
        t.Fatalf("aucune course detectee : la mesure a change\n%s", sortie)
    }
    if !strings.Contains(string(sortie), "DATA RACE") {
        t.Fatalf("le sous-processus a echoue, mais pas sur une course :\n%s", sortie)
    }
    // On publie les deux lignes qui nomment les acces, et rien de plus : le
    // reste du rapport porte des adresses qui changent a chaque execution.
    for _, l := range strings.Split(string(sortie), "\n") {
        if strings.Contains(l, "WARNING: DATA RACE") ||
            strings.Contains(l, "Write at") || strings.Contains(l, "Previous read at") {
            t.Logf("%s", strings.TrimSpace(l))
        }
    }
}
```

Le détecteur de course de Go est **dynamique** : il ne signale que les accès
qu'il observe pendant l'exécution. Tant qu'aucun test n'écrit le champ promu
en parallèle d'un appel, il ne voit rien et il rend un résultat vert. Et seul
quelqu'un qui **sait déjà** que le champ est public peut écrire ce test.

> Un outil dynamique ne trouve pas les défauts : il confirme ceux qu'un
> test a su reproduire.

Ce qui attrape cette classe entière, lui, est statique et tient en une
ligne : le champ n'est plus exporté, donc il n'est plus accessible, donc il
n'y a plus rien à reproduire.

## 5. Les champs nuls : trois pannes, un seul message

```go
// TestLesDeuxModesDePanneDUnChampNul repond a la question 5.
//
// Les trois pannes sont des paniques, et leur MESSAGE est le meme :
// « invalid memory address or nil pointer dereference ». Ce qui les
// distingue est la pile, et la pile ne survit pas a un recover : elle est
// deja deroulee quand le defer s'execute. La premiere version de ce test
// imprimait la trame du recover lui-meme pour les quatre cas, et elle
// paraissait juste.
//
// Chaque cas tourne donc dans un SOUS-PROCESSUS, qui panique vraiment.
func TestLesDeuxModesDePanneDUnChampNul(t *testing.T) {
    if cas := os.Getenv("CAS_NUL"); cas != "" {
        paniquer(cas)
        return
    }
    for _, cas := range []string{"compteur", "journal", "horloge"} {
        t.Run(cas, func(t *testing.T) {
            cmd := exec.Command(os.Args[0], "-test.run=TestLesDeuxModesDePanneDUnChampNul")
            cmd.Env = append(os.Environ(), "CAS_NUL="+cas)
            sortie, err := cmd.CombinedOutput()
            if err == nil {
                t.Fatalf("%s nul : aucune panique\n%s", cas, sortie)
            }
            message, fonction, position := lirePanique(string(sortie))
            if message == "" || fonction == "" {
                t.Fatalf("pas de panique lisible :\n%s", sortie)
            }
            t.Logf("%-9s %s", cas, message)
            t.Logf("%-9s dans %s", "", fonction)
            t.Logf("%-9s a   %s", "", position)
        })
    }
}
```

```go
// paniquer monte un service avec un champ nul et l'appelle. Elle tourne dans
// le sous-processus.
func paniquer(cas string) {
    h := pieces.Fixe{Instant: time.Date(2026, 6, 15, 10, 0, 0, 0, time.UTC)}
    s := &avant.Service{Horloge: h, Compteur: pieces.NouveauCompteur(),
        Logger: log.New(io.Discard, "", 0), URL: "u"}
    switch cas {
    case "compteur":
        s.Compteur = nil
    case "journal":
        s.Logger = nil
    case "horloge":
        s.Horloge = nil
    }
    _, _ = s.Appeler("/comptes")
}
```

Chaque cas tourne dans un **sous-processus**, et il y a une raison mesurée :
la pile ne survit pas à un `recover`, elle est déjà déroulée quand le `defer`
s'exécute. La première version de ce test imprimait la trame du `recover`
lui-même pour les trois cas — trois lignes identiques — et elle paraissait
juste.

```
compteur  panic: runtime error: invalid memory address or nil pointer dereference
          dans exemple/c23/ex3/pieces.(*Compteur).Incrementer(0x0, ...)
          a   pieces/pieces.go:52

journal   panic: runtime error: invalid memory address or nil pointer dereference
          dans log.(*Logger).output(...)
          a   log/log.go:202

horloge   panic: runtime error: invalid memory address or nil pointer dereference
          dans exemple/c23/ex3/avant.(*Service).Appeler(...)
          a   avant/avant.go:34
```

**Le message est identique dans les trois cas.** Les modes de panne ne se
distinguent donc pas par ce qu'un journal d'erreurs enregistre, mais par la
pile — et les trois piles pointent trois endroits de nature différente :

| Champ nul | La panique a lieu | Pour celui qui est de garde |
|---|---|---|
| `*Compteur` | dans `pieces`, une fonction que l'auteur du service n'a pas écrite | il faut lire le code d'un autre paquet pour comprendre |
| `*log.Logger` | **dans la bibliothèque standard**, `log/log.go:202` | il faut lire le code de Go |
| `Horloge` | dans `Appeler`, ligne 34 | le seul des trois qui désigne le code fautif |

Et un détail d'ordre, qui n'est pas un détail : `Incrementer` est appelée
**avant** `Printf`. Un service dont le compteur *et* le journal sont nuls ne
signale que le compteur. On corrige, on redéploie, et on retombe sur la même
panique avec une autre pile.

## 6. Le refactoring

```go
// Service est la passerelle d'appel du service interne.
//
// Les quatre champs sont NOMMES et non exportes. Consequence directe : le
// type expose deux methodes au lieu de vingt-six, il ne satisfait plus
// aucune interface par accident, et son mutex n'est plus verrouillable
// depuis l'exterieur.
type Service struct {
    horloge  pieces.Horloge
    compteur *pieces.Compteur
    journal  *log.Logger
    mu       sync.Mutex
    url      string
}
```

```go
// Nouveau construit le service, ou refuse de le construire.
//
// C'est ici que les trois paniques de la version incorporee disparaissent :
// un champ nul ne peut plus arriver jusqu'a Appeler.
func Nouveau(url string, h pieces.Horloge, c *pieces.Compteur, j *log.Logger) (*Service, error) {
    switch {
    case url == "":
        return nil, ErrURLAbsente
    case h == nil:
        return nil, fmt.Errorf("%w : horloge", ErrDependanceAbsente)
    case c == nil:
        return nil, fmt.Errorf("%w : compteur", ErrDependanceAbsente)
    case j == nil:
        return nil, fmt.Errorf("%w : journal", ErrDependanceAbsente)
    }
    return &Service{horloge: h, compteur: c, journal: j, url: url}, nil
}
```

```go
// Appeler rend l'adresse complete du chemin demande.
//
// Deux differences de comportement avec la version incorporee, et les deux
// sont voulues :
//
//  1. le refus est verifie AVANT la journalisation et avant le comptage. La
//     version d'origine journalisait et comptait un appel qu'elle refusait
//     ensuite, ce qui gonflait le compteur de tous les appels perdus.
//  2. le constructeur ayant refuse les champs nuls, il n'y a plus de garde
//     a l'interieur.
func (s *Service) Appeler(chemin string) (string, error) {
    if s.url == "" {
        return "", ErrIndisponible
    }
    s.mu.Lock()
    defer s.mu.Unlock()
    s.compteur.Incrementer(chemin)
    s.journal.Printf("appel de %s a %s", chemin, s.horloge.Maintenant().Format(time.RFC3339))
    return s.url + chemin, nil
}

// Total rend le nombre d'appels servis, tous chemins confondus.
//
// C'est la seule methode du compteur qui remonte, parce que c'est la seule
// que l'exploitation demande. Les quatre autres restent dans le compteur.
func (s *Service) Total() int { return s.compteur.Total() }
```

```go
// Trois assertions NEGATIVES. Elles sont plus rares que les positives et
// elles valent plus cher : une assertion positive dit ce que le type fait,
// une negative dit ce que personne ne pourra en faire.
func TestLeServiceNeSatisfaitPlusRienParAccident(t *testing.T) {
    var v any = monter(t, io.Discard)
    if _, est := v.(sync.Locker); est {
        t.Error("*Service est un sync.Locker : son mutex est verrouillable de l'exterieur")
    }
    if _, est := v.(fmt.Stringer); est {
        t.Error("*Service est un fmt.Stringer : un verbe de formatage imprimera autre chose que le service")
    }
    if _, est := v.(json.Marshaler); est {
        t.Error("*Service est un json.Marshaler : sa serialisation ne sera pas la sienne")
    }
    brut, err := json.Marshal(v)
    if err != nil {
        t.Fatalf("Marshal : %v", err)
    }
    if string(brut) != "{}" {
        t.Errorf("json.Marshal = %s, attendu {} : les champs sont non exportes", brut)
    }
    t.Logf("aucune des trois interfaces, et json.Marshal rend %s", brut)
}
```

```
aucune des trois interfaces, et json.Marshal rend {}
```

Trois assertions **négatives**. Elles sont plus rares que les positives et
elles valent plus cher : une assertion positive dit ce que le type fait, une
négative dit ce que personne ne pourra en faire.

| Qualificatif ajouté | Occurrences | Caractères |
|---|---|---|
| `mu.` | 2 | 6 |
| `compteur.` | 1 | 9 |
| `journal.` | 1 | 8 |
| `horloge.` | 1 | 8 |
| | | **31** |

**Trente-et-un caractères dans le corps d'`Appeler`.** Pas par appel du

### Ce que ça supprime

Il faut être honnête sur la question telle qu'elle est posée : le refactoring
ne supprime **aucune ligne**. Il en ajoute 48 — `avant/avant.go` fait 39
lignes, `apres/apres.go` en fait 87 — et l'essentiel de l'ajout est le
constructeur.

Ce qu'il supprime n'est pas du code, c'est de la surface :

| | Avant | Après |
|---|---|---|
| méthodes exportées | 26 | **2** |
| interfaces satisfaites par accident | 3 | **0** |
| champs modifiables de l'extérieur | 2 (`Horloge`, `URL`) | **0** |
| modes de panique à l'appel | 3 | **0** |
| mutex verrouillable de l'extérieur | 1 | **0** |
| méthodes pouvant appeler `os.Exit` | 3 | **0** |

Les trois paniques sont devenues une erreur, au moment où l'on peut encore
l'afficher :

```
apres : dependance absente : horloge
apres : dependance absente : compteur
apres : dependance absente : journal
apres : adresse absente
```

Et le comportement du chemin normal est préservé, à une différence près,
voulue et écrite dans le code : **le refus est vérifié avant la
journalisation**. La version d'origine journalisait et comptait un appel
qu'elle refusait ensuite :

```
=== RUN   TestLeJournalEstEcritAvantLeRefus
    appel refuse, et pourtant journalise : "appel de /comptes a 2026-06-15T10:00:00Z"
    et compte : /comptes = 1
--- PASS
```

Un service mal configuré produisait donc une ligne de journal et un
incrément de compteur **par appel perdu**. Le tableau de bord montrait du
trafic.

## 7. La réponse au développeur de l'équipe

> *« Avec des champs nommés, il faut écrire `s.horloge.Maintenant()` partout,
> c'est verbeux et ça n'apporte rien. »*

Trois phrases.

**Le « partout » se mesure : c'est 31 caractères, une fois, dans le corps
d'une méthode — et ces 31 caractères retirent 24 méthodes de l'interface
publique du service, dont trois qui appellent `os.Exit`.** Ce que
l'incorporation apporte, c'est que `s.Lock()` ligne 1 et `s.Incrementer()`
ligne 3 s'écrivent pareil alors qu'ils portent sur deux objets différents, et
c'est précisément ce qui a caché l'interblocage. Et la verbosité qu'on évite
en incorporant, on la repaye à chaque relecture de `Appeler`, où il faut
remonter la déclaration du type pour savoir à qui appartient chaque méthode.

## 8. La prochaine méthode ajoutée par une bibliothèque

Trois choses peuvent arriver, de la plus visible à la plus silencieuse.

### 1. La compilation casse — ambiguïté

Si deux des quatre types incorporés gagnent une méthode du **même nom au même
niveau**, l'appel devient ambigu. La leçon 2.3 l'a établi : l'ambiguïté est
*déclarable* mais pas *utilisable*. Le type continue de compiler ; c'est
`s.Nouvelle()` qui ne compile plus.

Visible immédiatement, à la montée de version, avec un message explicite.
C'est le cas **heureux**.

### 2. La compilation casse — collision avec une méthode du service

Si un type incorporé gagne `Appeler`, il n'y a pas d'erreur : la méthode du
service, déclarée au niveau zéro, **gagne**. Mais tout code qui faisait
`var _ UneInterface = s` et comptait sur la promotion change de cible en
silence. Visible seulement si une assertion de conformité existe.

### 3. Le type satisfait une interface que personne n'a voulue

Le plus silencieux, et le plus coûteux. Aucune erreur, aucun changement de
comportement local, et une bascule complète de ce que du code générique fait
du service — exactement les trois lignes de la section 2, une quatrième
s'ajoutant sans qu'une ligne du programme n'ait bougé.

### Le test qui attrape la troisième

```go
// lesVingtSixMethodes est l'instantane de l'interface publique de
// *avant.Service, au 7 octobre 2026, sous Go 1.23.
var lesVingtSixMethodes = []string{
    "Appeler",
    "Fatal", "Fatalf", "Fatalln", "Flags",
    "Incrementer", "Lock",
    "MarshalJSON", "Maintenant",
    "Output",
    "Panic", "Panicf", "Panicln", "Prefix", "Print", "Printf", "Println",
    "SetFlags", "SetOutput", "SetPrefix", "String",
    "Total", "TryLock",
    "Unlock",
    "Valeur", "Writer",
}

// TestLEnsembleDesMethodesExporteesEstFige est le test que demande la
// question 8, pour la troisieme chose — la plus silencieuse.
//
// Quand une bibliotheque ajoute une methode a un type incorpore, trois
// choses peuvent arriver. Celle-ci attrape la troisieme : le type se met a
// satisfaire une interface que personne n'a voulue, sans qu'une ligne du
// programme n'ait bouge et sans qu'aucune compilation n'echoue.
//
// Ce test a un precedent exact : sync.Mutex a gagne TryLock en Go 1.18.
// L'equipe qui aurait eu cet instantane l'aurait vu rougir le jour de la
// montee de version, avec le nom de la methode ajoutee dans le message. Les
// autres ne l'ont jamais su.
//
// Noter que l'instantane est mis a jour par celui qui casse le contrat, et
// que la mise a jour est une DECISION : il faut regarder la methode ajoutee
// et dire ce qu'elle change, pas corriger la liste pour repasser au vert.
func TestLEnsembleDesMethodesExporteesEstFige(t *testing.T) {
    ty := reflect.TypeOf(monter())
    vues := map[string]bool{}
    for i := 0; i < ty.NumMethod(); i++ {
        vues[ty.Method(i).Name] = true
    }
    attendues := map[string]bool{}
    for _, nom := range lesVingtSixMethodes {
        attendues[nom] = true
    }
    for nom := range vues {
        if !attendues[nom] {
            t.Errorf("methode APPARUE : %s — une bibliotheque l'a ajoutee a un"+
                " type incorpore. Dire ce qu'elle change avant de l'inscrire.", nom)
        }
    }
    for nom := range attendues {
        if !vues[nom] {
            t.Errorf("methode DISPARUE : %s — un type incorpore l'a retiree,"+
                " ou l'incorporation a change", nom)
        }
    }
    if len(lesVingtSixMethodes) != len(attendues) {
        t.Fatalf("la liste contient %d entrees pour %d noms distincts :"+
            " il y a un doublon", len(lesVingtSixMethodes), len(attendues))
    }
    t.Logf("%d methodes, instantane conforme", len(vues))
}
```

```
26 methodes, instantane conforme
```

Ce test a un précédent exact : **`sync.Mutex` a gagné `TryLock` en Go 1.18**.
L'équipe qui aurait eu cet instantané l'aurait vu rougir le jour de la montée
de version, avec le nom de la méthode ajoutée dans le message. Les autres ne
l'ont jamais su — et la leçon 2.3 a elle-même compté « deux méthodes de trop »
avant que son propre test ne réponde trois.

Deux précautions dans ce test, et les deux sont des règles du cours :

- il vérifie les **deux sens** : une méthode apparue et une méthode disparue.
  Un test qui ne vérifie qu'un sens laisse passer la moitié des changements ;
- il refuse les **doublons** dans sa propre liste, parce qu'une liste écrite à
  la main avec un nom en double ferait passer un compte faux.

Et la règle d'usage, qui vaut plus que le test :

> Un test d'instantané est mis à jour par celui qui casse le contrat, et la
> mise à jour est une **décision**. Il faut regarder la méthode ajoutée et
> dire ce qu'elle change, pas corriger la liste pour repasser au vert.
