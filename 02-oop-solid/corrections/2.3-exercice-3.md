# Correction 2.3 — Exercice 3 : la passerelle à quatre incorporations

> Rappel de l'énoncé : un `Service` qui incorpore `Clock`, `*Counter`,
> `*log.Logger` et `sync.Mutex`, « pour pouvoir écrire `s.Now()` plutôt
> que `s.clock.Now()` ». Une méthode déclarée, huit questions.

Le module a quatre paquets. Le code de l'énoncé est dans `before`, tel quel ;
le service refactoré dans `after` ; l'horloge et le compteur dans `parts`,
partagés par les deux, pour que la comparaison porte sur la **forme** du
service et sur rien d'autre. Tout passe sous `go vet ./...` et `go test -race
-count=1 ./...`.

```go
// ErrUnavailable is returned when the service has no address.
var ErrUnavailable = errors.New("before: service unavailable")

// Service is the exercise's type.
type Service struct {
    parts.Clock
    *parts.Counter
    *log.Logger
    sync.Mutex
    URL string
}

// Call is the only method the author wrote.
func (s *Service) Call(path string) (string, error) {
    s.Lock()
    defer s.Unlock()
    s.Increment(path)
    s.Printf("call from %s to %s", path, s.Now().Format(time.RFC3339))
    if s.URL == "" {
        return "", ErrUnavailable
    }
    return s.URL + path, nil
}
```

## 1. L'interface publique : 26 méthodes pour 1 déclarée

Comptée par `reflect`, pas à la main — écrite à la main elle aurait été
fausse, parce que personne ne connaît par cœur l'ensemble des méthodes de
`*log.Logger` :

```go
// TestTheInventoryOfExportedMethods answers question 1, with reflect and
// not by hand.
//
// The author declared ONE method. The type exposes many more, and the
// list is obtained, not assumed: written by hand it would have been wrong,
// because nobody knows by heart the full set of methods of
// *log.Logger.
func TestTheInventoryOfExportedMethods(t *testing.T) {
    ty := reflect.TypeOf(mount())
    byOrigin := map[string][]string{}
    for i := 0; i < ty.NumMethod(); i++ {
        name := ty.Method(i).Name
        switch {
        case name == "Call":
            byOrigin["declared"] = append(byOrigin["declared"], name)
        case name == "Now":
            byOrigin["Clock"] = append(byOrigin["Clock"], name)
        case name == "Lock" || name == "Unlock" || name == "TryLock":
            byOrigin["sync.Mutex"] = append(byOrigin["sync.Mutex"], name)
        default:
            if _, ok := reflect.TypeOf(parts.NewCounter()).MethodByName(name); ok {
                byOrigin["*Counter"] = append(byOrigin["*Counter"], name)
            } else {
                byOrigin["*log.Logger"] = append(byOrigin["*log.Logger"], name)
            }
        }
    }
    total := ty.NumMethod()
    if n := len(byOrigin["declared"]); n != 1 {
        t.Fatalf("%d method declared, want 1", n)
    }
    for _, origin := range []string{"declared", "Clock", "*Counter", "sync.Mutex", "*log.Logger"} {
        t.Logf("%-12s %2d : %s", origin, len(byOrigin[origin]),
            strings.Join(byOrigin[origin], " "))
    }
    t.Logf("TOTAL        %2d exported methods for 1 declared, so %d promoted",
        total, total-1)
    if total <= 1 {
        t.Fatal("no promotion measured: the test measures nothing")
    }
}
```

*Counter     5 : Increment MarshalJSON String Total Value

quel paquet qui tient un `*Service` peut arrêter le serveur, et la signature
qui le permet n'apparaît nulle part dans le code de l'équipe.

## 3. L'interblocage, et combien de mutex sont en jeu

Il y a **un** mutex pour le service, et c'est le problème : `Lock` et `Unlock`
sont promues, donc publiques. Un appelant qui verrouille le service — pour
enchaîner deux appels « de façon atomique », par exemple — s'interbloque avec
`Call`, qui verrouille le même mutex.

```go
// TestTheDeadlockIsReachableFromOutside answers question 3.
// There is only ONE mutex at stake, and that is the problem. Lock and Unlock are
// promoted, so public. A caller that locks the service (to
// make two calls "atomically", for example) deadlocks with
// Call, which locks the same mutex.
//
// The test cannot wait for the deadlock: it notes it with a timeout.
// A test that really waited would bring down the whole suite on the
// "all goroutines are asleep" from the runtime.
func TestTheDeadlockIsReachableFromOutside(t *testing.T) {
    s := mount()

    // Without an outside lock: the call returns at once.
    done := make(chan struct{})
    go func() { _, _ = s.Call("/healthy"); close(done) }()
    select {
    case <-done:
    case <-time.After(2 * time.Second):
        t.Fatal("a call without an outside lock does not return: the test is wrong")
    }

    // With the outside lock, taken because Lock is public.
    s.Lock()
    blocked := make(chan struct{})
    go func() { _, _ = s.Call("/blocked"); close(blocked) }()
    select {
    case <-blocked:
        s.Unlock()
        t.Fatal("the call returned: the mutex is not shared, the measure changed")
    case <-time.After(200 * time.Millisecond):
        t.Log("deadlock: Call waits for a mutex its caller holds," +
            " and its caller took it through a promoted method")
    }
    // The goroutine stays blocked until the end of the test process. We do not
    // unlock: it would unblock the flaw we measure, and the
    // service's counter would be incremented after the end of the test.
}
```

```
deadlock: Call waits for a mutex its caller holds,
               and its caller took it through a promoted method
```

Le test ne peut pas *attendre* l'interblocage : il le constate par un délai.
Un test qui attendrait vraiment ferait tomber la suite entière sur le
`all goroutines are asleep` du runtime.

### La deuxième moitié de la question : combien de mutex, vraiment

**Deux, et c'est pire qu'un.** Celui du service protège `URL` ; le compteur a
le sien, en champ nommé.

```go
// TestTheMutexIsNotTheCountersOne is the answer to the second half of
// question 3: how many mutexes are at stake.
//
// Two, and it is worse than one. The service's protects URL; the
// counter's protects its table. A reader of Call believes the s.Lock() of
// the first line protects the increment of the third: it protects nothing
// of what the counter does.
func TestTheMutexIsNotTheCountersOne(t *testing.T) {
    s := mount()
    var waiting sync.WaitGroup
    // The counter is called in parallel, and the service's mutex has
    // for nothing: it is the counter's named field that protects it.
    for i := 0; i < 100; i++ {
        waiting.Add(1)
        go func() { defer waiting.Done(); s.Increment("/parallele") }()
    }
    waiting.Wait()
    if n := s.Value("/parallele"); n != 100 {
        t.Fatalf("%d increments out of 100: the counter is not safe", n)
    }
    t.Log("100 concurrent increments without going through Call, without loss:" +
        " the counter protects itself, and the service's Lock() does nothing there")
}
```

```
100 concurrent increments without going through Call, without loss:
le counter se protege seul, et Lock() du service n'y sert a rien
```

Un lecteur d'`Call` voit `s.Lock()` ligne 1 et `s.Increment(path)` ligne
3, et conclut que le premier protège le second. Il ne protège rien de ce que
le compteur fait. Les deux lignes ont la même forme — `s.quelquechose()` — et
elles portent sur deux objets différents. **C'est l'incorporation qui rend les
deux lignes indiscernables.**

> Un champ nommé aurait écrit `s.mu.Lock()` et `s.counter.Increment()`.
> Trois caractères et neuf caractères de plus, et la question ne se posait
> pas.

## 4. Le deuxième défaut de concurrence, qui ne vient pas d'un mutex

L'incorporation promeut aussi les **champs**. `Clock` et `URL` sont des
champs publics de `*Service`, modifiables par n'importe quel paquet, à
n'importe quel moment, **pendant** qu'un appel est en cours.

```go
// Package race answers question 4: the second concurrency flaw,
// the one that does not come from a mutex.
//
// Embedding promotes FIELDS. So Clock and URL are public fields
// of *Service, changeable by any package, at any
// time, while a call is in progress. The mutex protects none
// that: Call takes it for itself, not for its callers.
package race

import (
    "io"
    "log"
    "os"
    "os/exec"
    "strings"
    "sync"
    "testing"
    "time"

    "example/c23/ex3/before"
    "example/c23/ex3/parts"
)

// TestTheRaceOnThePromotedClock causes the race. It runs only in
// the subprocess started by the next test, because a test that triggers
// a race makes the whole suite fail under -race.
func TestTheRaceOnThePromotedClock(t *testing.T) {
    if os.Getenv("COURSE_EX3") == "" {
        t.Skip("runs in the subprocess of TestTheDetectorSeesItOnlyIfATestCausesIt")
    }
    s := &before.Service{
        Clock:   parts.Fixed{Instant: time.Date(2026, 6, 15, 10, 0, 0, 0, time.UTC)},
        Counter: parts.NewCounter(),
        Logger:  log.New(io.Discard, "", 0),
        URL:     "https://interne.example.cm",
    }
    var waiting sync.WaitGroup
    waiting.Add(2)
    go func() {
        defer waiting.Done()
        for i := 0; i < 1_000; i++ {
            _, _ = s.Call("/accounts")
        }
    }()
    go func() {
        defer waiting.Done()
        // A single assignment is enough for the race. A thousand, so as not to
        // depend on scheduling.
        for i := 0; i < 1_000; i++ {
            s.Clock = parts.System{}
        }
    }()
    waiting.Wait()
}
```

```
WARNING: DATA RACE
Write at 0x00c000040a40 by goroutine 9:
Previous read at 0x00c000040a40 by goroutine 8:
```

### `go test -race` suffit-il ?

**Non**, et c'est la partie de la question qui compte.

```go
// TestTheDetectorSeesItOnlyIfATestCausesIt is the answer to "is go test
// -race enough?".
//
// No. Go's race detector is DYNAMIC: it reports only the
// accesses it sees during the run. As long as no test writes the
// promoted field in parallel with a call, it sees nothing and returns a
// green result, and only someone who already knows the field is public
// can write this test.
//
//    A dynamic tool does not find flaws: it confirms those
//    a test managed to reproduce.
func TestTheDetectorSeesItOnlyIfATestCausesIt(t *testing.T) {
    if os.Getenv("COURSE_EX3") != "" {
        t.Skip("we are in the subprocess")
    }
    cmd := exec.Command("go", "test", "-race", "-count=1",
        "-run", "TestTheRaceOnThePromotedClock", ".")
    cmd.Env = append(os.About(), "COURSE_EX3=1")
    output, err := cmd.CombinedOutput()
    if err == nil {
        t.Fatalf("no race detected: the measure changed\n%s", output)
    }
    if !strings.Contains(string(output), "DATA RACE") {
        t.Fatalf("the subprocess failed, but not on a race:\n%s", output)
    }
    // We publish the two lines that name the accesses, and nothing more: the
    // rest of the report carries addresses that change on each run.
    for _, l := range strings.Split(string(output), "\n") {
        if strings.Contains(l, "WARNING: DATA RACE") ||
            strings.Contains(l, "Write at") || strings.Contains(l, "Previous read at") {
            t.Logf("%s", strings.TrimSpace(l))
        }
    }
}
```

Le détecteur de course de Go est **dynamique** : il ne signale que les accès
qu'il observe pendant l'exécution. Tant qu'aucun test n'écrit le champ promu
en parallèle d'un appel, il ne voit rien et il rend un résultat vert. Et seul
quelqu'un qui **sait déjà** que le champ est public peut écrire ce test.

> Un outil dynamique ne trouve pas les défauts : il confirme ceux qu'un
> test a su reproduire.

Ce qui attrape cette classe entière, lui, est statique et tient en une
ligne : le champ n'est plus exporté, donc il n'est plus accessible, donc il
n'y a plus rien à reproduire.

## 5. Les champs nuls : trois pannes, un seul message

```go
// TestTheTwoFailureModesOfANilField answers question 5.
// The three failures are panics, and their MESSAGE is the same:
// "invalid memory address or nil pointer dereference". What
// tells them apart is the stack, and the stack does not survive a recover: it is
// already unwound when the defer runs. The first version of this test
// printed the recover's own frame for all four cases, and it
// looked right.
//
// So each case runs in a SUBPROCESS, which really panics.
func TestTheTwoFailureModesOfANilField(t *testing.T) {
    if tc := os.Getenv("CAS_NUL"); tc != "" {
        panicking(tc)
        return
    }
    for _, tc := range []string{"counter", "journal", "clock"} {
        t.Run(tc, func(t *testing.T) {
            cmd := exec.Command(os.Args[0], "-test.run=TestTheTwoFailureModesOfANilField")
            cmd.Env = append(os.About(), "CAS_NUL="+tc)
            output, err := cmd.CombinedOutput()
            if err == nil {
                t.Fatalf("nil %s: no panic\n%s", tc, output)
            }
            message, function, position := readPanic(string(output))
            if message == "" || function == "" {
                t.Fatalf("no readable panic:\n%s", output)
            }
            t.Logf("%-9s %s", tc, message)
            t.Logf("%-9s in %s", "", function)
            t.Logf("%-9s a   %s", "", position)
        })
    }
}
```

```go
// panicking mounts a service with a nil field and calls it. It runs in
// the subprocess.
func panicking(tc string) {
    h := parts.Fixed{Instant: time.Date(2026, 6, 15, 10, 0, 0, 0, time.UTC)}
    s := &before.Service{Clock: h, Counter: parts.NewCounter(),
        Logger: log.New(io.Discard, "", 0), URL: "u"}
    switch tc {
    case "counter":
        s.Counter = nil
    case "journal":
        s.Logger = nil
    case "clock":
        s.Clock = nil
    }
    _, _ = s.Call("/accounts")
}
```

Chaque cas tourne dans un **sous-processus**, et il y a une raison mesurée :
la pile ne survit pas à un `recover`, elle est déjà déroulée quand le `defer`
s'exécute. La première version de ce test imprimait la trame du `recover`
lui-même pour les trois cas — trois lignes identiques — et elle paraissait
juste.

```
counter  panic: runtime error: invalid memory address or nil pointer dereference
          dans example/c23/ex3/parts.(*Counter).Increment(0x0, ...)
          a   pieces/parts.go:52

journal   panic: runtime error: invalid memory address or nil pointer dereference
          dans log.(*Logger).output(...)
          a   log/log.go:202

clock   panic: runtime error: invalid memory address or nil pointer dereference
          dans example/c23/ex3/before.(*Service).Call(...)
          a   avant/before.go:34
```

**Le message est identique dans les trois cas.** Les modes de panne ne se
distinguent donc pas par ce qu'un journal d'erreurs enregistre, mais par la
pile — et les trois piles pointent trois endroits de nature différente :

| Champ nul | La panique a lieu | Pour celui qui est de garde |
|---|---|---|
| `*Counter` | dans `parts`, une fonction que l'auteur du service n'a pas écrite | il faut lire le code d'un autre paquet pour comprendre |
| `*log.Logger` | **dans la bibliothèque standard**, `log/log.go:202` | il faut lire le code de Go |
| `Clock` | dans `Call`, ligne 34 | le seul des trois qui désigne le code fautif |

Et un détail d'ordre, qui n'est pas un détail : `Increment` est appelée
**avant** `Printf`. Un service dont le compteur *et* le journal sont nuls ne
signale que le compteur. On corrige, on redéploie, et on retombe sur la même
panique avec une autre pile.

## 6. Le refactoring

```go
// Service is the gateway to call the internal service.
// The four fields are NAMED and unexported. Direct consequence: the
// type exposes two methods instead of twenty-six, it no longer satisfies
// no interface by accident, and its mutex can no longer be locked
// from outside.
type Service struct {
    clock   parts.Clock
    counter *parts.Counter
    journal *log.Logger
    mu      sync.Mutex
    url     string
}
```

```go
// New builds the service, or refuses to build it.
// It is here that the three panics of the embedded version disappear:
// a nil field can no longer reach Call.
func New(url string, h parts.Clock, c *parts.Counter, j *log.Logger) (*Service, error) {
    switch {
    case url == "":
        return nil, ErrMissingURL
    case h == nil:
        return nil, fmt.Errorf("%w: clock", ErrMissingDependency)
    case c == nil:
        return nil, fmt.Errorf("%w: counter", ErrMissingDependency)
    case j == nil:
        return nil, fmt.Errorf("%w: journal", ErrMissingDependency)
    }
    return &Service{clock: h, counter: c, journal: j, url: url}, nil
}
```

```go
// Call returns the full address of the requested path.
// Two behavior differences with the embedded version, and both
// are intended:
//
//  1. the refusal is checked BEFORE logging and before counting. The
//     original version logged and counted a call it refused
//     afterwards, which inflated the counter with all the lost calls.
//  2. since the constructor refused nil fields, there is no more guard
//     inside.
func (s *Service) Call(path string) (string, error) {
    if s.url == "" {
        return "", ErrUnavailable
    }
    s.mu.Lock()
    defer s.mu.Unlock()
    s.counter.Increment(path)
    s.journal.Printf("call from %s to %s", path, s.clock.Now().Format(time.RFC3339))
    return s.url + path, nil
}

// Total returns the number of calls served, all paths together.
//
// It is the only method of the counter that comes up, because it is the only one
// that operations ask for. The other four stay in the counter.
func (s *Service) Total() int { return s.counter.Total() }
```

```go
// TestTheServiceNoLongerSatisfiesAnythingByAccident is the counterpart of the test
// of the three interfaces of package before.
//
// Three NEGATIVE assertions. They are rarer than positive ones and
// they are worth more: a positive assertion says what the type does,

        t.Error("*Service is a fmt.Stringer: a format verb will print something other than the service")
    }
    if _, ok := v.(json.Marshaler); ok {
        t.Error("*Service is a json.Marshaler: its serialization will not be its own")
    }
    raw, err := json.Marshal(v)
    if err != nil {
        t.Fatalf("Marshal: %v", err)
    }
    if string(raw) != "{}" {
        t.Errorf("json.Marshal = %s, want {}: the fields are unexported", raw)

```
aucune des trois interfaces, et json.Marshal rend {}

Trois assertions **négatives**. Elles sont plus rares que les positives et
elles valent plus cher : une assertion positive dit ce que le type fait, une
négative dit ce que personne ne pourra en faire.

### Ce que ça supprime

Il faut être honnête sur la question telle qu'elle est posée : le refactoring
ne supprime **aucune ligne**. Il en ajoute 48 — `before/before.go` fait 39
lignes, `after/after.go` en fait 87 — et l'essentiel de l'ajout est le
constructeur.

Ce qu'il supprime n'est pas du code, c'est de la surface :

| | Avant | Après |
|---|---|---|
| méthodes exportées | 26 | **2** |
| interfaces satisfaites par accident | 3 | **0** |
| champs modifiables de l'extérieur | 2 (`Clock`, `URL`) | **0** |
| modes de panique à l'appel | 3 | **0** |
| mutex verrouillable de l'extérieur | 1 | **0** |
| méthodes pouvant appeler `os.Exit` | 3 | **0** |

Les trois paniques sont devenues une erreur, au moment où l'on peut encore
l'afficher :

```
apres : dependance absente : clock
apres : dependance absente : counter
apres : dependance absente : journal
apres : adresse absente
```

Et le comportement du chemin normal est préservé, à une différence près,
voulue et écrite dans le code : **le refus est vérifié avant la
journalisation**. La version d'origine journalisait et comptait un appel
qu'elle refusait ensuite :

```
=== RUN   TestLeJournalEstEcritAvantLeRefus
    appel refuse, et pourtant journalise : "appel de /accounts a 2026-06-15T10:00:00Z"
    et compte : /accounts = 1
--- PASS
```

Un service mal configuré produisait donc une ligne de journal et un
incrément de compteur **par appel perdu**. Le tableau de bord montrait du
trafic.

## 7. La réponse au développeur de l'équipe

> *« Avec des champs nommés, il faut écrire `s.clock.Now()` partout,
> c'est verbeux et ça n'apporte rien. »*

Trois phrases.

**Le « partout » se mesure : c'est 31 caractères, une fois, dans le corps
d'une méthode — et ces 31 caractères retirent 24 méthodes de l'interface
publique du service, dont trois qui appellent `os.Exit`.** Ce que
l'incorporation apporte, c'est que `s.Lock()` ligne 1 et `s.Increment()`
ligne 3 s'écrivent pareil alors qu'ils portent sur deux objets différents, et
c'est précisément ce qui a caché l'interblocage. Et la verbosité qu'on évite
en incorporant, on la repaye à chaque relecture de `Call`, où il faut
remonter la déclaration du type pour savoir à qui appartient chaque méthode.

## 8. La prochaine méthode ajoutée par une bibliothèque

Trois choses peuvent arriver, de la plus visible à la plus silencieuse.

### 1. La compilation casse — ambiguïté

Si deux des quatre types incorporés gagnent une méthode du **même nom au même
niveau**, l'appel devient ambigu. La leçon 2.3 l'a établi : l'ambiguïté est
*déclarable* mais pas *utilisable*. Le type continue de compiler ; c'est
`s.Nouvelle()` qui ne compile plus.

Visible immédiatement, à la montée de version, avec un message explicite.
C'est le cas **heureux**.

### 2. La compilation casse — collision avec une méthode du service

Si un type incorporé gagne `Call`, il n'y a pas d'erreur : la méthode du
service, déclarée au niveau zéro, **gagne**. Mais tout code qui faisait
`var _ UneInterface = s` et comptait sur la promotion change de cible en
silence. Visible seulement si une assertion de conformité existe.

### 3. Le type satisfait une interface que personne n'a voulue

Le plus silencieux, et le plus coûteux. Aucune erreur, aucun changement de
comportement local, et une bascule complète de ce que du code générique fait
du service — exactement les trois lignes de la section 2, une quatrième
s'ajoutant sans qu'une ligne du programme n'ait bougé.

### Le test qui attrape la troisième

```go
// theTwentySixMethods is the snapshot of the public interface of
// *before.Service, on 7 October 2026, under Go 1.23.
var theTwentySixMethods = []string{
    "Call",
    "Fatal", "Fatalf", "Fatalln", "Flags",
    "Increment", "Lock",
    "MarshalJSON", "Now",
    "Output",
    "Panic", "Panicf", "Panicln", "Prefix", "Print", "Printf", "Println",
    "SetFlags", "SetOutput", "SetPrefix", "String",
    "Total", "TryLock",
    "Unlock",
    "Value", "Writer",
}

// TestTheSetOfExportedMethodsIsFrozen is the test asked for by
// question 8, for the third thing: the quietest.
//
// When a library adds a method to an embedded type, three
// things can happen. This one catches the third: the type starts to
// satisfy an interface nobody wanted, without a line of the
// program moving and without any compilation failing.
//
// This test has an exact precedent: sync.Mutex gained TryLock in Go 1.18.
// The team that had this snapshot would have seen it turn red the day of the
// version bump, with the name of the added method in the message. The
// others never knew it.
//
// Note that the snapshot is updated by whoever breaks the contract, and
// that the update is a DECISION: one must look at the added method
// and say what it changes, not fix the list to go back to green.
func TestTheSetOfExportedMethodsIsFrozen(t *testing.T) {
    ty := reflect.TypeOf(mount())
    seen := map[string]bool{}
    for i := 0; i < ty.NumMethod(); i++ {
        seen[ty.Method(i).Name] = true
    }
    wanted := map[string]bool{}
    for _, name := range theTwentySixMethods {
        wanted[name] = true
    }
    for name := range seen {
        if !wanted[name] {
            t.Errorf("method APPEARED: %s: a library added it to an"+
                " embedded type. Say what it changes before adding it.", name)
        }
    }
    for name := range wanted {
        if !seen[name] {
            t.Errorf("method DISAPPEARED: %s: an embedded type removed it,"+
                " or the embedding changed", name)
        }
    }
    if len(theTwentySixMethods) != len(wanted) {
        t.Fatalf("the list holds %d entries for %d distinct names:"+
            " there is a duplicate", len(theTwentySixMethods), len(wanted))
    }
    t.Logf("%d methods, snapshot matches", len(seen))
}
```

```
26 methodes, instantane conforme
```

Ce test a un précédent exact : **`sync.Mutex` a gagné `TryLock` en Go 1.18**.
L'équipe qui aurait eu cet instantané l'aurait vu rougir le jour de la montée
de version, avec le nom de la méthode ajoutée dans le message. Les autres ne
l'ont jamais su — et la leçon 2.3 a elle-même compté « deux méthodes de trop »
avant que son propre test ne réponde trois.

Deux précautions dans ce test, et les deux sont des règles du cours :

- il vérifie les **deux sens** : une méthode apparue et une méthode disparue.
  Un test qui ne vérifie qu'un sens laisse passer la moitié des changements ;
- il refuse les **doublons** dans sa propre liste, parce qu'une liste écrite à
  la main avec un nom en double ferait passer un compte faux.

Et la règle d'usage, qui vaut plus que le test :

> Un test d'instantané est mis à jour par celui qui casse le contrat, et la
> mise à jour est une **décision**. Il faut regarder la méthode ajoutée et
> dire ce qu'elle change, pas corriger la liste pour repasser au vert.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | 26 méthodes exportées pour 1 déclarée. Le chiffre se mesure par `reflect` ; écrit à la main il est faux. |
| ⚫ | Trois des 25 méthodes promues appellent `os.Exit`. Un `*log.Logger` incorporé donne à tous ses appelants le droit d'arrêter le processus. |
| ⚫ | `Lock` et `Unlock` promues rendent le mutex public, donc l'interblocage atteignable depuis l'extérieur sans qu'une ligne du service ne soit fautive. |
| ⚫ | Deux mutex dans un même type, dont un promu, produisent deux lignes de la même forme — `s.Lock()` et `s.Increment()` — qui portent sur deux objets différents. |
| ⚫ | L'incorporation promeut les **champs**. Une dépendance qu'on croyait injectée à la construction devient modifiable à vie, en concurrence d'un appel. |
| ⚫ | `go test -race` est **dynamique** : il confirme les courses qu'un test a su reproduire, il ne les trouve pas. Le champ non exporté, lui, supprime la classe. |
| ⚫ | Trois champs nuls donnent **le même message de panique**. Ce qui les distingue est la pile, et elle pointe une fois le code d'un autre paquet, une fois la bibliothèque standard, une fois le code fautif. |
| ⚫ | Un `recover` déroule la pile avant le `defer` : pour publier la vraie trame, il faut un sous-processus qui panique pour de bon. |
| ⚫ | Le refactoring coûte **31 caractères** et n'enlève aucune ligne. Ce qu'il enlève est une surface : 24 méthodes, 3 interfaces, 2 champs publics, 3 paniques. |
| ⚫ | Les assertions **négatives** — « ce type n'est pas un `sync.Locker` » — valent plus cher que les positives : elles disent ce que personne ne pourra faire. |
| ⚫ | Contre la méthode ajoutée par une bibliothèque, le seul garde-fou est un **instantané de l'ensemble des méthodes exportées**, vérifié dans les deux sens. `sync.Mutex` a gagné `TryLock` en Go 1.18. |
