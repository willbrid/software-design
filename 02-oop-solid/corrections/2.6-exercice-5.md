# Correction 2.6 — Exercice 5 : le moteur de tarification qui allouait

> Rappel de l'énoncé : un refactoring « pour respecter OCP et DIP » transforme
> chaque règle de frais en type, enregistré dans un registre et construit
> depuis la configuration. 412 tests verts. Le vendredi suivant, à la pointe,
> le p99 de l'autorisation passe de 17 à 38 ms, le ramasse-miettes de 4 à
> 21 % du CPU, et 0,4 % des autorisations expirent.

J'ai mesuré les deux versions de l'énoncé, séparé les trois parts du coût, et
écrit la correction qui garde les types et le registre. Vert sous
`go vet ./...` et `go test -race -count=1 ./...`. Campagne de cinq
modifications, 5/5.

## 1. Le mécanisme, en trois phrases

> Pour chaque transaction, le moteur reconstruit les douze règles de sa
> configuration : il fabrique des objets, recopie et trie des tranches, avant
> d'appliquer le premier centime de frais. Ces objets meurent aussitôt, et le
> ramasse-miettes travaille en proportion du débit. À la pointe du vendredi,
> son travail s'ajoute à la file d'attente, et le p99 franchit le délai du
> réseau de cartes.

## 2. La mesure

Un banc par version, `-benchmem`, cinq exécutions. La configuration de
production — douze étapes, dont cinq de tranches à dix paliers — est écrite
dans le test ; la version d'avant ne sait exprimer que ses trois règles, donc
la version d'après est mesurée deux fois : sur les mêmes trois règles, et sur
les douze étapes.

// productionSteps is the production configuration: twelve steps, five of
// them "tiers" with ten tiers each.
func productionSteps() []Step {
    tiersParams := func(k int) Params {
        v := map[string]int64{}
        for i := range 10 {
            v[strconv.Itoa(i*50_000+k)] = int64(120 - i*5)
        }
        return Params{Values: v}
    }
    steps := []Step{{"commission", Params{map[string]int64{"fixed": 25}}}}
    for k := range 5 {
        steps = append(steps, Step{"tiers", tiersParams(k)})
    }
    for range 3 {
        steps = append(steps, Step{"commission", Params{map[string]int64{"fixed": 5}}})
    }
    for range 3 {
        steps = append(steps, Step{"discount", Params{map[string]int64{"CM": 100, "SN": 50}}})
    }
    return steps
}

## 3. Ramené à la pointe

À 4 200 transactions par seconde, avec la configuration de production :

- **222 600 allocations par seconde** (4 200 × 53) ;
- **13,1 Mo par seconde** (4 200 × 3 128 octets) ;
- **25 ms de CPU par seconde** pour la tarification elle-même
  (4 200 × 5,9 µs), soit 2,5 % d'un cœur.

**Ce que je sais** : la version d'avant n'allouait rien sur ce chemin ; la
version d'après y ajoute 13 Mo/s de déchets, qui ne vivent que le temps d'une
transaction, et le travail du ramasse-miettes est proportionnel au débit
d'allocation.

**Ce que je ne sais pas** : si ces 13 Mo/s suffisent à eux seuls à faire
passer le ramasse-miettes de 4 à 21 %. Ça dépend de la taille du tas vivant
et de `GOGC`, que l'énoncé ne donne pas : avec un petit tas vivant, le
ramasse-miettes tourne souvent et ce débit pèse lourd ; avec un gros, moins.
Mon modèle reproduit le **mécanisme**, pas forcément l'**ampleur** — la vraie
configuration a peut-être des paramètres plus gros, et le service alloue
ailleurs. Ce qui trancherait : `GODEBUG=gctrace=1` et un profil
`alloc_space` pris à la pointe, en production. Je ne publierai pas un
pourcentage que je n'ai pas mesuré.

## 4. Pourquoi lundi, mardi, mercredi et jeudi n'ont rien montré

Le coût ajouté est **par transaction**, donc proportionnel au trafic. À trafic
normal, il existe — 13 Mo/s à la pointe, une fraction le reste du temps —,
mais il ne fait franchir aucun seuil : le p99 monte un peu, sans alerte. Il
faut la pointe du vendredi pour que trois choses s'additionnent : le débit
d'allocation au maximum, le ramasse-miettes qui prend du CPU au service, et
les files d'attente qui transforment quelques millisecondes de plus en
dépassement du délai de 50 ms. Et le tableau de bord ne suivait ni les
allocations ni le ramasse-miettes : la cause était visible dès lundi, dans une
métrique que personne ne regardait.

## 5. Le refactoring avait-il tort ?

Il faisait trois choses à la fois. Je les ai séparées, sur les douze étapes :

- **L'interface** coûte presque rien : douze appels indirects, une centaine

- **Le registre** coûte quelque chose — environ 175 ns pour douze recherches
  dans une carte indexée par des chaînes —, sans allouer.
- **La construction par transaction** coûte tout le reste : **5 600 ns et
  52 allocations**. C'est la faute.

OCP et DIP n'étaient pas en cause. Les règles comme types et le registre sont
défendables ; ce qui ne l'est pas, c'est d'avoir payé « une modification de
configuration sans redémarrage » en reconstruisant la configuration **à chaque
transaction**, alors qu'elle change quelques fois par an.

Reste une allocation dans les trois lignes du tableau : je l'explique à la
question 7.

## 6. Corriger sans revenir en arrière

On garde les types, le registre et les fabriques. On les utilise **au
chargement** de la configuration, pas à chaque transaction :

```go
package pricing

import "sync/atomic"

// Compile builds the rules of a configuration, once. This is where the
// registry and the factories are used: at load time, not per transaction.
func Compile(steps []Step) []Rule {
    rules := make([]Rule, 0, len(steps))
    for _, s := range steps {
        rules = append(rules, registry[s.Name](s.Params))
    }
    return rules
}

// Compiled prices with rules built once per configuration. A configuration
// change still applies without a restart: Reload compiles the new rules and
// swaps them atomically; transactions in flight finish with the old ones.
type Compiled struct{ rules atomic.Pointer[[]Rule] }

func NewCompiled(steps []Step) *Compiled {
    c := &Compiled{}
    c.Reload(steps)
    return c
}

// Reload compiles a new configuration and makes it current.
func (c *Compiled) Reload(steps []Step) {
    rules := Compile(steps)
    c.rules.Store(&rules)
}

// Price applies the current rules. It does not allocate.
func (c *Compiled) Price(t *Transaction) {
    for _, r := range *c.rules.Load() {
        r.Apply(t)
    }
}
```

Mesuré : **~129 ns par transaction sur douze étapes**, contre ~5 900 — la même
chose que les règles construites à la main. Les montants ne changent pas — un
test compare le moteur d'origine et la version compilée sur deux
configurations, six montants et trois pays.

Et l'exigence « une modification de configuration s'applique sans
redémarrage » **tient toujours** : `Reload` compile la nouvelle configuration
et la publie par un pointeur atomique. Les transactions en cours finissent
avec l'ancienne, les suivantes prennent la nouvelle, et un test le vérifie.
Ce qu'on perd : une modification de configuration doit **appeler** `Reload`
— un signal, un abonnement au fichier, un point d'administration. Avant, elle
s'appliquait parce que tout était relu à chaque transaction ; c'était
exactement le problème.

## 7. La garantie

```go
// TestPricingDoesNotAllocate is the guarantee: pricing allocates nothing,
// whatever the configuration. It is exact, and it does not depend on the
// load: one transaction is enough to see an allocation.
//
// The transaction is allocated OUTSIDE the measured function. Its address is
// passed to an interface method, so it escapes to the heap whoever prices it
// — in production it already lives there, decoded from the request. What
// this test guards is what Price adds to it.
func TestPricingDoesNotAllocate(t *testing.T) {
    tx := &Transaction{}
    c := NewCompiled(productionSteps())
    if n := testing.AllocsPerRun(1000, func() {
        *tx = Transaction{Amount: 200_000, Country: "CM"}
        c.Price(tx)
    }); n != 0 {
        t.Fatalf("%.1f allocation(s) per transaction", n)
    }
    steps := productionSteps()
    e := Engine{Steps: func() []Step { return steps }}
    n := testing.AllocsPerRun(1000, func() {
        *tx = Transaction{Amount: 200_000, Country: "CM"}
        e.Price(tx)
    })
    t.Logf("for comparison, the engine of 02/03: %.0f allocation(s) per transaction", n)
}

// TestTheTransactionEscapes documents the 32 bytes the first version of the
// test above found: a transaction declared inside the measured function is
// allocated on every call, because its address goes to an interface method.
func TestTheTransactionEscapes(t *testing.T) {
    c := NewCompiled(productionSteps())
    if n := testing.AllocsPerRun(1000, func() {
        tx := Transaction{Amount: 200_000, Country: "CM"}
        c.Price(&tx)
        sink += tx.Fees
    }); n != 1 {
        t.Fatalf("%.1f allocation(s): the escape is gone, and this lesson must say so", n)
    }
}
```

`testing.AllocsPerRun`, de la bibliothèque standard, compte les allocations
moyennes d'une fonction sur mille exécutions. Seuil : **zéro**. Il n'est pas
statistique : une seule allocation par transaction le fait échouer, sur un
portable comme en intégration continue.

```
for comparison, the engine of 02/03: 52 allocation(s) per transaction
--- PASS: TestPricingDoesNotAllocate (0.01s)
--- PASS: TestTheTransactionEscapes (0.00s)
ok      example/c26/ex5/after    0.010s
```

Ce test m'a repris dans sa première version. J'y déclarais la transaction
**dans** la fonction mesurée, et il a échoué avec **une** allocation — sur la
version corrigée. Les 32 octets sont la transaction elle-même : son adresse
est passée à une méthode d'interface, `Apply`, et le compilateur, qui ne
sait pas quelle méthode sera appelée, ne peut pas prouver qu'elle ne la
garde pas. Il la met sur le tas. C'est la ligne `leaking param: t` de
l'analyse d'échappement de `Price` — et c'est l'allocation qui reste dans
les trois lignes du tableau de la question 5.

C'est un coût de l'interface que la leçon 2.6 n'avait pas mesuré : **pas
l'appel, mais l'analyse d'échappement**. Un pointeur passé à une méthode
d'interface s'échappe. Ici il ne coûte rien de plus en production, parce que
la transaction arrive déjà sur le tas, décodée de la requête ; le test mesure
donc ce que la tarification **ajoute**, et un second test fige l'échappement
pour que le jour où il disparaît, la leçon le dise.

Ce que la garantie ne couvre pas : le temps sans allocation (un calcul qui
devient quadratique), les verrous, et les allocations faites **ailleurs** sur
le chemin de l'autorisation — elle ne garde que `Price`.

## 8. « Beaucoup plus extensible »

La question que les relecteurs auraient dû poser :

> **« Combien d'allocations et de nanosecondes par transaction, avant et
> après ? »**

La réponse tenait en un banc de dix lignes, et elle était 0 contre 53. Le
refactoring était peut-être plus extensible ; personne n'avait mesuré ce qu'il
coûtait sur le chemin le plus chaud du système.

## 9. La garantie demandée

> *« Plus jamais un refactoring de conception qui dégrade la latence. »*

**La mesure qui tire avant la production** : pour chaque chemin chaud déclaré
— l'autorisation, la tarification —, un **test d'allocations** à seuil fixe,
comme celui de la question 7, dans la suite de tests ordinaire. Il tourne à
chaque demande de fusion, en quelques millisecondes. À côté, un **banc de
latence** comparé à la branche principale, avec un seuil large — +20 % de
ns/op — parce que le temps est bruité, comme la leçon l'a mesuré.

**Aurait-elle vu cet incident un lundi matin, à trafic normal ?**

**Oui — et c'est tout l'intérêt de mesurer par transaction plutôt qu'à la
charge.** Une allocation se voit sur **une** transaction : le test aurait dit
« 52 allocations » à la demande de fusion, lundi avant 16 h, sans aucun trafic.
La latence, elle, ne se voyait qu'à la pointe, parce qu'elle naît de
l'accumulation. Un test de charge aurait pu la voir, mais il aurait fallu
qu'il reproduise la pointe du vendredi. **On ne cherche pas l'effet là où il
est le plus visible ; on cherche la cause là où elle est la plus petite** :
une transaction, un compteur exact.

## 10. La campagne

```
Reload ne remplace plus la configuration         tuee
Compile oublie la premiere etape                 tuee
Price applique les regles a l'envers             tuee
Price recopie les regles a chaque transaction    tuee
Compile ignore le nom de l'etape                 tuee
5/5 tuees
```

Les cinq sont tuées, et chacune par un garde différent : l'équivalence des
montants voit l'étape oubliée, l'ordre inversé et le nom ignoré ; le test de
rechargement voit la configuration figée ; le test d'allocations voit la copie
des règles réintroduite à chaque transaction — la faute du 02/03 sous sa forme
la plus petite.
