# Correction 2.4 — Exercice 3 : le port de consultation de comptes

> Rappel de l'énoncé : une interface `Account` de cinq méthodes, une
> implémentation HTTP en production, un bouchon en mémoire qui fait passer les
> 64 tests du service, et trois incidents en six mois.

Quatre paquets — `accounts` (le port et sa batterie), `stub`, `httpd`,
`cache` —, verts sous `go vet ./...` et `go test -race -count=1 ./...`. Six
implémentations passées à la batterie. Campagne de vingt et une
modifications, 21/21 après deux passes.

## 1. Une seule cause

> **Le contrat n'était écrit nulle part. Chaque implémentation en a deviné un,
> et elles n'ont pas deviné le même.**

Les trois incidents sont trois endroits où les deux devinettes divergent :

| Incident | Ce que le bouchon a deviné | Ce que la production a deviné | La violation, en termes de la leçon |
|---|---|---|---|
| 1. solde d'un compte inexistant | 0, pas d'erreur | une erreur | **mode d'échec changé** — et c'est le bouchon qui viole |
| 2. bloquer un compte déjà bloqué | rien | une erreur | **mode d'échec changé** — dans l'autre sens |
| 3. ordre des opérations | ordre d'insertion | ordre de la base | **postcondition jamais écrite**, donc impossible à tenir |

Le compilateur n'a rien vu parce qu'il **ne vérifie que les signatures**.
`Balance(id string) (int64, error)` est satisfait par une fonction qui rend
`0, nil` pour tout le monde. Il n'existe pas, en Go, de façon d'écrire dans
une signature « rend `ErrUnknownAccount` si le compte n'existe pas ». Ce qui
n'est pas dans la signature doit être dans un test — et il n'y en avait pas.

Et les 64 tests du service passaient **à cause** du bouchon, pas malgré lui :
un test de service écrit contre un bouchon vérifie le service contre le
contrat *du bouchon*. Il encode la devinette. Plus il y a de tests de service,
plus la mauvaise devinette est solidement installée.

## 2. La batterie : douze clauses

Avant de les écrire, il faut **trancher** l'incident 2, parce que les deux
implémentations ne peuvent pas avoir raison toutes les deux. Je tranche pour
l'idempotence : bloquer un compte déjà bloqué réussit.

L'argument est d'exploitation, pas d'élégance. Un appel `Block` qui expire
côté client a peut-être été exécuté côté cœur. Le client réessaie. Si le
second appel rend une erreur, l'appelant ne sait plus si le compte est
bloqué : il a une erreur pour une opération qui a réussi. **Une opération qui
peut être réessayée doit être idempotente**, sinon chaque réessai est un
incident. Le bouchon avait raison ; c'est la production qui viole.

Les douze clauses :

| # | Clause | Origine |
|---|---|---|
| 1 | `Balance` d'un compte connu rend son solde | lecture — sans elle, les autres ne prouvent rien |
| 2 | `Balance` d'un compte inconnu rend `ErrUnknownAccount` | **incident 1** |
| 3 | `Operations` d'un compte inconnu rend `ErrUnknownAccount` | incident 1, généralisé |
| 4 | `IsBlocked` d'un compte inconnu rend `ErrUnknownAccount` | incident 1, généralisé |
| 5 | `Block` et `Unblock` d'un compte inconnu rendent `ErrUnknownAccount` | incident 1, généralisé |
| 6 | `Block` sans motif rend `ErrReasonRequired`, **et ne bloque pas** | lecture |
| 7 | `Block` puis `Unblock` changent ce que rend `IsBlocked` | lecture |
| 8 | `Block` un compte déjà bloqué réussit | **incident 2** |
| 9 | `Unblock` un compte non bloqué réussit | incident 2, symétrie |
| 10 | `Operations` rend du plus récent au plus ancien | **incident 3** |
| 11 | `Operations` ne rend que ce qui date de `since` ou après, borne incluse | lecture |
| 12 | Lectures et écritures concurrentes ne perdent rien | lecture |

Trois clauses viennent directement des incidents ; **quatre** viennent de
leur généralisation. C'est la remarque qui compte : l'incident 1 porte sur
`Balance`, mais la cause porte sur *toute méthode qui prend un identifiant*.
Corriger `Balance` seul, c'est attendre l'incident 1 bis sur `IsBlocked`. Un
incident se corrige au niveau de sa cause, et la cause ici est « que fait le
port d'un identifiant qui ne désigne rien ».

Les cinq clauses de lecture sont celles que les signatures **impliquent** sans
les dire : `since` existe, donc son sens fait partie du contrat (11) ; un
paramètre `reason` existe, donc son absence a un sens (6) ; un port appelé par
un serveur HTTP est appelé en parallèle (12).

Le cadre de la batterie : ce qu'elle demande à une implémentation, et rien de
plus.

```go
// Harness is all the battery asks of an implementation to put it to the
// test: a way to make an empty one, and a way to put an account in it.
// Nothing more. Every extra method in this Harness is a back door the
// battery allows itself, so one thing it no longer checks through the
// interface.
type Harness struct {
    New  func() Account
    Seed func(a Account, id string, balance int64, ops []Operation)
}

// Failure names a broken clause, and says why.
type Failure struct {
    Clause int
    Name   string
    Origin string
    Reason string
}

func (f Failure) String() string {
    return fmt.Sprintf("clause %d (%s) [%s]: %s",
        f.Clause, f.Name, f.Origin, f.Reason)
}
```

Et une clause, celle de l'incident 1, écrite une fois pour les cinq méthodes :

```go
// expectUnknown writes the "unknown account" clause once for all the methods
// that take an id. The test is on the IDENTITY of the error, not on its
// presence: returning ErrUnavailable for an account that does not exist is
// returning an error, and it still breaks the contract.
func expectUnknown(method string, err error) string {
    if err == nil {
        return method + " succeeded on an account that does not exist"
    }
    if !errors.Is(err, ErrUnknownAccount) {
        return fmt.Sprintf("%s returned %q, not ErrUnknownAccount", method, err)
    }
    return ""
}
```

### Ce que la batterie ne fixe pas

Deux décisions restent ouvertes, et il faut les dire plutôt que les laisser
deviner — c'est précisément ce qui a produit les trois incidents :

- **L'ordre des refus.** `Block("no-such-account", "")` : est-ce
  `ErrReasonRequired` ou `ErrUnknownAccount` ? Mes deux implémentations
  conformes vérifient le motif d'abord, mais aucune clause ne l'exige.
  Un appelant qui brancherait sur cet ordre dépendrait d'une devinette.
- **L'ordre de deux opérations de même date.** `accounts.Sort` départage par
  le libellé, mais la clause 10 utilise des dates distinctes. Je reviens sur
  ce point à la question 4 : c'est la campagne qui l'a trouvé.

## 3. Le relevé

| Implémentation | Clauses 1 à 11 cassées | Clause 12 (sous `-race`) | Total |
|---|---|---|---|
| bouchon naïf (celui de l'énoncé) | 2, 3, 4, 5, 6, 10, 11 | **cassée** | **8 / 12** |
| bouchon conforme | — | tenue | 0 / 12 |
| client HTTP sur le cœur de production | 8, 9 | tenue | **2 / 12** |
| client HTTP sur le cœur corrigé | — | tenue | 0 / 12 |

Le bouchon de l'énoncé est trois cartes et rien d'autre :

```go
// Naive is the statement's stub, as one writes it when the goal is to make
// the service's tests pass: three maps, and nothing else. It passes the
// service's 64 tests. It does not pass the battery.
type Naive struct {
    balances map[string]int64
    ops      map[string][]accounts.Operation
    blocked  map[string]bool
}

func NewNaive() *Naive {
    return &Naive{
        balances: map[string]int64{},
        ops:      map[string][]accounts.Operation{},
        blocked:  map[string]bool{},
    }
}

func (n *Naive) Put(id string, balance int64, ops []accounts.Operation) {
    n.balances[id] = balance
    n.ops[id] = ops
}

func (n *Naive) Balance(id string) (int64, error) { return n.balances[id], nil }

func (n *Naive) Operations(id string, since time.Time) ([]accounts.Operation, error) {
    return n.ops[id], nil
}

func (n *Naive) Block(id string, reason string) error {
    n.blocked[id] = true
    return nil
}

func (n *Naive) Unblock(id string) error {
    delete(n.blocked, id)
    return nil
}

func (n *Naive) IsBlocked(id string) (bool, error) { return n.blocked[id], nil }
```

Il passait les 64 tests du service, et il casse **huit clauses sur douze**.
La sortie de la batterie, telle quelle :

```
clause 2 (Balance of an unknown account returns ErrUnknownAccount) [incident 1]: Balance succeeded on an account that does not exist
clause 3 (Operations of an unknown account returns ErrUnknownAccount) [incident 1, generalized]: Operations succeeded on an account that does not exist
clause 4 (IsBlocked of an unknown account returns ErrUnknownAccount) [incident 1, generalized]: IsBlocked succeeded on an account that does not exist
clause 5 (Block and Unblock of an unknown account return ErrUnknownAccount) [incident 1, generalized]: Block succeeded on an account that does not exist
clause 6 (Block without a reason returns ErrReasonRequired and does not block) [reading]: Block without a reason returned <nil>
clause 10 (Operations returns newest to oldest) [incident 3]: order [salary rent groceries], want [groceries salary rent]
clause 11 (Operations only returns what dates from since or later) [reading]: since March 5: [salary rent groceries], want [groceries salary] (bound included)
```

La correction du bouchon tient en une idée : **une seule carte, et un seul
endroit qui dit « ce compte n'existe pas »**. Le bouchon naïf avait trois
cartes, donc trois réponses possibles à la question « ce compte existe-t-il »,
et aucune ne disait non.

```go
// read returns the account under a read lock, or ErrUnknownAccount. All the
// methods go through it or through write: the "unknown account" clause is
// held in a single place, not five times.
func (c *Compliant) read(id string, f func(*account)) error {
    c.mu.RLock()
    defer c.mu.RUnlock()
    a, ok := c.accounts[id]
    if !ok {
        return accounts.ErrUnknownAccount
    }
    f(a)
    return nil
}
```

### Le retournement : c'est la production qui viole

Le client HTTP casse les clauses 8 et 9, et **le client ne peut pas les
réparer seul**. Le cœur répond 409 à un second blocage :

```go
    case "POST block":
        var body struct{ Reason string }
        _ = json.NewDecoder(r.Body).Decode(&body)
        if body.Reason == "" {
            w.WriteHeader(http.StatusUnprocessableEntity)
            return
        }
        if k.production && k.blocked[id] {
            w.WriteHeader(http.StatusConflict)
            return
        }
        k.blocked[id] = true
        w.WriteHeader(http.StatusNoContent)
    case "DELETE block":
        if k.production && !k.blocked[id] {
            w.WriteHeader(http.StatusConflict)
            return
        }
        k.blocked[id] = false
        w.WriteHeader(http.StatusNoContent)
```

Pour absorber ce 409, le client devrait savoir qu'il signifie « déjà bloqué »
et pas un autre conflit. Il ne le sait pas. La seule façon de le savoir est de
lire `IsBlocked` avant de bloquer — deux appels, non atomiques, avec une
fenêtre entre les deux où un autre client peut débloquer. On aurait remplacé
une violation de contrat par une course.

> Une clause qu'un adaptateur ne peut pas tenir seul est une clause qui
> **déplace le travail de l'autre côté du fil**. Ici : le cœur doit rendre
> 204 sur un blocage idempotent, ou au minimum un code d'erreur distinct pour
> « déjà dans cet état ». Sans l'un ou l'autre, le contrat n'est pas tenable,
> et il faut le dire à l'équipe du cœur avec la clause à la main.

Le client, lui, ne traduit qu'à un endroit, et il ne traduit pas le 409 en une
sentinelle qu'il inventerait :

```go
// translate is the only place where an HTTP status becomes a port error. An
// implementation that translates in several places ends up translating in
// several ways.
func translate(status int) error {
    switch {
    case status >= 200 && status < 300:
        return nil
    case status == http.StatusNotFound:
        return accounts.ErrUnknownAccount
    case status == http.StatusUnprocessableEntity:
        return accounts.ErrReasonRequired
    case status == http.StatusConflict:
        // The core says "conflict". The port has no word for it, and this
        // client does not invent one: it returns it as is. See question 3.
        return errors.New("accounts: the core reports a conflict (409)")
    default:
        return fmt.Errorf("%w: status %d", accounts.ErrUnavailable, status)
    }
}
```

L'incident 3, en revanche, se répare côté client, et c'est ce que le relevé
mesure : le cœur simulé rend l'ordre de sa base (croissant), et la clause 10
tient quand même.

```go
func (c *Client) Operations(id string, since time.Time) ([]accounts.Operation, error) {
    q := "?since=" + url.QueryEscape(since.Format(time.RFC3339Nano))
    var r []operationJSON
    if err := c.do(http.MethodGet, path(id, "/operations"+q), nil, &r); err != nil {
        return nil, err
    }
    ops := make([]accounts.Operation, 0, len(r))
    for _, o := range r {
        ops = append(ops, accounts.Operation{Date: o.Date, Label: o.Label, Amount: o.Amount})
    }
    // The core returns its database's order. The contract states the port's
    // order. The client ALWAYS re-sorts, even if the core already sorts
    // right: the core's order is not documented, and an undocumented order
    // changes.
    accounts.Sort(ops)
    return ops, nil
}
```

## 4. Les trois clauses qui ne s'écrivent pas comme les autres

### L'ordre (clause 10) : comparer à une séquence écrite

```go
        {"Operations returns newest to oldest", "incident 3", func(h Harness) string {
            ops, err := ready(h).Operations(knownID, time.Time{})
            if err != nil {
                return "unexpected error: " + err.Error()
            }
            // We compare to a WRITTEN sequence, not to "is it sorted": an
            // ascending order is sorted too, and that is precisely
            // incident 3.
            got := fmt.Sprint(labels(ops))
            if want := "[groceries salary rent]"; got != want {
                return fmt.Sprintf("order %s, want %s", got, want)
            }
            return ""
        }},
```

Deux pièges, et la clause est écrite contre les deux :

1. **« Est-ce trié » ne suffit pas.** Un ordre croissant est trié. L'incident 3
   est précisément deux implémentations qui trient, chacune dans son sens.
   La clause compare à une séquence de libellés **écrite à la main**.
2. **Le jeu de données doit pouvoir faire échouer.** Les trois opérations sont
   insérées dans un ordre qui n'est ni croissant ni décroissant :

```go
// milestones returns three operations at DISTINCT dates and in an insertion
// order that is neither ascending nor descending: an implementation that
// returns its map as is cannot get it right by luck.
func milestones() []Operation {
    day := func(d int) time.Time {
        return time.Date(2026, time.March, d, 10, 0, 0, 0, time.UTC)
    }
    return []Operation{
        {Date: day(5), Label: "salary", Amount: 310000},
        {Date: day(1), Label: "rent", Amount: -95000},
        {Date: day(9), Label: "groceries", Amount: -4250},
    }
}
```

Avec des opérations insérées dans l'ordre croissant, une implémentation qui
rend sa carte telle quelle et une qui trie à l'envers échoueraient pareil ;
avec un ordre d'insertion décroissant, celle qui ne trie pas du tout
**passerait**. Le jeu de données fait partie de la clause.

Pas de sous-processus : une clause d'ordre échoue en rendant une chaîne.

### Le mode d'échec (clauses 2 à 6) : l'identité, pas la présence

`expectUnknown` (montré plus haut) teste `errors.Is(err, ErrUnknownAccount)`,
pas `err != nil`. Rendre `ErrUnavailable` pour un compte qui n'existe pas,
c'est rendre une erreur — et c'est casser le contrat quand même, parce que
l'appelant qui branche sur `ErrUnavailable` va **réessayer** un compte qui
n'existera jamais.

Le deuxième mode d'échec, c'est la panique. Une implémentation qui panique au
lieu de rendre une erreur ne doit pas emporter la batterie avec elle :

```go
// protectedCall turns a panic into a broken clause. Without it, an
// implementation that panics instead of returning an error does not get a
// red clause: it gets a battery that returns no report at all. Changing its
// failure mode is a Liskov violation like any other, and it must be measured
// like the others.
func protectedCall(f func(Harness) string, h Harness) (reason string) {
    defer func() {
        if r := recover(); r != nil {
            reason = fmt.Sprintf("panicked instead of returning: %v", r)
        }
    }()
    return f(h)
}
```

Toujours pas de sous-processus : une panique se rattrape. C'est toute la
différence avec la clause suivante.

### La concurrence (clause 12) : sous-processus, et sous `-race` seulement

```go
        {"Concurrent reads and writes lose nothing", "reading", func(h Harness) string {
            a := ready(h)
            var g sync.WaitGroup
            for i := range 8 {
                g.Add(1)
                go func() {
                    defer g.Done()
                    for range 500 {
                        if i%2 == 0 {
                            _ = a.Block(knownID, "review")
                            _ = a.Unblock(knownID)
                            continue
                        }
                        _, _ = a.Balance(knownID)
                        _, _ = a.IsBlocked(knownID)
                        _, _ = a.Operations(knownID, time.Time{})
                    }
                }()
            }
            g.Wait()
            // The last write of each writer is an Unblock, so the very last
            // write is one too: the final state is known.
            if b, err := a.IsBlocked(knownID); err != nil || b {
                return fmt.Sprintf("final state IsBlocked = %v, %v", b, err)
            }
            if ops, _ := a.Operations(knownID, time.Time{}); len(ops) != 3 {
                return fmt.Sprintf("%d operations after the load, want 3", len(ops))
            }
            return ""
        }},
```

Cette clause ne peut pas tourner dans le processus de test, pour une raison
précise : une carte Go écrite en concurrence **ne panique pas**. Le runtime
tue le processus avec une `fatal error` que `recover` ne voit jamais. Sur le
bouchon naïf, la clause 12 en processus, c'est une suite de tests qui meurt
sans relevé. D'où la coupe de l'API en deux :

```go
// Check runs the first ELEVEN clauses — those that fit in the test process —
// and returns the list of broken clauses.
func Check(h Harness) []Failure { return run(clauses()[:11], 0, h) }

// CheckConcurrency runs the TWELFTH clause, and it alone. It is apart because
// a Go map written concurrently does not panic: it kills the process with a
// "fatal error" that recover never sees. This clause must therefore run in a
// subprocess, under the race detector.
func CheckConcurrency(h Harness) []Failure { return run(clauses()[11:], 11, h) }
```

Et la deuxième question — sous détecteur de course ou pas ? — je l'ai
**mesurée** au lieu de la supposer. Vingt exécutions de la clause 12 seule,
dans chaque configuration :

| | sans `-race` | avec `-race` |
|---|---|---|
| bouchon naïf | 20 morts sur 20 | 20 courses détectées sur 20 |
| bouchon conforme | 20 réussites | 20 réussites |
| cache pressé (question 8) | **7 réussites, 9 morts, 4 échecs d'état final** | 20 courses détectées sur 20 |

Deux choses sont sorties de cette mesure, et aucune n'était prévue.

**Les vingt morts du bouchon naïf ne disent pas la même chose.** Quinze
`fatal error: concurrent map read and map write`, cinq `fatal error:
concurrent map writes`, selon l'entrelacement. Un pilote qui attendrait l'un
des deux messages échouerait une fois sur quatre, sur une implémentation dont
la faute est pourtant détectée à chaque fois.

**Le cache pressé passe la clause une fois sur trois.** Sa course n'existe que
pendant le premier défaut de cache — quelques microsecondes au début de la
charge — puis toutes les lectures tombent sur la carte remplie, et des
lectures concurrentes d'une carte sont sûres. Et quatre de ses treize échecs
ne sont pas des morts : la clause rend `final state IsBlocked = true`. Si la
première lecture de `IsBlocked` tombe pendant qu'un écrivain tient le blocage,
le cache retient `true` pour toujours — c'est sa faute de la clause 7,
l'invalidation oubliée, que la charge rend visible par hasard. Sans le
détecteur, la clause 12 est un tirage.

> Une clause qui passe de temps en temps sur une implémentation fautive n'est
> pas une clause. **La clause 12 ne s'affirme que sous `go test -race`**, et le
> pilote le dit au lieu de faire semblant :

```go
// TestClause12InASubprocess relaunches the test binary itself, with CLAUSE12
// naming the implementation, and reads what the child said as it died. The
// child is the same binary: it inherits the race detector if the parent was
// built with -race.
func TestClause12InASubprocess(t *testing.T) {
    if os.Getenv("CLAUSE12") != "" {
        t.Skip("already in the child")
    }
    // Without the detector, the clause is a coin toss: out of twenty runs,
    // the naive stub dies twenty times, but the hasty cache passes seven
    // times. A clause that passes now and then on a faulty implementation
    // is not a clause: it only holds under -race.
    if !underDetector {
        t.Skip("clause 12 is only measured under go test -race")
    }
    const race = "WARNING: DATA RACE"
    for _, c := range []struct {
        impl string
        want string // empty: the child must succeed
    }{
        {"naive", race},
        {"compliant", ""},
    } {
        t.Run(c.impl, func(t *testing.T) {
            cmd := exec.Command(os.Args[0],
                "-test.run=^TestClause12InProcess$", "-test.count=1")
            cmd.Env = append(os.Environ(), "CLAUSE12="+c.impl)
            out, err := cmd.CombinedOutput()
            if c.want == "" {
                if err != nil {
                    t.Fatalf("clause 12 breaks on %s:\n%s", c.impl, out)
                }
                return
            }
            if err == nil {
                t.Fatalf("the child succeeded on %s: the clause no longer sees anything", c.impl)
            }
            if !strings.Contains(string(out), c.want) {
                t.Fatalf("the child died without saying %q:\n%s", c.want, out)
            }
        })
    }
}
```

Le fils est le même binaire que le père, relancé avec `os.Args[0]` : il hérite
du détecteur si le père a été compilé avec `-race`, et le pilote n'a besoin ni
de la chaîne d'outils Go ni de recompiler.

| Clause | Comment elle s'écrit | Sous-processus ? |
|---|---|---|
| ordre (10) | comparaison à une séquence écrite, sur un jeu qui peut faire échouer | non |
| mode d'échec (2–6) | `errors.Is` sur la sentinelle ; `recover` par clause pour les paniques | non — une panique se rattrape |
| concurrence (12) | charge mêlant lectures et écritures, puis un état final connu | **oui** — une `fatal error` ne se rattrape pas ; **et sous `-race`** — sans lui, c'est un tirage |

## 5. Où vit la batterie

| Endroit | Ce qu'il permet | Ce qu'il coûte |
|---|---|---|
| **le paquet qui déclare l'interface** (`accounts`) | une seule importation pour les implémentations : port, sentinelles et batterie au même endroit | l'API du paquet grossit (`Harness`, `Failure`, `Check`) ; si la batterie importe `testing`, le paquet de production en dépend |
| **un paquet à côté** (`accountstest`, sur le modèle de `testing/fstest`) | peut importer `testing`, appeler `t.Helper`, piloter des sous-processus ; le paquet de production reste nu | un paquet de plus ; n'accède pas aux non-exportés du port |
| **un fichier `_test.go` partagé** | rien, en fait | un `_test.go` n'est compilé **que** dans les tests de son propre paquet ; il ne s'importe pas. Partagé entre trois paquets, c'est trois copies |

Le troisième endroit est un faux choix : il ne marche que si toutes les
implémentations sont dans le même paquet, et alors il n'y a rien à partager.

J'ai retenu le premier, pour une raison mesurable : la batterie ne fait
**pas** appeler `t.Errorf`, elle rend des `[]Failure`. Elle n'importe donc pas
`testing`, et le paquet `accounts` n'en dépend pas :

```
$ go list -f '{{join .Deps " "}}' ./ex3/accounts | tr ' ' '\n' | grep -c testing
0
```

Mais ce choix a un coût que j'ai payé dans ce corrigé même : le pilote de
sous-processus de la clause 12 a besoin de `testing` et d'`os/exec`, donc il
ne peut pas vivre dans `accounts`. Il est **copié** dans `stub` et dans
`cache` — 52 lignes, deux fois. Au troisième paquet qui en a besoin, la
batterie déménage dans un `accountstest`, pilote compris : deux copies se
surveillent, trois divergent.

## 6. Les sentinelles

```go
// The sentinels are part of the interface just as much as the signatures.
// A method that returns "an error" says nothing; a method that returns
// ErrUnknownAccount says something the caller can branch on.
var (
    ErrUnknownAccount = errors.New("accounts: unknown account")
    ErrReasonRequired = errors.New("accounts: reason required")
    ErrUnavailable    = errors.New("accounts: system unavailable")
)
```

Elles sont déclarées **dans `accounts`, avec l'interface**. Conséquence
directe : chaque implémentation importe le paquet du port.

```
accounts importe :
stub     importe : example/c24/ex3/accounts
httpd    importe : example/c24/ex3/accounts
cache    importe : example/c24/ex3/accounts
```

C'est une exception à la règle des leçons 2.2 et 2.3 — *« une implémentation
n'importe pas son appelant »* —, et elle est légitime pour la raison que la
leçon 2.4 donne : dès qu'un appelant écrit `errors.Is(err,
accounts.ErrUnknownAccount)`, il exige de l'implémentation **cette valeur
précise**. La sentinelle n'est pas un détail d'implémentation, c'est un mot
du contrat, au même titre que le nom `Balance`.

Ce qui reste interdit, et la liste d'importations le vérifie : `accounts`
n'importe **aucune** de ses implémentations. La dépendance va toujours de
l'implémentation vers le port, jamais l'inverse.

L'alternative existe — des erreurs reconnues par comportement, une interface
`interface{ Unknown() bool }` testée avec `errors.As` — et elle supprime
l'importation. Mais elle oblige chaque implémentation à déclarer son type
d'erreur, et elle déplace la question au lieu de la résoudre : la batterie,
elle, doit bien vivre quelque part et nommer ce qu'elle attend.

## 8. Le cache

### Ce qu'un décorateur casse le plus souvent

La leçon le dit en une phrase : **un décorateur doit traduire dans les deux
sens, et l'oubli est toujours dans le sens retour.** Pour un cache, les deux
sens sont :

- **en descendant**, une écriture qui passe par lui doit invalider ce qu'il
  retient — sinon la clause 7 tombe ;
- **en remontant**, un résultat du dessous ne doit être retenu que s'il est
  une valeur — une erreur retenue transforme une panne de dix secondes en
  panne de TTL.

Le cache qu'on écrit en un quart d'heure oublie les deux :

```go
// Hasty is the cache one writes in a quarter of an hour: it holds what
// Balance and IsBlocked return, errors included, and does not know that
// Block exists.
type Hasty struct {
    Next accounts.Account

    balances map[string]heldBalance
    blocks   map[string]heldBlock
}

type heldBalance struct {
    b   int64
    err error
}

type heldBlock struct {
    b   bool
    err error
}

func NewHasty(next accounts.Account) *Hasty {
    return &Hasty{
        Next:     next,
        balances: map[string]heldBalance{},
        blocks:   map[string]heldBlock{},
    }
}

func (h *Hasty) Balance(id string) (int64, error) {
    if r, ok := h.balances[id]; ok {
        return r.b, r.err
    }
    b, err := h.Next.Balance(id)
    h.balances[id] = heldBalance{b, err}
    return b, err
}

func (h *Hasty) IsBlocked(id string) (bool, error) {
    if r, ok := h.blocks[id]; ok {
        return r.b, r.err
    }
    b, err := h.Next.IsBlocked(id)
    h.blocks[id] = heldBlock{b, err}
    return b, err
}

func (h *Hasty) Operations(id string, since time.Time) ([]accounts.Operation, error) {
    return h.Next.Operations(id, since)
}

func (h *Hasty) Block(id, reason string) error { return h.Next.Block(id, reason) }

func (h *Hasty) Unblock(id string) error { return h.Next.Unblock(id) }
```

Passé à la batterie : **une seule clause cassée sur onze**, la 7.

```
clause 7 (Block then Unblock changes what IsBlocked returns) [reading]: after Block, IsBlocked = false, <nil>
```

Une sur onze, pour un cache qui a deux fautes. La deuxième — il retient les
erreurs — est **invisible pour la batterie**, parce que dans la batterie un
compte inconnu reste inconnu pour toujours : retenir `ErrUnknownAccount` ne
change aucun résultat. Pour la voir, il faut faire tomber le dessous puis le
relever, et le `Harness` ne sait pas faire ça. C'est la première chose qu'un
décorateur apprend à la batterie : **ses fautes vivent dans le temps, et la
batterie n'a pas d'horloge.**

Le cache qui tient le contrat :

```go
// readOrAsk is the only read path. It NEVER holds an error: a held
// ErrUnavailable turns a ten-second outage into a TTL-long outage, and a held
// ErrUnknownAccount makes unknown an account opened in the meantime.
func readOrAsk[T any](c *Cache, m map[string]held[T], id string, ask func(string) (T, error)) (T, error) {
    c.mu.Lock()
    r, ok := m[id]
    c.mu.Unlock()
    if ok && c.Now().Before(r.expires) {
        return r.v, nil
    }
    v, err := ask(id)
    if err != nil {
        return v, err
    }
    c.mu.Lock()
    m[id] = held[T]{v: v, expires: c.Now().Add(c.TTL)}
    c.mu.Unlock()
    return v, nil
}

func (c *Cache) Balance(id string) (int64, error) {
    return readOrAsk(c, c.balances, id, c.Next.Balance)
}

func (c *Cache) IsBlocked(id string) (bool, error) {
    return readOrAsk(c, c.blocks, id, c.Next.IsBlocked)
}

// Operations is not held: its result depends on since, and an (id, since)
// key would almost never be reused.
func (c *Cache) Operations(id string, since time.Time) ([]accounts.Operation, error) {
    return c.Next.Operations(id, since)
}

// forget is the DOWNWARD direction of the translation: a write that goes
// through the decorator invalidates what it holds. It is the classic
// omission.
func (c *Cache) forget(id string) {
    c.mu.Lock()
    delete(c.blocks, id)
    c.mu.Unlock()
}

func (c *Cache) Block(id, reason string) error {
    defer c.forget(id)
    return c.Next.Block(id, reason)
}

func (c *Cache) Unblock(id string) error {
    defer c.forget(id)
    return c.Next.Unblock(id)
}
```

### La clause nouvelle : la fraîcheur bornée

Le bouchon et le client HTTP sont la **source** de la valeur qu'ils rendent :
ils tiennent une fraîcheur immédiate sans avoir à la promettre. Le cache ne
l'est pas. Il introduit une clause que les deux autres n'avaient pas à tenir :

> **Clause 13.** Une écriture faite **sous** le décorateur — par un autre
> client du cœur, sans passer par lui — est visible au plus tard TTL après la
> lecture qui l'a précédée. La borne est incluse.

### La batterie peut-elle la vérifier ? Non.

Elle n'a que l'interface, et la clause 13 parle de trois choses que
l'interface ne montre pas :

1. **une porte pour écrire sous le décorateur** — sinon toute écriture passe
   par lui et l'invalide ;
2. **une horloge qu'on avance** — sinon vérifier un TTL de cinq secondes
   coûte cinq secondes par test, et vérifier sa **borne** coûte un test
   instable ;
3. **le seuil**, déclaré par le décorateur — la batterie ne peut pas deviner
   le TTL.

Il faut donc un jeu plus riche, et une clause qui vérifie **les deux côtés du
seuil** — une nanoseconde avant, où la valeur périmée est permise, et au seuil
pile, où elle ne l'est plus :

```go
// clock is the injected clock: without it, checking a five-second TTL costs
// five seconds per test, and checking its bound costs a flaky test.
type clock struct{ t time.Time }

func (c *clock) now() time.Time { return c.t }

// FreshnessHarness is what it takes ON TOP of the Harness to write clause 13:
// a door to write UNDER the decorator, as another client of the core would,
// a clock we move forward, and the threshold the decorator declares.
type FreshnessHarness struct {
    New func(c *clock) (accounts.Account, *stub.Compliant)
    TTL time.Duration
}

// checkFreshness is clause 13: a write made under the decorator is visible at
// most TTL after the read that preceded it. The bound is INCLUDED: at exactly
// TTL, the value must be fresh.
func checkFreshness(h FreshnessHarness) string {
    c := &clock{t: time.Date(2026, time.March, 9, 10, 0, 0, 0, time.UTC)}
    a, under := h.New(c)
    under.Put(id, 100, nil)
    if b, _ := a.Balance(id); b != 100 {
        return "first read wrong"
    }
    under.Put(id, 200, nil) // another client writes, without going through the cache
    c.t = c.t.Add(h.TTL - time.Nanosecond)
    if b, _ := a.Balance(id); b != 100 && b != 200 {
        return "before the threshold, a value that never existed"
    }
    c.t = c.t.Add(time.Nanosecond)
    if b, _ := a.Balance(id); b != 200 {
        return "at the threshold, the returned value is older than TTL"
    }
    return ""
}
```

Le seuil ici est de **cinq secondes**, et ce n'est pas un détail : c'est un
engagement envers l'appelant, qui doit le connaître pour savoir s'il peut
utiliser `Balance` avant un débit. Un solde vieux de cinq secondes est acceptable
pour un affichage, il ne l'est pas pour une autorisation de paiement. **Le
seuil est une clause du contrat du décorateur, et l'appelant qui ne peut pas le
tolérer ne doit pas recevoir le décorateur.** C'est encore Liskov : un cache
n'est substituable au client HTTP que pour les appelants qui tolèrent son TTL.

Et la panne retenue, que la batterie ne voyait pas, devient la clause 14,
avec le même genre de jeu enrichi — un dessous qu'on fait tomber une fois :

```go
// flaky is down for the first n calls to Balance.
type flaky struct {
    *stub.Compliant
    outages int
}

func (f *flaky) Balance(id string) (int64, error) {
    if f.outages > 0 {
        f.outages--
        return 0, accounts.ErrUnavailable
    }
    return f.Compliant.Balance(id)
}

// outageHeld is clause 14: a transient outage of the layer below does not
// outlive the outage. It too requires a richer Harness than the battery's:
// one must be able to bring the layer below down.
func outageHeld(decorate func(accounts.Account) accounts.Account) string {
    s := stub.NewCompliant()
    s.Put(id, 100, nil)
    a := decorate(&flaky{Compliant: s, outages: 1})
    if _, err := a.Balance(id); !errors.Is(err, accounts.ErrUnavailable) {
        return "the outage was not passed on"
    }
    if b, err := a.Balance(id); err != nil || b != 100 {
        return fmt.Sprintf("the outage was held: %d, %v", b, err)
    }
    return ""
}
```

## 9. La campagne

-timeout=60s ./ex3/...`. Les modifications qui ne compilent pas sont rejouées
sous une forme qui compile (`if false && …`) : une modification qui ne compile
pas n'a pas été jouée.

Note de méthode : la première exécution de la campagne n'a pas rendu ce
relevé. Elle s'est **bloquée** sur « Cache écrit sans verrou (2/2) » — un
`Lock` sans `Unlock`, donc un interblocage, et `go test` attend dix minutes par
défaut avant d'abandonner. Un interblocage est une modification tuée, mais il
faut un `-timeout` pour qu'elle le soit en temps raisonnable.

Huit survivants. Aucun n'est une branche à supprimer : les huit réclament un
test. Ils se rangent en quatre familles.

**Le jeu de données ne peut pas faire échouer (2).** « Sort sans
départage » survit parce que les trois jalons ont des dates distinctes ;
« since tronqué à la seconde » survit parce qu'ils sont posés à 10 h 00 pile.
Le premier réclame un test de `Sort` sur des dates égales. Le second réclame
un test d'adaptateur — c'est une clause de **traduction**, le temps traverse
le fil —, avec des opérations à 10:00:00,2 et 10:00:00,8 et un `since` à
10:00:00,5.

**Deux redondances qui se masquent l'une l'autre (2).** Le client vérifie le
motif localement **et** traduit le 422 du cœur. Tant que la vérification
locale tient, le 422 n'arrive jamais : sa traduction est une branche morte.
Tant que la traduction tient, la vérification locale peut disparaître sans que
rien ne change. Chacune des deux modifications survit, à cause de l'autre.

> Une redondance assumée sans un test **de chaque côté** n'est pas une
> redondance. C'est une branche morte qui attend son heure.

Deux tests, donc, un par côté : un tableau sur `translate` directement, et un
serveur qui compte ses appels pour vérifier qu'un `Block` sans motif ne
part pas sur le fil.

```go
// The client checks the reason AND translates the core's 422. Each masks the
// other: as long as the first holds, the second is never reached. A
// deliberate redundancy is therefore tested on both sides, separately.

func TestTranslate(t *testing.T) {
    for _, c := range []struct {
        status int
        want   error
    }{
        {http.StatusOK, nil},
        {http.StatusNoContent, nil},
        {http.StatusNotFound, accounts.ErrUnknownAccount},
        {http.StatusUnprocessableEntity, accounts.ErrReasonRequired},
        {http.StatusInternalServerError, accounts.ErrUnavailable},
        {http.StatusBadGateway, accounts.ErrUnavailable},
    } {
        got := translate(c.status)
        if (c.want == nil) != (got == nil) || (c.want != nil && !errors.Is(got, c.want)) {
            t.Errorf("status %d: %v, want %v", c.status, got, c.want)
        }
    }
}

func TestBlockWithoutAReasonDoesNotCallTheCore(t *testing.T) {
    var calls atomic.Int64
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        calls.Add(1)
        w.WriteHeader(http.StatusNoContent)
    }))
    defer srv.Close()
    c := &Client{Base: srv.URL, HTTP: srv.Client()}
    if err := c.Block("FR76", ""); !errors.Is(err, accounts.ErrReasonRequired) {
        t.Fatalf("Block without a reason: %v", err)
    }
    if n := calls.Load(); n != 0 {
        t.Fatalf("%d call(s) to the core for a malformed request", n)
    }
}
```

**Une clause d'effet qui n'a pas lu avant d'écrire (1).** « Cache.Block
n'invalide plus » survit parce que la clause 7 bloquait sans avoir lu
`IsBlocked` : il n'y avait rien en cache à invalider. `Unblock`, lui, était
couvert, parce que la clause lisait entre les deux. La clause 7 lit
maintenant **avant** la première écriture :

```go
        {"Block then Unblock changes what IsBlocked returns", "reading", func(h Harness) string {
            a := ready(h)
            // We READ before writing. Without this read, the clause cannot
            // see a cache that forgets to invalidate: it would hold nothing.
            if b, err := a.IsBlocked(knownID); err != nil || b {
                return fmt.Sprintf("before Block, IsBlocked = %v, %v", b, err)
            }
            if err := a.Block(knownID, "review"); err != nil {
                return "Block: " + err.Error()
            }
            if b, err := a.IsBlocked(knownID); err != nil || !b {
                return fmt.Sprintf("after Block, IsBlocked = %v, %v", b, err)
            }
            if err := a.Unblock(knownID); err != nil {
                return "Unblock: " + err.Error()
            }
            if b, err := a.IsBlocked(knownID); err != nil || b {
                return fmt.Sprintf("after Unblock, IsBlocked = %v, %v", b, err)
            }
            return ""
        }},
```

C'est aussi pourquoi le message de la clause 7 sur le cache pressé, à la
question 8, dit `after Block` : avant ce correctif, il disait
`after Unblock, IsBlocked = true` — le cache n'avait rien retenu avant le
blocage, et seul le déblocage le prenait en faute.

C'est la même faute que *« un test d'ordre s'observe depuis le point
intermédiaire »* (correction 2.2), vue d'un autre côté : un test d'effet doit
observer l'état **avant** l'effet, sinon il ne voit pas ce qui aurait dû être
oublié.

**La batterie n'est pas testée (3).** Aucune des six implémentations ne rend
une mauvaise sentinelle, ne panique, ou ne bloque en refusant. Donc retirer de
la batterie le test d'identité, le `recover`, ou la vérification de l'effet du
refus ne change aucun relevé. La batterie est du code ; elle se teste comme du
code, avec des fautes connues qu'on lui donne à voir :

```go
// The battery is code, so it gets tested. We feed it known faults, and check
// that it sees them. Each faulty type embeds the compliant stub and overrides
// ONE method: it is safe here, because no method of Compliant calls another
// of its methods on its own receiver (lesson 2.3).

type wrongSentinel struct{ *stub.Compliant }

func (w wrongSentinel) Balance(id string) (int64, error) {
    b, err := w.Compliant.Balance(id)
    if err != nil {
        return 0, accounts.ErrUnavailable
    }
    return b, nil
}

type panicker struct{ *stub.Compliant }

func (panicker) IsBlocked(string) (bool, error) { panic("IsBlocked not written yet") }

type refusalThatBlocks struct{ *stub.Compliant }

func (r refusalThatBlocks) Block(id, reason string) error {
    if reason == "" {
        _ = r.Compliant.Block(id, "?")
        return accounts.ErrReasonRequired
    }
    return r.Compliant.Block(id, reason)
}

func harness(decorate func(*stub.Compliant) accounts.Account) accounts.Harness {
    under := map[accounts.Account]*stub.Compliant{}
    return accounts.Harness{
        New: func() accounts.Account {
            s := stub.NewCompliant()
            a := decorate(s)
            under[a] = s
            return a
        },
        Seed: func(a accounts.Account, id string, b int64, ops []accounts.Operation) {
            under[a].Put(id, b, ops)
        },
    }
}

func broken(h accounts.Harness) []int {
    var out []int
    for _, f := range accounts.Check(h) {
        out = append(out, f.Clause)
    }
    return out
}

func TestTheBatterySeesTheFaultsWeGiveIt(t *testing.T) {
    for _, c := range []struct {
        name     string
        decorate func(*stub.Compliant) accounts.Account
        want     []int
    }{
        {"another sentinel", func(s *stub.Compliant) accounts.Account { return wrongSentinel{s} }, []int{2}},
        {"a panic", func(s *stub.Compliant) accounts.Account { return panicker{s} }, []int{4, 6, 7, 8}},
        {"a refusal that blocks", func(s *stub.Compliant) accounts.Account { return refusalThatBlocks{s} }, []int{6}},
    } {
        if got := broken(harness(c.decorate)); !slices.Equal(got, c.want) {
            t.Errorf("%s: broken clauses %v, want %v", c.name, got, c.want)
        }
    }
}
```

Chaque fautif incorpore le bouchon conforme et surcharge **une** méthode. La
leçon 2.3 dit quand c'est sûr — quand aucune méthode du type incorporé
n'appelle une autre de ses méthodes sur son propre récepteur — et `Compliant`
remplit la condition : toutes ses méthodes passent par `read` et `write`,
jamais par `IsBlocked` ou `Balance`.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Les trois incidents ont une cause : **le contrat n'était écrit nulle part**. Le compilateur ne vérifie que les signatures. |
| ⚫ | Les tests d'un service écrits contre un bouchon vérifient le service contre le contrat **du bouchon**. Plus il y en a, plus la mauvaise devinette est installée. |
| ⚫ | Un incident se corrige au niveau de sa cause. L'incident 1 porte sur `Balance` ; sa clause porte sur les cinq méthodes. |
| ⚫ | Une opération qui peut être réessayée doit être idempotente. Ici, c'est la production qui violait, pas le bouchon. |
| ⚫ | Une clause qu'un adaptateur ne peut pas tenir seul déplace le travail de l'autre côté du fil. Le 409 du cœur ne se répare pas dans le client sans créer une course. |
| ⚫ | Une clause d'ordre compare à une séquence **écrite**, sur un jeu de données capable de la faire échouer. « Est-ce trié » laisse passer l'incident 3. |
| ⚫ | Une clause de mode d'échec teste l'**identité** de l'erreur. Une panique se rattrape par clause ; une `fatal error` ne se rattrape pas. |
| ⚫ | La clause de concurrence tourne dans un sous-processus, et ne s'affirme que sous `-race`. Mesuré : sans lui, le cache pressé passe 7 fois sur 20. |
| ⚫ | Un test qui attend un échec attend sa **classe**, pas son libellé : le même bouchon meurt avec deux messages différents. |
| ⚫ | Les sentinelles sont des mots du contrat : elles vivent avec l'interface, et c'est la seule raison légitime d'importer le paquet du port. |
| ⚫ | Une soixantaine de lignes de batterie par signature, ici comme dans la leçon. Le prix de ce que le compilateur ne vérifie pas. |
| ⚫ | Un décorateur casse ce qu'il ne traduit pas dans les deux sens. Un cache : l'invalidation en descendant, les erreurs en remontant. |
| ⚫ | Les fautes d'un cache vivent dans le temps, et la batterie n'a pas d'horloge. La fraîcheur exige une porte sous le décorateur, une horloge injectée et un seuil déclaré. |
| ⚫ | Le TTL est une clause du contrat du décorateur : le cache n'est substituable que pour les appelants qui le tolèrent. |
| ⚫ | Une redondance sans un test de chaque côté est une branche morte qui attend son heure. |
| ⚫ | La batterie est du code : elle se teste avec des fautes connues. Sans ces tests, trois de ses vérifications pouvaient disparaître sans qu'aucun relevé ne change. |
