# Correction 2.4 — Exercice 3 : le port de consultation de comptes

> Rappel de l'énoncé : une interface `Compte` de cinq méthodes, une
> implémentation HTTP en production, un bouchon en mémoire qui fait passer les
> 64 tests du service, et trois incidents en six mois.

Quatre paquets — `comptes` (le port et sa batterie), `bouchon`, `httpd`,
`cache` —, verts sous `go vet ./...` et `go test -race -count=1 ./...`. Six
implémentations passées à la batterie. Campagne de vingt et une
modifications, 21/21 après deux passes.

## 1. Une seule cause

> **Le contrat n'était écrit nulle part. Chaque implémentation en a deviné un,
> et elles n'ont pas deviné le même.**

Les trois incidents sont trois endroits où les deux devinettes divergent :

| Incident | Ce que le bouchon a deviné | Ce que la production a deviné | La violation, en termes de la leçon |
|---|---|---|---|
| 1. solde d'un compte inexistant | 0, pas d'erreur | une erreur | **mode d'échec changé** — et c'est le bouchon qui viole |
| 2. bloquer un compte déjà bloqué | rien | une erreur | **mode d'échec changé** — dans l'autre sens |
| 3. ordre des opérations | ordre d'insertion | ordre de la base | **postcondition jamais écrite**, donc impossible à tenir |

Le compilateur n'a rien vu parce qu'il **ne vérifie que les signatures**.
`Solde(id string) (int64, error)` est satisfait par une fonction qui rend
`0, nil` pour tout le monde. Il n'existe pas, en Go, de façon d'écrire dans
une signature « rend `ErrCompteInconnu` si le compte n'existe pas ». Ce qui
n'est pas dans la signature doit être dans un test — et il n'y en avait pas.

Et les 64 tests du service passaient **à cause** du bouchon, pas malgré lui :
un test de service écrit contre un bouchon vérifie le service contre le
contrat *du bouchon*. Il encode la devinette. Plus il y a de tests de service,
plus la mauvaise devinette est solidement installée.

## 2. La batterie : douze clauses

Avant de les écrire, il faut **trancher** l'incident 2, parce que les deux
implémentations ne peuvent pas avoir raison toutes les deux. Je tranche pour
l'idempotence : bloquer un compte déjà bloqué réussit.

L'argument est d'exploitation, pas d'élégance. Un appel `Bloquer` qui expire
côté client a peut-être été exécuté côté cœur. Le client réessaie. Si le
second appel rend une erreur, l'appelant ne sait plus si le compte est
bloqué : il a une erreur pour une opération qui a réussi. **Une opération qui
peut être réessayée doit être idempotente**, sinon chaque réessai est un
incident. Le bouchon avait raison ; c'est la production qui viole.

Les douze clauses :

| # | Clause | Origine |
|---|---|---|
| 1 | `Solde` d'un compte connu rend son solde | lecture — sans elle, les autres ne prouvent rien |
| 2 | `Solde` d'un compte inconnu rend `ErrCompteInconnu` | **incident 1** |
| 3 | `Operations` d'un compte inconnu rend `ErrCompteInconnu` | incident 1, généralisé |
| 4 | `EstBloque` d'un compte inconnu rend `ErrCompteInconnu` | incident 1, généralisé |
| 5 | `Bloquer` et `Debloquer` d'un compte inconnu rendent `ErrCompteInconnu` | incident 1, généralisé |
| 6 | `Bloquer` sans motif rend `ErrMotifRequis`, **et ne bloque pas** | lecture |
| 7 | `Bloquer` puis `Debloquer` changent ce que rend `EstBloque` | lecture |
| 8 | `Bloquer` un compte déjà bloqué réussit | **incident 2** |
| 9 | `Debloquer` un compte non bloqué réussit | incident 2, symétrie |
| 10 | `Operations` rend du plus récent au plus ancien | **incident 3** |
| 11 | `Operations` ne rend que ce qui date de `depuis` ou après, borne incluse | lecture |
| 12 | Lectures et écritures concurrentes ne perdent rien | lecture |

Trois clauses viennent directement des incidents ; **quatre** viennent de
leur généralisation. C'est la remarque qui compte : l'incident 1 porte sur
`Solde`, mais la cause porte sur *toute méthode qui prend un identifiant*.
Corriger `Solde` seul, c'est attendre l'incident 1 bis sur `EstBloque`. Un
incident se corrige au niveau de sa cause, et la cause ici est « que fait le
port d'un identifiant qui ne désigne rien ».

Les cinq clauses de lecture sont celles que les signatures **impliquent** sans
les dire : `depuis` existe, donc son sens fait partie du contrat (11) ; un
paramètre `motif` existe, donc son absence a un sens (6) ; un port appelé par
un serveur HTTP est appelé en parallèle (12).

Le cadre de la batterie : ce qu'elle demande à une implémentation, et rien de
plus.

```go
// Jeu est tout ce que la batterie demande a une implementation pour pouvoir la
// mettre a l'epreuve : de quoi en fabriquer une vide, et de quoi y poser un
// compte. Rien de plus. Chaque methode en plus dans ce Jeu est une porte
// derobee que la batterie s'autorise, donc une chose qu'elle ne verifie plus
// par l'interface.
type Jeu struct {
    Nouveau   func() Compte
    Alimenter func(c Compte, id string, solde int64, ops []Operation)
}

// Echec designe une clause cassee, et dit pourquoi.
type Echec struct {
    Clause  int
    Nom     string
    Origine string
    Raison  string
}

func (e Echec) String() string {
    return fmt.Sprintf("clause %d (%s) [%s] : %s",
        e.Clause, e.Nom, e.Origine, e.Raison)
}
```

Et une clause, celle de l'incident 1, écrite une fois pour les cinq méthodes :

```go
// attendInconnu ecrit la clause « compte inconnu » une fois pour toutes les
// methodes qui prennent un id. Le test porte sur l'IDENTITE de l'erreur, pas
// sur sa presence : rendre ErrIndisponible pour un compte qui n'existe pas,
// c'est rendre une erreur, et c'est quand meme casser le contrat.
func attendInconnu(methode string, err error) string {
    if err == nil {
        return methode + " a reussi sur un compte qui n'existe pas"
    }
    if !errors.Is(err, ErrCompteInconnu) {
        return fmt.Sprintf("%s a rendu %q, pas ErrCompteInconnu", methode, err)
    }
    return ""
}
```

### Ce que la batterie ne fixe pas

Deux décisions restent ouvertes, et il faut les dire plutôt que les laisser
deviner — c'est précisément ce qui a produit les trois incidents :

- **L'ordre des refus.** `Bloquer("compte-qui-n-existe-pas", "")` : est-ce
  `ErrMotifRequis` ou `ErrCompteInconnu` ? Mes deux implémentations
  conformes vérifient le motif d'abord, mais aucune clause ne l'exige.
  Un appelant qui brancherait sur cet ordre dépendrait d'une devinette.
- **L'ordre de deux opérations de même date.** `comptes.Trier` départage par
  le libellé, mais la clause 10 utilise des dates distinctes. Je reviens sur
  ce point à la question 4 : c'est la campagne qui l'a trouvé.

## 3. Le relevé

| Implémentation | Clauses 1 à 11 cassées | Clause 12 (sous `-race`) | Total |
|---|---|---|---|
| bouchon naïf (celui de l'énoncé) | 2, 3, 4, 5, 6, 10, 11 | **cassée** | **8 / 12** |
| bouchon conforme | — | tenue | 0 / 12 |
| client HTTP sur le cœur de production | 8, 9 | tenue | **2 / 12** |
| client HTTP sur le cœur corrigé | — | tenue | 0 / 12 |

Le bouchon de l'énoncé est trois cartes et rien d'autre :

```go
// Naif est le bouchon de l'enonce, tel qu'on l'ecrit quand le but est de
// faire passer les tests du service : trois cartes, et rien d'autre. Il passe
// les 64 tests du service. Il ne passe pas la batterie.
type Naif struct {
    soldes map[string]int64
    ops    map[string][]comptes.Operation
    bloque map[string]bool
}

func NouveauNaif() *Naif {
    return &Naif{
        soldes: map[string]int64{},
        ops:    map[string][]comptes.Operation{},
        bloque: map[string]bool{},
    }
}

func (n *Naif) Poser(id string, solde int64, ops []comptes.Operation) {
    n.soldes[id] = solde
    n.ops[id] = ops
}

func (n *Naif) Solde(id string) (int64, error) { return n.soldes[id], nil }

func (n *Naif) Operations(id string, depuis time.Time) ([]comptes.Operation, error) {
    return n.ops[id], nil
}

func (n *Naif) Bloquer(id string, motif string) error {
    n.bloque[id] = true
    return nil
}

func (n *Naif) Debloquer(id string) error {
    delete(n.bloque, id)
    return nil
}

func (n *Naif) EstBloque(id string) (bool, error) { return n.bloque[id], nil }
```

Il passait les 64 tests du service, et il casse **huit clauses sur douze**.
La sortie de la batterie, telle quelle :

```
clause 2 (Solde d'un compte inconnu rend ErrCompteInconnu) [incident 1] : Solde a reussi sur un compte qui n'existe pas
clause 3 (Operations d'un compte inconnu rend ErrCompteInconnu) [incident 1, generalise] : Operations a reussi sur un compte qui n'existe pas
clause 4 (EstBloque d'un compte inconnu rend ErrCompteInconnu) [incident 1, generalise] : EstBloque a reussi sur un compte qui n'existe pas
clause 5 (Bloquer et Debloquer un compte inconnu rendent ErrCompteInconnu) [incident 1, generalise] : Bloquer a reussi sur un compte qui n'existe pas
clause 6 (Bloquer sans motif rend ErrMotifRequis et ne bloque pas) [lecture] : Bloquer sans motif a rendu <nil>
clause 10 (Operations rend du plus recent au plus ancien) [incident 3] : ordre [salaire loyer courses], attendu [courses salaire loyer]
clause 11 (Operations ne rend que ce qui date de depuis ou apres) [lecture] : depuis le 5 mars : [salaire loyer courses], attendu [courses salaire] (borne incluse)
```

La correction du bouchon tient en une idée : **une seule carte, et un seul
endroit qui dit « ce compte n'existe pas »**. Le bouchon naïf avait trois
cartes, donc trois réponses possibles à la question « ce compte existe-t-il »,
et aucune ne disait non.

```go
// lire rend le compte sous verrou de lecture, ou ErrCompteInconnu. Toutes les
// methodes passent par lui ou par ecrire : la clause « compte inconnu » est
// tenue a un seul endroit, et pas cinq fois.
func (c *Conforme) lire(id string, f func(*compte)) error {
    c.mu.RLock()
    defer c.mu.RUnlock()
    k, ok := c.comptes[id]
    if !ok {
        return comptes.ErrCompteInconnu
    }
    f(k)
    return nil
}
```

### Le retournement : c'est la production qui viole

Le client HTTP casse les clauses 8 et 9, et **le client ne peut pas les
réparer seul**. Le cœur répond 409 à un second blocage :

```go
    case "POST blocage":
        var corps struct{ Motif string }
        _ = json.NewDecoder(r.Body).Decode(&corps)
        if corps.Motif == "" {
            w.WriteHeader(http.StatusUnprocessableEntity)
            return
        }
        if n.production && n.bloques[id] {
            w.WriteHeader(http.StatusConflict)
            return
        }
        n.bloques[id] = true
        w.WriteHeader(http.StatusNoContent)
    case "DELETE blocage":
        if n.production && !n.bloques[id] {
            w.WriteHeader(http.StatusConflict)
            return
        }
        n.bloques[id] = false
        w.WriteHeader(http.StatusNoContent)
```

Pour absorber ce 409, le client devrait savoir qu'il signifie « déjà bloqué »
et pas un autre conflit. Il ne le sait pas. La seule façon de le savoir est de
lire `EstBloque` avant de bloquer — deux appels, non atomiques, avec une
fenêtre entre les deux où un autre client peut débloquer. On aurait remplacé
une violation de contrat par une course.

> Une clause qu'un adaptateur ne peut pas tenir seul est une clause qui
> **déplace le travail de l'autre côté du fil**. Ici : le cœur doit rendre
> 204 sur un blocage idempotent, ou au minimum un code d'erreur distinct pour
> « déjà dans cet état ». Sans l'un ou l'autre, le contrat n'est pas tenable,
> et il faut le dire à l'équipe du cœur avec la clause à la main.

Le client, lui, ne traduit qu'à un endroit, et il ne traduit pas le 409 en une
sentinelle qu'il inventerait :

```go
// traduire est le seul endroit ou un statut HTTP devient une erreur du port.
// Une implementation qui traduit a plusieurs endroits finit par traduire de
// plusieurs facons.
func traduire(statut int) error {
    switch {
    case statut >= 200 && statut < 300:
        return nil
    case statut == http.StatusNotFound:
        return comptes.ErrCompteInconnu
    case statut == http.StatusUnprocessableEntity:
        return comptes.ErrMotifRequis
    case statut == http.StatusConflict:
        // Le coeur dit « conflit ». Le port n'a pas de mot pour ca, et ce
        // client n'en invente pas : il le rend tel quel. Voir la question 3.
        return errors.New("comptes : le coeur signale un conflit (409)")
    default:
        return fmt.Errorf("%w : statut %d", comptes.ErrIndisponible, statut)
    }
}
```

L'incident 3, en revanche, se répare côté client, et c'est ce que le relevé
mesure : le cœur simulé rend l'ordre de sa base (croissant), et la clause 10
tient quand même.

```go
func (c *Client) Operations(id string, depuis time.Time) ([]comptes.Operation, error) {
    q := "?depuis=" + url.QueryEscape(depuis.Format(time.RFC3339Nano))
    var r []operationJSON
    if err := c.faire(http.MethodGet, chemin(id, "/operations"+q), nil, &r); err != nil {
        return nil, err
    }
    ops := make([]comptes.Operation, 0, len(r))
    for _, o := range r {
        ops = append(ops, comptes.Operation{Date: o.Date, Libelle: o.Libelle, Montant: o.Montant})
    }
    // Le coeur rend l'ordre de sa base. Le contrat dit l'ordre du port. Le
    // client retrie TOUJOURS, meme si le coeur trie deja bien : l'ordre du
    // coeur n'est pas documente, et un ordre non documente change.
    comptes.Trier(ops)
    return ops, nil
}
```

## 4. Les trois clauses qui ne s'écrivent pas comme les autres

### L'ordre (clause 10) : comparer à une séquence écrite

```go
        {"Operations rend du plus recent au plus ancien", "incident 3", func(j Jeu) string {
            ops, err := pret(j).Operations(idConnu, time.Time{})
            if err != nil {
                return "erreur inattendue : " + err.Error()
            }
            // On compare a une sequence ECRITE, pas a « est-ce trie » : un
            // ordre croissant est trie lui aussi, et c'est precisement
            // l'incident 3.
            got := fmt.Sprint(libelles(ops))
            if want := "[courses salaire loyer]"; got != want {
                return fmt.Sprintf("ordre %s, attendu %s", got, want)
            }
            return ""
        }},
```

Deux pièges, et la clause est écrite contre les deux :

1. **« Est-ce trié » ne suffit pas.** Un ordre croissant est trié. L'incident 3
   est précisément deux implémentations qui trient, chacune dans son sens.
   La clause compare à une séquence de libellés **écrite à la main**.
2. **Le jeu de données doit pouvoir faire échouer.** Les trois opérations sont
   insérées dans un ordre qui n'est ni croissant ni décroissant :

```go
// jalons rend trois operations a dates DISTINCTES et dans un ordre
// d'insertion qui n'est ni croissant ni decroissant : une implementation qui
// rend sa carte telle quelle ne peut pas tomber juste par chance.
func jalons() []Operation {
    jour := func(j int) time.Time {
        return time.Date(2026, time.March, j, 10, 0, 0, 0, time.UTC)
    }
    return []Operation{
        {Date: jour(5), Libelle: "salaire", Montant: 310000},
        {Date: jour(1), Libelle: "loyer", Montant: -95000},
        {Date: jour(9), Libelle: "courses", Montant: -4250},
    }
}
```

Avec des opérations insérées dans l'ordre croissant, une implémentation qui
rend sa carte telle quelle et une qui trie à l'envers échoueraient pareil ;
avec un ordre d'insertion décroissant, celle qui ne trie pas du tout
**passerait**. Le jeu de données fait partie de la clause.

Pas de sous-processus : une clause d'ordre échoue en rendant une chaîne.

### Le mode d'échec (clauses 2 à 6) : l'identité, pas la présence

`attendInconnu` (montré plus haut) teste `errors.Is(err, ErrCompteInconnu)`,
pas `err != nil`. Rendre `ErrIndisponible` pour un compte qui n'existe pas,
c'est rendre une erreur — et c'est casser le contrat quand même, parce que
l'appelant qui branche sur `ErrIndisponible` va **réessayer** un compte qui
n'existera jamais.

Le deuxième mode d'échec, c'est la panique. Une implémentation qui panique au
lieu de rendre une erreur ne doit pas emporter la batterie avec elle :

```go
// appelProtege transforme une panique en clause cassee. Sans lui, une
// implementation qui panique au lieu de rendre une erreur n'a pas une clause
// rouge : elle a une batterie qui ne rend aucun relevé. Changer son mode
// d'echec, c'est une violation de Liskov comme une autre, et elle doit se
// mesurer comme les autres.
func appelProtege(f func(Jeu) string, j Jeu) (raison string) {
    defer func() {
        if r := recover(); r != nil {
            raison = fmt.Sprintf("a panique au lieu de rendre : %v", r)
        }
    }()
    return f(j)
}
```

Toujours pas de sous-processus : une panique se rattrape. C'est toute la
différence avec la clause suivante.

### La concurrence (clause 12) : sous-processus, et sous `-race` seulement

```go
        {"Lectures et ecritures concurrentes ne perdent rien", "lecture", func(j Jeu) string {
            c := pret(j)
            var g sync.WaitGroup
            for i := range 8 {
                g.Add(1)
                go func() {
                    defer g.Done()
                    for range 500 {
                        if i%2 == 0 {
                            _ = c.Bloquer(idConnu, "controle")
                            _ = c.Debloquer(idConnu)
                            continue
                        }
                        _, _ = c.Solde(idConnu)
                        _, _ = c.EstBloque(idConnu)
                        _, _ = c.Operations(idConnu, time.Time{})
                    }
                }()
            }
            g.Wait()
            // La derniere ecriture de chaque ecrivain est un Debloquer, donc
            // la derniere ecriture tout court aussi : l'etat final est connu.
            if b, err := c.EstBloque(idConnu); err != nil || b {
                return fmt.Sprintf("etat final EstBloque = %v, %v", b, err)
            }
            if ops, _ := c.Operations(idConnu, time.Time{}); len(ops) != 3 {
                return fmt.Sprintf("%d operations apres la charge, attendu 3", len(ops))
            }
            return ""
        }},
```

Cette clause ne peut pas tourner dans le processus de test, pour une raison
précise : une carte Go écrite en concurrence **ne panique pas**. Le runtime
tue le processus avec une `fatal error` que `recover` ne voit jamais. Sur le
bouchon naïf, la clause 12 en processus, c'est une suite de tests qui meurt
sans relevé. D'où la coupe de l'API en deux :

```go
// Verifier passe les ONZE premieres clauses — celles qui tiennent dans le
// processus de test — et rend la liste des clauses cassees.
func Verifier(j Jeu) []Echec { return passer(clauses()[:11], 0, j) }

// VerifierConcurrence passe la DOUZIEME clause, et elle seule. Elle est a
// part parce qu'une carte Go ecrite en concurrence ne panique pas : elle tue
// le processus avec une « fatal error » que recover ne voit jamais. Cette
// clause doit donc tourner dans un sous-processus, sous le detecteur de
// course.
func VerifierConcurrence(j Jeu) []Echec { return passer(clauses()[11:], 11, j) }
```

Et la deuxième question — sous détecteur de course ou pas ? — je l'ai
**mesurée** au lieu de la supposer. Vingt exécutions de la clause 12 seule,
dans chaque configuration :

| | sans `-race` | avec `-race` |
|---|---|---|
| bouchon naïf | 20 morts sur 20 | 20 courses détectées sur 20 |
| bouchon conforme | 20 réussites | 20 réussites |
| cache pressé (question 8) | **11 réussites, 9 morts** | 20 courses détectées sur 20 |

Deux choses sont sorties de cette mesure, et aucune n'était prévue.

**Les vingt morts du bouchon naïf ne disent pas la même chose.** Quinze
`fatal error: concurrent map read and map write`, cinq `fatal error:
concurrent map writes`, selon l'entrelacement. Un pilote qui attendrait l'un
des deux messages échouerait une fois sur quatre, sur une implémentation dont
la faute est pourtant détectée à chaque fois.

**Le cache pressé passe la clause une fois sur deux.** Sa course n'existe que
pendant le premier défaut de cache — quelques microsecondes au début de la
charge — puis toutes les lectures tombent sur la carte remplie, et des
lectures concurrentes d'une carte sont sûres. Sans le détecteur, la clause 12
est un tirage à pile ou face.

> Une clause qui passe une fois sur deux sur une implémentation fautive n'est
> pas une clause. **La clause 12 ne s'affirme que sous `go test -race`**, et le
> pilote le dit au lieu de faire semblant :

```go
// TestClause12DansUnSousProcessus relance le binaire de test lui-meme, avec
// CLAUSE12 qui designe l'implementation, et lit ce que le fils a dit en
// mourant. Le fils est le meme binaire : il herite du detecteur de course si
// le pere a ete compile avec -race.
func TestClause12DansUnSousProcessus(t *testing.T) {
    if os.Getenv("CLAUSE12") != "" {
        t.Skip("deja dans le fils")
    }
    // Sans le detecteur, la clause est un tirage : sur vingt executions, le
    // bouchon naif meurt vingt fois, mais le cache presse passe onze fois. Une
    // clause qui passe une fois sur deux sur une implementation fautive n'est
    // pas une clause : elle ne s'affirme que sous -race.
    if !sousDetecteur {
        t.Skip("la clause 12 ne se mesure que sous go test -race")
    }
    const naif = "WARNING: DATA RACE"
    for _, c := range []struct {
        cas     string
        attendu string // vide : le fils doit reussir
    }{
        {"naif", naif},
        {"conforme", ""},
    } {
        t.Run(c.cas, func(t *testing.T) {
            cmd := exec.Command(os.Args[0],
                "-test.run=^TestClause12EnProcessus$", "-test.count=1")
            cmd.Env = append(os.Environ(), "CLAUSE12="+c.cas)
            sortie, err := cmd.CombinedOutput()
            if c.attendu == "" {
                if err != nil {
                    t.Fatalf("la clause 12 casse sur %s :\n%s", c.cas, sortie)
                }
                return
            }
            if err == nil {
                t.Fatalf("le fils a reussi sur %s : la clause ne voit plus rien", c.cas)
            }
            if !strings.Contains(string(sortie), c.attendu) {
                t.Fatalf("le fils est mort sans dire %q :\n%s", c.attendu, sortie)
            }
        })
    }
}
```

Le fils est le même binaire que le père, relancé avec `os.Args[0]` : il hérite
du détecteur si le père a été compilé avec `-race`, et le pilote n'a besoin ni
de la chaîne d'outils Go ni de recompiler.

| Clause | Comment elle s'écrit | Sous-processus ? |
|---|---|---|
| ordre (10) | comparaison à une séquence écrite, sur un jeu qui peut faire échouer | non |
| mode d'échec (2–6) | `errors.Is` sur la sentinelle ; `recover` par clause pour les paniques | non — une panique se rattrape |
| concurrence (12) | charge mêlant lectures et écritures, puis un état final connu | **oui** — une `fatal error` ne se rattrape pas ; **et sous `-race`** — sans lui, c'est un tirage |

## 5. Où vit la batterie

| Endroit | Ce qu'il permet | Ce qu'il coûte |
|---|---|---|
| **le paquet qui déclare l'interface** (`comptes`) | une seule importation pour les implémentations : port, sentinelles et batterie au même endroit | l'API du paquet grossit (`Jeu`, `Echec`, `Verifier`) ; si la batterie importe `testing`, le paquet de production en dépend |
| **un paquet à côté** (`comptestest`, sur le modèle de `testing/fstest`) | peut importer `testing`, appeler `t.Helper`, piloter des sous-processus ; le paquet de production reste nu | un paquet de plus ; n'accède pas aux non-exportés du port |
| **un fichier `_test.go` partagé** | rien, en fait | un `_test.go` n'est compilé **que** dans les tests de son propre paquet ; il ne s'importe pas. Partagé entre trois paquets, c'est trois copies |

Le troisième endroit est un faux choix : il ne marche que si toutes les
implémentations sont dans le même paquet, et alors il n'y a rien à partager.

J'ai retenu le premier, pour une raison mesurable : la batterie ne fait
**pas** appeler `t.Errorf`, elle rend des `[]Echec`. Elle n'importe donc pas
`testing`, et le paquet `comptes` n'en dépend pas :

```
$ go list -f '{{join .Deps " "}}' ./ex3/comptes | tr ' ' '\n' | grep -c testing
0
```

Mais ce choix a un coût que j'ai payé dans ce corrigé même : le pilote de
sous-processus de la clause 12 a besoin de `testing` et d'`os/exec`, donc il
ne peut pas vivre dans `comptes`. Il est **copié** dans `bouchon` et dans
`cache` — 52 lignes, deux fois. Au troisième paquet qui en a besoin, la
batterie déménage dans un `comptestest`, pilote compris : deux copies se
surveillent, trois divergent.

## 6. Les sentinelles

```go
// Les sentinelles font partie de l'interface au meme titre que les signatures.
// Une methode qui rend « une erreur » ne dit rien ; une methode qui rend
// ErrCompteInconnu dit quelque chose sur quoi l'appelant peut brancher.
var (
    ErrCompteInconnu = errors.New("comptes : compte inconnu")
    ErrMotifRequis   = errors.New("comptes : motif requis")
    ErrIndisponible  = errors.New("comptes : systeme indisponible")
)
```

Elles sont déclarées **dans `comptes`, avec l'interface**. Conséquence
directe : chaque implémentation importe le paquet du port.

```
comptes  importe :
bouchon  importe : exemple/c24/ex3/comptes
httpd    importe : exemple/c24/ex3/comptes
cache    importe : exemple/c24/ex3/comptes
```

C'est une exception à la règle des leçons 2.2 et 2.3 — *« une implémentation
n'importe pas son appelant »* —, et elle est légitime pour la raison que la
leçon 2.4 donne : dès qu'un appelant écrit `errors.Is(err,
comptes.ErrCompteInconnu)`, il exige de l'implémentation **cette valeur
précise**. La sentinelle n'est pas un détail d'implémentation, c'est un mot
du contrat, au même titre que le nom `Solde`.

Ce qui reste interdit, et la liste d'importations le vérifie : `comptes`
n'importe **aucune** de ses implémentations. La dépendance va toujours de
l'implémentation vers le port, jamais l'inverse.

L'alternative existe — des erreurs reconnues par comportement, une interface
`interface{ Inconnu() bool }` testée avec `errors.As` — et elle supprime
l'importation. Mais elle oblige chaque implémentation à déclarer son type
d'erreur, et elle déplace la question au lieu de la résoudre : la batterie,
elle, doit bien vivre quelque part et nommer ce qu'elle attend.

## 8. Le cache

### Ce qu'un décorateur casse le plus souvent

La leçon le dit en une phrase : **un décorateur doit traduire dans les deux
sens, et l'oubli est toujours dans le sens retour.** Pour un cache, les deux
sens sont :

- **en descendant**, une écriture qui passe par lui doit invalider ce qu'il
  retient — sinon la clause 7 tombe ;
- **en remontant**, un résultat du dessous ne doit être retenu que s'il est
  une valeur — une erreur retenue transforme une panne de dix secondes en
  panne de TTL.

Le cache qu'on écrit en un quart d'heure oublie les deux :

```go
// Presse est le cache qu'on ecrit en un quart d'heure : il retient ce que
// rend Solde et EstBloque, erreurs comprises, et ne sait pas que Bloquer
// existe.
type Presse struct {
    Dessous comptes.Compte

    soldes  map[string]soldeRetenu
    bloques map[string]blocageRetenu
}

type soldeRetenu struct {
    s   int64
    err error
}

type blocageRetenu struct {
    b   bool
    err error
}

func NouveauPresse(dessous comptes.Compte) *Presse {
    return &Presse{
        Dessous: dessous,
        soldes:  map[string]soldeRetenu{},
        bloques: map[string]blocageRetenu{},
    }
}

func (p *Presse) Solde(id string) (int64, error) {
    if r, ok := p.soldes[id]; ok {
        return r.s, r.err
    }
    s, err := p.Dessous.Solde(id)
    p.soldes[id] = soldeRetenu{s, err}
    return s, err
}

func (p *Presse) EstBloque(id string) (bool, error) {
    if r, ok := p.bloques[id]; ok {
        return r.b, r.err
    }
    b, err := p.Dessous.EstBloque(id)
    p.bloques[id] = blocageRetenu{b, err}
    return b, err
}

func (p *Presse) Operations(id string, depuis time.Time) ([]comptes.Operation, error) {
    return p.Dessous.Operations(id, depuis)
}

func (p *Presse) Bloquer(id, motif string) error { return p.Dessous.Bloquer(id, motif) }

func (p *Presse) Debloquer(id string) error { return p.Dessous.Debloquer(id) }
```

Passé à la batterie : **une seule clause cassée sur onze**, la 7.

```
clause 7 (Bloquer puis Debloquer change ce que rend EstBloque) [lecture] : apres Debloquer, EstBloque = true, <nil>
```

Une sur onze, pour un cache qui a deux fautes. La deuxième — il retient les
erreurs — est **invisible pour la batterie**, parce que dans la batterie un
compte inconnu reste inconnu pour toujours : retenir `ErrCompteInconnu` ne
change aucun résultat. Pour la voir, il faut faire tomber le dessous puis le
relever, et le `Jeu` ne sait pas faire ça. C'est la première chose qu'un
décorateur apprend à la batterie : **ses fautes vivent dans le temps, et la
batterie n'a pas d'horloge.**

Le cache qui tient le contrat :

```go
// lireOuDemander est le seul chemin de lecture. Il ne retient JAMAIS une
// erreur : un ErrIndisponible retenu transforme une panne de dix secondes en
// panne de TTL, et un ErrCompteInconnu retenu rend inconnu un compte ouvert
// entre-temps.
func lireOuDemander[T any](c *Cache, carte map[string]retenu[T], id string, demander func(string) (T, error)) (T, error) {
    c.mu.Lock()
    r, ok := carte[id]
    c.mu.Unlock()
    if ok && c.Maintenant().Before(r.expire) {
        return r.v, nil
    }
    v, err := demander(id)
    if err != nil {
        return v, err
    }
    c.mu.Lock()
    carte[id] = retenu[T]{v: v, expire: c.Maintenant().Add(c.TTL)}
    c.mu.Unlock()
    return v, nil
}

func (c *Cache) Solde(id string) (int64, error) {
    return lireOuDemander(c, c.soldes, id, c.Dessous.Solde)
}

func (c *Cache) EstBloque(id string) (bool, error) {
    return lireOuDemander(c, c.bloques, id, c.Dessous.EstBloque)
}

// Operations n'est pas retenue : son resultat depend de depuis, et une cle
// (id, depuis) ne se reutiliserait presque jamais.
func (c *Cache) Operations(id string, depuis time.Time) ([]comptes.Operation, error) {
    return c.Dessous.Operations(id, depuis)
}

// oublier est le sens DESCENDANT de la traduction : une ecriture qui passe par
// le decorateur invalide ce qu'il retient. C'est l'oubli classique.
func (c *Cache) oublier(id string) {
    c.mu.Lock()
    delete(c.bloques, id)
    c.mu.Unlock()
}

func (c *Cache) Bloquer(id, motif string) error {
    defer c.oublier(id)
    return c.Dessous.Bloquer(id, motif)
}

func (c *Cache) Debloquer(id string) error {
    defer c.oublier(id)
    return c.Dessous.Debloquer(id)
}
```

### La clause nouvelle : la fraîcheur bornée

Le bouchon et le client HTTP sont la **source** de la valeur qu'ils rendent :
ils tiennent une fraîcheur immédiate sans avoir à la promettre. Le cache ne
l'est pas. Il introduit une clause que les deux autres n'avaient pas à tenir :

> **Clause 13.** Une écriture faite **sous** le décorateur — par un autre
> client du cœur, sans passer par lui — est visible au plus tard TTL après la
> lecture qui l'a précédée. La borne est incluse.

### La batterie peut-elle la vérifier ? Non.

Elle n'a que l'interface, et la clause 13 parle de trois choses que
l'interface ne montre pas :

1. **une porte pour écrire sous le décorateur** — sinon toute écriture passe
   par lui et l'invalide ;
2. **une horloge qu'on avance** — sinon vérifier un TTL de cinq secondes
   coûte cinq secondes par test, et vérifier sa **borne** coûte un test
   instable ;
3. **le seuil**, déclaré par le décorateur — la batterie ne peut pas deviner
   le TTL.

Il faut donc un jeu plus riche, et une clause qui vérifie **les deux côtés du
seuil** — une nanoseconde avant, où la valeur périmée est permise, et au seuil
pile, où elle ne l'est plus :

```go
// horloge est l'horloge injectee : sans elle, verifier un TTL de cinq secondes
// coute cinq secondes par test, et verifier sa borne coute un test instable.
type horloge struct{ t time.Time }

func (h *horloge) maintenant() time.Time { return h.t }

// JeuFraicheur est ce qu'il faut EN PLUS du Jeu pour ecrire la clause 13 : une
// porte pour ecrire SOUS le decorateur, comme le ferait un autre client du
// coeur, une horloge qu'on avance, et le seuil que le decorateur declare.
type JeuFraicheur struct {
    Nouveau func(h *horloge) (comptes.Compte, *bouchon.Conforme)
    Ttl     time.Duration
}

// verifierFraicheur est la clause 13 : une ecriture faite sous le decorateur
// est visible au plus tard Ttl apres la lecture qui l'a precedee. La borne
// est INCLUSE : a Ttl pile, la valeur doit etre fraiche.
func verifierFraicheur(j JeuFraicheur) string {
    h := &horloge{t: time.Date(2026, time.March, 9, 10, 0, 0, 0, time.UTC)}
    c, dessous := j.Nouveau(h)
    dessous.Poser(id, 100, nil)
    if s, _ := c.Solde(id); s != 100 {
        return "premiere lecture fausse"
    }
    dessous.Poser(id, 200, nil) // un autre client ecrit, sans passer par le cache
    h.t = h.t.Add(j.Ttl - time.Nanosecond)
    if s, _ := c.Solde(id); s != 100 && s != 200 {
        return "avant le seuil, une valeur qui n'a jamais existe"
    }
    h.t = h.t.Add(time.Nanosecond)
    if s, _ := c.Solde(id); s != 200 {
        return "au seuil, la valeur rendue a plus de Ttl"
    }
    return ""
}
```

Le seuil ici est de **cinq secondes**, et ce n'est pas un détail : c'est un
engagement envers l'appelant, qui doit le connaître pour savoir s'il peut
utiliser `Solde` avant un débit. Un solde vieux de cinq secondes est acceptable
pour un affichage, il ne l'est pas pour une autorisation de paiement. **Le
seuil est une clause du contrat du décorateur, et l'appelant qui ne peut pas le
tolérer ne doit pas recevoir le décorateur.** C'est encore Liskov : un cache
n'est substituable au client HTTP que pour les appelants qui tolèrent son TTL.

Et la panne retenue, que la batterie ne voyait pas, devient la clause 14,
avec le même genre de jeu enrichi — un dessous qu'on fait tomber une fois :

```go
// capricieux tombe en panne pour les n premiers appels a Solde.
type capricieux struct {
    *bouchon.Conforme
    pannes int
}

func (c *capricieux) Solde(id string) (int64, error) {
    if c.pannes > 0 {
        c.pannes--
        return 0, comptes.ErrIndisponible
    }
    return c.Conforme.Solde(id)
}

// panneRetenue est la clause 14 : une panne passagere du dessous ne survit
// pas a la panne. Elle aussi exige un Jeu plus riche que la batterie : il
// faut pouvoir faire tomber le dessous.
func panneRetenue(decorer func(comptes.Compte) comptes.Compte) string {
    b := bouchon.NouveauConforme()
    b.Poser(id, 100, nil)
    c := decorer(&capricieux{Conforme: b, pannes: 1})
    if _, err := c.Solde(id); !errors.Is(err, comptes.ErrIndisponible) {
        return "la panne n'a pas ete transmise"
    }
    if s, err := c.Solde(id); err != nil || s != 100 {
        return fmt.Sprintf("la panne a ete retenue : %d, %v", s, err)
    }
    return ""
}
```

## 9. La campagne

Vingt et une modifications, jouées une à une sous `go test -race -count=1
-timeout=60s ./ex3/...`. Les modifications qui ne compilent pas sont rejouées
sous une forme qui compile (`if false && …`) : une modification qui ne compile
pas n'a pas été jouée.

### Première passe

```

Conforme.Bloquer accepte un motif vide           tuee
```

Note de méthode : la première exécution de la campagne n'a pas rendu ce
relevé. Elle s'est **bloquée** sur « Cache écrit sans verrou (2/2) » — un
`Lock` sans `Unlock`, donc un interblocage, et `go test` attend dix minutes par
défaut avant d'abandonner. Un interblocage est une modification tuée, mais il
faut un `-timeout` pour qu'elle le soit en temps raisonnable.

Huit survivants. Aucun n'est une branche à supprimer : les huit réclament un
test. Ils se rangent en quatre familles.

**Le jeu de données ne peut pas faire échouer (2).** « Trier sans
départage » survit parce que les trois jalons ont des dates distinctes ;
« depuis tronqué à la seconde » survit parce qu'ils sont posés à 10 h 00 pile.
Le premier réclame un test de `Trier` sur des dates égales. Le second réclame
un test d'adaptateur — c'est une clause de **traduction**, le temps traverse
le fil —, avec des opérations à 10:00:00,2 et 10:00:00,8 et un `depuis` à
10:00:00,5.

**Deux redondances qui se masquent l'une l'autre (2).** Le client vérifie le
motif localement **et** traduit le 422 du cœur. Tant que la vérification
locale tient, le 422 n'arrive jamais : sa traduction est une branche morte.
Tant que la traduction tient, la vérification locale peut disparaître sans que
rien ne change. Chacune des deux modifications survit, à cause de l'autre.

> Une redondance assumée sans un test **de chaque côté** n'est pas une
> redondance. C'est une branche morte qui attend son heure.

Deux tests, donc, un par côté : un tableau sur `traduire` directement, et un
serveur qui compte ses appels pour vérifier qu'un `Bloquer` sans motif ne
part pas sur le fil.

```go
// Le client verifie le motif ET traduit le 422 du coeur. Chacun masque
// l'autre : tant que le premier tient, le second n'est jamais atteint. Une
// redondance assumee se teste donc des deux cotes, separement.

func TestTraduire(t *testing.T) {
    for _, c := range []struct {
        statut int
        want   error
    }{
        {http.StatusOK, nil},
        {http.StatusNoContent, nil},
        {http.StatusNotFound, comptes.ErrCompteInconnu},
        {http.StatusUnprocessableEntity, comptes.ErrMotifRequis},
        {http.StatusInternalServerError, comptes.ErrIndisponible},
        {http.StatusBadGateway, comptes.ErrIndisponible},
    } {
        got := traduire(c.statut)
        if (c.want == nil) != (got == nil) || (c.want != nil && !errors.Is(got, c.want)) {
            t.Errorf("statut %d : %v, attendu %v", c.statut, got, c.want)
        }
    }
}

func TestBloquerSansMotifNAppellePasLeCoeur(t *testing.T) {
    var appels atomic.Int64
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        appels.Add(1)
        w.WriteHeader(http.StatusNoContent)
    }))
    defer srv.Close()
    c := &Client{Base: srv.URL, HTTP: srv.Client()}
    if err := c.Bloquer("FR76", ""); !errors.Is(err, comptes.ErrMotifRequis) {

    }
    if n := appels.Load(); n != 0 {
        t.Fatalf("%d appel(s) au coeur pour une requete mal formee", n)
    }
```

**Une clause d'effet qui n'a pas lu avant d'écrire (1).** « Cache.Bloquer
n'invalide plus » survit parce que la clause 7 bloquait sans avoir lu
`EstBloque` : il n'y avait rien en cache à invalider. `Debloquer`, lui, était
couvert, parce que la clause lisait entre les deux. La clause 7 lit
maintenant **avant** la première écriture :

```go
        {"Bloquer puis Debloquer change ce que rend EstBloque", "lecture", func(j Jeu) string {
            c := pret(j)
            // On LIT avant d'ecrire. Sans cette lecture, la clause ne peut pas
            // voir un cache qui oublie d'invalider : il n'aurait rien retenu.
            if b, err := c.EstBloque(idConnu); err != nil || b {
                return fmt.Sprintf("avant Bloquer, EstBloque = %v, %v", b, err)
            }
            if err := c.Bloquer(idConnu, "controle"); err != nil {
                return "Bloquer : " + err.Error()
            }
            if b, err := c.EstBloque(idConnu); err != nil || !b {
                return fmt.Sprintf("apres Bloquer, EstBloque = %v, %v", b, err)
            }
            if err := c.Debloquer(idConnu); err != nil {
                return "Debloquer : " + err.Error()
            }
            if b, err := c.EstBloque(idConnu); err != nil || b {
                return fmt.Sprintf("apres Debloquer, EstBloque = %v, %v", b, err)
            }
            return ""
        }},
```

C'est la même faute que *« un test d'ordre s'observe depuis le point
intermédiaire »* (correction 2.2), vue d'un autre côté : un test d'effet doit
observer l'état **avant** l'effet, sinon il ne voit pas ce qui aurait dû être
oublié.

**La batterie n'est pas testée (3).** Aucune des six implémentations ne rend
une mauvaise sentinelle, ne panique, ou ne bloque en refusant. Donc retirer de
la batterie le test d'identité, le `recover`, ou la vérification de l'effet du
refus ne change aucun relevé. La batterie est du code ; elle se teste comme du
code, avec des fautes connues qu'on lui donne à voir :

```go
// La batterie est du code, donc elle se teste. On la nourrit de fautes
// connues, et on verifie qu'elle les voit. Chaque fautif incorpore le bouchon
// conforme et surcharge UNE methode : c'est sur ici, parce qu'aucune methode
// de Conforme n'appelle une autre de ses methodes sur son propre recepteur
// (lecon 2.3).

type mauvaiseSentinelle struct{ *bouchon.Conforme }

func (m mauvaiseSentinelle) Solde(id string) (int64, error) {
    s, err := m.Conforme.Solde(id)
    if err != nil {
        return 0, comptes.ErrIndisponible
    }
    return s, nil
}

type paniqueur struct{ *bouchon.Conforme }

func (paniqueur) EstBloque(string) (bool, error) { panic("EstBloque pas encore ecrit") }

type refusQuiBloque struct{ *bouchon.Conforme }

func (r refusQuiBloque) Bloquer(id, motif string) error {
    if motif == "" {
        _ = r.Conforme.Bloquer(id, "?")
        return comptes.ErrMotifRequis
    }
    return r.Conforme.Bloquer(id, motif)
}

func jeu(decorer func(*bouchon.Conforme) comptes.Compte) comptes.Jeu {
    sous := map[comptes.Compte]*bouchon.Conforme{}
    return comptes.Jeu{
        Nouveau: func() comptes.Compte {
            b := bouchon.NouveauConforme()
            c := decorer(b)
            sous[c] = b
            return c
        },
        Alimenter: func(c comptes.Compte, id string, s int64, ops []comptes.Operation) {
            sous[c].Poser(id, s, ops)
        },
    }
}

func cassees(j comptes.Jeu) []int {
    var out []int
    for _, e := range comptes.Verifier(j) {
        out = append(out, e.Clause)
    }
    return out
}

func TestLaBatterieVoitLesFautesQuOnLuiDonne(t *testing.T) {
    for _, c := range []struct {
        nom     string
        decorer func(*bouchon.Conforme) comptes.Compte
        attendu []int
    }{
        {"une autre sentinelle", func(b *bouchon.Conforme) comptes.Compte { return mauvaiseSentinelle{b} }, []int{2}},
        {"une panique", func(b *bouchon.Conforme) comptes.Compte { return paniqueur{b} }, []int{4, 6, 7, 8}},
        {"un refus qui bloque", func(b *bouchon.Conforme) comptes.Compte { return refusQuiBloque{b} }, []int{6}},
    } {
        if got := cassees(jeu(c.decorer)); !slices.Equal(got, c.attendu) {
            t.Errorf("%s : clauses cassees %v, attendu %v", c.nom, got, c.attendu)
        }
    }
}
```

Chaque fautif incorpore le bouchon conforme et surcharge **une** méthode. La
leçon 2.3 dit quand c'est sûr — quand aucune méthode du type incorporé
n'appelle une autre de ses méthodes sur son propre récepteur — et `Conforme`
remplit la condition : toutes ses méthodes passent par `lire` et `ecrire`,
jamais par `EstBloque` ou `Solde`.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Les trois incidents ont une cause : **le contrat n'était écrit nulle part**. Le compilateur ne vérifie que les signatures. |
| ⚫ | Les tests d'un service écrits contre un bouchon vérifient le service contre le contrat **du bouchon**. Plus il y en a, plus la mauvaise devinette est installée. |
| ⚫ | Un incident se corrige au niveau de sa cause. L'incident 1 porte sur `Solde` ; sa clause porte sur les cinq méthodes. |
| ⚫ | Une opération qui peut être réessayée doit être idempotente. Ici, c'est la production qui violait, pas le bouchon. |
| ⚫ | Une clause qu'un adaptateur ne peut pas tenir seul déplace le travail de l'autre côté du fil. Le 409 du cœur ne se répare pas dans le client sans créer une course. |
| ⚫ | Une clause d'ordre compare à une séquence **écrite**, sur un jeu de données capable de la faire échouer. « Est-ce trié » laisse passer l'incident 3. |
| ⚫ | Une clause de mode d'échec teste l'**identité** de l'erreur. Une panique se rattrape par clause ; une `fatal error` ne se rattrape pas. |
| ⚫ | La clause de concurrence tourne dans un sous-processus, et ne s'affirme que sous `-race`. Mesuré : sans lui, le cache pressé passe 11 fois sur 20. |
| ⚫ | Un test qui attend un échec attend sa **classe**, pas son libellé : le même bouchon meurt avec deux messages différents. |
| ⚫ | Les sentinelles sont des mots du contrat : elles vivent avec l'interface, et c'est la seule raison légitime d'importer le paquet du port. |
| ⚫ | Une soixantaine de lignes de batterie par signature, ici comme dans la leçon. Le prix de ce que le compilateur ne vérifie pas. |
| ⚫ | Un décorateur casse ce qu'il ne traduit pas dans les deux sens. Un cache : l'invalidation en descendant, les erreurs en remontant. |
| ⚫ | Les fautes d'un cache vivent dans le temps, et la batterie n'a pas d'horloge. La fraîcheur exige une porte sous le décorateur, une horloge injectée et un seuil déclaré. |
| ⚫ | Le TTL est une clause du contrat du décorateur : le cache n'est substituable que pour les appelants qui le tolèrent. |
| ⚫ | Une redondance sans un test de chaque côté est une branche morte qui attend son heure. |
| ⚫ | La batterie est du code : elle se teste avec des fautes connues. Sans ces tests, trois de ses vérifications pouvaient disparaître sans qu'aucun relevé ne change. |
