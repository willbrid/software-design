# Correction 2.2 — Exercice 5 : l'incident de la TVA

> Rappel : une migration ajoute une cinquième valeur à `categorie_client` le
> 14 avril. Le `switch` de `calculateur/vat.go` a quatre cas et un `default`
> qui applique 19,25 %. Six semaines plus tard, 11 340 factures et
> 47,2 millions de FCFA de TVA facturés à tort à 180 ONG exonérées.

Tout ce qui suit est reproduit dans un module de cinq paquets de test, tous
verts sous `go vet` et `go test -race -count=1`. Les chiffres sont des sorties
de test, y compris ceux qui contredisent le post-mortem.

## 1. Les quatre décisions de conception (question 1)

La cause immédiate n'est pas la migration. La migration est correcte : elle
ajoute une valeur à une énumération, elle a été relue par deux personnes, et
le code de calcul était hors de son périmètre.

Voilà le code du jour de l'incident, reproduit à l'identique :

```go
// Package before is the code of the incident day, reproduced.
//
// It fits in thirty lines, it has 94 % coverage, sixty-one tests
// green, and it billed 47.2 million FCFA of VAT wrongly for six
// weeks. The four decisions that allowed it are named in the
// correction; this file carries them all.
package before

// StandardRatePerMille is the Cameroonian standard rate: 19.25 %.
const StandardRatePerMille = 192

// Invoice is an invoice before tax is computed.
type Invoice struct {
    Reference string
    // Category is a STRING read from the database. It is the first of the four
    // decisions: the type allows any value, so it allows
    // the one the migration created.
    Category string
    BaseFCFA int64
}

// Tax returns an invoice's VAT.
//
// The switch is on a string, it has four cases and a default. The default
// applies the standard rate and LOGS NOTHING: it is the second and the
// third of the four decisions.
func Tax(f Invoice) int64 {
    switch f.Category {
    case "ENTREPRISE":
        return f.BaseFCFA * StandardRatePerMille / 1000
    case "PARTICULIER":
        return f.BaseFCFA * StandardRatePerMille / 1000
    case "ADMINISTRATION":
        return 0
    case "ASSOCIATION_LOCALE":
        return 0
    default:
        // The standard rate, silently. Six weeks.
        return f.BaseFCFA * StandardRatePerMille / 1000
    }
}
```

Quarante et une lignes, et elles portent les quatre décisions.

| | La décision | Où elle est dans la leçon |
|---|---|---|
| **1** | `Category` est une **chaîne**, pas une énumération fermée | 2.1, *« le danger d'une chaîne non canonisée n'est pas qu'elle accepte n'importe quoi, c'est qu'elle accepte plusieurs écritures de la même chose »* — ici elle accepte une valeur de plus |
| **2** | le `default` **applique un taux** au lieu de refuser | 2.2, *« le `default` d'un `switch` sur un ensemble scellé est une dette »* — ici la dette n'est jamais remboursée |
| **3** | le `default` **ne journalise rien** | 2.2, *« le polymorphisme efface l'information qui te manquera pendant l'incident : laquelle »* |
| **4** | les tests sont **un par catégorie existante** | 2.2, le test par la répétition parcourt une liste écrite à la main : il ne peut pas tester une catégorie qui n'existe pas encore |

Et la décision qui n'en est pas une, mais qu'il faut nommer : **les deux
premiers `case` sont identiques**. `ENTREPRISE` et `PARTICULIER` rendent tous
les deux le taux normal. Ça veut dire que le `switch` ne distinguait
réellement que deux choses — taxé ou exonéré — et qu'un développeur pressé
devant ce code pouvait raisonnablement croire que le `default` était le cas
« taxé » par construction.

## 2. L'arithmétique du post-mortem (question 2)

C'est le passage le plus utile de cette correction, et il ne porte pas sur le
code.

L'énoncé demandait de vérifier la cohérence de trois nombres : 11 340
factures, 180 clients, 47,2 millions de FCFA. Le calcul :

```go
// TestThePostMortemArithmeticIsConsistent is the answer to question 2, and
// it is the most useful passage of this correction.
//
// The three figures of the post-mortem are consistent only for a
// precise mean invoice, and that value does not look like what
// an international NGO invoice is.
func TestThePostMortemArithmeticIsConsistent(t *testing.T) {
    // The VAT billed wrongly is the base x 192 per mille. We go back to the
    // database.
    totalBase := int64(wrongVATFCFA) * 1000 / vat.StandardRatePerMille
    perInvoice := totalBase / invoices
    perClient := invoices / clients
    perClientPerDay := float64(invoices) / float64(clients) / float64(incidentDays)

    t.Logf("total tax base               : %d FCFA", totalBase)
    t.Logf("mean invoice                 : %d FCFA", perInvoice)
    t.Logf("invoices per client          : %d over %d days", perClient, incidentDays)
    t.Logf("invoices per client per day  : %.2f", perClientPerDay)

    // The consistency check: the VAT recomputed from the mean
    // invoice must land back on the post-mortem's figure, give or take rounding.
    recomputed := perInvoice * invoices * vat.StandardRatePerMille / 1000
    gap := wrongVATFCFA - recomputed
    if gap < 0 {
        gap = -gap
    }
    if gap*1000/wrongVATFCFA > 1 {
        t.Fatalf("the three figures of the post-mortem are not consistent:"+
            " %d FCFA recomputed against %d announced", recomputed, wrongVATFCFA)
    }
    // And the finding that matters: a mean invoice of this amount, at this
    // pace, does not look like an international NGO.
    if perInvoice > 100_000 {
        t.Errorf("mean invoice of %d FCFA: the NGO profile would be plausible,"+
            " and the conclusion of the correction must be redone", perInvoice)
    }
}
```

```
base d'imposition totale        : 245833333 FCFA
facture meansne                 : 21678 FCFA
factures par client             : 63 sur 42 jours
factures par client et par jour : 1.50
```

Les trois nombres **sont cohérents**, mais seulement pour une facture moyenne
de **21 678 FCFA** — environ 33 euros — et un rythme de **1,5 facture par
client et par jour**.

Et là il faut s'arrêter. Une ONG internationale, c'est du matériel médical, des
véhicules, des loyers, des salaires. Une facture moyenne de 21 678 FCFA à
raison d'une et demie par jour, ce n'est pas le profil d'une ONG
internationale : c'est celui d'un commerce de quartier ou d'un abonnement
télécom.

> Les trois chiffres du post-mortem sont arithmétiquement cohérents et
> **métier-incohérents**. Ce que ça dit n'est pas que le post-mortem s'est
> trompé dans ses comptes : c'est que les 180 entités rangées sous
> `ONG_INTERNATIONALE` ne sont probablement pas 180 ONG internationales.

Autrement dit : **la migration a appliqué la nouvelle catégorie trop
largement**. Le service juridique a demandé une catégorie pour les ONG ; la
migration a vraisemblablement filtré sur un champ — un indicatif de nom, un
code d'activité — qui a attrapé 180 lignes dont une partie n'avait rien à y
faire.

Personne ne l'a vu, parce que le post-mortem s'est arrêté au `switch`. Il
avait trouvé une cause, et une cause suffit à écrire un post-mortem.

> **Vérifie la cohérence interne des chiffres d'un post-mortem.** Quand ils ne
> collent pas avec le métier, il y a un deuxième incident dedans — et c'est
> celui que personne ne cherche, parce que le premier est déjà expliqué.

Ce qui change l'ordre des corrections : avant de recalculer les 11 340
factures, il faut **relire la liste des 180 clients**.

## 3. Pourquoi les tests ne pouvaient pas voir venir (question 3)

Soixante-et-un tests, 94 % de couverture, un test par catégorie existante. La
propriété du modèle qui rendait le scénario inobservable tient en une phrase :

> **L'ensemble des valeurs de `Category` n'était pas connu du programme.**
> Un `string` a une infinité de valeurs, donc aucun test ne peut les
> parcourir, donc aucun test ne peut affirmer qu'elles sont toutes traitées.

Les soixante-et-un tests ont vérifié les quatre valeurs que leur auteur
connaissait. Ils ne pouvaient pas vérifier la cinquième, parce qu'elle
n'existait pas quand ils ont été écrits — et c'est exactement le mode de panne
du test par la répétition de la leçon 2.2 : il parcourt une liste écrite à la
main.

### Le test qui l'aurait attrapé

En une phrase, puisque c'est ce que l'énoncé demandait :

> **Un test qui lit le type énuméré de la base et exige qu'il ait exactement
> les mêmes valeurs que l'énumération du code.**

Il devait être écrit avant que la cinquième catégorie existe, et il aurait
échoué **le jour de la migration** — pas six semaines plus tard. Il est en
section 7.

## 4. Les trois durées (question 4)

| La durée | Ce qu'elle mesure | La conception pouvait-elle la réduire ? |
|---|---|---|
| **5 semaines et 2 jours** — migration → premier appel | le temps de **détection** | **oui, et à zéro** : un refus bloquant aurait arrêté le lot nocturne le 14 avril à 00h05 |
| **3 jours** — premier appel → quelqu'un regarde | le temps de **qualification** | **non.** C'est un problème d'organisation du support, pas de code |
| **20 minutes** — quelqu'un regarde → cause trouvée | le temps de **diagnostic** | oui, et il est déjà excellent. Vingt minutes pour trouver un `default`, c'est un code lisible |

Les deux termes du MTTR sont le temps de détection et le temps de réparation.
Et le résultat est brutal :

> **Les vingt minutes de diagnostic ne servent à rien face aux cinq semaines
> de détection.** Le code était lisible, la cause évidente, l'équipe
> compétente — et l'incident a duré six semaines parce que **rien ne l'a
> signalé**. Améliorer un diagnostic déjà à vingt minutes est le plus mauvais
> investissement disponible ici.

Un détail des trois jours qui mérite un mot quand même : le premier appel
client dit *« ma facture porte 19,25 % de TVA, mon association est
exonérée »*. C'est un diagnostic complet, formulé par le client. Il a fallu
trois jours et quatre appels pour que quelqu'un le lise comme tel.

## 5. L'indicateur qui ne pouvait pas bouger (question 5)

Le tableau de bord suivait **factures rejetées sur factures émises**, et il
est resté à 3 pour mille pendant six semaines. Mesure, sur le même lot, avant
et après la migration :

```
avant la migration  : 4200 factures, 0 rejetees, taux de rejet 0 pour mille (seuil 20)
apres la migration  : 4200 factures, 0 rejetees, taux de rejet 0 pour mille (seuil 20)
```

Et la raison est mécanique, pas accidentelle :

> **Aucune facture n'était rejetée.** Elles étaient toutes émises, au mauvais
> taux. Un indicateur qui compte les échecs ne voit jamais un **succès faux**.

C'est la même famille que le plancher de bruit de l'incident de la leçon 2.2,
mais le mécanisme est pire : là-bas l'indicateur était dilué, ici il était
**structurellement incapable** de bouger. Aucun seuil, aussi bas soit-il, ne
l'aurait fait tirer.

### L'indicateur qui tire, et sa date

```go
// Summary is the report of a batch of lines.
// It carries the number of rejections BY UNKNOWN VALUE, and it is the indicator that
// was missing. The dashboard on the incident day tracked the invoices
// rejected among invoices issued: a ratio that did not move, because
// that no invoice was rejected: they were all issued, at the wrong
// rate.
type Summary struct {
    Read     int
    Accepted int
    // RejectionsByValue counts rejections by unrecognized database value.
    // It is this map that would have shown "INTERNATIONAL_NGO: 180" on
    // 14 April at 00:05.
    RejectionsByValue map[string]int
}

// RejectionRatePerMille returns the batch's rejection rate, per mille.
func (b Summary) RejectionRatePerMille() int {
    if b.Read == 0 {
        return 0
    }
    return (b.Read - b.Accepted) * 1000 / b.Read
}
```

```go
// TestTheIndicatorThatFiresOnDayOne is the other half of question 5.
// The boundary counts rejections BY unrecognized VALUE. That indicator
// shown "INTERNATIONAL_NGO: 180" on the first nightly batch, and it was not
// noise floor: in normal operation it is exactly zero, because
// every value produced by the database is handled by the code: and it is the
// boundary test that guarantees it.
func TestTheIndicatorThatFiresOnDayOne(t *testing.T) {
    // In normal operation, before the migration.
    _, summaryBefore := boundary.ReadBatch(batchOfDay(t, false))
    t.Logf("before the migration: %d read, %d accepted, rejections by value %v, rate %d per mille",
        summaryBefore.Read, summaryBefore.Accepted, summaryBefore.RejectionsByValue,
        summaryBefore.RejectionRatePerMille())
    if len(summaryBefore.RejectionsByValue) != 0 {
        t.Fatalf("rejections in normal operation: %v", summaryBefore.RejectionsByValue)
    }

    // After the migration, with code that does NOT yet know the
    // new category. We simulate it by parsing a value absent from
    // the enumeration.
    unknownBatch := batchOfDay(t, false)
    for i := 0; i < clients; i++ {
        unknownBatch[i].Category = "INTERNATIONAL_NGO_V2"
    }
    _, summaryAfter := boundary.ReadBatch(unknownBatch)
    t.Logf("after the migration: %d read, %d accepted, rejections by value %v, rate %d per mille",
        summaryAfter.Read, summaryAfter.Accepted, summaryAfter.RejectionsByValue,
        summaryAfter.RejectionRatePerMille())

    if summaryAfter.RejectionsByValue["INTERNATIONAL_NGO_V2"] != clients {
        t.Fatalf("rejections = %v, want %d for the unknown value",
            summaryAfter.RejectionsByValue, clients)
    }
    // And the global rate crosses the threshold too, because this
    // time the lines are REJECTED and not issued at the wrong rate.
    if summaryAfter.RejectionRatePerMille() < rejectionAlertThreshold {
        t.Errorf("rejection rate %d per mille, below the threshold of %d",
            summaryAfter.RejectionRatePerMille(), rejectionAlertThreshold)
    }
}
```

```
avant la migration : 4200 lues, 4200 acceptees, rejets par valeur map[], taux 0 pour mille
apres la migration : 4200 lues, 4020 acceptees, rejets par valeur
                     map[INTERNATIONAL_NGO_V2:180], taux 42 pour mille
```

**Date de déclenchement : le 14 avril, au premier lot nocturne.** Et deux
propriétés qui en font un bon indicateur :

**Il nomme la valeur.** `ONG_INTERNATIONALE : 180` n'est pas une alerte, c'est
un diagnostic. Les vingt minutes de recherche deviennent zéro.

**Il n'a pas de plancher de bruit.** En régime normal il vaut exactement
`0` — pas « trois pour mille », pas « quelques-uns » : **zéro**. Parce que
toute valeur produite par la base est traitée par le code, et que c'est le
test de frontière qui le garantit. Un indicateur dont la valeur normale est
zéro peut avoir un seuil à un.

> Un indicateur qui vaut zéro en régime normal est le seul dont le seuil ne
> se négocie pas.

## 6. Le courriel du 10 avril (question 6)

*« Le problème, c'est que le courriel n'a pas été lu. »*

Deux phrases en réponse :

> Un courriel adressé à une équipe n'est pas un mécanisme : il n'a pas de
> destinataire responsable, pas d'accusé de réception, et pas de conséquence
> s'il n'est pas traité. Et même lu, même compris, même ajouté au carnet de
> sprint, il n'aurait rien empêché : il demandait d'ajouter une catégorie, pas
> de vérifier que le code refuse celles qu'il ne connaît pas.

Ce que la leçon 2.2 propose à la place est de **changer le sens de la
dépendance**. Le courriel demande à un humain d'agir avant une migration. Le
test de frontière demande à une **migration** de ne pas passer sans que le
code suive — et la migration, elle, ne peut pas oublier de lire un courriel.

> On ne remplace pas une communication par une meilleure communication. On la
> remplace par une **contrainte qui vit du même côté que le changement**.

## 7. La correction (question 7)

Les quatre propositions, et il faut les déployer **dans un ordre**.

| | Ce qu'elle empêche | Ce qu'elle n'empêche pas | Ce qu'elle coûte | Le jour de la sixième catégorie |
|---|---|---|---|---|
| **A** ajouter le cas | ce bug-là | la classe entière | 1 ligne, 20 minutes | **rien n'a changé** : le `default` est toujours là, et le prochain passe |
| **B** journaliser le `default` en ERREUR | rien, mais rend visible | l'émission des factures fausses | 1 ligne + une alerte | ça tire, et on perd une nuit de factures au lieu de six semaines |
| **C** `default` bloquant | **l'émission** d'une facture au taux inconnu | la migration | le lot nocturne s'arrête | ça bloque, et c'est ce qu'on veut |
| **D** énumération fermée + test de frontière | **la classe entière**, et avant la production | rien de ce qui compte | ~130 lignes de test et un paquet | **la construction échoue avant le déploiement** |

### L'ordre, et pourquoi

**B d'abord, le jour même.** Une ligne de journal, zéro risque, et elle donne
immédiatement la liste des références touchées — dont on a besoin pour la
section 8. Déployer C en premier arrêterait la facturation d'un coup, sans
savoir combien de lignes sont concernées.

**Puis A, dans la même journée.** On arrête l'hémorragie pour les 180 clients
identifiés. Ce n'est pas une correction, c'est un pansement, et il faut le
dire dans le message de commit.

**Puis C et D ensemble, dans la semaine.** Séparément, C bloque sans
expliquer et D explique sans bloquer. Ensemble :

```go
// Parse is the BOUNDARY: it is the only function of the program that
// turns a database string into a category.
//
// It is total in the sense that it always returns either a known category,
// or an error. It never returns a default category, and it is the
// only difference that matters with the code of the incident day.
func Parse(s string) (Category, error) {
    raw := strings.ToUpper(strings.TrimSpace(s))
    for c, code := range codes {
        if code == raw {
            return c, nil
        }
    }
    return unknown, fmt.Errorf("%w: %q", ErrUnknown, s)
}
```

```go
// For returns the rate that applies to a category.
// The type switch is replaced by a switch on the enumeration, and the default
// returns an error. That is all.
func For(c category.Category) (Rate, error) {
    switch c {
    case category.Company, category.Individual:
        return Rate{PerMille: StandardRatePerMille, Basis: "standard rate, art. 128 CGI"}, nil
    case category.Administration:
        return Rate{PerMille: 0, Basis: "exemption, art. 128 bis CGI"}, nil
    case category.LocalAssociation:
        return Rate{PerMille: 0, Basis: "association exemption, art. 128 ter CGI"}, nil
    case category.InternationalNGO:
        return Rate{PerMille: 0, Basis: "NGO agreement exemption"}, nil
    default:
        return Rate{}, fmt.Errorf("%w: %s", ErrCategoryNotHandled, c)
    }
}
```

Trois choses dans ces deux extraits, et la troisième n'était pas dans
l'énoncé.

**La valeur zéro n'est pas exportée.** `unknown` est privée : aucun paquet ne
peut l'écrire, donc aucun appelant ne peut fabriquer une catégorie invalide
par assignation.

**`For` rend un taux ET son fondement.** Un taux de TVA se justifie devant un
contrôle fiscal, et un entier seul ne se justifie pas. Un test exige que
chaque catégorie ait un fondement non vide.

**L'analyse et le rendu lisent la même table.** `codes` est déclarée une fois,
`Parse` la parcourt et `Code` la lit. Donc `Parse(c.Code()) == c` pour
toute catégorie, et un test le vérifie. Deux tables divergent ; une seule ne
peut pas.

### La frontière, et pourquoi il n'y en a qu'une

```go
// Package boundary is the layer that reads the database.
//
// It exists because the guarantee asked for by management, "that a value
// new in the database can never again cross the code without being
// handled", cannot be kept by the program alone, and one needs
// say why.
//
// The program does not control the database. An administrator can add an
// enumeration value without touching the code, and it is exactly what
// happened on 14 April. The only thing the program controls is what
// happens when it READS this value.
//
//    We do not make it impossible for a new value to appear. We make
//    impossible for it to CROSS. The boundary is the place, and there is
//    has only one.
package boundary
```

```go
// ReadBatch transforms a batch, and returns the accepted invoices with the summary.
// It does NOT stop at the first error: a nightly batch of a hundred thousand
// lines with one bad one must not lose the 99,999 others. But it
// does not lose them silently either: the summary counts them, by value.
func ReadBatch(lines []Line) ([]vat.Invoice, Summary) {
    b := Summary{Read: len(lines), RejectionsByValue: map[string]int{}}
    invoices := make([]vat.Invoice, 0, len(lines))
    for _, l := range lines {
        f, err := Read(l)
        if err != nil {
            b.RejectionsByValue[l.Category]++
            continue
        }
        invoices = append(invoices, f)
        b.Accepted++
    }
    return invoices, b
}
```

`ReadBatch` **ne s'arrête pas à la première erreur**, et c'est un choix. Un lot
nocturne de cent mille lignes dont une est mauvaise ne doit pas perdre les
99 999 autres. Mais il ne les perd pas en silence non plus : le bilan les
compte, par valeur.

## 8. Les 11 340 factures (question 8)

Trois populations, trois traitements. Et la section 2 en ajoute une quatrième
que l'énoncé n'avait pas prévue.

| Population | Combien | Traitement |
|---|---|---|
| factures **non payées**, client réellement exonéré | 9 030 | avoir et réémission avant échéance. Le client ne voit rien |
| factures **payées**, client réellement exonéré | 2 310 | avoir + remboursement de la TVA indûment perçue. C'est de l'argent à rendre, et il y a une déclaration fiscale à rectifier |
| factures des clients **mal classés** par la migration | **inconnu** — à établir | elles sont peut-être **justes**. Les rectifier serait une seconde erreur |
| déclarations de TVA déjà déposées | 1 ou 2 mois | rectificatives, et c'est le délai le plus contraignant du lot |

La troisième ligne est la raison pour laquelle l'ordre des opérations compte :

> **On ne corrige pas 11 340 factures avant d'avoir relu la liste des 180
> clients.** Une partie d'entre eux n'aurait jamais dû recevoir la nouvelle
> catégorie, et pour ceux-là le taux normal était le bon taux.

## 9. La garantie (question 9)

### Pourquoi « on rendra ça impossible » est faux

En deux phrases, et l'argument vient exactement de la leçon 2.2 :

> Le programme ne contrôle pas la base. Un administrateur peut ajouter une
> valeur à un type énuméré sans toucher au code, et aucun scellement Go n'y
> change rien — la méthode non exportée protège le programme contre les autres
> paquets Go, pas contre une instruction `ALTER TYPE`, parce que le compilateur
> Go ne lit pas PostgreSQL.
>
> Ce qu'on peut rendre impossible, ce n'est pas qu'une valeur nouvelle
> **apparaisse** : c'est qu'elle **traverse**.

### La propriété, et son endroit

```go
// Package category defines the CLOSED set of client categories.
//
// It is the first of the four fixes: the type is no longer a string,
// it is a closed enumeration whose zero value is not a category.
package category

import (
    "errors"
    "fmt"
    "slices"
    "strings"
)
```

> **Il n'existe qu'une seule fonction dans le programme qui transforme une
> chaîne en catégorie, et elle est totale** : elle rend soit une catégorie
> connue, soit une erreur. Jamais un défaut.

Et l'endroit n'est pas négociable, parce que la leçon 2.1 a donné le critère :
*le garde-fou doit être au niveau le plus bas qui puisse le porter.* Ici le
niveau le plus bas accessible au programme est **la couche qui lit la base** —
en dessous, c'est le SGBD, et le SGBD ne connaît pas le code.

Conséquence concrète : tout le reste du programme manipule des
`category.Category`, donc **tout le reste du programme est hors de portée de
ce mode de panne**. Il n'y a pas trois endroits à surveiller, il y en a un.

### Ce que ça coûte, chiffré en ce que ça interdit

| Ce qui devient interdit | Ce que ça coûte en pratique |
|---|---|
| ajouter une valeur en base sans toucher au code | **une migration de plus par catégorie** — le code d'abord, la base ensuite |
| faire tourner un lot avec des lignes non reconnaissables | les lignes sont rejetées, donc un lot nocturne peut rendre moins de factures que prévu, et quelqu'un doit regarder le matin |
| lire une catégorie depuis la base ailleurs qu'à la frontière | toute requête SQL nouvelle doit passer par `boundary.Read`, et une revue doit le vérifier |

Le troisième coût est le vrai, et c'est aussi le trou de la garantie : **rien
n'empêche un développeur d'écrire une nouvelle requête qui court-circuite la
frontière.** Le test de frontière ne le verra pas.

### La mesure, son seuil, son plancher de bruit

| | |
|---|---|
| **la mesure** | `Summary.RejectionsByValue` — le nombre de lignes rejetées, par valeur de base non reconnue |
| **le seuil** | **1**. Pas dix, pas un pour mille : **une** |
| **pourquoi ce seuil** | parce que la valeur normale est **zéro**, garantie par le test de frontière. Un seuil à un est donc le plus bas possible et le plus justifiable |
| **plancher de bruit** | **aucun**, et c'est la propriété qui le permet. C'est la différence avec l'indicateur de la leçon 2.2, qui mélangeait refus métier et pannes |

Et pour le second, il fallait inventer quelque chose. Voilà :

```go
// TestTheDatabaseSchemaAndTheCodeHaveTheSameValues is the BOUNDARY test,
// and it is the answer to the last question of the exercise.
//
// It reads the dump of the database's enumerated type and compares it to the enumeration of the
// code. Any divergence, one way or the other, makes the
// construction.
//
//    A value added to the database without being added to the code: this test fails,
//    and it is the incident of 14 April, caught on the day of the migration.
//
//    A value added to the code without being added to the database: this test fails
//    too, and it is the mirror failure mode: code that handles a
//    category the database will never produce, so dead code that
//    reassures.
//
// NOT GUARANTEED, and it must be said: this test compares the code with a FILE, not
// with the database. It is worth something only if the file is regenerated by the
// integration chain from the real database. Without that, it checks that a file
// matches some code, which interests nobody.
func TestTheDatabaseSchemaAndTheCodeHaveTheSameValues(t *testing.T) {
    inBase, err := schema.ValuesInBase(filepath.FromSlash(schemaPath))
    if err != nil {
        t.Fatalf("reading the schema: %v", err)
    }
    var inCode []string
    for _, c := range category.All() {
        inCode = append(inCode, c.Code())
    }
    slices.Sort(inCode)

    if !slices.Equal(inBase, inCode) {
        for _, v := range inBase {
            if !slices.Contains(inCode, v) {
                t.Errorf("the database knows %q, the code does not handle it"+
                    ": it is the incident of 14 April", v)
            }
        }
        for _, v := range inCode {
            if !slices.Contains(inBase, v) {
                t.Errorf("the code handles %q, the database will never produce it"+
                    ": dead code that reassures", v)
            }
        }
        t.Fatalf("base: %v\ncode: %v", inBase, inCode)
    }
    t.Logf("%d values, identical on both sides of the boundary: %v",
        len(inBase), inBase)
}
```

```
5 valeurs, identiques de part et d'autre de la frontiere :
[ADMINISTRATION ASSOCIATION_LOCALE ENTREPRISE ONG_INTERNATIONALE PARTICULIER]
```

Le test lit un **dump du schéma** et le compare à l'énumération du code. Il
tombe dans les **deux** sens, et les deux comptent :

| Divergence | Ce que c'est |
|---|---|
| la base connaît une valeur que le code ne traite pas | **l'incident du 14 avril**, attrapé le jour de la migration |
| le code traite une valeur que la base ne produira jamais | le mode de panne symétrique : du **code mort qui rassure** |

Le fichier lu n'est pas de la documentation :

```go
// Package schema reads the state of the enumerated type in the database.
//
// It exists for a single reason, and it is the answer to the last question
// of the exercise: "under which condition does your property survive the next
// database administrator?"
//
// Answer: on the condition that a test reads the database and compares it with the code. The
// seal of a Go enumeration protects the program against the other
// Go packages. It protects nothing against an ALTER TYPE statement, because
// the Go compiler does not read PostgreSQL.
package schema
```

Et la clause **NON GARANTI**, qui fait partie du test : *il compare le code à
un fichier, pas à la base. Il ne vaut que si le fichier est régénéré par la
chaîne d'intégration depuis la base réelle.* Sans ça, il vérifie qu'un fichier
correspond à du code, ce qui n'intéresse personne.

C'est aussi pour ça que `ValuesInBase` rend une erreur quand elle ne trouve
rien :

```go
// ValuesInBase reads the values of the enumerated type from a schema dump.
func ValuesInBase(path string) ([]string, error) {
    content, err := os.ReadFile(path)
    if err != nil {
        return nil, fmt.Errorf("schema: %w", err)
    }
    found := reason.FindAllStringSubmatch(string(content), -1)
    if len(found) == 0 {
        return nil, fmt.Errorf("%w: %s", ErrUnreadableSchema, path)
    }
    values := make([]string, 0, len(found))
    for _, t := range found {
        values = append(values, t[1])
    }
    slices.Sort(values)
    return slices.Compact(values), nil
}
```

> Le mode de panne d'un test qui compare deux listes est qu'il **n'en trouve
> aucune** et se déclare satisfait. Un test qui compare une liste vide à une
> liste vide passe toujours.

## 10. La campagne de modifications

Seize modifications, cinq paquets de test.

```
modification                                                       | tests qui tombent
-------------------------------------------------------------------+------------------
 1. Parse rend une categorie par defaut au lieu d'une erreur    | 7
 2. Parse ne canonise plus la casse                             | 2
 3. la valeur zero devient Company                              | 2
 4. Code() rend une chaine vide pour l'inconnu                     | 1
 5. l'ONG internationale disparait de la table des codes           | 5
 6. vat.For applique le taux normal par defaut                    | 2
 7. l'ONG internationale perd son exoneration                      | 3
 8. Tax n'exige plus de fondement                                 | 1
 9. une base negative est acceptee                                 | 1
10. l'erreur de Tax ne nomme plus la facture                      | 1
11. la frontiere avale la cause d'origine                          | 2
12. le lot ne compte plus les rejets par valeur                    | 3
13. le lot s'arrete a la premiere erreur                           | 3
14. le taux de rejet divise par zero                               | 1
15. le schema n'est plus lu, la liste est ecrite a la main         | 1
16. un schema vide est une reussite                                | 1

16/16 modifications detectees
```

Trois remarques.

**La modification 1 est l'incident lui-même**, réécrit en une ligne : faire
rendre à `Parse` une catégorie par défaut au lieu d'une erreur. Elle fait
tomber **sept** tests. Dans le code du jour de l'incident, elle ne faisait
tomber aucun des soixante-et-un.

**La modification 5 est la plus intéressante.** Retirer `ONG_INTERNATIONALE`
de la table des codes fait tomber cinq tests, et l'un des cinq est le test de
frontière — il dit *« la base connaît `ONG_INTERNATIONALE`, le code ne le
traite pas »*. C'est la phrase exacte qui aurait dû apparaître le 14 avril.

**La modification 15 est un avertissement.** Elle remplace la lecture du
fichier par la liste écrite à la main — la bonne liste. Le test de frontière
**passe**, puisque la liste est juste. Un seul test tombe : celui qui vérifie
qu'un schéma vide est une erreur.

> Un test qui lit une source de données extérieure peut être neutralisé en
> **falsifiant la source**, et il passera au vert. Ce qui l'attrape n'est pas
> un test de plus sur la comparaison : c'est le test qui garde **son mode de
> panne à lui**.

Et trois modifications n'ont d'abord pas compilé — un import devenu inutilisé
à chaque fois. Une modification qui ne compile pas n'est ni détectée ni
survivante : **elle n'a pas été jouée**, et il faut la rejouer sous une forme
qui compile.

## 11. Ce que cet incident devait faire comprendre

1. **Un `default` qui applique une valeur est une décision**, pas un filet de
   sécurité. Et une décision silencieuse est une décision que personne ne
   relit.
2. **Un `string` pour une énumération rend l'exhaustivité indémontrable.**
   Aucun test ne peut parcourir une infinité de valeurs.
3. **Vérifie l'arithmétique d'un post-mortem.** Ici elle révèle que les 180
   « ONG internationales » facturent 21 678 FCFA en moyenne, une fois et
   demie par jour — et donc qu'il y a un second incident dans le premier.
4. **Un indicateur qui compte les échecs ne voit jamais un succès faux.**
   Aucun seuil ne l'aurait fait tirer.
5. **Un indicateur qui vaut zéro en régime normal** est le seul dont le seuil
   ne se négocie pas.
6. **Vingt minutes de diagnostic ne servent à rien face à cinq semaines de
   détection.** Investis sur la détection.
7. **On ne remplace pas une communication par une meilleure communication**,
   mais par une contrainte qui vit du même côté que le changement.
8. **Le scellement d'une énumération Go ne protège rien contre un `ALTER
   TYPE`.** Le compilateur Go ne lit pas PostgreSQL.
9. **Ce qu'on rend impossible n'est pas qu'une valeur apparaisse, c'est
   qu'elle traverse** — et la frontière est le niveau le plus bas que le
   programme puisse porter.
10. **Un test qui lit une source extérieure se neutralise en falsifiant la
    source.** Ce qui l'attrape est le test de son propre mode de panne.
