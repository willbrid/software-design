# Correction 2.3 — Exercice 5 : l'incident du type qui satisfait `error`

> Rappel du post-mortem : onze jours, 214 000 réponses en 500, un tableau de
> bord resté à 2 pour mille, 53 tests verts, et un commit relu par deux
> personnes intitulé « simplifie l'accès aux champs de l'incident ».

Cinq paquets, verts sous `go vet ./...` et `go test -race -count=1 ./...` :
le code du 03/06 dans `reponse`, celui du 4.11.0 dans `v411`, l'intergiciel
tel quel dans `intergiciel`, le correctif dans `correction`, et le contrôle
de la question 9 dans `controle`.

## 1. Le mécanisme, en trois phrases, sans le mot « héritage »

`Incident` porte une méthode `Error() string`, et un type Go satisfait
l'interface `error` dès qu'il porte cette méthode — personne n'a besoin de le
déclarer. Quand `Reponse` a cessé d'avoir un champ `incident` pour avoir un
champ **anonyme** `Incident`, elle a reçu la méthode `Error()` de ce champ
dans son propre ensemble de méthodes, donc `Reponse` est devenue un `error`.
L'intergiciel, qui demandait depuis deux ans « est-ce que ce que je dois
écrire est un `error` ? », a commencé à répondre oui pour **toutes** les
réponses.

## 2. Pourquoi aucun des 53 tests ne pouvait voir le problème

Deux raisons différentes, une par paquet, et aucune des deux n'est de la
négligence.

### Les 41 tests du paquet `reponse` : ils vérifient les champs

```go
// TestLaFormeDesQuaranteEtUnTests est la reponse a la question 2 pour le
// paquet reponse.
//
// Les 41 tests verifient les CHAMPS de la reponse. Tous passent, avant comme
// apres, parce que l'incorporation ne change rien aux champs : Donnees,
// Total et Page sont au meme endroit, avec les memes valeurs. La couverture
// est de 97 % parce que les lignes de Traiter sont bien executees.
//
// Ce qu'aucun des 41 ne regarde, c'est l'ENSEMBLE DES METHODES du type.
func TestLaFormeDesQuaranteEtUnTests(t *testing.T) {
    r := reponse.Traiter(7)
    if len(r.Donnees) != 3 || r.Total != 3 || r.Page != 7 {
        t.Fatalf("reponse = %+v", r)
    }
    // Et l'acces promu, qui est la raison du commit : r.Code au lieu de
    // r.incident.Code.
    if r.Code != "" || r.Bloquant {
        t.Fatalf("incident = %+v", r.Incident)
    }
    t.Log("les champs sont corrects, la couverture est bonne, et le test est" +
        " vrai : il ne dit simplement rien du type")
}
```

Les champs sont **au même endroit avec les mêmes valeurs** avant et après :
`Donnees`, `Total`, `Page` ne bougent pas d'un octet. La couverture est de
97 % parce que les lignes de `Traiter` sont bien exécutées. Les 41 tests sont
vrais.

Ce qu'aucun des 41 ne regarde, c'est **l'ensemble des méthodes du type**. Et
c'est la seule chose que le commit a changée.

> La couverture mesure les lignes exécutées. Une méthode promue n'ajoute
> aucune ligne : elle change l'ensemble des méthodes d'un type. Il n'y a
> aucun pourcentage de couverture qui puisse voir ça.

### Les 12 tests de l'intergiciel : ils couvrent les deux cas, et il y en a trois

```
les deux cas testes passent, et le troisieme — une donnee QUI EST AUSSI une
erreur — rend 500
```

L'intergiciel distingue deux cas : une erreur, et une valeur qui n'en est pas
une. Ses douze tests couvrent les deux, à 100 %. Aucun ne lui donne une valeur
qui soit **les deux à la fois**, parce que ce cas n'existe pas dans la tête de
celui qui écrit une assertion de type : `v.(error)` se lit « est-ce une
erreur ou une donnée », alors qu'il demande « porte-t-elle `Error()` ».

> Une assertion de type sur `error` ne sépare pas les erreurs des données.
> Elle sépare ce qui porte `Error()` de ce qui ne le porte pas, et ce n'est
> pas la même partition.

## 3. Le test qui aurait été rouge le 03/06

En une phrase : **aucun type rendu par un gestionnaire ne doit satisfaire
`error`.**



Il porte sur le **type**, pas sur une réponse HTTP. Il ne sait rien de

| Phase | Du | Au | Durée | Ce qui s'est passé |
|---|---|---|---|---|
| **détection** | 03/06 14:20 | 14/06 09:15 | **10 j 19 h** | personne ne sait que la route est morte |

La conception pouvait réduire les trois, et très inégalement :

| Phase | Ce que la conception y change |
|---|---|
| **détection** | de **10 jours à quelques secondes**. Le test de la section 3 aurait empêché le déploiement ; à défaut, l'indicateur de la section 5 aurait tiré à 14:20. C'est 99,99 % du délai total |

**Toute la réduction est dans la détection**, et la détection est la seule des
trois que la conception peut faire tomber de plusieurs ordres de grandeur. Le
reste est du confort.

## 5. L'indicateur, et pourquoi il ne pouvait pas bouger

```go
// TestLeTauxDErreurApplicatifNePeutPasBouger est la reponse a la question 5.
//
// L'indicateur compte les fois ou un gestionnaire REND une erreur non nulle.
// Traiter ne rend pas d'erreur : sa signature est (int) Reponse, sans
// deuxieme valeur de retour. L'indicateur ne peut donc pas bouger, quelle
// que soit la reponse produite.
func TestLeTauxDErreurApplicatifNePeutPasBouger(t *testing.T) {
    requetes, erreursApplicatives, cinqCents := 0, 0, 0
    for page := 1; page <= 1_000; page++ {
        requetes++
        // C'est exactement ce que l'indicateur observe : la valeur de
        // retour du gestionnaire. Il n'y en a qu'une, et ce n'est pas une
        // erreur.
        r := reponse.Traiter(page)
        var err error // le gestionnaire n'en rend aucune
        if err != nil {
            erreursApplicatives++
        }
        if ecrire(r).Code >= 500 {
            cinqCents++
        }
    }
    if erreursApplicatives != 0 {
        t.Fatalf("%d erreurs applicatives : la mesure a change", erreursApplicatives)
    }
    if cinqCents != requetes {
        t.Fatalf("%d/%d reponses en 500", cinqCents, requetes)
    }
    t.Logf("%d requetes : %d erreurs applicatives (0 pour mille) et %d 500"+
        " (1000 pour mille)", requetes, erreursApplicatives, cinqCents)
    t.Log("le tableau de bord suivait la premiere colonne")
}
```

```
1000 requetes : 0 erreurs applicatives (0 pour mille) et 1000 500
(1000 pour mille)
le tableau de bord suivait la premiere colonne
```

L'indicateur comptait « le nombre de fois où un gestionnaire **rend** une
erreur non nulle ». Or la signature est `func Traiter(page int) Reponse` : il
n'y a **pas de deuxième valeur de retour**. Le numérateur de l'indicateur est
structurellement nul, et il l'était déjà avant le 03/06.

### Ce qu'il mesurait réellement

Pas le taux d'échec du service. **Le nombre de fois où un développeur avait
écrit `return err`.** C'est une mesure du code, pas du système — et elle est
restée à 2 pour mille parce que les quelques gestionnaires qui, eux, rendent
une erreur, ont continué à la rendre au même rythme.

> Un indicateur dont le numérateur est produit par le code qu'il surveille
> ne surveille rien. Il faut qu'il soit mesuré **au-dessus** de ce qu'il
> mesure.

### L'indicateur qui aurait tiré

| | |
|---|---|
| l'indicateur | **part des réponses HTTP en 5xx par route**, mesurée là où le statut est écrit — l'intergiciel, ou mieux le serveur en amont |
| pourquoi par route | 214 000 requêtes sur une route parmi des dizaines : un taux global aurait bougé, mais noyé. Le post-mortem dit « latence stable, taux d'erreur à 2 pour mille » : l'agrégat a masqué un 100 % |
| le seuil | **20 % de 5xx sur une route, sur une fenêtre de 5 minutes, avec au moins 20 requêtes** |
| le plancher de bruit | les 5xx légitimes d'une API de consultation : pannes de base, délais dépassés. Observé autour de **0,5 %**, donc un seuil à 20 % est à quarante fois le bruit |
| quand il aurait tiré | **le 03/06 vers 14:25**, soit cinq minutes après le déploiement de 14:20 — le temps de remplir la fenêtre. Le taux de la route était de 100 %, pas de 21 % |

Les onze jours deviennent **cinq minutes**. Et l'indicateur ne demande aucune
conception particulière : il demande seulement d'être mesuré au bon endroit et
découpé par route.

## 6. « Zéro client n'avait signalé avant le 14 »

C'est l'information la plus inquiétante du post-mortem, et elle ne concerne
pas le code.

Elle dit qu'une route d'API peut rendre **100 % d'erreurs pendant onze jours**
sans qu'un seul client appelle. Trois lectures possibles, et il faut savoir
laquelle :

| Lecture | Ce que ça implique |
|---|---|
| la route n'intéresse personne | 214 000 requêtes sur onze jours disent le contraire |
| les clients ont un contournement | c'est ce que dit l'appel du 14/06 : *« on a basculé sur l'export CSV »*. Les clients ont une procédure de secours, et ils s'en servent **sans nous le dire** |
| les clients n'ont personne à appeler | le canal de signalement est trop coûteux pour eux, donc le silence n'est pas une absence de problème |

Les deux dernières sont vraies en même temps, et elles changent les priorités
de correction :

1. **D'abord l'indicateur de la section 5**, avant même le correctif de code.
   Parce que ce que l'incident a établi, ce n'est pas qu'il y a un bug : c'est
   que **le silence des clients ne vaut rien comme signal**. Tant que c'est
   vrai, le prochain bug durera aussi onze jours, quelle que soit sa nature.
2. Ensuite le correctif, puis le contrôle de la section 9.
3. Et une action qui n'est pas technique : demander aux clients qui ont un
   contournement de nous le dire. Un client qui bascule sur l'export CSV est
   une alerte de production, et elle est aujourd'hui perdue.

> Un signal qui n'arrive que quand un client se fâche a une latence qui se
> compte en jours et un taux de faux négatifs qu'on ne connaît pas. Ce n'est
> pas un signal, c'est de la chance.

## 7. Les quatre propositions de correction

| | Ce qu'elle empêche | Ce qu'elle n'empêche pas | Ce qu'elle coûte | Le jour où un deuxième type incorpore `Incident` |
|---|---|---|---|---|
| **A** revenir au champ nommé | que **`Reponse`** soit un `error` | que n'importe quel autre type le devienne. L'aplatissement JSON revient aussi — en bien, cette fois | 1 fichier, et tous les `r.Code` deviennent `r.incident.Code`. Le compilateur les trouve tous | **le bug revient entier**, sur le nouveau type |
| **B** renommer `Error()` en `Message()` | la **classe entière** : aucun type incorporant `Incident`, présent ou futur, ne devient un `error` | qu'un autre type porte, lui, une méthode `Error()` légitime et soit incorporé ailleurs | tout le code interne qui remontait un `Incident` comme erreur doit l'écrire explicitement. Le compilateur trouve tous les points | **rien ne se passe.** C'est la seule des quatre dont c'est vrai |
| **C** champ explicite dans l'intergiciel | que **cet intergiciel** se trompe, pour tous les types | que `json.Marshal`, un `%v` de journal, un second intergiciel ou un client de test se trompent. `Reponse` reste un `error` | la signature de `Ecrire` change : une quarantaine de points d'appel, **tous trouvés par le compilateur** | rien côté intergiciel, et le type reste piégé partout ailleurs |
| **D** liste de types à ne pas traiter comme des erreurs | ce qui est dans la liste | tout ce qui n'y est pas encore | peu de lignes, et une **dette permanente** : la liste doit être tenue à jour par des gens qui ne savent pas qu'elle existe | **le bug arrive, et il faut l'avoir vécu pour penser à inscrire le nouveau type** |

**D est la pire des quatre, et c'est la plus tentante** parce qu'elle est la
plus petite : elle transforme un défaut de conception en une liste à maintenir,
c'est-à-dire en une procédure. Toute correction qui produit une liste à tenir
produit aussi le prochain incident.

### Ce que je retiens, et dans quel ordre je déploie

**C, puis B.** Jamais D. A nulle part.

| Ordre | Quoi | Pourquoi dans cet ordre |
|---|---|---|
| 1 | **C** | elle arrête l'hémorragie et elle ne change aucun contrat public. Déployable dans l'heure, et le compilateur garantit qu'aucun point d'appel n'est oublié |
| 2 | **B** | elle supprime la classe. Elle touche du code interne, donc elle mérite une revue, pas une urgence |
| 3 | le contrôle de la section 9 | parce que C et B ne protègent que ce qu'on a corrigé aujourd'hui |

### Le correctif, et la conclusion qui surprend

```go
// Package correction porte la correction retenue, et elle garde
// l'incorporation.
//
// C'est la conclusion de l'exercice : l'incorporation n'etait pas le bug.
// Le bug etait un type qui etait A LA FOIS une donnee et une erreur. Ici
// Reponse incorpore toujours Incident — r.Code s'ecrit toujours — et
// l'incident ne satisfait plus error.
package correction

import (
    "encoding/json"
    "errors"
    "fmt"
    "net/http"
)

// Incident est la trace d'un probleme rencontre pendant le traitement.
//
// Sa methode s'appelle Message et non Error. C'est la proposition B, et
// c'est elle qui supprime la CLASSE : aucun type qui incorpore Incident,
// present ou futur, ne devient une erreur par accident.
type Incident struct {
    Code     string `json:"code,omitempty"`
    Detail   string `json:"detail,omitempty"`
    Bloquant bool   `json:"bloquant,omitempty"`
}

// Message rend l'incident sous forme de texte.
func (i Incident) Message() string {
    if i.Code == "" {
        return ""
    }
    return fmt.Sprintf("incident %s : %s", i.Code, i.Detail)
}

// Present dit si la reponse porte un incident.
//
// L'incident vide se distingue maintenant de l'incident absent, ce qui
// n'etait pas le cas le 03/06 : le client recevait « incident  :  », sans
// code et sans detail.
func (i Incident) Present() bool { return i.Code != "" }

// EnErreur rend l'incident sous forme d'erreur, explicitement.
//
// C'est ce que le code interne faisait implicitement, et c'est ce qu'il doit
// maintenant ecrire. Le cout de la proposition B tient dans cette fonction
// et dans ses appels.
func (i Incident) EnErreur() error {
    if !i.Present() {
        return nil
    }
    return errors.New(i.Message())
}
```

```go
// Ecrire ecrit la valeur dans la reponse HTTP.
//
// C'est la proposition C : l'erreur est un PARAMETRE, et il n'y a plus
// d'assertion de type. L'intergiciel ne devine plus ce qu'on lui donne.
//
// Le cout est une signature qui change, donc une quarantaine de points
// d'appel a reprendre — mais le compilateur les trouve tous, et c'est la
// difference avec les trois autres propositions.
func Ecrire(w http.ResponseWriter, v any, err error) {
    w.Header().Set("Content-Type", "application/json")
    if err != nil {
        w.WriteHeader(http.StatusInternalServerError)
        _ = json.NewEncoder(w).Encode(map[string]string{"erreur": err.Error()})
        return
    }
    w.WriteHeader(http.StatusOK)
    _ = json.NewEncoder(w).Encode(v)
}
```

```go
func TestLeCorrectifRendDeuxCentsEtGardeLIncorporation(t *testing.T) {

    // Et avec un incident bloquant, le 500 porte enfin son code.
    r.Incident = correction.Incident{Code: "E-42", Detail: "quota depasse", Bloquant: true}
    rec = httptest.NewRecorder()
    correction.Ecrire(rec, r, r.Incident.EnErreur())
    if rec.Code != http.StatusInternalServerError {
        t.Fatalf("statut = %d, attendu 500", rec.Code)
    }
    if !strings.Contains(rec.Body.String(), "E-42") {
        t.Fatalf("le corps ne porte pas le code : %s", rec.Body.String())
    }
    t.Logf("avec incident  : %d %s", rec.Code, strings.TrimSpace(rec.Body.String()))
    t.Log("l'incorporation est toujours la : ce n'etait pas le bug")
}
```

```
sans incident  : 200 {"donnees":["a","b","c"],"total":3,"page":1}
avec incident  : 500 {"erreur":"incident E-42 : quota depasse"}
l'incorporation est toujours la : ce n'etait pas le bug
```

**`Reponse` incorpore toujours `Incident`.** `r.Code` s'écrit toujours — le
but du commit du 03/06 est conservé. Et le 500 porte enfin son code, parce
que `Present()` distingue maintenant l'incident vide de l'incident absent.

> L'incorporation n'était pas le bug. Le bug était un type qui était **à la
> fois une donnée et une erreur**. Le commit du 03/06 n'a pas créé ce type :
> il a seulement rendu visible, à travers `Reponse`, quelque chose qui était
> déjà vrai de `Incident`.

## 8. Ce qu'une relecture aurait dû chercher

Les deux relecteurs ont vu un commit qui remplace `incident Incident` par
`Incident` et qui simplifie trente accès. C'est un diff net, et il fait
exactement ce que son titre annonce.

Ce qu'ils n'ont pas vu est **ce que le diff ne contient pas** : l'ensemble des
méthodes de `Reponse` a changé, et ça n'apparaît nulle part dans le diff.

La question à poser sur **tout** commit qui transforme un champ nommé en champ
incorporé :

> **Quelles méthodes et quels champs ce type gagne-t-il, et qui, dans le
> programme, décide quelque chose en fonction de la présence d'une de ces
> méthodes ou d'un de ces champs ?**

Elle se décompose en quatre vérifications, dans cet ordre de gravité :

| | Vérification |
|---|---|
| 1 | le type incorporé porte-t-il une méthode d'une interface de la bibliothèque standard — `error`, `fmt.Stringer`, `json.Marshaler`, `sync.Locker`, `io.Closer` ? |
| 2 | y a-t-il, quelque part, une assertion de type ou un `switch` de type sur cette interface ? |
| 3 | les champs du type incorporé sont-ils exportés, et si oui, remontent-ils dans un JSON ou un formulaire qui constitue un contrat ? |
| 4 | une méthode du type incorporé appelle-t-elle une autre de ses méthodes sur son propre récepteur — le critère de la leçon ? |

La première ligne suffisait ici. Elle prend trente secondes, et elle ne peut
pas se poser à l'intuition : il faut lister l'ensemble des méthodes du type
incorporé. C'est pour ça que la réponse finale est un contrôle automatique et
pas une consigne de relecture.

## 9. Le contrôle

### Pourquoi « on fera attention » et « on n'incorporera plus rien » sont tous les deux faux

**« On fera attention »** est faux parce que l'information nécessaire n'est pas
dans le diff. Deux relecteurs compétents ont approuvé le commit ; il leur
aurait fallu, pour voir le problème, aller lire l'ensemble des méthodes d'un
type qui n'apparaît pas dans le diff et chercher dans tout le programme qui
fait une assertion dessus. Ce n'est pas de l'attention, c'est une recherche.

**« On n'incorporera plus rien »** est faux parce que l'incorporation est le
seul moyen, en Go, d'envelopper une interface en n'en redéfinissant qu'une
méthode — l'exercice 4 l'a mesuré sur `http.ResponseWriter`. L'interdire
remplacerait quatre lignes par trente dans chaque enveloppe, et ces trente
lignes seraient des délégations écrites à la main, c'est-à-dire un endroit de
plus où se tromper. Et il resterait l'aplatissement JSON, qui est souvent
exactement ce qu'on veut.

### Le contrôle retenu

```go
// Package controle est la RACINE DE COMPOSITION du correctif : il connait
// toutes les reponses que les gestionnaires rendent.
//
// C'est le critere de la correction 2.2/4 : une assertion ecrite dans un
// _test.go ne protege pas la construction. Le registre ci-dessous est donc
// du code de PRODUCTION, et il est l'endroit ou le controle de la question 9
// s'applique.
//
// Et c'est aussi le critere de la lecon 2.1 — le niveau le plus bas qui
// puisse porter un garde-fou. Le niveau le plus bas serait le paquet
// correction lui-meme, mais un paquet ne peut pas savoir s'il existe un
// DEUXIEME type ailleurs qui incorpore son Incident. Le controle a besoin de
// la liste complete, donc il vit la ou la liste complete existe.
package controle

import (
    "exemple/c23/ex5/correction"
)

// LesReponses est la liste des types rendus par les gestionnaires.
//
// Toute entree de la table de routage doit avoir sa valeur ici. Ce n'est pas
// une convention : le sondage de controle_test.go le verifie.
var LesReponses = []any{
    correction.Reponse{},
    correction.Solde{},
}
```

```go
// TestAucuneReponseNeSatisfaitUneInterfaceQuiChangeSonSort est le CONTROLE
// de la question 9.
//
// Il tire au moment du TEST, pas de la compilation : Go ne sait pas exprimer
// « ce type ne satisfait pas cette interface » a la compilation. C'est une
// limite du langage, et il faut la dire plutot que de la contourner par une
// convention.
//
// Les trois interfaces verifiees sont celles qui changent le SORT d'une
// valeur passee en any : error decide du statut HTTP, json.Marshaler decide
// du corps, fmt.Stringer decide de ce qu'un journal imprime.
func TestAucuneReponseNeSatisfaitUneInterfaceQuiChangeSonSort(t *testing.T) {
    if len(LesReponses) == 0 {
        t.Fatal("le registre est vide : le controle ne controle rien")
    }
    for _, v := range LesReponses {
        nom := fmt.Sprintf("%T", v)
        t.Run(nom, func(t *testing.T) {
            if _, est := v.(error); est {
                t.Errorf("%s satisfait error : tout intergiciel qui fait une"+
                    " assertion de type en fera un 500", nom)
            }
            if _, est := v.(json.Marshaler); est {
                t.Errorf("%s satisfait json.Marshaler : sa serialisation"+
                    " n'est plus celle de ses champs", nom)
            }
            if _, est := v.(fmt.Stringer); est {
                t.Errorf("%s satisfait fmt.Stringer : tout %%v du journal"+
                    " imprime autre chose", nom)
            }
        })
    }
    t.Logf("%d types de reponse, aucun ne satisfait error, json.Marshaler"+
        " ni fmt.Stringer", len(LesReponses))
}
```

```
2 types de reponse, aucun ne satisfait error, json.Marshaler ni fmt.Stringer
```

| | |
|---|---|
| **quand il tire** | au **test**. Pas à la compilation : Go ne sait pas exprimer « ce type ne satisfait pas cette interface ». C'est une limite du langage, et il faut la dire plutôt que la contourner par une convention |
| **où il vit** | dans `controle`, la **racine de composition** |
| **pourquoi pas plus bas** | le critère de la leçon 2.1 dit : le niveau le plus bas qui puisse porter le garde-fou. Ici le niveau le plus bas serait le paquet `correction` lui-même — mais un paquet ne peut pas savoir s'il existe, ailleurs, un **deuxième** type qui incorpore son `Incident`. Le contrôle a besoin de la liste complète, donc il vit là où la liste complète existe |
| **pourquoi pas dans un `_test.go` seul** | le registre est du code de **production**, pour la raison mesurée en 2.2/4 : une assertion dans un fichier de test ne protège pas la construction. Le registre, lui, est importé par le programme |

### Ce qu'il coûte, chiffré en ce qu'il interdit

| Ce qui devient interdit | Qui paye |
|---|---|
| qu'un type de réponse porte `Error()` | les gestionnaires qui voudraient rendre leur réponse directement comme erreur : ils écrivent `r.Incident.EnErreur()`, **un appel** |
| qu'un type de réponse porte `MarshalJSON()` | un type qui aurait besoin d'une sérialisation sur mesure doit la faire porter par un type dédié au transport, **un type de plus** |
| qu'un type de réponse porte `String()` | les journaux perdent le formatage sur mesure, et impriment les champs. **Zéro ligne de code**, un affichage moins joli |
| qu'un type de réponse échappe au registre | une ligne à ajouter au registre par type de réponse — et le sondage ci-dessous refuse qu'on l'oublie |

Quatre interdictions, un appel et un type de coût total. C'est le contrôle le
moins cher de cette série de corrections.

### La mesure pour ce qu'il ne couvre pas

Le contrôle ne vérifie que ce que le registre contient. Un type ajouté et non
inscrit passerait au vert. D'où le sondage qui rend le registre
non contournable :

```go
// TestLeRegistreEstExhaustif est ce qui rend le controle precedent
// non contournable.
//
// Sans lui, un type de reponse ajoute et non inscrit passe au vert : le
// controle ne verifie que ce qu'on lui a donne. Le sondage lit le paquet
// correction et compare la liste des structs qui incorporent Incident au
// registre.
func TestLeRegistreEstExhaustif(t *testing.T) {
    racine, err := filepath.Abs("../correction")
    if err != nil {
        t.Fatalf("racine : %v", err)
    }
    fs := token.NewFileSet()
    paquets, err := parser.ParseDir(fs, racine, nil, 0)
    if err != nil {
        t.Fatalf("analyse : %v", err)
    }
    if len(paquets) == 0 {
        t.Fatal("aucun paquet analyse : le sondage sonderait le vide")
    }
    var trouves []string
    for _, p := range paquets {
        for nom, fichier := range p.Files {
            if strings.HasSuffix(nom, "_test.go") {
                continue
            }
            ast.Inspect(fichier, func(n ast.Node) bool {
                spec, ok := n.(*ast.TypeSpec)
                if !ok {
                    return true
                }
                st, ok := spec.Type.(*ast.StructType)
                if !ok {
                    return true
                }
                for _, champ := range st.Fields.List {
                    if len(champ.Names) > 0 {
                        continue
                    }
                    if ident, ok := champ.Type.(*ast.Ident); ok && ident.Name == "Incident" {
                        trouves = append(trouves, spec.Name.Name)
                    }
                }
                return true
            })
        }
    }
    sort.Strings(trouves)

    var inscrits []string
    for _, v := range LesReponses {
        inscrits = append(inscrits, strings.TrimPrefix(fmt.Sprintf("%T", v), "correction."))
    }
    sort.Strings(inscrits)

    if strings.Join(trouves, ",") != strings.Join(inscrits, ",") {
        t.Fatalf("types qui incorporent Incident : %v\ntypes inscrits au"+
            " registre      : %v", trouves, inscrits)
    }
    t.Logf("%d types incorporent Incident, %d sont inscrits : %v",
        len(trouves), len(inscrits), trouves)
```

sauvé les onze jours.

### La question qui décide de tout : et si c'est la bibliothèque qui ajoute la méthode ?

**Oui, ce contrôle l'attrape** — et c'est la conséquence directe du choix de le
faire tirer au test plutôt qu'à la relecture.

`v.(error)` est évalué à l'exécution, sur l'ensemble des méthodes **réel** du
type. Que `Error()` vienne du code de l'équipe, d'une bibliothèque tierce
incorporée, ou d'une version de Go qui ajoute une méthode à un type de la
bibliothèque standard, l'assertion répond pareil. Le contrôle rougit à la
montée de version, pas en production.

Un contrôle qui aurait été une consigne de relecture — « vérifiez les méthodes
du type incorporé » — n'aurait rien vu : il n'y a pas de relecture le jour où
l'on passe de Go 1.17 à Go 1.18.

Il reste **une** chose qu'il n'attrape pas, et il faut la nommer : si la
bibliothèque ajoute la méthode à un type incorporé par un type **qui n'est pas
dans le registre**, le sondage ne la verra pas non plus, parce qu'il ne cherche
que les incorporations de `Incident`. Ce qu'il faut en plus est ce que
l'exercice 3 a construit :

> Un **instantané de l'ensemble des méthodes exportées** des types qui
> incorporent quelque chose, vérifié dans les deux sens. C'est le seul
> contrôle qui voie une méthode arriver sans qu'aucune ligne du programme
> n'ait bougé — et `sync.Mutex` a gagné `TryLock` en Go 1.18.

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Un type Go satisfait `error` dès qu'il porte `Error()`. Personne ne le déclare, donc personne ne le relit. |
| ⚫ | Un champ nommé devenu champ anonyme change **l'ensemble des méthodes** du type, et ce changement n'apparaît nulle part dans le diff. |
| ⚫ | La couverture de code ne peut pas voir une méthode promue : il n'y a aucune ligne nouvelle à exécuter. 97 % et 41 tests verts sur un code entièrement faux. |
| ⚫ | `v.(error)` ne sépare pas les erreurs des données. Il sépare ce qui porte `Error()` du reste, et ce n'est pas la même partition. |
| ⚫ | L'incorporation aplatit aussi le **JSON**. Trois champs ajoutés au contrat de l'API par un commit de simplification. |
| ⚫ | Sur onze jours d'incident, la conception ne peut réduire que la **détection** — et elle la réduit de dix jours à cinq minutes. Le reste est du confort. |
| ⚫ | Un indicateur dont le numérateur est produit par le code qu'il surveille ne surveille rien. Celui-ci comptait les `return err` écrits par des développeurs, pas les échecs du système. |
| ⚫ | Un agrégat masque un 100 % sur une route. Le découpage **par route** est ce qui fait la différence entre 2 pour mille et une alerte. |
| ⚫ | « Zéro client n'avait signalé » n'est pas une bonne nouvelle : c'est la preuve que le silence des clients ne vaut rien comme signal. Ça passe avant le correctif de code. |
| ⚫ | Toute correction qui produit une **liste à tenir à jour** produit aussi le prochain incident. C'est pour ça que la proposition D est la pire des quatre. |
| ⚫ | L'incorporation n'était pas le bug. Le bug était un type qui était **à la fois une donnée et une erreur** — et le correctif retenu garde l'incorporation. |
| ⚫ | Un contrôle qui tire au **test** attrape la méthode ajoutée par une bibliothèque ; une consigne de relecture ne l'attrape pas, parce qu'il n'y a pas de relecture le jour d'une montée de version. |
| ⚫ | Un contrôle par registre a besoin d'un **sondage d'exhaustivité**, qui a lui-même besoin de son **test négatif**. |
