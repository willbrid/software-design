## 1. `Number` — l'objet-valeur, et ce qu'il canonise

```go
// Package number defines the Cameroonian subscriber number.
//
// VALUE. Two numbers are the same number if their digits are the same.
package number

import (
    "errors"
    "fmt"
    "strings"
)

var (
    // ErrFormat: the input does not look like a number.
    ErrFormat = errors.New("number: invalid format")
    // ErrPrefix: the national number must start with 6.
    //
    // An error DISTINCT from the format one, because the caller's conduct is not
    // the same: an invalid format is fixed at input, an invalid prefix
    // means "this number is not a mobile": a landline, a short number,
    // a foreign number. The message to the user is different.
    ErrPrefix = errors.New("number: it is not a Cameroonian mobile number")
)

const prefix = "237"

// Number is a canonical MSISDN: 237 followed by nine digits.
type Number struct {
    msisdn string
}

// Parse accepts human spellings and returns ONE form.
//
// The three accepted forms are not an aesthetic choice: they are the
// three that really come in: the international one from an address
// book, the national one from a form, and the local one with the zero that
// people add out of landline habit.
func Parse(input string) (Number, error) {
    var b strings.Builder
    for _, r := range input {
        switch {
        case r >= '0' && r <= '9':
            b.WriteRune(r)
        case r == '+' || r == ' ' || r == '-' || r == '.' || r == '(' || r == ')':
            // Writing separators. Not data.
        default:
            return Number{}, fmt.Errorf("%w: %q in %q", ErrFormat, r, input)
        }
    }
    digits := b.String()

    // Normalization: we bring everything down to the nine-digit national form.
    national := digits
    switch {
    case strings.HasPrefix(digits, prefix) && len(digits) == 12:
        national = digits[3:]
    case strings.HasPrefix(digits, "0") && len(digits) == 10:
        national = digits[1:]
    }

    if len(national) != 9 {
        return Number{}, fmt.Errorf("%w: %d useful digits in %q",
            ErrFormat, len(national), input)
    }
    if national[0] != '6' {
        return Number{}, fmt.Errorf("%w: starts with %q", ErrPrefix, national[0])
    }
    return Number{msisdn: prefix + national}, nil
}

func MustParse(input string) Number {
    n, err := Parse(input)
    if err != nil {
        panic(err)
    }
    return n
}

func (n Number) IsZero() bool { return n.msisdn == "" }

// National returns the nine digits, for display.
func (n Number) National() string {
    if n.IsZero() {
        return ""
    }
    return n.msisdn[3:]
}

// String returns the canonical form, and it is the only one that leaves this package.
// A single written form, so a single map key, a single column.
func (n Number) String() string {
    if n.IsZero() {
        return "zero number"
    }
    return n.msisdn
}
```

Trois décisions à défendre.

**Les trois formes acceptées ne sont pas un choix esthétique.** Ce sont les
trois qui arrivent vraiment : l'international depuis un carnet d'adresses, le
national depuis un formulaire, et le local avec le zéro que les gens ajoutent
par habitude du fixe. Une quatrième — la saisie avec des points — est gratuite
une fois la boucle écrite.

**Le format et le préfixe sont deux erreurs distinctes**, et c'est la leçon 1.5
appliquée à un constructeur :

| L'erreur | La conduite de l'appelant |
|---|---|
| `ErrFormat` | *« vérifiez le numéro »* — l'utilisateur corrige sa saisie |
| `ErrPrefix` | *« ce n'est pas un numéro mobile »* — il n'y a rien à corriger, c'est un fixe |

Deux conduites, deux erreurs. Les fusionner produirait un message qui n'aide
personne, et le test le vérifie dans les deux sens :

```go
// TestFormatAndPrefixAreTwoDistinctErrors: the caller's conduct
// is not the same, so the errors are not the same. Lesson 1.5.
func TestFormatAndPrefixAreTwoDistinctErrors(t *testing.T) {
    _, errFormat := number.Parse("69123456")
    _, errPrefix := number.Parse("222123456")

    if errors.Is(errFormat, number.ErrPrefix) {
        t.Error("a format error is returned as a prefix error")
    }
    if errors.Is(errPrefix, number.ErrFormat) {
        t.Error("a prefix error is returned as a format error")
    }
}
```

**Une seule forme canonique sort du paquet.** Donc une seule clé de map, une
seule clé de cache, une seule colonne de base, un seul destinataire de SMS. Le
test le prouve avec cinq écritures :

```go
// TestThreeSpellingsOneValue is the property asked for by constraint
// 1 of the exercise.
func TestThreeSpellingsOneValue(t *testing.T) {
    spellings := []string{
        "+237 691 23 45 67",
        "237691234567",
        "0691234567",
        "691234567",
        "(237) 691-23-45-67",
    }

    first := number.MustParse(spellings[0])
    for _, e := range spellings[1:] {
        n, err := number.Parse(e)
        if err != nil {
            t.Fatalf("Parse(%q): %v", e, err)
        }
        if n != first {
            t.Fatalf("%q = %s, want %s", e, n, first)
        }
    }

    // Map key, without a hash function.
    seen := map[number.Number]int{}
    for _, e := range spellings {
        seen[number.MustParse(e)]++
    }
    if len(seen) != 1 || seen[first] != len(spellings) {
        t.Fatalf("map = %v, want one key seen %d times", seen, len(spellings))
    }
    if first.String() != "237691234567" {
        t.Fatalf("canonical form = %q", first.String())
    }
}
```

## 2. `Amount` — et le mécanisme qui interdit l'addition

```go
// Package amount defines a sum in CFA francs.
//
// VALUE. No cents: the FCFA has none, and a type that plans for them
// invites using them, then rounding them, then wondering where
// the three francs went.
package amount

import (
    "errors"
    "fmt"
    "math"
    "strconv"
)

var (
    // ErrNegative: a negative amount does not exist. A withdrawal is not a
    // negative deposit, it is an operation with another name.
    ErrNegative = errors.New("amount: negative")
    // ErrOverflow: the sum overflows int64. Unlikely, and that is the reason
    // why nobody checks it, until the day a test of
    // fuzzing or a badly parsed field produces 9 223 372 036 854 775 807.
    ErrOverflow = errors.New("amount: overflow")
    // ErrInsufficient: the subtraction would go below zero. It is a business
    // ANSWER, not an outage.
    ErrInsufficient = errors.New("amount: insufficient")
)

// Amount is a sum in FCFA, always positive or zero.
//
// The type is distinct from int64: that is what makes impossible
// balance + 1 or balance + operationCount. It costs a call to FCFA() everywhere
// where an integer is really needed, and that is the point: those places become
// visible, and there are few of them.
type Amount struct {
    fcfa int64
}

// Zero is the zero amount. The type's zero value IS a valid state here: a
// zero balance makes sense, and it is even the initial state of every wallet.
var Zero = Amount{}

func FCFA(n int64) (Amount, error) {
    if n < 0 {
        return Amount{}, fmt.Errorf("%w: %d", ErrNegative, n)
    }
    return Amount{fcfa: n}, nil
}

func MustFCFA(n int64) Amount {
    m, err := FCFA(n)
    if err != nil {
        panic(err)
    }
    return m
}

// Value returns the integer, and it is the only way out of the type.
func (m Amount) Value() int64 { return m.fcfa }

func (m Amount) IsZero() bool { return m.fcfa == 0 }

// Plus adds. Returns an error rather than a wrong result.
func (m Amount) Plus(other Amount) (Amount, error) {
    if m.fcfa > math.MaxInt64-other.fcfa {
        return Amount{}, fmt.Errorf("%w: %d + %d", ErrOverflow, m.fcfa, other.fcfa)
    }
    return Amount{fcfa: m.fcfa + other.fcfa}, nil
}

// Minus subtracts. Going below zero is a business answer, not a negative
// result.
func (m Amount) Minus(other Amount) (Amount, error) {
    if m.fcfa < other.fcfa {
        return Amount{}, fmt.Errorf("%w: %d - %d", ErrInsufficient, m.fcfa, other.fcfa)
    }
    return Amount{fcfa: m.fcfa - other.fcfa}, nil
}

// PerMille returns a fraction of the amount, rounded down.
//
// An integer per mille, not a float64: a fee of 1.5 % is 15 per
// mille, exactly, and 0.015 is not.
func (m Amount) PerMille(rate int64) (Amount, error) {
    if rate < 0 {
        return Amount{}, fmt.Errorf("%w: rate %d", ErrNegative, rate)
    }
    if rate != 0 && m.fcfa > math.MaxInt64/rate {
        return Amount{}, fmt.Errorf("%w: %d x %d", ErrOverflow, m.fcfa, rate)
    }
    return Amount{fcfa: m.fcfa * rate / 1000}, nil
}

// Exceeds compares.
func (m Amount) Exceeds(limit Amount) bool { return m.fcfa > limit.fcfa }

func (m Amount) String() string { return strconv.FormatInt(m.fcfa, 10) + " FCFA" }
```

### Pas de centimes

Le FCFA n'en a pas. Un type qui en prévoit invite à les utiliser, puis à les
arrondir, puis à se demander où sont passés les trois francs. C'est une décision
de modélisation, pas une optimisation.

### Le mécanisme de la contrainte 2, et ce qu'il coûte

La question demandait : *quel mécanisme Go te donne ça, et que coûte-t-il ?*

Le mécanisme est le **type nommé à champ privé**. `Amount` n'est pas un alias
de `int64` : c'est une structure dont le seul champ est inaccessible. Donc
`m + 1` ne compile pas, et le message du compilateur est explicite :

```
invalid operation: m + 1 (mismatched types amount.Amount and untyped int)
```

Noter qu'un `type Amount int64` ne suffirait **pas** : il autoriserait
`m + 1`, parce qu'une constante non typée s'adapte. C'est la différence entre un
type nommé et un type encapsulé, et elle décide de tout ici.

Le coût, et il est réel :

| Ce qu'on paie | Où ça se voit |
|---|---|
| un appel à `Value()` partout où il faut vraiment un entier | la sérialisation, le SQL, les métriques |
| une erreur à traiter sur chaque addition | `Plus` et `Minus` rendent `(Amount, error)` |
| pas d'opérateurs | `a.Plus(b)` au lieu de `a + b`, moins agréable à lire |
| pas de `Amount` dans un `switch` numérique | il faut passer par `Value()` |

Le deuxième point est celui qu'on sous-estime, et c'est pourtant le bon. Une
addition de sommes d'argent **peut** échouer, par dépassement. `a + b` ne le dit
pas ; `a.Plus(b)` oblige à décider quoi faire. Le test mesure que ce n'est pas
théorique :

```go
// TestOverflowIsDetected: the unlikely case nobody checks.
func TestOverflowIsDetected(t *testing.T) {
    almostMax := amount.MustFCFA(math.MaxInt64 - 10)

    if _, err := almostMax.Plus(amount.MustFCFA(11)); !errors.Is(err, amount.ErrOverflow) {
        t.Errorf("Plus: err = %v, want ErrOverflow", err)
    }
    if _, err := almostMax.PerMille(2); !errors.Is(err, amount.ErrOverflow) {
        t.Errorf("PerMille: err = %v, want ErrOverflow", err)
    }
}
```

### Et l'invariant qui déménage

`Minus` refuse de passer sous zéro, et rend `ErrInsufficient` — une **réponse
métier**, pas une panne. Conséquence que la question 3 attendait :

> L'invariant *« le solde n'est jamais négatif »* n'est pas tenu par une garde
> écrite dans le portefeuille. Il est tenu par le **type du solde**.

Un invariant délégué à un type est un invariant qui n'a **qu'un seul endroit à
relire**. C'est la réponse à la question 6 de l'exercice 1, et elle est
structurelle plutôt que disciplinaire.

### Pourmille plutôt qu'un flottant

```
func (m Amount) PerMille(taux int64) (Amount, error)
```

Des frais de 1,5 % sont **15 pour mille**, exactement. `0.015` ne l'est pas, et
la différence se voit au troisième calcul. Le test fixe l'arrondi comme une
décision commerciale, pas comme un détail :

```go
// TestFeesAreExactPerMille guards the decision not to use
// float64.
//
// The cases are chosen so that the difference shows: 1.5 % of 1,234,567
// is 18,518.505, and rounding is a commercial decision.
func TestFeesAreExactPerMille(t *testing.T) {
    tc := []struct {
        sum  int64
        rate int64
        want int64
    }{
        {1_000_000, 15, 15_000},
        {1_234_567, 15, 18_518}, // rounded down, in the client's favor
        {100, 15, 1},
        {66, 15, 0}, // 0.99 FCFA: the fee is zero, not "almost one"
        {1_000_000, 0, 0},
    }

    for _, c := range tc {
        fees, err := amount.MustFCFA(c.sum).PerMille(c.rate)
        if err != nil {
            t.Fatalf("PerMille(%d, %d): %v", c.sum, c.rate, err)
        }
        if fees.Value() != c.want {
            t.Errorf("%d x %d per mille = %d, want %d",
                c.sum, c.rate, fees.Value(), c.want)
        }
    }
}
```

Le cas `{66, 15, 0}` est le plus instructif : 0,99 FCFA de frais devient **zéro**,
pas « presque un ». C'est une décision — l'arrondi va vers le client — et elle
est écrite dans un test plutôt que dans un commentaire.

## 3. `Wallet` — l'entité, et le ⚫ qui ne coûte rien

```go
type Level int

const (
    // Unverified: no document provided.
    Unverified Level = iota + 1
    // IDCard: national identity card recorded.
    IDCard
    // Full: ID card and proof of address.
    Full
)

// Limit returns this level's daily limit.
//
// It is THE answer to question 3 of the exercise. The limit is NOT a field
// of the wallet: it is a FUNCTION of the level. The state "limit
// not matching the level" is therefore not "forbidden", it is
// NON-EXISTENT: there is nowhere to write it.
//
// It is a ⚫, and the kind of ⚫ that costs nothing: we did not add a
// guard, we removed a field. The best safeguard is the one that removes a
// piece of data rather than the one that watches one.
func (n Level) Limit() amount.Amount {
    switch n {
    case Unverified:
        return amount.MustFCFA(50_000)
    case IDCard:
        return amount.MustFCFA(500_000)
    case Full:
        return amount.MustFCFA(5_000_000)
    }
    // An unknown level has no permissive limit: it has a zero limit.
    // The default of an enumeration must always be the most
    // restrictive one, never the first of the list.
    return amount.Zero
}

func (n Level) Valid() bool { return n >= Unverified && n <= Full }

func (n Level) String() string {
    switch n {
    case Unverified:
        return "unverified"
    case IDCard:
        return "cni"
    case Full:
        return "full"
    }
    return "unknown level"
}

// Wallet is an ENTITY, identified by its number.
type Wallet struct {
    // Forbids ==: two descriptions of the same wallet at two instants
    // differ by their balance and are the SAME wallet.
    _ [0]func()

    number  number.Number
    balance amount.Amount
    level   Level
    blocked bool
    built   bool
}

// Open creates an empty wallet. A new wallet is not verified, and
// its balance is zero: both zero values are the right defaults here.
func Open(n number.Number) (Wallet, error) {
    if n.IsZero() {
        return Wallet{}, ErrNoNumber
    }
    return Wallet{number: n, balance: amount.Zero, level: Unverified, built: true}, nil
}
```

### La contrainte 3, et sa réponse

> *Le plafond journalier **découle** du niveau de vérification, et il est
> impossible de les désaccorder.*

La réponse n'est pas une garde. C'est une **suppression** :

```
func (n Level) Limit() amount.Amount
```

Le plafond n'est pas un champ du portefeuille. C'est une fonction du niveau. Il
n'existe donc **aucun endroit** où écrire un plafond qui ne correspond pas — pas
« c'est interdit », mais « ça n'existe pas ».

| Niveau | Mécanisme | Ce que ça vaut |
|---|---|---|
| 🟡 | un commentaire *« mettre à jour le plafond avec le KYC »* | rien, dès le deuxième développeur |
| 🟠 | un `SetNiveau` qui met les deux à jour | n'importe qui peut encore écrire le champ |
| 🔴 | champs privés, et un seul mutateur qui écrit les deux | il reste deux données à garder cohérentes |
| ⚫ | **le plafond n'est pas une donnée** | il n'y a plus rien à garder |

> Le meilleur garde-fou est celui qui **retire une donnée**, pas celui qui en
> surveille une. Chaque fois qu'un invariant lie deux champs, demande si l'un
> des deux ne serait pas une fonction de l'autre.

### Le défaut d'une énumération

```
    // Un unknown level n'a pas de plafond permissif : il a un plafond nul.
    return amount.Zero
```

Un niveau mal analysé — une colonne de base à 0, un entier venu d'un JSON — ne
doit pas tomber sur le plafond le plus large.

> Le défaut d'une énumération est toujours le choix le plus **restrictif**,
> jamais le premier de la liste.

C'est exactement le `default: 500` de la leçon 1.5, appliqué à une valeur métier
au lieu d'un statut HTTP. Et c'est testé :

```go
// TestAnUnknownLevelHasNoPermissiveLimit guards the choice of default.
// A badly parsed enumeration (a database column at 0, an integer from a
// JSON, must not land on the widest limit. The default of an
// enumeration is always the most restrictive choice.
func TestAnUnknownLevelHasNoPermissiveLimit(t *testing.T) {
    for _, n := range []wallet.Level{0, -1, 99} {
        if !n.Limit().IsZero() {
            t.Errorf("Level(%d).Limit() = %s, want zero", n, n.Limit())
        }
        if n.Valid() {
            t.Errorf("Level(%d) declares itself valid", n)
        }
    }

    if _, err := open(t).Check(99); !errors.Is(err, wallet.ErrUnknownLevel) {
        t.Errorf("Check(99): err = %v, want ErrUnknownLevel", err)
    }
}
```

### La contrainte 6 — la règle dans l'entité, la mesure en argument

```go
// CanSend is the RULE, and it receives the day's total because it does not
// hold it.
//
// GUARANTEED
//
//    Returns nil if and only if the wallet is built, not blocked, and
//    if dayTotal + m does not exceed the level's limit.
//
// NOT GUARANTEED
//
//    That dayTotal is still right when the caller acts. Read then act
//    is a check-then-act, and only a transaction closes it. This method
//    DECIDES; it does not PROTECT.
//
//    That the balance is enough: Debit says so, for a reason: an
//    insufficient balance and an exceeded limit call for two
//    for the caller, so two answers.
func (p Wallet) CanSend(m amount.Amount, dayTotal amount.Amount) error {
    if err := p.exist(); err != nil {
        return err
    }
    if p.blocked {
        return fmt.Errorf("%w: %s", ErrBlocked, p.number)
    }
    total, err := dayTotal.Plus(m)
    if err != nil {
        return fmt.Errorf("wallet: day total: %w", err)
    }
    if total.Exceeds(p.level.Limit()) {
        return fmt.Errorf("%w: %s totals %s + %s for a limit of %s",
            ErrLimitExceeded, p.number, dayTotal, m, p.level.Limit())
    }
    return nil
}
```

Et les deux clauses `NON GARANTI` que la question demandait d'écrire. La seconde
est celle qu'on oublie :

> Que le **solde** suffise : c'est `Debit` qui le dit, et pour une raison — un
> solde insuffisant et un plafond dépassé appellent deux conduites différentes
> chez l'appelant, donc deux réponses.

| L'issue | Ce que l'abonné peut faire |
|---|---|
| plafond dépassé | attendre demain, ou se faire vérifier |
| solde insuffisant | recharger |

Deux conduites, deux erreurs — et le test exerce les deux **en les croisant**,
ce qui est le seul moyen de prouver qu'elles ne sont pas confondues :

```go
// TestLimitAndBalanceAreTwoDifferentAnswers: two distinct conducts
// for the caller, so two errors. Lesson 1.5.
//
// An exceeded limit is solved by waiting for tomorrow or getting verified.
// An insufficient balance is solved by topping up. Merging the two is
// send back a message that helps nobody.
func TestLimitAndBalanceAreTwoDifferentAnswers(t *testing.T) {
    rich, err := open(t).Credit(amount.MustFCFA(1_000_000))
    if err != nil {
        t.Fatalf("Credit: %v", err)
    }
    // Unverified: limit 50,000, but a balance of one million.
    hundred := amount.MustFCFA(100_000)

    if err := rich.CanSend(hundred, amount.Zero); !errors.Is(err, wallet.ErrLimitExceeded) {
        t.Fatalf("limit: err = %v", err)
    }
    // The balance, however, is more than enough.
    if _, err := rich.Debit(hundred); err != nil {
        t.Fatalf("Debit: %v", err)
    }

    poor, err := open(t).Check(wallet.Full)
    if err != nil {
        t.Fatalf("Check: %v", err)
    }
    // Limit 5,000,000, balance zero.
    if err := poor.CanSend(hundred, amount.Zero); err != nil {
        t.Fatalf("the limit should not object: %v", err)
    }
    if _, err := poor.Debit(hundred); !errors.Is(err, amount.ErrInsufficient) {
        t.Fatalf("balance: err = %v", err)
    }
}
```

Un portefeuille riche mais non vérifié, un portefeuille vérifié mais vide. Si
les deux erreurs étaient fusionnées, ce test ne passerait pas.

### La frontière, au franc

```go
// TestTheLimitRuleExercisesTheBoundary: the day's total is an ARGUMENT, and
// the boundary is tested to the franc.
func TestTheLimitRuleExercisesTheBoundary(t *testing.T) {
    p, err := open(t).Check(wallet.IDCard) // limit 500,000
    if err != nil {
        t.Fatalf("Check: %v", err)
    }

    tc := []struct {
        total  int64
        amount int64
        want   error
        why    string
    }{
        {0, 500_000, nil, "the limit can be reached, it is not forbidden"},
        {499_000, 1_000, nil, "exactly at the limit"},
        {499_000, 1_001, wallet.ErrLimitExceeded, "one franc too many"},
        {500_000, 1, wallet.ErrLimitExceeded, "limit already reached"},
        {0, 500_001, wallet.ErrLimitExceeded, "in a single operation"},
    }

    for _, c := range tc {
        err := p.CanSend(amount.MustFCFA(c.amount), amount.MustFCFA(c.total))
        if !errors.Is(err, c.want) {
            t.Errorf("total %d + %d: err = %v, want %v (%s)",
                c.total, c.amount, err, c.want, c.why)
        }
    }
}
```

Le premier cas dit ce que le reste du tableau n'aurait pas dit : **le plafond est
atteignable.** 500 000 sur un plafond de 500 000 passe. C'est un plafond, pas une
limite stricte, et c'est le genre de décision qu'on découvre six mois plus tard
en lisant une réclamation.

## 4. La contrainte 5 — la valeur zéro, trois fois, trois réponses

| Type | Valide ? | Comment on le sait | Ce qu'on a fait |
|---|---|---|---|
| `Amount` | **oui** | un solde de zéro a un sens, c'est même l'état initial | on l'exporte sous le nom `Zero`, pour que personne n'écrive `Amount{}` |
| `Level` | **non** | `Level(0)` n'est aucun des trois niveaux | l'énumération commence à `iota + 1`, `Limit()` rend zéro, `Valid()` rend faux |
| `Number` | **non** | un numéro vide n'identifie rien | `IsZero()`, et `String()` rend `"number nul"` |
| `Wallet` | **non** | et **rien ne le trahit** : un solde nul et un numéro nul sont des valeurs zéro légitimes de leurs types | il faut un champ `built` dédié |

La dernière ligne est la moins élégante et la plus honnête. Elle mérite d'être
regardée en face :

```go
// TestTheZeroValueOfAWalletIsNotAWallet: the answer is NO, and
// no field gives it away: a zero balance and a zero number are legitimate
// zero values of their types. So we need the built field.
func TestTheZeroValueOfAWalletIsNotAWallet(t *testing.T) {
    var empty wallet.Wallet
    thousand := amount.MustFCFA(1000)

    if err := empty.CanSend(thousand, amount.Zero); !errors.Is(err, wallet.ErrNotFound) {
        t.Errorf("CanSend: err = %v", err)
    }
    if _, err := empty.Credit(thousand); !errors.Is(err, wallet.ErrNotFound) {
        t.Errorf("Credit: err = %v: a non-existent wallet got money", err)
    }
    if _, err := empty.Debit(thousand); !errors.Is(err, wallet.ErrNotFound) {
        t.Errorf("Debit: err = %v", err)
    }
    if _, err := empty.Check(wallet.Full); !errors.Is(err, wallet.ErrNotFound) {
        t.Errorf("Check: err = %v", err)
    }
    if _, err := empty.Block(); !errors.Is(err, wallet.ErrNotFound) {
        t.Errorf("Block: err = %v", err)
    }
}
```

Le test vérifie que les **cinq** opérations refusent la valeur zéro. Le cas de
`Credit` est celui qui fait peur : sans le champ `built`, un portefeuille
inexistant aurait reçu de l'argent, et cet argent n'aurait appartenu à personne.

> Quand aucun champ ne trahit la valeur zéro, il faut un drapeau explicite.
> C'est laid, c'est indispensable, et ça vaut mieux qu'un type dont la valeur
> zéro se comporte comme un objet valide.

## 5. La contrainte 4 — et la découverte de l'exercice

```go
// Package guard holds only decision tests.
package guard

import (
    "os"
    "os/exec"
    "path/filepath"
    "strings"
    "testing"

    // These three imports are not decorative: they are the CACHE GUARD.
    //
    // Go's test cache invalidates a package's result when a package
    // it depends on changes. A test that checks by running "go build" in a
    // subprocess depends on NOTHING in the compiler's sense: so Go has the
    // right to return a stale result, and it does.
    //
    // Measured, not assumed. Removing the [0]func() field from Wallet:
    //
    //    $ go test ./guard/              ok (cached)
    //    $ go test -count=1 ./guard/     FAIL
    //
    // The ⚫ had just disappeared, and the test said "all is well".
    //
    // The -count=1 guard is fragile: it lives in the command, not in
    // the code, and the first "go test ./..." gets around it. The robust guard
    // is this one: the test IMPORTS what it watches, so the cache
    // is invalidated, and the witness below really uses them.
    "example/mobile/amount"
    "example/mobile/number"
    "example/mobile/wallet"
)

// TestTheseProgramsDoNotCompile guards the three ⚫ of the model.
//
// Each case carries the FRAGMENT of the expected compile message, and it is
// required. While writing this file, the third case went green for
// a completely different reason: the program did not compile because an import
// was not used. The test was satisfied, and it checked nothing.
//
//    A test that expects a failure must check the REASON for the failure. Otherwise
//    any error satisfies it, and the first typo makes it
//    green forever.
//
// The witness of the next test is not enough to catch that: the witness says the
// model compiles, it does not say why the others do not compile.
func TestTheseProgramsDoNotCompile(t *testing.T) {
    tc := []struct {
        name  string
        code  string
        want  string
        guard string
    }{
        {
            name: "compare two wallets",
            code: `
    a, _ := wallet.Open(number.MustParse("691234567"))
    b, _ := a.Credit(amount.MustFCFA(1000))
    _ = a == b
`,
            want:  "cannot be compared",
            guard: "two states of the SAME wallet would be declared different",
        },
        {
            name: "write a limit",
            code: `
    m := amount.MustFCFA(10_000_000)
    n := number.MustParse("691234567")
    _ = n
    _ = wallet.Wallet{Limit: m}
`,
            want:  "unknown field Limit",
            guard: "the limit would become a field again, so it could drift from the level",
        },
        {
            name: "add an amount to an integer",
            code: `
    n := number.MustParse("691234567")
    p, _ := wallet.Open(n)
    _ = p
    m := amount.MustFCFA(1000)
    _ = m + 1
`,
            want:  "invalid operation",
            guard: "an amount would add to an index, an identifier, a counter",
        },
    }

    for _, c := range tc {
        t.Run(c.name, func(t *testing.T) {
            output, err := compile(t, c.code)
            if err == nil {
                t.Fatalf("the program compiled: %s\n%s", c.guard, output)
            }
            if !strings.Contains(output, c.want) {
                t.Fatalf("compilation failed, but not for the reason"+
                    " expected. Wanted a message holding %q, got:\n%s",
                    c.want, output)
            }
            t.Logf("%s", firstUsefulLine(output))
        })
    }
}

// TestTheModelBehaves is the WITNESS, and it runs IN PROCESS.
//
// Two reasons not to put it through the compiler like the others:
//
//  1. a witness that takes the same path as what it watches fails at the
//     same time as it;
//  2. in process, it creates the compile dependency that invalidates the cache.
//
// It checks the three ⚫ from their positive side: equality by identity
// answers, the limit follows the level, and amount arithmetic works.
func TestTheModelBehaves(t *testing.T) {
    a, err := wallet.Open(number.MustParse("691234567"))
    if err != nil {
        t.Fatalf("Open: %v", err)
    }
    b, err := a.Credit(amount.MustFCFA(1000))
    if err != nil {
        t.Fatalf("Credit: %v", err)
    }

    if !a.SameAs(b) {
        t.Error("two states of the same wallet should be the same wallet")
    }
    if b.Balance().Value() != 1000 {
        t.Errorf("balance = %s, want 1000 FCFA", b.Balance())
    }
    if a.Limit().Value() != 50_000 {
        t.Errorf("limit = %s, want 50 000 FCFA", a.Limit())
    }
}

const model = `package main

import (
    "example/mobile/amount"
    "example/mobile/number"
    "example/mobile/wallet"
)

func main() {
%s
}
`

func compile(t *testing.T, body string) (string, error) {
    t.Helper()

    root, err := filepath.Abs("..")
    if err != nil {
        t.Fatalf("root: %v", err)
    }
    records, err := os.MkdirTemp(root, "trial")
    if err != nil {
        t.Fatalf("records: %v", err)
    }
    t.Cleanup(func() { _ = os.RemoveAll(records) })

    source := filepath.Join(records, "main.go")
    content := strings.Replace(model, "%s", strings.TrimRight(body, "\n"), 1)
    if err := os.WriteFile(source, []byte(content), 0o600); err != nil {
        t.Fatalf("write: %v", err)
    }

    cmd := exec.Command("go", "build", "-o", filepath.Join(records, "bin"), source)
    cmd.Dir = records
    output, err := cmd.CombinedOutput()
    return string(output), err
}

func firstUsefulLine(output string) string {
    for _, l := range strings.Split(output, "\n") {
        if l = strings.TrimSpace(l); l != "" && !strings.HasPrefix(l, "#") {
            return l
        }
    }
    return output
}
```

Trois ⚫ gardés par un seul fichier. Mais ce fichier a eu **trois versions**, et
les deux premières étaient fausses. Il faut raconter les trois, parce que c'est
le vrai contenu de cette correction.

### Version 1 — elle passait pour la mauvaise raison

Le troisième cas vérifiait qu'on ne peut pas additionner un `Amount` et un
entier. Il passait. Voilà ce que disait le compilateur :

```
./main.go:5:2: "example/mobile/number" imported and not used
```

Le programme ne compilait pas, mais **pas pour la raison visée** : un import
inutilisé. Le test était satisfait et ne vérifiait rien du tout. Il serait resté
vert indéfiniment, y compris après la suppression du type `Amount`.

Je ne l'ai vu que parce que le test affichait le message avec `t.Logf`.

> **Un test qui attend un échec doit vérifier la raison de l'échec.** Sinon
> n'importe quelle erreur le satisfait, et la première faute de frappe le rend
> définitivement vert.

D'où le champ `want` dans le tableau de cas : chaque cas porte un fragment du
message de compilation qu'il exige.

### Version 2 — elle passait parce qu'elle était en cache

Puis j'ai appliqué la modification n° 7 de la campagne : retirer le champ
`[0]func()` de `Wallet`. Résultat :

```
$ go test ./garde/              ok    exemple/mobile/garde  (cached)
```

Le ⚫ venait de disparaître, et le test disait *« tout va bien »*.

Le mécanisme est exact et il faut le comprendre, parce qu'il touche **tous** les
tests de décision du niveau 1. Le cache de tests de Go invalide le résultat d'un
paquet quand un paquet **dont il dépend** change. Ce test valide en lançant
`go build` dans un sous-processus : il ne dépend de rien au sens du compilateur.
Go a donc parfaitement le droit de rendre une réponse périmée, et il le fait.

```
$ go test -count=1 ./garde/     FAIL  exemple/mobile/garde
```

Le remède par `-count=1` est fragile : il vit dans la commande, pas dans le code,
et le premier `go test ./...` le contourne.

### Version 3 — le remède, et il est dans les imports

> **Un test de décision doit dépendre, au sens du compilateur, de ce qu'il
> surveille.** Sinon il surveille une version qui n'existe plus.

Le fichier importe donc `amount`, `number` et `wallet`, et le témoin les
**utilise vraiment** — en processus, pas via un sous-processus. Deux bénéfices
d'un seul geste : le cache s'invalide, et le témoin ne tombe plus en même temps
que ce qu'il surveille.

Vérification : avec le champ retiré, et **sans** `-count=1` :

```
$ go test ./garde/
    garde_test.go:93: le programme a compile : two states of the SAME wallet would be declared different
FAIL  exemple/mobile/garde
```

### Les trois modes de panne de cette famille de tests

Pour mémoire, parce qu'aucun des trois n'est évident :

| Mode de panne | Le remède |
|---|---|
| passer parce que **tout** est cassé | un **témoin** qui réussit |
| passer **pour la mauvaise raison** | un **fragment de message** attendu |
| passer parce qu'il est **en cache** | **importer** ce qu'on surveille |

Et la portée : les tests de décision du niveau 1 ont tous le troisième défaut.
Celui qui lit la source avec `go/ast`, celui qui interroge `go list`, celui qui
compile un programme — les trois valident par un sous-processus, donc les trois
sont hors du graphe que Go connaît.

## 6. La campagne de modifications

| # | La modification | Qui crie |
|---|---|---|
| 1 | un niveau inconnu rend le plafond le plus large | `TestAnUnknownLevelHasNoPermissiveLimit` |
| 2 | la frontière du plafond devient `>=` au lieu de `>` | `TestTheLimitRuleExercisesTheBoundary` |

| 4 | `Amount.Minus` rend un négatif au lieu d'une erreur | **3 tests**, dans deux paquets |
| 5 | le préfixe `6` n'est plus vérifié | `TestLesSaisiesInvalidsSontRefusees` |

| 7 | le champ `[0]func()` est retiré de `Wallet` | `TestTheseProgramsDoNotCompile` — **après** le correctif du §5 |

Sept sur sept. Deux remarques.

**La n° 4 fait tomber trois tests dans deux paquets**, dont
`TestLeSoldeNeDevientJamaisNegatif` du portefeuille. C'est la signature d'un
invariant **délégué** : quand il tombe, il tombe partout où on s'appuyait
dessus. C'est bon signe — ça veut dire que l'appui est réel.

**La n° 7 est celle qui a révélé le bug du cache.** Sans la campagne, le
correctif du §5 n'aurait jamais été écrit, et le ⚫ aurait été gardé par un test
qui ne regardait plus rien.

> Une campagne de modifications ne mesure pas seulement le code. Elle mesure
> aussi **les tests qui prétendent le garder** — et c'est souvent là qu'elle
> trouve le plus.

## 7. La contrainte 7 — compter les lignes, et nommer ce qu'on a acheté

| | |
|---|---|
| `number` | 95 lignes |
| `amount` | 96 lignes |
| `wallet` | 220 lignes |
| **total modèle** | **411 lignes** |
| tests | 559 lignes |

Et les bugs que ce modèle rend **impossibles** — la question demandait trois, en
voici six, avec le mécanisme de chacun :

| Le bug | Ce qui le rend impossible |
|---|---|
| deux comptes pour un abonné parce que le numéro est écrit différemment | une seule forme canonique sort de `number` |
| un plafond qui ne correspond pas au niveau KYC | le plafond n'est pas une donnée |
| un solde négatif | `amount.Minus` rend une erreur |
| un montant additionné à un index, un compteur, un identifiant | le type encapsulé |
| un portefeuille inexistant qui reçoit de l'argent | le champ `built` |
| deux états du même portefeuille déclarés différents | `==` ne compile pas |

Et les trois qu'il ne rend **pas** impossibles, parce qu'il faut aussi savoir le
dire :

- **le dépassement de plafond par concurrence.** `CanSend` décide, il ne
  protège pas. La clause le dit. La fermeture est une transaction, niveau 5.
- **un plafond réglementaire mal paramétré.** Si la conformité demande 600 000 au
  lieu de 500 000, on change une constante — et rien ne vérifie qu'elle est la
  bonne. C'est une donnée de référence, pas un invariant.
- **un numéro recyclé par l'opérateur.** Le modèle croira que c'est le même
  abonné. C'est la question 2 de l'exercice 4, et le modèle n'y répond pas.

## Ce que ça ne règle pas

**Le plafond ne peut pas être personnalisé.** C'est la conséquence directe du ⚫ :
le plafond étant une fonction du niveau, on ne peut pas accorder 2 000 000 à un
commerçant particulier sans changer le type. Si le métier le demande — et il le
demandera —, deux options :

| Option | L'invariant devient | Ce qu'on perd |
|---|---|---|
| un champ `plafondAccorde` optionnel | « le plafond accordé ne dépasse pas le maximum du niveau » | le ⚫ devient un 🔴 : il y a de nouveau deux données |
| un `Level` par profil commercial | rien ne change | la liste des niveaux grossit, et elle devient une donnée de référence |

La seconde garde le ⚫ et c'est celle qu'il faut défendre en réunion. La première
est celle qui sera demandée. Savoir laquelle on choisit **avant** la réunion est
tout l'intérêt d'avoir écrit le modèle.

**`Level.Limit()` contient des montants en dur.** Ils devraient venir d'une
table de paramétrage, parce que le régulateur les change. Le ⚫ survit à ce
changement — le plafond reste une fonction du niveau, elle consulte juste une
table — mais la fonction devient `Limit(bareme Bareme)`, et le barème descend
en argument. Encore la même mécanique.

**Rien ne vérifie que `amount.PerMille` est appelé avec le bon taux.** Les
frais sont un paramètre, et un paramètre faux est un paramètre faux. C'est hors
du modèle, et c'est une donnée de référence à surveiller.

**L'identité reste le numéro de téléphone.** Ce n'est pas un oubli, c'est un
choix — et c'est le sujet de l'exercice 4, où il se révèle discutable.

---

## Ce qu'il faut retenir

1. **Une seule forme canonique sort d'un objet-valeur.** Donc une seule clé de
   map, de cache, de colonne, de destinataire.
2. **Deux conduites de l'appelant, deux erreurs** — format et préfixe, plafond
   et solde. Et on le vérifie en les croisant.
3. **Un type encapsulé, pas un type nommé.** `type Amount int64` autorise
   `m + 1` ; une structure à champ privé ne l'autorise pas.
4. **Une addition de montants peut échouer.** `a.Plus(b)` oblige à décider,
   `a + b` ne le dit pas.
5. **Un invariant délégué à un type n'a qu'un seul endroit à relire.** Le solde
   n'est jamais négatif parce que `Minus` le refuse.
6. **Le meilleur garde-fou retire une donnée** au lieu d'en surveiller une. Si
   un invariant lie deux champs, l'un est peut-être une fonction de l'autre.
7. **Le défaut d'une énumération est le choix le plus restrictif**, jamais le
   premier de la liste.
8. **Un plafond est atteignable.** Le premier cas du tableau de frontière dit ce
   que le reste n'aurait pas dit.
9. **Quand aucun champ ne trahit la valeur zéro, il faut un drapeau explicite.**
10. **Un test qui attend un échec doit vérifier la raison de l'échec.**
11. **Un test de décision doit dépendre, au sens du compilateur, de ce qu'il
    surveille** — sinon le cache le rend périmé, et il devient vert au pire
    moment.
12. **Une campagne de modifications mesure aussi les tests.** C'est souvent là
    qu'elle trouve le plus.
