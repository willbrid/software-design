## 1. `Numero` — l'objet-valeur, et ce qu'il canonise

```go
// Package numero definit le numero d'abonne camerounais.
//
// VALEUR. Deux numeros sont le meme numero si leurs chiffres sont les memes.
package numero

import (
    "errors"
    "fmt"
    "strings"
)

var (
    // ErrFormat : la saisie ne ressemble pas a un numero.
    ErrFormat = errors.New("numero : format invalide")
    // ErrPrefixe : le numero national doit commencer par 6.
    //
    // Erreur DISTINCTE du format, parce que la conduite de l'appelant n'est pas
    // la meme : un format invalide se corrige a la saisie, un prefixe invalide
    // veut dire « ce numero n'est pas un mobile » — un fixe, un numero court,
    // un numero etranger. Le message a l'utilisateur est different.
    ErrPrefixe = errors.New("numero : ce n'est pas un numero mobile camerounais")
)

const indicatif = "237"

// Numero est un MSISDN canonique : 237 suivi de neuf chiffres.
type Numero struct {
    msisdn string
}

// Analyser accepte les ecritures humaines et rend UNE forme.
//
// Les trois formes acceptees ne sont pas un choix esthetique : ce sont les
// trois qui arrivent reellement — l'international depuis un carnet
// d'adresses, le national depuis un formulaire, et le local avec le zero que
// les gens ajoutent par habitude du fixe.
func Analyser(saisie string) (Numero, error) {
    var b strings.Builder
    for _, r := range saisie {
        switch {
        case r >= '0' && r <= '9':
            b.WriteRune(r)
        case r == '+' || r == ' ' || r == '-' || r == '.' || r == '(' || r == ')':
            // Separateurs d'ecriture. Pas des donnees.
        default:
            return Numero{}, fmt.Errorf("%w : %q dans %q", ErrFormat, r, saisie)
        }
    }
    chiffres := b.String()

    // Normalisation : on ramene tout au national a neuf chiffres.
    national := chiffres
    switch {
    case strings.HasPrefix(chiffres, indicatif) && len(chiffres) == 12:
        national = chiffres[3:]
    case strings.HasPrefix(chiffres, "0") && len(chiffres) == 10:
        national = chiffres[1:]
    }

    if len(national) != 9 {
        return Numero{}, fmt.Errorf("%w : %d chiffres utiles dans %q",
            ErrFormat, len(national), saisie)
    }
    if national[0] != '6' {
        return Numero{}, fmt.Errorf("%w : commence par %q", ErrPrefixe, national[0])
    }
    return Numero{msisdn: indicatif + national}, nil
}

func MustAnalyser(saisie string) Numero {
    n, err := Analyser(saisie)
    if err != nil {
        panic(err)
    }
    return n
}

func (n Numero) EstNul() bool { return n.msisdn == "" }

// National rend les neuf chiffres, pour l'affichage.
func (n Numero) National() string {
    if n.EstNul() {
        return ""
    }
    return n.msisdn[3:]
}

// String rend la forme canonique, et c'est la seule qui sort de ce paquet.
// Une seule forme ecrite, donc une seule cle de map, une seule colonne.
func (n Numero) String() string {
    if n.EstNul() {
        return "numero nul"
    }
    return n.msisdn
}
```

Trois décisions à défendre.

**Les trois formes acceptées ne sont pas un choix esthétique.** Ce sont les
trois qui arrivent vraiment : l'international depuis un carnet d'adresses, le
national depuis un formulaire, et le local avec le zéro que les gens ajoutent
par habitude du fixe. Une quatrième — la saisie avec des points — est gratuite
une fois la boucle écrite.

**Le format et le préfixe sont deux erreurs distinctes**, et c'est la leçon 1.5
appliquée à un constructeur :

| L'erreur | La conduite de l'appelant |
|---|---|
| `ErrFormat` | *« vérifiez le numéro »* — l'utilisateur corrige sa saisie |
| `ErrPrefixe` | *« ce n'est pas un numéro mobile »* — il n'y a rien à corriger, c'est un fixe |

Deux conduites, deux erreurs. Les fusionner produirait un message qui n'aide
personne, et le test le vérifie dans les deux sens :

```go
// TestLeFormatEtLePrefixeSontDeuxErreursDistinctes : la conduite de l'appelant
// n'est pas la meme, donc les erreurs ne sont pas les memes. Lecon 1.5.
func TestLeFormatEtLePrefixeSontDeuxErreursDistinctes(t *testing.T) {
    _, errFormat := numero.Analyser("69123456")
    _, errPrefixe := numero.Analyser("222123456")

    if errors.Is(errFormat, numero.ErrPrefixe) {
        t.Error("une erreur de format est rendue comme une erreur de prefixe")
    }
    if errors.Is(errPrefixe, numero.ErrFormat) {
        t.Error("une erreur de prefixe est rendue comme une erreur de format")
    }
}
```

**Une seule forme canonique sort du paquet.** Donc une seule clé de map, une
seule clé de cache, une seule colonne de base, un seul destinataire de SMS. Le
test le prouve avec cinq écritures :

```go
// TestTroisEcrituresUneSeuleValeur est la propriete demandee par la contrainte
// 1 de l'exercice.
func TestTroisEcrituresUneSeuleValeur(t *testing.T) {
    ecritures := []string{
        "+237 691 23 45 67",
        "237691234567",
        "0691234567",
        "691234567",
        "(237) 691-23-45-67",
    }

    premier := numero.MustAnalyser(ecritures[0])
    for _, e := range ecritures[1:] {
        n, err := numero.Analyser(e)
        if err != nil {
            t.Fatalf("Analyser(%q) : %v", e, err)
        }
        if n != premier {
            t.Fatalf("%q = %s, attendu %s", e, n, premier)
        }
    }

    // Cle de map, sans fonction de hachage.
    vus := map[numero.Numero]int{}
    for _, e := range ecritures {
        vus[numero.MustAnalyser(e)]++
    }
    if len(vus) != 1 || vus[premier] != len(ecritures) {
        t.Fatalf("map = %v, attendu une cle vue %d fois", vus, len(ecritures))
    }
    if premier.String() != "237691234567" {
        t.Fatalf("forme canonique = %q", premier.String())
    }
}
```

## 2. `Montant` — et le mécanisme qui interdit l'addition

```go
// Package montant definit une somme en francs CFA.
//
// VALEUR. Pas de centimes : le FCFA n'en a pas, et un type qui en prevoit
// invite a les utiliser, puis a les arrondir, puis a se demander ou sont
// passes les trois francs.
package montant

import (
    "errors"
    "fmt"
    "math"
    "strconv"
)

var (
    // ErrNegatif : un montant negatif n'existe pas. Un retrait n'est pas un
    // depot negatif, c'est une operation d'un autre nom.
    ErrNegatif = errors.New("montant : negatif")
    // ErrDepassement : la somme deborde int64. Improbable, et c'est la raison
    // pour laquelle personne ne le verifie — jusqu'au jour ou un test de
    // fuzzing ou un champ mal analyse produit 9 223 372 036 854 775 807.
    ErrDepassement = errors.New("montant : depassement de capacite")
    // ErrInsuffisant : la soustraction passerait sous zero. C'est une REPONSE
    // metier, pas une panne.
    ErrInsuffisant = errors.New("montant : insuffisant")
)

// Montant est une somme en FCFA, toujours positive ou nulle.
//
// Le type est distinct de int64 : c'est ce qui rend impossible
// solde + 1 ou solde + nombreDOperations. Ca coute un appel a FCFA() partout
// ou il faut vraiment un entier — et c'est le but : ces endroits deviennent
// visibles, et ils sont peu nombreux.
type Montant struct {
    fcfa int64
}

// Zero est le montant nul. La valeur zero du type EST un etat valide ici : un
// solde de zero a un sens, et c'est meme l'etat initial de tout portefeuille.
var Zero = Montant{}

func FCFA(n int64) (Montant, error) {
    if n < 0 {
        return Montant{}, fmt.Errorf("%w : %d", ErrNegatif, n)
    }
    return Montant{fcfa: n}, nil
}

func MustFCFA(n int64) Montant {
    m, err := FCFA(n)
    if err != nil {
        panic(err)
    }
    return m
}

// Valeur rend l'entier, et c'est le seul moyen de sortir du type.
func (m Montant) Valeur() int64 { return m.fcfa }

func (m Montant) EstZero() bool { return m.fcfa == 0 }

// Plus additionne. Rend une erreur plutot qu'un resultat faux.
func (m Montant) Plus(autre Montant) (Montant, error) {
    if m.fcfa > math.MaxInt64-autre.fcfa {
        return Montant{}, fmt.Errorf("%w : %d + %d", ErrDepassement, m.fcfa, autre.fcfa)
    }
    return Montant{fcfa: m.fcfa + autre.fcfa}, nil
}

// Moins soustrait. Passer sous zero est une reponse metier, pas un resultat
// negatif.
func (m Montant) Moins(autre Montant) (Montant, error) {
    if m.fcfa < autre.fcfa {
        return Montant{}, fmt.Errorf("%w : %d - %d", ErrInsuffisant, m.fcfa, autre.fcfa)
    }
    return Montant{fcfa: m.fcfa - autre.fcfa}, nil
}

// Pourmille rend une fraction du montant, arrondie vers le bas.
//
// Un entier en pour mille, pas un float64 : des frais de 1,5 % sont 15 pour
// mille, exactement, et 0.015 ne l'est pas.
func (m Montant) Pourmille(taux int64) (Montant, error) {
    if taux < 0 {
        return Montant{}, fmt.Errorf("%w : taux %d", ErrNegatif, taux)
    }
    if taux != 0 && m.fcfa > math.MaxInt64/taux {
        return Montant{}, fmt.Errorf("%w : %d x %d", ErrDepassement, m.fcfa, taux)
    }
    return Montant{fcfa: m.fcfa * taux / 1000}, nil
}

// Depasse compare.
func (m Montant) Depasse(plafond Montant) bool { return m.fcfa > plafond.fcfa }

func (m Montant) String() string { return strconv.FormatInt(m.fcfa, 10) + " FCFA" }
```

### Pas de centimes

Le FCFA n'en a pas. Un type qui en prévoit invite à les utiliser, puis à les
arrondir, puis à se demander où sont passés les trois francs. C'est une décision
de modélisation, pas une optimisation.

### Le mécanisme de la contrainte 2, et ce qu'il coûte

La question demandait : *quel mécanisme Go te donne ça, et que coûte-t-il ?*

Le mécanisme est le **type nommé à champ privé**. `Montant` n'est pas un alias
de `int64` : c'est une structure dont le seul champ est inaccessible. Donc
`m + 1` ne compile pas, et le message du compilateur est explicite :

```
invalid operation: m + 1 (mismatched types montant.Montant and untyped int)
```

Noter qu'un `type Montant int64` ne suffirait **pas** : il autoriserait
`m + 1`, parce qu'une constante non typée s'adapte. C'est la différence entre un
type nommé et un type encapsulé, et elle décide de tout ici.

Le coût, et il est réel :

| Ce qu'on paie | Où ça se voit |
|---|---|
| un appel à `Valeur()` partout où il faut vraiment un entier | la sérialisation, le SQL, les métriques |
| une erreur à traiter sur chaque addition | `Plus` et `Moins` rendent `(Montant, error)` |
| pas d'opérateurs | `a.Plus(b)` au lieu de `a + b`, moins agréable à lire |
| pas de `Montant` dans un `switch` numérique | il faut passer par `Valeur()` |

Le deuxième point est celui qu'on sous-estime, et c'est pourtant le bon. Une
addition de sommes d'argent **peut** échouer, par dépassement. `a + b` ne le dit
pas ; `a.Plus(b)` oblige à décider quoi faire. Le test mesure que ce n'est pas
théorique :

```go
// TestLeDepassementEstDetecte : le cas improbable que personne ne verifie.
func TestLeDepassementEstDetecte(t *testing.T) {
    presqueMax := montant.MustFCFA(math.MaxInt64 - 10)

    if _, err := presqueMax.Plus(montant.MustFCFA(11)); !errors.Is(err, montant.ErrDepassement) {
        t.Errorf("Plus : err = %v, attendu ErrDepassement", err)
    }
    if _, err := presqueMax.Pourmille(2); !errors.Is(err, montant.ErrDepassement) {
        t.Errorf("Pourmille : err = %v, attendu ErrDepassement", err)
    }
}
```

### Et l'invariant qui déménage

`Moins` refuse de passer sous zéro, et rend `ErrInsuffisant` — une **réponse
métier**, pas une panne. Conséquence que la question 3 attendait :

> L'invariant *« le solde n'est jamais négatif »* n'est pas tenu par une garde
> écrite dans le portefeuille. Il est tenu par le **type du solde**.

Un invariant délégué à un type est un invariant qui n'a **qu'un seul endroit à
relire**. C'est la réponse à la question 6 de l'exercice 1, et elle est
structurelle plutôt que disciplinaire.

### Pourmille plutôt qu'un flottant

```
func (m Montant) Pourmille(taux int64) (Montant, error)
```

Des frais de 1,5 % sont **15 pour mille**, exactement. `0.015` ne l'est pas, et
la différence se voit au troisième calcul. Le test fixe l'arrondi comme une
décision commerciale, pas comme un détail :

```go
// TestLesFraisSontExactsEnPourMille garde la decision de ne pas utiliser de
// float64.
//
// Les cas sont choisis pour que la difference se voie : 1,5 % de 1 234 567
// vaut 18 518,505, et l'arrondi est une decision commerciale.
func TestLesFraisSontExactsEnPourMille(t *testing.T) {
    cas := []struct {
        somme   int64
        taux    int64
        attendu int64
    }{
        {1_000_000, 15, 15_000},
        {1_234_567, 15, 18_518}, // arrondi vers le bas, en faveur du client
        {100, 15, 1},
        {66, 15, 0}, // 0,99 FCFA : les frais sont nuls, pas « presque un »
        {1_000_000, 0, 0},
    }

    for _, c := range cas {
        frais, err := montant.MustFCFA(c.somme).Pourmille(c.taux)
        if err != nil {
            t.Fatalf("Pourmille(%d, %d) : %v", c.somme, c.taux, err)
        }
        if frais.Valeur() != c.attendu {
            t.Errorf("%d x %d pour mille = %d, attendu %d",
                c.somme, c.taux, frais.Valeur(), c.attendu)
        }
    }
}
```

Le cas `{66, 15, 0}` est le plus instructif : 0,99 FCFA de frais devient **zéro**,
pas « presque un ». C'est une décision — l'arrondi va vers le client — et elle
est écrite dans un test plutôt que dans un commentaire.

## 3. `Portefeuille` — l'entité, et le ⚫ qui ne coûte rien

```go
type Niveau int

const (
    // NonVerifie : aucune piece fournie.
    NonVerifie Niveau = iota + 1
    // CNI : carte nationale d'identite enregistree.
    CNI
    // Complet : CNI et justificatif de domicile.
    Complet
)

// Plafond rend le plafond journalier de ce niveau.
//
// C'est LA reponse a la question 3 de l'exercice. Le plafond n'est PAS un champ
// du portefeuille : c'est une FONCTION du niveau. L'etat « plafond ne
// correspondant pas au niveau » n'est donc pas « interdit », il est
// INEXISTANT — il n'y a aucun endroit pour l'ecrire.
//
// C'est un ⚫, et c'est le genre de ⚫ qui ne coute rien : on n'a pas ajoute une
// garde, on a supprime un champ. Le meilleur garde-fou est celui qui retire une
// donnee plutot que celui qui en surveille une.
func (n Niveau) Plafond() montant.Montant {
    switch n {
    case NonVerifie:
        return montant.MustFCFA(50_000)
    case CNI:
        return montant.MustFCFA(500_000)
    case Complet:
        return montant.MustFCFA(5_000_000)
    }
    // Un niveau inconnu n'a pas de plafond permissif : il a un plafond nul.
    // Le defaut d'une enumeration doit toujours etre le choix le plus
    // restrictif, jamais le premier de la liste.
    return montant.Zero
}

func (n Niveau) Valide() bool { return n >= NonVerifie && n <= Complet }

func (n Niveau) String() string {
    switch n {
    case NonVerifie:
        return "non verifie"
    case CNI:
        return "cni"
    case Complet:
        return "complet"
    }
    return "niveau inconnu"
}

// Portefeuille est une ENTITE, identifiee par son numero.
type Portefeuille struct {
    // Interdit == : deux descriptions du meme portefeuille a deux instants
    // different par leur solde et sont le MEME portefeuille.
    _ [0]func()

    numero    numero.Numero
    solde     montant.Montant
    niveau    Niveau
    bloque    bool
    construit bool
}

// Ouvrir cree un portefeuille vide. Un portefeuille neuf n'est pas verifie, et
// son solde est nul : les deux valeurs zero sont ici les bons defauts.
func Ouvrir(n numero.Numero) (Portefeuille, error) {
    if n.EstNul() {
        return Portefeuille{}, ErrSansNumero
    }
    return Portefeuille{numero: n, solde: montant.Zero, niveau: NonVerifie, construit: true}, nil
}
```

### La contrainte 3, et sa réponse

> *Le plafond journalier **découle** du niveau de vérification, et il est
> impossible de les désaccorder.*

La réponse n'est pas une garde. C'est une **suppression** :

```
func (n Niveau) Plafond() montant.Montant
```

Le plafond n'est pas un champ du portefeuille. C'est une fonction du niveau. Il
n'existe donc **aucun endroit** où écrire un plafond qui ne correspond pas — pas
« c'est interdit », mais « ça n'existe pas ».

| Niveau | Mécanisme | Ce que ça vaut |
|---|---|---|
| 🟡 | un commentaire *« mettre à jour le plafond avec le KYC »* | rien, dès le deuxième développeur |
| 🟠 | un `SetNiveau` qui met les deux à jour | n'importe qui peut encore écrire le champ |
| 🔴 | champs privés, et un seul mutateur qui écrit les deux | il reste deux données à garder cohérentes |
| ⚫ | **le plafond n'est pas une donnée** | il n'y a plus rien à garder |

> Le meilleur garde-fou est celui qui **retire une donnée**, pas celui qui en
> surveille une. Chaque fois qu'un invariant lie deux champs, demande si l'un
> des deux ne serait pas une fonction de l'autre.

### Le défaut d'une énumération

```
    // Un niveau inconnu n'a pas de plafond permissif : il a un plafond nul.
    return montant.Zero
```

Un niveau mal analysé — une colonne de base à 0, un entier venu d'un JSON — ne
doit pas tomber sur le plafond le plus large.

> Le défaut d'une énumération est toujours le choix le plus **restrictif**,
> jamais le premier de la liste.

C'est exactement le `default: 500` de la leçon 1.5, appliqué à une valeur métier
au lieu d'un statut HTTP. Et c'est testé :

```go
// TestUnNiveauInconnuNAPasDePlafondPermissif garde le choix du defaut.
//
// Une enumeration mal analysee — une colonne de base a 0, un entier venu d'un
// JSON — ne doit pas tomber sur le plafond le plus large. Le defaut d'une
// enumeration est toujours le choix le plus restrictif.
func TestUnNiveauInconnuNAPasDePlafondPermissif(t *testing.T) {
    for _, n := range []portefeuille.Niveau{0, -1, 99} {
        if !n.Plafond().EstZero() {
            t.Errorf("Niveau(%d).Plafond() = %s, attendu zero", n, n.Plafond())
        }
        if n.Valide() {
            t.Errorf("Niveau(%d) se declare valide", n)
        }
    }

    if _, err := ouvert(t).Verifier(99); !errors.Is(err, portefeuille.ErrNiveauInconnu) {
        t.Errorf("Verifier(99) : err = %v, attendu ErrNiveauInconnu", err)
    }
}
```

### La contrainte 6 — la règle dans l'entité, la mesure en argument

```go
// PeutEmettre est la REGLE, et elle recoit le cumule du jour parce qu'elle ne
// le detient pas.
//
// GARANTI
//
//    Rend nil si et seulement si le portefeuille est construit, non bloque, et
//    si cumuleDuJour + m ne depasse pas le plafond du niveau.
//
// NON GARANTI
//
//    Que cumuleDuJour soit encore juste quand l'appelant agira. Lire puis agir
//    est un check-then-act, et seule une transaction le ferme. Cette methode
//    DECIDE ; elle ne PROTEGE pas.
//
//    Que le solde suffise : c'est Debiter qui le dit, et pour une raison — un
//    solde insuffisant et un plafond depasse appellent deux conduites
//    differentes chez l'appelant, donc deux reponses.
func (p Portefeuille) PeutEmettre(m montant.Montant, cumuleDuJour montant.Montant) error {
    if err := p.exister(); err != nil {
        return err
    }
    if p.bloque {
        return fmt.Errorf("%w : %s", ErrBloque, p.numero)
    }
    total, err := cumuleDuJour.Plus(m)
    if err != nil {
        return fmt.Errorf("portefeuille : cumule du jour : %w", err)
    }
    if total.Depasse(p.niveau.Plafond()) {
        return fmt.Errorf("%w : %s cumule %s + %s pour un plafond de %s",
            ErrPlafondDepasse, p.numero, cumuleDuJour, m, p.niveau.Plafond())
    }
    return nil
}
```

Et les deux clauses `NON GARANTI` que la question demandait d'écrire. La seconde
est celle qu'on oublie :

> Que le **solde** suffise : c'est `Debiter` qui le dit, et pour une raison — un
> solde insuffisant et un plafond dépassé appellent deux conduites différentes
> chez l'appelant, donc deux réponses.

| L'issue | Ce que l'abonné peut faire |
|---|---|
| plafond dépassé | attendre demain, ou se faire vérifier |
| solde insuffisant | recharger |

Deux conduites, deux erreurs — et le test exerce les deux **en les croisant**,
ce qui est le seul moyen de prouver qu'elles ne sont pas confondues :

```go
// TestPlafondEtSoldeSontDeuxReponsesDifferentes : deux conduites distinctes
// chez l'appelant, donc deux erreurs. Lecon 1.5.
//
// Un plafond depasse se resout en attendant demain ou en se faisant verifier.
// Un solde insuffisant se resout en rechargeant. Fusionner les deux, c'est
// renvoyer un message qui n'aide personne.
func TestPlafondEtSoldeSontDeuxReponsesDifferentes(t *testing.T) {
    riche, err := ouvert(t).Crediter(montant.MustFCFA(1_000_000))
    if err != nil {
        t.Fatalf("Crediter : %v", err)
    }
    // NonVerifie : plafond 50 000, mais un million de solde.
    cent := montant.MustFCFA(100_000)

    if err := riche.PeutEmettre(cent, montant.Zero); !errors.Is(err, portefeuille.ErrPlafondDepasse) {
        t.Fatalf("plafond : err = %v", err)
    }
    // Le solde, lui, suffit largement.
    if _, err := riche.Debiter(cent); err != nil {
        t.Fatalf("Debiter : %v", err)
    }

    pauvre, err := ouvert(t).Verifier(portefeuille.Complet)
    if err != nil {
        t.Fatalf("Verifier : %v", err)
    }
    // Plafond 5 000 000, solde zero.
    if err := pauvre.PeutEmettre(cent, montant.Zero); err != nil {
        t.Fatalf("le plafond ne devrait pas s'opposer : %v", err)
    }
    if _, err := pauvre.Debiter(cent); !errors.Is(err, montant.ErrInsuffisant) {
        t.Fatalf("solde : err = %v", err)
    }
}
```

## 4. La contrainte 5 — la valeur zéro, trois fois, trois réponses

| Type | Valide ? | Comment on le sait | Ce qu'on a fait |
|---|---|---|---|
| `Montant` | **oui** | un solde de zéro a un sens, c'est même l'état initial | on l'exporte sous le nom `Zero`, pour que personne n'écrive `Montant{}` |
| `Niveau` | **non** | `Niveau(0)` n'est aucun des trois niveaux | l'énumération commence à `iota + 1`, `Plafond()` rend zéro, `Valide()` rend faux |
| `Numero` | **non** | un numéro vide n'identifie rien | `EstNul()`, et `String()` rend `"numero nul"` |
| `Portefeuille` | **non** | et **rien ne le trahit** : un solde nul et un numéro nul sont des valeurs zéro légitimes de leurs types | il faut un champ `construit` dédié |

La dernière ligne est la moins élégante et la plus honnête. Elle mérite d'être
regardée en face :

```go
// TestLaValeurZeroDUnPortefeuilleNEstPasUnPortefeuille : la reponse est NON, et
// aucun champ ne le trahit — un solde nul et un numero nul sont des valeurs
// zero legitimes de leurs types. Il faut donc le champ construit.
func TestLaValeurZeroDUnPortefeuilleNEstPasUnPortefeuille(t *testing.T) {
    var vide portefeuille.Portefeuille
    mille := montant.MustFCFA(1000)

    if err := vide.PeutEmettre(mille, montant.Zero); !errors.Is(err, portefeuille.ErrInexistant) {
        t.Errorf("PeutEmettre : err = %v", err)
    }
    if _, err := vide.Crediter(mille); !errors.Is(err, portefeuille.ErrInexistant) {
        t.Errorf("Crediter : err = %v : un portefeuille inexistant a recu de l'argent", err)
    }
    if _, err := vide.Debiter(mille); !errors.Is(err, portefeuille.ErrInexistant) {
        t.Errorf("Debiter : err = %v", err)
    }
    if _, err := vide.Verifier(portefeuille.Complet); !errors.Is(err, portefeuille.ErrInexistant) {
        t.Errorf("Verifier : err = %v", err)
    }
    if _, err := vide.Bloquer(); !errors.Is(err, portefeuille.ErrInexistant) {
        t.Errorf("Bloquer : err = %v", err)
    }
}
```

Le test vérifie que les **cinq** opérations refusent la valeur zéro. Le cas de
`Crediter` est celui qui fait peur : sans le champ `construit`, un portefeuille
inexistant aurait reçu de l'argent, et cet argent n'aurait appartenu à personne.

> Quand aucun champ ne trahit la valeur zéro, il faut un drapeau explicite.
> C'est laid, c'est indispensable, et ça vaut mieux qu'un type dont la valeur
> zéro se comporte comme un objet valide.

```go
func compiler(t *testing.T, corps string) (string, error) {
    t.Helper()

    racine, err := filepath.Abs("..")
    if err != nil {
        t.Fatalf("racine : %v", err)
    }
    dossier, err := os.MkdirTemp(racine, "essai")
    if err != nil {
        t.Fatalf("dossier : %v", err)
    }
    t.Cleanup(func() { _ = os.RemoveAll(dossier) })

    source := filepath.Join(dossier, "main.go")
    contenu := strings.Replace(modele, "%s", strings.TrimRight(corps, "\n"), 1)
    if err := os.WriteFile(source, []byte(contenu), 0o600); err != nil {
        t.Fatalf("ecriture : %v", err)
    }

    cmd := exec.Command("go", "build", "-o", filepath.Join(dossier, "bin"), source)
    cmd.Dir = dossier
    sortie, err := cmd.CombinedOutput()
    return string(sortie), err
}

func premiereLigneUtile(sortie string) string {
    for _, l := range strings.Split(sortie, "\n") {
        if l = strings.TrimSpace(l); l != "" && !strings.HasPrefix(l, "#") {
            return l
        }
    }
    return sortie
}
```

Le troisième cas vérifiait qu'on ne peut pas additionner un `Montant` et un

> n'importe quelle erreur le satisfait, et la première faute de frappe le rend

D'où le champ `attendu` dans le tableau de cas : chaque cas porte un fragment du
message de compilation qu'il exige.

Puis j'ai appliqué la modification n° 7 de la campagne : retirer le champ
`[0]func()` de `Portefeuille`. Résultat :

```

```

Le ⚫ venait de disparaître, et le test disait *« tout va bien »*.

Le mécanisme est exact et il faut le comprendre, parce qu'il touche **tous** les
tests de décision du niveau 1. Le cache de tests de Go invalide le résultat d'un
paquet quand un paquet **dont il dépend** change. Ce test valide en lançant
`go build` dans un sous-processus : il ne dépend de rien au sens du compilateur.
Go a donc parfaitement le droit de rendre une réponse périmée, et il le fait.

```
$ go test -count=1 ./garde/     FAIL  exemple/mobile/garde
```

Le remède par `-count=1` est fragile : il vit dans la commande, pas dans le code,
et le premier `go test ./...` le contourne.

### Version 3 — le remède, et il est dans les imports

> **Un test de décision doit dépendre, au sens du compilateur, de ce qu'il
> surveille.** Sinon il surveille une version qui n'existe plus.

Le fichier importe donc `montant`, `numero` et `portefeuille`, et le témoin les
**utilise vraiment** — en processus, pas via un sous-processus. Deux bénéfices
d'un seul geste : le cache s'invalide, et le témoin ne tombe plus en même temps
que ce qu'il surveille.

Vérification : avec le champ retiré, et **sans** `-count=1` :

```

    garde_test.go:93: le programme a compile : deux etats du MEME portefeuille seraient declares differents
FAIL  exemple/mobile/garde
```

### Les trois modes de panne de cette famille de tests

Pour mémoire, parce qu'aucun des trois n'est évident :

| Mode de panne | Le remède |
|---|---|
| passer parce que **tout** est cassé | un **témoin** qui réussit |
| passer **pour la mauvaise raison** | un **fragment de message** attendu |
| passer parce qu'il est **en cache** | **importer** ce qu'on surveille |

Et la portée : les tests de décision du niveau 1 ont tous le troisième défaut.
Celui qui lit la source avec `go/ast`, celui qui interroge `go list`, celui qui
compile un programme — les trois valident par un sous-processus, donc les trois
sont hors du graphe que Go connaît.

| # | La modification | Qui crie |
|---|---|---|
| 1 | un niveau inconnu rend le plafond le plus large | `TestUnNiveauInconnuNAPasDePlafondPermissif` |
| 2 | la frontière du plafond devient `>=` au lieu de `>` | `TestLaRegleDePlafondExerceLaFrontiere` |
| 3 | `Crediter` ne vérifie plus le blocage | `TestUnPortefeuilleBloqueNEmetNiNeRecoit` |
| 4 | `Montant.Moins` rend un négatif au lieu d'une erreur | **3 tests**, dans deux paquets |

> aussi **les tests qui prétendent le garder** — et c'est souvent là qu'elle
> trouve le plus.

## 7. La contrainte 7 — compter les lignes, et nommer ce qu'on a acheté

| | |
|---|---|
| `numero` | 95 lignes |
| `montant` | 96 lignes |
| `portefeuille` | 220 lignes |
| **total modèle** | **411 lignes** |
| tests | 559 lignes |

Et les bugs que ce modèle rend **impossibles** — la question demandait trois, en
voici six, avec le mécanisme de chacun :

| Le bug | Ce qui le rend impossible |
|---|---|
| deux comptes pour un abonné parce que le numéro est écrit différemment | une seule forme canonique sort de `numero` |

| un montant additionné à un index, un compteur, un identifiant | le type encapsulé |

| deux états du même portefeuille déclarés différents | `==` ne compile pas |

Et les trois qu'il ne rend **pas** impossibles, parce qu'il faut aussi savoir le

- **le dépassement de plafond par concurrence.** `PeutEmettre` décide, il ne

- **un plafond réglementaire mal paramétré.** Si la conformité demande 600 000 au
  lieu de 500 000, on change une constante — et rien ne vérifie qu'elle est la
  bonne. C'est une donnée de référence, pas un invariant.
- **un numéro recyclé par l'opérateur.** Le modèle croira que c'est le même
  abonné. C'est la question 2 de l'exercice 4, et le modèle n'y répond pas.

## Ce que ça ne règle pas

**Le plafond ne peut pas être personnalisé.** C'est la conséquence directe du ⚫ :
le plafond étant une fonction du niveau, on ne peut pas accorder 2 000 000 à un
commerçant particulier sans changer le type. Si le métier le demande — et il le
demandera —, deux options :

| Option | L'invariant devient | Ce qu'on perd |
|---|---|---|
| un champ `plafondAccorde` optionnel | « le plafond accordé ne dépasse pas le maximum du niveau » | le ⚫ devient un 🔴 : il y a de nouveau deux données |
| un `Niveau` par profil commercial | rien ne change | la liste des niveaux grossit, et elle devient une donnée de référence |

La seconde garde le ⚫ et c'est celle qu'il faut défendre en réunion. La première
est celle qui sera demandée. Savoir laquelle on choisit **avant** la réunion est
tout l'intérêt d'avoir écrit le modèle.

**`Niveau.Plafond()` contient des montants en dur.** Ils devraient venir d'une
table de paramétrage, parce que le régulateur les change. Le ⚫ survit à ce
changement — le plafond reste une fonction du niveau, elle consulte juste une
table — mais la fonction devient `Plafond(bareme Bareme)`, et le barème descend
en argument. Encore la même mécanique.

**Rien ne vérifie que `montant.Pourmille` est appelé avec le bon taux.** Les
frais sont un paramètre, et un paramètre faux est un paramètre faux. C'est hors
du modèle, et c'est une donnée de référence à surveiller.

**L'identité reste le numéro de téléphone.** Ce n'est pas un oubli, c'est un
choix — et c'est le sujet de l'exercice 4, où il se révèle discutable.

## Ce qu'il faut retenir

1. **Une seule forme canonique sort d'un objet-valeur.** Donc une seule clé de
   map, de cache, de colonne, de destinataire.
2. **Deux conduites de l'appelant, deux erreurs** — format et préfixe, plafond
   et solde. Et on le vérifie en les croisant.
3. **Un type encapsulé, pas un type nommé.** `type Montant int64` autorise
   `m + 1` ; une structure à champ privé ne l'autorise pas.
4. **Une addition de montants peut échouer.** `a.Plus(b)` oblige à décider,
   `a + b` ne le dit pas.
5. **Un invariant délégué à un type n'a qu'un seul endroit à relire.** Le solde
   n'est jamais négatif parce que `Moins` le refuse.
6. **Le meilleur garde-fou retire une donnée** au lieu d'en surveiller une. Si
   un invariant lie deux champs, l'un est peut-être une fonction de l'autre.
7. **Le défaut d'une énumération est le choix le plus restrictif**, jamais le
   premier de la liste.
8. **Un plafond est atteignable.** Le premier cas du tableau de frontière dit ce
   que le reste n'aurait pas dit.
9. **Quand aucun champ ne trahit la valeur zéro, il faut un drapeau explicite.**
10. **Un test qui attend un échec doit vérifier la raison de l'échec.**
11. **Un test de décision doit dépendre, au sens du compilateur, de ce qu'il
    surveille** — sinon le cache le rend périmé, et il devient vert au pire
    moment.
12. **Une campagne de modifications mesure aussi les tests.** C'est souvent là
    qu'elle trouve le plus.
