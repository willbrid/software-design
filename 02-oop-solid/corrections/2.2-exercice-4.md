# Correction 2.2 — Exercice 4 : la plateforme d'intégration

> Rappel de l'énoncé : des connecteurs qui arrivent par deux ou trois par
> trimestre — parfois écrits par le partenaire lui-même — et trois appelants
> aux besoins différents. Il fallait déclarer les interfaces, poser le
> vocabulaire partagé, mesurer, loger la sélection, et proposer une garantie.

L'axe est l'inverse de celui de l'exercice 2 : **variantes ouvertes,
opérations fermées**. C'est donc le cas de l'interface, et pas celui du type
somme. Tout ce qui suit est mesuré sur un module de sept paquets de test, tous
verts sous `go vet` et `go test -race -count=1`.

## 1. Les interfaces (question 1)

### Trois appelants, trois interfaces

| Appelant | Interface déclarée | Méthodes | Pourquoi exactement celles-là |
|---|---|---|---|
| `ordonnanceur` | `Collecteur` | **2** | il nomme une source dans ses journaux, et il lance une collecte |
| `supervision` | `Surveille` | **2** | il nomme une source dans son tableau, et il lit son état |
| `catalogue` | `Documentee` | **3** | il nomme une source, liste ses champs, et cite sa fréquence contractuelle |

```
$ ...                              Collecteur : 2 methodes
$ ...                              Surveille  : 2 methodes
$ ...                              Documentee : 3 methodes
$ connecteurs (chaque connecteur)             : 5 methodes
```

Cinq méthodes implémentées, et **aucun appelant n'en voit plus de trois**. Une
seule — `Source()` — est partagée par les trois interfaces, et ce n'est pas un
hasard : c'est le seul besoin que les trois ont en commun.

```go
// Collecteur est l'interface DE CE PAQUET. Deux methodes.
//
// Sa signature ne nomme que des types du paquet collecte, c'est-a-dire du
// vocabulaire partage : c'est a cette condition, et a cette condition
// seulement, qu'un connecteur n'a pas a importer son appelant.
type Collecteur interface {
    Source() collecte.Source
    Collecter(p collecte.Plage) ([]collecte.Enregistrement, error)
}

// Journal enregistre ce que fait l'ordonnanceur.
//
// Selection est appelee au moment du CHOIX, avant de savoir si ca marche. Sans
// cette ligne, une collecte incomplete n'est pas attribuable : celui qui ecrit
// la ligne de resultat ne sait pas quel connecteur a ete retenu. C'est la
// reponse a la question 7 de l'enonce.
type Journal interface {
    Selection(execution string, source collecte.Source, plage collecte.Plage)
    Resultat(execution string, source collecte.Source, enregistrements int, err error)
}
```

### Pourquoi pas une interface unique

Si on avait écrit une seule interface à cinq méthodes, le compte des doubles
de test aurait été :

| | Interface unique à 5 méthodes | Trois interfaces |
|---|---|---|
| double d'`ordonnanceur` | 5 méthodes, 3 jamais lues | **2**, 0 jamais lue |
| double de `supervision` | 5 méthodes, 3 jamais lues | **2**, 0 jamais lue |
| double de `catalogue` | 5 méthodes, 2 jamais lues | **3**, 0 jamais lue |
| **total** | **15 méthodes, 8 jamais lues** | **7 méthodes, 0 jamais lue** |

> Huit méthodes inutiles dans des doubles, ce ne sont pas huit lignes de trop :
> ce sont huit endroits où une future méthode ira se cacher, et huit valeurs
> que personne ne vérifie.

## 2. Le vocabulaire partagé (question 2)

La prédiction, avant d'écrire une ligne : si les signatures nommaient
`ordonnanceur.Plage` ou `supervision.Sante`, **chaque connecteur devrait
importer ses appelants**. L'interface serait bien déclarée chez l'appelant, et
la flèche serait quand même inversée — seulement déguisée.

Les types partagés vont donc dans leur propre paquet, en bas du graphe :

```go
// Package collecte porte le vocabulaire partage entre la plateforme et ses
// connecteurs.
//
// Ce paquet existe a cause d'une mesure. Les trois interfaces sont declarees
// chez leurs appelants, ce qui est la bonne regle — mais si leurs signatures
// nommaient ordonnanceur.Plage ou supervision.Sante, chaque connecteur
// devrait importer ses appelants, et la fleche serait seulement deguisee.
//
// Regle : declarer une interface chez l'appelant ne decouple que si sa
// signature ne nomme que des types PARTAGES. Le decouplage par interface
// deplace la dependance vers le vocabulaire ; si le vocabulaire n'a pas de
// paquet, elle retombe sur l'appelant.
package collecte
```

Et la mesure, après :

```
$ for p in collecte connecteurs ordonnanceur supervision catalogue registre; do
>   printf '%-14s : ' $p; go list -f '{{join .Imports " "}}' ./$p
> done
collecte       : errors fmt slices strings time
connecteurs    : errors exemple/integration/collecte fmt time
ordonnanceur   : errors exemple/integration/collecte fmt
supervision    : errors exemple/integration/collecte time
catalogue      : errors exemple/integration/collecte fmt slices
registre       : errors exemple/integration/catalogue exemple/integration/collecte exemple/integration/connecteurs exemple/integration/ordonnanceur exemple/integration/supervision fmt
```

`connecteurs` n'importe **aucun** des trois appelants. `collecte` n'importe
rien du module. Et `registre` importe tout — c'est la seule ligne qui a le
droit d'être longue, et la section 5 dit pourquoi.

## 3. Les connecteurs (question 3)

```go
// Package connecteurs contient les implementations concretes.
//
// Il n'importe AUCUN des trois paquets appelants — ni ordonnanceur, ni
// supervision, ni catalogue. C'est la mesure a retenir, et elle se verifie
// par go list.
//
// Chaque connecteur porte CINQ methodes. L'ordonnanceur en voit deux, la
// supervision deux, le catalogue trois, et une seule — Source — est partagee
// par les trois. Aucun appelant ne voit les cinq.
package connecteurs

import (
    "errors"
    "fmt"
    "time"

    "exemple/integration/collecte"
)
```

Les quatre connecteurs partagent un champ `base` dont les méthodes sont
promues. **Incorporation, pas héritage** : `base` n'est pas une classe mère,
c'est un champ. La différence est le sujet de la leçon 2.3 ; ici elle sert
seulement à ne pas recopier cinq fois le même code.

Deux décisions de conception méritent un mot, et la première est la plus
importante du module.

**La provenance est posée par le connecteur, à un seul endroit.**

```go
func (b base) collecter(p collecte.Plage) ([]collecte.Enregistrement, error) {
    maintenant := time.Time{}
    if b.horloge != nil {
        maintenant = b.horloge.Maintenant()
    }
    lignes, err := b.transport.Lire(p)
    if err != nil {
        *b.dernierEtat = collecte.Sante{
            Etat: collecte.Indisponible, Detail: err.Error(), Mesuree: maintenant,
        }
        return nil, fmt.Errorf("%w : %s : %w", ErrTransport, b.source, err)
    }
    lot := make([]collecte.Enregistrement, 0, len(lignes))
    for i, l := range lignes {
        cle, ok := l["cle"]
        if !ok {
            return nil, fmt.Errorf("%w : %s rang %d, champ « cle » absent",
                ErrLigneIllisible, b.source, i)
        }
        // La provenance est posee ICI, par le connecteur, et nulle part
        // ailleurs. Aucun appelant ne peut en fabriquer une autre.
        e, err := collecte.Nouveau(b.source, cle, l)
        if err != nil {
            return nil, fmt.Errorf("%s rang %d : %w", b.source, i, err)
        }
        lot = append(lot, e)
    }
    etat := collecte.Sain
    detail := fmt.Sprintf("%d enregistrements sur %s", len(lot), p)
    if len(lot) == 0 {
        // Zero enregistrement n'est pas une panne, mais ce n'est pas sain
        // non plus : une source contractuellement quotidienne qui rend zero
        // ligne est une source a regarder.
        etat = collecte.Degrade
        detail = "aucun enregistrement sur " + p.String()
    }
    *b.dernierEtat = collecte.Sante{Etat: etat, Detail: detail, Mesuree: maintenant}
    return lot, nil
}
```

**La sonde ne refait pas la collecte.** `Sante()` lit le dernier état connu et
ne déclenche rien. Un test le garde en comptant les appels au transport :

> Une sonde qui refait une collecte pour savoir si la collecte marche est une
> sonde qui double la charge du partenaire. Et quand le partenaire limite le
> débit, c'est la sonde qui fait tomber la collecte.

## 4. La garantie, et le ⚫ (question 8)

L'énoncé demandait une propriété qui rende le problème **visible** — pas
détectable, visible. La voilà :

```go
// Enregistrement est une donnee collectee chez un partenaire.
//
// Le champ source est le ⚫ de ce module, et c'est la reponse a la question 8
// de l'enonce. Il est PRIVE, il n'a pas de setter, et le seul constructeur
// l'exige. Consequence : il n'existe aucun chemin dans le programme qui
// produise un enregistrement sans provenance.
//
// L'etat « une donnee dans l'entrepot dont on ne sait pas quel connecteur l'a
// produite » n'est donc pas representable. Ce n'est pas une donnee qu'on
// surveille : c'est une donnee qui ne peut pas manquer.
type Enregistrement struct {
    source  Source
    cle     string
    valeurs map[string]string
}

// Nouveau construit un enregistrement. La provenance et la cle sont
// obligatoires.
func Nouveau(source Source, cle string, valeurs map[string]string) (Enregistrement, error) {
    if strings.TrimSpace(string(source)) == "" {
        return Enregistrement{}, ErrSourceVide
    }
    if strings.TrimSpace(cle) == "" {
        return Enregistrement{}, fmt.Errorf("%w : source %s", ErrCleVide, source)
    }
    // La carte est copiee : la rendre telle quelle donnerait a l'appelant le
    // droit de la modifier apres construction.
    cp := make(map[string]string, len(valeurs))
    for k, v := range valeurs {
        cp[k] = v
    }
    return Enregistrement{source: source, cle: cle, valeurs: cp}, nil
}
```

> Le champ `source` est privé, il n'a pas de setter, et le seul constructeur
> l'exige. **Il n'existe aucun chemin dans le programme qui produise un
> enregistrement sans provenance.** Ce n'est pas une donnée qu'on surveille :
> c'est une donnée qui ne peut pas manquer.

Quatre programmes qui ne compilent pas le gardent, et chacun porte le fragment
de message attendu :

```
./main.go:12:30: cannot refer to unexported field source in struct literal of type collecte.Enregistrement
./main.go:13:4:  e.source undefined (type collecte.Enregistrement has no field or
                 method source, but does have method Source)
./main.go:12:21: cannot refer to unexported field debut in struct literal of type collecte.Plage
./main.go:13:26: cannot use nom (variable of type string) as collecte.Source value
```

Le deuxième message est le plus agréable à lire : le compilateur dit non, et
il indique l'accesseur au passage.

### Ce que le ⚫ ne couvre pas, et comment on le complète

Trois trous, et il faut les nommer plutôt que de prétendre qu'une propriété
couvre tout.

**La valeur zéro du type.** `var e collecte.Enregistrement` compile et n'a pas
de provenance. Le ⚫ ferme le chemin du **constructeur**, pas celui de la
déclaration.

**Une provenance fausse.** Le type exige qu'une provenance *existe* ; il ne
peut pas exiger qu'elle soit celle du connecteur qui a produit
l'enregistrement.

Les deux se ferment au même endroit, et c'est l'ordonnanceur :

```go
// Collecter lance une collecte sur une source.
//
// Elle verifie la provenance de chaque enregistrement rendu. C'est la seule
// garantie que le type Enregistrement ne peut pas porter seul : il exige
// qu'une provenance existe, il ne peut pas exiger qu'elle soit celle du
// connecteur qui l'a produite.
func (o *Ordonnanceur) Collecter(execution string, source collecte.Source, p collecte.Plage) ([]collecte.Enregistrement, error) {
    c, ok := o.connecteurs[source]
    if !ok {
        err := fmt.Errorf("%w : %s", ErrAucunConnecteur, source)
        o.journal.Resultat(execution, source, 0, err)
        return nil, err
    }
    // Le choix est journalise AVANT l'appel : si la collecte part en timeout
    // de dix minutes puis que le processus est tue, la ligne existe deja.
    o.journal.Selection(execution, source, p)
    lot, err := c.Collecter(p)
    if err != nil {
        err = fmt.Errorf("%w : %s : %w", ErrCollecteEnEchec, source, err)
        o.journal.Resultat(execution, source, 0, err)
        return nil, err
    }
    for i, e := range lot {
        if e.Source() != source {
            err := fmt.Errorf("%w : %s a rendu un enregistrement de %s (rang %d)",
                ErrProvenanceFausse, source, e.Source(), i)
            o.journal.Resultat(execution, source, 0, err)
            return nil, err
        }
    }
    o.journal.Resultat(execution, source, len(lot), nil)
    return lot, nil
}
```

Le contrôle refuse **le lot entier** et non la ligne fautive. C'est un choix,
et il se défend : un connecteur qui se trompe de provenance sur une ligne
n'est pas un connecteur dont on garde les autres lignes.

**L'incomplétude.** Le type garantit qu'on sait *qui* a produit un
enregistrement. Il ne garantit pas que l'enregistrement est complet. Ça, c'est
une **mesure**, pas une propriété — et c'est le quatrième tiret de la
question 8 :

| | La mesure | Le seuil | Son plancher de bruit |
|---|---|---|---|
| champs manquants par source et par champ | `catalogue.ChampsManquants` | **tout champ manquant sur plus de 1 % d'un lot** | oui, et il est connu : certains champs sont contractuellement facultatifs |

Le plancher de bruit est la question que la leçon 2.2 oblige à poser, et la
réponse honnête est : **oui, il y en a un**, et on le traite comme l'incident
de la monétique — en séparant ce qui est une réponse normale de ce qui est une
anomalie. Concrètement : la fiche de catalogue doit distinguer les champs
**obligatoires** des champs **facultatifs**, et la mesure ne porte que sur les
premiers. Je ne l'ai pas implémenté, et il faut le dire : la fiche actuelle a
une seule liste de champs, donc la mesure a un plancher de bruit non nul et
le seuil de 1 % est un compromis, pas une vérité.

## 5. Le registre, et la quatrième interface (question 4)

**Oui, il lui faut une quatrième interface.** Et c'est légitime pour une
raison précise.

```go
// Connecteur est la QUATRIEME interface, et elle est la somme des trois.
//
// Noter comment elle est ecrite : par incorporation des trois autres, et non
// par recopie de leurs cinq methodes. Le jour ou l'ordonnanceur ajoute une
// methode a la sienne, celle-ci suit sans qu'on y touche — et les
// implementations qui ne suivent pas cassent la compilation ici.
type Connecteur interface {
    ordonnanceur.Collecteur
    supervision.Surveille
    catalogue.Documentee
}

// Config est la configuration : la liste des sources a activer.
type Config struct {
    Actives []collecte.Source
}
```

Noter comment elle est écrite : **par incorporation des trois autres**, pas
par recopie de leurs cinq méthodes. Le jour où l'ordonnanceur ajoute une
méthode à la sienne, celle-ci suit sans qu'on y touche.

```go
// Monte construit les trois vues a partir de la configuration et des
// connecteurs disponibles.
//
// Elle rend les TROIS, et chacune ne voit que ce qui la concerne. C'est ici,
// et seulement ici, qu'un connecteur est vu comme les trois choses a la fois.
func Monte(c Config, journal ordonnanceur.Journal, disponibles ...Connecteur) (
    *ordonnanceur.Ordonnanceur, *supervision.Tableau, []catalogue.Fiche, error) {

    parSource := map[collecte.Source]Connecteur{}
    for _, d := range disponibles {
        if _, deja := parSource[d.Source()]; deja {
            return nil, nil, nil, fmt.Errorf("%w : %s", ErrDoublon, d.Source())
        }
        parSource[d.Source()] = d
    }
    if len(c.Actives) == 0 {
        return nil, nil, nil, ErrAucuneSourceActive
    }

    var collecteurs []ordonnanceur.Collecteur
    var surveilles []supervision.Surveille
    var documentees []catalogue.Documentee
    for _, s := range c.Actives {
        d, ok := parSource[s]
        if !ok {
            return nil, nil, nil, fmt.Errorf("%w : %s", ErrSourceInconnue, s)
        }
        collecteurs = append(collecteurs, d)
        surveilles = append(surveilles, d)
        documentees = append(documentees, d)
    }

    o, err := ordonnanceur.Nouveau(journal, collecteurs...)
    if err != nil {
        return nil, nil, nil, err
    }
    fiches, err := catalogue.Construire(documentees...)
    if err != nil {
        return nil, nil, nil, err
    }
    return o, supervision.Nouveau(surveilles...), fiches, nil
}
```

> Le registre est la **racine de composition** : l'endroit où les choix de
> branchement sont faits. C'est le seul endroit du programme qui a le droit de
> tout connaître. Un paquet qui connaît tout et qui n'est pas la racine de
> composition est un paquet mal placé.

Et `Monte` rend les trois vues séparément : chaque appelant ne reçoit que ce
qui le concerne, et le fait qu'un connecteur soit les trois choses à la fois
ne sort jamais de ce fichier.

## 6. Le connecteur du partenaire (question 6)

Un partenaire écrit son connecteur dans son propre dépôt. Qu'est-ce qu'il doit
importer ? La réponse est dans le fichier, et elle est courte :

```go
// ConnecteurDuPartenaire est ecrit comme le serait celui d'un partenaire,
// dans son propre module.
//
// C'est la reponse a la question 6 de l'enonce. Il n'importe QUE collecte —
// le vocabulaire partage. Il ne connait ni ordonnanceur, ni supervision, ni
// catalogue, ni registre, et il ignore jusqu'au nom des interfaces qu'il
// satisfait.
type ConnecteurDuPartenaire struct {
    sante collecte.Sante
}

func (ConnecteurDuPartenaire) Source() collecte.Source { return "PARTENAIRE-X" }

func (c *ConnecteurDuPartenaire) Collecter(p collecte.Plage) ([]collecte.Enregistrement, error) {
    lignes, err := transportDuPartenaire{}.Lire(p)
    if err != nil {
        return nil, err
    }
    lot := make([]collecte.Enregistrement, 0, len(lignes))
    for _, l := range lignes {
        e, err := collecte.Nouveau(c.Source(), l["cle"], l)
        if err != nil {
            return nil, err
        }
        lot = append(lot, e)
    }
    c.sante = collecte.Sante{Etat: collecte.Sain, Mesuree: time.Now()}
    return lot, nil
}

func (c *ConnecteurDuPartenaire) Sante() collecte.Sante { return c.sante }

func (ConnecteurDuPartenaire) ChampsExposes() []string { return []string{"cle", "montant"} }

func (ConnecteurDuPartenaire) FrequenceContractuelle() string { return "quotidienne" }

// Les trois assertions de conformite. C'est la reponse a la seconde moitie de
// la question 6 : comment s'assurer que le partenaire ne casse pas la
// compilation quand on ajoute une methode a une interface. Reponse : on ne
// peut pas s'en assurer pour SON depot, mais on peut s'en assurer pour le
// notre — ces trois lignes cassent ICI, chez nous, et avant la publication.
var (
    _ ordonnanceur.Collecteur = (*ConnecteurDuPartenaire)(nil)
    _ supervision.Surveille   = (*ConnecteurDuPartenaire)(nil)
    _ catalogue.Documentee    = (*ConnecteurDuPartenaire)(nil)
)
```

**Il n'importe que `collecte`.** Il ne connaît ni `ordonnanceur`, ni
`supervision`, ni `catalogue`, ni `registre`, et il ignore jusqu'au nom des
interfaces qu'il satisfait. C'est le typage structurel de Go, et c'est ce qui
rend ce découpage possible.

### Et la seconde moitié de la question : comment ne pas le casser

La réponse honnête commence par ce qu'on ne peut pas faire : **on ne peut rien
garantir pour le dépôt du partenaire.** Ajouter une méthode à
`ordonnanceur.Collecteur` cassera son code, et aucune astuche ne l'évitera —
c'est le prix de l'axe qu'on a choisi, et la leçon 2.2 le dit : *ajouter une
opération coûte N implémentations*.

Ce qu'on peut faire, c'est le savoir **avant lui**. Et c'est là que la mesure
a donné un résultat que je n'attendais pas.

## 7. Les assertions de conformité, et où elles doivent vivre

J'avais mis les douze assertions dans `connecteurs/connecteurs_test.go`. Puis
j'ai ajouté une méthode à `ordonnanceur.Collecteur` et compté :

```
  erreurs de compilation du module  : 0
  erreurs dans les tests            : 4
```

**Zéro erreur au `go build`.** Un pipeline qui compile un binaire sans lancer
les tests aurait livré. Et il y a une tension réelle derrière ce chiffre :

| Où mettre l'assertion | Ce qu'on gagne | Ce qu'on perd |
|---|---|---|
| `connecteurs/connecteurs.go` | `go build` la voit | **`connecteurs` importe ses trois appelants** — le couplage qu'on vient de retirer |
| `connecteurs/connecteurs_test.go` | le découplage est préservé | `go build` ne voit rien |
| **`registre/registre.go`** | `go build` la voit | **rien** — ce paquet importe déjà les deux côtés |

```go
// Les assertions de conformite des quatre connecteurs maison.
//
// Elles sont ICI, et pas dans connecteurs/, pour une raison mesuree.
//
// Les mettre dans connecteurs/connecteurs.go obligerait ce paquet a importer
// ses trois appelants — exactement le couplage qu'on vient de retirer, et
// que go list permet de verifier.
//
// Les mettre dans connecteurs/connecteurs_test.go preserve le decouplage,
// mais la garantie devient plus faible qu'elle n'y parait. Mesure, en
// ajoutant une methode a ordonnanceur.Collecteur :
//
//    assertions dans _test.go  -> go build ./...  0 erreur, go vet ./...  4
//    assertions dans registre/ -> go build ./...  4 erreurs
//
// Un pipeline qui compile un binaire sans lancer les tests livrerait le
// premier cas. Le registre, lui, est deja le seul paquet a importer les trois
// appelants ET les connecteurs : c'est donc le seul endroit ou l'assertion ne
// coute aucun couplage nouveau.
//
//    Les assertions de conformite appartiennent a la racine de composition.
//    C'est le seul endroit du programme qui connait les deux cotes, et le
//    seul ou « go build » peut faire son travail.
var (
    _ Connecteur = connecteurs.SFTPFichierPlat{}
    _ Connecteur = connecteurs.APIRest{}
    _ Connecteur = connecteurs.BaseRepliquee{}
    _ Connecteur = connecteurs.FluxKafka{}
)
```

Après déplacement :

```
$ go build ./...
registre/registre.go:124:17: connecteurs.SFTPFichierPlat does not implement
    Connecteur (missing method Annuler)
... 4 erreurs
```

> **Les assertions de conformité appartiennent à la racine de composition.**
> C'est le seul endroit du programme qui connaît les deux côtés, et donc le
> seul où elles ne coûtent aucun couplage nouveau — et où `go build` peut
> faire son travail.

## 8. La sélection journalisée (question 7)

L'énoncé posait la question au futur : *six mois plus tard, une collecte sur
deux rend des données incomplètes et personne ne sait laquelle. Qu'est-ce que
tu as mis dans le code dès le premier jour ?*

Trois choses, et elles sont indépendantes.

**La provenance dans le type.** C'est le ⚫ de la section 4 : la phrase
« personne ne sait laquelle » est **non représentable** pour les données déjà
chargées, parce qu'aucun enregistrement ne peut exister sans provenance.

**Le journal au point de sélection, avant l'appel.** Pour les collectes qui
n'ont rien chargé, la provenance ne sert à rien — il n'y a pas
d'enregistrement. Il faut donc une ligne écrite **avant** que la collecte
commence, parce qu'une collecte qui part en timeout de dix minutes puis un
processus tué ne laissent rien derrière eux.

**La santé datée.** Un état `SAIN` mesuré il y a trois jours n'est pas une
information, c'est un souvenir. Deux mesures indépendantes, et il faut les
deux :

```go
// Package supervision surveille les sources.
//
// Son interface a DEUX methodes, et ce ne sont pas les deux de
// l'ordonnanceur. Meme implementation, deux vues differentes, chacune a la
// taille du besoin de son appelant.
package supervision
```

Et deux décisions d'énumération qui viennent de la leçon 2.1 :

> `Inconnu` est la **valeur zéro** de `Etat`, et `Degradees()` la compte comme
> une dégradation. Un tableau de bord qui affiche vert par défaut est un
> tableau de bord qui mentira au démarrage. Et un lot vide n'est pas une panne,
> mais ce n'est pas sain non plus : une source contractuellement quotidienne
> qui rend zéro ligne est une source à regarder.

## 9. La campagne de modifications

Dix-sept modifications, sept paquets de test.

```
modification                                                       | tests qui tombent
-------------------------------------------------------------------+------------------
 1. un enregistrement sans provenance est accepte                  | 1
 2. la cle vide est acceptee                                       | 1
 3. les valeurs ne sont plus copiees                               | 1
 4. Valeur() ne distingue plus l'absent du vide                    | 1
 5. une plage inversee est acceptee                                | 1
 6. l'heure n'est plus ecartee d'une plage                         | 1
 7. la valeur zero d'un Etat devient Sain                          | 4
 8. la provenance n'est plus verifiee par l'ordonnanceur           | 2
 9. la selection est journalisee APRES l'appel                     | 1
10. un lot vide est declare sain                                   | 1
11. la sante par defaut devient saine                              | 1
12. une ligne sans cle est ignoree au lieu de faire tomber le lot  | 1
13. ChampsExposes rend la tranche interne                          | 1
14. Inconnu ne compte plus comme degrade                           | 1
15. une mesure absente n'est plus perimee                          | 1
16. une configuration vide est acceptee                            | 1
17. ChampsManquants ne filtre plus par provenance                  | 1

17/17 modifications detectees
```

Trois ont d'abord survécu, et les trois diagnostics sont **différents**. C'est
le passage le plus utile de cet exercice.

### Survivant 1 — un mutant équivalent

La modification faisait rendre à `Champs()` sa tranche interne au lieu d'une
copie. Elle a survécu, et avant de chercher le test manquant il faut regarder
le code :

`Champs()` **construit une tranche neuve à chaque appel**, depuis la carte
interne. Il n'y a aucune tranche interne à fuiter. Les deux versions calculent
la même chose, pour toutes les entrées. **Mutant équivalent**, aucun test à
écrire, et la modification a été remplacée par une autre qui a du sens — sur
le booléen de `Valeur()`.

### Survivant 2 — du code mort, et un test qui passait pour la mauvaise raison

`base.Sante()` portait une branche *« si `dernierEtat` est nil, rendre
`Inconnu` »*. Changer le défaut de `Inconnu` à `Sain` dans cette branche n'a
rien cassé.

Raison : **les quatre constructeurs posent tous un pointeur non nul.** La
branche ne pouvait pas être atteinte. Et le test
`TestLaSanteEstInconnueAvantLaPremiereCollecte` passait — mais parce que la
valeur zéro de `Sante` a déjà `Inconnu` pour état, pas grâce au garde.

```go
// Sante rend le dernier etat connu, sans rien declencher.
//
// La premiere version de cette methode portait une branche « si dernierEtat
// est nil, rendre INCONNU ». La campagne de modifications l'a designee comme
// du CODE MORT : les quatre constructeurs posent tous un pointeur non nul, et
// la valeur zero de Sante a deja Inconnu pour etat. La branche ne pouvait pas
// etre atteinte, et le test qui verifiait l'etat initial passait pour une
// autre raison que celle que je croyais.
//
//    Une modification qui survit sur une branche designe parfois une
//    branche qui ne peut pas etre atteinte. Le remede n'est pas un test de
//    plus, c'est de retirer la branche.
func (b base) Sante() collecte.Sante { return *b.dernierEtat }
```

> Une modification qui survit sur une branche désigne parfois une branche qui
> **ne peut pas être atteinte**. Le remède n'est pas un test de plus, c'est de
> retirer la branche.

Et une fois la branche retirée, la modification se réécrit sur les
constructeurs — où elle tombe. Détail qui a son charme : elle n'a été
appliquée qu'à un seul des quatre constructeurs, et c'est le test qui parcourt
**les quatre** qui l'a attrapée. Le test spécifique, lui, portait sur un autre
connecteur.

### Survivant 3 — un garde qui n'était pas redondant, et qu'il fallait prouver

`Perimees` teste `sante.Mesuree.IsZero() || maintenant.Sub(...) > age`.
Retirer le premier terme a survécu : une mesure à l'an 1 est vieille de deux
mille ans, donc périmée de toute façon.

Il ne cesse de l'être que dans un cas : **si l'heure courante est elle aussi
la valeur zéro**. Une horloge non initialisée — et ce jour-là, sans le garde,
*toutes* les sources se déclareraient fraîches en même temps.

Le garde n'était donc pas redondant ; il manquait son test. Celui-ci passe
`time.Time{}` comme heure courante, et la modification tombe.

> Trois survivants, trois remèdes différents : **remplacer la modification**
> (mutant équivalent), **retirer la branche** (code mort), **écrire le test
> qui manquait** (garde réel mais non prouvé). Lire le code avant d'écrire un
> test est ce qui permet de choisir.

## 10. Ce que cet exercice devait faire comprendre

1. **Variantes ouvertes, opérations fermées** : c'est le cas de l'interface,
   et l'exercice 2 était l'inverse. Le même chapitre, deux réponses opposées.
2. **Trois appelants, trois interfaces**, de deux, deux et trois méthodes pour
   une implémentation qui en porte cinq.
3. **Le vocabulaire a besoin de son paquet**, sinon la dépendance revient par
   les arguments — et `go list` le dit sans discussion.
4. **La provenance dans le type** rend « personne ne sait laquelle » non
   représentable, et quatre programmes qui ne compilent pas le gardent.
5. **Un ⚫ a des trous, et il faut les nommer** : la valeur zéro, la
   provenance fausse, l'incomplétude. Les deux premiers se ferment chez
   l'appelant, le troisième est une mesure avec un plancher de bruit.
6. **La racine de composition a le droit de tout connaître**, et c'est là que
   vivent les assertions de conformité — mesure : 0 erreur au `go build`
   quand elles sont dans un `_test.go`, 4 quand elles sont au bon endroit.
7. **On ne peut rien garantir pour le dépôt du partenaire.** On peut
   seulement le savoir avant lui.
8. **Trois survivants, trois remèdes.** Un mutant équivalent, une branche
   morte, un garde non prouvé — et la première chose à faire devant un
   survivant est de lire le code, pas d'écrire un test.
