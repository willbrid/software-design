# Correction 2.5 — Exercice 1 : le client du prestataire de paiement

> Rappel de l'énoncé : une interface `psp.Client` de dix méthodes, déclarée à
> côté de son implémentation HTTP, six paquets qui l'importent, et la matrice
> d'usage rendue par le sondage de la leçon.

J'ai fait la coupe et toutes les mesures sur deux instantanés du même code —
`before` et `after` —, avec les mêmes tests de consommateurs des deux côtés.
Verts sous `go vet ./...` et `go test -race -count=1 ./...`. Campagne de huit
modifications, 8/8 après deux passes.

## 1. La prédiction

Six interfaces — **une par consommateur**, déclarée chez lui. C'est la
prédiction qu'il fallait écrire, et la suite la confirme avec une nuance : le
sixième consommateur, `limits`, avait déjà fait la coupe à sa façon.

## 2. La matrice, et `Status`

Les groupes se lisent directement :

| Consommateur | Méthodes appelées |
|---|---|
| `checkout` | `Authorize`, `Capture`, `Cancel` |
| `refund` | `Status`, `Refund` |
| `reconciliation` | `ListTransactions`, `Download` |
| `webhook` | `VerifySignature`, `Status` |
| `fraud` | `Score` |
| `limits` | `Limits` — invisible au sondage, voir la question 4 |

**`Status` va dans deux interfaces**, une chez `refund`, une chez
`webhook`. La tentation est d'en faire une troisième — `Statuses` — que les
deux incorporeraient. Elle ne gagne rien, et la mesure A dit pourquoi : quand
`Status` change, les deux consommateurs cassent de toute façon, puisqu'ils
l'appellent ; quand `Refund` change, seul le remboursement doit casser. Une
interface commune `{Status, Refund, VerifySignature}` ferait casser le
webhook pour `Refund`. Le critère d'ISP n'est pas « pas de méthode
déclarée deux fois », c'est **« pas de paquet qui casse pour une méthode qu'il
n'appelle pas »**, et deux déclarations de `Status` le tiennent.

## 3. Les six interfaces

```go
// Payments is what the checkout needs: authorize, capture, and cancel if
// the capture fails.
type Payments interface {
    Authorize(card string, a psp.Amount) (ref string, err error)
    Capture(ref string) error
    Cancel(ref string) error
}

type Checkout struct{ psp Payments }

func New(c Payments) Checkout { return Checkout{psp: c} }
```

```go
// Refunds is what the refund needs.
type Refunds interface {
    Status(ref string) (string, error)
    Refund(ref string, a psp.Amount) error
}
```

```go
// Statement is what the reconciliation needs: the day's statement, and its
// raw copy for the archive.
type Statement interface {
    ListTransactions(day time.Time) ([]psp.Transaction, error)
    Download(day time.Time, w io.Writer) error
}
```

```go
// Verifier is what receiving a notification needs. Status is in it, as in
// refund.Refunds: two consumers, two declarations, and neither is a copy of
// the other.
type Verifier interface {
    VerifySignature(body []byte, signature string) bool
    Status(ref string) (string, error)
}

type Receiver struct{ psp Verifier }

func New(c Verifier) Receiver { return Receiver{psp: c} }
```

```go
// Scorer is what the fraud check needs. Its only method speaks only of
// native types: fraud no longer imports psp.
type Scorer interface {
    Score(card string) (int, error)
}

// Strengthen tells whether the card's score requires strong verification.
func Strengthen(c Scorer, card string) (bool, error) {
    s, err := c.Score(card)
    return s >= 70, err
}
```

```go
// Reader reads a merchant's limit.
type Reader func(merchant string) (psp.Amount, error)

// LimitSource is what limits needs to build a Reader.
type LimitSource interface {
    Limits(merchant string) (psp.Amount, error)
}

// From returns the limits reader of a provider client.
func From(c LimitSource) Reader { return c.Limits }
```

Les noms disent ce dont le consommateur a besoin — `Payments`,
`Refunds`, `Statement`, `Verifier`, `Scorer`, `LimitSource` —, pas
ce que le prestataire sait faire. Aucun ne s'appelle `Client` : un client de
quoi, pour qui ?

Et la racine de composition, qui câble la même implémentation sur les six :

```go
// Ports gathers what each consumer receives.
type Ports struct {
    Payments  checkout.Payments
    Refunds   refund.Refunds
    Statement reconciliation.Statement
    Verifier  webhook.Verifier
    Scorer    fraud.Scorer
    Limits    limits.LimitSource
}

// Wire plugs a single implementation into the six ports.
func Wire(c psp.HTTP) Ports {
    return Ports{
        Payments:  c,
        Refunds:   c,
        Statement: c,
        Verifier:  c,
        Scorer:    c,
        Limits:    c,
    }
}
```

## 4. `Limits`, que le sondage croit inutilisée

Le sondage dit : *aucun consommateur*. Il a tort. Voici `limits` dans
l'instantané `before` :

```go
// Reader reads a merchant's limit.
type Reader func(merchant string) (psp.Amount, error)

// From returns the limits reader of a provider client.
func From(c psp.Client) Reader { return c.Limits }
```

`c.Limits` sans parenthèses : une **méthode prise comme valeur**. C'est
exactement le deuxième cas du test négatif de la leçon (`f := s.Outstanding`), et
le sondage ne le voit pas, par construction. Son erreur est toujours dans le
même sens — il sous-estime —, ce qui veut dire qu'une méthode qu'il déclare
inutilisée est une **piste**, jamais une décision.

Ce que je vérifie avant de supprimer, dans l'ordre :

1. `grep -rn 'Limits' --include=*.go .` — trouve `limits` en une seconde.
2. **Le compilateur, qui est la seule autorité** : je retire la méthode et je
   compile. Mesuré :

```
== before, Limits removed from the interface: 1 package(s) broken: limits
   ex1/before/limits/limits.go:14:43: c.Limits undefined (type psp.Client has no field or method Limits)
```

Le compilateur voit ce que le sondage ne voit pas : une méthode prise comme
valeur, une variable recopiée, une interface transmise. **Dans le dépôt**,
une suppression qui compile est une suppression sûre.

Ce que la matrice ne peut **jamais** voir, même avec un sondage parfait et un
compilateur : les consommateurs **hors du dépôt**. `psp` n'est pas sous
`internal/` ; un autre module peut l'importer, et aucune commande lancée ici
ne le saura. C'est la question de l'exercice 4, et elle n'a pas de réponse
locale.

Remarque : `limits` était déjà le consommateur le mieux découpé du dépôt — il
ne garde de `psp.Client` qu'une **fonction**, `Reader`. C'est le meilleur
ISP possible, et c'est précisément pour ça que le sondage ne l'a pas vu.

## 5. La mesure A, prédite puis mesurée

On ajoute un `context.Context` à `Status`, dans `psp` seulement.

**Ma prédiction était fausse**, et l'écart est l'enseignement. J'attendais
« beaucoup de paquets avant, un après ». Sur le code tel que l'énoncé le
donne — sans aucun test —, voici ce qui casse :

```
== before without doubles, ctx on Status: 2 package(s) broken: refund, webhook
   ex1/before/refund/refund.go:12:21: not enough arguments in call to c.Status
   ex1/before/webhook/webhook.go:22:22: not enough arguments in call to r.psp.Status
```

Deux paquets, les deux qui appellent `Status`. **Aucun paquet qui ne
l'appelle pas.** L'interface large ne coûte rien à la mesure A ici, et la
raison est mécanique : un paquet qui reçoit un `psp.Client` sans jamais
**implémenter** l'interface n'a aucune raison de casser quand une méthode
qu'il n'appelle pas change. Ce qui casse, ce sont les **implémentations** —
et dans ce dépôt, il n'y en a qu'une.

La première doublure de test change tout. J'ai écrit pour chaque consommateur
le test qu'il aurait dû avoir, avec une doublure de `psp.Client` — dix
méthodes, dont celles qu'il n'appelle pas :

lui-même — le programme qui branchera les deux ne compilera pas —, mais il
est **différé** jusqu'à ce programme. C'est pourquoi la racine de composition
doit exister dès la coupe, et câbler tout le monde.

## 6. `fraud` et ses 200 dépendances

Mesuré, avant et après :

```
before fraud: net/http=1 deps=200 ; psp imported=1
after  fraud: net/http=0 deps=1 ; psp imported=0
```

**De 200 dépendances à une — lui-même.** L'interface `Scorer` ne parle que
de `string`, `int` et `error` : `fraud` n'importe plus `psp`, donc plus
`net/http`, `crypto/hmac`, `encoding/json`, ni rien de ce qu'ils tirent.

Le type qui déciderait de la réponse : **un type de `psp` dans la signature de
`Score`**. Si le prestataire rendait un `psp.Score` — une structure avec une
note et un motif —, l'interface de `fraud` devrait le nommer, `fraud`
importerait `psp`, et les 200 dépendances reviendraient. C'est la leçon : *une
interface au bon endroit ne suffit pas si les types qu'elle nomme sont au
mauvais endroit.* Les autres consommateurs le montrent d'ailleurs déjà :
`checkout`, `refund` et `reconciliation` nomment `psp.Amount` ou
`psp.Transaction`, et tirent encore `psp`. Pour eux, la coupe ISP est faite ;
la coupe DIP ne l'est pas.

## 7. Le collègue et ses copies

Il a **raison** sur un point : `Status(ref string) (string, error)` est écrit
deux fois, et le jour où le prestataire change la signature, il faut changer
les deux.

Il a **tort** sur « il faut retrouver toutes les copies » : personne n'a à
les retrouver, le compilateur les liste. Mesuré à la question 5 : avec les
interfaces côté consommateur, l'erreur apparaît **dans la racine de
composition, une fois par copie**, chacune nommant le consommateur concerné.
Avec l'interface unique dans `psp`, l'erreur apparaît **dans les doublures de
six paquets**, dont quatre n'appellent pas la méthode — c'est-à-dire chez des
équipes qui n'ont rien à décider.

| | Interface unique dans `psp` | Interfaces chez les consommateurs |
|---|---|---|
| où l'erreur apparaît | dans les doublures de tous les consommateurs | dans la racine de composition |
| combien d'erreurs | une par usage d'une doublure — 8 ici, dans six fichiers de test | **une par consommateur qui appelle la méthode** — 2 |
| qui doit agir | tout le monde | ceux qui appellent la méthode |

« Un seul endroit » est vrai pour la **déclaration**. Pour le **changement**,
c'est l'inverse.

Les deux survivants sont dans la racine de composition, et ils disent la même
chose : **le compilateur vérifie le type de ce qui est câblé, pas que tout
l'est.** `Refunds: nil` compile ; un champ oublié dans le littéral
compile. Le consommateur paniquerait au premier appel. Les deux réclament un
test :

```go
// TestEverythingIsWired: the compiler checks the TYPE of what is wired, not
// that everything is. A forgotten port, or one wired to nil, compiles — and
// the consumer panics on the first call.
func TestEverythingIsWired(t *testing.T) {
    p := reflect.ValueOf(Wire(psp.HTTP{}))
    for i := range p.NumField() {
        if p.Field(i).IsNil() {
            t.Errorf("port %s is not wired", p.Type().Field(i).Name)
        }
    }
}
```

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Une interface par consommateur, déclarée chez lui. Une méthode peut figurer dans deux interfaces : le critère est qu'aucun paquet ne casse pour une méthode qu'il n'appelle pas, pas qu'aucune méthode ne soit écrite deux fois. |
| ⚫ | Le sondage sous-estime toujours. Une méthode qu'il croit inutilisée est une piste ; le compilateur décide, après suppression. Ici, une méthode prise comme valeur. |
| ⚫ | Ni le sondage ni le compilateur ne voient les consommateurs hors du dépôt. |
| ⚫ | **Une interface large coûte en proportion de ses implémentations, doublures comprises.** Mesuré : sans doublure, 0 paquet non appelant ne casse ; avec une doublure par consommateur, 4. |
| ⚫ | Sans racine de composition, le désaccord entre une implémentation et l'interface d'un consommateur est différé. La racine doit exister dès la coupe. |
| ⚫ | Le compilateur vérifie le type de ce qui est câblé, pas que tout l'est. Un test parcourt les ports et refuse un `nil`. |
| ⚫ | Une interface qui ne nomme que des types natifs libère son consommateur : `fraud` passe de 200 dépendances à 1. Un seul type du prestataire dans la signature, et tout revient. |
| ⚫ | « Un seul endroit » vaut pour la déclaration. Pour le changement, les interfaces chez les consommateurs donnent une erreur par consommateur concerné, et aucune chez les autres. |
