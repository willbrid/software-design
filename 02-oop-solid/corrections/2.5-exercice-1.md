# Correction 2.5 — Exercice 1 : le client du prestataire de paiement

> Rappel de l'énoncé : une interface `psp.Client` de dix méthodes, déclarée à
> côté de son implémentation HTTP, six paquets qui l'importent, et la matrice
> d'usage rendue par le sondage de la leçon.

J'ai fait la coupe et toutes les mesures sur deux instantanés du même code —
`avant` et `apres` —, avec les mêmes tests de consommateurs des deux côtés.
Verts sous `go vet ./...` et `go test -race -count=1 ./...`. Campagne de huit
modifications, 8/8 après deux passes.

## 1. La prédiction

Six interfaces — **une par consommateur**, déclarée chez lui. C'est la
prédiction qu'il fallait écrire, et la suite la confirme avec une nuance : le
sixième consommateur, `limites`, avait déjà fait la coupe à sa façon.

## 2. La matrice, et `Statut`

Les groupes se lisent directement :

| Consommateur | Méthodes appelées |
|---|---|
| `caisse` | `Autoriser`, `Capturer`, `Annuler` |
| `remboursement` | `Statut`, `Rembourser` |
| `rapprochement` | `ListerTransactions`, `Telecharger` |
| `webhook` | `VerifierSignature`, `Statut` |
| `fraude` | `Score` |
| `limites` | `Plafonds` — invisible au sondage, voir la question 4 |

**`Statut` va dans deux interfaces**, une chez `remboursement`, une chez
`webhook`. La tentation est d'en faire une troisième — `Statuts` — que les
deux incorporeraient. Elle ne gagne rien, et la mesure A dit pourquoi : quand
`Statut` change, les deux consommateurs cassent de toute façon, puisqu'ils
l'appellent ; quand `Rembourser` change, seul le remboursement doit casser. Une
interface commune `{Statut, Rembourser, VerifierSignature}` ferait casser le
webhook pour `Rembourser`. Le critère d'ISP n'est pas « pas de méthode
déclarée deux fois », c'est **« pas de paquet qui casse pour une méthode qu'il
n'appelle pas »**, et deux déclarations de `Statut` le tiennent.

## 3. Les six interfaces

```go
// Paiements est ce dont la caisse a besoin : autoriser, capturer, et annuler
// si la capture echoue.
type Paiements interface {
    Autoriser(carte string, m psp.Montant) (ref string, err error)
    Capturer(ref string) error
    Annuler(ref string) error
}

type Caisse struct{ psp Paiements }

func Nouvelle(c Paiements) Caisse { return Caisse{psp: c} }
```

```go
// Remboursements est ce dont le remboursement a besoin.
type Remboursements interface {
    Statut(ref string) (string, error)
    Rembourser(ref string, m psp.Montant) error
}
```

```go
// Releve est ce dont le rapprochement a besoin : le releve du jour, et sa
// copie brute pour l'archive.
type Releve interface {
    ListerTransactions(jour time.Time) ([]psp.Transaction, error)
    Telecharger(jour time.Time, w io.Writer) error
}
```

```go
// Verificateur est ce dont la reception d'une notification a besoin. Statut
// y figure, comme dans remboursement.Remboursements : deux consommateurs, deux
// declarations, et aucune n'est la copie de l'autre.
type Verificateur interface {
    VerifierSignature(corps []byte, signature string) bool
    Statut(ref string) (string, error)
}

type Recepteur struct{ psp Verificateur }

func Nouveau(c Verificateur) Recepteur { return Recepteur{psp: c} }
```

```go
// Evaluateur est ce dont la fraude a besoin. Sa seule methode ne parle que
// de types natifs : fraude n'importe plus psp.
type Evaluateur interface {
    Score(carte string) (int, error)
}

// Renforcer dit si le score de la carte impose une verification renforcee.
func Renforcer(c Evaluateur, carte string) (bool, error) {
    s, err := c.Score(carte)
    return s >= 70, err
}
```

```go
// Lecteur lit le plafond d'un marchand.
type Lecteur func(marchand string) (psp.Montant, error)

// Plafonnes est ce dont limites a besoin pour fabriquer un Lecteur.
type Plafonnes interface {
    Plafonds(marchand string) (psp.Montant, error)
}

// Depuis rend le lecteur de plafonds d'un client du prestataire.
func Depuis(c Plafonnes) Lecteur { return c.Plafonds }
```

Les noms disent ce dont le consommateur a besoin — `Paiements`,
`Remboursements`, `Releve`, `Verificateur`, `Evaluateur`, `Plafonnes` —, pas
ce que le prestataire sait faire. Aucun ne s'appelle `Client` : un client de
quoi, pour qui ?

Et la racine de composition, qui câble la même implémentation sur les six :

```go
// Ports regroupe ce que chaque consommateur recoit.
type Ports struct {
    Caisse         caisse.Paiements
    Remboursements remboursement.Remboursements
    Releve         rapprochement.Releve
    Verificateur   webhook.Verificateur
    Evaluateur     fraude.Evaluateur
    Plafonds       limites.Plafonnes
}

// Cabler branche une seule implementation sur les six ports.
func Cabler(c psp.HTTP) Ports {
    return Ports{
        Caisse:         c,
        Remboursements: c,
        Releve:         c,
        Verificateur:   c,
        Evaluateur:     c,
        Plafonds:       c,
    }
}
```

## 4. `Plafonds`, que le sondage croit inutilisée

Le sondage dit : *aucun consommateur*. Il a tort. Voici `limites` dans
l'instantané `avant` :

```go
// Lecteur lit le plafond d'un marchand.
type Lecteur func(marchand string) (psp.Montant, error)

// Depuis rend le lecteur de plafonds d'un client du prestataire.
func Depuis(c psp.Client) Lecteur { return c.Plafonds }
```

`c.Plafonds` sans parenthèses : une **méthode prise comme valeur**. C'est
exactement le deuxième cas du test négatif de la leçon (`f := d.Encours`), et
le sondage ne le voit pas, par construction. Son erreur est toujours dans le
même sens — il sous-estime —, ce qui veut dire qu'une méthode qu'il déclare
inutilisée est une **piste**, jamais une décision.

Ce que je vérifie avant de supprimer, dans l'ordre :

1. `grep -rn 'Plafonds' --include=*.go .` — trouve `limites` en une seconde.
2. **Le compilateur, qui est la seule autorité** : je retire la méthode et je
   compile. Mesuré :

```
== avant, Plafonds retire de l'interface : 1 paquet(s) casse(s) : limites
   ex1/avant/limites/limites.go:14:46: c.Plafonds undefined (type psp.Client has no field or method Plafonds)
```

Le compilateur voit ce que le sondage ne voit pas : une méthode prise comme
valeur, une variable recopiée, une interface transmise. **Dans le dépôt**,
une suppression qui compile est une suppression sûre.

Ce que la matrice ne peut **jamais** voir, même avec un sondage parfait et un
compilateur : les consommateurs **hors du dépôt**. `psp` n'est pas sous
`internal/` ; un autre module peut l'importer, et aucune commande lancée ici
ne le saura. C'est la question de l'exercice 4, et elle n'a pas de réponse
locale.

Remarque : `limites` était déjà le consommateur le mieux découpé du dépôt — il
ne garde de `psp.Client` qu'une **fonction**, `Lecteur`. C'est le meilleur
ISP possible, et c'est précisément pour ça que le sondage ne l'a pas vu.

## 5. La mesure A, prédite puis mesurée

On ajoute un `context.Context` à `Statut`, dans `psp` seulement.

**Ma prédiction était fausse**, et l'écart est l'enseignement. J'attendais
« beaucoup de paquets avant, un après ». Sur le code tel que l'énoncé le
donne — sans aucun test —, voici ce qui casse :

```
== avant sans doublures, ctx sur Statut : 2 paquet(s) casse(s) : remboursement, webhook
   ex1/avant/remboursement/remboursement.go:12:21: not enough arguments in call to c.Statut
   ex1/avant/webhook/webhook.go:22:22: not enough arguments in call to r.psp.Statut
```

Deux paquets, les deux qui appellent `Statut`. **Aucun paquet qui ne
l'appelle pas.** L'interface large ne coûte rien à la mesure A ici, et la
raison est mécanique : un paquet qui reçoit un `psp.Client` sans jamais
**implémenter** l'interface n'a aucune raison de casser quand une méthode
qu'il n'appelle pas change. Ce qui casse, ce sont les **implémentations** —
et dans ce dépôt, il n'y en a qu'une.

La première doublure de test change tout. J'ai écrit pour chaque consommateur
le test qu'il aurait dû avoir, avec une doublure de `psp.Client` — dix
méthodes, dont celles qu'il n'appelle pas :

## 6. `fraude` et ses 200 dépendances

Mesuré, avant et après :

```
avant  fraude : net/http=1 deps=200 ; psp importe=1
apres  fraude : net/http=0 deps=1 ; psp importe=0
```

**De 200 dépendances à une — lui-même.** L'interface `Evaluateur` ne parle que
de `string`, `int` et `error` : `fraude` n'importe plus `psp`, donc plus
`net/http`, `crypto/hmac`, `encoding/json`, ni rien de ce qu'ils tirent.

Le type qui déciderait de la réponse : **un type de `psp` dans la signature de
`Score`**. Si le prestataire rendait un `psp.Score` — une structure avec une
note et un motif —, l'interface de `fraude` devrait le nommer, `fraude`
importerait `psp`, et les 200 dépendances reviendraient. C'est la leçon : *une
interface au bon endroit ne suffit pas si les types qu'elle nomme sont au
mauvais endroit.* Les autres consommateurs le montrent d'ailleurs déjà :
`caisse`, `remboursement` et `rapprochement` nomment `psp.Montant` ou
`psp.Transaction`, et tirent encore `psp`. Pour eux, la coupe ISP est faite ;
la coupe DIP ne l'est pas.

## 7. Le collègue et ses copies

Il a **raison** sur un point : `Statut(ref string) (string, error)` est écrit
deux fois, et le jour où le prestataire change la signature, il faut changer
les deux.

Il a **tort** sur « il faut retrouver toutes les copies » : personne n'a à
les retrouver, le compilateur les liste. Mesuré à la question 5 : avec les
interfaces côté consommateur, l'erreur apparaît **dans la racine de
composition, une fois par copie**, chacune nommant le consommateur concerné.
Avec l'interface unique dans `psp`, l'erreur apparaît **dans les doublures de
six paquets**, dont quatre n'appellent pas la méthode — c'est-à-dire chez des
équipes qui n'ont rien à décider.

| | Interface unique dans `psp` | Interfaces chez les consommateurs |
|---|---|---|
| où l'erreur apparaît | dans les doublures de tous les consommateurs | dans la racine de composition |
| combien d'erreurs | une par usage d'une doublure — 8 ici, dans six fichiers de test | **une par consommateur qui appelle la méthode** — 2 |
| qui doit agir | tout le monde | ceux qui appellent la méthode |

« Un seul endroit » est vrai pour la **déclaration**. Pour le **changement**,
c'est l'inverse.

```

remboursement : ne verifie plus le statut  tuee
rapprochement : n'archive plus             tuee
webhook : ne verifie plus la signature     tuee
```

Les deux survivants sont dans la racine de composition, et ils disent la même
chose : **le compilateur vérifie le type de ce qui est câblé, pas que tout
l'est.** `Remboursements: nil` compile ; un champ oublié dans le littéral
compile. Le consommateur paniquerait au premier appel. Les deux réclament un
test :

```go
// TestToutEstCable : le compilateur verifie le TYPE de ce qui est cable, pas
// que tout l'est. Un port oublie, ou cable a nil, compile — et le
// consommateur panique au premier appel.
func TestToutEstCable(t *testing.T) {
    p := reflect.ValueOf(Cabler(psp.HTTP{}))
    for i := range p.NumField() {
        if p.Field(i).IsNil() {
            t.Errorf("le port %s n'est pas cable", p.Type().Field(i).Name)
        }
    }
}
```

## Ce qu'il faut retenir

| | |
|---|---|
| ⚫ | Une interface par consommateur, déclarée chez lui. Une méthode peut figurer dans deux interfaces : le critère est qu'aucun paquet ne casse pour une méthode qu'il n'appelle pas, pas qu'aucune méthode ne soit écrite deux fois. |
| ⚫ | Le sondage sous-estime toujours. Une méthode qu'il croit inutilisée est une piste ; le compilateur décide, après suppression. Ici, une méthode prise comme valeur. |
| ⚫ | Ni le sondage ni le compilateur ne voient les consommateurs hors du dépôt. |
| ⚫ | **Une interface large coûte en proportion de ses implémentations, doublures comprises.** Mesuré : sans doublure, 0 paquet non appelant ne casse ; avec une doublure par consommateur, 4. |
| ⚫ | Sans racine de composition, le désaccord entre une implémentation et l'interface d'un consommateur est différé. La racine doit exister dès la coupe. |
| ⚫ | Le compilateur vérifie le type de ce qui est câblé, pas que tout l'est. Un test parcourt les ports et refuse un `nil`. |
| ⚫ | Une interface qui ne nomme que des types natifs libère son consommateur : `fraude` passe de 200 dépendances à 1. Un seul type du prestataire dans la signature, et tout revient. |
| ⚫ | « Un seul endroit » vaut pour la déclaration. Pour le changement, les interfaces chez les consommateurs donnent une erreur par consommateur concerné, et aucune chez les autres. |
