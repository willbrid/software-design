# Correction 2.2 — Exercice 2 : la chaîne de dématérialisation

> Rappel de l'énoncé : quatre types de document, un ensemble fermé par le
> métier, et une question nouvelle par trimestre. Il fallait écrire le paquet
> `document` avec son scellement, ses deux tests d'exhaustivité, son test de
> non-compilation, ses assertions de conformité, puis mesurer les deux
> expériences et publier une campagne.

Tout ce qui suit est extrait d'un module qui compile, dont les 6 paquets de
test passent sous `go vet` et `go test -race -count=1`, et dont chaque chiffre
cité est une sortie de commande.

## 1. L'ensemble scellé

### La décision d'axe, avant d'écrire une ligne

L'énoncé donne les deux moitiés de la réponse, et elles sont explicites :

| | Ce que dit l'énoncé | Donc |
|---|---|---|
| **les variantes** | « il n'y en aura pas un cinquième avant au moins deux ans, parce que chaque type suppose un accord avec l'ordre » | ensemble **fermé**, et fermé par le métier |
| **les opérations** | « il en arrive une nouvelle par trimestre » | ensemble **ouvert** |

Fermé sur les variantes, ouvert sur les opérations : c'est le cas du type
somme scellé, et pas celui de l'interface. Si le relevé avait été l'inverse —
un type de document par trimestre, trois questions figées — la réponse serait
une interface, et tout ce qui suit serait faux.

### Le paquet, et son interface à une méthode

```go
// Package document definit les types de document que la chaine de
// dematerialisation accepte.
//
// L'ensemble est FERME, et il est ferme par le metier : chaque type suppose
// un accord avec l'ordre des experts-comptables, donc il n'en arrivera pas un
// cinquieme avant deux ans. Ce paquet le dit au compilateur avec une methode
// non exportee.
//
// Les quatre types sont des VALEURS au sens de la lecon 2.1 : champs prives,
// constructeur qui refuse le non-canonique, immuables, comparables. Deux
// factures dont tous les champs sont egaux SONT la meme facture — ce qui
// identifie une facture est son numero et son emetteur, et on ne change ni
// l'un ni l'autre sans emettre un autre document.
//
// La liste des imports de ce fichier est la mesure de la lecon : somme, jour,
// et le minimum de la bibliotheque standard. Ni le code de commerce, ni la
// matrice des roles.
package document
```

```go
// Document est l'ensemble ferme des types de document.
//
// document() n'est pas exportee : aucun type d'un autre paquet ne peut
// satisfaire cette interface, meme en declarant lui aussi une methode
// document(), parce que le nom d'une methode non exportee inclut le chemin de
// son paquet. L'ensemble des implementations tient dans ce fichier.
//
// C'est un ⚫ : l'etat « un type de document que ce paquet ne connait pas »
// n'est pas representable.
//
// Libelle est la SEULE operation portee par les variantes, et le critere est
// celui de la lecon : une methode appartient a la variante si et seulement si
// elle SE REPOND avec les champs de la variante.
//
//    Libelle                -> oui, avec les champs. Elle est ici.
//    DureeDeConservation    -> non, il faut le code de commerce. Paquet
//                              conservation.
//    DroitsDAcces           -> non, il faut la matrice des roles du cabinet.
//                              Paquet acces.
//    DoitEtreSignee         -> non, il faut le reglement eIDAS et la politique
//                              du cabinet. Paquet signature.
type Document interface {
    document()
    Libelle() string
}
```

Le critère, appliqué aux quatre questions de l'énoncé :

| Question | Se répond avec les champs du document ? | Où elle va |
|---|---|---|
| `Libelle` | **oui** | sur la variante |
| durée de conservation | non — il faut le code de commerce | paquet `conservation` |
| droits d'accès | non — il faut la matrice des rôles | paquet `acces` |
| signature électronique | non — il faut le règlement et la politique du cabinet | paquet `signature` |

Et la preuve que rien n'a fui est la liste des imports, pas une relecture :

```
$ go list -f '{{join .Imports " "}}' ./document
errors exemple/cabinet/jour exemple/cabinet/somme fmt strings

$ go list -f '{{join .Imports " "}}' ./conservation
errors exemple/cabinet/commerce exemple/cabinet/document exemple/cabinet/jour fmt

$ go list -f '{{join .Imports " "}}' ./acces
errors exemple/cabinet/document exemple/cabinet/roles fmt

$ go list -f '{{join .Imports " "}}' ./signature
errors exemple/cabinet/document fmt
```

`document` n'importe ni `commerce` ni `roles`. Les paquets `commerce` et
`roles` n'existent dans ce module que pour **rendre cette question
mesurable** : chaque paquet qui les importe est un paquet à qui on a demandé
de connaître le droit ou l'organigramme.

### Une variante, en entier

```go
// Facture est une facture recue ou emise.
type Facture struct {
    numero string
    siren  string
    ttc    somme.Somme
}

// NouvelleFacture construit une facture, ou refuse de la construire.
func NouvelleFacture(numero, siren string, ttc somme.Somme) (Facture, error) {
    if strings.TrimSpace(numero) == "" {
        return Facture{}, fmt.Errorf("%w : numero vide", ErrFormat)
    }
    if err := verifierSiren(siren); err != nil {
        return Facture{}, err
    }
    return Facture{numero: numero, siren: siren, ttc: ttc}, nil
}

func (f Facture) document()        {}
func (f Facture) Numero() string   { return f.numero }
func (f Facture) Siren() string    { return f.siren }
func (f Facture) TTC() somme.Somme { return f.ttc }
func (f Facture) Libelle() string  { return "Facture " + f.numero + " / SIREN " + f.siren }
```

C'est une **valeur** au sens de la leçon 2.1 : champs privés, constructeur qui
refuse le non-canonique, immuable, comparable. Et le gain n'est pas théorique
— une facture est une clé de map, et le test le vérifie plutôt que de
l'affirmer.

### Le détail de modélisation qui n'était pas dans l'énoncé

L'énoncé dit que le relevé bancaire porte « un solde de clôture ». J'ai
d'abord écrit `somme.Somme`, comme pour le TTC de la facture. C'est faux :

> Un solde de clôture peut être **négatif** — c'est un découvert. Un montant
> facturé ne peut pas l'être. Deux choses qui s'écrivent toutes les deux « de
> l'argent » et qui n'ont pas le même ensemble de valeurs valides ne sont pas
> le même type.

Donc `clotureCentimes int64` pour le relevé, et `somme.Somme` — positif ou
nul, garanti par son constructeur — pour la facture. C'est la question de la
leçon 2.1 sur la valeur zéro, posée une variante à la fois.

## 2. Les deux tests d'exhaustivité

```go
// Package exhaustivite_test achete ce que Go ne donne pas.
//
// Go donne la CLOTURE de l'ensemble des implementations : document() non
// exportee rend toute implementation hors du paquet impossible, et c'est
// gratuit. Il ne donne ni l'EXHAUSTIVITE du traitement — un type switch a
// trois cas plus un default compile parfaitement — ni la cloture de
// l'ensemble des VALEURS, puisque nil satisfait toute interface.
//
// Deux tests, et ils ne se remplacent pas :
//
//   - par la REPETITION : parcourir document.Variantes() et exiger qu'aucune
//     operation ne tombe dans son default. Simple, et ne vaut que si
//     Variantes() est complete.
//   - par la LECTURE DE LA SOURCE : lire document/*.go avec go/ast pour
//     etablir la liste vraie, puis lire les type switch du module. C'est
//     celui-la qui garde l'autre.
package exhaustivite_test
```

### Celui qui lit la source

```go
// variantesParLaSource : tout type du paquet document qui porte la methode
// non exportee document(). C'est la definition exacte de « appartenir a
// l'ensemble scelle », et elle ne depend d'aucune liste ecrite a la main.
func variantesParLaSource(t *testing.T) []string {
    t.Helper()
    fset := token.NewFileSet()
    paquets, err := parser.ParseDir(fset, paquetScelle, nil, 0)
    if err != nil {
        t.Fatalf("lecture de %s : %v", paquetScelle, err)
    }
    var noms []string
    for _, p := range paquets {
        for _, f := range p.Files {
            for _, d := range f.Decls {
                fn, ok := d.(*ast.FuncDecl)
                if !ok || fn.Recv == nil || fn.Name.Name != methodeSceau {
                    continue
                }
                if n := nomDuRecepteur(fn.Recv); n != "" {
                    noms = append(noms, n)
                }
            }
        }
    }
    slices.Sort(noms)
    if len(noms) == 0 {
        t.Fatalf("aucune variante trouvee : la methode de scellement ne s'appelle plus %q", methodeSceau)
    }
    return noms
}
```

La définition de « appartenir à l'ensemble scellé » est **opérationnelle** :
tout type du paquet qui porte la méthode non exportée. Elle ne dépend d'aucune
liste écrite à la main, et c'est tout l'intérêt.

Puis le parcours des `switch`, avec le cas `nil` exigé :

```go
// TestChaqueTypeSwitchSurUnDocumentEstExhaustif rembourse la dette du
// default.
//
// NON GARANTI : le critere « au moins un cas nomme une variante » est une
// heuristique. Un traitement ecrit en if/else echappe entierement. Ce test
// attrape le cas de tres loin le plus frequent — la variante ajoutee, le
// switch oublie — et pas tous les cas.
func TestChaqueTypeSwitchSurUnDocumentEstExhaustif(t *testing.T) {
    variantes := variantesParLaSource(t)
    examines := 0
    err := filepath.WalkDir(racine, func(chemin string, d fs.DirEntry, err error) error {
        if err != nil {
            return err
        }
        if d.IsDir() || !strings.HasSuffix(chemin, ".go") || strings.HasSuffix(chemin, "_test.go") {
            return nil
        }
        fset := token.NewFileSet()
        f, err := parser.ParseFile(fset, chemin, nil, 0)
        if err != nil {
            return fmt.Errorf("%s : %w", chemin, err)
        }
        if !importe(f, cheminImport) {
            return nil
        }
        ast.Inspect(f, func(n ast.Node) bool {
            sw, ok := n.(*ast.TypeSwitchStmt)
            if !ok {
                return true
            }
            traites := casDUnTypeSwitch(sw, variantes)
            if len(traites) == 0 {
                return true
            }
            examines++
            ligne := fset.Position(sw.Pos()).Line
            for _, v := range variantes {
                if !slices.Contains(traites, v) {
                    t.Errorf("%s:%d : ne traite pas document.%s (traites : %v)",
                        chemin, ligne, v, traites)
                }
            }
            if !traiteLeCasNil(sw) {
                t.Errorf("%s:%d : ne traite pas le cas nil", chemin, ligne)
            }
            return true
        })
        return nil
    })
    if err != nil {
        t.Fatalf("parcours : %v", err)
    }
    if examines == 0 {
        t.Fatal("aucun type switch examine : le test ne surveille plus rien")
    }
    t.Logf("%d type switch de production examines : %d variantes exigees dans chacun, plus le cas nil",
        examines, len(variantes))
}
```

Une propriété de ce test qu'on n'attend pas et qui se mesure : il a **découvert
tout seul** le troisième `switch`. Avant l'ajout du paquet `signature` il en
examinait deux, après il en examine trois, et personne n'a touché à sa
configuration.

```
2 type switch de production examines : 4 variantes exigees dans chacun, plus le cas nil
3 type switch de production examines : 4 variantes exigees dans chacun, plus le cas nil
```

Et la clause **NON GARANTI**, qui fait partie du test : le critère « au moins
un cas nomme une variante » est une heuristique, et un traitement écrit en
`if`/`else` lui échappe entièrement.

### Celui par la répétition, et pourquoi il ne suffit pas

```go
// TestAucuneOperationNeTombeDansSonDefault est le test par la repetition. Il
// est garde par TestLaListeVariantesEstComplete : sans ce garde-fou, il
// rendrait vert un switch a trois cas des lors que Variantes() en aurait
// oublie une.
func TestAucuneOperationNeTombeDansSonDefault(t *testing.T) {
    for _, v := range document.Variantes() {
        if _, _, err := conservation.Duree(v); err != nil {
            t.Errorf("conservation.Duree(%T) : %v", v, err)
        }
        if _, err := conservation.Echeance(v, jour.MustAnalyser("2026-01-15")); err != nil {
            t.Errorf("conservation.Echeance(%T) : %v", v, err)
        }
        for _, r := range roles.Tous() {
            // ErrInterdit est une REPONSE metier, pas une variante oubliee :
            // les distinguer est tout l'interet d'avoir deux erreurs.
            if _, err := acces.Pour(v, r); err != nil && !errors.Is(err, acces.ErrInterdit) {
                t.Errorf("acces.Pour(%T, %s) : %v", v, r, err)
            }
        }
    }
}
```

Il parcourt `Variantes()`, qui est une liste écrite à la main. La section 4
montre ce qui arrive quand cette liste est incomplète : **ce test passe au
vert** alors que trois `switch` sont incomplets. C'est pour ça que celui qui
lit la source le **garde** au lieu de le remplacer.

Noter aussi la distinction entre les deux erreurs d'`acces` : `ErrInterdit`
est une **réponse métier** — un stagiaire n'a rien à voir sur un relevé
bancaire — et `ErrTypeNonTraite` est une **variante oubliée**. Le test accepte
la première et refuse la seconde. Avec une seule erreur pour les deux, il
n'aurait pu refuser ni l'une ni l'autre.

## 3. Le test de non-compilation

Cinq cas, chacun avec le fragment du message attendu, et un témoin qui tourne
en processus.

```go
// Package garde ne contient que des tests de decision.
package garde

import (
    "os"
    "os/exec"
    "path/filepath"
    "strings"
    "testing"

    // GARDE DU CACHE, et ce n'est pas decoratif : un test qui valide en
    // lancant « go build » dans un sous-processus ne depend de rien au sens
    // du compilateur, donc Go a le droit de lui servir un resultat perime.
    // En important ce qu'il surveille, le test redevient sensible, et le
    // temoin ci-dessous les utilise vraiment.
    "exemple/cabinet/acces"
    "exemple/cabinet/conservation"
    "exemple/cabinet/document"
    "exemple/cabinet/jour"
    "exemple/cabinet/roles"
    "exemple/cabinet/somme"
)
```

Les deux premiers cas méritent d'être lus ensemble, parce que leurs messages
diffèrent et que la différence **est** la preuve du mécanisme :

```go
        {
            nom: "declarer un cinquieme type de document hors du paquet",
            declarations: `type DeclarationTVA struct{ Periode string }

func (d DeclarationTVA) Libelle() string { return "TVA " + d.Periode }

var _ document.Document = DeclarationTVA{}`,
            attendu: "missing method document",
            garde:   "l'ensemble des types de document cesserait d'etre ferme",
        },
        {
            // Le message n'est PAS le meme que dans le cas precedent, et
            // c'est la preuve du mecanisme. Sans methode document() du tout,
            // le compilateur dit « missing method ». Avec une methode
            // document() declaree dans un autre paquet, il dit
            // « UNEXPORTED method » : il la voit, et il la refuse parce que
            // le nom d'une methode non exportee inclut le paquet ou elle est
            // declaree.
            nom: "recopier la methode de scellement",
            declarations: `type DeclarationTVA struct{ Periode string }

func (d DeclarationTVA) Libelle() string { return "TVA " + d.Periode }
func (d DeclarationTVA) document()       {}

var _ document.Document = DeclarationTVA{}`,
            attendu: "unexported method document",
            garde:   "le scellement se contournerait en recopiant un nom de methode",
        },
```

```
./main.go:13:27: DeclarationTVA does not implement document.Document (missing method document)
./main.go:14:27: DeclarationTVA does not implement document.Document (unexported method document)
```

« *missing* » quand il n'y a pas de méthode `document()`. « *unexported* »
quand on la recopie dans un autre paquet : le compilateur **la voit**, et il
la refuse, parce que le nom d'une méthode non exportée inclut le chemin du
paquet où elle est déclarée. Les deux `document()` ne portent pas le même nom.

Les trois autres cas et leurs messages mesurés :

```
./main.go:15:23: cannot refer to unexported field numero in struct literal of type document.Facture
./main.go:15:12: undefined: roles.inconnu
./main.go:15:6: invalid operation: somme.MustCentimes(100) + 1 (mismatched types somme.Somme and untyped int)
```

Trois précautions dans ce fichier, et chacune répond à un mode de panne connu
depuis la leçon 2.1 :

1. **le fragment de message attendu par cas**, sinon n'importe quelle erreur
   satisfait le test et la première faute de frappe le rend définitivement
   vert ;
2. **le témoin en processus**, parce qu'un témoin qui passe par le même
   `go build` que ce qu'il surveille tombe en même temps que lui ;
3. **les imports du paquet surveillé**, qui sont la garde du cache — un test
   qui valide dans un sous-processus ne dépend de rien au sens du
   compilateur, donc Go a le droit de lui servir un résultat périmé.

Et un détail de construction qui a son importance : le gabarit du programme
d'essai utilise **les trois imports dans tous les cas**, par trois lignes
`_ = ...` dans `main`. Sans ça, un cas qui n'utilise pas `roles` échoue à
compiler pour « *imported and not used* » — et il passerait, pour la mauvaise
raison, exactement comme en 2.1.

## 4. Les assertions de conformité, mesurées en trois points

C'est la question 7, et la mesure donne mieux que ce que j'attendais.

J'ajoute une deuxième méthode à `Document`, et je compte les erreurs de
compilation dans trois configurations :

```
Une deuxieme methode est ajoutee a l'interface Document.
  avec les 4 assertions explicites ET Variantes()            : 8 erreur(s)
  sans les assertions explicites, mais avec Variantes()      : 4 erreur(s)
  sans assertion explicite ET sans Variantes()               : 0 erreur(s)
```

Trois choses à en tirer.

**Zéro erreur sans aucune assertion.** Go n'a pas de déclaration `implements`,
donc le compilateur n'a rien à vérifier. Quatre types qui n'implémentent plus
l'interface, et il se tait.

**`Variantes()` est une assertion de conformité qui ne se présente pas comme
telle.** Son littéral de slice assigne les quatre variantes à `Document`,
donc il déclenche la vérification. Il en donne quatre.

**Les assertions explicites doublent le compte, et c'est voulu.** Les huit
erreurs ne sont pas une redondance inutile : `Variantes()` existe pour les
tests, et rien ne garantit qu'elle existera toujours. Si quelqu'un la
remplace par un autre mécanisme, la garantie disparaîtrait **sans que rien ne
le signale**. Les quatre lignes explicites la rendent indépendante de l'usage
qu'on fait du paquet.

```go
// Variantes rend un exemplaire de chaque variante.
//
// Liste ecrite a la main, donc faillible : c'est ce que le paquet
// exhaustivite surveille en lisant ce fichier. Elle sert aussi d'assertion de
// conformite sans en avoir l'air — le litteral de slice assigne les quatre
// variantes a Document, donc ajouter une methode a l'interface donne quatre
// erreurs de compilation ici.
func Variantes() []Document {
    return []Document{
        Facture{numero: "F-2026-001", siren: "552100554", ttc: somme.MustCentimes(120_00)},
        BonDeLivraison{numero: "BL-77", refCommande: "CMD-12"},
        ReleveBancaire{iban: "FR7630006000011234567890189", mois: "2026-03", clotureCentimes: -4_250},
        Contrat{reference: "CTR-9", partieA: "CABINET", partieB: "CLIENT", effet: jour.MustAnalyser("2026-01-01")},
    }
}

// Les quatre assertions de conformite, ecrites explicitement en plus du
// litteral de Variantes(). Elles sont la declaration « implements » que Go
// n'a pas, et sans elles le compilateur n'a rien a verifier.
var (
    _ Document = Facture{}
    _ Document = BonDeLivraison{}
    _ Document = ReleveBancaire{}
    _ Document = Contrat{}
)
```

> Une garantie qui dépend d'un détail d'implémentation ailleurs dans le
> fichier n'est pas une garantie, c'est une coïncidence qui tient.

## 5. Les deux expériences

### Expérience 1 — ajouter une cinquième variante

J'ajoute `DeclarationTVA` au paquet scellé, par étapes, et je mesure à chaque
étape.

**Étape 1 — le type existe, et rien d'autre n'a bougé.**

```
$ go build ./...
COMPILE : OUI — le compilateur n'a rien a dire

$ go test -count=1 ./...
--- FAIL: TestLaListeVariantesEstComplete
    source      : [BonDeLivraison Contrat DeclarationTVA Facture ReleveBancaire]
    Variantes() : [BonDeLivraison Contrat Facture ReleveBancaire]

    ../signature/signature.go:39       : ne traite pas document.DeclarationTVA
```

Le compilateur n'a rien dit. **Deux tests** l'ont dit, et ils ont nommé les

Et le troisième test, celui par la répétition, lancé seul :

Le relais est fait : le garde est vert, et les deux tests qu'il gardait

**Étape 3 — les trois `switch` sont complétés.** Tout est vert. Bilan :

**Quatre fichiers de production, et zéro erreur de compilation à chaque
étape.**

### Ce que l'expérience a trouvé dans mon propre test

À l'étape 3, un test a **paniqué** au lieu d'échouer :

```
--- FAIL: TestLesLibellesSontLisibles
    document_test.go:126: libelle = "Declaration TVA 2026-03 / ...",
                          attendu "Contrat CTR-9 (CABINET / CLIENT)"
panic: runtime error: index out of range [4] with length 4
```

Ma première version parcourait `Variantes()` avec un index et lisait une
tranche d'attendus écrite à la main. Le cinquième type a décalé les quatre
comparaisons précédentes, puis l'index est sorti des bornes.

> Un test qui indexe une liste par la **position** d'une autre panique au lieu
> d'échouer, et un test qui panique ne dit pas ce qui manque.

Indexé par le **nom du type**, il échoue proprement, il nomme la variante dont
le libellé n'a pas été décidé, et il signale aussi le cas inverse — un
attendu déclaré pour un type qui a disparu :

```go
// TestLesLibellesSontLisibles est indexe par le NOM DU TYPE et non par la
// position.
//
// La premiere version parcourait Variantes() avec un index et lisait une
// tranche ecrite a la main. En ajoutant un cinquieme type pour l'experience,
// elle n'a pas echoue : elle a PANIQUE sur un index hors bornes, et elle a
// decale les quatre comparaisons precedentes au passage.
//
//    Un test qui indexe une liste par la position d'une autre panique au
//    lieu d'echouer, et un test qui panique ne dit pas ce qui manque.
//
// Indexe par le nom du type, il echoue proprement et il nomme la variante

        "document.Contrat":        "Contrat CTR-9 (CABINET / CLIENT)",

        vus[cle] = true

        }
```

### Expérience 2 — ajouter une quatrième question

C'est la question 9, et le paquet `signature` **est** la réponse.

```go
// Package signature repond a la quatrieme question, celle du trimestre
// suivant : « ce document doit-il etre signe electroniquement ? »
//
// Ce paquet EST la mesure de la seconde experience. Il a coute un paquet
// nouveau, et rien d'autre : le paquet document n'a pas bouge, ses quatre
// variantes n'ont pas bouge, et aucune d'elles n'a appris ce qu'est le
// reglement eIDAS.
package signature

import (
    "errors"
    "fmt"

    "exemple/cabinet/document"
)
```

```go
// Exigee dit si le document doit etre signe, et pourquoi.
//
// Le « pourquoi » n'est pas decoratif : une obligation de signature se
// justifie devant un controle, et un booleen seul ne se justifie pas.
func Exigee(d document.Document, p Politique) (bool, string, error) {
    switch v := d.(type) {
    case nil:
        return false, "", fmt.Errorf("%w : interface nulle", ErrTypeNonTraite)
    case document.Facture:
        if p.ToutesLesFactures {
            return true, "politique du cabinet : toutes les factures", nil
        }
        if p.SeuilCentimes > 0 && v.TTC().Centimes() > p.SeuilCentimes {
            return true, fmt.Sprintf("montant %s au-dela du seuil", v.TTC()), nil
        }
        return false, "facture sous le seuil", nil
    case document.BonDeLivraison:
        return false, "un bon de livraison n'engage pas juridiquement", nil
    case document.ReleveBancaire:
        // Il est recu de la banque, qui l'a deja scelle. Le signer une
        // seconde fois n'ajoute rien et masquerait le sceau d'origine.
        return false, "deja scelle par l'etablissement emetteur", nil
    case document.Contrat:
        return true, "un contrat est signe par definition", nil
    default:
        return false, "", fmt.Errorf("%w : %T", ErrTypeNonTraite, d)
    }
}
```

Le bilan, mesuré :

| | Coût |
|---|---|
| paquet nouveau | 61 lignes + 77 de test |
| modifications du paquet `document` | **0** |
| méthodes ajoutées à l'interface | **0** |
| variantes modifiées | **0** |
| nouvelles connaissances dans `document` | **0** — il importe toujours `errors fmt strings jour somme` |

Et le tableau des deux axes, rempli avec les chiffres de ce module :

| | ajouter une variante | ajouter une opération |
|---|---|---|
| **ensemble fermé** | 4 fichiers, 0 erreur de compilation, 3 tests | **1 paquet neuf, rien d'autre** |

Deux remarques sur la conception de `signature`, parce que ce ne sont pas des
détails.

`Exigee` rend **un booléen et une justification**. Une obligation de signature
se justifie devant un contrôle, et un booléen seul ne se justifie pas. C'est
la leçon 1.3 sur ce qu'une fonction doit rendre pour que son appelant puisse
agir.

`Politique.SeuilCentimes` à zéro signifie **« pas de seuil »** et non
« seuil à zéro ». Si c'était l'inverse, toute facture non nulle serait à
signer, et la valeur zéro d'un champ de configuration serait le choix le plus
contraignant au lieu du plus neutre. Un test le garde, et une modification de
la campagne le confirme.

## 6. La campagne de modifications

Quatorze modifications, sur six paquets de test.

```
modification                                                       | tests qui tombent
-------------------------------------------------------------------+------------------
 1. verifierSiren ne verifie plus la cle de Luhn                   | 2
 2. verifierIban ne verifie plus le modulo 97                      | 1
 3. l'IBAN n'est plus canonise                                     | 1
 4. un contrat avec soi-meme est accepte si la casse differe       | 1
 5. Variantes() oublie le contrat                                  | 3
 6. conservation.Duree perd son cas nil                            | 1
 7. conservation.Duree perd le cas du bon de livraison             | 4
 8. la bascule de 2008 est inclusive au lieu d'exclusive           | 2
 9. PlusAnnees ajoute des mois au lieu d'annees                    | 2
10. le stagiaire voit les releves bancaires                        | 2
11. la valeur zero d'un Droit devient Lecture                      | 1
12. le seuil de signature devient inclusif                         | 1
13. somme.Centimes accepte le negatif                              | 1
14. roles.Analyser n'uniformise plus la casse                      | 1

14/14 modifications detectees
```

Quatre remarques de méthode, parce que le relevé final cache le chemin.

**Trois modifications n'ont d'abord pas compilé** — les 6, 13 et 14. À chaque
fois, retirer le code laissait une variable ou un import inutilisé. Une
modification qui ne compile pas n'est ni détectée ni survivante : **elle n'a
pas été jouée**. Il faut la rejouer sous une forme qui compile, et ça prend
deux minutes : `if false && n < 0` plutôt que la suppression de la ligne.

**La modification 6 est la plus instructive.** Retirer le `case nil` de
`conservation.Duree` ne fait pas tomber le test qui passe `nil` — il passe
toujours, parce que le `default` l'attrape et rend la même erreur. Elle fait
tomber **le test d'exhaustivité**, qui exige le cas `nil` dans chaque
`switch`. Autrement dit : le garde-fou qui tient ici est celui qui lit la
source, pas celui qui essaie une valeur.

**La modification 8 est celle qui cherche la frontière.** Faire passer
`< AnneeDeLaReforme` à `<= AnneeDeLaReforme` ne change le résultat que pour
les contrats de l'année 2008 exactement. Elle tombe parce que le tableau de
test contient trois cas et que l'un d'eux est **le jour de l'an de 2008**. Un
tableau qui aurait testé 2007 et 2026 seulement aurait laissé passer une
erreur de cinq contre trente ans sur une année entière de contrats.

> Dans une règle qui dépend d'une date de réforme, le cas de test obligatoire
> n'est pas « avant » et « après » : c'est **la veille, le jour, et le
> lendemain**.

**La modification 9 est un rappel.** Elle casse `PlusAnnees` en ajoutant des
mois, et elle fait tomber deux tests dont l'un est le 29 février. Ce test
existe parce que `PlusAnnees` **documente son choix** plutôt que de le subir :
un 29 février plus cinq ans n'existe pas, et il tombe au 1er mars. Un
comportement documenté est un comportement testable ; un comportement subi ne
l'est pas.

## 7. Ce que cet exercice devait faire comprendre

1. **L'axe se lit dans l'énoncé**, et ici il y était en toutes lettres :
   « pas un cinquième avant deux ans » d'un côté, « une nouvelle par
   trimestre » de l'autre.
2. **Le critère de la méthode décide seul** de ce qui va sur la variante.
   `Libelle` oui, les trois autres non, et la liste des imports le prouve.
3. **La clôture est gratuite, l'exhaustivité se paie** : 236 lignes de test,
   dont une centaine de `go/ast`.
4. **`nil` est la cinquième variante**, et elle ne se déclare nulle part.
5. **Les assertions de conformité sont mesurables** : 8, 4, 0 selon la
   configuration — et le 4 vient d'un littéral de slice que personne n'avait
   écrit pour ça.
6. **Un test qui indexe par position panique au lieu d'échouer.** C'est
   l'expérience qui me l'a appris, pas la relecture.
7. **Une modification qui ne compile pas n'a pas été jouée.** Rejoue-la.
